# P6 元素世界当前生产实现完整解析

> 文档状态：Current Production Only
>
> 适用版本：Unity 6.3，P7 Demo 当前 ElementWorld 生产链路
>
> 本文只描述当前源码中仍被 Runtime 使用的实现。开发过程、已替换方案和未落地设想不属于本文内容，也不能作为面试陈述依据。

## 1. 系统目标与玩家可见结果

ElementWorld 是连接“法术产生元素”和“元素持续影响世界与角色”的 Gameplay 系统。玩家释放水球、毒球或粘液球后，投射物命中会提交对应材料；Fire、Water、Poison、Sticky 可以留存在世界中、参与反应，并通过 Exposure 转换为角色身上的 Burning、Wet、Poisoned、Sticky 状态。Water、Poison、Sticky 具有 GPU 粒子流体表现，Fire 使用独立的世界 Cell 与 GPU Parcel 表现。

这个系统解决的不是单一 Shader 问题，而是完整的数据闭环：

```text
Projectile / Initial Deposit / Persistent Source
→ Material Write Request
→ Material Simulation Route
→ Element Cell 或 GPU PBF Backend
→ Material Reaction
→ Gameplay Occupancy Query
→ Character Status Exposure
→ Rendering Snapshot
→ 玩家看到并踩到同一种材料
```

当前实现是 Hybrid Simulation。统一的材料身份和查询接口之下，不同材料选择适合自己的模拟后端：

- Fire：稀疏 Chunk 中的离散 `ElementCell`。
- Water、Poison、Sticky：共享一个 `GpuPbfFluidRuntime`，通过不同 `MaterialId` 和参数行区分物性。

因此，ElementWorld 不是“一个大数组模拟所有东西”，也不是“Gameplay 只看 Shader 颜色”。Gameplay 数据、GPU Simulation 和 Presentation 各有清楚的所有权。

## 2. Assembly 边界与责任划分

### 2.1 Game.Materials

`Game.Materials` 定义稳定的材料身份与材料目录。`MaterialId` 是紧凑枚举值，当前核心材料为 Fire、Water、Poison、Sticky。`MaterialCatalog` 使用 `ScriptableObject` 保存 Authoring Data，并在初始化时生成只读 Snapshot。

这一层只回答“这是什么材料”，不运行模拟，也不直接控制角色状态。

### 2.2 Game.ElementField

`Game.ElementField` 拥有世界材料的 Runtime State：

- 世界坐标到 Global Cell、Chunk Key 和 Local Cell 的映射。
- 稀疏 Chunk 的创建、保留、休眠与回收。
- Fire Cell 的写入、传播、反应和衰减。
- GPU PBF 液体的 Spawn、Fixed Tick、Collision、Sleep/Wake 与 Gameplay Readback。
- Material Backend Route、统一查询和角色 Exposure。

`ElementWorldRuntime` 是 Scene 中的总协调器，但具体数学与数据结构被拆到 Pure Logic、Store、Simulator 和 GPU Runtime 中，避免一个 `MonoBehaviour` 同时承担所有规则。

### 2.3 Game.Combat

`Game.Combat` 定义角色状态和元素反应的纯规则，例如 Extinguish、Toxic Combustion、Ignite Goo、Wet Cleanse。它不知道 Sparse Chunk、GPU Buffer 或 Renderer。

这样角色状态反应和世界材料反应可以共享公式，但不会让 Combat 反向依赖 ElementField。

### 2.4 Game.Rendering

`Game.Rendering` 只读取 ElementField 提供的只读 World/GPU Snapshot：

- `GpuLiquidSurfaceRenderer` 把液体粒子重建成三维 Surface。
- `GpuFireParcelRenderer` 把 Fire Cell 转换为有生命周期的 GPU 火焰表现。

Rendering 不写回 Gameplay Amount，不决定状态强度，也不能覆盖 Simulation Truth。

## 3. 数据驱动入口

### 3.1 ElementWorldProfile

`ElementWorldProfile` 是世界层的主要 `ScriptableObject`，保存：

- Cell Size 与 Chunk Size。
- Resident Chunk 上限。
-玩家周围 Active Radius。
- Tick Rate 与 Catch-up 上限。
- Sleep Grace 与稳定休眠阈值。
- Material Catalog。
- Material Simulation Routing。
- Material Reaction Bindings。
- Material Status Projection。

Runtime 初始化时把这些可编辑数据复制为值类型 Snapshot。热路径读取 Snapshot，不在每个 Tick 反复访问 `ScriptableObject`。

### 3.2 Material Simulation Route

Material Route 是“材料身份到模拟后端”的只读映射：

```text
MaterialId
→ MaterialSimulationBackendKind.ElementCell
或 MaterialSimulationBackendKind.GpuPbfLiquid
```

生产配置中，Fire 由 Element Cell 保存，Water、Poison、Sticky 由 GPU PBF 保存。`MaterialStateQueryRouter` 使用同一份最终 Route 选择查询来源，避免同时读取两套数据并把 Amount 重复相加。

### 3.3 Status Projection

Material Status Projection 负责把世界材料映射到角色状态语义，例如 Water 对应 Wet、Poison 对应 Poisoned、Sticky 对应 Sticky。它是数据映射，不负责 Physics 查询或状态累积；真正采样由 Exposure System 执行。

## 4. 世界坐标与 Sparse Chunk

### 4.1 三层坐标

系统使用三种离散坐标：

1. Global Cell：整个世界中稳定、唯一的格子坐标。
2. Chunk Key：Global Cell 所属的 Chunk 坐标。
3. Local Cell：Cell 在 Chunk 内部的局部坐标。

世界位置先减去固定 World Origin，再除以 Cell Size 得到 Global Cell。之后通过 Floor Division 拆成 Chunk Key 与 Local Cell。负坐标必须使用数学意义上的向下取整，不能依赖 C# 对负整数的向零截断，否则世界原点两侧会映射不连续。

玩家的 Transform 只是 Interest Point，不是坐标原点。玩家移动只改变哪些 Chunk 需要工作，不改变已经存在材料的世界身份。

### 4.2 ElementWorldStore

`ElementWorldStore` 是由 `ElementChunkKey` 映射到 `ElementWorldChunk` 的稀疏容器。只有材料写入或跨边界模拟确实需要某个区域时才创建 Chunk，因此存储成本随实际有内容的区域增长，而不是随整张关卡包围盒增长。

每个 `ElementWorldChunk` 拥有：

- 固定尺寸的 Cell Grid。
- Solid Mask。
- Dirty/Version 信息。
- 最近相关 Tick。
- Stable Tick 计数与 Simulation Wake 状态。

### 4.3 Resident、Interest Active 与 RequiresSimulation

这三个概念必须分开：

- Resident：Chunk 数据仍然存在。
- Interest Active：Chunk 位于当前关注窗口或拥有临时相关租约。
- RequiresSimulation：当前 Tick 是否真的需要运行 Solver。

稳定的非空 Chunk 可以保持 Resident 和可查询，同时进入 Solver-Sleeping。新的写入、邻居传输或反应会调用 Wake，使它重新参与模拟。这个拆分保护了 Gameplay 持久性，同时避免稳定材料永远消耗 CPU。

## 5. World Write Runtime 链路

### 5.1 写入来源

当前写入来源包括：

- `ElementDepositOnImpact`：投射物命中后提交材料 Deposit。
- `ElementWorldInitialDeposit`：场景启动时提交预放置材料。
- `ElementWorldPersistentFireSource`：持续生成 Fire。
- Debug Injector：只用于开发验证，不属于玩家流程。

这些来源不直接取得 Chunk 或 GPU Buffer，而是提交 `ElementWriteRequest`。Request 是值类型快照，包含世界位置、材料、Amount、Radius、Falloff 等写入信息。

### 5.2 ElementWorldWriteRouter

写入路由读取最终 Material Route：

```text
ElementWriteRequest
→ ElementCell Backend：进入 ElementWriteQueue
→ GpuPbfLiquid Backend：转换为 Fluid Deposit/Spawn Request
```

写入与查询共享同一份路由 Snapshot。这条不变量保证同一种材料不会“写到 GPU、查询却去读 Cell”。

### 5.3 Queue 的意义

Queue 把 Unity 事件发生的时间与 Fixed Simulation Tick 解耦。Projectile 可以在任意 Frame 命中，但材料写入只会在受控 Tick 边界消费。Queue 使用固定容量；容量不足时明确拒绝，而不是在热路径扩容或丢失一半事务。

## 6. Fire 的 Element Cell 模拟

Fire 存储在 Sparse Chunk 的 `ElementCell` 中。`ElementWorldSimulator` 每个固定 Tick 对需要模拟的 Active Chunk Snapshot 运行确定性 Stage。

核心顺序是：

```text
Apply queued writes
→ Rebuild activity snapshot
→ Plan cross-backend liquid/fire reactions
→ Simulate active Element Cells
→ Rebuild activity state
```

Element Cell Stage 使用 Current/Delta/Next 的两阶段提交思想：一个 Stage 内统一读取旧状态，把变化累计到 Delta，再统一 Commit。这样处理顺序不会让后遍历的 Cell 提前看到前一个 Cell 的“未来状态”。

Fire 可以衰减，也能与液体 Occupancy Snapshot 进行跨后端反应。反应产生的 Fire Delta、Element Add 或 Area Damage Command 会通过固定容量 Command Queue 原子提交。

## 7. GPU PBF 液体在 ElementWorld 中的位置

Water、Poison、Sticky 共享一个 GPU 粒子池和一套 Solver。每个粒子的 Metadata 保存 Alive、MaterialId、Sleeping、RequiresSimulation 等紧凑状态；Material Parameter Buffer 按 MaterialId 索引不同的 Density、Viscosity、Cohesion 等参数。

共享 Runtime 的原因是：

- 不需要为每种液体复制 Particle Pool、Spatial Hash 和 Solver。
- 不同材料仍能通过 MaterialId 独立渲染和参与反应。
- 同一固定 Tick 中可以统一处理碰撞、Sleep/Wake 和粒子生命周期。

GPU PBF 的具体 Solver、Readback 与 Surface Reconstruction 见《2026-08-09 GPU PBF流体模拟完整解析.md》。

## 8. Gameplay Occupancy 与角色 Exposure

### 8.1 为什么不能直接让 Gameplay 读 Renderer

Renderer 的 Triangle、颜色和 Alpha 是 Presentation 数据，可能因为相机、材质或 Surface 参数变化而不同。Gameplay 需要稳定地回答“某个 Global Cell 中有多少某种材料”，因此不能从屏幕 Pixel 或最终 Mesh 反推。

### 8.2 AsyncGPUReadback Snapshot

`FluidGameplayOccupancyBridge` 在 `LateUpdate` 以受控频率申请 GPU Readback Lease。GPU 先把活跃粒子的世界位置、MaterialId 与 Amount Scale 打包到 Gameplay Buffer，再通过 `AsyncGPUReadback` 异步传回 CPU。

回读完成后构建 `LiquidGameplaySnapshot`：这是固定容量的稀疏 Occupancy 表，按 Global Cell 与 MaterialId 查询离散 Amount。旧 Snapshot 在新 Snapshot 完整发布前继续可读，避免消费者看到半写状态。

它是低频 Gameplay Projection，不是逐粒子 Simulation Truth。因此液体视觉移动和角色状态采样之间允许存在一个受控 Snapshot Interval 的延迟。

### 8.3 ElementWorldExposureSystem

Exposure System 使用 NonAlloc Physics Query 找到 `StatusController`，把角色 Bounds 覆盖的 Cell 交给统一 Material Query Router：

```text
Character Bounds
→ Global Cell Range
→ MaterialStateQueryRouter
→ Element Cell 或 Liquid Occupancy
→ Status Projection
→ StatusController.Apply
```

角色站在 Sticky 中时获得接触态 40% 减速；离开后根据残留 Sticky 强度逐渐恢复。Wet、Poisoned 与 Burning 同样由状态系统管理，而不是由 Renderer 直接修改移动或生命值。

## 9. 当前元素反应

反应由三层组成：

1. `MaterialReactionBindingProfile`：无序材料对映射到 Reaction Id。
2. `ElementReactionEvaluator`：Pure Logic 计算消费、生成、阈值和时间预算。
3. Runtime Adapter：把结果写回 Status、Element Cell 或 GPU Command Queue。

当前核心语义包括：

- Water + Fire：Extinguish。约 1 Water 移除 2 Fire；角色 Wet 同样更有效地消除 Burning。
- Fire + Poison：Toxic Combustion，在满足阈值和 Wind-up 后产生范围伤害。
- Fire + Sticky：Ignite Goo，消费 Sticky 并生成 Fire。
- Water + Sticky：Absorb Water，把一部分 Water 粒子原位转换为 Sticky。
- 角色 Wet Cleanse：有限预算优先清洗 Poisoned，再处理 Sticky。

世界反应与角色状态反应共享纯规则，但写回容器不同。世界 Water 转换为 Sticky 不改变“角色身上的 Wet 可以清洗 Sticky”这一状态规则。

## 10. Rendering 边界

### 10.1 液体

液体 Rendering 读取 `FluidGpuSnapshot`，按 MaterialId 分别重建 Water、Poison、Sticky。每个 Renderer 使用一套完整 Active Bounds 的 Density Grid，经过 Anisotropy、Stylized Crown、Marching Cubes 和 Procedural Indirect Draw 得到三维 Surface。

Rendering 不改变粒子位置、Gameplay Occupancy 或 Material Reaction。

### 10.2 Fire

Fire Rendering 从只读 World 数据采样 Fire Cell，上传 GPU Seed，并由 Fire Parcel Runtime 驱动 Surface/Gas 生命周期。它与液体 Surface 是两条独立表现链，不共享 Material Amount，也不让粒子表现反向覆盖 Fire Cell。

## 11. 性能设计

### 11.1 CPU

- Sparse Chunk：只为真实内容分配世界数据。
- Fixed Tick：Gameplay 模拟频率不等于渲染帧率。
- Catch-up Cap：避免长帧后一次补跑无限 Tick。
- Solver-Sleeping：稳定数据保留但不重复求解。
- 预分配数组和固定容量 Queue：热路径不扩容。
- `OverlapSphereNonAlloc` 等 NonAlloc API：避免 Physics 查询分配。
- 无 LINQ、Closure、Boxing 和逐帧临时集合。

### 11.2 GPU

- 固定容量 Particle Buffer。
- Spatial Hash 限制邻居搜索范围。
- Indirect Dispatch 跳过没有 Solver 工作的 Tick。
- Material Parameter Row 让多种液体共享 Solver。
- Gameplay 使用低频 AsyncGPUReadback，不同步阻塞 Render Thread。
- Surface Buffer 长期复用，不在 `LateUpdate` 重新创建。

不能笼统宣称“整个项目 0 GC”或“任何设备性能都稳定”。准确表述应是：当前设计避免在指定 ElementWorld 热路径中产生托管分配，并通过 Profiler Marker、固定容量和 Sleep/Wake 控制工作量；具体性能结论只对实际捕获的 Profiler 场景成立。

## 12. Debug 方法

调试顺序必须从 Gameplay Truth 向 Presentation 外扩：

```text
Material Write 是否被 Queue 接受
→ Final Route 是否指向正确 Backend
→ Element Cell / GPU Particle 是否真实存在
→ Gameplay Snapshot 是否发布
→ Reaction / Exposure 是否读到 Amount
→ Surface/Fire Renderer 是否取得 Snapshot
→ Compute 是否生成 Triangle/Parcel
→ Shader、Bounds、Depth 与 Culling 是否可见
```

典型分层判断：

- 角色能获得状态但画面不可见：Gameplay Projection 存在，优先检查 Rendering。
- 粒子和 Surface 都不可见，World 初始化失败：先检查最早的配置错误，不处理后续级联日志。
- 连续施法越来越卡：先用 Profiler 区分 CPU Solver、GPU Solver、Surface Reconstruction 与 Fixed Tick Catch-up。
- Surface Triangle Count 为 0：检查 Density、Voxel Size、Iso Level、MaterialId 和 Bounds，不先改最终颜色。
- Triangle/Indirect Args 有效但不可见：检查 Shader Import、World Bounds、Depth、Cull 和 Fragment 输出。

## 15. 面试表达边界

推荐说法：

> 我实现的是一套数据驱动的混合元素世界。统一 MaterialId、Route、Reaction 和 Query Contract 之下，Fire 使用 Sparse Chunk Cell，Water、Poison、Sticky 共享 GPU PBF Solver。GPU 液体通过低频 AsyncGPUReadback 投影成 Gameplay Occupancy，角色 Exposure 和材料反应读取这份紧凑数据；Rendering 只读 GPU Snapshot 重建三维表面，不反向修改 Gameplay。性能上我把“数据是否存在”和“本 Tick 是否需要求解”分开，并使用固定容量 Queue、Buffer 复用、Spatial Hash、Indirect Dispatch 与 Solver-Sleeping 控制成本。

不应声称：

- 这是严格物理正确的真实流体。
- 所有元素都使用同一种 Solver。
- Renderer Mesh 是 Gameplay 判定来源。
- EditMode Tests 等于真实 GPU 或 Scene 已验证。
- 整个项目在所有路径上都是 0 GC。

## 16. 本文结论

ElementWorld 的核心不是某个视觉算法，而是一个稳定的数据边界：材料先获得统一身份，再被路由到合适的 Simulation Backend；Gameplay 通过统一查询和 Pure Reaction 读取结果；Rendering 只做表现。Sparse Chunk、GPU PBF、Async Readback 和三维 Surface 都服务于这条边界，而不是彼此独立的技术展示。
