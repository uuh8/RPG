## P6-B Task 1：固定世界坐标与稀疏 Chunk 数据地基

这一 Task 的目的不是马上让大地图出现水面，而是先解决连续世界最容易埋下根本性错误的两个问题：第一，同一个世界位置必须永远映射到同一个 Cell，即使玩家跨过原点、走到负坐标或离开后再返回也不能改变；第二，40～60 米关卡中绝大多数空间通常没有 Water/Fire，不能像 P6-A 实验场一样为整个包围盒一次性分配并逐 Tick 扫描所有 Cell。因此我们建立了“固定 Global Cell 坐标 + 稀疏 Chunk Dictionary”的数据层。玩家位置尚未接入，也没有替换现有 `ElementFieldRuntime`；新增代码只提供纯坐标换算和按需存储。一个 Chunk 仍然复用已经验证过的 `ElementGrid`，所以 Current/Next Double Buffer、Solid Mask、Amount Delta 和 Dirty Version 这些 P6-A 基础没有被复制成另一套规则。法术或关卡烘焙以后第一次触及某个 Chunk 时才创建它，单纯查询从未使用过的远方空间只得到 Empty，不产生内存副作用。这种先稳定数据身份、再做 Active/Sleep 调度的开发顺序，可以避免“玩家移动后旧水面漂移”“负坐标落错 Chunk”“为了 Streaming 重写整个 Simulator”等高代价返工。

### 1. 从世界位置反推到唯一 Cell：坐标层级与 Floor Division

连续关卡使用四层概念：`World Position` 是 Unity 中以米为单位的 `Vector3`；`Global Cell` 是从固定 Origin 开始、覆盖整个关卡的整数格坐标；`Chunk Key` 表示 Global Cell 属于哪个数据块；`Local Cell` 表示它在该 Chunk 内部的位置。玩家不是 Origin，`ElementWorldLabRoot` 也不会跟着玩家移动。核心公式是：

```text
globalCell = floor((worldPosition - worldOrigin) / cellSize)
chunk      = floor(globalCell / chunkSize)
local      = globalCell - chunk × chunkSize
```

当前 `cellSize = 0.25m`、`chunkSize = 8`，所以一个 Chunk 的边长是 `8 × 0.25m = 2m`。例如世界 X 为 `-0.01m` 时，除以 0.25 得到 `-0.04`，向下取整后 Global Cell X 必须是 `-1`，不能是 `0`。Global Cell `-1` 再分块时属于 Chunk `-1`，Local X 为 `7`；这与 Chunk `0` 的 Local `0` 在原点两侧连续相邻。

这里必须区分数学 `Floor Division` 与 C# 整数除法。C# 的 `-1 / 8` 向零截断得到 `0`，而空间分块需要向负无穷取整得到 `-1`。实现先计算普通商和余数，如果余数为负就把 Chunk 再减一，最后通过 `local = global - chunk × size` 得到 `[0, 7]` 范围内的正 Local 坐标。这个不变量很重要：后续 `ElementGrid` 的一维数组索引只接受非负局部坐标，负数只存在于 Chunk Key，不会直接进入数组下标。

`ElementWorldCoordinates` 是 `static` 纯数学类，不读取 Transform、不查玩家、不分配集合。`WorldToGlobalCell` 使用 `Mathf.FloorToInt`，并拒绝 0、负数、NaN 与 Infinity CellSize；`GlobalCellToChunkAndLocal` 对三个轴执行相同拆分；`ComposeGlobalCell` 用于测试反向组合，并在乘加时使用 `checked` 暴露整数溢出。纯函数的好处是可以用 NUnit 把边界值直接锁死，不必进入 Play Mode 才发现地图负半轴失效。

### 2. Chunk Key、Hash 与稀疏存储为什么适合连续小关卡

`ElementChunkKey` 是包含 X/Y/Z 三个 `int` 的 `readonly struct`，实现 `IEquatable<ElementChunkKey>`。它不是空间本身，也不是 GameObject，而是一张数据页的稳定身份证。`Dictionary` 查询时先使用 `GetHashCode` 找 Bucket，再用 `Equals` 确认三个坐标完全相同。实现用不同质数混合三个轴；Hash 允许冲突，因此正确性最终由 `Equals` 保证，Hash 的职责只是尽量把规则坐标均匀分散。泛型 Dictionary 会优先调用 `IEquatable<T>`，避免把 struct 装箱成 `object`，这也符合热路径避免 Boxing 的原则。

如果把一条 60m 长、假设 12m 宽和 4m 高的关卡全部做成 0.25m 连续网格，仅 Cell 数就是 `240 × 48 × 16 = 184,320`，而且 Current/Next、Solid、Delta、Dirty 等 Buffer 会把真实内存继续放大；更重要的是固定 Tick 若全量扫描，会把从未出现元素的空气也反复处理。稀疏方案用 `Dictionary<ElementChunkKey, ElementWorldChunk>` 只保存 Resident Chunk。读取未知 Key 时返回默认 `ElementCell`，且 Resident Count 不变；只有明确的创建请求才一次性分配该 Chunk。`MaximumResidentChunks` 是故障保护：如果坐标或法术写入出现失控，不允许系统静默持续吃内存。

`TryRemoveEmptyChunk` 只允许移除 `HasAnyElement == false` 的 Chunk。含有水或火但暂时离玩家很远的数据未来会进入 Sleep，而不能被当成空白删除，否则玩家返回时环境历史会凭空消失。当前 Task 用 `_nonEmptyCellCount` 维护是否存在元素：Cell 从 Empty 变为非空时加一，从非空变为空时减一，因此判断不需要每次扫描 512 个 Cell。真正的 Sleep Grace、Last Touched Tick 和 Active Set 属于调度职责，将在 Task 2 加入，而不是塞进最底层 Store。

### 3. 复用 `ElementGrid` 的 Buffer，以及为什么 Chunk 不是 GameObject

`ElementWorldChunk` 内部组合一个尺寸为 `8 × 8 × 8` 的 `ElementGrid`。每个 Chunk 有 `512` 个 Cell，并一次性持有 Current Cells、Next Cells、Solid Mask、Amount Delta、Cell Dirty 与 Version Buffer。Current/Next 是 `Double Buffer`：Simulation Stage 稳定读取 Current，把结果写入 Next，Stage 结束后交换引用，避免边遍历边修改导致顺序依赖。Solid Mask 将“这里有墙”与“这里有什么元素”分开；Amount Delta 为后续跨 Cell、跨 Chunk 守恒转移准备工作内存；Dirty Version 让 Rendering 只重建发生变化的数据块。

这些数组都只在创建 Chunk 时分配，之后 Tick 复用。内部 Buffer 属性保持 `internal`，只有 `Game.ElementField` 和通过 `InternalsVisibleTo` 授权的测试程序集能访问，`Game.Rendering` 等上层模块未来仍应通过只读接口消费结果，不能直接改数组。

一个 Chunk 不能等同于一个 GameObject。GameObject 会携带 Transform、Component、Unity Native Object 生命周期和场景层级管理成本，而 Gameplay Chunk 本质上只是紧凑数据。若一份数据一创建就生成对象，Streaming 很快会再次退化为大量 Scene Object。当前 Chunk 完全是普通 C# 对象；未来 Water Renderer 最多为“真正可见且 Active 的水 Chunk”建立一个可复用 Mesh 表现对象，Fire 继续共享少量 ParticleSystem。数据的 Resident/Sleep 生命周期与表现对象的 Active/Culling 生命周期因此可以独立控制。

### 5. TDD、Debug 过程、设计取舍与面试表达

本 Task 严格走了 RED→GREEN。先创建坐标和 Store 测试，清理旧编译产物后得到 27 个 `CS0103/CS0246`，错误全部指向预期缺失的四个类型，证明测试确实先于实现失败。第一次普通 `dotnet build` 曾错误地显示成功，原因不是功能已经存在，而是 Unity 自动生成的工程文件/旧增量产物尚未形成可信的全量编译证据；执行 Clean 后才获得真实 RED。生产脚本写入后，Unity 尚未生成 `.meta` 和刷新 `.csproj`，因此测试仍报告缺失类型；通过 Unity `Assets Refresh` 导入后，四份 `.meta` 与 Compile Item 出现，`Game.ElementField` 和 Tests 均达到 0 warning / 0 error。最终用户在 Unity Test Runner 中确认全部通过。

这里选择“每个 Chunk 组合一个 `ElementGrid`”，而不是立即重写一个高度优化的 SoA World Buffer。优点是最大限度复用 P6-A 已测试的 Buffer 和 Dirty 机制，降低 Demo 阶段架构迁移风险；缺点是每个 Chunk 都有独立数组对象和 Dictionary 间接访问，极大规模世界可能需要 Chunk Pool、SoA Page 或 NativeArray。当前连续小关卡最多数百 Resident Chunk，这个取舍优先保证正确性、可解释性和快速形成可玩 Demo。Task 2 再增加 Active/Sleep 调度，Task 3 才处理跨 Chunk 守恒；分阶段的原因是坐标错误、生命周期错误和模拟错误应当能被分别定位。

## P6-B Task 2：Interest Point、Active/Sleep 生命周期与远程活跃租约

这一 Task 的目标，是在 Task 1 已经能够“在任意固定世界坐标找到唯一 Chunk”的基础上，进一步回答“哪些 Chunk 现在值得花 CPU 推进模拟”。连续关卡不能让所有 Resident Chunk 永久以 10Hz 流动、反应和衰减，否则玩家走过的区域越多，每 Tick 成本越高；但也不能只模拟玩家脚下极小范围，否则远处射出的水球、火球和连锁反应会像被按下暂停键。最终方案把玩家 Transform 定义为 `Interest Point`，它只决定调度中心而不改变世界 Origin；玩家附近约 `40m × 40m` 的已存在 Chunk 进入 Active，远处仍含元素的 Chunk进入 Sleep 并保存历史，远处刚被法术写入或反应触及的 Chunk 则获得临时 `Active Grace Lease`。空 Chunk 在离开活跃范围且租约到期后才变为 Reclaimable。`ElementWorldRuntime` 使用固定 Tick 和预分配数组管理这些状态，不在 `Update()` 中使用 LINQ、临时 List 或遍历时修改 Dictionary。用户已在 SampleScene 创建固定的 `ElementWorldLabRoot`，把 WizardPlayer 作为 Interest Point，并验证移动时 Global Cell 和 Chunk Key 正确变化；场景尚未产生 World Cell 是正常边界，因为真正的按需写入和跨 Chunk 模拟属于 Task 3。

### 1. 玩家为什么是 Interest Point，而不是移动的世界原点

`Interest Point` 可以理解为 Streaming 和 Simulation 的“关注中心”。它回答的是“玩家现在附近哪些数据需要高频工作”，而不是“世界坐标从哪里开始”。`ElementWorldRuntime` 在初始化时固定保存自身 Transform Position 为 World Origin，之后用 Task 1 的公式计算玩家位置：

```text
interestGlobalCell = floor((playerWorldPosition - fixedWorldOrigin) / cellSize)
interestChunk      = floorDiv(interestGlobalCell, chunkSize)
```

当前 `cellSize=0.25m`、`chunkSize=8`，所以一个 Chunk 边长为 `2m`。玩家跨过约 2m 边界时 `Interest Chunk Key` 改变；玩家只在同一 Chunk 内移动时，Runtime 不需要反复重建 Activity Set。这个“只在 Chunk Key 改变时重算”的策略，本质上是 Spatial Quantization：把连续 Transform 位移压缩成低频整数区域事件，减少无意义调度。

如果让 `ElementWorldLabRoot` 跟随玩家，同一地面位置的 Global Cell 会随着 Origin 改变，旧水面、火焰和 Sleep 数据就无法稳定对应真实世界。现在 Root 始终保持 Position `(0,0,0)`、Rotation `(0,0,0)`、Scale `(1,1,1)`；WizardPlayer 只作为 Inspector 显式引用，不使用每帧 `FindObjectOfType`。这既消除了场景查找成本，也让依赖关系可见、可调试。

### 2. Resident、Active、Sleeping 与 Reclaimable 分别代表什么

`Resident` 与 `Active` 不是同一个维度。Resident 表示 Chunk 数据页已经存在于 `ElementWorldStore`；Active 表示本 Tick 会参与 Reaction、Flow、Decay。一个 Chunk 可以 Resident 但 Sleeping：它保留 Water/Fire 数据，却暂时不消耗模拟 CPU。`Reclaimable` 只用于“已经为空、离开玩家范围且 Grace 到期”的 Chunk，Runtime 可以把它从 Store 移除并释放整页 Buffer。

玩家窗口使用轴对齐 Chunk 距离，而不是球形欧氏距离：

```text
inside = abs(chunk.x - interest.x) <= radiusXZ
      && abs(chunk.z - interest.z) <= radiusXZ
      && abs(chunk.y - interest.y) <= radiusY
```

当前 `radiusXZ=10`、`radiusY=3`。每个 Chunk 是 2m，因此水平半径为 20m、完整宽度约 40m，垂直半径为 6m。采用 Chunk AABB 的原因是判定只需要整数减法、绝对值和比较，不需要开方；它也与后续 Chunk Mesh、Dictionary Key 和边界邻居天然对齐。代价是窗口角落比真正的 20m 圆多覆盖一些 Chunk，但稀疏 Store 只检查已经 Resident 的 Chunk，不会因为窗口扩大就创建空白世界。

状态规则可以概括为：

```text
在玩家窗口内                         → Active
不在窗口内，但 current-lastRelevant < graceTicks → Active（Grace Lease）
租约到期且仍含元素                   → Sleeping
租约到期且完全为空                   → Reclaimable
```

这是一种 Hysteresis：进入 Active 可以立即发生，离开 Active 却要等待 Grace Period，从而防止玩家站在边界附近时 Chunk 在 Active/Sleep 之间每帧抖动。边界使用 `< graceTicks`，意味着恰好达到 Grace Tick 时租约结束；测试专门锁定了 119、120、121 Tick，防止 `<=` 带来多一 Tick 的 Off-by-One。

### 3. 为什么还需要远程 Active Grace Lease

仅把玩家半径从 12m 扩大到 20m，只能改善大部分镜头范围内的连续性，但仍无法保证高速 Projectile 或 Trigger Payload 在更远处命中后立即模拟。因此 `LastRelevantTick` 不只由玩家窗口使用：Task 3 之后，写入、跨 Chunk 流动或反应触及某个 Chunk 时也会调用 `MarkRelevant(worldTick)`，给它续一个临时租约。这样玩家在 A 点发射远程火球命中 B 点，即使 B 超出常驻窗口，B 也会暂时 Active，完成 Deposit、Reaction 和扩散，然后才根据是否仍含元素转入 Sleep。

实现中有一个很容易出现的自续租 Bug：如果 Runtime 看到“Chunk 当前是 Active”就无条件把 `LastRelevantTick` 更新为当前 Tick，那么由 Grace Lease 保持 Active 的 Chunk 会每 Tick 给自己续租，永远无法 Sleep。现在只有“确实位于玩家窗口内”的 Chunk 在 Activity Rebuild 时刷新时间；远程 Chunk 必须由真实写入或相互作用显式 `MarkRelevant`。这体现了状态与原因的区别：Active 是结果，玩家接近、法术写入、边界反应才是续租原因。

## P6-B Task 3：按需写入与跨 Chunk Water/Fire 确定性模拟

这一 Task 的目的，是让 Task 1 的稀疏存储和 Task 2 的 Active/Sleep 调度第一次真正承载 Water/Fire Gameplay。玩家最终看到的是：水球即使命中 `2m Chunk` 的边界，水量也只按一次法术的总量沉积；水可以从某个 Chunk 的 Local X=7 连续流到相邻 Chunk 的 Local X=0，也可以从 Local Y=0 落入下方 Chunk；边界两侧的 Water/Fire 可以执行同一套 Extinguish 公式；远处 Sleeping Chunk 保存数据但不会偷偷流动、衰减。为实现这些结果，本 Task 没有把每个 Chunk 当成互不相干的小实验盒，而是把 Chunk 仅视为连续 Global Cell 世界的内存分页。写入采用稳定的两遍归一化扫描，模拟则先固定本 Tick 会参与计算的 Chunk Snapshot，再按 `Reaction → Down Flow → Horizontal Flow → Fire Decay` 分 Stage 推进；每个 Stage 统一读取旧 Current、把增减累计到 Delta/Next，最后所有 Chunk 一起 Commit。这样跨边界转移仍满足来源减少量等于目标增加量，后处理的 Chunk也不会提前读到前一个 Chunk 的“未来值”。Task 3 交付的是纯 World Write/Simulation Core，尚未把真实 Projectile、角色 Exposure、Water Mesh 或 Fire Particle 切换到新 Runtime；这些 Adapter 分别留在后续 Task，避免规则正确性和 Unity 场景集成混成一个无法定位的大问题。

### 1. 从最终效果倒推：Chunk 为什么不能成为元素世界的墙

`ElementWorldChunk` 可以理解为一页固定大小的数据，而不是 Minecraft 中玩家直接看到的方块，也不是一个 GameObject。当前一个 Chunk 为 `8 × 8 × 8 Cell`，CellSize 为 `0.25m`，所以分页边长为 `2m`。Global Cell `(8, 3, 4)` 会被拆成 Chunk `(1, 0, 0)` 的 Local Cell `(0, 3, 4)`；它与 Global Cell `(7, 3, 4)` 在数学上只相差一个 Cell，虽然数据存放在两个不同的 `ElementGrid` 数组中。邻居换算可以概括为：

```text
neighborGlobal = sourceGlobal + direction
neighborChunk  = floorDiv(neighborGlobal, chunkSize)
neighborLocal  = neighborGlobal - neighborChunk × chunkSize
```

生产代码为了避免每次都重新组合 Global Cell，使用等价的 `WrapAxis`：Local 坐标小于 0 时加上 `chunkSize` 并把 Chunk Key 减 1；Local 坐标大于等于 `chunkSize` 时减去 `chunkSize` 并把 Chunk Key 加 1。随后在已经排序的 Simulation Chunk Snapshot 中用 `Binary Search` 查找目标，查询复杂度由线性扫描的 `O(n)` 降为 `O(log n)`。因此边界只是数组分页边界，不是 Gameplay 边界。

连续世界还必须明确 Sleeping 的时间语义。Sleeping Chunk 的数据仍在 Store 中，查询时能读到历史；但它不进入本 Tick 的初始 Active Snapshot，所以不会自行 Flow、Reaction 或 Fire Decay。只有玩家窗口、真实 Deposit 或从 Active Chunk 跨边界传播等原因将它唤醒并 `MarkRelevant(worldTick)` 后，它才重新参与固定 Tick。这是“保存状态”和“消耗 CPU 推进状态”的分离。

### 2. 两遍归一化 Deposit：一次法术只能拥有一份 TotalAmount

球形 Deposit 最容易犯的错误，是先按 Chunk 切开球体，再对每个 Chunk 分别分配一次 `TotalAmount`。例如一个 `220 Amount` 的水球横跨两个 Chunk，如果每页各算一次，就会凭空变成最多 `440`，违反守恒。`ElementWorldWriteProcessor.TryApply` 因此在 Global Cell 范围内执行两遍稳定扫描，遍历顺序固定为 `Z → Y → X`。

第一遍只做统计，不写 Amount。对每个 Cell Center 计算其到命中点的距离，并根据配置得到权重：

```text
无衰减：weight = 1
线性衰减：weight = clamp01(1 - distance / radius)
可应用总量：targetAmount = min(TotalAmount, Σ capacity)
```

`capacity` 不只是空 Cell 的 `255`。相同材料只能补到 255；Water 写入 Fire 或 Fire 写入 Water 时，会先 1:1 抵消旧 Amount，再允许剩余新材料占据 Cell，所以命令最多可消费 `oldAmount + 255`。Solid、球体外部、已满或不兼容 Cell 不计入权重和容量。

第二遍才按“剩余 Amount / 剩余 Weight”逐 Cell 分配：

```text
share = round(remainingAmount × weight / remainingWeight)
share = clamp(share, 0, min(remainingAmount, capacity))
```

每处理一个 Cell，就从 `remainingAmount` 和 `remainingWeight` 中扣除对应值；最后一个有效 Cell接收可容纳的剩余量。相比“先为每格算百分比再独立取整”，这种做法不会因为许多小数分别舍入而稳定丢失大量 Amount；稳定的 Global Cell 顺序又保证余数每次落在同一组 Cell 上。写入实际改变 Chunk 时调用 `MarkRelevant(worldTick)`，使远程命中获得 Grace Lease。这里按需创建的是球体真正覆盖且可写的 Chunk，不会因为玩家 Active Radius 很大就创建整片空世界。

### 3. Boundary Halo、Snapshot/Delta 与 Stage Barrier

跨 Chunk Flow 在开始计算前可能需要一个尚不存在的接收页，例如边界 Water 要向下落入空 Chunk。若在 `Dictionary` Enumerator 正遍历 Store 时直接创建该页，C# 会使 Enumerator 失效；即使没有立刻抛异常，本 Tick 的计算集合也会随着遍历过程改变，结果难以推理。`ElementBoundaryNeighborPlanner` 因此分两阶段工作：先扫描初始 Active Chunk 的边界非空 Cell，把可能参与接收或反应的邻居 Key 去重写入预分配数组；扫描结束后再统一 `TryGetOrCreateChunk`。新邻居被标记为 Active 并续租，但 Planner 不递归扫描新建空页，因此不会沿着边界无限生成空 Chunk。这个预准备出来的一圈邻居就是离散模拟中的 `Halo` 或 Ghost Neighborhood：它让边界 Cell 在本 Tick 拥有完整邻域。

随后 `ElementWorldSimulator` 把 Active 与必要邻居复制到构造时预分配的数组，去重并按 `Z → Y → X` 做无分配 `Insertion Sort`。固定顺序非常重要，因为 `Dictionary` 枚举顺序不是 Gameplay 契约；浮点取整、有限容量和相邻竞争都可能让不同遍历顺序产生不同结果。

每个 Stage 都遵循同一模式：

```text
PrepareStage:
    Next = Current
    Delta = 0

SolveStage:
    只读所有 Chunk 的 Current
    来源 Delta -= transfer
    目标 Delta += transfer

ApplyDelta:
    Next = clamp(Current + Delta)

Stage Barrier:
    所有 Chunk 一起交换 Current / Next
```

核心守恒式为 `Σ sourceDelta + Σ targetDelta = 0`。例如水跨边界转移 20，来源记录 `-20`，目标记录 `+20`；它不会因为换了数组页就复制或消失。统一 Commit 就是 `Stage Barrier`：如果处理完一个 Chunk 便立刻交换，后面的 Chunk 会读到已更新值，水可能在同一 Stage 连续穿过多页，最终结果依赖 Chunk 顺序。现在所有 Chunk 在屏障前看到的是同一个旧时间切片。

规则顺序继续复用 P6-A。Reaction 只检查 `+X/+Y/+Z` 三个正方向，避免同一对 Cell 被双重计算，并调用 `ElementReactionEvaluator.CalculateExtinguishConsumption` 复用 P2/P6-A 的阈值与速率公式；Down Flow 优先使用 `MaxDownFlowPerTick`；Horizontal Flow 使用已验证的稳定差值公式并按 Tick 奇偶翻转方向，降低长期方向偏置；Fire 最后按固定 Amount/Tick 衰减。每一 Stage 完成后才进入下一 Stage，所以 Reaction 的结果可以影响本 Tick 后续 Flow，但同一个 Flow Stage 内不会读到刚流入的未来水量。

## P6-B Task 4：把真实法术与角色接入稀疏世界，并让稳定 Chunk 停止浪费 CPU

P6-B Task 4 的目的，是把前三个 Task 中已经通过纯测试验证的稀疏 World Core 接入真正可玩的 Unity 运行链。完成后，同一个 Water Projectile/Fireball Prefab 不需要知道当前场景使用固定实验 Field 还是连续稀疏 World：Projectile 命中只生成 `ElementWriteRequest`，唯一 Active Runtime 在固定 Simulation Tick 中消费它；新 Chunk 创建时立即把 Ground Collider `Rasterize` 到紧凑 `SolidMask`，所以 Water 会落在地面并横向摊开；角色或敌人的 Collider 进入 Water/Fire Cell 后，集中式 Exposure 再按 Amount 比例施加 Wet/Burning，并刷新持续来源的 Natural Decay Hold。这个 Task 的 Play Mode Gate 还揭示了一个比功能正确性更深的问题：水球次数越多，Gameplay 仍正确，但 `ElementWorld.Simulate` 会逐渐把主线程拖到数百毫秒。我们没有凭感觉更换 GPU 或缩小玩法范围，而是用 `ProfilerMarker` 把 Runtime 拆开，证明真正瓶颈是稳定水面仍被 Fixed Tick Solver 反复扫描。最终增加独立的 Solver Sleep/Wake 生命周期、同 Chunk Neighbor Fast Path 和无效工作剪枝，让稳定数据继续可见、可读取，却不再每 Tick 消耗 Simulation CPU。用户最终确认连续释放水球不再卡顿；Task 5 才会把这些已经真实存在的 World Cell 转换成 Water Mesh 与 Fire Particle，因此本 Task 结束时“Wet 正常但地面看不见水”是 Presentation 尚未接入，而不是 Deposit 失败。

### 1. 从玩家看到的结果倒推完整运行链

法术命中到状态反馈的主链如下：

```text
ProjectileBase.Impacted(point)
→ ElementDepositOnImpact 生成不可变 ElementWriteRequest
→ ElementRuntimeRegistry 把 Request 交给场景唯一 IElementWriteSink
→ ElementWorldRuntime 的预分配 Queue
→ Fixed Tick: ApplyWrites → Reaction → Flow → Decay
→ ElementWorldExposureSystem 用 NonAlloc Physics Broadphase 找角色
→ Collider.bounds 转为 Global Cell 范围并读取最大 Water/Fire Amount
→ StatusController.ApplySustainedStatus(Wet/Burning)
```

这里最重要的设计是 `Dependency Inversion`：Projectile 依赖的是“能够接收元素写入”这一抽象能力，而不是 `ElementFieldRuntime` 或 `ElementWorldRuntime` 的具体类型。`ElementRuntimeRegistry` 只保存一个 `IElementWriteSink` 引用；Runtime 在 `OnEnable` 注册、`OnDisable` 释放，第二个 Runtime 同时启用会被明确拒绝。这样可以避免一发水球随机写进两套世界，也不需要 Projectile 使用 `FindObjectOfType` 扫描 Scene。固定实验场仍可单独回归，连续关卡则切换到 World Runtime，法术 Prefab 不需要复制两份。

World Exposure 仍采用“一个系统集中查询角色”，而不是“每个 Cell 一个 Trigger”。每 `0.25s` 使用 `Physics.OverlapBoxNonAlloc` 对玩家 Interest Region 做 Broadphase；对命中的 Collider 按 `StatusController InstanceID` 去重，再把 AABB 的 `min/max` 映射成 Global Cell 范围。某个状态的施加量使用：

```text
normalizedAmount = cellAmount / 255.0
statusApply       = maxApplyPerExposure × normalizedAmount
```

取角色覆盖范围内的最大 Amount，而不是把所有 Cell 简单求和，可以避免体型较大或拥有多个 Collider 的角色仅因采样格数更多就获得不成比例的状态。`ApplySustainedStatus` 会刷新 Hold，但不会关闭 Reaction 或 Burning DoT；它只在连续环境来源存在时抑制普通 Natural Decay，离开后恢复既有下降规则。

### 2. Solid Bake、Fixed Tick 与三个不同的 Chunk 生命周期

新 World Chunk 首次按需创建时，`ElementFieldSolidBaker.BakeWorldChunk` 遍历该 Chunk 的 Local Cell Center，并用 `Physics.CheckBox` 查询 Ground Layer，把结果写入 `bool SolidMask[]`。这个 Physics 成本只在 Chunk 首次分配时支付；之后 Water Flow 只读连续数组，不能在每个 Cell、每个 Tick 中再次查询 Physics。Global/Local 映射为：

```text
globalCell = chunkKey × chunkSize + localCell
worldCenter = worldOrigin + (globalCell + 0.5) × cellSize
```

性能修复后需要严格区分三个概念。`Resident` 表示 Chunk 数据仍在 `ElementWorldStore`；`Interest Active` 表示 Chunk 位于玩家模拟窗口或具有 Grace Lease；`RequiresSimulation` 表示其中的 Cell 本 Tick 是否还可能继续变化。稳定水面可以同时满足“Resident、位于 Interest Region、但 Solver-Sleeping”。它仍能被 Exposure 与后续 Renderer 读取，玩家也仍会获得 Wet，只是不再重复执行 Reaction/Flow/Decay。新 Deposit、跨 Chunk 邻居转移或其他真实 Gameplay 事件会调用 `WakeForSimulation`，重新进入 Solver。为了避免一帧刚好无变化就错误休眠，Profile 使用 `SettleAfterUnchangedTicks = 2` 的 Hysteresis：连续两个 Simulation Tick 的 Changed Cells 都为 0 才进入稳定态。

### 3. 这次性能 Debug：怎样从“水球越多越卡”定位到 Solver

第一步是分离症状。角色能够进入 Wet，证明 Projectile→Queue→Cell→Exposure 的 Gameplay 链已经成立；地面看不见水，是 Task 5 Renderer 尚未接入，不能据此判断 Cell 不存在。真正的性能症状是水球次数增加后 Frame Time 持续恶化，因此我们先观察 Resident/Active/Sleep Count，再在 Runtime 加入：`ElementWorld.ApplyWrites`、`ElementWorld.Simulate`、`ElementWorld.RebuildActivity`、`ElementWorld.BakeChunkSolid` 四个顶层 `ProfilerMarker`。

第一次截图显示 Resident 与 Active 曾同时达到约 110，说明大量空 Chunk也被当成需要模拟的页。初步修复让空 Resident Chunk休眠，并在跨边界准备阶段先计算水平转移量：

```text
difference = sourceAmount - targetAmount
transfer   = min(maxLateralFlow, floor(difference / 8))
```

当 `transfer == 0` 时不创建邻居 Chunk，否则一个低水量边界 Cell 也会不断扩张 Resident Set。修复后 Inspector 已能看到 Active 减少、Sleeping 增加，但游戏仍会在大量水下卡顿，证明第一层原因不是全部答案。

第二次 Profiler 给出了决定性证据：某帧 CPU 约 `296.79ms`，其中 `ElementWorld.Simulate` 约 `262.95ms`，并且由于 Fixed Tick 欠债，同一 Rendering Frame 执行了 3 个 catch-up ticks；当时 `Resident=188`、`Active=69`、`Sleeping=119`、Active Element Cells 约 1631。复杂度可近似理解为：

```text
cost ≈ catchUpTicks × activeCells × simulationStages × neighborQueries
```

1631 个 Cell 本身并不巨大，但稳定水面仍在 10Hz 重复走 Reaction、Down Flow、四方向 Horizontal Flow、Fire Decay；一帧又补算三次，成本被放大。于是进一步加入 `ElementWorld.Simulate.PrepareNeighbors/Reaction/DownFlow/HorizontalFlow/FireDecay/Commit` 子 Marker，并做三类优化：稳定 Chunk经过两个无变化 Tick 后 Solver-Sleep；Reaction 直接跳过 Empty Cell；`TryResolveNeighbor` 对绝大多数仍位于同 Chunk 的邻居走数组 Fast Path，只有越过 Local 0/7 边界时才查询 Chunk Key。最终用户用相同的连续水球操作确认游戏不再逐渐卡顿。

这次 Debug 的核心经验不是“以后直接把 TickRate 调低”，而是先用 Marker 找到真正的 Hot Path，再消除语义上没有必要的工作。降低 TickRate 会同时改变水流、反应和衰减手感；Solver Sleep 则保留运动阶段的 10Hz 规则，只让已经稳定的区域停止计算。代价是需要正确设计 Wake 条件，并用测试保证 Sleeping 数据仍可被 Gameplay/Rendering 读取，否则优化会变成“把水删掉”。

面试时我会这样讲：我先通过 `IElementWriteSink` 和唯一 Registry 把 Projectile 与具体环境 Runtime 解耦，固定实验场和稀疏世界因此能复用同一法术；World Runtime 在 Fixed Tick 消费 Request，新 Chunk创建时把 Collider Rasterize 为 SolidMask，World Exposure 再用 NonAlloc Broadphase 和 Bounds→Global Cell 采样把 Water/Fire 反馈为 Wet/Burning。集成后出现连续放水越来越卡，我先用分层 ProfilerMarker证明瓶颈不是 Projectile、Exposure 或 Rendering，而是 `ElementWorld.Simulate` 单帧约 263ms 且发生三次 catch-up。进一步区分 Resident、Interest Active 与 RequiresSimulation，让稳定非空 Chunk经过 Hysteresis 后停止 Solver，但仍保留数据并可被 Exposure 读取；写入和跨 Chunk影响负责唤醒。同时对同 Chunk邻居做 Fast Path、跳过 Empty Reaction，并阻止零转移边界创建 Chunk。最终相同操作不再卡顿。这个优化保留了运动阶段的规则精度，代价是必须用测试锁定 Sleep/Wake 与只读可见性；它比单纯降低 TickRate 更符合 Gameplay 语义。

## P6-B Task 5：把稀疏 World Cell 转换成可回收的 Water Chunk Mesh 与共享 Fire Particle

P6-B Task 5 的目的，是让 Task 1～4 中已经能够写入、流动、反应、休眠并影响角色的稀疏 World Cell，真正变成玩家看得见的连续水面和火焰，同时不能把“小实验场能运行”的表现方案机械扩大成“大世界里每个 Cell 一个 GameObject”。最终结果是：Water Projectile 命中任意合法地面后，离散 Water Cell 按可见 Chunk 聚合为动态 Mesh，并继续交给我们自研的 `ElementWater.shader` 表现浅深色、流动法线、Depth、Fresnel 与 Foam；Fireball 命中后，Fire Cell 的固定世界坐标驱动全场共享的 Body/Core/Sparks 三层 `ParticleSystem`。玩家跨越 Chunk 时，旧水火不会跟随玩家或 Renderer Root 漂移；离开 Presentation 范围时只回收 Water View，不删除 Gameplay Chunk，返回后复用原来的 Mesh/GameObject 并根据当前 Version 恢复画面。这个 Task 还明确拆开了三种容易混淆的生命周期：`Resident` 决定世界数据是否存在，`RequiresSimulation` 决定 Solver 是否需要继续计算，`Presentation Visible` 决定 Renderer 是否应显示。稳定水面可以进入 Solver Sleep，却仍然必须可见并继续施加 Wet。因此 Rendering 只通过 `IElementWorldReadOnly` 读取“可见 Resident Chunk”，绝不能拿 Solver Active Snapshot 充当渲染列表。通过 View Pool、Dirty Version、每帧 Rebuild Budget、Global UV、Global Cell Hash Identity 与共享粒子上限，细粒度 Cell 数据被压缩为有边界的 Scene Object、Mesh Rebuild 和 Particle 成本，为后面的 40～60m 连续灰盒关卡提供了可扩展的 Presentation 基线。

### 1. 从玩家看到的结果反推完整 Presentation 链路

Water 的运行链如下：

```text
Water Projectile 命中
→ ElementWorldRuntime 在 Fixed Tick 修改 Water Cell 与 Chunk Version
→ IElementWorldReadOnly.CopyVisibleChunkKeys 复制玩家附近的可见 Resident Chunk
→ ElementWorldWaterRenderer 为每个需要显示的 Chunk 取得一个 Pool View
→ 本 Chunk或六邻域 Version 变化时，WaterChunkMeshBuilder 重建可见表面
→ MeshFilter/MeshRenderer 使用 shared M_ElementWater_Handwritten
→ ElementWater.shader 把几何水面表现成流动、深浅、反射与泡沫
```

Fire 的运行链如下：

```text
Fireball 命中
→ World Cell 记录 Fire Amount
→ ElementWorldFireRenderer 每个 Visual Tick 扫描可见 Chunk
→ Global Cell 坐标经过 Hash、Sample Cap、Probability 与 Jitter
→ ParticleSystem.EmitParams 写入世界位置、尺寸与颜色
→ PS_FireBody / PS_FireCore / PS_FireSparks 三套共享系统完成粒子生命周期
```

两条链的共同原则是 `Gameplay owns truth, Presentation owns representation`。Renderer 不能创建、删除或转移 Cell，也不能因为 View 被回收就把 Water/Fire 从 World Store 中删掉。反过来，Cell 只是紧凑数组中的 `MaterialKind + Amount`，它不需要知道自己由 Mesh、Particle、Gizmo 还是未来的 VFX Graph 显示。这样关闭 Renderer 后，Reaction、Flow、Wet/Burning 仍然成立；更换 Shader 或降低视觉预算也不会修改 Gameplay Amount。

Water 和 Fire 采用不同表现载体，是因为它们的视觉结构不同。Water 在稳定后趋向连续表面，多个相邻 Cell 可以合并成一个 Chunk Mesh；Fire 的轮廓快速变化、半透明、向上运动，需要 Lifetime、Velocity、Noise 和 Color/Size over Lifetime，适合共享 Particle Buffer。若两者都采用“每 Cell 一个 Prefab”，数百个 Cell 会变成数百个 Transform、Component、Renderer 和 Culling 单元，直接抵消紧凑 Cell 的性能价值。

### 2. Water Chunk View Pool：为什么回收的是表现对象，不是世界数据

`WorldWaterChunkView` 持有一个 `GameObject`、`MeshFilter`、`MeshRenderer`、动态 `Mesh` 和三个长期复用的 `List` Buffer。它不拥有 `ElementGrid`，只记录当前映射的 `ElementChunkKey`。`Assign` 把 View 放到对应 Chunk 的固定世界位置；`Release` 清空 Mesh、关闭 Renderer 并 Disable GameObject，但不会调用 Gameplay Store 的 Reclaim。`WorldWaterChunkViewPool` 采用固定 `MaximumViews`：优先返回已经绑定同一 Key 的 View，其次复用已释放 View，最后才在尚未到上限时创建新 View。这样玩家往返移动只发生 Enable/Disable、Key 改绑和 Mesh 重建，不会反复 `Instantiate/Destroy` 造成 Main Thread Spike、Native Mesh churn 与托管 GC 压力。

一个 Chunk View 的世界位置是：

```text
chunkWorldSize = chunkSize × cellSize
viewWorldPos    = worldOrigin + chunkKey × chunkWorldSize
```

当前 `chunkSize=8`、`cellSize=0.25m`，所以 Chunk 边长为 `2m`。Builder 写入 Mesh 的 Vertex 是相对该 Chunk 原点的 Local Space 坐标；View Transform 再把整个 Mesh 放进 World Space。这里必须区分 `Global Cell`、`Chunk-local Vertex` 与 `World Position`：Global Cell负责稳定身份和邻域查询，Local Vertex让每个 Mesh 的坐标值保持较小，Transform负责最终摆放。玩家的 Interest Point只决定“哪些 View 被分配”，不参与上述坐标公式，所以玩家移动不会拖走旧水面。

`ElementWorldWaterRenderer` 每帧从只读接口把 Presentation 可见 Key 复制进预分配数组。数组容量按 `MaximumResidentChunkCount` 分配，而不是按 View Cap分配；否则 Dictionary 只复制前 N 项时，枚举顺序可能随机决定远处 Chunk占用全部 View。World Runtime会把有元素的可见 Key按到 Interest Point 的整数距离和 Key稳定排序，Renderer再按顺序 Acquire，因此 View不足时优先显示近处。这个 Culling 只降级画面：没有 View 的 Chunk仍保留 Cell、Reaction 和状态暴露数据。

### 3. Water Geometry：Global UV、跨 Chunk 邻域剔面和 Dirty Signature

P6-A 的 `WaterChunkMeshBuilder` 原本只能读取一个固定数组；本 Task 增加 `BuildWorldChunk`，通过 `IElementWorldReadOnly.TryGetCell(Global Cell)` 查询跨 Chunk 邻居。单个 Water Cell 的可见高度仍是：

```text
fillRatio = amount / 255
surfaceY  = cellBottomY + cellSize × fillRatio
```

Builder 只生成没有上层 Water 的 Top，以及当前水面高于水平邻居的 Side Height Difference。若 Chunk A 边界 Cell 与 Chunk B 相邻 Cell 都有相同高度的 Water，A 的正 X Side和 B 的负 X Side都属于内部面，不应生成。这样既减少 Vertex/Index 和 Transparent Overdraw，也避免两张几乎共面的透明侧壁发生排序或深度冲突。每个 Quad仍使用 4 个 Vertex与 6 个 Index组成两个 Triangle，Winding 决定正面方向；上传后 `RecalculateNormals/Tangents/Bounds` 为 URP Lighting 与 Water Shader 的 TBN Normal提供数据。

P6-A 的 UV可以从固定 Field坐标开始；连续世界必须改为：

```text
uv = globalCellXZ × cellSize
```

Side UV 的纵轴也使用 Global World Height。这里使用“米”为纹理坐标尺度，而不是每个 Chunk从 `(0,0)` 重新开始。否则相邻 2m Chunk会从同一个 Noise相位重新采样，形成肉眼可见的重复方格接缝；玩家跨 Chunk时还会觉得 Shader纹理在重置。Global UV让两组移动 Noise、Normal扰动与 Foam Mask在 Chunk边界连续。

Mesh不应每帧全部重建。Gameplay Chunk的 `Version` 是 Dirty Tracking 的基础，但单看本 Chunk Version仍不够：A Chunk边界 Cell的 Side是否可见，取决于 B Chunk的邻居水位；如果只有 B发生变化，A自己的 Version不变，A会保留过期内部面或裂缝。因此 Renderer计算包含自己和六邻域版本的 Visual Signature：

```text
signature = FNV_Mix(
    selfVersion,
    negativeXVersion, positiveXVersion,
    negativeYVersion, positiveYVersion,
    negativeZVersion, positiveZVersion)
```

任一邻页变化都会让本 View重新构建。为防止一次大范围 Deposit在同一帧重建几十个 Mesh，`MaxChunkRebuildsPerFrame` 默认限制为 4；环形 Cursor从上次停下的位置继续扫描，避免列表前部持续变化的 Chunk永久占满预算而让后部发生 Starvation。代价是大范围变化可能跨几帧逐步完成，但 Frame Time更稳定。稳定水面最终 `Dirty Count/Rebuild Count` 回到 0，不会因为仍然显示就重复上传 Mesh。

### 4. Fire 的 Global Cell Hash Identity 与三层共享发射

P6-A Fire Sampler使用固定数组 `cellIndex` 作为视觉身份；在稀疏 World中，不同 Chunk都存在 Local Index 0～511，Dictionary枚举序号又会随加载、回收和插入顺序变化。若继续使用这些临时编号，不同 Chunk会出现同步火焰图案，或者玩家往返后同一个 Fire Cell突然换一套 Jitter。解决方法是把稳定 `Vector3Int Global Cell` 变成 Hash Identity。三个有符号坐标先按 FNV-1a合并：

```text
h0 = 2166136261
h1 = (h0 XOR uint(x)) × 16777619
h2 = (h1 XOR uint(y)) × 16777619
h3 = (h2 XOR uint(z)) × 16777619
```

随后使用 32-bit Avalanche，让输入坐标只变化一位时输出多数 bit也发生变化。Hash再混合 `visualSequence`、`layerSeed` 与 `channel`，取低 24 bit除以 `2^24`，得到严格位于 `[0,1)` 的确定性浮点数。`unchecked` 的整数溢出是 Hash的 wrap-around规则，不是 Bug；负坐标按二进制补码参与混合，因此世界原点两侧都有稳定身份。

发射概率仍为：

```text
threshold = layerProbabilityAtFullAmount × amount / 255
emit      = Hash01(globalCell, sequence, layer, channel0) < threshold
```

Jitter的 X/Z限制在 `±0.35 × cellSize`，Y只向上偏移，避免火焰出生在地面下；不同 channel让三个轴互不相关。Active Fire Cell超过视觉上限时，`Rational Stride`只让固定数量进入本次视觉采样，并用 Sequence旋转样本，避免同一批远处 Cell永久被视觉降级。这里削减的是 Particle发射机会，不是 Fire Amount。

`ElementWorldFireRenderer` 只保留 `PS_FireBody`、`PS_FireCore`、`PS_FireSparks` 三套系统。它关闭 ParticleSystem内置 Emission，使用 `ParticleSystem.EmitParams` 写入 Cell Center、StartSize和StartColor；三层继续复用 5A～5D 已调好的 Lifetime、Velocity、Noise、Color/Size over Lifetime与 Material。Simulation Space强制为 `World`，因此同一套系统可以同时服务相距很远的火区，已经发出的粒子也不会随 Emitter Root移动。视觉 Tick发生卡顿时不补发历史欠债，而是把 Accumulator归零；否则恢复的一帧会集中补发多轮 Particle，制造 CPU 与 Transparent Overdraw峰值。Gameplay Fixed Tick需要追赶才能保持规则时间，Presentation Visual Tick则允许丢帧，这正是两种生命周期不同的设计取舍。

### 6. TDD、Frame Debugger、Play Mode Gate、Debug 方法与面试表达

TDD先锁定最容易在大世界才暴露的两个 Water不变量：跨 Chunk相邻 Water不产生内部面、相邻页 UV不重新从0开始；同时锁定 View Pool复用和上限。RED阶段因 `IElementWorldReadOnly` 与 `WorldWaterChunkViewPool`尚不存在而得到两个预期缺失类型错误。实现 Water链后，显式包含新 Renderer的 `Game.Rendering.Tests`编译为0 warning/0 error。Fire部分先新增两个 Global Cell测试，RED阶段得到7个预期 `Vector3Int → int`缺失重载错误；实现 Global版本后再次编译为0 warning/0 error。最终用户在 Unity Test Runner确认 Rendering组全部绿色，`FireCellEmissionSamplerTests`为10项。

Play Mode验证覆盖了真实 Projectile命中、Water摊开、Fire三层发射和跨 Chunk移动。用户确认：水火都生成在命中世界位置；玩家移动改变 Interest Chunk后旧水火不瞬移；远处 Water View关闭，返回后重新出现；稳定水即使 Solver-Sleeping仍然可见；Fire Renderer的 Active/Sampled/Body/Core/Sparks计数随 Fire Cell变化。Frame Debugger进一步确认 Water由 `WorldWaterChunkView_x`按 Chunk Mesh绘制，而不是一个 Cell一个 Draw；Fire始终只有 Body/Core/Sparks三套共享 ParticleSystem Renderer，没有随着 Fire Cell数量生成额外对象。这里没有伪造固定 Draw Call数字，因为 URP Event分组与 SRP Batcher会影响 Frame Debugger显示方式；真正需要锁定的是对象与绘制粒度。

常见故障应按下面顺序定位：

1. **Gameplay有 Wet但没有水面：** 先看 World Water Renderer是否连接 `ElementWorldRuntime`与 Material，再看 `Visible Element Chunk Count/Assigned View Count`。不要因为 Chunk已经 Solver-Sleeping就把它从 Presentation列表过滤掉。
2. **跨 Chunk出现裂缝或内部水墙：** 先用 Builder测试检查 Global Neighbor查询，再检查 Visual Signature是否混入六邻域 Version；仅比较本 Chunk Version无法感知邻页变化。
3. **每个 Chunk的流动纹理从头重复：** 检查 UV是否由 `globalCellXZ × cellSize`生成，以及 View Transform是否只承担世界平移；不要把 Chunk-local XZ直接当最终 UV。
4. **远处水回收后再次回来创建大量对象：** 展开 Hierarchy观察 `WorldWaterChunkView_0...N`是否被复用；Pool Release应 Disable而不是 Destroy，Created Count不应随往返无限增长。
5. **Fire在不同 Chunk呈现完全同步图案或重新进入后跳变：** 检查 Hash Identity是否使用 Global Cell三轴，而不是 Local Cell Index、Active Ordinal或 Dictionary枚举位置。
6. **火焰跟着 Emitter Root移动：** Particle Main仍为 Local Simulation Space；必须使用 World，并保证 EmitParams.position是 World Cell Center。
7. **卡顿恢复帧突然爆出大量火：** Visual Tick正在补历史欠债。Presentation允许丢弃过期 Tick，应把 Accumulator归零而不是 while循环 catch-up。
8. **大量 Cell导致对象数量暴涨：** 检查是否误做了每 Cell/Chunk一个 ParticleSystem或水 Prefab；正确架构是 Water每可见 Chunk一个 pooled Mesh、Fire全世界三套共享系统。

面试时我会这样完整讲述：我先把元素 Gameplay与 Presentation做单向隔离，`Game.Rendering`只通过 `IElementWorldReadOnly`读取固定世界坐标下的可见 Resident Chunk。这个可见列表不能复用 Solver Active列表，因为稳定水会停止计算但仍必须显示和施加 Wet。Water属于连续表面，因此我按8³ Cell聚合成动态 Chunk Mesh；View Pool在固定上限内复用 GameObject、Mesh与List Buffer，离开显示范围只释放表现绑定，不删除 Gameplay数据。Builder根据 `amount/255`计算高度，只生成 Top和高于邻居的 Side；跨 Chunk直接查询 Global Cell邻居，UV使用 `globalCellXZ×cellSize`，所以内部面被剔除且移动 Noise跨页连续。Dirty Tracking不只比较本 Chunk Version，而是混合六邻域 Version，因为边界面受邻页控制；每帧最多重建4个，并用环形 Cursor避免 Starvation。

Fire不适合反复重建 Mesh，我复用了 Body/Core/Sparks三层共享 ParticleSystem。连续世界不能用 Local Index或 Dictionary序号做随机身份，所以我把有符号 Global Cell三轴用FNV-1a与32-bit Avalanche混合，再叠加 Visual Sequence、Layer Seed和Channel得到稳定 `[0,1)`，用于概率、Jitter和层间去相关。超过视觉预算时只降级采样，不修改 Gameplay Fire Amount。三套系统都使用 World Simulation Space和手动 `EmitParams`，对象数量固定；卡顿时不补发视觉 Tick，避免恢复帧 Overdraw峰值。TDD覆盖跨页剔面、Global UV、View复用上限和 Global Hash；Play Mode覆盖真实水火命中、跨 Chunk往返与坐标稳定；Frame Debugger证明水按 Chunk Draw、火只有三层共享系统。这个方案的取舍是 CPU Mesh Rebuild仍有预算延迟、透明 Chunk仍有排序和 Overdraw成本，但它在当前Demo规模下可测试、可Debug，并且把将来迁移 `MeshData/Jobs/Burst`或`VFX Graph/Compute Buffer`的边界保留在 Presentation层，不需要重写 Gameplay Solver。

## P6-B Task 6：连续元素世界的系统验收、性能预算与阶段收口

P6-B Task 6 的目的不是再添加一种新元素，也不是继续堆叠脚本，而是回答一个更接近真实项目交付的问题：Task 1～5 分别通过测试，并不自动等于“玩家已经可以在连续关卡中稳定使用这套系统”。坐标、存储、Simulation、Projectile、Exposure、Water Mesh 和 Fire Particle 都可能局部正确，却在玩家长距离移动、跨 Chunk、反复施法、远离再返回时发生组合故障。因此本 Task 把整个 Water/Fire Vertical Slice 当成一条完整产品链验收：玩家移动只改变 Streaming Interest，不改变元素的世界身份；Water/Fire 能跨 2m Chunk 边界流动和反应；远处数据、Solver 与视觉按不同规则休眠或回收；返回后非空数据恢复；Renderer 保持 Chunk/共享系统粒度；Profiler 必须能说明真正的 CPU 成本来自哪里。验收过程中还发现并解决了“连续释放水球后越来越卡”的系统级问题：瓶颈不是水球 Prefab 数量，也不是 Water Shader，而是大量仍被 Solver 扫描的 Chunk 叠加 Fixed Tick catch-up。Task 6 最终完成的是 Demo Gate 和知识收口，而不是宣称已经获得所有设备上的发布级性能认证；首个 S 形灰盒关卡属于关卡设计与流程实现，已明确移出本 Task，后续另立计划。

### 1. 为什么所有子模块都通过后，还必须做一次整体 Gate

单元测试通常验证一个局部不变量，例如“跨 Chunk 转移前后 Water 总量守恒”“未知 Chunk 的只读查询不会创建数据”“View Pool 不超过上限”。这些结论非常重要，但玩家体验是一条跨模块运行链：

```text
玩家点击施法
  → SpellCaster 实例化 Projectile
  → ElementDepositOnImpact 产生 ElementWriteRequest
  → ElementRuntimeRegistry 找到唯一 World Write Sink
  → ElementWorldRuntime 在 Fixed Tick 消费写入
  → World Store 按需创建 Chunk，并在首次创建时 Bake SolidMask
  → ElementWorldSimulator 推进 Reaction / Down Flow / Horizontal Flow / Fire Decay
  → ElementWorldExposureSystem 查询角色 Bounds 内的 Cell，施加 Wet/Burning
  → IElementWorldReadOnly 向 Rendering 暴露 Presentation 可见 Chunk
  → Water Chunk Mesh 与共享 Fire ParticleSystem 呈现最终画面
```

只要其中一段使用了不同的坐标 Origin、不同的 Chunk 生命周期或错误的“Active”定义，局部测试全部绿色时仍可能出现水跟随 Root 漂移、稳定水突然消失、Wet 存在但没有水面、远处 Chunk 一直占用 CPU 等问题。所以 Task 6 使用“验证金字塔”：底层由 Pure Function/EditMode Tests 锁定公式，中层通过 Scene 引用与 Play Mode 检查真实 Unity 生命周期，顶层用 Profiler/Frame Debugger验证性能和绘制粒度。三类证据回答的问题不同，不能互相冒充：

- EditMode Tests 证明确定性规则和边界条件，不证明 Scene 引用已经配置正确。
- Play Mode 证明真实 Projectile、Collider、Status 与 Renderer 接通，不给出可靠的 CPU/GPU 归因。
- Profiler/Frame Debugger 证明时间花在哪里、怎样绘制，不自动证明 Gameplay 公式正确。

这也是 Task 6 没有创建新 Gameplay 脚本的原因：它验证 Task 1～5 已经形成一个系统，并将发现的问题反馈到真正负责的层，而不是为了“看起来有产出”再加一个万能 Manager。

### 2. 固定世界身份与跨 Chunk：玩家移动时到底改变了什么

当前基础参数是 `cellSize = 0.25m`、`chunkSize = 8`，因此 Chunk 的世界边长为：

```text
chunkWorldSize = chunkSize × cellSize
               = 8 × 0.25m
               = 2m
```

世界位置映射仍使用 Task 1 确立的三步公式：

```text
globalCell = floor((worldPosition - worldOrigin) / cellSize)
chunkKey   = floorDiv(globalCell, chunkSize)
localCell  = floorMod(globalCell, chunkSize)
```

这里的 `worldOrigin` 在 Runtime 初始化时固定，绝不能改成玩家当前位置；`Interest Point` 通常引用 `WizardPlayer.transform`，但它只决定“哪些 Chunk 需要驻留、计算或显示”。因此玩家移动时允许变化的是 `Interest Global Cell` 和 `Interest Chunk Key`，不允许变化的是已经写入 Cell 的 Global Coordinate。可以把它理解为：玩家携带的是一个调度窗口，不是拖着一块元素地图行走。

跨 Chunk Gate 特别检查 Local Cell `7` 与相邻 Chunk Local Cell `0` 的连续关系。Water 水平转移的简化公式是：

```text
difference = max(sourceAmount - targetAmount, 0)
transfer   = min(maxLateralFlowPerTick, floor(difference / 8))
```

`difference / 8` 会把转移速度压低，减少两个 Cell在整数 Amount 下来回震荡；`maxLateralFlowPerTick` 给单 Tick 设置上限，避免高浓度 Cell 一帧搬空。跨 Chunk时来源减少量和目标增加量必须相等，Reaction也必须等量消耗 Water/Fire。Task 6 在真实场景中验证边界两侧的 Water Mesh没有裂缝、Fire可以和另一侧 Water反应；这同时覆盖了 Gameplay邻居查询与 Presentation邻域剔面，二者缺一不可。

### 3. 四种生命周期不能混为一个 `Active`

连续世界最关键的架构理解，是一个 Chunk 是否存在、是否模拟、是否显示和是否处于玩家调度范围，是四个彼此相关但不相同的问题：

| 概念 | 它回答的问题 | 稳定水面的典型状态 |
|---|---|---|
| `Resident` | 数据是否还保存在 `ElementWorldStore` 中 | 是；Water Amount 必须保留，玩家返回后仍存在 |
| `Interest Active` | 是否位于玩家附近，或仍处于 Gameplay Grace Lease | 通常是；附近数据允许查询和被新事件唤醒 |
| `RequiresSimulation` | Solver 本 Tick 是否真的需要扫描它 | 否；稳定水不应每 Tick重复跑四个 Stage |
| `Presentation Visible` | Renderer 是否应该为它保留/分配 View | 是；水稳定并不意味着视觉应消失 |

这四者拆开以后，下面几种行为才可以同时成立：

1. 一滩已经稳定的水仍然显示、仍能让角色 Wet，但不再持续消耗 Solver CPU。
2. 玩家离开远处非空区域时，Water Mesh View可以回收到 Pool，数据仍 Resident；返回后重新绑定 View即可恢复画面。
3. 空 Chunk离开 Interest Region并超过 `SleepGraceTicks` 后可以真正 Reclaim，降低 Resident Count。
4. 新 Projectile写入、相邻 Chunk跨边界 Flow/Reaction会调用 `WakeForSimulation`，把稳定 Chunk重新送回 Solver。

`ElementWorldChunk.RecordSimulationResult` 使用连续多个无变化 Tick的 Hysteresis，而不是一个 Tick没变化就立刻 Sleep。若 `changedCellCount == 0` 连续达到 `SettleAfterUnchangedTicks`，才令 `RequiresSimulation = false`；任何真实写入会清零计数并 Wake。Hysteresis 的作用是防止临界整数流动在 Sleep/Wake之间频繁抖动。`Resident` 与 `RequiresSimulation` 的分离也是这次性能修复的核心：保留数据不等于每帧计算数据。

Store 上限是安全阀而不是普通玩法规则。`MaximumResidentChunks` 达到后，新 Key会被拒绝，已有 Chunk仍保持一致；未知 Chunk的 `GetCellOrEmpty` 只返回 Empty，不能因为“读一下远方”就分配内存。非空 Chunk不能被普通 Reclaim删除，否则玩家离开再回来会发现水火凭空消失；空 Chunk才可在 Grace到期后回收。这些边界主要由 `ElementWorldStoreTests` 和 `ElementChunkActivityPlannerTests` 自动锁定，比手动跑到每一个极限位置更稳定。

### 4. 完整性能 Debug：为什么水球放得越多越卡

最初的现象是：连续释放 Water Projectile后，角色仍能正确进入 Wet，但游戏会随着水量和 Chunk数量增加而越来越卡。第一步不能凭画面直接把责任归给 Water Shader，因为“看不见水”与“CPU Simulation很慢”可以同时发生。Profiler添加/查看了以下分层 Marker：

```text
ElementWorldRuntime.Update
├── ElementWorld.ApplyWrites
├── ElementWorld.BakeChunkSolid
├── ElementWorld.RebuildActivity
├── ElementWorld.Simulate
│   ├── ElementWorld.Simulate.PrepareNeighbors
│   ├── ElementWorld.Simulate.Reaction
│   ├── ElementWorld.Simulate.DownFlow
│   ├── ElementWorld.Simulate.HorizontalFlow
│   ├── ElementWorld.Simulate.FireDecay
│   └── ElementWorld.Simulate.Commit
└── ElementWorld.Exposure
```

证据截图中，单帧 CPU约 `296.79ms`，其中 `ElementWorld.Simulate`约 `262.95ms`，并且同一帧执行了3次。这与 Profile的 `MaxCatchUpTicks = 3`一致：Fixed Tick Accumulator发现主线程已经落后，为了追赶 Gameplay时间在一帧内补跑多个 Tick；每个昂贵 Tick又让下一帧更晚，于是形成 `Spiral of Death`。它可以用一个近似成本模型理解：

```text
frameSimulationCost
≈ catchUpTickCount
  × requiresSimulationCellCount
  × simulationStageCount
  × averageNeighborQueryCost
```

当大量 Chunk虽然 Water已经稳定，却仍被当作“需要模拟”时，`requiresSimulationCellCount`不断增长；跨 Chunk邻居若总走 Dictionary/Binary Search慢路径，`averageNeighborQueryCost`也很高；再乘3次 catch-up，就会突然从几十毫秒放大到数百毫秒。Profiler当时还显示约188个 Resident Chunk，其中69个仍 Active、119个 Sleeping，活跃元素 Cell约1631个。这说明 Resident增长本身不一定是错误，真正需要缩小的是“本 Tick必须被 Solver扫描的集合”。

修复不是简单把 Tick Rate调低，而是分层处理根因：

- **Solver Sleep/Wake：** 稳定 Chunk在连续无变化后退出 Solver；新写入和真实跨 Chunk影响负责 Wake。这样保留世界持久性，同时让稳定水的持续成本接近零。
- **Same-Chunk Neighbor Fast Path：** 大多数邻居仍位于同一个8³ Chunk内，直接通过 Local Cell访问，只有越界时才查询 World Store，避免每个 Cell、每个 Stage都做全局查找。
- **Empty Reaction Pruning：** Empty Cell不可能产生 Water/Fire Reaction，提前跳过，减少无意义邻居查询。
- **Zero-Transfer Boundary Suppression：** 当 `floor(difference / 8) == 0` 时，不为了一个实际为0的转移创建边界邻 Chunk；否则薄水边缘会不断扩大 Resident集合。
- **Presentation不补历史欠债：** Gameplay Fixed Tick需要受控 catch-up来维护规则时间，但 Water Rebuild/Fire Emit是视觉采样，卡顿恢复后补发历史视觉 Tick只会制造 Mesh重建或 Overdraw峰值，因此视觉层可以丢弃过期采样。

这些优化存在明确取舍：Sleep必须以测试保证“后续写入一定会 Wake”；边界预准备不能漏掉真正可能接收流动/反应的 Chunk；Presentation丢 Tick会牺牲卡顿期间的每一次视觉采样，但不修改 Gameplay Amount。用户随后用相同的连续水球压力操作复测，确认游戏不再随释放次数逐渐变卡，这构成了本次 Demo Gate最重要的前后对照证据。

本轮没有保存优化后 Development Build 的完整 Marker毫秒表和 `GC Alloc = 0 B`截图，所以不能把“代码按预分配/NonAlloc原则设计”和“已经在目标构建上测得绝对零分配”写成同一结论。当前可以确认的是：热路径工作数组按 `MaximumResidentChunks`预分配，Simulation不应在 Tick内 `new`/LINQ，Exposure使用 `Physics.OverlapBoxNonAlloc`，Water View/Mesh与 Fire ParticleSystem复用；精确的目标机器 CPU/GPU/GC基线仍应在灰盒关卡内容稳定后，用 Development Build重新记录。

### 5. Rendering验收：Frame Debugger真正证明了什么

Water与Fire采用不同的表现聚合方式。Water按可见 Chunk构建一个可复用 Mesh View，而不是每个 Cell一个 Cube/GameObject；Fire则让整个连续世界复用 Body/Core/Sparks三套 ParticleSystem，通过 `ParticleSystem.EmitParams`在 Global Cell中心手动发射。Frame Debugger验收的重点不是死记一个 Draw Call数字，因为 URP Pass、透明排序和 SRP Batcher都会影响最终列表，而是确认绘制粒度没有退化：

- Water列表中看到的是 `WorldWaterChunkView_x`一类按 Chunk的 Renderer，不是几百个 Cell对象。
- Fire无论有多少 Fire Cell，Hierarchy仍只有 Body/Core/Sparks三层共享系统，不随 Cell数创建 ParticleSystem。
- 稳定但 Solver-Sleeping的水仍处于 Presentation Visible范围；玩家离开后 View释放，返回后从 Pool复用并根据 Global Cell重新生成。
- Water跨 Chunk内部相邻面被剔除，Global UV使用 `globalCellXZ × cellSize`，所以 Noise纹理不会在每个2m Chunk重新起始。

`WorldWaterChunkViewPool`解决的是 GameObject/Mesh生命周期；`WaterChunkMeshBuilder`解决的是 Geometry；`ElementWorldWaterRenderer`负责只读查询、Dirty Signature、Rebuild Budget和 View绑定。把三种职责拆开，既方便 Pure Test，也避免 Renderer同时掌握 Gameplay写权限。Fire侧的 `FireCellEmissionSampler`使用 Global Cell Hash作为稳定身份，避免 Dictionary枚举次序变化后火焰随机图案整片跳动。

# Task 1：建立 Cell、坐标换算与紧凑网格内核

Task 1 的目标不是马上显示一滩水或一片火，而是先建立后续所有系统都能信任的“空间数据底座”。如果没有这层底座，Projectile 可能用一套公式写入环境，角色 Exposure 用另一套公式采样，Rendering 又用第三套公式生成 Mesh，最终就会出现画面上明明有水、Gameplay 却读不到 Wet 的错位问题。本 Task 因此先定义 `ElementCell` 这种极小的值数据，用统一的 `ElementFieldCoordinates` 完成 World Space、Grid Space 与一维数组索引之间的转换，再由 `ElementGrid` 一次性拥有 Current/Next/Solid/Delta 四组连续数组。它还增加了 `ElementFieldProfile` 统一保存 Gameplay 调参，并用 `IElementFieldReadOnly` 规定未来 Rendering 只能读取、不能反向修改模拟。本阶段没有创建任何 Cube、Collider、Prefab、Scene 或视觉资源；可见效果为零是预期结果，但我们已经获得了 Cell 世界最关键的内存模型、坐标协议和程序集边界。

## 1. 从最终效果倒推：Cell 到底是什么

玩家最终看到的会是连续水面和跳动火焰，但 Gameplay 不能为每个小区域创建一个 GameObject。这里的 `Cell` 只是一条数据记录：`MaterialKind` 表示该空间小区域当前主要是哪种元素，`Amount` 表示该元素的离散含量。它更接近一张三维表格中的一个格子，而不是 Minecraft 中有 Mesh、Collider 和 Transform 的“方块对象”。未来 Water Mesh 和 Fire Particle 会读取这些格子并把离散数据包装成连续视觉，因此“模拟分辨率”和“画面精细度”不是同一个概念。

`ElementMaterialKind : byte` 显式使用 1-byte 底层枚举；`ElementCell` 又保存一个 `byte Amount`，所以核心有效载荷约为 2 bytes。`Amount` 的范围是 `0～255`，归一化到 Shader 或概率时使用：

```text
normalizedAmount = Amount / 255.0
```

相比每格保存一个 `float`，`byte` 把单通道数量从 4 bytes 降到 1 byte，并天然限制范围。代价是精度只有 256 档，而且加减时必须先提升到 `int`，完成 Clamp 后再转回 `byte`，否则会发生整数下溢或上溢。`Poison` 和 `Sticky` 目前只预留稳定枚举编号，P6-A 不实现它们的模拟规则，避免把“协议已预留”误写成“功能已完成”。

`IsEmpty` 同时检查 `MaterialKind == Empty` 和 `Amount == 0`。这是对模拟中间态的容错：某一步可能先把数量减到 0，稍后再统一清理种类；只要任一条件表示无有效物质，调用者就应把它当空 Cell，而不是继续参与流动。

## 2. 坐标与索引公式：为什么必须集中实现

Field 的 `Origin` 是网格最小角在 World Space 中的位置。首先把世界坐标平移到 Field 的 Local/Grid Space，再除以 CellSize 量化：

```text
local = worldPosition - origin

cellX = floor(local.x / cellSize)
cellY = floor(local.y / cellSize)
cellZ = floor(local.z / cellSize)
```

这里必须使用 `Floor`，不能使用 C# 的强制 `(int)` 转换。强制转换执行“朝 0 截断”，例如 `-0.04 / 0.25 = -0.16` 会变成 `0`，从而把 Field 左边界外的点错误放进第 0 格；`Floor(-0.16) = -1` 才能让 Bounds Check 正确拒绝它。网格采用半开区间：最小边界属于第 0 格，最大边界 `origin + dimensions * cellSize` 不属于 Field。半开区间可以让相邻 Cell 共用边界而不会同时认领同一个点。

三维坐标最终压入一维数组，公式是：

```text
index = x + sizeX * (y + sizeY * z)
```

这表示 X 是变化最快的轴。`(0,0,0)` 与 `(1,0,0)` 的 index 相差 1，因此按 X 扫描时会连续读取内存，更容易命中 CPU Cache。反向公式为：

```text
x  = index % sizeX
yz = index / sizeX
y  = yz % sizeY
z  = yz / sizeY
```

所有尺寸乘法都先提升为 `long`：`count = (long)sizeX * sizeY * sizeZ`。如果直接用 `int` 相乘，一个极端非法尺寸可能在检查前溢出成负数或很小的正数，随后错误地通过容量验证。`TryWorldToCell` 适合单点查询；`WorldToCellUnchecked` 则故意保留越界坐标，供后续范围写入先算球体 AABB、再 Clamp 到 Field。二者用途不同，不能为了“API 更少”强行合并。

## 3. 连续数组、Double Buffer 与所有权边界

`ElementGrid` 构造时一次性分配四个长度相同的数组：

```text
CurrentCells   当前 Tick 的只读来源
NextCells      下一 Tick 的写入结果
SolidMask      静态障碍标记
AmountDelta    同一阶段的累计数量变化
```

Current/Next 是后续 Double Buffer 的基础。若模拟一边遍历一边直接修改 Current，遍历顺序就会影响结果：先处理的水可以在同一 Tick 中再次流动，造成“一 Tick 穿过多格”；Double Buffer 让本 Tick 始终读取旧状态、统一写入新状态。`SolidMask` 与元素数据分开，是因为“这里有墙”是空间属性，不是第五种元素。若把墙伪装成 MaterialKind，反应和流动代码就会不断混入特殊分支。

四个数组只在构造时 `new`。未来固定 `10 Hz` 的 Simulation Tick 只会 `Clear` 或覆盖已有内容，不会每 Tick 新建数组、LINQ 或临时对象。这既满足项目的 `0 B GC Alloc` 目标，也比 `Cell[,,]` 或每 Cell 一个 class 更利于顺序访问。数组字段保持 private，程序集内部通过 internal 成员写入；测试程序集使用 `InternalsVisibleTo` 获得验证权限，但这不会把写入口暴露给 `Game.Rendering`。

## 6. 面试时如何完整讲述 Task 1

> 我在做 3D Noita-like 环境时，没有把 Cell 设计成 GameObject 方块，而是把它定义成紧凑值数据：一个 byte 枚举表示主要材质，一个 byte 表示 0～255 的含量。这样 16,384 个 Cell 的核心物质数据只有约 32 KiB，模拟分辨率与最终视觉分辨率可以解耦。所有 Cell 放在一维连续数组中，索引使用 `x + sizeX * (y + sizeY * z)`，让 X 方向连续访问更符合 CPU Cache；尺寸乘法先转 long，避免容量检查前 int overflow。

# Task 2：提取共享 Extinguish 消耗公式

Task 2 解决的是 P2 角色状态与 P6 空间 Cell 之间“规则必须一致、运行时容器又不能照搬”的架构问题。P2 中角色身上的 Burning/Wet 由 `ElementReactionRuntime` 跨帧推进，它除了计算数值，还要保存是否 Active、是否已经发布 Started、正式反应速率是否锁存以及何时发布 Resolved；如果 P6 给成千上万个 Cell Pair 各创建一个这样的 Runtime，内存、状态数量和 Debug 难度都会无谓增加。反过来，如果 Cell Simulator 自己复制一份 `min(Fire, Water, Rate × Δt)`，以后只改角色公式而忘记环境公式，就会出现同样的水火接触在角色身上和地面上得到不同结果。本 Task 因此把真正可共享的部分提取为 `ElementReactionEvaluator.CalculateExtinguishConsumption()` Pure Function：输入本步 Fire、Water、时间、速率模式和只读调参，输出双方各自应扣除的同一个数值；角色 Runtime 继续负责生命周期与 Formal Rate Latch，未来 Cell Simulator 只负责空间遍历和阈值判断。这样复用的是“物理/玩法定律”，不是不合适的对象生命周期。

## 1. 从最终行为倒推：为什么只共享公式

我们希望得到的最终行为是：角色身上 `80 Fire + 30 Wet` 会连续变化到 `50 Fire + 0 Wet`，未来一个空间位置中 Water 与 Fire 接触时也必须遵守等量中和与同一速率参数。这里包含两类性质不同的问题：

```text
无状态规则：给定 Fire、Water、Δt、Rate，本步应消耗多少？
有状态流程：何时 Started、是否锁定 Formal Rate、何时 Resolved、信号发给谁？
```

第一类是 `Pure Function`：相同输入永远得到相同输出，不读取 `Time`、`Physics`、`MonoBehaviour`、EventBus 或隐藏字段。第二类是 `Stateful Runtime`：同样的数值输入，在“刚启动”和“已经正式反应 0.4 秒”时可能需要不同事件输出。Task 2 只把第一类放进 `ElementReactionEvaluator`。这样 P2 Character Carrier 和 P6 Spatial Carrier 可以共享公式，同时保留各自正确的数据结构：角色数量少，适合保存反应生命周期；Cell 数量多，适合按固定 Tick 批量遍历紧凑数组。

## 2. 公式、变量和守恒如何理解

核心公式是：

```text
Rate = useFormalRate ? max(FormalRatePerSecond, 0)
                     : max(LowRatePerSecond, 0)

Consumed = min(
    max(Fire, 0),
    max(Water, 0),
    Rate × max(Δt, 0))
```

`Fire` 与 `Water` 是当前载体内可参与反应的存量；角色系统中它们的语义是 `0～100` 状态强度，未来 Cell 层会把 byte Amount 转换到自己的本步预算。`deltaTime`（公式中的 `Δt`）单位为秒，用于把“每秒速率”积分成本次模拟步的变化量。若 `FormalRatePerSecond = 50`、`Δt = 0.2`，本步时间预算就是 `10`。这也是为什么状态应从 80 平滑下降到 70，而不是一接触就瞬间跳变。

三个 `min` 上限分别解决三个问题。`Fire` 上限防止 Fire 被扣成负数；`Water` 上限防止 Water 被扣成负数；`Rate × Δt` 上限把反应速度交给时间推进。返回值只有一个 `consumed`，Runtime 同时执行：

```text
Fire'  = Fire  - Consumed
Water' = Water - Consumed
```

因此两边始终等量减少，这里的守恒不是说 Fire 和 Water 的总和不变，而是说反应计量关系固定为 `1:1`，不会凭空多扣某一边。以 `Fire=80, Water=30, Rate=100/s, Δt=1s` 为例：`min(80,30,100)=30`，结果正好是 `50/0`。若 Rate 配成负数，`max(rate,0)` 会让反应停止，而不会让负速率反向生成元素；若任一存量或 `Δt` 非正，Early Return 直接返回 0。

## 3. 角色 Runtime 为什么仍需要 Formal Rate Latch

`IsFormalExtinguish()` 判断的是“启动时双方是否都达到 FormalThreshold”。一旦正式反应 Started，角色设计要求高速率一直保持到任一方归零。假设阈值为 10、正式速率为 50/s、低速率为 10/s：`80 Fire + 30 Water` 在 0.4 秒后变成 `60/10`。如果每帧重新用当前 Water 判断正式状态，下一帧 Water 低于 10 后就会退回低速，剩余 Water 会拖很久才清零，破坏我们已确认的 `80/30 → 50/0` 连续反应体验。

所以 `_extinguishFormalSignalled` 不只是“VFX 是否发过”的标记，它也是一个跨帧 `Latch`：一旦变为 true，就持续把 `useFormalRate=true` 传给 Pure Function，直到 `FinishExtinguish()` 清理。Pure Function 故意不保存 Latch，因为未来 Cell Simulator 可能使用“每个固定 Tick 根据当前接触条件选速率”的空间语义；该选择由调用者负责，消耗数学仍然完全一致。这体现了 `Policy` 与 `Mechanism` 分离：Runtime 决定采用哪种速率策略，Evaluator 负责执行守恒计算机制。

# Task 3：实现写入队列与纯 Water/Fire Cell 模拟

Task 3 是 P6 第一次真正让“元素世界”开始变化，但它仍刻意没有创建 MonoBehaviour、Collider、Shader、Particle、Prefab 或 Scene。最终玩家会看到水弹落地后形成水、向低处流动，火焰与水接触后相互消耗，孤立火焰逐渐熄灭；为了让这些可见效果以后可控、可复现，本 Task 先把规则做成纯 C# Simulation Kernel。Projectile 等外部系统不直接修改 Grid，而是提交 `ElementWriteRequest` 到固定容量 Ring Buffer；固定 Tick 开始后先批量应用 Deposit，再按 `Reaction → Down Flow → Horizontal Flow → Fire Decay` 的顺序推进。每个 Stage 都从稳定的 Current Buffer 读取，通过预分配的 Amount Delta 累计变化，再交换 Current/Next，因而新落入下层的水不会在同一 Tick 中继续穿透。Cell 的实际变化只标记 Dirty，Tick 末每个 Dirty Chunk 的 Version 最多增加一次，为后续 Rendering 的按需重建提供低成本同步信号。

## 1. 从玩家效果倒推本 Task 的运行链路

未来一次 Water Projectile 命中地面的完整链路会是：

```text
Projectile Impact
→ ElementWriteRequest（世界位置、Water、总量、半径）
→ ElementWriteQueue（等待下一个固定 Tick）
→ ElementFieldWriteProcessor（World Space → Cell AABB → 分配 Amount）
→ ElementFieldSimulator
   ① Reaction
   ② Down Flow
   ③ Horizontal Flow
   ④ Fire Decay
→ ElementGrid.CurrentCells + ChunkVersion
→ 后续 Rendering 只读并重建 Dirty Chunk
```

Task 3 只完成中间的纯数据部分。现在 Play Mode 中看不到新画面是正确结果，因为还没有 Task 4 的 Runtime/Debug View，也没有后续 Water Mesh/Fire Particle。把规则与视觉分开后，如果水量不守恒，可以只检查数组和公式；如果规则正确但画面错误，再检查 Renderer，不会把 Physics、Shader 和 Simulation 混在一次 Debug 中。

## 2. Ring Buffer 与 Command Buffer 为什么适合 Projectile 写入

`ElementWriteRequest` 是 `readonly struct`，保存 `WorldPosition`、`MaterialKind`、`TotalAmount(ushort)`、`Radius` 和 `UseLinearFalloff`。它是一条命令快照，而不是对 Projectile GameObject 的引用；即使 Projectile 命中后立即销毁，固定 Tick 仍拥有完整输入。Projectile 也拿不到 `ElementGrid.SetCell()`，因此不能绕过模拟顺序直接改世界。

`ElementWriteQueue` 初始化时一次性分配固定长度数组，使用三个整数维护 Ring Buffer：

```text
enqueue：buffer[tail] = command
         tail = (tail + 1) % capacity

dequeue：command = buffer[head]
         head = (head + 1) % capacity
```

`head/tail` 到达数组末尾后通过取模回到 0，所以已经消费的前部空间可以复用。相比 `List<T>`，它不会在法术高峰自动扩容并复制数组；相比无限 Queue，它有明确内存上限。代价是满队列必须拒绝新命令，本实现返回 `false` 并累计 Rejected Count，未来 Runtime 决定是否用 `GameLog.Warn` 限频提示。纯 Queue 不写日志，因为日志策略和场景生命周期属于上层。

## 3. 球形 Deposit、权重归一化与异材料写入

范围写入先用：

```text
minCell = floor((impact - radius - origin) / cellSize)
maxCell = floor((impact + radius - origin) / cellSize)
```

得到球体的 Cell AABB，再 Clamp 到 Grid Bounds。不能先用 `TryWorldToCell` 拒绝越界端点：一个球即使中心靠近边界、部分伸出 Field，Field 内的部分仍应生效。只遍历 AABB 而不是全场 16,384 Cell，使成本与命中范围相关。`radius == 0` 单独作为 Point Deposit 处理，避免 `distance/radius` 除零。

Linear Falloff 权重公式为：

```text
d = distance(CellCenter, ImpactPosition)
weight = saturate(1 - d / radius)
```

第一遍只累计非 Solid、可接收 Cell 的 `weightSum`；第二遍用剩余量分配：

```text
share = round(remainingAmount × weight / remainingWeight)
remainingAmount -= share
remainingWeight -= weight
```

最后一个有效 Cell 得到剩余整数，减少每格独立 Round 引起的总量误差，而且不需要临时 `List` 保存命中 Cell。若目标是 Empty，直接写入；若是同材料，Amount 累加并 Clamp 到 255；若是 Water/Fire 异材料，先执行 `consumed=min(old,incoming)` 的 1:1 抵消，只有剩余 Incoming 才替换 MaterialKind。Poison/Sticky 在 P6-A 明确返回 Unsupported，不会因为枚举存在就假装已经实现规则。

## 4. Stage Pipeline、Double Buffer 与“不允许同 Tick 连锁移动”

Simulator 的固定顺序是 `Writes → Reaction → Down → Horizontal → Decay`。顺序本身就是 Gameplay 规则：水先与邻接火焰反应，剩余水才流动；火焰在所有接触反应之后再自然衰减。每个 Stage 开始时把 Current 复制到预分配 Next，随后只读取 Current，把变化写入预分配 `int[] AmountDelta` 或 Next，结束时交换两个数组引用。`Array.Copy`、`Array.Clear` 和引用交换都复用已有内存，不产生 per-Tick GC Alloc。

Down Flow 使用：

```text
sourceAvailable = sourceOriginal + sourceDelta
targetProjected = targetOriginal + targetDelta
capacity = 255 - targetProjected
transfer = min(sourceAvailable, capacity, MaxDownFlowPerTick)
```

关键点是本 Tick 新收到 Water 的目标 Cell 在 Current 中仍是 Empty，因此不会再次成为 Source。这使 Water 每 Tick 最多向下移动一格，避免按数组遍历方向“一帧穿过整列”。Horizontal Flow 的理想均衡量为：

```text
difference = sourceOriginal - targetOriginal
desired = max(difference / 2, 0)
transfer = min(desired, sourceAvailable, targetCapacity, MaxLateralFlowPerTick)
```

偶数 Tick 使用 `Left/Right/Forward/Back`，奇数 Tick 反向，降低固定方向总是先分到水的偏差；没有使用 `UnityEngine.Random`，所以相同 Grid、相同 Writes、相同 Tick 数一定得到相同 Checksum。它仍不是 Navier–Stokes Fluid Simulation，而是为 Gameplay 服务的离散 Cellular Flow：成本可控、规则可读、能被单元测试证明。

## 5. Reaction 量化、Chunk Version 与内存所有权

相邻 Pair 只检查 `+X/+Y/+Z`，保证无序 Cell Pair 只被访问一次。反应前把 byte Amount 映射为 P2 百分比：

```text
intensity = amount × 100 / 255
```

调用 Task 2 的 `CalculateExtinguishConsumption()` 后，再映射回 byte：

```text
consumedAmount = round(consumedIntensity × 255 / 100)
```

由于 byte 只有 256 档，连续浮点结果可能被 Round 成 0。`ElementFieldProfile.OnValidate()` 因此检查 `LowRate / TickRate × 255 / 100` 是否至少达到一个量化单位；不足时只警告，不偷偷修改策划参数。这个问题叫 Quantization Error：离散表示节省内存，但会失去小于一个量化步长的变化。

经计划复审，我们给 Simulation Snapshot 增加 `CellSize`，因为 World Deposit 不可能在不知道 CellSize 时完成坐标量化；同时让 `ElementGrid` 成为 Chunk Version 的唯一所有者。Grid 构造时预分配 Cell Dirty、Chunk Dirty 和 `uint[] ChunkVersions`。一个 Tick 内同一 Chunk 可以有很多 Cell/Stage 变化，但 Tick 末 Version 只增加一次。Rendering 未来只比较 `lastSeenVersion != currentVersion`，不会清除 Dirty，也不会反向修改 Gameplay。

Task 4 的目的，是把 Task 3 已经通过纯测试的 Water/Fire Simulation Kernel 接进真实 Unity 场景，同时继续保持“Unity Adapter 与纯规则分离”。玩家当前看到的不是最终水面 Shader 或火焰 Particle，而是 Scene View 中的蓝色、橙色和灰色 Cell Gizmo：蓝色表示 Water Gameplay 数据，橙色表示 Fire，灰色表示由场景 Collider 一次性 Rasterize 得到的 SolidMask。`ElementFieldRuntime` 在 `Awake` 中读取 `ElementFieldProfile`，一次性创建 Grid、Queue、Simulator 与只读 Settings Snapshot，再由 `Update` 把不稳定的 Rendering Frame 时间累积成固定 `10Hz` Tick；`ElementFieldSolidBaker` 只在初始化或手动 Rebuild 时调用 Physics，把 Ground/Environment 转换成 bool 数组，后续 Flow 不再逐 Cell 查询 Collider。用户已经实际确认 Water 会从空中下落、被地面阻挡并横向铺开，Fire 会按固定 Tick 衰减，相邻 Water/Fire 也会在暂停状态下随手动 Tick 等量减少至同时归零，证明 Runtime 调度、World→Cell、Solid、两级 Flow、Fire Decay 与 Reaction Stage 均已打通；最终 Unity Test Runner 显示 ElementField `41/41`、全项目 EditMode `207/207`，Console 为 `0 Error`，因此 Task 4 已完成。

## 1. 从可见结果倒推 Runtime 运行链路

当前 Water Gate 的完整链路是：


## 2. 固定 Tick Accumulator 与 Spiral of Death

Unity 的 `Update` 跟随 Rendering Frame，帧间隔可能是 6ms、16ms，也可能因打开 ContextMenu、暂停或 Editor 卡顿突然超过 300ms。Simulation 不能简单地“每帧移动一次”，否则高帧率机器中的水流得更快。Runtime 使用时间债务：

```text
tickInterval = 1 / TickRate = 1 / 10 = 0.1s
accumulatedTime += deltaTime
while accumulatedTime >= 0.1s:
    SimulateOneTick(0.1s)
    accumulatedTime -= 0.1s
```

单帧最多执行 `MaxCatchUpTicks = 3`。若 Editor 停顿一秒，理论上欠下 10 Tick，但只追赶 3 Tick并丢弃剩余债务。否则会形成 `Spiral of Death`：模拟越慢 → 需要追赶的 Tick 越多 → 当前帧更慢 → 下一帧债务更多。用户看到的 `discarded excessive fixed-tick debt` 是这个保护机制的限频 Warning，不是 Water 被清空或模拟崩溃。Runtime 在 `Time.timeScale == 0` 时不自动推进，但 `StepOnceForDebug()` 可以在暂停时明确执行一个 Tick，适合逐步观察 Stage。

## 3. Solid Bake、Gizmo Alpha 与本次 Debug 过程

Solid Baker 对每个 Cell 执行一次：

```text
cellCenter = origin + (cellCoordinate + 0.5) × cellSize
halfExtents = 0.49 × cellSize
Physics.CheckBox(cellCenter, halfExtents, IdentityRotation, SolidLayerMask, IgnoreTrigger)
```

`0.49` 而不是 `0.5`，是为了避免两个 Cell 在边界正好接触时把相邻 Collider 误算进来。用户现场得到 `BakedSolidCellCount = 977`，并看到灰色小方块包裹 Ground Layer 的场景物体，证明 Physics Rasterization 有效。Deposit 明确拒绝写入 Solid Cell，所以 Marker 必须位于 Field Bounds 内且不能落进灰色区域。

本次还暴露了一个纯 Presentation Bug。最初 Debug View 使用：

```text
alpha = Amount / 255
```

当 `TotalAmount = 220` 被半径 `0.75m` 的球形 Deposit 和后续 Horizontal Flow 分散到大量 Cell，每格 Amount 可能只有 1～几单位，Alpha 低于几个百分点；`ChangedCells` 与 `WaterTransfers` 明明持续变化，肉眼却看不到蓝色。修复后只对 Gizmo 使用：

```text
debugAlpha = max(Amount / 255, MinimumActiveAlpha)
MinimumActiveAlpha = 0.25
```

这不会把真实 Amount 从 1 改成 64，也不会影响守恒、Reaction 或未来 Shader，只保证“只要 Cell 非空，调试时就能看见”。回归测试 `NonEmptyDebugCellKeepsMinimumVisibleAlpha` 先因缺少公式得到 `CS0117`，实现后验证 `Amount=1` 仍得到 `0.25 Alpha`。此外，`OnDrawGizmosSelected` 只在真正选中挂载组件的 `ElementFieldLabRoot` 时执行；Inspector 锁定在 Root、但 Hierarchy 实际选中 Marker，并不算选中 Root。这解释了此前连 977 个灰色 Solid Cell 都看不到的现象。

Fire Gate 使用了一个有意加速的测试参数：`TickRate = 10`、`FireDecayPerTick = 32`、初始 `Amount = 220`。每个固定 Tick 执行 `nextAmount = max(0, currentAmount - 32)`，所以需要的 Tick 数和现实时间分别为：

```text
tickCount = ceil(220 / 32) = 7
lifetime = tickCount / TickRate = 7 / 10 = 0.7s
```

因此用户观察到“橙色小方块出现很短时间就消失”恰好是正确结果，而不是 Gizmo 丢失。退出 Play Mode 后，`ElementFieldRuntime` 在运行期创建的 Grid、LastStats 与 SolidMask 会随场景运行实例一起销毁，所以 Inspector 再次显示 `BakedSolidCellCount = 0` 和全零 Stats 也属于正常的 Unity 生命周期行为；这些字段是诊断运行态，并不会写回 Scene 或 ScriptableObject。

Reaction Gate 为了排除干扰，临时把 Down Flow、Horizontal Flow 与 Fire Decay 都设为 `0`，并把两个 `Amount = 30` 的 Water/Fire 写到相邻 Cell。二者强度为 `30 / 255 × 100% ≈ 11.76%`，超过 `FormalThreshold = 10%`；在 `FormalRate = 10%/s`、`TickRate = 10Hz` 下，每个 Tick 对双方等量消耗约 `round(10 × 0.1 × 255 / 100) = 3 Amount`。用户在暂停自动 Player Loop 后逐次执行 `Step One Tick`，截图记录到 `ReactionPairs = 1`、`WaterTransfers = 0`、`FireCellsDecayed = 0`，随后两个 Cell 同时归零。这组 Stats 把 Reaction 与水流、自然衰减区分开，因此比只观察“两个方块消失”更有诊断价值。

这里还要注意 `LastStats` 是单 Tick Snapshot，而不是从 Play 开始累计的计数器：每次 `SimulateOneTick` 都会用本 Tick 新建的 Stats 覆盖旧值。因此截图中的 `ProcessedWrites = 1` 只表示最后一次被观察的 Tick 处理了一个写入，不代表整个实验只写入过一个元素；`ReactionPairs = 1` 才表示该 Tick 确实处理了一对相邻 Water/Fire。

# Task 5：让真实 Water/Fire Projectile 写入 Cell

Task 5 的目的，是把前四个 Task 已经验证过的“有限元素场内核”真正接到玩家能够施放的法术上，使 P6 从 Debug 实验进入 Gameplay 闭环。此前点击 `Inject Water/Fire` 虽然可以证明 Grid、Queue、Flow、Decay 和 Reaction 正确，却不能证明现有的 Wand、`CastEvaluator`、`SpellCaster`、Projectile Physics 与环境场能够协同工作。本 Task 新建了最薄的 `ElementOrbProjectile` 和可复用的 `ElementDepositOnImpact`：前者复用 `ProjectileBase` 的飞行与碰撞骨架，后者监听同一物体上的 `Impacted` 事件，把命中点和 Inspector 配置封装为 `ElementWriteRequest`，再提交给 `ElementFieldRuntime` 的固定容量 Queue。Water 使用新 Prefab 和新 `SpellDefinition`，Fire 则直接在既有 Fireball Prefab 上组合沉积组件，不改变其爆炸、直接伤害与 Burning。最终实际验证了水球命中后生成会下落、摊开的蓝色 Cell；火球打入水面会消耗一片 Water；越界命中被安全忽略；水球不会错误造成伤害或 Burning；快速连发不会破坏 Queue；Trigger Fireball 的 Payload 与环境沉积能同时收到同一个命中事件。这个 Task 的关键学习价值不是“多挂了一个组件”，而是理解如何用 Composition、Event Subscription 和 Command Queue，在不污染纯法术解释器、不制造程序集反向依赖的前提下连接三套不同时间线的系统。

## 1. 从玩家看到的结果倒推完整运行链路

玩家看到的表面现象是：Wizard 发射一个带水面材质的小球，小球撞到地面后消失，命中处出现许多蓝色 Cell；这些 Cell 向下落，在 Solid Ground 上停止并横向摊开。随后 Fireball 打进水面，爆炸附近的蓝色区域出现缺口。这个结果实际跨越了 Spell Programming、Combat Projectile 和 ElementField 三层：

```text
Wizard 输入
→ WandLoadout：Spell_Emit_WaterField
→ CastEvaluator：纯数据求值得到 EmitCommand
→ SpellCaster：Instantiate PF_ElementWaterProjectile
→ ElementOrbProjectile / ProjectileBase：Rigidbody 飞行
→ ProjectileBase.OnCollisionEnter：得到 hitPoint / hitDirection
→ ProjectileBase.Impacted multicast event
   ├─ ElementDepositOnImpact：创建 Water WriteRequest
   └─ SpellCaster Trigger Handler：若有 Payload，则在命中点继续解释后缀法术
→ ElementFieldRuntime.Active.TryEnqueueWrite(request)
→ 下一个 10 Hz Simulation Tick
→ ApplyWrites：World Position → Cell Bounds → Amount 分配
→ SimulateStages：Reaction → Down Flow → Horizontal Flow → Fire Decay
→ ElementFieldDebugView：用蓝/橙 Gizmo 显示 Gameplay Cell
```

这里必须区分三种“表现”。飞行中的水球 Mesh 只是 Projectile Presentation，使用 `M_ElementWater_Handwritten` 让它看起来像水；蓝色小方块是 `ElementFieldDebugView` 的诊断 Gizmo；真正的水面 Mesh 与 Shader 聚合属于 Task 7。当前水球消失后出现 Gizmo，证明的是 Gameplay Data 已写入，不代表最终玩家版本会逐 Cell 绘制方块。这样的分层让 Debug 更可靠：如果 Projectile 不出现，沿 `CastEvaluator → SpellCaster → Prefab` 排查；Projectile 命中但 `Processed/Changed Cells` 不变，沿事件与 Queue 排查；Stats 变化但没有 Gizmo，排查 Field Bounds、选择状态和 Debug Alpha；Gizmo 正确但最终水面不正确，未来只排查 Rendering。

`ProjectileBase.OnCollisionEnter` 的顺序也很重要。它先处理友军穿透与 Bounce，再按需调用 `IDamageable.ReceiveHit`，然后调用子类 `OnImpact`（Fireball 在这里处理爆炸与 Burning），接着把 `_consumed` 设为 `true` 并广播 `Impacted(hitPoint, hitDir)`，最后延迟或立即销毁 GameObject。因此环境沉积发生在真实命中之后、Projectile 销毁之前；命中同阵营而穿透、达到最大寿命而自然销毁，都不会错误沉积元素。

## 2. 为什么采用 Composition，而不是继续堆 Projectile 子类

`ElementOrbProjectile` 本身是一个空子类：

```csharp
public sealed class ElementOrbProjectile : ProjectileBase
{
}
```

它不是“没有意义的代码”。`ProjectileBase` 是 `abstract`，Unity 不能直接把抽象类作为 Component 挂到 Prefab；我们需要一个最薄的具体类型，让水球获得统一的 `Rigidbody` 初始化、Continuous Collision Detection、同队 Projectile IgnoreCollision、最大寿命、伤害快照和 `Impacted` 事件。水球本身没有新的碰撞算法，因此不应该复制 Fireball 或 Arrow 的生命周期代码。

真正的环境行为放在独立的 `ElementDepositOnImpact` 中，这体现了 **Composition over Inheritance**：Prefab 通过组合多个职责单一的 Component 得到完整能力。Water Prefab 组合 `ElementOrbProjectile + ElementDepositOnImpact(Water)`；现有 Fireball 保留 `Fireball + ElementDepositOnImpact(Fire)`。如果把沉积逻辑写进 `WaterProjectile` 和 `Fireball` 两个子类，未来 Poison、Sticky、Meteor、Explosion 或 Trigger Projectile 都要重复一套 Queue、边界和参数校验；如果写进 `ProjectileBase`，所有 Arrow、Shield 等非元素 Projectile 也会被迫知道 ElementField，导致 `Game.Combat → Game.ElementField` 的反向依赖，破坏程序集层级。

本方案的依赖方向是：

```text
Game.ElementField
├─ depends on Game.Core：GameLog
└─ depends on Game.Combat：ProjectileBase / Impacted contract

Game.Combat
└─ 不知道 ElementField 存在
```

`ElementDepositOnImpact` 位于更上层的 `Game.ElementField`，它可以读取 Combat 提供的通用事件，但 Combat 不回头引用它。这是 **Dependency Inversion** 的一种实际用法：底层 Projectile 只公布“发生了命中”这一事实，上层环境模块决定该事实是否应当转成 Water/Fire 写入。

另外，本 Task 没有修改 `CastEvaluator`、`EmitCommand` 或 `SpellCaster` 的数据结构。原因是当前 Element Deposit 是 Prefab 固有能力：某个 `SpellDefinition` 选择哪个 Projectile Prefab，就自然选择了该 Prefab 上组合的环境行为。这样 `Game.Skills` 的纯解释器仍只负责“读 Wand 程序、产生 EmitCommand”，不会理解 Grid、Cell 或 World Bounds。取舍是目前 Wand Modifier 不能动态修改 `TotalAmount`、`Radius` 或 MaterialKind；如果未来要实现“水量 +50%”“火焰半径扩大”等法术修正，再把 Deposit Snapshot 正式提升到 `SpellDefinition → CastModifierState → EmitCommand → SpellCaster`，而不是为当前 Demo 过早扩张整个解释器协议。

## 3. Event Subscription、Unity 生命周期与 Trigger 为什么没有被破坏

`ElementDepositOnImpact` 在 `Awake()` 缓存同一 GameObject 上的 `ProjectileBase`，在 `OnEnable()` 使用 `+=` 订阅 `Impacted`，在 `OnDisable()` 使用 `-=` 取消订阅：

```csharp
private void OnEnable()
{
    if (_projectile == null)
        _projectile = GetComponent<ProjectileBase>();

    if (_projectile != null)
        _projectile.Impacted += OnProjectileImpacted;
}

private void OnDisable()
{
    if (_projectile != null)
        _projectile.Impacted -= OnProjectileImpacted;
}
```

这是标准的 Unity Event Subscription 生命周期。C# event 内部保存 Delegate，而 Delegate 又持有订阅对象引用；若对象禁用后不解除订阅，长期存活的 Publisher 可能让 Subscriber 不能被回收，或者在其逻辑已经无效时仍调用回调，形成 Memory Leak 或“幽灵沉积”。当前 Projectile 和 Deposit 通常一起销毁，理论上生命周期很短，但仍然成对订阅/退订，使组件在 Object Pool、临时 Disable 或未来 Prefab 复用场景中保持正确。

这里使用同对象上的直接 C# event，而不是全局 `EventBus<T>`，是有意的边界选择。`Impacted` 是“这一个 Projectile 实例”的局部生命周期通知，订阅者明确持有 Publisher；若发布到全局 EventBus，每颗 Projectile 都要附带 InstanceId，再由所有订阅者过滤，反而增加全局耦合。跨场景、跨对象且发布者与订阅者互不持有引用的 Gameplay Event 才适合 `EventBus<T>`。局部对象协作和跨模块全局广播不能机械地使用同一种工具。

Trigger Fireball 能继续工作，是因为 `Impacted` 是 multicast event。`ElementDepositOnImpact` 通过命名方法订阅，而 `SpellCaster.WirePayload` 对 `OnImpact` Trigger 通过 Lambda 订阅：

```csharp
proj.Impacted += OnProjectileImpacted;
proj.Impacted += (hitPoint, hitDir) => RunCast(payload, ...);
```

广播时两个 Delegate 都会被依次调用，所以同一次命中既可以沉积 Fire Cell，也可以在命中点继续执行捕获的 Wand 后缀。我们没有使用 `=` 覆盖事件，也没有让 Deposit `Destroy` Projectile 或清空事件，因此不会吃掉 Payload。用户实际配置 `TriggerFireball → Fireball` 后，确认首个 Projectile 命中沉积、后续 Payload 正常触发，证明新订阅者没有破坏既有法术编程链路。

需要理解一个边界：C# multicast Delegate 默认按订阅顺序调用，但架构不应依赖这个顺序。Deposit 只入队，Trigger 只继续施法，两者不共享可变局部状态，所以先后顺序不影响结果。如果未来某个回调会抛异常，异常可能中断后续 Delegate；生产级系统可在 Publisher 侧做隔离或要求 Subscriber 不抛出，但 P6-A 的两个回调都使用安全返回路径，不在事件中抛异常。

## 4. 为什么 Physics 命中只入队，而不是立即修改 Grid

Projectile 碰撞来自 Unity Physics 时间线，ElementField 则使用固定 `10 Hz` Simulation Tick。若在 `OnCollisionEnter` 里直接改 Grid，会出现几个问题：同样一秒内，Physics Step 和 Rendering Frame 的调度差异可能改变写入与 Reaction 顺序；同一帧多个 Projectile 直接穿插修改当前/下一 Buffer，可能破坏 Stage Pipeline；自动化测试也很难重现具体执行次序。因此 `ElementDepositOnImpact` 只构造 Value Snapshot 并调用：

```text
ElementFieldRuntime.Active.TryEnqueueWrite(in request)
```

`ElementWriteRequest` 保存命中瞬间的 `WorldPosition`、`MaterialKind`、`TotalAmount`、`Radius` 和 `UseLinearFalloff`。它不在后续 Tick 回查已经销毁的 Projectile，也不保留 GameObject 引用。这和 Combat 中 `DamageRequest` 的 Value Snapshot 思路相同：异步或延迟处理时，应当保存完成计算所需的数据，而不是依赖可能改变或销毁的来源对象。

Queue 是 Task 3 已建立的固定容量 Ring Buffer，当前 `MaxPendingWrites = 128`。容量限制针对“尚未被 Tick 消费的命中请求数量”，不是请求最终覆盖的 Cell 数量。一次半径 Deposit 即使修改数百个 Cell，仍只占一个 Queue Slot；快速连续发射约十个 Water Projectile 也远低于 128。固定数组避免运行期 `List` 扩容与 `GC Alloc`，队满时安全拒绝新请求，而不是覆盖尚未处理的旧请求。用户完成快速连发 Gate 后，Projectile 均能正常命中和沉积，Console 没有错误或卡死。

下一 Tick 的顺序是：

```text
ApplyWrites（按 Queue 顺序消费命中快照）
→ Reaction（相邻 Water/Fire 等量消耗）
→ Down Flow
→ Horizontal Flow
→ Fire Decay
```

`LastStats.ProcessedWrites` 是“最后一个 Tick”的 Snapshot，不是从进入 Play Mode 开始累计的 Counter。因此快速发射 10 次后 Inspector 不一定显示 10：写入可能被多个 Tick 分批消费，而后续没有新写入的 Tick又会覆盖为 0。诊断 Queue 时应同时观察 Cell 是否产生、`ChangedCells` 是否变化、是否有 `RejectedWrites` 和 Console Error，而不能只盯一个瞬时字段。

## 5. World Space、有限 Bounds 与球形 Deposit 的数学

本次最重要的实际 Debug 结论是：系统并没有“固定一个命中坐标才能生成 Cell”，它固定的是有限 Grid 的 Origin 与 Bounds。`ElementFieldRuntime.Awake()` 把 `ElementFieldLabRoot.transform.position` 记录为 `origin`，并使用 Profile 的 `Dimensions = (32,16,32)` 和 `CellSize = 0.25m` 创建 Grid。世界坐标转换公式为：

```text
localPosition = worldPosition - origin
cell = floor(localPosition / cellSize)
```

当前覆盖范围为：

```text
sizeWorld = dimensions × cellSize
          = (32,16,32) × 0.25m
          = (8m,4m,8m)
```

合法 Cell 必须满足：

```text
0 ≤ x < 32
0 ≤ y < 16
0 ≤ z < 32
```

假设 Origin 是 `(0,0,0)`，命中点 `(4,0.5,4)` 会映射到 `(16,2,16)`；命中 `x = 8.1m` 会得到 `cell.x = floor(8.1/0.25) = 32`，已经越界。负坐标必须使用 `floor` 而不是 C# 强制转换：`-0.04/0.25 = -0.16` 应落在 `-1`，若直接 `(int)-0.16` 会截断为 0，把 Field 外的位置错误写进边缘 Cell。

半径写入不是只检查球心。Processor 先求球体的 Axis-Aligned Bounding Box：

```text
minCell = WorldToCellUnchecked(hitPoint - radius)
maxCell = WorldToCellUnchecked(hitPoint + radius)
```

再把 Min/Max Clamp 到 Grid Bounds。因此球心在边界附近、球体只有一部分进入 Field 时，Field 内的有效部分仍可以沉积；整个球与 Field 没有有效 Cell 时，`weightSum = 0`，写入安全失败。用户最初朝任意场景障碍物发射水球时 Projectile 正常消失、但没有蓝色 Cell，最后定位为命中点位于这个 `8m×4m×8m` 盒子之外，而不是 Prefab、Shader 或事件失效。随后在 Field 内测试，成功生成大量 Cell。这一经历说明 Debug 应先确认坐标协议和 Bounds，再怀疑 Rendering。

开启 Linear Falloff 时，每个候选 Cell 的权重为：

```text
d = distance(cellCenter, hitPoint)
w = clamp01(1 - d / radius)
```

圆心附近权重大，边缘趋近 0。`TotalAmount` 是整个命中球共享的总预算，不是每个 Cell 都获得该值。Processor 第一遍求 `weightSum`，第二遍按剩余量和剩余权重分配：

```text
share = round(remainingAmount × weight / remainingWeight)
```

最后一个有效 Cell 自动取得余数，从而保持总量守恒。Water 配置为 `TotalAmount = 220, Radius = 0.75m`；Fire 配置为 `180, 0.6m`。`TotalAmount` 使用 `ushort` 表示一次请求可携带比单 Cell 更大的总预算，而单个 `ElementCell.Amount` 是 `byte`，范围 `0～255`；大量 Amount 会在多个 Cell 之间分配，单 Cell 饱和时也不会溢出。

Fireball 打入 Water 时有两种可能的消耗路径。若 Fire Request 写入已装 Water 的同一 Cell，Write Stage 先按 `1:1` 即时抵消；如果 Fire 与 Water 位于相邻 Cell，后续 Reaction Stage 按 P2 Extinguish 规则继续等量消耗。用户截图中爆炸附近水面消失一片，说明 Fire Deposit 确实进入 Grid 并与既有 Water 发生了空间交互，但单看画面不能断言每个 Cell 走的是哪一条路径；需要结合 `ReactionPairs` 和命中位置判断。这是区分“可见结果”和“内部具体 Stage”的重要习惯。

当前 Field 只支持 Axis-Aligned、单位缩放的 Root，并在 `Awake()` 固定 Origin。进入 Play Mode 后直接移动 Root 不会自动迁移已经存在的 Cell。未来若要让 Field 跟随玩家，需要实现 Grid Recenter、旧 Cell 搬移或淘汰、Solid Mask 重烘焙、Chunk Dirty 更新以及跨边界 Projectile 策略，这本质上接近 Minecraft 的 Chunk Streaming；P6-A 选择固定局部实验房，是用可控内存和确定性换取快速完成可玩 Demo。

## 7. TDD、Play Mode Gate 与实际踩坑

自动化部分采用 TDD：在实现 Component 前先编写 `ElementDepositOnImpactTests`，RED 阶段因类型尚不存在得到预期编译失败；实现后，以下 5 个 NUnit Case 由用户在 Unity Test Runner 中确认通过：Water 正常快照 1 个、非法 Amount 两个 TestCase、负 Radius 1 个、无 Active Field 安全失败 1 个。测试重点放在最容易自动化且确定的 Request 边界；真实 Rigidbody Collision、Prefab Serialized Reference、Gizmo 和 Trigger 多订阅属于 Unity 对象集成，因此用 Play Mode Gate 验证，避免为了测试而重新实现一个假的 Physics 世界。

Play Mode 实测结果如下：

| Gate | 操作 | 实际通过标准与结论 |
|---|---|---|
| Water 命中 | Water Projectile 命中 Field 内部 | Projectile 消失，蓝色 Cell 出现、下落、在 Ground 摊开；`ChangedCells/WaterTransfers` 有变化。 |
| Fire 命中与反应 | 在 Water 区域发射现有 Fireball | 爆炸位置的 Water 消失一片，证明 Fire Deposit 与 Water/Fire 写入或 Reaction 链路贯通。 |
| Field 外安全路径 | 命中有限 Bounds 外的障碍物 | Projectile 生命周期正常结束，不在 Grid 边缘错误生成 Cell，Console 无 Error；这是安全拒绝，不是 Prefab 失效。 |
| Combat 隔离 | Water Projectile 命中无状态敌人 | BaseDamage 0，不扣血、不施加 Burning；若命中点在 Field 内仍产生 Water。Wet 暂时不出现，因为 Cell→Status Exposure 属于 Task 6。 |
| 快速连发 | Field 内连续快速发射约 10 个 Water Projectile | Queue 未被破坏，Projectile 均能完成命中和沉积，没有持续 Rejected、卡死或 Console Error。 |
| Trigger Payload | Wand 配置 TriggerFireball→Fireball，BaseDraws 1 | 首次命中沉积 Fire，Payload 后缀仍正常执行，说明 `Impacted` 的 Deposit 和 Trigger 两个 Subscriber 可以并存。 |

本 Task 的踩坑可以总结为以下诊断顺序：

1. **Projectile 消失但没有 Cell。** 最初容易怀疑水材质或 Prefab 未配置，实际根因是命中点在 Field Bounds 外。先确认 `ElementFieldLabRoot` 的 Origin、`8m×4m×8m` 范围和 hitPoint，再检查 Queue；Shader 不可能决定 Gameplay Cell 是否存在。
2. **Stats 在变化但看不见 Gizmo。** Task4 已确认过两个原因：`OnDrawGizmosSelected` 要求 Hierarchy 真正选中 Root；低 Amount 分散后需用 `MinimumActiveAlpha` 保证调试可见。这些诊断工具条件在真实 Projectile Gate 中仍然适用。
3. **Fire Amount 一度被设为 22626。** `_totalAmount` 使用 `[Range(1, ushort.MaxValue)]` 会在 Inspector 显示跨度极大的 Slider，初学者拖动时很容易产生巨量数值。最终 Prefab 已人工改回 180，`OnValidate` 和 `TryBuildRequest` 只保证不越过 `ushort`，不会判断“设计上是否合理”。后续可把 Inspector 表现改为 `[Min(1)]` + `OnValidate Clamp`，让用户直接输入数值；这属于 Authoring UX 改进，不改变 Runtime 公式。
4. **火出现后很快消失。** 需要区分 Profile 的 `FireDecayPerTick` 与 Reaction。此前加速测试使用 32 会在约 0.7 秒内清空 220 Amount；正式 Gate 已恢复较低值。诊断时先暂停自动 Tick，再用 `Step One Tick` 隔离 Write、Reaction 与 Decay。
5. **为什么水球没有 Wet。** 当前只完成 Projectile→Cell；角色读取 Cell 并调用 `StatusController` 是 Task6。水球不直接施加 Wet 反而证明职责边界正确，否则 Projectile 状态与环境状态会重复叠加。
6. **为什么 `ProcessedWrites` 发射后又变成 0。** 它是 Last Tick Snapshot；下一 Tick 没有 Request 时自然覆盖为 0。长期累计统计与单 Tick Profiling 指标用途不同，不能混用。

## 8. 面试理解与模拟完整讲解

面试官可能会问：“为什么不用继承写一个 WaterProjectile，再给 Fireball 重写一次？”回答的重点不是背诵“组合优于继承”，而是说明变化维度。Projectile 的飞行、碰撞、同队过滤和销毁是一条稳定轴；命中后是否沉积 Water/Fire、沉积多少、半径多大是另一条可组合轴。如果用继承表示两个正交维度，WaterTriggerProjectile、FireTriggerProjectile、PoisonHomingProjectile 等组合会形成 Class Explosion。当前把稳定生命周期留在 `ProjectileBase`，把环境写入放进 `ElementDepositOnImpact`，Prefab 组合两者，既复用现有 Fireball，也让普通 Arrow 完全不感知 ElementField。

面试官可能会继续问：“为什么不用 EventBus？”可以回答：`Impacted` 是一个具体 Projectile 实例的局部事件，Publisher 和 Subscriber 在同一 Prefab 生命周期内直接关联，使用 C# event 类型安全、路径短，也不需要全局过滤。`EventBus<T>` 更适合跨对象、跨场景且双方不直接持有引用的通知。架构原则不是所有通信都强制 EventBus，而是根据 Lifetime 和 Ownership 选择最小合适工具；同时通过 `OnEnable/OnDisable` 成对订阅，避免强引用造成幽灵回调。

面试官还可能问：“为什么命中不能直接改 Cell？”可以从确定性回答：Physics Collision 与 ElementField 的 10 Hz Fixed Simulation 属于两条时间线。直接写 Grid 会让写入顺序受 Player Loop 和帧率影响，还可能在 Double Buffer Stage 中途改变数据。我们把命中数据做成 Value Snapshot，进入固定容量 Ring Buffer，在每个 Simulation Tick 的 ApplyWrites Stage 统一消费。这样相同的请求顺序产生相同结果，Queue 没有热路径扩容，Projectile 即使已经 Destroy 也不影响后续处理。

如果要求从头到尾完整介绍，我会这样回答：

> 这个功能的目标是让现有 Wand 发射的水球和火球真正改变一个有限 3D 元素场，同时不让法术解释器、战斗投射物和环境模拟互相污染。我先复用 `ProjectileBase` 已有的 `Impacted` Seam：水球只增加一个空的具体 Projectile 类型来取得公共 Rigidbody 生命周期，再把环境行为拆成 `ElementDepositOnImpact` Component。它在 `OnEnable` 订阅命中、`OnDisable` 退订，命中时把 World Position、Material、总量、半径和 Falloff 封装成值类型 Request，只提交到 `ElementFieldRuntime` 的固定容量 Queue。
>
> 我没有在 Collision Callback 里直接改 Grid，因为 Physics 和环境场的 Tick Rate 不同。所有命中请求在下一次 10 Hz Tick 的 ApplyWrites Stage 按顺序消费，再执行 Reaction、Down Flow、Horizontal Flow 和 Fire Decay。球形写入先把世界坐标按 `floor((world-origin)/cellSize)` 量化成 Cell Bounds，按 `max(0,1-distance/radius)` 计算权重，把 TotalAmount 守恒分配给有效 Cell。Grid 是有限的 32×16×32、0.25 米，也就是 8×4×8 米；越界命中会安全拒绝，而不是在数组边缘凭空生成元素。
>
> 架构上由 `Game.ElementField` 依赖 `Game.Combat` 的 Projectile Contract，Combat 不反向引用 Field。Water 用新 Prefab 配置零伤害和 220 Amount，Fireball 只组合一个 180 Amount 的 Deposit，原爆炸与 Burning 都保留。因为 `Impacted` 是 multicast event，Trigger Payload 与 Deposit 可以同时订阅；实际 Gate 验证了 Trigger→Fireball 后缀仍能执行。自动化测试覆盖 Request 快照和非法参数，Play Mode 又覆盖了真实碰撞、越界、快速连发、无错误 Burning 与 Payload 兼容。
>
> 调试中我遇到过 Projectile 消失但没有 Cell，最后不是 Shader 问题，而是命中点在有限 Field 外；也遇到过低 Amount Gizmo 不可见和大范围 Slider 导致 Fire Amount 误设。这让我形成了从 `Spell Asset → Prefab → Impacted → Queue → Bounds → Stats → Gizmo` 逐层排查的顺序。当前结果已经完成 Projectile→Environment，下一步是反向的 Environment→Status Exposure，让角色站入 Cell 后获得 Wet/Burning，形成真正的双向 Gameplay 闭环。

# Task 6：让 Cell 反向施加 Wet/Burning，并处理持续来源与自然衰减

Task 6 的目标，是补齐 P6-A 最关键的第二条方向：Task 5 已经实现“法术改变环境”，本 Task 再实现“环境改变角色”。最终玩家可以把 Water Projectile 打到地面形成 Water Cell，角色站进去后逐渐获得 Wet；Fireball 留下 Fire Cell 后，角色或敌人进入区域会获得 Burning 和已有 DoT；带 Burning 进入 Water 时，P2 的 Extinguish 仍会连续消耗双方。实现中没有给每个 Cell 创建 `GameObject` 或 `Trigger`，而是由一个 `ElementFieldExposureSystem` 每 `0.25s` 对整个有限 Field 做一次集中 `Physics.OverlapBoxNonAlloc`，再把候选 Collider 的 `Bounds` 换算成 Cell 范围并读取最大 Amount。实际 Gate 又暴露出第二层问题：Exposure 是 `4 Hz` 离散补充，`NaturalDecay` 却在每个 Rendering Frame 执行，低浓度 Water 的补充可能在两次采样之间被衰减抵消。为此本 Task 增加显式 `ApplySustainedStatus` 与帧率无关的 Hold Timer：持续来源存在时只暂停普通自然衰减，Reaction 与 DoT 仍正常运行；离开来源并经过短暂 Grace 后，原有衰减自动恢复。最终用户确认 Test Runner 全部通过，Water/Fire、Extinguish、Enemy Exposure 以及“站在水中不再越叠越低”的 Play Mode Gate 均通过，P6 的双向 Gameplay 闭环已经成立。

## 1. 从玩家看到的结果倒推完整运行链路

玩家看到角色站进水里后 Wet Icon 出现并逐渐上升，背后并不是水 Shader 在检测角色。Shader 只负责画面，不拥有 Gameplay Amount；真正的数据源仍是 `ElementGrid`。运行链路如下：

```text
Water/Fire Projectile 命中
→ ElementDepositOnImpact 入队
→ ElementField 固定 Tick 写入并模拟 Cell
→ ElementFieldExposureSystem 每 0.25s 查询角色 Collider
→ Collider.bounds 映射为离散 Cell 范围
→ 读取覆盖范围内最大 Water/Fire Amount
→ ApplySustainedStatus(Wet/Burning)
→ StatusController 处理强度、Reaction、DoT、NaturalDecay 与 EventBus
→ UI / Rendering 监听 StatusChangedEvent 更新 Icon 和角色材质
```

这条链路体现了 Gameplay 与 Presentation 分离：蓝色 Cell Gizmo 可以关闭，未来也会被连续 Water Mesh 取代，但 Wet 的计算结果不会改变；反过来，即使 Water Shader 很漂亮，只要对应位置没有 Water Cell，角色也不会获得 Wet。`Game.ElementField` 可以依赖 `Game.Combat` 的 `StatusController`，而 `Game.Combat` 不反向知道 Grid，这符合项目既定的单向程序集依赖。UI 与 Rendering 仍只通过状态事件读取结果，不修改 Cell 或状态。

## 2. 集中 Physics Query、Collider 去重与 Bounds→Cell 数学

最直接但不可采用的做法，是给 16,384 个 Cell 各建一个 Trigger。这样会产生同数量的 `GameObject`、`Transform`、Collider 和 Broadphase Proxy，既浪费内存，也把大量进入/离开事件交给 Physics Engine。另一个方案是每个角色每帧扫描 Grid，但角色数量增加后会重复执行相同的空间范围判断。本项目选择“一个 Field、一个低频集中查询”：

```text
fieldSize = Dimensions × CellSize
queryCenter = Origin + fieldSize × 0.5
halfExtents = fieldSize × 0.5
```

`Physics.OverlapBoxNonAlloc` 使用上述 World Space AABB、`Target Layers` 和预分配的 `Collider[64]`，只找可能处于 Field 内的 Player/Enemy Collider。`NonAlloc` 表示 Unity 把结果写入调用方提供的数组，不为每次查询创建新数组；固定容量也是明确的性能预算，超过 64 个候选时本轮会截断，而不是在热路径扩容。`QueryTriggerInteraction.Collide` 允许角色的 Trigger Hitbox 也进入候选，随后通过 `GetComponentInParent<StatusController>()` 找到真正的状态载体。

一个角色可能有 CharacterController、受击 Collider、攻击 Trigger 等多个 Collider。若按 Collider 直接 Apply，同一角色一次 Exposure 可能叠加多次。系统因此使用预分配的 `_targetIds` 与 `_targets` 做线性去重，以 `StatusController` 所在 GameObject 的 `InstanceID` 为身份。最多只有 64 个候选时，简单线性查找比每 Tick 建立或清理 `Dictionary` 更容易保持零 `GC Alloc`，也没有 Hash 容器扩容风险。

Broadphase 只回答“谁可能在 Field 里”，还必须把每个 Collider 的 World Space `Bounds` 精确换算为 Cell 范围。先做 AABB 相交判断：

```text
outside = bounds.max <= field.min 或 bounds.min >= field.max
sampleMin = max(bounds.min, field.min)
sampleMax = min(bounds.max, field.max)
cellMin = floor((sampleMin - Origin) / CellSize)
cellMax = floor((sampleMax - ε - Origin) / CellSize)
```

这里的 `ε` 是很小的 inset。如果 `Bounds.max` 恰好落在两个 Cell 的公共边界，下一格只是“接触边界”而没有实际体积重叠；不减 `ε` 会错误多采样一层。计算结果还会 Clamp 到 `[0, Dimensions-1]`，避免越界索引。随后遍历这个很小的局部 Cell Box，分别保留 Water 与 Fire 的最大 Amount。选择最大值而不是平均值，是因为角色 Collider 可能同时覆盖大量 Empty Cell；平均会把脚下真实踩中的一格高浓度火焰严重稀释。最大值语义可以理解为“角色当前接触到的最强局部元素”。

状态施加公式为：

```text
normalizedAmount = CellAmount / 255
appliedStatus = MaxApplyPerExposure × normalizedAmount
```

`CellAmount` 是 `byte`，范围为 `0～255`；`Max Wet/Burning Apply Per Tick = 10` 时，满 Cell 每次增加 10 点状态，Amount=128 时约增加 `10 × 128/255 ≈ 5.02`。环境没有角色攻击者，因此来源使用 Field Root 的稳定 `InstanceID`，Team 使用 `byte.MaxValue`。这仍是一个 Value Snapshot，不让状态长期持有场景对象引用。

## 3. 为什么最初只有大量水才出现 Wet：Amount、采样频率与 UI 阈值

首次 Play Mode Gate 中，单发 Water Projectile 形成了肉眼可见的蓝色 Cell，但 Wet Icon 不出现；多发水球后 Icon 才出现，却经常显示 `0%`。这不是 Prefab 或 Shader 没有接入状态，而是三层数值共同造成的结果。第一，原 `TotalAmount = 220` 会经球形 Linear Falloff 和后续 Flow 分散到许多 Cell，角色脚下单格 Amount 很低。第二，Exposure 每 `0.25s` 才施加一次，单次增长是 `10 × Amount/255`；例如 Amount=13 时仅增长约 `0.51`。第三，Wet 的 `NaturalDecayPerSecond = 8`，在下一个 `0.25s` 内理论上会下降 `8 × 0.25 = 2`。于是低浓度来源每次增加约 0.51、间隔中却减少约 2，状态会回到零；UI 又按整数百分比刷新，因此表现为不显示或短暂 `0%`。

把 Water Projectile 的 `TotalAmount` 从 220 调到 1600，解决的是“单发法术落地后局部 Cell 浓度不足”的内容调参问题，使一个水球足以形成有意义的水洼。但只提高 Amount 不能从架构上解决所有持续来源：浅水、弱火、未来毒雾仍可能遇到低频补充与逐帧衰减的时间尺度冲突。因此我们没有继续无限提高法术 Amount，也没有全局降低 Wet 衰减，而是增加了对“来源仍持续存在”的明确表达。

## 4. Sustained Hold：只暂停 NaturalDecay，不暂停 Reaction 与 DoT

普通 `ApplyStatus` 表示一次性施加，例如 Fireball 直接命中后给目标添加 Burning；`ApplySustainedStatus` 表示来源会周期性续杯，例如角色持续站在 Water Cell 或 `StatusVolume` 中。两者共用 `ApplyStatusInternal`，因此 Clamp、来源归因、DoT Timer、Reaction Dirty、VFX 和事件发布没有复制两套逻辑。区别只是持续入口会刷新 `StatusInstance.NaturalDecayHoldRemaining`：

```text
HoldRemaining = max(oldHold, applicationInterval + grace)
```

这里使用 `max` 而不是相加。若每次 Exposure 都累加 0.35 秒，角色站得越久，离开后可能积累几十秒免衰减；刷新则只表达“最近一次确认仍在来源中”，不会形成时间债务。当前 Exposure Interval 为 0.25 秒、Grace 为 0.10 秒，所以每次续杯把 Hold 刷新到 0.35 秒。Grace 用于覆盖帧边界、Physics 同步和离散采样的轻微误差，并不会继续增加状态。

Hold 在每帧采用分段积分，而不是简单写成 `if (hold > 0) return`：

```text
heldTime = min(HoldRemaining, deltaTime)
HoldRemaining = max(0, HoldRemaining - heldTime)
decayDeltaTime = deltaTime - heldTime
Intensity = max(0, Intensity - NaturalDecayPerSecond × decayDeltaTime)
```

假设剩余 Hold 为 0.10 秒，本帧或测试步长为 0.20 秒，则前 0.10 秒免衰减、后 0.10 秒正常衰减。这样结果与帧率无关，不会因为 30 FPS 与 144 FPS 在 Hold 到期边界上整帧多免或多扣。Intensity 归零时清空 Hold，防止未来重新激活时继承旧计时。

必须强调：Hold 只控制 `NaturalDecay`。`StatusController.Tick` 仍先运行 `ElementReactionRuntime`、应用 Reaction Frame，再运行普通衰减；Extinguish、WetCleanse、ToxicCombustion、IgniteGoo 的 Delta 不读取 Hold，Burning/Poison DoT Timer 也继续推进。因此“带 Burning 进入 Water”不会因为双方都来自持续环境就冻结，而是仍按 P2 规则平滑中和。普通 Fireball 继续调用 `ApplyStatus`，不会创建新 Hold，所以离开环境后的一次性 Burning 仍按旧规则立即自然衰减。

用户观察到修改后站在水中“最差几乎不提升，但不会降低”，这是符合设计的结果。Hold 不会凭空制造 Wet，只是移除不合理的间隔内反向衰减；实际净增长仍由 Water Cell Amount 决定。浅水可以近似持平或缓慢增长，深水增长更快，保留了环境浓度的 Gameplay 差异。

## 6. 测试、Editor Gate、踩坑与系统化 Debug

Task 6 首轮先编写六类 Exposure 测试：Water/Fire 按 Amount 比例施加、Empty 不施加、多 Collider 只施加一次、覆盖多格取最大强度、Field 外目标忽略。测试最初共同失败并不是业务公式错误，而是 EditMode 下 `AddComponent + SetActive` 不保证按 PlayMode 时间线自动调用普通 `Awake`；夹具随后显式执行 Runtime 初始化与 Exposure `Awake`，把“Unity 生命周期前提”与“Exposure 业务断言”分开。之后用户确认六项全部通过。

Task6A 又增加三类 Combat 核心测试与两类集成测试：Hold 到期分段衰减、重复刷新不累加、Hold 不阻断 Reaction；真实 ElementField 重复 Exposure 后离场恢复；StatusVolume 接触与离场使用同一契约。实现前的 RED 编译得到缺少 `ApplySustainedStatus` 的预期错误；实现后 `Game.Combat.Tests.csproj` 与 `Game.ElementField.Tests.csproj` 均为 `0 warning / 0 error`。热路径扫描没有发现 LINQ、`Debug.Log`、legacy `Input` 或逐 Tick 托管分配。最终用户在 Unity Test Runner 中确认全部测试通过，并完成 Play Mode Gate。

本次 Debug 形成了下面的排查顺序：

```text
ChangedCells/WaterTransfers 是否变化
→ 角色 Collider 是否真的位于 Field Bounds
→ Target Layers 是否包含 Collider 所在 Layer
→ Last Collider Count / Last Status Target Count 是否大于 0
→ Last Maximum Water/Fire Amount 是否大于 0
→ Last Wet/Burning Application Count 是否变化
→ StatusController 是否配置对应 StatusDefinition 与 ReactionProfile
→ UI 是否收到非零整数百分比事件
```

几个典型症状可以快速定位：看得到 Cell 但所有 Exposure Debug Count 为零，优先检查 `Target Layers` 和 Collider Layer；Collider Count 有值但 Status Target Count 为零，检查 Collider 的父级是否有启用的 `StatusController`；Application Count 有值但 Icon 不出现，检查脚下最大 Amount、单次换算值、StatusDefinition 与 UI 整数显示；多发水球才有 Wet，检查 Projectile `TotalAmount` 是否被半径和 Flow 过度稀释；站在来源中仍下降，则比较 `applicationInterval`、`NaturalDecayPerSecond` 与 Hold Grace，而不是先怀疑 Shader。

性能方面，Exposure 是 `4 Hz` 而非每帧执行，所有查询和去重容器均预分配；`ProfilerMarker` 允许在后续 Task 9 中单独查看 `ElementField.Exposure` CPU 与 `GC Alloc`。当前固定 64 候选是 P6-A 实验房预算，不是无限场景承诺；若未来同一 Field 内目标远超 64，应采用空间分区、分批查询或提高经过 Profiler 证明的容量，而不是悄悄改成每帧动态集合。

## 7. 面试时如何完整讲述 Task 6

面试时我会先从闭环目标讲起：我做的不是单独一块水 Shader，而是一套有限三维元素场。法术命中先写入紧凑 Cell，Task 6 再让 Cell 反向影响角色。为了避免每个 Cell 一个 Collider，我在 Field 级别每 0.25 秒做一次 `Physics.OverlapBoxNonAlloc` Broadphase，用预分配数组接收候选 Collider；再把每个 Collider 的 AABB 从 World Space 换算成 Cell Min/Max，只遍历角色实际覆盖的小范围，并分别取最大 Water/Fire Amount。一个角色可能有多个 Collider，所以我按 `StatusController InstanceID` 去重。最后用 `statusApply = maxApply × amount/255` 映射为 Wet 或 Burning，并把 Field InstanceID 作为环境来源快照。

实际测试时我发现一个时间尺度问题：Exposure 是 4 Hz，状态自然衰减却是每帧积分。低浓度水每次增加可能小于 0.25 秒内的衰减，因此角色明明一直站在水里，Wet 仍会下降甚至闪成 0%。我没有简单降低全局衰减，也没有让所有 Apply 自动免衰减，因为那会改变一次性 Fireball 的语义。我给 `StatusController` 增加了显式 `ApplySustainedStatus`，让周期性来源刷新一个 `interval + grace` 的 Hold。Hold 用 `min(remaining, deltaTime)` 把一帧拆成受保护与正常衰减两段，保证帧率无关；重复来源取 `max` 而不是累加，避免离场后欠下很长免衰减时间。它只暂停 NaturalDecay，Reaction 与 DoT 仍照常执行，所以 Burning 进入 Water 仍能 Extinguish。

验证上，我先用纯状态测试锁定 Hold 的到期公式、刷新语义和 Reaction 优先级，再用真实 Physics、ElementFieldRuntime 与 StatusController 做集成测试，覆盖 Bounds、多 Collider、越界和离场恢复。Play Mode 中又验证了玩家、敌人、Water、Fire、Extinguish 和普通一次性来源。这个实现的核心取舍是：用有限范围、固定容量和 4 Hz 采样换取可控 CPU/GC；用 Amount 保留浓度差异；用显式 Sustained API 区分“持续接触”和“一次命中”，而不是把所有状态来源粗暴地写成同一套规则。

# Task 7：把离散 Water Cell 聚合为连续 Chunk Mesh，并修复流动拓扑振荡

Task 7 的目的，是把前六个 Task 中“确实存在、能够流动和发生反应，但只能用调试小方块看见”的 Water Gameplay 数据，转换成玩家真正能看到的水面。最终结果不是给每个 Cell 套一个水材质，也不是让 Shader 自己决定哪里有水，而是建立一条职责清晰的数据链：`ElementFieldSimulator` 决定每个 Cell 的 `MaterialKind/Amount`；`WaterChunkMeshBuilder` 只读这些数据，提取顶面和外露侧面，生成 `Vertex/UV/Index`；`ElementWaterRenderer` 按 Chunk 管理 Unity `Mesh`、Dirty Version、重建预算和生命周期；此前亲手编写的 `ElementWater.shader` 再负责波纹、法线扰动、深度颜色、`Fresnel`、泡沫、透明混合等像素级表现。这样，Cell 仍然是低成本的 Gameplay 规则网格，而连续水面只是其 Presentation，不会反向污染模拟。Task Gate 还暴露了一个非常有价值的问题：流动区域出现规则棋盘格闪烁。排查证明 Renderer 并没有“随机画错”，而是旧水平扩散在四邻域上过量输出，使 Cell 在相邻 Tick 间反复 `Water ↔ Empty`；最终通过具有阻尼的 `/8` 四邻域传输公式修复。这个过程把 Mesh 生成、实时渲染、离散模拟、数值稳定性和系统化 Debug 串成了一次完整的客户端开发实践。

## 1. 从最终画面逆向拆解：一片水面实际上经过了哪些层

从结果倒推，一片会扩散、会被火球消耗、表面还带波纹的水，需要同时回答四个不同问题：

```text
Gameplay：这里是否有水？有多少？下一 Tick 流向哪里？
    ↓ IElementFieldReadOnly + Chunk Version
Geometry：哪些表面暴露在空气中？顶点放在哪里？三角形怎样连接？
    ↓ Position / UV / Index / Normal / Tangent
Rendering：这些三角形怎样被光照、着色、透明混合并显示成水？
    ↓ MeshRenderer + shared Material + ElementWater.shader
Scheduling：哪些 Chunk 发生变化？这一帧最多允许重建几个？
```

这四个问题不能混成一个脚本。若 Shader 直接承担 Gameplay，它只能根据屏幕像素做近似，不能可靠支持流动、守恒、灭火和角色 Wet；若 Gameplay 直接引用 `MeshRenderer`，`Game.ElementField` 就会依赖 Presentation，破坏单向架构；若每个 Cell 都创建一个 `GameObject + MeshRenderer`，16,384 个 Cell 会带来大量 Transform、Component、Culling 和 Draw Call 开销。因此当前方案采用“紧凑 Cell 负责规则，Chunk Mesh 负责几何，一个 Material 负责精细视觉”。

本实现的架构方向是：

```text
Game.ElementField
  ElementGrid / ElementFieldSimulator / ElementFieldRuntime
             │ 只读契约 IElementFieldReadOnly
             ▼
Game.Rendering
  WaterChunkMeshBuilder（纯几何转换）
             ▼
  ElementWaterRenderer（Mesh 生命周期与预算）
             ▼
  MeshFilter + MeshRenderer + M_ElementWater_Handwritten
             ▼
  ElementWater.shader（Vertex/Fragment GPU Pipeline）
```

这里的关键边界是“Rendering 可以读取 Gameplay，但不能写回 Gameplay”。`ElementWaterRenderer` 保存的是 `IElementFieldReadOnly`，不能调用 Deposit、Flow 或 Reaction；即使关闭 Renderer，水仍会在模拟中存在、流动、施加 Wet。反过来，即使换掉 Shader，Water Cell 的守恒和灭火规则也不会改变。这就是 Gameplay Model 与 Presentation 解耦的价值。

## 2. Mesh 基础：Vertex、Triangle、Index、Winding、Normal、Tangent 与 UV

### Vertex 与 Triangle

GPU 最终不是直接绘制“水”或“正方形”，而是 `Rasterization` 三角形。一个 `Vertex`（顶点）至少包含 Position，表示几何位置；还可以携带 UV、Normal、Tangent、Color 等属性。三个顶点组成一个 `Triangle`，两个 Triangle 组成一个 `Quad`：

```text
D ───── C
│     ／│
│   ／  │
│ ／    │
A ───── B

Triangle 0：A → B → C
Triangle 1：A → C → D
```

代码没有为每个 Triangle 重复写三份 Position，而是先将四个顶点写入 Vertex Buffer，再向 Index Buffer 写入六个整数：

```text
indices = [0, 1, 2, 0, 2, 3]
```

Index 的意思是“第几个顶点”，它决定连接关系。当前 Builder 为每个 Quad 保留独立的四个顶点，这会比全局共享顶点占用更多 Vertex，但有两个实际好处：不同面可以拥有独立 UV，`RecalculateNormals()` 也会得到清晰的 `Flat Normal`，不会把水平顶面与竖直侧壁错误平滑成圆角。P6-A 的 Chunk 很小，这个可理解性与可靠性优先于极致顶点压缩。

### Winding 与面朝向

`Winding Order` 是 Triangle 顶点绕序。可以用叉积求几何法线：

```text
e1 = B - A
e2 = C - A
N  = normalize(cross(e1, e2))
```

`cross`（叉积）得到同时垂直于 `e1/e2` 的向量，方向遵循右手定则。顶面必须让 `N.y > 0`；否则启用 `Cull Back` 后，摄像机从上面看可能发现整个水面被当成 Back Face 剔除。`SingleFullWaterCellCreatesTopAndExposedSides` 不只统计数量，也直接用上述公式检查顶面法线朝 `+Y`，这是“测试图形学不变量”，而不是只测某个实现细节。

### Normal、Tangent 与 TBN

`Normal` 表示表面朝向，是光照中 `N·L`、`N·V` 等计算的基础。`Tangent` 表示 UV 的 U 方向在三维表面上的方向；`Bitangent` 通常由 `cross(N,T)` 结合 handedness 得到。三者构成把 `Tangent Space` 法线转换到 `World Space` 的 `TBN Matrix`：

```text
TBN = [ T  B  N ]
N_world = normalize(TBN × N_tangent)
```

本 Task 只向 Mesh 上传 Position 和 UV，然后调用 `Mesh.RecalculateNormals()` 与 `Mesh.RecalculateTangents()`。前者根据 Triangle 几何求 Normal；后者根据 Position、UV、Normal 建立 Tangent。自研 Water Shader 才能据此把程序噪声生成的切线空间法线正确旋转到世界空间。若没有 Tangent，水纹法线可能随模型方向错误旋转，光照会显得粘在屏幕或空间方向不一致。

### UV 与连续纹理坐标

UV 是二维表面参数，不等同于 World Position。Shader 用 UV 采样或计算噪声：相同 UV 应对应相同纹理位置。如果每个 Cell 顶面都从 `(0,0)` 重置到 `(1,1)`，每隔 `0.25m` 就会重新开始一遍 Noise，Cell 边界会清晰可见。Builder 因此使用全局 Cell 坐标：第 `x,z` 格顶面的四角是 `(x,z)`、`(x,z+1)`、`(x+1,z+1)`、`(x+1,z)`。相邻 Cell 的公共边界得到相同 UV，跨 Chunk 也不会因为 Local Position 归零而断裂。`UvIsContinuousAcrossCellBoundary` 专门锁定这一点。

需要区分三种空间：Cell Coordinate 是整数网格坐标；Chunk Local Space 是顶点相对 Chunk 原点的位置；World Space 是最终场景位置。其关系为：

```text
chunkWorldSize = chunkSize × cellSize
chunkWorldOrigin = fieldOrigin + chunkCoordinate × chunkWorldSize
vertexWorld = chunkWorldOrigin + vertexChunkLocal
```

以当前 `chunkSize=8`、`cellSize=0.25m` 为例，一个 Chunk 边长是 `2m`。Mesh 顶点只需记录相对该 2m 区域的 Local Position，而 Chunk Transform 被放到真实 World Origin。这样数值小、定位清晰，也便于整块重建与剔除。

## 3. 从 Cell Amount 构建可见水面：高度、顶面与外露侧壁

`WaterChunkMeshBuilder.Build(...)` 是一个纯转换函数：输入只读 Field、Chunk Coordinate 与可复用 List，输出 Position、UV、Index。它不创建 `GameObject`、`Mesh`、Material，也不修改 Cell，因此可以用 NUnit 和 Fake Field 独立验证。

### Amount 如何变成水面高度

每个 Water Cell 的 `Amount` 是 `byte`，范围 `[0,255]`。本阶段用线性映射把存量转换成 Cell 内的填充比例：

```text
fillRatio = amount / 255
surfaceY = cellBottomY + cellSize × fillRatio
```

例如 `cellSize=0.25m`，`Amount=255` 时顶面位于 Cell 顶部；`Amount≈128` 时顶面位于约 `0.125m` 高。这里的 `surfaceY` 是 Chunk Local Space。这个公式不会声称模拟真实液体体积曲面，它只是让离散存量具有直观的几何反馈：水越多，格内可见高度越高。

### 为什么只生成可见表面

一个孤立 Water Cell 最多需要 `1 Top + 4 Side = 5 Quads`，不生成 Bottom，因为底面通常贴着地面、上层 Solid 或另一格水，对玩家不可见。顶面仅在 `(x,y+1,z)` 没有 Water 时生成；相同高度的水平邻居之间不生成内部 Side；邻居更低时，只补出两者 `surfaceY` 之间的高度差，不从 Cell 底部生成一整面重叠水墙。

这叫 `Surface Extraction`：从体素/Cell 占用数据中只提取边界。对两个相邻满水格，如果逐格无脑生成六面，会产生两个重叠内部面，浪费 Triangle，还可能出现 `Z-fighting`；剔除接触面后只留下外轮廓。当前算法是规则网格的 Block Surface Meshing，不是 `Marching Cubes`。它保留台阶状轮廓，优点是算法简单、Topology 可预测、容易测试；缺点是斜面与弧形边界不如 Marching Cubes 平滑。

六个 Builder 测试分别回答：孤立 Cell 是否得到 5 Quads；相邻同高 Water 是否去掉内部面；半 Amount 高度是否正确；UV 是否连续；Empty/Solid 是否不产水面；高低水位相邻时是否只生成高度差侧壁。测试关注的是几何不变量，而不是依赖 Scene、Camera 或 Material 的截图结果。

## 4. Chunk、Dirty Version 与每帧预算：为什么不每帧重建整个世界

当前实验场是 `32 × 16 × 32 = 16,384 Cell`，Chunk Size 为 8，因此 Chunk 数为：

```text
ceil(32/8) × ceil(16/8) × ceil(32/8)
= 4 × 2 × 4
= 32 Chunks
```

如果每个 Simulation Tick 都遍历 16,384 Cell 并上传整个水面 Mesh，即使只有一个火球改变了很小区域，也会重复处理大量不变数据。Task 3 已为 Chunk 维护 `Version`：当 Chunk 内 Cell 改变时 Version 增加；Renderer 保存 `currentVersions[]` 与 `lastSeenVersions[]`，二者不同才说明该 Chunk 是 Dirty。

但 Dirty 检测还不够。一次范围 Deposit 可能让许多 Chunk 同时变化，若同一帧全部重建，会形成 CPU 峰值和 Mesh Upload 峰值。`WaterChunkRebuildScheduler.SelectDirtyChunks` 因此接受 `maxRebuilds`，默认一帧最多选择 4 个 Dirty Chunk。它还保存环形 `_nextScanIndex`：下一帧从上次停止的位置继续扫描，防止数组前部的高频 Chunk 永远抢占预算，让后部 Chunk发生 `Starvation`。调度公式可以理解为：

```text
dirty(i) = currentVersion(i) != lastSeenVersion(i)
selectedCount ≤ min(maxRebuilds, selectedBufferLength)
```

只有 Mesh 成功上传后才执行：

```text
lastSeenVersion[i] = currentVersion[i]
```

这个顺序很重要：如果先确认 Version、后重建却抛错，Renderer 会误以为自己已经同步，修复代码后也不会自动重试。

`ElementWaterRenderer.Start()` 在 `ElementFieldRuntime.Awake()` 之后初始化，避免不同 GameObject 的 `Awake` 顺序依赖。它一次性为 32 个 Chunk 创建 `GameObject + MeshFilter + MeshRenderer + Mesh`，并给每个 Chunk 预分配三个 List。一个 8³ Chunk 有 512 Cell，按最坏 5 Quads/Cell 估算：

```text
vertexCapacity = 512 × 5 × 4 = 10,240
indexCapacity  = 512 × 5 × 6 = 15,360
```

这些是 Capacity 上界，不代表每个 Chunk 实际永远有这么多元素。重建时 `List.Clear()` 只把 Count 归零，保留内部数组；`Mesh.Clear(false)` 清除旧几何；随后使用 `SetVertices/SetUVs/SetTriangles` 上传新数据。这样避免在 `Update()` 热路径反复 `new List`、`new Mesh` 或 LINQ。`Mesh.MarkDynamic()` 告诉 Unity 该 Mesh 预计频繁更新；`IndexFormat.UInt16/UInt32` 根据最大顶点数选择；空 Chunk 直接关闭 `MeshRenderer.enabled`；运行时创建的 Native Mesh 在 `OnDestroy()` 中显式 `Destroy`，避免 Engine Object 泄漏。

所有 Chunk 使用 `sharedMaterial`，而不是 `renderer.material`。后者会为每个 Renderer 隐式克隆 Material，增加内存、让统一调参困难，并削弱合批机会。关闭 `shadowCastingMode` 与 `receiveShadows` 是当前透明水面的性能与视觉取舍。`ProfilerMarker("ElementWater.RebuildChunk")` 已预埋，Task 9 将用 Profiler 验证 CPU 与 `GC Alloc`，当前文档不把尚未取得的性能截图写成已完成证据。

## 5. Mesh 与自研 Water Shader 怎样接力完成最终视觉

Mesh 解决“哪里有表面”，Shader 解决“表面看起来是什么”。`MeshFilter` 把 Mesh 交给渲染管线，`MeshRenderer` 提供 Material 和 Renderer 状态，Material 保存 `ElementWater.shader` 的参数。一次 Draw Call 中，Vertex Shader 逐顶点处理 Position、UV、Normal、Tangent，`Rasterizer` 把三角形覆盖的区域离散成 Fragment；Fragment Shader 再逐像素计算颜色、法线、深度、反射边缘和 Alpha。

本 Task 没有重新购买或引入“一滩水”Prefab，也没有复制 Shader Graph。它复用此前亲手编写的 `ElementWater.shader` 与 `M_ElementWater_Handwritten`。Builder 提供的连续 UV 进入两组移动 Noise：

```text
uvA(t) = uv × scaleA + speedA × time
uvB(t) = uv × scaleB + speedB × time
noise  = combine(noiseA(uvA), noiseB(uvB))
```

两组不同尺度、方向和速度的 Noise 能减弱单一纹理重复感；Noise 经高度导数或法线近似转成 `Tangent Space` 扰动，再由 TBN 变换到 World Space。光照常用点积衡量夹角：

```text
NdotL = saturate(dot(N, L))
```

当 Normal 与 Light Direction 同向时点积接近 1，表面更亮；垂直时接近 0。`Fresnel` 用视线与法线的夹角增强掠射角反光：

```text
F = pow(1 - saturate(dot(N, V)), FresnelPower)
```

正视水面时 `N·V` 较大，F 较小；视线接近平行于表面时 `N·V` 较小，F 增大，因此边缘更亮。深浅颜色依据水面到场景几何的 Eye Depth 差近似厚度：

```text
thickness = max(sceneEyeDepth - waterSurfaceEyeDepth, 0)
depth01   = saturate(thickness / DepthFadeDistance)
color     = lerp(ShallowColor, DeepColor, depth01)
```

这里的 `Scene Depth` 来自相机 Depth Texture，表示水面后方已渲染不透明物体的深度。它不是对真实水体做 Ray Marching，而是屏幕空间近似，因此成本可控但存在屏幕边缘、透明物体和相机遮挡限制。接触泡沫则反过来使用小厚度区域：

```text
foam = 1 - saturate(thickness / FoamDistance)
```

水面与地形交界越近，thickness 越小，foam 越接近 1。

透明混合采用常规 `Alpha Blend`：

```text
C_out = C_water × alpha + C_background × (1 - alpha)
```

Shader Render State 为 `Blend SrcAlpha OneMinusSrcAlpha`、`ZWrite Off`、`ZTest LEqual`、`Cull Back`。`ZWrite Off` 避免水先写入 Depth 后把后续透明层完全挡住，但也意味着透明物体必须依赖排序；多个 Chunk 互相交叠时，Unity 通常按 Renderer 粗粒度排序而不是逐 Triangle 排序，某些角度可能出现透明顺序问题。`OIT`（Order-Independent Transparency）、Depth Prepass 或合并更大透明 Mesh 都是后续方案，但 P6-A 先记录限制，不为实验房过度设计。

还要注意：当前每个 Quad 使用独立 Vertex，`RecalculateNormals()` 产生 Flat Normal，因此相邻不同高度顶面/侧壁保留硬边。动态法线 Noise 会从视觉上弱化部分方块感，但不会从几何上真正变成光滑曲面。未来如果台阶仍明显，可以评估共享顶点平滑、顶点高度邻域滤波、`Marching Cubes`/`Surface Nets`，或仅对 Presentation 做时间插值；每种方法都会增加 Topology、法线连续性或更新成本。

## 6. 棋盘格闪烁的系统化 Debug：从错误假设到数值稳定性

### 先区分“Shader 闪烁”和“Topology 闪烁”

最初现象是：稳定区域看起来像正常水面，正在扩散的前沿则出现大量方格交替闪烁。因为画面使用透明 Shader，第一直觉很容易怀疑 Alpha、Noise、Depth Texture 或 `Z-fighting`。但规则棋盘状、严格贴合 Cell、只在流动时出现，是一个重要线索：它更像 Mesh Topology 在生成与删除，而不是连续 Noise 在变化。

正确的排查层次是：

```text
1. Cell：同一坐标在相邻 Tick 的 MaterialKind/Amount 是否振荡？
2. Builder：对同一个固定 Snapshot，输出 Vertex/Index 是否确定？
3. Renderer：没有 Version 变化时是否仍重建？重建空 Mesh 是否正确禁用？
4. Shader：把动态 Noise 暂停后，几何缺口是否仍存在？
5. Camera/Depth：缺口是否只随视角变化？是否存在共面 Z-fighting？
```

Builder 的纯测试与稳定区表现说明相同 Snapshot 会生成确定 Mesh；同时棋盘格与流动 Tick 同步，最后把根因缩小到 Simulation。旧水平传输对每一条边使用近似：

```text
transferPerEdge = (sourceAmount - targetAmount) / 2
```

这在只看一对 Cell 时像是在快速取平均，但二维网格的一个中心 Cell 最多有四个水平邻居。假设中心 Amount 为 64、四邻居都为 0，且每条边上限允许 16：中心会向每个方向发 16，总输出为 64，一个 Tick 后中心直接 Empty；下一 Tick 周围又可能向中心回流，于是奇数 Tick 与偶数 Tick 出现相反棋盘。Renderer 每次看到 MaterialKind 从 Water 变 Empty，就删除该格 Top；下一个 Tick 又重新生成，所以画面“闪”其实是对不稳定模拟的忠实显示。

### 用离散扩散理解稳定性

连续扩散方程可写作：

```text
∂u/∂t = D ∇²u
```

其中 `u` 可理解为浓度/水量，`D` 是扩散系数，`∇²`（Laplacian）衡量当前位置相对邻域平均的差。规则二维四邻域的显式离散形式可近似写成：

```text
u_i^(n+1) = u_i^n + k × Σ(u_j^n - u_i^n)
```

`n` 是 Tick，`j` 遍历四邻居，`k` 把时间步长、空间步长和扩散系数综合起来。对标准二维四邻域显式扩散，稳定性通常要求 `k ≤ 1/4`；在最高频的黑白棋盘模式上，`k=1/4` 仍可能得到符号翻转而缺少阻尼。这里不声称当前 Water Solver 是严格求解 Navier–Stokes；这个公式的作用，是提供“一个 Cell 同时连接四条边时，单边系数不能只按一维配对理解”的稳定性指导。

最终将单边水平传输集中为 Pure Function：

```text
difference = max(sourceAmount - targetAmount, 0)
transfer   = min(MaxLateralFlowPerTick, difference / 8)
```

也就是取 `k=1/8` 的阻尼方向。中心 64、四邻居 0 时，每边输出 8，总输出 32；中心仍保留 32，四邻居各得到 8，不再一帧变 Empty。传输仍通过 Delta Buffer 统一结算，因此来源减去多少、目标就增加多少，Amount 守恒；`maxTransfer` 继续控制单边速度。

整数除法也带来明确取舍：当差值小于 8 时结果为 0，小的水平差异会停住，水面不会无限趋近绝对均匀。这不是精确流体，但会减少永不停止的微小 Dirty Version 与 Mesh 重建，适合当前“游戏规则优先”的 Cell 系统。若未来希望更细腻，可以采用 Fixed-Point 余数累积、降低 Tick/Cell Size、保存分数 Amount，或让 Gameplay Amount 保持离散而 Presentation 只做平滑；不能简单把除数改回 2。

### 为什么第一次 Vertex Alpha 修复反而更糟

第一次尝试曾把 `Amount` 写入 Vertex Color Alpha，并让 Shader 对低 Amount 做可见阈值/平滑。想法是隐藏很薄的流动前沿，但它把“症状”遮罩当成“根因”修复：相邻 Cell 的 Amount 本来就在高低交替，Alpha 也随之高低交替，于是整个水面被切成更明显的透明棋盘，连稳定视觉区域也被破坏。这套 `AmountVisibility/SetColors/List<Color32>` 已完整回退。

这个失败很有学习价值：Presentation Filter 可以处理轻微抖动，但不能修复 Gameplay Topology 在 `Water/Empty` 间翻转。视觉层阈值还会制造新的不连续。只有先检查 Simulation Snapshot，才能判断应该修 Shader、Mesh 还是 Solver。最终方案改了数值根因，而没有让 Rendering 猜测“哪些水应该被藏起来”。

## 8. 面试时如何完整讲述 Task 7

面试时我会先说目标和边界：我做的是一个有限三维元素场，Gameplay 用紧凑 Cell 保存 Water 的类型和 `byte Amount`，但玩家不能直接看到调试体素。因此我在 `Game.Rendering` 建了一个只读 Presentation Bridge。它通过 `IElementFieldReadOnly` 观察 Gameplay，不允许写回；这样关闭 Renderer 不会影响流动、灭火或 Wet，替换 Shader 也不会改变规则。

几何上，我没有给每个 Cell 创建 GameObject，而是按 8³ Cell 分成 Chunk。纯 `WaterChunkMeshBuilder` 把 `Amount/255` 映射成格内高度，只生成没有上层 Water 的 Top，以及高于水平邻居的 Side 高度差，去掉内部面和底面。每个 Quad 用四个 Vertex 和六个 Index 组成两个 Triangle，Winding 用 `cross(B-A,C-A)` 保证顶面 Normal 朝上；UV 直接采用全局 Cell 坐标，所以 Noise 跨 Cell、跨 Chunk 连续。上传后 Unity 重算法线和 Tangent，给自研 Water Shader 的 TBN 法线扰动提供基底。

运行时我用 Chunk Version 做 Dirty Tracking：只有 Gameplay 改过的 Chunk 才重建。一次范围法术可能同时污染多个 Chunk，因此每帧最多重建四个，并用环形 Cursor 防止后部 Chunk 饥饿。所有 Mesh、数组和 List Capacity 在初始化分配，热路径只 Clear 与复用；Mesh 使用 `MarkDynamic`，Material 使用 `sharedMaterial`，空 Chunk 关闭 Renderer，运行时 Mesh 在销毁时显式释放。Shader 继续负责两组移动 Noise、`N·L` 光照、TBN、Scene Depth 深浅色、`Fresnel = (1-N·V)^p`、接触泡沫和 Alpha Blend。Mesh 决定形状，Shader 决定材质感，两者职责没有混淆。

Play Mode 中出现过规则棋盘闪烁。我先用几何纯测试排除 Builder 的非确定性，再根据“只在流动 Tick 出现、严格对齐 Cell”判断是 Topology 而非随机 Noise。旧水平流动按每条边 `(source-target)/2` 传输，但二维一个格有四邻居；中心 64 会一次向四边各发 16，瞬间变 Empty，下一 Tick 又回填。它对应显式离散扩散系数过大、高频棋盘模式不受阻尼。最终把单边传输改为 `min(maxFlow, max(source-target,0)/8)`，中心只输出一半并保持守恒，同时用测试锁定四邻域速率与棋盘阻尼。中间尝试过根据 Amount 做 Vertex Alpha 阈值，但它只是遮症状，还把高低 Amount 直接变成透明棋盘，因此完整回退。

最后我会主动说明取舍：当前是稳定、可测试、适合 16K Cell 的 CPU Chunk Surface Meshing，不是完整流体，也没有用 Marching Cubes 或 GPU Compute。Amount 的整数除法会留下小于 8 的差值，Flat Normal 和透明 Chunk 排序也有视觉上限。下一步我会用 `Frame Debugger` 验证按 Chunk 而非按 Cell Draw，用 Profiler 查看 `ElementWater.RebuildChunk` 的 CPU/GC，再决定是否需要 MeshData API、Job/Burst、Compute Shader 或更平滑的 Surface Reconstruction。这个回答既说明已经做成了什么，也说明公式、架构边界、Debug 证据和扩展条件。

# Task 8：把离散 Fire Cell 转换成共享三层粒子，并建立确定性视觉预算

Task 8 的目的，是让前面已经能写入、衰减、灭火并施加 Burning 的 Fire Cell，从橙色调试方块升级成玩家真正能辨认的动态火焰，同时继续保持“Gameplay 数据”和“Presentation 表现”分离。最终玩家用 Fireball 命中地面后，Fire Cell 的世界坐标驱动 Body、Core、Sparks 三层粒子；火量较高时发射概率、粒子尺寸和 Alpha 更强，Fire 自然衰减后表现随之减弱，Water 消耗 Fire 后停止产生新粒子，已经发出的粒子只按自身 Lifetime 自然退场。实现没有给每个 Cell 创建 ParticleSystem，而是整个 Field 只复用一组三层系统，通过 `ParticleSystem.EmitParams` 把每个被选中的 Cell Center 写成单个粒子的发射位置。为避免大量火区让表现成本无限增长，本 Task 又把确定性 Hash、精确 Sample Cap、空间 Jitter 与 Amount 映射拆成纯数学 `FireCellEmissionSampler`，先用 NUnit 锁定边界，再由 `ElementFireRenderer` 负责 Unity 生命周期和 Particle API。最终 Test Runner 中 Sampler 8/8、全项目 EditMode 243/243 通过，玩家实测了命中、衰减、灭火、相隔多火区和位置稳定；Task8 因此完成了 Fire Cell→Fire Presentation 的闭环，但 P6 整体仍需 Task9 做全量回归、Frame Debugger 与统一性能记录。

## 1. 从玩家看到的火焰反向拆解完整运行链路

玩家看到“火球落地后出现火焰”，表面上像是一个 VFX，实际经过了五层职责：

```text
Fireball 碰撞
→ ElementDepositOnImpact 提交 Fire DepositRequest
→ ElementFieldRuntime 固定 Tick 写入、反应并衰减 Fire Cell
→ IElementFieldReadOnly 暴露 MaterialKind / Amount / 坐标
→ ElementFireRenderer 每 0.10s 扫描并选择可表现 Fire Cell
→ FireCellEmissionSampler 计算 Hash、概率、Sample Cap、Jitter、Size
→ ParticleSystem.EmitParams 向 Body/Core/Sparks 手动发射
→ Particle Module + Fire Shader 完成上升、缩放、透明度与颜色
```

其中前两行属于 `Game.ElementField` Gameplay，后四行属于 `Game.Rendering` Presentation。`ElementFireRenderer` 持有的是 `IElementFieldReadOnly`，只能调用 `GetCell`、读取 Dimensions/Origin/CellSize，不能 Deposit、移动或删除 Fire。关闭整个 `PF_ElementFireEmitter` 后，Fire 仍会衰减、与 Water 反应并施加 Burning；反过来，即使粒子特别明亮，只要对应位置没有 Fire Cell，Gameplay 就不会凭空出现火。这条单向关系可以写成：

```text
Game.ElementField（事实：哪里有火、有多少）
              │ IElementFieldReadOnly
              ▼
Game.Rendering（解释：抽样哪些 Cell、如何画成火）
              ▼
Unity ParticleSystem + Fire Shader
```

这种拆分让数值规则和美术调参互不污染。例如把 `SparkProbability` 从 0.12 改成 0.05，只会减少火星，不会让 Fire Amount 消耗得更慢；把 Gameplay 的 `FireDecayPerTick` 调大，会让 Fire Cell 更快归零，Renderer 只是忠实地停止新发射。这里没有使用新的商城 Fire Prefab、Texture、Noise Map 或 Audio，全部复用 5A～5D 已经亲手制作并验证的 Body/Core/Sparks Shader、Material 和 Particle Module。

## 2. 为什么 Water 采用 Chunk Mesh，而 Fire 采用 ParticleSystem

Water 与 Fire 虽然都来自 Cell，但几何性质不同。Water 的主体是相对连续、低频变化的表面：需要明确的水面高度、外露侧壁、连续 UV、Scene Depth、Fresnel 和接触泡沫，因此 Task7 把许多 Cell 聚合成 Chunk Mesh。Fire 没有稳定的封闭表面，它快速向上运动、轮廓不断断裂重组，还伴随高温亮芯和零散火星。如果为 Fire 每 Tick 重建 Mesh，就必须持续改变 Topology、Vertex 与 Alpha，最后仍要额外做粒子式运动；如果为每个 Fire Cell 创建一个 ParticleSystem，最多 16,384 个 Cell 会带来大量 GameObject、Transform、Component、Culling 和 Update 管理开销。

当前方案因此采用“一整个 Field 共享三个 ParticleSystem”：

| 层 | 渲染方式 | 玩家感知 | 为什么单独存在 |
|---|---|---|---|
| Body | `Alpha Blend` + Vertical Billboard | 橙红色外焰、主要轮廓和透明边缘 | Alpha 能保留形状层次，不会让重叠区域无上限增亮，是火焰可读性的主体。 |
| Core | `Additive Blend` + Vertical Billboard | 靠近火焰根部的高温亮芯 | Additive 重叠越多越亮，适合表达能量，但数量必须低于 Body，避免 `Overdraw` 和过曝。 |
| Sparks | `Additive`/发光 Material + Stretched Billboard | 少量高速火星和运动方向 | Stretched Billboard 沿速度方向拉长，提供高频细节；概率最低、最大粒子数也最小。 |

`Billboard` 是始终朝向 Camera 的小型 Quad。ParticleSystem 为每个粒子保存 Position、Velocity、Remaining Lifetime、Size、Rotation、Color 等状态，Renderer 再把 Quad 交给 GPU。Body Shader 使用：

```text
Blend SrcAlpha OneMinusSrcAlpha
Cout = Csrc × α + Cdst × (1 - α)
```

Core 使用：

```text
Blend SrcAlpha One
Cout = Csrc × α + Cdst
```

Additive 不会用 `(1-α)` 压暗背景，所以非常适合亮芯与火星，但多个透明粒子覆盖同一屏幕像素时，每层都要执行 Fragment Shader，这就是 `Overdraw`。三层拆分的意义不是“层数越多越高级”，而是分别控制轮廓、能量和方向，并给每层独立的概率与粒子上限。Body/Core Shader 都是 `ZWrite Off`，避免透明 Quad 把 Depth 写死；代价是依赖透明排序，交叉粒子可能出现近似排序误差。

## 3. Fire Amount 怎样变成发射概率、尺寸与透明度

`ElementCell.Amount` 是一个 `byte`，范围 `[0,255]`。第一步先归一化：

```text
a = Amount / 255
a ∈ [0,1]
```

这个 `a` 同时控制三类视觉量。第一类是单次视觉 Tick 的发射概率：

```text
pEmit = clamp01(pLayer) × a
emit 当且仅当 hash01 < pEmit
```

`pLayer` 来自 `ElementFireRenderProfile`：Body=1、Core=0.75、Sparks=0.12。满 Amount 时 Body 每个视觉 Tick 都通过，Core 约有 75% 机会，Sparks 约有 12% 机会；Amount 只有 64 时，`a≈0.251`，三层概率都会相应降低。概率不等于“本轮一定按固定比例产生”，而是长期统计趋势，所以某一个 Tick 可能出现 Body 发射 4 个、Core 发射 5 个；这不违反 Core 概率更低，因为两层使用独立 Hash，必须观察多个 Tick 的平均分布。

第二类是尺寸：

```text
sizeMultiplier = lerp(minSize, maxSize, a)
startSize = ParticleMainStartSize × sizeMultiplier
```

当前 `minSize=0.4`、`maxSize=1.2`。Amount 很低时仍保留 40% 基础尺寸，避免刚产生的少量 Fire 完全不可辨认；满 Amount 则放大到 120%。`ParticleSystem.MinMaxCurve.Evaluate(0, sizeRandom)` 会继续保留 Particle Main 中 Two Constants 的随机区间，再乘 Amount 倍率。第三类是 Alpha：

```text
startAlpha = baseStartAlpha × a
```

`EmitParams.startColor` 通过 Particle Vertex Stream 进入 Shader；三个 Particle Material 都启用了 `_UseVertexColor=1`，所以逐粒子的 Alpha 会参与最终形状透明度。这里同时对概率、尺寸、Alpha 做映射，会让低 Amount 明显弱化，是有意的视觉曲线；如果未来发现衰减尾部消失太快，可以选择只调整其中一条，而不是修改 Gameplay Amount。

发射点不是严格落在 Cell Center。完全相同的位置会让许多 Billboard 重合，形成机械的格点阵列，因此用三个独立 Hash Channel 生成确定性 Jitter：

```text
x = (2hx - 1) × 0.35 × cellSize
y = hy × verticalJitter
z = (2hz - 1) × 0.35 × cellSize
position = cellCenter + (x,y,z)
```

XZ 最大只偏移 CellSize 的 35%，不会跨出本格；Y 只向上，避免火焰被抖进地面。`cellCenter` 由 World Space 公式得到：

```text
cellCenter = Origin + (coordinate + 0.5) × CellSize
```

Body/Core/Sparks 使用不同 Layer Seed 决定各自是否发射和颜色/尺寸随机，但位置使用共享的 `SharedPositionSeed`。这样一轮中三层若都发射，会从同一个局部火点开始，外焰与焰芯不会像早期实验那样彼此分离。

## 4. 确定性 Hash 与精确 Sample Cap：如何让表现可复现且有上限

如果每次直接调用 `UnityEngine.Random.value`，发射结果依赖一个全局随机状态：其他系统多调用一次 Random，就可能改变火焰分布，测试也难以复现。本 Task 使用输入驱动的整数 Hash：

```text
key = cellIndex
    XOR visualSequence × constantA
    XOR layerSeed
    XOR channel × constantB

h = Avalanche(key)
hash01 = (h AND 0x00FFFFFF) / 2^24
```

`Avalanche` 会通过 XOR Shift 和无符号整数乘法，让输入只改变一位时输出多数 Bit 都变化；`unchecked` 的 32-bit Wrap Around 是 Hash 的设计组成，不是溢出 Bug。只保留低 24 bit，是因为 `float` 尾数大约能精确表达 24 bit；除数使用 `2^24=16,777,216`，因此结果属于 `[0,1)`，永远不会等于 1。相同的 Cell、Visual Sequence、Layer 与 Channel 一定得到相同结果；改变 Layer Seed 可以让 Body/Core/Sparks 相互独立，改变 Channel 可以让 Probability、X/Y/Z Jitter、Size、Color 互不相关。

`visualSequence` 每完成一次视觉扫描加一，因此静止 Fire Cell 也不会每 0.1 秒重复完全相同的粒子图案。这里的“确定性”指相同输入得到相同输出，方便测试和 Debug；它不等于网络 Lockstep Determinism，因为不同机器的帧时序仍可能让某个 Field Snapshot 对应不同 Visual Sequence。Presentation 不参与 Gameplay，所以允许这种边界。

第二个问题是预算。若有 `activeCount=A` 个 Fire Cell，而 Profile 最多允许 `B=1024` 个参与本轮发射判断，简单做法是每隔 `ceil(A/B)` 取一个。但当 A 刚从 1024 增到 1025 时，步长突然变 2，只剩约一半 Cell 被选中，视觉密度会出现断崖。当前采用 `Rational Stride/Bresenham` 风格的 Bucket 变化判定：

```text
phase = hash(visualSequence) mod A
r = (activeOrdinal + phase) mod A

previousBucket = floor(r × B / A)
nextBucket     = floor((r + 1) × B / A)
select 当 nextBucket != previousBucket
```

当 `A≤B` 时直接选择全部 Active Cell；当 `A>B` 时，`floor(rB/A)` 从 0 逐步增长到 B，完整遍历恰好发生 B 次 Bucket 变化，所以严格选中 1024 个，而不是“大约 1024”。乘法使用 `long`，避免大计数下 `int` 溢出。Phase 每轮旋转选择位置，使被预算排除的 Cell 下一轮仍有机会参与，不会永久没有火焰。这个 Cap 只降级 Presentation：Gameplay 里的全部 Fire Cell 仍然正常衰减、反应和施加 Burning。

需要看清一个性能边界：当前 Renderer 为统计 Active Count 和执行抽样，每 0.1 秒对 16,384 Cell 做两遍 O(N) 扫描；Sample Cap 限制的是发射数量与透明粒子成本，不会把扫描复杂度降到 O(Active)。对 P6-A 的有限实验房这是可读、可靠的基线。如果 Task9 或更大 131K Cell 压测证明扫描成为瓶颈，可以再引入 Active Index List、Chunk Version 或按 Dirty Chunk 维护 Fire Emitter Cache；不能在没有 Profiler 证据前把复杂缓存提前塞入 Gameplay。

## 5. ElementFireRenderer 如何连接只读 Field 与 ParticleSystem

`ElementFireRenderer` 是 `Game.Rendering` 中的 Unity Adapter。`Start()` 而不是另一个 `Awake()` 获取 `_fieldRuntime.ReadOnlyField`，因为 `ElementFieldRuntime.Awake()` 先初始化 Grid；这样避免不同 GameObject 的 Awake 顺序隐含依赖。初始化阶段验证 Field、Profile 和至少一个 ParticleSystem 引用，缓存每层的 Main StartSize、StartColor、MaxParticles 和 Layer Seed，再关闭自动 `Emission Module`。关闭自动 Emission 不会阻止显式 `ParticleSystem.Emit`，它只避免 Prefab 按自己的 Shape 从根物体位置额外喷火。

`Update()` 不每帧扫描 Field，而是累积 `Time.deltaTime`：

```text
accumulator += deltaTime
if accumulator >= EmissionInterval:
    accumulator = 0
    EmitFromFireCells()
```

默认 Interval=0.10s，即 10 Hz。它与 Gameplay 10 Hz 当前数值接近，但属于独立的 Visual Tick：Gameplay 固定 Tick 必须维护反应和守恒，Rendering Tick 可以为了性能丢帧。代码在一次卡顿后不会 `while(accumulator>=interval)` 连续补发旧视觉债务，因为同帧补十轮粒子只会制造 Overdraw 尖峰，并不能恢复任何 Gameplay 正确性。`Time.timeScale<=0` 时直接返回，让 Wand Editor/暂停菜单同时停住视觉发射。

真正发射时，代码构造 value type `ParticleSystem.EmitParams`：

```csharp
ParticleSystem.EmitParams emitParams = default;
emitParams.position = position;
emitParams.startSize = baseStartSize * sizeMultiplier;
emitParams.startColor = startColorWithAmountAlpha;
particleSystem.Emit(emitParams, 1);
```

没有 `Instantiate`，没有给每个 Cell 建 GameObject。ParticleSystem 内部复用自己的 Particle Buffer，现有 Lifetime、Velocity over Lifetime、Color over Lifetime、Size over Lifetime、Noise 和 Renderer Module 继续处理“发射之后怎么运动和消失”。每次发射前检查 `particleSystem.particleCount >= maxParticles`，Body/Core/Sparks 的 Prefab 上限分别是 2048、1536、512；达到上限就跳过，避免大火区无限增长。

三层必须使用 `ParticleSystemSimulationSpace.World`。World Space 表示粒子一旦发出，Position 存在世界坐标中，不再跟随 Emitter Transform；因此后创建远处火区时，旧火区粒子不会瞬移过去。代码也会在初始化时强制改成 World 并记录 Warning，Prefab 则提前正确配置，减少运行时纠错。相反，Local Space 会让粒子位置相对发射器 Transform 保存，移动共享根物体可能拖走所有旧粒子，完全不适合“一个系统服务多个世界位置”。

`PS_FireCore` 仍可在 Hierarchy 中作为 `PS_FireBody` 的子物体，这只是 Transform/Authoring 层级；但是 Body 的 `Sub Emitters` Module 必须移除 Core 引用并关闭。旧实验中 Sub Emitter 表示“Body 粒子在 Birth/Death/Collision 时自动创建 Core 粒子”，而 Task8 已由 `ElementFireRenderer` 分别对 Body/Core/Sparks 调用 Emit。若两条关系同时存在，Core 会被手动发一次、又被 Body 自动触发一次，导致数量翻倍、Overdraw 增大，Inspector Emission Count 也与画面不一致。这次纠错说明：GameObject 父子关系不等于 ParticleSystem 发射依赖，看到 `Select Sub-Emitter Owner` 时要继续检查 Module，而不能只看 Hierarchy。

热路径没有 LINQ、临时数组、List、Closure 或托管对象创建。`new Vector3`、`ElementCell`、`EmitParams` 都是 value type；`ParticleLayerState` 是引用类型，但只在 Start 初始化一次。`ProfilerMarker("ElementFire.Emit")` 包住两遍 Field Scan、Hash 和三层 Emit，便于在 CPU Profiler 中与 `ParticleSystem.Update` 分开定位。

## 6. ScriptableObject、Prefab、Material 与场景装配

`ElementFireRenderProfile` 是纯表现 `ScriptableObject`，当前资产 `ElementFireRenderProfile_P6A.asset` 保存：

```text
MaxSampledFireCells = 1024
EmissionInterval = 0.10s
BodyProbabilityAtFullAmount = 1.00
CoreProbabilityAtFullAmount = 0.75
SparkProbabilityAtFullAmount = 0.12
MinSizeMultiplier = 0.40
MaxSizeMultiplier = 1.20
VerticalJitter = 0.08m
```

`OnValidate()` 会处理负值、NaN、Infinity、Probability 越界以及 MaxSize 小于 MinSize，避免错误 Inspector 数据进入运行时。Profile 不保存 Material、Fire Amount 或 Reaction Rules：Material 属于 Prefab 每层 Renderer，Gameplay 数据属于 ElementField Profile，两者变化原因不同，不应塞进同一个“大配置”。

最终 Prefab 为：

```text
PF_ElementFireEmitter
├── PS_FireBody       MaxParticles=2048，Vertical Billboard，Body Alpha Material
│   └── PS_FireCore   MaxParticles=1536，Vertical Billboard，Core Additive Material
└── PS_FireSparks     MaxParticles=512，Stretched Billboard，Sparks Material
```

三个子物体 Local Position 都为 0，Particle Main 使用 World Simulation Space，自动 Emission 在运行时被 Renderer 关闭。Body/Core/Sparks 保留 5A～5D 调好的 Lifetime、Velocity、Color/Size over Lifetime、Noise 与 Material。场景中的 Prefab 实例放在 `ElementFieldLabRoot` 下，`ElementFireRenderer.FieldRuntime` 指向该 Root 上的 `ElementFieldRuntime`，Profile 指向 P6A 资产，三个 Particle 引用指向各自子组件。Prefab Asset 不能持有 Scene Object 引用，所以 `_fieldRuntime` 在 Asset 中为空、在 SampleScene 的实例 Override 中赋值，这是 Unity Prefab 的正常边界，不是漏配。

Material 的 `_UseVertexColor=1` 很关键：否则 EmitParams 写入的 Amount Alpha 不会参与自研 Shader，低火量与满火量可能看起来一样。Body 使用 `M_ElementFireBody_Particle`，Core 使用 `M_ElementFireCore_Particle`，Sparks 使用 `M_ElementFireSparks_Particle`。本 Task 没有修改 `ElementFireBody.shader` 或 `ElementFireAdditive.shader`，而是把已经验证的单个火焰视觉单元升级为 Cell 驱动的空间分布系统。

常见故障应按以下顺序排查：

1. **完全没有火。** 看 `LastActiveFireCellCount`。若为 0，先查 Projectile Deposit、Field Bounds 与 Fire Decay；若大于 0 但 Emission 全 0，再查 Profile Probability、Particle 引用、MaxParticles、组件 enabled。Shader 不会决定 Gameplay Cell 是否存在。
2. **Prefab 原点自己冒火。** 自动 Emission Rate/Burst 或旧 Sub Emitter 仍在工作。`ElementFireRenderer` 会关闭三个 Emission Module，但 Prefab Authoring 也应清理，避免 Edit Preview 和初始化前出现错误粒子。
3. **旧火焰跟着共享 Root 瞬移。** Simulation Space 仍是 Local。切换 World，并确认手动 position 使用 World Cell Center。不要用移动一个发射器去“轮流服务”不同火区。
4. **焰芯明显比外焰多一倍。** 检查 Body 的 `Sub Emitters` 是否仍引用 Core。Hierarchy 中 Core 作为 Child 可以保留，Sub Emitter 生命周期关系必须删除。
5. **灭火后仍短暂看到火。** 先看 Emission Count 是否已变 0。已经发出的 Particle 不代表 Fire Cell 仍存在，它会按 0.25～1.15s Lifetime 自然消失；若要求瞬间清屏，需要额外位置级 Particle Kill 机制，会增加复杂度，当前不做。
6. **单 Tick Core 数量偶尔高于 Body。** 独立 Hash 的正常统计波动，不要用一帧判断长期概率。若长期 Core 过强，再调整 Probability、Material Intensity 或 MaxParticles。
7. **低 Amount 看不出衰减差异。** 检查三个 Material 的 `_UseVertexColor=1`，因为 Amount Alpha 通过 Particle Color Vertex Stream 进入 Shader；关闭该开关会丢失逐粒子 Alpha。
8. **画面过亮、帧率下降。** 在 Scene View Overdraw 与 Profiler 中区分透明 Fragment 成本和 CPU Emit 成本。优先降低 Core/Sparks Probability、Lifetime 或 MaxParticles，而不是破坏 Gameplay Cell 数量。

`ElementFire.Emit` Marker 的目标是让扫描/Hash/Emit 与 Unity 自身 `ParticleSystem.Update` 分开观察。检查 `GC Alloc` 时要看 Marker 本身，不要把 UI、Enemy、Editor 的整帧分配归咎于 Fire。代码层已排除 LINQ、临时集合与热路径引用类型创建；Task8 的开发者 Gate确认可以收口，但 Task9 仍要在统一场景、统一采样窗口和 Development Build 中保存精确数据，才能形成作品集级性能结论。

## 9. 方案比较、当前取舍与后续扩展边界

| 方案 | 优点 | 缺点 | 本阶段结论 |
|---|---|---|---|
| 每个 Fire Cell 一个 ParticleSystem | 最直观，每格独立控制 | 数千 GameObject/Transform/Component，管理和 Culling 成本高 | 拒绝。 |
| Fire Chunk Mesh | 可控制 Draw Call、几何连续 | 火焰 Topology 快速变化，仍需动态运动、透明 Noise 和火星 | 不适合作为主体。 |
| 一组三层共享 ParticleSystem + EmitParams | 复用 5A～5D 视觉；任意世界位置发射；对象数固定；易调试 | CPU 要扫描 Field；透明 Overdraw；缺少单区域粒子精确删除 | 当前采用。 |
| VFX Graph / Compute Buffer | 大规模 GPU 粒子、可直接消费 StructuredBuffer | 调试、平台兼容、GPU 数据上传和学习成本更高 | 等大场压力测试与 Profiler 证据。 |

当前方案本质上是 CPU Gameplay Field 与 Unity Particle Buffer 之间的 Presentation Adapter。它没有模拟烟流体、温度场、浮力或光照体积，也没有把每个 Cell 映射成永久粒子。每 0.1s 的概率发射会产生统计噪声，但三层 Lifetime 在时间上把离散 Tick 融合成连续观感。未来可以按实际展示需求增加 Light Pool、Heat Distortion、Steam、Decal 或 VFX Graph；这些属于视觉增强，不能反向改变 Fire Reaction 的唯一真相来源。

Task9 需要把 Water 与 Fire 放在同一可玩脚本下做全量回归，并统一记录：EditMode/PlayMode Tests、Frame Debugger Draw Call、`ElementWater.RebuildChunk`、`ElementFire.Emit`、`GC Alloc`、Particle Count、极端 Deposit 与错误恢复。只有这些证据完成，P6-A 才能从“功能可玩”升级为“性能边界清楚、可用于作品集讲解”。

## 10. 面试问答与模拟完整讲解

面试官可能问：“为什么不为每个 Cell 创建一个火焰 Prefab？”我会先区分数据粒度和对象粒度。Cell 是紧凑数组中的 4 Byte 左右 Gameplay 数据，16,384 个 Cell 可以低成本固定 Tick；GameObject/ParticleSystem 则包含 Transform、Component、Native Engine Object、Culling 和更新管理。让二者一一对应会把细粒度数据优势全部抵消。因此整个 Field 只保留 Body/Core/Sparks 三个 ParticleSystem，Cell 只在视觉 Tick 提供世界位置和 Amount，`EmitParams` 把它们写入共享 Particle Buffer。对象数量固定，视觉数量由 Sample Cap 和 MaxParticles 控制。

面试官可能问：“Hash 为什么比 Random 更适合？”我会回答：这里不需要不可预测性，而需要可复现、无全局状态耦合的视觉采样。整数 Hash 由 cellIndex、visualSequence、layerSeed、channel 构成，相同输入稳定得到同一 `[0,1)`；Body/Core/Sparks 和 Jitter 各 Channel 互相独立。它不会消耗 `UnityEngine.Random` 的全局序列，所以其他系统增加一次 Random 调用不会改变火焰分布，也能用 NUnit 直接验证概率边界和 Jitter 范围。它只是 Presentation Determinism，不声称网络帧同步。

面试官可能继续问：“如何保证超过 1024 个 Fire Cell 时正好抽 1024 个？”可以解释 Bucket 公式：对旋转后的 Active Ordinal `r` 比较 `floor(rB/A)` 与 `floor((r+1)B/A)`，只有 Bucket 增长时选中。遍历 A 项时 Bucket 总共从 0 增长 B 次，因此严格选 B 项；Phase 让每个 Tick 轮换样本。相比 `ceil(A/B)` 固定跨步，它不会在 A 刚超过 B 时让样本数突然减半。

面试官问：“为什么必须用 World Simulation Space？”我会说明 Local Space 把粒子坐标绑定在 Emitter Transform 下，移动共享发射器会拖走所有历史粒子。一个系统要同时服务多个相距很远的 Fire Cell，发射位置必须是世界坐标，旧粒子也必须留在各自世界位置。因此 Cell Center 用 `Origin+(coord+0.5)×CellSize` 算 World Position，Particle Main 使用 World Space；Prefab Root 只负责承载组件，不再代表唯一发射地点。

如果要求从头到尾完整介绍，我会这样回答：

> 我做的是有限三维元素场中的 Fire Presentation。Gameplay 用紧凑 Cell 保存 `MaterialKind` 和 byte Amount，火球命中后只提交 Deposit，固定 10 Hz Simulator 决定写入、Water/Fire 反应和衰减。Rendering 通过 `IElementFieldReadOnly` 单向读取结果，不允许修改 Cell。因为 Fire 是快速变化、半透明、向上运动的非稳定表面，我没有像 Water 那样重建 Chunk Mesh，也没有给每个 Cell 建 ParticleSystem，而是整个 Field 复用 Body、Core、Sparks 三个系统。
>
> Renderer 每 0.1 秒统计 Active Fire Cell，并用纯数学 Sampler 做确定性视觉抽样。Hash Key 由 cellIndex、visualSequence、layerSeed 和 channel 组成，经 32-bit Avalanche 后取低 24 bit 除以 2^24，得到稳定的 `[0,1)`。发射阈值是 `layerProbability×Amount/255`，尺寸在 0.4 到 1.2 倍之间线性插值，Alpha 也乘 Amount；位置以 Cell Center 为基准，在 XZ 不超过 0.35 Cell、Y 只向上做确定性 Jitter。超过 1024 个 Active Cell 时，我用 Rational Stride Bucket 变化严格选中 1024 个，并按 Visual Sequence 旋转样本，视觉降级不会删除 Gameplay Cell。
>
> Unity 侧使用 `ParticleSystem.EmitParams` 直接覆盖 Position、StartSize 和 StartColor，已有 Lifetime、Velocity、Color/Size over Lifetime、Noise 与 Shader 继续负责粒子发出后的运动。Body 是 Alpha Blend 外焰，Core 与 Sparks 是 Additive 高温细节；Additive 更亮但 Overdraw 更高，所以概率和 MaxParticles 更低。三个系统使用 World Simulation Space，确保多个火区同时存在时旧粒子不会随共享 Root 瞬移。自动 Emission 与旧 Core Sub Emitter 都被关闭，避免从 Prefab 原点额外发射或焰芯重复。
>
> 性能边界上，整个 Field 只有三个 ParticleSystem，Body/Core/Sparks 上限为 2048/1536/512，视觉抽样上限 1024。热路径不使用 LINQ、临时集合或托管对象，`ElementFire.Emit` ProfilerMarker 把 CPU 扫描与 Unity Particle Update 分开。TDD 先验证 Hash、概率、精确 Cap、Jitter 和 Amount 映射；Unity Test Runner 中 Sampler 8/8、全项目 243/243 通过，Play Mode 又验证了命中、衰减、灭火、多火区和 World Space 稳定。当前仍是 16K Cell 的 CPU 基线，Task9 会用统一 Development Build 和 Profiler 数据决定是否需要 Active List、Chunk Cache、Job/Burst 或 VFX Graph，而不会为了技术炫技提前复杂化。
