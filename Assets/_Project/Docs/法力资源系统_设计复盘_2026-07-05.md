## 0. 先建立心智模型

一句话理解这个功能：

> `Mana` 不是“火球数量”，而是“玩家每隔多久能释放一次复杂法术程序”的节奏控制器。

在你的项目里，法术编程系统已经允许玩家把很多法术按顺序放进法杖，比如：

```text
三重射击 -> 增伤 -> 追踪 -> 触发火球 -> 陨石术
```

如果没有资源限制，玩家可以无限快速释放非常长、非常强的法术组合。这样会出现两个问题：

1. 战斗节奏失控：强力组合没有代价，玩家只会一直按最强方案。
2. 法术编程失去取舍：玩家不需要考虑“我这套法杖是不是太贵了”。

所以 `Mana` 系统的核心价值不是“让玩家少放技能”，而是让玩家在设计法杖时产生取舍：

- 低成本法术：可以频繁释放，稳定输出。
- 高成本组合：爆发很强，但打完要等蓝条恢复。
- 触发链法术：前段和 payload 分开扣费，让链式玩法更自然。

这也是很多动作 RPG、Roguelike、Noita-like 系统中资源条的本质：**限制频率，而不是限制乐趣**。

## 1. 从玩家看到的效果倒推实现链路

玩家看到的结果：

1. 屏幕上有一条蓝色 Mana 条。
2. 蓝条会随时间自动恢复。
3. 释放法术时蓝条减少。
4. 如果当前蓝量不够，点击攻击不会发出法术。
5. 如果触发类火球命中后要释放后续法术，那么后续法术会在触发时再次检查蓝量。

系统内部实际发生的链路是：

```text
玩家点击攻击
-> WizardController 缓存本次施法输入
-> PlayerWizardAttackState 在动画释放点调用 SpellCaster.CastWand
-> SpellCaster.RunCast 询问 CastEvaluator：本层法术需要多少 Mana
-> ManaComponent 判断能不能支付
-> 能支付：ManaComponent.Spend 扣蓝
-> CastEvaluator.Evaluate 解释法杖程序，产出 EmitCommand
-> SpellCaster 根据 EmitCommand 生成投射物 / 静态投射物
-> UI 的 PlayerManaBar 每帧读取 ManaComponent.Normalized 更新蓝条
```

触发类 payload 的链路是：

```text
触发投射物释放时：只支付触发投射物所在层的 Mana
-> 投射物命中 / 定时结束
-> ProjectileBase 事件回调 SpellCaster.RunCast(payload)
-> payload 作为新的一层重新 EstimateManaCost
-> Mana 足够才释放后续法术
```

这个设计很重要：**触发 payload 不预付费，而是在真正触发时付费。**

原因是 payload 的释放是未来事件，可能发生，也可能不发生。例如触发火球没命中敌人，后续陨石术就不会释放。如果一开始就把陨石术的钱扣掉，玩家会觉得“不公平”：我还没看到陨石，蓝已经没了。

## 2. 需求拆解与基础知识

### 2.1 这个功能拆成哪些小问题

这次功能表面上叫“蓝条”，但真实开发时不能只做 UI。它至少包含五个小功能：

| 小功能 | 要解决的问题 |
|---|---|
| Mana 数据组件 | 谁保存当前 Mana、最大 Mana、恢复速度？ |
| Mana 自动恢复 | 每秒怎么恢复，如何不超过上限？ |
| 法术成本估算 | 当前这次法杖程序到底要花多少 Mana？ |
| 施法扣费 | Mana 不够时怎么阻止整次施法？ |
| HUD 蓝条 | 玩家怎么看到当前 Mana 状态？ |

这几个问题分别属于不同模块，所以不能全部塞进一个脚本里。

### 2.2 基础知识：资源系统是什么

游戏里的资源系统常见有三类：

1. 消耗型资源：药水、箭矢、炸弹，用完就没。
2. 恢复型资源：Mana、Stamina、Energy，消耗后随时间恢复。
3. 条件型资源：怒气、连击点、热量，需要通过战斗行为积累或释放。

这次做的是恢复型资源。它的设计目标通常不是永久限制玩家，而是控制单位时间内的行为强度。

举例：

```text
玩家最大 Mana = 100
每秒恢复 = 20
普通火球成本 = 10
复杂陨石触发链成本 = 80
```

这样普通火球可以频繁用，复杂法术虽然能放，但放完要等几秒。玩家自然会开始思考：

- 我需要这么多修正法术吗？
- 我要不要把高成本法术留给关键时机？
- 我的法杖是稳定输出型，还是爆发型？

这就是资源系统对战斗设计的价值。

### 2.3 基础知识：为什么需要“估算成本”

你的法术系统不是固定技能按钮，而是一个解释器：

```text
WandLoadout = 程序
SpellDefinition = 指令
CastEvaluator = 解释器
EmitCommand = 输出命令
SpellCaster = Unity runtime 桥接
```

法杖里每个格子可能是：

- `Emit`：真正产生投射物。
- `StaticProjectile`：产生静态投射物，例如陨石。
- `Modify`：修改后续投射物，例如增伤、追踪、重力。
- `Multicast`：改变本次释放的投射物预算，例如三重射击。

因此本次施法成本不能简单写成：

```text
所有格子的 ManaCost 相加
```

因为触发类法术会捕获后缀 payload，并结束当前层求值：

```text
触发火球 -> 陨石术 -> 增伤
```

释放触发火球时，当前层只应该支付“触发火球”的成本。后面的“陨石术 -> 增伤”是 payload，应该等触发火球命中后再支付。

所以我们需要 `CastEvaluator.EstimateManaCost(...)`：它要按照解释器真实读法，估算“当前层会读到哪些法术”，而不是机械地遍历全部数组。

## 3. 业界常见实现方案

### 方案一：在角色控制器里硬编码 Mana

做法：

```text
WizardController 里放 currentMana / maxMana
点击攻击时判断 currentMana 是否足够
够就扣，不够就不放
```

优点：

- 最快。
- 初学者容易写。
- 适合只有一个固定技能的 Demo。

缺点：

- 和法术编程系统不匹配。
- `WizardController` 会变得越来越胖。
- UI 如果想读 Mana，就要引用 `Game.Character`，破坏你项目的 asmdef 方向。
- payload、Modify、Multicast 的成本语义很难写清楚。

这个方案不适合你的项目。

### 方案二：Mana 作为战斗资源组件，SpellCaster 负责扣费

做法：

```text
ManaComponent 挂在 WizardPlayer 上
SpellCaster 释放法术前询问 ManaComponent
PlayerManaBar 读取 ManaComponent 显示蓝条
CastEvaluator 只负责纯逻辑估算
```

优点：

- 模块职责清晰。
- `Game.Character` 和 `Game.UI` 都能依赖 `Game.Combat`，不破坏架构。
- Mana 未来可以给敌人、Boss、其他职业共用。
- `CastEvaluator` 仍然保持纯逻辑，方便单元测试。

缺点：

- 需要多改几个模块。
- 需要设计“当前层成本估算”。

这是本次最终采用的方案。

### 方案三：事件驱动资源系统

做法：

```text
SpellCaster 发布 TrySpendManaEvent
ManaSystem 监听事件并返回结果
UI 监听 ManaChangedEvent
```

优点：

- 模块解耦更强。
- 适合大型项目，特别是多人、Buff、装备、网络同步复杂时。

缺点：

- 当前项目阶段过重。
- “请求-返回结果”的 EventBus 设计会比较别扭，因为 EventBus 更适合广播结果，不适合同步查询。
- 初学阶段会增加理解成本。

所以这次没有采用完整事件化方案，而是先用直接组件引用。这个选择更符合当前项目阶段。

## 4. 最终方案与技术细节

### 4.1 `ManaComponent`：资源状态的拥有者

文件：

```text
Assets/_Project/Scripts/Combat/Resources/ManaComponent.cs
```

它在架构中的位置：

```text
Game.Combat
```

为什么放在 `Game.Combat`？

因为它不是法师专属输入逻辑，也不是 UI 表现。它是一个战斗资源，和 `HealthComponent` 类似，都属于“角色战斗状态”。你的 asmdef 关系是：

```text
Game.Combat
├── Game.Skills
├── Game.Character
└── Game.UI
```

`SpellCaster` 在 `Game.Character`，`PlayerManaBar` 在 `Game.UI`，二者都可以引用 `Game.Combat`。如果把 `ManaComponent` 放在 `Game.Character`，`Game.UI` 就不能直接引用它，否则会破坏依赖方向。

核心字段：

```csharp
[SerializeField, Min(1f)] private float _maxMana = 100f;
[SerializeField, Min(0f)] private float _manaRegenPerSecond = 20f;
[SerializeField] private bool _startFull = true;

private float _currentMana;
```

涉及的 Unity API：

| API | 作用 |
|---|---|
| `MonoBehaviour` | 让组件能挂在 GameObject 上，并接收 `Awake` / `Update` |
| `[SerializeField]` | private 字段仍然显示在 Inspector，方便调参 |
| `[Min(1f)]` | Inspector 中限制最小值，避免最大 Mana 小于等于 0 |
| `Awake()` | 初始化当前 Mana |
| `Update()` | 每帧恢复 Mana |
| `Time.deltaTime` | 当前帧和上一帧之间的秒数，用于帧率无关恢复 |
| `Mathf.Min` | 防止恢复超过最大值 |
| `Mathf.Max` | 防止负数成本和非法配置 |
| `Mathf.Clamp01` | 把蓝条比例限制在 0 到 1 |

恢复逻辑：

```text
每帧增加 ManaRegenPerSecond * Time.deltaTime
如果超过 MaxMana，就钳制到 MaxMana
```

为什么要乘 `Time.deltaTime`？

因为不同电脑帧率不同。如果不乘 `Time.deltaTime`，60 FPS 每秒恢复 60 次，144 FPS 每秒恢复 144 次，帧率越高恢复越快，这是错误的。乘上 `Time.deltaTime` 后，恢复速度就变成“每秒多少点”，与帧率无关。

### 4.2 `CastEvaluator.EstimateManaCost`：当前层成本估算

文件：

```text
Assets/_Project/Scripts/Skills/CastEvaluator.cs
```

新增接口：

```csharp
public static float EstimateManaCost(
    IReadOnlyList<SpellDefinition> spells,
    int baseDraws,
    CastModifierState incomingMods)
```

它的职责是：**按照解释器当前层真实读法，算出这一层需要多少 Mana。**

为什么放在 `CastEvaluator`？

因为只有 `CastEvaluator` 最懂法杖解释规则：

- `Modify` 什么时候生效。
- `Multicast` 怎么增加 draw budget。
- `Emit` / `StaticProjectile` 什么时候消耗 draw budget。
- 触发类法术什么时候捕获 payload 并结束当前层。

如果把成本估算写在 `SpellCaster`，`SpellCaster` 就必须复制一份解释器逻辑。这样以后解释器语义变了，扣费逻辑很可能忘记同步，产生隐藏 bug。

估算规则：

| 法术类型 | 是否计费 | 备注 |
|---|---|---|
| `Modify` | 是 | 只要被当前层读到就计费 |
| `Multicast` | 是 | 只要被当前层读到就计费 |
| `Emit` | 是 | 只有 `drawBudget > 0` 时才计费 |
| `StaticProjectile` | 是 | 和 `Emit` 一样，是产出类法术 |
| payload suffix | 当前层不计费 | 等触发时作为新层计费 |
| `null` 法术 | 不计费 | 跳过 |
| 负数 `ManaCost` | 按 0 处理 | 防止负成本回蓝 |

这里最关键的是 `drawBudget`。比如：

```text
BaseDraws = 1
法杖 = 火球 Mana 10 -> 火球 Mana 10
```

当前层只会发第一个火球，所以成本是 10，不是 20。

再比如：

```text
BaseDraws = 1
法杖 = 三重射击 Mana 5 -> 火球 10 -> 火球 10 -> 火球 10
```

三重射击增加额外 draw，当前层会读到并产出 3 个火球，所以成本是：

```text
5 + 10 + 10 + 10 = 35
```

### 4.3 `CastEvaluator.Evaluate`：修正旧的 fizzle 语义

旧逻辑里，Mana 主要是对 `Emit` / `StaticProjectile` 生效；这会造成一个问题：

```text
增伤 Mana 20 -> 三重射击 Mana 10 -> 火球 Mana 5
```

如果 `Modify` 和 `Multicast` 不扣 Mana，玩家就可以免费叠加强力修正类法术，这和你的设计目标冲突。

所以这次把 `Evaluate` 里的 Mana 语义也改了：只要解释器读到某个法术，就先尝试支付它的 `ManaCost`。

这样 `CastEvaluator` 的纯逻辑语义和 runtime 的估算语义保持一致。

注意：runtime 现在采用方案 A，所以 `SpellCaster` 会先估算总成本，够了才调用 `Evaluate`。此时传给 `Evaluate` 的是 `float.PositiveInfinity`，避免二次因为 Mana 中断。`Evaluate` 保留 fizzle 逻辑，是为了单元测试和未来可能的“中途 fizzle”方案保留纯逻辑能力。

### 4.4 `SpellCaster`：施法运行时桥接

文件：

```text
Assets/_Project/Scripts/Character/Spells/SpellCaster.cs
```

它在法术系统中的位置：

```text
CastEvaluator 只产出纯数据 EmitCommand
SpellCaster 把 EmitCommand 变成 Unity 场景里的真实投射物
```

这次改动前，`SpellCaster` 有一个占位字段：

```text
_availableMana = 9999f
```

这代表运行时几乎等于无限 Mana。现在改为：

```text
private ManaComponent _mana;
```

流程变成：

```text
RunCast
-> CastEvaluator.EstimateManaCost
-> TrySpendMana
-> CastEvaluator.Evaluate
-> SpawnForwardProjectile / SpawnSkyfallProjectile
```

`TrySpendMana` 的设计重点：

1. `requiredMana <= 0`：直接允许施法。
2. `_mana == null`：输出 `GameLog.Warn`，临时按无限 Mana 处理。
3. Mana 不足：输出 `GameLog.Info`，返回 false。
4. Mana 足够：调用 `_mana.Spend(requiredMana)`。

为什么 `_mana == null` 时不直接禁止施法？

这是一个工程上的兼容选择。因为你的项目里已经有大量已有测试场景和 Prefab，如果一接入 Mana 就强制要求所有 `SpellCaster` 都配好 `ManaComponent`，很容易导致旧场景全部不能施法，调试体验变差。

所以这次做了软兼容：

```text
没配 ManaComponent -> 给警告 -> 允许施法
```

等功能稳定后，如果你想更严格，可以改成：

```text
没配 ManaComponent -> 不允许施法
```

### 4.5 `PlayerManaBar`：HUD 显示层

文件：

```text
Assets/_Project/Scripts/UI/PlayerManaBar.cs
```

它的职责非常单一：

```text
读取 ManaComponent.Normalized
-> 平滑更新 Image.fillAmount
```

涉及的 Unity API：

| API | 作用 |
|---|---|
| `UnityEngine.UI.Image` | UGUI 图片组件 |
| `Image.fillAmount` | 填充型图片的填充比例，范围 0 到 1 |
| `Mathf.MoveTowards` | 让显示值平滑逼近目标值 |
| `Mathf.Approximately` | 判断两个 float 是否近似相等 |

为什么不用 EventBus？

因为 Mana 是每帧缓慢恢复的连续值。假如每帧都发布 `ManaChangedEvent`，意义不大，还会增加事件噪音。UI 每帧读取一个 float，成本很低，逻辑也直接。

和血条的区别：

- 血量主要由受击事件改变，适合订阅 `DamageReceivedEvent`。
- Mana 会每帧自动恢复，适合 UI 直接轮询 `ManaComponent.Normalized`。

这就是“不是所有 UI 都必须事件驱动”的例子。架构不是死规则，要看数据变化方式。

## 5. 架构设计与脚本拆解

### 5.1 整体架构图

```text
Game.Skills
  SpellDefinition
    - ManaCost
    - Kind
    - Emit / Modify / Multicast / StaticProjectile 数据

  CastEvaluator
    - EstimateManaCost：估算当前层成本
    - Evaluate：解释法术程序，产出 EmitCommand

Game.Combat
  ManaComponent
    - 当前 Mana
    - 最大 Mana
    - 每秒恢复
    - CanSpend / Spend

Game.Character
  SpellCaster
    - 引用 WandLoadout
    - 引用 ManaComponent
    - 施法前检查并扣 Mana
    - 将 EmitCommand 转成真实投射物

Game.UI
  PlayerManaBar
    - 引用 ManaComponent
    - 引用 UGUI Image
    - 更新蓝条 fillAmount
```

### 5.2 为什么这是合理的分层

`Game.Skills`：

只处理法术程序的“数学和规则”，不处理场景对象，不知道玩家是谁，也不知道蓝条 UI 是什么。

`Game.Combat`：

存放战斗状态组件。`ManaComponent` 和 `HealthComponent` 类似，都是挂在角色身上的战斗状态。

`Game.Character`：

处理角色施法行为。`SpellCaster` 是角色和法术系统之间的 runtime 桥。

`Game.UI`：

只做显示，不决定能不能施法。

这符合你项目的依赖方向：

```text
Game.Combat <- Game.Character
Game.Combat <- Game.UI
Game.Skills <- Game.Character
```

UI 不需要引用 `Game.Character`，`Game.Skills` 不需要引用 `Game.Combat.ManaComponent`，所以模块边界没有被破坏。

### 5.4 为什么不把 ManaCost 只算产出类法术

这是一个设计取舍点。

如果只有 `Emit` / `StaticProjectile` 扣 Mana，那么玩家可以免费堆叠：

```text
三重射击 -> 增伤 -> 追踪 -> 重力 -> 轨道 -> 弹跳 -> 火球
```

这会让修正类法术变成“没有代价的增强插件”。随着你的 Modify 越来越多，法术系统会快速膨胀失控。

让所有 `SpellKind` 都消耗 Mana 后，玩家就要考虑：

- 我是否真的需要这个修正？
- 是选择伤害更高，还是蓝耗更低？
- 是稳定输出，还是爆发输出？

这会让法术编程更像“构筑”，而不是无脑堆 buff。

### 5.5 为什么 payload 触发时再扣费

触发类法术有一个特殊点：后续法术不是立刻释放，而是被投射物带出去，等命中或定时后再释放。

如果预付费，会出现：

```text
玩家支付了陨石术 Mana
-> 触发火球没命中
-> 陨石术没出现
```

玩家会觉得蓝被白扣了。

如果触发时再扣费，结果是：

```text
触发火球释放时：只扣触发火球的钱
触发火球命中时：再检查能不能支付陨石术的钱
```

这更符合玩家直觉，也给玩法留下空间：

- 玩家可能在触发前回了一些 Mana。
- 玩家可能故意用低成本触发物，等待触发时再支付高成本 payload。
- 如果触发时 Mana 不够，payload 不释放，这本身也是一种构筑风险。

## 6. 踩坑与 Debug

### 6.1 坑一：不能只在 `SpellCaster` 里简单相加 ManaCost

最直觉的写法是：

```text
遍历 wand.Spells，把所有 ManaCost 加起来
```

这个写法是错的。

原因：

1. `drawBudget` 会限制产出类法术读取数量。
2. `Multicast` 会动态增加 `drawBudget`。
3. 触发类法术会捕获 suffix 并结束当前层。
4. payload 的后续法术不能预扣费。

解决方式：

把估算逻辑放进 `CastEvaluator.EstimateManaCost`，让它镜像解释器的真实读法。

### 6.2 坑二：`Modify` / `Multicast` 也要消耗 Mana

旧的 fizzle 语义更偏向“投射物扣费”，但你明确要求所有类型都消耗 Mana。这是正确的，因为修正类法术也有战斗价值。

解决方式：

在 `Evaluate` 中，`Modify` 和 `Multicast` 分支也调用 `TrySpend`。

### 6.3 坑三：`Game.UI` 不能引用 `Game.Character`

如果把 `ManaComponent` 放在 `Game.Character`，`PlayerManaBar` 想显示蓝条，就要从 `Game.UI` 引用 `Game.Character`。这会破坏项目依赖规则。

解决方式：

把 `ManaComponent` 放在 `Game.Combat`。它是战斗资源组件，放这里符合职责，也符合 asmdef 依赖方向。

### 6.4 坑四：`dotnet build` 不等于 Unity Test Runner 执行测试

开发过程中用 `dotnet build` 可以验证 C# 编译，但它不会真正执行 NUnit EditMode tests。

所以这里要区分：

```text
dotnet build 通过 = 编译没问题
Unity Test Runner 通过 = 测试逻辑真的执行通过
Play Mode 验证通过 = Editor 场景和 Inspector 配置没问题
```

这次静态验证通过了，但蓝条资源拖拽、`Image Type = Filled`、`SpellCaster` 引用等仍然需要 Unity Editor 中验证。

### 6.5 坑五：UI 蓝条需要 `Image Type = Filled`

`PlayerManaBar` 改的是：

```csharp
_fill.fillAmount = _displayFill;
```

但 `fillAmount` 只有在 UGUI `Image` 的 `Type = Filled` 时才有可见效果。如果图片类型是 `Simple`，代码运行了，数值也变了，但画面看起来不会变。

这是 Unity UI 新手非常常见的坑。

## 8. 大厂面试 Q&A

### Q1：为什么 `ManaComponent` 放在 `Game.Combat`，而不是 `Game.Character`？

答：

因为 Mana 是战斗资源状态，不是角色输入或动画状态。`SpellCaster` 在 `Game.Character` 需要扣 Mana，`PlayerManaBar` 在 `Game.UI` 需要显示 Mana。项目的 asmdef 依赖里，`Game.Character` 和 `Game.UI` 都可以依赖 `Game.Combat`，但 `Game.UI` 不应该依赖 `Game.Character`。所以放在 `Game.Combat` 可以同时满足职责和依赖方向。

### Q2：为什么要做 `EstimateManaCost`，而不是直接把法杖里所有法术成本相加？

答：

因为法术系统是解释器，不是静态列表。`Multicast` 会改变 draw budget，`Emit` 和 `StaticProjectile` 只有在预算足够时才会被执行，触发类法术会捕获 suffix 并结束当前层。如果简单全量相加，会把本次不会执行的法术和 payload 后续法术也算进去，导致扣费不符合玩家感知。因此需要一个镜像解释器读取规则的当前层估算函数。

### Q3：为什么 payload 不预扣费？

答：

payload 是未来事件，不一定发生。例如触发投射物可能没命中。如果释放触发投射物时就把后续陨石的 Mana 扣掉，玩家会遇到“没看到效果但资源没了”的负反馈。触发时再扣费更符合因果关系：效果真正发生时才支付成本。同时这也让链式法术有更明确的风险：触发时如果 Mana 不够，payload 不释放。

### Q4：Mana 不足时为什么整层失败，而不是能放几个算几个？

答：

这是方案 A，强调玩家对法术程序的确定性预期。对于法术编程系统来说，玩家通常希望“我配置的这一段程序要么执行，要么不执行”，而不是因为 Mana 不够只发出前半段，导致结果难以预测。尤其在 `Modify` 和 `Multicast` 混合时，中途 fizzle 可能会产生很难理解的半成品行为。当前阶段整层失败更清晰，也更容易调试。

### Q5：为什么 UI 没有通过 EventBus 监听 ManaChangedEvent？

答：

因为 Mana 是连续恢复资源，每帧都会变化。每帧发布事件会产生大量事件噪音，收益不大。UI 直接读取 `ManaComponent.Normalized` 并更新 `Image.fillAmount` 更简单可靠。血条更适合事件驱动，因为血量主要由离散受击事件改变；Mana 更适合轻量轮询，因为它持续恢复。

### Q6：如何避免 Mana 估算和实际执行逻辑不一致？

答：

关键是把估算逻辑放在 `CastEvaluator`，而不是 `SpellCaster`。`CastEvaluator` 是解释器核心，最了解 `drawBudget`、`Multicast`、payload 捕获等规则。并且给 `EstimateManaCost` 写测试，覆盖 `Modify`、`Multicast` 和 payload 不预扣费。这样当解释器语义变化时，测试能提醒我们同步成本规则。

### Q7：如果未来有装备、Buff 减少 ManaCost，怎么扩展？

答：

可以在 `SpellCaster` 估算得到基础成本后，引入一个资源成本修正阶段，例如：

```text
baseCost -> ManaCostModifierPipeline -> finalCost
```

装备、Buff、状态效果都可以在这个 pipeline 中修改成本。为了保持 `Game.Skills` 纯逻辑，`CastEvaluator` 只负责估算基础成本，角色身上的动态修正由 `Game.Character` 或 `Game.Combat` 层处理。

### Q8：这个设计在网络游戏中需要注意什么？

答：

网络游戏里 Mana 扣费应该由服务器权威处理，客户端只能预测显示。客户端点击施法时可以本地预测扣蓝和播放动画，但服务器需要重新校验 Mana、法杖配置、法术成本和触发 payload。payload 触发也要在服务器端再次检查资源，避免客户端作弊释放高成本后续法术。

## 9. 模拟面试者完整讲解

如果我在面试中介绍这个功能，我会这样讲：

我在项目的 Noita-like 法术编程系统中接入了一个恢复型 Mana 资源系统。这个系统的目标不是限制玩家使用法术，而是控制复杂法术组合的释放频率，让玩家在构筑法杖时需要考虑成本和收益。比如简单火球可以频繁释放，而三重射击、增伤、追踪、陨石这类组合虽然爆发高，但会消耗大量 Mana，释放后需要等待蓝条恢复。

架构上我没有把 Mana 写进 `WizardController`，因为那样会把角色输入、动画状态和资源系统耦合在一起。我把 `ManaComponent` 放在 `Game.Combat`，它和 `HealthComponent` 类似，负责保存当前 Mana、最大 Mana、每秒恢复速度，并提供 `CanSpend` 和 `Spend` 接口。这样 `Game.Character` 里的 `SpellCaster` 可以扣 Mana，`Game.UI` 里的 `PlayerManaBar` 也可以读取 Mana，不会破坏项目的 asmdef 依赖方向。

法术系统本身是解释器结构，`WandLoadout` 是程序，`SpellDefinition` 是指令，`CastEvaluator` 是纯逻辑解释器，`SpellCaster` 是 Unity runtime 桥接。因为法杖不是简单技能列表，所以 Mana 成本不能直接把所有格子相加。比如 `Multicast` 会动态增加 draw budget，触发类法术会捕获 suffix 作为 payload 并结束当前层。因此我在 `CastEvaluator` 中新增了 `EstimateManaCost`，它按照当前层真实解释规则估算本次会读到的法术成本。

runtime 流程是：`SpellCaster.RunCast` 先调用 `EstimateManaCost` 得到当前层成本，然后询问 `ManaComponent.CanSpend`。如果 Mana 不够，本层施法整体失败，不生成任何投射物，也不扣 Mana；如果 Mana 足够，就先调用 `Spend` 扣费，再调用 `CastEvaluator.Evaluate` 生成 `EmitCommand`，最后由 `SpellCaster` 实例化投射物或静态投射物。触发类 payload 不是预扣费，而是在命中或定时触发时作为新的一层重新调用 `RunCast`，这样后续法术只有真正发生时才支付成本。

UI 方面我新增了 `PlayerManaBar`，它引用玩家身上的 `ManaComponent` 和一个 UGUI `Image`，每帧读取 `ManaComponent.Normalized`，用 `Mathf.MoveTowards` 平滑更新 `Image.fillAmount`。这里没有使用 EventBus，因为 Mana 是连续恢复资源，每帧都会变化，直接轮询更简单；而血条主要由受击这种离散事件驱动，所以更适合事件。

这次实现里我重点保证了两个边界：第一，所有类型的法术都会消耗 Mana，包括 `Modify` 和 `Multicast`，避免玩家免费堆叠修正法术；第二，payload 不预扣费，避免玩家释放触发投射物但没触发成功时被提前扣掉后续法术成本。整体上这个系统把资源管理和法术解释器结合起来，让法术编程从“随便堆强效果”变成了有成本、有节奏、有构筑取舍的战斗系统。

## 10. 后续可扩展方向

1. 增加 `ManaChangedEvent`：如果未来 Mana 不再每帧恢复，而是更多由离散事件改变，可以再事件化。
2. 增加 Mana 不足反馈：例如蓝条闪烁、音效、屏幕提示。
3. 增加法杖预览成本：在 Wand Editor 中显示当前法杖本层预计 Mana 消耗。
4. 增加动态成本修正：装备、Buff、Debuff 可以改变 `ManaCost`。
5. 增加敌人 Mana：让某些法师敌人也受到资源限制，避免无限施法。
6. 增加 Overheat / Cooldown 混合机制：强力法杖不仅消耗 Mana，还可能增加热量。

## 11. 本功能的学习路线

建议你按这个顺序看代码：

1. 先看 `ManaComponent.cs`：理解资源状态怎么保存和恢复。
2. 再看 `PlayerManaBar.cs`：理解 UI 如何读取资源比例。
3. 再看 `CastEvaluator.EstimateManaCost`：理解为什么法术程序需要“当前层成本估算”。
4. 再看 `CastEvaluator.Evaluate`：理解所有 `SpellKind` 如何扣费。
5. 最后看 `SpellCaster.RunCast`：理解 runtime 如何把 Mana 检查、扣费、法术解释、投射物生成串起来。

这个顺序是从简单状态到复杂解释器，再到 runtime 桥接。不要一上来就看 `SpellCaster`，因为它连接了太多系统，初学时容易迷路。
