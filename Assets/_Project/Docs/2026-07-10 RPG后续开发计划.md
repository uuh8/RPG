# RPG 后续开发计划

创建时间：2026-07-10 16:05

适用项目：Unity 6.3 / URP / 3D RPG / Noita-like 法术编程系统

目标读者：正在学习 Unity 客户端、战斗系统和计算机图形学的开发者

---

## 0. 这份计划解决什么问题

当前项目已经不再是一个只有角色移动和单个攻击的练习项目，而是已经具备以下基础：

- Warrior、Archer、Wizard 三类角色与通用角色状态机。
- 基础 Enemy 系统与近战、远程敌人。
- 统一伤害入口 `IDamageable.ReceiveHit(in DamageRequest)`。
- Noita-like 法术编程解释器：`Emit / Modify / Multicast`。
- 命中触发、定时触发与 payload 后缀捕获。
- 法力上限、消耗、恢复与施法失败规则。
- 弹跳、重力、追踪、轨道等投射物修正。
- 普通投射物、静态投射物、陨石、保护盾、可交互护盾。
- Burning、Wet、Poisoned、Sticky 百分比状态系统。
- 法术编程 UI、血条、法力条和状态 UI。

项目现在面临的核心问题已经不是“还能再加什么法术”，而是：

1. 如何让现有系统形成真正有策略的战斗闭环。
2. 如何把状态、法术、环境和图形表现连接起来。
3. 如何把图形学学习转化为可运行、可分析、可写进作品集的成果。
4. 如何控制 Noita-like 元素世界的规模，不把 RPG 做成一个无底洞式的引擎项目。

因此，后续开发不采用“想到一个法术就做一个法术”的堆内容路线，而采用以下循环：

```text
学习一个原理
-> 制作最小技术实验
-> 接入法术或状态玩法
-> 放进真实战斗场景验证
-> 使用 Profiler / Frame Debugger 检查
-> 形成解析文档、演示视频和面试材料
```

这条循环同时服务三个目标：

- 游戏目标：让法术组合和元素反应真正好玩。
- 学习目标：把数学、Rendering、Shader、GPU 知识变成实践。
- 求职目标：展示架构、图形学、性能和战斗设计的综合能力。

## 1. 总体方向：三条主线并行，但按里程碑汇合

后续项目有三条主线。

### 1.1 主线 A：法术编程与元素玩法

目标是继续强化项目最有辨识度的部分：

```text
法术排列
-> 解释器求值
-> 运行时实体
-> 状态施加
-> 元素反应
-> 环境变化
-> 产生新的组合结果
```

这条线关注“规则是否有涌现性”。

### 1.2 主线 B：图形学与 Rendering

目标不是单纯购买 VFX 资源或堆 Particle System，而是亲自实现一部分可解释的 Rendering 技术：

- 向量、矩阵、坐标空间和 `Quaternion`。
- `Vertex Shader` / `Fragment Shader` 数据流。
- 纹理采样、Noise、UV 动画。
- `Fresnel`、`Emission`、法线和基础光照。
- 深度、透明、混合、`Overdraw`。
- `MaterialPropertyBlock` 与实例级 Shader 参数。
- `Decal`、轨迹、光束和屏幕空间效果。
- `Compute Shader`、GPU Instancing 或 Indirect Rendering 的受控实践。

这条线关注“画面为什么这样产生、性能代价是什么”。

### 1.3 主线 C：战斗验证与完整游戏闭环

法术再复杂，如果敌人只是站着挨打，玩法价值仍然无法证明。该主线负责提供真实验证环境：

- 有明确读招和反制方式的敌人。
- 能检验不同法术组合的 Boss。
- 环境危险、状态弱点和阶段变化。
- 一局游戏中的获取、编程、战斗、奖励循环。

这条线关注“技术是否真的改善游戏体验”。

### 1.4 三条主线怎样汇合

```text
图形学提供可见反馈与空间能力
             |
             v
法术/状态提供可组合的玩法规则
             |
             v
敌人和关卡检验规则是否形成决策
```

每个里程碑至少要同时交付其中两条主线的成果。只做一个漂亮 Shader、不接玩法，不算阶段完成；只加数值规则、玩家看不见结果，也不算完整成果。

### 1.5 世界形态：Hybrid Element World

本项目不照搬 Noita 的二维逐像素世界，也不把整个 3D 场景改造成 Minecraft 式米级方块。三维空间的 Cell 数量会随边长按立方增长；真正的成本不仅是内存，还包括邻域模拟、Mesh/Collider 更新、透明渲染、存档和 AI 寻路。

因此采用 `Hybrid Element World`：

| 层级 | 推荐表示 | 作用 |
|---|---|---|
| 大世界主体 | 普通 Mesh、Terrain、静态场景 | 保持 3D RPG 的画面、Physics 与性能 |
| 可交互元素区域 | 分块的稀疏体素或规则网格 | 仅在局部模拟 Water、Poison、Fire、Sticky |
| 精细视觉 | 自制 Shader、VFX、Decal、粒子与程序化几何 | 隐藏 Cell 粒度，表现连续的流动、扩散和反应 |
| 可破坏对象 | 专门设计的 Destructible Prefab | 受控支持木箱、墙体、柱子等破坏，不承诺任意几何体都可破坏 |
| 角色表面 | `StatusController` | 保存 Burning、Wet、Poisoned、Sticky 等百分比状态 |

必须区分两类数据：

- `StatusKind.Wet` 表示角色表面的潮湿程度。
- 未来 `MaterialKind.Water` 表示空间 Cell 中实际存在的水量。

二者可以进入相同的元素反应语义，但不能强行共用同一个运行时容器。P2 先建立与载体解耦的反应内核；P6 再让局部 Cell 成为新的元素载体。

### 1.6 精细视觉必须自研

水、毒、火、粘液以及蒸汽、燃烧、爆发等核心效果，不直接使用资源商城提供的完成品 Prefab。Prefab 仍然是 Unity 中合理的封装单位，但内部核心视觉必须由项目自行创作并能够解释：

```text
Element Prefab
├── Gameplay Carrier：P2 的 Trigger/Volume，或 P6 的 Cell 数据
├── 自制 Shader / Material
├── 自制或程序化 Mesh
├── 自制 Particle System / VFX Graph
├── 自制 Decal / Light 组合
└── 生命周期、对象池和质量降级控制
```

正式技术路线采用方案 A：

1. 使用 `Shader Graph + Particle System/VFX Graph + Decal` 快速组合完整效果。
2. 选择一个代表性效果，用手写 `HLSL` 重做核心 Shader，并比较数据流、可读性、Shader Variant、Draw Call 与 GPU 成本。
3. 可以使用自制 Noise、基础几何和通用音频素材，但不能依赖无法解释或无法修改的黑盒视觉包。
4. 每种元素表现都必须由 Gameplay 数据驱动；不能只做与规则无关的循环动画。

| 阶段 | 核心成果 | 图形学实践 | 玩法价值 | 优先级 | 当前状态 |

| P2 | 载体解耦的元素反应内核 + 自研元素视觉 | 混合、Decal、深度、VFX 生命周期 | 状态开始产生组合策略 | 最高 | 下一阶段 |

| P5 | Boss 战斗验证切片 | Telegraph、Decal、溶解、Hit Flash | 形成完整战斗闭环 | 高 | 未开始 |

## 3. P0：建立可持续开发基线

### 3.1 阶段目标

在继续加玩法之前，先让现有法术系统变得“可观察”。复杂组合最难 Debug 的地方，是玩家只看到最终效果，却不知道解释器、运行时和投射物分别做了什么。

本阶段不追求新玩法，追求让后面每次开发都更快。

### 3.2 具体任务

#### 任务 A：法术求值 Trace

为开发环境提供一次施法的结构化 Trace：

```text
输入 WandLoadout
-> 读取哪些 SpellDefinition
-> draw budget 如何变化
-> 修正状态怎样累积
-> 输出多少 EmitCommand
-> 每个 EmitCommand 的最终 mana、damage、speed、motion、payload
```

要求：

- Trace 只在 `UNITY_EDITOR` 或 `DEVELOPMENT_BUILD` 可用。
- 使用 `GameLog`，不使用 `Debug.Log`。
- 正常 Release 不承担字符串拼接和 boxing 开销。
- 能通过开关关闭，避免 Console 被每帧刷屏。

#### 任务 B：投射物空间 Debug Gizmos

在 Scene View 可选择显示：

- 当前速度向量。
- 碰撞法线。
- 反射方向。
- Homing 搜索半径与当前目标。
- Orbit 圆心、半径、局部旋转轴。
- Gravity 加速度方向。

对应图形学知识：

- 向量加减。
- `Dot Product`。
- `Cross Product`。
- 向量投影与分解。
- 世界空间和局部空间转换。

#### 任务 C：建立性能基线场景

建立一个专用测试场景，至少包含：

- 单发普通火球。
- 三重射击。
- 触发嵌套。
- 轨道 + 追踪组合。
- 多个状态同时存在。
- 50、100、200 个活跃投射物的压力档位。

记录：

- Main Thread 时间。
- Render Thread 时间。
- `Batches` / `SetPass Calls`。
- 活跃投射物数量。
- 每帧 `GC Alloc`。
- 状态 VFX 数量。

### 3.3 架构落点

- `Game.Skills`：提供纯求值 Trace 数据或可选诊断结果。
- `Game.Character`：记录 `SpellCaster` 的 runtime bridge 输出。
- `Game.Combat`：提供投射物 Gizmos 和活跃数量统计。
- `Game.Rendering`：仅负责绘制调试信息，不修改 Combat 数据。

不要让正式玩法逻辑依赖 Debug 系统。

### 3.4 完成标准

- 看到一个异常法术时，能在 5 分钟内判断错误位于求值层、运行时桥接层还是投射物层。
- Profiler 中普通战斗热路径保持 0 B `GC Alloc`。
- 压力测试能够稳定复现，不依赖手工临时摆场景。
- 形成一页“法术系统 Debug 链路”笔记。

## 4. P1：状态可视化 2.0，完成第一组图形学成果

### 4.1 玩家最终看到什么

当前状态主要依靠 Icon、百分比和独立 VFX 表达。升级后，角色本体的材质表现也会随状态强度连续变化：

- Burning 越高，表面火焰边缘和 `Emission` 越明显。
- Wet 越高，表面高光越强，产生水膜感。
- Poisoned 越高，颜色扰动、流动纹理越明显。
- Sticky 越高，局部粘液覆盖或拖尾越明显。
- 状态从 100% 衰减到 0% 时，表现连续减弱，而不是突然消失。

### 4.2 为什么把它作为第一个图形学项目

它已经有完整 Gameplay 数据源：`StatusController` 的 `Intensity`。图形学层不需要先发明新规则，只需要学习怎样把 0-100 的状态值转成像素结果。

这是最清晰的数据链：

```text
StatusController.Intensity
-> StatusChangedEvent / Rendering Bridge
-> MaterialPropertyBlock
-> Shader Property
-> Vertex/Fragment 计算
-> 玩家看到连续视觉变化
```

### 4.3 具体任务

#### 任务 A：状态材质参数桥

建立只负责表现的组件，将状态百分比写入 Shader：

```text
_BurningIntensity
_WetIntensity
_PoisonIntensity
_StickyIntensity
```

使用 `MaterialPropertyBlock`，不要通过 `renderer.material` 为每个角色复制 Material。

需要理解：

- Shared Material 与实例参数的区别。
- 为什么访问 `renderer.material` 可能生成材质实例。
- `MaterialPropertyBlock` 如何保持同材质的批处理机会。
- Gameplay 层不能直接引用具体 Shader。

#### 任务 B：Burning Shader

第一版只做三个效果：

1. Noise 驱动的边缘扰动或遮罩。
2. 状态强度控制的 `Emission`。
3. 世界空间或对象空间的向上流动。

重点知识：UV、纹理采样、Time、坐标空间、颜色 HDR、Bloom 与 `Emission` 的关系。

#### 任务 C：Wet Shader

第一版目标：

- 增强 `Specular`。
- 调整 Smoothness。
- 使用 `Fresnel` 或视线与法线夹角，让边缘水膜更明显。

重点知识：法线、视线方向、`Dot Product`、`N dot V`、光照模型。

#### 任务 D：Poisoned / Sticky 表现

不要一次做两个复杂 Shader。推荐：

- Poisoned：流动 Noise + 颜色混合。
- Sticky：Particle 拖尾或地面 `Decal`，先不做复杂表面流体。

#### 任务 E：强度混合与多状态共存

验证：

- Burning + Wet 同时存在时，两种参数可以同时传入。
- Shader 有明确优先级或混合规则。
- 不因为状态组合而生成新的 Material。

### 4.4 技术选型

学习顺序建议：

1. 先用 Shader Graph 快速验证视觉公式。
2. 选 Burning 或 Wet 中的一个，用手写 HLSL 重做核心部分。
3. 对比两种实现生成的 Shader、可读性和性能。

不要把“会使用 Shader Graph 节点”误认为已经理解 Rendering。必须能够解释：

- 顶点数据怎样进入 `Vertex Shader`。
- 插值后怎样进入 `Fragment Shader`。
- 当前公式运行在每顶点还是每像素。
- 透明、Blend 和 ZWrite 为什么会影响排序与 Overdraw。

### 4.5 完成标准

- 四种状态至少有两种自制 Shader 表现，另外两种可以先使用 VFX/Decal。
- 状态强度变化能够连续驱动画面。
- 10 个角色共享材质时，不生成 10 份独立 Material。
- 使用 Frame Debugger 解释主要 Draw Call。
- 使用 Profiler 检查状态更新没有产生持续 GC。
- 产出一份状态 Rendering 解析和 30-60 秒对比视频。

## 5. P2：载体解耦的元素反应内核与自研视觉 MVP

### 5.1 阶段目标与边界

状态系统目前解决“角色身上有什么”，本阶段解决“不同元素相遇会发生什么”。P2 是 Noita-like 元素玩法开始产生涌现性的地方，也是未来有限元素场的规则基础。

P2 不实现细粒度流体、稀疏体素和任意地形破坏。环境仍使用简单 `Trigger/Volume` 作为 Gameplay 载体，但水、毒、火、粘液及其反应表现必须由项目自行制作。真正的 Cell 流动、扩散和物质转换留到 P6。

> **2026-07-15 执行状态：** P2 的状态规则、Reaction Kernel、`StatusVolume`、Water 自研 Shader 与 Fire 5A～5D Body/Core/Sparks 已达到 `P2 Core / Demo Gate`，足以支撑 Water/Fire Cell 垂直切片。Steam、Poison/Sticky 环境视觉、Toxic/Ignite 高级反馈、Decal、Pooling 和完整性能收口继续保留为 `P2 Visual Polish Backlog`，没有删除，也不计为已经完成。

### 5.2 第一批正式反应

| 输入状态 | 反应 | Gameplay 结果 | 自研视觉结果 |
|---|---|---|---|
| Burning + Wet | Extinguish | Burning 快速下降，Wet 同时消耗 | 蒸汽上升、湿润消退、短暂冷色到灰白色过渡 |
| Burning + Sticky | Ignite Goo | Sticky 消耗，Burning 强度或持续伤害提高 | 粘液亮边点燃、局部火舌与地面焦痕 Decal |
| Poisoned + Burning | Toxic Combustion | 消耗部分 Poisoned，触发一次小范围爆发 | 毒色体积收缩后爆开、冲击环与短生命周期残留 |

第一版只实现以上三条。`Wet + Ice -> Freeze` 等规则等冰系来源出现后再设计，避免提前扩张枚举与表现资产。

### 5.3 架构核心：Reaction Kernel 与载体分离

P2 的核心不是在 `StatusController` 中继续增加 `if`，而是建立纯规则求值链：

```text
Element Snapshot + Reaction Definition
-> Reaction Evaluator（纯逻辑）
-> Reaction Result
   ├── 消耗哪些输入与多少强度
   ├── 施加哪些输出状态
   ├── 是否产生伤害/范围效果
   ├── ReactionId / 表现上下文
   └── 冷却与连锁控制事实
```

运行时适配器负责把纯结果写回具体载体：

```text
P2：StatusController Adapter -> 修改角色状态
P6：ElementField Adapter   -> 修改 Material Cell
```

必须迁移并删除当前 `StatusController` 内 `Burning + Wet` 的硬编码加速衰减，避免旧规则与新规则重复结算。反应求值需要确定性顺序、单次求值输出上限、同反应冷却，以及明确的同帧连锁策略。

### 5.4 具体任务

#### 任务 A：反应规则数据

引入 `StatusReactionDefinition` 或更通用的等价数据结构，至少描述：

- 稳定的 `ReactionId` 与显示名称。
- 输入元素、最低强度阈值与每次消耗量。
- 输出状态、即时伤害或范围效果。
- 优先级、冷却时间与是否允许参与连锁。
- 表现层使用的视觉/音频标识，不直接保存 Rendering 执行逻辑。

规则资产由 `Game.Combat` 读取，不写进 `Fireball`、角色 Controller 或具体 VFX Prefab。

#### 任务 B：纯规则求值与测试

使用不可变输入快照求值，至少验证：

- 强度刚好等于阈值时能触发，低于阈值时不能触发。
- 消耗后强度 Clamp 到 0，不出现负值。
- 多条规则同时满足时按明确优先级得到稳定结果。
- 默认不在同一次求值中递归读取刚生成的输出；需要连锁时进入下一次受预算限制的求值。
- 冷却中的相同反应不会每帧重复触发。
- 单次最大反应数量达到预算后安全停止。

#### 任务 C：角色状态运行时适配

让 `StatusController` 提供受控的快照读取和强度消耗接口，由反应协调器统一调用。`StatusController` 仍然拥有角色状态、自然衰减、DoT 与移动倍率；纯求值器不引用 `MonoBehaviour`、Scene 对象或 VFX。

状态来源和击杀归属必须保留 `SourceId / SourceTeam` 快照。反应伤害需要在详细计划中明确归属规则，不能默认为环境或丢失攻击者。

#### 任务 D：简单环境载体

P2 建立四种 `Trigger/Volume` 原型：

- 水池：按固定 tick 施加 Wet。
- 毒雾：按固定 tick 施加 Poisoned。
- 粘液地面：按固定 tick 施加 Sticky。
- 火焰区域：按固定 tick 施加 Burning。

它们只通过统一状态接口施加元素，不直接修改角色速度、血量、材质或 UI。Physics 查询复用 Buffer，持续区域不得在 `Update` 中产生 GC Alloc。

#### 任务 E：反应事件与表现桥

Combat 在确定反应已经结算后发布值类型 `ElementReactionEvent`：

```text
Combat Reaction Kernel
-> 写回 Gameplay 结果
-> 发布 ElementReactionEvent（ReactionId、位置、方向、强度、TargetId）
-> Game.Rendering 选择并播放对应自研表现
```

Gameplay 不直接引用具体 VFX Prefab。表现层可以丢弃低优先级效果或使用对象池降级，但不能反向修改反应结果。

### 5.5 自研精细视觉交付

本阶段不从资源商城导入完成的水池、火堆、毒池或粘液 Prefab。可以使用 Prefab 组织自制组件和资源，但必须保留可学习、可调试的源资产。

| 元素/反应 | 自研组成 | 重点知识 |
|---|---|---|
| Water | 简单水面 Mesh、Shader Graph 水材质、法线/Noise 扰动、深度颜色与边缘过渡 | UV、法线、`Fresnel`、Scene Depth、透明排序 |
| Fire | Particle System 或 VFX Graph、Additive/Alpha 混合火焰材质、HDR Emission | 粒子生命周期、颜色曲线、Blend、Bloom、Overdraw |
| Poison | 半透明体积粒子、滚动 Noise、接地软边缘 | 深度淡化、Noise、透明层叠、颜色可读性 |
| Sticky | 地表 Mesh/Decal、UV 扭曲、高光与缓慢流动 | Decal 投影、切线空间、Smoothness、流动错觉 |
| Steam | 水火反应粒子、上升速度与尺度曲线 | 生命周期、透明排序、低频 Noise |
| Ignite Goo | 点燃遮罩、局部火焰、焦痕 Decal | 遮罩混合、HDR、地表法线 |
| Toxic Combustion | 收缩预备、爆发粒子、冲击环与残留 | 时间曲线、Billboard、Additive、效果分层 |

至少选择 Water 的核心表面 Shader 用手写 `HLSL` 重做，并与 Shader Graph 版本比较。比较重点不是肉眼谁更漂亮，而是 `Vertex/Fragment` 数据流、属性组织、生成代码、Shader Variant、Draw Call 与 GPU 时间。

资产依赖原则：

- Noise/Mask 优先通过 Shader 或项目内工具生成；如使用贴图，保存源文件和生成说明。
- 基础 Mesh 使用 Unity Primitive、自建低模或程序化生成，不依赖商城成品模型。
- P2 的视觉 MVP 不强制外部音频；缺少 SFX 时允许静音占位。正式音频建议使用 48 kHz、16/24-bit WAV，导入后按用途选择压缩设置。
- 每个视觉 Prefab 都要有目的、生命周期、最大并发数、目标路径和无资源 fallback，详细值在 P2 实施计划中锁定。

### 5.6 分阶段交付与 Editor Gate

#### P2-A：反应内核 + Fire/Water + Extinguish

- 完成纯 `Reaction Kernel`、规则资产和状态适配。
- 迁移旧的 Wet 灭火硬编码。
- 完成自研 Fire、Water、Steam 原型。
- 用户在 Unity Editor 验证规则、画面、0 B 热路径 GC 后再进入 P2-B。

#### P2-B：Poison/Sticky + 两条进阶反应

- 完成自研 Poison、Sticky 环境表现。
- 完成 Ignite Goo 与 Toxic Combustion 的 Gameplay 和视觉反馈。
- 验证三条反应的优先级、冷却、伤害归属和组合行为。

#### P2-C：生命周期、Decal 与性能收口

- 对短生命周期反应 VFX 评估并接入对象池。
- 设定最大并发、距离裁剪与低优先级效果降级。
- 使用 Profiler、Frame Debugger 和 Overdraw 视图检查 CPU/GPU 成本。
- 产出 Shader Graph 与手写 HLSL 对比、反应数据流图和演示视频。

### 5.7 完成标准

- 三个元素反应都能由法术与环境载体触发。
- 反应规则不写死在 `Fireball`、角色、环境 Trigger 或 VFX 中。
- P2 的规则核心未来可由 `ElementField Adapter` 复用，不依赖 `StatusController` 才能求值。
- 每条反应都有 EditMode 边界测试；关键运行时链路有 PlayMode/Editor 验证清单。
- 同一反应有冷却与输出预算，不会每帧爆发或形成无上限连锁。
- 水、毒、火、粘液及三种反应视觉均为项目自研，而不是商城完成品。
- 玩家不看数值，也能通过颜色、形态、时序和声音区分反应。
- 稳定状态和反应热路径保持 0 B `GC Alloc`；透明效果的 Overdraw 与最大并发有记录。

## 6. P3：重构修正冲突模型与投射物运动管线

### 6.1 为什么这个阶段必须做

现有 Modify 已经包含重力、追踪、轨道、弹跳、增速和增伤。随着修正增加，以下冲突会越来越多：

- Orbit 想控制位置，Homing 想控制方向。
- Gravity 每帧改变速度，某些轨道逻辑可能直接覆盖速度。
- 投射物 prefab 有天生运动特性，法术修正又想覆盖它。
- 后出现的修正是否覆盖前面的修正，需要统一规则。

如果继续在 `ProjectileBase` 中不断增加 `if` 和 `switch`，最终每增加一个修正，都要重新测试所有旧修正组合。

### 6.2 推荐的修正规则

把修正分为三类通道：

#### 数值通道：可以组合

- Damage Add / Multiply。
- Speed Add / Multiply。
- Bounce Count。
- Lifetime。
- Scale。

它们按明确的加法、乘法和 clamp 顺序合成。

#### 独立行为通道：可以共存

- Gravity。
- Bounce。
- Trail。
- OnHit 状态施加。
- Payload Trigger。

这些功能通常不争夺同一个最终方向，可以同时保留。

#### 运动主导通道：互斥或按优先级覆盖

- Straight。
- Homing。
- Orbit。
- Future Beam / Boomerang / Sine Motion。

第一版采用确定性规则：同一运动主导通道中，法杖里更靠后的 Modify 获得更高优先级。投射物 prefab 的天生运动是 Base Layer，法术修正是 Override Layer。

### 6.3 运动更新顺序

建议形成明确的运动步骤：

```text
读取上帧 Rigidbody 状态
-> 主导运动计算 desired velocity/direction
-> Gravity 等独立加速度叠加
-> Speed 约束
-> 碰撞和 Bounce 由 Physics 处理
-> 朝向跟随最终速度
```

重点不是一定使用某个 Design Pattern，而是所有投射物必须遵守同一更新顺序。

### 6.4 图形学与数学实践

- 局部坐标系与正交基。
- 向量投影、拒绝分量和分解。
- `Quaternion.LookRotation` 与旋转插值。
- `Vector3.RotateTowards`。
- 参数曲线、角速度和线速度。
- `FixedUpdate`、Rigidbody 与离散物理步进。

### 6.5 具体任务

- 为 `CastModifierState` 明确每个字段所属通道。
- 让 `EmitCommand` 保存最终、不可变的修正快照。
- 建立 prefab 默认值与法术覆盖值的合并规则。
- 为冲突规则添加 EditMode 测试。
- 为典型组合建立 Play Mode 验证矩阵。
- UI Tooltip 显示“后置运动修正会覆盖前置运动修正”。

### 6.6 组合验证矩阵

至少验证：

| 组合 | 预期 |
|---|---|
| Gravity -> Homing | Homing 主导转向，同时保留重力 |
| Homing -> Orbit | Orbit 覆盖 Homing 主导权 |
| Orbit -> Homing | Homing 覆盖 Orbit 主导权 |
| SpeedUp -> Gravity | 速度修正和重力共存 |
| Bounce -> Homing | 反弹后继续搜索或追踪目标 |
| prefab 天生追踪 -> Orbit | 法术 Orbit 覆盖 prefab 基础追踪 |

### 6.7 完成标准

- 新增运动修正时，不需要修改所有旧修正脚本。
- 同一法杖排列始终得到确定结果。
- 玩家能够通过“后面的优先”预测冲突结果。
- 关键数学过程能用 Gizmos 解释。
- 运动热路径没有 LINQ、闭包和每帧分配。

## 7. P4：光束类与空间型法术

### 7.1 阶段目标

目前绝大多数 Emit 最终都会生成 `ProjectileBase`。为了让法术语言继续成长，需要验证一个重要问题：`Emit` 是否只能生成飞行投射物，还是能生成更广义的运行时效果。

推荐新增第一种非传统 Emit：光束类法术。

### 7.2 第一版光束玩法

- 从施法点向瞄准方向发射持续很短的 Beam。
- 使用 Raycast 或 SphereCast 计算命中。
- 对命中目标造成一次伤害或短周期伤害。
- 命中墙面时截断，不穿透所有几何体。
- 可以被增伤、法力、散射、多重等通用修正影响。
- 第一版不要求所有 Projectile Motion Modify 都对 Beam 有意义。

### 7.3 第二版：反射光束

在第一版稳定后增加有限次数反射：

```text
reflection = direction - 2 * dot(direction, normal) * normal
```

每次 Raycast 获得碰撞法线，计算下一段方向。必须设置最大反射次数和最大总距离，避免无限循环。

### 7.4 架构设计重点

不要让 `CastEvaluator` 直接认识 Raycast。纯求值层只输出足够的数据：

```text
EmitCommand
-> RuntimeKind = Projectile / Beam / Field
-> damage / range / width / duration / modifiers
```

`SpellCaster` 或更通用的 runtime bridge 根据 `RuntimeKind` 选择具体运行时执行器。

这一步会检验当前 `EmitCommand` 是否把“Emit”错误地等同于“Projectile prefab”。如果需要重构，必须先写 spec 和 plan，分阶段迁移旧法术。

### 7.5 图形学实践

- Ray、Line、Plane 和法线。
- 反射向量。
- 相机朝向与瞄准射线。
- Procedural Mesh 或 LineRenderer 的取舍。
- Beam UV 沿长度滚动。
- Additive Blend、深度交界和软边缘。
- 多段光束连接处的视觉连续性。

### 7.6 后续空间型法术候选

按优先级考虑：

1. 反射光束。
2. 穿透光束。
3. 锥形喷射法术。
4. 圆盘/扇面领域。
5. 折射光束。
6. 传送门类空间法术。

一次只做一个，不并行展开。

### 7.7 完成标准

- 光束作为正式 SpellDefinition 进入法术编程 UI。
- 光束能与至少三种通用修正组合。
- 反射次数、总距离、命中去重都有硬上限。
- Scene View 能显示每段 Ray 和碰撞法线。
- 能解释 Beam Shader 的坐标、UV、Blend 和深度问题。

## 8. P5：制作一场能验证法术系统的 Boss 战

### 8.1 阶段目标

这一阶段不是为了展示 AI 数量，而是制作一个“系统考题”。Boss 必须迫使玩家使用法术编程、状态反应、空间判断和资源管理。

### 8.2 Boss 设计建议：元素构装体

Boss 分为三个阶段：

#### Phase 1：移动与瞄准考验

- 远程直线攻击。
- 地面 Telegraph 后的范围攻击。
- 玩家需要使用移动、冲刺和基础法术输出。

#### Phase 2：元素状态考验

- Boss 获得火焰或毒素形态。
- 特定状态能够削弱护甲、打断蓄力或改变攻击模式。
- 环境中出现水池、毒雾或粘液区域。

#### Phase 3：法术组合考验

- Boss 提高移动速度或召唤护盾。
- 单发高伤法术难以命中，需要 Homing、Multicast、Trigger 或 Beam 组合。
- 玩家要在法力恢复节奏中选择爆发窗口。

### 8.3 AI 与架构任务

- 在现有 `EnemyStateMachine` 上增加 Boss 专属状态，不重写第二套 AI 框架。
- 使用 `BossDefinition` 或组合式数据定义阶段阈值、招式表和冷却。
- Telegraph 与伤害判定分离：先发布预警，再在明确时刻结算伤害。
- Boss 状态抗性通过 Combat 数据表达，不写进 UI。
- 通过 EventBus 驱动 Boss UI、音乐和阶段表现。

### 8.4 图形学实践

- 地面 Telegraph：Decal、投影、深度和透明混合。
- Boss Hit Flash：Shader 参数和时间曲线。
- 阶段转换：Dissolve、Emission、Noise。
- 死亡效果：溶解或 Mesh 粒子，不只调用 `Destroy`。
- 状态弱点：材质颜色、Fresnel 或局部特效反馈。

### 8.5 战斗设计验收

玩家必须能回答：

- Boss 下一招是什么，依据哪个视觉信号判断？
- 为什么此时使用 Wet、Burning 或 Poisoned？
- 为什么选择 Homing、Trigger、Multicast 或 Beam？
- 什么时候应该等待 mana 恢复，什么时候应该释放长法术链？

如果最优策略仍然只是连续发射同一个普通火球，说明 Boss 没有真正检验法术系统。

### 8.6 完成标准

- 一场 3-5 分钟、可重复游玩的 Boss 战。
- 至少三个阶段或两个阶段加一个明显 Enrage。
- Telegraph 清晰，伤害判定与画面时间一致。
- 至少两种不同法术 Build 都能通关，且打法明显不同。
- 录制一段完整演示视频，并保存一份 Boss 设计复盘。

## 9. P6：有限元素场实验室，不直接做完整沙盒世界

### 9.1 阶段边界

本阶段开始接近最初的 Noita-like 元素世界设想，但范围必须被严格限制：

- 不生成无限世界。
- 不追求每个像素都是物质。
- 不做物理精确的 Navier-Stokes 流体。
- 不一开始就做 Marching Cubes。
- 不让整个主场景都变成可破坏体素。

第一目标是一个独立、有限、可关闭的“元素实验房”。

P6 不重新发明元素反应和视觉语言。它复用 P2 的 `Reaction Kernel` 与自研 Water/Poison/Fire/Sticky 表现，只新增空间 Cell 载体、局部模拟和批量 Rendering Bridge。

> **当前先执行 P6-A Water/Fire Vertical Slice：** 第一轮只使用 Water 与 Fire，在 `32 × 16 × 32`、`0.25m Cell`、`10 Hz` 的有限实验房中完成“法术写入 → Cell 模拟 → Water/Fire 反应 → 角色 Wet/Burning → 自研连续视觉”的双向闭环。Poison、Sticky、GPU Instancing、ComputeBuffer/Compute Shader 和 `64 × 32 × 64` 压力规模仍属于后续完整 P6，不因 P6-A 完成而自动勾选。

### 9.2 建议的第一版规模

先建立低风险正确性网格，再在预算允许时提高粒度：

```text
正确性基线：32 x 16 x 32 = 16,384 Cells
目标实验房：8m x 4m x 8m，0.125m Cell
             64 x 32 x 64 = 131,072 Cells
```

Cell 是 Gameplay 数据分辨率，不要求玩家看到一个个方块。最终通过连续表面、粒子、Decal 或实例化几何隐藏格子感。若 131,072 Cells 超出 CPU/GPU 预算，应降低活跃范围或模拟频率，而不是无条件维持目标分辨率。

每个 Cell 只保存必要数据：

- MaterialKind：Air / Water / Poison / Sticky / Fire。
- Amount：0-255。
- Temperature：第一版可以暂不加入。
- Flags：本 tick 是否活跃。

模拟不需要每帧更新。可以使用固定低频 tick，例如 5-10 Hz，并只更新 Active Cells。

### 9.3 第一版规则

- Water 向较低相邻格移动。
- Fire 消耗可燃 Material，并产生短生命周期。
- Water 接触 Fire 后双方消耗，产生 Steam 表现事件。
- Poison 接触 Fire 后触发小范围 Toxic Combustion。
- 角色进入对应区域时，通过统一接口施加 Wet/Poisoned/Sticky/Burning。
- 法术命中网格时可以写入、移除或转换少量 Cell。
- Cell 反应通过适配器调用 P2 的纯反应语义；`MaterialKind.Water` 与角色 `StatusKind.Wet` 保持数据模型分离。

### 9.4 CPU 与 GPU 分期

#### 阶段 1：CPU 规则正确性

- 使用紧凑数组存储 Cell。
- 固定 tick。
- Active Set 或 Dirty Region。
- 先用简单 Gizmos/实例显示结果。
- 给反应规则写测试。

#### 阶段 2：GPU 表现

- 使用 `ComputeBuffer` 或 GraphicsBuffer 传递可见 Cell。
- 使用 GPU Instancing 绘制大量相似元素。
- 将 P2 自研材质升级为读取 Cell/Chunk 数据的批量表现，不替换成商城元素 Prefab。
- 水面、毒雾、火焰与粘液允许采用不同 Rendering 策略，不强求所有元素共享一种 Mesh 生成方式。
- 尝试 `Compute Shader` 做并行状态更新前，先解决双缓冲和邻居读取问题。

#### 阶段 3：更高级表面表现，可选

- 水面 Mesh 或 Screen-space 表现。
- Volume/雾。
- Marching Cubes 或 Surface Nets。

第三阶段不是必做项。面试作品中，一个规则清晰、性能受控的有限元素场，比一个不稳定的“伪无限世界”更有价值。

### 9.5 需要重点学习的图形学/GPU知识

- 规则网格与数据布局。
- CPU Cache 与连续内存。
- `Compute Shader` Thread Group。
- GPU 并行读写冲突。
- 双缓冲 Ping-Pong。
- GPU Instancing。
- Indirect Draw。
- Frustum Culling。
- 透明对象的排序问题。
- CPU-GPU 同步和 Readback 成本。

### 9.6 性能护栏

开发前先写死预算：

- 最大网格尺寸。
- 每 tick 最大活跃 Cell 数。
- 最大反应次数。
- 最大可见实例数量。
- 最大 CPU 模拟耗时。
- 最大 GPU 绘制耗时。

建议第一阶段目标不是“越多越好”，而是在目标机器上让元素场 CPU 与 GPU 各自稳定控制在明确预算内。

### 9.7 完成标准

- 元素实验房可以独立启用和关闭。
- 水、火、毒至少有两种真实反应。
- 法术能改变元素场，元素场能反向施加角色状态。
- Cell 粒度被自研连续视觉隐藏，玩家不会把实验房看成简单的小方块堆叠。
- 相同 Seed 和输入能得到可复现结果，或明确记录非确定性来源。
- Profiler 中能区分模拟成本和渲染成本。
- 规模超过预算时会降级或拒绝生成，而不是直接卡死。

---

## 10. P7：构建一局可玩的 Roguelite 闭环

### 10.1 为什么放到后面

法术编程的乐趣不仅来自组合，还来自“当前拿到什么，就用什么解决问题”。因此最终需要获取、编程、测试和奖励循环。但如果过早做随机地图、掉落和存档，会分散玩法核心开发。

### 10.2 第一版单局流程

```text
进入起始房
-> 获得少量随机法术
-> 在安全区编辑 WandLoadout
-> 通过普通战斗房
-> 获得新法术或恢复资源
-> 进入元素环境房
-> 再次调整法术组合
-> Boss 战
-> 结算本局
```

### 10.3 具体任务

- 法术掉落与拾取。
- 法术库存和编程框之间的正式数据分离。
- Seeded Random，保证可复现 Debug。
- 房间模板与连接规则，不做完全自由的程序化几何。
- 法术稀有度、基础权重和最小保底。
- 一局内临时数据与永久资产分离，避免 Play Mode 修改 ScriptableObject。
- 暂停、失败、重新开始和结算流程。

### 10.4 图形学实践

- 不同房间的 Lighting 与后处理分区。
- 元素区域的体积雾和颜色管理。
- 法术拾取物的轮廓、Fresnel 或 Dissolve。
- 基于距离的 LOD 和 VFX 降级。

### 10.5 完成标准

- 从开始到 Boss 结算形成 10-15 分钟完整流程。
- 每局至少有一次“因为获得新法术而修改组合”的决策。
- 固定 Seed 可以复现房间和掉落。
- 退出 Play Mode 后不会污染用于编辑的原始 ScriptableObject。

## 11. P8：性能、工程化与作品集收口

### 11.1 这不是最后才做的事情

性能检查应在每个阶段进行，P8 只是集中收口。不要等所有系统完成后才第一次打开 Profiler。

### 11.2 CPU 侧检查

- `Update` / `FixedUpdate` 中 0 B `GC Alloc`。
- 不在 hot path 使用 LINQ、closure、boxing。
- Physics 查询使用 NonAlloc 版本或复用 Buffer。
- 投射物、状态 VFX 和反应 VFX评估对象池。
- 触发 payload 有递归深度、输出数量和活跃实体预算。
- 元素网格只更新 Active Region。

### 11.3 GPU 侧检查

- Frame Debugger 检查 Draw Call 和 Pass。
- 检查透明 VFX 的 `Overdraw`。
- 检查 Shader Variant 数量。
- 检查 Material 实例化和批处理破坏。
- 用 RenderDoc 或 Unity Rendering Debugger 查看目标帧。
- 为低优先级 VFX 设置距离、数量和质量降级。

### 11.4 工程化收口

- 清理 `_Debug` 临时代码或放入明确的开发工具路径。
- 补齐 asmdef 与依赖检查。
- 核心纯逻辑全部有 EditMode 测试。
- 建立最小 PlayMode 集成测试。
- 建立统一 GameLog 分类。
- 检查 EventBus 订阅释放和场景切换清理。
- 将运行时 WandLoadout 与编辑资产分离。
- 整理 Inspector 字段和 Tooltip，减少配置错误。

### 11.5 作品集交付物

最终至少准备：

1. 2-3 分钟核心玩法视频。
2. 30 秒法术组合快速展示。
3. 一张系统架构图。
4. 一张状态/元素反应数据流图。
5. 一组 Shader 前后对比图。
6. 一张 Profiler 或 Frame Debugger 分析图。
7. 一个完整 Boss 战视频。
8. 一篇技术总结：法术解释器、Rendering 或元素场三选一深入讲。
9. 简历上的三到五条量化描述。

## 12. 推荐的实际执行节奏

不按“先把课程学完”安排，而按问题驱动安排。每个功能采用以下循环。

### 第一步：玩法问题

先用一句话定义玩家问题，例如：

```text
玩家看不出 Burning 强度，只能看 UI 数字。
```

### 第二步：理论问题

把它转成需要学习的知识：

```text
怎样把状态强度传入 Shader？
怎样利用法线和视线方向制造湿润边缘？
```

### 第三步：最小实验

在独立材质球、测试角色或测试场景验证一个公式，不先接整个系统。

### 第四步：工程接入

确定数据由谁拥有、谁只消费结果、跨 asmdef 怎样通信。

### 第五步：真实组合验证

不能只测单一效果。例如 Wet Shader 完成后，要验证 Wet + Burning 同时存在。

### 第六步：性能验证

记录 CPU、GPU、GC、Draw Call、Overdraw，不凭肉眼判断性能。

### 第七步：学习输出

每个阶段至少留下：

- 一份中文解析文档。
- 一张数据流或架构图。
- 一个短视频或 GIF。
- 一个可回答的面试问题。

---

## 13. 每个阶段都必须回答的五个问题

开发任何新功能前，先回答：

1. 玩家会看到什么不同？
2. 这个功能增加了什么决策，而不只是增加什么特效？
3. 数据归谁拥有，运行时由谁执行，表现由谁显示？
4. 最坏情况下会生成多少对象、多少 Draw Call、多少递归或多少 Cell？
5. 完成后怎样证明它有效，而不是“看起来应该能用”？

如果其中两个问题答不出来，功能还不适合进入实现。

## 14. 明确暂时不做的内容

以下内容并非永远不做，而是当前收益不足以覆盖成本：

- 无限体素世界。
- 物理精确流体。
- 自研完整 Scriptable Render Pipeline。
- 全场景任意几何破坏。
- 光线追踪作为主渲染方案。
- 大规模联机同步。
- 数百种法术内容堆叠。
- 多法杖、复杂词条、装备锻造同时展开。
- 在元素规则还没有验证前制作复杂程序化世界。
- 用资源商城完成品替代水、毒、火、粘液及核心反应的自研视觉过程。

这些功能容易让项目规模迅速膨胀，却未必能增强“法术编程 + 元素反应 + 3D 空间”的核心辨识度。

## 15. 最近三个开发阶段的建议顺序

不要一次规划半年后每天写什么。当前只锁定最近三个阶段：

### 近期第一阶段：P0 开发基线

成果：法术 Trace、运动 Gizmos、性能测试场景。

原因：它会降低后面所有图形学和法术组合的 Debug 成本。

### 近期第二阶段：P1 状态可视化 2.0

成果：Burning 和 Wet 的 Shader 驱动表现、MaterialPropertyBlock 桥接。

原因：现有状态系统已经提供稳定数据源，这是图形学与 Gameplay 最自然的第一次汇合。

### 近期第三阶段：P2 元素反应 MVP

成果：载体解耦的 `Reaction Kernel`、三条数据驱动反应、四种简单环境载体，以及 Water/Poison/Fire/Sticky 和三种反应的自研视觉。P2 按 A/B/C 三个 Editor Gate 分期交付，不在本阶段实现真实 Cell 流动。

原因：它会把“状态系统”从角色身上的四个百分比，升级成真正影响法术构筑和环境决策的玩法系统，同时为 P6 的有限元素场提供可复用规则内核和视觉语言。

完成这三个阶段后，再根据实际体验决定 P3 和 P4 的先后细节。如果现有修正冲突已经频繁阻碍内容开发，优先 P3；如果修正体系稳定但缺少新的空间玩法，则进入 P4。

---

## 16. 最终应形成的项目叙事

最终这个项目不应被描述为：

> 我使用 Unity 做了一个 RPG，并实现了很多技能和特效。

更有价值的叙事是：

> 我实现了一套 Noita-like 的数据驱动法术解释器，将法术组合求值、投射物运行时、统一伤害、百分比状态和载体解耦的元素反应连接成可扩展管线。针对 3D 世界采用 Hybrid Element World：普通场景承载大世界，局部稀疏 Cell 承载元素模拟，自研 Shader、VFX、Decal 和程序化几何隐藏 Cell 粒度并表现水、毒、火、粘液。针对 3D 空间重新设计追踪、反射、轨道和光束法术；在系统允许触发递归和大量运行时实体的前提下，通过求值预算、对象池、NonAlloc 查询、活跃区域更新和 GPU/CPU Profiling 控制性能，最终用一场多阶段 Boss 战和一局 Roguelite 流程验证玩法价值。

这段叙事同时包含：

- 游戏玩法设计。
- Unity 客户端架构。
- C# 与数据驱动。
- 计算机图形学。
- Physics 与空间数学。
- 性能优化。
- 测试与 Debug 方法。

这才是后续开发真正要积累的“项目含金量”。
