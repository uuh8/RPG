## P7 总体目标与边界

第一版 Demo 只保留 Wizard 作为玩家角色，使用现有 Fireball、WaterField、Shield、Meteor、Trigger/Timed、Modify 和 Multicast 法术。关卡采用手工制作的 S 形连续小型布局：安全起点后依次经过三个普通战斗区域，区域之间至少获得一次能够影响 Wand 编程的新法术，最后击败精英并结算。Water/Fire Sparse ElementWorld 继续提供环境 Cell、流动、Extinguish、Wet/Burning 与自研 Rendering。

# Task 0：从“元素世界完成”切换到“完整单局开发”

Task 0 的目的，是在进入新功能前给项目建立一个清晰的阶段边界。此前 P6 已经完成两条可玩的双向链路：一条是法术命中后通过唯一 `IElementWriteSink` 把 Water/Fire 写入固定世界坐标的稀疏 Chunk，经过固定 Tick 进行流动、衰减、反应和 Solver Sleep/Wake；另一条是 ElementWorld 通过集中 Exposure 把 Cell Amount 映射为角色 Wet/Burning，并由 Water Chunk Mesh、自研 Water Shader 和共享 Fire Body/Core/Sparks Particle 形成连续视觉。P6 最关键的性能问题——稳定水面仍被重复扫描导致 `ElementWorld.Simulate` 单帧达到数百毫秒——也已经通过 Profiler 证据定位，并用 Resident/RequiresSimulation 分离、稳定 Chunk休眠、写入/边界唤醒和无效工作剪枝解决。继续把 Poison、Sticky、Steam 或灰盒地图塞进 P6，只会让“阶段完成”失去意义。

因此本 Task 把 P6 作为已结束的冻结依赖，并把首个灰盒关卡、Encounter、奖励、功能性 UI、Victory/Defeat 和 Restart 统一归入 P7。功能性 UI 不是最后贴上去的装饰：没有 Main Menu，玩家只能依赖 Unity Editor 的 Play Button；没有目标 HUD，玩家不知道门为什么不开；没有 Pause/Settings，Demo 缺少基本应用控制；没有 Result/Restart/Return To Main Menu，一局也没有明确的开始和结束。与此同时，我们没有直接开始在 `SampleScene` 里摆更多 Cube，而是先制定 P7 的产品目标和架构边界：Scene 负责空间和引用，`Game.Run` 负责本局 Gameplay 状态，`Game.UI` 负责反馈与用户操作入口，Enemy/Player 保持原职责，ElementWorld 继续是独立系统。这样开发者以后遇到“门不开”“怪死了不计数”“关闭一个 Panel 后游戏意外恢复”“退出 Play Mode 后法杖被污染”等问题时，可以沿清晰的数据链定位，而不是在一个万能 Scene Manager 中搜索互相耦合的 if/switch。

## 1. 为什么“关卡搭建”不等于“地图编辑”

地图编辑主要处理空间：Floor、Wall、Ramp、Cover、Lighting、Camera Sightline 和移动距离。它决定玩家能不能走、战斗空间够不够、敌人是否被障碍卡住，但它本身不会形成一局游戏。

一局游戏还需要四类状态：

| 层级 | 典型问题 | P7 的负责者 |
|---|---|---|
| 空间状态 | 玩家在哪个区域，Trigger/Gate/Collider 在哪里 | `P7_DemoRun` Scene 与灰盒物体 |
| 战斗状态 | 哪些 Enemy 属于本区，还剩多少，是否清场 | `DemoEncounterController + EncounterProgressTracker` |
| 单局状态 | 当前第几关，是否失败/胜利，能否继续推进 | `DemoRunController + RunProgressTracker` |
| 表现状态 | 当前目标、奖励、Pause、Settings、Victory/Defeat | `Game.UI` Controllers，只读 Run Event/Settings |
| 应用状态 | 当前在 Main Menu 还是 Gameplay，是否正在切换 Scene | `P7_MainMenu/P7_DemoRun + DemoSceneTransitionController` |

如果只搭地图，玩家可以从起点一路跑到终点，敌人可能全部同时追来，死亡后没有失败界面，最终敌人死亡也没有胜利。反过来，如果只写流程而没有先验证空间尺度，Gate 可能堵住 CharacterController，Camera 可能穿墙，当前使用直线追击的 Enemy 可能被复杂掩体永久卡住。P7 必须让“空间 Authoring”和“流程 Runtime”分工合作。

## 2. 为什么新增 `Game.Run`，而不是把流程写进 Player、Enemy 或 UI

项目现有依赖遵循单向结构。`HealthComponent` 负责 HP 与 `DeathEvent`，Enemy Controller 负责感知和战斗 FSM，Wizard/SpellCaster 负责施法，ElementWorld 负责环境模拟，UI 负责显示。谁都不应该顺便拥有“这一局打到第几关”的真相。

若把清场逻辑写进 Enemy：每个敌人都要知道同区其他敌人、门和最终胜利，普通 AI 将与具体关卡绑定。若写进 Player：玩家移动/攻击脚本会开始管理 Gate、奖励和 Scene Reload，难以复用也难测试。若写进 UI：表现层会反向修改 Gameplay，破坏现有只读边界。

因此选择新增 `Game.Run`：

```text
Game.Run 读取 DeathEvent
→ 纯 Tracker 求值 Encounter/Run 状态
→ Scene Adapter 开关 Enemy 与 Gate
→ 发布 Encounter/Run Event
→ Game.UI 只读显示
```

`Game.Run` 计划依赖 `Game.Core + Game.Combat + Game.Skills`，但不依赖 `Game.Character` 和 `Game.UI`。Character/UI 后续可以只读 Run Spell Session/Event，因此依赖仍然向上，不形成循环。

这种模块化不是为了“多建一个文件夹显得专业”，而是让变化原因分离：修改敌人攻击 AI 不需要重测房间顺序；修改 UI 文案不改变胜负；将来用随机 Room Graph 替换手工顺序，也不必重写 Health/Death 规则。

## 3. Encounter 与 Run 是两个不同层级的状态机

Encounter 表示一个战斗区域的局部生命周期：

```text
Waiting → Armed → Active → Cleared
```

- `Waiting`：还没轮到本区，即使玩家或其他 Collider 误入，也不启动。
- `Armed`：前区完成，本区 Entry Trigger 可以接受玩家。
- `Active`：关闭 Gate、激活成员 Enemy、统计本区 Death。
- `Cleared`：成员全部死亡，只发布一次完成并打开出口。

Run 表示整局的更高层生命周期：

```text
NotStarted → Running → Completed
                    └→ Failed
```

`Completed` 和 `Failed` 是 Terminal State。进入后，普通 DeathEvent 或 Trigger 不能继续推进，只能通过 Restart 创建新一局。把两层分开可以避免一个常见错误：为了判断最终胜利，让每个 Encounter 都知道自己是不是最后一个；正确做法是 Encounter 只报告“我完成了”，由 RunProgressTracker 决定是否还有下一关。

Death 统计使用 `HealthComponent.Id / DeathEvent.TargetId`，不使用 GameObject Name、Tag 文本或 Enemy 数量轮询。原因是 ID 与 Combat 事件同源，重复 DeathEvent 可以去重，场外敌人死亡也可以安全忽略，而且不需要在 `Update()` 每帧执行 `FindObjectsOfType`。

## 4. 为什么 P7 必须解决 ScriptableObject 运行时污染

当前 Wand Editor 会把拖拽结果写回 `WandLoadout.Spells`。`WandLoadout` 是 Project 中的 ScriptableObject Asset；在 Unity Editor 的 Play Mode 中修改它，退出 Play Mode 后可能保留改动。实验阶段这方便调试，但单局系统加入奖励和 Restart 后会产生错误语义：上一局拿到的法术可能永久留在下一局，甚至被提交到 Git。

P7 采用 Authoring Template 与 Runtime Clone：

```text
Project Asset（起始模板）
→ Play Mode Awake: Object.Instantiate
→ Runtime Clone（本局可编辑）
→ SpellCaster 与 Wand UI 共享同一 Clone
→ Scene 结束时 Destroy
```

只克隆 `SpellLibrary/WandLoadout` 容器，不克隆每个 `SpellDefinition`。法术定义仍是不可变的共享数据，Runtime 只改变“我本局拥有哪些法术”和“法杖中的引用顺序”。Clone 使用 `HideFlags.DontSave`，表达它不能被保存为场景或资产。这个设计既保留 Data-driven Authoring，也建立了 Roguelite 最基本的 Run-Scoped State。

## 5. 手工关卡与随机关卡的取舍

原总计划的 P7 包含 Seed、房间组合、稀有度与随机权重。这些能力有价值，但当前直接实现会同时引入 Room Graph、Spawner、Reward Table、Seed State、Save/Reload 和 Debug Reproduction，开发风险会显著超过“完整一局”本身。

第一版采用手工 S 形连续关卡，奖励也确定。优点是：

- 每次测试敌人、距离、奖励和元素位置完全一致，容易复现 Bug。
- 可以精确安排第一次普通战斗、第一次元素互动和第一次重新编程。
- 能先测出哪些房间模板真正好玩，再把它们放入随机池。
- 录制作品视频时不会因随机结果缺少核心展示。

随机化不是越早越好。它应当变化已经成立的模板，而不是替代关卡设计。P7-A Demo 完整后，P7-B 可以把 `DemoRunDefinition` 的线性顺序替换为 Seeded Room Selection，同时复用 Encounter/Run/UI/Restart 内核。

## 6. 为什么功能性 UI 属于 P7 核心，而不是完成后的美化

游戏 UI 可以分成两类。第一类是 Presentation Polish，例如漂亮 Logo、复杂过场动画、动态背景和最终字体；这些可以在 Demo 主流程完成后优化。第二类是 Functional UI，它决定玩家能否理解和控制应用：Start Game 建立运行入口，Objective HUD 解释当前目标，Reward Feedback 告诉玩家获得了什么，Pause 提供中断控制，Victory/Defeat 定义一局的终点，Restart/Return To Main Menu 建立下一次循环。P7 必须完成第二类，否则我们得到的是“可以在 Unity Editor 中演示的一组系统”，而不是可以交给别人独立试玩的游戏。

P7 的 UI 生命周期计划如下：

```text
P7_MainMenu
  → Start Game
  → P7_DemoRun
       ├─ Gameplay HUD / Wand Editor / Reward Feedback
       ├─ Pause → Resume / Settings / Restart / Main Menu
       ├─ Victory → Restart / Main Menu
       └─ Defeat  → Restart / Main Menu
```

这里最容易踩坑的是 `Time.timeScale`。当前 Wand Editor 会直接设置 0 或 1；若 Pause Menu 和 Victory Panel 也各自这样做，关闭 Wand Editor 可能把仍处于 Pause/Victory 的游戏恢复。P7 因此计划使用 `RunPauseCoordinator` 记录 `WandEditor`、`PauseMenu`、`TerminalResult` 等 Pause Reason：只有所有原因都释放时才恢复 `Time.timeScale = 1`。这和“多个系统共享一个 bool”相比，多表达了一层所有权，但能准确回答“现在为什么暂停”。

Settings 也要区分 User Preference 与 Run State。Master Volume、Mouse Sensitivity、Fullscreen 应跨 Scene 和应用重启保留，因此用 `Game.Core.UserSettingsService + PlayerPrefs`；HP、Enemy Count、Runtime Wand、Encounter Index 属于本局，不能存入 PlayerPrefs。MVP 的 Master Volume 使用 `AudioListener.volume`，优点是现有 AudioSource 无需统一改 Output；代价是没有 Bus、Duck 和 dB Mixing，正式 Audio 阶段再迁移 `AudioMixer`。这体现 Demo 开发中的核心取舍：功能必须真实可用，但不提前建设当前内容还验证不了的复杂系统。

## 9. 当前方案的 Trade-off 与未来扩展缝

| 当前决策 | 获得的收益 | 付出的代价 | 后续扩展 |
|---|---|---|---|
| 线性 Encounter 顺序 | 可复现、易教学、易平衡 | 每局空间不变化 | 用 Seeded Room Graph 生成 Definition 顺序。 |
| 预放置并按需激活 Enemy | Scene 可视、初学者易配置 | 房间复用/随机数量较弱 | 改为数据驱动 Spawner，仍输出同一 Health ID 列表。 |
| 精英使用 Prefab Variant | 快速形成终局，不新增 AI 风险 | Boss 行为层次较少 | Demo 后新增多阶段 Boss FSM/Telegraph。 |
| Runtime Clone 法杖 | 不污染资产，Restart 干净 | Character/UI 增加 Run Session 绑定 | 未来将 Clone 数据序列化成正式 Save/Run Snapshot。 |
| 初版不用复杂 NavMesh | 不引入新系统，保留现有 Enemy | Arena 障碍不能太复杂 | 若地编需要，再增加 NavMeshAgent/Pathfinding Task。 |
| 独立 Main Menu + Demo Run Scene | 有真实启动/返回边界，Restart 能彻底清理本局 | 多一个 Scene 和 Build Profile 配置 | 未来可在 Boot Scene 上增加 Save/Profile/Loading。 |
| 集中 Pause Reason | Wand/Pause/Result 不互相覆盖 `Time.timeScale` | 比直接写 0/1 多一个协调器 | 未来可扩 Photo Mode、Cutscene、System Dialog。 |
| `PlayerPrefs` 保存三项设置 | 快速、跨 Scene、无需 Save System | 不适合复杂存档或云同步 | 后续迁移正式 Settings/Profile Save。 |

## 10. 面试时如何解释这次阶段设计

如果面试官问“你做完元素系统后，怎么把它变成一款能玩的 Demo”，可以这样回答：

> P6 结束时，我已经有了法术解释器、统一投射物和伤害、角色状态，以及固定世界坐标的稀疏 Water/Fire Cell。它们分别通过测试并不代表已经形成游戏，所以 P7 的目标不是再增加一种技术，而是建立完整 Run Flow。我先把一局拆成 Encounter 局部状态和 Run 全局状态：Encounter 只负责本区 Armed、Active、Cleared，Run 负责顺序、Completed、Failed。HealthComponent 仍然只发布 DeathEvent，Game.Run 通过 TargetId 去重和统计，Enemy AI、Player 和 UI 都不拥有流程真相。
>
> 我选择新增只依赖 Core、Combat、Skills 的 Game.Run 模块，纯 Tracker 先用 NUnit 锁定重复死亡、越序启动和 Terminal State，再由 MonoBehaviour Adapter 接 Scene Trigger、Enemy 和 Gate。UI 只订阅 Run Event，ElementWorld 继续独立模拟。这样以后把手工房间替换成 Seeded Room Graph，不需要修改伤害和敌人 AI。
>
> Roguelite 还要求本局数据和永久资产分离。原来的 Wand Editor 在 Play Mode 会直接修改 ScriptableObject，所以我计划从只读模板创建 Runtime Clone，让 SpellCaster 和 UI 共享同一份本局 Wand/Library，奖励只写 Clone，Restart 后重新从模板开始。第一版使用手工 S 形关卡和确定奖励，是为了先建立可复现的 10～15 分钟完整流程；随机房间和权重留到模板经过实战验证后再加入。这个取舍让我能更快得到可录制、可测试、可解释的作品 Demo，而不是先做一个没有稳定内容的随机框架。
>
> 我还把功能性 UI 当成 Run Flow 的一部分，而不是最后的美术包装。Demo 从独立 Main Menu 启动，局内 HUD 只消费 Run Event，Pause、Wand Editor 和 Victory/Defeat 通过 Pause Reason 协调器共同管理 Time.timeScale，避免多个 Panel 相互覆盖。Restart 重新加载 Demo Scene，Return To Main Menu 回到应用入口；Master Volume、Mouse Sensitivity、Fullscreen 属于跨局 User Settings，用 Core Service 和 PlayerPrefs 保存，而 Encounter、HP、Runtime Wand 仍然只存在于本局。这样 Standalone Build 可以由其他人独立完成“开始—游玩—结算—重开/返回”的闭环，而不是依赖我在 Unity Editor 旁边解释。
