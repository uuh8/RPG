# 重力类修正法术设计复盘

创建时间：2026-07-04 11:40:28  
功能状态：已在 Unity Editor / Play Mode 中测试通过  
目标读者：战斗系统设计新手，重点理解设计思路、开发思路、架构集成思路

---

## 1. 功能一句话总结

“重力类修正法术”不是一个新的火球 prefab，也不是一个新的投射物脚本。它是一个 `Modify` 法术，用来修改后续 `Emit` 投射物的运动模型：让后续投射物启用 Unity `Rigidbody` 的重力。

例如法杖：

```text
[重力] [普通火球]
```

含义是：

```text
普通火球仍然是普通火球，但这次生成时会打开 Rigidbody.useGravity，所以飞行轨迹从直线变成抛物线。
```

这次功能真正训练的是一个架构判断：

> 当一个新法术只是改变“后续投射物的属性”时，它应该作为 `Modify` 接入解释器链路，而不是为每种组合单独创建新技能。

如果把它做成 `GravityFireball`，后续就会继续出现：

```text
GravityBouncyFireball
GravityTimedFireball
GravityTriggerFireball
GravityTripleFireball
```

这就是组合爆炸。Noita-like 法术编程系统的价值，正是用“指令组合”替代“硬编码技能组合”。

## 2. 基础知识和原理

### 2.1 重力对投射物意味着什么

在游戏里，一个投射物的运动常见有两类：

```text
直线运动：
    速度方向基本不变，火球像激光一样朝准星方向飞。

抛物线运动：
    初速度仍然由施法方向决定，但每个物理步都会受到重力加速度影响，轨迹逐渐下坠。
```

在 Unity 中，如果投射物由 `Rigidbody` 控制，是否受重力主要由这个字段决定：

```csharp
Rigidbody.useGravity
```

当 `useGravity = false` 时，火球可以保持直线飞行。  
当 `useGravity = true` 时，Unity Physics 会在 `FixedUpdate` 物理模拟中持续给刚体施加重力加速度。

### 2.2 Unity 里的相关组件和 API

| 技术点 | 作用 |
|---|---|
| `Rigidbody` | 让投射物参与 Unity 3D physics simulation |
| `Rigidbody.useGravity` | 控制刚体是否受到全局重力影响 |
| `Rigidbody.linearVelocity` | Unity 6 中设置刚体速度 |
| `Physics.gravity` | Unity 项目的全局重力向量，默认接近 `(0, -9.81, 0)` |
| `ProjectileBase.Init(...)` | 当前项目里所有投射物初始化速度、阵营、伤害、重力开关的入口 |
| `SpellDefinition` | 法术数据资产，Editor 中配置“这个法术是什么” |
| `CastEvaluator` | 法术解释器，负责把法杖序列解释成发射命令 |
| `EmitCommand` | 解释器输出的纯数据命令 |
| `SpellCaster` | 把纯数据命令转换成真实 Unity 投射物实例 |

### 2.3 为什么重力是“修正”，不是“投射物”

这是你需要重点建立的设计判断。

`Emit` 法术回答的问题是：

```text
我要发射什么？
```

例如：

```text
普通火球
触发火球
定时火球
```

`Modify` 法术回答的问题是：

```text
后续发射出来的东西要被怎样修改？
```

例如：

```text
加伤害
加速度
散射
弹跳
重力
```

重力本身不产生投射物，它只改变后续投射物的飞行方式。所以它应该是 `Modify`。

### 2.4 抛物线不是重新计算出来的，而是交给物理系统

这次 MVP 没有自己写：

```csharp
velocity += gravity * deltaTime;
position += velocity * deltaTime;
```

原因是当前项目投射物已经使用 `Rigidbody`。既然底层已经交给 Unity Physics，那么重力功能最小、最稳定的接入点就是：

```csharp
proj.Init(..., useGravity: cmd.UseGravity);
```

也就是让 Unity 自己做每个物理步的重力积分。

## 3. 实现方案对比

### 3.1 方案 A：做一个新的 `GravityFireball` prefab

做法：

复制一个火球 prefab，把它的 `Rigidbody.useGravity` 默认勾上，然后创建一个新的 `SpellDefinition` 指向这个 prefab。

优点：

- 实现最快。
- 对新手来说直观。
- 不需要改解释器代码。

缺点：

- 无法和现有修正系统自然组合。
- 会产生大量组合 prefab。
- `[重力] [触发火球]`、`[重力] [定时火球]`、`[重力] [弹跳] [火球]` 都要额外手工处理。
- 不符合 Noita-like 法术编程系统的核心思想。

结论：

不采用。它适合一次性技能，不适合“法术编程系统”。

### 3.2 方案 B：在 `ProjectileBase` 上增加一个“受重力”开关，由 `SpellCaster` 注入

做法：

`SpellDefinition` 上配置 `ModUseGravity`，解释器把它传到 `EmitCommand.UseGravity`，运行时 `SpellCaster` 实例化投射物后调用：

```csharp
proj.Init(..., useGravity: cmd.UseGravity);
```

优点：

- 完全沿用现有法术解释器链路。
- 所有后续 `Emit` 都能被重力修正影响。
- 不需要新增投射物 prefab。
- `Game.Skills` 仍然保持纯逻辑，不碰 Unity 物理对象。
- 代码改动小，符合 MVP。

缺点：

- 目前只是开关，不能配置重力倍率。
- 使用的是项目全局 `Physics.gravity`，不是每颗投射物自定义重力。

结论：

这是本次最终采用的方案。

### 3.3 方案 C：自定义 Projectile Physics 系统

做法：

完全不依赖 `Rigidbody.useGravity`，而是在 `ProjectileBase` 或独立 `ProjectileMotion` 中自己维护：

```csharp
velocity += customGravity * deltaTime;
position += velocity * deltaTime;
```

优点：

- 可控性最高。
- 可以做每个投射物不同的重力方向、重力倍率、空气阻力、曲线轨迹。
- 适合复杂弹幕或竞技项目。

缺点：

- 当前阶段复杂度过高。
- 要处理 collision detection、穿透、高速碰撞、反弹后的速度更新等问题。
- 会和现有 `ProjectileBase` 的 `Rigidbody` 体系产生职责重叠。

结论：

作为未来升级方向保留。本次不采用，因为当前需求只是“给投射物添加重力”。

### 3.4 方案 D：用 `Physic Material` 或 mass/drag 调效果

做法：

通过 `Rigidbody.mass`、`drag`、`Physic Material` 等参数调出类似下坠或弹道差异。

优点：

- 适合真实物理手感调试。

缺点：

- 不适合作为法术语义。
- 很难通过 `CastEvaluator` 进行确定性解释。
- 不利于后续写测试。

结论：

不采用。它更像物理材质调参，不是法术编程指令。

## 4. 最终方案与技术选择

最终选择：

```text
把重力做成 Modify 法术参数：
SpellDefinition.ModUseGravity
    -> CastModifierState.UseGravity
    -> CastEvaluator.BakeEmit(...)
    -> EmitCommand.UseGravity
    -> SpellCaster
    -> ProjectileBase.Init(... useGravity)
    -> Rigidbody.useGravity
```

这条链路每一层负责一个明确问题：

| 层级 | 技术 | 解决的问题 |
|---|---|---|
| 数据层 | `SpellDefinition.ModUseGravity` | Editor 中如何配置“重力修正法术” |
| 规则状态层 | `CastModifierState.UseGravity` | 解释器读到 Modify 后如何累计当前修正 |
| 解释器层 | `CastEvaluator.BakeEmit` | 后续 Emit 如何获得当前修正快照 |
| 边界数据层 | `EmitCommand.UseGravity` | 纯逻辑结果如何传给运行时 |
| 运行时桥接层 | `SpellCaster` | 如何把解释结果注入真实 projectile |
| 投射物层 | `ProjectileBase.Init(... useGravity)` | 如何最终打开或关闭 `Rigidbody.useGravity` |

注意这里最重要的不是 `bool` 本身，而是这条数据流。

如果你之后做“穿透修正”“追踪修正”“分裂修正”，都应该先问：

```text
这个功能是不是后续投射物的属性/行为修正？
如果是，它是否也应该沿着 SpellDefinition -> CastModifierState -> EmitCommand -> SpellCaster -> ProjectileBase 传递？
```

## 5. 架构设计与拆解

### 5.1 在整体架构中的位置

重力修正跨越了五层：

```text
Game.Skills 数据定义层
    SpellDefinition

Game.Skills 纯规则层
    CastModifierState
    CastEvaluator
    EmitCommand

Game.Character 运行时桥接层
    SpellCaster

Game.Combat 投射物执行层
    ProjectileBase

Unity Physics
    Rigidbody.useGravity
```

为什么不是直接在 `ProjectileBase` 里写死？

因为 `ProjectileBase` 不应该知道“这是哪个法术导致我受重力”。它只应该知道：

```text
这颗投射物初始化时，外部告诉我 useGravity 是 true 还是 false。
```

为什么不是在 `CastEvaluator` 里直接操作 `Rigidbody`？

因为 `CastEvaluator` 属于 `Game.Skills`，它是纯规则层。它不能碰 `GameObject`、`Transform`、`Rigidbody`、`Instantiate`。否则就失去可测试性，也破坏模块边界。

### 5.2 数据层：`SpellDefinition`

新增字段：

```csharp
public bool ModUseGravity = false;
```

它的含义是：

```text
如果这个 SpellDefinition 是 Kind=Modify，那么它会让后续投射物启用重力。
```

Editor 中你会创建一个类似 `Spell_Mdy_Gravity` 的 `ScriptableObject`，配置：

```text
Kind = Modify
ModUseGravity = true
```

这个资产本身不产生火球，只改变后续火球的运动方式。

### 5.3 规则状态层：`CastModifierState`

新增字段：

```csharp
public readonly bool UseGravity;
```

默认值：

```csharp
public static CastModifierState Default
    => new CastModifierState(0f, 1f, 1f, 0f, 0, false);
```

这里最后的 `false` 表示：

```text
没有任何修正法术时，默认不启用重力，保持原本直线火球行为。
```

`Apply` 里的叠加规则：

```csharp
UseGravity || modify.ModUseGravity
```

这个设计很重要。它表示重力是一个“只要启用过就保持启用”的开关。

例如：

```text
[重力] [加伤害] [火球]
```

解释过程是：

```text
Default.UseGravity = false
读到 [重力]：UseGravity = false || true = true
读到 [加伤害]：UseGravity = true || false = true
读到 [火球]：发射命令 UseGravity = true
```

为什么不是加法？

因为重力当前是布尔开关，不存在：

```text
UseGravity = 2
```

如果未来要做“重力倍率”，那才应该设计成：

```csharp
float GravityScale;
```

### 5.4 解释器层：`CastEvaluator`

`CastEvaluator` 在 `BakeEmit` 时，把当前修正状态写入 `EmitCommand`：

```csharp
mods.UseGravity
```

这一步的含义是：

```text
当解释器终于读到一个 Emit 法术时，把此刻已经累计好的所有修正，烘焙成一条发射命令。
```

所以：

```text
[重力] [火球]
```

会得到：

```text
EmitCommand.UseGravity = true
```

而：

```text
[火球] [重力]
```

会得到：

```text
第一个火球 UseGravity = false
```

因为 `Modify` 只影响它后面的 `Emit`，不回头影响已经发射的投射物。这就是“从左到右解释器”的基本规则。

### 5.5 边界数据层：`EmitCommand`

新增字段：

```csharp
public readonly bool UseGravity;
```

`EmitCommand` 是解释器和运行时之间的合同。它表达：

```text
这颗投射物本次生成时，应该使用什么伤害、速度、散射、弹跳次数、是否启用重力、payload 等。
```

注意：`EmitCommand.UseGravity` 是一次发射的快照。

它不是全局状态，也不是修改 `SpellDefinition` 资产本身。这样可以避免 Play Mode 中一次施法影响下一次施法。

### 5.6 运行时桥接层：`SpellCaster`

关键改动：

```csharp
proj.Init(team, attackerId, cmd.Damage, cmd.DamageType,
          dir * cmd.Speed, casterCollider, useGravity: cmd.UseGravity);
```

以前火球运行时固定传：

```csharp
useGravity: false
```

所以所有法术火球都是直线。现在改成：

```csharp
useGravity: cmd.UseGravity
```

这就让解释器输出真正影响到投射物实例。

`SpellCaster` 在架构里是桥：

```text
左边：Game.Skills 的纯数据 EmitCommand
右边：Unity 场景里的真实 ProjectileBase
```

所以它是最适合做这次注入的位置。

### 5.7 投射物执行层：`ProjectileBase`

这次没有新增 `ProjectileBase` 逻辑，因为已有接口已经支持：

```csharp
public void Init(..., bool useGravity = true)
{
    ...
    _rb.useGravity = useGravity;
}
```

这说明前面架构留了一个很好的扩展点：`ProjectileBase.Init` 已经把“是否受重力”作为初始化参数暴露出来。

所以本次功能不是去重写投射物运动，而是把法术系统的结果接到这个已有参数上。

这是工程中很常见的工作方式：

```text
不要看到新需求就新增系统。
先找现有系统有没有合适的扩展点。
如果有，优先把新语义接到已有扩展点。
```

## 6. 和现有功能的集成关系

### 6.1 和普通火球

```text
[重力] [普通火球]
```

结果：

```text
普通火球生成时 useGravity=true，飞行轨迹下坠。
```

如果没有 `[重力]`：

```text
[普通火球]
```

结果：

```text
useGravity=false，保持直线飞行。
```

### 6.2 和弹跳类修正

```text
[重力] [弹跳] [普通火球]
```

结果：

```text
UseGravity = true
BounceCount = N
```

含义是：

```text
火球会受重力下坠，同时碰到环境时可以反弹。
```

这里有一个重要区别：

```text
重力：持续影响运动，每个物理步都生效。
弹跳：只在 collision 发生时生效。
```

所以两者的架构位置不同：

```text
重力最终落在 Rigidbody.useGravity。
弹跳最终落在 ProjectileBase.TryBounce。
```

但它们在法术系统中的传递方式相同：

```text
SpellDefinition -> CastModifierState -> CastEvaluator -> EmitCommand -> SpellCaster -> ProjectileBase
```

这就是架构一致性的价值。

### 6.3 和触发类火球

```text
[重力] [触发火球] [普通火球]
```

结果：

```text
触发火球本体会下坠。
触发火球命中后释放 payload。
payload 运行时会继承 PayloadMods.UseGravity。
```

也就是说，当前实现中：

```text
如果触发火球前面有 [重力]，payload 里的后续火球也会继承重力修正。
```

原因是 `EmitCommand` 不只保存本体的 `UseGravity`，还保存了：

```csharp
PayloadMods
```

触发 payload 时，会把这个修正快照作为下一层解释器的起点。

这点非常重要。它解释了为什么测试里要覆盖：

```csharp
PayloadTrigger_PayloadModsPreserveUseGravity
```

### 6.4 和定时类火球

```text
[重力] [定时火球] [普通火球]
```

结果：

```text
定时火球会在下坠过程中计时。
如果到达指定时间时投射物仍然存在，则销毁本体并释放 payload。
payload 也会继承 UseGravity。
```

这里要区分两个系统：

```text
重力系统：改变投射物飞行轨迹。
定时触发系统：改变投射物生命周期结束方式。
```

两者互不冲突，因为它们作用在不同生命周期节点：

```text
重力：物理模拟阶段持续生效。
定时：计时结束时触发 payload。
```

### 6.5 和多重法术

```text
[重力] [三重] [火球] [火球] [火球]
```

结果：

```text
三个火球都会 UseGravity=true。
```

因为 `[重力]` 修改的是当前 `CastModifierState`，而 `CastModifierState` 会影响后续所有 `Emit`，直到本层解释结束。

## 7. 改动脚本清单

| 脚本 | 改动 |
|---|---|
| `SpellDefinition.cs` | 新增 `ModUseGravity` 字段，让 `Modify` 法术能声明“后续投射物启用重力” |
| `CastModifierState.cs` | 新增 `UseGravity` 字段，默认 `false`，`Apply` 中用 `||` 累计 |
| `CastEvaluator.cs` | `BakeEmit` 时把 `mods.UseGravity` 写入 `EmitCommand` |
| `EmitCommand.cs` | 新增 `UseGravity` 快照字段 |
| `SpellCaster.cs` | `ProjectileBase.Init` 不再固定 `useGravity:false`，改为 `useGravity: cmd.UseGravity` |
| `CastModifierStateTests.cs` | 增加默认不启用重力、修正后启用重力的测试 |
| `CastEvaluatorTests.cs` | 增加 `UseGravity` 烘焙进 `EmitCommand`、payload mods 继承的测试 |

没有改动：

| 脚本 | 原因 |
|---|---|
| `ProjectileBase.cs` | 已经有 `Init(... bool useGravity)` 扩展点，本次只接线，不需要新增运动逻辑 |
| `WizardController.cs` | 角色输入只负责发起施法，不关心投射物是否受重力 |
| `WandEditorController.cs` | UI 只编辑法术顺序，不解释法术语义 |
| `DamagePipeline.cs` | 重力不改变伤害公式 |

## 8. 踩坑与 Debug

### 8.1 坑点一：不要直接改火球 prefab 的默认重力

最容易犯的错误是：

```text
我想让火球受重力，那我直接把 Fireball prefab 的 Rigidbody.useGravity 勾上。
```

这会导致一个严重问题：

```text
所有火球都受重力，而不是只有 [重力] 修正后的火球受重力。
```

这破坏了法术编程系统的核心：

```text
同一个 Emit，在不同前置 Modify 下应该表现不同。
```

正确做法是：

```text
prefab 保持通用。
每次发射时根据 EmitCommand.UseGravity 决定本实例是否受重力。
```

### 8.2 坑点二：不要让 `CastEvaluator` 依赖 Unity Physics

错误方向：

```text
在 CastEvaluator 里判断重力，然后直接操作 Rigidbody。
```

这是架构错误。`CastEvaluator` 是纯解释器，它应该可以在 EditMode tests 中运行，不需要场景对象。

正确边界：

```text
CastEvaluator 只输出 UseGravity=true/false。
SpellCaster 才把这个结果应用到真实 ProjectileBase。
```

### 8.3 坑点三：payload 是否继承重力

这个问题容易被忽略。

如果法杖是：

```text
[重力] [触发火球] [普通火球]
```

那么触发火球命中后释放的普通火球，是否应该也受重力？

本次设计选择：

```text
继承。
```

原因是触发火球捕获 payload 时，同时保存了 `PayloadMods` 快照。玩家直觉上也更容易理解为：

```text
[重力] 放在触发火球前面，会影响这个触发法术链条后续释放出来的投射物。
```

所以测试中专门验证：

```csharp
Assert.IsTrue(_out[0].PayloadMods.UseGravity);
```

### 8.4 坑点四：重力和弹跳组合时要理解职责边界

如果出现：

```text
[重力] [弹跳] [火球]
```

火球下坠后反弹，反弹后还会继续下坠。这不是 bug。

原因是：

```text
Rigidbody.useGravity=true 会持续生效。
弹跳只是碰撞瞬间改一次速度方向。
```

如果未来想要“反弹后不再受重力”，那就不是当前重力修正语义，而是另一个法术或一个更复杂的 projectile behavior 规则。

### 8.5 坑点五：Unity Editor 中资产配置容易漏

代码写完后，Editor 里还必须有对应 `SpellDefinition` 资产：

```text
Kind = Modify
ModUseGravity = true
```

还要把它加入 `SpellLibrary.Available`，否则 UI 里看不到这个法术。

这是数据驱动系统的常见调试顺序：

```text
代码字段存在
-> ScriptableObject 资产配置正确
-> SpellLibrary 收录
-> WandLoadout 实际放入该法术
-> CastEvaluator 输出正确
-> SpellCaster 注入正确
-> ProjectileBase 表现正确
```

## 9. 大厂面试 Q&A

### Q1：为什么把重力做成 `Modify`，而不是新建一个重力火球？

A：因为重力改变的是投射物的运动属性，而不是投射物类型本身。做成 `Modify` 后，它可以作用于任意后续 `Emit`，例如普通火球、触发火球、定时火球，未来也可以作用于冰弹、雷球等。如果做成 `GravityFireball`，每增加一种组合都要创建新 prefab 或新技能，最终会产生组合爆炸。当前项目是 Noita-like 法术编程系统，核心目标就是用解释器和修正链路支持组合，而不是硬编码每种组合。

### Q2：重力开关从法术资产到投射物实例是怎么传递的？

A：数据从 `SpellDefinition.ModUseGravity` 开始。解释器读到 `Kind=Modify` 的法术时，会通过 `CastModifierState.Apply` 把 `UseGravity` 设为 true。后续读到 `Emit` 时，`CastEvaluator.BakeEmit` 会把当前 `mods.UseGravity` 写入 `EmitCommand.UseGravity`。运行时 `SpellCaster` 实例化 projectile 后，调用 `ProjectileBase.Init(..., useGravity: cmd.UseGravity)`。最后 `ProjectileBase.Init` 内部设置 `Rigidbody.useGravity`。

### Q3：为什么 `UseGravity` 用 `bool`，而不是 `float GravityScale`？

A：本次需求是“给投射物添加重力”，MVP 只需要区分是否启用 Unity 全局重力，所以 `bool` 足够，代码和 Editor 配置也更简单。`float GravityScale` 可以作为未来扩展，例如弱重力、强重力、反重力。但它会引入新的设计问题：多个重力修正如何叠加，是相加还是相乘，是否允许负值，是否覆盖全局 `Physics.gravity`。这些超出本次需求，所以先用 `bool`。

### Q4：为什么不在 `ProjectileBase` 里根据法术名字判断是否受重力？

A：那会让 `ProjectileBase` 依赖法术系统细节，破坏模块隔离。`ProjectileBase` 属于 `Game.Combat`，它应该是通用投射物执行层，只接收运行时参数，不应该知道 `SpellDefinition`、`CastEvaluator` 或具体法术名字。当前做法是由 `SpellCaster` 作为桥接层，把 `EmitCommand` 的结果注入 `ProjectileBase`，保持依赖方向清晰。

### Q5：重力修正和触发 payload 的关系是什么？

A：触发类投射物在 `EmitCommand` 中保存 payload 和 `PayloadMods` 快照。重力修正如果在触发火球之前出现，就会进入这个快照。触发发生时，`SpellCaster.RunCast` 会以 `PayloadMods` 作为下一层解释器的起点，所以 payload 中释放的后续投射物也会继承 `UseGravity=true`。这让法术链条行为更一致。

### Q6：这次有没有修改 `ProjectileBase`？

A：没有新增 `ProjectileBase` 逻辑，因为现有 `ProjectileBase.Init` 已经有 `useGravity` 参数，并会设置 `_rb.useGravity`。这次重点是把法术解释器输出接到这个已有扩展点上。工程上这是更好的选择：优先复用已有稳定扩展点，而不是重复实现运动系统。

### Q7：如果未来要做“反重力”或“重力倍率”，怎么扩展？

A：可以把 `bool UseGravity` 演进成更通用的字段，例如 `float GravityScale` 或 `Vector3 CustomGravity`。解释器层仍然沿用当前链路，只是 `CastModifierState` 和 `EmitCommand` 携带的字段从 bool 变成数值或向量。运行时可能需要从 `Rigidbody.useGravity` 切换到自定义 gravity integration，因为 Unity 内置 `useGravity` 只支持是否使用全局重力，不支持 per-projectile gravity scale。

## 10. 模拟面试者完整讲解

我在项目中实现了一个 Noita-like 法术编程系统里的重力类修正法术。这个功能的核心不是做一个新的重力火球 prefab，而是把“受重力”作为一种后续投射物的修正属性接入现有解释器链路。玩家在法杖中写 `[重力] [火球]` 时，火球仍然是原来的火球 `Emit`，但这次生成的 projectile 实例会启用 `Rigidbody.useGravity`，所以飞行轨迹从直线变成抛物线。

架构上，我遵循了现有的 `SpellDefinition -> CastModifierState -> CastEvaluator -> EmitCommand -> SpellCaster -> ProjectileBase` 主链路。首先在 `SpellDefinition` 上增加 `ModUseGravity`，让 Editor 中可以创建一个 `Kind=Modify` 的重力法术资产。然后在 `CastModifierState` 中增加 `UseGravity`，解释器从左到右读到这个 Modify 时，用 `UseGravity || modify.ModUseGravity` 累计当前修正状态。这样只要前面出现过重力修正，后续 Emit 都会继承这个状态。

当解释器读到后续 `Emit` 时，`CastEvaluator.BakeEmit` 会把当前 `mods.UseGravity` 写入 `EmitCommand.UseGravity`。这里我保持 `Game.Skills` 是纯逻辑层，它只计算“这次应该发射什么”，不接触 `GameObject`、`Rigidbody` 或 `Collision`。真正的运行时桥接发生在 `SpellCaster`，它实例化投射物后调用 `ProjectileBase.Init(..., useGravity: cmd.UseGravity)`，最后由 `ProjectileBase.Init` 设置刚体的 `Rigidbody.useGravity`。

这个设计的好处是，它没有为重力火球创建特殊类型，也没有让 `ProjectileBase` 反向依赖法术系统。`ProjectileBase` 只接收一个运行时参数，完全不知道这个参数来自哪个法术。这样重力可以自然和普通火球、触发火球、定时火球、弹跳修正、多重法术组合。尤其是触发 payload 场景中，`EmitCommand` 会保存 `PayloadMods` 快照，因此 `[重力] [触发火球] [普通火球]` 这种链条里，payload 释放出的后续火球也能继承重力语义。

开发过程中我刻意把本次需求控制在 MVP 范围内，只做 `bool UseGravity`，不做 `GravityScale`。原因是 Unity `Rigidbody.useGravity` 已经能满足“添加重力”的需求，而且现有 projectile 系统已经使用 `Rigidbody`。如果现在引入自定义重力倍率，就需要讨论多个重力修正如何叠加、是否允许负重力、是否脱离 `Physics.gravity` 等额外语义，容易过度设计。后续如果要扩展到反重力、强重力或每个 projectile 独立重力方向，可以把 `UseGravity` 演进成 `GravityScale` 或自定义 gravity config，但主链路不需要改变。

我还补了 EditMode 纯逻辑测试，覆盖默认状态不启用重力、重力修正会被烘焙进 `EmitCommand`、触发 payload 的 `PayloadMods` 会保留 `UseGravity`。这样可以保证解释器层的语义稳定。最终 Play Mode 中的视觉表现由 Unity Editor 验证，因为抛物线轨迹依赖真实 `Rigidbody` 和场景物理环境。

## 11. 建议阅读脚本顺序

如果你要回头学习这个功能，建议按下面顺序看，不要按文件夹随机点：

```text
1. SpellDefinition.cs
   先看 ModUseGravity 是如何作为数据入口出现的。

2. CastModifierState.cs
   再看 UseGravity 如何从 Modify 累计成当前解释器状态。

3. CastEvaluator.cs
   看 BakeEmit 如何把 mods.UseGravity 写入 EmitCommand。

4. EmitCommand.cs
   理解它是纯逻辑层和运行时层之间的合同。

5. SpellCaster.cs
   看 cmd.UseGravity 如何被传入 ProjectileBase.Init。

6. ProjectileBase.cs
   最后看 Init 如何设置 Rigidbody.useGravity。

7. CastModifierStateTests.cs / CastEvaluatorTests.cs
   用测试反推设计意图，确认默认值、叠加规则、payload 继承规则。
```

这个顺序本质上就是数据流顺序：

```text
资产配置 -> 解释器状态 -> 发射命令 -> 运行时实例 -> Unity Physics
```

只要你能沿着这条链路读懂，后面做“穿透”“追踪”“分裂”“重力倍率”等法术修正，思路都是同一套。
