# 2026-09-02 法师敌人法术编程完整解析

> 状态：代码、生产资产、Prefab 连接与 focused EditMode Test 已完成；真实 P7 Scene Playthrough、受击打断观察和 Profiler capture 仍需在 Unity Editor 中手动验证。本文严格区分静态可确认事实、自动化测试证据和待验证边界。

## 1. 本次功能解决了什么问题

玩家看到的结果仍然是法师敌人在合适距离保持站位、播放施法动画，并在动作释放点朝玩家释放法术。系统能力发生了实质变化：原实现把法师敌人固定写成“生成一颗 Fireball”，投射物 Prefab、速度和伤害分别散落在敌人数据与攻击数据中；现在敌人使用与玩家、Boss 相同的法术编程管线。普通法师在 Prefab 上配置一段 `WandLoadout`，因此当前稳定释放一套火球程序；精英怪可以在同一数组中 Authoring 两到三套程序，每次真正释放时均匀随机选择，并排除上一次选择，避免连续重复带来的观感单调。

这次改动保留了敌人原有的感知、Kite、FSM、攻击冷却、受击和死亡职责。新增能力只替换“攻击释放点之后具体产出什么”的部分。敌人 FSM 仍决定何时攻击，法术解释器仍决定一段程序产生哪些命令，Combat 仍统一处理投射物碰撞和伤害。这种职责划分让法师敌人的行为节奏与法术内容可以独立配置，也避免再维护一条敌人专用的 Fireball 生成链。

## 2. 玩家效果与系统责任地图

```text
开发者 Authoring
  ├─ EnemyDefinition：移动、感知、攻击距离、冷却、受击、Kite 距离
  ├─ AttackDefinition：施法动画名与动画内释放时间
  └─ RangedEnemyController Prefab：1～N 个 WandLoadout 法术程序
                         │
                         ▼
Enemy FSM：判断何时进入施法状态、何时被 Hurt/Death 打断
                         │
                         ▼
纯选择规则：从有效程序中选下一项，多候选时排除上一次
                         │
                         ▼
SpellCaster Runtime Adapter：解释程序并创建 Unity 对象
                         │
                         ▼
ProjectileBase / Combat：飞行、碰撞、Team 过滤、ReceiveHit、死亡事件
```

各层所有权如下：

| 层 | 业务含义 | 数据或状态所有者 | 读写关系 |
|---|---|---|---|
| Authoring Data | 开发者离线配置敌人会什么法术 | `WandLoadout[]` 由 `RangedEnemyController` 的 Prefab 序列化；程序内容由 `WandLoadout`、`SpellDefinition` 资产持有 | Editor 写入，Runtime 只读 |
| Runtime State | 保存本敌人上一次实际选择的有效程序索引 | `RangedEnemyController._lastProgramIndex` | 只在真正到达动画释放点并选中程序后更新 |
| Pure Logic | 把候选数、上次索引和随机样本映射为下一索引 | `EnemySpellProgramSelector` | 无 Scene 查询、无可变状态，可独立测试 |
| Unity Runtime Adapter | 把纯解释结果转换为 Prefab、Rigidbody 和碰撞生命周期 | `SpellCaster` | 接收 Program 与施法上下文，调用 `CastEvaluator`，消费 `EmitCommand` |
| Combat | 处理投射物命中、伤害和阵营过滤 | `ProjectileBase`、`HealthComponent` | 投射物提交 `DamageRequest`，目标统一 `ReceiveHit` |
| Presentation | 播放 Animator、VFX、命中反馈和血条变化 | Animator、Projectile Prefab、事件消费者 | 消费 Gameplay 结果，不决定法术规则 |

## 3. 为什么 `WandLoadout` 放在 Controller Prefab，而不放在 `EnemyDefinition`

`EnemyDefinition` 属于 `Game.Combat` assembly，保存移动、感知、攻击节奏和受击等通用敌人数据；`WandLoadout` 属于 `Game.Skills`，而 `Game.Skills` 已经依赖 `Game.Combat`。如果让 `EnemyDefinition` 直接引用 `WandLoadout`，依赖会变成：

```text
Game.Combat → Game.Skills → Game.Combat
```

这会形成 assembly 循环，破坏底层 Combat 不依赖上层法术语义的边界。因此，法术程序引用由本来就依赖 Combat 与 Skills 的 `Game.Character` 持有，具体位置是场景中的远程敌人控制器（`RangedEnemyController`）。

这也解释了 ScriptableObject 与 Prefab 的关系：

- `SpellDefinition` 是一条可复用的法术指令资产，例如敌人火球的 Prefab、伤害、速度和 DamageType。
- `WandLoadout` 是有序指令数组，也就是一段可执行程序。
- Enemy Prefab 是 Runtime 角色模板，保存它要引用哪几段程序、施法原点在哪里，并携带真正执行程序的 `SpellCaster` 组件。

ScriptableObject 适合保存可复用、可视化编辑且能够被多个 Prefab 共享的静态配置；Prefab 适合保存组件组成、Transform 引用和“这个敌人选择哪些资产”的装配关系。每个敌人的可变状态，例如上次选中了哪一项，不写回 ScriptableObject，避免多个实例共享并污染运行时状态。

## 4. 关键数据结构及生命周期

### 4.1 原始配置数组与有效程序缓存

开发者配置的程序列表是一个 `WandLoadout[]` 引用数组（`_spellPrograms`）。数组允许普通敌人填一项，也允许 Prefab Variant 覆盖为两到三项。它可能包含 `null` 或空 `WandLoadout`，所以 Controller 在 `Awake` 中进行两遍扫描：第一遍统计有效数量，第二遍写入紧凑数组（`_validPrograms`）。

有效条件是：Program 引用存在、`Spells` 数组存在且至少包含一条指令。压缩后，攻击热路径只面对连续有效项，不需要每次释放都扫描空值，也不需要 LINQ 或临时 `List`。代价是每个敌人在 `Awake` 发生一次数组分配；这是用初始化成本换取稳定热路径的 Trade-off。

### 4.2 上一次程序索引

保存上一次实际选择结果的是一个 `int`（`_lastProgramIndex`），初始值为 `-1`，表示尚未释放过。它记录的是紧凑有效数组中的索引，而非 Inspector 原始数组索引。这样选择规则始终处理 `[0, validCount)` 的连续范围，不会被原数组中的空洞干扰。

如果施法前摇被 Hurt 或 Death 打断，动画没有到达释放点，选择函数不会运行，这个索引也不会推进。到达释放点后，即使某条 `EmitCommand` 因 Prefab 配错而没有成功 Instantiate，本次 Program 已经被选择，索引仍会更新；下一次不会因内容错误而持续选择同一项。

## 5. 随机选择规则与数学映射

随机来源是 Unity 在 Runtime 给出的 `[0, 1]` 样本（`Random.value`）。纯规则接收这个样本，不自行访问 Unity，因此规则可以用确定输入测试。

假设有效程序有三项，索引为 `[0, 1, 2]`，上一次是 `1`：

```text
原始索引：        0   1   2
排除上次选择：    0       2
紧凑候选索引：    0       1
```

算法先把随机样本映射到两个紧凑候选 `[0, 1]`。如果紧凑索引大于等于被排除的原索引，就加一：

```text
compact = 0 → result = 0
compact = 1 → result = 2
```

候选数组在逻辑上跳过了 `1`，代码不需要为每次选择创建 `[0, 2]` 这样的临时数组。两个剩余候选各占一半样本区间，因此保持均匀映射。`sample == 1`、负数、`NaN` 与 Infinity 会先钳制或清洗，避免数组越界。

选择规则的复杂度是 `O(1)`，不分配托管内存。多候选时可以保证相邻两次不重复；它不保证长序列严格轮询，也不保证短样本中每项出现次数完全相等。

## 6. 完整 Runtime 调用链

```text
EnemyControllerBase.Update
  → 当前 Enemy FSM State.Update
  → EnemyRangedAttackState.Update
      读取 Animator 当前状态、shortNameHash、normalizedTime
      确认已经进入目标施法动画且不处于 Transition
      normalizedTime 到达 AttackDefinition.ArrowSpawnTime
  → RangedEnemyController.CastSelectedProgram
      从 _validPrograms 选择一项
      记录 _lastProgramIndex
      计算 CastOrigin 与玩家胸口目标点
  → SpellCaster.CastProgram(..., SpellManaPolicy.IgnoreMana)
  → CastEvaluator 解释 WandLoadout.Spells
  → 复用 List<EmitCommand> 输出纯命令快照
  → SpellCaster 根据 SpawnMode 创建 Forward / Static / Skyfall 对象
  → ProjectileBase.Init 注入 Team、AttackerId、伤害、速度与施法者 Collider
  → ProjectileBase 碰撞或 Trigger Payload 回调
  → IDamageable.ReceiveHit(in DamageRequest)
  → HealthComponent 扣血并发布 DamageReceivedEvent / DeathEvent
```

攻击状态中的单次布尔门闩（`_released`）非常关键。动作超过释放时间后，后续每帧的 `normalizedTime` 仍满足条件；门闩确保一次动画只提交一次 Program。这里使用“释放”命名，因为一段 Program 可以生成多发、Trigger、Shield 或 Skyfall，业务语义已经超出“发射一颗火球”。

## 7. 瞄准与 3D 数学

法术生成点是敌人模型法杖前端的世界空间 Transform（`_castOrigin`）。目标点取玩家世界坐标加一个竖直偏移（`Vector3.up * _aimHeightOffset`），让投射物瞄准胸口而非脚底。Controller 向 `SpellCaster` 提交的是两个世界空间点：生成点和目标点。

`SpellCaster` 内部计算：

```text
direction = aimPoint - spawnPosition
direction = Normalize(direction)
velocity = direction * spellSpeed
```

两点相减得到带长度的方向向量；Normalize 后只保留方向；再乘以 `SpellDefinition.BaseSpeed` 得到单位为米/秒的初速度。若两点几乎重合，则使用敌人的 `transform.forward` 作为稳定降级方向。

## 8. `IgnoreMana` 的业务含义

Enemy 调用显式程序入口时传入 `SpellManaPolicy.IgnoreMana`。它表示法术仍经过同一个 `CastEvaluator`、`EmitCommand`、Projectile 与 Payload 链，只跳过对施法者 `ManaComponent` 的检查和扣除。Enemy 的释放频率继续由 `AttackCooldown`、FSM 和动画控制，因此当前 Gameplay 节奏没有引入敌人 Mana 资源。

这个策略参数只影响一次调用，不修改玩家入口。玩家继续通过 `CastWand` 使用 `SpendCasterMana`，现有回归测试验证零 Mana 时玩家施法失败，而同一 Program 经 `IgnoreMana` 可以解释执行。

## 9. 删除旧字段后的单一数据源

旧的 `EnemyDefinition.ProjectileSpeed` 与 `EnemyDefinition.ProjectilePrefab` 已删除。现在：

- 法术内容由 `SpellDefinition` 唯一配置：Prefab、伤害、速度、DamageType、SpawnMode、Payload 等。
- 程序顺序由 `WandLoadout` 唯一配置。
- 敌人攻击节奏仍由 `EnemyDefinition` 配置：AttackRange、AttackCooldown、RetreatDistance。
- 动画释放时机仍由 `AttackDefinition.ArrowSpawnTime` 配置。

保留 `AttackDefinition` 的原因是它仍承担 Animator 状态名和释放时机；删除整个攻击资产会把动画时序硬编码回 Controller。

## 10. 方案取舍与边界

### Prefab 数组与独立 EnemySpellProfile

当前选择 Prefab 上直接保存 `WandLoadout[]`。普通敌人一项、精英 Variant 两到三项时，它的 Authoring 路径短，运行时也只需一个数组。代价是多个 Prefab 若要共享完全相同的“程序池及选择策略”，需要重复数组引用。等程序池出现权重、条件、阶段或大量跨 Prefab 复用时，独立 Profile ScriptableObject 才会带来更明显收益。

### 避免连续重复与完全独立随机

完全独立随机实现更简单，但两到三项时很容易连续多次命中同一项，玩家会感觉敌人没有能力变化。排除上一项改善短期观感，同时仍保留随机性。代价是序列存在一阶相关性：下一次概率受上一次结果约束。

### 动画轮询与 Animation Event

项目统一通过 `AnimatorStateInfo.normalizedTime` 和数据中的释放时间驱动攻击，不额外维护 Animation Event。它让时序集中在 ScriptableObject 并便于不同动画复用同一代码。代价是状态名必须与 Animator 精确一致，而且 CrossFade 期间需要检查 `shortNameHash` 与 Transition，避免在错误动画中释放。

## 11. Debug 路线

### 症状：只播放施法动画，没有法术

按数据向 Runtime 的顺序检查：

```text
RangedEnemyController.Spell Programs
→ WandLoadout.Spells 是否为空
→ SpellDefinition.Kind / ProjectilePrefab
→ Prefab 根节点是否有 SpellCaster
→ Cast Origin 是否保留法杖前端引用
→ AttackDefinition.AnimationStateName 与 ArrowSpawnTime
→ Animator 当前 shortNameHash / Transition
```

### 症状：连续出现相同程序

先用确定 sample 调用纯选择器，确认 `programCount` 与 `previousIndex`。再检查 Controller 保存的是有效数组索引，并确认实际攻击是否到达释放点。施法前摇被打断不会推进上次索引，这是预期语义。

### 症状：法术会伤到友军或归属错误

检查 `CastProgram` 收到的 `HealthComponent.TeamId`、`HealthComponent.Id` 和敌人 `CharacterController` Collider。Payload 使用施法时捕获的值快照继续运行，不应在未来命中帧重新查找 Enemy。

## 12. 性能与证据边界

代码层面可以确认：

- 有效数组只在 `Awake` 创建；攻击状态每帧不会创建选择集合。
- 选择规则为 `O(1)`，没有 LINQ、闭包或装箱。
- `SpellCaster` 复用内部 `List<EmitCommand>` 与音效去重集合。
- Projectile `Instantiate` 属于离散施法成本，仍会产生对象创建成本；本次没有引入 Object Pool。

自动化测试可以确认：

- 纯选择规则覆盖零、单、多候选、无连续重复与异常样本。
- Runtime Adapter 会过滤无效 Program，并以 `IgnoreMana` 调用统一法术管线。
- 生产火球资产保持 10 伤害、18 速度、Magical，默认 Program 只有一条指令。
- `MagicEnemy_Base.prefab` 拥有 `SpellCaster`、Cast Origin 和一项默认 Program。

本次实际自动化结果：`Game.Character.Tests` EditMode 共 104 项，104 项通过；显式 Program 的既有 PlayMode 回归 1 项，1 项通过。PlayMode 结果证明共享 `SpellCaster.CastProgram` 与 Projectile 生命周期入口可运行，但它没有代替 P7 场景中 Enemy Animator、FSM 和打断行为的人工验收。

当前不能据此声称：

- P7 场景中 Animator、受击打断、死亡与导航已完成 Scene Playthrough。
- 多个敌人同时施法达到某个具体 CPU 耗时或 `GC Alloc` 数字。
- 三程序在真实动画释放中已经连续观察 20 次。

这些结论需要 Play Mode、Scene Playthrough 与 Profiler capture 分别补充证据。

## 14. 面试口述参考

我把法师小兵的攻击拆成“什么时候施法”和“施放什么程序”两部分。敌人的感知、Kite 和 FSM 继续决定进入施法状态，攻击动画到达数据配置的释放时间后，远程敌人控制器才从开发者配置的法术程序中选一套执行。普通法师配置一个 `WandLoadout`，精英怪可以配置两到三套；多个候选时我保存上一次实际释放的索引，用一个纯函数把随机样本映射到排除上一项后的紧凑索引，所以能够避免连续重复，也不会在施法时创建临时数组。

选出的程序统一交给 `SpellCaster.CastProgram`，继续复用玩家和 Boss 的 `CastEvaluator`、`EmitCommand`、Projectile、Trigger Payload 与 Combat 伤害链。Enemy 传 `IgnoreMana`，因此不消耗 Mana，攻击频率仍由 FSM、动画和冷却控制。数据边界上，我没有把 `WandLoadout` 塞进 `EnemyDefinition`，因为后者位于 `Game.Combat`，那样会让 Combat 反向依赖 Skills 并形成 assembly 循环；程序引用放在同时依赖两者的 `Game.Character` Controller Prefab 上。这个设计的 Trade-off 是当前 Prefab 数组适合一到三套简单配置，将来若程序池需要权重或复杂条件，才值得再抽独立 Profile。
