> 目标读者：正在学习 Unity Graphics、ShaderLab、HLSL 与 Particle System 的初学者  
> 对应阶段：P2 / Task 6 / Step 5A～5D  
> 当前结论：5A～5D 已由开发者在 Unity Editor 中完成视觉验证；5E `Extinguish Steam`、5F Rendering/Profiler Gate、正式 `EV_FireArea` Prefab 尚未完成。  
> 对应源码：`Assets/_Project/Art/Elemental/Shaders/ElementFireCore.hlsl`、`ElementFireBody.shader`、`ElementFireAdditive.shader`

本文解释的不是“真实燃烧模拟”，而是一套面向 3D RPG 局部火区的**程序化火焰视觉近似**。它没有求解燃料、氧气、温度场、流体速度、压力或 Navier–Stokes 方程，也没有构造真正的体积火焰。当前方案把复杂问题拆成两个层次：GPU Shader 决定“一张火焰片上的每个像素是什么颜色、透明度和轮廓”，CPU Particle System 决定“场景中有多少张火焰片、它们在哪里出生、怎样运动、何时消失”。最终通过 Alpha Body、Additive Core 和 Additive Sparks 三层叠加，形成具有外轮廓、高温焰芯和能量逸散方向的火区。

## 0. 先从最终结果出发：玩家看到的火焰到底由什么组成

最终画面看起来是一片持续燃烧的火区：橙红色外焰保持可辨认的轮廓；每一片外焰内部有更小、更亮的黄白色焰芯；少量火星快速向上逸出；单片火焰自身还会产生向上流动、顶部摆动和局部明暗变化。这个结果并不是由一个“火焰 Prefab 黑盒”产生，而是由不同技术各自解决不同问题：

```text
单片火焰的程序化数学（GPU Fragment Shader）
    ├── UV 高度函数          → 下宽上窄的静态轮廓
    ├── 双层 Value Noise     → 向上流动与边缘破碎
    ├── Temperature Mask     → 底部/局部高温配色
    ├── Alpha Blend          → 有厚度感的橙红外焰
    └── Additive Blend       → 黄白高温焰芯与火星

多片火焰的生命周期（Unity Particle System）
    ├── PS_FireBody          → 外焰的位置、数量、尺寸与消亡
    ├── Birth Sub Emitter
    │   └── PS_FireCore      → 与外焰一一配对的内部焰芯
    └── PS_FireSparks        → 独立、稀疏、快速上升的火星

二者组合
    └── 多张始终面向 Camera 的程序化火焰 Billboard
```

可以把一帧中某个火焰 Fragment 的最终输出概括为：

```text
UV + Time
  ↓
双层 Value Noise
  ├──> Center Offset / Width Offset ──> Shape Mask
  └──> Temperature Mask

Shape Mask + Temperature Mask + Height Color
  ├──> Body RGB / Alpha ──> Alpha Blend
  └──> Core RGB / Alpha ──> Additive Blend

Particle Vertex Color / Alpha
  └──> 再控制每个粒子一生中的颜色与透明度
```

这里必须先纠正一个常见误解：我们没有“在 3D 空间里直接画一团火”。Particle System 实际生成许多 Quad，`Vertical Billboard` 或 `Stretched Billboard` 负责调整这些 Quad 的朝向和形状；Shader 再对每张 Quad 覆盖到的 Fragment 计算一个火焰 Mask。看起来像连续火焰，是因为人眼把多张透明、动态、相互重叠的二维火焰片整合成了一个整体。

### 当前成果的明确边界

- 已完成：程序化单片轮廓、双层 Value Noise、向上流动、温度配色、Body/Core 两种 Blend、Particle Vertex Color、Body/Core 一一配对、火星与三层组合。
- 未完成：Wet + Burning 的 Steam、反应事件驱动、正式环境 Prefab、Frame Debugger/Profiler/Overdraw 性能 Gate。
- 没有实现：真实体积火、流体模拟、热折射、动态灯光、Shadow Casting、燃料传播或 Gameplay Burning 规则。
- 当前 Fire Visual 是 Rendering 表现；角色是否 Burning、状态扣血与元素反应仍由 `Game.Combat` 的 Gameplay 代码负责。

## 1. 用“难题拆解”反向追问：为什么最终画面像火

如果一开始就打开 Shader 文件并同时写 Noise、颜色、粒子和 Blend，很容易出现“画面不对，但不知道错在哪一层”的问题。我们的做法是从最终结果反向追问，把模糊的“做一团火”变成可以单独验收的小问题。

### 第一层追问：最终画面提供了哪些火焰视觉线索

| 玩家看到的线索 | 如果缺失会怎样 | 对应技术 |
|---|---|---|
| 下宽上窄、顶部收尖 | 只像矩形贴片 | UV Height Function + Shape Mask |
| 边缘柔和而非硬切 | 像剪纸或 UI 图标 | `smoothstep` + Alpha |
| 图案持续向上 | 像静止 Logo | `_Time.y` + Moving UV |
| 根部稳定、顶部活跃 | 像整块布左右漂移 | Height Influence `y²` |
| 橙红外焰仍然可见 | 亮背景中丢失整体形状 | Alpha Blend Body |
| 中心更亮、更热 | 缺少温度层次 | Additive Core + HDR Color |
| 每片 Core 都在 Body 内 | 焰芯和外焰像两套无关粒子 | Birth Sub Emitter |
| 少量高速亮点上升 | 缺少能量逸散与运动方向 | Additive Stretched Billboard Sparks |
| 出生和死亡连续 | 粒子突然弹出/消失 | Color/Size over Lifetime |

### 第二层追问：这些线索分别需要什么输入数据

| 小功能 | 输入 | 中间量 | 输出 |
|---|---|---|---|
| 静态轮廓 | Quad UV、宽度参数 | `height01`、`halfWidth`、`distanceFromCenter` | `shapeMask` |
| 流动破碎 | UV、`_Time.y`、Noise Scale/Speed | `noiseA`、`noiseB`、`combinedNoise` | `centerOffset`、`widthOffset` |
| 温度配色 | UV.y、`combinedNoise` | `temperatureMask` | Body/Core RGB 与 Alpha 权重 |
| 粒子生命周期 | Age、Lifetime、Curve | `normalizedAge` | 粒子 Color、Alpha、Size |
| 多片空间分布 | Shape、Emission、Velocity | 粒子 Position/Velocity | 火区整体形态 |
| Body/Core 配对 | Parent Particle Birth | Source Position/Size/Rotation | 同位置的 Core Particle |

### 第三层追问：应该按照什么顺序开发

最终效果的依赖是“轮廓 → 动画 → 分层材质 → 多粒子组合”，因此实际开发顺序就是 5A～5D：

1. **5A：单 Quad 静态轮廓。**只验证 Mask 数学，不加入 Time、Noise 或 Particle System。
2. **5B：程序化流动。**在静态轮廓正确的前提下，用稳定 Noise 扭曲中线和宽度。
3. **5C：Body/Core 分层。**复用同一轮廓数学，只改变颜色职责与 Blend State。
4. **5D：Particle System 三层火区。**让大量火焰片获得出生、运动、消亡和配对关系。

这种顺序的价值不只是“容易做”，更重要的是每个 Gate 都有唯一问题：5A 错了就查几何 Mask；5B 错了就查 Noise/Time；5C 错了就查 Blend/颜色；5D 错了才查 Particle System。它把视觉 Debug 从“猜参数”变成了可定位的数据流验证。

## 2. 开始读 Shader 前必须掌握的基础概念

### 2.1 Shader、Material、Mesh、Particle System 分别是什么

- **Mesh** 提供顶点、三角形和 UV。当前每个火焰粒子最终都以一个 Quad 为绘制载体。
- **Shader** 是 GPU 程序，规定顶点怎样变换、每个 Fragment 怎样计算颜色和 Alpha，以及使用什么 Render State。
- **Material** 是某个 Shader 的参数实例。Body、Core、Sparks 可以复用 Shader，但持有不同颜色、宽度、强度等参数。
- **Particle System** 是粒子生命周期与空间运动系统。它不理解“这是火”；它只管理 Position、Velocity、Color、Size、Lifetime 等数据。
- **ParticleSystemRenderer** 把每个活着的 Particle 转换成 Billboard Quad，并把粒子 Color 等 Vertex Stream 送进 Shader。

因此，“Shader 做外观、Particle System 做运动”不是一句口号，而是明确的数据边界：Shader 不负责决定场景里有多少火焰片，Particle System 也不负责在 Quad 内判断哪个像素属于火焰。

### 2.2 Vertex、Fragment 与 Rasterization

当前 Shader 的简化管线为：

```text
Object Space Vertex
  ↓ Vertex Shader：Object → World → View → Clip
Clip Space Triangle
  ↓ Rasterization：判断覆盖哪些屏幕像素，并插值 UV/Color
Fragment Shader
  ↓ 计算 Shape Mask、Noise、RGB、Alpha
Blend Stage
  ↓ 与 Framebuffer 里已有背景颜色混合
Screen Pixel
```

Vertex Shader 每个顶点执行一次，Fragment Shader 对三角形覆盖到的每个 Fragment 执行。火焰的主要成本通常在 Fragment 阶段，因为透明火焰片重叠时，同一屏幕像素可能重复运行多次，这就是 `Overdraw`。

### 2.3 Coordinate Space 与当前用到的 UV Space

`positionOS` 的 `OS` 是 Object Space，表示顶点相对当前 Quad 原点的位置。`TransformObjectToHClip` 依次完成 Object → World → View → Homogeneous Clip Space 变换，最终结果写入 `SV_POSITION`。

火焰轮廓主要在 UV Space 中计算。标准 Quad 的 UV 通常为：

```text
uv.x = 0：左边界        uv.x = 1：右边界
uv.x = 0.5：水平中线
uv.y = 0：底部          uv.y = 1：顶部
```

UV 是无单位的局部参数空间，不是米。一个 Scale 为 1 的 Quad 和一个被放大十倍的 Quad，只要 UV 相同，程序化轮廓在各自表面上的相对比例就相同。代价是世界空间火焰细节会随 Particle Size 一起放大。

### 2.4 Mask 是整个效果的核心语言

Mask 是通常处于 `[0,1]` 的标量：

- `0`：完全不属于某效果；
- `1`：完全属于某效果；
- 中间值：连续过渡区域。

三个最常见函数为：

```text
Saturate(x) = Clamp(x, 0, 1)

Lerp(A, B, t) = A × (1-t) + B × t

Smoothstep(e0, e1, x)：
    t = Saturate((x-e0)/(e1-e0))
    result = t² × (3-2t)
```

`Lerp` 用 Mask 在两个端点之间连续混合。`Smoothstep` 与普通 Step 不同，它在边界两侧连续过渡，且 Hermite 曲线两端的一阶导数为零，所以适合做柔边和渐隐。

### 2.5 `_Time.y` 与 Particle Normalized Age 是两套时间

Shader 使用 Unity 内置 `_Time.y`，它表示持续增长的场景时间，所有使用该 Material 的 Fragment 都能据此让 Noise 连续移动。Particle System 另有每个粒子的年龄：

```text
normalizedAge = age / lifetime
```

`normalizedAge=0` 是出生，`=1` 是死亡。`Color over Lifetime` 和 `Size over Lifetime` 曲线横轴使用的就是这个归一化时间。Shader Time 决定火焰片内部纹路如何流动；Particle Age 决定整张火焰片如何出生和消亡，两者不能互相替代。

## 3. Step 5A：先在一张 Quad 上画出静态火焰轮廓

5A 的目标不是“做好火焰”，而是回答最底层问题：**给定一个矩形 Quad，怎样用数学把它裁成下宽上窄、边缘柔和的火焰 Mask？**

核心函数是 `ElementFireShapeFromOffsets`。在 5A 中，`centerOffset` 和 `widthOffset` 都传入 0，因此轮廓完全静态且左右对称。

### 3.1 把 UV.x 变成“到中线的距离”

源码：

```hlsl
float distanceFromCenter = abs((uv.x * 2.0 - 1.0) - centerOffset);
```

先做坐标映射：

```text
xCentered = 2 × uv.x - 1
```

于是：

```text
uv.x = 0   → xCentered = -1
uv.x = 0.5 → xCentered =  0
uv.x = 1   → xCentered =  1
```

再取绝对值：

```text
distanceFromCenter = |xCentered - centerOffset|
```

这样左右两侧被转换成同一个“离中线多远”的非负距离。`centerOffset=0` 时轮廓左右对称；5B 中让它随 Noise 变化，就能让某一高度的火焰中线左右摆动。

### 3.2 用高度决定半宽

源码：

```hlsl
float height01 = saturate(uv.y);
float shapedHeight = pow(height01, max(shapePower, 0.0001));
float halfWidth = saturate(lerp(baseWidth, tipWidth, shapedHeight) + widthOffset);
```

对应公式：

```text
y_s = y^p
w(y) = Lerp(BaseWidth, TipWidth, y_s) + WidthOffset
```

其中：

- `height01`：当前 Fragment 在火焰中的归一化高度；
- `baseWidth`：底部半宽，1 表示从中线一直到 Quad 边界；
- `tipWidth`：顶部半宽；
- `shapePower = p`：控制“在哪个高度开始明显收窄”；
- `widthOffset`：5B 用 Noise 添加的局部宽度变化。

当 `0<y<1` 时：

- `p > 1`：`y^p < y`，火焰在中下部更久地保持接近 BaseWidth，到上部才快速收窄；
- `p = 1`：宽度线性变化；
- `0 < p < 1`：`y^p > y`，较早向 TipWidth 收窄。

这一步把“火焰下宽上窄”从美术描述变成了一条可调的宽度曲线。

### 3.3 用 `smoothstep` 把硬边界变成柔边

如果只写：

```text
distanceFromCenter < halfWidth ? 1 : 0
```

边缘会是突然从 1 跳到 0 的硬切，像剪纸。当前实现为：

```hlsl
float innerEdge = max(halfWidth - safeSoftness, 0.0);
float horizontalMask = 1.0 - smoothstep(
    innerEdge,
    max(halfWidth, 0.0001),
    distanceFromCenter);
```

其空间关系是：

```text
距离 < halfWidth-softness：Mask ≈ 1
距离处于柔边区间：Mask 从 1 平滑下降到 0
距离 ≥ halfWidth：Mask = 0
```

`edgeSoftness` 越大，轮廓越柔、越像半透明火气；过大则整片火焰失去清晰主体。它是 UV 距离，不是世界单位。

### 3.4 底部淡入与顶部淡出

底部 Mask：

```hlsl
float bottomMask = smoothstep(0.0, baseFade, height01);
```

顶部 Mask：

```hlsl
float topMask = 1.0 - smoothstep(tipFadeStart, 1.0, height01);
```

底部 `y=0` 时为 0，经过 `baseFade` 后接近 1，避免 Quad 底边出现一条硬直线。顶部在 `tipFadeStart` 之前接近 1，之后逐渐降到 0，避免火焰尖端在 Quad 顶边被矩形裁断。

最后三个条件相乘：

```hlsl
return saturate(horizontalMask * bottomMask * topMask);
```

可以把乘法理解为逻辑“AND”的连续版本：一个 Fragment 必须同时位于横向轮廓内、已经完成底部淡入、尚未完成顶部淡出，最终 Mask 才高。

### 3.5 5A 为什么必须单独验收

静态 Gate 通过时，我们能确认：

- UV 方向正确，底部和顶部没有颠倒；
- 宽度函数连续；
- 左右对称；
- `smoothstep` 边缘没有硬锯齿；
- 顶部和底部没有被 Quad 边界截断。

如果静态轮廓本身错误，后面加入 Noise 只会让错误更难观察。先证明 `centerOffset=0`、`widthOffset=0` 的基线，是程序化视觉开发中非常重要的 Debug 方法。

## 4. Step 5B：让静态轮廓产生连续向上流动和顶部摆动

5B 要解决两个问题：一是火焰内部不能像静态图标；二是火焰边缘不能始终保持完美光滑的数学曲线。我们没有导入 Noise Texture，而是手写 `Hash + Value Noise`，得到一个可重复、连续变化的程序化标量场。

### 4.1 Hash：稳定伪随机，而不是每帧重新随机

源码：

```hlsl
float ElementFireHash21(float2 position)
{
    position = frac(position * float2(123.34, 456.21));
    position += dot(position, position + 45.32);
    return frac(position.x * position.y);
}
```

`Hash21` 的含义是“二维输入，输出一个标量”。它不是密码学 Hash，也不是物理随机数；它只是通过乘法、`dot` 与 `frac` 把相邻格点打散到 `[0,1)`。

```text
frac(x) = x - floor(x)
```

同一个输入格点始终得到同一个输出，因此空间图案稳定。动画来自“采样坐标移动”，而不是每帧换一套随机值。若每帧重新随机，视觉结果会闪烁；稳定 Hash + 连续移动坐标才会形成流动。

常数 `123.34`、`456.21`、`45.32` 只是经验 Seed，用来降低 X/Y 相关性，不是火焰物理常数。

### 4.2 Value Noise：把离散随机格点变成连续场

对任意采样位置 `p`：

```hlsl
float2 cell = floor(position);
float2 local = frac(position);
float2 smooth = local * local * (3.0 - 2.0 * local);
```

- `cell` 找到当前整数网格；
- `local` 表示当前位置在格子内部的 `[0,1]²` 坐标；
- `smooth=f²(3-2f)` 对局部坐标做 Hermite 平滑。

四个角点分别取得稳定随机值：

```text
a = Hash(cell + (0,0))
b = Hash(cell + (1,0))
c = Hash(cell + (0,1))
d = Hash(cell + (1,1))
```

再做 Bilinear Interpolation：

```text
bottom = Lerp(a, b, smooth.x)
top    = Lerp(c, d, smooth.x)
noise  = Lerp(bottom, top, smooth.y)
```

为什么不能直接输出某个格点的 Hash？因为那样整个格子内部都是同一个值，经过边界时会突然跳变，得到方块噪声。Bilinear Interpolation 让值在格内连续；Hermite 曲线让格子边界处的斜率也更平缓。

### 4.3 Noise Scale 的图形学意义

采样实际使用：

```text
Noise(movingUV × NoiseScale)
```

Scale 放大采样坐标。一个 `[0,1]` UV 区域乘以 3，会跨越约 3 个 Noise 格；乘以 7，会跨越更多格。因此：

- Scale 小：低频、大块、变化缓慢；
- Scale 大：高频、小块、细节更碎。

注意这描述的是 UV Space Frequency。Particle Size 改变时，世界空间中每个 Noise 块的实际尺寸也会改变。

### 4.4 为什么“采样坐标向下”会看到图案向上

第一层移动坐标：

```hlsl
float2 movingUvA = uv - float2(0.0, upwardSpeedA * timeValue);
```

考虑 Noise 中某个特征原本出现在采样坐标 `y0`。屏幕当前 UV 高度 `y` 想采到它，需要：

```text
y - speed × time = y0
```

移项得到：

```text
y = y0 + speed × time
```

因此随着时间增加，屏幕上看到的特征位置向更大的 UV.y 移动，也就是向火焰顶部移动。这里移动的是**采样坐标**，不是 Mesh Vertex。

### 4.5 为什么使用两层 Noise

第二层 Noise 使用镜像 X 和固定偏移：

```hlsl
float2 movingUvB = float2(1.0 - uv.x + 3.17, uv.y + 5.31)
    - float2(0.0, upwardSpeedB * timeValue);
```

`1-uv.x` 改变横向方向，`3.17/5.31` 打散采样起点，不让两层总在相同格点上高度相关。两层组合为：

```hlsl
combinedNoise = saturate(noiseA * 0.65 + noiseB * 0.35);
```

当前职责不是严格的 FBM 物理模型，而是风格化分工：

- `noiseA` 权重更高、频率相对低，主要让轮廓中线产生大尺度摆动；
- `noiseB` 权重较低、频率相对高，主要改变局部宽度、破坏完美边缘。

程序化 Noise 不代表免费。每层 Value Noise 需要四次 Hash 和多次插值，两层意味着 Fragment ALU 成本明显高于一次普通 Texture Sample；最终是否优于 Flipbook 必须在 5F 用 GPU Profiler 验证。

### 4.6 从 `[0,1]` Noise 转换成可左右扰动的 `[-1,1]`

Value Noise 输出主要处于 `[0,1]`。如果直接乘强度，偏移只能朝正方向。当前实现中心化：

```hlsl
float centeredNoiseA = noiseA * 2.0 - 1.0;
float centeredNoiseB = noiseB * 2.0 - 1.0;
```

映射关系为：

```text
0   → -1
0.5 →  0
1   →  1
```

这样中线既能向左也能向右，宽度既能收缩也能扩张。

### 4.7 为什么扰动要乘 `y²`

```hlsl
float heightInfluence = height01 * height01;
float centerOffset = centeredNoiseA * distortionStrength * heightInfluence;
float widthOffset = centeredNoiseB * detailStrength * heightInfluence;
```

对应公式：

```text
I(y) = y²
CenterOffset = (2NoiseA-1) × DistortionStrength × I(y)
WidthOffset  = (2NoiseB-1) × DetailStrength     × I(y)
```

几个关键高度：

```text
y=0   → I=0
y=0.5 → I=0.25
y=1   → I=1
```

因此根部几乎不动，中部只获得四分之一扰动，顶部获得完整扰动。它不是流体力学方程，而是把“火焰附着在燃烧表面、上部受热流影响更大”的观察特征编码成稳定的美术约束。如果不乘高度权重，整张火焰片会像一块左右漂移的布。

### 4.8 Temperature Mask：高度与动态 Noise 共同表示“热区”

```hlsl
float baseHeat = 1.0 - saturate(height01);
float mixedHeat = lerp(baseHeat, combinedNoise, saturate(noiseWeight));
return pow(saturate(mixedHeat), max(contrast, 0.0001));
```

公式为：

```text
BaseHeat = 1-y
MixedHeat = Lerp(BaseHeat, CombinedNoise, HeatNoiseWeight)
TemperatureMask = Saturate(MixedHeat)^HeatContrast
```

- `BaseHeat=1-y`：底部热、顶部冷的稳定高度梯度；
- `CombinedNoise`：随时间上升的局部热团；
- `HeatNoiseWeight=0`：只看高度；
- `HeatNoiseWeight=1`：只看 Noise；
- `HeatContrast>1`：压低中间灰度，让高值区域更集中；
- `HeatContrast<1`：扩大中高值区域。

这只是温度视觉 Mask，不是真实摄氏温度，也不是黑体辐射换算。它的价值是让颜色和亮度变化共享一个有明确含义的控制信号。

## 5. Step 5C：为什么要把外焰 Body 与高温 Core 拆成两个 Shader

单个 Blend Mode 很难同时满足两个目标：外焰要在亮背景上仍保留橙红轮廓，高温核心又要具有“向背景增加光能”的亮感。因此我们复用同一套轮廓/Noise 数学，但使用两个不同的 ShaderLab Render State。

### 5.1 Body 的颜色链

Body 首先按高度混合底色与顶色：

```hlsl
half3 heightColor = lerp(_BottomColor.rgb, _TopColor.rgb, saturate(input.uv.y));
```

```text
HeightColor = Lerp(BottomColor, TopColor, y)
```

再根据 Temperature Mask 向 `_HotColor` 混合：

```hlsl
half hotBlend = saturate(temperatureMask * _HotColorStrength);
half3 temperatureColor = lerp(heightColor, _HotColor.rgb, hotBlend);
```

```text
HotBlend = Saturate(TemperatureMask × HotColorStrength)
TemperatureColor = Lerp(HeightColor, HotColor, HotBlend)
```

最终颜色还乘 Particle Vertex Color 与整体强度：

```text
BodyRGB = TemperatureColor × VertexTint.rgb × ColorIntensity
```

Body Alpha 为：

```hlsl
float alphaVariation = lerp(
    1.0 - saturate(_AlphaNoiseStrength),
    1.0,
    combinedNoise);

finalAlpha = saturate(
    shapeMask * _GlobalAlpha * alphaVariation * vertexTint.a);
```

公式：

```text
AlphaVariation = Lerp(1-AlphaNoiseStrength, 1, CombinedNoise)
BodyAlpha = Saturate(
    ShapeMask × GlobalAlpha × AlphaVariation × ParticleAlpha
)
```

`AlphaVariation` 的最低值仍为 `1-Strength`，所以默认不会把 Body 打穿成大量透明孔洞。Body 的职责是保持连续外轮廓，而不是展示最强能量分区。

### 5.2 Alpha Blend 为什么适合 Body

ShaderLab：

```shaderlab
Blend SrcAlpha OneMinusSrcAlpha
```

RGB 混合公式：

```text
Cout = Csrc × α + Cdst × (1-α)
```

- `Csrc`：当前火焰 Fragment 颜色；
- `Cdst`：Framebuffer 中已经存在的背景颜色；
- `α`：Body Fragment 输出 Alpha。

Alpha 增加时，火焰颜色占比提高、背景占比下降，因此 Body 能形成稳定的橙红色“主体”。它的缺点是多层重叠会不断遮盖背景，排序错误时也会暴露透明渲染问题。

### 5.3 Additive Core 的颜色与 Alpha 链

Core 复用 `ElementFireAnimatedShape` 与 `ElementFireTemperatureMask`，但宽度更窄、顶部更早淡出。颜色链为：

```hlsl
half3 heightColor = lerp(_BottomColor.rgb, _TopColor.rgb, input.uv.y);
half heatBrightness = lerp(0.35, 1.0, temperatureMask);
half3 finalColor = heightColor
    * vertexTint.rgb
    * heatBrightness
    * _ColorIntensity;
```

Alpha 链为：

```text
CoreAlpha = Saturate(
    ShapeMask
    × GlobalAlpha
    × AlphaVariation
    × Lerp(0.4, 1, TemperatureMask)
    × ParticleAlpha
)
```

这让温度高的区域不仅颜色更亮，对 Additive Framebuffer 的贡献也更大。

### 5.4 Additive Blend 为什么适合高温 Core 与 Sparks

ShaderLab：

```shaderlab
Blend SrcAlpha One
```

RGB 混合公式：

```text
Cout = Csrc × α + Cdst
```

目标颜色 `Cdst` 不会乘以 `(1-α)` 被压暗，而是保留原值，再加上火焰贡献。Additive 的中性元素是黑色：

```text
Csrc = 0 → Cout = Cdst
```

因此它非常适合光、火星、魔法亮芯等发光感，但有明确风险：重叠越多越亮，HDR 强度、粒子数量或 Alpha 过高都会导致过曝。Additive 负责“增强”，不能代替 Body 保持外形。

### 5.5 HDR Color 与 Bloom 的关系

Material 中 `[HDR]` Color 可以让 RGB 分量超过 1。在线性 HDR Render Target 中，这些高亮值可以被后处理 Bloom 识别并扩散成光晕。即使没有 Bloom，Additive 仍会增加 Framebuffer 亮度；但“周围泛光”不是 Shader 自动产生的，通常需要 URP HDR + Bloom。当前阶段没有把动态 Point Light 加入火区，以避免额外灯光和阴影成本。

### 5.6 Render Queue、Depth 与 Cull

Body：

```text
Queue = Transparent（通常 3000）
```

Core：

```text
Queue = Transparent+10（通常 3010）
```

Core 排在 Body 后绘制，使共面实验 Quad 和叠层粒子更稳定地表现“核心覆盖在主体之上”。这不是完整透明排序解决方案；真正排序还受 Camera Distance、Renderer Sorting、同 Queue 顺序等影响。

两个 Shader 都使用：

```shaderlab
ZWrite Off
ZTest LEqual
Cull Off
```

- `ZWrite Off`：透明 Fragment 不写 Depth Buffer，避免先画的火焰片错误挡住后画的透明片；代价是透明排序与 Overdraw。
- `ZTest LEqual`：仍读取已有 Depth，墙后的火焰通常不会穿墙显示。
- `Cull Off`：Quad 正反面都绘制，方便 Billboard/实验 Quad 从两侧可见；代价是潜在额外 Fragment 成本。

### 5.7 为什么 Additive Fog 要向黑色衰减

Body 使用 `MixFog`，它会把远处颜色向场景 Fog Color 混合，这是普通表面的自然行为。Additive 如果也向 Fog Color 混合，再执行加法，就会把 Fog Color 额外叠加到背景，产生远处反而发亮的错误。因此 Additive 使用：

```hlsl
finalColor = MixFogColor(finalColor, half3(0,0,0), fogFactor);
```

距离越远，Additive 贡献越接近黑色，也就是“什么都不增加”。这体现了一个重要原则：不同 Blend Mode 的中性元素不同，Fog 处理不能机械复制。

## 6. Shader 代码结构逐层讲解

### 6.1 为什么拆成一个 HLSL Core 和两个 ShaderLab 文件

```text
ElementFireCore.hlsl
    ├── Hash / Value Noise
    ├── Static/Animated Shape
    └── Temperature Mask

ElementFireBody.shader
    ├── Body Material Properties
    ├── Alpha Blend Render State
    └── Body Vertex/Fragment 输出

ElementFireAdditive.shader
    ├── Core/Sparks Material Properties
    ├── Additive Blend Render State
    └── Additive Vertex/Fragment 输出
```

轮廓和 Noise 属于可复用的“纯数学”，Blend、Queue、颜色职责属于具体 Pass。把公共数学放进 `.hlsl` 可以防止 Body 与 Core 各复制一份后逐渐不一致。Render State 不能在一个 Fragment 内按像素随意切换，因此 Body 与 Core 使用两个 Shader，而不是在一个 Shader 里用 `if` 选择 Blend。

`ElementFireStaticShape` 仍然保留为静态入口，它只是给 `ElementFireShapeFromOffsets` 传入两个 0。这样调试时可以明确回到 5A 基线，而不需要删除动画代码；正式 Body/Core 则调用 `ElementFireAnimatedShape`。这相当于给同一套核心数学保留“静态测试入口”和“动态生产入口”。

### 6.2 `Properties`：Material Inspector 与 GPU 参数的入口

例如：

```shaderlab
_BaseWidth("Base Half Width", Range(0.05, 1)) = 0.72
[HDR] _BottomColor("Bottom Color", Color) = (...)
[Toggle] _UseVertexColor("Use Particle Vertex Color", Float) = 0
```

- ShaderLab `Properties` 让参数被 Material 序列化并显示在 Inspector；
- `Range` 是 Inspector Slider 限制，不会自动改变 GPU 数学；
- `[HDR]` 允许编辑超过 1 的颜色；
- `_UseVertexColor` 当前在 HLSL 中作为 Float 参与 `lerp`，不是依赖 `#pragma shader_feature` 的编译 Variant。

当前做法避免了 Vertex Color 开/关产生两套 Shader Variant，但 Fragment 始终会执行一次 `lerp`。普通实验 Quad 使用 0，Particle Material 使用 1。

### 6.3 `CBUFFER_START(UnityPerMaterial)` 与 SRP Batcher

Material 参数放在：

```hlsl
CBUFFER_START(UnityPerMaterial)
    half4 _BottomColor;
    ...
CBUFFER_END
```

这是 URP/SRP Batcher 期望的常量缓冲布局。Material 参数在一次 Draw Call 中作为共享常量读取，而不是每个 Fragment 从 CPU 重新发送。写进正确 CBUFFER 是“具备 SRP Batcher 兼容布局”的必要条件，但不等于所有 Particle Draw Call 一定被合批；实际 Batching、Instancing 与 SetPass 仍要用 Frame Debugger/Profiler 验证。

### 6.4 `Attributes`：GPU 从 Mesh/Particle Vertex Buffer 读取什么

```hlsl
struct Attributes
{
    float4 positionOS : POSITION;
    float2 uv         : TEXCOORD0;
    half4 color       : COLOR;
};
```

- `POSITION`：Object Space Vertex Position；
- `TEXCOORD0`：Quad UV；
- `COLOR`：Particle System 为每个 Particle 生成并随顶点传入的 Color/Alpha。

一张 Billboard Quad 的四个顶点共享同一粒子 Color，但拥有不同 UV。Rasterization 会在三角形内部插值 UV，因此 Fragment Shader 才能在一张 Quad 上画出连续轮廓。

### 6.5 `Varyings`：Vertex Stage 传给 Fragment Stage 什么

```hlsl
struct Varyings
{
    float2 uv          : TEXCOORD0;
    half fogFactor     : TEXCOORD1;
    half4 color        : COLOR;
    float4 positionCS  : SV_POSITION;
};
```

`positionCS` 决定三角形覆盖屏幕的区域；`uv`、`color`、`fogFactor` 会被 Rasterizer 插值后交给每个 Fragment。颜色对同一粒子的四个顶点通常相同，所以插值后仍相同；UV 则从四角连续变化。

### 6.6 Vertex Shader 做了什么，又故意没做什么

```hlsl
output.positionCS = TransformObjectToHClip(input.positionOS.xyz);
output.uv = input.uv;
output.color = input.color;
output.fogFactor = ComputeFogFactor(output.positionCS.z);
```

它完成坐标变换与数据转发，没有做 Vertex Displacement。火焰的摆动只发生在 Fragment Mask 中，所以真实 Quad 边界没有改变。优点是只需四个顶点，成本与实现简单；缺点是火焰侧面轮廓仍受 Billboard Quad 限制，近距离观察会暴露二维感。

### 6.7 Body Fragment Shader 的完整执行顺序

```text
1. input.uv + _Time.y
2. ElementFireAnimatedShape
   ├── noiseA/noiseB
   ├── centerOffset/widthOffset
   ├── shapeMask
   └── combinedNoise
3. ElementFireTemperatureMask
4. HeightColor（底色→顶色）
5. TemperatureColor（HeightColor→HotColor）
6. 乘 VertexTint.rgb 与 ColorIntensity
7. MixFog
8. ShapeMask × GlobalAlpha × AlphaVariation × VertexTint.a
9. 输出 half4(RGB, Alpha)
10. 固定管线执行 Alpha Blend
```

这说明 Shader 的颜色和透明度不是一条链：`shapeMask` 主要决定哪里可见，`temperatureMask` 主要决定哪里更热，`vertexTint.a` 负责每个 Particle 的生命周期淡入淡出。不同 Mask 各有职责，才能独立调试。

### 6.8 Additive Fragment Shader 的不同点

Additive 不需要 `_HotColor` 再次混色，而是让 Temperature Mask 直接控制亮度和 Alpha 权重；最后 Fog 向黑色衰减，再交给 `Blend SrcAlpha One`。相同轮廓数学产生视觉一致的 Body/Core，但更窄的 Material 参数与不同 Blend 让 Core 只出现在主体内部。

### 6.9 URP 与 HLSL 内置 API

| API/宏 | 作用 |
|---|---|
| `TransformObjectToHClip` | Object Space Position 变换为 Clip Space |
| `_Time.y` | Unity 提供的连续时间，驱动 Moving UV |
| `ComputeFogFactor` | 根据 Clip Depth 计算 URP Fog 因子 |
| `MixFog` | 普通颜色向场景 Fog Color 混合 |
| `MixFogColor` | 指定目标颜色；Additive 用黑色作为中性目标 |
| `UNITY_SETUP_INSTANCE_ID` 等 | 支持 Unity Instancing 数据路径与 Stereo 宏布局 |
| `#pragma multi_compile_fog` | 为 Fog 开关生成所需 Variant |
| `#pragma multi_compile_instancing` | 编译 Instancing 支持路径 |
| `#pragma target 3.5` | 指定最低 Shader Model 能力目标 |

当前 Shader 没有调用 `UniversalFragmentPBR`，也没有采样主光、阴影或 GI。它本质上是自定义的透明 Unlit/Emissive 风格 Pass，只接入了 URP 的坐标、Fog、Pipeline Tag 与基础宏。这适合火焰，因为火通常被视为自发光视觉；但它目前也不会真实照亮周围物体。

### 6.10 为什么有时使用 `float`，有时使用 `half`

- Noise 坐标、`pow`、轮廓距离和 Mask 中间量使用 `float`，降低累计精度误差和移动抖动风险；
- 最终颜色、Fog 与部分权重使用 `half`，在支持原生 FP16 的 GPU 上可能降低寄存器/算术成本。

这不是“所有颜色都必须 half、所有数学都必须 float”的绝对规则。移动端是否受益、是否出现 Banding，需要在目标设备验证；PC 上编译器也可能把二者映射到相同硬件精度。

### 6.11 源码里的 `max`、`min` 与 `saturate` 为什么不是多余防御

公共函数中多次出现：

```hlsl
max(shapePower, 0.0001)
max(edgeSoftness, 0.0001)
max(baseFade, 0.0001)
min(saturate(tipFadeStart), 0.9999)
```

这些保护的是公式定义域与数值稳定性：

- `pow(0,0)` 在不同实现中可能产生未定义或不希望的结果，所以指数保留极小正数；
- `smoothstep(edge0,edge1,x)` 需要两个边界形成有效区间，Softness/Fade 为 0 会让上下界重合；
- `tipFadeStart=1` 会让顶部 Smoothstep 的两个边界都等于 1，因此限制到 `0.9999`；
- `saturate(halfWidth)` 防止 Noise Width Offset 把宽度推到负数或超出整个 Quad；
- `saturate` 还保证 Mask、混合权重和 Alpha 留在 `[0,1]`，避免负透明度或过量 Lerp 外插。

Material Inspector 的 `Range` 能限制正常手动输入，但运行时代码、Animation、MaterialPropertyBlock 或旧序列化数据仍可能写入边界外数值。因此 GPU 侧保护仍有意义。它们不是为了掩盖错误，而是让公共数学面对极端输入时保持可预测。

## 7. Step 5D：为什么 Shader 做完后还需要三层 Particle System

水面可以由一张连续 Plane 表示，水 Shader 只需改变这个固定表面的每个 Fragment。火焰不同：它没有稳定表面，轮廓不断出生、上升、缩小和消失，多个火舌之间还需要空间随机性。单张 Quad Shader 只能让一张矩形内部的图案移动，不能自动产生“很多独立火舌的生命周期”。所以火焰需要 Shader 与 Particle System 配合。

### 7.1 当前实验层级

```text
FireParticleLab
├── PS_FireBody
│   └── PS_FireCore
└── PS_FireSparks
```

`PS_FireCore` 是 `PS_FireBody` 的子物体，并被 Body 的 `Sub Emitters` 模块以 `Birth` 类型引用。Sparks 是独立系统，因为火星只需要在整个火区中稀疏出现，不需要与某个 Body 粒子一一绑定。

### 7.2 粒子数量不是只看 Max Particles

稳定连续发射时，平均可见粒子数可以粗略估算为：

```text
Nvisible ≈ EmissionRate × AverageLifetime
```

例如 Body Rate 约为 12/s，Lifetime 约 0.75～1.15s，平均 Lifetime 约 0.95s：

```text
Nvisible ≈ 12 × 0.95 ≈ 11.4
```

`Max Particles=24` 是容量上限，不代表屏幕上始终有 24 个。这个估算能帮助我们在改 Lifetime 或 Rate 时预判密度，而不是只靠肉眼反复试。

### 7.3 `PS_FireBody`：负责主体密度和生命周期

当前核心思路：

- `Shape = Box`：在一条扁平火区范围内随机产生出生位置；
- `Emission Rate ≈ 12/s`：维持约十余片外焰；
- `Lifetime ≈ 0.75～1.15s`：每片火焰停留时间有随机差异；
- `Start Size ≈ 0.65～0.95`：避免所有火舌完全同尺寸；
- `Velocity over Lifetime`：主要沿 Local Y 上升，X 只有轻微随机漂移；
- `Color over Lifetime`：出生快速淡入，存活中段可见，死亡前淡出；
- `Size over Lifetime`：先增长到峰值，再逐渐缩小；
- `Vertical Billboard`：面向 Camera，同时保持世界竖直方向，避免普通 Billboard 随 Camera Roll/俯仰呈现不自然倒伏；
- Renderer 使用 `M_ElementFireBody_Particle`，Shader 开启 Particle Vertex Color。

若归一化年龄为 `τ`，Body 的尺寸可以概念化为分段曲线：

```text
τ≈0      ：约 0.65，避免零尺寸突然跳出
τ≈0.15   ：增长到约 1.0
τ≈0.6    ：逐渐降到约 0.7～0.8
τ=1      ：降到约 0.2，同时 Alpha 已接近 0
```

Size Curve 与 Alpha Curve 联合很重要：尺寸仍较大但 Alpha 已归零时，粒子能平滑消失；若 Alpha 保持 1 到最后一帧，即使 Size 变小也会产生“啪”地消失。

### 7.4 Particle Vertex Color 怎样进入 Shader

数据链为：

```text
Start Color
  × Color over Lifetime
  × 其他 Particle Color 模块
  ↓ ParticleSystemRenderer Vertex Stream COLOR
Attributes.color : COLOR
  ↓ Vertex Shader 转发
Varyings.color : COLOR
  ↓ Fragment Shader
vertexTint.rgb / vertexTint.a
```

Material Color 是整批粒子共享的；Particle Vertex Color 是每个粒子独立的数据。Shader 中：

```hlsl
half4 vertexTint = lerp(half4(1,1,1,1), input.color, _UseVertexColor);
```

实验 Quad 把开关设为 0，避免没有正确 Color Stream 时影响结果；Particle Material 设为 1，使生命周期 Alpha 真正控制 Fragment Alpha。如果 Particle 曲线已经设置但火焰不淡出，第一检查项就是 Material 是否启用了 `_UseVertexColor`、Renderer 是否提供 Color Stream。

### 7.5 `PS_FireCore`：为什么最初会与 Body 分离

最初 Body 与 Core 是两个独立的 sibling Particle System。即使它们使用相同 Box Shape，也会分别执行随机采样：

```text
Body 出生位置 = RandomBody(Box, time, seedA)
Core 出生位置 = RandomCore(Box, time, seedB)
```

两套 Random Seed、Emission Time 和 Lifetime 彼此独立，所以“统计分布相似”不等于“一一重合”。画面中就会出现 Core 在一处、Body 在另一处。这不是 Shader 错误，而是粒子关系建模错误。

### 7.6 Birth Sub Emitter 怎样解决一一配对

修正后的关系：

```text
Body Particle Birth
    ↓ 触发 Sub Emitter
Core 在 Parent Particle 的出生位置发射一次
    ↓ 继承 Size + Rotation
Core Lifetime 更短、Size 系数更小、Shape/独立 Velocity 关闭
```

Body `Sub Emitters` 中配置：

```text
Type = Birth
Emitter = PS_FireCore
Emit Probability = 1
Inheritance = Size + Rotation
```

Core 自身：

- `Looping = Off`、`Play On Awake = Off`；
- `Rate over Time = 0`；
- Burst 在 `t=0` 产生 1 个；
- Shape 关闭，防止再次随机偏移出生位置；
- 独立 Velocity over Lifetime 关闭；
- Inherit Velocity 使用 Initial，继承 Parent 出生时运动趋势；
- Lifetime 约 0.45～0.75s，比 Body 更短；
- Start Size 约 0.55～0.70，作为相对 Parent Size 的较小核心；
- Renderer 使用更窄的 Additive Material。

这里没有继承 Parent Color，是一个很重要的细节：Body 的 Color over Lifetime 在出生点 Alpha 约为 0。如果 Core 继承 Color，它出生时可能把 Alpha 0 一并继承，导致 Additive Core 不可见或亮度异常。我们只继承空间/几何相关的 Size 与 Rotation，让 Core 使用自己的生命周期颜色。

Sub Emitter 的价值不是“让 Core 成为子物体”这么简单。Hierarchy 只表达 Transform 父子关系；真正保证每次 Body Birth 都触发 Core 的，是 Body Particle System 的 `Sub Emitters` 模块。

### 7.7 `PS_FireSparks`：为什么保持独立

火星不是每片火舌都必须拥有的内部结构，而是整个火区偶尔释放的高能亮点。因此它使用独立 Box Shape 与 Emission：

- Rate 约 6/s、Lifetime 约 0.25～0.5s；
- Start Size 约 0.035～0.075，远小于 Body；
- Velocity 主要向上，Y 约 1.4～2.6，X/Z 只有随机扰动；
- Color over Lifetime 快速淡入后淡出；
- Size over Lifetime 单调缩小；
- Additive Material 提供高亮；
- `Stretched Billboard` 沿速度方向拉长，`Speed Scale≈0.08`、`Length Scale≈1.5`；
- Noise Strength 约 0.15、Frequency 约 0.7、Scroll Speed 约 0.35，Damping 开启。

基础运动近似为：

```text
P(t) = P0 + Vt
```

加入 Particle Noise 后可概念化为：

```text
P(t) = P0 + Vt + N(P,t) × S
```

`V.y` 保持主要上升方向，Noise 只破坏机械直线感。Strength 过大或 Frequency 过高会让火星高频抖动、横向乱飞，失去热气流方向。

### 7.8 Vertical Billboard 与 Stretched Billboard 的区别

- **Vertical Billboard**：Quad 面向 Camera，但保持竖直轴，适合主体火舌。Shader 的 UV.y 始终可以稳定解释为“从火焰底部到顶部”。
- **Stretched Billboard**：Quad 会沿 Particle Velocity 拉伸，适合火星、雨滴、速度线。速度越大，轨迹越长。

如果 Body 使用 Stretched Billboard，粒子速度会改变整片火焰的长宽比，Shader 内部精心设计的轮廓容易被拉成光条；如果 Sparks 使用普通 Vertical Billboard，又会更像小火苗而不是高速亮点。Renderer Mode 是视觉职责的一部分，不只是显示选项。

## 8. 变量词典：每个参数改变最终画面的哪一部分

### 8.1 轮廓与流动参数

| 参数 | 数学含义 | 增大后的视觉结果 | 常见风险 |
|---|---|---|---|
| `_BaseWidth` | `y=0` 附近的归一化半宽 | 根部更宽 | 接近 1 时顶满 Quad 边界 |
| `_TipWidth` | `y=1` 附近半宽 | 尖端更粗 | 失去尖锐感 |
| `_ShapePower` | `pow(y,p)` 的指数 | `p>1` 时更晚收窄 | 过大形成突然尖缩 |
| `_EdgeSoftness` | 横向 Mask 柔边宽度 | 边缘更柔 | 轮廓发虚、Overdraw 区域扩大 |
| `_BaseFade` | 底部淡入高度 | 消除底边硬线 | 太大导致根部悬浮 |
| `_TipFadeStart` | 顶部开始淡出的高度 | 越大越晚消失 | 太大可能被 Quad 顶边截断 |
| `_NoiseScaleA` | 低频采样频率 | 单片内出现更多大尺度变化 | 过高失去“大尺度”职责 |
| `_NoiseScaleB` | 高频采样频率 | 边缘细节更碎 | 高频闪动、Fragment ALU 不变但画面更乱 |
| `_UpwardSpeedA/B` | UV/秒的采样速度 | 内部特征更快上升 | 太快像电视噪点 |
| `_DistortionStrength` | 中线横向位移振幅 | 顶部摆动更强 | 整片像蛇形或断裂 |
| `_DetailStrength` | 局部半宽变化振幅 | 边缘更破碎 | 可能产生过窄、翻转或闪烁轮廓 |

### 8.2 温度、颜色与透明参数

| 参数 | 作用 | 关键理解 |
|---|---|---|
| `_BottomColor` | UV 底部基色 | Body 与 Additive Material 含义不同 |
| `_TopColor` | UV 顶部基色 | 与 Bottom 做 Height Lerp |
| `_HotColor` | Body 的局部高温颜色 | 只有 Body Shader 使用 |
| `_ColorIntensity` | 最终 RGB 乘数 | HDR 下可超过 1；Additive 过高易过曝 |
| `_GlobalAlpha` | 整个 Material 的透明权重 | 还会乘 Shape/Noise/Particle Alpha |
| `_UseVertexColor` | 是否消费 Particle COLOR Stream | 实验 Quad=0，Particle Material=1 |
| `_HeatNoiseWeight` | 高度热度与动态 Noise 的混合权重 | 0 只按高度，1 只按 Noise |
| `_HeatContrast` | Temperature Mask 的 `pow` 指数 | 大于 1 让热区更集中 |
| `_HotColorStrength` | Body 向 HotColor 混合的强度 | 不改变轮廓，只改变颜色分区 |
| `_AlphaNoiseStrength` | Noise 对 Alpha 的调制幅度 | Body 应克制，Core 可更明显 |

### 8.3 Particle 参数

| 参数/模块 | 解决的问题 | 调整时先观察什么 |
|---|---|---|
| Emission Rate | 单位时间出生多少粒子 | 与 Lifetime 一起决定平均密度 |
| Start Lifetime | 每个粒子存活多久 | 密度、上升距离、动画节奏同时变化 |
| Start Size | 初始 Billboard 尺寸 | 屏幕覆盖与 Overdraw |
| Shape Box | 出生位置空间分布 | 是否与预期火区范围一致 |
| Velocity over Lifetime | 上升与横摆趋势 | Local/World Space 是否正确 |
| Color over Lifetime | 淡入、稳定、淡出 | Vertex Color 是否真正进入 Shader |
| Size over Lifetime | 生长与消亡形态 | Curve 横轴是 Normalized Age |
| Sub Emitters | Parent/Child 粒子事件关系 | Hierarchy 子物体本身不等于 Sub Emitter |
| Noise | 连续随机轨迹扰动 | Strength/Frequency 是否破坏主方向 |
| Renderer Mode | Quad 如何朝向或拉伸 | Body 与 Sparks 职责不同 |

## 10. 本次实现中出现的真实问题与 Debug

### 10.1 `Size over Lifetime` 看起来无法编辑

Unity 6.3 中，模块里的长条曲线预览本身就是 `Size` 字段；选中后详细曲线编辑器出现在 Inspector 底部的 `Particle System Curves` 区域。如果底部区域折叠或 Inspector 高度不足，就会误以为没有曲线编辑入口。

解决步骤不是改代码，而是：

1. 勾选 `Size over Lifetime`；
2. 点击模块中的曲线预览条；
3. 展开 Inspector 底部 `Particle System Curves`；
4. 在曲线上增加/拖动 Key；
5. 观察横轴 0～1 的 Normalized Age，而不是世界秒数。

这个问题提醒我们：Unity Editor 的“数据不存在”和“数据编辑器被折叠”是两种不同故障，应先确认序列化字段是否存在，再查 UI 展示。

### 10.2 焰芯和外焰分开不是正常最终效果

当 Body/Core 是独立 Particle System 时，它们的 Box Shape 和随机出生各自运行。即使数值相同，随机序列也不同，所以焰芯不会自动落在外焰内部。

错误诊断链：

```text
Shader 轮廓是否错误？
  └── 单独 Quad 正常，所以不是 Shader

Material Queue 是否错误？
  └── Core 能显示，只是位置不同，所以不是 Blend/Queue

Particle 出生位置是否共享？
  └── 两套独立 Shape/Emission，没有共享 Parent Birth
      → 根因
```

修复为 Birth Sub Emitter 后，位置数据链由“两个独立随机采样”变成“Core 响应 Body Birth”，问题才从架构上消失。只把两个 GameObject 设为父子但不配置 Sub Emitters，不会解决问题。

### 10.3 Core 继承 Color 可能出生即透明

Body 为了平滑淡入，在 Normalized Age=0 时 Alpha 接近 0。如果 Birth Core 继承 Parent Color，它可能继承这个低 Alpha。最终我们只继承 Size 与 Rotation，让 Core 使用自己的 Color over Lifetime。Debug Sub Emitter 时应逐项检查继承字段，而不是一键全选。

### 10.4 Additive 过曝不能只靠降低一种颜色解决

Additive 最终贡献由多个因子共同决定：

```text
Contribution
≈ RGB × ColorIntensity × GlobalAlpha
  × ParticleAlpha × TemperatureWeight × OverlapCount
```

所以过曝可能来自：Material HDR Color、Intensity、Alpha、粒子数量、尺寸、Core/Body 重叠数量或 Bloom。正确 Debug 是逐项隔离，而不是只把颜色从白改成橙。

### 10.5 Particle 曲线有效但 Shader 不响应

若 Color over Lifetime 的 Alpha 已变化，但画面仍保持不透明，应检查：

```text
ParticleSystem Color Curve
  ↓ Renderer Vertex Stream 是否包含 COLOR
Attributes.color 是否声明 COLOR Semantic
  ↓ Vertex 是否转发
Fragment 是否乘 input.color.a
  ↓ Material _UseVertexColor 是否为 1
```

这是一条跨 CPU Particle Data、Vertex Buffer、Vertex Shader 与 Fragment Shader 的完整数据链，任何一处断开都会让 Editor 曲线“看起来设置了但没有效果”。

### 10.6 透明粒子排序与 Overdraw

`ZWrite Off` 解决了透明片互相深度遮挡的一类问题，但没有让透明排序变得完美。多个 Billboard 交叉、Camera 进入火区或粒子尺寸过大时，仍可能出现排序跳变。Additive 对排序通常不如 Alpha 敏感，因为加法近似可交换；Body Alpha Blend 的前后顺序会影响结果。

Debug 应观察：Material Queue、ParticleSystemRenderer Sorting Fudge/Order、Camera Distance、粒子 Bounds 与 Screen Overdraw。不能简单把所有粒子 Queue 拉开很多值，因为那会破坏它们与其他透明物体的全局关系。

## 11. 一套可重复的 Fire Debug 顺序

```text
1. Console：Shader 是否编译；粉色通常先查 Include/Pass/Pipeline Tag
2. 单 Quad + 静态 Shape：临时关闭动画，确认 UV 与 Mask
3. 输出 shapeMask.xxx：确认轮廓、柔边、底/顶 Fade
4. 输出 noiseA/noiseB/combinedNoise 灰度：确认连续、向上、无闪烁
5. Distortion=0、Detail=0，再逐个恢复：区分中线与宽度扰动
6. 输出 temperatureMask.xxx：确认高度与动态热区
7. Body 单独播放：检查 Alpha Blend、Color/Size over Lifetime
8. Core 单独播放：检查 Additive 强度和窄轮廓
9. Body+Core：检查 Birth Sub Emitter 位置、Size、Rotation、Color 继承
10. Sparks 单独播放：检查 Velocity、Stretched Billboard 与 Noise
11. 三层组合：检查职责、过曝、密度、透明排序
12. Frame Debugger：确认 Body Pass 与 Additive Pass、Queue/Draw 顺序
13. Overdraw/GPU Profiler：固定 Camera，比对 1/4/8 个火区成本
```

临时输出 Mask 时可以直接：

```hlsl
return half4(shapeMask.xxx, 1.0h);
```

Alpha 固定为 1 是为了避免灰度 Mask 又被背景 Alpha Blend 稀释。一次只输出一个中间量，验证后恢复正式代码。

## 12. 性能、替代方案与设计取舍

### 12.1 当前 GPU 成本主要来自哪里

- 每个火焰 Fragment 计算两层 Value Noise；每层包含四次 Hash、`floor/frac/dot/lerp` 等 ALU；
- `pow` 用于 Shape Curve 与 Temperature Contrast；
- Body + Core 至少产生两层透明覆盖，Sparks 再增加小面积覆盖；
- `Cull Off` 允许正反面，某些视角可能增加 Fragment；
- HDR Additive 与 Bloom 会增加后处理可见成本；
- 粒子尺寸越大、越靠近 Camera，Screen Space Overdraw 越严重。

Particle System 的 C# Managed `GC Alloc` 不是本效果的主要成本来源，但 CPU 仍需要模拟粒子、更新 Bounds、构建/提交 Renderer 数据。Shader 没有在 Managed Heap 分配内存，不代表整套 VFX 没有 CPU/GPU 成本。

### 12.2 为什么当前不使用商城 Fire Prefab

本阶段目标不只是“尽快有一团火”，还要学习 Mask、Noise、Blend、Coordinate Space、Particle Lifetime 和 Debug 数据链。第三方 Prefab 可以用于生产对比或参考，但会隐藏关键数学与参数关系，也不一定匹配项目元素反应架构。自研方案让视觉资产能够按 Wet/Fire 反应强度进一步参数化。

### 12.3 为什么不一开始就做 Flipbook

Flipbook 是业界常见方案：离线模拟/绘制多帧火焰，运行时只做 Texture Sample 与帧动画。它通常比每 Fragment 手写多层 Noise 更可预测，也容易获得复杂细节；代价是需要纹理资源、显存、压缩与固定动画内容，近距离重复会暴露相同帧序列。

当前先保留程序化版本，因为它适合学习、可调且无外部贴图。如果 5F 证明多火区 Fragment ALU 或 Overdraw 超出预算，可以把**自研结果**烘焙为 `512×512 RGBA Flipbook`，而不是换成商城黑盒。那是基于 Profiler 证据的优化，不是对当前方案的否定。

### 12.4 为什么不用 VFX Graph

VFX Graph 适合大量 GPU Particle、复杂 Spawn/Update Context 和高数量特效；当前 Body/Core/Sparks 只有几十个 CPU Particle，Particle System 更容易逐模块学习、调试和与 Sub Emitter 配对。未来大规模火海可能适合 VFX Graph，但不能武断地说 GPU 方案一定更快；数量、Screen Overdraw、Shader 成本和平台都要测量。

### 12.5 为什么不做真实体积火或流体模拟

体积火可能使用 3D Texture、Ray Marching、Sparse Volume、Fluid Grid 或预烘焙 Simulation，能提供更真实的内部密度与视差，但计算、资源与工程复杂度远超 P2 局部元素区需求。当前目标是风格化、可控、可复用的 RPG 元素反馈，不是工业燃烧模拟。

### 12.6 当前尚未通过的性能结论

5A～5D 的视觉 Gate 已由开发者验证，但不能据此宣称性能合格。仍需在 5F：

- 用 Frame Debugger 确认 Body 为 Alpha Pass、Core/Sparks 为 Additive Pass；
- 用 Overdraw 观察三层透明覆盖；
- 用 CPU/GPU Profiler 对比 1/4/8 个火区；
- 检查 Particle Bounds 与 Camera Culling；
- 记录目标分辨率、Camera 位置、灯光/Post Processing 条件；
- 再决定保留程序化 Noise 还是烘焙 Flipbook。

## 13. 模拟面试者：向大厂客户端/图形面试官完整讲解开发过程

我在项目 P2 中需要实现一套自研元素视觉，其中 Fire 的目标不是购买一套现成火焰 Prefab，而是做一个能被环境火区、角色 OnFire 和后续 Wet Extinguish 复用的视觉基础。首先我明确了边界：当前不是物理燃烧或体积流体模拟，而是基于程序化 Fragment Mask、透明混合和 Particle System 的风格化火焰。Gameplay 的 Burning、DoT 和元素反应由 `Game.Combat` 负责；Shader 和 Particle System 只负责 Rendering，后续通过 Prefab/Rendering Bridge 组合，避免视觉层拥有状态规则。

我没有直接把所有效果堆在一起，而是从玩家最终看到的结果反向拆解。要像火，至少需要下宽上窄的柔和轮廓、向上流动、根部稳定顶部活跃、橙红外焰、黄白高温核心以及少量快速上升的火星。然后我把实现分为四个 Gate：5A 只画静态轮廓；5B 加程序化 Noise 和流动；5C 拆分 Alpha Body 与 Additive Core；5D 再用 Particle System 管理多片火焰的出生、运动、配对和死亡。这样每个阶段只有一类变量，发生错误时可以定位到 Shape、Noise、Blend 或 Particle Lifecycle，而不是同时猜所有参数。

在 5A 中，我使用 Quad 的 `[0,1]` UV。先把 `uv.x` 映射到 `[-1,1]` 并取到中线的绝对距离，再用 `pow(uv.y, ShapePower)` 重新分布高度，根据 `lerp(BaseWidth, TipWidth, shapedHeight)` 得到每个高度的半宽。`ShapePower>1` 时中下部保持宽度更久、顶部再快速收窄。横向边缘不用二值 Step，而用 `1-smoothstep(width-softness,width,distance)` 生成柔边；底部和顶部再分别用 Smoothstep 淡入淡出，最终三个 Mask 相乘。这一步只输出静态、左右对称的火焰轮廓，先证明 UV 和 Mask 数学正确。

在 5B 中，我没有导入 Noise Texture，而是手写二维 Value Noise。Hash 将二维整数格点稳定映射到 `[0,1)`；对采样点取 `floor` 和 `frac`，获得格子与局部坐标；局部坐标用 `f²(3-2f)` 做 Hermite 平滑；四个角点 Hash 通过两次 X Lerp 和一次 Y Lerp 得到连续标量场。动画使用 `Noise((UV-speed×time)×scale)`，采样坐标向下移动时，屏幕上同一特征满足 `y=y0+speed×time`，所以视觉向上。我使用两层不同 Scale、Speed、镜像和 Seed 的 Noise：低频层主要移动中线，高频层主要改变局部半宽。

为了让根部附着、顶部活跃，我把中心化 Noise 乘以 `y²`。在底部影响为 0，中部 `y=0.5` 时只有 0.25，顶部才获得完整扰动。中线偏移公式是 `(2NoiseA-1)×DistortionStrength×y²`，宽度偏移是 `(2NoiseB-1)×DetailStrength×y²`。这不是 Navier–Stokes，而是把观察到的火焰特征编码成风格化约束。我还用 `BaseHeat=1-y` 与 Combined Noise 做 Lerp，再通过 `pow` 调整对比度，得到 Temperature Mask；它表达颜色权重，不代表真实温度或黑体辐射。

在 5C 中，我把公共 Hash、Value Noise、Shape 和 Temperature 函数放入 `ElementFireCore.hlsl`，Body 与 Core 两个 Shader Include 同一文件，避免数学复制后漂移。Body 使用 `Blend SrcAlpha OneMinusSrcAlpha`，屏幕公式是 `Csrc×α+Cdst×(1-α)`，它负责在亮暗背景上保留橙红主体；Core 使用 `Blend SrcAlpha One`，公式是 `Csrc×α+Cdst`，负责增加黄白高温亮度。两个 Shader 不能靠 Fragment 分支切换 Blend，因为 Blend 是 Draw/Pass 级固定 Render State，所以必须拆为两个 Pass/Material。Core 使用更窄的 Base/Tip Width、更早的 Tip Fade 和更克制的粒子数量。

两个 Shader 都使用 Transparent Queue、`ZWrite Off`、`ZTest LEqual` 和 `Cull Off`。ZWrite Off 避免较早绘制的透明火焰片写深度后挡住后续透明片，但会带来排序和 Overdraw；ZTest 仍让墙体深度遮挡火焰；Cull Off 兼容双面 Quad，但可能增加 Fragment。Core Queue 设置为 `Transparent+10`，让其在 Body 后绘制。普通 Fog 可以向 Fog Color 混合；Additive 的中性元素是黑色，所以我使用 `MixFogColor(...,black,...)` 让远处 Additive 贡献归零，避免把雾色额外加到背景。

Shader 的 Vertex Stage 只用 `TransformObjectToHClip` 把 Object Space Position 变换到 Clip Space，并转发 UV、Particle Color 和 Fog Factor，没有做 Vertex Displacement。Rasterizer 插值 UV 后，Fragment Stage 计算 Noise、Shape Mask、Temperature Mask、RGB 与 Alpha。Body Alpha 是 `Shape×GlobalAlpha×AlphaVariation×ParticleAlpha`；Particle Alpha 来自 ParticleSystemRenderer 的 COLOR Vertex Stream。实验 Quad 把 `_UseVertexColor` 设为 0，Particle Material 设为 1。Material 参数放在 `UnityPerMaterial CBUFFER` 以符合 URP/SRP Batcher 布局，但是否实际合批仍需要 Frame Debugger 验证。

在 5D 中，Particle System 负责 Shader 无法解决的多实例生命周期。`PS_FireBody` 用扁平 Box Shape 产生火舌，Rate 与 Lifetime 的乘积近似平均可见数量；Velocity 主要向上；Color/Size over Lifetime 让粒子淡入、成长、缩小并淡出；Vertical Billboard 保持 UV.y 对应世界竖直方向。`PS_FireCore` 最初作为独立 sibling 发射器时，虽然 Shape 参数相似，但两套随机出生位置和时间互不相关，导致焰芯与外焰分开。我没有继续靠调 Box 大小碰运气，而是改成 Body 的 Birth Sub Emitter：每个 Body Birth 触发一个 Core，继承 Size 与 Rotation，关闭 Core Shape 和独立 Velocity，并让 Core 更小、寿命更短。

Sub Emitter 中我没有继承 Color，因为 Body 的生命周期在出生时 Alpha 接近 0，继承后可能让 Core 出生即透明。这次问题让我认识到 Hierarchy 父子关系只影响 Transform；Particle 的事件配对必须通过 Sub Emitters 模块明确建立。Sparks 则保持独立，因为它们是整个火区的稀疏能量逸散，不要求每片 Body 都有一个。Sparks 使用较短 Lifetime、更高 Y Velocity、Additive Material、Stretched Billboard 和轻微 Particle Noise；Stretched Billboard 按速度方向拉长，提供明确上升轨迹。

性能上，我不会因为“没有外部贴图”就宣称更快。当前每个 Fragment 有两层 Value Noise，每层需要四个 Hash 和多次 ALU；Body/Core 透明重叠带来 Overdraw，Additive 与 Bloom 也有成本。程序化方案的优点是可学习、无贴图依赖、参数连续可调，缺点是 Fragment ALU 与重复图案仍需评估。后续我会在固定 Camera、分辨率和 Post Processing 条件下，用 Frame Debugger 确认 Pass/Queue，用 Overdraw 查看透明覆盖，用 CPU/GPU Profiler 对比 1、4、8 个火区。如果程序化版本超出预算，我会把自研结果烘焙成 RGBA Flipbook，以 Texture Bandwidth 和显存换取更低、更稳定的 ALU，而不是直接替换成第三方成品。

这项实现让我完整走通了从视觉目标、问题拆解、UV Mask、Smoothstep、Hash、Value Noise、Moving UV、Height Weight、Temperature Mask、Alpha/Additive Blend、ShaderLab Render State、URP Fog、Particle Vertex Stream、Normalized Lifetime Curve、Billboard、Sub Emitter，到最终组合验证的开发过程。我也能明确说明当前没有真实体积、流体、热折射、动态照明、Steam 和正式性能结论。对我来说，重点不仅是“做出一团火”，而是能解释每个视觉线索由哪条数据链产生、为什么选择这种实现、错误发生时怎样逐层定位，以及在性能数据出现后怎样决定保留程序化版本还是转为自制 Flipbook。
