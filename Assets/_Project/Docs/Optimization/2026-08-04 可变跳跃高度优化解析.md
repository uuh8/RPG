# 2026-08-04 可变跳跃高度优化解析

> 状态：代码实现与 C# 编译验证已完成；Variable Jump Height 的既有 EditMode 测试已通过。Task 2 新增测试仍需在 Unity Test Runner 中点跑，实际动画观感与 Profiler 数据仍需 Play Mode 验收。

## Task 1：Variable Jump Height（可变跳跃高度）

本次优化让同一个 Jump 输入同时支持短跳和完整跳：玩家持续按住 Jump 时，角色沿用原来的 `_jumpForce` 与上升重力，达到原有最大高度；玩家在上升阶段提前松开 Jump 时，系统立即将当前垂直速度乘以 `_jumpCutVelocityMultiplier`，默认保留 `50%`，因此角色更快到达跳跃顶点。该设计不是持续给角色施加额外向上的力，而是在松键瞬间执行一次 `Jump Cut`，所以操作反馈干脆，也不会改变既有的下降重力、水平空中控制、`Jump Buffer`、`Coyote Time`、二段跳预算或 `Animator` 结构。普通跳、`Coyote Jump` 与二段跳共用完全相同的截断语义。

### 1. 玩家看到的结果与基础原理

当前角色不使用 `Rigidbody` 完成移动，而是由 `CharacterController.Move()` 消费代码维护的 `VerticalVelocity`。起跳时会执行：

```text
VerticalVelocity = JumpForce
```

空中每帧再用半隐式欧拉积分更新速度：

```text
v(next) = v(current) + Physics.gravity.y × gravityMultiplier × deltaTime
```

旧实现只根据 `VerticalVelocity` 的正负选择上升重力或下降重力，没有读取 Jump 是否仍被按住，因此短按和长按拥有相同的初速度与重力曲线，最高点自然完全一致。

本次加入的 `Jump Cut` 在松键且仍在上升时执行一次：

```text
VerticalVelocity = VerticalVelocity × JumpCutVelocityMultiplier
```

默认倍率是 `0.5`。例如松键前的上升速度为 `6 m/s`，截断后变为 `3 m/s`；重力会从更低的速度继续把它减到 `0`，所以角色更早到达顶点。倍率越小，短跳越低、手感越干脆；倍率为 `1` 时速度不变，相当于关闭 Variable Jump Height。

这里选择“削减现有速度”而不是“松键后持续增加重力”，是因为目标手感明确要求立即截断。增加重力会得到更平滑的曲线，但松键响应没有直接修改速度清晰，而且会与现有 `_gravityMultiplier` 的职责重叠。

### 2. Input System 到 FSM 的运行链路

```text
Player/Jump InputAction
├─ performed
│  └─ OnJumpPerformed() → 写入 JumpBufferCounter
└─ IsPressed()
   └─ PlayerControllerBase.Update() 每帧读取当前是否仍按住

普通跳 / Coyote Jump / 二段跳真正取得 JumpForce
└─ ArmJumpCut()
   └─ JumpCutRuntime.Arm()：本次跳跃允许截断一次

后续每帧 PlayerControllerBase.Update()
└─ JumpCutRuntime.Evaluate(VerticalVelocity, isJumpHeld)
   ├─ 未武装：不修改
   ├─ 仍按住且正在上升：保留完整速度
   ├─ 已松开且正在上升：乘倍率并解除武装
   └─ 已到顶点或下降：解除武装，不修改速度
```

这里没有订阅 `InputAction.canceled`，而是轮询 `InputAction.IsPressed()`。关键原因是 `Jump Buffer`：玩家可能在落地前按下并松开 Jump，真正起跳要等到之后落地。如果只在 `canceled` 回调当场修改速度，此时角色还没有获得新的 `JumpForce`，释放事件会被浪费；实际起跳后反而仍是完整高度。现在的实现只在“真正获得跳跃初速度”时调用 `ArmJumpCut()`，下一帧再读取按键当前状态，因此提前松开的缓冲跳会自然表现为短跳。

`JumpCutRuntime` 放在 `PlayerControllerBase` 的常驻 `Update()` 路径，而不是只放进 `PlayerAirborneState`。这样即使角色在上升中暂时切换到空中施法状态，或者 Air Dash 暂停了垂直位移，本次跳跃保存的正向 `VerticalVelocity` 仍能响应松键。它是 `Awake()` 时创建并持续复用的普通 C# 对象；每帧只进行布尔判断和浮点运算，不创建数组、闭包或临时对象。

### 4. 测试、调参与 Debug

自动化测试重点保护以下边界：

- 武装后在上升阶段松键，`6` 以默认倍率截断为 `3`，第二帧仍保持 `3`，证明不会连续乘法。
- 持续按住时保持完整速度，之后松键才截断。
- 到达顶点或开始下降后解除武装，未来其他来源产生的向上速度不会被旧跳跃误伤。
- 即使旧 Prefab 或代码传入小于 `0`、大于 `1` 的倍率，运行时也通过 `Mathf.Clamp01` 限制到安全范围。

Inspector 调参位置：Wizard 根对象上的 `WizardController` 组件 → `Jump` 分组 → `Jump Cut Velocity Multiplier`。

推荐从 `0.5` 开始：

- `0.3`：短跳很低，松键制动感强。
- `0.5`：短跳与完整跳区分明显，同时不至于生硬停顿。
- `0.7`：差异较温和，更偏自然动作游戏。
- `1.0`：关闭 Jump Cut，退回旧行为。

Play Mode 验证清单：

1. 用 Wizard 在同一平地分别轻点和持续按住 Jump，确认最高点明显不同。
2. 从平台边缘离开后在 `Coyote Time` 内起跳，分别验证短按和长按。
3. 空中触发二段跳，分别验证短按和长按；确认每次跳跃都独立武装。
4. 落地前提前轻点 Jump 并松开，确认 `Jump Buffer` 触发的是短跳。
5. 在上升中施法或 Air Dash 后松键，确认恢复垂直运动时没有异常高跳。
6. 在顶点或下降阶段才松键，确认下落曲线没有突然变化。
7. 打开 Unity Profiler，检查 `PlayerControllerBase.Update()` 的 `GC Alloc` 为 `0 B`，并观察 CPU 没有异常尖峰。

常见故障定位：如果短按与长按仍然一样高，先确认 Prefab 上的倍率不是 `1`，再确认场景中的角色确实使用包含新字段的 `PlayerControllerBase` 子类；如果短按像被瞬间吸向地面，倍率可能过低；如果只有普通跳生效而二段跳无效，应检查对应起跳路径是否调用了 `ArmJumpCut()`。

面试表达可以概括为：Variable Jump Height 的核心不是重新计算一条跳跃曲线，而是把 Jump Input 的持续状态引入垂直速度积分。起跳建立一次可消费的 Jump Cut 权限，松键时只在正向速度阶段削减一次，顶点后自动失效；这种 one-shot state 既避免每帧重复乘法，也兼容 `Jump Buffer` 与跨 FSM State 的空中行为。

## Task 2：二段跳 Trigger 滞留与短跳动画阶段同步

本次修复处理 Variable Jump Height 上线后暴露出的两类 Animator 时序问题。第一类是二段跳在 `JumpAir_MagicWand` 中设置了 `jump Trigger`，但旧 Animator 没有空中消费该 Trigger 的转移；Trigger 因此一直保留到落地，等角色回到 Idle/Run 后才被消费，表现为“角色已经落地，却突然补播一次起跳”。第二类是旧跳跃动画依赖固定 `Exit Time` 顺序播放：`JumpStart → JumpAir` 必须等待动画进度，`JumpEnd → Idle/Run` 也必须等待较长落地段。短跳的物理周期可能早于动画周期结束，于是 Gameplay 已经落地，Animator 仍在补播 JumpStart 或 JumpAir。

### 1. 根因：Trigger 与 Bool 参数的生命周期不同

`jump` 是 `Trigger`。它不是“只存在一帧”的普通布尔值，而是一次等待 Animator 转移消费的事件。如果当前状态没有以它为 Condition 的合法转移，该 Trigger 不会自动代表“这次机会已经过期”。旧链路是：

```text
ExecuteExtraJump()
→ SetTrigger("jump")
→ 当前 JumpAir 没有 jump 转移，无法消费
→ 落地进入 JumpEnd
→ 回到 Idle/Run
→ Idle/Run 的 jump → JumpStart 终于消费 Trigger
→ 出现幽灵起跳动画
```

修复后由 `Any State → JumpStart_MagicWand` 统一消费真正起跳时设置的 `jump Trigger`。普通跳、二段跳、`Coyote Jump` 都会立即重新进入 JumpStart；`Can Transition To Self` 保持开启，所以玩家即使在第一次 JumpStart 尚未结束时快速触发二段跳，也能从头重播起跳动作。

这里不会让“单纯按下 Jump”随意打断攻击或 Dash。`InputAction.performed` 只写入 `JumpBufferCounter`，只有 Gameplay FSM 真正批准并执行普通跳、Coyote Jump 或二段跳时，才会调用 `Animator.SetTrigger`。因此 Animator 仍然服从 Gameplay 决策，而不是绕过状态机自行跳跃。

`PlayerGroundedState.Enter()` 还会先执行 `ResetTrigger(JumpHash)`，清除异常路径遗留的旧 Trigger。若落地时存在合法 `Jump Buffer`，随后的 `ExecuteJump()` 会重新设置 Trigger，所以防御性清理不会吞掉真正的新跳跃。

### 2. 用真实物理阶段驱动 JumpStart、JumpAir 与 JumpEnd

Wizard 新增 Animator Bool 参数 `isFalling`：

```text
isFalling = !isGrounded && VerticalVelocity <= 0
```

判定由纯函数 `JumpAnimationPhaseResolver.IsFalling()` 完成。`VerticalVelocity > 0` 表示仍在上升；速度减到 `0` 或负数表示达到顶点并开始下降；接地时无论残余速度是多少，都不能视为 Falling。`WizardController` 通过共享 Controller 提供的 `SyncCharacterAnimatorParameters()` seam 每帧写入该参数。它没有被强行写进 Warrior/Archer 原型 Animator，避免向不存在的参数调用 `SetBool` 而每帧报错。

新的 Wizard 跳跃转移如下：

| Source | Destination | Condition | Has Exit Time | Blend |
|---|---|---|---|---|
| Any State | JumpStart | `jump` | Off | `0.05s` |
| JumpStart | JumpEnd | `isGrounded = true` | Off | `0.05s` |
| JumpStart | JumpAir | `isFalling = true` | Off | `0.05s` |
| JumpStart | JumpAir | 时间兜底 | On，`0.625` | `0.05s` |
| JumpAir | JumpEnd | `isGrounded = true` | Off | `0.05s` |
| Idle | JumpAir | `isGrounded = false` | Off | `0.05s` |
| Run | JumpAir | `isGrounded = false` | Off | `0.05s` |
| AirDash | JumpAir | `isGrounded = false` | Off | `0.05s` |
| JumpEnd | Idle/Run | `speed` 分流 | On，`0.15` | `0.05s` |

JumpStart 保留一条时间兜底转移，是为了防止完整长跳上升时间较长时，起跳 Clip 一直停留到顶点；而 `isFalling` 与 `isGrounded` 两条无 Exit Time 转移保证短跳可以随真实物理状态提前离开 JumpStart。如果 airtime 极短、来不及进入 JumpAir，Animator 会直接 `JumpStart → JumpEnd`，不会落地后再补播空中动作。

“秒切”并不意味着所有 Blend 都必须为 `0`。完全零 Blend 会让骨骼从一个 Clip 的 Pose 瞬间跳到另一个 Pose，产生明显 Pop。本轮统一采用约 `0.05s` 的极短 CrossFade：条件一旦满足便立即启动切换，同时保留少量姿势连续性。JumpEnd 则保留约 `15%` 的最短落地可读时间，避免落地动作完全看不见；新的 jump Trigger 可经 Any State 随时打断它。

## Task 3：可调 CrossFade 与长短跳配置回归

上一版为了追求“秒切”，把 Wizard 跳跃阶段的多个 `Transition Duration` 统一缩短到 `0.05s`。这解决了 Animator 状态滞后，却忽略了 Animation Clip 之间的 Pose 差异：`JumpStart_MagicWand` 的手臂仍在身体下方，而 `JumpAir_MagicWand` 的手臂位于头顶，约三帧的 Blend 无法形成自然的中间姿势，因此出现明显 Pose Pop。与此同时，Wizard Prefab 的 `_jumpCutVelocityMultiplier` 被序列化为 `1`，等价于完全关闭 Jump Cut；场景实例后来已有开发者手调的 `0.713` Override，本轮予以保留。

### 1. 为什么改为代码驱动 CrossFade

`AnimatorStateTransition.duration` 是 Animator Controller Asset 中的静态配置，不能在 Runtime 绑定一个 MonoBehaviour Inspector 字段。仅在 `WizardController` 暴露浮点数、却继续使用 Controller 内写死的 Transition，并不能实现真实调参。

因此 Wizard 的跳跃动画改为：

```text
Gameplay FSM 批准普通跳 / Coyote Jump / 二段跳
→ PlayJumpStartAnimation()
→ CrossFadeInFixedTime(JumpStart, OtherBlendDuration)

PlayerControllerBase.Update()
→ Gameplay State 更新物理速度与接地状态
→ WizardController.SyncCharacterAnimatorParameters()
→ JumpAnimationPhaseResolver 计算目标阶段
→ 仅当阶段变化时执行一次 CrossFadeInFixedTime
```

Animator Controller 中 JumpStart、JumpAir、JumpEnd 的旧跳跃 Transition 已解除引用，避免 Asset Transition 与代码 CrossFade 同时命中。`ReadEffectiveAnimatorState()` 在 CrossFade 期间读取目标 State，而不是继续读取 Source State；否则每帧都会重复启动同一过渡，动画进度永远无法完成。

阶段决策仍同时照顾物理响应与 Clip 可读性：短跳一旦进入下降便允许 `JumpStart → JumpAir`；完整长跳则让 JumpStart 至少播放到 `normalizedTime = 0.625` 后进入循环空中姿势；落地立即进入 JumpEnd，并保留约 `15%` 的最短落地段后再回到 Idle/Run。二段跳每次都从 `JumpStart` 的 `normalizedTime = 0` 重播。

### 2. Inspector 参数含义

Wizard 根对象 → `WizardController` → `Wizard Jump Animation`：

| 参数 | 默认值 | 影响范围 | 调大/调小的结果 |
|---|---:|---|---|
| `Jump Start To Air Blend Duration` | `0.18s` | 只控制 JumpStart → JumpAir | 调大后手臂举起更连贯，但太大会显得动作拖泥带水；调小更利落，但低于约 `0.1s` 容易再次出现 Pose Pop。建议 `0.15~0.22s`。 |
| `Jump Other Blend Duration` | `0.12s` | 进入 JumpStart、自然离地进入 JumpAir、JumpAir/JumpStart → JumpEnd、JumpEnd → Idle/Run | 调大让所有辅助切换更柔和；太大会造成落地和二段跳视觉响应滞后。建议 `0.08~0.16s`。 |

共享 Jump 分组中的 `Jump Cut Velocity Multiplier` 控制的不是动画，而是短跳物理高度：

- `0.3`：松键后只保留 30% 上升速度，短跳非常明显。
- `0.5`：Prefab 默认值，短跳与长跳区分清楚。
- `0.713`：当前 `P7_DemoRun` 场景实例的开发者 Override，差异更温和。
- `1`：保留全部上升速度，等价于关闭 Variable Jump Height。

这三个参数的职责必须分开理解：两个 Blend Duration 只改变骨骼 Pose 如何混合，不改变角色轨迹；Jump Cut Multiplier 只改变垂直速度，不直接决定播放哪个 Clip。

## Task 4：Air Dash 垂直动量与起跳 VFX

本轮包含一个手感修正和一个表现层反馈。Air Dash 的体感问题最初看起来像“冲刺期间仍在积累重力”，但代码证据表明 `PlayerDashState` 根本没有调用 Airborne 的 `HandleGravity()`，并且空中冲刺位移明确使用 `velocity.y = 0`。真正的问题是冲刺只暂停了垂直位移，却完整保存进入前的 `VerticalVelocity`；如果角色在高速下落时开始 Dash，结束后会立即恢复旧负速度，于是产生“悬停结束后突然猛坠”的反直觉反馈。修复不是重复关闭重力，而是在 Air Dash 进入瞬间按可调倍率处理旧垂直动量。

起跳反馈使用开发者提供的 `Assets/_Project/Art/Prefabs/Wizard/Jump.prefab`。该 Prefab 包含 4 个非循环、`Play On Awake` 的 ParticleSystem，根节点已带适合地面喷发的旋转与缩放；最长系统 Duration 为 5 秒，但 `Stop Action = None`，因此仅 Instantiate 而不清理会不断残留空 GameObject。本轮在生成后安排 5.5 秒自动销毁。

### 1. Air Dash Vertical Velocity Retention

Wizard 根对象 → `WizardController` 的共享 `Dash` 分组新增：

`Air Dash Vertical Velocity Retention`，范围 `0~1`，Prefab 默认 `0`。

进入 Air Dash 时执行：

```text
VerticalVelocity = VerticalVelocity × Clamp01(Retention)
```

- `0`：清空进入前的上升或下落动量；Dash 结束后从接近 0 的速度重新积累重力，最平滑。
- `0.25`：保留 25% 动量，仍有惯性但不会完整恢复高速下坠。
- `0.5`：折中方案。
- `1`：旧行为，完整保留冲刺前速度。

Dash 期间仍然不积分重力，垂直位移仍为 0。本参数只决定“暂停之前的旧速度在恢复时剩多少”，不会改变 Dash 水平距离、持续时间或 Cooldown。策略被拆成纯函数 `AirDashVerticalVelocityPolicy.Apply()`，测试覆盖负向下落、正向上升以及小于 0/大于 1 的安全 Clamp。

### 2. 所有起跳路径共用 Jump Started Feedback

共享状态不直接引用 Wizard 的美术 Prefab，而是在 `PlayerControllerBase` 中提供统一入口：

```text
普通地面跳 / Coyote Jump / 二段跳
→ PlayJumpStartedFeedback()
   ├─ PlayJumpStartAnimation()
   └─ PlayJumpVfx()                 ← Wizard override
```

这样以后新增起跳反馈时不需要在三条路径分别复制代码，也不会出现“普通跳有特效、二段跳漏播”的分支漂移。Wizard 通过 override 实例化 `_jumpVfxPrefab`；其他原型角色的基类实现为空，不会错误复用 Wizard 美术。

VFX 生成位置由 `CharacterController.bounds` 计算：取世界 Bounds 的中心 X/Z 与 `bounds.min.y`，再叠加可调垂直偏移。地面跳因此出现在地面附近，Coyote Jump 和二段跳则出现在角色当时的脚底。实例不作为角色子物体，生成后留在世界坐标，不会跟着玩家升空。

Wizard 的 `Wizard Jump VFX` 分组包含：

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `Jump Vfx Prefab` | `Jump.prefab` | 每次真正取得跳跃初速度时播放的 Prefab。 |
| `Jump Vfx Vertical Offset` | `0.02` | 相对 CharacterController 脚底的 Y 偏移；穿进地面时调高，悬空时调低。 |
| `Jump Vfx Lifetime` | `5.5s` | 实例自动销毁延迟；应不短于 Prefab 最长粒子 Duration。 |

这里选择一次性 `Instantiate + Destroy`，因为跳跃是离散输入，不属于每帧 Hot Path，符合项目允许的一次性分配边界。若未来角色能高频连续跳跃或同屏玩家数量明显增加，再引入 ParticleSystem Pool；当前直接上对象池会增加回收状态重置、跨 Prefab 配置与生命周期复杂度，收益有限。

### 3. Play Mode 验收

1. 在角色高速下落时触发 Air Dash，分别将 Retention 调为 `0 / 0.25 / 0.5 / 1`，确认 Dash 结束后的下落速度逐渐增强。
2. 在上升阶段触发 Air Dash，确认该参数同样按比例保留上升速度。
3. 分别触发普通跳、平台边缘 Coyote Jump 与二段跳，确认每次都只生成一个 Jump VFX。
4. 观察普通跳 VFX 留在起跳地面，二段跳 VFX 留在触发时的空中位置，不跟随角色。
5. 连续跳跃后在 Hierarchy 搜索 `(Clone)`，等待 5.5 秒确认实例自动销毁。
6. 使用 Profiler 确认常规 Update 仍为 `GC Alloc = 0 B`；Instantiate 的分配只应出现在实际起跳帧。
