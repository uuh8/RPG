# Arrow敌人抛物线射击完整解析（更新中）

## Task 1：普通 Arrow 敌人的目标点弹道

本 Task 的玩家可见结果是：普通弓箭敌人沿用已有远程敌人的发现、追击、后撤、站档输出、受击和死亡流程；到弓攻击动画的释放帧时，它发射一支受重力影响的 Arrow。箭并不是始终朝玩家当前方向直飞，而是在释放瞬间把玩家的世界坐标加上胸口高度保存为目标点。运行时根据发射点、目标点、`Physics.gravity` 和配置速度反解初速度，因此理想连续轨迹会经过该胸口点。目标点只锁定一次，玩家在箭离弦后侧移仍可以躲开，这既给玩家反应空间，也避免低成本的持续追踪箭造成不公平体验。

这一功能没有创建第二套弓箭 Enemy AI。`RangedEnemyController` 已经负责远程敌人的 Kite 距离带、感知、视线检查、动画释放时机和法术程序选择；Arrow Enemy 只是给该控制器配置了另一套 `WandLoadout`、另一份 `EnemyDefinition` 和另一种瞄准模式。这样未来加入不同箭种，例如毒箭、爆炸箭、散射箭时，只需要增加法术数据或 Prefab Variant，而不必让 AI 状态机分叉。现有 Wizard Enemy 默认仍为 `Direct`，不会受到抛物线规则影响。

### 1. 运行链路与模块边界

```text
EnemyRangedAttackState
  -> RangedEnemyController.CastSelectedProgram
  -> 锁定 玩家位置 + 胸口高度
  -> SpellCaster.CastProgram
  -> CastEvaluator 输出 EmitCommand
  -> SpellCaster 选择 Direct / BallisticToPoint 初速度
  -> ProjectileBase.Init 写入 Rigidbody velocity
  -> Arrow 碰撞后进入 IDamageable.ReceiveHit 伤害总线
```

`Game.Skills` 仍然只解释“法术指令序列”，不会访问 Scene、`Transform` 或 `Rigidbody`。Arrow 的 `[重力修正, Arrow 发射]` 先由 `CastEvaluator` 变成带 `UseGravity = true` 的 `EmitCommand`；真正生成 Prefab、写入初速度和启动物理的责任仍在 `Game.Character.SpellCaster`。`Game.Combat` 的 `Arrow` 和 `ProjectileBase` 因而不需要知道 Enemy、法术程序或 Animator，继续只负责投射物生命周期、碰撞和统一伤害入口。

创建的 `SpellAimMode` 位于 `Game.Character`。它是“这一次根层发射该怎样把世界目标点转成速度”的 Runtime Authoring 选项：`Direct = 0` 保持原有方向乘速度，`BallisticToPoint = 1` 才使用目标点弹道。把 `Direct` 放在枚举零值是兼容性设计：旧 Prefab 缺少该序列化字段时，Unity 读取默认零值，法师火球仍然直飞。

### 2. 为什么反解初速度，而不是只给 Arrow 开 Gravity

只有打开 `Rigidbody.useGravity`，再把 `velocity` 写成“朝胸口方向乘固定速度”，箭会在飞行中下坠，通常会落在目标点下方。为了让连续轨迹经过目标点，需要使用匀加速度公式：

```text
target = origin + velocity * time + 0.5 * gravity * time²
velocity = (target - origin - 0.5 * gravity * time²) / time
```

`BallisticTrajectory.TrySolveVelocity` 是纯函数。它先用“距离 / 名义速度”得到飞行时间，再用最小飞行时间保护近距离情况，最后反解速度。这里的 `BaseSpeed` 是决定飞行时长和弧线观感的名义速度；因为要补偿 Y 方向重力，最终初速度模长可以大于它。该方案保证给定目标在数学上可达。另一种“固定速度 + 两个抛射角”的方案更接近真实弓力，但远目标或高处目标会出现判别式无解，无法满足本任务“经过 aimPoint”的要求。

Unity PhysX 按固定时间步离散积分，因此上述结论是连续运动学保证。实际能否碰到角色还取决于 Arrow/角色 Collider 尺寸、`Fixed Timestep`、途中墙体和 Layer Collision Matrix；这不是公式错误。代码会拒绝 `NaN`、无穷、零速度和起终点重合，防止把非法速度写入 `Rigidbody` 后造成不可预测的物理状态。

### 4. 数据与 Editor Authoring

Arrow Enemy 的法术程序是 `EnemySpell_Mdy_Gravity -> EnemySpell_Emit_Arrow`。`Modify` 只累积修正快照，不消耗 `BaseDraws`；因此 `Enemy_Arrow_Program` 的 `BaseDraws = 1` 仍能产生一条 Arrow。Arrow Emit 使用 `Physical` 伤害、12 点基础伤害、16 的名义速度和已有 `Arrow.prefab`。EnemyDefinition 负责移动速度 4、侦测/脱战 16/18、攻击距离 14、后撤距离 5 和 1.8 秒攻击冷却；这些是战斗节奏数据，不放进 C# 常量。

`Tools/Norn/Arrow Enemy/Create Or Update Authoring` 菜单工具会创建或更新所有 Arrow 资产，并以 `MagicEnemy_Base` 为组件结构基线生成独立的 `ArrowEnemy_Base`。它切换到 `BowHero.controller`、启用 `Bow1`、关闭 `Wand1_R`、绑定 Arrow Program、设置 `BallisticToPoint`、设置 Bow 受击/死亡状态。这样复制的是成熟的 Enemy 组件组合，不是对 Wizard Prefab 的修改；之后调整 Arrow Enemy 不会回写法师敌人。

### 5. Debug 路径、取舍与回归边界

如果箭持续打到脚下，先检查 Program 是否将 Gravity Modifier 放在 Arrow Emit 前、Arrow Prefab 是否实际引用、Prefab `_aimMode` 是否为 `BallisticToPoint`，最后检查 `_castOrigin`。如果箭从敌人身体内出生后立即消失，应把发射 Transform 调到弓身前方，确认没有落在 `CharacterController` 内；不要先扩大 Collider 或关闭重力。若箭越过玩家，先确认玩家在释放后没有移动，再调 `BaseSpeed`：值更小使飞行时间更长、弧线通常更高，值更大使轨迹更平。若没有播放攻击或没有生成箭，检查 `Attack01_Bow` 状态名、动画释放时间 `ArrowSpawnTime` 和 Animator 的退出连线。

回归时要特别观察 Wizard Enemy：它必须仍为 `Direct`，火球的直线、伤害和冷却不变。Payload、Skyfall、StaticAtPoint、Homing、Orbit 与 Bounce 没有继承 Arrow 根层的旧目标点，避免已有法术机制被无关的弹道数据污染。连续攻击的性能验证应在 Unity Profiler 中确认 Enemy Update/FSM 没有新增每帧 `GC Alloc`；Arrow `Instantiate` 是离散施放成本，不属于每帧分配问题。

### 6. 高台远程敌人的 Line of Sight 起点修复

本次排查确认，玩家目标点原本已经通过 `_aimHeightOffset = 1` 从角色 Root 上移到胸口，并非玩家脚底。真正的设计问题是攻击遮挡检查复用了 `_castOrigin`：这个 Transform 的业务含义是“箭矢或法术从哪里生成”，通常绑定在弓、法杖或武器骨骼附近，会受模型结构和动画姿势影响；它不能同时代表 AI 的眼睛。高台向下攻击时，过低或偏内的武器节点到玩家胸口的直线可能先穿过脚下平台，导致 `Physics.Linecast` 把平台误判为射击通道上的障碍。

`RangedEnemyController` 现在把两种空间语义分开：真实投射物仍从 `_castOrigin` 生成；攻击资格的 `Line of Sight` 从可选 `_lineOfSightOrigin` 发出，未配置时使用敌人 Root 上方 `_lineOfSightOriginHeight = 1.6m` 的稳定眼睛位置，终点继续是玩家胸口。这样旧 Prefab 无需立即增加节点也能获得合理默认行为；不同身高的敌人可在 Prefab 中放置独立 `SightOrigin` 子物体精确 Authoring。不要把它挂在会随攻击动画剧烈摆动的武器节点下。

需要区分三个判断：`EnemyPerception` 只用有限高度圆柱负责发现/保持目标，不做墙体视线；`CanAttackTarget` 才用眼睛到胸口的 `Linecast` 判断当前能否攻击；`SpellCaster` 最后仍以武器释放点和胸口目标点生成真实投射物。新增 EditMode 回归用例覆盖“脚底线被自身高台挡住、眼睛线无遮挡”的几何场景。当前 `dotnet build` 已确认 Character 与 Tests 程序集 0 warning、0 error；Unity Test Runner 与真实高台 Scene Playthrough 仍需在 Editor 中验证。
