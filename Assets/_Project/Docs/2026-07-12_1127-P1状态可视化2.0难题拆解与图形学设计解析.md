## 一、先从最终结果开始：P1 到底完成了什么

玩家最终看到的效果是：角色被火球命中并进入 `Burning` 后，衣服和身体表面会逐渐出现向上流动的火纹、灼烧颜色和发光；角色进入 `Wet` 后，表面会逐渐变得更加光滑，在观察角度接近轮廓的位置出现一层轻微的水膜高光，并带有很弱的冷色调。`Burning` 与 `Wet` 可以同时显示；当潮湿加速灭火时，燃烧画面会跟着 Gameplay 中不断下降的燃烧强度逐渐消退，而不是突然消失。

更重要的是，这不是只在一个测试球体上调出来的 Material：受控角色、法师敌人和战士敌人已经接入同一套角色 Shader。它们可以共享四份生产 Material，却保留各自原本的衣服外观，并且每个角色拥有独立的燃烧、潮湿强度。一个敌人着火不会让其他共享 Material 的角色一起着火。

把最终结果反向追踪，完整链路是：

```text
玩家看见角色表面发生变化
    ↑
URP 使用 SG_CharacterStatusLit 计算每个可见 Fragment 的颜色、光滑度和 Emission
    ↑
Shader 读取 _BurningIntensity / _WetIntensity 等 0~1 参数
    ↑
MaterialPropertyBlock 为每个 Renderer 保存独立参数
    ↑
StatusMaterialController 接收事件、归一化并平滑参数
    ↑
StatusChangedEvent 告诉表现层“哪个角色的哪种状态变成了多少”
    ↑
StatusController 维护 Gameplay 中 0~100 的 Burning/Wet 状态
    ↑
火球命中、状态衰减、Wet 灭火等战斗规则
```

这条反向链路正好给出了 P1 的“难题拆解”：

1. 怎样在不破坏原角色外观的前提下，让角色使用我们自己的 Shader？
2. 怎样把 Gameplay 的 0~100 状态强度可靠地送到 GPU？
3. 多个角色共享 Material 时，怎样保持每个角色的状态互不影响？
4. 怎样从噪声构造出会向上流动、强度连续变化的燃烧 Mask？
5. 怎样用 PBR 参数、向量点积和 Fresnel 构造“潮湿”，而不是简单染蓝？
6. Burning、Wet、原始贴图、受击闪红怎样在同一个 Shader 和同一个 Renderer 上共存？
7. 怎样验证它不是“测试场景里看起来能动”，而是架构正确、可推广、可测试的系统？

下面按照实际开发依赖顺序解决这些小问题，但每个问题都会先从可见结果反推“为了得到这个结果，系统还缺什么信息”。

## 二、难题一：先保住原角色外观，再谈状态效果

### 2.1 从结果反推问题

我们希望替换 Shader 后，角色仍然穿着原本的衣服，保留原有颜色、凹凸、金属和遮蔽细节。只有在出现状态时，Shader 才在原外观上叠加 Burning 或 Wet。

这意味着新 Shader 不能从“一个纯色球”开始，也不能只输出状态颜色。它首先必须完整重建原角色使用的 PBR 材质输入，然后把状态计算插入这些输入与 URP Lit 输出之间。

### 2.2 Material、Shader、Texture、Mesh 与 UV 的关系

初学 Shader 时最容易产生一个误解：Material 中有贴图，所以给两个角色换成同一个 Material 后，它们应该长得一样。实际上最终外观由多项数据共同决定：

```text
最终外观
= Mesh 的几何形状
+ Mesh 顶点的 UV 坐标
+ Material 引用的 Texture 与风格参数
+ Shader 的采样、光照和状态计算
+ Renderer 独立的 MaterialPropertyBlock 参数
```

Texture 可以理解为一张地图，UV 是 Mesh 顶点写在地图上的坐标。Fragment Shader 采样 Base Map 的核心思想是：

```text
C_tex = Texture(BaseMap, uv)
```

其中：

- `BaseMap` 是 Material 引用的颜色贴图；
- `uv=(u,v)` 通常位于 `[0,1]×[0,1]`；
- `C_tex` 是当前 Fragment 从贴图上读取的颜色。

本项目的 Modular RPG 角色使用了 `Texture Atlas`。一张 `Costumes_Albedo` 中可以放很多套衣服，不同衣服 Mesh 的 UV 指向图集中的不同区域。因此玩家和敌人即使共享 `M_CharacterStatus_Costumes`，也会因为 Mesh UV 不同而采样到不同衣服区域。共享 Material 不等于共享 Mesh，也不等于共享 UV。

这也是这套方案能够同时满足“少量共享 Material”和“不同角色仍保留各自服装”的关键。

### 2.3 PBR 基线需要哪些输入

我们创建的 `SG_CharacterStatusLit` 是 URP 的 `Lit Shader Graph`，而不是 `Unlit Shader`。Lit 的含义是：Shader 会把材质参数交给 URP 的光照模型，结果会响应 Directional Light、阴影、环境光、反射探针和 Camera 观察方向。

第一版恢复了以下输入：

| 输入 | Shader Graph 属性 | 作用 |
|---|---|---|
| 基础颜色 | `_BaseColor`、`_BaseMap` | 角色最主要的颜色和花纹 |
| 法线贴图 | `_BumpMap`、Normal Scale | 改变微表面法线，让平面看起来有布纹和凹凸 |
| 金属/光滑度贴图 | `_MetallicGlossMap`、Smoothness | 决定哪些区域像金属、哪些区域更光滑 |
| 环境遮蔽 | `_OcclusionMap`、Occlusion Strength | 压暗缝隙与遮挡区域的间接光 |
|自发光 | `_EmissionMap`、Emission Color | 表面主动发出的光色，是 Burning 发光的基础输出通道 |

颜色基线可以简化写为：

```text
C_base = Sample(BaseMap, UV) × BaseColor
```

这里的乘法通常是逐通道乘法。例如贴图颜色 `(0.8,0.5,0.2)` 乘颜色参数 `(1,0.8,0.8)`，结果为 `(0.8,0.4,0.16)`。Color 参数因此常被称为 Tint。

Normal Map 通常使用 `Tangent Space` 编码。贴图中常见的蓝紫色并不是最终表面颜色，而是用 RGB 编码一个方向。Shader 将它解码成局部法线，再通过角色表面的 `Tangent-Bitangent-Normal` 基底变换到光照使用的空间。它影响的是光照计算，不应该接到 Base Color。

Unity 这套角色资源的 Metallic/Smoothness 使用 Packed Map：

```text
Metallic   = MetallicSmoothnessMap.r
Smoothness = MetallicSmoothnessMap.a × SmoothnessParameter
```

`Smoothness` 与 `Roughness` 表达相反概念，常用近似关系是：

```text
Roughness ≈ 1 - Smoothness
```

Smoothness 高时，微表面法线分布更集中，高光更锐利；Smoothness 低时，高光更宽、更散。URP Lit 内部会用比这个解释更完整的 BRDF，但对初学者来说，先建立“Smoothness 控制高光形状，不是直接让颜色变白”的认识最重要。

### 2.4 业界常见方案与我们的选择

**方案一：直接修改第三方 Shader。**

优点是最快继承原资源全部功能；缺点是第三方包更新后容易冲突，而且状态逻辑会与供应商代码耦合。项目要求不修改 `Assets/ThirdParty`，因此没有采用。

**方案二：复制第三方 Shader，再在副本上开发。**

能够保留复杂原效果，但会带入大量暂时不理解的代码，学习成本高，后续还要维护一份 Fork。

**方案三：从 URP Lit Shader Graph 重建必要 PBR 基线，再加入状态。**

这是最终方案。它让每一条贴图链、Normal、Smoothness、Emission 都是我们亲手建立和理解的，同时不破坏第三方资产。代价是必须人工核对每个 Texture 与 Channel。

### 2.5 Unity 中实际用到的技术

- `URP Lit Shader Graph`：生成兼容 URP 光照、阴影、深度等 Pass 的 Shader。
- `Sample Texture 2D`：按 UV 采样 Base、Normal、Packed、AO、Emission 贴图。
- `UV` Node：提供 Mesh 插值后的 UV0。
- `Normal Strength`：缩放 Tangent-space Normal Map 的扰动强度。
- `Multiply`：组合贴图与 Color、强度等参数。
- `Split`：拆分 Packed Map 的 R/G/B/A Channel。
- Shader Graph Blackboard 的 `Reference`：决定 C# 和 Material 访问属性时使用的真实名称，例如 `_BaseMap`。

### 2.6 本阶段真实踩坑

第一次看到蓝紫色贴图时，很容易疑惑“我们不是在做 Shader 吗，为什么还要找贴图”。原因是 Shader 是计算规则，Texture 是规则读取的数据。Shader Graph 并不会自动知道角色原来使用哪张 Normal Map；必须从原 Material 找到对应贴图并赋给新 Material。

另一个容易犯的错误是直接把测试材质替换到所有角色上。正确流程是复制四个类别的生产 Material，让它们引用各自的 Atlas；Lab Material 只用于 A/B Comparison，不应该成为正式角色材质。

## 三、难题二：把 Gameplay 数值变成 Shader 能使用的参数

### 3.1 从结果反推问题

角色的火纹不是 Boolean 开关。`Burning=20` 应该只有较弱火纹，`Burning=100` 应该非常明显；状态自然衰减时，画面也应连续变弱。

Gameplay 的 `StatusController` 使用策划容易理解的 `0~100`，而 Shader 中的 `Lerp`、Mask 与大部分归一化计算习惯使用 `0~1`。因此需要一个专门的表现桥完成：

```text
状态权威数据 → 目标对象识别 → 0~1 归一化 → 时间平滑 → 写入 Renderer
```

这个职责由 `StatusMaterialController` 承担。

### 3.2 为什么 Shader 不直接读取 StatusController

CPU 上的 C# 对象与 GPU 上执行的 Shader 是两个不同世界。Shader Graph 生成的 Shader 不会自动访问 `MonoBehaviour`，也不能在 Fragment Shader 中调用 `StatusController.GetIntensity()`。

CPU 必须显式把数据提交给渲染系统：

```text
CPU C#：决定数据是什么、属于哪个角色
GPU Shader：对大量 Vertex/Fragment 并行计算画面
```

`Custom Function` 也不是 C# 与 Shader Graph 联动组件。它只是把一段 HLSL GPU 函数嵌入 Shader Graph。C# 与 Shader 的数据联动仍然依靠 Material 属性、`MaterialPropertyBlock`、Global Shader Property、ComputeBuffer 等数据接口。

### 3.3 跨模块架构

P1 没有让 Combat 直接引用 Rendering。正确方向是：

```text
Game.Combat.StatusController
    ↓ 发布 StatusChangedEvent
Game.Rendering.StatusMaterialController
    ↓ 只读订阅
Renderer / Shader
```

Gameplay 不知道 Shader 是否存在，也不会为了画面去修改战斗规则。将来换成其他 Shader、VFX Graph 或低配模式，`Burning` 的伤害和 `Wet` 灭火仍然正确。

`StatusChangedEvent` 是 `struct` 并实现 `IGameEvent`。关键数据包括：

- `TargetId`：哪个角色发生变化；
- `Kind`：Burning、Wet、Poisoned、Sticky；
- `Intensity`：Gameplay 强度；
- `IsActive`：状态是否仍激活。

`TargetId` 必须过滤。EventBus 是全局广播通道，如果不比较目标 ID，任何敌人着火都会驱动所有订阅者。

### 3.4 归一化公式

转换公式是：

```text
I_shader = clamp(I_gameplay / 100, 0, 1)
```

代码使用：

```csharp
Mathf.Clamp01(statusIntensity * 0.01f)
```

`Mathf.Clamp01(x)` 是 Unity API，等价于 `min(max(x,0),1)`。它不仅完成范围限制，也防御错误输入：例如 Gameplay 意外传入 150，Shader 仍只得到 1，而不会让 Lerp 与 Emission 失控。

### 3.5 为什么还要时间平滑

Event 中的目标值可能从 0 一次跳到 1。如果直接写入 Shader，画面会瞬间切换，更像材质开关而不是状态附着。我们使用：

```text
current = MoveTowards(current, target, responseSpeed × deltaTime)
```

Unity API `Mathf.MoveTowards(current,target,maxDelta)` 每帧最多移动 `maxDelta`，并且不会越过目标。默认 `_responseSpeed=4` 时，从 0 到 1 最快约需：

```text
time = distance / speed = 1 / 4 = 0.25 second
```

乘 `Time.deltaTime` 的原因是把“每帧变化量”转换成“每秒变化速度”。否则 30 FPS 与 120 FPS 会产生不同过渡时间。

四种状态被放入一个 `Vector4`：

```text
X = Burning
Y = Wet
Z = Poisoned
W = Sticky
```

这是紧凑的值类型状态，不会因为逐帧复制产生托管堆 `GC Alloc`。当前 Shader 已完成 Burning 和 Wet 的视觉链；Poisoned 与 Sticky 的 Float 通道已经贯通，但具体图形效果仍是后续扩展，不能在面试中说成已完成。

### 3.6 Unity 生命周期与 API

`[RequireComponent(typeof(StatusController))]`：告诉 Unity 添加 `StatusMaterialController` 时必须同时存在 `StatusController`。它把组件依赖显式化，减少 Inspector 漏配。

`[DisallowMultipleComponent]`：禁止同一 GameObject 重复添加多个状态材质控制器，避免同一 Renderer 被重复写入。

`Awake()`：缓存组件、创建 `MaterialPropertyBlock`、收集 Renderer。`Awake` 适合一次性初始化，数组分配放在这里而不是 `Update()`。

`OnEnable()`：订阅 `EventBus<StatusChangedEvent>`，并主动从 `StatusController` 同步当前值。主动同步很重要，因为对象池中的角色重新启用时，状态事件可能已经在禁用期间发布过。

`OnDisable()`：取消订阅并清零视觉参数，防止对象池复用后短暂保留上次的火纹。

`Update()`：只有 `_isTransitioning=true` 时才执行平滑；稳定状态立即 return，不重复提交 Renderer 数据。

`gameObject.GetInstanceID()`：取得 Unity Object 在当前运行期间的实例 ID，用作事件收件人地址。它适合运行时关联，不应当作为跨存档永久 ID。

`Shader.PropertyToID(string)`：把属性字符串预先转换成整数 ID。它避免 `Update` 热路径反复进行字符串查找，且减少拼写散落。

`GetComponentsInChildren<Renderer>()`：在 `Awake` 自动收集当前激活的子节点 Renderer。当前方案只保留 `MeshRenderer` 与 `SkinnedMeshRenderer`，排除 `ParticleSystemRenderer` 和 `TrailRenderer`。

这里有一个明确边界：不传 `includeInactive=true` 时，只会收集当时激活的模块化部件。以后若运行时换装会启用新的 Renderer，就需要显式 Renderer 列表、刷新接口或注册机制。当前固定装配角色不受影响。

## 四、难题三：共享 Material，但每个角色状态必须独立

### 4.1 从结果反推问题

玩家和敌人可以使用相同的四份生产 Material：BodyParts、Costumes、HeadParts、Weapons。共享可以减少 Material 资产数量，也更符合模块化角色资源的 Atlas 设计。

但是如果直接执行：

```csharp
sharedMaterial.SetFloat("_BurningIntensity", 1f);
```

修改的是共享资产状态，所有引用它的角色都会一起变化。

如果使用：

```csharp
renderer.material.SetFloat(...);
```

Unity 会为 Renderer 创建 `Material Instance`。角色多、部件多时会产生大量实例，增加内存、材质管理和批处理压力。

### 4.2 最终方案：MaterialPropertyBlock

`MaterialPropertyBlock`，简称 `MPB`，允许为某个 Renderer 覆盖少量 Shader 属性，而不复制整份 Material。

可以把它理解为：

```text
Shared Material：所有角色共同遵循的材质配方与默认风格
MPB：某一个 Renderer 这一次绘制时使用的局部参数覆盖
```

因此可以得到：

```text
角色 A：共享 Material + Burning=1.00
角色 B：共享 Material + Burning=0.25
角色 C：共享 Material + Wet=0.80
```

### 4.3 为什么必须先 Get，再 Set

本项目已有 `CharacterCombatFeedback` 使用 MPB 写入 `_BaseColor` 实现受击闪红。状态控制器如果每次创建一个空 Block 后直接 Set，会覆盖同一 Renderer 上其他系统已经写入的属性。

正确流程是：

```csharp
renderer.GetPropertyBlock(block);
block.SetFloat(BurningId, burning);
block.SetFloat(WetId, wet);
renderer.SetPropertyBlock(block);
```

`Renderer.GetPropertyBlock` 读取该 Renderer 当前已有覆盖；状态系统只修改自己拥有的四个 Float；`Renderer.SetPropertyBlock` 再整体提交。这样受击闪红与状态效果可以共存。

这背后体现了一个重要架构原则：多个表现系统共享同一个 MPB 时，每个系统只能修改自己拥有的字段，并保留其他字段。

### 4.4 共享 Material 为什么没有让敌人穿上玩家衣服

这次敌人替换材质后的测试进一步验证了 Atlas + UV 机制。四份生产 Material 引用整套部件图集，而每个敌人节点的 Mesh UV 指向图集中的不同区域。因此 Material 共享的是“整张地图和渲染方法”，不是“地图上的同一个地址”。

状态参数由 MPB 独立覆盖，基础外观由 Mesh UV 独立采样，二者正好互不冲突。

### 4.5 业界其他方案

**每角色 Material Instance。** 实现简单，适合对象很少或属性变化很多的场景；缺点是实例数量与内存增长明显。

**Shader 全局数组 + 实例索引。** 可为大量角色批量提交状态，适合大规模 Crowd，但架构和 Shader 数据管理复杂，当前规模没有必要。

**GPU Instancing。** 适合大量相同 Mesh/Material，实例属性可以放在 Instanced Buffer；但本项目角色是多个不同模块化 SkinnedMeshRenderer，不是最直接的 MVP 路线。

**MaterialPropertyBlock。** 最适合当前“共享 Material、每 Renderer 只有几个 Float 不同”的需求，因此被采用。

需要诚实说明：MPB 不自动保证所有情况下都提升 Batching。它可能影响 SRP Batcher 或具体 Draw Call 合并方式，必须通过 `Frame Debugger` 和 `Profiler` 实测，不能只凭经验宣称“一定更快”。它当前最明确的价值是避免 Material Instance，并建立正确的每 Renderer 参数语义。

## 五、难题四：怎样从数学上生成向上流动的燃烧区域

### 5.1 从结果反推问题

燃烧不能只是把角色整体染红。我们希望表面出现不规则、会流动的局部火纹，而且状态越强，火纹覆盖面积和亮度越大。

要得到这个结果，需要逐层构造：

```text
角色表面位置
→ 二维噪声坐标
→ 随时间移动坐标
→ Simple Noise 灰度图
→ Threshold 截取区域
→ Smoothstep 软化边缘
→ BurningIntensity 控制覆盖与亮度
→ Mask 驱动 Base Color 和 Emission
```

### 5.2 为什么使用 Object Space Position

Shader Graph 的 `Position(Object)` 表示 Fragment 在角色对象局部空间中的位置。与 World Space 相比，它会跟随角色移动。

如果使用 World Position：角色向前跑时，噪声仿佛固定在世界里，角色表面会穿过火纹，产生“投影在空间中的图案”。使用 Object Space 后，火纹附着在角色身上，移动、冲刺时不会留在原地。

Object Space 的代价是：多个独立子 Renderer 可能具有不同局部坐标原点和缩放，接缝处不一定完全连续。第一版接受轻微接缝；如果未来要严格连续，可以使用角色根节点空间或传入统一坐标变换矩阵。

### 5.3 从三维位置构造二维 Noise UV

Simple Noise 接收二维坐标。角色是三维的，因此我们组合 Object Position：

```text
P = (Px, Py, Pz)

horizontal = Px + 0.37 × Pz
vertical   = Py + Time × BurnFlowSpeed

noiseUV = (horizontal, vertical) × BurnNoiseScale
```

`Px + 0.37Pz` 的作用是让角色前后表面不完全采到相同图案。如果只使用 X 和 Y，沿 Z 方向相隔的表面可能得到重复火纹。0.37 不是物理常数，只是打破对称性的风格参数。

`vertical = Py + Time×Speed` 表示采样坐标沿 Y 轴随时间移动。需要注意：我们移动的是“采样窗口”，看到的纹理运动方向可能与坐标偏移方向产生直觉上的反向，因此最终必须在实际模型上验证。本次开发最初使用减法，视觉上火纹向角色的 `-Y` 运动，后来改为加法，实际效果才符合“向上流动”。

`BurnNoiseScale` 控制空间频率：

- Scale 小：Noise 变化慢，形成大块火纹；
- Scale 大：Noise 变化快，形成细碎火纹。

Shader Graph 的 `Simple Noise` 节点自身也有 Scale。我们最终把节点内部 Scale 设为 1，只在外部统一缩放 UV，避免同一个频率被乘两次导致参数难以理解。

### 5.4 Noise 是什么

Noise 函数把连续坐标映射为看似随机但空间连续的标量：

```text
n = Noise(noiseUV), n ∈ [0,1]
```

相邻坐标产生相近数值，因此它不像白噪声那样每个像素完全跳变。Noise 输出本身只是灰度数据，还不是火焰。接下来要把灰度变成区域 Mask。

### 5.5 BurningIntensity 的感知曲线

最初直接使用线性强度时，`BurningIntensity<0.5` 的变化不明显。原因不是数据没写进去，而是人眼对覆盖面积与亮度的感知，加上 Threshold 非线性，让低值区间被压缩。

最终增加响应曲线：

```text
I = saturate(BurningIntensity)
I_visual = pow(I, 0.6)
```

当指数小于 1 时，小输入会被抬高：

```text
0.25^0.6 ≈ 0.435
0.50^0.6 ≈ 0.660
1.00^0.6 = 1.000
```

它没有改变 Gameplay 状态，只改变视觉映射。这样 25% Burning 也能被看见，同时 100% 仍保持上限 1。

这是一种 `Response Curve`。它说明 Gameplay 数值与视觉感知不一定要线性对应，只要映射单调、可解释，并且不反向改变战斗逻辑。

### 5.6 Threshold 与 Smoothstep

我们让强度控制 Noise 的截取阈值：

```text
threshold = lerp(0.95, 0.35, I_visual)
```

`Lerp(a,b,t)` 的公式是：

```text
lerp(a,b,t) = a(1-t) + bt
```

强度低时 Threshold 接近 0.95，只有 Noise 中非常亮的少量区域通过；强度高时 Threshold 降到 0.35，更多区域通过。

硬阈值可以写成：

```text
mask = noise >= threshold ? 1 : 0
```

但它会产生锯齿和突兀边缘。我们使用：

```text
lower = threshold - BurnMaskSoftness
upper = threshold + BurnMaskSoftness
mask  = smoothstep(lower, upper, noise)
```

`smoothstep` 在 lower 以下输出 0，在 upper 以上输出 1，中间使用平滑三次曲线过渡。标准形式是：

```text
t = saturate((x-edge0)/(edge1-edge0))
smoothstep(edge0,edge1,x) = t²(3-2t)
```

最后再乘视觉强度：

```text
finalBurnMask = mask × I_visual
```

乘这一步非常关键。Threshold 负责“覆盖哪里”，强度乘法负责“覆盖有多强”。当 BurningIntensity=0 时，最终 Mask 必须严格为 0。

### 5.7 Mask 怎样影响颜色与 Emission

焦灼颜色分支：

```text
burnTarget = originalBaseColor × BurnSurfaceColor
burnBlend  = saturate(finalBurnMask × 0.75)
burnedBase = lerp(originalBaseColor, burnTarget, burnBlend)
```

这里使用乘法 Tint，而不是直接替换成纯黑或纯红，因此原衣服纹理细节仍然保留。

自发光分支：

```text
burnEmission = BurnEmissionColor × finalBurnMask
finalEmission = originalEmission + burnEmission
```

`Emission` 表示表面主动输出的辐射亮度，不依赖场景灯光照到它。HDR Color 可以超过普通 0~1 范围，为 Bloom 提供高亮源。

但 `Emission` 与 `Bloom` 不是同一件事：

- Emission 在 Shader 中产生高亮像素；
- Bloom 是 Camera Post-processing，从已经渲染好的图像中提取超过 Threshold 的亮区，进行模糊并叠回画面。

因此要在 Game View 看见光晕，还需要：

1. Camera 开启 Post Processing；
2. 场景 `Global Volume` 添加并启用 Bloom；
3. Emission HDR 强度高于 Bloom Threshold；
4. 在 Game View/Camera 输出观察，而不是只看 Material Preview。

### 5.8 Burning 的备选实现方案

**粒子系统覆盖。** 火焰体积感好、容易制作火苗，但难以精确贴合所有模块化角色表面，粒子数量和 Overdraw 也需控制。

**第二层 Shell Mesh。** 复制角色外壳并使用透明火焰 Shader，轮廓明显；缺点是额外 Draw Call、透明排序和 Skinned Mesh 成本。

**Decal / Projector。** 适合局部烧痕，但模块化动画角色的全身动态覆盖与方向控制更复杂。

**屏幕后处理。** 可以做全局热扭曲，但难以只识别某个角色，通常需要额外 Mask Buffer。

**统一 Surface Shader + 辅助 VFX。** 当前选择 Shader 负责稳定的全身状态可读性，既有 OnFire VFX 继续负责体积火焰。两者互补，而不是互相替代。

## 六、难题五：怎样用图形学表达“潮湿”，而不是给角色染蓝

### 6.1 从结果反推问题

现实中的湿润表面通常会出现：

1. 微表面被水膜填平，高光更集中；
2. 掠射角反射更明显，轮廓出现水膜感；
3. 材料可能轻微变暗或偏冷；
4. 它不会像火一样主动发光。

因此 Wet 被拆成三条视觉线索：

```text
Smoothness 提升：主要物理材质信号
Fresnel Edge：随视角变化的水膜轮廓
轻微 Tint：保证正面区域仍有状态可读性
```

### 6.2 Smoothness：水膜改变微表面

先得到原始光滑度：

```text
baseSmoothness = MetallicSmoothnessMap.a × Smoothness
```

潮湿目标使用：

```text
wetTargetSmoothness = max(baseSmoothness, WetSmoothness)
finalSmoothness = lerp(baseSmoothness, wetTargetSmoothness, WetIntensity)
```

为什么必须使用 `max`？假设：

```text
布料 base=0.20，WetSmoothness=0.92 → target=0.92
金属 base=0.98，WetSmoothness=0.92 → target=0.98
```

Wet 应让粗糙布料更光滑，但不应该把原本 0.98 的金属降到 0.92。`Maximum` Node 保留了材质原有差异。

为什么不能直接 `finalSmoothness=WetIntensity`？因为那会把所有贴图区域抹平成同一个数值。状态 Shader 的目标不是删除原材质身份，而是在原材质上进行有方向的修改。

### 6.3 Fresnel 的向量与点积基础

定义：

```text
N = 当前 Fragment 的 World Space 表面法线
V = 从当前 Fragment 指向 Camera 的 World Space 视线方向
```

向量归一化公式：

```text
normalize(v) = v / |v|
|v| = sqrt(vx² + vy² + vz²)
```

两个单位向量的点积：

```text
N·V = NxVx + NyVy + NzVz = cos(theta)
```

其中 theta 是 N 与 V 的夹角：

- 表面正对 Camera：theta 接近 0 度，`N·V≈1`；
- 表面接近轮廓：theta 接近 90 度，`N·V≈0`。

因此边缘 Mask 可以写成：

```text
f = 1 - saturate(dot(normalize(N), normalize(V)))
```

再使用 Power 控制边缘宽度：

```text
F_wet = pow(f, WetFresnelPower)
```

例如 `f=0.5`：

```text
0.5^1 = 0.5
0.5^2 = 0.25
0.5^4 = 0.0625
0.5^8 = 0.00390625
```

Power 越大，中间值被压得越低，只剩非常接近轮廓的区域，因此边缘更窄。

Normal 与 View Direction 必须位于同一 Coordinate Space。World Space 与 Object Space 使用不同坐标基底，即使两边都有 XYZ，直接点积也没有正确夹角意义。我们统一选择 World Space。

### 6.4 与真实 Fresnel 的关系

实时 PBR 常使用 Schlick Approximation：

```text
F(theta) = F0 + (1-F0)(1-cos(theta))^5
```

`F0` 是正视角基础反射率。空气到水的折射率大约为 `n1=1`、`n2=1.33`，其正视反射率近似：

```text
F0 = ((n1-n2)/(n1+n2))²
   ≈ ((1-1.33)/(1+1.33))²
   ≈ 0.02
```

也就是说，真实水面正视仍有少量反射，掠射角反射快速增强。

当前公式 `pow(1-N·V,Power)` 是风格化 Fresnel Mask，不是完整水膜 BRDF：它没有模拟双层介质、折射和严格能量守恒。选择它的原因是战斗可读性、参数可调性和初学阶段的可理解性。面试时应主动说明这是有意识的近似，而不是误称为“真实水模拟”。

### 6.5 HLSL Custom Function 的作用

节点版 Fresnel 完成后，我们在 `StatusFresnel.hlsl` 中实现同一公式：

```hlsl
float3 normal = normalize(NormalWS);
float3 viewDirection = normalize(ViewDirectionWS);
float ndotv = saturate(dot(normal, viewDirection));
Fresnel = pow(1.0 - ndotv, max(Power, 0.0001));
```

Shader Graph 的 `Custom Function` 使用 File 模式引用该文件，函数名填写 `StatusFresnel`。节点 Precision 选择 `Single` 时，对应 32-bit `float`，Shader Graph 会寻找 `StatusFresnel_float`；选择 Half 时会寻找 `StatusFresnel_half`。

HLSL 文件同时提供 float/half 两版：

- `float`：通常 32-bit，便于桌面平台学习、对照和调试；
- `half`：通常对应较低精度，部分移动 GPU 吞吐更好，但是否值得使用必须实测。

`max(Power,0.0001)` 用来避免负指数、`0^0` 或接近无穷大的不稳定输入。

为什么已经有 Shader Graph 还要写 HLSL？不是因为二者必须配套，而是因为：

1. Graph 适合观察数据流和中间 Preview；
2. HLSL 适合封装可复用公式、代码审查和精确控制；
3. 用同一 Fresnel 分别实现，可以帮助理解“节点最终也会生成 Shader 代码”。

Shader Graph 与手写 Shader 最终都要变成 GPU 执行的 Shader 程序。Graph 是可视化代码生成工具，不是另一种渲染原理。

### 6.6 水膜颜色组合

先做轻微冷色 Tint：

```text
wetTintTarget = burnedBaseColor × WetTintColor
wetTintAmount = WetIntensity × WetTintStrength
wetTintedColor = lerp(burnedBaseColor, wetTintTarget, wetTintAmount)
```

Tint Strength 很小，因为 Wet 的主要信息应该来自 Smoothness 与 Fresnel，而不是整体变蓝。

再计算边缘贡献：

```text
wetEdgeMask = F_wet × WetIntensity × WetEdgeStrength
wetEdgeContribution = WetEdgeColor × wetEdgeMask
finalBaseColor = wetTintedColor + wetEdgeContribution
```

`WetEdgeColor` 使用普通 Color，不使用 HDR，也不进入 Emission。水膜是反射信号，不是主动能量源；否则黑暗中的湿角色仍会自发蓝光，更像护盾。

这种把 Edge 加到 Base Color 的方式是风格化近似，并不严格满足能量守恒。更物理的升级方案是使用 Clear Coat、Specular 或自定义双层 BRDF，但第一版的复杂度与项目需求不匹配。

### 6.7 Wet 的备选实现方案

**只提高 Smoothness。** 最接近基础 PBR，成本低；但在缺少环境反射或镜头较远时不够明显。

**只做冷色 Tint。** 非常便宜、识别稳定；但容易看成中毒或冰冻，缺少潮湿材质感。

**动态水滴 Normal / Flow Map。** 视觉更丰富；需要额外 Texture Sample、UV 流动与美术资源。

**Clear Coat 双层材质。** 更符合水膜覆盖物体的物理含义；需要更复杂的 Shader Target 或自定义 BRDF。

**屏幕空间反射/真实水层。** 效果高级，但成本和工程复杂度远超战斗状态需求。

最终选择 Smoothness + Fresnel + 弱 Tint，是在物理线索、战斗可读性、性能和学习价值之间的平衡。

## 七、难题六：多个状态怎样在同一个 Shader 内正确组合

### 7.1 为什么没有为每个状态创建一个 Shader

如果每种状态一个 Shader，就会出现：

```text
Neutral Shader
Burning Shader
Wet Shader
Burning+Wet Shader
Burning+Poisoned Shader
Wet+Sticky Shader
……
```

状态数量增加后，组合数量接近 `2^N`，这就是 `Combinatorial Explosion`。同时频繁替换 Material/Shader 会增加状态管理、动画过渡和渲染状态切换复杂度。

最终方案是一个统一的 `SG_CharacterStatusLit`，使用四个独立强度作为输入：

```text
_BurningIntensity
_WetIntensity
_PoisonedIntensity
_StickyIntensity
```

当前只实现 Burning 与 Wet 的视觉数学，另外两项是架构预留。统一 Shader 让后续状态能够沿同一数据通道扩展，但每新增一个状态仍需评估 Fragment 成本与组合顺序。

### 7.2 当前组合顺序

颜色链：

```text
原始 PBR Base Color
→ Burning 焦灼 Tint
→ Wet 冷色 Tint
→ Wet Fresnel Edge
→ URP Lit Base Color
```

光滑度链：

```text
原始 Packed Smoothness
→ Wet 提升
→ URP Lit Smoothness
```

自发光链：

```text
原始 Emission
+ Burning Mask × Burn Emission Color
→ URP Lit Emission
```

Wet 不直接在 Shader 里把 BurningIntensity 减掉。Wet 灭火属于 Gameplay，发生在 `StatusController.Tick()`：当 Burning 与 Wet 共存时，额外增加 Burning 每秒衰减。随后 EventBus 发布较低强度，Shader 自然显示较弱火纹。

这样不会出现 CPU 认为 Burning=80、GPU 却因为 Wet 擅自显示成 20 的两套真相。

### 7.3 Material 参数与运行时参数的职责

运行时状态参数回答“现在有多少”：

```text
_BurningIntensity
_WetIntensity
_PoisonedIntensity
_StickyIntensity
```

Material 风格参数回答“这个世界里的效果长什么样”：

```text
BurnNoiseScale
BurnFlowSpeed
BurnMaskSoftness
BurnSurfaceColor
BurnEmissionColor
WetSmoothness
WetFresnelPower
WetEdgeColor / Strength
WetTintColor / Strength
```

这种拆分让 Gameplay 设计师调整状态数值时，不会意外改变 Shader 风格；图形程序或 Technical Artist 调整火纹与水膜时，也不会修改伤害和衰减规则。

### 7.4 另一种业界方案：Shader Keyword

可以使用 Shader Keyword 编译 `BURNING_ON`、`WET_ON` 变体，在状态关闭时跳过对应计算。但四个 Boolean 状态理论上就可能产生 16 种组合，更多状态会形成大量 Shader Variants，增加编译时间、Build 大小和 Warmup 压力。

当前采用 Float 强度统一计算，优点是连续过渡和组合简单，缺点是状态为 0 时部分 Fragment 运算仍可能执行。是否引入 Keyword 应由 GPU Profiler 数据决定，而不是提前优化。

## 八、难题七：怎样证明架构正确，而不是“刚好看起来能用”

### 8.1 自动化测试覆盖了什么

`StatusMaterialControllerTests` 使用真实 `EventBus`、`StatusController`、Renderer 与 MPB，不只测试一个纯函数。

**测试一：目标过滤与归一化。**

给其他 TargetId 发布 Burning=100，当前角色必须保持 0；给当前角色发布 150，最终必须 Clamp 为 1。它验证全局事件不会串角色，且 0~100 到 0~1 的边界正确。

**测试二：Wet=50 与受击颜色共存。**

先在 MPB 写入 `_BaseColor=magenta`，再发布 Wet=50，最终 Wet 必须为 0.5，同时 `_BaseColor` 不变。它验证状态桥遵守“先 Get 后 Set”。

**测试三：共享 Material，独立状态。**

两个 Renderer 引用同一个 Shared Material，一个 Burning=1，另一个 Burning=0.25。断言共享引用仍相同，而 MPB 数值不同。它直接验证 P1 最重要的材质共享设计。

**测试四：Disable 生命周期。**

组件禁用后取消事件订阅并清零状态，避免对象池复用残留。

### 8.2 测试为什么曾经全部超时

测试最初进入当前场景时继承了 `Time.timeScale=0`。本项目 Wand Editor 会通过 `Time.timeScale=0` 暂停游戏；此时 `Time.deltaTime=0`，所以：

```text
maxDelta = responseSpeed × deltaTime = 0
```

`MoveTowards` 永远无法前进，测试等待状态收敛就会超时。

错误修法是让生产代码在暂停时仍使用 Unscaled Delta Time，因为那会改变“暂停时视觉是否继续变化”的设计语义。最终在测试前显式执行 `Time.timeScale=1`，建立测试所需的正常游戏时间前置条件。

这个 Debug 很有价值：测试失败不一定表示被测算法错误，也可能是 Test Fixture 没有隔离全局 Unity 状态。

### 8.3 Shader 开发中的真实问题与定位方式

**问题一：Burning 低于 0.5 时几乎看不见。**

数据链正常，问题在视觉映射。通过 `pow(I,0.6)` 抬高低强度响应，而不是篡改 Gameplay 强度。

**问题二：火纹向 -Y 流动。**

检查 Object Position、Time 与 Add/Subtract 链，最终把垂直坐标改为 `Y + Time×Speed`，并在真实角色模型上验证。纹理采样运动方向必须看结果，不能只凭公式符号猜测。

**问题三：BurningIntensity=0 仍有红黄发光。**

说明 Emission Color 绕过 Mask 直接进入最终 Emission。修复原则是所有状态贡献最终都必须乘状态 Gate：

```text
burnEmission = BurnEmissionColor × finalBurnMask
```

**问题四：Bloom 设置了却看不到。**

区分 Material Preview、Scene View 与 Camera Game View，检查 Camera Post Processing、Global Volume、Bloom Threshold 和 HDR Emission 强度。

**问题五：误以为 Wet 要创建第二个 Shader。**

从状态可共存反推，必须使用统一 Shader，否则会产生组合爆炸。Lab Material 可以有四份，但 Shader 只有一个。

**问题六：Fresnel Custom Function 没有 Float Preview 选项。**

Unity Shader Graph UI 中显示的是 `Single`，对应 HLSL 的 32-bit float；不是所有界面都直接写 Float。

**问题七：HLSL 与节点版比较链误接进生产输出。**

正确比较方式是：节点版与 HLSL 版相减后取 Absolute 只作为诊断 Preview；生产 Wet 链直接接 HLSL Fresnel。否则差值接近 0，Wet Edge 也会被错误清空。

**问题八：替换 Material 后敌人没有变成玩家衣服。**

这不是 Bug，而是 Mesh UV 在同一 Atlas 中采样不同区域。通过观察共享 Material 与不同 Mesh 的结果，反而验证了资产组织方式正确。

### 8.4 图形 Debug 的“从输出往回查”方法

当最终画面不对时，不要随机调参数。按输出逆向断开并检查：

```text
最终 Base Color / Smoothness / Emission
← 状态贡献是否乘 Intensity
← Mask 是否为正确 0~1
← Threshold / Fresnel 中间值
← Noise / Dot Product
← Position、Normal、View Direction、UV
← Material Texture 与属性 Reference
← C# 写入的 MPB 值
← Event 与 Gameplay 状态
```

Shader Graph 节点 Preview 很适合这种单步诊断：白色通常代表 1，黑色代表 0，灰色代表中间值。先证明数据，再讨论美术参数。

### 8.5 性能边界

CPU 侧：

- `Shader.PropertyToID` 只初始化一次；
- Renderer 数组只在 `Awake` 收集；
- 稳定状态 `_isTransitioning=false` 时 `Update` 立即返回；
- 不在热路径使用 LINQ、Closure、字符串拼接或数组分配；
- 只有数值改变时才调用 `SetPropertyBlock`。

GPU 侧：

- Burning 增加 Object Position 运算、Simple Noise、Smoothstep、Lerp 与 Emission；
- Wet 增加 Smoothness 运算、Normalize、Dot、Power、Tint 与 Edge；
- 统一 Shader 即使状态为 0，某些运算仍可能存在；
- 使用同一个 Opaque Lit Shader，避免额外透明 Shell 的 Overdraw 与排序问题。

`Frame Debugger` 应检查 Forward Lit、ShadowCaster、Depth 等 Pass 是否正常，有没有意外 Transparent Pass，有没有 Material Instance；`Profiler` 应关注 `StatusMaterialController.Update` 的 CPU 时间与 `GC Alloc`。GPU 成本则需要在目标硬件上比较状态关闭、Burning、Wet、Combined 的帧数据。

### 9.3 为什么 Rendering 可以依赖 Combat

## 十、模拟大厂面试 Q&A

### Q1：请概括这个系统，而不是只描述 Shader 画面

**回答：**我把它设计成 Gameplay、表现桥和 GPU Shader 三层。Combat 的 StatusController 是 0~100 状态权威数据源，通过带 TargetId 的 StatusChangedEvent 发布变化；Rendering 的 StatusMaterialController 归一化并平滑强度，通过 MaterialPropertyBlock 给每个 Renderer 写独立参数；统一 URP Lit Shader 保留原角色 PBR 外观，再根据 Burning/Wet 强度计算火纹、Emission、Smoothness 和 Fresnel。这样共享 Material 的多个角色仍可显示不同状态，且视觉替换不会改变战斗规则。

### Q2：为什么用 MaterialPropertyBlock，不直接修改 Material？

**回答：**修改 Shared Material 会让所有角色同时变化；`renderer.material` 会隐式创建 Material Instance。MPB 可以在共享 Material 的前提下为每个 Renderer 覆盖少量 Float。写入前我会先 `GetPropertyBlock`，只修改自己拥有的四个字段，再 Set 回去，避免覆盖受击闪红系统写入的 `_BaseColor`。我也不会声称 MPB 必然提高批处理，SRP Batcher 和 Draw Call 仍需 Frame Debugger 实测。

### Q3：燃烧火纹是怎样生成的？

**回答：**我使用 Object Space Position 构造二维噪声坐标，横向为 `x+0.37z`，纵向为 `y+time×speed`，再乘 Noise Scale。Simple Noise 输出 0~1 连续灰度；根据 BurningIntensity 的响应曲线计算 Threshold，用 Smoothstep 得到软边 Mask。Mask 一路把 Base Color Lerp 到焦灼颜色，另一路乘 HDR Burn Color 加到 Emission。Object Space 让火纹随角色移动，时间项产生向上流动。

### Q4：为什么 BurningIntensity 使用 `pow(I,0.6)`？

**回答：**线性输入在低于 0.5 时视觉不明显，主要是 Threshold 覆盖面积和人眼感知造成的非线性。我没有修改 Gameplay 数值，而是在 Shader 中使用单调 Response Curve 抬高低强度可读性。0.25 会映射到约 0.435，1 仍映射为 1，因此保持排序和上限。

### Q5：解释 Wet 的 Fresnel 公式。

**回答：**我取 World Space 的 Normal N 与 View Direction V，Normalize 后计算点积 `N·V=cosθ`。正对镜头时接近 1，轮廓处接近 0，所以 `1-saturate(N·V)` 得到边缘 Mask，再用 Power 控制宽度。最终乘 WetIntensity、EdgeStrength 和 EdgeColor。它是风格化 Fresnel；完整 Schlick 近似还会包含 F0：`F=F0+(1-F0)(1-cosθ)^5`。当前没有模拟完整双层水膜和能量守恒。

### Q6：为什么 Wet Smoothness 使用 Max？

**回答：**Wet 应提高粗糙表面的光滑度，但不应让原本比目标更光滑的金属变粗糙。我先计算 `target=max(base,wetTarget)`，再按 WetIntensity 从 Base Lerp 到 Target。这样既保留 Packed Map 的区域差异，也保证状态修改方向正确。

### Q7：Shader Graph 与 HLSL 是什么关系？为什么两者都用？

**回答：**Shader Graph 最终也会生成 Shader 代码供 GPU 执行。Graph 适合可视化数据流、观察中间 Mask；HLSL 适合封装公式、复用和代码审查。我先用节点建立 Fresnel，再用 Custom Function 调用 `StatusFresnel.hlsl` 实现相同公式，并用 Absolute Difference 比较。Custom Function 不是 C# 交互接口，C# 仍通过 MPB 向 Shader 提交参数。

### Q8：多个状态为什么不用切换 Shader？

**回答：**状态可以共存，独立 Shader 会产生 `2^N` 组合爆炸和材质切换问题。我使用统一 Shader 与四个 0~1 强度，按明确顺序组合 Base Color、Smoothness 和 Emission。当前 Burning 与 Wet 已实现，Poisoned/Sticky 只有数据接口预留。以后如果统一 Shader 成本过高，再基于 GPU 数据评估 Keyword 或分层方案。

### Q9：为什么敌人与玩家共用 Material，外观却不同？

**回答：**角色资源使用 Texture Atlas。Material 引用整张 Atlas，而 Mesh UV 决定当前三角形采样哪一块。玩家和敌人的 Mesh/UV 不同，因此共享同一 Costumes Material 也会读取不同衣服区域。状态强度则由每 Renderer 的 MPB 独立覆盖。

### Q10：这个实现最大的工程风险是什么？

**回答：**第一，自动 Renderer 缓存当前只扫描 Awake 时激活的子节点，运行时换装需要刷新或注册机制；第二，多个表现系统共享 MPB 时必须遵守字段所有权和 Get-Modify-Set；第三，统一 Shader 会增加每 Fragment 成本，状态为 0 时也可能执行部分计算；第四，多 SkinnedMeshRenderer 的 Object Space 不完全一致，火纹接缝可能需要统一 Root Space。它们都是已知边界，可以按项目规模继续演进。

### Q11：你怎样测试这个功能？

**回答：**CPU/Renderer 桥使用 PlayMode 风格的 UnityTest 验证 TargetId、Clamp、平滑、共享材质独立值、MPB 字段保留和 Disable 清理；Shader 通过 Neutral/Burning/Wet/Combined Lab Material 做中间节点与真实模型 A/B；Gameplay 验证玩家和法师/战士敌人的命中、衰减、组合与受击反馈；最后用 Frame Debugger 检查 Pass、Material Instance 和 Draw Call，用 Profiler 验证 Update 热路径与 GC Alloc。

### Q12：如果继续升级，你会做什么？

**回答：**短期会给 Poisoned/Sticky 设计与其 Gameplay 语义匹配的视觉信号，并建立状态优先级和颜色空间规则；中期会解决运行时模块化换装 Renderer 注册、统一 Root Space Noise，以及动态 Wet Normal；长期再评估 Clear Coat、自定义 BRDF、局部接触湿润 Mask 和 GPU 侧状态数据批处理。每一步先做视觉目标和 Profiler 验证，不会为了技术复杂度本身升级。

## 十一、模拟面试者从头到尾完整讲解

我在项目中实现了一套基于 Gameplay 状态强度驱动的角色表面状态可视化，第一阶段完成了 Burning 和 Wet。这个功能不是只做一个 Shader 特效，而是把现有状态系统、跨模块事件、Renderer 参数隔离和 URP Lit Shader 串成了完整闭环。

首先，我把 Combat 的 StatusController 保持为唯一权威数据源。它用 0~100 保存 Burning、Wet 等状态，负责自然衰减、燃烧 DoT 和 Wet 加速灭火。每当状态的有效百分比发生变化，它发布 StatusChangedEvent，其中包含 TargetId、StatusKind、Intensity 和 IsActive。Gameplay 不引用 Rendering，因此更换视觉方案不会影响伤害和状态反应。

随后我在 Game.Rendering 增加 StatusMaterialController，作为只读表现桥。它通过 EventBus 订阅状态事件，用当前 GameObject 的 Instance ID 过滤收件人，把 0~100 Clamp 并归一化到 0~1，再用 `MoveTowards(current,target,responseSpeed×deltaTime)` 做约 0.25 秒的视觉平滑。四种状态被放在 Vector4 中，稳定后 Update 立即返回，避免持续提交渲染参数。

为了让玩家和敌人共享 Material 但拥有独立状态，我没有修改 Shared Material，也没有调用会生成实例的 `renderer.material`，而是使用 MaterialPropertyBlock。每个 Renderer 在绘制时拥有自己的 Burning/Wet Float 覆盖。写入时先 GetPropertyBlock，再只修改状态字段并 Set 回去，因此可以与已有的受击闪红 `_BaseColor` 共存。自动化测试专门验证了两个 Renderer 引用同一个 Material 时仍能分别保持 1.0 和 0.25 的燃烧强度。

Shader 部分从 URP Lit Graph 开始，先恢复原角色的 Base Map、Normal Map、Metallic/Smoothness Packed Map、AO 与 Emission，确保无状态时外观接近原材质。角色资源采用 Texture Atlas，所以玩家和敌人即使复用四份 BodyParts、Costumes、HeadParts、Weapons Material，也会通过各自 Mesh UV 采样不同区域，不会因此穿上同一套衣服。

Burning 的核心是用 Object Space Position 构造动态 Noise Mask。我将三维位置投影成 `float2(x+0.37z, y+time×flowSpeed)`，乘 Noise Scale 后输入 Simple Noise。Object Space 让图案跟随角色；Time 项让采样持续向上流动。Noise 再经过由 BurningIntensity 控制的 Threshold 和 Smoothstep，形成软边火纹。因为线性强度在低值时不够明显，我使用 `pow(saturate(I),0.6)` 做视觉响应曲线。最终 Mask 一方面将原 Base Color 混合到焦灼 Tint，另一方面乘 HDR Burn Color 加入 Emission。Camera 的 Bloom 只负责从高亮 Emission 中提取并扩散光晕，不属于 Shader 自发光本身。

Wet 没有采用简单染蓝，而是组合三种材质线索。首先从 Packed Map Alpha 得到 Base Smoothness，使用 `max(base,wetTarget)` 保证潮湿只提高光滑度，再按 WetIntensity Lerp。其次使用 World Space 的法线 N 和视线 V，计算 `pow(1-saturate(dot(normalize(N),normalize(V))),power)`，得到正面弱、轮廓强的 Fresnel Mask。最后只加入很弱的冷色 Tint 和非 HDR Edge Color，保证状态可读但不让水膜在黑暗中自发光。

为了学习和验证节点与代码的等价关系，我先用 Shader Graph 的 Normalize、Dot Product、Saturate、One Minus 和 Power 搭出 Fresnel，再把同一公式封装到 `StatusFresnel.hlsl`，通过 Custom Function 调用。两条链用 Absolute Difference 做诊断，生产输出接 HLSL Fresnel。这样既利用 Graph 的中间 Preview，也建立了 HLSL 函数、float/half Precision 和 Coordinate Space 的基础认识。

Burning 与 Wet 位于同一个统一 Shader 中，因为状态允许共存。组合顺序是原 PBR Base Color 先进入 Burning 焦色，再进入 Wet Tint 和 Fresnel Edge；Wet 只修改 Smoothness 与 Base Color，不修改 Emission。Wet 灭火仍发生在 StatusController，Shader 只显示不断下降的 BurningIntensity，从而避免 CPU 与 GPU 各自维护一套战斗规则。

开发中我处理了多个真实问题：Unity 测试继承 `Time.timeScale=0` 导致平滑永不收敛；低 Burning 强度不可读，需要非线性响应；Time 与 Y 的符号导致火纹方向相反；Emission 绕过 Mask 导致 Burning=0 仍发光；Bloom 在 Material Preview 中不可见；Custom Function 的 `Single` 实际对应 HLSL float；节点版与 HLSL 版差值链不能误接生产输出。这些问题都使用从最终输出向输入逐层检查的方式定位，而不是随机调参数。

最终，这套系统已在受控角色、法师敌人和战士敌人上验证。它的价值不只是两个视觉效果，而是建立了一套可扩展的状态渲染架构：Gameplay 只表达状态含义，Rendering 负责数据桥接，Material 保存世界的视觉风格，Shader 负责 GPU 并行绘制。后续 Poisoned、Sticky 或元素环境效果都可以沿这条链扩展，同时继续通过 Frame Debugger、Profiler 和自动化测试控制复杂度与性能。

## 十二、读完后应真正掌握的知识

如果不看任何代码，应该能够复述下面这条主线：

```text
状态不是 Shader 自己产生的。
Gameplay 先决定“谁有多少状态”，
C# 表现桥再决定“把哪个数值交给哪个 Renderer”，
MaterialPropertyBlock 保证共享材质的角色仍有独立参数，
Shader 最后用 Noise、Lerp、Smoothstep、Dot、Power、PBR 参数
把 0~1 数值翻译成玩家看得见的 Burning 与 Wet。
```

应该能够解释以下公式，而不只是记住节点连接：

```text
归一化：I_shader = clamp(I_gameplay / 100, 0, 1)

时间平滑：current = MoveTowards(current, target, speed × deltaTime)

线性插值：lerp(a,b,t) = a(1-t) + bt

Burning 响应：I_visual = pow(saturate(I), 0.6)

Burning Mask：smoothstep(threshold-softness,
                             threshold+softness,
                             noise) × I_visual

Wet Smoothness：lerp(base,
                     max(base,wetTarget),
                     WetIntensity)

向量归一化：normalize(v)=v/|v|

点积：N·V=|N||V|cos(theta)，单位向量时等于 cos(theta)

风格化 Fresnel：pow(1-saturate(dot(normalize(N),normalize(V))),power)

Schlick Fresnel：F=F0+(1-F0)(1-cos(theta))^5
```

最后还应能明确说出当前系统没有做什么：它没有模拟真实火焰流体，没有实现真实水层折射与完整能量守恒，没有完成 Poisoned/Sticky Shader，没有保证 MPB 在所有硬件和 Renderer 组合下都提升 Batching，也没有解决任意运行时换装部件的自动注册。这些不是失败，而是 P1 为控制范围而主动保留的工程边界。
