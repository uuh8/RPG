# Task 1：开局文字玩法介绍

## 1. 功能目的与玩家体验

开局说明的目标不是堆砌操作手册，而是在玩家真正需要信息的时刻建立三个认知：这次 Run 要从 P7 前往 P8、角色如何移动与使用空中机动、法杖如何按照从左到右的顺序解释法术。最终内容采用三页结构，并使用“命运在此落笔”“让脚步先于咒语”“法杖会忠实执行你的意志”这类世界观语言承载教程信息。这样既保留沉浸感，也让按键和规则有明确落点；它和 Defeat 页的 “Fate has not spoken its final word” 属于同一种 Narrative UI 设计——功能信息仍然准确，但表达不跳出游戏世界。

引导每个 Run 自动显示一次，同时允许玩家从 Pause Menu 主动重开。自动显示负责首次 Onboarding，主动重开负责遗忘后的查阅。若只做“一生只显示一次”的 `PlayerPrefs`，开发过程中重装、换电脑、清档和版本更新都需要额外迁移；若每次进入 Scene 都显示，又会反复打断玩家。因此最终把“是否已展示”放在本次 Run 的 Session 状态里。

## 2. 数据、视图和生命周期为什么分开

核心文件：

| 文件 | 职责 |
|---|---|
| `Assets/_Project/Scripts/UI/GameplayGuideDefinition.cs` | `ScriptableObject` 数据；保存页面 Title 与 Body |
| `Assets/_Project/Scripts/UI/GameplayGuideController.cs` | 翻页、打开/关闭、按钮状态、滚动复位和 Pause 协调 |
| `Assets/_Project/Scripts/Run/Runtime/RunSessionCoordinator.cs` | 保存“本 Run 是否已展示”的 Runtime 事实 |
| `Assets/_Project/Scripts/Run/Core/RunPauseReason.cs` | 为引导分配独立 Pause Reason |
| `Assets/_Project/ScriptableObjects/P7/P7_GameplayGuide/P7_GameplayGuide.asset` | P7 三页正式文案数据 |

`GameplayGuideDefinition` 不知道 Canvas，也不调用 Pause；它只是可复用数据。`GameplayGuideController` 属于 Presentation，负责把第 N 页数据写入 Text，并响应 Previous / Next Button。`RunSessionCoordinator` 才拥有跨 Scene 的 Run 生命周期事实。这个分层遵守 Data-driven：文案调整不需要改 C#，UI 布局调整不污染 Run 状态，Run 重启时也能统一清空展示标记。

Runtime 调用链：

```text
P7 Scene 启动
  -> GameplayGuideController.Start
  -> RunSessionCoordinator.TryMarkGameplayGuideShown()
  -> 第一次返回 true
  -> RequestPause(GameplayGuide)
  -> 显示第 1 页并解锁 Cursor
  -> PreviousPage / NextPageOrClose
  -> 最后一页关闭
  -> ReleasePause(GameplayGuide)
```

独立 `RunPauseReason.GameplayGuide` 很重要。若 UI 直接写 `Time.timeScale = 0/1`，Guide 与 Wand Editor 或 Pause Menu 同时存在时，一个窗口关闭就可能错误地把另一个窗口的暂停解除。Pause Reason 相当于“谁申请了暂停”的所有权记录：只有所有原因都释放后，游戏才能恢复。

## 3. 正文超出范围为什么必须使用 Scroll View

UGUI 的 `Text` 或 TMP Text 只负责生成文字 Geometry，并不会因为父框变小就自动提供滚动。文本高度超过可视区域后，超出的部分会被裁掉；要让玩家查看完整内容，需要一个 `ScrollRect` 结构：

```text
BodyScrollView (ScrollRect)
└─ Viewport (Image + RectMask2D)
   └─ Content (VerticalLayoutGroup + ContentSizeFitter)
      └─ BodyText
```

- `Viewport` 是窗口，`RectMask2D` 只显示窗口内部的 UI Geometry；
- `Content` 是可滚动的长纸张，其高度应由正文的 Preferred Height 驱动；
- `VerticalLayoutGroup` 负责排列子项；
- `ContentSizeFitter.Vertical Fit = Preferred Size` 让 Content 随正文增长；
- `ScrollRect` 改变 Content 的 `anchoredPosition`，实现滚动。

这里常见的错误是同时让多个组件争夺同一个 RectTransform 尺寸。例如 `VerticalLayoutGroup.Child Force Expand Height` 与 `ContentSizeFitter` 配置冲突，可能出现 Layout Warning、Content 高度固定或正文被拉伸。正确思路是先明确“谁负责算高度”：本结构中 BodyText 报告 Preferred Height，Content 汇总后扩张，Viewport 只负责裁剪。

翻页时 Controller 会在布局完成后把：

```csharp
_bodyScrollRect.verticalNormalizedPosition = 1f;
```

重置为顶部。`verticalNormalizedPosition = 1` 表示顶部，`0` 表示底部。若不重置，玩家在第一页滚到底部后翻到第二页，仍会停在第二页底部，看起来像“新页面没有正文”。这是一个典型的 UI State 泄漏：页面数据换了，但滚动状态没有换。

## 4. 验收、Debug 与可继续改进项

已验收的玩家路径包括：每个 Run 首次自动出现、三页可前后翻、长正文可滚动、翻页回到顶部、最后一页关闭后恢复游戏、Pause Menu 可重新打开。

Debug 顺序应从外到内：

1. Panel 不出现：检查 Controller 是否放在始终 Active 的对象上，及 `Definition/Panel/PauseCoordinator` 引用；
2. 游戏未暂停：检查 `RunPauseReason.GameplayGuide` 是否被请求，避免直接改 `Time.timeScale`；
3. 正文被裁掉：检查 `Viewport/RectMask2D/ContentSizeFitter`，不要只扩大 Text；
4. 滚不动：检查 `ScrollRect.Content` 和 `Viewport` 引用、Vertical 勾选、Content 高度是否真的大于 Viewport；
5. 翻页停在底部：检查页面刷新后是否主动将 `verticalNormalizedPosition` 设为 `1`。

如果未来需要本地化，应将页面文本从单一字符串进一步迁移到 Localization Key；当前三页规模下，独立 SO 已经比硬编码更合适，不必提前引入完整 Localization 系统。

## 5. Standalone Build Cursor 消失：Unity 生命周期与全局状态所有权

### 5.1 症状为什么只在 Build 中稳定出现

2026-07-29 的 Windows Development Build 中，Main Menu 可以正常显示 Cursor；点击开始进入 P7 后，Gameplay Guide 正常显示并暂停游戏，但 Cursor 消失，玩家无法点击“下一页”。这证明 Canvas、Button、EventSystem 和 Guide 页面数据都已经工作，故障点不是“Guide 没打开”，而是 Guide 打开之后 Cursor 状态又被覆盖。

反向追踪所有 `Cursor.lockState` 与 `Cursor.visible` 写入点后，得到真实调用链：

```text
Main Menu
  -> DemoMainMenuController.Start
  -> CursorLockMode.None + visible=true

Scene Transition
  -> RunPauseCoordinator.PrepareForSceneTransition
  -> 保持 Cursor 解锁，避免全局状态污染新 Scene

P7 Guide
  -> GameplayGuideController.Start
  -> RequestPause(GameplayGuide)
  -> Time.timeScale=0
  -> CursorLockMode.None + visible=true

P7 Player
  -> PlayerControllerBase.Start
  -> CursorLockMode.Locked
  -> 系统 Pause Reason 仍然存在，但 Cursor 被角色脚本覆盖
```

Unity 的生命周期规则是：在 Scene 初次更新前，所有启用对象的 `Awake` 都会先于任意 `Start` 完成；但不同 GameObject 上两个 `Start` 的相对先后不应被当成业务契约。旧实现要求 Guide 的 `Start` 必须晚于 Player 的 `Start` 才正确，这就是 **Execution Order Race**。Editor 中一次运行正常不能证明顺序安全；Standalone Build 的加载、对象反序列化和执行环境差异只是把原本已经存在的竞态暴露出来。

### 5.2 为什么最终修复是“单一所有权”

`Cursor` 与 `Time.timeScale` 都是 Unity 全局状态。Player、Guide、Wand Editor、Pause Menu 如果各自直接写，就会形成 Last Writer Wins：最后执行的脚本获胜，但它不知道其他 UI 是否仍需要 Cursor。最终规则集中到 `RunPauseCoordinator`：

```text
RunPauseCoordinator.Awake
  -> Gameplay 默认：Locked + Hidden

第一个 Pause Reason 申请
  -> 保存暂停前 Time Scale
  -> TimeScale = 0
  -> None + Visible

仍有任意 Pause Reason
  -> 保持暂停与可见 Cursor

最后一个 Pause Reason 释放
  -> 恢复 Time Scale
  -> Locked + Hidden
```

`PlayerControllerBase.Start` 现在只初始化 `TargetFacing` 和 Gameplay FSM，不再拥有 Cursor。这里选择 `RunPauseCoordinator.Awake` 建立初始 Gameplay 状态，是利用可靠的生命周期边界：Coordinator 的 `Awake` 一定早于 Guide 的 `Start`；随后 Guide 申请暂停并解锁 Cursor，不会再被 Player `Start` 覆盖。

### 5.3 为什么没有采用两个看似更快的修复

**方案一：设置 Script Execution Order。** 它能让 Guide 晚于 Player，但仍保留两个模块写同一全局状态。以后 Wand Editor、Pause Menu 或新角色又可能引入新的顺序依赖；业务正确性被藏在 Project Settings 中，也不利于测试，所以拒绝。

**方案二：Guide 在 `Update` 中每帧执行 `Cursor.visible=true`。** 它会掩盖所有权冲突，并在 UI 关闭边界与其他 Panel 争抢；即使赋值本身没有显著 `GC Alloc`，逐帧写一个只在状态切换时需要改变的全局值也没有必要，所以拒绝。

# Task 2：技能文字 Tooltip

## 1. 功能目的与数据真相

Wand Editor 中的 Icon 是法术程序的“指令符号”。玩家如果只能看到图标，就必须靠试错记住 Mana、Damage、元素、Emit/Modify/Multicast 类型和特殊规则，学习成本过高。最终效果是在 PaletteContainer 与 FrameContainer 的任意法术 Icon 上悬停，无需点击就显示同一套 Tooltip；拖拽开始时隐藏，移出时隐藏。Palette 与 Frame 共用逻辑，避免同一个 Spell 在两个区域显示不同内容。

技能信息的业务真相属于 `SpellDefinition`，而不属于 Slot Prefab。数据包括 Display Name、Icon、`SpellElement`、Description，以及可从数值推导的 `SpellTraitFlags`。如果把文案硬编码在 `SpellSlotView`，每新增法术都要修改 UI 代码；放在 SO 后，设计者可以在 Inspector 中独立填写，Runtime 只读取。

## 2. 单实例 Presenter 与 Pointer 调用链

核心文件：

| 文件 | 职责 |
|---|---|
| `Assets/_Project/Scripts/Skills/SpellDefinition.cs` | 法术数据源：Icon、名称、元素、描述、Kind、数值与 Trigger 配置 |
| `Assets/_Project/Scripts/UI/ISpellTooltipHandler.cs` | Slot 与 Presenter 之间的小接口 |
| `Assets/_Project/Scripts/UI/SpellSlotView.cs` | 实现 `IPointerEnterHandler/IPointerExitHandler`，上报当前 Spell |
| `Assets/_Project/Scripts/UI/SpellTooltipPresenter.cs` | 唯一 Tooltip 实例；填充内容、跟随 Pointer、屏幕边界限制 |
| `Assets/_Project/Scripts/UI/WandEditorController.cs` | 同时给 Palette/Frame Slot 提供 Presenter，并在拖拽时隐藏 |
| `Assets/_Project/Art/Prefabs/UI/PF_SpellTooltip.prefab` | 正式 Tooltip Prefab |

Runtime 调用链：

```text
EventSystem 检测 Pointer 进入 SpellSlotView
  -> OnPointerEnter(PointerEventData)
  -> TooltipPresenter.Show(SpellDefinition, screenPosition)
  -> 写入 Icon / Name / Type / Element / Mana / Damage / Traits / Description
  -> 将屏幕坐标转换为 Canvas Local Position
  -> Clamp 到 Canvas 可见边界

Pointer 移动
  -> Presenter.UpdatePosition(screenPosition)

Pointer 离开或开始 Drag
  -> Presenter.Hide()
```

使用单实例而不是每个 Slot 一个 Tooltip，有三个好处：Hierarchy 更干净；不需要几十个 Panel 同时存在；所有定位、边界限制和样式只维护一份。Pointer Move 期间只更新位置，不应重新拼接完整文案，否则会产生不必要的字符串和 `GC Alloc`。文本在 Enter 或 Spell 改变时刷新即可。

## 3. RectTransform：为什么“同一个 Prefab”仍可能定位不同

Tooltip 跟随 Pointer 不是简单写 `transform.position = mousePosition`。UGUI 可能运行在 `Screen Space - Overlay`、`Screen Space - Camera` 或 `World Space` Canvas；`PointerEventData.position` 是 Screen Space，而 `RectTransform.anchoredPosition` 是相对 Anchor 的 Parent Local Space。必须通过：

```csharp
RectTransformUtility.ScreenPointToLocalPointInRectangle(...)
```

把屏幕坐标转换到目标 Canvas 的局部坐标，再写入 Tooltip Panel。

为了让“左上角贴着鼠标”，Panel 应使用固定 Anchor，并令 `pivot = (0, 1)`：

- Pivot X=0：定位点在左边；
- Pivot Y=1：定位点在上边；
- 因而鼠标位置对应左上角。

本功能经历了四段具有代表性的 Debug：

1. Tooltip 最初出现在屏幕左上角甚至屏幕外。根因不是 Pointer Event 没触发，而是 Panel 使用 Stretch Anchor，导致 `anchoredPosition` 的参照与预期不同。修正为固定 Anchor，并统一坐标转换。
2. P7 能显示，进入 P8 后完全不显示。根因是 P8 Scene 没有 Tooltip Prefab 实例或 `WandEditorController._tooltipPresenter` 未绑定。Prefab Asset 存在不代表每个 Scene 自动拥有实例。
3. P8 能显示后，变成 Tooltip 左中点跟随 Pointer。检查 Prefab 的 Pivot 是 `(0,1)`，说明共享 Prefab 本身正确。
4. 最终发现 P8 的 Prefab Instance Root 有 `Pos Y = 212.723` Override。同一个 Prefab Asset 在不同 Scene 中仍可拥有不同 Instance Override；这个额外 Root Offset 改变了最终坐标。把 Root RectTransform 归零后，两张地图一致。

这段经历揭示了 Unity Prefab 的重要基础：**Prefab Asset 提供默认值，Scene 中的 Prefab Instance 可以保存 Override。** “用了同一个 Prefab”只能证明默认结构相同，不能证明实例的 Transform、引用和激活状态相同。

## 4. 验收与排错清单

已验收：P7/P8、Palette/Frame、悬停无需点击、移出隐藏、拖拽隐藏、Tooltip 左上角跟随 Pointer、屏幕边缘不出界。

排错顺序：

1. EventSystem 和 Canvas `GraphicRaycaster` 是否存在；
2. Icon 上是否有会接收 Raycast 的 Graphic，是否被透明全屏 Image 阻挡；
3. Slot 是否取得同一个 `ISpellTooltipHandler`；
4. `WandEditorController._tooltipPresenter` 是否在当前 Scene 绑定；
5. Panel Anchor/Pivot、Canvas Render Mode 和 Camera 是否匹配；
6. Prefab Instance 是否有 Root Position/Scale Override；
7. Profiler 中 Pointer Move 是否出现持续字符串分配。

# Task 3：Boss Defeat 三按钮

## 1. 三种按钮不是三个文案，而是三种运行范围

失败页最终保留沉浸式文案，并提供：

- `Retry Boss`：只重置 P8 Boss Encounter，保留这次 Run 已经获得的法术与状态；
- `Restart Run`：从 P7 开始一轮全新的 Run，清空 Run 级进度；
- `Return To Main Menu`：结束当前 Run，回到主菜单。

这三者的关键不是 Button Label，而是 **Reset Scope**。如果三个 Button 最终都调用同一个 Scene Reload，它们即使写着不同文字，也只是视觉上的三个按钮。正确实现必须让 `RunSessionCoordinator` 或相应导航入口明确区分“只重开 Encounter”“重建整个 Run”“离开 Run”。

## 2. Runtime 调用与架构边界

UI Button 只发送意图，不自己清空所有系统：

```text
DefeatPanel Button.onClick
  -> BossHUDController / Run Navigation 方法
  -> RetryBoss：重建或重载 P8 Encounter
  -> RestartRun：创建新 Run 并进入 P7
  -> ReturnToMainMenu：结束 Run 并加载 Main Menu
```

UI 不应直接枚举 Spell、HP、Boss 和 Scene 对象逐个复位，因为它不知道 Run 状态的完整所有权。统一交给 Run 层可以避免漏清一个字段，也便于以后加入 Save/Load。

## 3. 验收与 Debug

三个按钮均已在 P8 实际验收。排错时不要只看跳到了哪张 Scene，还要检查：

- Retry Boss 后 Wand Program 与本 Run 数据是否保留；

# Task 4：Boss Phase 粒子表现

## 1. 为什么 VFX 位置不能只由 Controller 的三个字段决定

Phase 2 的效果位于 Boss 法杖，Phase 3 的效果位于 Boss 身体，这说明它们没有统一的空间基准。如果把两个 Prefab 都直接作为 Boss Root 子物体，并假设 Local Position `(0,0,0)` 就正确，法杖特效会停在角色原点，且不会随手部 Bone 的动画移动。最终使用 **Socket**：

```text
Boss
├─ BossVisual / Skeleton
│  └─ Hand Bone
│     └─ Active Wand
│        └─ Phase2WandVfxSocket
│           └─ phase2 Loop VFX
└─ Phase3BodyVfxSocket
   └─ phase3 Loop VFX
```

Socket 是一个空 GameObject，它保存“这个效果相对挂点的 Local Position / Local Rotation / Local Scale”。Phase 2 Socket 应位于实际使用的法杖或手部 Bone 下，因而能随 Animator 的 Bone Transform 更新；Phase 3 Socket 可以在身体中心附近。每个阶段独立 Socket 的意义在于：Controller 只决定**什么时候显示**，Socket 决定**在哪里显示**，VFX Prefab 决定**显示什么**。

## 2. 事件驱动与互斥显示

`BossPhaseVfxController` 属于 Presentation。它按 Boss 的 `HealthComponent.Id` 过滤 Phase Event，避免场景中其他实体的 Event 误触发。收到阶段变化后，对预置的 Root 执行互斥 `SetActive`：

```text
Boss HP 到达阈值
  -> Boss Gameplay 发布 Phase Changed Event
  -> BossPhaseVfxController 过滤 Boss Id
  -> Phase 1：Phase2 Off，Phase3 Off
  -> Phase 2：Phase2 On，Phase3 Off
  -> Phase 3：Phase2 Off，Phase3 On
```

没有为每次 Phase 切换动态 `Instantiate/Destroy`，因为整阶段 Loop VFX 适合预置并切 Active：逻辑直观，不会在切阶段瞬间产生实例化峰值，也容易在 Prefab Mode 调位置。代价是对象从开局就存在于内存中；目前只有两个 VFX，成本可以接受。

## 3. 粒子坐标空间基础

Particle System 的 Simulation Space 决定粒子出生后如何跟随：

- `Local`：已发射粒子继续跟随父 Transform，适合贴附法杖的光环；
- `World`：粒子出生后留在世界位置，适合拖尾、烟雾或撒落火星；
- `Custom`：相对指定 Transform 模拟。

“发射器要跟随法杖”和“已经发出的粒子要跟随法杖”是两个问题。即使 VFX GameObject 放在 Bone 下，若 Simulation Space 是 World，旧粒子仍会留在世界空间；这不一定是 Bug，而是视觉设计选择。还需检查 Local Scale、Renderer Bounds 和 Culling，避免 Boss Teleport 后效果不见。

已验收：Phase 1 无额外效果，Phase 2 法杖效果位置正确，Phase 3 身体效果正确，阶段间互斥且能跟随 Boss。

# Task 5：P7 / P8 场景 BGM

## 1. 为什么当前选择 Scene-local MusicRoot

P7 与 P8 各有一个 `MusicRoot`，包含 `AudioSource` 和 `SceneMusicController`：

```text
P7 Scene / MusicRoot -> BGM_P7_Exploration.mp3
P8 Scene / MusicRoot -> BGM_P8_Boss.mp3
```

当前只有两个顺序加载的场景，不需要跨场景无缝 Crossfade，因此 Scene-local 方案比全局 `DontDestroyOnLoad` Audio Manager 更简单、更不易叠音。Scene 卸载时旧 AudioSource 自然销毁，新 Scene 启动后播放自己的 Clip。若同时使用 Scene-local 与 `DontDestroyOnLoad`，最常见的结果是进入 P8 后两首 BGM 一起播放，所以本阶段明确不额外持久化。

## 2. AudioSource 与 Import Settings

`SceneMusicController` 在 `Awake` 中统一设置：

- `playOnAwake = false`：先完成 Controller 配置，再在 `Start` 主动播放；
- `loop = true`：BGM 循环；
- `spatialBlend = 0`：2D Audio，不受玩家和声源距离影响；
- Clip 与 Volume 来自 Inspector。

正式资源位于：

- `Assets/_Project/Art/Audio/BGM/BGM_P7_Exploration.mp3`
- `Assets/_Project/Art/Audio/BGM/BGM_P8_Boss.mp3`

长音乐使用 `Load Type = Streaming`，Unity 播放时持续从磁盘读取较小缓冲，而不是把完整解压 PCM 长驻内存。它降低长音频的内存占用，但增加少量磁盘 I/O 与解码成本。`Vorbis` 是适合 BGM 的有损压缩，质量设为约 0.7；`Load In Background` 避免主线程同步等待完整资源准备。短而频繁的 SFX 通常更适合 `Decompress On Load`，不能把 BGM 的导入方案机械套用到所有声音。

本阶段没有做 Fade/Crossfade。若未来场景切换需要无缝音乐，才应引入持久化 Music Service、双 AudioSource 交叉淡入淡出和 AudioMixer Snapshot。当前遵守 YAGNI：先满足两个独立场景且无叠音的真实需求。

## 3. 验收和 Audio Debug

已验收：P7 播放探索 BGM，进入 P8 后旧曲停止并播放 Boss BGM，循环正常，无明显叠音。

若没有声音，依次检查 Clip、Mute、Volume、`AudioListener.volume`、场景中是否存在且只存在一个有效 AudioListener、AudioSource 是否真的 `isPlaying`。若出现叠音，搜索所有 AudioSource、`DontDestroyOnLoad` 对象和 Scene 重复实例；若出现爆音或加载延迟，再使用 Audio Profiler 观察 Voice、DSP CPU 和 Streaming。

# Task 6：Wizard 二段跳

## 1. 二段跳本质是“空中动作预算”

“二段跳”不是检测按了两次 Space，而是角色离地后拥有一次额外 Jump Consumption。若直接写 `if (jumpCount < 2)`，以后加入 Buff、不同角色或三段跳时会把角色能力写死在 State 中。最终使用纯 C# `PlayerAirActionBudget`，保存：

- 最大额外跳跃次数；
- 当前剩余额外跳跃次数；
- 最大空中冲刺次数；
- 当前剩余空中冲刺次数。

每次稳定进入 Grounded 时 `ResetForGrounded()`；空中按 Jump 时 `TryConsumeExtraJump()`。这个类不继承 `MonoBehaviour`，不依赖 Unity Scene，因此可用 EditMode Test 精确验证预算边界。

## 2. FSM 调用链与 Jump Buffer

```text
PlayerControllerBase Input 回调
  -> JumpBufferCounter = JumpBufferTime
  -> Update 递减计时器
  -> PlayerAirborneState 检查待消费 Jump
  -> PlayerAirActionBudget.TryConsumeExtraJump()
  -> VerticalVelocity = JumpForce
  -> 清空 Jump Buffer
```

Input callback 不直接让角色跳，因为回调发生时角色可能处于 Attack、Dash 或着陆前的临界帧。统一 Buffer Counter 后，FSM 在自己的优先级中消费输入，避免低帧率或状态切换吃键。

第一次从 Grounded 起跳不消耗“额外跳跃”；只有 Airborne 中再次起跳才消耗。落地后预算恢复。若在斜坡或边缘反复 Grounded/Airborne 抖动，要确保只有可信的落地状态重置预算，否则可能在墙边无限刷新。

## 3. 设计取舍与验收

第一版额外跳沿用 `JumpForce`，手感一致，但代码保留独立能力边界，未来可以增加 `ExtraJumpForce`、VFX 或不同 Animator State。共享能力写在 `PlayerControllerBase` 与公共 State，而角色差异由 Inspector 数值控制：Wizard 配置一次额外跳跃，其他角色可设为 0。这样不是把 Wizard 规则硬编码进 `PlayerAirborneState`。

已验收：离地后可再跳一次、第三次无效、落地恢复、Coyote Time 与 Jump Buffer 不被破坏、空中攻击和落地转换正常。

# Task 7：Wizard 空中冲刺

## 1. 与地面 Dash 共用运动状态，但不共用表现

Air Dash 和 Ground Dash 都需要锁定方向、持续时间、速度、冷却与 `CharacterController.Move`，所以继续复用 `PlayerDashState`；但它们使用不同 Animator State Hash。`PlayerControllerBase` 在 `Awake` 中对 `_dashStateName` 与 `_airDashStateName` 只做一次 `Animator.StringToHash`，避免每帧字符串查找。Wizard 的空中动画为 `AirDashForward_MagicWand`。

Airborne Transition Priority 中，合法的 Dash Input 会先尝试消耗 `TryConsumeAirDash()`。每次滞空只有一次预算，落地与额外跳跃预算一起重置。Dash Buffer 与 Air Dash Budget 是两个概念：

- Buffer 表示“玩家刚才是否按过，短时间内仍允许 State 消费”；
- Budget 表示“这一轮滞空是否还有使用次数”；
- Cooldown 表示“技能在时间上是否解锁”。

三者分开后，规则更清晰，也能分别测试。

## 2. 竖直速度的最终策略

最终实现不是进入 Air Dash 时把 `VerticalVelocity` 永久清零。Air Dash 期间传给 `CharacterController.Move` 的 `velocity.y` 为 0，所以角色在 Dash 的短时间内不升不降；但进入前保存于 Controller 的 `VerticalVelocity` 没有被覆盖。Dash 结束回到 Airborne 后，重力从原有速度继续积分。

```text
进入前正在上升 VerticalVelocity = +4
  -> Air Dash 期间实际 y 位移 = 0
  -> 退出后仍从约 +4 继续，随后受 Gravity 下降
```

这样能保留玩家进入 Dash 前的跳跃阶段，避免每次 Air Dash 都强制变成从零开始下落。另一种方案是把 `VerticalVelocity = 0`，手感会更“重”、更可预测；两者都合理，但必须明确。当前代码选择“冻结位移、保留状态”，本文以实际最终实现为准。

## 3. Animator 常见误区

代码通过 `Animator.CrossFadeInFixedTime` 直接进入 Air Dash State，所以 Animator Controller 不需要一条进入 AirDash 的 Transition；但 AirDash State 仍需要正确的 Exit Transition。C# 结束的是 Gameplay FSM，它不会自动把 Animator 播回 Idle/Jump。若动画卡在最后一帧，应先检查 Animator State 的 Has Exit Time 与 outgoing transition，而不是怀疑 Dash Timer。

已验收：地面使用原 Dash 动画，空中使用独立动画；一次滞空只能 Air Dash 一次；落地刷新；Dash 后回到 Grounded 或 Airborne；无无限刷新与动画卡死。

# Task 8：扩展 CastEvaluator——完整法术编程系统解析

## 1. 为什么这是玩法层改动，而不是一次 Parser 修补

法杖系统的核心比喻是：**Wand 是 Program，Spell 是 Instruction，CastEvaluator 是 Interpreter，EmitCommand 是解释后的执行命令。** 玩家在 FrameContainer 中排列法术，不是在选择一个预制“技能组合”，而是在编写一小段从左到右执行的程序。`Modify` 改变后续指令的参数，`Multicast` 改变一次 Cast 能抽取多少个 Action，`Trigger` 把另一段 Action 捕获为 Payload，并在碰撞或计时条件满足后执行。

旧实现把 Trigger 后面的整个 Wand Suffix 当 Payload，虽然能实现“命中后再释放”，却无法稳定表示并行 Trigger：

```text
Triple
Trigger
Meteor
Trigger
Meteor
Trigger
Meteor
```

如果第一个 Trigger 吞掉后面所有 Spell，外层 Triple 就只得到一个 Trigger；玩家看到的是“三连发 + 三个 Trigger”，Runtime 却不是三个并行触发器。这不是单个数值 Bug，而是语言语义不完整。Task 8 的关键成果是定义了可递归的 **Action Boundary**：每个 Trigger 只捕获紧随其后的一个完整 Action；这个 Action 内部可以包含 Modifier、Multicast、普通 Emit，甚至另一个 Trigger。

## 2. 三层结构：Data、Pure Evaluation、Unity Runtime

### 2.1 Game.Skills：数据与纯解释器

| 文件 | 职责 |
|---|---|
| `SpellDefinition.cs` | 一条 Spell Instruction 的 SO 数据 |
| `SpellKind.cs` | `Emit / Modify / Multicast / StaticProjectile` 与 Spawn Mode |
| `PayloadTriggerMode.cs` | `None / OnImpact / AfterDelay` |
| `WandLoadout.cs` | Spell 数组与 `BaseDraws`，即 Program |
| `CastModifierState.cs` | 当前 Modifier 的不可变 Value Snapshot |
| `EmitCommand.cs` | 纯输出命令，不持有 Scene Object |
| `CastEvaluator.cs` | 左到右解释、Action 边界、Mana、Payload 捕获和安全上限 |
| `Diagnostics/CastTrace*` | Editor/Development Build 的逐步解释 Trace |

`Game.Skills` 可以引用 Unity 的 `ScriptableObject`、Prefab/AudioClip 数据类型，但 `CastEvaluator` 不调用 `Instantiate`、Physics 或 Scene API。它接收输入集合并填充输出 List，因此核心语义可以在 EditMode 中测试。

### 2.2 Game.Character：SpellCaster Runtime Bridge

`SpellCaster` 知道施法点、方向、Team、Collider、Projectile 和 Scene，因此它属于 `Game.Character`。它把纯 `EmitCommand` 翻译成 Unity 对象：

```text
EmitCommand
  -> Instantiate Projectile Prefab
  -> Init attacker/team/damage/speed/direction
  -> 配置 Gravity / Bounce / Homing / Orbit
  -> 绑定 OnImpact 或 AfterDelay Payload
```

这个 Bridge 让 `Game.Skills` 不依赖 `Game.Combat` 的具体 Projectile Runtime，也让 `Game.Combat` 不反向依赖法术语言。

### 2.3 Game.Combat：通用命中事实

`ProjectileBase` 只发布通用 `Impacted(hitPoint, hitDirection)` 与 `TimedTriggerElapsed(...)` 通知。它不知道 Payload 是 Meteor、Fireball 还是另一个 Trigger。`SpellCaster` 订阅这些通知后继续解释 Payload。这正是单向依赖：

```text
Game.Skills 纯数据/规则
      ↓
Game.Character Runtime Bridge
      ↓
Game.Combat Projectile / Damage Funnel
```

Combat 不知道 Skills，因此以后弓箭、敌人投射物也能继续使用同一 Projectile 基础设施。

## 3. 法术语言的四类 Instruction

### 3.1 Emit

`Emit` 消耗一份 Draw Budget，并生成一条 `EmitCommand`。命令包含 Prefab、最终 Damage、Speed、DamageType、Spread、Bounce、Gravity、Motion Mode、SFX，以及可选 Trigger Payload。

### 3.2 StaticProjectile

它在 Draw 语义上也属于“生成一个结果”，所以同样消耗一份 Draw；区别主要在 Spawn Mode，例如 `StaticAtPoint` 生成 Shield，或 `SkyfallAtPoint` 在目标点上空生成 Meteor。

### 3.3 Modify

`Modify` 不消耗 Draw，而是改变当前 `CastModifierState`，只影响它之后被解释的 Emit。典型合并规则：

- Flat Damage 使用加法；
- Damage Multiplier 和 Speed Multiplier 使用乘法；
- Spread、Bounce 使用加法；
- Gravity 等布尔能力使用 OR；
- Homing / Orbit 这种主 Motion Mode 冲突时，后出现的有效主模式覆盖前者。

例子：

```text
DamageUp
Fireball
```

在 `BaseDraws = 1` 时仍能生成一颗强化 Fireball，因为 Modify 不占 Draw。

反例：

```text
Fireball
DamageUp
Fireball
```

`BaseDraws = 1` 时第一颗 Fireball 已耗尽预算，后面的 Modifier 与第二颗 Fireball 根本不会进入当前 Cast。Modifier 不是“全局扫描后应用到所有弹丸”，顺序就是玩法。

### 3.4 Multicast

`Multicast` 不直接生成 Projectile，也不消耗 Draw；它把 `ExtraDraws` 加入当前 Action 的预算。Triple 的作用近似：

```text
drawBudget = 1
读到 Triple：drawBudget += 2
随后允许三个 Emit 各消耗 1
```

本系统是 Single-pass、No Shuffle、No Wraparound。Wand 读到末尾后，即使预算还有剩余也会结束，不会自动绕回开头。这使结果可预测，也避免无意无限循环。

## 4. Evaluate：一次解释必须维护哪些状态

`CastEvaluator.Evaluate` 的核心局部状态是：

| 状态 | 含义 |
|---|---|
| `i` | 当前读取 Spell 的 Cursor |
| `drawBudget` | 当前层还允许产生多少个 Emit |
| `manaLeft` | 当前层剩余 Mana |
| `mods` | 到当前位置为止累计的 Modifier Snapshot |
| `output` | 已生成的 `EmitCommand` |

可读化伪代码如下：

```text
清空 output
drawBudget = BaseDraws
mods = incomingMods
manaLeft = availableMana
i = 0

while i 未到末尾
  and drawBudget > 0
  and output.Count < 64:

    spell = spells[i]

    if spell 为 null:
        i++
        continue

    if 当前层 Mana 不足:
        标记 Fizzle
        break

    if Modify:
        扣 Mana
        mods = mods.Apply(spell)
        i++

    if Multicast:
        扣 Mana
        drawBudget += ExtraDraws
        i++

    if Emit / StaticProjectile:
        扣 Mana

        if 是 Trigger:
            payloadStart = i + 1
            payloadEnd = FindActionEnd(payloadStart)
            payload = CaptureRange(payloadStart, payloadEnd)
            i = payloadEnd
        else:
            payload = Empty
            i++

        output.Add(BakeEmit(spell, mods, payload))
        drawBudget--
```

这里最容易忽略的点是 Trigger 捕获 Payload 后，外层 Cursor 必须跳到 `payloadEnd`。否则 Payload Spell 会既被捕获一次，又被外层再次执行，形成重复发射。

## 5. Action 到底是什么

本系统没有先构建 AST，而是用 `FindActionEnd` 在扁平 Spell Array 中计算边界。一个 Action 的定义为：

> 从某个 Cursor 开始，以 `Draw Budget = 1` 解释；Modifier 不消耗预算，Multicast 增加预算，Emit/StaticProjectile 消耗一份预算；遇到 Trigger 时，该 Trigger 在当前 Action 中只算一个 Emit，但 Cursor 递归越过它自己的一个 Payload Action。当前 Action 的预算耗尽时，边界结束。

`FindActionEnd` 的伪代码：

```text
FindActionEnd(spells, start, depth):
    if depth >= 16:
        return 安全边界

    cursor = start
    drawBudget = 1

    while cursor 未到末尾 and drawBudget > 0:
        spell = spells[cursor]

        if null:
            cursor++

        else if Modify:
            cursor++

        else if Multicast:
            drawBudget += ExtraDraws
            cursor++

        else if Emit / StaticProjectile:
            drawBudget--
            cursor++

            if spell 是 Trigger:
                cursor = FindActionEnd(spells, cursor, depth + 1)

    return cursor
```

这个函数只找结构边界，不生成 Projectile、不应用 Damage，也不真正执行 Payload。它类似 Parser 中的“读完一个 Expression”，而 `Evaluate` 类似 Interpreter 中的“求值”。

## 6. 关键例子一：三个并行 Trigger 各自携带 Meteor

Program：

```text
0 Triple
1 TriggerFireball
2 Meteor
3 TriggerFireball
4 Meteor
5 TriggerFireball
6 Meteor
```

假设 `BaseDraws = 1`。

| 外层步骤 | Cursor | 外层 Draw Budget | 发生什么 |
|---|---:|---:|---|
| 开始 | 0 | 1 | 准备读取 |
| Triple | 0 -> 1 | 3 | ExtraDraws=2 |
| Trigger 1 | 1 | 3 | 自己消耗一份外层 Draw |
| `FindActionEnd(2)` | 2 -> 3 | — | Meteor 是一个完整 Payload Action |
| 输出 Trigger 1 | 3 | 2 | Payload 只含 Meteor 1 |
| Trigger 2 | 3 | 2 | 再捕获位置 4 的一个 Action |
| 输出 Trigger 2 | 5 | 1 | Payload 只含 Meteor 2 |
| Trigger 3 | 5 | 1 | 再捕获位置 6 的一个 Action |
| 输出 Trigger 3 | 7 | 0 | Payload 只含 Meteor 3，外层结束 |

最终外层输出是三个独立 Trigger Projectile。每颗命中时，`SpellCaster` 分别执行自己捕获的 Meteor Payload。这正是 Task 8 修复前无法稳定表达的目标。

## 7. 关键例子二：一个 Trigger 的 Payload 内部使用 Triple

Program：

```text
0 Orbit
1 TriggerFireball
2 Triple
3 Fireball
4 Fireball
5 Fireball
```

外层 `BaseDraws = 1`：

1. Orbit 是 Modify，写入 `mods`，不消耗 Draw；
2. TriggerFireball 消耗外层唯一一份 Draw；
3. `FindActionEnd(2)` 从 Payload 开始，以预算 1 读取；
4. 读到 Triple 后预算变为 3；
5. 三个 Fireball 分别消耗预算；
6. Payload 边界落在数组末尾。

外层只生成一颗 TriggerFireball，但它携带 `[Triple, Fireball, Fireball, Fireball]`。命中后 Payload 以 `BaseDraws = 1` 重新 Evaluate：Triple 扩展预算，生成三颗 Fireball。由于 Trigger 在捕获时还保存了 `PayloadModifiers = Orbit Snapshot`，这三颗 Payload Fireball 继承 Orbit。

这说明“外层 Multicast 产生多个 Trigger”和“Payload 内 Multicast 产生多个 Payload Emit”是两种不同层级：

```text
Triple -> Trigger -> Meteor ...   = 外层有多个 Trigger
Trigger -> Triple -> Fireball...  = 一个 Trigger 命中后产生多个 Fireball
```

顺序变化就会改变程序结构，这是法术编程的可玩性来源。

## 8. 关键例子三：嵌套 Trigger 与递归

```text
OuterTrigger
InnerTrigger
Meteor
```

外层 Evaluate：

1. OuterTrigger 捕获从 InnerTrigger 开始的一个 Action；
2. `FindActionEnd` 遇到 InnerTrigger；
3. InnerTrigger 在这一层消耗一个 Draw，但函数递归越过它自己的 Payload Action；
4. Meteor 成为 InnerTrigger 的 Payload；
5. 因而 OuterTrigger Payload 是 `[InnerTrigger, Meteor]`。

Runtime：

```text
OuterTrigger 命中
  -> Evaluate [InnerTrigger, Meteor]
  -> 生成 InnerTrigger，Payload=[Meteor]
  -> InnerTrigger 命中
  -> Evaluate [Meteor]
  -> 生成 Meteor
```

每次递归的 Payload 都是原 Program 中更靠后的严格切片，因此自然越来越短，不会重新读取整个 Wand。这个“严格缩短”是终止性不变量。

## 9. Modifier Snapshot：为什么 Trigger 命中后仍保留原来的强化

`CastModifierState` 是 `readonly struct`。每次 `Apply` 返回一个新值，而不是让所有 Projectile 共享一个可变 Modifier 对象。`BakeEmit` 把当前最终 Damage、Speed 等数值写进 `EmitCommand`，同时把 Trigger Payload 应继承的 Modifier Snapshot 保存下来。

Snapshot 的意义是时间解耦。Trigger Projectile 可能几秒后才命中；期间玩家可能编辑 Wand、切换装备或施放另一套 Modifier。如果命中时再回头读取当前 Wand，就会产生“子弹发射时是一套规则，命中时突然变成另一套规则”的 Temporal Coupling。Value Snapshot 保证发射瞬间已经决定的事实不会漂移。

伤害示意：

```text
finalDamage = (BaseDamage + DamageAddFlat) * DamageMultiplier
finalSpeed  = BaseSpeed * SpeedMultiplier
```

Spread、Bounce、Gravity、Homing、Orbit 等同样在 EmitCommand 中快照。`SpellCaster` 只消费结果，不重新解释 Modifier 的先后顺序。

## 10. Mana 为什么按“当前层”支付

`SpellCaster.RunCast` 先调用 `CastEvaluator.EstimateManaCost` 估算当前将被执行的一层 Action，再尝试从 `ManaComponent` 扣除。玩家 Mana 不足时，当前层整体不开始，避免已经发出一半 Projectile 后才 Fizzle。Boss 可以通过 `IgnoreMana` 使用同一程序但不受玩家资源限制。

Trigger Payload 的 Mana 不在外层发射时预付，而是在 Trigger 真正执行时支付：

```text
施放 Trigger
  -> 支付 Trigger 当前层成本
  -> Projectile 飞行
  -> 若命中，Payload RunCast
  -> 届时估算并支付 Payload 当前层成本
```

这样没有命中的 Trigger 不会无条件预付 Payload。`EstimateManaCost` 必须和 `Evaluate` 使用相同 Action Boundary 与 Cursor 跳转；若两者语义不一致，就会出现“估算说够，执行却 Fizzle”或“多扣 Mana”。因此 Estimate 不是随便遍历整个数组求和。

这里存在一个设计选择：Noita 类游戏也可能在初次施放时一次性收取完整嵌套成本。当前系统采用 Layer-by-layer Payment，它已被 Runtime 和测试共同定义；若以后改变，必须同步修改 Estimate、Evaluate、UI Preview 和测试，而不能只改一个扣蓝位置。

## 11. SpellCaster 如何把 EmitCommand 变成可见结果

完整 Runtime 调用链：

```text
WizardController 捕获鼠标按下瞬间的 ClickAimPoint
  -> 将一次 Cast 放入输入队列
  -> PlayerWizardAttackState 进入施法动画
  -> 到 AttackDefinition.ArrowSpawnTime
  -> SpellCaster.CastWand(...)
  -> ResolveWand：优先 RunSpellSession Runtime Clone，回退 Inspector Wand
  -> RunCast
     -> EstimateManaCost
     -> Mana Preflight
     -> CastEvaluator.Evaluate 填充复用的 _emits List
     -> 遍历 EmitCommand
        -> ForwardProjectile
        -> StaticAtPoint
        -> SkyfallAtPoint
        -> WirePayload
  -> ProjectileBase.Init
  -> Physics 飞行与碰撞
  -> IDamageable.ReceiveHit(in DamageRequest)
```

三种 Spawn Mode：

- `ForwardProjectile`：从施法点沿 Aim Direction 生成普通 Projectile；
- `StaticAtPoint`：在目标点生成 Shield、Field 等静态对象；
- `SkyfallAtPoint`：先确定地面落点，延迟后在上方生成 Meteor。

`WirePayload` 根据 Trigger Mode 工作：

```text
OnImpact
  -> 订阅 ProjectileBase.Impacted
  -> 命中时 RunCast(payload, baseDraws=1, payloadMods, hitPoint, hitDirection, depth+1)

AfterDelay
  -> 订阅 TimedTriggerElapsed
  -> ArmTimedTrigger(delay)
  -> 到时在当前位置和方向 RunCast(...)
```

这里使用的 lambda 会为带 Payload 的离散 Projectile 建立回调，它不是每帧 hot path 分配；在当前施法频率下可接受。若以后进行 Projectile Pooling 或每秒数百 Trigger 的压力测试，应把订阅生命周期、闭包分配和归还 Pool 时的事件清理作为重点。

## 12. 安全边界：为什么递归仍然需要硬上限

严格更短 Payload 已经提供逻辑收敛，但工程上仍保留：

- `MaxActionDepth = 16`：防御异常数据、未来语义变化或错误递归；
- `MaxEmitCommands = 64`：限制单层输出，防止极端 Multicast 造成一帧大量实例化；
- `MaxRuntimeTriggerDepth` 与 Evaluator 深度一致：Runtime 不允许无限 Trigger 链；
- No Wraparound：到数组末尾就结束；
- null Spell 安全跳过；
- Payload 为空时 Trigger Mode 退化为 None，不制造无意义回调。

注意 `MaxEmitCommands = 64` 是**单层命令上限**，不是整个递归树的严格全局 Projectile 上限。一个 Trigger 层可以在未来产生下一层；真实最坏规模还受每层上限、深度、Mana、碰撞是否发生和 Program 长度共同影响。若作品进入高并发阶段，需增加整次 Cast Tree 的共享 Global Budget，而不是误以为单层 64 已经解决所有爆炸式增长。

## 13. 性能：纯解释很便宜，真正昂贵的通常是 Runtime Spawn

本系统已有 Profiler Marker：

- `Spell.Evaluate`：纯解释器；
- `Spell.RuntimeSpawn`：实例化与 Runtime 配置；
- `Projectile.Motion`：Projectile 每帧运动。

`CastEvaluator` 的循环是线性的；Trigger 边界会递归扫描子 Action，但 Program 长度目前很短。Payload `CaptureRange` 会建立新的 Spell 引用列表，这是每次离散 Cast 的一次性分配，不在 `Update/FixedUpdate` hot path；输出 List 由 `SpellCaster` 复用。真正更可能出现尖峰的是 `Instantiate` 多个 Projectile、VFX、Collider/Physics 注册和后续粒子渲染。

优化顺序应以证据为准：

1. 用 `Spell.Evaluate` 判断纯解释是否真是瓶颈；
2. 用 `Spell.RuntimeSpawn` 观察并发 Projectile 的实例化成本；
3. 检查 Timeline 中的 `GC.Alloc` 来源；
4. 若 Spawn 占主导，再引入 Projectile/VFX Pool；
5. 若 Evaluate 占主导，再考虑预编译 Action Boundary 或缓存 Program AST。

不能一开始就把 Wand 编译成复杂 AST 并维护增量缓存。当前玩家可以在 Wand Editor 修改 SO/Runtime Clone，扁平 Array + 边界函数更容易理解、测试和调试；只有 Profiler 证明必要时才增加缓存失效复杂度。

## 15. Cast Trace：调试解释器时不要只看最终 Projectile

最终 Projectile 数量不对时，只看 Scene 很难分辨是 Evaluator 边界、Mana、Spawn、Physics 还是碰撞问题。`CastTraceCollector` 在 Editor/Development Build 中记录解释步骤，可回答：

- Cursor 当前在哪；
- 读到了哪种 SpellKind；
- Draw Budget 如何变化；
- Modifier 在何时应用；
- Trigger 捕获的 Payload Start/End；
- 为什么 Fizzle 或达到上限。

推荐 Debug 分层：

```text
第一层：WandLoadout 数据是否按预期排列
第二层：CastTrace / CastEvaluator output 是否正确
第三层：SpellCaster 是否遍历并 Spawn 每条 EmitCommand
第四层：Projectile Init 参数、Collider、Layer、Team 是否正确
第五层：Impacted / TimedTriggerElapsed 是否触发
第六层：Payload RunCast 的 depth、Mana、origin、direction 是否正确
第七层：DamageRequest 是否到达 HealthComponent
```

如果 Evaluator 已输出三条 Trigger Command，而 Scene 只有两颗 Projectile，问题在 Runtime Spawn 或 Prefab；如果只输出一条，才回到 Action Boundary。这样可以避免在错误层级反复调 VFX 或 Collider。

## 16. 为什么没有采用其他方案

### 16.1 为每种组合写专用代码

例如看到 `Triple + Trigger + Meteor` 就进入一个硬编码分支。优点是短期快，缺点是组合数量呈指数增长，玩家换顺序后立即失效，也背离 Noita-like 玩法。最终拒绝。

### 16.2 Trigger 永远捕获整个剩余 Suffix

实现最简单，也适合最早 MVP；但无法表达并行 Trigger，且第一个 Trigger 容易吞掉后续结构。Task 8 正是对此的扩展。

### 16.3 Trigger 只捕获紧随其后的一个 Spell

能解决部分问题，却会把 `Trigger -> Triple + 3 Fireball` 错切成只有 Triple。Multicast 和 Modifier 是 Action 的组成部分，不是独立 Payload 结果，因此必须捕获一个完整 Action。

### 16.4 先编译为完整 AST

AST 能让结构更显式，也便于做 Preview 和复杂语言特性；代价是 Parser、节点类型、缓存、编辑失效和序列化复杂度显著增加。当前扁平数组与 `FindActionEnd` 已能清晰表达所需语义，并有严格上限，因此保留更小实现。未来若加入 Conditional、Loop、Random、Branch，再评估 AST。

## 17. 面试式总结：如何讲清整个系统

可以这样回答：

> 我把法杖设计成一个 Data-driven 的小型解释器系统。`WandLoadout` 是按顺序排列的 Program，`SpellDefinition` 是 Instruction。`Game.Skills.CastEvaluator` 是纯逻辑层，它维护 Cursor、Draw Budget、Mana 和不可变的 Modifier Snapshot，输出不依赖 Scene 的 `EmitCommand`；`Game.Character.SpellCaster` 是 Runtime Bridge，负责把命令变成 Projectile、Static Field 或 Skyfall，并通过 `Game.Combat.ProjectileBase` 的通用 Impact/Timer 通知递归执行 Trigger Payload。  
>   
> Task 8 的关键是把 Trigger Payload 从“整个剩余 Suffix”改成“紧随其后的一个完整 Action”。Action 以 Draw Budget=1 开始，Modifier 不占 Draw，Multicast 扩充 Draw，Emit 消耗 Draw；遇到嵌套 Trigger 时递归越过它自己的一个 Payload Action。这样外层 Triple 可以抽出三个并行 Trigger，而 Trigger 内部的 Triple 又可以产生三个 Payload Projectile。Payload 是严格更短的后续切片，并有 16 层递归和每层 64 条输出上限。Modifier 和伤害等使用 Value Snapshot，保证 Projectile 命中时不会受后来编辑 Wand 的影响。  
>   
> 架构上 Skills 只做纯规则，Character 负责 Unity Runtime，Combat 保持不知道法术系统的单向依赖。测试覆盖并行 Trigger、内部 Multicast、嵌套缩短、Mana 当前层支付和 Runtime Bridge；Profiler 用 `Spell.Evaluate`、`Spell.RuntimeSpawn` 与 `Projectile.Motion` 区分解释成本和实例化/运动成本。

如果能够解释清楚“Action Boundary 为什么存在”“为什么 Snapshot”“为什么 Combat 不引用 Skills”“为什么单层上限不是全局上限”，就不只是会调用 Unity API，而是真正理解了玩法系统、语言语义、架构边界和工程安全性。

# 阶段收口结论

P8-B 的八项需求已经形成完整的双场景体验：Guide 负责首次认知，Tooltip 负责即时查阅，Defeat 三按钮明确失败后的选择范围，Phase VFX 和 BGM 建立视觉/听觉状态，Double Jump 与 Air Dash 完善 Wizard Game Feel，而扩展后的 `CastEvaluator` 则让玩家能够用一致的递归 Action 语义编写真正可组合的法术。

这次最重要的工程经验有四点：

1. 玩家可见的小功能背后也有明确所有权：Guide 文案属于 SO，暂停属于 Run Coordinator，VFX 属于 Presentation，位置属于 Socket；

3. 移动能力应建模为可测试的 Budget 与 FSM Transition，而不是在 Input 回调里堆条件；
4. 玩法解释器必须先定义语言语义和终止性，再谈 Runtime 特效；否则组合越多，特例越多。
