# 弹跳类修正法术设计复盘

创建时间：2026-07-04  
功能状态：已在 Unity Editor / Play Mode 中测试通过  
目标读者：战斗系统设计新手，重点理解设计思路、开发思路、架构集成思路

---

## 1. 功能一句话总结

“弹跳类修正法术”不是一个新的火球，而是一个 `Modify` 法术。它会让后续 `Emit` 投射物获得若干次“碰到环境后按物理反射方向继续飞行”的能力。

例如法杖：

```text
[弹跳] [普通火球]
```

含义是：

```text
普通火球仍然是普通火球，但本次发射时拥有 1 次或多次环境弹跳能力。
```

这次功能真正训练的是架构判断：

> 新需求来了，不是马上写一个 `BouncyFireball`，而是判断它应该沿着法术解释器链路如何传递。

## 2. 基础知识和原理

### 2.1 弹跳的数学原理

弹跳本质是向量反射。

投射物有一个入射方向 `incoming`，碰撞面有一个法线 `normal`。反射方向可以通过 Unity API 计算：

```csharp
Vector3 reflected = Vector3.Reflect(incoming, normal);
```

你可以这样理解：

```text
incoming = 火球撞向墙面的方向
normal   = 墙面朝外的方向
reflected = 火球应该反弹出去的方向
```

如果是理想平面反射，入射角等于反射角。

### 2.2 Unity 物理相关知识

这个功能涉及几个 Unity 组件和 API：

| 技术点 | 作用 |
|---|---|
| `Rigidbody` | 投射物移动和碰撞由刚体参与 |
| `Rigidbody.linearVelocity` | Unity 6 中设置投射物速度 |
| `Collision` | `OnCollisionEnter` 中拿到碰撞信息 |
| `ContactPoint.normal` | 碰撞面的法线，用于计算反射 |
| `Vector3.Reflect` | 根据入射方向和法线计算反射方向 |
| `CollisionDetectionMode.ContinuousDynamic` | 高速投射物防穿透 |

### 2.3 游戏语义

弹跳不是“命中终点”，它只是“飞行路径发生变化”。

所以本功能定义为：

```text
碰到环境 + 剩余弹跳次数 > 0：
    反射并继续飞，不触发 Impacted，不销毁

碰到敌人：
    不弹跳，照常造成伤害并销毁

弹跳次数耗尽后碰到环境：
    按普通命中处理，可以触发 Impacted
```

这条语义很关键。否则会出现“火球每次撞墙都释放 payload”的错误玩法。

## 3. 实现方案对比

### 3.1 方案 A：使用 Unity `Physic Material`

做法：

给投射物和环境 Collider 配置 `Physic Material`，通过 `Bounciness` 让 Unity 自动反弹。

优点：

- 实现快。
- 看起来接近真实物理。

缺点：

- 很难控制“弹跳次数”。
- 很难和 `SpellDefinition -> CastEvaluator -> EmitCommand` 的法术架构集成。
- 很难定义弹跳和 payload 的关系。
- 表现受物理材质、质量、阻尼、碰撞设置影响，可控性差。

结论：

不适合当前项目。你的目标不是做纯物理弹球，而是做可编程法术行为。

### 3.2 方案 B：在 `ProjectileBase` 中手动反射

做法：

投射物撞到环境时，如果还有弹跳次数：

1. 读取碰撞法线。
2. 用 `Vector3.Reflect` 算反射方向。
3. 设置 `Rigidbody.linearVelocity`。
4. 消耗一次弹跳次数。
5. 提前 `return`，不走命中和销毁逻辑。

优点：

- 弹跳次数可控。
- payload 语义可控。
- 能沿现有法术解释器链路传参。
- 实现成本适合当前阶段。

缺点：

- `ProjectileBase` 增加了一种 projectile behavior。
- 以后行为越来越多时，可能需要抽象成 `ProjectileBehavior` 系统。

结论：

这是本次最终采用的方案。

### 3.3 方案 C：通用 `ProjectileBehavior` 系统

做法：

把弹跳、穿透、追踪、分裂都做成独立 behavior：

```text
BounceBehavior
PierceBehavior
HomingBehavior
SplitBehavior
```

`ProjectileBase` 在生命周期节点调用它们。

优点：

- 长期扩展性强。
- 更像商业项目中复杂 projectile runtime behavior 的方向。

缺点：

- 当前阶段过度设计。
- 需要处理行为优先级、组合冲突、生命周期顺序、运行时配置对象。

结论：

作为未来演进方向保留，不作为本次 MVP。

## 4. 最终方案与技术选择

最终选择：

```text
把弹跳作为 Modify 法术参数，
沿解释器链路传递 BounceCount，
在 ProjectileBase 中执行环境反射。
```

完整数据流：

```text
SpellDefinition.ModBounceAdd
    ↓
CastModifierState.BounceCount
    ↓
CastEvaluator.BakeEmit(...)
    ↓
EmitCommand.BounceCount
    ↓
SpellCaster
    ↓
ProjectileBase.ConfigureBounce(...)
    ↓
ProjectileBase.TryBounce(...)
```

这里每一步都解决一个明确问题：

| 问题 | 技术 |
|---|---|
| 弹跳法术如何配置 | `SpellDefinition.ModBounceAdd` |
| 多个弹跳法术如何叠加 | `CastModifierState.BounceCount` |
| 解释器结果如何传给运行时 | `EmitCommand.BounceCount` |
| 运行时如何配置投射物实例 | `ProjectileBase.ConfigureBounce(int)` |
| 投射物如何反射 | `Vector3.Reflect` + `Rigidbody.linearVelocity` |
| 如何防止弹跳触发 payload | `TryBounce` 成功后提前 `return` |

## 5. 架构设计与集成

### 5.1 在法术编程系统中的位置

弹跳法术横跨五层：

```text
数据层：SpellDefinition
纯规则层：CastModifierState / CastEvaluator
边界对象层：EmitCommand
运行时桥接层：SpellCaster
投射物执行层：ProjectileBase
```

它不属于：

- `DamagePipeline`：弹跳不是伤害公式。
- `HealthComponent`：弹跳不是生命系统。
- `WizardController`：角色输入不关心投射物是否弹跳。
- `WandEditorController`：UI 只编辑法术序列，不解释法术语义。

这就是架构判断。

### 5.2 数据层：`SpellDefinition`

新增字段：

```csharp
public int ModBounceAdd = 0;
```

它只对 `Kind = Modify` 有意义。

Editor 中创建 `Spell_Mdy_Bounce` 时，配置：

```text
Kind = Modify
ModBounceAdd = 1
```

这样它本身不发射投射物，只是修改后续投射物。

### 5.3 纯规则层：`CastModifierState`

新增字段：

```csharp
public readonly int BounceCount;
```

`Apply` 时累加：

```csharp
BounceCount + modify.ModBounceAdd
```

这意味着：

```text
[弹跳] [弹跳] [火球]
```

会得到：

```text
BounceCount = 2
```

### 5.4 解释器层：`CastEvaluator`

`CastEvaluator` 本身不执行弹跳。

它只在 `BakeEmit` 时把当前修正状态写入 `EmitCommand`：

```csharp
mods.BounceCount
```

这保持了 `Game.Skills` 的纯逻辑边界：

```text
解释器只算结果，不碰 Rigidbody，不碰 Collision，不碰 Transform。
```

### 5.5 边界对象：`EmitCommand`

新增：

```csharp
public readonly int BounceCount;
```

`EmitCommand` 是解释器和运行时之间的“合同”。

它表达：

```text
这颗投射物本次生成时，拥有 N 次环境弹跳。
```

注意：`EmitCommand.BounceCount` 是“生成时的初始弹跳次数”，不是运行时剩余次数。  
剩余次数属于具体投射物实例，放在 `ProjectileBase._bounceRemaining`。

### 5.6 运行时桥接层：`SpellCaster`

新增调用：

```csharp
proj.ConfigureBounce(cmd.BounceCount);
```

这一步很关键。

`SpellCaster` 是桥：

```text
它懂 Skills 的 EmitCommand，
也懂 Combat 的 ProjectileBase。
```

所以它负责把解释器结果注入真实投射物实例。

### 5.7 投射物执行层：`ProjectileBase`

新增运行时字段：

```csharp
private int _bounceRemaining;
private float _currentSpeed;
```

新增方法：

```csharp
public void ConfigureBounce(int bounceCount)
```

新增核心逻辑：

```csharp
private bool TryBounce(Collision collision, IDamageable target)
```

碰撞流程变成：

```text
同阵营：
    pass-through

环境 + 有弹跳次数：
    TryBounce
    return

敌人 / 弹跳耗尽：
    走原命中流程
```

这保证弹跳不会破坏原来的战斗系统。

## 6. 和现有功能的集成关系

### 6.1 和普通火球

```text
[弹跳] [普通火球]
```

普通火球获得环境弹跳次数。  
撞敌人仍然造成伤害并销毁。

### 6.2 和多重法术

```text
[弹跳] [三重] [火球] [火球] [火球]
```

由于弹跳在 `CastModifierState` 中累计，后续每个 `Emit` 都会获得相同 `BounceCount`。

### 6.3 和触发类火球

```text
[弹跳] [触发火球] [普通火球]
```

弹跳时不触发 payload。  
最终命中敌人，或弹跳耗尽后撞到环境，才触发 payload。

这是因为 `TryBounce` 在 `Impacted?.Invoke(...)` 之前执行，并且成功弹跳后直接 `return`。

### 6.4 和定时类火球

```text
[弹跳] [定时火球] [普通火球]
```

弹跳不影响计时。  
投射物只要仍然存在，`TimedTriggerElapsed` 仍会正常触发。

## 7. 踩坑与 Debug

### 7.1 问题：弹跳方向不符合物理规律

现象：

```text
火球有时不按反射方向飞。
有时撞地后贴着地面前进。
```

初始错误思路是：

```csharp
Vector3 velocity = _rb.linearVelocity;
Vector3 incoming = velocity.normalized;
Vector3 reflected = Vector3.Reflect(incoming, normal);
```

问题在于：`OnCollisionEnter` 被调用时，Unity 物理系统可能已经对 `Rigidbody.linearVelocity` 做了接触求解修正。  
此时读到的速度不一定是“碰撞前的入射速度”。

解决：

```csharp
Vector3 intendedVelocity = _launchVelocity.sqrMagnitude > 1e-6f ? _launchVelocity : velocity;
Vector3 incoming = intendedVelocity.normalized;
```

也就是用我们自己保存的 `_launchVelocity` 作为入射方向来源。

### 7.2 问题：弹跳后贴着表面滑行

原因：

投射物反弹后仍然可能和碰撞面保持接触，下一帧继续被物理接触约束影响。

解决：

```csharp
_rb.position += normal * 0.03f;
```

反弹时沿法线方向把刚体轻微推出接触面，减少连续接触导致的贴地滑行。

### 7.3 问题：弹跳时不能触发 payload

如果弹跳时继续走原命中逻辑，会执行：

```csharp
OnImpact(...)
Impacted?.Invoke(...)
Destroy(...)
```

这样每次撞墙都会释放触发 payload。

解决：

```csharp
if (TryBounce(collision, target))
    return;
```

弹跳成功就提前返回，不进入命中流程。

### 7.4 问题：为什么不让敌人也触发弹跳？

本次 MVP 语义定义为：

```text
环境弹跳，敌人终止。
```

原因：

- 玩家容易理解。
- 不影响伤害结算。
- 不引入“打到敌人后继续飞”的穿透语义。

未来如果要“打到敌人后继续飞”，那应该是另一个法术：`Pierce` / 穿透。

## 9. 大厂面试 Q&A

### Q1：为什么弹跳要做成 Modify，而不是新建一个弹跳火球？

A：因为弹跳是投射物行为修正，不是火球类型本身。做成 `Modify` 后，它可以作用于任意后续 `Emit`，例如普通火球、触发火球、定时火球，未来也可以作用于冰弹、雷球。这样符合 Noita-like 法术编程系统的组合思想，避免 `BouncyFireball`、`TimedBouncyFireball` 这类组合爆炸。

### Q2：弹跳参数如何从法术资产传到真实投射物？

A：数据从 `SpellDefinition.ModBounceAdd` 开始，解释器读取 Modify 时累积到 `CastModifierState.BounceCount`。当后续 Emit 被 `CastEvaluator` 烘焙时，`BounceCount` 写入 `EmitCommand`。运行时 `SpellCaster` 实例化投射物后，调用 `ProjectileBase.ConfigureBounce(cmd.BounceCount)` 注入到投射物实例。最后 `ProjectileBase.TryBounce` 在环境碰撞时执行弹跳。

### Q3：为什么不在 `CastEvaluator` 里处理弹跳？

A：`CastEvaluator` 是纯规则解释器，不应该依赖 Unity 物理、`Rigidbody`、`Collision` 或 `Transform`。它只负责算出“这次投射物应该有几次弹跳”。真正的物理反射属于投射物运行时行为，放在 `ProjectileBase`。

### Q4：弹跳和触发 payload 如何避免冲突？

A：`TryBounce` 插入在原命中流程之前。环境弹跳成功后直接 `return`，不会执行 `OnImpact`、`Impacted` 和 `Destroy`。所以弹跳只是改变飞行路径，不算命中终点。只有敌人命中或弹跳耗尽后的环境碰撞才触发 payload。

### Q5：调试中遇到的关键问题是什么？

A：最关键的问题是最初用 `Rigidbody.linearVelocity` 作为入射方向，但 `OnCollisionEnter` 中这个速度可能已被 Unity 物理接触求解修改，导致反射方向不符合物理预期。修复方式是使用 `_launchVelocity` 作为我们自己保存的“碰撞前意图速度”，反弹后再更新 `_launchVelocity`，并沿碰撞法线轻微推出刚体，避免贴面滑行。

### Q6：这个设计以后如何扩展到穿透或追踪？

A：当前弹跳先用字段方式接入主链路，保持 MVP 简洁。未来如果 projectile behavior 增多，可以把 `BounceCount`、`PierceCount`、`HomingStrength` 等收敛成一个 `ProjectileRuntimeConfig`，再进一步抽象成 behavior pipeline。但当前阶段不提前引入复杂系统，避免过度设计。

## 10. 模拟面试者完整讲解

我在这个项目里实现了一个 Noita-like 法术编程系统中的弹跳类修正法术。这个功能的设计重点不是做一个新的弹跳火球 prefab，而是把弹跳作为 `Modify` 指令接入现有的法术解释器架构。玩家把弹跳法术放在火球前面时，解释器从左到右读取法术，把 `ModBounceAdd` 累积到 `CastModifierState.BounceCount`，后续的 `Emit` 在 `CastEvaluator.BakeEmit` 阶段会把这个值写入 `EmitCommand`。

运行时由 `SpellCaster` 负责桥接纯规则和 Unity 场景。它实例化投射物后调用 `ProjectileBase.ConfigureBounce`，把 `EmitCommand.BounceCount` 注入到具体投射物实例。这样 `Game.Skills` 仍然保持纯逻辑，不依赖 Unity 物理；`Game.Combat` 的 `ProjectileBase` 也不需要知道 `SpellDefinition` 或 `CastEvaluator`，只接收一个运行时配置值。

投射物碰撞时，我在 `ProjectileBase.OnCollisionEnter` 的同阵营过滤之后、原命中结算之前插入了 `TryBounce`。如果碰到的是环境，并且还有剩余弹跳次数，就使用碰撞法线和 `Vector3.Reflect` 计算反射方向，设置 `Rigidbody.linearVelocity`，消耗一次弹跳次数，然后提前返回。这样弹跳不会触发 `OnImpact` 或 `Impacted`，也不会释放命中 payload。敌人命中仍然走原来的伤害结算和销毁逻辑。

开发中一个关键 Debug 点是，最开始用 `Rigidbody.linearVelocity` 作为入射方向，结果反射方向不符合物理规律。原因是 `OnCollisionEnter` 触发时，Unity 物理系统可能已经修改了刚体速度。后来我改为使用 `_launchVelocity` 保存投射物的意图飞行速度，反弹后更新这个速度，并沿碰撞法线轻微推出刚体，解决了错误反射和贴地滑行问题。

这个功能体现的架构价值是：新增法术行为没有绕过解释器，也没有做成特殊技能类，而是沿着 `SpellDefinition -> CastModifierState -> CastEvaluator -> EmitCommand -> SpellCaster -> ProjectileBase` 的主链路集成。这样后续做穿透、追踪、分裂等投射物行为修正时，可以复用同样的设计思路。
