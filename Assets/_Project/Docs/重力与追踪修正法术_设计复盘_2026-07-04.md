# 重力与追踪修正法术设计复盘

创建时间：2026-07-04 14:07:04  
功能状态：已在 Unity Editor / Play Mode 中测试通过  
目标读者：战斗系统设计新手，重点理解设计思路、开发思路、架构集成思路

## 1. 两个功能一句话总结

“重力修正”和“投射物追踪修正”都是 `Modify` 法术。它们不直接生成投射物，而是修改后续 `Emit` 投射物的运动行为。

```text
[重力] [普通火球]
```

含义是：

```text
普通火球仍然是普通火球，但本次生成时启用 Rigidbody.useGravity，飞行轨迹从直线变成下坠抛物线。
```

```text
[追踪] [普通火球]
```

含义是：

```text
普通火球仍然是普通火球，但本次生成后会检测附近敌人，并在短时间内有限转向敌人。
```

这两个功能最重要的共同点：

```text
都不是新火球。
都不是新 SpellKind。
都不是特殊 prefab。
都沿同一条法术解释器链路接入。
```

主链路是：

```text
SpellDefinition
    -> CastModifierState
    -> CastEvaluator
    -> EmitCommand
    -> SpellCaster
    -> ProjectileBase
    -> Unity Physics / Projectile Runtime
```

你要重点理解的是：这两个功能训练的是“如何把一个新玩法接进架构”，而不只是“怎么让火球下坠/转弯”。

## 2. 基础知识和原理

### 2.1 `Emit` 和 `Modify` 的区别

在当前法术编程系统里，可以把法杖理解成一段程序：

```text
WandLoadout = 程序
SpellDefinition = 指令
CastEvaluator = 解释器
EmitCommand = 解释器输出
SpellCaster = 把输出变成 Unity 运行时对象
ProjectileBase = 投射物生命周期与碰撞执行
```

`Emit` 指令回答：

```text
我要生成什么？
```

例如：

```text
普通火球
触发火球
定时火球
```

`Modify` 指令回答：

```text
后续生成出来的东西要被怎样修改？
```

例如：

```text
增伤
加速
散射
弹跳
重力
追踪
```

重力和追踪都不自己生成火球，只改变后续火球的运动行为，所以它们应该是 `Modify`。

### 2.2 重力的基础原理

重力改变的是投射物的运动轨迹。

没有重力时：

```text
投射物获得一个初速度。
如果没有其他力影响，它会大致沿速度方向直线飞行。
```

启用重力后：

```text
投射物仍然有初速度。
但 Unity Physics 会持续给 Rigidbody 施加全局重力加速度。
速度的 Y 方向会逐渐向下变化。
轨迹变成抛物线。
```

Unity 中对应的关键字段是：

```csharp
Rigidbody.useGravity
```

它是 Unity `Rigidbody` 组件上的内置属性，用来决定这个刚体是否受全局 `Physics.gravity` 影响。

### 2.3 追踪的基础原理

追踪改变的是投射物的速度方向。

完全追踪通常会这样做：

```text
每帧直接把投射物方向改成目标方向。
```

这会接近必中，不符合本项目需求。

本次做的是有限追踪：

```text
投射物先正常飞。
检测到范围内有敌人后，只启动一次追踪窗口。
窗口时间内，投射物每个物理步最多转一定角度。
窗口结束后，不再继续追踪。
```

核心数学是：

```text
currentDir = 当前速度方向
desiredDir = 从投射物指向目标的位置方向
newDir = 从 currentDir 朝 desiredDir 转一小步
```

Unity 提供的内置 API 是：

```csharp
Vector3.RotateTowards(currentDir, desiredDir, maxRadiansDelta, maxMagnitudeDelta)
```

它不会瞬间把方向改成目标方向，而是限制“这一步最多转多少弧度”。这就是防止完全锁头的关键。

## 3. Unity API 和组件重点解释

### 3.1 `Rigidbody`

`Rigidbody` 是 Unity 物理系统的刚体组件。当前项目里投射物使用 `Rigidbody` 控制飞行、碰撞和速度。

这次涉及的属性：

```csharp
_rb.useGravity = useGravity;
_rb.linearVelocity = velocity;
```

`useGravity` 控制是否受重力。  
`linearVelocity` 是 Unity 6 中刚体线速度属性，用来读取或设置刚体当前速度。

### 3.2 `Rigidbody.useGravity`

这是重力修正真正落地的 API。

```csharp
_rb.useGravity = true;
```

表示这个投射物参与全局重力模拟。

```csharp
_rb.useGravity = false;
```

表示这个投射物不受全局重力影响，火球保持直线风格。

注意：`useGravity` 是开关，不是倍率。  
如果以后要做“强重力”“弱重力”“反重力”，不能只靠这个 bool，需要自定义 gravity scale 或手写 velocity 积分。

### 3.3 `Physics.gravity`

这是 Unity 项目的全局重力向量。默认接近：

```text
(0, -9.81, 0)
```

当 `Rigidbody.useGravity = true` 时，Unity Physics 会按这个重力向量影响刚体速度。

本次没有直接修改 `Physics.gravity`，因为那会影响整个项目里所有受重力刚体，不适合单个法术效果。

### 3.4 `Physics.OverlapSphereNonAlloc`

这是追踪修正用于扫描敌人的关键 API。

```csharp
int hitCount = Physics.OverlapSphereNonAlloc(
    transform.position,
    _homingRadius,
    s_homingHits);
```

作用：

```text
以投射物当前位置为球心，半径为 _homingRadius，找出范围内的 Collider。
结果写入预先准备好的 Collider[] 数组。
返回实际命中数量。
```

为什么用 `OverlapSphereNonAlloc`，而不是 `Physics.OverlapSphere`？

- `Physics.OverlapSphere` 会**返回新数组**，如果很多投射物频繁调用，容易产生 `GC Alloc`。  
- `OverlapSphereNonAlloc` **使用传入的数组**，不会每次分配新数组，更适合运行时频繁扫描。

### 3.5 `Collider` 和 `GetComponentInParent<IDamageable>()`

追踪扫描拿到的是 `Collider`，但投射物真正要追踪的是“敌方可受击目标”。

所以代码要从 Collider 向父物体查找：

```csharp
IDamageable damageable = hit.GetComponentInParent<IDamageable>();
```

`IDamageable` 是当前项目中“可以被攻击”的统一接口。  
它提供：

```csharp
byte TeamId { get; }
bool IsAlive { get; }
void ReceiveHit(in DamageRequest req);
```

追踪只需要前两个：

```text
TeamId：过滤同阵营。
IsAlive：过滤已死亡目标。
```

### 3.6 `Vector3.RotateTowards`

这是有限追踪的核心 API。

```csharp
Vector3 newDir = Vector3.RotateTowards(
    velocity.normalized,
    toTarget.normalized,
    maxRadians,
    0f);
```

参数含义：

| 参数 | 含义 |
|---|---|
| `velocity.normalized` | 当前飞行方向 |
| `toTarget.normalized` | 指向目标的理想方向 |
| `maxRadians` | 本次最多转多少弧度 |
| `0f` | 向量长度不在这里改变，只改变方向 |

这比直接 `LookAt` 或直接 `velocity = desiredDir * speed` 更适合本功能，因为它保留了“打空”的可能。

### 3.7 `FixedUpdate`

追踪放在 `FixedUpdate` 里执行。

原因：

```text
追踪会修改 Rigidbody.linearVelocity。
Rigidbody 属于物理系统。
物理速度修改通常放在 FixedUpdate 更稳定。
```

`Update` 更适合普通游戏逻辑计时、输入、UI。  
`FixedUpdate` 更适合物理速度、物理力、刚体运动。

## 4. 实现方案对比

### 4.1 重力修正的方案

#### 方案 A：复制一个 `GravityFireball` prefab

做法：

复制火球 prefab，把 `Rigidbody.useGravity` 勾上。

优点：

- 快。
- 直观。

缺点：

- 会产生 `GravityFireball`、`GravityBouncyFireball`、`GravityTriggerFireball` 等组合爆炸。
- 不能体现法术编程系统的组合价值。
- 一改 prefab 就影响所有使用该 prefab 的地方。

结论：

不采用。

#### 方案 B：通过法术解释器传 `UseGravity`

做法：

```text
SpellDefinition.ModUseGravity
-> CastModifierState.UseGravity
-> EmitCommand.UseGravity
-> SpellCaster
-> ProjectileBase.Init(... useGravity)
-> Rigidbody.useGravity
```

优点：

- 保持同一个火球 prefab。
- 每次发射实例可以根据法术组合决定是否受重力。
- 完全符合 Noita-like 组合思路。
- 改动小，复用已有 `ProjectileBase.Init` 扩展点。

结论：

采用。

#### 方案 C：自定义重力积分

做法：

手写：

```csharp
velocity += gravity * deltaTime;
```

优点：

- 可以做重力倍率、反重力、自定义方向。

缺点：

- 当前需求过度设计。
- 会和 Unity `Rigidbody` 体系产生职责重叠。

结论：

未来如果做“重力倍率”再考虑。

### 4.2 追踪修正的方案

#### 方案 A：完全追踪

做法：

每帧直接朝敌人飞：

```csharp
rb.linearVelocity = desiredDir * speed;
```

优点：

- 实现简单。
- 效果明显。

缺点：

- 接近必中。
- 走位价值下降。
- 和多重、触发、定时组合后容易强度失控。

结论：

不采用。

#### 方案 B：有限时间 + 有限转向

做法：

```text
扫描范围内敌人。
第一次发现敌人后锁定。
启动追踪计时器。
计时期间用 Vector3.RotateTowards 小幅转向。
计时结束后停止追踪。
```

优点：

- 提升命中容错，但不保证命中。
- 参数可调：范围、持续时间、转向速度。
- 容易和现有投射物系统集成。
- 面试时能清楚解释平衡边界。

结论：

采用。

#### 方案 C：目标预测追踪

做法：

预测目标未来位置：

```text
predictedPosition = targetPosition + targetVelocity * leadTime
```

优点：

- 更像真实导弹。
- 技术上更高级。

缺点：

- 当前敌人系统没有统一速度接口。
- 更难平衡。
- 可能比普通追踪更接近必中。

结论：

当前不做。

#### 方案 D：通用 `ProjectileBehavior` 系统

做法：

把弹跳、重力、追踪、穿透、分裂等做成 behavior pipeline。

优点：

- 长期扩展性最好。

缺点：

- 当前阶段过重。
- 需要重新设计生命周期、优先级、冲突处理。

结论：

作为未来重构方向，不作为这次 MVP。

## 5. 最终技术方案

### 5.1 重力最终技术方案

新增数据：

```csharp
public bool ModUseGravity = false;
```

解释器状态：

```csharp
public readonly bool UseGravity;
```

叠加规则：

```csharp
UseGravity || modify.ModUseGravity
```

运行时落地：

```csharp
proj.Init(..., useGravity: cmd.UseGravity);
```

最终 Unity API：

```csharp
_rb.useGravity = useGravity;
```

这个方案的本质是：

```text
重力是投射物初始化参数。
它只需要在投射物生成时决定一次。
后续由 Unity Physics 持续处理。
```

### 5.2 追踪最终技术方案

新增数据：

```csharp
public float ModHomingRadius = 0f;
public float ModHomingDuration = 0f;
public float ModHomingTurnRateDegrees = 0f;
```

解释器状态：

```csharp
public readonly float HomingRadius;
public readonly float HomingDuration;
public readonly float HomingTurnRateDegrees;
```

叠加规则：

```csharp
HomingRadius = Mathf.Max(HomingRadius, modify.ModHomingRadius);
HomingDuration = HomingDuration + modify.ModHomingDuration;
HomingTurnRateDegrees = HomingTurnRateDegrees + modify.ModHomingTurnRateDegrees;
```

为什么这样叠加？

```text
半径取最大：避免两个追踪法术让范围线性膨胀到过大。
持续时间相加：多个追踪表示追踪窗口更久。
转向速度相加：多个追踪表示修正能力更强。
```

运行时落地：

```csharp
proj.ConfigureHoming(
    cmd.HomingRadius,
    cmd.HomingDuration,
    cmd.HomingTurnRateDegrees);
```

投射物执行：

```text
FixedUpdate
    -> TickHoming
        -> 未锁定时按间隔 OverlapSphereNonAlloc 扫描
        -> 找到最近敌方存活 IDamageable
        -> 锁定一次，启动 homingRemaining
        -> 计时期间 RotateTowards 修正 linearVelocity
```

## 6. 架构设计与拆解

### 6.1 总体架构位置

这两个功能都跨越以下层：

```text
数据层：
    SpellDefinition

纯规则层：
    CastModifierState
    CastEvaluator

边界数据层：
    EmitCommand

运行时桥接层：
    SpellCaster

投射物执行层：
    ProjectileBase

Unity 底层：
    Rigidbody / Physics / Collider
```

它们不应该进入：

| 不进入的模块 | 原因 |
|---|---|
| `WizardController` | 角色只负责发起施法，不关心投射物如何飞 |
| `DamagePipeline` | 这两个功能不改变伤害公式 |
| `HealthComponent` | 这两个功能不属于生命值系统 |
| `WandEditorController` | UI 只编辑法术顺序，不解释法术语义 |
| `EnemyControllerBase` | 敌人不需要知道自己被追踪 |

### 6.2 `SpellDefinition`：数据入口

改动字段：

```csharp
public bool ModUseGravity = false;
public float ModHomingRadius = 0f;
public float ModHomingDuration = 0f;
public float ModHomingTurnRateDegrees = 0f;
```

这是 Editor 可配置的入口。

对应资产：

```text
Spell_Mdy_Gravity
    Kind = Modify
    ModUseGravity = true

Spell_Mdy_Homing
    Kind = Modify
    ModHomingRadius = 6
    ModHomingDuration = 0.6
    ModHomingTurnRateDegrees = 120
```

注意：`SpellDefinition` 是数据，不是运行时状态。  
不能把“剩余追踪时间”“已锁定目标”等运行时信息放到这里。

### 6.3 `CastModifierState`：解释器当前修正状态

`CastModifierState` 表示解释器从左到右读法术时，当前已经累计了哪些修正。

重力字段：

```csharp
public readonly bool UseGravity;
```

追踪字段：

```csharp
public readonly float HomingRadius;
public readonly float HomingDuration;
public readonly float HomingTurnRateDegrees;
```

它是 `readonly struct`，好处是：

```text
值语义清晰。
没有 MonoBehaviour 生命周期。
适合 EditMode tests。
不会在解释器里引用 Unity 场景对象。
```

### 6.4 `CastEvaluator`：纯解释器

`CastEvaluator` 不生成火球，不查找敌人，不改刚体。

它只做：

```text
读法杖序列。
遇到 Modify，更新 CastModifierState。
遇到 Emit，把当前状态烘焙到 EmitCommand。
```

关键点：

```csharp
mods.UseGravity
mods.HomingRadius
mods.HomingDuration
mods.HomingTurnRateDegrees
```

都在 `BakeEmit` 时写入 `EmitCommand`。

这就是“纯规则层”的边界。

### 6.5 `EmitCommand`：解释器到运行时的合同

`EmitCommand` 表示：

```text
本次要生成一个什么投射物，它的伤害、速度、散射、弹跳、重力、追踪、payload 是什么。
```

新增字段：

```csharp
public readonly bool UseGravity;
public readonly float HomingRadius;
public readonly float HomingDuration;
public readonly float HomingTurnRateDegrees;
```

这些都是“一次发射的快照”。

为什么要快照？

```text
因为投射物生成后，不能再回头读 SpellDefinition。
SpellDefinition 是资产数据，Play Mode 中还可能被 UI 修改。
运行时投射物应该只依赖生成时得到的固定参数。
```

### 6.6 `SpellCaster`：运行时桥接

`SpellCaster` 是关键桥梁。

它一边懂：

```text
Game.Skills.EmitCommand
```

另一边懂：

```text
Unity GameObject
Game.Combat.ProjectileBase
```

所以它负责把解释器输出注入投射物实例：

```csharp
proj.ConfigureBounce(cmd.BounceCount);
proj.ConfigureHoming(cmd.HomingRadius, cmd.HomingDuration, cmd.HomingTurnRateDegrees);
proj.Init(..., useGravity: cmd.UseGravity);
```

为什么不让 `ProjectileBase` 自己读 `SpellDefinition`？

因为那会让 `Game.Combat` 反向依赖 `Game.Skills`，破坏模块边界。

### 6.7 `ProjectileBase`：投射物执行层

重力落点：

```csharp
_rb.useGravity = useGravity;
```

追踪落点：

```csharp
ConfigureHoming(...)
TickHoming(Time.fixedDeltaTime)
TryAcquireHomingTarget()
```

追踪运行时字段：

```csharp
private float _homingRadius;
private float _homingDuration;
private float _homingTurnRateDegrees;
private bool _homingEnabled;
private bool _homingAcquired;
private float _homingRemaining;
private float _homingScanTimer;
private Transform _homingTarget;
private IDamageable _homingTargetDamageable;
```

这些字段属于“具体投射物实例的运行时状态”，所以放在 `ProjectileBase`，不能放在 `SpellDefinition` 或 `EmitCommand`。

## 8. 与现有系统的组合关系

### 8.1 和普通火球

```text
[重力] [普通火球]
```

普通火球下坠。

```text
[追踪] [普通火球]
```

普通火球靠近敌人后有限转向。

### 8.2 重力 + 追踪

```text
[重力] [追踪] [普通火球]
```

结果：

```text
UseGravity = true
HomingRadius > 0
HomingDuration > 0
HomingTurnRateDegrees > 0
```

运行时：

```text
Unity Physics 持续让火球下坠。
TickHoming 在追踪窗口内调整速度方向。
```

这两者会共同影响轨迹。  
如果轨迹看起来不是简单曲线，这是正常的组合结果。

### 8.3 和弹跳

```text
[重力] [追踪] [弹跳] [普通火球]
```

结果：

```text
火球受重力。
火球可有限追踪。
火球撞环境时可反射。
```

职责边界：

```text
重力：持续物理影响。
追踪：追踪窗口内微调速度方向。
弹跳：碰撞瞬间改速度方向。
```

这些功能都改“运动”，但发生时机不同。

### 8.4 和触发类火球

```text
[重力] [追踪] [触发火球] [普通火球]
```

结果：

```text
触发火球本体受重力并可追踪。
触发后释放的普通火球也继承 PayloadMods，因此也有重力/追踪修正。
```

这是因为 `EmitCommand` 里保存了：

```csharp
PayloadMods
```

触发 payload 时，下一层解释器以这个修正快照作为起点。

### 8.5 和定时类火球

```text
[重力] [追踪] [定时火球] [普通火球]
```

结果：

```text
定时火球本体受重力并可追踪。
如果它存活到 delay，则释放 payload。
payload 继承重力和追踪。
```

注意：

```text
追踪可能让定时火球提前撞到敌人或环境。
如果提前命中，定时 payload 不释放。
```

这符合定时类法术已有规则：必须“仍然存在”才触发。

### 8.6 和多重法术

```text
[追踪] [三重] [火球] [火球] [火球]
```

结果：

```text
三个火球都获得追踪配置。
每颗火球独立扫描、独立锁定、独立计时。
```

这里不要误解成“一个追踪目标被三颗火球共享”。  
每个投射物实例都有自己的 `_homingTarget` 和 `_homingRemaining`。

## 9. 踩坑与 Debug

### 9.1 坑点：不要直接改火球 prefab

错误做法：

```text
把 Fireball prefab 的 Rigidbody.useGravity 勾上。
或者复制一个 HomingFireball prefab。
```

问题：

```text
这会绕过法术解释器。
普通火球、重力火球、追踪火球会变成不同 prefab。
组合数量会爆炸。
```

正确做法：

```text
Prefab 保持通用。
每次发射时由 EmitCommand 决定本实例参数。
```

### 9.2 坑点：不要在 `CastEvaluator` 中碰 Unity 物理

错误做法：

```text
CastEvaluator 里查找敌人。
CastEvaluator 里改 Rigidbody。
```

问题：

```text
Game.Skills 会依赖 Unity 场景对象。
EditMode tests 会变难。
模块边界被破坏。
```

正确边界：

```text
CastEvaluator 只产出 UseGravity / Homing 参数。
ProjectileBase 才执行物理行为。
```

### 9.3 坑点：追踪不能每帧 `new` 或 LINQ

错误做法：

```csharp
var hits = Physics.OverlapSphere(...);
var target = hits.Where(...).FirstOrDefault();
```

问题：

```text
OverlapSphere 返回新数组。
LINQ 可能产生迭代器/闭包分配。
投射物多时会产生 GC Alloc。
```

正确做法：

```csharp
private static readonly Collider[] s_homingHits = new Collider[16];
Physics.OverlapSphereNonAlloc(..., s_homingHits);
for 循环手动筛选。
```

### 9.4 坑点：追踪不能无限重新锁定

如果目标死亡后立刻扫描新目标，投射物会变成：

```text
自动寻找下一个敌人的智能导弹。
```

这超出本次设计。

当前语义是：

```text
每颗投射物只启动一次追踪窗口。
目标丢失后停止追踪，不重新锁定。
```

这样强度更可控。

### 9.5 坑点：追踪时间窗口应按时间流逝，而不是按“成功转向帧”流逝

如果速度接近 0 时不扣追踪时间，追踪窗口可能被异常延长。

正确语义是：

```text
追踪窗口是时间窗口。
只要目标有效，计时就应该流逝。
```

因此实现中会在目标有效后扣：

```csharp
_homingRemaining -= deltaTime;
```

然后再根据当前速度决定是否能转向。

### 9.6 坑点：Editor 资产配置漏项

代码写完后还必须配置资产：

```text
Spell_Mdy_Gravity
Spell_Mdy_Homing
SpellLibrary.Available
```

如果 UI 里看不到法术，优先检查：

```text
资产是否创建
Kind 是否是 Modify
字段是否配置
是否加入 SpellLibrary
WandLoadout 是否实际放入
```

## 10. 大厂面试 Q&A

### Q1：为什么重力和追踪都做成 `Modify`？

A：因为它们不决定“发射什么”，而是决定“后续发射物如何运动”。`Emit` 负责生成投射物，`Modify` 负责修改后续投射物的属性或行为。这样可以避免 `GravityFireball`、`HomingFireball`、`GravityHomingBouncyTimedFireball` 这种组合爆炸，也符合 Noita-like 法术编程的指令组合思想。

### Q2：这两个修正如何从法术资产传到真实投射物？

A：数据从 `SpellDefinition` 开始，解释器读到 `Modify` 后写入 `CastModifierState`。后续读到 `Emit` 时，`CastEvaluator.BakeEmit` 把当前状态写入 `EmitCommand`。运行时 `SpellCaster` 根据 `EmitCommand` 实例化投射物，并调用 `ProjectileBase` 的配置方法或 `Init` 参数。最终重力落到 `Rigidbody.useGravity`，追踪落到 `ConfigureHoming` 和 `TickHoming`。

### Q3：为什么 `CastEvaluator` 不直接处理追踪？

A：`CastEvaluator` 是纯解释器，不应该依赖 Unity 场景对象、物理查询或 `Rigidbody`。追踪需要扫描 Collider、判断 `IDamageable`、修改刚体速度，这些都属于运行时投射物行为，应放在 `ProjectileBase`。这样 `Game.Skills` 可以保持可测试、可预测、低耦合。

### Q4：为什么追踪不是完全追踪？

A：完全追踪会让投射物每帧直接朝目标飞，容易变成必中。当前设计用 `Vector3.RotateTowards` 限制每秒最大转向角度，并且只在有限时间窗口内追踪。这样它提升命中容错，但仍然保留打空可能，更容易平衡，也保留敌人走位价值。

### Q5：追踪如何避免 GC Alloc？

A：目标扫描使用 `Physics.OverlapSphereNonAlloc`，结果写入静态预分配 `Collider[]` 缓冲。筛选目标使用普通 `for` 循环，不使用 LINQ，不在热路径中 `new` 数组或列表。同时扫描只在未锁定目标时按 `_homingScanInterval` 间隔执行，不是每个物理步都扫描。

### Q6：追踪如何选择目标？

A：MVP 选择检测范围内最近的敌方存活 `IDamageable`。过滤条件是目标非空、`IsAlive == true`、`TeamId != attackerTeam`。本阶段不做 Boss 优先、血量最低优先、准星最近优先等复杂策略，避免过早设计。

### Q7：重力和追踪组合时谁优先？

A：它们不使用显式优先级，而是在不同层面共同影响速度。`Rigidbody.useGravity` 让 Unity Physics 持续施加重力，`TickHoming` 在追踪窗口内修正 `linearVelocity` 的方向。组合后的轨迹可能更复杂，但这是法术组合系统允许的表现。后续如果需要更严格控制，可以增加“只调整水平转向”或自定义 motion pipeline。

### Q8：为什么追踪目标丢失后不重新锁定？

A：因为本功能定位是“一次有限弹道修正”，不是智能导弹。目标丢失后重新锁定新目标会显著提高强度，甚至形成自动索敌。当前设计中每颗投射物最多启动一次追踪窗口，目标丢失后保持当前速度继续飞行，更容易平衡。

### Q9：为什么追踪参数这样叠加？

A：半径取最大，是为了避免多个追踪修正把扫描范围线性堆到过大；持续时间相加，表示追踪窗口更久；转向速度相加，表示转向能力更强。这三个规则分别控制范围、时间、强度，比较符合玩家直觉，也方便平衡。

### Q10：如果后续 projectile behavior 越来越多，该怎么演进？

A：当前把弹跳、定时、追踪放进 `ProjectileBase` 是 MVP 阶段可接受的，因为行为数量还少，改动直观。后续如果继续增加穿透、分裂、吸附、返回施法者等行为，应考虑抽象 `ProjectileRuntimeConfig` 或 `ProjectileBehaviorPipeline`，把不同生命周期点的行为拆出去，避免 `ProjectileBase` 变成过大的上帝类。

## 11. 模拟面试者完整讲解

我在这个项目里实现了两个 Noita-like 法术编程系统中的投射物修正法术：重力修正和追踪修正。它们的共同点是都没有做成新的火球类型，而是作为 `Modify` 指令接入现有解释器。玩家写 `[重力] [火球]` 时，火球仍然是原来的 `Emit`，但本次实例会启用 `Rigidbody.useGravity`；玩家写 `[追踪] [火球]` 时，火球也仍然是原来的 `Emit`，但本次实例会获得有限时间的追踪能力。

架构上，我沿用了项目已有的主链路：`SpellDefinition -> CastModifierState -> CastEvaluator -> EmitCommand -> SpellCaster -> ProjectileBase`。首先在 `SpellDefinition` 上增加重力和追踪相关字段，让它们能通过 `ScriptableObject` 资产配置。然后在 `CastModifierState` 中增加对应状态，解释器从左到右读到 `Modify` 时更新当前状态。重力是 bool 开关，用 `UseGravity || modify.ModUseGravity` 累计；追踪有三个参数，半径取最大、持续时间相加、转向速度相加。

当解释器读到后续 `Emit` 时，`CastEvaluator.BakeEmit` 会把当前修正状态烘焙进 `EmitCommand`。这里我保持 `Game.Skills` 纯逻辑，它只产出“这次发射应该带什么参数”，不接触 `Rigidbody`、`Collider` 或场景查询。运行时由 `SpellCaster` 作为桥接层，把 `EmitCommand` 应用到真实投射物实例上。重力通过 `ProjectileBase.Init(..., useGravity: cmd.UseGravity)` 落到 `Rigidbody.useGravity`；追踪通过 `ProjectileBase.ConfigureHoming(...)` 注入到投射物运行时状态中。

重力实现比较轻，因为 `ProjectileBase.Init` 原本就支持 `useGravity` 参数，所以我只是把法术解释器输出接到这个扩展点上。这样没有重力修正时火球仍然直线飞行，有重力修正时同一个火球 prefab 的本次实例才会下坠。这个设计避免了复制 `GravityFireball` prefab，也避免了组合爆炸。

追踪实现更复杂一些。我没有做完全追踪，而是设计成有限追踪窗口。投射物在 `FixedUpdate` 中执行 `TickHoming`。如果尚未锁定目标，就按扫描间隔使用 `Physics.OverlapSphereNonAlloc` 在范围内查找 Collider，再通过 `GetComponentInParent<IDamageable>()` 找到可受击目标，并过滤同阵营和死亡目标。找到目标后只锁定一次，启动 `_homingRemaining` 计时器。计时期间用 `Vector3.RotateTowards` 把当前速度方向逐步转向目标方向，并写回 `Rigidbody.linearVelocity`。计时结束后停止追踪，目标丢失也不重新锁定新目标。

这个方案的核心取舍是控制强度和保持架构边界。完全追踪更简单，但容易必中；有限追踪通过范围、时间、转向速度三个参数控制强度，保留打空可能。目标扫描使用 `OverlapSphereNonAlloc` 和静态缓冲，避免运行时 `GC Alloc`。解释器层只做数据，不做物理；投射物层只接收运行时配置，不知道具体法术资产。这样重力、追踪、弹跳、触发、定时、多重都可以组合，同时系统仍然保持清晰的依赖方向。

最后我补了 EditMode 纯逻辑测试，验证默认状态、修正叠加、只影响后续 `Emit`、payload mods 继承等规则。实际的抛物线、追踪轨迹和组合表现则由 Unity Editor / Play Mode 验证，因为它们依赖真实 `Rigidbody`、Collider 和场景目标。整体来说，这两个功能体现的是一种可扩展的法术编程开发思路：新增玩法时先判断它在架构中属于数据、解释器状态、运行时桥接还是投射物执行，再沿既有链路接入，而不是绕过系统写特例。

## 12. 建议阅读脚本顺序

不要按文件夹随机点。建议按数据流顺序看：

```text
1. SpellDefinition.cs
   看 ModUseGravity / ModHomingRadius / ModHomingDuration / ModHomingTurnRateDegrees。

2. CastModifierState.cs
   看 UseGravity 和 Homing 参数如何累计。

3. CastEvaluator.cs
   看 BakeEmit 如何把当前修正状态写入 EmitCommand。

4. EmitCommand.cs
   理解它是纯解释器层和运行时层之间的合同。

5. SpellCaster.cs
   看 ConfigureHoming 和 Init(useGravity) 如何把参数注入真实投射物。

6. ProjectileBase.cs
   看 Rigidbody.useGravity、ConfigureHoming、TickHoming、TryAcquireHomingTarget。

7. CastModifierStateTests.cs / CastEvaluatorTests.cs
   用测试反推规则：默认值、叠加、只影响后续、payload 继承。
```

这条阅读顺序对应的理解路径是：

```text
资产配置
-> 解释器状态
-> 发射命令
-> 运行时实例
-> Unity Physics / Projectile Runtime
```

只要这条链路掌握了，后续做“穿透”“分裂”“吸附”“返回施法者”等投射物修正法术，都会更容易判断该把代码放在哪里。
