# 陨石术与静态投射物：设计复盘

创建时间：2026-07-04  
功能范围：StaticProjectile / 静态投射物、Meteor / 陨石术、SkyfallAtPoint 生成模式、与 Modify / Multicast / Trigger Payload 的集成  
面向读者：战斗系统与法术编程系统初学者

---

## 0. 先用一句话建立整体理解

这次功能不是单纯做一个“陨石技能”，而是在法术编程系统里新增一种“产出类法术”：

```text
StaticProjectile / 静态投射物
```

普通 `Emit` 法术的语义是：

```text
从施法点沿发射方向飞出去
```

静态投射物的语义是：

```text
以当前释放点作为效果位置，在该位置生成某种存在物或效果
```

陨石术就是第一个静态投射物案例：

```text
释放点 / 命中点
-> 地面出现落点提示 NovaFireball_LandingSite
-> 延迟一小段时间
-> 空中生成 NovaFireball
-> NovaFireball 朝落点飞行
-> 落地后生成 NovaExplosion_Hit / FireField
-> AreaDamage 对范围内敌人造成伤害
```

更重要的是，最终我们把规则确定为：

```text
SpawnMode 只决定“投射物如何出生”
Modify 继续决定“投射物出生后如何运动、造成多少伤害”
```

所以陨石术也可以被 `增伤`、`加速`、`弹跳`、`追踪`、`轨道`、`重力` 等修正类法术影响。哪怕结果很怪，也允许它发生。因为法术编程系统的核心乐趣不是“设计师提前筛掉无用组合”，而是“玩家能实验出可解释的奇怪组合”。

## 1. 玩家最终看到的效果

### 1.1 单独释放陨石术

法杖排列：

```text
[陨石术]
```

玩家看到：

```text
玩家附近地面出现 NovaFireball_LandingSite
短暂延迟后，NovaFireball 从上方坠落
撞到地面或敌人后，生成 NovaExplosion_Hit 和 FireField
爆炸 / 火场对敌人造成范围伤害
```

因为静态投射物没有“传统发射方向”的概念，所以单独释放时，它以当前施法点附近作为效果位置。

### 1.2 配合触发类火球术

法杖排列：

```text
[触发火球] [陨石术]
```

玩家看到：

```text
先发射触发火球
火球命中敌人或环境
命中点出现落点提示
陨石从命中点上方砸下来
```

这个组合才是陨石术最典型的玩法。触发火球负责把“释放点”带到远处，陨石术负责在那个远处位置产生强力效果。

### 1.3 配合修正类法术

最终规则是：

```text
[增伤] [陨石术] -> 陨石直击、爆炸、火场伤害提高
[加速] [陨石术] -> 陨石下落速度提高
[弹跳] [陨石术] -> 陨石撞地后可能弹起来
[追踪] [陨石术] -> 陨石生成后可能朝敌人偏转
[轨道] [陨石术] -> 陨石可能进入轨道运动
[重力] [陨石术] -> 陨石受 Rigidbody gravity 影响
```

注意：如果加了运动类修正，`NovaFireball_LandingSite` 只代表“初始预测落点”，不再保证一定是最终命中点。这是有意保留的法术编程乐趣。

## 2. 该功能涉及的基础知识和原理

### 2.1 法术编程系统的解释器模型

本项目的法术系统不是“每个技能写一个独立技能类”，而是解释器模型：

```text
WandLoadout = 程序
SpellDefinition = 指令
CastEvaluator = 解释器
EmitCommand = 解释结果 / 运行时命令
SpellCaster = Unity 运行时桥接器
ProjectileBase = 投射物生命周期
AreaDamage = 范围伤害执行器
```

法杖里的每个格子不是单独技能按钮，而是一条指令。施法时系统从左到右读取这些指令，逐步累计状态，最后输出要生成的投射物命令。

这类似一个很小的脚本语言：

```text
Modify 指令：改变后续产出的参数
Multicast 指令：增加本次能产出多少个投射物
Emit / StaticProjectile 指令：真正产出运行时对象
```

### 2.2 “产出类法术”和“修正类法术”

在这个系统里，法术不是都一样的。它们可以分成几类：

```text
Emit：普通投射物，比如火球
StaticProjectile：静态投射物，比如陨石、火环、黑洞、地雷
Modify：修正后续产出，比如增伤、加速、弹跳、追踪
Multicast：改变产出数量，比如三重射击
```

关键点：

```text
Modify 自身不产出东西
Modify 只改变当前的 CastModifierState
后续第一个或多个产出类法术会把这个状态 bake 进 EmitCommand
```

所以 `[增伤] [陨石术]` 的含义不是“增伤直接攻击敌人”，而是：

```text
增伤更新当前修正状态
陨石术产出时读取这个修正状态
最终陨石命令里的 Damage 变大
```

### 2.3 静态投射物不是“不动的投射物”

“静态投射物”这个名字容易误解。它不是说这个东西不能移动，而是说：

```text
它的释放方式不依赖普通发射方向
它以某个世界位置作为效果位置
```

例如 Noita 里的很多法术也有类似语义：它们不一定从法杖口直线飞出去，而是在当前位置、命中点、指定点生成某种效果。

所以陨石术虽然是 `StaticProjectile`，但陨石本体 `NovaFireball` 仍然是 `ProjectileBase`，仍然可以有速度、碰撞、重力、追踪、弹跳、轨道。

### 2.4 触发 payload 的基础原理

触发类火球术的工作方式是：

```text
触发火球本身是一个 Emit
它捕获自己后面的法术作为 Payload
火球命中时，ProjectileBase.Impacted 事件触发
SpellCaster 在命中点重新运行 Payload
```

所以：

```text
[触发火球] [陨石术]
```

会变成：

```text
第一层施法：只生成触发火球
命中后第二层施法：在命中点运行 [陨石术]
```

这也是为什么陨石可以落在远处。

### 2.5 AOE 伤害和直击伤害的区别

陨石有两种伤害来源：

```text
直击伤害：NovaFireball 作为 ProjectileBase 撞到敌人时造成
AOE 伤害：NovaFireball 落地后生成 NovaExplosion_Hit / FireField，其中 AreaDamage 造成
```

一开始我们只让 `EmitCommand.Damage` 进入 `ProjectileBase.Init`，因此它只影响直击伤害。后来发现玩家实际感受到的陨石主要伤害来自爆炸，所以必须让 `AreaDamage` 也接收动态伤害快照。

这就是后来新增 `AreaDamage.ConfigureDamage(...)` 的原因。

## 3. 游戏开发中常见的实现方案

### 3.1 方案 A：把陨石写成一个独立技能脚本

做法：

```text
新建 MeteorSpell.cs
玩家按键时直接 Instantiate NovaFireball_LandingSite
然后延迟 Instantiate NovaFireball
落地后爆炸
```

优点：

```text
实现最快
逻辑集中
适合传统 ARPG 单个技能
```

缺点：

```text
无法自然融入法术编程
很难被 Modify / Multicast / Trigger Payload 组合
每加一个技能都要写一个特殊类
系统会从“解释器”退化成“技能表”
```

这个方案适合普通技能系统，不适合 Noita-like 法术编程系统。

### 3.2 方案 B：继续把陨石塞进 Emit

做法：

```text
Kind 仍然是 Emit
SpellDefinition 上加 SpawnMode
SpawnMode = SkyfallAtPoint 时走陨石生成
```

优点：

```text
不用新增 SpellKind
改动比新增类型少
```

缺点：

```text
Emit 的概念会变宽
普通投射物和静态投射物在设计层不容易区分
以后做火环、黑洞、地雷时，所有东西都挤在 Emit 里
对学习和面试表达不够清晰
```

这个方案技术上可行，但概念边界不够好。

### 3.3 方案 C：新增 StaticProjectile，但复用产出链路

最终采用这个方案。

做法：

```text
新增 SpellKind.StaticProjectile
新增 SpellSpawnMode.SkyfallAtPoint
CastEvaluator 把 Emit 和 StaticProjectile 都视为产出类法术
EmitCommand 快照保存 SpawnMode 和 Skyfall 参数
SpellCaster 根据 SpawnMode 决定如何生成运行时对象
NovaFireball / AreaDamage 继续复用已有战斗系统
```

优点：

```text
概念清晰：静态投射物是新的玩法分类
架构复用：不新建一套 StaticSpellCaster
组合自然：Modify / Multicast / Trigger Payload 都能继续工作
扩展性好：以后火环、黑洞、地雷都可以沿用这个类别
```

缺点：

```text
需要同时改数据层、解释器层、运行时层、战斗层
如果某一层漏了，就会出现“看起来配置了但运行时没生效”
```

这个方案最符合本项目的目标：做一个可扩展、可面试讲清楚的法术编程系统。

## 4. 最终用到的技术和 Unity API

### 4.1 ScriptableObject

使用位置：

```text
SpellDefinition
WandLoadout
SpellLibrary
```

作用：

```text
把法术数据做成 Unity 资产
设计师可以在 Inspector 中配置
新增法术时优先新建 asset，而不是写硬编码
```

陨石术对应的 `SpellDefinition` 关键字段：

```text
Kind = StaticProjectile
SpawnMode = SkyfallAtPoint
ProjectilePrefab = NovaFireball
LandingSitePrefab = NovaFireball_LandingSite
BaseDamage = 陨石基础伤害
BaseSpeed = 陨石下落速度
SkyfallHeight = 从落点上方多高生成
LandingSiteDuration = 落点提示显示多久后生成陨石
```

### 4.2 enum

新增：

```csharp
public enum SpellKind : byte
{
    Emit = 0,
    Modify = 1,
    Multicast = 2,
    StaticProjectile = 3,
}
```

为什么 `StaticProjectile = 3` 必须加在最后？

Unity 序列化 `enum` 时保存的是整数值。已有资产里：

```text
Emit = 0
Modify = 1
Multicast = 2
```

如果把新值插到中间，会导致已有资产的 `Kind` 错位。例如原本 `Multicast = 2` 的资产可能变成别的类型。这是 Unity 项目里扩展 enum 时非常重要的坑。

新增：

```csharp
public enum SpellSpawnMode : byte
{
    ForwardProjectile = 0,
    SkyfallAtPoint = 1,
}
```

`SpellKind` 解决“这是什么类型的法术”，`SpellSpawnMode` 解决“这个产出类法术如何生成运行时对象”。

### 4.3 readonly struct

`EmitCommand` 是 `readonly struct`。

作用：

```text
保存一次施法时的完整快照
避免运行时再回头读可变的 SpellDefinition asset
让 CastEvaluator 输出纯数据，SpellCaster 再消费纯数据
```

为什么这重要？

如果运行时一直引用 `SpellDefinition`，那么 Play Mode 中玩家编辑法杖或资产，可能影响已经生成的投射物。快照能保证：

```text
这颗陨石生成时的伤害、速度、修正参数已经固定
后续 asset 怎么变，不影响它
```

### 4.4 Coroutine 和 WaitForSeconds

使用位置：

```csharp
StartCoroutine(SpawnSkyfallProjectileAfterDelay(...));
yield return new WaitForSeconds(cmd.LandingSiteDuration);
```

作用：

```text
先显示落点提示
等待 LandingSiteDuration 秒
再生成 NovaFireball
```

`Coroutine` 是 Unity 中常用的延迟执行机制。它不是新线程，而是 Unity 在主线程中按帧推进的迭代器。

`WaitForSeconds` 会受 `Time.timeScale` 影响。也就是说如果游戏暂停，等待时间也会暂停。这个行为对当前功能是合理的，因为打开法杖编辑器时游戏本来就暂停。

### 4.5 Object.Instantiate

使用位置：

```csharp
Object.Instantiate(cmd.LandingSitePrefab, landingPoint, markerRotation);
Object.Instantiate(cmd.ProjectilePrefab, spawnPos, Quaternion.LookRotation(fallDir));
```

作用：

```text
生成落点提示
生成陨石本体
```

踩坑点：

一开始落点提示使用了：

```csharp
Quaternion.identity
```

这会强制实例的世界旋转为 `(0, 0, 0)`，覆盖 prefab 上设置的 `Rotation X = -90`。后来改成：

```csharp
Quaternion markerRotation = cmd.LandingSitePrefab.transform.rotation;
Object.Instantiate(cmd.LandingSitePrefab, landingPoint, markerRotation);
```

这样可以保留 prefab 自己的美术朝向。

### 4.6 Quaternion.LookRotation

使用位置：

```csharp
Quaternion.LookRotation(fallDir)
```

作用：

让陨石模型的前方向对准下落方向。

Unity 中 `Quaternion` 是旋转数据结构。`LookRotation(direction)` 会生成一个旋转，使物体的 `forward` 方向朝向 `direction`。

### 4.7 Rigidbody 和 Collider

`NovaFireball` 继承自 `ProjectileBase`，而 `ProjectileBase` 要求：

```csharp
[RequireComponent(typeof(Rigidbody))]
[RequireComponent(typeof(Collider))]
```

作用：

```text
Rigidbody：让投射物参与物理运动
Collider：让投射物能发生碰撞
OnCollisionEnter：碰撞时进入伤害和爆炸逻辑
```

`ProjectileBase.Init(...)` 中会设置：

```csharp
_rb.linearVelocity = velocity;
_rb.useGravity = useGravity;
_rb.collisionDetectionMode = CollisionDetectionMode.ContinuousDynamic;
```

相关 Unity API：

```text
Rigidbody.linearVelocity：Unity 6 中设置刚体线速度
Rigidbody.useGravity：是否使用 Unity 物理重力
CollisionDetectionMode.ContinuousDynamic：高速投射物使用的连续碰撞检测，减少穿透地面或敌人的概率
```

### 4.8 Physics.RaycastNonAlloc

使用位置：

```csharp
Physics.RaycastNonAlloc(origin, Vector3.down, _landingHits, 50f, ~0, QueryTriggerInteraction.Ignore);
```

作用：

```text
从释放点上方向下打射线
找到真正的地面点
让落点提示贴到地面，而不是悬在手部施法点
```

为什么用 `RaycastNonAlloc`？

普通 `Physics.RaycastAll` 会分配新数组，可能产生 `GC Alloc`。本项目性能规则要求热路径避免分配。这里虽然不是每帧，但仍然使用预分配数组更稳：

```csharp
private readonly RaycastHit[] _landingHits = new RaycastHit[8];
```

### 4.9 Physics.OverlapSphereNonAlloc

使用位置：

```csharp
Physics.OverlapSphereNonAlloc(transform.position, _radius, _buf, _hitMask, QueryTriggerInteraction.Ignore);
```

这是 `AreaDamage` 的范围检测。

作用：

```text
检测爆炸半径内有哪些 Collider
找到其父级上的 IDamageable
对敌人造成 DamageRequest
```

`NonAlloc` 的意义同样是避免每次范围伤害都分配数组。

### 4.10 GetComponentsInChildren

使用位置：

```csharp
AreaDamage[] areas = go.GetComponentsInChildren<AreaDamage>(true);
```

作用：

```text
爆炸 prefab / 火场 prefab 的 AreaDamage 可能挂在子物体上
所以不能只查根节点
```

参数 `true` 表示即使子物体当前 inactive，也能查到组件。

### 4.11 Destroy

使用位置：

```csharp
Object.Destroy(marker, Mathf.Max(0.05f, cmd.LandingSiteDuration + 0.5f));
Destroy(go, lifetime);
```

作用：

```text
落点提示显示一段时间后自动销毁
爆炸特效 / 火场在生命周期结束后自动销毁
```

这是临时 VFX 和投射物对象必须处理的生命周期问题。否则场景里会不断积累对象。

## 5. 架构设计与拆解

### 5.1 总体数据流

陨石术完整链路如下：

```text
WizardController
-> PlayerWizardAttackState
-> SpellCaster.CastWand
-> CastEvaluator.Evaluate
-> EmitCommand
-> SpellCaster.RunCast
-> SpawnSkyfallProjectile
-> NovaFireball / ProjectileBase
-> OnCollisionEnter
-> NovaFireball.OnImpact
-> NovaExplosion_Hit / FireField
-> AreaDamage
-> IDamageable.ReceiveHit
-> HealthComponent
```

每一层的职责不同：

```text
Game.Skills：解释法杖，输出纯数据
Game.Character：把纯数据变成 Unity 场景对象
Game.Combat：投射物、碰撞、伤害、AOE
Game.UI：只负责法杖编辑展示和拖拽，不参与运行时伤害
```

### 5.2 为什么不把陨石逻辑写进 CastEvaluator

`CastEvaluator` 属于 `Game.Skills`，它必须保持纯逻辑：

```text
不能 Instantiate
不能 Physics.Raycast
不能查场景对象
不能依赖 MonoBehaviour 生命周期
```

它只做：

```text
读取 SpellDefinition
维护 drawBudget / mana / CastModifierState
输出 EmitCommand
```

这样它可以被 EditMode tests 测试，也不会受 Unity scene 状态影响。

### 5.3 为什么用 EmitCommand 作为中间层

如果没有 `EmitCommand`，`SpellCaster` 可能会直接读 `SpellDefinition`：

```text
SpellCaster 读法术资产
SpellCaster 自己算修正
SpellCaster 自己处理 payload
```

这会导致职责混乱。

现在的拆分是：

```text
CastEvaluator 负责“算清楚本次应该产出什么”
EmitCommand 负责“保存这次产出的完整快照”
SpellCaster 负责“把快照落地成 Unity 对象”
```

这就是架构中的“解释器”和“运行时桥接器”分离。

### 5.4 StaticProjectile 如何融入现有法术架构

新增 `StaticProjectile` 后，最重要的语义是：

```text
它和 Emit 一样是产出类法术
它消耗 drawBudget
它能被 Multicast 增加数量
它能被 Modify 修正
它能作为 trigger payload 被捕获
```

代码上体现在 `CastEvaluator`：

```csharp
case SpellKind.Emit:
case SpellKind.StaticProjectile:
    ...
    output.Add(BakeEmit(spell, mods, ...));
    drawBudget--;
    break;
```

这意味着我们没有给静态投射物单独写一套解释器，而是把它纳入现有“产出类法术”的解释规则。

### 5.5 SpawnMode 的位置

`SpellKind.StaticProjectile` 表示：

```text
这是静态投射物类别
```

`SpellSpawnMode.SkyfallAtPoint` 表示：

```text
这个产出对象的出生方式是从天而降
```

这两个概念不能混成一个。

原因是未来可以继续扩展：

```text
StaticProjectile + SkyfallAtPoint：陨石
StaticProjectile + StaticArea：火环 / 毒池
StaticProjectile + PlaceMine：地雷
StaticProjectile + SummonAtPoint：召唤物
```

如果只靠 `SpellKind`，以后 enum 会膨胀成：

```text
Meteor
FireRing
BlackHole
Mine
Summon
```

这会让解释器变成技能表，不利于法术编程系统扩展。

### 5.6 陨石和 Modify 的最终规则

我们一开始做过一个保守设计：

```text
SkyfallAtPoint 不吃 Homing / Orbit / Bounce / Gravity
```

理由是希望陨石一定砸到预告落点。

但后来你指出这会削弱法术编程的乐趣。最终规则调整为：

```text
SpawnMode 只管出生方式
Modify 管出生后的行为
```

所以现在陨石生成后走同一个方法：

```csharp
ConfigureProjectileMotion(proj, cmd, index, count);
proj.Init(... useGravity: cmd.UseGravity);
```

这让陨石和普通投射物一样可以被运动类修正影响。

### 5.7 为什么 AreaDamage 要支持动态伤害

陨石本体的伤害来自 `ProjectileBase`：

```text
proj.Init(team, attackerId, cmd.Damage, cmd.DamageType, ...)
```

但陨石真正主要伤害来自爆炸：

```text
NovaExplosion_Hit -> AreaDamage
```

`AreaDamage` 原本只读 prefab 上的 `_damagePerHit`，导致：

```text
[增伤] [陨石术]
-> 陨石直击变强
-> 爆炸伤害不变
```

这不符合玩家直觉。因此新增：

```csharp
AreaDamage.ConfigureDamage(float damagePerHit, DamageType type)
```

然后 `NovaFireball` 在生成爆炸 / 火场后执行：

```csharp
areas[i].Init(_attackerId, _attackerTeam);
areas[i].ConfigureDamage(_damage, _type);
```

这样 AOE 也吃到 `EmitCommand.Damage` 的快照。

## 7. 踩坑与 Debug

### 7.1 Rider 显示大量红线，但命令行能编译

现象：

```text
Rider 中 SpellCaster 报 ConfigureBounce / ConfigureHoming / PhaseOffsetDegrees 等找不到
```

排查：

```text
dotnet build RPG.sln --no-restore /m:1
结果 0 errors
```

结论：

```text
代码真实编译没问题
Rider / Unity 项目模型缓存没有及时刷新
```

处理方式：

```text
Unity Editor 中 Assets -> Open C# Project
Rider 中 Invalidate Caches and Restart
优先看 Unity Console 的真实 CSxxxx 错误，而不是 IDE 临时红线
```

学习点：

IDE 红线不等于编译错误。定位 C# 问题时，命令行 build 和 Unity Console 更可靠。

### 7.2 落点提示方向不对

现象：

```text
Prefab 中 NovaFireball_LandingSite 设置 Rotation X = -90 后看起来正确
Play Mode 中生成出来方向仍然错误
```

根因：

代码生成 marker 时使用：

```csharp
Quaternion.identity
```

这会强制实例旋转为世界 `(0,0,0)`，覆盖 prefab 自己的旋转。

修复：

```csharp
Quaternion markerRotation = cmd.LandingSitePrefab.transform.rotation;
Object.Instantiate(cmd.LandingSitePrefab, landingPoint, markerRotation);
```

学习点：

`Instantiate(prefab, position, rotation)` 中传入的 `rotation` 会决定实例的世界旋转，不会自动保留 prefab 根节点 rotation。想保留 prefab 的旋转，就要显式传入 `prefab.transform.rotation`。

### 7.3 陨石看起来不吃增伤

现象：

```text
[增伤] [陨石术]
敌人受到的爆炸伤害没有变化
```

根因：

```text
Modify 已经影响了 EmitCommand.Damage
ProjectileBase.Init 也拿到了动态 Damage
但 NovaExplosion_Hit 的 AreaDamage 使用 prefab 上固定 _damagePerHit
```

也就是说，增伤只影响了陨石本体直击，没有影响玩家最直观看到的爆炸。

修复：

```text
AreaDamage 增加 ConfigureDamage
NovaFireball 生成爆炸 / 火场后，把 _damage / _type 注入给 AreaDamage
```

学习点：

当一个技能由多个伤害来源组成时，必须明确每个伤害来源是否吃同一套伤害快照。否则玩家会觉得“修正没生效”。

### 7.4 一开始屏蔽了运动类修正

现象：

```text
[追踪] [陨石术]
[弹跳] [陨石术]
[轨道] [陨石术]
效果不明显或完全不生效
```

根因：

早期代码里对 Skyfall 投射物写死：

```csharp
ConfigureBounce(0);
ConfigureHoming(0f, 0f, 0f);
ConfigureOrbit(0f, 0f, 0f, 0f);
useGravity: false;
```

设计初衷是保证陨石砸到落点。

后来调整设计原则：

```text
法术编程系统应该允许奇怪组合发生
设计师不应该提前替玩家判断组合有没有战斗价值
```

修复：

```csharp
ConfigureProjectileMotion(proj, cmd, index, count);
proj.Init(... useGravity: cmd.UseGravity);
```

学习点：

Noita-like 系统的核心不是“所有组合都平衡”，而是“组合规则一致且可解释”。如果组合很怪，只要不崩溃、不死循环、不严重破坏性能，就应该允许。

### 7.5 落点高度不对

潜在问题：

```text
直接使用施法点作为落点，可能让 LandingSite 悬在玩家手部高度
```

解决：

```csharp
Physics.RaycastNonAlloc(origin, Vector3.down, _landingHits, 50f, ~0, QueryTriggerInteraction.Ignore);
```

从释放点上方向下找地面，把落点修正到地面。

学习点：

3D 游戏中“一个点”经常不是地面点。尤其角色施法点通常在手部、胸口或武器口。要做地面提示，通常需要 raycast 到地面。

## 8. 设计原则总结

### 8.1 静态投射物不是独立系统

静态投射物应该是法术编程系统里的新法术类别，而不是绕开法术解释器的特殊技能。

正确链路：

```text
SpellDefinition
-> CastEvaluator
-> EmitCommand
-> SpellCaster
-> ProjectileBase / AreaDamage
```

错误方向：

```text
WizardController 里直接写 MeteorSpell
```

### 8.2 `Kind` 和 `SpawnMode` 要分开

`Kind` 表达语义类别：

```text
Emit / Modify / Multicast / StaticProjectile
```

`SpawnMode` 表达生成方式：

```text
ForwardProjectile / SkyfallAtPoint
```

这样未来扩展不会把系统变成一堆 hardcode 技能。

### 8.3 Modify 应该优先允许组合

最终规则：

```text
默认允许 Modify 作用于所有产出类法术
只有会导致崩溃、死循环、无限生成、严重性能问题时才禁止
```

这条规则是法术编程系统的核心。

### 8.4 伤害快照要覆盖所有伤害来源

如果一个法术有：

```text
直击
爆炸
火场
DoT
```

那么要明确每一类伤害是否吃 `EmitCommand.Damage`。

这次我们让 `NovaFireball` 的爆炸和火场都吃动态伤害，保证玩家的 `[增伤] [陨石术]` 直觉成立。

## 9. 模拟大厂面试 Q&A

### Q1：你为什么要新增 `StaticProjectile`，而不是直接把陨石做成普通 `Emit`？

答：

普通 `Emit` 的语义是从施法点沿方向发射投射物，而陨石这类法术的语义是以某个释放点或命中点作为效果位置，在该位置生成一个运行时效果。为了保持概念清晰，我新增了 `SpellKind.StaticProjectile` 表示静态投射物类别。同时我没有另起一套系统，而是让它复用 `CastEvaluator -> EmitCommand -> SpellCaster` 这条产出链路。这样它仍然可以被 `Modify`、`Multicast`、`Trigger Payload` 组合，符合 Noita-like 法术编程的解释器模型。

### Q2：为什么 `StaticProjectile = 3` 要加在 enum 最后？

答：

Unity 序列化 enum 时保存的是整数值。已有资产里 `Emit=0`、`Modify=1`、`Multicast=2`。如果我把新枚举插到中间，会导致已有 ScriptableObject 资产的 `Kind` 错位，可能把原来的 Multicast 资产解释成别的类型。因此新增 enum 值必须追加到末尾，保证历史资产兼容。

### Q3：`SpellKind` 和 `SpellSpawnMode` 的区别是什么？

答：

`SpellKind` 是解释器语义，表示这条指令在法杖程序中扮演什么角色，比如产出、修正、多重、静态投射物。`SpellSpawnMode` 是运行时生成方式，表示一个产出类法术如何被实例化，比如沿方向发射，或以某点为落点从天而降。把两者分开后，未来可以继续扩展更多生成模式，而不需要把每个具体技能都写进 `SpellKind`。

### Q4：为什么 `CastEvaluator` 不直接生成陨石？

答：

`CastEvaluator` 属于纯逻辑层，目标是可测试、可预测、不依赖场景。它不能调用 `Instantiate`、`Physics.Raycast` 或访问 MonoBehaviour 生命周期。它只负责解释法杖序列并输出 `EmitCommand`。真正的 Unity 对象生成放在 `SpellCaster`，这样架构边界清晰，`Game.Skills` 保持纯逻辑，`Game.Character` 作为运行时桥接层。

### Q5：为什么要用 `EmitCommand` 快照？

答：

`EmitCommand` 保存一次施法中已经计算好的结果，包括伤害、速度、修正状态、payload、spawn mode、skyfall 参数等。这样投射物生成后不需要再回读 `SpellDefinition`。这能避免运行时资产被修改影响已经发射的投射物，也让 `SpellCaster` 只消费纯数据，职责更清楚。

### Q6：陨石如何和触发火球联动？

答：

触发火球在解释阶段会捕获自己后面的法术作为 payload，但当前层只生成触发火球。火球命中时，`ProjectileBase.Impacted` 事件被触发，`SpellCaster` 在命中点用预算 1 重新运行 payload。如果 payload 是陨石术，那么 `SkyfallAtPoint` 会把命中点当作落点，生成落点提示并召唤陨石。

### Q7：为什么一开始陨石的增伤没有影响爆炸？

答：

因为陨石有多个伤害来源。`EmitCommand.Damage` 已经传给了 `ProjectileBase.Init`，所以直击伤害会被增伤影响。但爆炸来自 `NovaExplosion_Hit` prefab 上的 `AreaDamage`，它原本使用 Inspector 固定的 `_damagePerHit`，没有接收动态伤害快照。后来我给 `AreaDamage` 增加了 `ConfigureDamage`，并在 `NovaFireball` 生成爆炸和火场后注入 `_damage/_type`，这样爆炸和火场也能被增伤修正。

### Q8：为什么后来允许陨石吃追踪、弹跳、轨道、重力这些运动类修正？

答：

这是从玩法设计角度调整的。法术编程系统的核心乐趣是让玩家实验组合，而不是设计师提前判断组合是否“有用”。所以最终规则是：`SpawnMode` 只决定投射物如何出生，`Modify` 决定出生后的运动和数值。只要组合不会导致崩溃、死循环或严重性能问题，就应该允许它发生。这样即使陨石被追踪、弹跳或轨道改得很奇怪，也属于可解释的玩家实验结果。

### Q9：落点提示为什么需要 raycast？

答：

3D 游戏里施法点通常在角色手部或武器口，不一定在地面。如果直接把这个点作为落点提示位置，提示可能悬空。所以在 `SpellCaster` 中用 `Physics.RaycastNonAlloc` 从释放点上方向下检测地面，把 `LandingSite` 放到真实地面位置。使用 NonAlloc 版本是为了避免分配数组，符合项目避免不必要 `GC Alloc` 的性能规则。

### Q10：这个设计未来怎么扩展？

答：

未来可以继续扩展 `SpellSpawnMode`，例如 `StaticArea`、`PlaceMine`、`SummonAtPoint`。也可以扩展静态投射物内容，例如火环、黑洞、地雷、召唤物。因为现在静态投射物已经接入 `CastEvaluator` 和 `EmitCommand`，这些新法术天然可以被 `Modify`、`Multicast`、`Trigger Payload` 组合，不需要为每个法术写一套独立技能系统。

## 10. 模拟面试者完整讲解

如果我在面试中介绍这个功能，我会这样讲：

我在项目的 Noita-like 法术编程系统中新增了“静态投射物”类别，并用陨石术作为第一个落地案例。这个功能的目标不是单独写一个陨石技能，而是扩展法术解释器的表达能力，让系统支持“不沿施法方向发射，而是在指定位置生成效果”的法术。

原有系统中，法杖是一个 `WandLoadout`，每个法术是一个 `SpellDefinition`，施法时由 `CastEvaluator` 从左到右解释，输出一组 `EmitCommand`。`SpellCaster` 再把这些纯数据命令转成 Unity 场景中的投射物。为了接入陨石，我新增了 `SpellKind.StaticProjectile`，并且把它和普通 `Emit` 一样视为产出类法术。这样它会消耗 draw budget，也能被 `Multicast` 增加数量，被 `Modify` 修正数值和运动，被触发类法术作为 payload 捕获。

在数据层，我给 `SpellDefinition` 增加了 `SpawnMode`、`LandingSitePrefab`、`SkyfallHeight`、`SkyfallBackOffset`、`LandingSiteDuration` 等字段。这里我没有把陨石写死在代码里，而是把“怎么生成”做成数据配置。`SpellKind` 表示法术类别，`SpellSpawnMode` 表示运行时生成方式，比如普通投射物是 `ForwardProjectile`，陨石是 `SkyfallAtPoint`。

在解释器层，`CastEvaluator` 不负责生成陨石，也不访问 Unity 场景。它只把当前修正状态和法术数据 bake 成 `EmitCommand`。这样 `Game.Skills` 保持纯逻辑，可以做 EditMode 单元测试。`EmitCommand` 中保存了本次施法的完整快照，包括伤害、速度、弹跳、追踪、轨道、重力，以及 skyfall 参数。

在运行时层，`SpellCaster` 根据 `EmitCommand.SpawnMode` 分流。普通 `ForwardProjectile` 沿发射方向生成投射物。`SkyfallAtPoint` 则先用 `Physics.RaycastNonAlloc` 把释放点修正到地面，生成 `NovaFireball_LandingSite` 落点提示，然后通过 `Coroutine` 等待一段时间，再从上方生成 `NovaFireball` 并给它一个朝向落点的初速度。生成后它仍然调用统一的 `ConfigureProjectileMotion`，所以陨石也能吃弹跳、追踪、轨道、重力等运动类修正。

战斗层复用了已有的 `ProjectileBase`、`NovaFireball` 和 `AreaDamage`。`NovaFireball` 继承自 `ProjectileBase`，碰撞后在 `OnImpact` 中生成爆炸和火场。为了让 `[增伤] [陨石术]` 的结果符合玩家直觉，我给 `AreaDamage` 增加了 `ConfigureDamage`，让 `NovaFireball` 生成爆炸和火场后，把自身的动态 `_damage/_type` 注入给 AOE。这样增伤不仅影响陨石直击，也影响爆炸和火场。

这个功能开发中有几个关键 debug 点。第一个是落点提示方向问题，原因是我最初 Instantiate marker 时传了 `Quaternion.identity`，覆盖了 prefab 上的 `Rotation X=-90`，后来改为使用 prefab 自己的 `transform.rotation`。第二个是陨石看起来不吃增伤，根因是主要伤害来自 `AreaDamage` 的 prefab 固定值，而不是 `EmitCommand.Damage`，所以我补了动态伤害注入。第三个是运动类修正一开始被我屏蔽，后来基于法术编程系统的乐趣原则改为允许组合，明确 `SpawnMode` 只控制出生方式，`Modify` 控制出生后的行为。

整体上，这个功能的核心价值是：我没有为了陨石写一套特殊技能系统，而是扩展了解释器的指令集和运行时生成模式。这样未来做火环、黑洞、地雷、召唤物等静态投射物时，都可以沿用这套结构，并天然接入法术编程的组合规则。
