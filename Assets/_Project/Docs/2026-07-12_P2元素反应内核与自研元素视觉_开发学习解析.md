# Task 1：建立可复用、可测试的元素反应规则内核

## 1. Task 目的与实际成果

Task 1 的目标不是马上让场景出现蒸汽、毒爆或粘液燃烧，而是先建立一套独立于角色、环境 Cell 和视觉表现的“元素反应语言”。过去 `Burning`、`Wet` 等概念更接近角色 Buff；如果直接把所有交互写进 `StatusController.Update()`，未来 P6 环境 Cell 还要重新实现一遍，而且规则会与 `MonoBehaviour` 生命周期、`Time`、`Physics`、VFX 混在一起，很难测试和复用。因此本 Task 抽象出 Fire、Water、Poison、Goo 四条 `ElementChannel`，用只读 `ElementStateSnapshot` 描述一次计算看到的元素事实，用 `StatusSource` 保存攻击者归属，用一组可序列化 Tuning 保存阈值和倍率，再由无状态的 `ElementReactionEvaluator` 负责正式灭火、Wet Cleanse、Toxic Combustion、Ignite Goo 的启动判断与基础公式。最终得到的是一个位于 `Game.Combat` 底层的纯规则内核：它还不操作角色和场景，却为 Task 2 连续状态机、Task 3 角色 Adapter，以及未来环境模拟提供了唯一且确定的规则来源。

玩家在 Task 1 完成后暂时看不到新的视觉效果，这是有意的。该阶段交付的是“可证明正确的数学与数据边界”，不是表现层。类似做法在商业项目中很常见：先把决定胜负、伤害和资源消耗的规则做成 deterministic core，再由 Unity Runtime 和 Rendering 层执行与呈现。

## 2. 需要理解的基础知识和设计原则

### 纯函数与 Determinism

`ElementReactionEvaluator` 的方法只读取参数并返回结果，不读取或修改共享状态。同一份 Snapshot、Tuning 和 `deltaTime` 总会得到相同结果，这就是这里需要的 **Determinism**。它使 NUnit EditMode 测试不需要启动 Scene，也让错误可以被定位为“输入错、公式错或 Adapter 错”，而不是所有逻辑混在一个 `Update()` 中。

纯函数不等于整个系统自动线程安全，也不意味着代码已经能直接搬进 Burst/Job System。当前只是没有共享可变状态；上层未来仍会接触 `MonoBehaviour`、`Physics` 和 `EventBus`，它们受 Unity Main Thread 约束。

### `enum : byte` 与序列化稳定性

`ElementChannel`、`ElementReactionId` 都显式使用 `enum : byte`。`enum` 给整数赋予业务含义；底层 `byte` 只占一个字节，适合未来放入 Cell、Mask 或紧凑 Snapshot。更关键的是每个成员都显式指定整数值，因为 Unity 会序列化枚举的数值。如果将来随意插入或重排成员，旧 Asset 中保存的数值可能被解释成另一个元素。

因此测试不仅检查名称，也锁定数值。这不是“测试语言语法”，而是在保护未来 ScriptableObject、Prefab 和存档兼容性。

### `readonly struct` 与 Value Snapshot

`StatusSource` 和 `ElementStateSnapshot` 使用 `readonly struct`。`struct` 是值类型，传递时携带一份值语义快照；`readonly` 表示构造后字段不能被修改。一次反应判断先从载体读取 Fire/Water/Poison/Goo，再形成 Snapshot，Evaluator 在整次计算中看到的是同一份事实。

这避免了典型顺序错误：如果规则一边读取 `StatusController` 一边立刻修改，先执行灭火还是先执行毒爆会改变后续判断；Snapshot + Result 则让流程变成“先读 → 统一计算 → 再写回”。这与现有 `DamageRequest` 的 Value Snapshot 思想一致：攻击者即使随后被销毁，已经产生的计算输入也不会失效。

### Source 为什么只保存 Id 和 Team

DoT 或延迟反应可能晚于施法者 GameObject 的生命周期。如果保留 `GameObject`、`Transform` 或 `HealthComponent` 引用，来源销毁后可能变成 Unity 的伪空引用；同时纯逻辑会被迫依赖场景对象。`StatusSource` 只保存 `AttackerId` 和 `AttackerTeam`，足以支持伤害归属、阵营过滤和事件追踪，又保持规则层与场景解耦。

### Tuning 与数据驱动

阈值、速率和倍率不能散落为 Magic Number。Task 1 使用带 `[Serializable]` 的 Tuning struct，例如 `ExtinguishTuning`、`WetCleanseTuning`、`ToxicCombustionTuning`、`IgniteGooTuning`。`[Serializable]` 是 Unity/C# Attribute，使字段未来能作为其他可序列化对象或 `ScriptableObject` 的子数据出现在 Inspector 中；Task 1 尚未创建最终 Profile Asset，但数据形状已经与规则算法分离。

数据驱动不代表“所有数字都必须立即做成 ScriptableObject”。先定义最小 Tuning 类型可以避免过早引入 Asset 生命周期和 Editor 配置；Task 3 再建立供角色使用的 Profile，职责会更清晰。

## 4. 核心公式与运行链路

### 启动阈值

正式灭火要求 Fire 与 Water 都达到阈值，并使用包含边界的 `>=`。例如阈值为 10 时，`9.99/100` 不正式触发，`10/10` 正式触发。Toxic 同时检查 Fire 与 Poison；Ignite 同时检查 Fire、Goo、Wet 抑制阈值，以及 Fire 是否还有足够容量接收 Goo 转换结果。

Ignite 的剩余容量计算为：

```text
RemainingFireCapacity = 100 - Clamp(Fire, 0, 100)
```

容量检查避免 Fire 已接近 100 时仍启动一个马上无法推进的 Process，也为 Task 2 的转换守恒提供前置条件。

### Wet Cleanse 的有限预算

需求规定 Wet 通常会加速负面状态下降，并且同时存在 Poison 与 Goo 时先清 Poison、再清 Goo。如果分别计算两个独立倍率，就会让同一份 Wet 能力被重复消费。因此先生成有限 Budget：

```text
NormalizedWet = Clamp(Wet, 0, 100) / 100
Budget = FullWetBudgetPerSecond × NormalizedWet × deltaTime
```

然后按顺序分配：

```text
PoisonRemoved = min(Poison, Budget × PoisonMultiplier)
Budget -= PoisonRemoved / PoisonMultiplier
GooRemoved = min(Goo, Budget × GooMultiplier)
```

这里除以 PoisonMultiplier 是把“实际清掉的 Poison”换算回消耗了多少基础 Budget。如果 Poison 用完还有余额，Goo 才能获得剩余部分；如果 Poison 吃满预算，Goo 本帧不下降。这比两个独立 decay multiplier 更准确地表达资源优先分配。

Evaluator 会防御负数 Tuning、零倍率、负 `deltaTime` 和超范围强度，使用 `MaxZero`、`Clamp`、`Min` 保证公式不会输出负清洗量或除以零。防御性数学不是掩盖配置错误；未来 Profile 验证仍应提示非法 Inspector 数据，但纯内核必须保证错误输入不会扩散为 NaN 或负状态。

## 5. 方案选择、测试与 Debug

可以选择的方案包括：直接在 `StatusController.Update()` 写 if/else、为每个反应制作 `MonoBehaviour`、用反应组合查表，或者建立纯 Evaluator。直接写 Controller 最快但耦合最重；多个 MonoBehaviour 便于 Inspector 观察，却使执行顺序、生命周期和跨载体复用变复杂；组合查表适合离散合成配方，却不擅长连续清洗和强度公式。因此最终选择“抽象 Channel + Snapshot + Tuning + 纯 Evaluator”，用少量明确代码换取可测试性和未来 Cell 复用。

开发采用 TDD：先写期望 API 和边界用例，确认类型缺失导致 Red，再补最小实现直到 Green。`ElementReactionEvaluatorTests` 共 15 个测试实例，覆盖：

- enum 序列化整数稳定；
- Extinguish 阈值是否包含等号；
- Wet Cleanse 是否严格先 Poison 后 Goo；
- Poison 消耗满 Budget 时 Goo 是否保持不变；
- Toxic 是否必须同时满足 Fire/Poison；
- Ignite 是否在 Wet=10 时被禁止；
- Fire 剩余容量是否足够。

当 Task 1 规则出错时，建议按“Snapshot 输入 → Tuning → Evaluator Result → Adapter”由内向外检查。Wet Cleanse 最值得手算 Budget：如果 Poison 尚未清完而 Goo 同时下降，优先检查是否给两个状态重复使用了完整预算。不要先怀疑 Unity 生命周期，因为本层根本没有生命周期依赖。

## 6. 完成边界与面试表达

Task 1 已完成元素词汇、来源/状态 Snapshot、数据 Tuning、阈值判断、Wet Cleanse 预算公式以及纯逻辑测试；尚未实现跨帧 Process、生命周期阶段、状态写回、实际伤害、EventBus 和视觉。这些不是遗漏，而是架构分层：Task 1 只负责“事实和公式”。

# Task 2：实现连续元素反应 Runtime

## 1. Task 目的与实际成果

Task 2 的目标，是把 Task 1 中“某一刻是否满足条件”的静态公式，发展为能够跨越许多帧保存历史的连续反应执行器。真实玩法并不是每帧互不相关的 if/else：正式灭火从 `80 Fire + 30 Water` 启动后应稳定推进到 `50 Fire + 0 Water`；Toxic Combustion 要经历 Wind-up，预热期间仍可能被 Wet Cleanse 削弱；Ignite Goo 遇到足够 Wet 时需要暂停，Wet 降低后再恢复，而不是反复销毁和新建反应。为此我们创建普通 C# 类 `ElementReactionRuntime`，以三个固定 Process 字段保存 Extinguish、Toxic、Ignite 的运行状态；每次 `Tick` 读取 Snapshot 和 `deltaTime`，返回一个值类型 `ElementReactionFrame`，其中描述四种状态 Delta、自然衰减抑制 Mask、可选范围伤害命令以及离散生命周期 Signal。它仍然不直接操作 `StatusController`、`Physics`、`EventBus` 或 VFX，因此连续规则保持可测试、可复用和 0 GC 友好；真正接入 Unity 角色生命周期属于 Task 3。

本 Task 还通过 30 FPS 与 120 FPS 测试证明正式灭火结果与帧率无关，并在测试过程中发现并修复了“正式反应中途跌破阈值后错误降档”的真实设计 Bug。同时我们纠正了一条错误测试预期：Wet 暂停 Ignite 只代表停止 Goo→Fire 转换，并不妨碍更高优先级的 Wet Cleanse 继续清理 Goo。

## 2. 连续模拟、状态机和生命周期原理

### Frame-rate Independence

Unity 游戏逻辑以离散帧运行。要表示“每秒消耗 50”，必须使用：

```text
本帧消耗 = RatePerSecond × deltaTime
```

30 FPS 时单帧步长约 `1/30`，120 FPS 时约 `1/120`；每帧量不同，但一秒累计应相同。Runtime 没有直接读取 `Time.deltaTime`，而是让 Adapter 把 `deltaTime` 作为参数传入：测试可以主动模拟不同帧率，未来 Cell 也可以选择固定 Simulation Step。

最后一步使用 `min(CurrentAmount, FrameBudget)`，保证状态不会穿过零。浮点比较使用小的 `Epsilon` 处理累计误差，而不是期待二进制浮点恰好等于 0。

### 为什么需要有状态 Runtime

Task 1 Evaluator 是无状态的，无法记住“上一帧已启动”。Runtime 保存：Process 是否 Active、是否 Paused、Wind-up 已经过多久、计划/实际消费量、Cooldown 和触发来源。它因此属于 **Stateful Domain Runtime**，但不是 Unity Component。

Runtime 使用 `MarkDirty(source)` 通知“外部输入发生了值得重新评估的变化”。`Tick` 并非每帧无条件重新创建反应：只有 Dirty 时检查新 Process，已经 Active 的 Process 则继续推进。`CancelAll()` 用于未来载体死亡或禁用时统一产生 Cancelled Signal 并清理状态。

生命周期使用 `Started / Paused / Resumed / Resolved / Cancelled`：Started 让视觉开始；Paused/Resumed 表达 Process 仍存在但暂不推进；Resolved 表示正常完成；Cancelled 表示死亡、禁用或条件不足导致非正常终止。表现层必须区分 Resolved 和 Cancelled，例如毒爆正常完成才应播放爆炸，取消只清理预热 VFX。

### 固定 Process 与通用集合的取舍

业界常见替代方案是 `List<ReactionProcess>` 加多态基类或 Interface，新增反应容易，但需要处理对象创建、集合扩容、遍历顺序、回收和虚调用。本阶段只有三条确定反应，又明确要求 Update 热路径避免分配，因此选择三个固定 Process 状态字段。优点是同类不会重复、顺序显式、容量可证明、调试直接；缺点是反应数量大量增长时类会膨胀。未来若规模确实增长，可迁移到预分配数组或固定容量 Pool，而不是现在提前建设通用框架。

Task 2 没有调用 Unity 内置运行 API。`deltaTime` 是外部传入的普通 `float`，没有直接读取 `UnityEngine.Time`；范围伤害只是 `ReactionDamageCommand` 数据，没有调用 `Physics.OverlapSphereNonAlloc`；生命周期只是 Signal 数据，没有发布 `EventBus<T>`；视觉没有 `Instantiate`。这种刻意的“不执行”是架构边界：Runtime 决策，Adapter/Resolver 执行，Rendering 呈现。

`StatusMask` 使用 `[Flags]`，每个状态占一个 bit，例如 Fire=`1<<0`、Water=`1<<1`，可以用按位 OR 同时表示多个自然衰减应被反应接管：

```csharp
frame.SuppressNaturalDecay |= StatusMask.Fire | StatusMask.Water;
```

Task 3 读取 Mask 后避免同一状态既被 Reaction 消耗、又在同帧重复执行普通衰减。

架构链路如下：

```text
Task 1 Snapshot + Evaluator + Tuning
                  ↓
Task 2 ElementReactionRuntime
                  ↓ ElementReactionFrame
Task 3 StatusController Adapter
       ├─ 把 Delta 写回 Status
       ├─ 依据 Mask 处理普通衰减
       ├─ 把 Signal 发布为 ElementReactionEvent
       └─ 把 DamageCommand 交给伤害执行层
                  ↓
Task 4 NonAlloc 范围伤害 / Task 6+ 自研视觉
```

## 4. Runtime 的确定执行顺序与三条反应

每帧按以下顺序处理：

```text
更新 Cooldown
→ Dirty 时检查并启动新 Process
→ Extinguish
→ Wet Cleanse（先 Poison，后 Goo）
→ Toxic Wind-up / Resolve
→ Ignite Goo
```

“多个 Process 能同时 Active”不代表没有优先级。只要它们会修改相同资源，就必须固定顺序，否则结果会受代码遍历顺序影响。Wet Cleanse 排在 Toxic 推进之前，因此预热期间清洗会减少毒爆实际消费与伤害；Ignite 排在最后，而且 Wet 只暂停 Ignite 转换，不阻止 Cleanse。

### Extinguish：启动阈值与持续规则分离

正式灭火达到阈值后发布 Started，并锁存正式模式：

```text
Consumed = min(Fire, Water, FormalRate × deltaTime)
FireDelta = -Consumed
WaterDelta = -Consumed
```

直到一方为零再 Resolved。关键点是阈值只用于“能否启动”，不是每帧重新决定速率。第一次实现每帧检查正式阈值，Water 从 30 降到 10 以下后错误切换到低速，导致 `80/30` 一秒后约为 `57/0`；30/120 FPS 测试暴露问题后，改为 `_extinguishFormalSignalled` 锁存高速模式，最终稳定得到 `50/0`。

阈值以下仍允许低速中和，满足“未达到特殊反应阈值时仍有基础交互”的需求，但不会发布正式 Steam Started Signal。

### Toxic Combustion：计划消费、实际消费和 Command

启动时保存触发 Source、计划消费量和 Wind-up；每帧逐步消费 Poison。Wind-up 结束时以 `_toxicConsumed` 而非最初 Poison 计算：

```text
Damage = BaseDamage + ActualConsumedPoison × DamagePerPoison
```

如果 Wet Cleanse 抢先削弱 Poison，实际消费和伤害都会下降；低于 `MinEffectiveConsume` 则发 Cancelled，不凭空产生爆炸。成功时 Runtime 设置 `HasAreaDamage` 并输出 `ReactionDamageCommand(Source, Amount, Radius)`，Task 4 才通过 `Physics.OverlapSphereNonAlloc` 和现有 `IDamageable.ReceiveHit` 漏斗执行范围伤害。

### Ignite Goo：转换、容量与 Wet 暂停

Ignite 每帧按 `GooConsumePerSecond` 消费 Goo，以 `FirePerGoo` 生成 Fire，同时受 Fire 100 上限限制。Wet 达到 `WetInhibitThreshold` 时仅把 Ignite 切换为 Paused 并发一次 Signal；持续 Wet 不会每帧重复发 Paused。Wet 降低后发一次 Resumed，本帧不立即转换，下一帧继续，给 Event/VFX 一个清晰生命周期边界。

此时 Wet Cleanse 依然能减少 Goo。最初测试错误地断言“Paused 时 GooDelta=0”，但这与已经确认的全局规则冲突：Wet 应持续帮助玩家清理负面 Buff。正确断言是 Ignite 不增加 Fire，而 Cleanse 仍让 Goo 下降。

## 5. Frame Result、0 GC、测试和 Debug

### 为什么 Frame 使用固定 Signal Slot

`ElementReactionFrame` 使用 `Signal0/Signal1/Signal2 + SignalCount`，而不是 `List<ReactionSignal>`。当前只有三条固定 Process，同一帧生命周期变化的上限可以显式约束。这样 Tick 不需要创建数组或 List，也不会扩容。超过容量时当前实现不再加入；若未来增加反应，必须同步扩大容量或引入预分配 Buffer，并新增溢出测试，不能默默依赖旧上限。

新 Process 的启动帧只发送 Started，从下一 Tick 才推进，避免同一 Process 在一帧内 Started 又 Resolved，既减少 Signal 峰值，也让视觉至少拥有一个稳定的启动边界。

### 热路径性能设计

- Runtime 计划由 Adapter 在 `Awake()` 创建一次并复用；
- 三个 Process 使用字段，不在 Tick 中 `new` 状态对象；
- Snapshot、Frame、Signal、DamageCommand 使用值类型；
- 无 LINQ、Closure、Delegate、字符串拼接或动态集合；
- 不在 Runtime 内执行 Physics、EventBus、VFX Instantiate。

使用 struct 不自动等于 0 GC：Boxing 到 `object`/非泛型接口、Closure 捕获和集合扩容仍会分配。当前只能从代码结构说明“没有明显托管分配点”；最终必须在 Task 11 用 Unity Profiler 验证热路径 `GC Alloc = 0 B`。

### 测试覆盖与结果

`ElementReactionRuntimeTests` 有 11 个测试实例，覆盖：

- 30 FPS 与 120 FPS 的 `80/30 → 50/0` 一致性；
- 阈值以下使用低速灭火；
- Toxic 只在 Wind-up 后结算，并按实际消费产生伤害；
- Wet Cleanse 降低 Toxic 实际消费和伤害；
- Ignite 一秒 Goo→Fire 转换；
- Wet 阈值触发 Paused/Resumed，同时 Cleanse 继续；
- `MarkDirty` 不重复创建 Active Process；
- Extinguish、Toxic、Ignite 可同时 Active，且不突破 Signal Budget；
- `CancelAll` 阻止待结算 Toxic 伤害；
- `deltaTime=0` 不推进过程。

结果为新增 11/11，通过；加 Task 1 后元素反应专项累计 26/26；`dotnet build Game.Combat.Tests.csproj --nologo --no-restore` 为 0 Warning、0 Error。Unity Test Runner 中曾误选父节点触发包含 PlayMode 的全项目测试，已取消；因此本文只记录实际获得的专项与编译证据，不把那次误触发描述为完整回归通过。

### Debug 顺序

出现问题时先检查输入 Snapshot 和 Tuning；再确认外部变化是否调用 `MarkDirty`；然后观察对应 Process 的 Active/Paused、Elapsed、Cooldown；手算 `Rate × deltaTime` 与末帧 Clamp；检查输出 Frame 的 Delta、Mask、DamageCommand、Signal。Task 3 接入后才继续检查状态写回、EventBus 和 VFX。这个顺序能把纯数学 Bug、状态机 Bug、Adapter Bug 和表现 Bug 分开。

# Task 3：把 StatusController 改造成角色 Adapter

## 1. Task 目的与实际成果

Task 3 的目标，是把前两个 Task 中完全脱离场景的 Reaction Kernel 接入现有角色状态系统，让 `Burning/Wet/Poisoned/Sticky` 成为纯 Runtime 与 Unity 世界之间的 Adapter。此前 `StatusController` 自己遍历四种状态、计算自然衰减、用 `_wetExtinguishBurningPerSecond` 额外加速 Burning，并在同一循环中处理 DoT、VFX 和事件；这种写法只能表达“Wet 让 Burning 掉得更快”，无法承载正式灭火、Wet Cleanse、Toxic Wind-up、Ignite 暂停等跨帧语义，也会与 Task 2 Runtime 重复计算。本 Task 删除旧的专用灭火字段，引入 `ElementReactionProfile` 作为数据入口；`StatusController` 每帧先构建只读 Snapshot，调用 Runtime 得到 `ElementReactionFrame`，再统一写回 Delta、依据 `StatusMask` 避免自然衰减重复扣除、最后按反应后的最终强度结算 DoT。Runtime 的生命周期 Signal 被转换成 `ElementReactionEvent` 发布给未来 Rendering，而范围毒爆 DamageCommand 暂留到 Task 4 执行。结果是原有 `StatusController` 从“规则拥有者”转变为“Unity Adapter”：它仍管理状态实例、旧 VFX 和角色组件生命周期，但元素交互的唯一规则来源已经下沉到可测试内核。

这个 Task 是 P2 第一次真正跨过纯逻辑与 `MonoBehaviour` 的边界。新增集成测试证明 `ApplyStatus` 当帧只建立反应，不瞬间跳变；下一次 0.6 秒 Tick 才把 `80/30` 连续推进到 `50/0`；Wet=40 时清洗预算严格先给 Poison；Started 只发布一次离散事件。测试还暴露了 Unity EditMode 中 `Awake` 不保证先于直接 API 调用的生命周期差异，因此事件发布边界增加了安全的 TargetId 初始化，但没有把 `GetInstanceID()` 放进逐帧路径。

## 2. Adapter Pattern、Unity 生命周期与 Tick 顺序

**Adapter Pattern** 的作用，是把两个接口形状不同但语义兼容的系统连接起来。Reaction Runtime 只理解 Fire/Water/Poison/Goo、Snapshot 和 Frame；现有角色系统使用 `StatusKind`、`StatusInstance`、`HealthComponent`、VFX 与 EventBus。`StatusController` 负责映射：

```text
StatusInstance[Burning/Wet/Poisoned/Sticky]
                    ↓ BuildReactionSnapshot
ElementStateSnapshot[Fire/Water/Poison/Goo]
                    ↓ Runtime.Tick
ElementReactionFrame
                    ↓ ApplyReactionFrame
状态写回 / EventBus / 后续 Damage Resolver
```

这一拆分的关键是“谁负责决策、谁负责执行”：Runtime 决定数值和阶段，Adapter 负责访问 Unity Object。`Game.Combat` 仍没有依赖 `Game.Character` 或 `Game.Rendering`，所以敌人、玩家都能使用同一个 `StatusController`；Rendering 未来只订阅 `ElementReactionEvent`，不会反向修改 Gameplay。

`Awake()` 缓存 `IDamageable`、TargetId、StatusDefinition，并创建 Reaction Runtime；`OnEnable()` 订阅 `DeathEvent`，`OnDisable()` 成对取消订阅并调用 `CancelAll()`。这样角色死亡或组件禁用时，预热中的 Toxic、暂停的 Ignite 等 Process 不会留下 stale state，表现层也能收到 Cancelled 进行清理。

新的 Tick 顺序是：

```text
Build Snapshot → Runtime.Tick → ApplyReactionFrame
→ ApplyNaturalDecay（跳过 Suppress Mask）
→ TickDamageOverTime（读取最终强度）
→ 清理归零状态、发布 StatusChangedEvent
→ 重算移动速度
```

顺序本身就是玩法规则。DoT 放在 Reaction 和自然衰减之后，保证本次伤害使用清洗/灭火后的最终强度；`StatusMask` 防止一个被 Reaction 接管的状态在同帧又执行普通衰减。Wet Cleanse 没有在 Adapter 中重新实现，因为 Task 2 Runtime 已负责有限预算；重复实现会让 Poison/Goo 一帧清洗两次。

## 4. 核心实现链路与重要细节

`ApplyStatus` 仍负责叠加强度、Clamp 到 0~100、更新外部来源和初始化 DoT Timer。区别是写入后调用 `MarkDirty(new StatusSource(sourceId, sourceTeam))`，随后用零时间步 `Tick(snapshot, 0)`：这一步只建立满足条件的 Process 并发布 Started，不消费元素。这样同帧 UI 能知道反应开始，又不会出现用户明确禁止的“80/30 瞬间变 50/0”；下一次 `TickForTests(0.6)` 或正常 `Update` 才按 Rate×deltaTime 连续推进。

`ApplyReactionFrame` 只修改 Intensity，不修改 Source。原因是 Cleanse/Extinguish 是现有状态之间的内部演化，不是一次新的外部施加；若每帧覆盖 Source，Poison DoT 的伤害归属会被 Wet 来源抢走。只有 `ApplyStatus` 能更新 Source，这保持了攻击者归属的因果关系。

`SuppressNaturalDecay` 是 `[Flags] enum`：Runtime 用 bit 表示本帧哪些状态已由反应消费，Adapter 通过按位 AND 判断是否跳过普通衰减。它解决的是“同一职责重复执行”，而不是暂停整个状态。未被 Mask 的 Poison/Sticky 仍可按 Definition 自然衰减。

Reaction Signal 会同步转换为 `ElementReactionEvent`。这里只发布 Started/Paused/Resumed/Resolved/Cancelled，不发布逐帧 Progress；连续强度本身已经通过 `StatusChangedEvent` 提供给状态材质。若每帧都走 EventBus，会扩大调用量、让表现层难以区分生命周期边界，也增加 Debug 噪声。

本 Task 故意不执行 `frame.AreaDamage`。`StatusController` 已看见这个 Command，但真正的 `Physics.OverlapSphereNonAlloc`、Team Filter、重复 Collider 去重和 `DamageRequest` 要由 Task 4 的专用 Resolver 负责。Adapter 不能为了“先看到效果”把范围查询临时塞进 Tick，否则下一 Task 又要拆除。

# Task 4：实现 Toxic Combustion NonAlloc 范围伤害

## 1. Task 目的与实际成果

这个 Task 同时完成了纯 Kernel 与 Unity Physics 的第二条关键桥梁：Task 3 负责状态写回和事件，Task 4 负责范围伤害执行。我们没有把 Physics 放进 `ElementReactionRuntime`，因为 Runtime 仍要被未来 P6 Cell 和无 Scene 测试复用。PlayMode 测试通过代码创建中心目标、敌对目标、来源同队目标和带两个 Collider 的目标，直接验证敌我过滤、中心伤害、去重、来源归属、伤害数值以及取消命令。最终 Task 4 专项 2/2、Combat 56/56、C# Build 0 Warning/0 Error。

## 2. 从纯 Command 到 Unity Physics 的职责边界

完整链路现在是：

```text
ElementReactionRuntime
  → ReactionDamageCommand(Source, Amount, Radius)
  → ElementReactionFrame.HasAreaDamage
  → StatusController.ApplyReactionFrame
  → AreaReactionDamageResolver.Resolve
  → Physics.OverlapSphereNonAlloc
  → IDamageable.ReceiveHit(in DamageRequest)
  → HealthComponent / DamagePipeline / DamageReceivedEvent / DeathEvent
```

Runtime 只决定“应当在当前位置发生半径多大、数值多少、归属谁的伤害”，Resolver 决定“Unity 场景里哪些 Collider 对应可受伤目标”。这属于 **Command Pattern** 与 **Adapter/Executor** 的组合：Command 是可测试的意图，Executor 接触副作用。若把 `Physics.OverlapSphereNonAlloc` 写进 Runtime，纯测试必须创建 Physics Scene，未来 Cell 也无法在 Job 或离线模拟中复用规则。

Resolver 是普通 C# 对象而非 `MonoBehaviour`，因为它不需要独立的 Unity 生命周期和 Inspector 数据。`StatusController.Awake()` 预创建一次 Resolver；只有 EditMode 工具在 `Awake` 前调用公开 API 时才在 DamageCommand 分支低频兜底创建。正常游戏 Tick 不会重复 `new` Resolver、Collider 数组或 HashSet。

## 4. NonAlloc 查询、敌我过滤和去重原理

`Physics.OverlapSphereNonAlloc(center, radius, buffer, layerMask, queryTriggerInteraction)` 把命中的 Collider 写入调用者提供的数组，并返回实际写入数量。与返回新 `Collider[]` 的 `Physics.OverlapSphere` 相比，它避免每次毒爆创建结果数组。Resolver 构造时一次性创建 `Collider[32]`，后续反复复用。

当前 LayerMask 使用 `Physics.AllLayers`，因为项目尚未建立专用 Damageable Layer；`QueryTriggerInteraction.Collide` 让 Hurtbox Trigger 也能被查询。之后如果场景 Collider 数量增大，应通过专用 LayerMask 缩小 Broad Phase 候选，而不是先盲目扩大 Buffer。

一个角色经常有 `CharacterController`、身体 Collider、受击 Trigger 等多个碰撞体。Physics 返回的是 Collider，不是角色，因此仅遍历命中会造成一次毒爆重复扣血。Resolver 对每个 Collider 调用：

```text
hit.GetComponentInParent<IDamageable>()
```

这样子物体 Hurtbox 可以找到父物体的 `HealthComponent`。随后把实现 `IDamageable` 的 Component 转成 InstanceID，并加入预创建的 `HashSet<int>`；`Add` 返回 false 说明本次 Resolve 已处理过该目标，立即跳过。每次查询前只调用 `Clear()`，HashSet 保留内部 Bucket，不重新分配。

筛选顺序为：Collider 有效 → 找到活着的 `IDamageable` → Team 与 Source.Team 不同 → InstanceID 首次出现。先做低成本判断再去重，减少 HashSet 操作。伤害方向使用目标位置减爆炸中心并 Normalize；中心目标方向长度接近 0 时使用 `Vector3.up`，避免零向量进入反馈系统。

固定 Buffer 的 trade-off 是命中超过 32 个 Collider 时，额外目标不会进入本次结果。NonAlloc API 不会自动扩容，这是稳定内存的代价。当前小规模 RPG 战斗 32 个 Collider 足够，后续 Task 11 应用 Profiler 和压力场景确认；若确实溢出，可以提高固定容量、分层查询或显式记录截断警告，但不能在热路径临时分配更大数组。

## 5. DamageRequest 语义、TDD 与验证

Resolver 根据 Command 构造：

```text

DamageType = Magical

```

## 2. 为什么使用主动固定 tick，而不是 OnTriggerStay

Unity 常见的区域效果有两类实现。第一类依赖 `OnTriggerEnter/Stay/Exit`：进入时将目标加入集合、离开时移除，再在 `Update` 或 Coroutine 中施加。它适合需要精确维护“当前区域内对象集合”的系统，但角色多个 Collider 会触发多份回调；还必须处理 Collider 被禁用、对象销毁、漏掉 Exit、场景卸载和集合清理。若直接在 `OnTriggerStay` 中施加，回调频率又跟 Physics Step 绑定，状态增长速度会受 `Fixed Timestep` 影响，并可能对同一角色重复施加。

第二类是本项目采用的固定 tick 主动查询：`Update` 只累计时间，到达 `_tickInterval` 时调用一次 `Physics.OverlapBoxNonAlloc`，本 tick 看到什么就处理什么，不维护跨帧成员集合。它的 trade-off 是每 0.25 秒才更新一次，边缘进出存在最多一个 tick 的响应延迟；优点是语义简单、故障恢复自然、成本可预算，并且未来 Water/Fire/Poison/Sticky 四个 Prefab 可以完全共用。P2 的环境状态并不要求逐 Physics Frame 精确，因此 4 Hz 查询比持续 `OnTriggerStay` 更合适。若未来出现高速穿越极薄 Volume 的玩法，应加厚 Collider、缩短 tick，或为该特殊机关使用 Sweep/Trigger Enter，而不是把全部环境区都改成每帧查询。

卡顿帧可能一次跨过多个 tick。实现使用 `FloorToInt(elapsed / interval)` 算出跨过数量，并把 `_applyAmount * completedTicks` 合并成一次 `ApplyStatus`。当前状态语义是“强度累加后 Clamp 到 0~100”，所以同帧连续施加 3 次 5 与一次施加 15 等价；合并能避免一次卡顿触发多次 Physics 查询。这个等价性依赖当前 `ApplyStatus` 不为每次输入产生独立 Stack 或随机效果；未来若状态输入改成逐次 Proc，就必须重新审视该优化。

## 4. BoxCollider 从 Local Space 到 World Space 的数学与 Physics 查询

`BoxCollider.center` 和 `size` 存储在 Collider 的 Local Space。假设本地中心为 `c_local`，Transform 的 Local-to-World 矩阵为 `M`，世界中心就是 `c_world = M × c_local`；Unity API 用 `Transform.TransformPoint(_box.center)` 完成该运算，它会包含位置、旋转与缩放。`Physics.OverlapBoxNonAlloc` 的 `halfExtents` 要求 World Space 半尺寸，因此先计算 `size * 0.5`，再与 `abs(lossyScale)` 分量相乘；绝对值避免负缩放产生负半径，查询朝向使用 `boxTransform.rotation`。

这里采用 `lossyScale` 是普通层级中旋转/缩放 Box 的常见近似。若祖先层级同时具有非均匀缩放和旋转，数学上会形成 Shear，而 Unity 的 Box 查询接口不能直接表达任意 Sheared Box；环境 Prefab 应避免这种层级，保持 Volume 根节点做平移/旋转，缩放尽量直接作用在同一节点。Gizmo 使用 `box.transform.localToWorldMatrix`，再用本地 `center/size` 绘制，因此 Scene 视图能直观看到 Local Box 经矩阵变换后的范围。四种颜色只用于编辑辅助，不参与运行时 Gameplay，也不会创建 Material 或 Draw Call。

查询指定 `QueryTriggerInteraction.Collide`，因为角色 Hurtbox 和 Volume 自己都可能是 Trigger；返回结果仍会通过是否能在父级找到 `StatusController` 过滤。`LayerMask` 默认 All Layers，便于 MVP 直接工作；正式场景角色和环境数量增加后，应配置为角色 Hurtbox/Character Layer，减少 Physics Broad Phase 候选。不能用 LayerMask 代替逻辑去重：一个角色在同一 Layer 仍可能有多个 Collider。

## 5. NonAlloc、目标去重、来源设计与性能边界

普通 `Physics.OverlapBox` 会返回新 `Collider[]`，周期调用会产生 Managed Allocation；`OverlapBoxNonAlloc` 则把结果写入调用者提供的固定数组。`StatusVolume` 在组件创建时一次性拥有 `Collider[32]` 和 `HashSet<int>(32)`，tick 时只 `Clear()` 并复用内部容量，不在 `Update`、Physics 查询和遍历中使用 LINQ、闭包或 `new`。`GetComponentInParent<StatusController>` 把子级 Hurtbox 归并到角色根；随后以 `StatusController.GetInstanceID()` 加入 HashSet，`Add` 返回 false 即代表本 tick 已处理该角色。

固定 Buffer 的代价是区域内超过 32 个 Collider 时只处理 Physics 返回的前 32 个，本 Task 的要求是容量满时不抛异常，而不是动态扩容。动态扩容会让极端战斗帧突然分配内存，反而破坏性能可预测性。后续 Task 11 应在 1/4/8 个环境区和多角色场景中用 Profiler 验证 `GC Alloc = 0 B`，并观察 Buffer 是否经常满；若确实溢出，优先配置专用 LayerMask、减少无关 Collider，其次才评估把固定容量提高到 64。当前自动化测试证明 API 在 40 个重叠 Collider 下安全，但没有证明第 33 个目标必然被施加，这正是 NonAlloc 固定容量的明确边界。

环境 `sourceId` 使用 Volume GameObject 的 `GetInstanceID()`，`sourceTeam` 默认 `byte.MaxValue`（255）。它们是来源快照而非对象引用：Volume 之后即使销毁，已经施加的 Poison DoT 仍保存数值来源，不会因为悬空 `GameObject` 引用报错。Team 255 只是“中立环境”的约定，不是特殊引擎常量；当前 Damage Funnel 采用 Team 相等即友军，所以两个 Team 255 的环境实体不会互相伤害，但角色通常不是 255。若未来需要所有阵营都能被环境伤害，应引入明确的 Faction Relationship 规则，而不是到处硬编码“255 例外”。
