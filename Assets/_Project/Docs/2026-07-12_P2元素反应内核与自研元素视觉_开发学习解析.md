# 第一部分：Task 1——纯元素数据类型与公式

## 1. Task 1 最终实现了什么

Task 1 没有修改角色身上的 `StatusController`，也没有生成水、火、蒸汽或爆炸。玩家在 Play Mode 中暂时看不到新玩法，这是有意的开发顺序，不是功能失效。

它建立了 P2 最底层的“规则地基”：

```text
输入：某一时刻的 Fire / Water / Poison / Goo 数量
      + 每种元素来自谁
      + 数据驱动的阈值/倍率

                 |
                 v

       ElementReactionEvaluator

                 |
                 v

输出：是否达到正式反应阈值
      Wet 本帧能清除多少 Poison/Goo
      是否允许启动毒爆或点燃粘液
```

这一层只负责回答“规则上是否成立、数值应该是多少”，不负责：

- 每帧推进反应。
- 修改角色状态。
- 扣血。
- 查找 Collider。
- 发布 EventBus。
- 播放 Shader、Particle System 或 VFX Graph。

这条边界非常重要。系统越复杂，越需要先把“算数”与“Unity Runtime”分开。

## 2. 先建立总体心智模型

### 2.1 Status、Element Channel 与 Material 不是同一层

当前项目有角色状态：

```text
StatusKind.Burning
StatusKind.Wet
StatusKind.Poisoned
StatusKind.Sticky
```

它们描述 **“角色身上发生了什么”** 。例如 Wet=40 表示角色表面有 40% 潮湿强度。

Task 1 新增的抽象通道是：

```text
ElementChannel.Fire
ElementChannel.Water
ElementChannel.Poison
ElementChannel.Goo
```

它们描述 **“反应公式正在处理哪类元素”** ，不限定元素存在哪里。

未来两种 Adapter 可以这样映射：

```text
角色状态 Adapter：
Burning -> Fire
Wet -> Water
Poisoned -> Poison
Sticky -> Goo

P6 Cell Adapter：
MaterialKind.Fire -> Fire
MaterialKind.Water -> Water
MaterialKind.Poison -> Poison
MaterialKind.Sticky -> Goo
```

因此，`StatusKind.Wet` 不等于 `MaterialKind.Water`，但它们都能向 Reaction Kernel 提供 Water 事实。

### 2.2 为什么不让 Evaluator 直接接收 StatusController

如果 API 是：

```csharp
Evaluate(StatusController controller)
```

那么纯规则就被角色组件绑死了：

- 测试必须创建 GameObject。
- 必须等待 Unity 调用 Awake/Update。
- P6 Cell 没有 StatusController，无法复用。
- Evaluator 很容易直接修改状态，产生隐藏副作用。

当前 API 使用 `ElementStateSnapshot`：

```csharp
Evaluate(in ElementStateSnapshot snapshot)
```

Snapshot 是一次求值所需事实的只读副本。它不在乎事实来自玩家、敌人、水池还是未来 Cell。

## 3. 基础知识：enum、byte 与序列化稳定性

### 3.1 enum 是有名字的整数

```csharp
public enum ElementChannel : byte
{
    Fire = 0,
    Water = 1,
    Poison = 2,
    Goo = 3,
}
```

`enum` 让代码使用 `Fire`，而不是难以理解的数字 0。底层指定 `byte`，表示每个值占 1 Byte，可表达 0–255。

这里选择 `byte` 不是为了微小的内存优化，而是为了表达边界：P2 的元素和反应数量很少，不需要 32-bit `int` 的范围。

### 3.2 为什么显式写 = 0、= 1

Unity 会把 enum 作为数字保存进 `ScriptableObject`、Prefab 或 Scene。假设旧资产保存：

```text
Reaction = 1
```

如果后来在枚举最前面插入一个新值，却没有显式编号，原来的 1 可能从 ToxicCombustion 变成 Extinguish。

因此反应 ID 明确固定：

```text
Extinguish = 0
ToxicCombustion = 1
IgniteGoo = 2
```

测试 `SerializedEnumValues_AreStable` 不是在测试 C# 会不会计数，而是在保护持久化数据契约。

### 3.3 将来怎样安全新增枚举值

只能追加新值并显式指定新编号：

```csharp
Freeze = 3
```

不要在中间插入，也不要重新使用已经删除的编号。若必须迁移编号，需要编写正式 Asset Migration，而不是直接改 enum。

## 4. 基础知识：struct、readonly struct 与值快照

### 4.1 class 与 struct 的核心区别

简化理解：

- `class` 变量通常保存“对象引用”。多个变量可以指向同一个对象。
- `struct` 变量保存“值”。赋值通常复制内容。

`StatusSource` 使用：

```csharp
public readonly struct StatusSource
{
    public readonly int Id;
    public readonly byte Team;
}
```

它只保存伤害归属需要的两个事实，不保存 `GameObject attacker`。

### 4.2 为什么不保存攻击者 GameObject

状态和 DoT 可能持续数秒。施法者在此期间可能死亡、被销毁或离开场景。如果状态持有攻击者对象并在每次伤害时回查，会产生：

- MissingReferenceException。
- 场景对象被状态意外长期引用。
- 伤害结算依赖一个已经不存在的对象。

值快照只保存：

```text
SourceId
SourceTeam
```

即使施法者销毁，伤害归属事实仍然存在。这和现有 `DamageRequest` 的 value snapshot 设计一致。

### 4.3 readonly 的意义

`readonly struct` 表达：构造完成后不能修改字段。

这能防止求值器偷偷执行：

```csharp
snapshot.Fire -= 20;
```

Evaluator 只能读取输入并返回结果。真正写回由后续 Adapter 统一处理。

### 4.4 in 参数为什么适合 Snapshot

方法签名使用：

```csharp
IsFormalExtinguish(
    in ElementStateSnapshot snapshot,
    in ExtinguishTuning tuning)
```

`in` 表示按只读引用传递值类型：

- 方法不能修改输入。
- 较大的 struct 不需要为每次调用复制全部字段。
- API 明确表示“这是输入事实”。

不要机械地给所有小 struct 加 `in`。这里使用它主要是为了只读语义，以及 Snapshot 后续还会扩展来源信息。

## 5. Snapshot 为什么能避免顺序错误

假设系统直接边读边改：

```text
检查 Extinguish
-> 立刻扣 Fire/Water
-> 检查 Toxic Combustion 时看到的是新值
```

另一名开发者如果交换两个 if 的位置，就可能得到不同结果。

Snapshot/Result 模式是：

```text
1. 完整读取旧状态，建立 Snapshot
2. 所有纯判断只读 Snapshot
3. Runtime 按正式优先级产生 Frame Result
4. Adapter 统一 Clamp 并写回
```

Task 1 只建立了第 1、2 步；Task 2 会建立第 3 步；Task 3 才接入 StatusController 完成第 4 步。

## 6. Tuning：为什么规则数值不写死在 Evaluator

Task 1 使用四组 `[Serializable] struct`：

| Tuning | 当前字段 | 解决的问题 |
|---|---|---|
| ExtinguishTuning | 正式阈值、低速/正式速率 | 控制水火中和强度 |
| WetCleanseTuning | 满 Wet 时每秒预算 | 控制通用清洗能力 |
| ToxicCombustionTuning | Fire/Poison 阈值 | 控制毒爆启动 |
| IgniteGooTuning | Fire/Goo/Wet/容量阈值 | 控制粘液点燃 |

`[Serializable]` 使这些 struct 将来可以显示在 `ScriptableObject` Inspector 中。

`[Min(0f)]` 是 Editor 配置提示和限制，不能取代 Runtime 防御。代码仍通过 `MaxZero` 处理负值，因为：

- 测试可以直接构造 struct，绕过 Inspector。
- 旧资产或文本合并可能产生非法值。
- Runtime 不能把“Inspector 应该正确”当成安全保证。

Task 1 只添加测试需要的字段。Wind-up、伤害、半径、冷却等字段将在 Task 2/4 的失败测试出现后再加入。这是 TDD 的 YAGNI：没有行为要求，就不提前增加字段。

## 7. ElementReactionEvaluator 的纯函数设计

### 7.1 什么是纯函数

简化定义：

```text
相同输入 -> 永远得到相同输出
执行时不修改外部世界
```

Task 1 的 Evaluator 不访问：

- `Time.deltaTime`
- `Physics`
- `EventBus`
- `GameObject/Transform`
- `MonoBehaviour`
- `Random`

`deltaTime` 若参与公式，也必须由调用者作为普通 float 显式传入。

纯函数的价值：

- EditMode 测试快，不需要加载场景。
- Bug 可以用一组数字稳定复现。
- 不受帧率、对象启用顺序和 Physics 时机影响。
- P6 可以直接复用。

### 7.2 Extinguish 阈值

```text
formal = Fire >= threshold AND Water >= threshold
```

阈值是 inclusive：恰好 10 应该触发。否则 UI 显示 10%，玩家却发现没有反应，会产生认知冲突。

测试同时覆盖：

- Fire 低于阈值。
- Water 低于阈值。
- 双方恰好等于阈值。
- 双方明显高于阈值。

### 7.3 Toxic Combustion 阈值

```text
Fire >= 25 AND Poison >= 20
```

使用 AND 而不是 OR，因为 Burning 是点火条件，Poison 是燃料。缺少任意一个都不能形成正式毒爆。

### 7.4 Ignite Goo 的四个条件

```text
Fire >= 15
Goo >= 20
Water < 10
100 - Fire >= RequiredFireCapacity
```

这里 `Water < 10` 是严格小于。用户已经确认 Wet=10 时完全禁止点燃。

剩余 Fire 容量用于防止浪费 Goo：Fire=90、需要 10 容量时允许；Fire=90.01 时容量不足 10，禁止启动。

## 8. Wet Cleanse 有限预算公式详解

### 8.1 为什么必须有预算

用户确认 Wet 不能同时全速清洗 Poison 与 Sticky，而是：

```text
先清 Poison
-> Poison 清完
-> 剩余能力再清 Sticky
```

如果分别计算两个独立加速倍率，同一份 Wet 会被使用两次，优先级没有实际意义。因此每帧先生成一份有限 Budget。

### 8.2 第一步：按 Wet 强度生成预算

```text
Budget = FullWetBudget * clamp(Wet, 0, 100) / 100 * deltaTime
```

当前基线：

```text
FullWetBudget = 30/s
Wet = 40
deltaTime = 1s

Budget = 30 * 0.4 * 1 = 12
```

### 8.3 第二步：先清 Poison

Poison multiplier=0.75，表示每花 1 点预算，只能清除 0.75 Poison。

如果 Poison=3：

```text
清除 3 Poison 需要的预算 = 3 / 0.75 = 4
剩余预算 = 12 - 4 = 8
```

如果 Poison=100，12 点预算最多清：

```text
12 * 0.75 = 9 Poison
```

此时预算耗尽，Goo 本帧清除量必须是 0。

### 8.4 第三步：剩余预算清 Goo

Goo multiplier=1.25：

```text
8 剩余预算 * 1.25 = 10 Goo
```

因此完整示例得到：

```text
输入：Wet=40, Poison=3, Goo=20, dt=1
输出：PoisonRemoved=3, GooRemoved=10
```

### 8.5 为什么 Result 不直接返回新强度

`WetCleanseResult` 返回“移除了多少”，而不是最终 Poison/Goo：

```csharp
PoisonRemoved
GooRemoved
```

原因是后续同一 Frame 还可能有 Toxic Wind-up、Ignite Goo 和自然衰减。Task 2 会把不同过程产生的 Delta 汇总，Task 3 再统一写回，避免多个模块争抢最终值。

## 9. 防御性数学与边界处理

Evaluator 内部有三个小函数：`MaxZero`、`Min`、`Clamp`。

它们的作用不是重新发明 `Mathf`，而是让纯公式文件不依赖 Unity API：

- `MaxZero`：负调参按 0 处理。
- `Min`：不能清除超过当前剩余量的状态。
- `Clamp`：Wet 和 Fire 只按 0–100 解释。

例如 Wet=150 不应该产生 150% 清洗能力，先 Clamp 到 100。

需要注意：正式 `ElementReactionProfile` 尚未创建。Task 2/3 会通过 Profile 的 `OnValidate` 保证正式阈值为合理正数；当前纯层的职责是安全处理输入，而不是决定策划配置界面。

## 12. 常见替代方案与 trade-off

### 12.1 直接在 StatusController 中写 if

优点：代码少、马上能看到效果。

缺点：

- 规则、时间、伤害、VFX 全挤在 Update。
- 无法供 P6 Cell 复用。
- 测试需要 GameObject。
- 多反应优先级越来越难验证。

因此不采用。

### 12.2 Dictionary<ElementChannel, float>

优点：新增元素时不用改 struct 字段。

缺点：

- 热路径有哈希查询。
- 更容易发生运行时分配。
- 当前只有固定四通道，动态容器没有收益。
- 读取 `snapshot.Fire` 比 Dictionary key 更直观。

P2 选择显式字段。未来元素数量真正变大时，再以测试保护的方式迁移紧凑数组，而不是现在提前抽象。

### 12.3 每个反应一个 MonoBehaviour

优点：Unity Inspector 直观。

缺点：反应之间共享 Water/Fire 时会竞争写入；生命周期顺序取决于 MonoBehaviour Update 顺序；P6 Cell 无法使用。

因此 Process 将由 Task 2 的普通 C# Runtime 统一排序。

## 13. 性能与 GC Alloc

Task 1 的热路径类型都是值类型和 static 纯函数：

- 没有 `new class`。
- 没有数组/List/Dictionary。
- 没有 LINQ。
- 没有 closure/delegate。
- 没有 boxing。

`new ElementStateSnapshot(...)` 创建的是值类型局部值，不等于在 Managed Heap 上分配对象。需要区分：

```text
使用 new 语法 ≠ 一定产生 GC Alloc
new class 通常分配对象
new struct 通常只是构造一个值
```

Task 2 会让 Runtime 在 Awake 创建一次并复用；Task 3 接入后再用 Profiler 验证真实热路径 0 B，而不是只根据代码形式推断。

## 14. Debug 方法论

Task 1 的 Debug 输入全部是数字，推荐按以下顺序：

```text
1. 打印/断言 Snapshot 四个强度
2. 检查使用的是哪组 Tuning
3. 手算阈值或 Budget
4. 比较 Evaluator Result
5. 最后才怀疑 Unity 生命周期
```

Wet Cleanse 出错时手算：

```text
总预算 = FullBudget * Wet/100 * dt
PoisonRemove = min(Poison, Budget * PoisonMultiplier)
剩余预算 = Budget - PoisonRemove/PoisonMultiplier
GooRemove = min(Goo, 剩余预算 * GooMultiplier)
```

如果 Goo 在 Poison 尚未清完时下降，优先检查是否给 Goo 重复使用了原始总预算。

## 15. 大厂面试 Q&A

### Q1：为什么做 ElementChannel，不直接用 StatusKind？

因为 StatusKind 是角色载体语义，未来环境 Cell 使用 MaterialKind。ElementChannel 是 Reaction Kernel 的抽象输入，使同一纯规则可以被不同 Adapter 复用，避免 Kernel 依赖 StatusController。

### Q2：Snapshot 解决什么问题？

Snapshot 固定一次求值看到的事实，防止判断过程中边读边改导致顺序不确定。Runtime 产生 Delta，Adapter 统一写回，便于测试和明确优先级。

### Q3：为什么 StatusSource 不保存 GameObject？

DoT/反应可能晚于攻击者生命周期。保存 Id/Team 值快照可避免攻击者销毁后的引用错误，也与现有 DamageRequest 设计一致。

### Q4：Wet Cleanse 为什么不是两个独立衰减倍率？

用户要求先清 Poison、再清 Sticky。若两者独立计算，会重复使用同一 Wet 能力。有限 Budget 可以表达资源优先分配，并让测试精确验证。

### Q5：纯函数是否自动意味着线程安全？

Task 1 的 static 方法没有共享可变状态，具备良好的线程安全基础；但这不表示整个 Game.Combat 可以直接放到 Job。后续 Runtime、Physics 和 EventBus 仍有主线程约束。

# Task 2：连续元素反应 Runtime

## 18. Task 2 的目的

Task 1 回答“当前数值能否触发反应”，Task 2 回答“反应触发后如何跨越许多帧连续推进、暂停、恢复或结束”。我们实现了纯 C# 的 `ElementReactionRuntime`：它保存过程记忆，但仍不直接修改 `StatusController`、造成场景伤害或播放 VFX。

## 19. 为什么不能每帧只调用 Evaluator

`ElementReactionEvaluator` 是无状态纯函数，不记得上一帧发生过什么；真实反应却有历史：正式灭火启动后要从 `80 Fire + 30 Water` 连续推进到 `50 Fire + 0 Water`，不能在 Water 跌破阈值后突然降档；Toxic Combustion 有 Wind-up，期间可能被 Wet Cleanse 削弱；Ignite Goo 被 Wet 压制后应进入 `Paused`，条件解除后发出 `Resumed`，而不是被当成新反应重复启动。因此 Runtime 是纯规则与 Unity 场景之间的“有状态执行层”。

## 20. 基础原理：离散帧模拟连续变化

游戏循环每帧只计算一次，“每秒减少 50 点”必须写成：

```text
本帧变化量 = 每秒速率 × deltaTime
```

30 FPS 时每帧约减 `50/30`，120 FPS 时每帧减 `50/120`，一秒累计都约为 50，这叫 **Frame-rate Independence**。最后一帧还用 `min(剩余量, 本帧预算)` Clamp，防止数值穿过零。忘记乘 `deltaTime` 会让高帧率机器上的反应更快，是常见游戏逻辑 Bug。

## 21. 新增类型及职责

### `ElementReactionPhase`

定义 `Started / Paused / Resumed / Resolved / Cancelled`。`Resolved` 表示正常完成，`Cancelled` 表示角色死亡、禁用或外部终止；两者必须区分，因为正常毒爆可播放爆炸，而取消只能清理预热表现。

### `ElementReactionFrame`

Runtime 不直接写回角色，而是返回一张“本帧结算单”：四种元素 Delta、被规则接管的 `StatusMask`、可选 `ReactionDamageCommand`，以及最多三个离散 `ReactionSignal`。这种 **Command/Result Boundary** 让核心只描述“应该发生什么”，Task 3 的 Adapter 再决定如何在 Unity 世界执行，因此纯测试不需要 GameObject，也不会让 Runtime 依赖 `HealthComponent`、`EventBus` 或 VFX。

### `ElementReactionTuningSnapshot`

Inspector 中的可序列化 Tuning 适合配置；Runtime 构造时把它复制成只读 Snapshot，使正在运行的 Process 不会受到外部对象中途修改的影响，并让测试输入稳定。

### `ElementReactionRuntime`

它是普通 C# 对象而非 `MonoBehaviour`。将来由 `StatusController` 在 `Awake` 中预创建并复用；Unity 不会自动调用它的 `Update`，Adapter 会显式传入状态 Snapshot 与 `deltaTime` 调用 `Tick`。

## 22. 为什么选择固定 Process

常见通用方案是 `List<ReactionProcess>` 加多态对象，扩展灵活，但可能引入实例化、扩容、遍历和回收复杂度。本项目当前只有三条确定反应，因此使用固定字段保存 Extinguish、Toxic、Ignite Process。这样同类反应天然不会重复加入，数量上限明确，也无需每帧创建集合或 Enumerator。取舍是反应很多时字段会膨胀；等规模真正增长后再迁移到预分配数组或固定容量 Pool，而不提前建设用不到的通用框架。

## 23. 每帧结算顺序

```text
更新 Cooldown
→ Dirty 时评估并启动新 Process
→ Extinguish
→ Wet Cleanse（先 Poison，后 Goo）
→ Toxic Wind-up / Resolve
→ Ignite Goo
```

`Dirty` 表示外部状态发生离散变化，需要重新检查启动条件，而不是每帧重复启动。反应可以同时 Active，但共享资源的修改仍必须有确定顺序：灭火先消费 Fire/Water；Wet Cleanse 始终工作并先毒后粘液；Toxic 读取清洗后的实际 Poison；Ignite 最后运行，Wet 达到压制条件时只暂停 Ignite，不冻结清洗系统。

## 24. 三条反应的实现

### Extinguish

正式灭火启动时锁存正式速率，此后持续计算：

```text
consume = min(Fire, Water, FormalRate × deltaTime)
FireDelta = WaterDelta = -consume
```

直到其中一方为零。第一次实现曾每帧重算阈值，Water 跌破启动阈值后降为低速，导致 `80/30` 一秒后约为 `57/0`；测试捕获了这个需求偏差。修复后，阈值只决定是否启动正式反应，不决定中途降档。低强度 Fire + Water 仍按低速互相消耗，但不会冒充正式 Steam 反应重复发送 `Started`。

### Toxic Combustion

达到门槛后保存启动来源并累计 Wind-up。到时按“实际仍可消费的 Poison”产生一次 DamageCommand：

```text
ActualConsumed = min(CurrentPoison, MaxPoisonConsume)
Damage = BaseDamage + ActualConsumed × DamagePerPoison
```

Wet Cleanse 在 Wind-up 中仍会削减 Poison，所以最终伤害随之降低；若剩余量低于最小有效消费量则取消。Runtime 只产生命令，Task 4 才用 NonAlloc 范围查询真正伤害场景目标。

### Ignite Goo

Ignite 按 `GooConsumePerSecond` 连续消费 Goo，再用 `FirePerGoo` 转换成 Fire。Wet 达到压制阈值时，Ignite 停止转换并发送一次 `Paused`，但 Process 保留，Wet Cleanse 仍能降低 Goo；Wet 降低后发送一次 `Resumed`，下一帧继续转换。这说明“暂停一个特殊反应”并不等于冻结整个元素系统。

## 25. Signal 与 0 GC 设计

`ReactionSignal` 只报告生命周期边界，不逐帧发送 Progress。Frame 使用 `Signal0/1/2 + SignalCount`，而非每 Tick 创建 `List`；当前三条固定 Process 同帧最多需要三个槽位。Process 启动帧只发 `Started`，从下一帧才推进，避免同帧 Started+Resolved 挤占容量，也让视觉至少拥有稳定的启动边界。

热路径设计还包括：Runtime 预创建复用；Process 使用固定字段；Frame、Signal、Command、Snapshot 均为值类型；无 LINQ、Closure、逐帧字符串、Physics、Instantiate 或 EventBus。要注意“用了 struct 就一定 0 GC”是错误的：Boxing、Closure 和集合扩容仍会分配，最终还需 Task 11 用 Profiler 验证 `GC Alloc = 0 B`。

## 26. TDD 过程与两类失败

我们先写 11 个 `ElementReactionRuntimeTests`，确认缺少类型时为 Red，再实现最小 Runtime。用例覆盖 30/120 FPS 一致性、低速灭火、Toxic Wind-up/清洗削弱/伤害、Ignite 转换/暂停/恢复、同类不重复、三 Process 并行、固定 Signal 容量、`CancelAll` 和零 `deltaTime`。

首次运行 8/11 通过，失败分成两类：

1. **代码错误**：正式灭火每帧重算阈值；修复为启动时锁存模式。
2. **测试预期错误**：测试认为 Ignite 暂停时 Goo 不应变化，但需求明确 Wet Cleanse 仍清洗负面状态；正确结果是 Fire 不增加、Goo 继续下降。

TDD 不只检查代码，也迫使需求优先级变成可反驳的例子。测试错时不能为了 Green 扭曲正确设计，而要回到已确认规则判断究竟哪一边错误。
