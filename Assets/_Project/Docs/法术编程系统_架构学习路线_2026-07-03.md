# 法术编程系统架构学习路线

创建时间：2026-07-03  
目标：帮助你先理解“法术编程系统”的总体架构，再知道应该按什么顺序阅读脚本。

---

## 1. 先回答一个关键问题：为什么你会觉得脚本很多、看不懂？

这不是你理解能力的问题，而是因为“法术编程系统”不是一个普通技能。

普通技能系统通常是：

```text
玩家按键 -> FireballSkill.Cast() -> 生成火球 -> 命中扣血
```

这种系统脚本少，但扩展性弱。

你的系统现在是：

```text
玩家编辑一串法术
-> 角色施法
-> 解释器读取法术序列
-> 输出发射命令
-> 运行时生成投射物
-> 投射物命中或计时
-> 可能再次运行后续法术
-> 最后进入战斗伤害系统
```

它脚本多，是因为它把不同责任拆开了。

这就是架构的核心：

> 架构不是“有多少文件”，而是“每一类问题应该归谁负责”。

如果你不知道每个脚本属于哪一层，就会觉得所有脚本都混在一起。  
如果你先知道架构分层，再看脚本，脚本数量反而会变得可控。

---

## 2. 这个系统的总架构：四层

你可以先把整个法术编程系统理解成四层：

```text
第 1 层：法术数据层（“法术是什么？”）
    SpellDefinition / WandLoadout / SpellLibrary

第 2 层：纯规则解释层（“这一串法术应该产生什么结果？”）
    CastEvaluator / CastModifierState / EmitCommand / SpellAiming / WandEditOps

第 3 层：Unity 运行时桥接层（“解释器结果怎么变成场景里的对象？”）
    SpellCaster / WizardController / PlayerWizardAttackState

第 4 层：投射物与战斗执行层（“生成出来的攻击如何飞行、命中、扣血？”）
    ProjectileBase / Fireball / AreaDamage / BurnStatus / HealthComponent / DamagePipeline
```

这四层分别回答四个问题：

| 层级 | 回答的问题 | 典型脚本 |
|---|---|---|
| 法术数据层 | “法术是什么？” | `SpellDefinition` |
| 纯规则解释层 | “这一串法术应该产生什么结果？” | `CastEvaluator` |
| Unity 运行时桥接层 | “解释器结果怎么变成场景里的对象？” | `SpellCaster` |
| 投射物与战斗执行层 | “生成出来的攻击如何飞行、命中、扣血？” | `ProjectileBase` |

你学习这个系统时，永远先问：

> 我现在看的这个脚本是在回答哪一个问题？

只要能回答这个问题，你就不会迷路。

---

## 3. 架构主线：数据从哪里来，到哪里去？

不要一开始看所有脚本。先记住这一条主线：

```text
WandLoadout.Spells
    ↓
CastEvaluator.Evaluate(...)
    ↓
List<EmitCommand>
    ↓
SpellCaster
    ↓
ProjectileBase.Init(...)
    ↓
ProjectileBase.OnCollisionEnter / TimedTriggerElapsed
    ↓
HealthComponent.ReceiveHit(...)
```

这就是法术编程系统的“脊柱”。

所有其他脚本都挂在这条主线上：

- UI 是为了编辑 `WandLoadout.Spells`
- `SpellDefinition` 是 `WandLoadout.Spells` 里的元素
- `CastModifierState` 是 `CastEvaluator` 运行时的临时状态
- `EmitCommand` 是 `CastEvaluator` 输出给 `SpellCaster` 的结果
- `ProjectileBase` 是 `SpellCaster` 实例化出来的运行时对象
- `HealthComponent` 是投射物命中后进入的战斗结算入口

如果你只记一张图，记这张：

```text
玩家配置法杖
    ↓
WandLoadout
    ↓
CastEvaluator
    ↓
EmitCommand
    ↓
SpellCaster
    ↓
ProjectileBase
    ↓
Combat Damage
```

## 4. 架构里最重要的分工

### 4.1 `SpellDefinition` 不负责施法

`SpellDefinition` 只是数据。

它负责描述：

- 这个法术叫什么
- 图标是什么
- 是 `Emit`、`Modify` 还是 `Multicast`
- 如果是投射物，prefab 是什么
- 基础伤害、速度、音效是什么
- payload 触发方式是什么

它不负责：

- 实例化火球
- 判断命中
- 扣血
- 播放动画

这是第一个关键认知。

如果你把 `SpellDefinition` 当成“技能类”，就会看不懂。  
它更像一条“指令数据”。

---

### 4.2 `CastEvaluator` 不负责 Unity 世界

`CastEvaluator` 是解释器。

它只做一件事：

> 把一串 `SpellDefinition` 解释成一组 `EmitCommand`。

它不负责：

- `Instantiate`
- `Transform`
- `Rigidbody`
- `Collider`
- `AudioSource`
- 敌人是谁
- 玩家在哪里

这就是为什么它叫“纯规则层”。

它的好处是：

- 可以做 EditMode tests
- 不依赖场景
- 不会被 Unity 生命周期干扰
- 规则集中，不散落在火球、UI、角色控制器里

---

### 4.3 `EmitCommand` 是解释器和运行时的合同

你可以把 `EmitCommand` 理解成一张“发射订单”。

`CastEvaluator` 不直接发射火球，而是写一张订单：

```text
我要发射哪个 prefab
最终伤害是多少
最终速度是多少
散射角是多少
有没有 payload
payload 什么时候释放
payload 继承什么 modifier 快照
```

然后 `SpellCaster` 拿着这张订单去 Unity 场景里执行。

这就是架构里的“边界对象”。

边界对象很重要，因为它让两层之间不用互相知道太多：

```text
CastEvaluator 不需要知道怎么 Instantiate
SpellCaster 不需要知道 modifier 怎么计算
```

---

### 4.4 `SpellCaster` 是桥，不是规则核心

`SpellCaster` 的位置很特殊。

它一只脚踩在 `Game.Skills`：

- 调用 `CastEvaluator`
- 读取 `EmitCommand`
- 处理 payload

另一只脚踩在 Unity 运行时：

- `Instantiate`
- 取 `ProjectileBase`
- 调 `ProjectileBase.Init`
- 订阅 `Impacted`
- 订阅 `TimedTriggerElapsed`

所以它是桥接层。

你看 `SpellCaster` 时不要问“法术规则为什么在这里”，而要问：

> 解释器已经算完了，SpellCaster 如何把结果落地到 Unity 场景？

---

### 4.5 `ProjectileBase` 不知道法术系统

这是一个很重要的架构边界。

`ProjectileBase` 属于 `Game.Combat`。它只知道：

- 我是一个投射物
- 我有速度
- 我会碰撞
- 我命中了就结算伤害
- 我可以广播 `Impacted`
- 我可以广播 `TimedTriggerElapsed`

它不知道：

- 什么是 `SpellDefinition`
- 什么是 `WandLoadout`
- 什么是 payload
- 什么是 `CastEvaluator`

为什么？

因为投射物系统不只给 Wizard 法术用，也可以给 Archer、敌人远程攻击用。

如果 `ProjectileBase` 直接依赖法术系统，Combat 层就被 Skills 层污染了。

当前架构是：

```text
ProjectileBase 只广播“我命中了 / 我计时到了”
SpellCaster 决定“收到这个事件后要不要释放 payload”
```

这就是模块隔离。

---

## 5. 推荐阅读顺序

下面是我建议你的学习顺序。不要跳着看。

### 第 0 步：先不看 UI

先不要看 `WandEditorController`、`SpellSlotView` 这些 UI 脚本。

原因：

UI 脚本引用多、事件多、拖拽多，容易让你误以为系统很乱。  
但 UI 只是编辑 `WandLoadout` 的工具，不是法术系统的核心。

先理解核心主线，再回头看 UI。

---

### 第 1 步：看数据定义

先看：

```text
SpellKind.cs
PayloadTriggerMode.cs
SpellDefinition.cs
WandLoadout.cs
```

目标不是记字段，而是回答：

1. 一个法术有哪几类？
2. 一根法杖如何保存法术序列？
3. 什么字段只对 `Emit` 有意义？
4. 什么字段只对 `Modify` 有意义？
5. 什么字段只对 `Multicast` 有意义？
6. payload 触发条件如何表达？

你看完这一层后，应该能说出：

```text
SpellDefinition 是一条指令的数据。
WandLoadout 是一组指令的数组。
SpellKind 决定这条指令被解释器如何处理。
PayloadTriggerMode 决定 Emit 是否携带后续法术，以及何时释放。
```

如果你还不能这样总结，就不要急着看 `SpellCaster`。

---

### 第 2 步：看解释器

然后看：

```text
CastModifierState.cs
EmitCommand.cs
CastEvaluator.cs
SpellAiming.cs
```

阅读重点：

1. `CastEvaluator.Evaluate` 的输入是什么？
2. `CastEvaluator.Evaluate` 的输出是什么？
3. `Modify` 如何改变 `CastModifierState`？
4. `Multicast` 如何改变 `drawBudget`？
5. `Emit` 如何变成 `EmitCommand`？
6. 触发/定时类法术如何捕获 payload？

这一层是最重要的。

你要把它当成一个小型编程语言解释器看，而不是当成 Unity 技能代码看。

简单说：

```text
CastEvaluator 读程序
CastModifierState 是当前运行状态
EmitCommand 是输出结果
```

---

### 第 3 步：看运行时桥接

然后看：

```text
SpellCaster.cs
```

只看它如何做这几件事：

1. 调 `CastEvaluator.Evaluate`
2. 遍历 `EmitCommand`
3. `Instantiate` 投射物 prefab
4. 调 `ProjectileBase.Init`
5. 如果有 payload，订阅事件
6. 命中或定时后再次 `RunCast`

你看 `SpellCaster` 时，脑子里要有这句话：

> `SpellCaster` 不决定法术规则，它只执行解释器给出的命令。

---

### 第 4 步：看投射物生命周期

然后看：

```text
ProjectileBase.cs
Fireball.cs
AreaDamage.cs
BurnStatus.cs
```

阅读重点：

1. 投射物如何初始化？
2. 速度、伤害、阵营如何被注入？
3. 命中时如何过滤同阵营？
4. 命中时如何发 `DamageRequest`？
5. `Impacted` 事件何时触发？
6. `TimedTriggerElapsed` 事件何时触发？
7. `_consumed` 如何防止重复触发？

这一层已经不再是“法术解释器”，而是“Combat 投射物执行”。

---

### 第 5 步：看 Wizard 施法入口

然后看：

```text
WizardController.cs
PlayerWizardAttackState.cs
```

阅读重点：

1. 玩家左键如何被记录？
2. `ClickAimPoint` 为什么要在按下瞬间锁定？
3. 为什么不是输入瞬间直接发射，而是动画释放帧调用？
4. `PlayerWizardAttackState` 如何调用 `SpellCaster.CastWand`？

这一层回答：

> 玩家操作如何进入法术系统？

---

### 第 6 步：最后看 UI

最后再看：

```text
SpellLibrary.cs
WandEditOps.cs
WandEditorController.cs
SpellPaletteView.cs
WandFrameView.cs
SpellSlotView.cs
IWandDragHandler.cs
SlotKind.cs
```

阅读重点：

1. `SpellLibrary` 如何提供可选法术？
2. UI 如何显示法术图标？
3. 拖拽如何变成 insert/move/remove？
4. `WandEditOps` 为什么是纯逻辑？
5. `WandEditorController` 为什么要暂停游戏？

这一层回答：

> 玩家如何编辑那串 `WandLoadout.Spells`？

看 UI 之前你必须先理解：

```text
UI 不解释法术。
UI 只是编辑法术序列。
真正的解释发生在 CastEvaluator。
```

## 6. 你应该用什么方式读代码？

不要从文件夹第一个脚本开始读。  
也不要试图一次性理解所有字段。

我建议你按“问题驱动”的方式读。

### 问题 1：普通火球是怎么发出来的？

只追这一条链：

```text
WandLoadout
-> CastEvaluator
-> EmitCommand
-> SpellCaster
-> ProjectileBase.Init
```

先不要管 UI、触发、定时。

### 问题 2：增伤为什么能影响后面的火球？

只追：

```text
SpellDefinition.Kind = Modify
-> CastModifierState.Apply
-> CastEvaluator.BakeEmit
-> EmitCommand.Damage
```

### 问题 3：触发火球为什么命中后能释放后续火球？

只追：

```text
CastEvaluator.CaptureSuffix
-> EmitCommand.Payload
-> SpellCaster 订阅 Impacted
-> ProjectileBase.OnCollisionEnter
-> Impacted.Invoke
-> SpellCaster.RunCast(payload)
```

### 问题 4：定时火球为什么不需要命中？

只追：

```text
PayloadTriggerMode.AfterDelay
-> SpellCaster 订阅 TimedTriggerElapsed
-> ProjectileBase.ArmTimedTrigger
-> ProjectileBase.TickTimedTrigger
-> TimedTriggerElapsed.Invoke
-> SpellCaster.RunCast(payload)
```

按这些问题读，比按文件读更有效。

## 7. 什么叫“架构懂了”？

不是你能背出所有脚本字段。

而是当提出一个新需求时，你能判断它应该改哪一层。

例如：

### 需求：新增一个火球图标

改：

```text
SpellDefinition asset
SpellLibrary
UI icon
```

不应该改：

```text
CastEvaluator
ProjectileBase
DamagePipeline
```

### 需求：新增“弹跳 Modifier”

可能改：

```text
SpellDefinition
CastModifierState
EmitCommand
CastEvaluator
SpellCaster
ProjectileBase
```

因为它是“法术规则影响投射物行为”。

### 需求：新增敌人火抗

主要改：

```text
DefenseProfile
DamagePipeline
HealthComponent
可能的 UI 显示
```

不应该塞进：

```text
SpellCaster
CastEvaluator
```

因为抗性是伤害结算规则，不是法术解释规则。

### 需求：新增法杖存档

主要改：

```text
WandLoadout runtime copy
Save data
WandEditor UI
```

不应该改：

```text
ProjectileBase
DamagePipeline
```

这就是架构思维。

## 8. 最容易混淆的三个边界

### 8.1 `SpellDefinition` vs `EmitCommand`

`SpellDefinition` 是原始资产数据。

```text
这个火球基础伤害是 10
```

`EmitCommand` 是本次施法算完后的快照。

```text
这个火球经过增伤后，本次最终伤害是 18
```

不要在运行时修改 `SpellDefinition` 来实现增伤。

---

### 8.2 `CastEvaluator` vs `SpellCaster`

`CastEvaluator` 负责“算”。

```text
这一串法术会产生几个投射物？
伤害是多少？
有没有 payload？
```

`SpellCaster` 负责“做”。

```text
生成 prefab
设置速度
订阅事件
播放音效
```

如果你发现自己想在 `CastEvaluator` 里写 `Instantiate`，说明边界错了。

---

### 8.3 `ProjectileBase` vs `SpellCaster`

`ProjectileBase` 负责投射物生命周期。

```text
飞行
碰撞
计时
销毁
广播事件
```

`SpellCaster` 负责法术 payload 语义。

```text
命中后运行 payload
定时后运行 payload
```

如果你发现自己想在 `ProjectileBase` 里引用 `SpellDefinition`，说明边界错了。

---

## 9. 从面试角度怎么讲这个架构？

你可以这样讲：

> 我把法术编程系统拆成了纯规则层和 Unity 运行时层。法杖是一段 `WandLoadout` 序列，每个 `SpellDefinition` 是一条指令。施法时 `CastEvaluator` 从左到右解释这段序列，处理 `Emit`、`Modify`、`Multicast`，输出纯数据 `EmitCommand`。这一层不依赖 Unity 场景，所以可以做 EditMode 测试。然后 `SpellCaster` 作为运行时桥接层，把 `EmitCommand` 实例化成 `ProjectileBase` 投射物，并根据 payload 类型订阅命中或定时事件。投射物命中后仍然走统一的 Combat 漏斗，也就是 `IDamageable`、`HealthComponent` 和 `DamagePipeline`。这样法术组合规则、Unity 对象生成、投射物生命周期和伤害结算是分离的，后续加新法术或新触发条件时不会把所有逻辑写成一堆技能特例。

这段话如果你能理解并说出来，说明你已经抓住了架构核心。

## 10. 建议你的学习安排

### 第一天：只看数据层和解释器

目标：

```text
能解释 SpellDefinition、WandLoadout、CastEvaluator、EmitCommand 的关系。
```

不要看 UI。

### 第二天：看 SpellCaster 和 ProjectileBase

目标：

```text
能解释“解释器输出如何变成真实火球”。
```

### 第三天：看触发/定时 payload

目标：

```text
能解释 payload 为什么是严格后缀，以及事件如何让 payload 在未来释放。
```

### 第四天：看 UI

目标：

```text
能解释 UI 只是编辑 WandLoadout，不负责法术语义。
```

### 第五天：自己画图

你可以自己画一张：

```text
WandLoadout -> CastEvaluator -> EmitCommand -> SpellCaster -> ProjectileBase -> DamagePipeline
```

然后把每个脚本贴到对应节点下面。

只要你能自己画出来，这个系统就基本入门了。

---

## 11. 最后一句总结

学习这个系统的顺序不是：

```text
从文件夹第一个脚本看到最后一个脚本
```

而是：

```text
先理解四层架构
再记住主数据流
再按数据层 -> 解释器 -> 运行时桥 -> 投射物战斗 -> 角色入口 -> UI 的顺序看
最后用具体问题反向追调用链
```

你真正要掌握的不是“每个脚本写了什么”，而是：

> 一个新法术需求来了，我能判断它属于数据、解释规则、运行时桥接、投射物生命周期、战斗结算，还是 UI 编辑。

这就是架构能力。
