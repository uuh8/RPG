# 护盾术与静态投射物反弹：设计复盘

创建时间：2026-07-05  
功能范围：静态投射物类型法术、保护盾生成、投射物反弹、阵营改写、与触发类法术联动

---

## 0. 先建立整体心智模型

护盾术本质上不是一个“普通防御技能”，而是法术编程系统里的一个新型 `StaticProjectile`。

它和陨石术同属“静态投射物”大类：这类法术没有天然的前方发射速度，默认会在“当前施法点”生成。如果直接释放，当前施法点就是玩家附近；如果它被触发类火球术放进 payload，那么当前施法点就会变成火球击中的位置；如果它以后被定时类法术触发，当前施法点也可以是原投射物消失时的位置。

所以护盾术的关键不是“在玩家身上生成一个盾”，而是：

> 在法术解释器当前提供的空间点生成一个可反弹投射物的静态场。

这句话很重要，因为它决定了护盾术不是写死在玩家控制器里的技能，而是可以参与法术编程组合的“指令”。

完整链路如下：

```text
WandLoadout 中排布护盾术
  -> CastEvaluator 把 SpellDefinition 解释成 EmitCommand
  -> SpellCaster 根据 SpawnMode.StaticAtPoint 在当前点生成护盾 prefab
  -> ProjectileShield 监听进入护盾范围的 ProjectileBase
  -> ProjectileBase.ReflectByShield 改写投射物方向、阵营、攻击者
  -> 投射物继续飞行，并通过原有 Damage/HealthComponent 系统造成伤害
```

这套设计的核心价值是复用：护盾不直接处理伤害，不直接认识敌人，也不额外开一套“反弹伤害系统”。它只是改写投射物，让投射物继续走原本的战斗管线。

## 1. 基础知识和原理

### 1.1 静态投射物是什么

在 Noita 这类法术编程游戏里，法术大致可以分为几类：

- 会向前飞的投射物，例如火球、箭、魔弹。
- 修改后续法术的修正器，例如加速、重力、追踪、弹跳。
- 多重施法器，例如三重射击。
- 不依赖发射方向、在某个点生成效果的静态投射物，例如爆炸场、黑洞、护盾、召唤物、地面陷阱。

护盾术属于最后一类。它的重点不是“速度”，而是“生成位置”和“持续效果”。

在你的项目里，静态投射物不是独立于法术系统的技能，而是 `SpellKind.StaticProjectile` 加上不同的 `SpellSpawnMode` 来表达：

- `SkyfallAtPoint`：从天上向某个点坠落，例如陨石术。
- `StaticAtPoint`：直接在某个点生成，例如护盾术。

这里要特别注意：`StaticAtPoint` 只描述“生成方式”，不表示“永远不能动”。护盾当前不会动，是因为护盾 prefab 没有运动逻辑；如果以后给它加跟随、漂移、轨道、收缩等组件，它仍然可以移动。

### 1.2 反弹的物理原理

投射物反弹使用的是向量反射。

假设投射物当前速度方向是 `incoming`，护盾表面法线是 `normal`，反弹方向可以用 Unity 内置 API：

```csharp
Vector3 reflected = Vector3.Reflect(incoming, normal);
```

它背后的数学含义是：

```text
reflected = incoming - 2 * dot(incoming, normal) * normal
```

你不需要手写这个公式，因为 Unity 已经提供了 `Vector3.Reflect`。但理解这个公式有助于 Debug：如果 `normal` 错了，反弹方向一定会错。

所以护盾反弹最重要的不是“调用 Reflect”，而是拿到一个合理的反弹法线。

当前实现里，法线近似为：

```text
投射物位置 - 护盾中心
```

这相当于把护盾看成一个球形表面。投射物从球的某个方向进入，就按球面法线反弹出去。这和你的护盾 prefab 是球形盾的表现也一致。

### 1.3 Trigger 和 Collision 的区别

Unity 里 `Collider` 有两种常用交互方式：

- 普通碰撞：走 `OnCollisionEnter`，会产生物理接触，可能改变刚体运动。
- 触发器：勾选 `Is Trigger`，走 `OnTriggerEnter`，只检测进入，不产生物理阻挡。

护盾术使用 `OnTriggerEnter`，原因是它不希望 Unity 物理系统自动把投射物弹开，也不希望投射物走普通 `ProjectileBase.OnCollisionEnter` 后立刻爆炸或销毁。

我们需要的是：

```text
投射物进入护盾范围
  -> 护盾主动接管逻辑
  -> 计算反弹方向
  -> 改写投射物速度和阵营
  -> 投射物继续存在
```

如果使用普通 Collision，火球可能会把护盾当成一个命中目标，走原本的碰撞爆炸流程，这和“反弹”目标冲突。

### 1.4 阵营改写为什么重要

你的需求里有两个关键规则：

1. 玩家阵营的投射物也会被护盾反弹，增加趣味性。
2. 被反弹的投射物不会伤害释放护盾的玩家；如果反弹了敌方投射物，敌方投射物会反过来伤害敌方。

这意味着反弹不是单纯改变方向，还必须改变投射物的“归属”。

在项目的战斗系统里，伤害通过 `DamageRequest -> IDamageable.ReceiveHit -> HealthComponent` 进入统一管线。投射物内部保存了：

- `attackerTeam`：攻击者阵营。
- `attackerId`：攻击者身份。

投射物命中时会根据阵营过滤友方目标。  
所以护盾反弹敌方投射物时，如果只改方向不改阵营，敌方投射物仍然属于敌方，结果可能仍然伤害玩家或无法伤害敌人。

最终设计是：护盾反弹成功后，把该投射物改写为护盾拥有者阵营。

```text
敌人火球进入玩家护盾
  -> 火球方向被反射
  -> 火球 team 改成 Player team
  -> 火球 attackerId 改成护盾释放者
  -> 火球再次命中敌人时，走正常伤害管线
```

这样做的好处是：反弹后的投射物不需要特殊伤害逻辑，仍然复用已有的 `ProjectileBase` 命中规则。

### 1.5 为什么护盾不直接调用伤害

护盾不直接造成伤害，而是让被反弹的投射物继续飞。

这样设计有三个好处：

1. 保留原投射物特性：火球的爆炸、燃烧、伤害类型、速度等仍然有效。
2. 组合性更强：以后如果有冰弹、毒弹、穿透弹，被反弹后仍然保留自己的行为。
3. 架构更干净：护盾只负责“反弹”，伤害仍由 `ProjectileBase` 和 `HealthComponent` 处理。

这就是法术编程系统里很重要的设计思想：每个法术组件只改变一部分规则，不吞掉其他系统。

## 2. 常见实现方案与取舍

### 方案一：把护盾做成普通 Collider，让物理系统自动反弹

做法：

- 护盾 prefab 上放一个普通 `Collider`。
- 投射物上有 `Rigidbody`。
- 依赖 Unity Physics 的碰撞反弹。

优点：

- 实现简单。
- 看起来很像真实物理。

缺点：

- 反弹方向、速度、能量损失受物理材质和 Rigidbody 设置影响，不够可控。
- 很难顺便改写投射物阵营。
- 投射物可能触发原本的 `OnCollisionEnter` 爆炸逻辑。
- 对法术编程系统来说太黑盒，后续扩展成本高。

结论：不适合你的项目。因为护盾术不是纯物理玩具，而是一个有明确战斗规则的法术。

### 方案二：护盾直接销毁投射物并生成一个新的反向投射物

做法：

- 敌方火球进入护盾。
- 护盾销毁原火球。
- 护盾根据原火球参数重新 Instantiate 一个玩家火球，方向为反射方向。

优点：

- 逻辑直观。
- 新生成投射物天然可以设置阵营。

缺点：

- 需要复制大量投射物状态，例如伤害、速度、修正器、触发 payload、粒子状态。
- 如果原投射物身上有追踪、轨道、重力、弹跳等运行时状态，复制会很麻烦。
- 容易引入“新火球和旧火球表现不一致”的问题。

结论：可用于简单游戏，但不适合你的法术编程系统。因为你的投射物已经承载很多动态修正状态，销毁重建会丢失上下文。

### 方案三：护盾作为 Trigger，直接改写进入的 ProjectileBase

做法：

- 护盾 Collider 设置为 `Is Trigger`。
- `ProjectileShield.OnTriggerEnter` 捕获进入的投射物。
- 调用投射物自己的 `ReflectByShield`。
- 投射物内部改写速度、阵营、攻击者，并继续飞行。

优点：

- 不走普通碰撞爆炸流程。
- 不需要重建投射物，能最大限度保留原对象状态。
- 可以集中在 `ProjectileBase` 内部处理速度、阵营、运动模式冲突。
- 护盾只依赖 `ProjectileBase`，不需要认识具体火球、箭、陨石。

缺点：

- 需要你自己写反弹逻辑。
- 需要处理与 Homing、Orbit、Gravity 等运动修正的冲突。

结论：这是最终采用的方案。它最符合当前项目“组合性”和“可扩展性”的目标。

### 方案四：做一个 Projectile Manager，全局管理所有投射物和护盾

做法：

- 场景里有一个全局管理器。
- 每帧查询所有护盾和投射物距离。
- 距离进入范围则反弹。

优点：

- 可以做复杂规则，例如多个护盾优先级、反弹统计、批量优化。
- 对 ECS 或大规模弹幕有一定价值。

缺点：

- 当前项目规模不需要。
- 每帧扫描容易增加复杂度。
- 会绕开 Unity Physics 已经提供的 Trigger 检测。

结论：不是当前阶段最优解。你的项目目前更适合基于 Collider 的事件式触发。

## 3. 最终用到的技术

### 3.1 ScriptableObject 数据驱动

护盾术仍然通过 `SpellDefinition` 配置，而不是写死在代码里。

相关字段包括：

- `Kind = StaticProjectile`
- `SpawnMode = StaticAtPoint`
- `ProjectilePrefab = 保护盾 prefab`
- `ShieldReflectCount = 反弹次数`
- `ManaCost = 法力消耗`
- `Icon / DisplayName = UI 展示`

`ScriptableObject` 的作用是把“游戏数据”从代码里拿出来，让你可以在 Unity Editor 里配置法术，而不是每次新增法术都改 C#。

这是商业项目里非常常见的做法：代码负责规则，`ScriptableObject` 负责内容。

### 3.2 `SpellSpawnMode.StaticAtPoint`

`StaticAtPoint` 是一个生成模式，含义是：

```text
在当前法术上下文提供的位置生成 prefab。
```

它不关心这个 prefab 后续会不会移动，也不关心这个 prefab 是护盾、陷阱、光环还是召唤物。

这个抽象很关键。因为如果把护盾写成 `ShieldSpawnMode`，那以后做毒雾、冰冻区域、召唤炮台时又要加新分支。现在用 `StaticAtPoint`，后续很多“点位生成型法术”都能复用。

### 3.3 `Instantiate`

`SpellCaster` 使用 Unity 的：

```csharp
Instantiate(prefab, position, rotation);
```

在运行时生成护盾对象。

这里的 `position` 来自当前施法上下文：

- 直接释放：玩家施法点。
- 触发释放：投射物命中点。
- 定时释放：投射物消失点。

这就是护盾术能和触发类火球联动的原因。

### 3.4 `Collider` 与 `Is Trigger`

护盾 prefab 上需要一个 `Collider`，通常可以用 `SphereCollider`。

重点是勾选：

```text
Is Trigger = true
```

这样投射物进入护盾范围时，Unity 会调用：

```csharp
OnTriggerEnter(Collider other)
```

而不是普通的 `OnCollisionEnter`。

如果 `Is Trigger` 没勾，护盾更像一堵实体墙，火球可能会走普通碰撞爆炸流程，不符合需求。

### 3.5 `OnTriggerEnter`

`ProjectileShield` 通过：

```csharp
private void OnTriggerEnter(Collider other)
```

监听进入护盾范围的 Collider。

`other` 是进入触发器的那个对象的 Collider。由于投射物 prefab 的 Collider 不一定就在挂 `ProjectileBase` 的同一个 GameObject 上，所以代码使用：

```csharp
other.GetComponentInParent<ProjectileBase>()
```

这比 `other.GetComponent<ProjectileBase>()` 更稳，因为很多 prefab 会把 Collider 放在子物体上。

### 3.6 `Vector3.Reflect`

反弹方向用：

```csharp
Vector3.Reflect(incoming, normal)
```

其中：

- `incoming` 是投射物当前速度方向。
- `normal` 是护盾球面近似法线。

这个 API 是 Unity 内置向量函数，适合做镜面反射、弹跳、盾反、激光反射等功能。

### 3.7 `Rigidbody.linearVelocity`

投射物使用 `Rigidbody` 运动。反弹时，需要直接改写刚体速度：

```csharp
_rb.linearVelocity = newVelocity;
```

Unity 6 使用 `linearVelocity` 表示刚体线速度。旧版本常见写法是 `velocity`。

如果只改 transform.forward，不改 Rigidbody 速度，投射物看起来可能转向了，但实际运动方向不会变。

### 3.8 `Quaternion.LookRotation`

反弹后，投射物模型需要朝向新的飞行方向：

```csharp
Quaternion.LookRotation(reflectedDirection)
```

`Quaternion.LookRotation` 会根据一个方向向量生成旋转。  
你的项目里 `ProjectileBase` 还保留了 `_modelForwardOffsetEuler`，用于处理模型本身朝向和 Unity forward 不一致的问题。

### 3.9 `Physics.IgnoreCollision`

护盾生成后，需要忽略护盾与释放者自己的碰撞：

```csharp
Physics.IgnoreCollision(_shieldCollider, _ownerCollider);
```

反弹后，还需要刷新同阵营投射物之间的忽略碰撞关系。原因是敌方投射物被玩家护盾反弹后，它的阵营已经变成玩家阵营。此时它应该遵守玩家阵营投射物的碰撞规则。

`Physics.IgnoreCollision` 是 Unity Physics 提供的 API，用来让两个 Collider 不再互相产生碰撞或 Trigger 影响。

### 3.10 `Destroy`

护盾有反弹次数限制。每成功反弹一次，次数减一；次数耗尽后：

```csharp
Destroy(gameObject);
```

这会销毁整个护盾对象。

这里采用“次数耗尽立刻销毁”的规则，因为你明确选择了该方案。它的优点是反馈清晰：护盾还能不能用，玩家可以通过是否存在来判断。

## 4. 架构设计与拆解

### 4.1 护盾术在架构中的位置

护盾术跨了三个层次：

```text
Game.Skills
  负责描述“护盾术是什么法术”

Game.Character
  负责把法术解释结果变成 Unity 场景对象

Game.Combat
  负责护盾和投射物的战斗交互
```

更具体地说：

```text
SpellDefinition
  -> CastEvaluator
  -> EmitCommand
  -> SpellCaster
  -> ProjectileShield
  -> ProjectileBase
  -> HealthComponent / DamagePipeline
```

这里有一个很重要的模块边界：

- `Game.Skills` 不应该 Instantiate prefab。
- `Game.Skills` 不应该依赖 `ProjectileShield`。
- `Game.Combat` 不应该知道 `SpellDefinition`。
- `SpellCaster` 是桥接层，它可以读 `EmitCommand`，也可以生成 Unity 对象。

这就是为什么护盾术没有直接写进 `CastEvaluator` 的 runtime 行为。`CastEvaluator` 只输出纯数据，真正生成和交互放在运行时层处理。

### 4.2 为什么不把护盾写进 WizardController

如果把护盾术写进 `WizardController`，会得到一个传统技能系统：

```text
按键 -> WizardController.SpawnShield()
```

这种方式短期很快，但会破坏法术编程玩法。因为它无法自然支持：

- 火球命中后生成护盾。
- 定时投射物结束时生成护盾。
- 三重射击中混入护盾。
- 护盾被法术修正影响。
- 后续静态投射物统一扩展。

所以护盾必须作为 `SpellDefinition` 的一种数据进入解释器，而不是成为角色控制器上的硬编码技能。

### 4.3 为什么 `StaticAtPoint` 放在 SpawnMode，而不是单独做 ShieldKind

护盾术有两个维度：

```text
法术类别：StaticProjectile
生成方式：StaticAtPoint
具体行为：ProjectileShield 组件
```

这三个维度分开后，系统才容易扩展。

如果你以后做毒雾：

```text
Kind = StaticProjectile
SpawnMode = StaticAtPoint
Prefab = PoisonCloud
```

如果以后做冰冻陷阱：

```text
Kind = StaticProjectile
SpawnMode = StaticAtPoint
Prefab = IceTrap
```

如果以后做从天而降的闪电柱：

```text
Kind = StaticProjectile
SpawnMode = SkyfallAtPoint
Prefab = LightningStrike
```

也就是说，`SpawnMode` 只管“怎么生成”，具体玩法由 prefab 上的组件决定。

### 4.4 添加和改动的脚本

#### `Assets/_Project/Scripts/Skills/SpellKind.cs`

改动点：

- 增加 `SpellSpawnMode.StaticAtPoint`。

作用：

- 让法术数据可以表达“在当前点直接生成”的静态投射物。

设计意义：

- 它是护盾术进入法术编程系统的语义入口。
- 它不绑定护盾，可以被未来的点位型法术复用。

#### `Assets/_Project/Scripts/Skills/SpellDefinition.cs`

改动点：

- 增加 `ShieldReflectCount` 字段。

作用：

- 在 `SpellDefinition` 资产里配置护盾可反弹次数。

设计意义：

- 护盾次数属于法术数据，不应该写死在 `ProjectileShield` 里。
- 不同护盾可以配置不同强度，例如小护盾 1 次，大护盾 5 次。

#### `Assets/_Project/Scripts/Skills/EmitCommand.cs`

改动点：

- 增加 `ShieldReflectCount`。

作用：

- 把 `SpellDefinition` 中的护盾次数烘焙到一次施法的输出命令里。

设计意义：

- `EmitCommand` 是一次施法的 value snapshot。
- 运行时不应该再回头查原始 `SpellDefinition`，因为 spell asset 可能在 Play Mode 中被 UI 改动。

#### `Assets/_Project/Scripts/Skills/CastEvaluator.cs`

改动点：

- 在生成 `EmitCommand` 时，把 `ShieldReflectCount` 写入命令。

作用：

- 纯解释器不关心护盾怎么反弹，只负责把法术数据解释成运行时命令。

设计意义：

- 维持了 `CastEvaluator` 的纯逻辑性质。
- 它仍然可以被 EditMode Tests 验证，不依赖 Unity 场景。

#### `Assets/_Project/Scripts/Character/Spells/SpellCaster.cs`

改动点：

- 在 `RunCast` 里处理 `SpellSpawnMode.StaticAtPoint`。
- 增加生成静态投射物的逻辑。
- 生成后查找 `ProjectileShield` 并调用 `Init`。

作用：

- 把 `EmitCommand` 变成场景中的护盾对象。

设计意义：

- `SpellCaster` 是法术系统和 Unity Runtime 的边界。
- 它知道 prefab、Instantiate、Transform，但不处理具体战斗反弹。

#### `Assets/_Project/Scripts/Combat/Projectiles/ProjectileShield.cs`

新增脚本。

作用：

- 挂在护盾 prefab 上。
- 保存护盾拥有者阵营、攻击者 ID、剩余反弹次数。
- 监听进入护盾范围的 `ProjectileBase`。
- 调用投射物自身的反弹接口。
- 次数耗尽后销毁护盾。

设计意义：

- 护盾行为封装在一个独立组件里。
- 未来做不同护盾时，可以继承或新增类似组件，而不污染 `SpellCaster`。

#### `Assets/_Project/Scripts/Combat/Projectiles/ProjectileBase.cs`

改动点：

- 增加 `ReflectByShield`。
- 增加刷新同阵营投射物忽略碰撞的方法。

作用：

- 投射物自己负责反弹后的内部状态改写。

设计意义：

- 只有 `ProjectileBase` 最清楚自己的 Rigidbody、速度、阵营、运动模式和碰撞注册状态。
- 护盾不应该直接乱改投射物内部字段，否则封装性会变差。

### 4.5 数据流详解

#### 直接释放护盾

```text
玩家点击施法
  -> WizardController 记录 ClickAimPoint
  -> PlayerWizardAttackState 到达释放帧
  -> SpellCaster.CastWand
  -> CastEvaluator 输出 StaticAtPoint 护盾命令
  -> SpellCaster 在玩家施法点生成护盾
```

这时护盾出现在玩家附近。

#### 触发火球 + 护盾

法术排列示例：

```text
触发类火球术 -> 护盾术
```

运行过程：

```text
CastEvaluator 遇到触发火球
  -> 把后续护盾术捕获为 payload
  -> 发射触发火球
  -> 火球命中敌人或场景
  -> ProjectileBase.Impacted 通知 SpellCaster
  -> SpellCaster.RunCast(payload, hitPoint, hitDirection, ...)
  -> 护盾在 hitPoint 生成
```

这说明护盾术本身没有特殊判断“我是不是被触发了”。它只服从当前上下文提供的位置。这是法术编程系统的正确方向。

#### 护盾反弹敌方火球

```text
敌方火球进入护盾 Trigger
  -> ProjectileShield.OnTriggerEnter
  -> 找到 ProjectileBase
  -> 计算护盾中心到火球的法线
  -> projectile.ReflectByShield(normal, ownerTeam, ownerAttackerId)
  -> 火球速度被反射
  -> 火球阵营变为护盾拥有者阵营
  -> 火球继续飞
  -> 命中敌人后走原本 ProjectileBase.OnCollisionEnter
  -> HealthComponent.ReceiveHit
```

护盾没有直接调用 `ReceiveHit`，这是架构上最干净的一点。

## 5. 踩坑与 Debug

### 5.1 护盾不能用普通碰撞，否则会变成“墙”

问题：

如果护盾 Collider 没有勾选 `Is Trigger`，投射物可能会触发普通碰撞。对于火球来说，普通碰撞往往意味着爆炸、销毁、触发 payload。

解决：

护盾使用 Trigger，并由 `ProjectileShield.OnTriggerEnter` 主动处理反弹。

排查方式：

- 检查护盾 prefab 的 Collider。
- 确认 `Is Trigger = true`。
- 确认投射物至少有一方带 `Rigidbody`，否则 Trigger 事件可能不会按预期触发。

### 5.2 如果护盾总是在玩家位置生成，说明上下文位置丢了

问题：

静态投射物最容易写错的地方是：生成时直接用 caster transform.position。

这样会导致触发类火球命中敌人后，payload 里的护盾仍然生成在玩家身边。

解决：

`SpellCaster.RunCast` 必须接收当前上下文位置 `spawnPos`。  
直接施法时这个位置来自玩家；触发 payload 时这个位置来自 hitPoint。

设计原则：

```text
静态投射物不自己决定生成在哪里，它服从法术上下文。
```

### 5.3 如果敌方火球被反弹后仍然不能伤害敌人，说明阵营没有改写

问题：

只改速度，不改 team，会导致投射物仍然属于原敌方阵营。

解决：

`ProjectileBase.ReflectByShield` 中改写：

```text
_attackerTeam = 护盾拥有者阵营
_attackerId = 护盾释放者 ID
```

这样反弹后的投射物自然能伤害敌人，且不会伤害释放护盾的玩家。

### 5.4 如果反弹方向很怪，优先检查法线

问题：

`Vector3.Reflect` 本身通常不会错，错的一般是 `normal`。

护盾是球形，所以合理法线是：

```text
投射物位置 - 护盾中心
```

如果使用投射物 forward、玩家 forward 或 hitDirection，可能会得到不稳定方向。

解决：

当前实现使用球心到投射物的方向作为法线，并加入 fallback：

- 优先使用 `other.transform.position - shield.position`
- 不可靠时使用 `other.bounds.center - shield.position`
- 仍然不可靠时使用 `transform.forward`

### 5.5 如果反弹后仍然被追踪或轨道修正拉走，说明运动模式冲突没有处理

问题：

你的投射物现在已经支持 Homing、Orbit、Gravity、Bounce 等修正。  
如果一个正在 Orbit 的投射物被护盾反弹，但下一帧 Orbit 逻辑又继续覆盖它的速度，那么玩家看到的就不是反弹，而是“护盾没效果”。

解决：

当前实现里，`ReflectByShield` 会关闭容易直接覆盖飞行方向的运动模式，例如 Homing 和 Orbit。

这属于“后发生的强控制行为覆盖前面的运动控制”。  
它和你之前提出的“多个修正冲突时以后面的为主”的方向一致。

### 5.6 如果反弹后的投射物和同阵营投射物发生奇怪碰撞，需要刷新 IgnoreCollision

问题：

投射物生成时，项目里有同阵营投射物互相忽略碰撞的注册逻辑。  
敌方火球被玩家护盾反弹后，它的阵营变了，但之前建立的碰撞忽略关系没有自动更新。

解决：

反弹后调用刷新逻辑，让该投射物重新和当前同阵营投射物建立 `Physics.IgnoreCollision`。

### 5.7 如果护盾不销毁，检查反弹次数是否只在成功反弹后减少

问题：

Trigger 进入不一定代表一定成功反弹，例如进入的是非投射物、已经销毁的投射物、速度为 0 的对象。

解决：

只有 `projectile.ReflectByShield(...)` 返回成功时，才减少次数。  
次数减到 0 后立刻 `Destroy(gameObject)`。

这样可以避免非投射物浪费护盾次数。

## 6. 大厂面试 Q&A

### Q1：你为什么把护盾做成 StaticProjectile，而不是玩家角色技能？

答：

因为这个项目的核心玩法是法术编程，护盾不应该只是一个按键技能，而应该是可以进入 wand sequence 的一条指令。  
如果把它写在 `WizardController` 里，它只能在玩家身边释放，很难和触发类、定时类、多重施法、修正类法术组合。  
把它做成 `StaticProjectile` 后，它服从当前施法上下文的位置。直接释放就在玩家处，触发释放就在命中点，后续也可以接入定时触发和其他组合。这更符合 Noita-like 系统的可组合性。

### Q2：为什么护盾用 Trigger，而不是普通 Collision？

答：

因为普通 Collision 会进入投射物原本的碰撞命中流程，火球可能直接爆炸或销毁。护盾想要的是“检测投射物进入范围，然后主动改写它的运动和阵营”，不希望 Unity 物理系统先接管结果。  
所以我使用 `Collider.isTrigger` 和 `OnTriggerEnter`。Trigger 只负责通知进入事件，反弹方向、阵营、次数消耗由代码控制。

### Q3：反弹方向如何计算？

答：

我把护盾近似成一个球面，反弹法线取“护盾中心指向投射物当前位置”的方向。然后用 Unity 的 `Vector3.Reflect(incoming, normal)` 计算反射方向。  
这样符合球形护盾的视觉直觉：从哪一侧撞进来，就从对应球面法线方向反弹出去。

### Q4：敌人的火球被玩家护盾反弹后，为什么能伤害敌人？

答：

因为反弹时不只是改速度，还会改写投射物的 ownership。  
`ProjectileBase.ReflectByShield` 会把投射物的 team 和 attackerId 改成护盾拥有者。这样反弹后的火球继续走原来的伤害管线，但阵营已经变成玩家阵营，所以命中敌人时会被视为玩家攻击。

### Q5：为什么不销毁原投射物再生成一个新的投射物？

答：

销毁重建看起来简单，但会丢失很多运行时状态，比如伤害快照、触发 payload、速度、重力、弹跳次数、特效状态、其他修正器状态。  
当前系统的投射物已经是法术编程的运行结果，身上可能携带很多组合状态。直接改写原 `ProjectileBase` 可以最大程度保留这些状态，也更容易和后续法术组合兼容。

### Q6：护盾术如何和触发类火球联动？

答：

触发类火球在 `CastEvaluator` 中会捕获后续法术作为 payload。火球命中后，`ProjectileBase.Impacted` 通知 `SpellCaster` 在 hitPoint 执行 payload。  
护盾术本身只知道自己是 `StaticAtPoint`，所以它会在当前上下文点生成。这个当前点在触发 payload 中就是命中点，因此护盾自然出现在火球击中的地方。

### Q7：如果投射物已经有 Homing 或 Orbit，护盾反弹后怎么处理冲突？

答：

这是运动控制权的问题。Homing 和 Orbit 都会持续改写投射物方向，如果反弹后不处理，它们可能下一帧又把速度覆盖回去。  
当前策略是：护盾反弹属于一次强制方向改写，会关闭 Homing 和 Orbit 这类直接控制方向的运动模式，让玩家能看到明确的反弹结果。  
更长期可以做成统一的 projectile motion stack 或 priority system，但当前阶段先在 `ProjectileBase` 中集中处理冲突，复杂度更可控。

### Q8：这个功能如何保证架构不污染？

答：

我把职责分层：

- `SpellDefinition` 存护盾法术数据。
- `CastEvaluator` 只输出纯 `EmitCommand`，不接触 Unity 场景。
- `SpellCaster` 负责根据命令 Instantiate prefab。
- `ProjectileShield` 负责护盾范围检测和次数消耗。
- `ProjectileBase` 负责自身反弹、阵营、速度、碰撞关系。

这样 `Game.Skills` 不依赖 `Game.Combat` 的具体护盾组件，`Game.Combat` 也不知道法术定义。模块边界比较清晰。

### Q9：为什么反弹次数放在 SpellDefinition，而不是写死在 ProjectileShield？

答：

因为反弹次数是法术平衡数据，不是组件固定规则。  
放在 `SpellDefinition` 里后，可以做出不同等级、不同消耗、不同次数的护盾。`ProjectileShield` 只作为运行时执行器，接收本次施法传入的次数。

### Q10：如果让你继续优化这个系统，你会做什么？

答：

我会把所有会改写投射物运动的效果抽象成一个统一的 motion mode 或 motion controller，明确谁拥有当前运动控制权，以及后续修正如何覆盖或叠加前面的修正。  
现在 Homing、Orbit、Shield Reflect 已经出现冲突处理需求。短期在 `ProjectileBase` 里集中处理是合理的，但长期如果继续增加牵引、回旋、锁链、风场等法术，就需要更正式的优先级和生命周期管理。

## 7. 模拟面试者完整讲解

这个功能我设计的是一个 Noita-like 法术编程系统中的静态投射物法术，具体表现是保护盾。它不是传统意义上写死在角色控制器里的防御技能，而是和火球、陨石一样，可以放进 wand sequence 中参与组合。

我首先把需求拆成两个层面：第一是法术系统层面，它要能表达“在当前上下文点生成一个静态投射物”；第二是战斗系统层面，这个静态投射物要能反弹进入范围的投射物，并且正确处理阵营归属。为了支持后续更多点位型法术，我没有把生成方式命名为 Shield，而是在 `SpellSpawnMode` 中加入了 `StaticAtPoint`。这样护盾、陷阱、毒雾、召唤物以后都可以复用同一个生成语义。

在数据层，我把护盾术配置成 `SpellDefinition`，它的 `Kind` 是 `StaticProjectile`，`SpawnMode` 是 `StaticAtPoint`，并且增加了 `ShieldReflectCount` 作为可配置的反弹次数。`CastEvaluator` 仍然保持纯逻辑，只把这个数据烘焙进 `EmitCommand`，不做任何 Unity Runtime 操作。这样法术解释器仍然是可测试、可推理的。

在运行时层，`SpellCaster` 根据 `EmitCommand` 判断生成方式。如果是 `StaticAtPoint`，它就在当前施法上下文的位置 Instantiate prefab。这个位置非常关键：直接施法时是玩家施法点，触发类火球命中后执行 payload 时就是命中点。因此护盾术不需要写任何特殊逻辑，就能自然支持“触发火球命中处生成护盾”的组合。

护盾 prefab 上挂了 `ProjectileShield`。它使用 Trigger Collider 监听投射物进入，而不是使用普通物理碰撞。原因是普通碰撞会触发投射物原本的命中爆炸流程，而护盾需要主动接管逻辑。`ProjectileShield.OnTriggerEnter` 会用 `GetComponentInParent<ProjectileBase>` 找到投射物，计算球形护盾表面的近似法线，然后调用投射物自己的 `ReflectByShield`。

真正的反弹逻辑放在 `ProjectileBase` 内部，因为只有投射物自己最了解自己的 Rigidbody、速度、阵营、攻击者、当前运动模式和碰撞忽略关系。反弹时我使用 `Vector3.Reflect` 计算新方向，保留原速度大小，改写 `Rigidbody.linearVelocity`，同时把投射物的 team 和 attackerId 改成护盾拥有者。这样敌方火球被玩家护盾反弹后，不需要额外写伤害逻辑，它继续走原本的 `ProjectileBase -> HealthComponent -> DamagePipeline` 管线，就会自然伤害敌人，并且不会伤害释放护盾的玩家。

这个功能里比较容易踩坑的是运动修正冲突。项目里投射物已经支持 Homing、Orbit、Gravity、Bounce 等修正，其中 Homing 和 Orbit 会持续改写方向。如果护盾反弹后不关闭这些强控制运动，下一帧它们可能把反弹速度覆盖掉，玩家看起来就像护盾没生效。所以我在反弹接口里集中处理这类冲突，让护盾反弹拥有一次明确的运动控制权。

整体上，这个功能的设计重点不是单独实现一个护盾，而是把“护盾”作为一种可组合的法术指令接入现有架构。它复用了 SpellDefinition 的数据驱动、CastEvaluator 的解释器、SpellCaster 的运行时桥接、ProjectileBase 的投射物管线和 HealthComponent 的伤害系统。这样实现后，护盾术既能直接释放，也能被触发类法术放到命中点生成，还能保留后续扩展空间。

## 8. 建议阅读代码顺序

如果你想理解护盾术，不建议一上来直接看 `ProjectileShield`，否则容易只看到“反弹代码”，看不到它为什么能进入法术编程系统。

推荐顺序：

1. `SpellKind.cs`  
   先看 `StaticProjectile` 和 `StaticAtPoint` 的语义，理解护盾术属于哪类法术。

2. `SpellDefinition.cs`  
   看护盾术的数据从哪里配置，尤其是 `ShieldReflectCount`。

3. `CastEvaluator.cs`  
   看法术解释器如何把 `SpellDefinition` 变成 `EmitCommand`。

4. `EmitCommand.cs`  
   看一次施法结果里保存了哪些运行时快照。

5. `SpellCaster.cs`  
   看 `StaticAtPoint` 如何在当前上下文位置生成 prefab。

6. `ProjectileShield.cs`  
   看护盾如何检测投射物、计算法线、消耗次数。

7. `ProjectileBase.cs`  
   看投射物如何真正改写速度、阵营、运动模式和碰撞关系。

8. `HealthComponent.cs` / `DamagePipeline.cs`  
   最后看反弹后的投射物如何复用原有伤害管线。

这个顺序对应的是“数据定义 -> 解释器 -> 运行时生成 -> 战斗交互 -> 伤害结算”，也就是系统真实执行的方向。

## 9. Editor 检查清单

护盾术后续如果重新配置 prefab，可以按这个清单检查：

1. 护盾法术 `SpellDefinition`
   - `Kind = StaticProjectile`
   - `SpawnMode = StaticAtPoint`
   - `ProjectilePrefab` 指向护盾 prefab
   - `ShieldReflectCount` 大于 0
   - `ManaCost` 根据强度配置
   - `Icon` 和 `DisplayName` 配好

2. 护盾 prefab
   - 挂有 `ProjectileShield`
   - 有一个合适大小的 `Collider`
   - `Collider.Is Trigger = true`
   - Layer Collision Matrix 允许它检测投射物
   - 视觉球体大小和 Collider 大小一致或接近

3. 投射物 prefab
   - 挂有 `ProjectileBase` 子类
   - 有 `Rigidbody`
   - 有 Collider
   - 速度不是 0，否则无法计算有效反弹方向

4. 联动测试
   - 直接释放护盾：应该在玩家当前施法点生成。
   - 触发火球 + 护盾：护盾应该在火球命中点生成。
   - 玩家火球撞护盾：应该被反弹，不伤害释放者。
   - 敌人火球撞护盾：应该被反弹，并能伤害敌人。
   - 反弹次数耗尽：护盾应该立刻销毁。
