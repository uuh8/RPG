# 手写 URP 水 Shader：从最终水面反向拆解图形学原理

> 创建日期：2026-07-13  
> 项目环境：Unity 6.3（6000.3.16f1）、URP 17.3、PC Renderer  
> 目标读者：第一次完整开发手写 Shader、正在准备 Unity 客户端/图形方向面试的开发者  
> 对应源码：`Assets/_Project/Art/Elemental/Shaders/ElementWater.shader`、`ElementWaterCore.hlsl`  
> 本文范围：解释当前已经实现的程序化水面；不把 Refraction、真实流体、Vertex Displacement、Tessellation 或 P6 Cell 模拟描述成已完成。

- UV 和 Noise 决定水纹怎样移动；
- Normal 决定高光怎样变化；
- Camera Depth 决定深浅水颜色；
- Fresnel 决定观察角变化；
- Foam Mask 决定岸边接触线；
- Alpha Blend 决定能看到多少水底。

---

## 0. 先看结果：我们最终交给屏幕的到底是什么

玩家看到的是一块透明、会流动、随水深变色、斜视时反光增强、岸边带有泡沫、还能响应 URP 灯光的水面。这个结果容易让初学者误以为我们“模拟了一池水”，但当前 Shader 实际没有求解流体速度、压力、质量守恒，也没有改变水面 Mesh 的顶点位置。它完成的是一个更明确的问题：

> 对水面 Mesh 覆盖到的每个 Fragment，根据 UV、时间、Camera、场景深度和灯光，计算这个 Fragment 的表面颜色、法线、光滑度与 Alpha，然后交给 URP PBR Lighting 和透明混合。

可以先把最终 Fragment 的主要数据关系压缩为五个 Mask 和两条输出：

```text
双向移动 Value Noise
    ├──> 动态 Normal ────────────────┐
    ├──> 深度边界扰动                │
    └──> 泡沫断裂                    │
                                      │
Camera Depth ──> Water Thickness ──> Depth Mask
动态 Normal + View Direction ──────> Fresnel Mask
Water Thickness + Noise ───────────> Foam Mask

Depth/Fresnel/Foam Masks ──────────> Albedo + Alpha
动态 Normal + Albedo + Smoothness ─> URP PBR Lighting
PBR Color + Alpha + Background ─────> 屏幕最终颜色
```

当前颜色链的核心公式是：

```text
DepthColor   = Lerp(ShallowColor, DeepColor, DepthMask)
FresnelColor = Lerp(DepthColor, FresnelColorProperty, FresnelMask)
FinalAlbedo  = Lerp(FresnelColor, FoamColor, FoamMask)
```

当前透明度链是：

```text
DepthAlpha   = Lerp(ShallowAlpha, DeepAlpha, DepthMask)
FresnelAlpha = FresnelMask × FresnelAlphaStrength
FoamAlpha    = FoamMask × FoamAlphaBoost

FinalAlpha = Saturate(
    (DepthAlpha + FresnelAlpha + FoamAlpha) × WaterAlpha
)
```

`Lerp(A,B,t)` 的完整定义为：

```text
Lerp(A,B,t) = A × (1-t) + B × t
```

当 `t=0` 时完整选择 A；当 `t=1` 时完整选择 B；中间值产生连续过渡。`Saturate(x)` 等价于 `Clamp(x,0,1)`。这两个函数贯穿整个 Shader，因为 Shader 的常见思路不是“判断水是浅还是深”，而是先生成连续的 `0~1 Mask`，再用 Mask 混合两个端点。

最终屏幕像素还要经过 Alpha Blend：

```text
ScreenColor
= WaterLitColor × FinalAlpha
 + BackgroundColor × (1-FinalAlpha)
```

因此，当前水面不是一个独立“蓝色层”。它同时依赖水自身的材质计算和水面之前已经画入 Framebuffer 的背景。

## 1. 从最终效果反向进行“难题拆解”

面对“做一池可信的水”这个模糊目标，如果直接打开 Shader Graph 或开始写 HLSL，很容易堆出一组互相影响、无法 Debug 的公式。正确做法是先从玩家看到的结果不断追问“为什么”，直到每个问题都能变成一个独立、可验证的小功能。

### 第一层追问：为什么它看起来是一池水，而不是一块蓝色 Plane

因为最终画面同时提供了多种视觉线索：

- 可以看到水下背景，所以它是透明介质的近似；
- 水越深颜色越深、Alpha 越高，所以有“厚度”；
- 表面高光在移动，所以有动态微表面；
- 斜视角反射增强，所以具有 Fresnel 视角关系；
- 水和地面接触处有泡沫，所以水面与场景不是完全割裂的；
- 它接受灯光、阴影、GI 和雾，所以仍属于 3D 场景，而不是贴在屏幕上的 UI。

### 第二层追问：这些线索分别需要什么数据

| 最终线索 | 必要输入 | 生成的中间量 |
|---|---|---|
| 水面流动 | Mesh UV、`_Time.y`、两组 Scale/Speed | `waveNoiseA/B`、`combinedNoise` |
| 动态高光 | Noise 高度、World Position、TBN | `normalTS`、`dynamicNormalWS` |
| 深浅颜色 | Camera Depth、水面 World Position | `waterThickness`、`depthMask` |
| 斜视反光 | Normal、View Direction | `fresnelMask` |
| 岸边泡沫 | `waterThickness`、Noise | `contactMask`、`foamMask` |
| 透明层次 | Depth/Fresnel/Foam Masks | `finalAlpha` |
| 场景光照 | Albedo、Normal、Smoothness、灯光/GI | `UniversalFragmentPBR` 输出 |

### 第三层追问：这些输入从哪里进入 GPU

```text
Mesh Vertex Buffer
  ├── positionOS / normalOS / tangentOS / uv
  ↓ WaterVertex
Varyings
  ├── positionWS / normalWS / tangentWS / uv / shadowCoord
  ↓ Rasterization 插值
WaterFragment
  ├── Material Properties（颜色、速度、强度）
  ├── Unity Built-in Variables（_Time、Camera 矩阵）
  ├── _CameraDepthTexture
  └── URP 灯光、阴影与 GI
```

由此可以得到实际开发顺序。它与上面的逆向思考方向相反：先搭建最底层透明 Pass，再逐层加入可独立验证的小功能。

```text
1. 透明 URP Lit 基线
2. UV 随时间移动
3. 手写 Hash 与 Value Noise
4. 双层 Noise 合成
5. Height-to-Normal 与 TBN
6. Scene Depth 水层厚度
7. 深浅颜色与深度 Alpha
8. Fresnel
9. 岸边泡沫
10. URP PBR、雾、阴影与性能验证
```

后面的章节就按这个开发顺序讲解，但每一节都先说明“它解决了最终画面的哪个问题”。

## 2. 小功能一：先得到一块能参与 URP 光照的透明水面

### 2.1 需要先区分 Shader、Material、Mesh 与 Renderer

- `ElementWater.shader` 是 GPU 程序和 Render State 的定义；
- `M_ElementWater_Handwritten` 是一组具体参数；
- Plane Mesh 提供顶点、三角形、UV、Normal 和 Tangent；
- `MeshRenderer` 把 Mesh 与 Material 提交给 URP；
- `StatusVolume` 属于 Gameplay，既不向 Shader 提供深度，也不负责画水。

Shader 与 Material 的关系类似函数与实参：Shader 声明 `_ShallowColor`，Material 决定这池水的 `_ShallowColor` 具体是多少。

### 2.2 Render Queue、Depth Test 与 Depth Write

当前 SubShader 使用：

```hlsl
"RenderType" = "Transparent"
"Queue"      = "Transparent"
Blend SrcAlpha OneMinusSrcAlpha
ZWrite Off
ZTest LEqual
Cull Back
```

不透明物体通常先画并写入 Color Buffer 和 Depth Buffer；透明水面随后读取已经完成的不透明场景，才能看到水下物体并采样 `_CameraDepthTexture`。

`ZTest LEqual` 表示当前水面 Fragment 的深度小于等于 Depth Buffer 时才可能通过，水仍然会被前方墙体遮挡。`ZWrite Off` 表示通过后不把水自身深度写回。它解决“第一层透明面把后续透明对象完全挡住”的问题，但引入透明排序限制：多个透明物体互相交叠时，仅靠 Depth Buffer 无法得到任意顺序都正确的结果。

`Cull Back` 只画正面。水下观察若直接改成 `Cull Off`，会同时画正反面，可能造成法线方向错误、Alpha 叠加两次和 Overdraw 翻倍；正式水下视角应该独立设计，而不是把 Cull 关闭当万能修复。

### 2.3 Alpha Blend 的图形学含义

对 `Blend SrcAlpha OneMinusSrcAlpha`，简化颜色公式为：

```text
Cout = Csrc × Asrc + Cdst × (1-Asrc)
```

- `Csrc`：当前 Water Fragment 经 PBR 后的颜色；
- `Asrc`：`finalAlpha`；
- `Cdst`：Framebuffer 中已经存在的背景；
- `Cout`：混合后写回的颜色。

如果 Alpha=0.2，水面贡献 20%，背景贡献 80%；Alpha=0.8 时反过来。这里的 Alpha 是风格化混合权重，不是严格的物理透射率。真实介质吸收常使用 Beer-Lambert Law：

```text
T(d) = exp(-σ × d)
```

`T` 是经过距离 `d` 后剩余的透射比例，`σ` 是吸收系数。当前实现没有使用该公式，而是使用更容易调参的浅/深 Alpha Lerp。面试时应主动说明这个边界。

### 2.4 Vertex Stage 与 Fragment Stage 为什么要分开

`WaterVertex` 对 Mesh 每个顶点执行，主要完成位置和基底变换；`WaterFragment` 对 Rasterization 产生的大量 Fragment 执行，负责细致 Noise、Normal、Depth、颜色和光照。

把复杂 Noise 放在 Fragment 的原因是当前 Plane 顶点密度低：逐顶点算 Noise 后再插值会丢失高频细节。但 Fragment 次数远大于 Vertex，透明 Overdraw 还可能让同一像素重复执行，所以它的成本更高。这个选择是画面质量与 GPU 成本的 trade-off。

## 3. 小功能二：让一张静态 Plane 获得连续流动纹理

### 3.1 UV 是什么

UV 是 Mesh 表面携带的二维坐标。常见 Plane 的左下角约为 `(0,0)`，右上角约为 `(1,1)`。顶点只保存少量 UV，Rasterization 会为三角形内部 Fragment 做透视正确插值。忽略透视修正细节时，可以用重心坐标理解：

```text
uv_fragment = λ0×uv0 + λ1×uv1 + λ2×uv2
λ0 + λ1 + λ2 = 1
```

所以 Shader 可以在每个 Fragment 得到连续 UV，而不是只有顶点处有坐标。

### 3.2 Panning：静态坐标怎样“流动”

移动 UV 的公式非常简单：

```text
UV'(t) = UV + Speed × Time
```

`Speed=(sx,sy)` 表示每秒在 U、V 方向平移多少。它不是在移动 Mesh，也不是在移动 Camera；它改变的是“当前 Fragment 去程序化纹理的哪个位置取值”。因此视觉纹理会流过静止表面。

当前使用两层：

```text
uvA = uv + WaveSpeedA × time
uvB = uv + WaveSpeedB × time
```

两层速度方向不同，例如 `(0.05,0.02)` 与 `(-0.03,0.04)`。若两层方向相同，结果仍容易呈现整齐的单向滑动；交叉方向能形成干涉般的复杂变化，但它仍不是物理波动方程。

### 3.3 为什么没有 Panner 节点也能实现

Shader Graph 实验时没有找到 `Panner`，最终用 `Time × WaveSpeed` 接入 `Tiling And Offset / Offset`。这不是退而求其次，而是手工写出了 Panner 的本质公式。节点只是公式的 UI 封装；理解 `UV + Speed×Time` 后，节点是否存在不再构成阻碍。

## 4. 小功能三：不使用贴图，自己生成 Value Noise

### 4.1 为什么需要 Noise

只有线性移动 UV 不会自己产生图案；必须有一个函数把二维坐标映射成不同高度：

```text
height = Noise(uv)
```

资源商城常见方案是采样一张 Noise Texture 或 Normal Map。当前为了学习和自研，选择程序化 `Value Noise`：不依赖外部贴图，代价是增加 ALU 运算。

### 4.2 Hash：怎样让每个格点得到稳定伪随机值

GPU 上不能让每个 Fragment 共用一个不断修改状态的传统随机数生成器。水面还要求相同格点每帧返回相同值，否则图案会闪烁。于是使用纯函数：

```text
r = Hash21(integerCell)
```

它满足“同输入同输出”，只是结果看起来缺少规律。`ElementWaterHash21` 使用 `frac`、点积和常数扰动把二维坐标折叠为 `[0,1)` 标量。`frac(x)=x-floor(x)`，例如：

```text
frac(3.75)=0.75
frac(8.12)=0.12
```

这些 Hash 常数不是水的物理参数，只是经验性地打散坐标相关性。更高质量 Hash 可降低方向性和周期，但会增加计算量。

### 4.3 从随机格点到连续表面

给定 `position`：

```text
cell  = floor(position)   // 当前整数格子
local = frac(position)    // 格内坐标 (u,v)
```

查询四角：

```text
v00 = Hash(cell + (0,0))
v10 = Hash(cell + (1,0))
v01 = Hash(cell + (0,1))
v11 = Hash(cell + (1,1))
```

先沿 X，再沿 Y 做 Bilinear Interpolation：

```text
bottom = Lerp(v00,v10,smooth.x)
top    = Lerp(v01,v11,smooth.x)
value  = Lerp(bottom,top,smooth.y)
```

直接使用 `local` 虽能保证数值连续，但格子边界的斜率会突变。当前先使用三次 Hermite 曲线：

```text
smooth(f) = f²(3-2f)
```

它满足：

```text
smooth(0)=0
smooth(1)=1
smooth'(0)=0
smooth'(1)=0
```

边界导数为零，所以相邻格子连接更柔和。Value Noise 最终只产生标量高度，不直接产生颜色或法线。

### 4.4 Scale 为什么越大纹理越细

代码使用：

```text
NoisePosition = MovingUV × WaveScale
```

当 UV 从 0 变化到 1：

- Scale=2，NoisePosition 大约跨过 2 个格子；
- Scale=15，跨过约 15 个格子。

因此 Scale 是 UV 空间频率，不是视觉尺寸本身。Mesh UV 若缩放或铺法改变，同一个 Scale 的世界空间大小也会改变；这正是 UV Space 方案的 trade-off。若未来希望不同尺寸水池保持相同世界波纹尺寸，可以改用 World Position XZ 作为 Noise 坐标。

### 4.5 双层合成

```text
CombinedNoise = Saturate((NoiseA + NoiseB) × 0.5)
```

乘 0.5 是求平均，避免两层 `[0,1]` 相加后进入 `[0,2]`。实验中曾把“合并 Noise”误认成后续 `Depth+Noise` 的最终 `Saturate` 输出；正确 Combined Noise 是 A/B 相加后第一次乘 0.5 的结果。前者只描述纹理，后者已经混入水深，不能再作为纯泡沫断裂信号。

## 5. 小功能四：把 Noise 高度变成会影响高光的动态 Normal

### 5.1 Height 与 Normal 的区别

Noise 输出一个标量 `H(u,v)`，可以理解为一张虚拟 Height Field。光照需要的却是三维单位法线 `N`。法线描述表面朝向，不描述绝对高度。

最直观的高度场法线近似可以写成：

```text
N ≈ normalize((-∂H/∂u × Strength,
               -∂H/∂v × Strength,
                1))
```

若沿 U 方向高度不断升高，表面就向另一侧倾斜。`Strength=0` 时得到平坦 Tangent Normal `(0,0,1)`。

当前实现为了适应透视、Mesh 尺寸和世界位置，沿用了 Shader Graph `Normal From Height` 的更完整形式：利用 `ddx/ddy` 获得相邻 Fragment 的 World Position 和 Height 变化，构造世界空间 Surface Gradient，再转回 Tangent Space。

`ddx(x)` 与 `ddy(x)` 是 Fragment Derivative，近似 GPU 同一像素 Quad 内水平方向、垂直方向的数值差。它们只能在 Fragment Stage 中使用。Derivative 对分支不连续和极小三角形可能敏感，因此 Normal Strength 不能无限增大。

### 5.2 TBN 与 Coordinate Space

每个 Mesh 表面建立局部基底：

```text
T：Tangent，沿 UV 的 U 方向
B：Bitangent，沿 UV 的 V 方向
N：几何 Normal，垂直表面
```

形成矩阵：

```text
TBN = [T B N]
Nworld = normalize(TBN × Ntangent)
```

同一张 Tangent Space 波纹可以正确贴在任意旋转的水面上。`tangentOS.w` 和 `GetOddNegativeScale()` 保存 Handedness；镜像 UV 或负缩放会改变 Bitangent 朝向，若忽略符号，部分模型的法线会翻转。

Coordinate Space 是水 Shader 最容易被面试追问的地方：Object Space 随模型变化；World Space 是全场景统一坐标；View/Eye Space 以 Camera 为原点；Clip Space 用于裁剪和透视除法；Screen Space 用于采样深度；Tangent Space 是每个表面的局部 TBN 基。两个向量只有在同一空间下点积，结果才表示真实夹角。

### 5.3 Normal Blend 为什么不能直接相加

平坦 Tangent Normal 是 `(0,0,1)`。若直接 A+B，两个法线的 Z 基准会变成约 2，再 Normalize 后 XY 相对变小，结果反而趋于平坦。当前使用 Shader Graph Default Normal Blend 近似：

```text
Nblend = normalize((Ax+Bx, Ay+By, Az×Bz))
```

它把 XY 当作斜率累加，同时避免 Z 基准被重复相加。更高级的 Reoriented Normal Mapping（RNM）在大角度时更准确，但当前波纹强度较低，Default Blend 足够且更易解释。

### 5.4 Normal 为什么能让平面看起来起伏

最简单的 Lambert Diffuse 含有：

```text
Diffuse = Albedo × LightColor × max(dot(N,L),0)
```

其中 `L` 是指向灯光的单位方向，单位向量点积：

```text
dot(N,L)=cosθ
```

改变 N 就会改变每个 Fragment 的受光强度。PBR 高光还会依赖 N、V、L 和 Half Vector，因此移动 Normal 会产生流动高光。Mesh 轮廓没有变化，所以从侧面看仍是平面；这是 Bump Mapping，不是 Geometry Displacement。

实验中 `Wave Normal Strength=0.864` 能非常明显地证明链路，但正式值降到约 `0.15~0.35`。过强会让水像褶皱金属，这是调试极值与生产参数必须分开的典型例子。

## 6. 小功能五：从 Camera Depth 估算“这条视线穿过了多厚的水”

### 6.1 Depth Buffer 保存的不是普通世界距离

Camera 绘制不透明场景时会把最近表面的 Depth 写入 Depth Buffer。为了透视投影和精度分配，Raw Depth 通常是非线性的：近处获得更多精度，远处更稀疏；URP 还可能使用 Reversed-Z。不能直接拿 Raw Depth 与世界单位相减。

当前通过：

```hlsl
SampleSceneDepth(screenUV)
LinearEyeDepth(rawDepth,_ZBufferParams)
```

恢复 Eye Depth。Orthographic Camera 的深度关系不同，所以代码使用 `unity_OrthoParams.w` 选择 `LinearDepthToEyeDepth`。这不是为了当前一定使用正交相机，而是避免 Shader 对 Camera 类型做隐藏假设。

### 6.2 水体厚度公式

```text
WaterThickness
= max(SceneEyeDepth - WaterSurfaceEyeDepth, 0)
```

- `SceneEyeDepth`：水面后方最近不透明地面到 Camera 的 Eye Depth；
- `WaterSurfaceEyeDepth`：当前水面 Fragment 到 Camera 的 Eye Depth；
- 差值：沿 Camera 视线穿过水层的距离。

它不是竖直水深。Camera 越倾斜，同一竖直深度对应的视线距离可能越长，所以颜色和泡沫宽度会随视角略变。这是低成本 Screen Space Water 常见 trade-off。

### 6.3 从任意距离变成 0~1 Mask

```text
Depth01 = Saturate(
    max(WaterThickness,0) / DepthFadeDistance
)
```

`DepthFadeDistance` 定义经过多长视线距离后视为“完全深水”。除法将距离归一化；`Saturate` 截断到 `[0,1]`。

为了避免深浅边界像规则色带，加入中心化 Noise：

```text
CenteredNoise = CombinedNoise - 0.5
DepthMask = Saturate(
    Depth01 + CenteredNoise × DepthNoiseStrength
)
```

减 0.5 将 Noise 从约 `[0,1]` 移到 `[-0.5,0.5]`，因此它既能让局部稍深，也能让局部稍浅；不减时只能单向推深。

### 6.4 Scene Depth 的前置条件

PC RP Asset 必须开启 Depth Texture；水下地面必须是不透明且写入 Depth 的物体；水自身在透明阶段绘制，不能指望当前水面已经存在于它采样的 Camera Depth Texture 中。Shader Graph 节点 Preview 中 Scene Depth 相关节点显示纯白并不能证明接线错误，因为 Preview 没有真实场景深度，必须在 Scene/Game View 判断。

## 7. 小功能六：用 Depth Mask 同时驱动颜色与透明度

### 7.1 深浅颜色

```text
DepthColor = Lerp(ShallowColor,DeepColor,DepthMask)
```

`DepthMask=0` 时显示浅青；达到深水距离后显示深蓝。颜色只是风格化近似。更物理的吸收会让不同波长随距离指数衰减，而不是简单 RGB Lerp；P2 选择 Lerp 是因为参数直观、Gameplay 可读、容易 Debug。

### 7.2 深浅 Alpha

```text
DepthAlpha = Lerp(ShallowAlpha,DeepAlpha,DepthMask)
```

浅水更容易看到水底，深水水面自身颜色权重更高。颜色与 Alpha 使用同一个 Mask，保证视觉语义一致，但参数分开：深蓝不必自动等同于完全不透明。

`WaterAlpha` 作为末端全局倍率，而不是替代 Shallow/Deep Alpha：

```text
FinalAlpha = LocalAlpha × WaterAlpha
```

这样既保留深浅差异，又能整体淡入淡出。Material Property 中的 `Range(0,1)` 主要约束 Inspector Slider；C# 仍可能通过底层 API 写入越界值，所以 Shader 末端仍使用 `saturate` 保护。

## 8. 小功能七：Fresnel 为什么让斜视水面反光更强

### 8.1 从单位向量点积开始

定义：

```text
N：当前动态表面法线
V：Fragment 指向 Camera 的方向
```

Normalize 后：

```text
dot(N,V)=|N||V|cosθ=cosθ
```

- 正视水面：`θ≈0°`，`N·V≈1`；
- 掠射角：`θ≈90°`，`N·V≈0`。

所以：

```text
Fbase = Saturate(1-dot(N,V))
F = pow(Fbase,FresnelPower)
```

会得到正面接近 0、斜视边缘接近 1 的 Mask。

Power 改变宽度而不是简单亮度。例如 `0.5`：

```text
0.5¹=0.5
0.5²=0.25
0.5⁴=0.0625
0.5⁸≈0.0039
```

Power 越大，中间值越快被压低，只保留更接近掠射角的区域。

### 8.2 为什么 N 和 V 使用 Tangent Space

动态 Normal 最先以 Tangent Space 表示。可以把 N 转到 World，再与 World V 点积，也可以把 V 转到 Tangent 后计算；两种做法只要空间一致就成立。当前把 `ViewDirectionWS` 通过 TBN 逆变换到 Tangent Space，与 `normalTS` 计算 Fresnel，避免再引入一组不同定义的法线。

### 8.3 与物理 Fresnel 的差距

常见 Schlick Approximation：

```text
F(θ)=F0+(1-F0)(1-cosθ)⁵
```

空气到水的折射率约为 1 与 1.33，正视反射率近似：

```text
F0=((n1-n2)/(n1+n2))²≈0.02
```

当前 `pow(1-N·V,Power)` 没有显式 F0，也没有严格做反射/透射能量守恒；随后还用 Fresnel Mask Lerp 到青白颜色，并增加 Alpha。因此它是风格化 Fresnel，用于清晰表达水面，不是完整物理介质模型。另一方面，`UniversalFragmentPBR` 本身也会计算 Dielectric Specular，高 Smoothness 会产生真实 Lit 高光；当前额外 Fresnel Color 是艺术增强。面试时应该主动区分二者，不能说成“实现了完整水的物理 Fresnel”。

## 9. 小功能八：利用同一深度差生成岸边泡沫

### 9.1 接触线 Mask

当地面深度接近水面深度时：

```text
WaterThickness≈0
```

所以构造：

```text
ContactMask
= 1-Saturate(WaterThickness/FoamDistance)
```

- 接触处约为 1；
- 达到 FoamDistance 时为 0；
- FoamDistance 越大，泡沫带越宽。

如果直接用 ContactMask，结果是一条连续、规则的亮边，更像描边而不是泡沫。

### 9.2 用 Smoothstep 把移动 Noise 变成断裂纹理

```text
FoamNoise = Smoothstep(0.35,0.70,CombinedNoise)
```

`Smoothstep(edge0,edge1,x)` 在低于 edge0 时输出 0，高于 edge1 时输出 1，中间使用平滑曲线过渡。相比 `Step` 的硬切换，它保留抗锯齿友好的柔边。

最终：

```text
FoamMask = Saturate(
    ContactMask × FoamNoise × FoamStrength
)
```

泡沫 Mask 最后同时控制颜色和 Alpha：

```text
FinalAlbedo = Lerp(FresnelColor,FoamColor,FoamMask)
FoamAlpha   = FoamMask × FoamAlphaBoost
```

泡沫放在颜色链最后，保证不会再被深水色或 Fresnel 色覆盖。它只是 Surface Mask，没有粒子飞溅、流体汇聚和真实泡沫寿命。

## 10. 小功能九：把自研表面数据接回 URP PBR Lighting

当前 Shader 没有从零重写完整 BRDF，而是准备 `SurfaceData` 和 `InputData` 后调用：

```hlsl
UniversalFragmentPBR(inputData,surfaceData)
```

### SurfaceData：材质是什么

```text
albedo        = FinalAlbedo
metallic      = 0
smoothness    = _Smoothness
normalTS      = Dynamic Normal
occlusion     = 1
emission      = 0
alpha         = FinalAlpha
```

水是 Dielectric（非金属），所以 Metallic=0。Smoothness 高意味着 Microfacet Normal 分布更集中，高光更窄、更清晰；它不等于直接提高亮度。Emission=0，因为普通水不是能量源，不应在黑暗中自发光。

### InputData：像素处于什么环境

```text
positionWS / positionCS
dynamicNormalWS
viewDirectionWS
shadowCoord
vertexLighting
bakedGI
fogFactor
normalizedScreenSpaceUV
```

URP 使用这些数据计算主光、附加光、阴影、GI 和镜面 BRDF。最终 `MixFog` 处理雾，再由 Pass 的 Alpha Blend 与背景混合。

使用 URP Lighting 不是“没有手写 Shader”。自研职责是水的表面信号与 Render State；成熟通用 PBR、阴影和灯光循环由 Render Pipeline 复用。这种边界能避免复制 URP 内部大量平台与光照代码，也更符合工程实践。

|---|---|---|---|
| `_ShallowColor` | Depth Color Lerp A | 浅水区域趋向该颜色 | Color.a 当前不控制透明度 |

## 13. 实现过程中的真实踩坑与 Debug

### 13.1 `Range 0~1` 不是一种单独 Property 类型

Shader Graph Blackboard 里先创建 `Float`，再把 Mode 改为 Slider 并设置 Min/Max。`Range` 是 Inspector 交互约束，不是新的底层数值类型。手写 Shader 对应 `Range(0,1)` Property，HLSL 中仍然是标量。

### 13.2 当前 Shader Graph 版本没有 Panner

没有继续寻找同名节点，而是回到公式：

```text
Offset=Time×Speed
MovingUV=UV+Offset
```

使用 `Multiply + Tiling And Offset` 完成验证，手写 HLSL 最终直接表达公式。这个问题说明掌握数学比记节点名称可靠。

### 13.3 “合并 Noise”接错到最终 Saturate

泡沫 `Smoothstep` 需要纯 `(NoiseA+NoiseB)×0.5`。若接到 `Depth01+Noise` 后的最终 Saturate，信号已经包含场景深度；深水区长期接近 1，泡沫断裂不再由纯流动纹理控制。Debug 方法是给关键中间量明确命名，并把每个 Mask 临时输出为灰度 Base Color。

### 13.4 把波纹与 Fresnel 放进一个 Custom Function 形成环

最初考虑一个函数同时输出 Wave Noise、Depth 和 Fresnel，但 Fresnel 需要动态 Normal，动态 Normal 又需要先消费 Wave Noise：

```text
Function Wave Output -> Normal From Height -> Function Fresnel Input
```

同一个 Shader Graph 节点无法让输出再回到自己的输入，这是有向图 Cycle。解决方案是拆为 `ElementWaterWaves` 与 `ElementWaterSurface` 两个入口，保持：

```text
Wave -> Normal -> Surface
```

后来正式改为手写完整 Shader，这个数据依赖仍保留在 Fragment 的执行顺序中。

### 13.5 Scene Depth 节点 Preview 全白

Preview 没有真实 Camera Depth Texture，不能用节点小窗口判断深度链。应在真实 Scene 中放置不同高度的水下地面，并把 Shallow/Deep 临时设为高对比色验证。Depth Texture 未启用、地面是 Transparent 或水面绘制顺序不对，都会使深度失效。

### 13.6 Normal Strength 调试值污染正式质感

强度 0.864 能证明动态法线存在，却让正式水面像液态金属。正确流程是：先用极值证明数据链，再恢复 0.15~0.35 做美术判断。所有 Slider 都应区分“诊断值”和“生产值”。

### 13.7 修改注释时误删一行执行代码

本次扩充注释时，替换 PBR 末尾注释块意外覆盖了：

```hlsl
half4 color = UniversalFragmentPBR(inputData,surfaceData);
```

后续 `color.rgb` 因而引用未声明变量。问题在提交 Unity 前被尾部静态复核发现。根因不是 Shader 数学，而是补丁范围包含了代码行。修复只恢复这一行，并再次触发 Unity Import。经验是：注释修改也必须查看局部 Diff/上下文，不能因为“不改逻辑”就跳过编译验证。

### 13.8 透明水的常见错误不能只靠调颜色解决

| 症状 | 优先检查 |
|---|---|
| 整块粉色 | Shader Compile Error、Include 路径、URP Pipeline Tag |
| 水完全不见 | Material Shader、MeshRenderer、WaterAlpha、Alpha Blend、Camera Culling Mask |
| 水完全实心 | Shallow/Deep Alpha、Blend、材质是否用了错误 Shader |
| 深浅完全一致 | PC Depth Texture、地面是否 Opaque、DepthFadeDistance、DepthMask 输出 |
| 泡沫铺满水面 | 是否误用最终 Depth Saturate、FoamDistance/Threshold 是否过大 |
| 泡沫完全没有 | WaterThickness 是否始终大、FoamStrength/AlphaBoost、接触几何关系 |
| 波纹不移动 | `_Time.y`、WaveSpeed.xy、是否正在 Pause、Noise 坐标是否使用 MovingUV |
| 高光方向怪异 | TBN、tangent.w、负缩放、Normal 是否 Normalize、空间是否一致 |
| 斜视没有变化 | Fresnel N/V 空间、Power、FresnelColor 是否与 DepthColor 太接近 |
| 水后透明粒子消失/乱序 | ZWrite、Transparent Queue、Renderer Sorting、透明交叠 |
| GPU 时间上升 | 大面积透明 Overdraw、Fragment Noise/Derivative、附加灯和阴影 Variant |

## 14. 一套可重复的 Debug 顺序

不要同时猜颜色、Alpha、Depth 和 Lighting。按从管线外层到中间 Mask 的顺序缩小范围：

```text
1. Console：Shader 是否编译，是否粉色
2. Frame Debugger：是否进入 WaterForward、Draw 顺序是否在 Opaque 后
3. Render State：Queue/Blend/ZWrite/ZTest/Cull
4. Mesh 数据：UV、Normal、Tangent、Scale 是否合理
5. CombinedNoise：临时输出灰度，确认移动/频率
6. Normal：Strength=0 与 0.3 A/B，移动 Camera/Light
7. WaterThickness：临时输出灰度，改变水下地面高度
8. DepthMask：Shallow=绿、Deep=蓝，DepthNoiseStrength=0
9. FresnelMask：临时输出黑白，只移动 Camera
10. FoamMask：FoamColor=纯白，Strength=1，逐步恢复参数
11. Alpha：Shallow=0.05、Deep=0.95 做极值验证
12. URP Lighting：Smoothness=0/1、检查 Directional Light/GI/Shadow
13. Profiler/Overdraw：恢复正式参数后再评估性能
```

临时输出 Mask 时应让 Alpha=1，避免 Mask 颜色又被背景混合稀释。例如：

```hlsl
return half4(depthMask.xxx,1);
```

这类 Debug 输出只能短时使用，验证后恢复。一次只观察一个变量，才能知道是哪条链路生效。

Frame Debugger 用于回答“画了什么 Pass、顺序和 Render Target 是什么”；Rendering Debugger 用于检查 Pipeline Feature 与材质/光照调试视图；GPU Profiler 用于量化时间；Overdraw 视图用于观察同一屏幕区域被透明层重复绘制多少次。工具职责不同，不能用 Frame Debugger 的 Draw Call 数直接代替 GPU 性能结论。

## 15. 性能与方案取舍

### 当前成本来自哪里

- 每 Fragment 两次程序化 Value Noise：每层查询四个 Hash 并插值；
- 两次 Height-to-Normal：使用 `ddx/ddy` 与向量运算；
- 一次 Camera Depth Texture Sample；
- `pow` Fresnel；
- URP PBR 主光、附加光、阴影、GI；
- Transparent Overdraw：同一像素可能重复执行整个 Fragment。

当前没有外部 Noise/Normal/Foam Texture Sample，节省资源依赖和 Texture Bandwidth，但不代表“程序化一定更快”。Noise 从纹理采样成本换成了 ALU；性能优劣必须在目标 GPU、分辨率和屏幕覆盖率下测量。

### 为什么不做 Vertex Displacement

当前目标是局部元素区域中的细水面，动态 Normal 已能表达微小波纹。Vertex Displacement 需要足够密 Mesh，否则只会移动少数顶点形成大折面；增加 Tessellation/网格密度会提高 Vertex 成本和几何复杂度。P2 先保留平面轮廓，避免把视觉实验扩展成海洋系统。

### 为什么不加入 Refraction

Refraction 需要采样 Camera Opaque Texture，并用 Normal 扰动 Screen UV。它能增强水下扭曲，但会增加一次屏幕纹理采样、产生屏幕边缘/遮挡伪影，并让第一版教学代码更复杂。方案 A 明确先完成当前效果，Refraction 作为后续独立增量，而不是偷偷写进“已完成”清单。

### 为什么用手写 Shader 而不是继续堆 Shader Graph

Shader Graph 适合原型、可视化数据流和美术调参；复杂后节点与跨屏幕连线会降低可读性。手写 HLSL 能直接展示公式、Render State、Coordinate Space 和 URP API，也更容易进行代码审查与面试讲解。代价是需要自己管理 Pass、Keyword、精度、Include 与平台兼容，修改也不如节点对美术友好。

当前路线是：Shader Graph 负责早期视觉验证，正式版本用 ShaderLab+HLSL。两者不是谁“更高级”，而是服务不同阶段。

## 16. 面试常见追问与回答要点

### Q：这是不是一个真实流体模拟

不是。它是 Screen Space Depth 与程序化表面着色的风格化水 Shader。没有 Navier-Stokes、速度场、压力场、质量守恒和 Cell 流动；Gameplay 水区域仍由 `StatusVolume` 表示。P6 才可能把 Cell Material 数据映射到同一元素反应内核。

### Q：为什么 Value Noise 是连续的

随机值只存在整数格点，格内使用平滑后的 Bilinear Interpolation。Hermite 曲线 `f²(3-2f)` 在 0/1 两端导数为零，降低格子边界斜率突变。

### Q：为什么 Normal From Height 不改变轮廓

它只在 Fragment Shader 修改参与光照的 Normal，没有修改 Vertex Shader 的 Position。它属于 Bump Mapping；侧面轮廓和真实阴影几何仍是原 Plane。

### Q：Tangent Space 的意义是什么

它给每个表面建立 TBN 局部坐标，使同一套局部波纹能复用于不同旋转的三角形。平坦法线固定为 `(0,0,1)`，最后通过 TBN 变换到 World Space 参与光照。

### Q：为什么 Scene Depth 要线性化

Perspective Depth 经过投影后不是线性世界距离，近处精度更高。直接相减无法代表水层厚度，所以必须用 `_ZBufferParams` 和 URP 函数恢复 Eye Depth；Orthographic 还要走不同转换。

### Q：Depth Thickness 有什么局限

它是沿 Camera 视线的 Screen Space 差值，不是竖直水深；受 Camera 角度和不透明场景可见性影响，也无法读取尚未写入 Depth 的透明物体。

### Q：解释 Fresnel 公式

单位 N、V 点积为夹角余弦。正视 `N·V≈1`，掠射角 `≈0`，因此 `pow(1-saturate(N·V),Power)` 得到边缘 Mask。当前是风格化近似；物理 Schlick 还包含 F0 和固定五次幂结构。

### Q：为什么水的 Metallic 是 0

水是 Dielectric，不是金属。它仍有 Dielectric Specular，URP PBR 会使用基础反射率；Smoothness 控制镜面反射分布。把水设成 Metallic=1 会让 Base Color 进入金属反射语义，产生错误材质。

### Q：为什么泡沫不做 Particle System

当前泡沫是静态水面与地面接触线，Depth Mask 能以单个 Surface Pass 低成本生成；飞溅、浪花和体积泡沫才适合粒子。两者可以未来叠加，不必用一种技术解决所有泡沫。

### Q：怎样证明性能不是凭感觉

在目标场景用 GPU Profiler 比较水关闭/开启，固定 Camera 和灯光；用 Overdraw 看屏幕覆盖；用 Frame Debugger确认 Pass 和 Draw 顺序；逐步关闭 Additional Lights、Shadows、第二层 Noise 定位主要成本。重点关注 Fragment GPU 时间，而不是 C# GC，因为 Shader 不在 CPU Managed Heap 分配。

### Q：手写 Shader 最大的工程风险是什么

需要自己维护 URP API、Keyword、Pass、精度与 Render State；URP 升级可能改变 Include 或数据结构。应限制自定义范围、复用 `UniversalFragmentPBR`、保留 Unity Import/Frame Debugger 验证，并通过清晰函数边界隔离水面数学。

## 17. 模拟面试者：从头到尾完整讲解开发思路

我在项目 P2 中需要做一个能承载 Wet 环境的自研水面，但目标不是实现海洋或真实流体，而是在 3D RPG 的局部可交互区域里，用可控成本提供水的关键视觉线索。Gameplay 与 Rendering 是分离的：`StatusVolume` 在 `Game.Combat` 中通过 `OverlapBoxNonAlloc` 周期性给角色施加 Wet；Water Shader 只负责绘制。最终由 `EV_WaterPool` Prefab 组合 BoxCollider、StatusVolume 和 Water Visual，因此替换 Shader 不会改变元素反应规则。

开发时我没有直接堆一个复杂 Shader，而是从结果反向拆成透明基线、流动纹理、微表面法线、深浅水、Fresnel、泡沫和 URP Lighting。先用 Shader Graph 验证每段 Mask，再迁移为 `ShaderLab + HLSL`，因为复杂 Graph 的连线开始降低可读性，而手写代码能明确表达公式、Render State 和 Coordinate Space。正式 Shader 使用 Transparent Queue、`Blend SrcAlpha OneMinusSrcAlpha`、`ZWrite Off`、`ZTest LEqual` 和 `Cull Back`。我知道 ZWrite Off 能避免透明面过早遮挡后续透明物，但也会带来排序与 Overdraw 问题，所以把它作为透明方案的明确 trade-off，而不是默认模板。

水面流动从 UV Panning 开始，公式是 `UV'=UV+Speed×Time`。我没有使用外部 Noise 贴图，而是手写二维 Value Noise：先对整数格点做稳定 Hash，再取得四个角点随机值，通过 `f²(3-2f)` 平滑局部坐标，做两次 Lerp 得到 Bilinear Interpolation。为了降低单层纹理整齐平移的人工感，我使用两组不同 Scale 和 Speed 的 Noise，并取平均。Scale 控制 UV 空间频率，Speed 是 UV/秒；这也意味着世界空间波纹大小会受 Mesh UV 影响，是当前方案的限制。

Noise 首先作为 Height Field。为了让水面产生动态高光，我使用 Fragment Derivative `ddx/ddy` 估算相邻 Fragment 的世界位置和高度变化，构造 Surface Gradient，得到 Tangent Space Normal。Tangent、Bitangent、Normal 构成 TBN 基底，Tangent Normal 通过 TBN 变换到 World Space，再交给 URP 光照。两层 Normal 不能直接相加，因为平坦法线都含有 Z=1 的基准；我采用 Default Normal Blend，将 XY 斜率相加、Z 相乘并 Normalize。这个效果只改变光照，不修改 Vertex Position，所以属于 Bump Mapping，外轮廓仍然是 Plane。

深浅水使用 Camera Depth Texture。Fragment 先通过 Screen UV 采样水面后方最近的不透明表面 Raw Depth，再根据 Perspective 或 Orthographic Camera 线性化为 Eye Depth；水面自身 Eye Depth 由 World Position 变换得到。两者相减得到沿视线方向的 `waterThickness`，再除以 `DepthFadeDistance` 并 Saturate 成 `Depth01`。我用中心化后的 Combined Noise 对深浅边界做双向扰动，最终用 DepthMask 同时 Lerp Shallow/Deep Color 和 Shallow/Deep Alpha。这里的厚度沿视线而非竖直方向，透明度也是艺术 Lerp 而非 Beer-Lambert 吸收，我会在面试中明确说明物理近似边界。

Fresnel 使用动态 Tangent Normal 与同空间 View Direction。Normalize 后 `N·V=cosθ`，正视接近 1、掠射角接近 0，所以使用 `pow(1-saturate(N·V),FresnelPower)` 得到边缘 Mask。Power 越大，边缘越窄。这个 Mask 用于向 Fresnel Color 过渡并增加少量 Alpha。它不是完整 Schlick Fresnel，因为没有显式 F0 与能量守恒；URP PBR 本身还会基于 Dielectric 和 Smoothness 计算镜面反射，我额外的 Fresnel Color 是为了 RPG 视角下的视觉可读性。

岸边泡沫复用同一个水层厚度，使用 `1-saturate(thickness/FoamDistance)` 得到接触线，再用 `smoothstep` 处理移动 Combined Noise，打碎规则边缘。FoamMask 最后覆盖颜色并增加 Alpha，所以不会被深水色或 Fresnel 二次覆盖。这是 Surface 接触线，不是飞溅粒子；后续如果需要浪花，会单独使用 Particle/VFX，而不是让一个 Shader 承担所有水现象。

最后我把 Final Albedo、Dynamic Normal、Smoothness、Alpha 等写入 `SurfaceData`，把 World Position、View Direction、Shadow Coordinate、GI 和 Fog 写入 `InputData`，调用 URP 的 `UniversalFragmentPBR`。这样自研部分专注水面信号，主光、附加光、阴影、GI 和 BRDF 复用管线能力。水设置 Metallic=0、Emission=0、高 Smoothness，符合非金属透明介质的基本材质方向；透明混合仍是风格化近似。

Debug 时我按管线顺序定位：先看 Console 与 Frame Debugger 是否进入 `WaterForward`，再查 Queue/Blend/ZWrite；然后把 CombinedNoise、DepthMask、FresnelMask、FoamMask 分别临时输出灰度，并使用极端参数验证端点；Normal 用 Strength=0/0.3 对比，Fresnel 只移动 Camera，Depth 用不同高度的不透明地面验证。性能上重点看大面积透明 Overdraw、两层程序化 Noise、Derivative、Depth Sample、PBR Additional Lights 和 Shadow Variant。我不会把“没有外部贴图”等同于更快，而会在目标分辨率和 GPU 上用 Profiler量化。

这项实现对我的价值不只是做出一池水，而是完整走通了从视觉目标、问题拆解、Shader Graph 原型、数学公式、Coordinate Space、手写 ShaderLab/HLSL、URP Pipeline 接入到 Frame Debugger/Profiler 验证的流程。同时我能明确说明当前没有实现真实流体、折射和几何波浪，并给出下一步可以按需求增加 Opaque Texture Refraction、Beer-Lambert Absorption、World Space Noise 或 Vertex Displacement，而不是把未来方向包装成现有成果。
