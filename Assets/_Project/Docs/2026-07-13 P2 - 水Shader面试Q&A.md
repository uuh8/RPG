面试官通常不会因为候选人背出了一个名词就判断他真正理解。例如，回答“Fresnel 就是边缘光”只描述了现象，没有解释向量关系、公式来源、当前实现和物理边界；回答“透明物体要关掉 ZWrite”也只是记住了模板，没有说明 Depth Test、排序和 Overdraw 的后果。

这份题库按照真实面试的方式组织：面试者先直接回答问题，再根据问题类型选择最合适的展开方式。数学题会从定义和公式推导，Rendering Pipeline 题会沿数据流说明，工程题会讲验证工具和 trade-off，质疑题会诚实说明当前实现没有完成什么。回答中反复出现的核心能力包括：

- 能把玩家看到的效果还原成 GPU 数据流；

# 第一组：项目介绍与需求拆解

## Q1 ⭐：请你先介绍一下这个水 Shader。你具体实现了什么？

**面试官：** 你简历上写了自研水 Shader。先用两三分钟介绍一下，不要一上来逐行念代码。

**面试者：**

我实现的是一个运行在 Unity 6.3、URP 17.3 下的手写透明水面 Shader。它的目标不是求解真实流体，而是在普通水面 Mesh 上，通过程序化信号构造足够可信、并且能服务 RPG Gameplay 可读性的水面视觉。

从最终画面看，它包含六个主要线索。第一，水面透明并且浅水比深水更容易看见水底；第二，两层不同方向移动的 `Value Noise` 让表面持续流动；第三，我把 Noise 高度转换成动态 `Tangent Space Normal`，让平面在光照下产生移动高光；第四，通过采样 `Camera Depth Texture`，估算当前水面 Fragment 到后方不透明表面的视线方向厚度，从而得到深浅颜色和透明度；第五，用动态 Normal 与 View Direction 的点积构造风格化 `Fresnel`，让掠射角区域更亮、更不透明；第六，用同一份水体厚度叠加移动 Noise，生成岸边接触泡沫。最后我把 Albedo、Normal、Smoothness、Alpha 等写入 URP 的 `SurfaceData`，把 World Position、View Direction、Shadow、GI、Fog 等写入 `InputData`，调用 `UniversalFragmentPBR` 复用 URP 的 Lit Lighting。

工程上我先用 Shader Graph 做视觉原型，验证每条 Mask 是否成立；随着连线变复杂，我把实现迁移为 `ShaderLab + HLSL`。`ElementWater.shader` 负责 Pass、Render State、URP 接入和最终颜色合成，`ElementWaterCore.hlsl` 负责 Hash、Value Noise、Height-to-Normal、Normal Blend、Depth Mask 与 Fresnel 这些可独立理解的数学函数。这样既保留了 Shader Graph 快速原型的优势，也让正式实现中的公式、Coordinate Space 和性能成本更容易审查。

我会明确说明当前边界：它没有模拟速度场、压力、质量守恒，没有 `Vertex Displacement`，也没有实现 Refraction 或严格的 Beer-Lambert Absorption。因此它是程序化风格水面，不是真实流体模拟。

**面试官追问：** 这项工作中最能体现你个人能力的部分是什么？

**面试者：**

我认为不是“做出蓝色透明水”本身，而是完整走通了从视觉目标到数学信号再到 URP Pipeline 的过程。我能解释每一个画面线索由什么输入产生、处于什么 Coordinate Space、如何验证中间 Mask，以及为什么选择这种近似。比如岸边白色不是一张 Prefab 贴图，而是由 `waterThickness` 构造接触 Mask，再用移动 Noise 打碎；波纹也不是直接下载 Normal Map，而是手写 Value Noise 后用 Fragment Derivative 转为 Normal。与此同时，我能主动说明它的物理不准确处和性能瓶颈，而不是只展示最终截图。

**学习复盘：**

- 面试官考察的是候选人能否先建立全局模型，再进入细节。
- 开场应包含“效果、核心技术、工程组织、边界”四部分，但不必机械报标题。
- 不要说“我实现了真实水体”或“物理水”，当前代码并不支持这个结论。

## Q2 ⭐：你是怎么把“做一池水”拆成可实现问题的？

**面试官：** 水是一个很模糊的需求。你开始开发时如何拆解，而不是直接堆节点？

**面试者：**

我采用从最终画面反向追问的方式。先不考虑代码，而是问“为什么玩家会把这块 Plane 识别成水”。我得到的主要视觉证据是透明、深浅变化、连续运动、会变化的高光、掠射角反射和岸边接触线。然后把每个证据改写成一个有输入和输出的小问题。

例如，“水在流动”可以改写为：怎样让一个静态 Mesh 的采样坐标随时间连续变化？输出是移动 UV；“水面有细小起伏”可以改写为：怎样从标量高度场得到用于 Lighting 的单位 Normal？输出是 `normalTS`；“深处更蓝”可以改写为：怎样从 Screen Position 和 Camera Depth 得到一个 0 到 1 的厚度 Mask？输出是 `depthMask`；“斜看更亮”可以改写为：怎样根据 Surface Normal 和 View Direction 的夹角得到连续 Mask？输出是 `fresnelMask`。

再往下拆，每个 Mask 都可以单独灰度输出并验证。我的开发顺序是先建立透明 Lit 基线，再做单层 UV Panning 和 Noise，接着做双层 Noise、Height-to-Normal、Scene Depth、Fresnel、泡沫，最后组合颜色与 Alpha。这个顺序很重要，因为后面的效果依赖前面的中间量：泡沫依赖 Depth 与 Noise，Fresnel 依赖动态 Normal。如果一开始就把所有公式写到一个函数里，出现画面异常时无法知道是输入、空间还是混合顺序错了。

**面试官追问：** 为什么你偏爱 0 到 1 的 Mask？

**面试者：**

因为 Mask 可以把复杂连续现象统一为权重。`0` 表示完全选择 A，`1` 表示完全选择 B，中间值表示平滑混合。以颜色为例：

```text
Lerp(A,B,t) = A × (1-t) + B × t
```

只要 Depth、Fresnel、Foam 都输出稳定的 0 到 1，后续就能用相同的 `lerp` 思维组合颜色、Alpha 或其他材质参数。Mask 还方便 Debug：临时把它作为灰度 Base Color 输出，就能直观看到数据分布。相比大量二值 `if`，连续 Mask 通常也能避免硬边和分支发散，更适合风格化材质调参。

**学习复盘：**

- 重点不是背开发步骤，而是把视觉语言转换成可测试的数据问题。
- 面试中说出“每条链路可单独灰度验证”，会体现 Debug 意识。
- `Mask` 是 Shader 设计的通用语言，不只适用于水。

## Q3：你为什么说它不是真实流体？如果面试官说它只是“假水”，你怎么回答？

**面试官：** 你的水没有流体模拟，那不就是一层假效果吗？技术含量在哪里？

**面试者：**

它确实是视觉近似，我不会回避“假”这个事实，但实时渲染的核心本来就是在预算内选择对玩家最有效的近似。真实流体通常至少涉及速度场、压力场、对流、不可压缩约束、边界条件等问题，例如基于 Navier-Stokes Equation 做网格或粒子求解；水面几何还可能需要 Height Field、FFT Ocean、Shallow Water Equation、SPH 或其他模拟。当前 Shader 没有保存上一帧状态，也没有求解这些方程，所以不能称为流体模拟。

它解决的是另一个工程问题：在第三人称 RPG 的常见观察距离下，用有限的 Fragment 运算提供水的识别线索，并且保持参数可调、可与 Gameplay Volume 分离。程序化 Noise 负责运动和微表面，Camera Depth 负责与场景几何关系，Fresnel 负责观察角关系，URP PBR 负责灯光响应。这些部分仍然要求理解 Rendering Pipeline、3D 数学、Coordinate Space、深度线性化、透明排序和 GPU 性能。

如果需求升级到“水会被角色推动并形成涟漪”，我不会声称调 Noise 参数就能解决，而会引入独立的 Simulation/Interaction Layer，例如低分辨率 RenderTexture 保存扰动场，由角色写入冲击，再让 Shader 采样；如果要大海远景，可能考虑 Gerstner Waves 或 FFT；如果是小体积高交互液体，才评估更昂贵的粒子或网格模拟。技术选择应由玩法尺度和平台预算决定。

**面试官追问：** 为什么当前没有做 Vertex Displacement？

**面试者：**

当前 Plane 顶点密度有限，而 Vertex Shader 只能在顶点上计算位移；如果 Mesh 不细分，波形会非常粗。如果提升细分度，又会增加 Vertex 数量，并带来阴影、碰撞、边界接缝等问题。当前水主要以俯视角观看，小尺度起伏用 Normal Mapping 已能提供高光变化，因此第一版选择不改变轮廓。若未来近距离观察水面或需要明显波峰，我会先明确波长和最大振幅，再提高可控范围内的网格密度，使用 Gerstner Wave 等解析函数做 Vertex Displacement，并同时处理 Depth、ShadowCaster 与岸边穿插问题。

**学习复盘：**

- 面试官的质疑是在测试你能否区分 Simulation 与 Shading。
- 好回答不是辩称“看起来真就是真”，而是承认边界并说明需求升级路径。

# 第二组：Rendering Pipeline 与透明渲染

## Q4 ⭐：`Shader`、`Material`、`Mesh` 和 `Renderer` 分别是什么？它们如何协作？

**面试官：** 很基础的问题：你场景里的一池水，到底由哪些 Unity 对象共同完成？

**面试者：**

`Mesh` 保存几何数据，例如 Vertex Position、Normal、Tangent、UV 和 Triangle Index。它回答“画什么形状”。水面当前是一个 Plane，所以几何轮廓仍然是平面。

`Shader` 是 GPU 程序和 Render State 的定义。`ElementWater.shader` 声明 Properties、Transparent Queue、Blend、ZWrite、Vertex/Fragment Entry，以及如何计算每个 Fragment 的材质数据。它回答“这些几何经过什么渲染算法”。

`Material` 是某个 Shader 的参数实例。多个水池可以使用同一个 Shader，但拥有不同的 `_ShallowColor`、`_WaveScaleA`、`_FoamDistance` 等值。它回答“这一次使用什么具体参数”。Material 并不复制一份 Shader 源代码，而是保存 Shader 引用、属性值和 Keyword 状态。

`MeshRenderer` 负责把 Transform、Mesh 和 Material 提交给 Render Pipeline；严格说 Mesh 数据通常由同一对象的 `MeshFilter` 提供，Renderer 负责可见性、排序、阴影与 Draw Call 相关状态。Camera 和 URP 决定何时、以什么 Pass 绘制它。

因此数据流可以概括为：CPU 侧场景收集可见 Renderer，准备 Material 和 Transform；GPU 读取 Mesh Vertex Buffer 执行 Vertex Shader；Rasterizer 生成 Fragment；Fragment Shader 读取插值数据、Material 常量、Depth Texture 和 Lighting，输出颜色，再经过 Depth Test 与 Alpha Blend 写入 Render Target。

**面试官追问：** 修改 Material 参数和修改 Shader 有什么不同？

**面试者：**

修改普通 Material Property 主要改变常量数据，不改变 GPU 程序结构，通常不需要重新编译 Shader；修改 Shader 源码会触发 Import/Compile，可能影响所有使用它的 Material。若用 Keyword 切换功能，则可能选择不同 Shader Variant；这比普通 Float 分支更复杂，因为 Variant 数量会影响编译时间、构建体积和运行时状态切换。当前水的大多数调参都设计成普通 Property，是因为颜色、速度、强度需要连续调节，不值得为每种数值生成 Variant。

**学习复盘：**

- 这是基础题，但要能从 Unity 对象说到 GPU 数据流。
- 不要把 Material 说成“贴图”或把 Shader 说成“材质”。

## Q5 ⭐：请从一个水面顶点开始，完整讲到屏幕 Pixel 是怎么产生的。

**面试官：** 不要只说 Vertex Shader 和 Fragment Shader 两个词，沿 Graphics Pipeline 讲完整一点。

**面试者：**

CPU 首先由 Unity/URP 做场景剔除、排序和渲染批次组织，然后提交 Draw Call。GPU 从 Vertex Buffer 读取 `POSITION`、`NORMAL`、`TANGENT`、`TEXCOORD0` 等 Vertex Attribute。`WaterVertex` 执行 Object Space 到 Clip Space 的变换，核心关系可以写成：

```text
p_world = M_model × p_object
p_view  = M_view  × p_world
p_clip  = M_proj  × p_view
```

Clip Space 顶点先经过 Clipping，裁掉 View Frustum 之外的部分；再做 Perspective Divide，把 `x,y,z` 除以 `w` 得到 NDC；Viewport Transform 把 NDC 映射到屏幕坐标。随后 Primitive Assembly 根据 Index 把顶点组成 Triangle，Rasterization 判断哪些采样点被三角形覆盖，并为每个候选 Fragment 插值 UV、World Position、Normal、Tangent、Shadow Coord 等 `Varyings`。

Fragment Shader 不等于“给屏幕上的一个 Pixel 只执行一次”。它针对 Rasterization 产生的 Fragment/Sample 执行；Fragment 可能在 Early/Late Depth Test 被丢弃，也可能因为 MSAA 有多个 Sample，还可能被多个透明层重复覆盖。`WaterFragment` 计算 Noise、Normal、Depth、Fresnel、Foam 和 URP Lighting，返回 `SV_Target`。之后 Output Merger 按 Depth/Stencil 和 Blend State，把 Source Color 与当前 Framebuffer 的 Destination Color 合成。最终 Render Target 还可能经过 Post-processing、Tone Mapping 等步骤，才成为屏幕显示的 Pixel。

**面试官追问：** `Varyings` 为什么叫插值变量？所有字段都自动线性插值吗？

**面试者：**

它是 Vertex Shader 输出、Fragment Shader 输入的跨阶段数据。三角形内部的值由 Rasterizer 根据重心坐标插值。对于 Perspective Camera，普通 UV 等属性通常执行 Perspective-correct Interpolation，不是简单在屏幕二维坐标上线性插值。简化理解时可以写：

```text
P = λ0P0 + λ1P1 + λ2P2,  λ0+λ1+λ2=1
```

但透视正确插值还要考虑每个顶点的 `1/w`。另外有些语义可以声明 `nointerpolation`，整数/实例信息也有不同规则。当前水的 UV、positionWS、normalWS 等使用默认插值；Normal 到 Fragment 后仍要 Normalize，因为线性插值后的单位向量一般不再保持长度为 1。

**学习复盘：**

- 高频考点包括 Clip Space、Perspective Divide、Rasterization、Fragment 与 Pixel 的区别。
- “Normal 插值后要重新 Normalize”是很典型的追问。

## Q6：为什么 Noise 和大部分水面运算放在 Fragment Shader，而不是 Vertex Shader？

**面试官：** 把计算放 Vertex 不是更便宜吗？

**面试者：**

通常 Vertex 数量远少于 Fragment 数量，所以同一公式放在 Vertex Stage 确实可能更便宜。但能否移动取决于信号的空间频率和视觉目标。当前 Plane 顶点密度低，如果每个顶点只算一次 Noise，再让 Rasterizer 插值，三角形内部只得到低频渐变，无法保留程序化波纹、泡沫断裂和细小 Normal 的高频细节。Scene Depth 也是逐 Fragment 的屏幕空间信息，放 Vertex 后插值会产生明显误差。

因此我把 World/Clip Position、几何 Normal/Tangent、Shadow Coord、Fog 等适合逐顶点准备的数据放在 `WaterVertex`，把两层 Value Noise、`ddx/ddy`、Depth Sample、Fresnel、Foam 和最终 Lighting 放在 `WaterFragment`。这是质量优先的选择，代价是水覆盖屏幕面积较大时 Fragment 成本高，透明 Overdraw 还会让同一屏幕区域重复执行。

如果性能不足，我不会简单把所有东西搬到 Vertex，而会按频率拆分：低频大波可以 Vertex 计算，高频细节保留 Fragment；或者使用预计算 Noise/Normal Texture，把多个 Hash 与插值 ALU 换成 Texture Sample；也可以降低第二层 Noise、附加灯或阴影 Variant。优化前要先用 GPU Profiler 测量，而不是仅凭“Vertex 更少”做结论。

**面试官追问：** `ddx/ddy` 为什么只能在 Fragment 语境下使用？

**面试者：**

Fragment Derivative 通常基于 GPU 以 2×2 Pixel Quad 并行执行的相邻 Fragment，硬件通过同一 Quad 内数值差近似屏幕方向导数。Vertex Shader 没有这种相邻屏幕 Fragment Quad，因此不能用同样方式得到 `ddx/ddy`。Derivative 还会受动态分支、三角形边界和 Helper Invocation 影响，所以它是屏幕空间局部近似，不是解析几何的精确偏导。

**学习复盘：**

- 回答要同时说明“为什么质量更好”和“付出了什么性能代价”。
- 面试官可能从 Stage 选择继续追问 GPU Quad 与 Derivative。

## Q7 ⭐：透明水面的 `Blend SrcAlpha OneMinusSrcAlpha` 是什么意思？请写出公式。

**面试官：** 不要回答“这就是 Alpha Blend”，解释 Source、Destination 和最终结果。

**面试者：**

在当前 Pass 中，水的 Fragment Shader 输出是 Source，Framebuffer 中在它之前已经绘制的背景是 Destination。`Blend SrcAlpha OneMinusSrcAlpha` 对 RGB 的简化公式是：

```text
C_out = C_src × A_src + C_dst × (1 - A_src)
```

当水 Alpha 为 0.2 时，水自身光照颜色贡献 20%，背景贡献 80%；Alpha 为 1 时只保留水颜色；Alpha 为 0 时颜色完全来自背景。当前 Shader 先计算：

```text
depthAlpha   = lerp(ShallowAlpha, DeepAlpha, depthMask)
fresnelAlpha = fresnelMask × FresnelAlphaStrength
foamAlpha    = foamMask × FoamAlphaBoost
finalAlpha   = saturate((depthAlpha + fresnelAlpha + foamAlpha) × WaterAlpha)
```

再把 `finalAlpha` 交给 Blend。这里的 Alpha 是艺术控制的覆盖权重，并不是严格的光学透射率。

值得注意的是 Straight Alpha 和 Premultiplied Alpha 不同。当前 RGB 没有预先乘 Alpha，所以使用 `SrcAlpha`；如果输出 `C_src` 已经乘过 Alpha，就应考虑 `Blend One OneMinusSrcAlpha`，否则会重复乘 Alpha、边缘变暗。当前实现属于 Straight Alpha。

**面试官追问：** Alpha 通道本身会怎么混合？

**面试者：**

若没有为 RGB 和 Alpha 分别声明 Blend Factor，当前同一组 Factor 也作用于 Alpha，因此简化后是：

```text
A_out = A_src × A_src + A_dst × (1-A_src)
```

它并不是简单把 `A_src` 原样写入目标。当前主要消费的是最终 RGB，Shader 最后显式 `color.a = finalAlpha` 只定义 Source Alpha；如果后处理或其他 Pass 依赖 Camera Color Alpha，就应明确设计分离的 Alpha Blend Factor，而不能只从 RGB 公式推断目标 Alpha 的意义。

**学习复盘：**

- 必须能写出 Blend Equation，并解释 Straight 与 Premultiplied Alpha。
- 不能把 Alpha 直接说成“透明度物理值”；当前只是风格化混合权重。

## Q8 ⭐：为什么透明水通常 `ZWrite Off`，但仍然保留 `ZTest LEqual`？有什么副作用？

**面试官：** 这是透明 Shader 模板里常见的两行。分别解释，别背模板。

**面试者：**

`ZTest LEqual` 表示当前水 Fragment 的深度小于等于 Depth Buffer 中已有深度时才通过。因此，如果一堵不透明墙在水面前方，水会被墙遮挡。关闭 Depth Test 会让水无视前后关系覆盖在墙上，这是错误的。

`ZWrite Off` 表示水通过测试后不把自身深度写入 Depth Buffer。普通 Alpha Blend 需要先看到背景颜色，再将水叠上去；多个透明对象通常按从远到近排序。如果前面绘制的透明水写入深度，后面的透明粒子或水层即使颜色本应混合，也可能因为深度测试直接被拒绝，形成生硬缺口。因此常见透明 Pass 关闭 ZWrite。

副作用是透明对象之间不能依靠 Depth Buffer 自动解决任意交叠。Unity 通常以 Renderer 级别按距离排序，但相交 Mesh、同一 Mesh 内三角形、粒子穿过水面时仍可能顺序错误。`ZWrite Off` 还削弱某些 Early-Z 优化；即使最终 Alpha 很低，昂贵 Fragment Shader 仍可能执行，并产生 Overdraw。

当前还使用 `Cull Back`，只渲染正面。如果直接改 `Cull Off` 支持水下观察，会把正反面都画一遍，可能导致法线朝向、Alpha 累加和 Overdraw 问题。更完整的水下方案应显式处理 Front Face/Back Face 和水下体积，而不是只关剔除。

**面试官追问：** 有哪些透明排序改进方案？

**面试者：**

要看需求。简单场景可调整 Render Queue、Sorting Priority、拆分 Renderer 或避免几何互穿；粒子与水可以用软粒子或专门的合成顺序。对形状复杂的透明物，可以先做 Depth Prepass 再做颜色 Pass，但这会改变内部层叠语义并增加 Draw Call；`Alpha Clipping` 能写深度但只适合二值边缘，不适合连续透明水；更通用的 Order-independent Transparency 如 Weighted Blended OIT 或 Per-pixel Linked List 成本和兼容性更高，URP 中也需要额外实现。当前 RPG 水池采用约束场景几何和排序的传统方案，是成本与效果的取舍。

**学习复盘：**

- `ZTest` 决定“能不能画”，`ZWrite` 决定“画完是否更新深度”，二者不能混为一谈。
- 面试官喜欢追问透明排序，因为它能区分“会套模板”和“理解 Pipeline”。

# 第三组：3D 数学、Coordinate Space 与常用函数

## Q9 ⭐：当前水 Shader 用到了哪些 Coordinate Space？为什么向量不能跨空间直接运算？

**面试官：** 请沿当前代码说明 Object、World、View、Clip、Screen 和 Tangent Space。

**面试者：**

`Object Space` 是 Mesh 自己的局部坐标，`Attributes.positionOS/normalOS/tangentOS` 来自这里；物体移动、旋转或缩放时，这些局部数值本身不需要变化。通过 Model Matrix 得到 `World Space`，它把场景中的物体放入统一坐标系，当前 `positionWS`、`dynamicNormalWS`、灯光方向和 Camera World Position 都能在这个空间交互。

`View/Eye Space` 以 Camera 为参考，通常 Camera 看向 View Space 的负 Z。当前用 `-TransformWorldToView(positionWS).z` 得到水面自身的正 Eye Depth。`Clip Space` 是 Projection 后、Perspective Divide 前的齐次坐标，`SV_POSITION` 用于 Clipping、Rasterization 和屏幕定位。`Screen Space` 是屏幕采样坐标，当前通过 `GetNormalizedScreenSpaceUV(input.positionCS)` 得到 0 到 1 UV，用来采样 `_CameraDepthTexture`。

`Tangent Space` 是每个表面局部的坐标系：Tangent 是 U 方向，Bitangent 是 V 方向，Normal 是表面朝外方向。平坦 Tangent Normal 是 `(0,0,1)`。程序化波纹先在 Tangent Space 表示，这样同一组局部波纹可以贴到不同旋转的表面。

向量的三个数字依赖它的 Basis。World Space 的 `(0,1,0)` 表示世界向上，Tangent Space 的 `(0,1,0)` 表示沿表面 Bitangent；它们不是同一个方向。点积 `dot(N,V)` 只有在 N 和 V 使用同一 Basis 时才等于实际夹角的余弦。当前做 Fresnel 时把 `viewDirectionWS` 转为 `viewDirectionTS`，再与 `normalTS` 点积；做 Lighting 时则把 `normalTS` 转成 `dynamicNormalWS`，与 World Space 灯光交互。

**面试官追问：** Position 和 Direction 做矩阵变换有什么区别？

**面试者：**

齐次坐标中 Position 通常写成 `(x,y,z,1)`，Direction 写成 `(x,y,z,0)`。矩阵最后一列的 Translation 只会影响 `w=1` 的 Position，不应改变 Direction。Normal 又比普通 Direction 特殊：在 Non-uniform Scale 下，直接乘 Model Matrix 会破坏它与表面 Tangent 的垂直关系，理论上需要使用 Model Matrix 左上 3×3 的 Inverse Transpose；Unity 的 `GetVertexNormalInputs` 等 API 封装了相关处理和平台差异。

**学习复盘：**

- 能说出空间名称不够，要说明每种数据为什么位于该空间。
- 高频追问是 Position/Direction 的 `w`、Normal Matrix、Non-uniform Scale。

## Q10 ⭐：请解释 `Dot Product`、`Cross Product` 和 Normalize，它们在水 Shader 中分别做了什么？

**面试官：** 从数学定义讲，不要只列 API 名。

**面试者：**

三维向量点积定义为：

```text
a · b = axbx + ayby + azbz = |a||b|cosθ
```

如果 a、b 都 Normalize 成单位向量，长度都是 1，那么 `a·b=cosθ`。它能衡量两个方向的一致程度：同向为 1，垂直为 0，反向为 -1。当前 Fresnel 使用单位 `normalTS` 和 `viewDirectionTS` 的点积；正视时 N 与 V 近似同向，`N·V≈1`，掠射角时接近垂直，`N·V≈0`。Height-to-Normal 中也用 Dot 计算行列式相关标量。

Cross Product 定义产生一个同时垂直于两个输入向量的向量，方向服从右手定则，长度为：

```text
|a × b| = |a||b|sinθ
```

当前用 `cross(baseNormalWS,tangentWS)` 恢复 Bitangent 方向；Height-to-Normal 也用 Cross Product 构造 Surface Gradient 的辅助向量。交换输入顺序会取反：`a×b=-(b×a)`，所以顺序不能随便换。

Normalize 是 `v/|v|`，把长度变为 1、保留方向。点积要表达纯角度时需要单位向量；插值后的 Normal、Normal Blend 后的结果、TBN 变换后的 Normal 都可能偏离单位长度，所以代码会再次 Normalize。零向量无法安全除以长度，因此 URP 提供 `SafeNormalize` 等保护实现。

**面试官追问：** 为什么 Cross Product 得到 Bitangent 后还要乘符号？

**面试者：**

`cross(N,T)` 只根据右手规则给出一个方向，但 Mesh 的 UV 可能被镜像，Transform 也可能有负缩放，这会改变 Tangent Basis 的 Handedness。Unity 把相关符号保存在 `tangentOS.w`，再结合 `GetOddNegativeScale()`。当前代码把二者相乘保存为 `tangentWS.w`，最后：

```text
B = tangentSign × normalize(cross(N,T))
```

忽略这个符号时，一部分镜像模型上的 Normal Map 会左右翻转或高光方向不一致。

**学习复盘：**

- 数学定义、几何意义、项目用法三者都要说到。
- `Cross Product` 的顺序和 Handedness 是常见深挖点。

## Q11：TBN 矩阵到底是什么？当前代码怎样在 Tangent 与 World Space 之间转换？

**面试官：** 你一直提 TBN，请明确写出它代表什么。

**面试者：**

TBN 是以 Tangent、Bitangent、Normal 三个互相正交或近似正交的 Basis Vector 组成的变换基底：

```text
TBN = [ T  B  N ]
```

如果采用列向量约定，那么 Tangent Space 向量 `v_t` 转 World Space 可以写为：

```text
v_w = TBN × v_t
```

例如平坦 Tangent Normal `(0,0,1)` 经过 TBN 后正好得到第三个 Basis，也就是几何 Normal N。`(1,0,0)` 会变成 World Tangent T，`(0,1,0)` 会变成 Bitangent B。

当前 Fragment 先 Normalize 插值后的 `normalWS` 和 `tangentWS`，用带符号的 Cross Product 恢复 `bitangentWS`，然后建立 `float3x3 tangentToWorld`。程序化高度场经过 `ElementWaterNormalFromHeight` 得到 `normalTS`，再用 URP 的 `TransformTangentToWorld` 得到 `dynamicNormalWS` 供 PBR Lighting 使用。反方向做 Fresnel 时，使用 `TransformWorldToTangent(viewDirectionWS,tangentToWorld)` 把观察方向放到与 `normalTS` 相同的空间。

如果 T、B、N 不是单位且互相垂直，TBN 的逆矩阵不再简单等于转置。当前通过 Unity 提供的 Mesh Tangent、Normal 变换和 Normalize 建立接近 Orthonormal 的 Basis；对于严重 Non-uniform Scale 或不良 Mesh Tangent，仍应检查导入数据和变换。

**面试官追问：** 为什么不把所有 Normal 直接留在 World Space？

**面试者：**

完全可以，关键是统一空间。Tangent Space 的优势是局部表面表达可复用：同一波纹函数不需要知道水面在世界里朝哪个方向，平坦基准始终是 `(0,0,1)`。最终 Lighting 需要 World Normal 时再转换。若波纹由 World Position XZ 生成、并且只允许水平水面，直接在 World Space 构造也可能更简单，但可旋转复用性较差。当前选择 Tangent Space 是为了与标准 Normal Mapping 和 URP Lit 数据流一致。

**学习复盘：**

- 面试官可能要求现场画 Basis 或写矩阵。
- 牢记“空间选择没有唯一答案，但参与同一运算的数据必须一致”。

## Q12 ⭐：UV 是什么？为什么修改 UV 能让水面看起来流动？

**面试官：** Plane 本身没有动，为什么玩家会看到纹路移动？

**面试者：**

UV 是 Mesh 顶点携带的二维 Surface Coordinate。常见 Plane 的 U、V 大致从 0 到 1，Rasterizer 会把顶点 UV 透视正确地插值到每个 Fragment。UV 本身不一定只用于 Texture Sampling；任何二维函数都可以把 UV 当输入。当前 Value Noise 接收二维坐标，所以改变输入坐标就等于在表面上移动采样位置。

Panning 的公式是：

```text
UV'(t) = UV + Speed × Time
```

假设某个屏幕 Fragment 的原始 UV 固定为 `(0.4,0.6)`，Speed 为 `(0.05,0.02)`。时间增加 1 秒后，它查询 Noise 的坐标变成 `(0.45,0.62)`；几何位置没动，但这个位置读取到的是 Noise 场中另一个值，于是图案相对表面移动。`Speed` 的单位可以理解为 UV/秒，正负号控制方向。

当前使用两组不同的 `_WaveSpeedA.xy` 和 `_WaveSpeedB.xy`，并使用 `_Time.y`。`Vector` Property 有 xyzw 四个分量，但这里只消费 xy。Scale 在 Panning 后作用：

```text
NoisePosition = MovingUV × WaveScale
```

Scale 越大，单位 UV 中经过的 Noise 格子越多，纹理频率越高、视觉结构越细。

**面试官追问：** UV Space 方案有什么缺陷？

**面试者：**

同一 `_WaveScale` 的世界波纹尺寸依赖 Mesh UV 展开和物体缩放。一个 1 米 Plane 和一个 20 米 Plane 如果都用 0 到 1 UV，单位世界距离经过的 UV 不同，波纹世界尺寸就不同；UV 接缝也可能造成 Noise 不连续。若希望多个水池保持统一的世界波长，可以用 `positionWS.xz` 作为 Noise 坐标，或把世界尺寸传入修正 UV。但 World Space Noise 会让移动水体像“穿过固定噪声场”，是否合理取决于需求。当前实验水面形状规则、UV 可控，所以选择更直观的 UV Space。

**学习复盘：**

- “图案移动”本质是采样域移动，不是几何移动。
- 高频追问是 Scale、Speed 的单位以及 UV Space 与 World Space 的 trade-off。

## Q13：`lerp`、`saturate`、`smoothstep` 和 `pow` 在当前水 Shader 中分别承担什么角色？

**面试官：** 这些函数很基础，但请解释公式和使用原因。

**面试者：**

`lerp(A,B,t)` 是 Linear Interpolation：

```text
lerp(A,B,t) = A × (1-t) + B × t
```

当前用 Depth Mask 混合 Shallow/Deep Color 与 Alpha，用 Fresnel Mask 混合 Depth Color/Fresnel Color，用 Foam Mask 混合 Fresnel Color/Foam Color。`t` 最好处于 0 到 1，否则会产生 Extrapolation。

`saturate(x)` 等价于 `clamp(x,0,1)`，通常是 GPU 友好的内建操作。当前用于把 Depth、Fresnel、Foam 和最终 Alpha 限制为合法权重。它也能防止多项相加后越界，但频繁 Saturate 不能替代对输入范围的理解。

`smoothstep(edge0,edge1,x)` 先把 x 映射到 0 到 1，再应用三次 Hermite Curve：

```text
t = saturate((x-edge0)/(edge1-edge0))
smoothstep = t²(3-2t)
```

它在两端一阶导数为 0，比硬 `step` 有柔和边缘。当前用 `smoothstep(0.35,0.70,combinedNoise)` 把连续 Noise 变成块状但不锯齿的泡沫纹理。

`pow(x,p)` 计算幂。当前 Fresnel 为：

```text
F = pow(saturate(1-N·V), FresnelPower)
```

当底数处于 0 到 1 时，Power 越大，中间值衰减越快，Fresnel 带越窄。`pow` 比简单乘加昂贵一些，并且负底数配非整数指数可能产生非法结果，所以先 Saturate。

**面试官追问：** 为什么 `Value Noise` 里也用了 `t²(3-2t)`？

**面试者：**

如果直接用格子内坐标 local 做 Linear Interpolation，Value 在格子边界能连续，但斜率会突然改变，视觉上容易出现格子感，后续 Height-to-Normal 会把斜率突变放大成接缝。Hermite Curve 满足 `f(0)=0`、`f(1)=1`，且 `f'(0)=f'(1)=0`，相邻格子的边界斜率衔接更柔和。它不是让随机值更随机，而是在改变插值权重的变化速度。

**学习复盘：**

- 基础函数题要讲清输入范围、公式、图形意义和项目用法。
- 不要把 `smoothstep` 说成普通 Clamp，它还包含平滑曲线。

# 第四组：程序化波纹、Normal、Depth、Fresnel 与泡沫

## Q14 ⭐：Shader 里的 Hash 是什么？为什么不用普通随机数？

**面试官：** 你说 Value Noise 依赖 Hash。先解释 Hash 在这里解决了什么问题。

**面试者：**

这里的 `ElementWaterHash21` 是一个无状态的伪随机映射：输入一个 `float2` 坐标，输出一个看似无规律的 `[0,1)` 标量，所以命名中的 21 可以理解为 two-to-one。它最重要的性质不是密码学安全，而是 Deterministic：相同格点永远得到相同结果，相邻不同格点尽量去相关。

GPU 会并行执行大量 Fragment，它们没有一个适合逐 Fragment 共享、不断推进的 CPU 风格 Random State。如果每帧或每次执行同一格点都得到不同值，Noise 会闪烁，不能形成随 UV 平移的稳定空间场。因此我们需要纯函数：

```text
randomValue = Hash(gridCoordinate)
```

当前函数先用不同常数缩放 x、y，再 `frac` 折回 0 到 1；然后通过 Dot Product 把两个分量交叉混合，最后对 `position.x × position.y` 再取 `frac`：

```hlsl
position = frac(position * float2(123.34, 456.21));
position += dot(position, position + 45.32);
return frac(position.x * position.y);
```

`frac(x)=x-floor(x)`，所以输出被折叠到 `[0,1)`。这些常数只是经验性的打散参数，不是物理常数。这个 Hash 足以用于风格水纹，但可能存在周期、方向相关性或浮点精度差异；它不适合密码学，也不能保证所有平台位级一致。

**面试官追问：** Hash 和 Noise 是一回事吗？

**面试者：**

不是。Hash 给离散格点生成不连续的伪随机值；直接把 Hash 作为每个 Fragment 输出，会出现剧烈跳变和电视雪花。Value Noise 在 Hash 格点之间做平滑插值，构造连续标量场。可以说 Hash 提供“随机样本”，Noise 定义“如何在样本之间重建连续函数”。如果用 Gradient Noise，例如 Perlin Noise，格点存的是伪随机梯度，插值的是梯度与局部位移的 Dot Product；当前实现是更容易解释的 Value Noise。

**面试官追问：** 为什么不直接采样一张 Noise Texture？

**面试者：**

Noise Texture 是很常见、并且可能更快的生产方案：一次或少数 Texture Sample 能替代多次 Hash 和 Lerp，还能由美术精确控制频谱。当前选择程序化 Hash/Value Noise，主要是为了自研学习、减少外部资源依赖，并可以无限按坐标生成。代价是增加 ALU，而且质量未必优于优秀纹理。不能简单说“没有贴图所以性能更好”；应在目标 GPU 上比较 ALU、Texture Bandwidth、Cache 命中与屏幕覆盖。

**学习复盘：**

- 要区分 Stateful Random、Stateless Hash 和 Continuous Noise。
- 好回答应主动说明程序化与 Texture Noise 的性能 trade-off。

## Q15 ⭐：请从头推导二维 `Value Noise`。为什么它是连续的？

**面试官：** 假设我让你现场写思路，你会怎么从任意二维坐标得到连续 Noise？

**面试者：**

给定连续坐标 `p=(x,y)`，第一步用 `floor(p)` 得到当前整数格子的左下角坐标 `cell`，用 `frac(p)` 得到格子内部局部坐标 `local=(u,v)`：

```text
cell  = floor(p)
local = frac(p)
```

第二步，对当前格子的四个角做 Hash：

```text
h00 = Hash(cell + (0,0))
h10 = Hash(cell + (1,0))
h01 = Hash(cell + (0,1))
h11 = Hash(cell + (1,1))
```

第三步，不直接用 u、v，而先应用 Hermite Fade：

```text
s(t) = t²(3-2t)
su = s(u),  sv = s(v)
```

第四步做 Bilinear Interpolation。先沿 x 混合上下两条边，再沿 y 混合：

```text
bottom = lerp(h00,h10,su)
top    = lerp(h01,h11,su)
noise  = lerp(bottom,top,sv)
```

它跨格子连续的原因是相邻格子共享边界角点。比如从左格子到右格子经过共同边界时，左格子的 `u→1`，右格子的 `u→0`，两侧都收敛到相同的边界 Hash 组合。Hermite Fade 还让 `s'(0)=s'(1)=0`，所以边界处一阶变化更柔和。严格说，这个三次 Fade 通常提供 C1 风格的边界平滑，但由离散 Hash 和有限精度构造的整体函数仍是程序化近似；如果需要更高阶导数连续性，可以使用五次 Fade `6t^5-15t^4+10t^3`。

**面试官追问：** Bilinear Interpolation 真的是“线性”吗？

**面试者：**

它分别对 x 和 y 是线性的，但包含 `u×v` 交叉项，所以不是整个二维平面上的单一 Linear Function。展开普通 Bilinear Interpolation 可以写成：

```text
f(u,v)=h00(1-u)(1-v)+h10u(1-v)+h01(1-u)v+h11uv
```

当前只是把 u、v 换成平滑后的 su、sv。这个表达也能看出四个角权重之和为 1，因此只要四个 Hash 都在 0 到 1，插值结果也保持在它们的凸包范围内。

**面试官追问：** Value Noise 有哪些视觉缺陷？

**面试者：**

它可能保留网格方向感，低质量 Hash 会产生规律，单个 Octave 的频谱也比较单调。常见改进包括叠加多个频率和振幅的 fBM、旋转每层坐标、使用 Gradient Noise/Simplex Noise，或直接使用艺术可控的 Noise Texture。但每增加一层都会增加 Hash 和插值成本。当前水用两层不同 Scale/Speed 的 Value Noise，只做到足够打散，不声称是完整 fBM。

**学习复盘：**

- 这是一道很适合白板推导的题，必须能写出四角采样与两次 Lerp。
- 注意“Value 连续”和“Derivative 完全连续”不是同一个结论。

## Q16：为什么使用两层不同方向的 Noise？它和 fBM 有什么区别？

**面试官：** 一层 Noise 已经会动了，第二层在解决什么问题？

**面试者：**

单层 Noise 以固定 Scale 和 Speed 平移时，整个图案像一张纹理沿同一方向滑动，容易看出刚性运动和网格方向。当前分别计算：

```text
NA = ValueNoise((UV + SpeedA×Time) × ScaleA)
NB = ValueNoise((UV + SpeedB×Time) × ScaleB)
CombinedNoise = saturate((NA+NB)×0.5)
```

两组默认速度方向不同，Scale 也不同，因此局部结构会交叉变化，不容易被识别为同一张图平移。两层 Noise 还分别转为 Normal 后做 Normal Blend，而不是只对 CombinedNoise 生成一次 Normal，这样两种斜率方向都能参与高光。

这和标准 fBM 不完全相同。fBM 通常按多个 Octave 叠加，频率按 Lacunarity 增长、振幅按 Persistence 衰减，例如：

```text
fBM(p)=Σ amplitude_i × Noise(frequency_i × p)
```

当前只是两层等权平均，并且各自有独立 Panning Direction，更接近“双层动态 Noise”。如果面试中把它直接称为完整 fBM，会过度包装。

**面试官追问：** 为什么 `CombinedNoise-0.5`？

**面试者：**

CombinedNoise 大致在 0 到 1。如果直接乘 `_DepthNoiseStrength` 加到 Depth Mask，它只能单向增加深度，整个边界会系统性向深水方向偏移。减去 0.5 后大致变为 `[-0.5,0.5]`：

```text
centeredNoise = CombinedNoise - 0.5
DepthMask = saturate(normalizedDepth + centeredNoise×Strength)
```

于是部分区域推深、部分区域推浅，边界围绕原位置双向扰动。这里体现的是把 Unipolar Signal 转为 Bipolar Signal 的常见做法。

**学习复盘：**

- 两层 Noise 解决的是运动规律感，不等同于物理水波叠加。
- `x-0.5` 的意义是从单极信号转为双极扰动。

## Q17 ⭐：你如何把一个标量 Height Field 转换成 Normal？`ddx/ddy` 到底是什么？

**面试官：** 这是水面高光的核心，请详细解释，不要只说用了 Normal From Height。

**面试者：**

Height Field `H(x,y)` 只描述每个位置的高低，Normal 描述局部表面朝向。最直观的二维局部模型是把表面写成：

```text
P(x,y) = (x, y, H(x,y))
```

沿 x、y 的 Tangent 近似为：

```text
Tx = (1,0,∂H/∂x)
Ty = (0,1,∂H/∂y)
```

它们 Cross Product 后得到与表面垂直的方向，符号约定不同可能写成：

```text
N ∝ (-∂H/∂x, -∂H/∂y, 1)
N = normalize(N)
```

当前代码使用更适合任意表面和透视投影的 Surface Gradient 写法。`ddx(value)`、`ddy(value)` 由相邻 Fragment Quad 的值差近似当前值沿屏幕 x/y 的变化率。代码同时取 `ddx/ddy(positionWS)` 与 `ddx/ddy(height)`，通过 Cross/Dot 和 Determinant 把屏幕方向的高度变化映射回世界表面梯度：

```hlsl
surfaceGradient = surface
    * (heightDerivativeX * crossY + heightDerivativeY * crossX);
perturbedNormalWS = normalize(baseNormalWS - strength * surfaceGradient);
```

最后再把 perturbed World Normal 转回 Tangent Space。`strength=0` 时公式退化回原几何 Normal；Strength 增大时倾斜更明显。

**面试官追问：** 既然用了 Height，为什么水的轮廓仍然是平面？

**面试者：**

因为 Height 只用于修改 Lighting Normal，没有写入 Vertex Position，也没有改变真正的 Depth、Silhouette 或 Collision。这属于 Bump Mapping/Normal Perturbation。光照看到表面方向变化，所以内部区域像有凹凸；但从侧面看轮廓仍是一条直线，物体也不会真正被波峰遮挡。要改变轮廓必须做 Vertex Displacement、Tessellation 或真正几何模拟。

**面试官追问：** Derivative 有哪些坑？

**面试者：**

原始 `ddx/ddy` 是屏幕空间有限差分，它的数值会随投影和屏幕覆盖尺度变化；当前 Surface Gradient 写法同时使用 Position 与 Height 的导数，目的正是抵消这种参数化尺度，让最终表面梯度比直接使用 `ddx(height)` 更稳定，但它仍是离散近似。三角形边界与不连续信号附近可能不稳定；在 Non-uniform Dynamic Branch 内，邻居 Fragment 可能走不同路径，Derivative 也可能失去直观意义，GPU 会使用 Helper Invocation 维持部分导数计算。Noise 如果有硬 Step，Normal 会出现尖锐或闪烁，因此当前先用平滑 Value Noise。Derivative 也会增加 Fragment 成本，不能因为没有 Texture Sample 就认为免费。

**学习复盘：**

- 最好能写出 `(-dH/dx,-dH/dy,1)` 的直觉公式。
- 要明确当前实现是 Normal Perturbation，不是 Geometry Displacement。

## Q18：为什么两张 Normal 不能直接相加？当前 Normal Blend 的依据是什么？

**面试官：** 你有 `normalA` 和 `normalB`，直接 `normalize(A+B)` 不行吗？

**面试者：**

Tangent Space 的平坦 Normal 是 `(0,0,1)`。假设两张 Normal 都只有小斜率，直接相加会把两个 Z 基准也相加，得到接近 `(x1+x2,y1+y2,2)`。Normalize 后 XY 相对 Z 的比例反而被压小，合并结果可能比预期更平，而且这种相加没有正确组合局部斜率。

当前采用与 Shader Graph Default Normal Blend 相近的近似：

```text
Nblend = normalize(
    (A.x+B.x,
     A.y+B.y,
     A.z×B.z)
)
```

XY 可以理解为局部斜率贡献相加，Z 相乘避免重复叠加两个“朝外基准”。它对当前小幅波纹足够直观、成本低。更准确的方案包括 Reoriented Normal Mapping（RNM），它把 Detail Normal 重新定向到 Base Normal 的局部朝向，在大角度组合时保留细节更好；但公式更复杂，当前效果和学习目标不需要立刻引入。

**面试官追问：** 为什么 Blend 后还要 Normalize？

**面试者：**

因为上述代数组合不保证结果长度为 1，而 Lighting 中 `N·L`、`N·V` 都假定 Normal 是单位方向。不 Normalize 会把向量长度混入亮度和 Fresnel，产生不可预测结果。Normal 从 Vertex 插值到 Fragment、TBN 变换后也应考虑重新 Normalize。

**学习复盘：**

- 不能只回答“Unity 有 Normal Blend 节点”。要解释平坦 Normal 的 Z 基准。
- 主动提 RNM 可以体现知道更高质量方案，但不要假装当前已经实现。

## Q19 ⭐：Depth Buffer 里存的是什么？为什么必须线性化？

**面试官：** 你采样 `Scene Depth` 算水深。Raw Depth 能直接相减吗？

**面试者：**

通常不能。Perspective Projection 后，Depth Buffer 保存的是由 View-space z 经过 Projection 和 Perspective Divide 映射得到的值，不是与真实距离成线性关系的米数。常见形式可以抽象为 `a + b/z`，近处分配更多精度、远处精度更低；URP/平台还可能使用 Reversed-Z，让远平面接近 0、近平面接近 1，以改善浮点深度精度。不同 Graphics API 的 NDC Depth Range 也可能不同。

因此当前使用 URP API 而不是手写假定：

```hlsl
rawSceneDepth = SampleSceneDepth(screenUV);
sceneEyeDepth = LinearEyeDepth(rawSceneDepth,_ZBufferParams);
```

Orthographic Camera 没有相同的 Perspective `1/z` 分布，所以代码根据 `unity_OrthoParams.w` 选择 `LinearDepthToEyeDepth`。水面自身 Depth 则通过：

```hlsl
surfaceEyeDepth = -TransformWorldToView(positionWS).z;
```

二者变到相同的 Eye Depth 语义后才能相减。若直接拿 Raw Scene Depth 减 World Distance 或 Clip z，既单位不同、空间也不同，结果会随 Camera Near/Far 和视角非线性变化。

**面试官追问：** Depth Buffer 为什么会有 Z-fighting？

**面试者：**

Depth 精度有限，而且 Perspective 下远处分辨率较差。当两个表面在相同像素上的深度差小于可表示间隔时，量化结果会在前后之间不稳定，形成 Z-fighting。改善方式包括合理提高 Near Plane、避免极端 Far/Near Ratio、使用 Reversed-Z/浮点深度、让共面几何有实际间隔或使用合适 Depth Bias。简单把 Far Plane 拉得更远通常会恶化精度。

**学习复盘：**

- 必须说出 Raw Depth 非线性、Eye Depth 线性化、Reversed-Z/API 差异。
- 不要把 Depth Buffer 说成“保存到 Camera 的世界距离”。

## Q20 ⭐：当前 `waterThickness` 是怎么计算的？它真的是水深吗？

**面试官：** 写出公式，并说明它的几何意义和缺陷。

**面试者：**

在当前水面 Fragment 的 Screen UV 上，`Scene Depth` 给出这条 Camera Ray 后方最近的、已写入 Depth Texture 的 Opaque Surface 的 Eye Depth；水面自身也有 Eye Depth。因此：

```text
waterThickness = max(sceneEyeDepth - surfaceEyeDepth, 0)
```

它估计的是沿当前观察射线从水面到水底/障碍物的距离，不是沿 World Up 的垂直水深。Camera 越斜，同一垂直水深对应的 Ray Distance 通常越长，所以颜色和泡沫可能随视角变化。这对风格化浅水边界常常可接受，但不是严格体积厚度。

得到 thickness 后再归一化：

```text
normalizedDepth = saturate(max(thickness,0)/DepthFadeDistance)
centeredNoise   = CombinedNoise - 0.5
depthMask       = saturate(
    normalizedDepth + centeredNoise×DepthNoiseStrength)
```

`DepthFadeDistance` 定义从浅水过渡到完整深水色大约需要多大的 Eye-space 厚度；`max(...,0)` 防止错误排序或精度导致负厚度；Noise 只扰动过渡边界，不取代真实 Scene Depth。

**面试官追问：** 哪些对象不会进入这份 Scene Depth？

**面试者：**

通常 Camera Depth Texture 主要来自 Opaque 阶段或 Depth Prepass。水自身处于 Transparent Queue，后方其他透明对象也通常不写 Depth，因此它们不会成为可靠的“水底”。如果水下地面使用 Transparent Shader、关闭 ZWrite，或 URP Asset/Camera 没有正确生成 Depth Texture，厚度会失效。Sky 没有普通几何深度，采样到 Far Plane 时也要谨慎。当前方案依赖 PC Renderer 开启 Depth Texture，并要求水底是写深度的不透明几何。

**面试官追问：** 如何得到更接近垂直水深的结果？

**面试者：**

仅凭单张 Camera Depth Texture 很难知道任意世界竖直方向的交点。规则水体可以传入 Water Surface Height，并结合水底 World Position 重建后计算垂直差；首先要从 Screen UV + Raw Depth 重建水底 World Position，再做 `dot(surface-bottom,worldUp)`。复杂体积可能需要水体几何、额外 Depth Pass、Signed Distance Field 或专门的 Volume 数据。是否值得取决于视角变化是否真的暴露当前误差。

**学习复盘：**

- 一定要说“沿视线的 thickness”，不能直接称为真实垂直水深。
- Scene Depth 的来源与透明物限制是常见追问。

## Q21：为什么深水更蓝、更不透明？当前实现和 Beer-Lambert Law 有什么区别？

**面试官：** 你的深浅颜色是物理吸收吗？

**面试者：**

当前不是严格物理吸收，而是用同一个 `depthMask` 分别插值颜色和 Alpha：

```text
depthColor = lerp(ShallowColor,DeepColor,depthMask)
depthAlpha = lerp(ShallowAlpha,DeepAlpha,depthMask)
```

它的优点是参数直观：策划或美术能明确控制浅水端点、深水端点和过渡距离；颜色与 Alpha 共用 Mask，视觉语义一致。缺点是线性 Lerp 不符合光在参与介质中的指数衰减，也没有真正采样并衰减背景光谱。

更物理的吸收常用 Beer-Lambert Law：

```text
T(λ,d) = exp(-σ_a(λ) × d)
```

`T` 是波长 λ 的剩余透射率，`σ_a` 是吸收系数，d 是光在介质中传播的距离。因为不同 RGB 通道吸收系数不同，传播距离增长后红光可能更快衰减，水体呈蓝绿。若有 Scattering，还需要更完整的 Participating Media 模型。当前 Alpha Blend 只是把水表面颜色盖到背景上，并没有按通道对 Background 做真实透射计算。

**面试官追问：** 如果升级，你会怎么做？

**面试者：**

在 Screen-space 近似中，可以采样 Camera Opaque Texture 得到水下背景颜色，用 thickness 计算逐通道 Transmittance：

```text
transmittance = exp(-absorptionRGB × thickness)
absorbedBackground = sceneColor × transmittance
```

再叠加 In-scattering、Specular/Fresnel Reflection 和 Foam。这样比 Alpha Lerp 更接近物理，但需要 Opaque Texture Sample、处理折射 UV 越界与前景泄漏，并明确 Transparent 合成。当前版本先保留可调的 Lerp，是学习范围和 RPG 可读性的选择。

**学习复盘：**

- 主动区分艺术 Alpha 与 Optical Transmittance，会比强行“物理正确”更加分。
- 能写出 Beer-Lambert 公式并解释每个量即可，不必冒充已实现体积散射。

## Q22 ⭐：请从 Dot Product 推导当前 Fresnel，并比较 Schlick Approximation。

**面试官：** 为什么斜着看水面更亮？你的公式是什么？

**面试者：**

先把 Surface Normal N 和 Fragment 指向 Camera 的 View Direction V 都 Normalize，并确保在同一 Tangent Space。单位向量点积：

```text
N·V = cosθ
```

正视时 θ 接近 0°，`cosθ≈1`；掠射角时 θ 接近 90°，`cosθ≈0`。因此：

```text
fresnelBase = saturate(1-N·V)
fresnelMask = pow(fresnelBase,FresnelPower)
```

正视区域接近 0，边缘/掠射区域接近 1。Power 大于 1 时，中间值进一步变小，所以反射带变窄、更集中在掠射角；Power 较小时过渡更宽。当前 Mask 用于把 Depth Color Lerp 到 `_FresnelColor`，并增加少量 Alpha，从视觉上强化水面边缘和斜视区域。

但这只是风格化 Fresnel Mask。常见 Schlick Approximation 是：

```text
F(θ)=F0+(1-F0)(1-cosθ)^5
```

Dielectric 在法线入射时的反射率可以由折射率近似：

```text
F0=((n1-n2)/(n1+n2))²
```

空气到水大约 `n1≈1.0`、`n2≈1.33`，所以 F0 约 0.02。Schlick 具有明确的法线入射基值和固定五次形状；当前公式没有显式 F0，也用可调 Power 和艺术颜色/Alpha，所以不能称为完整物理 Fresnel。

**面试官追问：** URP PBR 已经有 Specular，为什么还额外算 Fresnel？会不会重复？

**面试者：**

`UniversalFragmentPBR` 的 Lit BRDF 已会根据 Dielectric、Smoothness、Normal、View/Light Direction 计算 Microfacet Specular，其中包含 Fresnel 相关项。当前额外 Mask 不是替代该 BRDF，而是艺术增强：直接把 Albedo 向青白色过渡并增加 Alpha，使第三人称 RPG 俯视角下的水体边界更易读。它确实可能产生“双重强化”，参数过大时会像塑料或自发光边缘，所以 `_FresnelAlphaStrength` 和颜色需要克制。生产中如果追求物理一致性，我会减少这层艺术 Albedo Fresnel，把反射交给更完整的 Environment Reflection/SSR/Reflection Probe。

**面试官追问：** 如果 N 和 V 没有 Normalize 会怎样？

**面试者：**

点积会变成 `|N||V|cosθ`，长度被混入结果，不再只代表角度。插值和 Normal Blend 都可能改变长度，因此代码在 Fresnel 函数内显式 Normalize。若 N、V 还处于不同 Coordinate Space，即使都单位化也没有意义。

**学习复盘：**

- 必须会从 `N·V` 解释角度变化，并知道 Schlick 的 F0。
- 诚实说明“当前艺术 Fresnel + URP Specular 可能重复”是深度理解的表现。

## Q23：岸边泡沫是怎么生成的？为什么能贴着交界线？

**面试官：** 你没有 Foam Texture，白色边缘从哪里来？

**面试者：**

泡沫复用水体厚度。水面和水下几何刚接触时，Scene Eye Depth 与 Surface Eye Depth 很接近，`waterThickness≈0`；远离交界线后 thickness 增大。因此先构造：

```text
contactMask = 1-saturate(waterThickness/FoamDistance)
```

接触处约为 1，达到 `_FoamDistance` 后降到 0。它提供“泡沫在哪里”的空间约束，但单独使用会是一条规则、连续的白边。

然后用移动 Combined Noise 做断裂：

```text
foamNoise = smoothstep(0.35,0.70,combinedNoise)
foamMask  = saturate(contactMask×foamNoise×FoamStrength)
```

`smoothstep` 把连续 Noise 中较高区域筛成有柔边的块状图案；与 contactMask 相乘后，只有接触带内的块状区域保留。最后：

```text
finalAlbedo = lerp(fresnelColor,FoamColor,foamMask)
foamAlpha   = foamMask×FoamAlphaBoost
```

泡沫放在颜色链最后，避免又被深水色或 Fresnel 覆盖。Noise 随时间移动，所以接触边缘不会完全静止。

**面试官追问：** 这是真正的泡沫模拟吗？

**面试者：**

不是。它是 Screen-space Depth Intersection Mask，没有泡沫粒子的生成、寿命、聚合、流速或消散，也没有根据浪峰曲率生成海面白沫。Camera 角度变化会改变 thickness，透明水下物也不进入可靠深度。若需要撞击飞溅，我会用 Particle System/VFX Graph；若要波峰泡沫，可以基于 Wave Curvature/Jacobian 或高度斜率；若要持续交互泡沫，可用 RenderTexture 保存 Foam Field。当前方案只解决静态岸边的低成本视觉提示。

**面试官追问：** 为什么不直接用 `step`？

**面试者：**

`step` 会生成硬二值边界，容易 Alias 和闪烁；`smoothstep` 在阈值区间内连续过渡，能减少锯齿并让艺术调参更柔和。如果要求屏幕空间恒定 Anti-aliasing，还可以用 `fwidth` 根据 Fragment Derivative 自适应阈值宽度，但当前没有加入。

**学习复盘：**

- 这道题要把“接触位置”和“泡沫纹理”两条信号分开讲。
- 不要把 Surface Mask 说成 Particle/VFX 或流体泡沫模拟。

# 第五组：URP 接入、Shader 工程与 GPU 性能

## Q24 ⭐：你为什么调用 `UniversalFragmentPBR`？`SurfaceData` 和 `InputData` 分别是什么？

**面试官：** 你手写了水面数学，为什么最后不自己把光照也写完？

**面试者：**

我的自研部分负责生成水的 Surface Signal，URP 负责通用 Lighting。`SurfaceData` 描述“这个 Fragment 的材质是什么”，例如：

```text
albedo        = finalAlbedo
metallic      = 0
smoothness    = _Smoothness
normalTS      = normalTS
occlusion     = 1
emission      = 0
alpha         = finalAlpha
clearCoat     = 0
```

`InputData` 描述“这个 Fragment 在场景中的渲染上下文是什么”，例如 World Position、World Normal、View Direction、Shadow Coordinate、Fog、Vertex Lighting、Baked GI、Screen UV 和 TBN。当前动态 Normal 已转换为 `dynamicNormalWS` 写入 `inputData.normalWS`；真正参与 `UniversalFragmentPBR` 光照方向计算的是这份 World Normal。`surfaceData.normalTS` 仍按结构体语义填写，但 `UniversalFragmentPBR` 不会替我再次把它转换成 World Space。`SampleSHPixel` 在当前 Pass 中提供基于 SH/Probe 的低频环境光，`VertexLighting` 支持逐顶点附加灯路径，Shadow Coord 让主光实时阴影参与计算。

`UniversalFragmentPBR(inputData,surfaceData)` 会根据 URP 当前 Keyword/Lighting Path 计算 BRDF、主光、附加光、阴影和 GI。最后 `MixFog` 处理雾，Pass 的 Blend 再与背景合成。

我不重写整套 BRDF 的原因是职责和风险。水特有的是 Noise、Depth、Fresnel、Foam；主光、Additional Lights、阴影、GI 与 Microfacet BRDF 属于 Render Pipeline 的通用能力。复用 URP 能减少重复公式，让水与场景其他 Lit Material 的基本灯光风格一致。

但“调用 `UniversalFragmentPBR`”不等于“自动获得 URP Lit 的全部能力”。Custom Shader 仍要自己提供正确的 `InputData`、Keyword 和 Pass。当前实现有 Forward 主 Pass、主光/附加光/实时阴影与 SH Probe 路径，但没有 Lightmap UV/Lightmap Keyword，也把 `shadowMask` 固定为 1，因此不能声称完整支持 Baked Lightmap/ShadowMask；它也没有声明 Light Layers、Reflection Probe Blending 等完整 Lit Variant。URP 升级后 Include、Struct 字段、Keyword 或函数签名还可能变化。所以更准确的表述是“复用 URP PBR 核心，并实现当前水面所需的子集”。

**面试官追问：** PBR 的 BRDF 大致在解决什么？

**面试者：**

BRDF 描述给定入射光方向 L 和观察方向 V 时，表面向 V 反射多少 Radiance。实时 Microfacet PBR 通常把 Diffuse 和 Specular 分开，Specular 由 Normal Distribution Function、Geometry/Visibility Term 和 Fresnel Term 组成，常见抽象形式是：

```text
f_specular = D × G × F / (4(N·L)(N·V))
```

`D` 描述 Microfacet Normal 分布，Smoothness/Roughness 会影响它；`G` 描述微表面之间的遮蔽与阴影；`F` 描述界面 Fresnel。当前没有自己实现这些项，而是准备 URP 所需数据后复用 `UniversalFragmentPBR`。这不代表我可以完全不理解 BRDF，而是工程上避免重复维护 Pipeline 已有能力。

**面试官追问：** 为什么水的 Metallic 是 0，Smoothness 较高？

**面试者：**

水是 Dielectric，不具有金属那种自由电子导致的有色高反射，因此 Metallic 设为 0。Dielectric 仍然有低 F0 的 Specular，不是“没有反射”。较高 Smoothness 表示 Microfacet Normal 分布更集中，Specular Highlight 和环境反射更清晰；Smoothness 低时高光会扩散、看起来浑浊或粗糙。当前水仍使用风格化 Albedo/Alpha，不能因为接入 PBR 函数就声称整个透明模型物理正确。

**学习复盘：**

- `SurfaceData` 是材质，`InputData` 是光照上下文，这是回答主线。
- 能说出 Microfacet BRDF 的 D/G/F 含义即可体现底层理解，不必现场重写 URP。

## Q25：`CBUFFER`、SRP Batcher、Shader Keyword 和 Variant 与这份水 Shader 有什么关系？

**面试官：** 从 Shader 工程角度讲讲，而不只是画面公式。

**面试者：**

Material Property 在 ShaderLab 的 `Properties` 中暴露给 Inspector，但 HLSL 仍需要对应变量。当前把所有 Per-Material 参数放入：

```hlsl
CBUFFER_START(UnityPerMaterial)
    ...
CBUFFER_END
```

Constant Buffer 是 GPU 读取小量只读常量的标准方式。SRP Batcher 的核心思路之一，是让兼容 Shader 的 Per-Material 数据使用稳定的 `UnityPerMaterial` 布局，把 Material 数据持久放在 GPU Buffer，Draw 之间主要切换 Buffer Binding，而不是反复重建大量状态。它减少的是 CPU 提交开销，不会减少水 Fragment 内两层 Noise 或 PBR 的 GPU 计算。

当前还声明了多组 `#pragma multi_compile`：主光阴影、Cascade/Screen Shadow、Additional Lights、Cluster/Forward+ 路径、附加光阴影、Soft Shadow、Fog、Instancing 等。Keyword 组合会生成 Shader Variant，不同运行条件选择对应编译程序。优点是运行时路径更明确，避免在一个 Shader 中承担所有动态分支；缺点是组合可能呈笛卡尔积增长，增加编译时间、构建体积和 Warm-up 压力。URP 会做部分 Stripping，但项目仍应只保留真实使用的功能。当前 Cluster 路径仍使用旧 `_FORWARD_PLUS` 名称，后面的追问会说明版本问题。

普通 Float Property 和 Keyword 不同。`_WaveNormalStrength` 改数值只是更新常量；如果用 Keyword 打开/关闭第二层 Noise，可能选择另一个 Variant。连续参数不适合 Keyword；只有能显著裁掉一整条昂贵代码路径、并且状态种类有限时，才值得评估 Shader Feature。

**面试官追问：** `multi_compile` 和 `shader_feature` 有什么常见区别？

**面试者：**

概念上，`multi_compile` 通常用于 Pipeline/全局确实可能需要的组合，构建时更倾向保留；`shader_feature` 更适合 Material 局部可选功能，Unity 可以根据构建中实际 Material Keyword 使用情况剥离未用 Variant。具体 Stripping 行为还受 Unity/URP 版本和配置影响。滥用任一者都会产生 Variant Explosion，所以不能为每个普通开关都生成 Variant。

**面试官追问：** 你当前写的是 `_FORWARD_PLUS`，它在 URP 17.3 中还是推荐写法吗？

**面试者：**

不是推荐写法。对照项目实际安装的 URP 17.3 Package Source，Unity 6.1 起 `_FORWARD_PLUS` 已被标为 Deprecated，新的 Keyword 是 `_CLUSTER_LIGHT_LOOP`，对应宏是 `USE_CLUSTER_LIGHT_LOOP`。`Core.hlsl` 目前还包含向后兼容层：检测到 `_FORWARD_PLUS` 时会定义新的 Cluster Keyword，所以当前 Shader 可以编译和运行，但 Package Source 明确提示旧 Keyword 可能增加无效编译成本。正式整理时应该把：

```hlsl
#pragma multi_compile _ _FORWARD_PLUS
```

更新为：

```hlsl
#pragma multi_compile _ _CLUSTER_LIGHT_LOOP
```

这也是为什么手写 URP Shader 不能只看几年前的教程：API 能编译不代表仍是当前版本推荐路径，必须对照本项目 Package Source。

**面试官追问：** 当前只有一个 `UniversalForward` Pass，会缺什么？

**面试者：**

当前只有 `WaterForward`，所以它能完成透明水面的主颜色渲染，但不是完整的 Lit Multi-pass Shader。它没有 `ShadowCaster`，不能按自己的水面形态正常写入 Shadow Map；没有 `DepthOnly/DepthNormals`，不会像 Opaque Lit 那样参与相应 Depth/Normal Prepass、SSAO 等路径；没有 `MotionVectors`，无法提供完整的物体/顶点运动向量；也没有 `Meta` Pass 支持标准 Lightmapping 烘焙导出。透明水未必需要所有 Pass，例如连续透明通常本来就不写普通 Depth，但每一项都应该由需求决定，而不是因为主 Pass 能显示就假设全部兼容。

**面试官追问：** 你使用了 `half` 和 `float`，依据是什么？

**面试者：**

颜色和部分 Lighting 数据可以使用 `half`，在移动 GPU 上可能降低寄存器和算术成本；但 World Position、Depth Difference、UV 经大 Scale 后的坐标、Derivative 和除法更需要 `float` 精度。Desktop GPU 上 half 可能仍以 32-bit 执行，不能假定一定加速。当前对 Position/Depth/Noise 核心多用 float，对 Color/部分 URP Surface 数据用 half，是保守划分。优化精度前要在目标平台检查视觉误差、Shader Compiler 输出和 GPU Profile。

**学习复盘：**

- SRP Batcher 优化 CPU Draw Submission，不是让 Fragment 数学“自动更快”。
- Keyword、Variant、普通 Property 的区别是 Unity Graphics 面试高频点。

## Q26 ⭐：这份水 Shader 的主要 GPU 成本在哪里？你会如何优化？

**面试官：** 不要泛泛说“减少计算”，按成本来源和验证顺序回答。

**面试者：**

我会先按频率看成本。Vertex Stage 很轻，主要瓶颈通常在 Fragment，因为水可能覆盖大量屏幕，而且是 Transparent，Overdraw 会让同一区域多次执行完整 Fragment。

单次水 Fragment 的主要成本包括：两层 Value Noise，每层查询四个 Hash 并做多次 Lerp；两次 Height-to-Normal，需要 `ddx/ddy`、Cross、Dot、Normalize；一次 Camera Depth Texture Sample 和线性化；一次 `pow` Fresnel；泡沫、颜色和 Alpha 的多次算术；最后还有 `UniversalFragmentPBR` 的主光、Additional Lights、Shadow、GI 与 Specular。真实最贵项会随平台、灯光数量、分辨率和水的屏幕覆盖变化，不能只靠数指令判断。

我的验证流程是固定 Camera、分辨率、灯光和场景，记录水开启/关闭的 GPU Frame Time；用 GPU Profiler 或平台工具看对应 Pass，用 Frame Debugger 确认 Draw 顺序和 Variant，用 Overdraw/Rendering Debugger 看覆盖。然后逐项做 A/B：关闭第二层 Noise、Normal、Depth Sample、Additional Lights/Shadow，判断时间变化。Frame Debugger 的 Draw Call 数不能代替 GPU 时间，CPU Profiler 的 `GC Alloc` 也不能衡量 Shader ALU。

优化按收益与画质风险从低到高进行：

1. 先控制水面屏幕覆盖和透明层交叠，减少 Overdraw；
2. 限制不必要的 Additional Lights 与 Shadow Variant；
3. 为低质量档关闭第二层 Noise、泡沫或逐像素附加灯；
4. 评估把程序化 Noise/Normal 烘焙为可平铺 Texture，以 Texture Bandwidth 换 ALU；
5. 对远处水使用简化 Shader/LOD，降低 Normal 和 Depth 细节；
6. 在验证精度后，把合适中间量从 float 降为 half；
7. 若水有大量不可见区域，调整 Mesh 形状，使几何更贴合实际水域，避免用大矩形 Plane 覆盖空区域。

**面试官追问：** 程序化 Noise 和 Texture Noise 哪个一定更快？

**面试者：**

没有一定答案。程序化 Noise 增加 ALU、寄存器和依赖链，但减少 Texture Fetch 和资源；Texture Noise 依赖 Texture Unit、Bandwidth、Cache 和采样精度，但现代 GPU 对纹理采样高度优化。移动 Tile-based GPU、桌面独显、不同分辨率和 Overdraw 下结论可能不同。应实现可比版本，在相同画面和目标设备上测量。当前选择程序化主要为了学习与资源独立，不把它包装成性能优势。

**面试官追问：** 为什么透明 Overdraw 特别危险？

**面试者：**

Opaque 通常能通过 Front-to-back 排序和 Early-Z 丢弃被遮挡 Fragment；透明为了正确 Blend 往往 Back-to-front、ZWrite Off，后画层仍需读取 Destination 并执行 Blend。多个透明水、粒子、雾叠加时，同一 Pixel 会重复运行昂贵 Shader。即使 Alpha 很低，也不代表 Fragment 免费。移动端 Fill Rate 与 Bandwidth 受限时，大面积半透明尤其敏感。

**学习复盘：**

- 性能题必须包含“成本清单、测量工具、A/B 方法、分级优化”。
- 不要没有数据就声称“零性能问题”或“程序化更快”。

## Q27 ⭐：如果水面效果错误或全黑/全白，你会怎样系统 Debug？说说真实遇到的问题。

**面试官：** 我不想听“多试几个参数”。给我一套可重复的方法。

**面试者：**

我会从 Pipeline 外层向内部信号逐层缩小范围，而不是同时猜颜色、Depth、Normal 和 Lighting。

第一层检查 Console/Editor.log 是否有 Shader Compile Error，Material 是否选择正确 Shader，Renderer、Camera Culling Mask 和 URP Renderer 是否正确。第二层用 Frame Debugger 确认 `WaterForward` Pass 是否执行、位于 Opaque 之后、Render Target 和 Variant 是什么，再检查 Queue、Blend、ZWrite、ZTest、Cull。第三层检查 Mesh 是否有有效 UV、Normal、Tangent，Transform 是否有异常负缩放。

接着把复杂输出逐个替换为 Debug Color，并暂时令 Alpha=1，避免背景混合干扰观察：先输出 `CombinedNoise.xxx`，确认静止图案与 Panning；再输出 `normalTS*0.5+0.5`；再输出 `depthMask.xxx` 并把 Shallow/Deep 设成黑白极值；Fresnel 只移动 Camera 验证角度；Foam 把颜色设纯白、Strength 设 1。一次只恢复一条链路。

实际开发中遇到过几类典型问题。Shader Graph 中没有找到 `Panner`，我没有继续搜节点，而是回到公式 `UV'=UV+Speed×Time`，用 `Time×Speed` 接到 `Tiling And Offset` 的 Offset。创建 `Range 0~1` 时也发现它不是独立 Property 类型，而是 Float 的 Slider Mode。Scene Depth Node Preview 一直白，是因为 Graph Preview 没有真实 Camera Depth，必须在 Scene/Game View 用不同高度的 Opaque 地面验证。

还有一次把“合并 Noise”误接成了包含 Depth 的最终 Saturate，导致泡沫信号被深度污染；修复方法是明确区分纯 `CombinedNoise=(A+B)×0.5` 和最终 `DepthMask`。设计 Custom Function 时还险些形成 `Wave Output → Normal From Height → Fresnel Input → 同一 Function` 的逻辑环，最后拆成 Waves 与 Surface 两个单向函数。迁移手写 Shader 后，补注释时补丁误删了 `half4 color = UniversalFragmentPBR(...)`；虽然没有主动改逻辑，但局部尾部复核发现 `color` 未声明，恢复后重新触发 Unity Import。这个问题说明“只改注释”也必须看 Diff 和编译结果。

**面试官追问：** 你分别在什么时候使用 Frame Debugger、Rendering Debugger、Profiler？

**面试者：**

Frame Debugger 回答“这一帧按什么顺序画了哪些 Pass、使用什么 Render Target/Keyword，某次 Draw 前后画面怎样变化”；Rendering Debugger 更适合查看 Pipeline Lighting、Material、Overdraw 等调试视图；Profiler/GPU Module 回答 CPU/GPU 时间分布；RenderDoc、PIX、Xcode GPU Frame Debugger 或厂商工具能继续查看资源绑定、Shader Invocation 和平台瓶颈。工具职责不同，不能用 Frame Debugger 看见 1 个 Draw 就断言这个 Pass 很便宜。

**学习复盘：**

- 面试官看重的是假设驱动、逐层隔离，而不是“我最后调好了”。
- 真实 Bug 复盘要包含现象、根因、修复和可复用经验。

# 第六组：架构边界、方案质疑与继续演进

## Q28 ⭐：这个视觉水面怎样与 Wet Gameplay 区域集成？未来你会怎样升级它？

**面试官：** 水不仅要看，还会让角色 Wet。你会让 Shader 直接控制状态吗？

**面试者：**

不会让 Shader 控制 Gameplay。Shader 在 GPU 上逐 Fragment 执行，职责是生成画面；Wet 的进入、持续、退出和元素反应属于 CPU Gameplay 规则，需要稳定碰撞体、状态数值和可测试逻辑。让 Gameplay 读取 Shader Pixel 或让 Shader 持有状态规则，会形成错误依赖，也很难处理网络、存档、AI 与无头测试。

我的设计是 Prefab 组合而不是代码互相引用：一个水域可以有不可见 Gameplay Child，挂 Trigger/`StatusVolume` 一类组件负责施加 Wet；另一个 Visual Child 使用 Water Mesh、Material 和当前 Shader。两者共享 Transform/Bounds，但职责独立。关闭 Visual Child 后状态区域仍工作，更换 Shader 不改变 Wet 数值；关闭 Gameplay Child 后可以只做装饰水。跨模块的角色状态表现遵守项目架构，由 `Game.Rendering` 订阅 `Game.Core` EventBus 中的状态事件，不让 `Game.Combat` 反向引用 Rendering。

截至当前，手写水 Shader 和 Material 原型已经完成，但与正式不可见 Buff Volume 的 Prefab 组装、Bounds 同步和 Play Mode Gate 仍属于 P2 Task 6 后续步骤。我在面试中会明确区分“Shader 已完成”和“正式水域 Prefab 集成待完成”，不会把计划当成果。

如果继续升级，我会按问题独立增量，而不是把所有能力塞进一个巨型 Shader：

- **Refraction**：开启/采样 Camera Opaque Texture，用动态 Normal 扰动 Screen UV；处理屏幕边缘越界、错误折射前景和额外 Texture Sample；
- **Absorption**：使用 Thickness 与 Beer-Lambert 做逐通道 Transmittance；
- **Reflection**：按场景选择 Reflection Probe、Planar Reflection 或 SSR，处理成本和缺失信息；
- **Geometry Wave**：近景使用 Gerstner Wave/Height Field 做 Vertex Displacement，并同步 Shadow/Depth；
- **Interactive Ripple**：用低分辨率 RenderTexture 保存扰动场，角色/投射物写入冲击，Shader 采样；
- **World-space Consistency**：从 UV Noise 改为 World XZ 或传入尺度，使不同水池保持统一波长；
- **Quality Tier**：桌面保留双层 Noise/Depth/Foam，移动端使用纹理 Normal、简化灯光和远景 LOD。

**面试官追问：** 如果只能选一个升级，你先做什么？

**面试者：**

我不会只按“效果最炫”选择，而先看游戏镜头与玩法。当前 RPG 强调元素交互，最有项目辨识度的可能是 Interactive Ripple 或状态反应视觉，因为它让水与玩家、法术产生反馈；如果纯粹提升材质可信度，Refraction 是直观增量，但会引入 Opaque Texture 和 Screen-space Artifact。正式决定前我会先建立性能预算和验收场景，用最小原型比较投入产出。

**面试官追问：** 最后用一段话总结这项实现体现了什么能力。

**面试者：**

这项实现体现的不只是我会写一个 Shader，而是我能从玩家看到的水面反向拆出透明、流动、微表面、深度、观察角和接触线，再把它们落实为 UV Panning、Value Noise、Fragment Derivative、TBN、Camera Depth、Fresnel 与 URP PBR 数据流；我能解释这些公式所在的 Coordinate Space、Render State 和性能成本，也能用中间 Mask、Frame Debugger 和 GPU Profiler 系统定位问题。在工程上，我把视觉与 Wet Gameplay Volume 分离，并且能诚实说明当前没有真实流体、Refraction、Beer-Lambert 和几何波浪。对我而言，项目价值是完成了一次从需求拆解、Graph 原型、手写 HLSL、Pipeline 集成、Debug 到演进规划的完整图形功能开发。
