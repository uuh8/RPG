## 0. 先建立心智模型

要理解这次迁移，先把“模拟用什么表示世界”和“玩家看见什么形状”拆开。**Simulation Discretization** 是让计算机用有限份数据近似连续世界的方式。现有 Legacy 方案把空间切成固定大小的 Cell；每个 Cell 保存 `ElementMaterialKind.Water` 与 `byte Amount`。这很适合火、水、固体的离散规则、稀疏 Chunk 和可预测的 Gameplay 查询，但水的最小移动步长、可停留位置和碰撞边界都被 Cell 网格锁定。

PBF 也不是“完全连续”的魔法：它同样离散，只是离散单位从“固定格子里的量”换成“可移动的粒子”。一个粒子至少有 Position、Velocity、Mass/Radius 等数值状态；Solver 在每个 Substep 用邻居粒子估算密度，再把过密的位置投影开。粒子是**数值离散点**，不是最终水面。

为了让玩家看到连续水体，Rendering 需要第三种表示：**Density Field**。它是在三维采样点上询问“附近粒子贡献的密度有多大”的 Scalar Field（每个位置只有一个数值）。把密度大于 Iso Level 的区域视作水体内部，小于它的区域视作空气，`Marching Cubes` 才能在两者交界处提取连续 Triangle Surface。可以把它理解为：粒子负责“水怎么动”，Density Field 负责“许多点合起来看像哪一团水”，Mesh 与 Shader 负责“这团水如何被光照和相机显示”。

```text
Simulation Truth                         Visual representation
Legacy: Cell(Material, Amount)    ->     CPU visual density / Surface Nets -> Mesh -> Shader
目标: GPU PBF Particle Buffer     ->     GPU Density Field -> Marching Cubes -> Indirect Draw -> Shader
```

这里的连续性是 **Visual Continuity**：表面轮廓和光照上不再逐格断裂；它不等于无限精度，也不自动保证物理真实。PBF 的稳定性、粒子半径、Smoothing Radius、Solver Iterations、Collision Proxy 与 Density Field 分辨率共同决定近似质量和成本。

## 当前 Legacy Runtime 链（源码阅读所得）

```text
Water Projectile 命中
-> ElementDepositOnImpact.TryBuildRequest / TryDepositAt
-> ElementRuntimeRegistry.ActiveSink : IElementWriteSink
-> ElementWorldRuntime.TryEnqueueWrite
-> ElementWriteQueue
-> Update 中 ElementFieldTickAccumulator.Consume(Time.deltaTime)
-> 每个固定 Tick：ElementWorld.ApplyWrites
-> ElementWorld.RebuildActivity
-> ElementWorld.Simulate
   -> PrepareNeighbors / Reaction / DownFlow / HorizontalFlow / FireDecay / Commit
-> ElementWorldWaterRenderer.Update
   -> SyncViews / 读取 IElementWorldReadOnly
   -> Dirty Version + 每帧 Rebuild Budget
   -> WorldWaterVolumeMeshBuilder（Visual Density、SDF、CPU Surface Nets）
   -> ElementWorldWater.RebuildChunk
   -> ElementWorldWater.UploadMesh -> Unity Mesh / ElementWater Shader
```

这条链有两个重要边界。第一，`ElementDepositOnImpact` 不直接写 Grid；Projectile 的 Physics 命中时刻和 ElementWorld 的固定 Tick 不同，写入先进入 Queue 才能以稳定顺序被集中消费。第二，`ElementWorldWaterRenderer` 只通过 `IElementWorldReadOnly` 读取；它可建 Mesh，但不允许反向修改 Water、Fire 或 Chunk。

`ElementWorldRuntime` 的 Inspector 已暴露 `ResidentChunkCount`、`ActiveChunkCount`、`SleepingChunkCount` 与 `ActiveElementCellCount`。它们分别回答“数据是否还存在”“是否在 Interest Region 内且要被 Solver 推进”“稳定但仍保留的数据有多少”“本轮活动元素量有多少”，不可混为一个“活跃水量”指标。稳定水进入 Solver-Sleeping 后仍必须对 Renderer 与 Gameplay 查询可读，否则会出现水一静止就消失的错误。

## Task 0：建立当前基线与唯一增量解析文档

### 1. 目的、现象与这次真正要替换的层

本 Task 的目的不是提前实现 PBF，而是先把“现在到底慢在哪里、方格感到底来自哪里、以后怎样公平比较”固定下来。玩家目前可能看到水弹命中后以约一个 Cell 为单位下落、横向摊开或形成阶梯轮廓；即使最终 Mesh 采用圆角、`Signed Distance Field (SDF)`、Visual Density Filter 与 `Surface Nets`，水量的产生、转移与停留仍来自 `ElementWorldSimulator` 对 `Water Cell / byte Amount` 的 Down Flow 与 Horizontal Flow。换言之，旧 Renderer 已经在努力把离散输入**画得更圆**，却没有改变水在模拟里只能按格移动的事实。

**Simulation Discretization** 解决“计算机怎样存储和推进水”：Legacy 是固定 Cell，目标 PBF 是移动粒子；它决定运动轨迹、惯性、碰撞和最小可分辨尺度。**Visual Continuity** 解决“相机看到的边界是否连续”：它可用 SDF、Density Field、Surface Nets、Marching Cubes、Normal 与透明材质实现；它决定轮廓、接缝和高光，但不能反向让 Cell 产生 Velocity、粒子邻居约束或连续碰撞。两者相关却不是同一层。

现有 `Surface Nets` 已解决了一个真实问题：从连续 Scalar/SDF 采样中抽出封闭 Mesh，避免直接给每个 Cell 画方块；Visual Density Filter 还能在不跨越 Solid 的条件下平滑相邻低量 Water 的**表现输入**。但它的输入依旧是 Cell Snapshot，且重建发生在 CPU，需要 Mesh Upload。PBF 真正替换的是 Water 的 Simulation Truth：每个 Water 写入以后生成/唤醒粒子，粒子在 GPU 上经 Density Constraint、Position Correction 与 Collision Projection 推进；不是只把旧 Mesh 换一种 Shader。

因此“只换 Shader”不足：Shader 的 Vertex/Fragment Stage 通常只接收已经存在的 Mesh、Buffer 或 Texture。它可以改变颜色、Fresnel、法线扰动、透明度和局部顶点外观，却不能替代 CPU Cell Solver 的状态转移，也不能凭空从没有连接关系的格状输入推导可控的飞溅、惯性与碰撞。若 Cell 输入本身是孤立的，Shader 甚至可能放大透明高光形成的碎点；若 Mesh 没有 Triangle，调 Alpha 更不会产生水面。正确迁移顺序是先替换 Simulation Truth，再用 Density Field 将粒子转换成适合 Extraction 的连续场，最后让 Shader 做材质表达。

### 4. Legacy 与目标 PBF 的职责边界

| 层 | Legacy 当前职责 | 目标 PBF 职责 | 不应发生的越界 |
|---|---|---|---|
| Gameplay 写入 | `ElementWriteRequest` 经 `IElementWriteSink` 进入 Queue | 入口仍只接收 Water 写入，按模式路由到 PBF Spawn Queue | Projectile/Pefab 直接写 Cell 或直接操作 GPU Buffer |
| Simulation Truth | CPU Water Cell、Amount、固定 Tick 转移 | GPU Particle Position/Velocity/Alive/MaterialId | CPU 再运行一套 Water Flow 与粒子结果竞争 |
| Surface construction | CPU Visual Density/SDF + Surface Nets + Mesh Upload | GPU Density Field + Marching Cubes + `Graphics.RenderPrimitivesIndirect` | Renderer 反向修改粒子或 Gameplay |
| Gameplay 查询 | Cell Water 参与 Wet/Fire | 低频 `AsyncGPUReadback` 生成的 Occupancy Snapshot | 每帧同步 `GetData()` / `WaitForCompletion()` |
| 回退 | 当前链完整保留 | `WaterSimulationMode.LegacyCell` 可恢复当前链 | 未验证 PBF 前删除 Legacy Renderer/Material |

**Density Field 与 Surface Nets 的关系。** Legacy Surface Nets 的输入是经过表现层处理的 Cell-centric Scalar/SDF；它已经能从正负符号变化附近放一个表面 Vertex 并连接为网格。目标 Density Field 的输入则是粒子与 Kernel：某采样点周围的粒子越多、越近，密度越高。两者都把“离散数据”转换为“连续标量场”，但输入的 Simulation Truth 不同；Task 0 的迁移目标是把后者放在 GPU，最终使用 Marching Cubes，以免把大量粒子/密度回读到 CPU 再上传 Mesh，抵消 GPU Solver 的收益。

## Task 1：建立 PBF 数据契约、Profile 与固定容量 Pure Logic

### 1. 本 Task 的目的、完成边界与玩家意义

Task 1 还没有让场景中的 Water 变成粒子，也没有创建 `GraphicsBuffer`、`ComputeShader`、碰撞或 Surface。它先把之后每一层都要共享的“量纲、容量和时间”固定成可测试的 Contract：Water 未来会由 `ElementWriteRequest.TotalAmount` 表示进入量，而 PBF GPU Pool 只接受明确的 `ParticleCount`；不稳定的 Rendering Frame 时间必须先转成有上限的固定 Tick；连续施法产生的 Spawn Command 必须先进入固定容量队列，不能在高峰期临时扩容。这样 Task 2 才可以只关心 CPU→GPU Upload 与生命周期，而 Task 4 的 PBF Solver 只关心预测位置、邻居和约束，不需要在热路径重新讨论 Inspector 参数或数组大小。

玩家最终会看到连续流动的水，但这一层并不把“更圆的画面”误当作流体模拟。它保护的是后续体验的下限：单次 Water 写入不会因为 `Amount` 除不尽而悄悄丢失尾数；卡顿时不会无限补跑导致恢复帧更慢；频繁水弹不会因为 `List` 扩容产生不可预测的 `GC Alloc`。当前新增代码仍只属于 `Game.ElementField`，未引用 `Game.Rendering`，也没有修改 Legacy Water、Projectile、Scene、Prefab 或任何现有写入入口；真实的 `ElementWriteRequest(Water) -> FluidSpawnRequest` 路由将在 Task 9 接入，不能把本 Task 的数据准备误说成场景功能已经完成。

### 2. 数据契约、Authoring Data 与 Runtime Snapshot

`WaterSimulationMode.cs` 定义 `LegacyCell = 0` 与 `GpuPbf = 1`。把已验证的 Legacy 保持为序列化默认值是一个兼容性选择：旧 Profile、缺少 Compute 支持或还未配置 PBF Runtime 的场景不会仅因枚举新增而意外切换真相来源。`FluidSpawnRequest.cs` 是 CPU 到未来 GPU Spawn Kernel 的 `readonly struct`，快照保存 World Position、Initial Velocity、Radius、Particle Count、Material Id、Seed 与 Flags；它描述一次命令，不持有 `MonoBehaviour`、Prefab 或 Renderer 引用。

`LiquidSimulationProfile.cs` 是可在 Inspector 编辑的 `ScriptableObject` Authoring Data，给出首轮起点：Particle Capacity 为 8192、Substeps 为 2、Solver Iterations 为 4。`LiquidSimulationSettings.cs` 则是在 Runtime 初始化边界由 `CreateSettings()` 生成的不可变值副本，完整包含 Capacity、Hash Capacity、Spawn 请求上限、Amount→Particle 比例、粒子/Density、Fixed Tick、Substep、Solver、PBF 稳定项、重力/速度、碰撞、Sleep 和 Catch-up 参数。这里的 **Snapshot** 不是复制一份资产来保存，而是让 Runtime 只保存普通值；Play Mode 中 Inspector 再改 Profile 不会让同一轮 GPU Solver 一半按旧密度、一半按新 Iteration。代价是调参后必须重新初始化 Runtime（首版要求退出再进入 Play Mode），换来确定的生命周期与零次每帧 SO 查询。

`Amount Units Per Particle` 是量化比例，不是“粒子质量”也不是“一个 Amount 永远对应一个粒子”。例如总量 21、每粒子代表 8 单位时，`ceil(21 / 8) = 3`；向上取整避免尾数 Water 消失，随后以 Profile 的固定 Pool 上限裁剪，避免单次命令请求超出 GPU 能表达的 Slot 数。以后低频 Occupancy Bridge 会反向用 `particleCount * amountUnitsPerParticle` 近似 Legacy Amount，因此它天然有一个粒子单位的量化误差边界，不能被描述成精确质量守恒。

### 3. 固定容量、Ring Buffer 与 Clock

`FluidCapacityPlanner.cs` 是 Unity-free Pure Math。它把请求 Particle Capacity 向上归一为 **Power-of-two**：例如 5000 变成 8192。Power-of-two 不是为了“更大就更快”的口号；GPU 的 Bitonic Sort、线程分组以及后续 Spatial Hash 更容易使用整齐的层级和位掩码，减少边界分支。代价是 5000 个预期粒子仍要预留 8192 个 Slot，显存会有空洞；本阶段选择一次性固定显存上界，而不是在 Gameplay 中 resize `GraphicsBuffer` 造成卡顿。Hash Table Capacity 进一步至少为 Particle Capacity 的两倍，降低桶冲突压力，并仍保留 Power-of-two 的 mask 优势。

`FluidSpawnQueue.cs` 是固定数组的 FIFO Ring Buffer。构造时只分配一次 `FluidSpawnRequest[]`；`TryEnqueue` 在满时返回 `false`，不扩容、不覆盖旧命令；`CopyAndClear` 以 FIFO 顺序复制到调用方长期 Upload Array 并归还队列 Slot。这个选择牺牲了“无上限地接收所有水弹”，却保证 Projectile 高峰下没有 `List` 扩容、Closure 或临时数组。未来 Runtime 需要把满队列和 GPU Free Slot 不足分别记为低频 Overflow 诊断，不能静默把水写回 Legacy Cell 作为假回退。

`FluidSimulationClock.cs` 使用 `double Accumulator` 把 Frame delta 转为固定 Tick 数：Fixed Tick 是一次完整 Simulation 时间步，Substep 是该 Tick 内为了数值稳定而继续切分的小步，Solver Iteration 则是在同一 Substep 内反复投影 Density Constraint 的次数，三者不可互换。当 10 Hz Clock 收到 0.45 秒长帧、Max Catch-up 为 3 时只执行 3 Tick，并丢弃剩余旧债务；这是用极端卡顿时少量时间完整性换取不发生 **Spiral of Death** 的 trade-off。`MaxSupportedCatchUpTicks = 8` 进一步把配置限制在可预期的单帧循环上界内，避免错误 Profile 写入 `int.MaxValue` 后，Clock 自己成为卡顿源；Settings 与 Profile 的初始化边界共用这个 Contract。Pause 不调用 Clock，因此没有“暂停期间积压、恢复后补跑”的隐藏 Debt。

## Task 2：GPU Buffer 生命周期、Spawn Kernel 与粒子 Debug Renderer

### 1. 目的、范围与这一步实际完成了什么

Task 2 把 Task 1 的数据 Contract 接到真实 GPU 资源，但它仍不是完整 `Position Based Fluids (PBF)`。`GpuPbfFluidRuntime` 在启动边界创建固定容量 Particle Pool，将所有 Slot 初始化为 inactive；固定 Tick 中把 CPU Queue 的 Spawn 命令上传，然后依序执行 `SpawnParticles -> ApplyGravity -> PredictPositions -> CommitPositions`。在接好场景和 Material 后，开发者应能看到圆盘粒子生成并受重力下落；暂停时不消费 Clock，恢复后不会补跑暂停期间的时间。

此阶段故意没有 Spatial Hash、邻居密度、Lambda、位置修正、碰撞投影或 Velocity Update。`PredictedPositions` 只是被 Commit 回 Position，不是被 Density Constraint 投影后的不可压缩液体。也就是说，这一步验证的是 GPU Pool、Buffer Layout、Compute Dispatch、显存释放和可视化观察窗口；不能把“粒子已在 GPU 上移动”表述为“PBF Solver 已完成”。

### 2. CPU Memory、VRAM、Count/Stride 与 SoA

托管数组存在 CPU RAM，适合固定 Queue 和小批 Upload；`GraphicsBuffer` 是 Unity 管理的 GPU/VRAM 资源，供 Compute Shader 与 Rendering 直接访问。`Count` 是元素数量，`Stride` 是单个元素的字节数，二者相乘决定资源大小。C# 与 HLSL 必须读取同一布局：`Vector4/float4` 是 16 bytes，`uint2` 是 8 bytes，Spawn Request 是两个 `float4` 加一个 `uint4` 的 48 bytes。若两端 Stride 不同，GPU 从第二个元素开始就会读取错误地址。

`FluidGpuResourceSet` 采用 **SoA (Structure of Arrays)**：Position、Velocity、Metadata 等分别在不同 Buffer。这样 Gravity Kernel 不必加载后续 Spatial Hash 才需要的字段；代价是所有 Kernel 必须以同一 particle index 访问多条 Buffer，并共同尊重 active flag。它的 `Dispose()` 不依赖 Finalizer：每个 `GraphicsBuffer` 在 `OnDisable`/`OnDestroy` 的同一幂等入口释放并置 `null`。Finalizer 的时机不可预测，不能当作 VRAM 生命周期方案。

| Buffer | 布局 / 容量 | 写者 | 读者 | 责任 |
|---|---|---|---|---|
| Positions、PredictedPositions、Velocities、DeltaPositions | `float4` / Particle Capacity | Initialize、Spawn、Gravity、Predict、Commit | Debug Shader；后续 PBF/Collision | Position.w 为 active 标记。 |
| DensityLambda、Metadata、SpatialEntries | `float2/uint2` / Particle Capacity | Initialize、Spawn | Lifecycle；后续 Hash/Density | Metadata.x=MaterialId，y=flags。 |
| CellRanges | `uint2` / Hash Capacity | Initialize；后续 Hash Build | 后续邻居查询 | Task 2 仅清空哨兵值。 |
| FreeIndices、Counters | `uint` | Initialize、Spawn | Spawn/Test-only Readback | 固定 Pool 的空闲 Slot 与 Free/Active/Dropped 计数。 |
| SpawnRequests | 48 bytes / Max Requests | CPU `SetData` | Spawn Kernel | Position/Radius、Velocity、Material/Seed/Flags/Count。 |

### 3. Compute Thread、Dispatch Group 与 Runtime 链

Compute Shader 不会“每粒子自动运行一次”。`[numthreads(64,1,1)]` 指定一个 **Thread Group** 有 64 个线程；C# 用 `ceil(count / 64)` Dispatch Group，末组由 Kernel 的 Capacity 判断裁掉越界线程。`InitializePool` 清空粒子与 Hash Buffer 并建立 Free Stack；`SpawnParticles` 用 `InterlockedCompareExchange` 原子地取得空闲 Slot，满 Pool 时只增加 Dropped Counter。Seed 与 Local Index 经纯 Hash 得到确定性球内采样；`UseLinearFalloff` 只改变新粒子的半径采样密度，不会改写旧粒子的 Metadata 或质量。

```text
LiquidSimulationProfile.CreateSettings（一次）
-> GpuPbfFluidRuntime：ResourceSet + Clock + 固定 Queue/Upload Array
-> InitializePool Dispatch：inactive Slot + Free Stack
-> TryEnqueueSpawn(in request)
-> Update（DefaultExecutionOrder -200，未暂停）
-> Clock.Consume -> Queue.CopyAndClear -> SetData 有效范围
-> Spawn -> 每个 Substep：Gravity -> Predict -> Commit
-> IFluidGpuSource.TryGetGpuSnapshot -> Debug Renderer（只读）
```

热路径不执行 `new`、LINQ、`Find` 或动态容器扩容。每帧只读取 `_simulationBoundsCenter.position` 和序列化 Size 形成 `ActiveBounds`；缺 Compute Support、Profile、Compute Shader、Bounds Center 或非正 Size 时，Runtime 使用 `GameLog` 仅诊断一次并禁用自身。它不注册 `IElementWriteSink`，所以并未改变 Legacy Water 的 simulation truth。

**D3D11.0 初始化边界（Fix Round 3）。** Unity 的真实 Shader import 指出一个 Compute Kernel 不能同时使用超过 8 个 RW UAV（Unordered Access View，GPU 可读写资源视图）；原始 `InitializePool` 同时清十条 Buffer，超过此上限。现在初始化严格分为两个有序 Dispatch：`InitializePool` 只清 Positions、Predicted、Velocities、DensityLambda、Metadata、Delta、SpatialEntries、FreeIndices，共 **8** 个 RW UAV；`InitializePoolAuxiliary` 再清 CellRanges 与 Counters，共 **2** 个。其余 Kernel 的静态 RW UAV 数为 Spawn=8、Gravity=2、Predict=4、Commit=3。C# 不再使用“把所有 Buffer 绑给每个 Kernel”的方便写法，因为 Buffer binding 是 per-kernel；这样同一 HLSL 在 D3D11.0 的资源上限内仍能表达完整初始化。`TryPopFreeIndex` 的无限 CAS 循环末尾还带有不可达 fallback return，这是给 D3D11 控制流分析器的完备路径证明，不改变 CAS 成功/失败语义。

### 4. `SV_VertexID` Billboard 与 Presentation 边界

`GpuFluidParticleDebugRenderer` 不会为每个粒子创建 GameObject 或 Mesh。一次 `Graphics.RenderPrimitives` 提交 `ParticleCapacity * 6` 顶点；Vertex Shader 用 `SV_VertexID / 6` 取粒子 Slot、用余数构成两个三角形。**Billboard** 使用 inverse View Matrix 的 camera right/up 在 world space 展开 quad，随后 `TransformWorldToHClip` 转入 Clip Space；inactive Slot 的 Position.w 为零，直接移出 Clip Space，避免透明 Fragment Overdraw。

长期复用的 `MaterialPropertyBlock` 每帧只更新 Positions Buffer、Bounds、Size 和 Color，因此不复制 Material Asset、也不在 Update 分配。该 URP Shader 是 Phase A/B 的透明圆盘 Debug 视图；它会产生 Overdraw，不能作为最终 Marching Cubes 水面质量或 GPU 预算的证据。正式 P7 Renderer 将读取 Density Field/Mesh Extraction，而非本 Shader。

## Task 3：GPU Spatial Hash、Bitonic Sort 与 27 邻域查询契约

### 1. 目的、已完成范围与玩家可见边界

Task 3 解决的是 PBF 在“每个粒子要找谁”这一层的规模问题，而不是提前计算 density、lambda 或位置修正。若有 `N` 个粒子，最直接的做法是让每个粒子遍历全部其他粒子，候选配对数量随 `N²` 增长：粒子数翻倍，比较量约变为四倍。这个算法在几十个粒子时很直观，却不能作为 2K、4K 或 8K 流体粒子的固定 Tick 路径。现在已把每个 active `PredictedPosition` 按正的 `SmoothingRadius h` 划入 **Uniform Grid**：PBF 后续只需要检查目标 cell 加周围 `3×3×3=27` 个 cell 的候选范围，而不是扫描整个 Pool。玩家不会仅因本 Task 立刻看到“更像水”的效果，因为 density constraint 仍属 Task 4；但这一步已经建立了后续让密集粒子稳定互相影响而不把 CPU/GPU 时间花在全局盲扫上的数据路径。

这里的 cell 是从 world position 除以 `h` 后做 `Floor` 得出的整数三维坐标。必须是 `Floor` 而不是 C# 的截断：`-0.01 / h` 应进入 `-1` cell，若错误地进入 `0`，负世界坐标附近的相邻粒子会在 CPU reference 与 GPU Kernel 之间分到不同桶。`ParticleCapacity` 与 `HashTableCapacity` 都沿用 Task 1 的 power-of-two 约束；前者使固定容量 Bitonic Sort 有定义，后者让 HLSL 用 `hash & (capacity - 1)` 代替 modulo。没有新增用户资产、Scene、Prefab 或 `.meta`，仍未接入 `IElementWriteSink`，也没有改变 Legacy Water 的 Simulation Truth。

### 2. Hash bucket 不是 cell：排序、Range 与二次过滤

`_SpatialEntries` 的每个元素继续是 8-byte `uint2(bucket, particleIndex)`，没有为了方便而把真实 `int3 cell` 塞进排序 entry。Fix Round 2 新增与 Pool 等长、16-byte 的 `_SpatialCells=int4(x,y,z,activeAtBuild)`：`BuildSpatialEntries` 同时记录每个 slot 的 `Floor(position/h)` 与 active 标记。active 粒子的 `bucket` 是该快照 cell 的确定性 hash；inactive Slot 使用 `uint.MaxValue`，因此按 `(bucket, particleIndex)` 的字典序排序后必然位于末尾。随后 `_CellRanges[bucket]` 保存半开区间 `[start, end)`：Clear Kernel 把所有桶设为 `(uint.MaxValue, 0)`，Build Kernel 对 `x` 使用 `InterlockedMin(start)`、对 `y` 使用 `InterlockedMax(sortedIndex + 1)`。这避免了两个 GPU thread 先读同一个 `uint2`、各自改一半再写回所造成的 read-modify-write 竞争。

Hash 只把无限多个真实 cell 映射进有限个 bucket，所以 **hash collision 不等于粒子碰撞，也不等于两个粒子在同一 cell**。某个 bucket 的 `[start,end)` 只是候选列表；PBF、Surface Density 或测试必须用该 `particleIndex` 的 `_SpatialCells` 与目标 build-time `int3 cell` 比较，排除 collision。关键点是它**不能**在 PBF Apply 后重新 `Floor(PredictedPosition/h)`：Range 是本 Substep 开始时按旧 cell 排出的，位置迭代跨过 cell 边界后再用当前 cell 查旧 Range，会把 self/邻居错误丢成零 density。距离仍从当前 `PredictedPosition` 重算并经 Kernel 支持域过滤，所以固定的是“候选归属”，不是物理距离。

### 3. Bitonic Stage/Pass 与 GPU 执行顺序

Bitonic Sort 不是一次 Dispatch 就完成。容量为 8 时，CPU Pure Helper 给出的固定序列是 `(Stage, Pass) = (2,1)、(4,2)、(4,1)、(8,4)、(8,2)、(8,1)`；一般 `log₂(N)` 层的总 Dispatch 数为 `log₂(N) × (log₂(N)+1) / 2`。Runtime 在 `Awake/OnEnable` 初始化边界缓存四个 Spatial Hash Kernel ID 和全部 `Shader.PropertyToID`，随后每个 Substep 严格提交：`Gravity -> Predict -> BuildSpatialEntries -> BitonicSort 的全部 Stage/Pass -> ClearCellRanges -> BuildCellRanges -> Commit`。这保证后续约束读取的是当前预测位置的已排序数据，而本 Task 不会假装执行尚未实现的 density/lambda。

GPU thread 没有固定的逐粒子执行顺序。每个 Bitonic compare-swap 只允许较小 index 的 thread 写入这一对槽位，避免同一地址有两个 writer；每个 Pass 单独 Dispatch，前一 Pass 的结果才会成为下一 Pass 的完整输入。所有 Kernel 对 `ParticleCapacity` 或 `HashTableCapacity` 做 bounds guard。Runtime 热路径没有 `FindKernel`、字符串属性查找、`new`、LINQ、closure 或同步 `GraphicsBuffer.GetData()`；`GpuFluid.SpatialHash.Build`、`GpuFluid.SpatialHash.Sort`、`GpuFluid.SpatialHash.Ranges` 是共享常量名的 CPU Submission `ProfilerMarker`，也是三个 GPU `CommandBuffer.BeginSample/EndSample` 的 Sample 名。三个 CommandBuffer 在 `Awake/OnEnable` 的初始化边界各录制一次完整的 `SetCompute*`、per-kernel `SetComputeBufferParam` 与固定容量 Dispatch：Build 录一条、Sort 录全部 Stage/Pass、Ranges 录 Clear+Build。每个 Substep 只执行已录制命令，不会重新 `new`、`Clear` 或录制；顺序保持 `Predict immediate -> Build CB -> Sort CB -> Ranges CB -> Commit immediate`。`OnDisable/OnDestroy` 先幂等 `Release` 三个 CommandBuffer 再释放 GraphicsBuffer，因此 re-enable 会用新资源重新录制。GPU Sample 已存在于命令流，但 GPU Profiler 的实际耗时仍须在 Editor 中实测，不能把 Sample 名称当成性能数据。

## Task 4：PBF Density Constraint、Position Correction 与速度更新

### 1. 目的、直觉与本 Task 的完成边界

本 Task 把 Task 3 的“谁可能是邻居”变成“过密粒子怎样互相推开”。`Position Based Dynamics (PBD)` 的直觉不是先求一个精确的压力力再积分，而是先按已有速度得到一个 **Predicted Position**，再问这个暂定位置是否违反约束；若违反，就把位置投影回较合理的状态。`Position Based Fluids (PBF)` 把约束具体化为 Density：每个粒子将 `Smoothing Radius h` 内的 Poly6 权重相加，得到 Density；它相对 `Rest Density` 偏高，表示这一区域“装下的水太多”，需要迭代位置修正。玩家最终会看到水团比单纯 Gravity/Commit 更能保持体积、不会轻易塌成一串独立粒子；但 Task 4 不包含 Collider Projection（Task 5）、Density Field 或最终水面，因此不能把它称为完整可玩的水体。

本 Task 没有新增模型、纹理、VFX、音频、字体、Prefab 或 Scene 资产，也不接入 `IElementWriteSink`。唯一新增的 Inspector 依赖是 `GpuPbfFluidRuntime` 上的 `PbfSolver.compute` 引用；若未赋值，Runtime 在初始化边界用一次 `GameLog.Warn` 禁用自身，而不会在 Update 中反复报错。

### 2. Kernel、Lambda 与两阶段位置提交

`PbfKernelMath` 是 `Game.ElementField` 的 CPU reference，锁定 3D Poly6：`315/(64πh^9) * (h²-r²)^3`，以及 3D Spiky Gradient：`-45/(πh^6) * (h-r)^2 * rHat`。当 `r≈0` 时 `rHat` 没有方向，所以 CPU/HLSL 都返回零向量；当 `r>=h` 时两者均不贡献。这样两个完全重合的粒子不会因“除以零方向”写出 NaN。`Lambda = -C/(Σ|∇C|² + Epsilon)`，其中 `C=Density/RestDensity-1`；`Lambda Epsilon` 是孤立粒子 Gradient 全为零时仍保证有限除法的下限。

每次 Solver Iteration 的顺序严格为 `ComputeDensityLambda -> ComputeDeltaPosition -> ApplyDeltaPosition`。第二段只能读取这一轮的 `PredictedPositions`，把本粒子的总修正写入私有 `DeltaPositions[index]`；第三段才统一提交，因此没有两个 GPU thread 一边读邻居、一边改邻居 Position 的 race。Spatial Hash 在每个 Substep 的 Predict 后只 build 一次；`SpatialCells` 固定本次 Build 的中心/候选 cell，查询不再被 Apply 后的当前 cell 漂移破坏，而距离仍使用当前预测位置。`Maximum Position Correction` 是 Profile Snapshot 的正且有限数据项，默认 `0.08`；创建 Settings 时还要求小于 `h`，Inspector 会限制到 `0.5h`，防止单步跨越整个支持域。Apply 发现 NaN/Infinity 时写零并原子累计 `NumericalErrorCounterIndex=3`；否则 Clamp 单粒子修正长度。`Artificial Pressure` 使用有界 `sCorr=-k*clamp(W(r)/W(0.3h),0,1)^4`，在近距离提供有限排斥，减少 clumping，又不让分母极小把 correction 放大成爆炸值。

### 3. Velocity、XSPH、Vorticity 与固定 Tick 链

位置迭代完成后，基础 Velocity 必须从 **校正后** 的预测位置反推：`(PredictedPosition - OldPosition) / dt`；如果仍沿用 Gravity 前的 Velocity，PBF 刚做的体积修正会在下一 Tick 丢失。`XSPH` 是速度平滑：它读取同一份旧 Velocity 与当前 Density，按标准 `viscosity * (m_j/rho_j) * (v_j-v_i) * W` 写入 `DeltaVelocities`，再由 `ApplyDeltaVelocities` 写回；`rho_j` 非有限或小于 epsilon 时跳过，避免除零。Profile 把 XSPH Viscosity 限为 `[0,1]`，使它仍是有界平滑系数。`Vorticity` 用同一 `m_j/rho_j` 权重计算 curl，`eta` 使用 `(absOmegaJ-absOmegaI)` 的局部差分而不是绝对量累加，也按 `Vorticities -> DeltaVelocities -> ApplyDeltaVelocities` 两阶段执行。Profile 的 Viscosity/Vorticity 为零时 Runtime 完全跳过对应 Dispatch；最后统一 Clamp `MaxSpeed`，再调用既有 `CommitPositions`。

运行链现在是：`Clock.Consume -> 每个 Fixed Tick Upload Spawn -> 每个 Substep Gravity -> Predict -> Spatial Hash -> N 次 PBF 三 Kernel -> UpdateVelocity -> optional XSPH -> optional Vorticity -> ClampVelocity -> Commit`。`Fixed Tick Rate / Substeps / Solver Iterations` 分别控制每秒逻辑步数、每个 Tick 的时间切片和每个切片中“拉回约束”的次数；Clock 的 Max Catch-up 和 dropped debt 仍由 Task 1 的固定 Clock 保留，Task 4 没有加入 per-frame 字符串、日志、`new` 或 LINQ。Task 5 的 Collision Projection 预留在 Apply 后、下一次 Iteration 前。

### 5. Fix Round 3：free-stack slot 与数值 oracle 的索引 Contract

GPU Pool 的 active particle 由 free-stack 分配和回收，`activeCount` 只表示数量，绝不表示 active 数据位于数组前缀。新增的 capacity=4、仅 slot 1/3 active 回归先验证 `SetUniformActiveDensity` 只写这两个 metadata active slot；随后让真实 PBF Density Dispatch 与 CPU brute-force Poly6 对照平均误差，并故意破坏高位 slot 3 的 GPU Density，要求 oracle 检出差异。为保证这个测试不是连续 slot 的偶然通过，`ReadBruteForceAverageDensityError`、`AssertGpuDensityMatchesBruteForce` 与 `SetUniformActiveDensity` 都完整读取 `Metadata` 后按 `ActiveFlag` 迭代，`activeCount` 仅作平均值除数。两套强制注入 `Rebuild` 已以 0 warning/0 error 编译这些修改；Unity Test Runner、PbfSolver Compute import 与真实 GPU Dispatch 仍需在 Editor 执行，不能由该静态编译代替。

## Task 5：Box/Sphere/Capsule Collider Proxy 与稳定性 Gate

### 1. 目的、玩家现象与本 Task 的完成边界

Task 4 已能让粒子在邻居之间维持密度，却还不知道地面、墙壁或容器存在：Gravity 会继续把 Predicted Position 推过几何体，PBF Density Correction 也只处理“水和水太挤”，不会自动处理“水和墙重叠”。本 Task 因此增加第二类 `Position Constraint`：每次 Density 的 `ApplyDeltaPosition` 之后，把进入固体禁止区域的粒子中心投影回可行区域；位置迭代全部结束后，再把碰撞法向写入速度，表现出停止、滑动、摩擦或有限反弹。玩家最终应能看到水撞上水平地面、旋转挡板、Sphere 与 Capsule 障碍后留在外侧，而不是穿透；但是本 Task 仍只生成粒子状态，没有 Density Field、Marching Cubes 与正式水面，不能把它称为最终视觉流体。

源码已覆盖显式 `FluidColliderAuthoring`、64-byte GPU Proxy、固定容量 Collector、Box/Sphere/Capsule Projection、Collision Velocity Response 与四类 120-tick GPU fixture。当前只取得 C# 强制注入编译证据；Unity Editor 尚未导入 `PbfCollision.compute`，真实 GPU Test Runner、Phase B 长时间 Sandbox、PlayMode、Profiler 与穿透统计均未取得。本 Task 不需要外部模型、纹理、VFX、音频、字体、Prefab 或 Scene 资产；Editor 后续只需用 Unity Primitive Collider 构造 Sandbox。`MeshCollider` 明确被过滤，P7 Scene 也未被修改。

### 2. World Space、Shape Local Space、矩阵与 64-byte Proxy

`World Space` 是整个 Scene 共用的坐标系；粒子的 Position、Gravity 和 Velocity 都在这里。Box 的“左、上、前”却会随 Transform Rotation 变化，直接在 World Space 写六个面的判断很容易把 45° 墙当作未旋转墙。因此每个 Proxy 保存三行 `World-to-Shape` 仿射矩阵：每行 `float4`，前三项描述旋转 Basis，第四项描述平移；把 `float4(worldPoint, 1)` 分别与三行点乘，就得到以 Collider 中心为原点的 `Shape Local Space`。在这个空间内，OBB 又变回轴对齐 Box，Capsule 的长轴也统一为 Local Y，GPU 只需维护一套简单公式。

三行矩阵占 48 bytes，`float3 Parameters` 占 12 bytes，最后的 `uint Shape` 占 4 bytes，总计固定 64 bytes。`FluidColliderProxyTests` 与 `FluidGpuLayoutContractTests` 同时用 `Marshal.SizeOf` 和真实 `GraphicsBuffer.stride` 锁住它；只改 C# 字段而不改 HLSL 会立刻把显存解释错位。这里故意把 Scale 烘焙为 World-meter 参数，而矩阵只保留 Rotation/Translation：Box 参数是乘过绝对 `lossyScale` 的 Half Extents；Sphere Radius 乘三个缩放轴的最大值，避免非均匀 Scale 下几何保护范围变小；Capsule 根据 `Collider.direction` 找出轴向 Scale 与两个垂直轴的最大 Scale，再保存 World Radius 与圆柱轴的 Half Segment。若父子层级混合非均匀 Scale 与 Rotation，会产生严格 OBB 无法表达的 `Shear`，首版使用 `lossyScale + rotation` 的保守近似；需要精确任意仿射边界时应改用 SDF/Voxelization，而不是假装 64-byte Primitive Proxy 能完整表达它。

`Minkowski Expansion` 可以用一个初学者直觉理解：GPU 没有拿“有半径的小球粒子”去和原始 Collider 做复杂相交，而是先把固体边界向外扩张一个 `ParticleRadius`，再把粒子中心当作点。Box 的三轴 Half Extents 都加 Radius，Sphere/Capsule 的 Radius 也加 Particle Radius；只要点落在扩张后的固体内部，就沿最近退出方向推到表面。这样投影后的粒子中心与真实固体表面至少相隔自身半径，不会只把中心推到墙面而让半个粒子仍埋在墙里。

### 3. 显式收集、无 GC 热路径与 Runtime Collision 链

`FluidColliderProxyCollector` 只在初始化时对配置的 `_fluidColliderRoot` 调用一次 `GetComponentsInChildren<FluidColliderAuthoring>(true)`。这次 Unity API 返回数组会分配，但它处于初始化边界；Collector 随后把 Authoring、受支持 Collider、Proxy、上次 Matrix 与 Dirty Version 压入预分配的固定数组，Fixed Tick 不再调用 `FindObjectsByType`、层级扫描、LINQ、Closure 或临时数组。未挂 `FluidColliderAuthoring` 的普通 Physics Collider 完全不进入 GPU；MeshCollider 等不支持 Shape 不占 Slot。Box/Sphere/Capsule 即使初始化时 Authoring Disabled、GameObject Inactive、Trigger 或 Collider Disabled，也先按层级顺序占据稳定 Slot，只把 Proxy 写成 invalid Shape sentinel；以后 Enable/Activate/关闭 Trigger 并 `MarkDirty()` 时可在原 Index 变为有效。`MaxFluidColliders` 与 Overflow 因而按“显式且受支持的 Authoring”计数，不会因初始可用状态不同而让后续对象换 Index。

Static Proxy 初始化后不比较 Transform，避免 64 个静态地面每 Tick 重建；Dynamic Proxy 才比较 `localToWorldMatrix`。Collider Size/Center 等序列化参数改变时没有可靠的通用 Transform 信号，因此 Authoring 提供 `MarkDirty()`：Dynamic Transform 变化或任意 Authoring Dirty Version 变化时，只重建固定数组中的对应槽位，再把同一个数组上传到长期存在的 `ColliderProxies` Buffer。组件 Disable 后槽位不会压缩，而是写入 GPU 可跳过的 invalid Shape sentinel，保持其他 Proxy Index 稳定。这是 CPU 管理少量 Scene Boundary、GPU 并行处理大量粒子的分工；若对每个粒子调用 `Physics.ComputePenetration` 或 `Collider.ClosestPoint`，8K 粒子乘 64 Collider 既回到 CPU 主线程成本，也会破坏当前 GPU Simulation Truth。

每个 Substep 的执行顺序现在是：

```text
Refresh/Upload changed Collider Proxy（每 Fixed Tick，只有 Dirty 才上传）
-> ClearCollisionContacts
-> Gravity -> Predict -> Build Spatial Hash
-> 每次 Solver Iteration：DensityLambda -> DeltaPosition -> ApplyDeltaPosition
                             -> ProjectCollisions
-> UpdateVelocities = (corrected predicted - old position) / dt
-> optional XSPH -> optional Vorticity
-> ApplyCollisionVelocities -> ClampVelocities -> CommitPositions
```

Collision Position Projection 必须放在每次 PBF Apply 后，否则最后一次 Density Correction 仍可能把粒子推回墙内；Velocity Response 则放在 `UpdateVelocities`、XSPH 与 Vorticity 全部结束之后、Clamp 之前。原因是这三者都会写 Velocity：放在 Update 前会被位置反推覆盖，放在 XSPH/Vorticity 前又可能被邻居平滑或旋涡力重新写入朝墙内的 Normal 分量。这里只执行一次，避免两次 Response 把 Tangent Friction 重复相乘而过度耗散。

每粒子的 `CollisionContactManifold` 不是一个“法向和”，而是四个独立 `float4 Contact`，固定 64 bytes；xyz 保存归一化 World Normal，w 是 active flag。墙角的 +X/+Y 必须分别限制速度，相反的 +X/-X 也必须保留为两个约束，若先相加会错误地得到零向量。Project 按 Collider/Iteration 顺序插入第一个空 Slot，同方向（dot ≥ 0.9995）复用，超过四个方向时确定性保留最先四个且不把容量边界记为 Numerical Error。Velocity 逐 Contact 拆成 Normal/Tangent：inward Normal 按 Restitution 反向，Tangent 乘 `1-Friction`；随后执行固定八轮零 Restitution 半空间投影。若极端非正交组合仍有任一 `dot(v,n)<-epsilon`，安全退化为零速度，因此每个已存 Normal 都是最终 Gate；相反法向是合法约束，不增加 Numerical Error Counter。`PbfCollision.compute` 的 RW UAV 数仍为 Clear=1、Project=3、Velocity=2，Contact 在 Velocity Kernel 通过单独的 read-only SRV 名称读取，均低于 D3D11 每 Kernel 8 个 UAV 的上限。

Endpoint Projection 还会有 `Tunneling`：若上一位置在薄墙左侧、Predicted Position 一步到了右侧，两端都“不在墙内”，只检查终点就会漏掉中间穿越。现在每个 Proxy 先把 `_Positions` 的 Old Position 到当前 Predicted Position 看成一条 Swept Segment，按不大于 Particle Radius 的间隔做最多 32 次固定采样；第一次进入 Minkowski-expanded Shape 后，再做 6 次 Bisection（二分搜索）逼近进入时刻 `Time of Impact (TOI)`，把粒子停在入口面外一个很小的 Skin。Box/Sphere/Capsule 统一复用各自 expanded-shape inside/projection 公式。固定上限避免一个恶意速度让单线程无限循环；Settings 同时强制 `MaxSpeed*SubstepDt + SolverIterations*MaximumPositionCorrection <= 32*ParticleRadius`，所以合法 Runtime 参数不会因达到 32 次上限而把采样间隔放大。Dynamic Collider 自身高速扫过粒子的 CCD 仍不在本阶段，它只覆盖静态/本 Substep 视为静态的 Proxy 与粒子 Segment。

当前是**单向耦合**：Collider 改变粒子，粒子不会给 Rigidbody 施加反作用力。这适合静态世界、机关与由 Gameplay 驱动的挡板，成本可控且确定性更强。**双向耦合**还需把每粒子的冲量按 Collider/Rigidbody 聚合，再异步或同步回 CPU Physics，并解决一帧延迟、所有权与线程同步；不属于首版。MeshCollider 也没有简单的固定 64-byte解析距离公式：GPU 通常需要把 Mesh 预烘焙成 `Signed Distance Field (SDF)` 或 Voxel Grid，才能对任意点高效查询 Distance/Gradient。首版拒绝 MeshCollider 是明确的性能/能力边界，不是漏写一个 `switch` 分支。

### 5. Fix Round 1：稳定 Slot、Contact Manifold 与 Swept Collision

### 6. Fix Round 2：Expanded Surface 起点的方向判定

Fix Round 1 的 Sweep 仍有一个边界短路：`IsInsideExpandedShape` 把“恰好在表面”也视为 inside，旧代码见 start inside 就退出 Sweep。若薄 Box 的 expanded left face 是 `x=-0.11`，粒子 Old Position 恰为 `-0.11`、Predicted 一步到 `+1`，Endpoint 仍在另一侧外部，于是 Sweep 与 Endpoint Projection 都不处理，产生 Surface-start Tunneling。这里不能只把 `<=` 偷换成 `<`：浮点误差可能让同一几何边界在不同 Shape/Graphics API 上落到两侧，而且 Deep-inside 与 Boundary 的物理含义本来不同。

新逻辑先调用对应 Shape 的 Projection 得到 `startProjected/startNormal`，用 `length(startProjected-start)` 与 `1e-5` Boundary Epsilon 区分状态。Boundary 且 `dot(segment,startNormal)<0` 表示沿 outward normal 的反方向进入 Solid，立即把目标设为 `start surface + normal*CCD skin` 并登记 Contact；Boundary 且点积非负表示向外离开，允许运动。Deep-inside 则交给当前 Endpoint Projection 选择最近退出面。Sphere/Capsule 的 Projection 用 `distanceSquared > expandedRadiusSquared` 才判外部，所以“等于表面”能返回合法 Contact；Box 原本已覆盖等号。非 Sweep 的 Endpoint-inside Projection 也统一增加 Skin，降低下一 Tick 在等号附近反复翻转的概率。

Fix2 先新增真实 GPU fixture：0.02m Thin Box、Particle Radius 0.1m，Old 精确位于 expanded surface `x=-0.11`，Predicted 为 `x=+1`，期望被保留在约 `-0.1101`。旧 HLSL 按控制流必然漏过；但当前没有可调用的 Unity Test Runner，所以只取得测试先写与 C# 编译证据，不能声称实际 GPU RED。修改 Kernel 后，Production/Tests 两套强制注入 Rebuild 均为 Exit 0、0 warning、0 error；UAV 仍为 Clear=1、Project=3、Velocity=2。PbfCollision importer 与该 fixture 的数值 GREEN 继续待 Editor。

## Task 6：Isotropic Density Field 与 Surface Grid 资源

### 1. 目的、玩家最终会看到什么，以及“连续密度仍要离散采样”的基础矛盾

Task 5 结束时，GPU 已经保存会流动、维持密度并避开 Primitive Collider 的粒子，但直接把每个粒子画成 Sphere/Billboard 只会得到一串珠子，无法出现参考视频里连成整体、带连续轮廓与高光的水团。本 Task 新增中间表示 `Density Field`：对于空间中的任意一点，遍历其 Kernel Support 内的粒子，把每个粒子的质量乘 `Poly6 Kernel` 权重后求和，得到一个标量 Density。离粒子越近贡献越大，达到 Smoothing Radius 时贡献平滑归零；多个粒子的贡献可以叠加。因此它不是“某个粒子属于哪一个水面三角形”，而是在空间中形成一座座会重叠的平滑密度山。Task 7 再用 `Iso Level` 切出“密度等于某个阈值”的等值面，才能把大量离散粒子连接成一张 Triangle Surface。

`Scalar Field` 的 Scalar 表示每个位置只有一个数值，而不是 Position/Velocity 那样的 Vector。数学上我们可以把 `density(worldPosition)` 想象成对连续位置都能求值的函数，但 GPU 不可能保存无限多个世界坐标，因此要在规则的三维 `Lattice`（采样点阵）上取有限样本。`Voxel` 常被直觉地理解为三维 Pixel，不过这里要严格区分：`Resolution=(Nx,Ny,Nz)` 表示 Lattice Sample 数；相邻八个 Sample 围成一个 Voxel Cell，所以 Cell 数是 `(Nx-1)*(Ny-1)*(Nz-1)`。如果某轴只有一个 Sample，它既没有间距也围不出 Cell，Planner 因而强制每轴至少 2 个 Sample。

离散采样不等于画面一定离散。它更像用有限像素保存一条连续曲线：只要采样间距足够小，之后在相邻 Sample 之间做插值，就能重建视觉上连续的边界。`Nyquist` 的完整理论针对带限信号，但这里可以先记住一个工程直觉：若水面最细的变化尺度小于约两个采样间距，Lattice 就没有足够信息描述它，结果可能被抹平、断开或产生跳动；提高 Resolution 能保留更细的水滴和薄片，却会同时增加 Density Dispatch、3D Texture 显存和下一步 Marching Cubes Cell 数。三轴都扩大 2 倍时，Sample 总数约扩大 8 倍，这就是“分辨率立方成本”，不能把 2D Texture 的平方成本直接套用到 3D。

本 Task 完成的是源码与 C# Contract，不是最终可见水面：`FluidDensity.compute` 只写 R32 Float 3D Texture，尚未执行 Marching Cubes、Indirect Draw 或正式 Water Shader。没有新增外部模型、贴图、Normal Map、VFX、音频、字体、Prefab、Material 或 Scene 依赖，也没有修改用户已有的 P7 Scene。

### 2. Bounds、Padding、Resolution、实际 Voxel Size 与 World-to-Grid Mapping

`FluidSurfaceGridPlanner` 从 Interest/Active `Bounds` 建立 Lattice。先在六个方向扩张 `BoundsPadding`，让靠近可见区域边缘的粒子 Kernel 仍有样本空间；`WorldOrigin` 是扩张后最小角，也就是 Texture sample `(0,0,0)` 的世界坐标。每个 sample 的映射是：

```text
worldPosition = WorldOrigin + int3(x, y, z) * ActualVoxelSize
```

反向理解时，`(worldPosition-WorldOrigin)/ActualVoxelSize` 得到连续 Grid 坐标；Texture 的整数 index 则对应明确 Sample。负世界坐标不会改变这套映射，但 Spatial Hash 的 cell 必须用 `floor(position/h)`：例如 `-0.01/h` 属于 cell -1，若用 C#/HLSL 的整数截断会错误落到 cell 0，Density Gather 就可能漏邻居。

目标 Resolution 不是简单的 `size/voxel`。每轴先计算 `ceil(paddedSize/TargetVoxelSize)+1`：Ceiling 保证至少有足够 Cell 覆盖完整 Bounds，额外的 `+1` 把 Cell 数转成 Sample 数。若结果超过 `MaximumResolutionPerAxis`，就 Clamp Sample 数，再用 `paddedSize/(resolution-1)` 反算三轴各自的实际 `Vector3 VoxelSize`。这样最后一个 Sample 始终精确位于 Bounds Max，而不是把尾部世界空间裁掉；代价是达到上限后某一轴实际间距可能大于目标值，表面细节会变粗。

Planner 对 Bounds Center/Size、Target Voxel、Padding、Iso Level 做 NaN/Infinity/零值验证，并在 `SampleCount`、`CellCount`、每 Cell 最多五 Triangle 与 96-byte Triangle Buffer 容量乘法前先转 `long`、使用 `checked`。这不是为了真的分配数十亿 Texture，而是让错误 Profile 在纯 CPU 初始化边界确定地抛出，而不是先发生 `int` 回绕再用负 Count 调 Unity Native API。`FluidSurfaceGridSettings.IsResourceCompatibleWith` 刻意忽略 Origin，只比较 Resolution、实际 Voxel Size 与 Maximum Triangle Count：相同大小的 Bounds 纯平移时，Texture/Buffer 的形状没有改变，只需更新 WorldOrigin，不应触发昂贵的 VRAM 释放与重分配；Bounds 大小或 Profile Resolution/Capacity 改变时才返回不兼容。

`LiquidRenderProfile` 是 Presentation `ScriptableObject`，保存 Target Voxel Size、每轴最大 Resolution、Padding、Iso Level 与 Maximum Triangle Count；`CreateSettings()` 生成不可变 `LiquidRenderSettings` Snapshot。Runtime 应只在初始化/重新进入 Play Mode 时取得一次 Snapshot：若 Inspector 在运行中把 Voxel Size 改了一半，却只改 Dispatch 参数而没有同步重建 Texture/Buffer，Resolution 与资源容量会互相矛盾。因此当前 Contract 明确不热更新 Profile；已有 Snapshot 不会随 Asset 后续编辑而改变。

### 3. R32 3D Texture、Buffer 生命周期与 Isotropic Density Gather

`FluidSurfaceGpuResources` 在构造边界先检查 `supports3DRenderTextures`、每轴不超过 `SystemInfo.maxTexture3DSize`，以及 `GraphicsFormat.R32_SFloat` 是否支持 `GraphicsFormatUsage.LoadStore`。Density Texture 使用 `RenderTextureDescriptor`：X/Y 分别进入 width/height，Z 进入 `volumeDepth`，`dimension=Tex3D`，`graphicsFormat=R32_SFloat`，无 Depth、无 MSAA、无 Mip，并在 `Create()` 前启用 `enableRandomWrite`。`R32` 表示每个 Sample 只有一个 32-bit Float，正好保存 Scalar Density；若错误使用 RGBA Float，显存会无意义扩大约四倍。`Create()` 返回 false 会立即销毁临时 Texture 并抛错，不会把“有 C# 对象但没有底层 GPU Resource”当成初始化成功。

同一资源所有者还按 Task 7/8 的固定 Contract 预分配：每 Triangle 96 bytes 的 Structured Buffer、显式 uint Triangle Counter、显式 uint Overflow Counter、`GraphicsBuffer.Target.IndirectArguments` 且 stride 为 `GraphicsBuffer.IndirectDrawArgs.size=16` 的 Args Buffer，以及每粒子 64 bytes 的 Anisotropy Buffer。Counter 是普通 Structured Buffer，不使用 Append/CopyCount；Task 7 会用独立 Kernel 把 Triangle Counter 转成 Indirect Args。所有资源在构造半途失败时进入同一个 Dispose，`OnDisable/OnDestroy` 也可重复 Dispose；3D Texture 显式 `Release` 并 Destroy，GraphicsBuffer Dispose 后立即置 null，避免显存依赖 Finalizer。Bounds 纯平移只调用 `TryUpdateGrid` 更新设置，不创建 Texture/Buffer。

`FluidDensity.compute` 的一个 `[numthreads(4,4,4)]` thread 对应一个 Lattice Sample，直接覆盖 `_DensityTexture[id]`，所以无需先 Clear，也没有多个 Thread 写同一 texel 的 Race Condition。Thread 先计算 World Position，再用 `floor(world/h)` 找中心 Spatial Cell，遍历 3×3×3 共 27 个相邻 Cell。每个 Cell 通过 Hash 得到 Bucket Range，但 Hash Bucket 只是候选集合：Kernel 仍检查 `SpatialCells[particleIndex].xyz == requiredCell`，排除不同真实 Cell 碰巧得到相同 Hash 的 Collision；还要同时检查 Metadata Active Flag、Position.w 与 finite。合法邻居最终累加：

```text
density(x) = Σ particleMass * 315 / (64πh^9) * (h² - |x-pj|²)^3
             仅当 |x-pj| < h
```

`h` 是 Smoothing Radius，也叫 Kernel Support Radius。域外权重严格为 0，所以只查 27 个 h-sized Cell 足够，不必遍历所有粒子；这把朴素的 `voxelCount * particleCount` 降为 `voxelCount * localNeighborCount`。当前是 `Isotropic`，各方向只看欧氏距离，Kernel 是球形；高速流动会仍有“棉花糖/串珠”感，Task 8 才用局部 Covariance 将球形 Kernel 变为有界的方向性 Kernel。

### 4. 为什么完整 Tick 后要再发布一次 Spatial Hash

Task 4 为了控制 Solver 成本，在每个 Substep 的 Predict 后只构建一次 Spatial Hash；随后多个 PBF Iteration 会修改 Predicted Position，却继续使用 build-time `SpatialCells` 与候选 Range。这对 Solver 是刻意的稳定 Snapshot：Maximum Correction 被限制，Iteration 内不能让“当前 cell”去查询“旧 Range”，否则两套语义混用会漏 self/neighbor。Task 5 的 Collision Projection 也可能继续移动粒子，Commit 后当前 Position 已不等于 Predict 时的 Cell。

Density Field 属于 Rendering Consumer，它在完整 Simulation Tick 后读取粒子。如果继续使用 Solver 的 pre-correction Hash，某个粒子已经被推过 cell 边界，Density Kernel 用当前位置计算距离、却会被旧 `SpatialCells` 的 exact-cell filter 排除，画面就会出现局部密度洞或水面闪断。本 Task 因而在所有 Substep 完成、最后一次 Commit 后额外执行一次 `BuildSpatialHash()`，Predicted 与 committed current Position 此时一致；这份 post-commit Hash 明确是发布给 Rendering 的 current-position Snapshot。它不是每个 Iteration 重排，也不是在每个 Substep 额外再排一次，而是每个完整 Fixed Tick 一次，保留 Solver 原有“每 Substep 一次 Sort”取舍，同时避免 Presentation 消费失效索引。外层 `GpuFluid.SpatialHash.PublishCurrent` Profiler Marker 将这次发布与 Solver 的 Build/Sort/Ranges 聚合明确区分。`FluidGpuSnapshot` 还新增 `ParticleMass` 并把 Layout Version 提升到 3，让 Rendering 使用 Simulation 的同一质量参数；Render Profile 不复制 Particle Mass，避免调出两套互相矛盾的 Density。

当前 Runtime 链变为：

```text
每个 Fixed Tick：Upload Spawn / Dirty Collider
-> 每个 Substep：Gravity -> Predict -> Solver Spatial Hash
                  -> PBF Iterations + Collision
                  -> Velocity Filters -> Collision Velocity -> Clamp -> Commit
-> 完整 Tick 结束：Post-commit Spatial Hash（发布给 Rendering）
-> IFluidGpuSource.TryGetGpuSnapshot
-> Task 7 Renderer：Density Dispatch -> Marching Cubes -> Indirect Draw
```

## Task 7：GPU Marching Cubes、Indirect Draw 与 Procedural Water Shader

本 Task 把 Task 6 的 3D `Scalar Field` 真正变成 Camera 可以看到的连续三角面。要先分清三个阶段：`Marching Cubes` 只负责从 Density 等值面提取几何；`Rasterization` 把每个 Triangle 覆盖成候选 Fragment；URP `Fragment Shader` 才计算 Depth、Fresnel、Foam、Triplanar Wave 与 PBR Lighting。粒子不是顶点，Density Sample 也不是像素；它们经过 `Particle -> Scalar Field -> Triangle Buffer -> Indirect Draw -> Fragment` 才成为最终水面。本实现让每个 GPU Thread 独占一个 Cell，用标准 256×16 Case Table 找相交 Edge，将每个 Triangle 作为连续 96-byte Struct 写入固定容量 Buffer；CPU 不回读 Triangle Count，而由 `BuildIndirectArgs` Kernel 直接写 16-byte Draw Command。Procedural Shader 再用 `SV_VertexID` 找到 Triangle/Corner，输出 World Position/Normal 到 Clip Space。这样避免每帧创建 Unity `Mesh`、GPU→CPU Readback 与 CPU→GPU Mesh Upload，同时用显式 Overflow Counter 保证容量不足时只截断画面，不写越界破坏 VRAM。

### 1. 一个 Cell 如何从 8 个 Corner 变成 Triangle

Density Texture 存的是 Lattice Sample。相邻 2×2×2 共八个 Sample 围成一个 Cell；因此 Resolution 为 9×9×9 时只有 8×8×8 个 Cell。Corner 编号约定为：z=0 平面的 0-1-2-3，z=1 平面的 4-5-6-7；12 条 Edge 是两个平面各四条环边，再加四条 Z 方向连接边。Kernel 对八个 Density 执行 `density >= IsoLevel`，每个 Corner 得到一个 bit：

```text
caseIndex = bit0 | bit1<<1 | ... | bit7<<7

例如只有 Corner 0 在液体内部：caseIndex = 00000001₂ = 1
标准 Case 1 的 Triangle Row = [0, 8, 3, -1, ...]
表示等值面依次穿过 Edge 0、8、3，形成一个 Triangle
```

Edge 两端 Density 是 `dA/dB`，世界位置是 `pA/pB`。等值面在线段上的比例为 `t=(iso-dA)/(dB-dA)`，最终 Vertex 是 `lerp(pA,pB,t)`。当分母接近零时用固定 `t=0.5`，其他情况 Clamp 到 `[0,1]`，避免浮点误差把顶点推到 Cell 外。Case 0 表示八角都在外部，Case 255 表示八角都在内部，两者都没有边界 Triangle；任何 Case 最多五个 Triangle。`MarchingCubesTables.hlsl` 将标准 16-entry Row 每四个 signed byte 打包进一个 `uint`：0..11 是 Edge，`0xff` 解码为 -1 Terminator。它不改变拓扑，只把常量存储缩小四倍。表值来自 scikit-image 0.23.2 `CASESCLASSIC`，文件中保留 scikit-image team Copyright、BSD-3-Clause 条款摘要与原始仓库 Attribution；测试把解包后的全部 4096 bytes 锁定为 SHA-256 `19bf7699...e809b`，比只抽查几个 Case 更能防止手误。

### 2. Triangle Counter、Race Condition 与 Overflow 为什么这样设计

GPU Cell Thread 的执行顺序不确定，多个 Thread 不能共同写普通 `triangleCount++`，否则会发生 `Race Condition`：大家先读到相同旧值，再覆盖彼此。`InterlockedAdd(_TriangleCounter[0],1,triangleIndex)` 是 `Atomic Operation`，保证每个合格 Triangle 得到唯一 Index。这里不使用 `AppendStructuredBuffer`，也不使用 `GraphicsBuffer.CopyCount`：当前 Counter 是显式普通 uint，`CopyCount` 只认识 Append/Counter Buffer 的内部隐藏计数；混用会让 Draw Args 看不到真实数值。

每个 `FluidSurfaceVertex` 是两个 `float4`：`positionWS.xyz + padding` 与 `normalWS.xyz + padding`，固定 32 bytes；三个 Vertex 连续组成 96-byte `FluidSurfaceTriangle`。Thread 一次性写完整 Triangle，避免三个独立 Vertex Append 被其他 Thread 交错，造成错误拓扑。Atomic 返回的 `triangleIndex` 即使超过容量也继续计数，便于知道真实需求；但只有 `triangleIndex < MaximumTriangleCount` 才写 Buffer，否则只 Atomic 增加 Overflow Counter。最后 Args Kernel 读取 Counter，计算 `vertexCountPerInstance=min(count,capacity)*3`，并固定 `instanceCount=1/startVertex=0/startInstance=0`。Args Buffer 以 `GraphicsBuffer.Target.IndirectArguments` 创建、总计 16 bytes；Compute 在 D3D11 的 `R32_UINT` UAV 语义下用 `RWBuffer<uint>` 写四个槽，而不是误声明普通 Structured C# Struct。整个链路没有 `CopyCount`，CPU 也不调用 `GetData()`。

### 3. Gradient Normal、Winding、Backface Culling 与几何兜底

光照 Normal 不是“Triangle 朝哪”这么简单。对连续 Density `ρ(x)`，Gradient `∇ρ` 指向 Density 增长最快的方向；本项目 Density 高的一侧是液体内部，所以 outward normal 是 `-normalize(∇ρ)`。Kernel 在 Vertex 的 X/Y/Z 两侧各采一次 Density，以 `f(x+h)-f(x-h)` 的 Central Difference 估计三个偏导，并除以 `2h`。3D Texture 使用 Linear Filter，World Position 先换为 Grid 坐标，再以 `(grid+0.5)/resolution` 对齐 texel center。若 Gradient 太短、出现非法数值或局部 Field 几乎平坦，就用 `cross(p1-p0,p2-p0)` 的 Geometric Normal 兜底。

Normal 还不等于 `Winding`。Rasterizer 根据 Vertex 顺序判定 Front/Back Face，`Cull Back` 会丢弃背面；如果 Lookup 的 inside 约定与 Density 定义相反，即使 Normal 数值正确，也可能整片表面被剔除。因此每个 Triangle 还计算 inside/outside Corner Centroid 的方向，并优先用三个 Gradient Normal 的和作为 outward Reference；若 Geometric Normal 与它点积小于零，就交换 p1/p2 与 n1/n2，翻转 Winding。结果同时满足：顶点 Normal 朝外、几何 Front Face 朝外、封闭液体可安全 `Cull Back`。这能降低透明 Overdraw，但不等于解决所有透明排序；URP 仍只能按整个 Draw 的真实 `worldBounds` 排序，单个封闭水体内部 Triangle 不会逐三角排序。

### 4. Procedural Indirect Draw、Shader Stage 与坐标空间

传统 Mesh Vertex Shader 从 Vertex Buffer 读 `POSITION/NORMAL`；本实现没有 CPU Mesh，而是让 `Graphics.RenderPrimitivesIndirect` 根据 GPU Args 决定 Vertex 数量。`ElementLiquidProcedural.shader` 必须先 `#define UNITY_INDIRECT_DRAW_ARGS IndirectDrawArgs`，再 include `UnityIndirect.cginc`；Vertex Shader 开头执行 `InitIndirectDrawArgs(0)`，随后把原始 `SV_VertexID` 传给 `GetIndirectVertexID`。这个 helper 修正不同 Graphics API 对 `startVertex` 的语义差异。修正后的 ID 做：

```text
triangleIndex = vertexID / 3
cornerIndex   = vertexID % 3
TriangleBuffer[triangleIndex] -> v0/v1/v2
positionCS = TransformWorldToHClip(positionWS)
```

Marching Cubes 已写 World Space，不能再乘一次 Object-to-World，否则水体会重复平移/缩放。`Clip Space` 是 Vertex Shader 交给 Rasterizer 的齐次坐标；Rasterizer 完成裁剪、透视除法、Viewport 映射和三角形内部插值，Fragment Shader 才得到连续的 Position/Normal。Procedural Vertex 没有美术 Mesh Tangent，所以 `ElementWaterCore.hlsl` 新增 `ElementWaterBuildOrthonormalBasis`：选一根不与 Normal 平行的参考轴，通过两次 Cross Product 构造正交 T/B/N，供 Normal From Height 使用。Shader 复用 Legacy Water Core 的 Triplanar Value Noise、Depth/Fresnel 数学，再保持相同的 Color/Alpha/Wave/Depth/Foam Property 名称与默认值，最终仍交给 `UniversalFragmentPBR`。它是新的 Shader，不修改 Legacy `Game/Elemental/Water` Material 行为；正式 `.mat` 与 Scene 绑定留给集成 Task。

透明水设置 `Queue=Transparent`、Alpha Blend、`ZWrite Off`、`ZTest LEqual` 与 `Cull Back`。`ZWrite Off` 避免先画的半透明水遮掉后续透明物，但也意味着透明物体无法靠 Depth Buffer 自动得到完美交叠；`worldBounds` 必须使用 Padding 后 Density Grid 的真实 Bounds，而不是 10000m 假范围，否则 Frustum Culling 与透明物整体排序都会失真。Scene Depth 只记录水后方第一个不透明表面，因此 `sceneEyeDepth-surfaceEyeDepth` 是视线方向厚度近似，不是精确封闭水体内部路径长度；这是实时 URP 首版的视觉 trade-off。

## Task 8：Anisotropic Kernel 还原流动水团外形

### 1. 目的、完成内容与玩家能感知的变化

Task 7 已能把球形 `Poly6 Kernel` 叠成连续水面，但每个粒子的影响范围仍是各方向相同的球。高速水流、越过台阶或倾倒时，粒子常沿速度方向排成一列；若仍给每个粒子画圆球状密度山，最终表面就容易出现“串珠”或一团团棉花糖。Task 8 不修改 PBF 的 Position、Velocity、Collision 或 Gameplay Truth，而是在 `Game.Rendering` 中根据每个粒子的局部邻域构造有硬上限的椭球 Kernel：邻域呈线状时沿主方向拉长、横向收窄；邻域对称或样本不足时回退球形。这样只改变 Surface Reconstruction 的轮廓连续性，不会偷偷改变水量、碰撞或 Wet/Fire 规则。

本 Task 新增 `FluidAnisotropy.compute` 两个粒子 Pass、64-byte `FluidAnisotropyTransform`、Profile A/B 参数、隔帧更新调度，以及 `FluidDensity.compute` 的 Anisotropic Gather。Renderer 链变为：

```text
Simulation 发布 current-position Hash
-> 到达更新帧：Gather Mean
-> Build Covariance + Jacobi Eigen Decomposition + Transform
-> GatherAnisotropicDensity（非更新帧复用上次 Transform）
-> Marching Cubes -> Indirect Args -> Procedural Draw
```

没有新增外部模型、贴图、Normal Map、VFX、音频、字体、Prefab、Material 或 Scene 依赖。视觉是否达到参考视频方向必须在 Unity Editor 中以 Isotropic/Anisotropic A/B 实际观察，源码与 C# 编译不能替代画面证据。

### 2. Mean、Covariance Matrix 与 Eigen 的几何直觉

`Mean` 是邻域的加权中心：`mean = Σ(wj*pj)/Σwj`。随后令每个邻居相对 Mean 的位移为 `d=pj-mean`，构造对称 `Covariance Matrix C=Σ(w*d*transpose(d))/Σw`。矩阵对角线表示沿 X/Y/Z 的分散程度，非对角线表示轴之间的相关性；因此斜向水流的主方向不必等于任何世界轴。

`Eigenvector` 可以理解为 Covariance 自己最自然的三条正交方向，`Eigenvalue` 是样本沿对应方向的分散强度。Compute 使用固定五轮 `Symmetric Jacobi Eigen Decomposition`：依次旋转消去 XY、XZ、YZ 非对角项，并累计方向。固定循环次数不依赖 GPU Thread 调度，也不需要动态分配。球形对称邻域三个 Eigenvalue 近似相等；线状邻域最大 Eigenvalue 对应的 Eigenvector 就是水流主方向。

### 3. Scale Clamp、体积保持与 64-byte Affine Transform

直接使用 Eigenvalue 比例会把稀疏表面粒子拉成针。实现以 `sqrt(dominantVariance/transverseVariance)` 得到原始伸长量，再受 `MinimumAnisotropyScale`、`MaximumAnisotropyScale` 与 `MaximumAnisotropyRatio` 三重限制。最长世界轴为 `long`，两个短轴取 `short=1/sqrt(long)`，所以 `long*short*short=1`，单粒子 Kernel 的体积近似保持。

对单位主轴 `a`，对称正定 world-to-kernel 矩阵为 `A=inverseShort*I+(inverseLong-inverseShort)*a*transpose(a)`。每粒子 64 bytes 由四个 `float4` 组成：前三行是 `kernelPoint=A*worldPoint+translation` 的 3×4 Affine Transform，第四行保存三个世界 Scale 与 Valid Flag。Translation 为 `-A*mean`，因此 Mean 映射到 Kernel 原点。邻居不足、Covariance/Eigen 非 finite 时写以原粒子为中心的 Identity fallback；Inactive slot 整记录清零。测试使用非紧凑 active slot，避免误读 buffer[0] 默认零值形成假阳性。

### 4. 为什么 Anisotropic Density 不能继续只查 27 个 Cell

Isotropic Kernel 的世界支持域正好是 `h`，Hash Cell Size 也是 `h`，所以固定 `3^3=27` Cell 足够。最长轴为 `1.8h` 时，Hash Cell -1 的粒子仍可能影响 Cell +1 的 Sample；继续查询 27 Cell 会漏贡献并让水流沿伸长方向断裂。

Profile 因而硬限制 `MaximumAnisotropyScale<=2`，Settings 计算 `AnisotropyCellRadius=ceil(maxScale)`。Anisotropic Gather 最坏遍历 `5^3=125` Cell，再用 Affine 后的距离精筛；Isotropic A/B 路径仍只查 27 Cell。Mean 相对原粒子的漂移还受 `centerOffset+maxScale*h<=cellRadius*h` 约束，保证整个椭球落在已查询范围内。代价是候选 Cell 上界约增至 4.6 倍，必须由 GPU Profiler 衡量，不能允许任意大 Scale 使成本立方失控。

### 5. 隔帧更新、首次初始化与零分配热路径

Covariance/Jacobi 比球形 Density 更贵，Profile 可每 N 个 Rendering Frame 更新一次 Transform，中间帧复用长期 Buffer；关闭 `UseAnisotropy` 时完全不查找、不绑定、不 Dispatch Anisotropy Kernel。隔帧逻辑不能只写散落的 `frameIndex%interval`：组件禁用会释放 Buffer，重新启用后的新 VRAM 未初始化，第一帧若被跳过会让 Density 读取零矩阵。纯值类型 `FluidAnisotropyUpdateSchedule` 保证构造和 `Reset()` 后第一次必定更新，此后才遵守间隔。

每个 Kernel 只绑定所需资源：Clear 写一个 Counter Buffer；Mean 写 Transform；Build 写 Transform+Counters；Density 只写 R32 Texture。Profile Snapshot、Kernel/Property ID、Schedule 与资源都在生命周期边界创建；正常 `LateUpdate` 只 Set 参数、Dispatch 与 Draw，不 `new`、不用 LINQ/Closure/Boxing，也不同步 Readback。

### 7. Task 8 Fix 1：为什么隔帧缓存还需要粒子版本与 Shader fallback

隔帧复用不是简单的“矩阵晚几帧跟随位置”。粒子池的 slot 会经历 inactive→Spawn/reuse 的生命周期变化：Anisotropy 上次更新时会把 inactive slot 写成全零；若新粒子在下一次定时更新前占用该 slot，旧 Density 把零 affine 当真，就会让所有 World Position 映射到 Kernel 原点，产生错误的 `Poly6(0)` 密度峰。这里的缓存身份已经变了，因此不能只靠 frame interval 判断“旧结果还能用”。

Fix 1 在 Simulation→Presentation Contract 增加 `TopologyVersion`。`GpuPbfFluidRuntime.TryEnqueueSpawn` 只有在固定容量 Queue 成功接纳请求后才递增 `uint`，失败入队不触发无意义刷新；Snapshot 按值复制该版本。Renderer 的纯值类型 `FluidAnisotropyUpdateSchedule` 保存最近版本，只要 `snapshot.TopologyVersion != lastTopologyVersion` 就在 Density 前立即重算。它不比较大于/小于，所以版本从 `uint.MaxValue` wrap 到 0 仍然是一次变化。强刷完成后计数器重新进入既有 interval，因而不会把节流永久关闭，也没有新增每帧托管分配。

版本是一层“让正确数据及时产生”的防线，但 Shader 仍不应盲信跨帧 cache。`FluidAnisotropyTransform.scaleValidity.w` 是 affine 的有效标志；Anisotropic Density 现在只有在 flag 有效且变换结果 finite 时才使用矩阵，否则用 `worldPosition-particlePosition`。后者等价于“以当前粒子 Position 为中心的 Identity Kernel”，既不会把零矩阵误解为峰值，也不会因为一个坏 affine 丢掉整个 active 粒子的 Isotropic 贡献。这是 Defense in Depth：version 防正常生命周期不同步，consumer validation 防未初始化数据、未来错误调用或数值损坏。

回归测试刻意选择非紧凑 slot 14，先让其 transform 保持全零，再把它作为 active 粒子写入当前 Position 和 Spatial Hash；Anisotropic Density 必须与 Isotropic Density 在粒子中心及旧零 affine 峰位置一致。另一个 Pure schedule test 覆盖相同版本遵守 interval、版本变化立即刷新，以及 `uint.MaxValue→0` wrap。RED 阶段分别得到缺 Snapshot contract 的 2 个预期 compile error 与缺 version-aware schedule 的 9 个预期 `CS1501`；实现后 ElementField/Rendering 的 Production+Tests 四程序集 fresh Rebuild 均为 0 warning/0 error。这里仍必须区分：C# 编译已经 GREEN，GPU fixture 尚未由 Unity Test Runner 执行。

当前 `Editor.log` 已证明两个 Compute 在 D3D11 被 `ComputeShaderImporter` 处理且没有 Shader error；日志仍记录编译器认为 `isnan/isinf` redundant 的 warning。旧日志还记录 Poly6 的 `pow(h,9)` negative-base 保守 warning，源码现已用固定乘法表达九次方，但 Editor 尚未对这一修改产生新 importer 记录，所以不能提前宣称 warning 已消失。后续 Gate 是重新 import、实际运行 `GpuFluidAnisotropyTests`，再进行 D3D11/D3D12 A/B、Frame Debugger、GPU Profiler 与 `GC Alloc=0 B` 检查。

### 8. Task 8 Fix 2：版本代表“GPU 已提交的拓扑”，不是“CPU 已收到命令”

Fix 1 把 `TopologyVersion` 放在成功 enqueue 后递增，仍混淆了两个时间点：Queue 接纳表示 CPU 已记录一条未来 Spawn Command；只有固定 Tick 中的 `SpawnParticles Dispatch` 提交后，GPU Buffer topology 才进入改变序列。考虑一帧内的执行顺序：外部脚本可能在 Runtime `Update` 之后、Renderer `LateUpdate` 之前 enqueue，或者 Simulation Clock 本帧得到 `tickCount=0`。若这时提前发布版本，Renderer 会对尚未 Spawn 的 inactive slot 重算；下一 Tick 真正 Spawn 时版本不再变化，于是新粒子反而可能继续复用旧 transform。

Fix 2 引入 internal、Pure value type `FluidTopologyVersionTracker`，让 `PublishedVersion` 的语义收紧为“已提交到 Graphics Queue 的粒子 topology 版本”。`TryEnqueueSpawn` 重新只返回固定容量 Queue 的成功/失败，不碰版本。`UploadQueuedSpawns` 取得非零 `requestCount`，上传 request 并调用 `SpawnParticles Dispatch` 后，才执行 `PublishAfterSpawnDispatch(requestCount)`。Renderer 的 Anisotropy Dispatch 在之后的 `LateUpdate` 提交；同一 Graphics Queue 维持命令顺序，因此它看到新版本时，前面的 Spawn 已经排在读取之前。这里不要求 CPU 等 GPU 完成，也不做同步 Readback。

测试不使用 Reflection 去伪造 `Awake/Update/LateUpdate`。Focused Pure Test 组合真实 `FluidSpawnQueue` 与 tracker：第一次 enqueue 成功但版本保持 0；Queue 已满时第二次 enqueue 失败且仍为 0；模拟非空 Spawn Dispatch 提交后才变为 1；空批次不变；另覆盖 `uint.MaxValue→0` wrap。RED 是缺少 tracker 时 2 个预期 `CS0246`，0 warning；实现后 ElementField/Rendering Production+Tests 四程序集 fresh Rebuild 均 0 warning/0 error。这个测试锁定发布时机的 C# Contract；真实 Unity PlayerLoop、GPU command ordering 与 invalid-transform fixture 仍需 Unity Test Runner/Editor Gate。

Fix 2 保存后，Unity 已对 `FluidDensity.compute` 产生新的 D3D11 `ComputeShaderImporter` artifact；新日志没有 Shader error，原先由通用 `pow(f,e)` 引起的 negative-base warning 也已消失，只剩编译器认为 `isnan()` 冗余的提示。这一条只能证明 Compute Asset 成功 Import，不能替代 GPU Test、D3D12、视觉 A/B 或 Profiler。

## Task 9：Water 写入路由、Legacy 回退与 P7 Source 兼容

### 1. 目的、完成内容与玩家可见结果

Task 9 把原来所有 `ElementWriteRequest` 都进入 Cell Queue 的单一路径，扩展为“仍只有一个公开 Write Sink、但 Water 根据初始化时锁定的模式选择唯一后端”。`LegacyCell` 下，Water、Fire 与既有 Source 完全沿用 Cell Queue、稀疏 Chunk 和 Water/Fire Solver；`GpuPbf` 下，Water 被转换为 `FluidSpawnRequest` 并进入固定容量 GPU Spawn Queue，Fire 仍写 Cell。这里不是把同一份 Water 同时写两遍做保险：Cell Water 和 PBF Particle 都代表水量，双写会让一发水弹生成两份 Simulation Truth，后续 Wet、灭火、渲染和守恒都无法判断哪一份是真实数据。

本 Task 还在 `ElementWriteRequest` 中加入向后兼容的 `InitialVelocity`。旧五参数 constructor 仍得到 `Vector3.zero`，所以 Persistent Fire、Initial Deposit 和既有调用点不改变；Projectile impact 只提供命中点、方向和标量 speed，不认识 `GpuPbfFluidRuntime`、`GraphicsBuffer` 或 Compute。`_fluidInitialSpeed` 默认 0，含义是旧 Prefab 不继承命中动量；Task 13 的 Editor Gate 必须在目标 Water Projectile 上显式配置可玩速度，避免新增序列化字段让旧资产在没有人工验收时突然改变手感。

### 2. Adapter、Router、Single Writer 与序列化 Feature Toggle

`IFluidDepositSink` 是纯 Contract：它只回答液体子系统是否初始化，以及能否接纳一个不可变 `ElementWriteRequest`。`ElementWorldWriteRouter` 不访问 Unity 生命周期和 GPU，按 `WaterSimulationMode`、`MaterialKind` 选择一个下游：PBF Water 只调用 Fluid；其他请求只调用 Cell。Fluid 缺失、未初始化、Queue 满或完整粒子数越界时返回 false，绝不在失败分支偷偷回写 Cell。这让失败是可观察的容量/装配问题，而不是隐藏的 simulation backend 切换。

```text
LegacyCell（默认 0）
Projectile / Initial Deposit / Persistent Source
-> ElementRuntimeRegistry 唯一 IElementWriteSink
-> ElementWorldRuntime -> ElementWriteQueue
-> ElementWorldWriteProcessor -> Cell Water / Fire
-> Reaction -> Down Flow -> Horizontal Flow -> Fire Decay -> Commit
-> ElementWorldWaterRenderer（Legacy Mesh）

GpuPbf
Water Projectile -> 同一个 ElementWorldRuntime Router
-> IFluidDepositSink -> FluidDepositQueueAdapter
-> ceil(TotalAmount / AmountUnitsPerParticle)，完整数量越界则整笔拒绝
-> GpuPbfFluidRuntime.TryEnqueueSpawn -> Spawn Queue
-> 固定 Tick Spawn Dispatch 后才发布 TopologyVersion
-> PBF Solver -> GpuLiquidSurfaceRenderer

Fire / 非 Water Source -> ElementWriteQueue -> Cell Fire Decay / Commit
```

`WaterSimulationMode.LegacyCell=0` 是序列化兼容边界：旧 `ElementWorldProfile.asset` 没有新字段时，Unity 反序列化为 0，继续旧行为。Profile 在 Runtime 初始化时快照 `SimulateCellWater`，之后不逐帧回读 `ScriptableObject`。若设备不支持 Compute 或 Graphics Device 为 Null，只有 `ElementWorldRuntime` 在初始化期把 effective mode 决定为 Legacy 并限频 `GameLog.Warn`；Profile 仍不被修改。若设备支持但 PBF component 缺失、初始化失败或 Queue 满，则用户明确选择的 PBF 请求必须失败，不能把配置错误伪装成 Legacy 成功。切换 Profile 后需要退出并重新进入 Play Mode，因为模式同时决定大型 GPU/Legacy Mesh 资源的生命周期，不支持运行中半拆半建。

### 3. Amount、Seed、Falloff 与 Initial Velocity 如何成为 Spawn Command

`FluidDepositQueueAdapter` 使用整数除法加 remainder 做 Ceiling。例如 `TotalAmount=17`、`AmountUnitsPerParticle=8` 得到 3 个粒子；不能先 clamp 到 capacity，因为 2 个粒子只代表最多 16 个 Amount，会静默丢掉尾量。若完整 `ParticleCount` 大于 Profile 的总 Particle Capacity，整笔拒绝。Queue 满也拒绝，并且失败不推进 Seed；只有成功入队才让 `uint Seed` 单调递增，wrap 后仍保持确定的序列变化。

`Radius` 直接成为 Spawn Distribution 半径；`UseLinearFalloff` 映射到 `FluidSpawnFlags.UseLinearFalloff`，只改变球内/圆盘采样密度，不改变粒子质量。`InitialVelocity` 是 impact direction 的 normalized vector 乘可调 speed；零方向保持零，Fire 强制为零。Gpu Runtime 的 `TryEnqueueDeposit` 最终仍调用既有 `TryEnqueueSpawn`，所以 capacity validation、固定 Queue 和 Task 8 Fix 2 的 topology publish 点没有被绕过：enqueue 只是 CPU 未来工作，版本仍在非空 Spawn Dispatch 提交后才变化。

### 4. PBF 模式为何必须完整跳过 Cell Water Solver

关闭 Cell Water 不能只把 Down Flow 设成 0。旧 Cell 中可能残留 Water；若 `PrepareNeighbors` 仍扫描它，就会在 Chunk 边界创建新的接收 Chunk、触发 Solid Bake 并扩大 Solver 工作集。若 Reaction 仍运行，残留 Cell Water 还会消耗 Fire，相当于 PBF Water 与旧 Water 同时灭火。因此 `SimulateCellWater=false` 时完整跳过 `PrepareNeighbors`、Reaction、Down Flow 和 Horizontal Flow；不清空残留 Cell，因为 mode 只在进入 Play 时初始化，运行中删除数据会破坏可逆性和调试证据。

Fire Decay、Stage Commit、Dirty Version、`RefreshNonEmptyCellCount`、`RecordSimulationResult` 与 Chunk activity 仍继续。结果是旧 Water 保持可读但不再演化或创建邻居，Fire 仍按原 tick 衰减，变化仍能通过版本和 activity 被消费者观察。Legacy settings 的兼容 constructor 默认 `SimulateCellWater=true`，旧数值测试继续走原公式。

### 7. Fix Round 1：为什么 GPU Command 必须统一拒绝 NaN/Infinity

`Vector3.normalized` 不是非法浮点清洗器：输入含 `Infinity` 时，长度计算和除法可能得到 `NaN`；只验证 `Radius` 也无法阻止污染过的 `WorldPosition` 或 `InitialVelocity` 写进 Spawn Buffer。`FluidSpawnRequestValidator` 因而成为统一 Command Boundary，要求位置、速度三轴以及半径全部是 finite。Projectile Adapter 也在建立 `ElementWriteRequest` 前拒绝非法命中点、方向和 speed，避免坏值先进入普通 Queue、到更深层才被拒绝。这里选择“整笔拒绝”而不是 clamp：NaN 没有合理方向，Infinity 也没有可解释的世界坐标，静默改成 0 会掩盖上游 Physics/VFX 错误。

另一个边界是 `LiquidRenderProfile.CreateSettings()`：ScriptableObject 可能被旧序列化数据、Reflection 或未触发 `OnValidate` 的工具写成非法值，构造 immutable settings 会抛异常。Renderer 的 `Awake` 现在只调用一次 CreateSettings，并由 `LiquidRenderSettingsFactory.TryCreate` 捕获后走 `DisableWithFailure`；这样 Unity 生命周期不会被异常打断，也不会在条件判断和正式赋值时重复创建两份 snapshot。Anisotropy Compute 的存在性检查必须放在 settings 成功之后，因为是否启用它正是 snapshot 中的配置。

Fix 的 focused compilation RED 为缺少 safe factory 的 `CS0103`，补齐后 ElementField/Tests、Rendering/Tests 四套 fresh forced Rebuild 均 0 warning/0 error。新增 NUnit 行为断言尚未由 Unity Test Runner 执行；Task 13 仍需用非法 Profile fixture 验证组件被禁用且 Console 只有一次 `GameLog.Warn`，并用非有限 impact 输入确认 Queue 计数不变。

## Task 10：低频 AsyncGPUReadback、Liquid Occupancy 与 Wet

### 1. 目的、完成内容与玩家可见结果

Task 10 在 GPU PBF Water 与 CPU Gameplay 之间建立低频只读桥梁。PBF 粒子位置仍是唯一 `Simulation Truth`，Renderer 每帧直接读 GPU Buffer；`Wet` 不需要逐帧精确粒子位置，因此每 0.25 秒把 GPU 粒子投影成 CPU Global Cell Occupancy。玩家进入稳定水池或穿过飞溅水团时，角色会在一次完成的 Readback/Exposure 周期后获得 Wet；Fire 仍完全读取 Legacy Cell，即使 PBF Snapshot 尚未产生或 Readback 失败也不会被吞掉。

GPU 侧新增唯一的 packed `GameplaySamples` Buffer，每个 slot 是一个 16-byte `float4`：`xyz` 保存 committed world position，`w` 保存 tag。tag=0 表示 inactive；active 则为 `materialId+1`。这个 `+1` 很重要：若直接把 `materialId` 写入 w，编号 0 的材质会和 inactive 混淆。Pack Kernel 同时读取 Position 与 Metadata，并只发起一个 `AsyncGPUReadback.RequestIntoNativeArray`，所以 CPU 不会把两个不同 GPU 时刻的 position/active/material 拼在一起，也没有用 `Position.w` 猜 active 的错误捷径。

### 2. Double Buffer、single-flight 与明确 Readback Lease

`FluidGameplayOccupancyBridge` 在 `Awake` 按固定 Particle Capacity 一次性分配两块 `Allocator.Persistent NativeArray<Vector4>`。它的 `[DefaultExecutionOrder(100)] LateUpdate` 晚于 GPU Runtime 的 Update，先请求 source Dispatch `PackGameplaySamples`，再把同一 packed Buffer 异步写入当前 write array。Callback 使用初始化时缓存的 method-group delegate，不在请求点创建 lambda；single-flight 状态机保证上一请求未完成时不会发第二个。完成后在主线程 Binning 到 staging snapshot，成功才交换 published/staging 引用，形成 data、Bounds、LayoutVersion、TopologyVersion、SnapshotVersion 的原子发布；GPU error、非法 metadata、非法 sample 或 rebuild 失败都保留旧 snapshot。

Readback 发起时冻结 `Bounds / Origin / CellSize / Capacity / AmountUnitsPerParticle / LayoutVersion / TopologyVersion`。这是因为 GPU 完成可能晚于玩家或 Interest Bounds 移动：若用完成帧的新 Bounds 解释旧粒子，会把同一 world position 映射到错误窗口。Source 用 `FluidReadbackLeaseTracker` 明确记录 outstanding lease；`GpuPbfFluidRuntime.OnDisable/OnDestroy` 遇到 lease 时只标记 deferred release，callback 或 Bridge 最终 `OnDestroy` exactly-once 解除 lease 后才释放 `GraphicsBuffer`。最终销毁若请求仍未完成，Bridge 只允许一次 `WaitForCompletion`；正常 Update/LateUpdate 不同步等待，也没有 `GraphicsBuffer.GetData()`。

### 3. Deterministic Binning、负坐标与 Amount 量化

`LiquidGameplaySnapshot` 使用初始化时预分配的 open-addressing arrays，不用 `Dictionary`、LINQ 或临时集合。它严格按 GPU particle slot 0→capacity-1 的顺序处理，只接受 active Water；inactive、非 Water 与 NaN/Infinity position 全跳过。世界坐标转换复用 `floor((position-origin)/cellSize)`，因此原点负侧 `-0.01` 正确进入 cell -1，而不是被 C# 截断成 0。Bounds 采用 half-open `[min,max)`，max 面上的粒子属于相邻窗口；查询整数范围则用 `max-inset` 得到最后有效 Cell。

每个 Water particle 为对应 Cell 增加 `AmountUnitsPerParticle`，累加在 255 饱和，避免 byte wrap。固定 slot 顺序让同一 GPU slot snapshot 的 Binning 可重复；它不是把粒子重新变成 Cell Solver，Occupancy 只服务 Wet 和后续 Fire Reaction 查询，不参与 Down/Horizontal Flow 或 Surface reconstruction。Metadata validator 统一拒绝 nonfinite Origin、Bounds center/size/min/max、非法 CellSize/Capacity/amount；校验在清空 staging arrays 之前执行，失败不会破坏上一份 published data。

### 6. Fix Round 1：为什么延迟 Bounds 不能合成一个巨大 Physics Query

Task 10 初版把“当前 Legacy/Fire Active Bounds”和“上一份低频 Water Snapshot Bounds”合成一个包围二者的 `Bounds`，再执行一次 `Physics.OverlapBoxNonAlloc`。这在两个区域接近时看似省一次查询，但 Interest Point 传送或快速跨区时，两份 Bounds 可能相距很远；合并后的 Box 会覆盖中间大量与 Water/Fire 都无关的 Collider。由于 NonAlloc Buffer 固定为 64，Unity 并不保证返回顺序，中间对象可能先占满 Buffer，真正位于当前 Fire 区域的角色反而收不到 `Burning`。

修复引入无分配的 `ElementExposureBroadphasePlan`：Query 0 永远是当前 Legacy Bounds，优先保护 Fire 权威路径；仅在 PBF 且存在有效 Water Snapshot、两份 Bounds 不同时增加 Query 1。两个 Query 复用同一 `Collider[]` 与既有 Target 去重数组，不创建临时集合。精确采样仍分别询问 `ILiquidOccupancyReadOnly` 与 Legacy Cell，因此拆分的是 Physics Broadphase，不会制造第二份 Water Truth。

同时增加 `FluidReadbackIntervalPolicy`。`[Min]` 与 `OnValidate` 只覆盖正常 Inspector 编辑；损坏 YAML 或 Runtime 工具仍可能写入 `NaN`。浮点比较中 `NaN < interval` 为 false，原实现会因此每个可用帧都发 Readback。现在非有限值回到 0.25 秒，零/负数 clamp 到 0.05 秒，并在 `Awake` 再防御一次。

两条回归都遵循 TDD：缺少 Broadphase Plan 时 fresh forced build 得到 0 warning、4 个预期缺类型错误；缺少 interval policy 时得到 0 warning、1 个预期 `CS0103`。最小实现后 focused `Game.ElementField.Tests` fresh Rebuild 为 0 warning、0 error。Unity Test Runner 尚未执行，所以该证据仍只属于 C# compilation；Task 13 需要用相距很远的 Water/Fire Bounds 与超过 64 个中间 Collider 做 PlayMode 压力验证。

## Task 11：GPU Water 与 CPU Fire 的事务式灭火反应

Task 11 解决的是“水和火不再活在同一份数据里以后，怎样继续守恒地灭火”。Legacy 中 Water 与 Fire 都是 CPU Cell，Solver 可以在一个数组阶段里同时扣减；现在 Water 是 GPU Particle，Fire 仍是 CPU Cell，而且 CPU 只每隔约 0.25 秒拿到一份延迟 Occupancy Snapshot。若直接在发现接触时先扣 Fire、再通知 GPU 减水，GPU Queue 满或组件失效就会出现火灭了但水没少；若每个 10Hz Tick 重复使用同一份 Readback，又会把一张旧快照里的水反复花掉。本 Task 因此加入固定容量双命令队列、`SnapshotVersion` 去重、同快照 Water reservation 与 48-byte GPU Consume Command。玩家可见目标是：水弹、水池或少量飞溅接触 Fire 时，Fire 与对应水粒子一起减少；低量接触仍按 Low Rate 反应，达到阈值才使用 Formal Rate；Legacy 模式的旧 Cell 反应完全保留。

### 1. 为什么需要 Transaction，而不只是两次函数调用

这里的 `Transaction` 不是数据库，而是“一组跨两个系统的改动，要么全部被 Queue 接受，要么全部不发生”。CPU Fire 的 Timeline 是 `ElementWorldRuntime` 固定 Tick；GPU Water 的 Timeline 是 `GpuPbfFluidRuntime` fixed tick 和 Graphics Queue。两者不能在同一条 C# 语句里真正同时完成，但可以在进入各自 Timeline 前保证命令成对存在。

`FluidReactionCommandQueue` 内部有两个预分配 Ring Buffer：一个保存 `ElementCellDeltaRequest`，另一个保存 `FluidConsumeCommand`。Batch Admission 先检查 Fire 侧剩余槽位和 Consume 侧剩余槽位；任一不足便返回 false，两个 head/count 都不变。只有两侧都能容纳时才复制数据。之后 CPU 可以先取走 Fire Delta，GPU 可以稍后独立取走 Consume Command；它们到达各自 Tick Boundary 的时间不同，但来源是同一个已成功事务。

### 2. 同格、六邻域、阈值与连续公式

Planner 对每个 Fire Cell 按固定顺序检查七个 Water Cell：同格、`-X/+X/-Y/+Y/-Z/+Z`。只检查六个轴向邻居而不检查 20 个斜邻居，是因为 Cell 接触面代表明确的相邻体积；对角只碰到边或点，若也算会显著扩大反应范围并让小水滴隔角灭火。

Cell 的 `byte Amount` 范围是 `[0,255]`，而 `ElementReactionEvaluator` 的 Fire/Water 强度语义是 `[0,100]`，因此 Planner 先乘 `100/255` 转为强度，再调用共享公式：

```text
formal = fireIntensity >= FormalThreshold
      && waterIntensity >= FormalThreshold

consumedIntensity = min(fire, water, selectedRate * snapshotInterval)
consumedAmount = round(consumedIntensity * 255 / 100)
```

这样角色 Status 反应、Legacy Cell 反应和 PBF/Cell 桥接仍共享同一个 Pure Formula，不会演变成三套含义不同的“灭火速度”。Bridge 的 Readback 比 Cell Tick 慢，因此 Runtime 使用清洗后的 Snapshot interval（至少不短于 Cell tick）推进公式；若错误地每张 0.25 秒快照只乘 0.1 秒 Cell tick，实际灭火速度会无意降低。

### 3. SnapshotVersion 与 Water Reservation 分别解决什么

`SnapshotVersion` 防的是“跨 Tick 重复”：同一份 Readback 可能被多个 Cell Tick 看见，Planner 成功提交一次后记录版本；再次看见相同版本直接跳过。Queue full 时不能记录版本，否则本次两侧都未提交，却再也无法重试。

Water reservation 防的是“同一 Tick 内重复”：一个 Water Cell 可能同时邻接左右两个 Fire Cell。两者若都读取 snapshot 原始 Amount=8，便会各计划消费 8，总计 16。Planner 用预分配数组记录“这个 Global Cell 已预留多少”，后一个接触只能使用剩余量。它不使用 `Dictionary`，因为该路径在固定 Tick 内，容量已由 Profile 给定，线性扫描小数组换来了零 `GC Alloc` 与稳定顺序。

### 4. 粒子 Quantization 为什么只能近似守恒

Fire Amount 可以扣 3，但 GPU 不能删除 0.375 个粒子。若 `AmountUnitsPerParticle=8`，消费 3 必须向上取整为 1 粒子，也就是水侧实际最多减少 8。误差范围是：

```text
0 <= particleCount * AmountUnitsPerParticle - plannedWaterAmount
  < AmountUnitsPerParticle
```

关键是同一 Water Cell 的所有接触先累计，再只做一次 `ceil`。若每个接触分别向上取整，多个不足一粒子的误差会累加，无法再保证“小于一个粒子”。`FluidConsumeCommand` 因此按 Water Global Cell 聚合，携带 inclusive Cell AABB、MaterialId、最大粒子数和 deterministic Seed；Fire Delta 的条数可以多于 GPU Command 条数，所以双队列事务支持两侧不同 count。

### 5. GPU Consume Kernel、Free Stack 与原子操作

`ConsumeParticles` 使用 `[numthreads(1,1,1)]`：每个 Group 对应一条低频反应命令，Thread 从 Seed 旋转后的 slot 开始，最多扫描 `ParticleCapacity` 次。它先检查 Metadata 的 active flag 和 MaterialId，再用 `floor((worldPosition-worldOrigin)/cellSize)` 计算 Global Cell，并与 Command 的 inclusive AABB 比较。

多个命令可能同时找到一个粒子，所以“先读 active 再直接清零”会 double-free。Kernel 对 Metadata flag 使用 `InterlockedCompareExchange (CAS)`：只有把预期旧 flag 成功交换为 0 的 Thread 获得该 slot。成功者再原子增加 Free Count，把 particle index 压回 Free Stack，原子减少 Active Count，并清理核心 Position/Velocity/Density 暂存。该 Kernel 正好绑定 8 个 RW UAV，Consume Command Buffer 是只读 SRV，保持 D3D11 的 UAV 上限。Consume Dispatch 位于 Spawn 之后、Solver 之前；非空 Dispatch 提交后才推进 `TopologyVersion`，让 Anisotropy/Rendering 知道 slot 生命周期已变化。

## Task 12：粒子 Sleep/Wake、Interest 与 GPU Indirect Dispatch

Task 12 解决的是“水静止后，怎样停止重复求解，却仍然保留为可见、可查询、可再次唤醒的水”。如果只用一个 `active` 布尔值，关闭它会同时让粒子离开 Solver、Spatial Hash、Density Field 和 Gameplay Occupancy：静止水虽然省了计算，却会从画面和 Wet 查询中消失；若一直保持 active，稳定水池又会永远执行 Gravity、PBF Iteration、Collision 与 Velocity Filter。本 Task 因此把粒子生命周期拆成四个正交含义，并在 GPU 上统计 Awake 数量、生成 `Indirect Dispatch Args`。没有 Awake 粒子时，整条高成本 Solver 链提交零工作组；存在 Awake 粒子时仍覆盖完整 slot capacity，避免稀疏高位 slot 被漏算。玩家可见结果应是静水仍保持水面与 Wet，新的粒子、邻近运动、Collider 变化或 Interest Bounds 重入会再次唤醒它。

### 1. 一个 `active` 为什么不够：四个 Activity Flag

粒子 Buffer 使用固定 slot pool。一个 slot 是否“存在”、是否“在当前关心区域”、是否“这一 Tick 要移动”、是否“稳定休眠”是四个不同问题：

| Flag | 含义 | 典型消费者 |
|---|---|---|
| `Alive` | slot 已分配给一个真实粒子，不能回到 Free Stack | Consume、Gameplay packed readback |
| `InterestActive` | 粒子位于当前 Simulation/Rendering Bounds 内 | Spatial Hash、Density、Anisotropy |
| `RequiresSimulation` | 本 Tick 必须执行 Gravity/PBF/Collision/Commit | Solver 与 Collision Kernel |
| `Sleeping` | 粒子仍存在且在 Interest 内，但已连续稳定足够久 | Debug、Wake Planner；它不能与 `RequiresSimulation` 同时成立 |

因此状态不变量是：Free 的四位全零；Awake 为 `Alive + InterestActive + RequiresSimulation`；Sleeping 为 `Alive + InterestActive + Sleeping`；Bounds 外仍保留 `Alive`，但另外三位清零。Bounds 外不能直接 free，因为 Interest Region 只是“当前值得模拟/显示的区域”，不是世界存档边界。它重新进入 Bounds 时会恢复 Awake，而不是创建一份新粒子。

`FluidGpuCommon.hlsl` 提供三个精确 Predicate：`FluidIsAlive`、`FluidIsInInterest`、`FluidRequiresSimulation`。旧 `FLUID_ACTIVE_FLAG` 只保留给历史 fixture 一次性构造默认 Awake metadata；新 Kernel 不允许继续把所有语义混在这一位上。

### 2. Sleep 判定：速度低还不等于真正稳定

只检查 Velocity 会产生假休眠。例如一个粒子速度暂时接近零，但它位于过密水团中，下一次 PBF Constraint 本应把它推开；若此时休眠，密度错误会冻结。`UpdateParticleActivity` 同时要求：

```text
speed <= SleepVelocityThreshold
abs(density - restDensity) / restDensity <= SleepDensityErrorThreshold
```

两个条件连续满足 `SleepAfterStableTicks` 次，才从 Awake 进入 Sleeping。任何一次速度或相对密度误差超限都会把稳定计数清零。`StableTickCounters` 是每 slot 一个 `uint`，使用饱和递增而不是自然溢出；这样一个长期稳定粒子不会在约 2^32 Tick 后突然回到零。

Spawn 的 Density 初始为 0，而 Profile 强制 `SleepDensityErrorThreshold < 1`，所以新粒子不会因为初速度恰好为零而立即睡眠。离开 Bounds 会清 Stable Tick；重新进入、收到 Wake Request 或全局 Wake 也会清零，要求它重新证明稳定。

### 3. 两阶段 Wake：为什么不能在一个 Dispatch 中递归改邻居

运动粒子接近 Sleeping 粒子时，后者必须醒来，否则 Awake 粒子虽然能把 Sleeping 粒子当密度邻居，Sleeping 粒子自身却不会响应约束。`MarkNeighborWakeRequests` 先读取上一 Tick 已发布的 Spatial Hash，只扫描 Sleeping 粒子的 27 个邻 Cell；发现 Smoothing Radius 内存在 `RequiresSimulation` 邻居时，只写 `_WakeRequests[slot]=1`。随后独立的 `UpdateParticleActivity` 才统一修改 Metadata。

这种 two-phase 设计避免了 GPU 数据竞争：若同一 Dispatch 一边读取 flag 一边把邻居改成 Awake，不同 Thread Group 的执行顺序没有保证，Wake 可能在一帧内随机递归传播，也可能完全看不到刚写入的状态。现在一次 Tick 只传播一圈，结果由输入 Buffer 决定。Spawn 本身已经是 Awake；Consume、Collider Proxy 变化与 Bounds 变化目前采用保守的 `wakeAll`，优点是不会漏掉受影响粒子，代价是复杂场景中可能瞬间唤醒较多水。未来若 Profiler 证明这是瓶颈，可把 Collider/Consume 影响范围改成带 padding 的 AABB Wake，而不改变四 Flag Contract。

### 4. Indirect Dispatch、零工作组与稀疏 slot 陷阱

`UpdateParticleActivity` 用 GPU `InterlockedAdd` 统计 Awake/Sleeping/Interest 数量；`WriteSolverDispatchArgs` 把统计结果写入两个 `GraphicsBuffer.Target.IndirectArguments` Buffer。Solver Args 的三个 `uint` 分别是 `groupCountX, 1, 1`。AwakeCount 为零时 `groupCountX=0`，Gravity、Predict、PBF、Collision、Velocity 与 Commit 都不启动工作组；非零时 `groupCountX=ceil(ParticleCapacity/64)`。

这里故意没有写 `ceil(AwakeCount/64)`。固定 pool 经 Spawn/Consume 后会产生洞：假设 capacity=65，只有 slot 64 Awake，AwakeCount=1；若只派发一个 64-thread group，Thread index 只覆盖 0–63，slot 64 永远不会模拟。当前方案仍让每个 Kernel 扫完整 capacity，再用 `FluidRequiresSimulation` early-out。它节省的是“全体休眠时整条 Solver 为零”，而不是 Awake 粒子很多时的 slot compaction。进一步按 AwakeCount 缩小 groups，必须先把 Awake slot index compact 成连续列表，并让所有 Kernel 通过该列表间接索引。

Spatial Hash 的 Solver 内版本也由 Indirect Args 控制；但完整 Tick 结束后仍直接发布一次 current-position Hash。原因是 Sleeping 粒子仍应参与 Density/Anisotropy/下一 Tick Wake，Rendering 也必须读取 Commit 后的位置。CPU `ProfilerMarker` 与已有 CommandBuffer GPU Sample 保留，用于把 Build、Sort、Ranges 分开观察。

### 5. 独立 Overflow Counter 与低频 AsyncGPUReadback

“容量不足”不是一个统一错误。它们发生在不同 owner、计量单位也不同：

| Inspector 指标 | Owner / 单位 |
|---|---|
| Rejected Particle | GPU Pool 不足而没生成的粒子数 |
| Spawn Request Overflow | CPU Spawn Ring Buffer 拒绝的 request 条数 |
| Collider Overflow | Collector 超出 Proxy 容量的 collider 条数 |
| Reaction Queue Overflow | Fire/Consume 事务队列拒绝的 batch 条数 |
| Triangle Overflow | Marching Cubes 超出 Triangle capacity 的 triangle 数 |
| Awake/Sleeping/Interest | GPU Activity 分类后的粒子数 |

这些值不能共用一个 Counter，否则看到“3”时无法判断是少了三个粒子、三个命令还是三个 Triangle。CPU 已知的 Queue/Collector 计数直接读取；GPU Activity/Rejected/Triangle 使用不高于 2Hz 的 `AsyncGPUReadback`，且每个 owner 只允许一个 outstanding request。它们只用于 Development Inspector，不参与当 Tick 的 Solver Gate：延迟 Readback 只能诊断，不能作为物理正确性的控制输入。

资源释放同样要尊重异步所有权。`OnDisable` 停止新请求，但 outstanding request 完成前不 Dispose 它正在读取的 Buffer；callback 完成后再释放。`OnDestroy` 是最终生命周期边界，允许最多一次 `WaitForCompletion`，随后幂等释放。Simulation 侧还要与 Task 10 Gameplay readback lease 协调：两种 readback 任意一个仍持有资源，都不能提前 Dispose。

### 7. TDD、Debug 路径、证据边界与面试回答

Tests-first 首个 forced build 在 `FluidActivityPlanner.cs` 尚不存在时得到 Exit 1、0 warning、1 个预期 `CS2001`。Pure tests 锁定连续 N Tick 休眠、不稳定清零、Wake 重置、Bounds 外保留 Alive、重入 Awake、Free 全零，以及 capacity=65/仅 slot64 Awake 时仍需要两个工作组。GPU fixture 进一步构造稀疏高位 slot，从 stable tick 进入 Sleeping 时要求 indirect args 为 0，再写 Wake Request 后要求恢复 RequiresSimulation 且 args.x=2。当前 Editor 已重新导入 Lifecycle、Spatial Hash、Solver、Collision、Density 与 Anisotropy Compute，日志中未见对应 Shader/Compute error；但 Unity Test Runner 没有执行 GPU fixture，所以不能把“导入无错”表述成“GPU 数值通过”。

若静水消失，按 `Metadata flags -> Spatial Hash Interest predicate -> Density/Anisotropy predicate -> Surface extraction` 检查，最常见错误是把 Sleeping 当作 inactive。若水永远不睡，检查 Velocity、DensityLambda、RestDensity、StableTick 与 WakeAll 是否每帧误触发；Collider Transform 若持续被标记 dirty，也会保守唤醒全部 Interest 水。若少量高位粒子不动，检查是否错误使用 `ceil(AwakeCount/64)` 而没有 compact index。若关闭组件时出现 GraphicsBuffer disposed/readback error，检查 Gameplay lease、debug outstanding request 与 renderer counter callback 的释放顺序。

面试时可以回答：**我把粒子的 Resident、Interest、RequiresSimulation 与 Sleeping 拆成四个 GPU flag，因为稳定水退出 Solver 后仍必须留在 Hash、Density 和 Gameplay 查询里。Sleep 同时要求速度和相对密度误差连续稳定 N Tick；Wake 用两阶段 request 避免 GPU 同一 Dispatch 读写 flag 的非确定传播。GPU Activity Counter 直接生成 Indirect Args，零 Awake 时 Solver 是零工作组；非零时仍覆盖完整 capacity，防止固定池中稀疏高位 slot 被 AwakeCount 缩组漏掉。所有调试 Counter 独立计量并低频 AsyncGPUReadback，绝不参与当 Tick 物理控制，teardown 也等待 outstanding ownership 安全结束。**
