# GPU PBF 流体当前生产实现完整解析

> 文档状态：Current Production Only
>
> 适用版本：Unity 6.3，P7 Demo 当前 Water、Poison、Sticky 流体链路
>
> 本文只描述当前生产源码、配置和测试仍支持的实现。开发过程、被替换的表现路径和未落地设想不属于本文，也不能作为模拟面试的事实来源。

## 1. 玩家看到的效果

Water、Poison、Sticky 不是静态贴花或预制动画，而是由 GPU 粒子驱动的可运动液体。投射物命中地面、墙体或其他 Collider 后生成对应材料粒子；粒子受重力、碰撞、不可压缩约束、黏性和内聚力影响，可以下落、聚合、摊开和融合。

三种液体共享一套 GPU PBF Runtime，但通过 MaterialId 和独立参数行呈现不同物性：

- Water：流动性较强，用于 Wet 与灭火。
- Poison：更黏稠，用于 Poisoned 与 Toxic Combustion。
- Sticky：琥珀色、最高黏度与内聚，用于持续减速和 Sticky 反应。

Gameplay 与 Rendering 都来自同一批 GPU Particle State，但读取方式不同：Gameplay 读取低频 Occupancy Snapshot，Rendering 读取 GPU Buffer 重建三维 Surface。

## 2. 为什么选择 GPU PBF

### 2.1 PBF 是什么

基于位置的流体（Position Based Fluids，PBF）把不可压缩条件写成 Position Constraint。每个 Substep 先预测粒子位置，再通过多轮约束迭代修正局部密度，最后由位置变化更新 Velocity。

它不是严格求解 Navier–Stokes 方程，而是面向实时交互的近似方法。优势是约束迭代稳定、容易与 Collision Projection 结合，也适合用 Compute Shader 并行处理大量粒子。

### 2.2 为什么放到 GPU

PBF 的主要成本来自邻域计算。每个粒子都需要访问 Smoothing Radius 内的邻居来估算 Density、Lambda 和位置修正。如果在 CPU 上对所有粒子两两比较，复杂度接近 `O(n²)`；GPU Spatial Hash 把候选限制在附近 Cell，并让粒子 Kernel 并行执行。

代价是 Gameplay 无法像读取普通 C# 数组一样立即访问 GPU Particle Buffer，因此系统额外建立 AsyncGPUReadback 的 Gameplay Projection。

## 3. Assembly 与数据所有权

### 3.1 Game.ElementField

`Game.ElementField` 拥有真实液体 Runtime State：

- Particle Position、Predicted Position、Velocity 与 Metadata。
- Fixed Tick、Substep 和 Solver Iteration。
- Spatial Hash、Collision Proxy 和 Sleep/Wake。
- Spawn、Consume、Convert Command Queue。
- Gameplay Readback 与 Occupancy Snapshot。

主 Runtime 是 `GpuPbfFluidRuntime`。

### 3.2 Game.Rendering

`Game.Rendering` 只读取 `FluidGpuSnapshot`：

- `GpuLiquidSurfaceRenderer`：Density、Anisotropy、Stylized Crown、Marching Cubes、Indirect Draw。
- `LiquidRenderProfile`：Surface Reconstruction 的 Authoring Data。
- `ElementLiquidProcedural.shader`：最终 URP 液体材质。

Rendering 不修改 Particle Position、Material Amount、Reaction 或 Status。

### 3.3 Game.Combat

`Game.Combat` 定义角色状态和 Material Reaction 的纯规则。它不引用 GPU Buffer、Compute Shader 或 ElementWorld Runtime。

## 4. Authoring Data 与 Runtime Snapshot

### 4.1 LiquidSimulationProfile

`LiquidSimulationProfile` 保存整个 Solver 的共享配置：

- Particle Capacity。
- Particle Radius、Mass 与 Rest Density 基线。
- Fixed Tick Rate、Substeps、Solver Iterations。
- Gravity 与 Max Speed。
- Smoothing Radius。
- Hash Table Capacity。
- Collision Friction 与 Restitution。
- Tensile、Vorticity 和 Sleep 参数。
- Simulation Bounds。
- Liquid Material Settings Table。

初始化时它生成不可变 `LiquidSimulationSettings`。资源容量、Buffer Layout 和 Dispatch 依赖这些值，因此进入 Play Mode 后不会在热路径动态重建。

### 4.2 LiquidMaterialSettingsTable

多种液体共享 Solver，但每种材料拥有独立参数行。参数通过 `MaterialId` 索引，当前包含 Density、Viscosity、Cohesion、Max Cohesion Delta Speed 和 Gameplay Amount Scale 等信息。

GPU Buffer 中不是保存 `ScriptableObject` 引用，而是紧凑数值结构。Compute Shader 读取 Particle Metadata 中的 MaterialId，再索引对应参数行。

### 4.3 LiquidRenderProfile

`LiquidRenderProfile` 只控制三维 Surface：

- Target Voxel Size。
- Maximum Resolution Per Axis。
- Bounds Padding。
- Iso Level。
- Maximum Triangle Count。
- Anisotropy 开关、更新间隔和尺度约束。
- Stylized Crown 高度、Falloff 与邻居阈值。

这些值不改变 PBF Particle State，也不改变 Gameplay Occupancy。

## 5. GPU Buffer 与 Particle Metadata

`FluidGpuResourceSet` 在初始化时创建并持有长期 GPU 资源。关键 Buffer 包括：

- Positions：当前世界空间位置。
- PredictedPositions：本 Substep 约束求解中的预测位置。
- Velocities：世界空间速度。
- Metadata：Alive、MaterialId、Sleeping、RequiresSimulation 等紧凑标记。
- SpatialEntries：按 Hash Key 排序的粒子条目。
- CellRanges：每个 Hash Cell 在排序数组中的范围。
- SpatialCells：处理 Hash Collision 时保存真实 Cell 坐标。
- LiquidMaterialParameters：按 MaterialId 索引的物性参数。
- SolverDispatchArgs：Indirect Dispatch 参数。
- GameplaySamples：供 AsyncGPUReadback 的紧凑打包结果。

Buffer 采用固定 Layout，并由 C# Contract Tests 与 HLSL Stride 共同约束。不能只在 C# 增加字段而不更新 Compute Shader，也不能只改 Shader 顺序而不更新 CPU 端结构。

## 6. Spawn 与 Deposit

### 6.1 Projectile 命中

`ElementDepositOnImpact` 在投射物命中后创建 `ElementWriteRequest`。`ElementWorldWriteRouter` 根据 Material Route 判断 Water、Poison、Sticky 应进入 `GpuPbfLiquid` Backend，再由 `FluidDepositQueueAdapter` 转成 `FluidSpawnRequest`。

直接命中的角色状态由 `ProjectileStatusOnImpact` 单独处理，因此“命中立刻获得少量状态”和“地面生成流体”是两个职责清楚的 Component。

### 6.2 Fixed-capacity Spawn Queue

`TryEnqueueSpawn` 只把值类型 Request 放入固定容量 Queue。真正的 Particle Slot 分配和初始化发生在后续 Fixed Tick。Queue 满或 Request 非法时明确返回 false，不在热路径扩容。

Spawn Request 包含：

- World Position。
- Radius。
- Particle Count 或总 Amount。
- MaterialId。
- Initial Velocity。
- Seed。

GPU Lifecycle Kernel 从 Free Pool 取得 Slot，写入 Position、Velocity 与 Metadata，并推进 Topology Version。

## 7. Fixed Tick 与时间模型

`GpuPbfFluidRuntime.Update` 使用 `FluidSimulationClock` 把 `Time.deltaTime` 转换为固定 Tick 数。暂停时不消费 Clock，因此恢复后不会积累一大段 Simulation Debt。

每个 Fixed Tick 的高层顺序为：

```text
Refresh changed collider proxies
→ Upload Spawn / Consume / Convert commands
→ Mark neighbor wake requests
→ Update particle activity and indirect args
→ For each Substep:
     Clear contacts
     Apply gravity
     Predict positions
     Build solver spatial hash
     Repeat Solver Iterations:
         Compute density and lambda
         Compute delta position
         Apply delta position
         Apply tensile correction when enabled
         Project collisions
     Update velocities
     Apply cohesion
     Apply viscosity
     Apply vorticity
     Apply collision velocity response
     Clamp velocities
     Commit positions
→ Publish current-position spatial hash
```

固定 Tick 让 Solver 结果不直接依赖 Rendering Frame Rate；Substep 缩短单次积分跨度；Solver Iteration 提高约束收敛程度。三者都会增加成本，不能把它们当作免费的画质参数。

## 8. Spatial Hash

### 8.1 目标

邻域 Kernel 只需要检查 Smoothing Radius 附近的粒子。系统把世界位置除以 Cell Size 得到离散 Spatial Cell，再 Hash 到固定容量表。

### 8.2 数据流程

```text
Predicted Position
→ Build Spatial Entry (hash, particle index)
→ GPU Bitonic Sort
→ Build Cell Range
→ Neighbor Kernel 查询附近 Cell Range
→ 使用真实 Cell 坐标过滤 Hash Collision
```

排序后的同一 Hash Key 条目连续存放，CellRanges 可以用起止索引定位候选。由于不同真实 Cell 可能产生相同 Hash，Kernel 还必须比较 `SpatialCells`，不能把 Hash 相等当作空间位置相同。

Solver 每个 Substep 在 Predict 后构建一次 Candidate Snapshot。约束迭代复用候选集合，前提是 Position Correction 被限制在安全范围内。完整 Tick 结束后再发布 Current-position Hash，供 Rendering Density Reconstruction 使用。

## 9. PBF Constraint

### 9.1 Density

粒子密度来自邻居质量和 Smoothing Kernel 的加权和：

```text
ρ_i = Σ_j m_j W(p_i - p_j, h)
```

其中 `h` 是 Smoothing Radius。距离超过 `h` 的粒子不参与该粒子的密度估算。

### 9.2 Constraint 与 Lambda

不可压缩目标可以写成：

```text
C_i = ρ_i / ρ0 - 1
```

`ρ0` 是 Rest Density。Solver 根据 Constraint Gradient 计算 Lambda，再根据自身和邻居 Lambda 计算 Delta Position。

### 9.3 Strict two-phase 写回

Compute Shader 不能让所有 Thread 一边读取邻居 Position、一边直接改写共享 Position，否则结果依赖 Thread 调度顺序。当前实现分成：

1. Compute Density/Lambda，只写自己的 Lambda Slot。
2. Compute Delta Position，只写自己的 Delta Slot。
3. Apply Delta Position，统一修改 Predicted Position。

这是 GPU 并行正确性的核心不变量。

## 10. Collision

场景 Collider 先被转换为紧凑 `FluidColliderProxy`，GPU Solver 不会在每个 Particle Thread 中调用 Unity Physics API。

每个 Solver Iteration 在位置修正后重新执行 Collision Projection，因为 Density Correction 可能再次把粒子推入墙体。Velocity Filter 完成后，再应用一次 Collision Velocity Response，分离法线速度、摩擦和弹性；之后不再有其他 Filter 把速度改回墙内方向。

Collider Proxy 发生变化时会上传并唤醒相关粒子。固定容量 Proxy Buffer 防止运行时无限增长。

## 11. 液体物性

### 11.1 Viscosity

黏性（Viscosity）通过 XSPH 风格的邻居速度平滑减少局部速度差。值越高，液体相邻粒子越倾向于一起运动。Sticky 使用更高黏度，因此流动和摊开更慢。

### 11.2 Cohesion

内聚力（Cohesion）对特定距离范围内的邻居施加有限速度修正，使液团更容易保持整体。它只在局部邻域内生效，不把所有粒子拉向一个全局中心；超过支持距离后修正归零，因此液体仍可分裂和重新融合。

### 11.3 Tensile 与 Vorticity

Tensile Correction 抑制粒子在自由表面附近不合理地互相吸附或塌缩；Vorticity 补偿数值耗散造成的旋转细节损失。它们是可调的实时近似，不代表现实流体参数的严格物理单位。

## 12. Sleep、Wake 与活动范围

Particle Alive 不等于每个 Tick 都要参与 Solver。Metadata 分开保存：

- Alive：Slot 当前属于有效液体。
- Sleeping：粒子已经稳定，可跳过大部分求解。
- RequiresSimulation：这一 Tick 必须参与 Solver。

粒子在连续多个 Tick 低于速度阈值后可以 Sleeping。新 Spawn、Consume、Convert、Collider 变化、活动 Bounds 变化或邻居 Wake Request 会重新唤醒相关粒子。

`SolverDispatchArgs` 由 GPU Activity Pass 写入；当没有需要求解的粒子时，Indirect Dispatch 不启动工作组。这样稳定液体仍能被 Gameplay 和 Rendering 读取，但不会持续支付完整 Solver 成本。

## 13. 多液体共享 Runtime

Water、Poison、Sticky 共用：

- Particle Pool。
- Spatial Hash。
- Solver Dispatch。
- Collider Proxy。
- Activity/Sleep Buffer。
- Gameplay Readback Buffer。

每个粒子的 MaterialId 决定：

- 读取哪一行 Liquid Material Parameters。
- Gameplay Snapshot 统计到哪一种材料。
- 哪个 `GpuLiquidSurfaceRenderer` 会在 Density Pass 中采样它。
- Material Reaction 如何消费或转换它。

这种设计减少 Runtime 复制，但也要求所有 GPU Layout、Parameter Table 和 Material Catalog 保持一致。

## 14. Gameplay Readback

### 14.1 为什么需要 Projection

GPU Particle Buffer 是 Simulation Truth，但 `StatusController`、Material Reaction 和 CPU Physics 需要在 CPU 上查询。同步读取 GPU 会阻塞 CPU 等待 Render Thread，因此当前使用低频 `AsyncGPUReadback`。

### 14.2 Readback Lease

`FluidGameplayOccupancyBridge` 在 `LateUpdate` 申请 Readback Lease。GPU 先运行 Pack Kernel，把每个有效粒子的世界位置、MaterialId 和 Amount Scale 写入紧凑 Buffer。Graphics Queue 保证它排在本 Frame 的 Simulation Dispatch 之后。

异步回调完成后，Bridge 在主线程构建新的 `LiquidGameplaySnapshot` 并一次性发布 Version。资源释放需要等待 Outstanding Readback 完成，避免释放正在被 GPU/Driver 使用的 Buffer。

### 14.3 Occupancy Snapshot

Snapshot 按 Global Cell 与 MaterialId 聚合为 GMU（Gameplay Material Unit）。GMU 是 Gameplay 投影标尺，不等同于现实质量。

消费者可以：

- 查询某个 Cell 中某种材料的 Amount。
- 枚举某种材料占用的 Cell。
- 查询每个 Particle 对应的 Amount Scale。

Snapshot 更新频率低于 Rendering，因此 Gameplay 状态允许有受控延迟，但不会读取半完成数据。

## 15. 世界材料反应

`LiquidCellReactionSystem` 读取同一版本的 Liquid Occupancy 与 Fire Cell Samples，使用 `MaterialReactionCatalogSnapshot` 决定反应，再把结果计划成固定容量命令：

- `ElementCellDeltaRequest`：减少 Fire。
- `ElementCellAddRequest`：生成 Fire。
- `FluidConsumeCommand`：删除指定材料粒子。
- `FluidConvertCommand`：把粒子 MaterialId 原位转换。
- `WorldReactionDamageCommand`：产生范围伤害。

Command Batch 先检查容量，再整体提交。这样不会只删除一边却丢失另一边的结果。

当前重要关系：

- Water 消耗量与 Fire 移除量独立，约 1 Water 移除 2 Fire。
- Water 接触 Sticky 时，有限数量 Water 粒子原位变成 Sticky。
- Fire 接触 Sticky 时消费 Sticky 并增加 Fire。
- Fire 与 Poison 满足条件后产生 Toxic Combustion。

## 16. 单 Surface Reconstruction

当前每种液体使用一条完整 Active Bounds 的三维表面链：

```text
FluidGpuSnapshot
→ Plan one Density Grid
→ Gather Surface Support / Anisotropy
→ Dispatch Density
→ Dispatch Marching Cubes
→ Build Indirect Arguments
→ RenderPrimitivesIndirect
```

每个 Water、Poison、Sticky Renderer 分别按 Target MaterialId 过滤粒子，但共享同一个 Fluid GPU Snapshot。

## 17. Density Lattice

Density Lattice 是覆盖 World Bounds 的三维标量场。每个 Voxel Sample 保存该世界位置附近目标液体粒子的密度贡献。

`FluidSurfaceGridPlanner` 根据：

- Active Bounds。
- Bounds Padding。
- Target Voxel Size。
- Maximum Resolution Per Axis。

计算 Grid Resolution、World Origin 和实际 Voxel Size。Resolution Clamp 后必须重新计算 Voxel Size，确保 Grid 仍覆盖完整 Bounds。

三维网格成本近似为：

```text
ResolutionX × ResolutionY × ResolutionZ
```

每轴扩大两倍，总 Sample 数约扩大八倍。因此 Target Voxel 与 Resolution 是显存和 Compute 成本的重要控制点。

## 18. Anisotropic Reconstruction

球形 Density Kernel 容易让液体表面看成一串圆球。Anisotropy 根据粒子邻域的空间分布构造方向性 Transform，使 Kernel 沿液流方向拉长、沿薄轴收缩。

当前步骤包括：

1. Gather 邻居 Mean 与 Support。
2. 估算局部协方差方向。
3. 构造受最小尺度、最大尺度和比例上限约束的 Transform。
4. Density Pass 使用 Transform 计算方向性距离。

邻居不足时回退到以原粒子为中心的 Isotropic Identity，避免孤立粒子产生不稳定长针。Anisotropy 可以隔帧更新，但 Particle Topology Version 改变时必须立即更新，防止新 Slot 读取旧 Transform。

## 19. Stylized Crown

Stylized Crown 是 Presentation-only 的卡通体积增强。它根据 Surface Support 判断粒子更接近液团内部还是边缘：

- 边缘邻居少，不额外抬高，保持轮廓收口。
- 内部邻居充分，Density Kernel 向世界 `+Y` 延展，形成较厚的中央体积。

它不修改 Particle Position、Collision、Gameplay Occupancy 或 Reaction。Crown Height Ratio 表示相对于 Smoothing Radius 的表现延展，不是实际粒子高度。

## 20. Marching Cubes

Marching Cubes 遍历 Density Grid 的每个立方体 Cell，比较八个 Corner Density 与 Iso Level，得到 8-bit Case Index。查表后在发生符号变化的 Edge 上插值 Vertex Position，并输出 Triangle。

核心数据：

- Density Texture：三维标量场。
- Triangle Table：256 种 Corner Case 到 Edge 序列的映射。
- Triangle Buffer：Position 与 Normal。
- Triangle Counter：真实生成数量。
- Overflow Counter：超出硬容量的数量。
- Indirect Arguments：最终 Vertex Count 与 Instance Count。

Normal 来自 Density Gradient，表示标量场增长最快方向。Vertex Shader 使用 World-space Position 转到 Clip Space；Fragment Shader 再计算液体颜色、Fresnel、Foam、Wave Normal、Lighting 与 Transparency。

Triangle Buffer 固定容量，超过上限时增加 Overflow Counter，而不是越界写 GPU Memory。

## 21. Procedural Indirect Draw

Surface 没有创建或更新 Unity `Mesh`。Compute Shader 直接写 Triangle Buffer 和 Indirect Arguments，`GpuLiquidSurfaceRenderer` 调用：

```text
Graphics.RenderPrimitivesIndirect
```

Vertex Shader 根据 `SV_VertexID` 计算 Triangle Index 与 Corner Index，从 Structured Buffer 读取对应 Position/Normal。

`RenderParams.worldBounds` 必须等于实际 Density Grid 的 World Bounds。URP 使用它进行整批 Culling 和透明排序；Bounds 错误会导致 GPU 已经生成 Triangle，但 Draw 被相机剔除。

## 22. Liquid Shader

`ElementLiquidProcedural.shader` 是 URP Transparent Pass。职责包括：

- Vertex Stage：读取 Procedural Triangle，输出 Clip-space Position、World Position 和 Normal。
- Fragment Stage：结合 Shallow/Deep Color、Fresnel、Foam、Wave Normal 和 URP Lighting 计算最终颜色。
- Depth：使用当前 Scene Depth 参与软交界或深浅判断。
- Transparency：通过 Alpha Blend 与场景合成。

Material 决定颜色和表现参数；Shader 定义 GPU 程序；Triangle Buffer 提供几何；Renderer 绑定资源并提交 Draw。这四者不能混为一谈。

## 23. Fire Parcel 是独立表现链

Fire 不进入液体 Particle Pool。`GpuFireParcelRenderer` 从 Fire Cell 采样 Seed，驱动独立的 GPU Parcel Lifecycle，并重建 Fire Surface 与 Gas 表现。

Fire Parcel 的 Surface/Gas 交接是当前火焰视觉的一部分，不属于液体 Surface Pipeline。面试时必须分别描述，不能把 Fire Parcel 的 Billboard 或 Gas Shader 说成 Water、Poison、Sticky 的表面实现。

## 24. 性能约束

### 24.1 CPU 热路径

- Queue、Upload Array、Readback Storage 和 Callback 在初始化时创建。
- 不在 `Update`、Fixed Tick 或 `LateUpdate` 使用 LINQ。
- 不创建 Closure、临时 List 或逐帧 Array。
- Shader Property ID 预缓存。
- Debug Readback 低频轮询，不同步读取整个 Buffer。

### 24.2 GPU 成本

主要成本来自：

- Particle Capacity。
- Fixed Tick × Substeps × Solver Iterations。
- Spatial Hash Sort。
- 邻居候选数量。
- Density Grid 三维 Sample 数。
- Marching Cubes Cell 数与 Triangle 数。
- Water、Poison、Sticky 各自的 Surface Reconstruction。

优化必须先用 Profiler 确认瓶颈属于 Simulation、Readback 还是 Surface，不能只凭画面卡顿修改参数。

## 25. 当前诊断字段

`GpuPbfFluidRuntime` 在 Editor/Development 暴露低频计数，例如 Awake、Sleeping、Interest、Rejected Spawn 和 Queue Overflow。

`GpuLiquidSurfaceRenderer` 暴露：

- Pipeline Stage。
- Has Snapshot / Resources Ready。
- Grid Resolution 与 Voxel Size。
- Triangle Count。
- Indirect Vertex/Instance Count。
- Triangle Overflow。
- Draw Bounds。
- 第一组三角形 Position、Normal 与 Geometry Stage。

诊断顺序：

```text
Waiting for Snapshot
→ Waiting for Resources
→ Density / No Surface Triangles
→ Indirect Arguments
→ Geometry and Draw Bounds
→ Shader / Depth / Culling / Fragment
```

只有前一层有证据通过后，才进入后一层。

## 26. 常见问题的正确归因

### 26.1 有 Wet/Poisoned/Sticky，但液体不可见

这证明 Gameplay Snapshot 至少曾经包含对应材料，不证明 Surface Renderer 正常。检查 Fluid Snapshot、Density、Triangle、Indirect Args、Shader Import 和 World Bounds。

### 26.2 液体可见，但角色状态稍晚出现

Rendering 直接读取 GPU Buffer，Gameplay 读取低频 AsyncGPUReadback Snapshot，两者频率不同。只要延迟处于配置的 Snapshot Interval 内，就属于架构预期。

### 26.3 粒子穿墙

检查 Collider Proxy 是否收集、上传、参与每轮 Position Projection，以及 Velocity Response 后是否仍有 Kernel 改写向墙内速度。

### 26.4 液体碎散

先区分 Simulation 与 Reconstruction：

## 29. 模拟面试核心回答

> 我在项目里实现的是一套多材料共享的 GPU PBF 流体。Water、Poison 和 Sticky 共用固定容量 Particle Pool、Spatial Hash、PBF Solver、Collision 和 Sleep/Wake，粒子通过 MaterialId 索引不同的黏性、内聚力和 Gameplay Amount 参数。每个 Fixed Tick 会先处理 Spawn、Consume 和 Convert，再按 Substep 执行重力、位置预测、Spatial Hash、密度约束、碰撞投影和速度修正。为了避免 GPU 数据和 Gameplay 强耦合，我用低频 AsyncGPUReadback 把粒子投影成按 Global Cell 聚合的 Occupancy Snapshot，角色状态与世界反应读这份快照；Rendering 则直接读取 GPU Buffer，通过 Density Lattice、Anisotropy、Stylized Crown 和 Marching Cubes 生成 Triangle Buffer，最后用 Procedural Indirect Draw 交给 URP Shader。这样 Gameplay、Simulation 和 Presentation 使用同一材料事实，但各自保持独立频率和责任。它的 Trade-off 是三维 Density 与 Marching Cubes 有明显 GPU 成本，Gameplay Readback 也存在受控延迟，所以我用固定容量资源、Spatial Hash、Solver-Sleeping、Indirect Dispatch、Buffer 复用和分层 Profiler 诊断控制风险。

## 30. 本文结论

当前 GPU 流体的核心链路是：统一 MaterialId 驱动共享 PBF Solver，异步投影支撑 Gameplay，完整三维 Density 与 Marching Cubes 支撑 Rendering。判断实现是否正确时必须分别验证 Particle Simulation、Gameplay Snapshot、Reaction、Surface Geometry 与 Shader，不能用其中一层的成功替代其他层的证据。

## 31. Chunk Streaming：自动 Archive 半链

当前实现已经能在 Interest Chunk 变化并经过 Grace 后，把 Warm Region 外的 GPU 粒子归档到 RAM Cell Store；当 Free Particle 低于 Gameplay Reserve 时，容量压力可立即触发归档。`FluidChunkStreamingRuntime` 处于普通 GPU Simulation `Update` 之后，用 Transaction Id 串行化转移过程。

一次 Archive 的权威顺序为：

```text
GPU Lock + Pack
→ AsyncGPUReadback
→ callback 只登记完成状态
→ 下一次 Update 聚合为 (Chunk, LocalCell, Material)
→ RAM Store 原子 Commit 成功
→ GPU Release，slot 返回 Free Stack
```

任一步失败都在 RAM Store 发布前调用 GPU Cancel；未取得 Backend Lease 时不会误调用 Cancel/Release。组件销毁时等待已发出的 Readback，然后取消 GPU 事务并恰好释放一次 Lease，避免 Domain Reload 留下锁定粒子。

`ElementWorldRuntime` 只有在 Profile 开启 Streaming、有效液体后端为 GPU PBF、且 `FluidChunkStreamingRuntime` 初始化成功时，才把液体写入口切到 Streaming Runtime。Warm 区写入立即进入 GPU；Archive/Cold 区写入保存到固定容量 `FluidPendingWriteQueue`。当前 Restore 尚未实现，所以生产场景的 Feature Toggle 继续关闭；本节证明的是“远处流体能够安全转成 RAM 真值并释放 GPU 容量”，还不能证明“返回后流体恢复可见”。

新增 Focused Tests 覆盖 `FluidChunkStreamingPlannerTests`、`FluidChunkArchiveBuilderTests`、`FluidChunkArchiveStoreTests`、`FluidPendingWriteQueueTests`、`FluidChunkTransferStateTests`、`GpuFluidChunkArchiveTests` 和 `FluidChunkStreamingRuntimeTests`。本轮 Unity 完整 EditMode Gate 结果为 536 Passed / 0 Failed / 0 Skipped。

## 32. Restore Planner：从 Cell Amount 回到确定性粒子

Cold Archive 以 Cell 为单位保存总 Amount，恢复前必须重新扩展为逐粒子上传数据。`FluidChunkRestorePlanner` 要求 Amount 能被该材料的 Amount Scale 整除，然后精确生成商所表示的粒子数；无法整除视为 Archive 损坏并拒绝恢复，避免取整制造或吞掉 Gameplay 物质量。

粒子在 Cell 内按三维 lattice 放置并加入受限的确定性 jitter。随机种子只依赖 Archive 身份与 Snapshot Version，因此重复恢复结果可重放，不受全局随机状态、帧率或遍历顺序影响。每个 `FluidGpuRestoreParticle` 固定为 32 byte，包含 World Position、MaterialId、平均 Velocity 与 TransactionId；GPU Reservation 回执 `FluidGpuTransferStatus` 固定为 16 byte。当前 CPU Planner 和布局测试已完成，GPU all-or-nothing Reserve/Stage/Activate/Rollback 仍在下一实现步骤中。

## 33. GPU Restore 事务与 Gameplay Topology Gate

Restore 使用 `Reserve → Stage Core → Stage Auxiliary → Status Readback → Activate/Rollback`。Reservation 单线程一次性扣减整批 FreeCount并保留 Gameplay Spawn Reserve；容量不足不接触任何 Slot。Stage 粒子只有 `RestoreLoading`，没有 Alive。Activate 才设置 Alive 与活动 Flags；Rollback 只回收仍带 RestoreLoading 的 Slot，所以重复调用保持幂等。

`GpuPbfFluidRuntime` 持有 Restore Transaction Lease，上传预分配粒子数组并通过 16-byte Status Buffer 返回 Reservation 结果。Commit 后发布新的 Topology Version。Streaming Runtime 在 Gameplay Occupancy 的 Topology Version 追上前保留 RAM Archive，追上后才删除 Cold Record。真实 Compute fixture 已验证容量失败、Stage 非 Alive、ActiveBounds 分类、错误 TransactionId、Rollback exactly-once 与 Counter 守恒；完整 EditMode Gate 为 544 Passed / 0 Failed / 0 Skipped。

## 34. Streaming Gameplay Authority 与写入重放

`FluidChunkStreamingRuntime` 同时实现 `IFluidDepositSink` 与 `ILiquidOccupancyReadOnly`。Warm GPU Chunk 读取 Gameplay Bridge；刚恢复但 Topology 尚未追上的 Chunk读取 RAM Archive；Cold Region 外拒绝查询。组合查询只暴露 Warm Bounds，并在复制 Occupied Cell 时按 Chunk Authority 去重。

写入覆盖 Cold 或 Transfer 区域时，完整 `ElementWriteRequest` 进入固定 Ring Buffer。恢复完成后按 FIFO 重放；队首仍不可写或 GPU Sink 拒绝时停止，不先 Dequeue。这样 Projectile 的 Amount、Radius、Falloff、Velocity 和 SurfaceNormal 都不会因延迟重新计算。

Reaction 与 Exposure 使用不同读视图。Exposure 只关心玩家附近“当前应该接触什么”，所以读取 Streaming 组合权威；Reaction 会发出只能命中真实 GPU 粒子的 Consume/Convert Command，因此只读取 GPU Gameplay Bridge。完整调用链为 `Projectile → WriteRouter → Streaming Deposit → GPU/Pending → Archive/Restore → Gameplay Query → Reaction/Exposure`。本轮完整 EditMode Gate 为 547 Passed / 0 Failed / 0 Skipped，并验证 Idle Tick 与 Warm Query 零 managed allocation。

## 35. Phase C 完成：GPU Resident 与 RAM Archive 的完整生命周期

Phase C 结束后的流体生命周期为：Warm Region 中的逐粒子数据由 GPU PBF 模拟；离开 Warm+Padding 且经过 2 秒 Grace 后，GPU 锁定候选并异步打包；CPU 按 `(Chunk, LocalCell, Material)` 聚合 Amount 与平均速度，只有 RAM Store 原子提交成功才释放对应 Slot。返回区域时，CPU 按材料 Amount Scale 确定性展开粒子；GPU 一次性 Reservation 成功后先写 `RestoreLoading`，状态回读匹配 Transaction 才 Activate。Gameplay Snapshot 追上新 Topology 前，RAM Archive 继续回答查询，之后才删除 Archive Record。

场景启用参数为 Warm Padding=1、Archive Grace=2 s、最多 512 个 Archive Chunk、65536 条 Cell Record、256 条 Pending Write、512 个 Gameplay Spawn Reserve。Water 仍为 8 GMU/particle，Poison 与 Sticky 仍为 4 GMU/particle；Streaming Planner 始终读取材料自己的 Scale，未把比例硬编码或强行统一。

真实 DX12 Sandbox 对 24 个目标粒子完成 24 个恢复，最终 Pool 为 Alive=30、Free=8162、Dropped=0。D3D11 Development Player 对 4096 粒子得到 Peak Archive=4096、Restored=4096、最终 Alive=4096、Free=4096、Dropped=0；Archive/Restore Error 与 Rollback 均为 0。P7/P8 保存场景 Smoke 分别提交 2302 与 24 粒子，未发生池丢弃。`GpuLiquidSurfaceRenderer` 继续读取同一个 GPU Source；Archive 不创建第二套 Renderer，Cold 数据也不会被 Surface Reconstruction 扫描。

本阶段的性能边界同样明确：Target 60 的 A02 P99 帧间隔为 17.946 ms，首次 Restore 附近出现一次 144 B GC，后续 Restore 为 0 B；单次 Archive/Restore wall duration 峰值约 50.10/33.56 ms。Phase D 应把恢复批次摊开，并研究稳定液体的低成本局部表示。磁盘持久化、Cold 区连续演化和局部无限注入不属于当前实现。
