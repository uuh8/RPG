# 法术编程系统完整设计解析

创建时间：2026-07-03  
适用版本：当前项目已完成普通火球、修正/多重、触发类火球、定时类火球后的版本  
阅读目标：不是背代码，而是理解这个系统为什么这样拆、每一层负责什么、以后新增法术时应该往哪里扩展。

---

## 0. 先建立总心智模型

这个系统最核心的一句话是：

> 法杖是一段程序，法术是一条指令，施法就是运行一个解释器，解释器输出“本次要发射什么”，运行时再把这些输出变成真实投射物。

如果把它类比成编程语言：

| 游戏概念 | 编程语言类比 | 项目里的实现 |
|---|---|---|
| 法杖栏位 | 源代码数组 | `WandLoadout.Spells` |
| 一个法术图标 | 一条指令 | `SpellDefinition` |
| 普通火球 | 输出指令 | `SpellKind.Emit` |
| 增伤、加速、散射 | 修改状态的指令 | `SpellKind.Modify` |
| 双重、三重 | 改变读取预算的指令 | `SpellKind.Multicast` |
| 触发类火球 | 携带后续指令的输出 | `PayloadTriggerMode.OnImpact` |
| 定时类火球 | 延迟释放后续指令的输出 | `PayloadTriggerMode.AfterDelay` |
| 法术解释器 | 读取程序并生成结果 | `CastEvaluator` |
| 发射真实投射物 | 把纯数据落地到 Unity 场景 | `SpellCaster` |

完整链路如下：

```text
玩家在 UI 里拖拽法术
    ↓
WandLoadout 保存法术序列
    ↓
WizardController 捕获点击与瞄准点
    ↓
PlayerWizardAttackState 到动画释放帧
    ↓
SpellCaster.CastWand(...)
    ↓
CastEvaluator.Evaluate(...) 纯逻辑求值
    ↓
输出 List<EmitCommand>
    ↓
SpellCaster Instantiate 投射物并 Init
    ↓
ProjectileBase 飞行、碰撞、计时
    ↓
进入 Combat 伤害漏斗，或触发 payload 再次施法
```

这套架构最大的价值是：以后新增很多法术时，不应该为每个组合写一个新技能类，而是增加新的“指令类型”或“解释规则”。这就是“法术编程系统”和普通技能系统的区别。

## 1. 开发顺序总览：把复杂玩法拆成可验证的小功能

从效果倒推，这个系统可以拆成 8 个小功能：

1. 定义法术数据：先让“一个法术是什么”变成可配置资产。
2. 编写纯解释器：让一串法术能算出“这次应该发射哪些东西”。
3. 加入修正/多重规则：让前面的法术影响后面的法术。
4. 接入 Unity 运行时：把解释器输出的纯数据变成真实投射物。
5. 接入 Wizard 角色：让左键施法、动画释放帧、瞄准点和法杖系统连起来。
6. 制作法杖编辑 UI：让玩家能在运行时拖拽组合。
7. 加入命中触发：投射物命中后释放后续法术。
8. 加入定时触发：投射物存在一段时间后释放后续法术。

为什么不能一上来就写“定时火球”？

因为定时火球不是一个孤立技能。它依赖前面的所有基础设施：

- 它必须知道“后续法术”是什么，所以需要 payload 机制。
- 它必须能在投射物生命周期中等待，所以需要 `ProjectileBase` 计时事件。
- 它必须能在某个位置再次施法，所以需要 `SpellCaster.RunCast(...)` 支持递归运行一段子序列。
- 它必须不会无限递归，所以需要 `CastEvaluator` 对 payload 做严格后缀捕获。

所以这个功能正确的开发方式不是“写一个 TimedFireball.cs”，而是先建立一套可组合的解释器架构。

## 2. 小功能一：定义法术数据

### 2.1 基础知识和原理

游戏里的技能系统通常有两类信息：

1. 数据：伤害、速度、图标、音效、投射物 prefab。
2. 行为：如何读取数据、何时生成投射物、如何结算伤害。

本项目遵循 `Data-driven` 原则，所以法术本身使用 `ScriptableObject` 存数据，而不是把火球伤害、速度写死在代码里。

核心文件：

- `Assets/_Project/Scripts/Skills/SpellDefinition.cs`
- `Assets/_Project/Scripts/Skills/SpellKind.cs`
- `Assets/_Project/Scripts/Skills/PayloadTriggerMode.cs`
- `Assets/_Project/Scripts/Skills/WandLoadout.cs`
- `Assets/_Project/Scripts/Skills/SpellLibrary.cs`

`SpellDefinition` 是一个法术资产，里面包含三类字段：

```text
通用字段：
DisplayName / Icon / ManaCost

Emit 字段：
ProjectilePrefab / BaseDamage / BaseSpeed / DamageType / CastSfx
PayloadTrigger / PayloadDelaySeconds

Modify 字段：
ModDamageAddFlat / ModDamageMul / ModSpeedMul / ModSpreadAddDegrees

Multicast 字段：
ExtraDraws
```

注意：一个 `SpellDefinition` 不一定都是“发射火球”。它可以是 `Emit`，也可以是 `Modify`，也可以是 `Multicast`。这就是“法术是指令”的关键。

### 2.2 常见实现方案

业界常见做法大致有四种：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 硬编码技能类 | `FireballSkill.Cast()`、`IceSkill.Cast()` | 最直观，适合少量技能 | 组合爆炸，扩展性差 |
| 配表技能系统 | 表里填技能 ID、伤害、特效 | 商业项目常见，策划友好 | 很难表达复杂组合逻辑 |
| `ScriptableObject` 技能资产 | 每个技能一个 SO | Unity 项目常见，编辑器友好 | 如果行为写进 SO 子类，容易类爆炸 |
| 解释器/指令系统 | 法杖是一串指令，解释器运行 | 最适合法术编程 | 初期架构成本更高 |

本项目选择第四种：`ScriptableObject` 负责数据，`CastEvaluator` 负责解释规则。

这不是因为它最简单，而是因为它最符合目标玩法：玩家不是单纯选择一个技能，而是在排列一段“技能程序”。

### 2.3 最终用到的技术

- `ScriptableObject`：保存可复用的法术数据资产。
- `enum : byte`：用 `SpellKind` 区分指令类别，用 `PayloadTriggerMode` 区分 payload 释放条件。
- `CreateAssetMenu`：让 Unity Editor 能通过菜单创建 `SpellDefinition`。
- `FormerlySerializedAs`：从旧的 `IsTrigger` 迁移到新的 `PayloadTrigger`，避免旧资产丢字段。
- `Tooltip` / `Header` / `Min`：改善 Inspector 配置体验，降低填错概率。

`PayloadTriggerMode` 的意义很重要：

```text
None       = 普通投射物
OnImpact   = 命中后释放后续法术
AfterDelay = 存活指定时间后释放后续法术
```

以前如果只有 `bool IsTrigger`，只能表达“是不是触发”。现在用 enum 后，可以自然扩展更多条件，例如以后可能有：

- `OnExpire`
- `OnBounce`
- `OnPierce`
- `OnOwnerCommand`

这就是从 `bool` 升级为 `enum` 的架构收益。

### 2.4 架构设计与拆解

这一层处在 `Game.Skills` 模块。

它不依赖 `Game.Character`，也不依赖 `Game.UI`。这是正确的，因为法术数据应该是底层玩法数据，不应该知道“谁在施法”或“UI 怎么显示”。

脚本职责：

| 脚本 | 职责 |
|---|---|
| `SpellKind.cs` | 定义法术指令类别：`Emit` / `Modify` / `Multicast` |
| `PayloadTriggerMode.cs` | 定义 payload 释放条件 |
| `SpellDefinition.cs` | 单个法术的数据定义 |
| `WandLoadout.cs` | 一根法杖的法术序列和基础抽取数 |
| `SpellLibrary.cs` | UI 调色板可展示的所有法术来源 |

关键设计点：

`SpellDefinition` 没有自己实现 `Cast()`。这是刻意的。

如果每个法术自己实现施法逻辑，就会变成：

```text
FireballSpell.Cast()
TriggerFireballSpell.Cast()
TimedFireballSpell.Cast()
TripleFireballSpell.Cast()
DamageBoostedTimedTriggerFireballSpell.Cast()
```

组合越多，类越多。最终系统会变成不可维护的“技能特例堆”。

当前架构里，`SpellDefinition` 只是数据，真正的“组合含义”由解释器统一解释。

### 2.5 踩坑与 Debug

1. `bool IsTrigger` 不够扩展  
   早期命中触发可以用一个 bool 表达，但定时触发加入后，bool 无法区分触发条件。解决方式是引入 `PayloadTriggerMode`。

2. 旧资产迁移问题  
   如果直接删掉 `IsTrigger` 字段，已有触发类火球资产可能变回普通火球。解决方式是用 `FormerlySerializedAs("IsTrigger")` 和 `OnValidate()` 迁移旧值。

3. 图标不是行为  
   UI 左上角的小太阳只是表现层提示，真正决定行为的是 `SpellDefinition.PayloadTrigger`。不能用图标来判断法术逻辑。

### 2.6 面试 Q&A

**Q：为什么用 `ScriptableObject` 存法术，而不是 MonoBehaviour？**  
A：法术定义是数据资产，不需要挂在场景对象上，也不需要生命周期回调。`ScriptableObject` 适合做可复用配置，多个法杖和 UI 都可以引用同一个法术资产。

**Q：为什么不让每个 `SpellDefinition` 子类自己实现逻辑？**  
A：这个系统核心是组合。如果每种行为都做子类，组合逻辑会分散到大量类里，难以保证顺序、修正、触发、递归的一致性。统一解释器能把组合语义集中管理。

## 3. 小功能二：纯解释器 `CastEvaluator`

### 3.1 基础知识和原理

`CastEvaluator` 是整个系统的大脑。

它做的事情不是发射火球，而是回答一个问题：

> 给我一串法术、一点法力、一个初始修正状态，我应该输出哪些 `EmitCommand`？

它的输入：

```text
spells        = 法术序列
baseDraws     = 基础抽取数
availableMana = 当前可用法力
incomingMods  = 外部传入的修正状态
output        = 输出列表，复用避免频繁分配
```

它的输出：

```text
List<EmitCommand>
CastSummary
```

`EmitCommand` 是“本次发射命令”的纯数据快照，包含：

- 投射物 prefab
- 最终伤害
- 最终速度
- 伤害类型
- 散射角
- 音效
- payload
- payload 的触发条件
- payload 的延迟时间
- payload 捕获时的修正快照

### 3.2 常见实现方案

| 方案 | 特点 | 是否适合本项目 |
|---|---|---|
| 技能组合查表 | 预先配置“火球+增伤=强火球” | 不适合，组合数量爆炸 |
| `if/else` 顺序扫描 | 直接在施法代码里判断每个法术 | 初期能跑，但运行时和规则耦合 |
| 行为树 / 节点图 | 每个节点有输入输出 | 强大，但 MVP 成本偏高 |
| 解释器 | 一次扫描指令序列，输出命令 | 当前最合适 |
| 小型 VM / Bytecode | 编译成字节码再执行 | 过重，当前没必要 |

当前选择解释器，因为它能在复杂度和可扩展性之间取得平衡。

### 3.3 最终用到的技术

- `static class CastEvaluator`：纯逻辑，无 Unity 场景依赖。
- `readonly struct CastSummary`：返回法力消耗和是否 fizzle。
- `readonly struct EmitCommand`：输出命令不可变，避免运行时被随意修改。
- `CastModifierState`：不可变修正状态，每次 `Apply` 返回新快照。
- `List<EmitCommand> output` 由外部传入并复用，避免每次施法都 new 一个列表。
- `IReadOnlyList<SpellDefinition>`：解释器只读法术序列，不直接修改法杖。

解释流程简化如下：

```text
drawBudget = baseDraws
mods = incomingMods

从左到右读取 spells:
    Modify:
        mods = mods.Apply(spell)

    Multicast:
        drawBudget += spell.ExtraDraws

    Emit:
        如果 drawBudget <= 0，停止发射
        如果法力不足，fizzle 并停止
        如果带 payload:
            捕获后缀作为 payload
            输出一个 EmitCommand
            结束当前层
        否则:
            输出一个普通 EmitCommand
```

### 3.4 架构设计与拆解

这一层仍然在 `Game.Skills`。

关键原则：`CastEvaluator` 不知道 Unity 场景，也不调用 `Instantiate`。

它不应该知道：

- 玩家是谁
- 投射物生成在哪里
- Rigidbody 怎么飞
- AudioSource 怎么播放
- 敌人怎么受伤

它只知道“法术规则”。

相关脚本：

| 脚本 | 职责 |
|---|---|
| `CastEvaluator.cs` | 法术序列解释器 |
| `CastModifierState.cs` | 当前修正状态 |
| `EmitCommand.cs` | 解释器输出命令 |
| `SpellAiming.cs` | 多发散射角计算 |
| `CastEvaluatorTests.cs` | 验证解释器规则 |
| `CastModifierStateTests.cs` | 验证修正叠加 |
| `SpellAimingTests.cs` | 验证散射角 |

### 3.5 为什么 payload 是“后缀捕获”

假设法杖是：

```text
[触发火球] [普通火球] [普通火球]
```

解释器读到第一个触发火球时，会把它后面的序列捕获成 payload：

```text
触发火球.payload = [普通火球] [普通火球]
```

然后当前层结束。

为什么要结束当前层？

因为“触发火球”的语义是：先发射一个携带后续法术的火球，后续法术要等它触发时再释放。如果当前层不结束，那么后续普通火球会立刻发射一次，命中后又发射一次，语义就错了。

为什么 payload 只捕获后缀？

因为这样天然防止无限递归。每深入一层，待执行序列都会更短。

错误设计示例：

```text
触发火球命中后重新执行整根法杖
```

这样如果法杖第一张还是触发火球，就可能无限链式触发，必须额外加递归深度保护、输出数量保护、时间保护。当前 MVP 用“严格后缀”避免了这个问题。

### 3.6 踩坑与 Debug

1. 解释器不能实例化 Unity 对象  
   如果 `CastEvaluator` 里直接 `Instantiate`，它就无法做 EditMode 纯测试，也会让 `Game.Skills` 反向依赖运行时场景。

2. 修正状态必须是快照  
   触发类法术需要把命中后 payload 的修正状态带过去。如果只保存引用或运行时重新计算，可能因为外部状态变化导致命中时表现不一致。

3. payload 为空时不能仍然标记为触发  
   如果触发类火球后面没有法术，应该退化为普通投射物，否则命中时订阅事件但没有东西释放，Debug 会很难判断。

4. 多重和触发的交互要明确  
   当前语义是：读到触发类 Emit 后捕获后缀并结束当前层。也就是说，触发类法术更像“控制流指令”，不是普通多发的一员。

### 3.7 面试 Q&A

**Q：为什么把核心规则做成 pure logic？**  
A：因为法术组合规则复杂，最需要可测试性。纯逻辑不依赖 Unity 生命周期和场景对象，可以用 EditMode tests 验证 modifier、multicast、payload 捕获、mana fizzle 等核心语义。

**Q：如何避免触发类法术无限递归？**  
A：payload 捕获的是当前法术之后的严格后缀。每一层递归都会让待执行序列变短，所以天然收敛。除非未来改成重新执行整根法杖，否则不需要额外递归深度保护。

## 4. 小功能三：修正、多重、散射、法力

### 4.1 基础知识和原理

这部分解决的是“法术之间如何互相影响”。

普通技能系统里，一个火球的伤害就是火球自己的伤害。但法术编程系统里，前面的法术可以改变后面的法术：

```text
[增伤] [火球]
```

这里“增伤”不是发射物，而是修改解释器内部的 `CastModifierState`。

```text
[三重] [火球] [火球] [火球]
```

这里“三重”不是自己发射三个火球，而是增加 `drawBudget`，允许后续更多 `Emit` 被读取。

### 4.2 最终技术实现

`CastModifierState` 保存当前累计修正：

- `DamageAddFlat`
- `DamageMul`
- `SpeedMul`
- `SpreadDegrees`

`Modify` 指令调用：

```text
mods = mods.Apply(spell)
```

`Emit` 指令被烘焙成 `EmitCommand` 时，读取当前 `mods`：

```text
damage = (BaseDamage + DamageAddFlat) * DamageMul
speed  = BaseSpeed * SpeedMul
spread = SpreadDegrees
```

`Multicast` 修改：

```text
drawBudget += ExtraDraws
```

`SpellAiming` 负责把散射角转换成每个投射物的 yaw 偏移。解释器只输出“需要散射多少度”，真正转方向由 `SpellCaster` 做。

### 4.3 架构意义

这里最重要的是：修正类法术不直接找“下一个火球”。

它只是改变当前解释器状态。后面所有 Emit 都会自然读取这个状态。

这比“增伤法术主动修改后一个法术资产”更安全，因为：

- 不会污染 `ScriptableObject` 原始资产。
- 不会让 UI 中的法术数据被运行时改坏。
- 不需要处理引用共享导致的副作用。
- 可以把修正快照传给 payload。

### 4.4 踩坑与 Debug

1. 不能修改 `SpellDefinition.BaseDamage`  
   那是资产数据。如果运行时改它，Play Mode 中所有引用该资产的法杖都会受影响。

2. 散射不应该由解释器直接算 Quaternion  
   解释器不该依赖 Transform、相机、世界方向。它只输出角度，运行时知道发射方向后再应用。

3. 法力 fizzle 要在解释器层处理  
   如果等投射物生成后再扣法力，就很难保证多发、触发、payload 的一致性。

### 4.5 面试 Q&A

**Q：为什么修正状态设计成不可变快照？**  
A：它让一次施法的结果稳定可预测，也方便 payload 捕获。命中触发可能发生在未来某一帧，如果当时重新读取全局 modifier，结果会受后续施法影响。

**Q：Multicast 为什么是增加 draw budget，而不是直接生成多个投射物？**  
A：因为多重本质是控制解释器读取更多后续 Emit。这样它可以和不同 Emit、Modify、Trigger 组合，而不是绑定某一种投射物。

## 5. 小功能四：运行时桥接 `SpellCaster`

### 5.1 基础知识和原理

`CastEvaluator` 只输出命令，不碰 Unity 场景。那谁来真正发射火球？

答案是 `SpellCaster`。

`SpellCaster` 是“纯逻辑”和“Unity 运行时”之间的桥。

它做四件事：

1. 调用 `CastEvaluator.Evaluate(...)`。
2. 根据 `EmitCommand` 实例化投射物 prefab。
3. 调用 `ProjectileBase.Init(...)` 注入伤害、阵营、速度、施法者 Collider。
4. 如果该投射物有 payload，订阅投射物事件，在未来再次运行 payload。

核心文件：

- `Assets/_Project/Scripts/Character/Spells/SpellCaster.cs`

它放在 `Game.Character`，不是 `Game.Skills`。

原因是它需要知道 Unity 场景、Transform、Collider、投射物实例化，这已经是角色运行时层的职责。

### 5.2 常见实现方案

| 方案 | 做法 | 问题 |
|---|---|---|
| `CastEvaluator` 直接 Instantiate | 求值器生成真实投射物 | 破坏纯逻辑，难测试 |
| 投射物自己读取法杖 | 火球 prefab 知道整个法杖 | Combat 反向依赖 Skills/Character |
| 全局 EventBus 发布触发事件 | 投射物命中后发全局事件 | 可行，但对单个投射物 payload 来说过重 |
| `SpellCaster` 作为桥 | 解释器输出命令，运行时执行命令 | 当前选择 |

### 5.3 最终用到的技术

- `MonoBehaviour`：`SpellCaster` 挂在 Wizard 上。
- `Instantiate`：生成投射物 prefab。
- `ProjectileBase.Init(...)`：统一注入投射物运行参数。
- `AudioSource.PlayClipAtPoint(...)`：播放施法音效。
- `HashSet<AudioClip>`：同一次施法里同一个音效只播放一次，避免多重法术声音叠爆。
- `List<EmitCommand>`：复用 `_emits`，避免每次施法分配列表。
- C# event：订阅 `ProjectileBase.Impacted` 和 `ProjectileBase.TimedTriggerElapsed`。

`SpellCaster` 运行 payload 的方式是递归调用内部 `RunCast(...)`：

```text
普通施法：
RunCast(整根法杖, baseDraws, 默认修正, 发射点, 瞄准方向)

命中触发：
RunCast(payload, 1, payloadMods, 命中点, 命中方向)

定时触发：
RunCast(payload, 1, payloadMods, 当前投射物位置, 当前飞行方向)
```

### 5.4 架构设计与拆解

`SpellCaster` 处在中间层：

```text
Game.Skills      ← 纯规则
      ↑
Game.Character   ← SpellCaster，把规则应用到角色运行时
      ↓
Game.Combat      ← ProjectileBase / DamageRequest / IDamageable
```

它同时接触：

- `WandLoadout`
- `CastEvaluator`
- `EmitCommand`
- `ProjectileBase`
- `DamageType`
- `Collider`
- `Transform`

这也是为什么它必须是桥接层。它是少数几个允许同时理解“法术规则”和“Unity 场景”的地方。

### 5.5 踩坑与 Debug

1. prefab 必须带 `ProjectileBase` 派生组件  
   如果 `EmitCommand.ProjectilePrefab` 不是合法投射物，`SpellCaster` 没法 Init。此类问题通常表现为法术图标能拖进法杖，但点击后没有正常投射物。

2. 施法音效不能每个 Emit 都无脑播放  
   三重火球如果播放三次同一个音效，会造成爆音。用 `_playedSfx` 去重。

3. payload 的方向要来自触发点  
   命中触发用命中方向，定时触发用当前飞行方向，而不是重新读取玩家相机方向。否则触发结果会被玩家后续转镜头影响。

4. `SpellCaster` 不应该处理伤害结算  
   伤害仍然走 `ProjectileBase -> IDamageable -> HealthComponent -> DamagePipeline`。这样法术投射物和其他投射物共享同一套 Combat 漏斗。

### 5.6 面试 Q&A

**Q：为什么 `SpellCaster` 在 `Game.Character`，而不是 `Game.Skills`？**  
A：`Game.Skills` 是纯规则层，不应该依赖 Unity 场景对象。`SpellCaster` 需要 Transform、Collider、Instantiate、ProjectileBase，所以它属于角色运行时桥接层。

**Q：触发 payload 为什么由 `SpellCaster` 订阅投射物事件，而不是投射物直接调用解释器？**  
A：投射物属于 `Game.Combat`，如果直接引用 `Game.Skills` 或 `Game.Character`，会破坏模块依赖方向。投射物只广播通用事件，`SpellCaster` 决定如何响应。

## 6. 小功能五：Wizard 角色施法接入

### 6.1 基础知识和原理

玩家按下左键不是立刻在输入回调里发射火球，而是进入角色攻击流程：

```text
WizardController 捕获左键按下
    ↓
记录 ClickAimPoint
    ↓
进入 PlayerWizardAttackState
    ↓
根据动画 normalizedTime 等待释放帧
    ↓
调用 SpellCaster.CastWand(...)
```

这样设计是为了让施法跟角色动画同步。

如果输入瞬间直接发射，动画会变成装饰；如果动画释放帧控制发射，玩家会感觉火球是从动作中释放出来的。

### 6.2 最终用到的技术

- Unity Input System：项目规定不能用旧 `Input` 类。
- `WizardController`：捕获攻击输入、记录点击瞬间瞄准点、排队一次施法。
- `PlayerWizardAttackState`：施法动画状态，在 `ArrowSpawnTime` 类似的释放时机调用 `SpellCaster`。
- `Animator.CrossFadeInFixedTime`：代码驱动进入施法动画。
- `ResolveAimTargetPoint`：屏幕中心瞄准辅助，锁定点击瞬间目标点。

### 6.3 架构设计与拆解

这一层涉及：

| 脚本 | 职责 |
|---|---|
| `WizardController.cs` | Wizard 输入与施法队列 |
| `PlayerWizardAttackState.cs` | 施法动画时序 |
| `SpellCaster.cs` | 真正运行法杖 |
| `PlayerControllerBase.cs` | 共享移动、状态机、瞄准辅助 |

关键点是：`WizardController` 不解释法术序列。它只负责“什么时候施法”和“向哪里施法”。

### 6.4 踩坑与 Debug

1. 瞄准点必须在按下瞬间锁定  
   如果到动画释放帧才读取相机方向，玩家按下后转动镜头会导致火球方向漂移。

2. 输入要能排队  
   如果冷却或动画期间点击被直接丢弃，玩家会感觉输入不灵。当前用队列/缓冲思路保证快点击不会被轻易吃掉。

3. 旧 Meteor 重攻击已经退役
   旧的 Wizard 特例状态、配置与序列化字段已经安全删除；当前 Meteor 是普通法术数据，统一经过 `SpellDefinition → CastEvaluator → SpellCaster` 执行。

### 6.5 面试 Q&A

**Q：为什么不在输入回调里直接调用 `SpellCaster.CastWand`？**  
A：角色动作游戏需要动画和判定同步。输入只表达意图，真正释放应该由攻击状态在动画释放帧触发，这样能统一管理硬直、空中施法、冷却和动作表现。

## 7. 小功能六：法杖编辑 UI

### 7.1 基础知识和原理

法术编程系统必须让玩家能编辑“程序”。因此 UI 不是简单技能栏，而是一个小型编辑器：

```text
左侧/上方：SpellLibrary 提供可选法术
下方/中间：WandLoadout 当前法杖序列
拖拽：从法术库插入、在法杖内移动、拖出移除
```

### 7.2 常见实现方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只在 Inspector 配置 | 开发最快 | 玩家无法运行时编辑 |
| 固定快捷栏 | 简单 | 不像法术编程 |
| 运行时拖拽编辑器 | 符合玩法目标 | UI 代码更多 |

当前选择运行时拖拽编辑器，因为它是核心玩法的一部分。

### 7.3 最终用到的技术

- UGUI：`Image`、`Text`、`CanvasGroup`、slot prefab。
- EventSystem drag/drop 接口：`BeginDrag`、`Drag`、`EndDrag`、`Drop`。
- `Time.timeScale = 0`：打开编辑器时暂停游戏。
- Cursor lock/unlock：打开 UI 时释放鼠标，关闭后恢复。
- `WandEditOps`：纯逻辑执行 insert/remove/move。

### 7.4 架构设计与拆解

相关脚本：

| 脚本 | 职责 |
|---|---|
| `SlotKind.cs` | 区分 Palette 槽位和 WandFrame 槽位 |
| `IWandDragHandler.cs` | slot 和 controller 之间的拖拽协议 |
| `SpellSlotView.cs` | 单个格子的显示与拖拽事件转发 |
| `SpellPaletteView.cs` | 从 `SpellLibrary` 创建可选法术格子 |
| `WandFrameView.cs` | 显示并修改当前 `WandLoadout` |
| `WandEditorController.cs` | 打开/关闭 UI、暂停、拖拽 ghost、drop 仲裁 |
| `WandEditOps.cs` | 纯数组编辑逻辑 |

UI 层只负责编辑 `WandLoadout`，不负责解释法术。

这是一个重要边界：

```text
UI 可以改“程序文本”
UI 不运行“程序语义”
```

语义仍然只在 `CastEvaluator` 里。

### 7.5 踩坑与 Debug

1. Play Mode 修改 `ScriptableObject` 会改资产  
   当前 MVP 接受这个行为，因为它方便调试。以后如果要做正式存档，需要在运行时 clone 一份 loadout，退出时保存到玩家存档。

2. 打开 UI 要暂停角色输入和相机  
   如果只显示 UI 不暂停游戏，拖拽时角色还会移动或镜头还会转。当前通过 `Time.timeScale = 0` 和 cursor 状态处理。

3. slot 视图要保持“哑”  
   `SpellSlotView` 不应该知道怎么修改法杖。它只报告“我被拖了/被放下了”，具体规则由 `WandEditorController` 和 `WandFrameView` 处理。

### 7.6 面试 Q&A

**Q：为什么编辑操作也要做纯逻辑 `WandEditOps`？UI 里直接改数组不行吗？**  
A：拖拽 UI 很容易产生边界 bug，例如同列表移动时 index 偏移。把 insert/remove/move 抽成纯逻辑，可以用单元测试覆盖，UI 只负责把用户操作翻译成编辑命令。

## 8. 小功能七：命中触发类法术

### 8.1 玩家看到的效果

玩家把法杖排成：

```text
[触发类火球] [普通火球]
```

点击施法时，只先发射一个带小太阳标志的火球。这个火球命中敌人或环境后，会在命中点释放后面的普通火球。

### 8.2 基础知识和原理

这个功能本质是事件回调：

```text
投射物命中
    ↓
ProjectileBase 触发 Impacted(hitPoint, hitDir)
    ↓
SpellCaster 收到事件
    ↓
在 hitPoint 运行 payload
```

这里有一个关键架构原则：

`ProjectileBase` 不知道什么是法术 payload。

它只知道自己“命中了”，然后广播一个通用事件：

```text
Impacted(Vector3 point, Vector3 direction)
```

至于命中后要不要释放后续法术，是 `SpellCaster` 的职责。

### 8.3 最终用到的技术

- `ProjectileBase.Impacted`：命中事件。
- `SpellCaster` 订阅事件。
- `EmitCommand.Payload`：被捕获的后续法术。
- `EmitCommand.PayloadMods`：payload 捕获时的修正快照。
- `PayloadTriggerMode.OnImpact`：命中触发条件。
- `OnCollisionEnter`：Unity 物理碰撞入口。
- `IDamageable.ReceiveHit`：命中伤害仍然进入统一 Combat 漏斗。

### 8.4 架构设计与拆解

触发类法术牵涉三个模块：

```text
Game.Skills
    CastEvaluator 捕获 payload，生成带 payload 的 EmitCommand

Game.Character
    SpellCaster 实例化投射物，订阅 Impacted

Game.Combat
    ProjectileBase 处理碰撞，广播 Impacted
```

这个拆法避免了反向依赖：

- `Game.Combat` 不引用 `Game.Skills`
- `Game.Skills` 不引用 `Game.Character`
- `Game.Character` 作为桥接层连接两边

### 8.5 踩坑与 Debug

1. 同阵营穿透不应该触发  
   玩家火球碰到自己或友方时，会忽略碰撞。这种情况不应该算命中，也不应该释放 payload。

2. 超时销毁不应该触发命中 payload  
   命中触发只在真实碰撞时发生。如果飞到最大生命周期自然销毁，不释放命中 payload。

3. payload 要在命中点释放，而不是玩家手上释放  
   如果回到玩家手上释放，触发类法术就失去了“远端展开”的意义。

4. 命中方向要传下去  
   payload 发射方向使用命中方向，可以让后续火球沿原飞行方向继续展开。

### 8.6 面试 Q&A

**Q：为什么不用全局 EventBus 处理 `Impacted`？**  
A：这里事件是某个具体投射物携带的 payload 行为，生命周期和投射物实例强绑定。用实例 event 更直接，也避免全局事件需要额外匹配 projectile id。

**Q：如果触发类火球后面又是触发类火球，会怎样？**  
A：第一层捕获严格后缀。命中后运行 payload，payload 中的触发类火球又会捕获它自己的后缀。每深入一层，序列更短，所以链式触发会自然结束。

## 9. 小功能八：定时类法术

### 9.1 玩家看到的效果

玩家把法杖排成：

```text
[定时类火球] [普通火球]
```

点击后先发射定时类火球。如果它在指定时间内没有命中或销毁，时间到后：

1. 当前定时火球消失。
2. 在它消失的位置释放后续普通火球。

它和命中触发的差异是：

```text
命中触发：需要碰到实体或环境才释放 payload
定时触发：不需要命中，只要求投射物活到指定时间
```

### 9.2 基础知识和原理

定时触发本质是投射物生命周期计时：

```text
SpellCaster 发现 PayloadTrigger = AfterDelay
    ↓
实例化投射物
    ↓
订阅 TimedTriggerElapsed
    ↓
调用 ProjectileBase.ArmTimedTrigger(delay)
    ↓
ProjectileBase.Update 每帧倒计时
    ↓
时间到，广播当前位置与当前方向
    ↓
SpellCaster 在该位置运行 payload
    ↓
销毁当前投射物
```

注意定时触发不是 `Coroutine` 写在 `SpellCaster` 里，而是放在 `ProjectileBase` 中。

原因是“是否仍然存在”这个条件属于投射物生命周期。投射物如果提前命中、销毁、被别的规则消费，就不应该再由一个外部协程在未来强行触发 payload。

### 9.3 常见实现方案

| 方案 | 做法 | 问题 |
|---|---|---|
| `SpellCaster.StartCoroutine(delay)` | 外部等几秒后释放 | 投射物可能已销毁，位置/方向失真 |
| 给定时火球单独写 `TimedFireball` | 特例清晰 | 每种定时投射物都要重复逻辑 |
| 给投射物加通用 timer component | 可行 | 当前项目已有 `ProjectileBase` 生命周期中心 |
| `ProjectileBase` 内置定时事件 | 当前选择 | 所有投射物可复用定时触发 |

### 9.4 最终用到的技术

- `PayloadTriggerMode.AfterDelay`
- `SpellDefinition.PayloadDelaySeconds`
- `ProjectileBase.TimedTriggerElapsed`
- `ProjectileBase.ArmTimedTrigger(float delaySeconds)`
- `ProjectileBase.Update()`
- `Time.deltaTime`
- `_consumed` 防重复消费
- `Destroy(gameObject)`
- `ResolveCurrentDirection()`

`ProjectileBase` 内部关键语义：

```text
如果 _consumed == true，不再触发
如果没 ArmTimedTrigger，不计时
每帧减少 _timedTriggerRemaining
时间到：
    _consumed = true
    TimedTriggerElapsed(position, currentDirection)
    Destroy(gameObject)
```

提前碰撞时：

```text
OnCollisionEnter(...)
    _consumed = true
    Impacted(...)
    Destroy(...)
```

所以一个投射物不能既命中触发又定时触发。谁先消费，谁生效。

### 9.5 架构设计与拆解

定时类法术新增/改动的脚本：

| 脚本 | 改动 |
|---|---|
| `PayloadTriggerMode.cs` | 新增 `AfterDelay` |
| `SpellDefinition.cs` | 新增 `PayloadTrigger` enum 和 `PayloadDelaySeconds` |
| `EmitCommand.cs` | 增加 payload 触发模式与延迟时间字段 |
| `CastEvaluator.cs` | `BakeEmit` 根据 payload 与模式写入 `PayloadTrigger` 和 delay |
| `SpellCaster.cs` | 根据 `PayloadTrigger` 分支订阅 `Impacted` 或 `TimedTriggerElapsed` |
| `ProjectileBase.cs` | 新增通用定时触发事件、计时器、`ArmTimedTrigger` |
| `CastEvaluatorTests.cs` | 覆盖定时 payload 的解释器语义 |

这里的关键设计是：定时触发没有新建一个“定时火球专用运行时代码路径”。

它复用了同一套 payload 机制：

```text
OnImpact   = 何时释放 payload 的条件之一
AfterDelay = 何时释放 payload 的另一种条件
```

因此定时触发只是 payload 系统的扩展，不是另一个独立技能系统。

### 9.6 踩坑与 Debug

1. `Update` 设计要小心  
   如果 `ProjectileBase.Update` 是 `protected virtual`，子类重写后可能忘记调用 `base.Update()`，导致定时器不走。当前更稳的做法是基类 `private Update()` 固定执行计时，再调用 `OnProjectileUpdate()` 给子类扩展。

2. delay 必须小于投射物最大生命周期  
   如果 `PayloadDelaySeconds` 大于 prefab 的 `_maxLifetime`，投射物会先被生命周期销毁，定时 payload 不会触发。这个需要在 Editor 配置时检查。

3. 碰撞先发生就不再定时触发  
   这是设计语义，不是 bug。定时类法术描述的是“若投射物仍然存在，到时间释放后续法术”。

4. `delaySeconds <= 0` 不在 Arm 调用栈内立即触发  
   当前设计是在下一次 `Update` 触发，避免 `ArmTimedTrigger` 调用时重入 `RunCast`，让调用栈更清晰。

5. 定时方向不能只用初始发射方向  
   如果以后加入重力、追踪、反弹，当前方向应该来自 Rigidbody 当前速度。`ResolveCurrentDirection()` 正是为这个准备的。

### 9.7 面试 Q&A

**Q：为什么定时触发放在 `ProjectileBase`，不是 `SpellCaster` 的 coroutine？**  
A：定时条件和投射物生命周期绑定。投射物是否仍然存在、当前在哪、当前方向是什么，都应该由投射物自己提供。外部 coroutine 容易在投射物已销毁后继续执行，产生悬空逻辑。

**Q：定时触发和命中触发如何避免重复触发？**  
A：`ProjectileBase` 用 `_consumed` 作为消费标记。命中或计时到达都会先设置 `_consumed = true`，另一路看到已消费就直接返回。

## 10. 伤害系统如何与法术系统连接

法术系统不重新发明伤害结算。

投射物命中后仍然走 Combat 统一漏斗：

```text
ProjectileBase.OnCollisionEnter
    ↓
IDamageable.ReceiveHit(in DamageRequest)
    ↓
HealthComponent.ReceiveHit
    ↓
DamagePipeline.Resolve
    ↓
扣血
    ↓
DamageReceivedEvent / DeathEvent
```

这非常重要。

如果法术系统自己扣血，弓箭系统、敌人投射物、近战系统、状态系统会各有一套伤害逻辑，后续加防御、暴击、Buff、元素抗性时会崩。

当前设计里，法术只负责“生成什么攻击”，Combat 负责“攻击如何结算”。

```text
UI 可以引用 Skills，因为 UI 要显示和编辑法术数据。
Character 可以引用 Skills 和 Combat，因为角色要施法并生成投射物。
Combat 不引用 Skills，因为伤害系统不应该知道法术编程系统。
Skills 不引用 Character，因为法术规则不应该知道具体角色。
```

## 13. 从结果倒推：三个例子理解解释器

### 13.1 普通火球

法杖：

```text
[普通火球]
```

解释结果：

```text
输出 1 个 EmitCommand
PayloadTrigger = None
Payload = null
```

运行时：

```text
SpellCaster 生成一个 Fireball
ProjectileBase.Init 注入伤害和速度
命中后走 Combat 伤害
```

### 13.2 增伤 + 普通火球

法杖：

```text
[增伤] [普通火球]
```

解释过程：

```text
读到增伤：mods.DamageAddFlat 或 DamageMul 改变
读到火球：用当前 mods 烘焙最终伤害
```

关键点：

增伤没有修改火球资产，只修改解释器状态。

### 13.3 触发火球 + 普通火球

法杖：

```text
[触发火球] [普通火球]
```

第一次解释：

```text
输出 1 个触发火球 EmitCommand
Payload = [普通火球]
PayloadTrigger = OnImpact
```

命中后：

```text
ProjectileBase.Impacted
SpellCaster.RunCast(payload)
输出并生成普通火球
```

### 13.4 定时火球 + 普通火球

法杖：

```text
[定时火球] [普通火球]
```

第一次解释：

```text
输出 1 个定时火球 EmitCommand
Payload = [普通火球]
PayloadTrigger = AfterDelay
PayloadDelaySeconds = 配置值
```

运行时：

```text
SpellCaster 订阅 TimedTriggerElapsed
ProjectileBase.ArmTimedTrigger(delay)
时间到且未被消费
SpellCaster.RunCast(payload)
销毁定时火球
```

## 14. Debug 方法论

调这个系统时，不要一上来盯着场景看。应该按层定位：

### 14.1 如果法术没发出来

先问：

1. `WandLoadout.Spells` 里有没有法术？
2. `WizardController` 有没有进入施法状态？
3. `PlayerWizardAttackState` 是否到了释放帧？
4. `SpellCaster.CastWand` 是否被调用？
5. `CastEvaluator` 是否输出了 `EmitCommand`？
6. `ProjectilePrefab` 是否为空？
7. prefab 上是否有 `ProjectileBase` 派生组件？

### 14.2 如果修正不生效

先看解释器：

1. `Modify` 是否排在 `Emit` 前面？
2. `SpellDefinition.Kind` 是否真的设置成 `Modify`？
3. `ModDamageMul` 默认是否为 1，而不是 0？
4. `CastEvaluatorTests` 是否覆盖该组合？

### 14.3 如果触发类不触发

先看：

1. `PayloadTrigger` 是否为 `OnImpact`？
2. 触发法术后面是否真的有 payload？
3. 投射物是否真实命中，而不是同阵营穿透？
4. `ProjectileBase.Impacted` 是否执行？
5. `SpellCaster` 是否订阅了事件？

### 14.4 如果定时类不触发

先看：

1. `PayloadTrigger` 是否为 `AfterDelay`？
2. `PayloadDelaySeconds` 是否小于投射物 `_maxLifetime`？
3. 投射物是否提前命中并被 `_consumed`？
4. `ArmTimedTrigger` 是否被调用？
5. `ProjectileBase.Update` 是否运行？
6. 是否有 payload 可释放？

## 15. 大厂面试 Q&A

### Q1：请概括这个法术编程系统的架构。

A：我把它拆成三层。第一层是 `Game.Skills` 的纯规则层，用 `ScriptableObject` 定义法术数据，用 `CastEvaluator` 从左到右解释法杖序列，输出 `EmitCommand`。第二层是 `Game.Character` 的运行时桥接层，`SpellCaster` 把 `EmitCommand` 实例化为 Unity 投射物，并处理 payload 触发。第三层是 `Game.Combat` 的战斗结算层，`ProjectileBase` 负责飞行、碰撞、生命周期事件，命中后统一进入 `IDamageable` 和 `DamagePipeline`。这样法术组合规则、角色施法时机、伤害结算分别独立。

### Q2：为什么用解释器，而不是每个法术一个技能类？

A：因为玩法目标是组合。每个法术一个技能类适合固定技能，但不适合法术编程。比如增伤、三重、触发、定时可以和任意 Emit 组合，如果靠技能类表达，会产生组合爆炸。解释器把法术视为指令，组合语义集中在一个地方，新增法术更多是新增数据或规则，而不是新增大量特例技能。

### Q3：这个系统如何保证可测试？

A：核心规则在 `CastEvaluator`、`CastModifierState`、`SpellAiming`、`WandEditOps` 这些 pure logic 中，不依赖 `MonoBehaviour`、Transform、场景对象或物理系统，所以可以用 EditMode tests 验证。运行时 `SpellCaster` 只负责把纯输出落地到 Unity 实例。

### Q4：如何避免触发类法术无限递归？

A：payload 捕获的是触发法术之后的严格后缀。每次触发运行的是更短的序列，所以递归会自然收敛。这个设计比重新运行整根法杖更安全，不需要额外递归深度限制就能避免最常见的无限触发。

### Q5：定时触发为什么放在 `ProjectileBase`？

A：因为定时触发依赖投射物是否仍然存在、当前位置和当前方向，这些信息属于投射物生命周期。放在 `SpellCaster` coroutine 中会有投射物已销毁但 coroutine 仍继续的问题。`ProjectileBase` 内部用 `_consumed` 控制命中和计时互斥，语义更稳定。

### Q6：`Game.Combat` 为什么不能引用 `Game.Skills`？

A：Combat 是底层战斗漏斗，弓箭、敌人投射物、近战、状态伤害都依赖它。如果 Combat 反向知道法术系统，会导致模块耦合扩大。当前做法是 Combat 只广播通用投射物事件，Character 层的 `SpellCaster` 根据事件运行法术 payload。

### Q7：怎么处理性能和 GC？

A：核心解释器输出列表由调用方复用，避免每次施法分配新的 `List<EmitCommand>`。伤害请求和结果使用 struct 快照。投射物命中、范围检测也尽量沿用现有 Combat 的 NonAlloc 思路。需要注意的是 payload 捕获当前会创建 suffix list，这是离散施法/触发时的一次性分配，MVP 可接受；如果将来高频触发很多，可以改成 slice/range 表示。

### Q8：当前系统有什么可改进点？

A：第一，真实法力池和 UI 还没有完整接入，当前运行时可用法力还是占位。第二，Play Mode 编辑 `WandLoadout` 会修改资产，后续正式版本应 clone 运行时 loadout 并接存档。第三，payload 捕获目前使用 List 分配，未来可以优化为只保存原序列和起止索引。第四，触发条件还可以扩展到弹跳、穿透、过期、手动引爆等。

## 16. 模拟面试者完整讲解

如果我要向面试官介绍这个功能，我会这样讲：

我在这个项目里实现的是一个类 Noita 的法术编程系统。它不是传统的固定技能系统，而是把法杖看成一段程序，把每个法术看成一条指令。玩家在 UI 中拖拽法术形成一个序列，施法时系统从左到右解释这个序列，最后输出一组发射命令，再由运行时把这些命令转成真实投射物。

架构上我把它分成三层。最底层的规则在 `Game.Skills`，包括 `SpellDefinition`、`WandLoadout`、`CastEvaluator`、`EmitCommand`。这一层是纯逻辑，不直接依赖 Unity 场景，也不实例化投射物。`CastEvaluator` 根据 `SpellKind` 处理三类指令：`Emit` 产生投射物命令，`Modify` 修改当前修正状态，`Multicast` 增加抽取预算。这样增伤、加速、散射、双重、三重都不是写死技能，而是解释器状态变化。

第二层是 `Game.Character` 里的 `SpellCaster`。它是纯规则和 Unity 运行时之间的桥。`SpellCaster` 调用解释器拿到 `EmitCommand`，然后实例化投射物 prefab，注入伤害、速度、阵营、施法者 Collider，并根据命令决定是否订阅投射物的命中事件或定时事件。这样 `Game.Skills` 保持纯净，`Game.Combat` 也不需要知道法术系统。

第三层是 `Game.Combat`。投射物仍然继承 `ProjectileBase`，命中后统一走 `IDamageable.ReceiveHit`、`HealthComponent` 和 `DamagePipeline`，不会为法术单独写一套伤害结算。为了支持触发类法术，我在 `ProjectileBase` 上提供了 `Impacted` 通用事件；为了支持定时类法术，又加入了 `TimedTriggerElapsed` 和 `ArmTimedTrigger`。投射物自身只负责生命周期事件，不知道 payload 是什么，payload 由 `SpellCaster` 响应事件后再次运行解释器。

触发类和定时类法术的共同点是它们都是携带 payload 的 `Emit`。解释器读到这类 Emit 时，会捕获它后面的严格后缀作为 payload，并结束当前层读取。命中触发是在 `ProjectileBase.Impacted` 时释放 payload；定时触发是在投射物存活到指定时间后释放 payload。由于 payload 是严格后缀，每一层递归的序列都会变短，所以链式触发天然收敛，不会轻易无限递归。

UI 方面，我用 `SpellLibrary` 提供可选法术，用 `WandEditorController`、`SpellPaletteView`、`WandFrameView` 和 `SpellSlotView` 实现运行时拖拽编辑。UI 只编辑 `WandLoadout` 里的法术序列，不解释语义。真正的语义仍然集中在 `CastEvaluator`，这保证了 UI、角色输入、战斗结算不会各自实现一套法术逻辑。

这个设计的主要取舍是：前期架构比硬编码火球复杂，但它换来了组合能力和可扩展性。以后如果我要加追踪、弹跳、穿透、范围扩大、随机散射或更多触发条件，优先考虑把它们建模成新的 modifier、payload trigger mode 或投射物通用事件，而不是为每个组合写新技能类。这样系统能随着法术数量增长保持可维护。

## 17. 后续学习重点

如果你要真正掌握这个系统，建议按这个顺序读代码：

1. 先读 `SpellDefinition.cs`，理解一个法术资产有哪些数据。
2. 再读 `CastEvaluator.cs`，理解“从左到右解释”。
3. 再读 `EmitCommand.cs` 和 `CastModifierState.cs`，理解为什么要用快照。
4. 再读 `SpellCaster.cs`，看纯输出如何变成 Unity 投射物。
5. 再读 `ProjectileBase.cs`，看命中事件和定时事件如何向上层开放。
6. 最后读 UI 相关脚本，理解玩家如何编辑法术序列。

理解顺序不要反过来。直接从 UI 或特效开始看，会觉得到处都是对象引用；先从解释器看，才能抓住这个系统的主线。
