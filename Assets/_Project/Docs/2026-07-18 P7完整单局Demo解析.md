## P7 总体目标与边界

第一版 Demo 只保留 Wizard 作为玩家角色，使用现有 Fireball、WaterField、Shield、Meteor、Trigger/Timed、Modify 和 Multicast 法术。关卡采用手工制作的 S 形连续小型布局：安全起点后依次经过三个普通战斗区域，区域之间至少获得一次能够影响 Wand 编程的新法术，最后击败精英并结算。Water/Fire Sparse ElementWorld 继续提供环境 Cell、流动、Extinguish、Wet/Burning 与自研 Rendering。

完整 Seeded Random、随机房间拼接、法术稀有度、复杂掉落表、永久存档、Poison/Sticky/Steam 与新 Boss FSM 均不阻塞第一版 Demo。这个取舍不是降低工程质量，而是把“作品是否已经可完整游玩”放在“系统是否覆盖所有未来设想”之前。只有完整流程稳定后，随机化才有一个可靠模板可供变化，否则随机系统只会随机组合尚未验证的房间和规则。

预期运行链如下：

```text
启动 Standalone Build
→ Main Menu：Start Game / Settings / Quit
→ Fade + LoadSceneAsync
→ 进入安全起点
→ 打开 Wand Editor，确认起始法术
→ Encounter 1：基础战斗
→ 清场、开门、获得法术奖励
→ 在安全间隔重新编程
→ Encounter 2：Water/Fire 元素互动
→ Encounter 3：组合压力测试
→ Final Encounter：最终精英
→ Victory 结算
→ Restart 后恢复干净的 Enemy、Gate、ElementWorld 与 Runtime Wand
  或 Return To Main Menu

任意时刻 Player Death
→ Defeat 结算
→ Restart 或 Return To Main Menu

Running 中按 Pause
→ Resume / Settings / Restart / Return To Main Menu
```

# Task 0：从“元素世界完成”切换到“完整单局开发”

Task 0 的目的，是在进入新功能前给项目建立一个清晰的阶段边界。此前 P6 已经完成两条可玩的双向链路：一条是法术命中后通过唯一 `IElementWriteSink` 把 Water/Fire 写入固定世界坐标的稀疏 Chunk，经过固定 Tick 进行流动、衰减、反应和 Solver Sleep/Wake；另一条是 ElementWorld 通过集中 Exposure 把 Cell Amount 映射为角色 Wet/Burning，并由 Water Chunk Mesh、自研 Water Shader 和共享 Fire Body/Core/Sparks Particle 形成连续视觉。P6 最关键的性能问题——稳定水面仍被重复扫描导致 `ElementWorld.Simulate` 单帧达到数百毫秒——也已经通过 Profiler 证据定位，并用 Resident/RequiresSimulation 分离、稳定 Chunk休眠、写入/边界唤醒和无效工作剪枝解决。继续把 Poison、Sticky、Steam 或灰盒地图塞进 P6，只会让“阶段完成”失去意义。

因此本 Task 把 P6 作为已结束的冻结依赖，并把首个灰盒关卡、Encounter、奖励、功能性 UI、Victory/Defeat 和 Restart 统一归入 P7。功能性 UI 不是最后贴上去的装饰：没有 Main Menu，玩家只能依赖 Unity Editor 的 Play Button；没有目标 HUD，玩家不知道门为什么不开；没有 Pause/Settings，Demo 缺少基本应用控制；没有 Result/Restart/Return To Main Menu，一局也没有明确的开始和结束。与此同时，我们没有直接开始在 `SampleScene` 里摆更多 Cube，而是先制定 P7 的产品目标和架构边界：Scene 负责空间和引用，`Game.Run` 负责本局 Gameplay 状态，`Game.UI` 负责反馈与用户操作入口，Enemy/Player 保持原职责，ElementWorld 继续是独立系统。这样开发者以后遇到“门不开”“怪死了不计数”“关闭一个 Panel 后游戏意外恢复”“退出 Play Mode 后法杖被污染”等问题时，可以沿清晰的数据链定位，而不是在一个万能 Scene Manager 中搜索互相耦合的 if/switch。

## 1. 为什么“关卡搭建”不等于“地图编辑”

地图编辑主要处理空间：Floor、Wall、Ramp、Cover、Lighting、Camera Sightline 和移动距离。它决定玩家能不能走、战斗空间够不够、敌人是否被障碍卡住，但它本身不会形成一局游戏。

一局游戏还需要四类状态：

| 层级 | 典型问题 | P7 的负责者 |
|---|---|---|
| 空间状态 | 玩家在哪个区域，Trigger/Gate/Collider 在哪里 | `P7_DemoRun` Scene 与灰盒物体 |
| 战斗状态 | 哪些 Enemy 属于本区，还剩多少，是否清场 | `DemoEncounterController + EncounterProgressTracker` |
| 单局状态 | 当前第几关，是否失败/胜利，能否继续推进 | `DemoRunController + RunProgressTracker` |
| 表现状态 | 当前目标、奖励、Pause、Settings、Victory/Defeat | `Game.UI` Controllers，只读 Run Event/Settings |
| 应用状态 | 当前在 Main Menu 还是 Gameplay，是否正在切换 Scene | `P7_MainMenu/P7_DemoRun + DemoSceneTransitionController` |

如果只搭地图，玩家可以从起点一路跑到终点，敌人可能全部同时追来，死亡后没有失败界面，最终敌人死亡也没有胜利。反过来，如果只写流程而没有先验证空间尺度，Gate 可能堵住 CharacterController，Camera 可能穿墙，当前使用直线追击的 Enemy 可能被复杂掩体永久卡住。P7 必须让“空间 Authoring”和“流程 Runtime”分工合作。

## 2. 为什么新增 `Game.Run`，而不是把流程写进 Player、Enemy 或 UI

项目现有依赖遵循单向结构。`HealthComponent` 负责 HP 与 `DeathEvent`，Enemy Controller 负责感知和战斗 FSM，Wizard/SpellCaster 负责施法，ElementWorld 负责环境模拟，UI 负责显示。谁都不应该顺便拥有“这一局打到第几关”的真相。

若把清场逻辑写进 Enemy：每个敌人都要知道同区其他敌人、门和最终胜利，普通 AI 将与具体关卡绑定。若写进 Player：玩家移动/攻击脚本会开始管理 Gate、奖励和 Scene Reload，难以复用也难测试。若写进 UI：表现层会反向修改 Gameplay，破坏现有只读边界。

因此选择新增 `Game.Run`：

```text
Game.Run 读取 DeathEvent
→ 纯 Tracker 求值 Encounter/Run 状态
→ Scene Adapter 开关 Enemy 与 Gate
→ 发布 Encounter/Run Event
→ Game.UI 只读显示
```

`Game.Run` 计划依赖 `Game.Core + Game.Combat + Game.Skills`，但不依赖 `Game.Character` 和 `Game.UI`。Character/UI 后续可以只读 Run Spell Session/Event，因此依赖仍然向上，不形成循环。

这种模块化不是为了“多建一个文件夹显得专业”，而是让变化原因分离：修改敌人攻击 AI 不需要重测房间顺序；修改 UI 文案不改变胜负；将来用随机 Room Graph 替换手工顺序，也不必重写 Health/Death 规则。

## 3. Encounter 与 Run 是两个不同层级的状态机

Encounter 表示一个战斗区域的局部生命周期：

```text
Waiting → Armed → Active → Cleared
```

- `Waiting`：还没轮到本区，即使玩家或其他 Collider 误入，也不启动。
- `Armed`：前区完成，本区 Entry Trigger 可以接受玩家。
- `Active`：关闭 Gate、激活成员 Enemy、统计本区 Death。
- `Cleared`：成员全部死亡，只发布一次完成并打开出口。

Run 表示整局的更高层生命周期：

```text
NotStarted → Running → Completed
                    └→ Failed
```

`Completed` 和 `Failed` 是 Terminal State。进入后，普通 DeathEvent 或 Trigger 不能继续推进，只能通过 Restart 创建新一局。把两层分开可以避免一个常见错误：为了判断最终胜利，让每个 Encounter 都知道自己是不是最后一个；正确做法是 Encounter 只报告“我完成了”，由 RunProgressTracker 决定是否还有下一关。

Death 统计使用 `HealthComponent.Id / DeathEvent.TargetId`，不使用 GameObject Name、Tag 文本或 Enemy 数量轮询。原因是 ID 与 Combat 事件同源，重复 DeathEvent 可以去重，场外敌人死亡也可以安全忽略，而且不需要在 `Update()` 每帧执行 `FindObjectsOfType`。

## 4. 为什么 P7 必须解决 ScriptableObject 运行时污染

当前 Wand Editor 会把拖拽结果写回 `WandLoadout.Spells`。`WandLoadout` 是 Project 中的 ScriptableObject Asset；在 Unity Editor 的 Play Mode 中修改它，退出 Play Mode 后可能保留改动。实验阶段这方便调试，但单局系统加入奖励和 Restart 后会产生错误语义：上一局拿到的法术可能永久留在下一局，甚至被提交到 Git。

P7 采用 Authoring Template 与 Runtime Clone：

```text
Project Asset（起始模板）
→ Play Mode Awake: Object.Instantiate
→ Runtime Clone（本局可编辑）
→ SpellCaster 与 Wand UI 共享同一 Clone
→ Scene 结束时 Destroy
```

只克隆 `SpellLibrary/WandLoadout` 容器，不克隆每个 `SpellDefinition`。法术定义仍是不可变的共享数据，Runtime 只改变“我本局拥有哪些法术”和“法杖中的引用顺序”。Clone 使用 `HideFlags.DontSave`，表达它不能被保存为场景或资产。这个设计既保留 Data-driven Authoring，也建立了 Roguelite 最基本的 Run-Scoped State。

## 5. 手工关卡与随机关卡的取舍

原总计划的 P7 包含 Seed、房间组合、稀有度与随机权重。这些能力有价值，但当前直接实现会同时引入 Room Graph、Spawner、Reward Table、Seed State、Save/Reload 和 Debug Reproduction，开发风险会显著超过“完整一局”本身。

第一版采用手工 S 形连续关卡，奖励也确定。优点是：

- 每次测试敌人、距离、奖励和元素位置完全一致，容易复现 Bug。
- 可以精确安排第一次普通战斗、第一次元素互动和第一次重新编程。
- 能先测出哪些房间模板真正好玩，再把它们放入随机池。
- 录制作品视频时不会因随机结果缺少核心展示。

随机化不是越早越好。它应当变化已经成立的模板，而不是替代关卡设计。P7-A Demo 完整后，P7-B 可以把 `DemoRunDefinition` 的线性顺序替换为 Seeded Room Selection，同时复用 Encounter/Run/UI/Restart 内核。

## 6. 为什么功能性 UI 属于 P7 核心，而不是完成后的美化

游戏 UI 可以分成两类。第一类是 Presentation Polish，例如漂亮 Logo、复杂过场动画、动态背景和最终字体；这些可以在 Demo 主流程完成后优化。第二类是 Functional UI，它决定玩家能否理解和控制应用：Start Game 建立运行入口，Objective HUD 解释当前目标，Reward Feedback 告诉玩家获得了什么，Pause 提供中断控制，Victory/Defeat 定义一局的终点，Restart/Return To Main Menu 建立下一次循环。P7 必须完成第二类，否则我们得到的是“可以在 Unity Editor 中演示的一组系统”，而不是可以交给别人独立试玩的游戏。

P7 的 UI 生命周期计划如下：

```text
P7_MainMenu
  → Start Game
  → P7_DemoRun
       ├─ Gameplay HUD / Wand Editor / Reward Feedback
       ├─ Pause → Resume / Settings / Restart / Main Menu
       ├─ Victory → Restart / Main Menu
       └─ Defeat  → Restart / Main Menu
```

这里最容易踩坑的是 `Time.timeScale`。当前 Wand Editor 会直接设置 0 或 1；若 Pause Menu 和 Victory Panel 也各自这样做，关闭 Wand Editor 可能把仍处于 Pause/Victory 的游戏恢复。P7 因此计划使用 `RunPauseCoordinator` 记录 `WandEditor`、`PauseMenu`、`TerminalResult` 等 Pause Reason：只有所有原因都释放时才恢复 `Time.timeScale = 1`。这和“多个系统共享一个 bool”相比，多表达了一层所有权，但能准确回答“现在为什么暂停”。

Settings 也要区分 User Preference 与 Run State。Master Volume、Mouse Sensitivity、Fullscreen 应跨 Scene 和应用重启保留，因此用 `Game.Core.UserSettingsService + PlayerPrefs`；HP、Enemy Count、Runtime Wand、Encounter Index 属于本局，不能存入 PlayerPrefs。MVP 的 Master Volume 使用 `AudioListener.volume`，优点是现有 AudioSource 无需统一改 Output；代价是没有 Bus、Duck 和 dB Mixing，正式 Audio 阶段再迁移 `AudioMixer`。这体现 Demo 开发中的核心取舍：功能必须真实可用，但不提前建设当前内容还验证不了的复杂系统。

# Task 1：创建独立 S 形灰盒 Scene，先验证“走得通”

Task 1 的目的不是把地图“做漂亮”，而是用最低成本验证一局游戏所依赖的空间条件。我们从 `SampleScene` 的实验场中抽离出 Wizard、Camera、HUD 和连续 `ElementWorld`，建立独立的 `P7_DemoRun` Scene，再按安全起点、走廊、三个普通 Arena、最终精英 Arena 的顺序搭出 S 形路线。每块 Floor、Wall 和 Obstacle 都不是单纯的美术物体：Floor 决定 `CharacterController` 是否能稳定接地以及 Element Projectile 是否能向 `Ground` 写入；Wall 决定玩家边界和 Camera Collision；Obstacle 决定走位、视线、Projectile 碰撞以及当前直线追击 Enemy 的可用空间。我们还定位并修复了一个经典 Third-person Camera 穿墙问题：不是通过缩小 `Near Clip Plane` 隐藏症状，而是让 `CinemachineThirdPersonFollow` 用带体积的碰撞查询收缩 Camera 距离。最后，Wizard 完整往返、Dash、现有近战/远程 Enemy，以及 Water/Fire 命中不同位置的 `Ground` 后生成 Cell/视觉都通过验证。这意味着 Task 1 已经交付了一个真正可承载后续 Encounter 和 Run Flow 的空间基座，而不是另一张孤立的测试地图。

## 1. 从玩家最终看到的结果，反推灰盒要证明什么

玩家最终感受到的是一条连续推进的路线：从安全区域出发，经走廊进入 Arena，在有掩体的空间中移动、Dash、发射法术，与敌人战斗，然后继续前往下一区域。为了让这个结果成立，Scene 必须同时满足以下约束：

| 玩家看到的结果 | Scene 中必须成立的技术条件 | 本 Task 的验证方式 |
|---|---|---|
| Wizard 能走完整条路线 | Floor 连续、`Collider` 非 Trigger、Layer 正确、没有小缝或不可见墙 | 从起点走到最终 Arena 后原路返回，并穿插 Jump/Dash |
| 靠墙时不会看到墙体内部 | Camera 的期望位置到实际位置之间进行 Collision Query；墙体在查询的 `LayerMask` 中 | 贴墙旋转、墙角、窄 Corridor、Dash 靠墙、离墙恢复 |
| Enemy 能接近并攻击 | Arena 不能依赖当前 AI 不具备的 Pathfinding；主要通路足够宽 | 临时放入 SwordEnemy 与 MagicEnemy，观察追击、攻击和绕开简单障碍的结果 |
| Water/Fire 能成为地形 | Projectile 命中对象属于 `Ground`，`ElementWorld` 能把 World Position 映射到 Global Cell/Chunk | 在不同区域向地面发射水球和火球，确认生成对应 Water/Fire |
| 后续能加入 Encounter | 区域具有清晰的父节点和入口/出口，而不是一堆无语义 Cube | `__Level` 下按 Start/Corridor/Arena 命名并分组 |

这就是“灰盒是空间测试代码”的含义。代码里的 Unit Test 用输入和输出验证规则；灰盒则用尺寸、Collider、视线和运动验证空间规则。若在这个阶段直接追求材质、灯光和装饰，之后一旦发现 Arena 太窄或 Camera 必然穿墙，返工成本会更高。

Scene 的运行依赖链可以压缩为：

```text
Wizard Input
→ CharacterController.Move / Dash
→ Floor、Wall、Obstacle Collider
→ Cinemachine Third Person Follow 计算 Camera 期望位置
→ Avoid Obstacles 修正实际 Camera 距离

SpellCaster 发射 Projectile
→ Projectile 与 Ground Collider 碰撞
→ Element Deposit Request 使用命中 World Position
→ ElementWorld 将位置量化为 Global Cell / Chunk
→ Water Solver 或 Fire Simulation
→ WorldWaterRenderer / Fire Particle Presentation
```

## 2. Scene 分层、五个区域与障碍物为什么这样搭

`P7_DemoRun` 的顶层按职责划分为 `__Systems`、`__Gameplay`、`__Level`、`__Encounters` 和 `__UI`。这种分组不是运行时性能优化，主要是 Authoring Architecture：场景复杂后，开发者可以迅速判断某个对象属于全局系统、玩家、空间、战斗流程还是 UI，避免把 Enemy、Trigger、Camera 和地板混在同一层。`__Encounters` 在 Task 1 保持空白，是因为本 Task 只验证空间；Task 3 才会把正式 Encounter Controller、成员和 Gate 放进去。

`__Level` 内的主要结构如下：

```text
StartSafeZone
→ Corridor_01
→ Arena_01_Basics
→ Corridor_02
→ Arena_02_Elements
→ Corridor_03
→ Arena_03_Programming
→ Corridor_Final
→ Arena_04_Elite
```

这些名称同时表达玩家教学顺序。`StartSafeZone` 给玩家观察 HUD、移动和打开 Wand Editor 的安全时间；`Arena_01_Basics` 验证基础移动、瞄准和普通战斗；`Arena_02_Elements` 预留较开放地面，避免大量细碎障碍阻断 Water 的流动和 Fire 的分布；`Arena_03_Programming` 用柱体制造 Projectile 碰撞与视线变化，适合观察 Homing、Bounce、Trigger 和 Multicast；`Arena_04_Elite` 保持中央空间开阔，让精英战有回旋余地。Corridor 不只是连接几何，它还负责隔开战斗节奏、遮挡后续区域，并为未来 Gate、Reward 和重新编程提供明确位置。

障碍物遵守“少量、可读、不会形成复杂死胡同”的原则：基础 Arena 使用错位掩体，元素 Arena 使用低平台，编程 Arena 使用留有宽主通路的柱体，精英 Arena 使用四角柱并保持中心开放。原因是当前 Enemy 使用 `CharacterController` 朝目标方向直线移动，没有 `NavMeshAgent` 或 A* Pathfinding。复杂 U 形墙和窄迷宫会把“AI 不会寻路”错误包装成“关卡更丰富”，最终表现是 Enemy 永久顶墙。当前设计接受较简单的空间，以换取可靠的 Demo 战斗；未来若需要复杂地编，应单独升级 Navigation，而不是继续靠手工摆放碰运气。

用 Cube 搭 Floor/Wall/Obstacle 时还要理解 `Transform` 与 `BoxCollider`：默认 Cube 的中心在物体原点，边长为 1。因此高度为 `H`、底面要落在 `Y = 0` 的 Cube，其中心应放在 `Y = H / 2`。例如高度 2m 的墙应把中心设在 `Y = 1`。若只改 `Scale.y = 2` 却把中心留在 `Y = 0`，墙会有一半埋入地面；这不一定立刻报错，却会让视觉、碰撞和后续尺寸推理变得混乱。

## 3. 经典 Debug：为什么 Third-person Camera 会穿墙，以及正确修复

### 现象与错误直觉

Wizard 靠近墙体并旋转视角时，Camera 会进入墙体，Game View 随后看到墙背后或墙体内部，像出现了“透视”。一个常见直觉是减小 Camera 的 `Near Clip Plane`。但 `Near Clip Plane` 只定义 Camera 从多远处开始 Rasterization，并不会改变 Camera Transform 的位置；Camera 中心仍在墙内时，缩小它只是改变墙面被裁切的位置。再加上多数不透明材质启用 `Backface Culling`，从墙体背面看时背向 Camera 的三角形不会被绘制，于是后方场景暴露出来。

### 根因定位

本项目使用 Cinemachine 3.1.6 的 `CinemachineThirdPersonFollow`。排查发现：

- `Avoid Obstacles` 没有启用，因此 Follow 算出的理想 Camera 位置不会被场景碰撞修正；
- `Collision Filter` 仍只包含 `Default`，而新建墙体位于 `Ground` Layer；
- 墙体虽然有 `BoxCollider`，但 Camera Query 根本没有查询这些 Layer。

所以问题不是墙“没有碰撞”，而是 Camera Collision 使用了错误的功能开关和 `LayerMask`。这是 Debug 中很重要的区分：Player Collision 与 Camera Collision 是两条独立查询链，玩家撞不穿墙不代表 Camera 也知道墙的存在。

### 为什么使用 SphereCast，而不是一条 Raycast

Camera 不是数学上的一个点，最终图像来自 Near Plane 上的一块矩形。只从跟随目标向 Camera 中心发一条 `Raycast`，只能保证中心线没有穿过障碍，墙角仍可能切入 Near Plane。`SphereCast` 把相机近似成带半径的体积，虽然不是精确矩形，但成本低、稳定，适合实时第三人称避障。

Near Plane 尺寸可以由 Perspective Projection 的几何关系估算。设：

- Near Clip Distance 为 `n`；
- Vertical Field of View 为 `FOV_y`；
- Aspect Ratio 为 `a = width / height`。

Near Plane 的半高、半宽和外接圆半径分别为：

```text
h = n × tan(FOV_y / 2)
w = h × a
r = sqrt(h² + w²)
```

以当前常见配置 `n = 0.3m`、`FOV_y = 60°`、`a = 16/9` 为例：

```text
h = 0.3 × tan(30°) ≈ 0.173m
w = 0.173 × 16/9 ≈ 0.308m
r = sqrt(0.173² + 0.308²) ≈ 0.353m
```

因此 `Camera Radius ≈ 0.35m` 不是随便试出的 Magic Number，而是 Near Plane 外接圆的近似。实际项目仍需按 Camera FOV、Near Clip、角色肩位构图和狭窄空间微调。

### 最终配置与 Damping 取舍

- 启用 `CinemachineThirdPersonFollow > Avoid Obstacles`；
- `Collision Filter` 包含墙体所在的 `Ground` Layer；
- `Camera Radius` 约为 `0.35`；
- `Damping Into Collision = 0`，检测到墙时立即缩短 Camera 距离，避免用平滑换来数帧穿模；
- `Damping From Collision ≈ 0.3`，离开墙体时平滑恢复，减少 Camera 突然弹回造成的不适；
- 保持期望 `Camera Distance`，不要为了避墙永久缩短正常构图；
- 墙体实际子对象必须是 `Ground` Layer，且 `BoxCollider.IsTrigger = false`。

这里的 Trade-off 是：`Camera Radius` 太小会在墙角漏检，太大会在窄道中过早压近角色；`Damping From Collision` 太大会让 Camera 离墙后长时间贴着角色，太小则会明显弹出；`Collision Filter` 若误包含 Player/Enemy，Camera 可能被角色 Collider 干扰并抖动。最终必须用贴墙旋转、内外墙角、窄走廊、Dash 靠墙和离墙恢复的组合 Gate 验证，而不是只在一面平墙前观察一次。

## 4. Enemy 与 ElementWorld Gate 分别证明了什么

临时放入 SwordEnemy 和 MagicEnemy 的目的不是提前实现 Encounter，而是验证当前灰盒没有突破既有 AI 的能力边界。近战 Enemy 的 `DetectRadius < LoseRadius` 构成 Hysteresis：进入较小半径后锁定目标，只有离开较大半径才丢失，避免玩家站在边界附近时 Idle/Chase 快速抖动；远程 Enemy 还要在攻击距离与后退距离之间维持空间。测试通过说明核心动线、Arena 宽度和障碍布局能承载现有直线追击 AI。它不代表 Enemy 已经具备完整 Pathfinding，也不代表 Task 1 的临时对象就是正式关卡成员；Task 3 会用 Encounter 数据和成员引用取代临时摆放。

Water/Fire Gate 验证的是另一条跨模块链路。Projectile 击中 `Ground` Layer 的 GameObject 后，命中点的 `World Position` 被提交给 `ElementWorld`；World Coordinates 再把它量化为 Global Cell 和 Chunk Key，创建或唤醒对应 Sparse Chunk。Water 进入流动模拟并由 Water Renderer 表现，Fire 进入衰减/反应并驱动共享 Body/Core/Sparks Particle。开发者已确认水球与火球击中新 Scene 的 Ground 后都会正常生成对应水域和火焰，说明连续世界并未绑定旧 `ElementFieldLabRoot` 的固定小范围。

这也体现 Gameplay Data 与 Presentation 的分离：Cell 是否存在、Amount 如何变化属于 `Game.ElementField`；水面 Mesh/Shader 和火焰 Particle 属于 `Game.Rendering`。如果未来再次出现“Wet 能增加但地上看不到水”，应先分别检查 World Store/Exposure 与 Renderer，而不是立即把两者当作同一个 Bug。

| 症状 | 优先检查 |

# Task 2：用纯 C# 状态机建立可测试的单局流程真相

Task 2 的目的，是在真正开关 Scene 里的门、激活敌人或显示 HUD 之前，先回答两个最容易被 Scene 细节掩盖的问题：一个战斗区域究竟在什么条件下算清场，以及整局游戏究竟允许按照什么顺序推进。我们没有把这些判断直接写进 Trigger、Enemy 或 UI，而是新增独立 `Game.Run` Assembly，并把规则拆为两级纯 C# Tracker。`EncounterProgressTracker` 只管理一个区域的敌人成员、死亡去重与 `Waiting → Armed → Active → Cleared` 生命周期；`RunProgressTracker` 只管理多个区域的顺序和 `NotStarted → Running → Completed/Failed` 整局状态。二者都不知道 `GameObject`、`Transform`、`Collider`、Animator、Gate 或 UI，因此可以用毫秒级 EditMode NUnit 精确重现重复 `DeathEvent`、场外死亡、越序触发、空 Encounter 和胜负竞争等边界条件。

本 Task 同时建立了未来 Scene 集成的两端。输入端是 `DemoRunDefinition`：它用 `ScriptableObject` 保存 Encounter 顺序、UI 文案和确定性法术奖励，但刻意不保存 Scene Enemy/Gate 引用，也不保存“当前打到第几关”这种 Runtime State。输出端是三个 `struct + IGameEvent`：Scene Adapter 在纯 Tracker 接纳状态变化后，才发布 Encounter Started、Encounter Completed 或 Run State Changed 事实。后续 Gate、Reward 和 UI 都消费同一份已经裁定的事实，不能各自根据 GameObject 是否 Active 去猜流程。开发过程遵循 TDD：先写 12 个测试并亲眼确认因生产类型缺失而 RED，再写满足测试的最小实现转为 GREEN；开发者最终确认 `Game.Run.Tests` 12 passed、全项目 313 passed/0 failed。这样 Task 3 要调试的只剩“Scene 对象是否被正确翻译成 Tracker 输入”，而不是同时怀疑底层规则本身。

## 1. 从最终效果反推：为什么要有两级状态机

最终玩家看到的效果是一条线性的因果链：进入区域、门关闭、敌人激活、逐个击杀、最后一只死亡、门打开、下一区域可进入；最终精英死亡则出现 Victory。若把这条链全部写进一个 `DemoRunController.Update()`，它会同时维护 Enemy 数量、Gate、UI、Reward 和整局胜负。任何一个重复事件都可能造成多开门、多发奖励或胜利后又失败。

因此先把问题反向拆成两层：

```text
单区事实：这次死亡是否属于本区、是否首次出现、是否让剩余数归零？
    ↓ EncounterProgressTracker
整局事实：当前允许启动第几区、完成后是否还有下一关、是否已经胜利/失败？
    ↓ RunProgressTracker
Scene 结果：开关 Gate、激活 Enemy、生成 Reward、更新 HUD
    ↓ Task 3 以后由 Adapter 执行
```

这里使用的是 `Finite State Machine`（FSM，有限状态机）：系统只能处于有限个命名状态中，输入命令只有在当前状态允许时才会产生转换。它比散落的 `_hasStarted`、`_isCleared`、`_hasFailed` 多个 bool 更安全，因为多个 bool 会产生非法组合，例如“既 Cleared 又 Active”或“Completed 后仍可 Start”。Enum 状态一次只能取一个值，转换函数再把合法边界集中起来。

`EncounterState` 的语义是：

- `Waiting`：配置已存在，但整局顺序尚未允许玩家进入；
- `Armed`：当前区域已经获得启动资格，等待玩家进入 Trigger；
- `Active`：战斗已经开始，此时才接受本区 Enemy Death；
- `Cleared`：所有成员的首次有效死亡均已记录，是单区 Terminal State。

`RunState` 的语义是：

- `NotStarted`：尚未建立本局；
- `Running`：允许当前 Encounter 按顺序推进；
- `Completed`：最后一个 Encounter 已完成；
- `Failed`：Player 已死亡；
- `Completed` 与 `Failed` 都是整局 `Terminal State`。迟到的 Enemy Death 或 Player Death 不能覆盖结算，只有 Restart 创建新 Scene/新 Tracker 才能开始另一局。

## 2. `EncounterProgressTracker`：成员集合、去重与清场公式

一个 Encounter 不能仅保存 `remainingEnemyCount--`。如果同一 Enemy 因重复订阅或对象销毁顺序发布两次死亡事件，计数会被减两次；如果场外 Enemy 死亡也被减，门会提前打开。正确模型需要同时知道“谁属于本区”和“谁已经被本区记录死亡”。

脚本使用两个 `HashSet<int>`：

```text
E = 本 Encounter 的 Enemy TargetId 集合
D = 已接纳死亡的 TargetId 集合
Remaining = |E| - |D|
Cleared ⇔ State = Active 且 |D| = |E|
```

`HashSet` 基于 Hash Table，平均情况下 `Add` 与 `Contains` 为 `O(1)`；`List.Contains` 则为 `O(n)`。当前每区敌人很少，两者性能都足够，但 `HashSet.Add` 返回值天然表达“首次插入还是重复值”，正好用于 Death 去重。`TargetId` 来自现有 `HealthComponent.Id / GameObject.GetInstanceID()`，Tracker 不需要引用或保活 Enemy GameObject。

`Configure(IEnumerable<int>)` 是离散的开战前配置，不在 `Update()` 热路径执行，所以这里允许清空并填充 `HashSet`。它对三类错误 Fail Fast：输入为 null、出现重复 ID、集合为空。特别是空 Encounter 不能默认为“等以后再说”，否则进入区域后没有 Enemy 能产生 DeathEvent，Gate 会永久关闭，成为典型 `Soft Lock`。配置错误在初始化时抛出，比玩家玩到中途才发现门不开更容易定位。

`RecordDeath(targetId)` 只有同时满足以下条件才返回 true：当前为 Active、ID 属于 `E`、ID 尚未加入 `D`。短路逻辑为：

```text
Accepted = Active ∧ Contains(E, id) ∧ Add(D, id)
```

场外 ID、重复 ID、尚未开战或已经 Cleared 的迟到事件全部返回 false。调用方以后只能在 true 时更新 HUD 或检查清场，从源头避免重复副作用。

## 3. `RunProgressTracker`：顺序约束与胜负竞争

整局 Tracker 不关心每区有多少 Enemy，它只关心 Encounter 总数、当前索引与当前区域是否 Active。`StartRun(count)` 要求 `count > 0`，把索引设为 0 并进入 Running；`TryStartEncounter(index)` 只有在 Running、没有正在进行的区域、且 `index == CurrentEncounterIndex` 时成功。这个等式就是防止越序进入 Arena 2/3 的纯规则，Scene Gate 只是后续对规则结果的物理表现。

`CompleteCurrentEncounter()` 只有当前区域 Active 时生效。若还有后续区域，索引加一并把 Active 复位为 false，表示下一关只是获得资格，仍需玩家真正进入 Trigger；若当前已经是最后一关，则进入 Completed。判断式为：

```text
HasNext = CurrentIndex + 1 < EncounterCount
HasNext  → CurrentIndex = CurrentIndex + 1, Running
!HasNext → Completed
```

`FailRun()` 只允许从 Running 进入 Failed。所有公开命令在 Completed/Failed 下都返回 false，使状态转换具备 `Idempotency`：相同结束命令重复到达不会产生第二次有效副作用。注意 Idempotent 不等于每次都返回 true，而是第一次改变状态后，后续重复输入不能再次改变结果。Task 3 的 MonoBehaviour 会根据返回值决定是否发布 Event、开门或结算，因此这种布尔返回值是纯内核与副作用层之间的重要接口。

## 4. `DemoRunDefinition` 与 EventBus：Authoring Data、Runtime State、Scene Reference 的边界

`DemoRunDefinition` 是 `ScriptableObject`，用于让关卡设计者在 Inspector 中配置有序 `DemoEncounterDefinition[]`。数组顺序是游玩顺序；每项包含 `DisplayName`、`ObjectiveText` 和可为空的 `RewardSpell`。这些值是跨运行共享且不会在一局中变化的 Authoring Data。`SpellDefinition` 也是只读共享资产引用，奖励系统以后只把这个引用加入 Runtime Library，不克隆每张法术卡。

它刻意不保存三类数据：

- 不保存 Enemy/Gate/Trigger GameObject，因为这些引用属于具体 Scene；相同 Run Definition 未来可以用于不同 Scene 布局；
- 不保存 CurrentEncounterIndex/RunState，因为 ScriptableObject 是 Project Asset，把 Runtime State 写进去会在退出 Play Mode 后污染作者数据；
- 不自行开门或发奖励，因为数据资产不应承担 Scene Side Effect。

`GetEncounter(index)` 对越界和 null 配置显式报错，避免后续 Controller 获得 null 后在更远处才发生难定位的 `NullReferenceException`。`EncounterCount` 则成为 Task 3 校验“Definition 数量是否与 Scene 中 DemoEncounterController 数量一致”的统一来源。

三个 Event 都是 `struct + IGameEvent`，符合项目 `EventBus<T>` 的跨模块协议：

- `EncounterStartedEvent`：区域索引、总区域数、初始 Enemy 数；
- `EncounterCompletedEvent`：区域索引、总区域数、确定性 RewardSpell；
- `RunStateChangedEvent`：PreviousState、CurrentState、当前 Encounter 索引。

事件传递的是已经发生的事实，而不是“请 UI 帮我判断是否胜利”的命令。`struct` Value Type 配合泛型约束可以避免装箱；EventBus 同步派发，让 Gate、HUD 和 Reward 在同一 Gameplay 事件后响应。订阅者必须在 `OnEnable` 订阅、`OnDisable` 退订，防止 Scene Reload 后留下 Stale Subscriber；这会在 Task 3/6 的 MonoBehaviour 集成中落实。

# Task 3（已完成）：把纯流程接入 Enemy、DeathEvent、Trigger 与 Gate

Task 3 的目的，是把 Task 2 中“不认识 Unity”的两层纯状态机真正接到可游玩的 Scene，同时守住模块边界：Enemy 仍然只负责 AI、受伤与死亡，Gate 仍然只负责阻挡与显示，Trigger 仍然只负责感知玩家进入，谁都不能私自决定整局进度。最终实现形成了一条单向链路：`DemoRunController` 把 `DemoRunDefinition` 的 Authoring Data 与 Scene 中按顺序配置的 Encounter 装配起来，并且只给当前 Encounter 授予 `Armed` 权限；`EncounterEntryTrigger` 使用 `LayerMask` 过滤进入者，把有效的 `OnTriggerEnter` 转成开战请求；`DemoEncounterController` 激活本区 Enemy、关闭入口和出口 Gate，并把 `DeathEvent.TargetId` 交给纯 `EncounterProgressTracker` 去重与裁定；清场后再打开 Gate、发布完成事实，整局控制器据此推进下一关或进入 `Completed`。这一设计让空间触发、战斗事实与流程权限彼此分离，也让 9 项 PlayMode Test 和完整 Arena 1/2 Editor Gate 分别验证组件生命周期与真实游玩链路。

## 1. 为什么需要 Scene Adapter，而不是让 Enemy 自己开门

纯 `EncounterProgressTracker` 只接受整数 ID 和状态命令，它不知道 `GameObject`、`Collider.enabled`、对象激活或 EventBus。这种纯度让重复死亡、场外死亡和 Terminal State 可以在毫秒级 EditMode 测试中验证，但纯对象本身无法改变 Scene。`DemoEncounterController` 因而承担 Adapter 职责：一端读取 Unity Scene 引用并转换为纯输入，另一端把 Tracker 已经接纳的结果翻译成 Unity Side Effect。

数据流如下：

```text
Inspector 中的 HealthComponent[]
  → gameObject.GetInstanceID()
  → EncounterProgressTracker.Configure(enemyIds)

DeathEvent.TargetId
  → EncounterProgressTracker.RecordDeath(targetId)
  → 若返回 false：场外、重复、状态不允许，什么也不做
  → 若返回 true 且 IsCleared：ArenaGate 打开 + EncounterCompletedEvent
```

这种边界防止 Enemy 反向依赖关卡流程。Enemy 只负责 AI、受伤与死亡；`HealthComponent` 仍然只发布死亡事实。Gate 也不统计敌人，只接收“关闭或打开”的最终命令。如果以后把门模型换成力场、升降门或粒子屏障，只需改变 `ArenaGate` 的表现引用，不需要修改清场公式。

这里使用 `Array.Empty<T>()` 给 serialized array 提供非 null 默认值，减少未配置对象导致的无意义 `NullReferenceException`；使用普通 `for` 循环遍历 Scene 引用，避免 LINQ 和闭包分配。Enemy 激活、Gate 切换和 Encounter Event 都是离散事件，不在 `Update()` 热路径里执行。`DemoEncounterController.Initialize()` 中一次性创建 Enemy ID 数组是关卡启动时的冷路径分配，和每帧 `GC Alloc` 禁令并不冲突。

`LayerMask` 的过滤公式是：

```text
enteringLayerBit = 1 << other.gameObject.layer
isAllowed = (playerLayers.value & enteringLayerBit) != 0
```

Unity 的 Layer 编号是 `0..31`，而 `LayerMask` 是一个 32-bit bit field。`1 << n` 表示只把第 n 位设为 1；再用 bitwise AND 与允许集合求交集，结果非 0 就说明进入者属于允许的 Layer。它比用对象名称或 Tag 字符串维护流程权限更直接，也不会因为 Enemy、Projectile 碰到 Trigger 而误开战。

## 3. Unity 生命周期为什么会决定测试类型

`EditMode Test` 适合纯 C#、ScriptableObject 数据校验和不依赖 Player Loop 的 Editor API。它不会天然保证 GameObject 按真实运行顺序经历 `Awake → OnEnable → Update → OnDisable → Destroy`。`PlayMode Test` 则运行在 Player Loop 中，适合验证 MonoBehaviour 生命周期、Coroutine、物理、延迟 `Destroy` 和 Scene 行为。

`DemoEncounterController` 的死亡处理依赖以下链路：

```text
GameObject 激活
  → OnEnable()
  → EventBus<DeathEvent>.Subscribe(OnDeath)
  → Publish(DeathEvent)
  → OnDeath 被同步调用
  → Tracker.RecordDeath

Component 禁用或 GameObject 销毁
  → OnDisable()
  → EventBus<DeathEvent>.Unsubscribe(OnDeath)
```

如果测试环境根本没有可靠触发 `OnEnable`，即使 TargetId、Tracker 和断言都正确，死亡事件也不会到达 Controller。因此“纯规则是否正确”和“Unity 生命周期是否正确连接规则”必须用不同测试层验证。

## 4. 踩坑与 Debug：为什么连续修改断言仍然失败

最初四个 Controller 测试被放在 Editor-only `Game.Run.Tests` 中。失败现象是发布第一个本区 `DeathEvent` 后，`RemainingEnemyCount` 仍为 2。第一轮排查怀疑 `HealthComponent.Id` 尚未在 EditMode 执行 `Awake`，于是测试改用与正式事件同源的 `gameObject.GetInstanceID()`；失败仍然存在，说明 ID 不是根因。第二轮把 Controller GameObject 先设为 inactive，注入引用后再激活，以模拟 Scene 反序列化后进入 `OnEnable` 的顺序；仍然失败。

随后不再猜测，而是直接检查 `EventBus<DeathEvent>` 的订阅委托。诊断证明当前 Controller 的 `OnDeath` 根本不在订阅列表里，也就是失败发生在 Event 到 Tracker 之前。这一步把调查范围从“成员 ID、去重公式、Gate”缩小到“生命周期”。曾经尝试在 Editor-only 测试内部使用 `EnterPlayMode/ExitPlayMode`，但 Mode 切换会引发 Domain Reload，使测试夹具字段和对象引用跨域失效，出现新的 `NullReferenceException`。这不是业务代码的新 Bug，而是测试架构继续与生命周期对抗的结果。

最终修复不是再加等待帧或放宽断言，而是纠正测试分层：

1. 纯 `EncounterProgressTracker/RunProgressTracker` 留在 Editor-only EditMode Assembly；
2. `DemoEncounterControllerTests.cs` 连同 `.meta` 移入 `RunPlayMode`，保留 GUID；
3. 新建独立 PlayMode Test Assembly；
4. 移除 `UnityEditor.SerializedObject` 和测试内部的 Mode 切换；
5. 用测试专用 `Reflection` 注入 private serialized references；
6. TearDown 先 `SetActive(false)` 同步触发 `OnDisable`，再 `Destroy` 并等待一帧完成延迟销毁，最后清空 static EventBus。

后来加入 `DemoRunController` 自动 `Start()` 后，测试又暴露出一个更细的生命周期问题：测试若手动调用 `Initialize()`，下一帧 Unity 又执行 `Start()`，就可能把“测试安排的初始化时机”和“Production 自动初始化”混在一起。最终保留 Production 的幂等保护，并把测试分别写成“验证 Start 自动初始化”和“显式初始化后不会重复产生 Side Effect”，而不是靠任意增加等待时间来碰运气。

期间还出现过 `CS0246`：PlayMode Test 找不到 Runtime 类型。根因不是类型真的不存在，而是测试脚本所在文件夹与 `.asmdef` 的编译边界不一致。Unity 的 Assembly Definition 决定一份脚本能引用哪些 Assembly；文件移动到正确的 `RunPlayMode` 边界并补齐 `Game.Run / Game.Core / Game.Combat` 引用后，类型才处在正确依赖图中。另一些 Console 中的 `GameObjectInspector.m_Targets`、`SerializedObjectNotCreatableException` 是 Unity Inspector 持有已销毁测试对象的 Editor UI stale state；判断业务测试应看 Test Runner assertion 和 Runtime 日志，不能把 Editor 面板自身的残留异常误判成 Encounter 规则失败。

最终自动化证据是 `Game.Run.PlayMode.Tests` 9 项全部通过：5 项验证单区 Controller、Gate、DeathEvent 与 Entry Trigger，4 项验证整局初始化、顺序推进和 Terminal State。它们证明 Adapter 在真实 Unity 生命周期下正确订阅、处理、退订并保持幂等。

## 5. Scene 装配、整条运行链和最终 Editor Gate

这一阶段最终在 `P7_DemoRun` 中先装配两个 Encounter。`DemoRunDefinition_P7.asset` 保存两个有序定义；`DemoRunRoot` 上的 `_encounters` 必须以相同顺序引用 `Encounter_01_Basics` 与 `Encounter_02_Elements`。每个 Encounter 都有自己的 Enemy 成员、入口/出口 `ArenaGate` 和一个带 `BoxCollider.isTrigger = true` 的 `EntryTrigger`。Gate 的 `Blocker` Collider 必须是普通 Collider 而不是 Trigger；Entry Trigger 的 `Player Layers` 只选 Player。

完整运行顺序是：

```text
Scene Start
  → DemoRunController.Initialize
  → 初始化两个 Encounter，只有 Encounter 0 被 Arm
  → Player 进入 Encounter 0 Entry Trigger
  → Waiting? 拒绝；Armed? 迁移到 Active
  → 入口/出口 Gate 关闭，本区 Enemy 激活
  → HealthComponent 死亡发布 DeathEvent
  → 本区 Tracker 过滤场外 ID 与重复 ID
  → 最后一名有效成员死亡，Encounter 0 Cleared 并开门
  → DemoRunController 推进 CurrentEncounterIndex，Arm Encounter 1
  → Encounter 1 重复上述流程
  → 最终完成后 RunProgressTracker 进入 Completed
  → 发布一次 RunStateChangedEvent，留给后续 Victory UI 消费
```

开发者在 Editor 中验证了整条链路：第二关不能越序启动；进入第一关后入口和出口都关闭且只激活本区 Enemy；击杀其中一人不会提前开门；本区全部死亡后开门并激活下一关资格；第二关清场后整局进入 `Completed`。水球、火球、Water/Fire Cell 与 Enemy 战斗仍符合预期，说明关卡 Adapter 没有破坏既有 Combat 和 ElementWorld 链路。

## 6. 设计取舍、边界与面试表达

当前方案使用“Scene 中预放置、开战时激活”的 Enemy，而不是开战时动态 Instantiate。它的优点是地编能直观看见阵型、引用配置简单、Demo 阶段没有运行时生成和回收复杂度；缺点是大量关卡时 Scene 会膨胀，后续正式项目更适合使用 Spawn Point + Object Pool。Gate 目前通过显隐同一个 Blocker 来表现，优点是验证迅速；以后替换为动画门、Shader 力场或 VFX 时，只需要扩展 `ArenaGate` 的 Presentation，不应把清场规则塞回门脚本。

Task 3 的边界是“战斗流程已经可玩且顺序正确”，它没有解决法术奖励是否污染 Project Asset。下一步 Task 4 会把 `P7_StartingWandLoadout` 和 `P7_StartingSpellLibrary` 当作只读 Authoring Template，在每局开始时创建 Runtime Clone；拾取奖励和法杖编辑只修改 Clone，Restart 再从模板生成干净状态。

面试时可以这样解释当前阶段：

> 我把关卡流程拆成纯 Tracker 和 Scene Adapter 两层。EncounterProgressTracker 与 RunProgressTracker 只处理状态、索引、成员 ID 和死亡去重，不引用 Unity；DemoRunController 只负责把 Definition 顺序装配到 Scene，DemoEncounterController 把 HealthComponent 转成 Instance ID，并把有效状态变化翻译为激活敌人、开关 Gate 和 EventBus 事件；EncounterEntryTrigger 则只把 Physics Trigger 转成开始请求。这样 Enemy 不需要认识门，Gate 也不需要认识敌人，UI 后续只消费事实事件。
>
> 我在测试上也做了同样分层。纯状态机留在 EditMode；依赖 OnEnable、Start、OnTriggerEnter、EventBus 和延迟 Destroy 的 Adapter 放在独立 PlayMode Assembly。调试时最初像 TargetId 错误，但检查 EventBus delegate 后发现实际是 EditMode 生命周期没有订阅；强行切换 Play Mode 又引入 Domain Reload，所以最终纠正测试边界。后来再处理自动 Start 与测试显式 Initialize 的竞争，并依靠幂等初始化消除重复 Side Effect。最终 9 项 PlayMode Test 和 Arena 1/2 的完整 Editor Gate 都通过，分别证明组件级生命周期和真实游玩链路成立。

## 1. Authoring Template 与 Runtime State 为什么必须分开

`ScriptableObject` 是 Unity Project 中的序列化资产。它适合保存设计师在 Inspector 中配置的起始法术、法术顺序和数值，因为多个 Scene 对象可以共享同一份 Data-driven 数据；但它不会天然变成“进入 Play Mode 后自动回滚的一局存档”。如果运行时代码直接修改 Project Asset 的数组，修改的是编辑数据本身，而不是仅属于当前 Run 的瞬时状态。

Task 4 把数据分成三层：

```text
P7_StartingSpellLibrary.asset / P7_StartingWandLoadout.asset
  = Authoring Template，只定义一局开始时应该有什么
        ↓ RunSpellSession.Initialize()
RuntimeLibrary / RuntimeWand
  = 当前 Run 的可变容器，HideFlags.DontSave
        ↓
SpellCaster 读取 RuntimeWand
Wand Editor 读取并编辑同一个 RuntimeWand / RuntimeLibrary
Reward 只追加到 RuntimeLibrary
        ↓ Scene 卸载 / Restart
OnDestroy 回收 Clone；新 Scene 再从 Template 创建干净状态
```

这里既使用 `Object.Instantiate(ScriptableObject)` 创建 Runtime Clone，又显式复制 `Available` 和 `Spells` 数组。原因是我们真正要隔离的是可变容器的所有权：本局可以重新排列或扩展数组，但模板数组不能一起变化。数组元素仍然引用相同的 `SpellDefinition` 资产，这是有意的 shallow copy；每张法术卡在本 Task 中是共享的只读定义，没有必要把图标、Prefab、伤害等整份数据重复克隆。这样既避免资产污染，也避免制造一套难以同步的 Runtime SpellDefinition 副本。

`HideFlags.DontSave` 表达 Runtime Clone 不应该被保存进 Scene 或 Project Asset。`RunSpellSession.OnDestroy()` 则完成所有权闭环：谁创建 Runtime Clone，谁负责销毁。`Instantiate`、数组复制和奖励时的新数组都属于开局或拾取这类低频离散事件，不在 `Update/FixedUpdate` 热路径，因此不违反每帧 0 B `GC Alloc` 的性能规则。

## 3. Encounter 奖励如何做到不提前、不串关、不重复

奖励链路不是“玩家碰到场景里的发光物就读自己 Inspector 中的 Spell”，而是从已经裁定的 Encounter 事实开始：

```text
DemoRunController.Initialize
  → DemoEncounterController 得到权威 encounterIndex
  → BindChildRewards()
  → inactive 的 SpellRewardPickup 也被绑定相同 index

Encounter 清场
  → EncounterProgressTracker 首次进入 Cleared
  → DemoEncounterController 发布 EncounterCompletedEvent
       EncounterIndex + Definition.RewardSpell
  → 只有编号匹配的 Pickup 进入 Available
  → 启用 Visual 子物体和 Trigger

Player 进入 Trigger
  → LayerMask 验证
  → RunSpellSession.TryGrantSpell
  → RunSpellInventoryOps.TryAppendUnique
  → 成功：更新 RuntimeLibrary + SpellRewardGrantedEvent
  → 已拥有：不重复加入
  → 两种结果都会把世界拾取物标记 Consumed 并隐藏
```

`_available` 与 `_consumed` 分别表示“规则是否解锁”和“世界拾取物是否已经处理”。二者不能合成一个 bool：一个未通关的奖励是未解锁但也未消费；一个已经拾取的奖励则是已解锁过且已消费。`OnEncounterCompleted` 还检查事件编号，所以后续关卡即使 GameObject 已存在，也不会因前一关完成而提前显示。

最容易漏掉的是 inactive 对象的查找语义。Unity 的 `GetComponentsInChildren<T>()` 默认不包含 inactive 子物体；而奖励恰好在清场前需要隐藏。若不传 `true`，父 Encounter 初始化时找不到它，Prefab 上残留的旧 `_encounterIndex` 就不会被覆盖。这里使用 `GetComponentsInChildren<SpellRewardPickup>(true)`，明确把 inactive 子物体纳入初始化绑定。它返回数组并产生一次分配，但初始化是低频冷路径；相比在 `Update` 中轮询或让每个 Reward 手填编号，这个 trade-off 更安全、更容易诊断。

## 5. Debug 案例：UI 为空，Wizard 为什么仍会发射默认火球

Task 4 验收中出现过一个非常有教学价值的症状：Wand 编程界面显示当前法杖为空，但点击施法后 Wizard 仍然发射旧的默认 Fireball。这个现象说明“UI 显示的数据”和“SpellCaster 实际求值的数据”不是同一个 Source of Truth，而不是 `CastEvaluator` 忽略了空法杖。

`SpellCaster.ResolveWand()` 的选择顺序是：

```text
若 _runSpellSession != null
且 Session 已初始化
且 RuntimeWand != null
    → 使用本局 RuntimeWand
否则
    → 回退旧 Inspector _wand
```

当 `WizardPlayer` 上 `SpellCaster` 的 **Run Spell Session** 没有拖入引用时，第一组条件立即失败，于是 Caster 使用旧 `_wand`。与此同时，Wand Editor 可以已经绑定自己的 Run Session，显示另一份 Runtime 数据；结果便是 UI 看起来为空，实际施法却读取仍含 Fireball 的旧模板。这也是为什么只盯着 UI Slot、Projectile Prefab 或 CastEvaluator 都找不到根因。

正确定位过程应从现象反推数据源：

1. UI 能显示空数组，说明 Runtime Wand 本身可能确实为空。
2. 仍能生成 Fireball，说明 Caster 获得的输入数组不为空。
3. 检查 `ResolveWand` 的 fallback 条件，而不是先修改解释器。
4. 在 `P7_DemoRun/__Gameplay/WizardPlayer` 选择 `SpellCaster`，确认 **Run Spell Session** 引用指向 `DemoRunRoot` 上的 `RunSpellSession`。
5. 重新进入 Play Mode：空 Runtime Wand 应无法施法；把 Fireball 拖入 Runtime Wand 后才恢复发射。

这个 Bug 同时体现四个 Unity/架构知识点：Project Asset 是 Authoring Template，Runtime Clone 是本局状态；`[SerializeField]` 只声明字段可被 Inspector 序列化，不会自动寻找 Scene 组件；兼容旧场景的 fallback 会把“缺引用”转化为“看似仍可运行但数据错位”；诊断时必须比较每个消费者的真实数据源，而不能只看最终画面。修复是补齐 Inspector 引用，没有修改 CastEvaluator 或硬编码 Fireball。

## 6. Trade-off、后续边界与模拟面试回答

当前方案选择 Runtime `ScriptableObject` Clone，而不是建立一套完全独立的 Save DTO。优点是现有 SpellCaster、Wand Editor 和纯求值器可以继续读取 `WandLoadout/SpellLibrary`，迁移面小，Restart 通过 Scene 重载自然得到干净状态；缺点是 Scene 中多个消费者必须正确绑定同一 Session，而且 Runtime 状态暂时不能跨 Scene 保存。P7 第一版只有一个 Demo Run Scene，这个边界合理；未来若增加跨 Scene 房间或正式存档，应把 Run Snapshot 序列化为纯数据，再由 Session 恢复，而不是给 Clone 加 `DontDestroyOnLoad` 后继续扩大隐式生命周期。

奖励采用确定性 `DemoRunDefinition.RewardSpell`，而不是随机 Loot Table。它牺牲了每局随机性，但让教学节奏、平衡测试和 Bug 复现稳定：开发者能明确知道 Arena 1 后玩家拥有什么，Arena 3 应检验哪种编程选择。P7-B 再在已经成立的奖励接口后替换为 Seeded Random，不需要改 Pickup 与 Session 的所有权边界。

面试时可以这样从头讲解：

> 在完整单局 Demo 中，我先解决了 ScriptableObject 的所有权问题。原 Wand Editor 会直接写 Project Asset，所以我新增 Game.Run 的 RunSpellSession，把起始 SpellLibrary 和 WandLoadout 只当 Authoring Template。开局使用 Object.Instantiate 创建 HideFlags.DontSave 的 Runtime Clone，并显式复制法术引用数组；SpellDefinition 仍共享，因为它们是只读定义。SpellCaster、Palette 和 Wand Frame 都注入同一个 Session，因此施法与 UI 编辑拥有同一个 Source of Truth；Scene 卸载时 Session 销毁 Clone，Restart 会从模板恢复。
>

>
> 测试上我用 EditMode 锁定数组隔离、去重和新一局恢复，用 PlayMode 覆盖 EventBus、Active State 和 Trigger，再在真实 Scene 验证奖励不提前、不串关、不重复以及模板不被污染。最后一次全量 EditMode 是 321 项中 320 项通过，仍有一个 Encounter Binding 自动化测试债务，所以我不会声称全量通过。实际 Debug 中还遇到 UI 为空但仍发默认火球：沿数据源检查发现 SpellCaster 没绑定 RunSpellSession，因兼容 fallback 读取了旧 Wand；补齐 Inspector 引用后 UI 和施法重新共享 Runtime Wand。这个案例让我建立了从症状比较消费者数据源、再检查序列化引用和 fallback 的调试方法。

## 1. `AttackDefinition`、`EnemyDefinition` 与 Prefab 各自拥有什么

本 Task 最容易混淆的不是算法，而是三种 Unity Asset 看起来都在描述“敌人”。它们实际上处于不同层级：

```text
P7_EliteMagicEnemy.prefab                场景实体与组件组合
├─ HealthComponent                       本实体 HP、Team、Defense
├─ Animator / CharacterController         动画与移动碰撞能力
└─ RangedEnemyController
   └─ P7_EliteMagicEnemyDefinition.asset  AI 行为与攻击节奏
      ├─ Move/Detect/Lose/AttackRange
      ├─ AttackCooldown/Retreat/ProjectileSpeed
      ├─ ProjectilePrefab → Fireball
      └─ Attack → Enemy_Wizard_AttackDefinition
                    单次攻击的伤害类型、基础伤害、生成时刻与动画状态名
```

`AttackDefinition` 回答“一次攻击是什么”：例如基础伤害、`DamageType`、`ArrowSpawnTime` 和 `AnimationStateName`。普通 Magic 与 Elite 可以共享同一份 AttackDefinition，表示二者使用同一种攻击动作；如果以后只想改变 Elite 单发伤害，应复制一份 P7 专用 AttackDefinition，而不能直接修改共享资产，否则普通 Magic 也会变化。

`EnemyDefinition` 回答“这个 AI 怎样行动和多久攻击一次”。它属于 `Game.Combat` 的 Data 层，不引用具体 Character Controller 类型，但由 `RangedEnemyController` 读取远程字段。HP 不放在这里，而在 Prefab 的 `HealthComponent` 上；这样 AI 配置和生命实体不会出现两份互相冲突的 Max HP。

Prefab 回答“Scene 中实际生成什么对象”。`Prefab Variant` 继承 `MagicEnemy_Base` 已验证的 Animator、CharacterController、Projectile Spawn Point、Status 与 Feedback 组件，只覆盖 Elite 自己的 Definition、HP、Scale 等序列化值。与复制一个完全独立 Prefab 相比，Variant 能继续接收 Base Prefab 的通用修复；代价是必须理解 Override 只属于 Variant，不能误点 Apply 回 Base 让普通敌人一起变化。

## 3. 四区运行链为什么不需要 Enemy 认识 Gate

四区内容变化后，流程仍是同一条稳定链：

```text
DemoRunController.Initialize
  → 校验 Definition 数量 == Scene Encounter 数量
  → 初始化四个 DemoEncounterController
  → 只 Arm Encounter 0

玩家进入当前已 Armed 的 EntryTrigger
  → EncounterProgressTracker: Armed → Active
  → DemoEncounterController 关闭本区 Gate、激活本区 Enemy Members

任意成员 HealthComponent 死亡
  → 发布 DeathEvent(TargetId)
  → 本区 Tracker 判断：是否成员、是否首次死亡、是否 Active
  → 最后一名权威成员死亡后进入 Cleared
  → 打开 Gate、发布 EncounterCompletedEvent

DemoRunController 接收完成事实
  → RunProgressTracker 推进 CurrentEncounterIndex
  → Arm 下一 Encounter
  → 最终 Encounter 完成后进入 RunState.Completed
```

Elite 不需要知道自己是最终敌人，也不需要在死亡时直接弹 Victory。它只是最终 Encounter 的一个 `HealthComponent` 成员；`DeathEvent.TargetId` 与初始化记录的 `gameObject.GetInstanceID()` 相同，因此仍能进入通用去重公式。谁是最终关由 `DemoRunController` 的顺序和 `RunProgressTracker` 决定，而不是由 Prefab 名称、Tag 或 Boss 脚本决定。这使 Elite 将来替换成另一种敌人、多个敌人或真正 Boss FSM 时，Run Flow 不需要重写。

`Enemy Members` 是清场真相的 Scene 边界：Hierarchy 中存在 Enemy 但没有拖入数组，它的死亡不会计数；数组仍引用已删除对象，则初始化会报 Missing；数组漏掉 Elite，则区域可能提前清场。反过来，数组包含不属于该区域的 HealthComponent，远处死亡也可能错误推进。因此技术检查只关心“实际参与本区流程的对象是否与权威数组一致”，不规定设计师应该放几个或放在哪里。

## 1. 暂停为什么不是一个 bool：`RunPauseReason` 与所有权模型

如果 Wand Editor 和 Pause Menu 都直接执行 `Time.timeScale = 0`，再在各自关闭时执行 `Time.timeScale = 1`，就会产生典型的 Lost Update：Wand Editor 先暂停，Pause Menu 或 Victory 随后也要求暂停，此时关闭 Wand Editor 会无条件写回 1，导致仍然打开的菜单背后 Gameplay 恢复。问题不在于 `Time.timeScale` API 本身，而在于多个调用方共享同一个全局状态却没有表达“谁仍然持有暂停”。

`RunPauseReason` 使用 `[Flags] enum : byte` 表示三种正交原因：`WandEditor`、`PauseMenu`、`TerminalResult`。`RunPauseCoordinator.RequestPause` 使用按位 OR 加入原因，`ReleasePause` 使用按位 AND 与取反移除原因；重复申请和重复释放都是幂等操作。第一个原因加入时才保存暂停前的正 `Time.timeScale`、写入 0 并解锁 Cursor；只有最后一个原因移除后才恢复原速度并重新锁定 Cursor。这样 UI 不拥有全局时间，它只拥有自己的 Reason。

```text
None
  → Request(WandEditor)                 Active = WandEditor, TimeScale = 0
  → Request(PauseMenu)                  Active = WandEditor | PauseMenu
  → Release(WandEditor)                 Active = PauseMenu, 仍保持 0
  → Release(PauseMenu)                  Active = None, 恢复 Gameplay

Running → Completed / Failed
  → Release(PauseMenu)
  → Request(TerminalResult)
  → Victory / Defeat 始终保持暂停
```

`PrepareForSceneTransition` 是另一个重要边界。`Time.timeScale` 是 Unity 的全局静态状态，不会因为某个 Panel 隐藏就自动恢复；如果在暂停中直接加载新 Scene，新 Scene 的 Coroutine、Animator 或依赖 scaled time 的初始化可能看起来像“加载后卡死”。因此 Restart/Return 在调用 `SceneManager.LoadSceneAsync` 前强制清空原因、恢复 1 并将 Cursor 设为菜单可用状态。`OnDisable` 还提供 Scene 卸载或组件被禁用时的兜底清理。代价是当前设计假设一局只有一个权威 Coordinator；如果未来出现局部 Slow Motion，应把时间倍率合成提升为独立 Time Service，而不是继续给 Reason 增加速度语义。

## 2. HUD 为什么读取权威快照，而不是自己数 DeathEvent

HUD 若直接订阅所有 `DeathEvent` 并执行 `remaining--`，会把场外 Enemy、重复死亡、其他 Team 甚至 Player Death 都算进去。`DemoEncounterController` 已经拥有 `EncounterProgressTracker` 和成员 ID 集合，因此它才是“这次死亡是否属于当前 Active Encounter、是否首次有效”的权威。当前实现只在 `_tracker.RecordDeath(TargetId)` 返回 true 后发布 `EncounterProgressChangedEvent`，事件携带 `EncounterIndex / EncounterCount / RemainingEnemyCount` 快照；无关或重复 ID 不产生 UI 事件。HUD 只显示收到的结果，不复制成员过滤规则。

玩家失败也采用同一原则。`DemoRunController` 新增序列化 `_playerHealth`，订阅 `DeathEvent` 后只比较 `deathEvent.TargetId == _playerHealth.Id`；Enemy Death 不会触发 Defeat。匹配后仍由纯 `RunProgressTracker.FailRun()` 决定能否从 `Running` 进入 `Failed`，因此重复 Player Death 或胜利后迟到的死亡事件不能覆盖 Terminal State。Controller 只在真实状态迁移成功后发布一次 `RunStateChangedEvent`，Victory/Defeat Panel 不自行查找 Player、Enemy 或 Gate。

`DemoRunHudController` 位于 `Game.UI` Presentation 层，订阅 Encounter Started/Progress/Completed、Spell Reward Granted 和 Run State Changed。它从 `DemoRunController.Definition` 只读获得 `DemoEncounterDefinition.DisplayName/ObjectiveText`，从事件获得动态数量；常驻逻辑没有 `Update()`，因此不会每帧进行字符串拼接或 Scene Search。Notification 复用一个 Panel 和一个 Coroutine，使用 `WaitForSecondsRealtime`，即使 Wand Editor 或 Pause Menu 把 `Time.timeScale` 设为 0，提示仍能按真实时间收起。每次通知产生少量字符串和 Coroutine 分配属于低频离散 UI 行为，不是 Gameplay 热路径。

## 4. 一个 UICanvas 为什么可以容纳多个界面

`Canvas` 是 UGUI 的渲染与缩放边界，不等于“一个 Canvas 只能有一页”。`P7_DemoRun` 的 `UICanvas` 已有 `Canvas / CanvasScaler / GraphicRaycaster`，Player HUD、Wand Editor、Run HUD 和菜单共享它，可以使用一致的分辨率缩放与输入射线规则。具体页面是否出现由根 GameObject 的 Active State 决定，同级对象越靠后越晚绘制、视觉上越靠上。Gameplay HUD 常开；Notification 平时 inactive，只在事件发生时短暂出现；Pause/Settings/Victory/Defeat 初始 inactive，并由一个 Controller 互斥切换。Pause 的半透明背景覆盖 HUD 属于有意 Overlay，不表示状态冲突；Terminal 时 Gameplay HUD 会隐藏。

拆成多个 Canvas 可以隔离 `Canvas Rebuild` 或建立不同 Sorting Order，但也会增加缩放、排序和多个 `GraphicRaycaster` 的维护成本。当前 UI 数量小、主要由低频事件更新，没有 Profiler 证据要求拆分，因此单 Canvas 是更小的正确方案。未来若 Profiler 显示频繁变化的血条导致 `Canvas.BuildBatch` 成为瓶颈，再把高频 HUD 与静态菜单拆到独立 Canvas；性能架构应由测量驱动。

## 6. Trade-off、常见故障与模拟面试回答

常见故障可以按症状反推所有权：按 Escape 没反应，先检查 `InputActionReference` 是否选择 `Player/Pause` 而非 `UI/Cancel`；关闭 Wand Editor 后结算背后恢复，检查两个 UI 是否引用同一个 Coordinator，而不是某一处仍直接写 Time Scale；Enemy 死亡弹 Defeat，检查 Player Health 是否错误拖成 Enemy；剩余数量重复下降，检查 UI 是否又自行订阅 DeathEvent；Restart 后画面卡住，检查 Scene Load 前是否执行了 `PrepareForSceneTransition`；Panel 看似重叠，先检查 Active State 与 Hierarchy Sibling Order，而不是先创建更多 Canvas。

面试时可以这样完整说明：

> 我在完整单局 Demo 中把 UI 设计成 Run 状态的只读消费者。Encounter Controller 已经拥有成员 ID 和去重 Tracker，所以每次有效 Enemy Death 后由它发布剩余数量快照，HUD 不直接对所有 DeathEvent 做减法；Player Death 则由 DemoRunController 比较序列化 Player Health 的 Instance ID，调用纯 RunProgressTracker 进入一次性 Failed，再发布 RunStateChangedEvent。这样 Victory/Defeat Panel 不判断 Enemy，也不反向修改 Gameplay。
>
> 暂停部分我没有让 Wand Editor、Pause Menu 和终局界面分别写一个 bool，而是使用 Flags Enum 表达三个 Pause Reason。唯一 RunPauseCoordinator 通过位运算持有原因集合：第一个 Reason 把 Time.timeScale 设为 0，最后一个释放才恢复，所以关闭 Wand Editor 不会误恢复仍打开的 Pause 或 Victory。Scene Load 前还显式恢复 Time Scale 与 Cursor，避免全局静态状态污染下一 Scene。Wand Editor 和 Pause Controller 只申请自己的原因，并通过 ForceClose 与原因查询避免两个交互层争抢 Cursor。

# Task 7（已完成）：Main Menu、跨 Scene Settings 与可复用 Fade 应用外壳

Task 7 的目的，是把“在 Unity Editor 里打开战斗 Scene 并按 Play”提升为真正的游戏应用生命周期。Task 6 已经让单局拥有 Pause、Victory、Defeat、Restart 和 Return 按钮，但当时 Return 指向的 Main Menu 尚不存在，Settings 也只是一个导航外壳；直接调用 `SceneManager.LoadSceneAsync` 虽然能换场景，却会暴露 Camera/UI 初始化跳变、允许按钮重复点击，并可能把 `Time.timeScale=0`、Cursor 或尚未刷盘的设置带到下一 Scene。本 Task 因此分成两条相互独立又在 Scene 边界汇合的技术链：第一条由 `Game.Core.UserSettingsService` 统一管理 Master Volume、Mouse Sensitivity 与 Fullscreen，使 Main Menu、Pause Settings 和 Character 通过值快照共享同一 Source of Truth；第二条由 `Game.UI.DemoSceneTransitionController` 把 Start、Restart、Return 包进可复用的 Fade Transaction，在黑色全屏遮罩下封锁输入、恢复全局状态、保存设置并异步加载。最终 `P7_MainMenu` 与 `P7_DemoRun` 各自持有同一 Settings/Fade Prefab 的实例，不依赖 `DontDestroyOnLoad` 单例；开发者已验证完整跨 Scene 流程、设置实时生效与保持、Fade In/Out 和重复加载防护。这个 Task 让 Demo 从“可玩的一局”成为具有启动、返回、重启和用户偏好保存的可展示作品。

## 1. Settings 为什么位于 Game.Core，而不是 Main Menu 或 Wizard

Master Volume、Mouse Sensitivity 和 Fullscreen 都不属于某一局 Run，也不属于某个具体角色。Main Menu 可以修改它们，Pause Settings 也可以修改；Audio、Character 和平台窗口又分别需要消费其中一部分。如果把数值保存在 `DemoMainMenuController`，加载 `P7_DemoRun` 后该对象被销毁；如果让 UI 直接引用 `WizardController` 修改 `_lookSensitivity`，就会形成 `Game.UI → Game.Character` 的上层直连，也无法让未来其他角色自动复用。因此设置的唯一 Source of Truth 放在最底层 `Game.Core`，上层只读取不可变快照或订阅值类型 Event。

`UserSettingsValues` 是 `readonly struct`，包含三个只读属性和统一 Clamp 规则：Master Volume 为 `0～1`；Mouse Sensitivity 为 `0.25～2` 的倍率；Fullscreen 为 bool。它主动处理 `NaN` 和正负 Infinity，非法浮点数回退默认值，而不是让异常数据继续进入 Audio 或 Camera。选择“倍率”而不是直接保存“度/像素”，是为了保留 `PlayerControllerBase._lookSensitivity` 作为角色/设备 Authoring Base：

```text
Effective Look Sensitivity
  = Inspector Base Look Sensitivity
  × UserSettingsValues.MouseSensitivity

Wizard Base = 0.12
Multiplier 0.25 → 0.03 度/像素
Multiplier 2.00 → 0.24 度/像素
```

`UserSettingsService` 使用集中常量封装三个 `PlayerPrefs` Key。`RuntimeInitializeOnLoadMethod(BeforeSceneLoad)` 在每次 Play/应用启动前重建静态快照，即使 Editor 关闭 Domain Reload 也不会沿用上一次 Play 的脏静态值。读取后先 `Sanitize()`，再应用 `AudioListener.volume` 和 `Screen.fullScreen`；真实变化才发布 `UserSettingsChangedEvent`。Slider 拖动时 `Set` 只更新 Runtime、PlayerPrefs 内存缓存和消费者，不立即执行连续磁盘写入；Settings Panel 关闭或 Scene Transition 前才调用 `PlayerPrefs.Save()`。这个方案适合三个小型设置，但 PlayerPrefs 不是 Run Save、角色存档或大数据数据库，未来正式音频混音应把线性 Master Volume 迁移到 `AudioMixer` dB 参数。

`PlayerControllerBase` 在 `OnEnable` 订阅设置事件并立即读取当前快照，在 `OnDisable` 对称退订；Camera 的 `LateUpdate` 只多做一次 float 乘法，不产生 `new`、LINQ、Boxing 或 GC Alloc。`DemoSettingsController` 使用 `Slider.SetValueWithoutNotify` 与 `Toggle.SetIsOnWithoutNotify` 刷新 UI，避免“打开 Panel 刷新控件 → 触发 OnValueChanged → 又写一遍设置”的回调环。共享 `PF_P7_SettingsPanel` 的 Back Button 不保存某个 Scene Controller 引用：Main Menu Instance 调用 `DemoMainMenuController.CloseSettings`，DemoRun Instance 调用 `DemoPauseMenuController.CloseSettings`，这些是各 Scene 的 Override，而 Slider/Toggle 与 `DemoSettingsController` 留在 Prefab 内共享。

## 2. Fade 玩家看到了什么，它解决的却不只是画面好看

玩家点击 Start 时看到 Main Menu 逐渐变黑，短暂黑屏后新 Scene 从黑色淡入；Restart 和 Return 走相同流程。视觉上它消除了 Scene 瞬切的生硬感，工程上它同时建立了一个 Scene Transition Transaction：开始后拒绝第二个请求、用全屏 UI 阻挡按钮、在黑屏中隐藏 Camera/Lighting/HUD 初始化差异、恢复全局时间与 Cursor、把 Settings 刷盘，再调用 `LoadSceneAsync`。如果只让 Button 直接调用 SceneManager，这些职责会散落在 Start/Restart/Return 三个入口中，很容易出现某条路径忘记恢复 `Time.timeScale` 或忘记防双击。

完整时序如下：

```text
新 Scene 激活
  → PF_P7_SceneFade.Awake
  → CanvasGroup Alpha = 1，Blocks Raycasts = true
  → Start: FadeInRoutine
  → Alpha 1 → 0
  → Blocks Raycasts = false，玩家获得控制

Start / Restart / Return
  → LoadScene(sceneName)
  → _isTransitioning 已为 true？是：拒绝重复请求
  → 否：锁定 Transition，Blocks Raycasts = true
  → FadeRoutine(currentAlpha, 1)，画面变黑
  → Time.timeScale = 1
  → Cursor 解锁并显示
  → UserSettingsService.Save()
  → SceneManager.LoadSceneAsync(sceneName)
  → 旧 Scene 卸载
  → 新 Scene 自己的 Fade Prefab 从 Alpha 1 淡入到 0
```

这里使用 `Time.unscaledDeltaTime` 是关键。Pause、Victory 和 Defeat 都可能让 `Time.timeScale=0`；普通 `Time.deltaTime` 此时同样为 0，`elapsed += deltaTime` 永远不增长，Fade Coroutine 会永久停在第一帧，Restart/Return 也永远无法进入加载。Unscaled Time 代表不受 Gameplay 时间倍率影响的真实帧间隔，适用于 Pause UI、Loading、Fade 等应用层表现。`Mathf.Clamp01(elapsed/duration)` 把进度限制到 `0～1`，`Mathf.Lerp(from,to,t)` 再把进度映射为 Alpha；循环结束后显式写入最终 to 值，消除浮点累积导致的尾差。

## 3. `PF_P7_SceneFade` 每个组件、参数和配置理由

Fade Prefab 的结构有意保持极小：

```text
PF_P7_SceneFade
├─ RectTransform
├─ Canvas
├─ CanvasScaler
├─ GraphicRaycaster
├─ DemoSceneTransitionController
└─ FadeBlocker
   ├─ RectTransform
   ├─ CanvasRenderer
   ├─ Image
   └─ CanvasGroup
```

### 根对象 Canvas：为什么它与普通 UI 分开

普通 Player HUD、Wand Editor、Pause 和 Run Menu 可以共享 `UICanvas`，因为它们的显隐由 Active State 与 Sibling Order 管理。但 Fade 是应用层最上方的安全幕布，必须在任何 Scene、任何菜单组合下都覆盖全部 UI。因此它使用独立 `Canvas`，`Render Mode = Screen Space - Overlay`，不依赖 Camera 是否已初始化；`Sorting Order = 1000`，明确高于普通 Canvas 的 0。这里拆 Canvas 不是为了“一个界面一个 Canvas”，而是为了建立跨所有 Presentation 的固定顶层排序边界。代价是多一个 Canvas/Batch 边界，但 Fade 只在 Scene 进入或切换时变化，且只含一个 Image，这个成本远小于排序不可靠的风险。

`CanvasScaler` 保留 UGUI 的屏幕适配入口；纯色全屏遮罩本身不依赖具体像素美术，但未来加入 Loading Text/Icon 时可以共享尺度规则。`GraphicRaycaster` 让这个 Canvas 上 Raycast Target 开启的 Image 真正参与 EventSystem 射线检测；只设置 `CanvasGroup.blocksRaycasts=true` 却没有 GraphicRaycaster，顶层 Canvas 不会产生 UI Raycast Hit，后面的按钮仍可能收到点击。

根对象当前实际 Inspector 参数如下：

| 组件 | 参数 | 当前值 | 为什么这样配置 |
|---|---|---|---|
| `Canvas` | Render Mode | `Screen Space - Overlay` | 直接覆盖最终屏幕，不依赖 Main Camera 是否已经生成、启用或完成 URP 渲染。|
| `Canvas` | Pixel Perfect | Off | Fade 是纯色遮罩，没有需要像素对齐的 Sprite；开启只会增加不必要的坐标取整约束。|
| `Canvas` | Sort Order | `1000` | 建立高于普通 HUD、Pause、Wand Editor 和 Terminal Panel 的固定顶层边界。|
| `Canvas` | Target Display | `Display 1` | P7 Demo 只使用主显示器；未来多显示器项目需要为每个目标显示器单独决定遮罩策略。|
| `CanvasScaler` | UI Scale Mode | `Constant Pixel Size` | 当前遮罩靠 Anchor Stretch 覆盖屏幕，不依赖参考分辨率缩放；Scale Factor 保持 1 即可。|
| `CanvasScaler` | Scale Factor | `1` | 不额外放大或缩小 UI 单位。这个值不会改变四向 Stretch 的全屏覆盖关系。|
| `CanvasScaler` | Reference Pixels Per Unit | `100` | UGUI 默认值；当前 Image 没有 Sprite，因此不会影响黑幕视觉。|
| `GraphicRaycaster` | Ignore Reversed Graphics | On | 忽略背向 Raycaster 的 Graphic，是 Screen Space UI 的合理默认保护。|
| `GraphicRaycaster` | Blocking Objects | `None` | Fade 只需要阻挡 UGUI Pointer Event，不需要让 2D/3D Physics Collider 参与 UI 射线判断。|
| `GraphicRaycaster` | Blocking Mask | `Everything` | 当前 Blocking Objects 为 None，所以它不会额外执行 Physics Blocking；保留默认值不会扩大运行时职责。|

这里有一个容易混淆的基础点：`CanvasScaler` 决定“UI 单位如何随分辨率缩放”，`RectTransform Anchor` 决定“子 Rect 的边缘如何依附父 Rect”。FadeBlocker 能覆盖 2K、4K 和超宽屏，真正起决定作用的是四向 Stretch Anchor，而不是把 CanvasScaler 的 Reference Resolution 写成某个目标分辨率。当前 Fade 只有纯色遮罩，所以 `Constant Pixel Size` 已足够；将来若增加固定字号的 Loading Text、Logo 或进度条，再评估是否切换为 `Scale With Screen Size`，并根据目标宽高比选择 Match 参数。

### FadeBlocker RectTransform：为什么必须四向 Stretch

最终保存值为：

```text
Anchor Min = (0, 0)
Anchor Max = (1, 1)
Anchored Position = (0, 0)
Size Delta = (0, 0)
```

Anchor Min/Max 表示相对父 Rect 的比例坐标。`(0,0)→(1,1)` 意味着左下角绑定父级左下、右上角绑定父级右上；Size Delta 0 表示四边没有额外偏移，所以无论 16:9、16:10、超宽屏、2K、4K 或窗口缩放，遮罩都与 Canvas 同尺寸。早期 Prefab 使用中心 Anchor 加固定 `1920×1080`，在 Full HD Gate 中看不出问题，却可能在更大或不同比例 Game View 露出边缘。最终通过 Free Aspect 检查并修正为 Stretch，这个 Debug 案例说明 UI 响应式验证不能只在目标分辨率截图上完成。

### Image：黑色视觉与 Raycast Target

`Image.Color = RGBA(0,0,0,1)` 提供不透明黑幕；没有 Sprite 也能用 UGUI 默认白纹理乘黑色绘制。黑色比透明截图或复杂 Loading Illustration 更稳定，不需要额外美术资产，也能遮住新 Scene 初始化过程。`Raycast Target = true` 不是为了让 Image 能点击，而是让它成为覆盖全屏的 UI Hit Target：当 CanvasGroup 允许阻挡时，EventSystem 首先命中它，底层 Start/Restart 按钮不会收到第二次点击。

### CanvasGroup：一个组件同时管理可见性和输入所有权

最终 Authoring 参数为：

```text
Alpha = 1
Interactable = false
Blocks Raycasts = true
Ignore Parent Groups = false
```

Alpha 1 保证 Scene 第一帧先黑屏，避免在 `Start()` 执行 Fade In 前闪出一帧未初始化画面。`Interactable=false` 表示 FadeBlocker 本身不是交互控件；`Blocks Raycasts=true` 表示初始 Fade In 期间阻断下层 UI，Controller 在完全透明后才设为 false。`Ignore Parent Groups=false` 让它遵守正常 CanvasGroup 组合规则。选择 CanvasGroup 而不是每帧改 `Image.color.a`，是因为它同时管理整棵子树的 Alpha 和 Raycast；未来添加 Loading Icon/Text 时不需要逐组件调透明度。

### DemoSceneTransitionController 参数

`Fade Canvas Group` 必须引用子物体 FadeBlocker 的 CanvasGroup；漏配时 `Awake` 使用 `GameLog.Error` 报告并禁用组件，避免无引用继续产生 NullReference。`Fade Duration = 0.25s` 是功能 Demo 的折中：足以让玩家感知过渡，又不让两个小 Scene 显得拖沓；设置为 0 时代码走即时分支，便于测试或无动画平台。Controller 的 `_isTransitioning` 是幂等 Guard：第一次请求置 true 并启动 Coroutine，后续快速点击直接返回 false。它没有 `Update()`，只有进入 Scene 和切换 Scene 时创建低频 Coroutine；Coroutine 状态机与 `LoadSceneAsync` 会产生离散分配，但不属于 Gameplay 热路径，也不会造成逐帧 GC Alloc。

### 从零在 Unity Editor 复现这个 Prefab

如果不依赖现有资产，从零创建时应按以下顺序理解和操作，而不是机械地复制数值：

1. 在 Hierarchy 使用 `GameObject → UI → Canvas` 创建根对象并命名为 `PF_P7_SceneFade`。创建 Canvas 时 Unity 会自动附带 `RectTransform`、`Canvas`、`CanvasScaler` 和 `GraphicRaycaster`；保留这四个组件，并把 Canvas 改为 `Screen Space - Overlay`、Sort Order 改为 `1000`。独立 Canvas 的目的，是让 Fade 拥有跨所有普通 UI 的排序边界。
2. 在根对象下使用 `UI → Image` 创建 `FadeBlocker`。Unity 会自动添加 `RectTransform`、`CanvasRenderer` 和 `Image`。将 RectTransform Anchor Preset 设为横向、纵向都 Stretch，并确认 Anchor Min `(0,0)`、Anchor Max `(1,1)`、Anchored Position `(0,0)`、Size Delta `(0,0)`；这一步决定不同分辨率下不会露边。
3. 将 Image 的 Source Image 留空、Material 留空、Color 设为不透明黑色、Image Type 保持 `Simple`、Raycast Target 勾选。空 Sprite 的 UGUI Image 仍可通过默认白纹理乘以 Color 绘制纯色矩形；Raycast Target 则让它在过渡期间成为真正的全屏输入命中面。
4. 在 `FadeBlocker` 上添加 `CanvasGroup`，设为 Alpha `1`、Interactable Off、Blocks Raycasts On、Ignore Parent Groups Off。Alpha 1 保证 Scene 第一帧先黑；Interactable Off 表示遮罩不是 Button；Blocks Raycasts On 与 Image/GraphicRaycaster 一起阻断下层 UI。`CanvasRenderer` 是 Image 向 Canvas 提交顶点和材质的底层桥梁，由 Unity 自动维护，`Cull Transparent Mesh` 保持默认 On，不需要业务脚本直接访问。
5. 在根对象添加 `DemoSceneTransitionController`，把 `FadeBlocker` 的 CanvasGroup 拖入 `Fade Canvas Group`，将 Fade Duration 设为 `0.25`。这个序列化引用是 Controller 改 Alpha 和输入所有权的唯一目标；不能拖 Image、根 Canvas 或其他 Panel 代替。
6. 把根对象拖到 `Assets/_Project/Art/Prefabs/P7/UI/` 保存为 `PF_P7_SceneFade.prefab`，然后在 `P7_MainMenu` 与 `P7_DemoRun` 各放一个 Prefab Instance。两个实例必须从 Scene 加载时就保持 Active；旧 Scene 实例负责 Fade Out，新 Scene 实例负责 Fade In。

Authoring 中 Alpha 1、Blocks Raycasts true 与 `Awake()` 中再次赋值看似重复，实际上是有意的双层保护：Prefab 静态状态保证 Scene 激活到脚本执行之前不会先闪一帧；`Awake()` 的运行时重置保证即使上一轮在 Editor 中把 Prefab 停留在透明状态，或关闭 Domain Reload 后进入新 Play，Transition 仍从确定状态开始。Inspector 配置负责“第一帧资产状态”，代码负责“每次运行时不变量”，两者职责不同。

## 4. 为什么每个 Scene 各放一个实例，而不用 DontDestroyOnLoad

当前方案是“旧 Scene 的实例负责 Fade Out，新 Scene 的实例负责 Fade In”。Main Menu 和 DemoRun 都放置同一 `PF_P7_SceneFade` Prefab Instance，旧实例随旧 Scene 卸载，新实例的 Awake 在新 Scene 中重新建立 Alpha 1 和输入阻挡。这避免了 `DontDestroyOnLoad` 常见复杂度：重复 Singleton、第二个 Scene 又生成一份 Fade、跨 Scene Inspector 引用失效、回到 Main Menu 时销毁顺序、关闭 Domain Reload 后静态 Instance 残留。

代价是每个可切换 Scene 都必须放一份 Prefab；漏放时新 Scene 不会 Fade In。对 P7 两个小 Scene 来说，显式 Authoring Contract 更容易检查。未来若 Scene 数量很大、需要加载进度 UI、Addressables 或 Additive Bootstrap Scene，可以把 Transition 提升为常驻 App Service；但不能只因为“全局功能”就过早引入生命周期更隐蔽的 Singleton。

# Task 8（已完成）：Initial Water 与可被 Water 压制的 Persistent Fire Source

Task 8 的目的不是继续扩展 P6 Solver，而是把已经成立的 ElementWorld 技术能力交给 Level Designer 使用。P6 已经证明 Projectile 命中后可以通过 `ElementDepositOnImpact` 创建 Water/Fire Cell，但如果元素只能在玩家施法后出现，它更接近“法术附带的环境效果”，还不是关卡本身可以表达的战术语言。本 Task 因此新增两种职责明确的 Scene Adapter：`ElementWorldInitialDeposit` 在场景开始时向唯一 `IElementWriteSink` 提交一次 Request，用于预置稳定浅水；`ElementWorldPersistentFireSource` 则以低频 Pulse 持续提交普通 Fire Request，用于火盆、岩浆裂隙或魔法火源。Persistent 并不意味着 Fire Cell 获得“无敌”标记：普通 Fire Decay、Water/Fire 1:1 Reaction、Chunk Sleep/Wake、Status 与 Rendering 全部保持 P6 原样。玩家投入 Water 后仍能暂时压制火源，残留 Water 会抵消后续 Pulse；当 Water 被逐渐消耗，Fire 才自然重新出现。开发过程中先后定位了“一次性 Fire 在玩家到达前已经衰减”和“Radius 从 0.5 增大到 1 后三维覆盖体积扩大约 8 倍、Amount Density 过低”两个问题，最终四个区域的 Initial Water/Persistent Fire、暂停、复燃、普通 Fire 衰减和离开返回 Gate 均由开发者确认正常。Task 8 由此把 ElementWorld 从背景表现升级为可重复 Authoring、可测试、可调参的关卡 Gameplay 资源。

## 1. 两种 Authoring 生命周期与共同写入架构

两个新组件都位于 `Game.ElementField` Assembly 的 Runtime Adapter 层，因为它们需要认识 `ElementWriteRequest`、`ElementMaterialKind` 和 `ElementRuntimeRegistry`，但不需要 `Game.Run`、`Game.UI` 或 `Game.Rendering`。它们只描述“在什么世界坐标、以多大半径、写入多少元素”，不知道 Cell、Chunk、ParticleSystem 或 Water Mesh 如何实现：

```text
Level Designer 放置 Scene Marker
  ├─ ElementWorldInitialDeposit.Start（一次）
  └─ ElementWorldPersistentFireSource.Start/Coroutine（低频多次）
                ↓
       readonly struct ElementWriteRequest
                ↓
       ElementRuntimeRegistry.ActiveSink
                ↓
          IElementWriteSink.TryEnqueueWrite(in request)
                ↓
       ElementWorldRuntime Write Queue
                ↓
       固定 Simulation Tick
                ↓
  WriteProcessor → Reaction/Flow/Decay → Status/Rendering
```

这里继续坚持 P6 的时间线解耦：MonoBehaviour 的 `Start` 或 Coroutine 只负责把值类型 Command 入队，真正的 Cell 修改仍发生在 ElementWorld 固定 Tick。这样不会因为某一帧先执行 Source 还是 Renderer 就直接改写 Grid，也不会让关卡组件获得 Store 写权限。`ElementRuntimeRegistry` 继续保证当前 Scene 只有一个 Active Sink；Source 不使用 `FindObjectOfType`、不缓存另一套 Runtime，也不会在找不到 Sink 时偷偷创建第二个 ElementWorld。

`ElementWorldInitialDeposit` 是 One-shot 生命周期。`Start()` 在 `_depositOnStart` 开启时调用 `TryQueueDeposit()`；只有成功进入 Queue 后 `_hasSubmitted` 才变为 true，第二次调用直接拒绝。如果配置无效、Runtime 缺失或 Queue 拒绝，本次失败不会消耗 One-shot，修正场景后仍可重试。`ResetAndQueueDeposit()` 是显式关卡重置/Context Menu 入口，它先清除状态再提交一次，而不是让 `Update()` 不断写入。这个区别很重要：One-shot 表示“初始条件”，不是“持续来源”。

`ElementWorldPersistentFireSource` 是 Source 生命周期。它的 Request 永远固定为 `ElementMaterialKind.Fire`，因此 Inspector 不提供 Material 下拉框，避免把“持续 Water”误配成 Persistent Fire。`Start()` 立即 Pulse 一次，让第一轮 Simulation Tick 就能看到 Fire；之后 Coroutine 按 `_pulseInterval` 重复调用 `TryPulse()`。每个 Pulse 都是普通 Fire Request，所以它仍会 Decay、能被 Water 抵消，也会进入同一套 Fire Renderer。Persistent 的含义是“Source 持续补充”，不是“Cell 永远不变”。

## 2. Persistent Fire 的 Coroutine、Pause 和零热路径分配

持续功能最容易写成 `Update()` 中累计时间，但那会让每个 Source 每帧进入分支，并容易在错误实现中重复创建 YieldInstruction、闭包或临时集合。本实现没有 `Update()`，生命周期如下：

```text
Awake
  → Clamp Pulse Interval
  → new WaitForSeconds(interval)，只创建一次并缓存

Start
  → _hasStarted = true
  → 立即 TryPulse()
  → StartCoroutine(PulseRoutine())

PulseRoutine
  → yield return 同一个 _pulseWait
  → TryPulse()
  → 循环

OnDisable
  → StopCoroutine
  → 清空 Coroutine 引用

再次 OnEnable（已经执行过 Start）
  → 立即恢复一次 Pulse
  → 重新启动 Coroutine
```

首次 `OnEnable` 不直接 Pulse，是因为 Unity 只保证所有 `Awake` 先于所有 `Start`，却不保证不同 GameObject 的 `OnEnable` 顺序。如果 Source 在 `OnEnable` 立刻访问 Registry，而 `ElementWorldRuntime.OnEnable` 尚未注册，就会形成依赖 Script Execution Order 的偶发失败。因此首次启动统一放在 `Start`；此时 Runtime 已在 `Awake/OnEnable` 完成初始化和注册。`_hasStarted` 只用于区分首次 Enable 与运行时重新启用。

Coroutine 使用 `WaitForSeconds`，也就是 Scaled Time。Pause Menu、Wand Editor 或终局 Panel 把 `Time.timeScale` 设为 0 时，ElementWorldRuntime 本身停止 Tick，Fire Source 也同步停止等待和 Pulse；Resume 后两者一起恢复。这里不能使用 Task 7 Fade 所用的 `Time.unscaledDeltaTime`：Fade 属于暂停状态下仍必须完成的应用层过渡，而环境火源属于 Gameplay，暂停时继续燃烧和消耗 Water 会违反玩家预期。同样是“时间”，选择 Scaled/Unscaled 必须根据系统语义决定，不能机械复用。

`WaitForSeconds` 和 Coroutine Enumerator 会在初始化/启停这一离散边界产生少量分配，但循环中复用同一个 YieldInstruction；每次 `ElementWriteRequest` 是 `readonly struct` 局部值，并通过 `in` 参数传递。没有 LINQ、Boxing、数组创建或每帧字符串拼接。`GameLog` 诊断调用在 Release 由 Conditional Attribute 连同参数求值一起剔除；缺少 Sink 或 Queue 拒绝时 `_diagnosticIssued` 只允许输出一次，成功 Pulse 后才重新开放未来诊断，避免 Source 数量较多时 Console Spam。`MinimumPulseIntervalSeconds = 0.25f` 是防御边界，防止 Inspector 误填极小值挤满 `MaxPendingWrites`；正常关卡从 1～2 秒量级开始调试。

## 3. Water 为什么能压制“常驻”火焰，以及为什么不修改 P6 Cell

最初讨论过三种方案：修改 Fire Cell 增加 Permanent 标记、在 Initial Deposit 内增加 Persistent Mode、或者建立独立 Source。最终选择独立 Source，因为它最符合职责隔离，也保留已有元素规则。

如果给 Cell 增加 Permanent 标记，`ElementCell` 的紧凑协议、Fire Decay、Water Reaction、Chunk 生命周期、Rendering 和未来存档都要理解一个新状态；还必须回答 Water 命中 Permanent Fire 时是完全无效、暂时熄灭还是移除标记。这会为一个关卡 Authoring 需求污染 P6 Solver。把 One-shot/Persistent 都塞进 Initial Deposit 虽然少一个脚本，却让同一 MonoBehaviour 同时管理一次性状态、Coroutine、重启与两套 Inspector 语义。独立 `ElementWorldPersistentFireSource` 多一个小文件，但调用者从类型名就能理解生命周期，测试也可以分别固定。

当前 Water 压制不需要新的 `Suppressed` bool。既有写入与 Reaction 已经按 Amount 抵消相反元素：

```text
当前 Water Amount = 600
下一次 Fire Pulse = 512
  → Fire 先消耗 512 Water
  → Water 仍剩 88
  → 视觉上没有 Fire

再下一次 Fire Pulse = 512
  → 先消耗剩余 88 Water
  → 多出的 424 才形成 Fire
  → 火源自然重新点燃
```

因此“压制多久”不是写死的倒计时，而是玩家投入的 Water、Water 流动、Pulse Amount 和 Pulse Interval 共同产生的系统性结果。投入更多 Water 就压制更久；停止供水后 Source 逐步夺回区域。普通 Fireball 创建的 Fire 没有 Source 补充，仍会按照 `_fireDecayPerTick=1` 在 10Hz Tick 中自然消失。开发者已经验证持续火源、Water 暂时压制/复燃与普通 Fire 自然衰减同时成立，这证明 Task 8 没有把“所有 Fire 都永久化”。

## 4. Prefab、Scene Gizmo 与 Inspector 参数怎样配置

Task 8 最终使用两个正式 Prefab：

```text
Assets/_Project/Art/Prefabs/P7/ElementField/
├─ PF_P7_InitialWaterDeposit.prefab
└─ PF_P7_PersistentFireSource.prefab
```

它们都是不可见的 Gameplay Marker，只需要 Transform 和对应脚本，不需要 MeshRenderer、Collider、ParticleSystem 或材质。Water Mesh 与三层 Fire Particle 仍由现有 `ElementWorldWaterRenderer`、`ElementWorldFireRenderer` 读取 Gameplay 数据生成。把表现组件塞进每个 Source 会形成“一 Cell/一 Source 一个 ParticleSystem”的扩张模式，既破坏读写边界，也会造成 GameObject、Draw/Overdraw 与维护成本膨胀。

`PF_P7_InitialWaterDeposit` 的字段含义：

| 字段 | 作用 | 设计原因 |
|---|---|---|
| Material Kind | P7 使用 Water | 组件保留 Water/Fire 通用 Request 能力，但正式 P7 Prefab 只承担 Initial Water。|
| Total Amount | 整次写入总预算 | 不是每个 Cell 的 Amount；范围越大，单 Cell 平均越低。|
| Radius | World Space 球形半径 | 0 表示只写中心 Cell；必须避免完全埋进 Solid。|
| Use Linear Falloff | 中心权重大、边缘权重小 | 让浅水边界更自然，但会进一步降低外圈 Amount。|
| Deposit On Start | Scene Start 自动提交 | 关闭后只能由显式流程调用；不能依赖 Update。|

`PF_P7_PersistentFireSource` 的字段含义：

| 字段 | 作用 | 设计原因 |
|---|---|---|
| Pulse Amount | 每次 Fire Request 的总预算 | 与 Radius 共同决定单 Cell Density，也决定 Water 需要投入多少 Amount 才能压制。|
| Radius | 每次 Pulse 的 World Space 球形半径 | 不是单纯视觉尺寸；改变它会改变覆盖 Cell 数量。|
| Use Linear Falloff | 使用中心到边缘的线性权重 | 中心火焰更强，避免均匀硬边；调大 Radius 时必须重新检查 Density。|
| Pulse Interval | 两次 Request 的 Scaled-Time 间隔 | 越短越难压制且写入频率越高；最小防御值 0.25 秒。|
| Successful Pulse Count | Play Mode 已成功入队次数 | 证明 Source/Registry/Queue 边界成立，不等价于所有 Cell 最终都写入成功。|
| Rejected Pulse Count | 构造、Registry 或 Queue 边界失败次数 | 正常应为 0；持续增长时检查 Runtime、Queue 和配置。|

Scene 中统一放在 `__Level/InitialElementDeposits`（也可语义化改名为 `ElementSources`）下，而 `ElementWorldRoot` 仍位于 `__Systems`。前者是关卡内容，后者是唯一 Runtime/Simulation 所有者；Source 不应成为 ElementWorldRoot 的实现子节点。各区域最终使用的 Persistent Fire Scene Instance Radius 为 `0.5m`，位置和数量属于 Level Design；技术要求是 Marker 中心略高于地板表面，球形范围至少覆盖可写入的非 Solid Cell。

两个组件都实现 `OnDrawGizmosSelected()`：Initial Water/Fire 用蓝/橙 Wire Sphere，Persistent Fire 用橙色 Wire Sphere；`Handles.Label` 在 `#if UNITY_EDITOR` 内显示 Material/Amount/Radius 或 Pulse/Interval。`Gizmos` 和 `UnityEditor.Handles` 只服务 Scene Authoring，不进入 Player Gameplay。`OnValidate()` 改善 Inspector 输入体验，但运行时的 `TryBuildRequest/TryBuildPulseRequest` 仍再次校验，因为旧 Prefab、反射或运行时代码可能绕过 OnValidate。`[DisallowMultipleComponent]` 防止同一个 Marker 意外挂两份 Source；`[SerializeField]` 保持字段由 Scene/Prefab Authoring，而不是公开任意写入。

## 5. 两次关键 Debug：Decay 生命周期与 Radius³ Density

第一轮问题是“Water 能看到，Initial Fire 看不到”。最初 Fire 使用 One-shot `Amount=180 / Radius=0.75 / Linear Falloff`。Water 稳定后可以进入 Solver-Sleeping，数据仍 Resident、Renderer 仍可见；Fire 却必须在每个 10Hz Tick 执行 `Amount-1`。180 是整个球形 Deposit 的总预算，分配到大量 Cell 后大部分只有 1～5 Amount，在 0.1～0.5 秒内就归零。Fire Renderer 的 Body 发射阈值还是 `BodyProbability × Amount/255`，低 Amount 同时意味着极低粒子概率，所以 Fire 甚至可能没形成明显视觉就消失。更重要的是，即使把单 Cell 填到最大 255，也只能在 `255 / 10Hz = 25.5s` 后耗尽，无法保证玩家几分钟后到达后续区域仍看到“地图常驻火焰”。根因不是 Renderer 缺失，而是用 One-shot 数据描述了 Persistent 生命周期。修复是独立低频 Source，而不是调低全局 Decay。

第二轮问题是“出生区域常驻 Fire 正常，其他区域仍看不到或很快消失”。Inspector 显示远区 Source 的 `Successful Pulse Count=70`、`Rejected=0`，证明 Coroutine、Registry 和 Queue 都正常，故障发生在 Request 入队之后。静态检查发现出生区域实例 Radius 为 0.5，而多个远区实例 Override 为 1，Pulse Amount 都是 512。球形覆盖体积满足：

```text
V = 4/3 × π × r³

V(r=1) / V(r=0.5)
  = 1³ / 0.5³
  = 8
```

Radius 翻倍会覆盖约 8 倍体积，而不是 2 倍；在 CellSize 固定为 0.25m 时，近似意味着覆盖 Cell 数量也按立方增长。Amount 不变时单 Cell Density 约降到八分之一，于是每 Cell 更快被 `FireDecayPerTick` 清空，Renderer 的 `Amount/255` 发射概率也同步下降。将相关 Scene Instance Radius 统一恢复为 0.5 后，持续燃烧恢复正常。另一种等密度思路是把 Amount 近似放大 8 倍，但那会同时改变 Water 压制成本与写入规模；本 Demo 选择缩小范围。这个案例说明在 3D Grid 系统中，Radius 是 Gameplay 数据参数，不只是 Gizmo 或视觉尺寸；调参必须考虑平方/立方增长关系。

还有一个容易误判的边界：`ElementWorldFireRenderer` 只读取 Wizard Interest 范围内的可见 Chunk，远区不持续发粒子是 Presentation Budget，不等于 Source 停止。靠近后 Renderer 才重新读取相应 Chunk；Source 的 Successful Pulse、Runtime 的 Processed/Rejected Writes 和 Renderer 的 Active Fire Cell Count 分别属于不同边界，排错时必须逐层观察，不能看到“无粒子”就直接归因于写入失败。

## 2. 最后一项测试债务：为什么 Runtime 正确但 Fixture 仍会失败

`Game.Run.Tests.SpellRewardEncounterBindingTests.BindChildRewards_OverridesCopiedSerializedEncounterIndex_IncludingInactivePickup`

异常不是 Reward Runtime 逻辑断言失败，而是测试辅助方法在后续反射写字段时遇到 `NullReferenceException`。沿创建路径向前检查后发现，Fixture 直接调用：

```csharp
rewardObject.AddComponent<SpellRewardPickup>();
```

但 `SpellRewardPickup` 声明了 `[RequireComponent(typeof(Collider))]`，而测试临时 GameObject 没有 Collider。`RequireComponent` 的本意是表达 Authoring Contract：真实 Reward Pickup 必须有 Collider 才能通过 Trigger 被玩家拾取。Unity Editor 正常用 Add Component 创建时通常会补齐依赖；测试环境中这次创建被拒绝并返回空引用，后续错误看起来才像 Reflection 失败。

修复只修改 `Assets/_Project/Tests/Run/SpellRewardEncounterBindingTests.cs`：先给测试 GameObject 添加 `BoxCollider`，并设为 `isTrigger = true`，再添加 `SpellRewardPickup`。这不是为“让断言变绿”而降低 Production 约束，恰恰相反，是让 Fixture 和真实 Prefab 遵守同一组件合同。修复后重新执行完整 EditMode 得到 351/351，而不是只重跑这一项；Production 中的 `DemoEncounterController`、`SpellRewardPickup` 和 Reward Prefab 都没有因测试债务而修改。

这个案例适合初学者记住一个 Debug 顺序：不要把堆栈最后一行当作根因。`SetPrivateField` 报空引用，只说明传入对象为空；继续向上问“对象为什么没创建出来”，再检查 Component Attribute 和 Console 中更早的 Unity 错误，才能找到真正前置条件。

## 4. 性能验收如何区分“持续热路径”和“离散成本”

性能验收首先要区分发生频率。`Update`、`FixedUpdate`、固定 10Hz ElementWorld Tick 和每帧 Rendering 是 Hot Path；Scene Load、点击按钮、Reward Pickup、一次 Projectile Instantiate 和通知 Coroutine 启动是 Discrete Event。项目规则要求 Hot Path 不制造 `new`、LINQ、Boxing 或 `GC Alloc`，但不禁止所有运行时分配，否则连加载 Scene 或生成 Projectile 都无法完成。

Task 9 对 P7 新增链路做了静态审计：

- `ElementWorldInitialDeposit` 没有 `Update`，只在 Start 或显式 Reset 后提交一次值类型 `ElementWriteRequest`。
- `ElementWorldPersistentFireSource` 没有逐帧写入；它使用低频 Scaled-Time Coroutine，`WaitForSeconds` 在初始化/参数变化时创建并复用，不在每个 Pulse 中 `new YieldInstruction`。
- `RunPauseCoordinator` 在界面开关时更新 Pause Reason，不用每帧搜索当前 Panel。
- `DemoSceneTransitionController` 的 Coroutine、`LoadSceneAsync` 与 Scene Object 创建只发生在场景切换事务中。
- HUD Notification 的 `WaitForSecondsRealtime` 是通知触发时的离散分配，不是 Update 中持续分配；通知频率由 Encounter/Reward Event 限制。
- ElementWorld 核心继续保留 `ElementWorld.ApplyWrites`、`ElementWorld.Simulate`、`ElementWorld.RebuildActivity`、`ElementWorld.BakeChunkSolid` 与 `ElementWorld.Exposure` 等 `ProfilerMarker`，便于把 Queue、Solver、Rebuild 和 Exposure 分开观察。

Task 8 的完整连续实玩确认四区 Persistent Fire、Water 压制/复燃、离开返回与普通 Fire Decay 均正常，没有重新观察到 P6 的 Solver Stall。这里必须诚实区分“验证过的结论”和“没有新采集的素材”：本次快速 Task 9 没有重新制作一套长局 Profiler 数值截图或 Frame Debugger 截图，因此不能写成“Task 9 新测得每个 Marker 为某个毫秒数”。P6 已保存 Solver 优化过程，P7 保存 Marker、热路径代码边界、Runtime Count 与连续实玩结果；后续录制作品集时可以在 Development Build 中重新截取目标机器的 CPU/GPU/GC 样本。这样既完成技术收口，也避免用肉眼流畅伪造数值证据。

Frame Debugger 的检查重点也不是“Draw Call 越少越好”，而是确认批次与透明层级符合设计：Water 按 Active Chunk 生成 Mesh；Fire 使用共享 Body/Core/Sparks Particle Renderer，而不是每个 Cell Instantiate ParticleSystem；普通 Gameplay UI 共享 `UICanvas`，Scene Fade 使用 Sorting Order 1000 的独立 Overlay Canvas；Inactive Panel 不参与 Raycast，FadeBlocker 只在 Transition 时通过 `CanvasGroup.blocksRaycasts` 阻挡输入。独立 Fade Canvas 多一次 Canvas 管理成本，但换来可靠的最高层遮罩和跨 Scene 相同配置，这是为正确性接受的小额开销。

## 6. 作品集素材、简历表达与 trade-off

P7 已具备录制作品 Demo 的技术链。推荐 60～90 秒视频按“问题—机制—结果”组织，而不是只录角色清怪：

```text
Main Menu + Fade
→ 打开 Wand Editor 展示 Spell Program
→ Projectile 写入 Water/Fire ElementWorld
→ 清场、Gate 打开、拾取 Reward
→ Runtime Wand 因奖励发生变化
→ Persistent Fire 被 Water 压制并复燃
→ Final Elite
→ Victory / Return
```

Profiler/Frame Debugger 截图应单独表现 P6 已发生过的真实优化：先给出 `ElementWorld.Simulate` Stall 的样本，再解释 Resident 不等于 RequiresSimulation、稳定 Chunk 进入 Solver-Sleeping、Write/Boundary Effect 才 Wake，最后给出优化后的 Marker 与 `GC Alloc`。不要只放一张“当前很快”的图，因为面试官更关心你如何定位根因、怎样证明修复没有破坏语义，以及优化的边界是什么。

简历可以把 P7 整体写成：

> 基于 Unity 6 / URP 构建 Wizard 单职业连续关卡 Demo：设计独立 Game.Run 状态层，用纯 Tracker、EventBus 与 Scene Adapter 驱动四区 Encounter、Gate、Reward、Victory/Defeat；通过 Runtime ScriptableObject Clone 隔离本局 Spell Inventory 与 Authoring Asset；统一 Pause Reason，完成 Main Menu、持久化 Settings、Unscaled-Time Scene Fade 和异步加载；将 Sparse ElementWorld 接入 Initial Water/Persistent Fire 关卡资源，并通过 351 项 EditMode、12 项 PlayMode 与 Windows Development Build 完成回归验收。

主要 trade-off 是第一版采用手工 S 形路线和确定性 Reward，不做 Seeded Random。这样牺牲了 Roguelite 的内容变化，却得到一条可重复 Debug、可测试、可录制的 Vertical Slice。最终 Elite 使用数据变体而非新 Boss FSM，表现层次有限，但证明 EnemyDefinition、Combat Funnel 与 Run Flow 能组合复用。Settings 用 `PlayerPrefs` 和 `AudioListener.volume`，适合 MVP，却不替代未来 `AudioMixer`、Save Schema 与 Migration。Scene Fade 每个 Scene 放一个实例，避免 `DontDestroyOnLoad` 生命周期复杂度，代价是每个新 Scene 都必须遵守显式 Authoring Contract。

## 7. 模拟面试回答：如何从头讲清楚 P7

如果面试官问“你怎样把分散的法术、战斗和元素系统做成一局完整 Demo”，可以这样回答：

> 我先把完整单局拆成三层真相。最底层 Combat、Skills、ElementField 继续负责伤害、法术解释和元素模拟，不知道当前是第几关；中间新增 Game.Run，用纯 EncounterProgressTracker/RunProgressTracker 表达顺序、成员去重和 Terminal State，再由 MonoBehaviour Scene Adapter 订阅 DeathEvent、控制 Enemy 与 Gate；最上层 Game.UI 只订阅 Run Event 显示 HUD、Pause 和结算，不自己推断胜负。这样清场规则能做 EditMode Test，Scene 只负责装配。
>
> 奖励系统没有直接修改 SpellLibrary 或 WandLoadout Asset。我把 ScriptableObject 定义为 Authoring Template，进入一局时由 RunSpellSession 创建 Runtime 数据；Reward Pickup 只向 Session 去重添加 Spell，SpellCaster 和 Wand Editor 都读同一个 Runtime Source。我们还定位过一个典型 Inspector Bug：UI 显示 Runtime Wand 为空，但 SpellCaster 因 Run Spell Session 引用没接上而回退旧 WandLoadout，角色仍会发默认火球。症状同时包含“UI 空”和“仍能攻击”，因此根因不是 CastEvaluator，而是两个消费者没有连接到同一数据源。
>
> UI 生命周期中最关键的是 Pause 所有权。我没有让 Wand Editor、Pause Menu 和 Victory 各自写 Time.timeScale，而是让 RunPauseCoordinator 持有多个 Pause Reason；只有最后一个 Reason 释放才恢复。Scene Transition 使用独立 Sorting Order 1000 Canvas、黑色全屏 Image、CanvasGroup 和 Unscaled Time Coroutine：先 Fade Out 并阻挡输入，再恢复 Time/Cursor、保存 Settings、LoadSceneAsync；新 Scene 自己从黑色 Fade In。Unscaled Time 是因为 Pause 时 scaled deltaTime 为 0，否则 Return/Restart 会永远停在黑屏前。
>
> ElementWorld 方面，我没有修改 P6 Solver 来做“永久火”。Persistent Fire Source 只按低频 Pulse 提交普通 Fire Request，Water/Fire Reaction、Decay、Chunk Sleep/Wake 和 Renderer 保持原样，所以 Water 能暂时压制，Source 后续又会自然复燃。一次 Debug 中，远区 Source 的 Successful Pulse 持续增长但画面没火，最终发现 Radius 从 0.5 变 1 后三维覆盖体积约放大 8 倍，固定 Amount 被摊薄，Cell 更快衰减且粒子采样概率更低。这个定位沿 Source、Queue、Simulation、Rendering 分层，而不是看到没粒子就改 Coroutine。
>
> 最终我用四层证据验收：Solution Build 检查依赖，EditMode 351/351 验证规则，PlayMode 12/12 验证 Unity 生命周期，Windows Development Build 验证 Main Menu、Settings 和真实 Quit。最后一个失败测试不是 Runtime Bug，而是 Fixture 漏建 RequireComponent 的 Collider；我只修 Fixture 并重新 Run All。这个项目让我能说明的不只是“做了哪些功能”，而是状态归属、跨模块依赖、运行时数据隔离、暂停/场景事务、性能 Marker，以及如何用证据关闭一个阶段。

Task 9 至此正式收口，P7 第一版完整结束。此后的随机地图、更多职业、复杂 Boss、扩展元素或正式作品集录制，都必须作为新的阶段重新确认目标与计划，不能继续在 P7 中无边界追加。
