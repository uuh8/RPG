## 一、怎么使用这份 Q&A

大型游戏客户端面试对校招生的要求，通常不是“做出了一个看起来很炫的效果”就够了。面试官更在意四件事：

1. 你是否能用清楚的架构语言概括自己的工作，而不是只描述画面；
2. 你是否理解节点背后的向量、公式、Coordinate Space 和渲染阶段；
3. 你是否理解 Unity API 的隐含行为、性能代价和生命周期；
4. 你是否知道当前方案的边界，能否提出基于数据的升级路线。

本文每个回答尽量遵循以下结构：

```text
是什么：先给定义或结论。
为什么：解释需求、原理和取舍。
怎么做：落回 P1 中的公式、脚本或 Unity API。
边界：主动说明当前方案不解决什么，以及如何验证。
```

练习时不要逐字背诵。推荐先遮住回答，自己口述 60~90 秒，再对照补全。面试官继续追问时，要从项目实现下沉到基础原理，而不是重复第一遍答案。

## 二、项目开场与总体设计

### Q1：请你用一分钟介绍 P1 状态可视化系统

**面试者回答：**

**是什么：**我实现了一套由 Gameplay 状态强度实时驱动的角色表面状态可视化，目前完成了 `Burning` 和 `Wet`。它不是两个孤立的 Material，而是 `Gameplay → EventBus → Rendering Bridge → MaterialPropertyBlock → URP Lit Shader` 的完整链路。

**为什么：**角色状态具有 0~100 的连续强度，而且玩家和敌人会共享 Material。我要同时解决状态平滑变化、多角色参数隔离、原 PBR 外观保留以及 Burning/Wet 共存问题。

**怎么做：**`StatusController` 负责状态叠加、衰减、DoT 和 Wet 灭火，并发布带 `TargetId` 的 `StatusChangedEvent`。`StatusMaterialController` 将强度归一化到 0~1并用 `MoveTowards` 平滑，再通过 `MaterialPropertyBlock` 给每个 Renderer 写独立参数。统一的 `SG_CharacterStatusLit` 保留 Base Map、Normal、Metallic/Smoothness、AO 和 Emission，Burning 使用 Object Space 流动 Noise、Threshold、`Smoothstep` 与 HDR Emission；Wet 使用 Smoothness 提升、Fresnel Edge 和轻微 Tint。

**边界：**当前完成的是风格化战斗状态，不是火焰流体或真实水膜模拟；Poisoned/Sticky 只打通了参数通道，尚未完成视觉效果。性能结论需要结合 Frame Debugger 和 Profiler，而不能仅凭用了 MPB 就声称一定更快。

---

### Q2：这个功能中你认为最难的三个问题是什么？

**面试者回答：**

第一是**共享 Material 与独立状态的矛盾**。修改 Shared Material 会让所有角色一起变化，而 `renderer.material` 会创建 Material Instance。我最终使用 `MaterialPropertyBlock`，并通过自动化测试证明同一 Shared Material 的两个 Renderer 可以分别持有 1.0 和 0.25 的 Burning。

第二是**如何把抽象状态变成有材质依据的视觉信号**。Burning 不能只是染红，所以我用流动 Noise 产生局部 Mask，并同时驱动焦灼颜色和 Emission；Wet 不能只是染蓝，所以主要改变 Smoothness，并用 **`N·V` 构造 Fresnel 水膜。**

第三是**如何让多个系统在同一个 Renderer 上共存**。状态表现与受击闪红都使用 MPB。如果直接 Set 一个空 Block，就会清掉其他系统的字段。我采用 `GetPropertyBlock → 只修改自己字段 → SetPropertyBlock` 的协议，并写测试验证 `_BaseColor` 不被 Wet 写入覆盖。

这三个问题分别对应资产共享、图形学表达和引擎状态管理，说明这个功能不只是 Shader 节点连接。

---

### Q3：为什么把 Gameplay、Rendering Bridge 和 Shader 分成三层？

**面试者回答：**

**是什么：**三层分别拥有状态语义、CPU 到 GPU 的数据提交、GPU 表面计算。

**为什么：**如果 Shader 自己推断燃烧强度，或 Rendering 反向修改 Gameplay，就会出现两套状态真相。更换 Shader 可能改变伤害和衰减，架构不可维护。CPU 和 GPU 的执行模型也不同，Shader 不能直接调用 `MonoBehaviour`。

**怎么做：**Combat 中的 `StatusController` 是 0~100 的权威数据源；Rendering 中的 `StatusMaterialController` 只读订阅事件、归一化、平滑和写 MPB；Shader 只接收 0~1 参数并绘制。依赖方向是 `Rendering → Combat → Core`，Combat 不引用 Rendering。

**边界：**这种事件驱动拆分提高了解耦，但也增加了链路定位成本，因此我保留了清晰的属性 Reference、只读诊断属性和自动化测试。

---

### Q4：为什么状态强度在 Gameplay 中使用 0~100，而 Shader 使用 0~1？

**面试者回答：**

0~100 对策划和 UI 百分比更直观；Shader 中的 `Lerp`、Mask、`Saturate` 和颜色混合通常使用归一化 0~1。二者服务不同层，不必强行统一表示。

我在表现桥中使用：

```text
I_shader = clamp(I_gameplay × 0.01, 0, 1)
```

对应 Unity API 是 `Mathf.Clamp01(statusIntensity * 0.01f)`。Clamp 还能防止错误数据，例如 150 被限制为 1，避免 Emission 或插值越界。

关键是转换只发生在边界，Gameplay 内部仍保持统一单位，Shader 内部也始终使用 0~1，避免单位在各处混用。

---

### Q5：为什么视觉变化需要额外平滑？状态数值本身不是已经会衰减吗？

**面试者回答：**

**Gameplay 衰减**与**视觉响应**解决的是两个问题。状态可能在命中瞬间从 0 增加到 45，这个离散事件如果直接写 Shader，会在一帧内切换画面；之后自然衰减虽然连续，但初始附着仍然突兀。

我使用：

```text
current = MoveTowards(current, target, responseSpeed × deltaTime)
```

`Mathf.MoveTowards` 每帧最多移动 `maxDelta` 且不会越过目标。默认速度 4 表示 0 到 1 最快约 0.25 秒。乘 `Time.deltaTime` 后，过渡时长与帧率基本无关。

视觉平滑不会回写 Gameplay，因此不会延迟伤害、灭火和 UI 百分比。它只是 Presentation 的时间滤波。对象重新 Enable 时则直接同步当前值，不从 0 播放一次错误过渡。

## 三、渲染管线与 Shader 基础

### Q6：从 CPU 到屏幕，一个状态参数大致经历了什么？

**面试者回答：**

CPU 上，`StatusMaterialController` 把状态值写入 Renderer 的 `MaterialPropertyBlock`。Unity 在组织 Draw Call 时，把 Mesh、Material、对象变换和属性覆盖提交给渲染管线。

GPU 上，Vertex Shader 先处理 Mesh 顶点，将 Object Space Position 变换到 Clip Space，并输出 UV、Normal 等插值数据；Rasterization 把三角形覆盖区域离散成 Fragment；Fragment Shader 对每个 Fragment 采样贴图、计算 Burning/Wet Mask 和材质参数；URP Lit 再结合光照、阴影和环境信息得到颜色。最后 Camera 输出经过 Bloom 等 Post-processing，写入屏幕。

所以 `_BurningIntensity` 不是“直接控制角色变红”的魔法变量，它只是 GPU 程序的一项输入。最终画面还依赖 Mesh、UV、材质贴图、光照、Camera 和后处理。

---

### Q7：Vertex Shader 和 Fragment Shader 分别做什么？P1 的主要计算在哪一阶段？

**面试者回答：**

Vertex Shader 以顶点为粒度，主要负责坐标变换并准备传给后续阶段的数据；Fragment Shader 以光栅化后的 Fragment 为粒度，负责贴图采样、材质参数和光照相关输出。

P1 的 Burning Noise、Threshold、Wet Fresnel 和颜色组合主要属于 Fragment 阶段，因为我希望效果在角色表面拥有像素级变化。如果把 Noise 只在 Vertex 阶段计算后插值，低面数 Mesh 上会丢失细节；但 Fragment 数远多于 Vertex，成本也更高。

未来如果性能成为瓶颈，可以把变化缓慢、线性的部分前移到 Vertex 阶段，但 Noise、`Smoothstep` 与视角相关 Fresnel 是否适合前移需要验证插值误差。

---

### Q8：什么是 Rasterization？它和你的 Shader 有什么关系？

**面试者回答：**

Rasterization 是把经过投影和裁剪的三角形转换成屏幕上被覆盖 Fragment 的过程。它会根据重心坐标插值顶点输出，例如 UV、World Position、Normal。

P1 中 Fragment Shader 使用的 UV、Position 和 View Direction 都依赖这一步产生的每 Fragment 数据。需要注意透视投影下普通线性插值会变形，所以 GPU 对 UV 等属性进行 Perspective-correct Interpolation。

P1 没有修改 Rasterization 本身，但理解它能解释为什么 Shader Graph 的 Position Node 在表面上看起来是连续的，也能解释为什么 Fragment 计算量与屏幕覆盖像素和 Overdraw 相关，而不只与 Mesh 顶点数相关。

---

### Q9：为什么选择 URP Lit，而不是 Unlit？

**面试者回答：**

`Unlit` 主要直接输出颜色，不自动表现 Directional Light、阴影、Normal Map、Metallic、Smoothness 等材质响应。它适合 UI、特定特效或不受光照影响的风格。

角色原外观使用 PBR 数据，Wet 的主要信号又依赖 Smoothness 与视角高光，因此必须建立在 Lit 上。如果用 Unlit，我就要自己重写大量光照和阴影逻辑，且很难保持角色原材质质感。

我创建 URP Lit Shader Graph，先重建 Base Map、Normal、Packed Metallic/Smoothness、AO 和 Emission，再加入状态。它让 URP 继续负责 Forward Lit、ShadowCaster、Depth 等 Pass，而我专注于修改 Surface 输入。

---

### Q10：什么是 PBR？你这个项目中具体使用了哪些 PBR 参数？

**面试者回答：**

PBR，即 `Physically Based Rendering`，不是单一算法，而是一组基于物理直觉组织材质和光照的工作流。核心目标是让材质参数在不同光照环境下仍然保持相对稳定和可解释。

本项目采用 Metallic Workflow：

- Base Color：非金属的漫反射颜色，金属的反射颜色来源；
- Metallic：区分导体与非导体行为；
- Smoothness：控制微表面分布和高光锐利程度；
- Normal：改变微表面朝向；
- Ambient Occlusion：减弱缝隙区域的间接光；
- Emission：表面主动发出的辐射亮度。

我没有手写完整 BRDF，而是把这些 Surface 参数交给 URP Lit。Burning 修改 Base Color 和 Emission，Wet 修改 Smoothness并增加风格化 Fresnel 提示。

严格来说，我的 Wet Edge 加到 Base Color 不完全满足能量守恒，因此它是 PBR 基线上的风格化增强，不是完整物理水层。

---

### Q11：Smoothness 和 Roughness 是什么关系？为什么潮湿会提高 Smoothness？

**面试者回答：**

Smoothness 描述微表面法线分布的集中程度，Roughness 描述粗糙程度，二者在很多工作流中近似互补：

```text
Roughness ≈ 1 - Smoothness
```

粗糙表面拥有更分散的微表面朝向，高光更宽、更弱；光滑表面的微表面朝向更集中，高光更锐利。水膜会填平部分微观凹凸，所以潮湿常表现为 Smoothness 上升。

我的实现不是直接设为 Wet 值，而是：

```text
target = max(baseSmoothness, wetSmoothness)
final  = lerp(baseSmoothness, target, WetIntensity)
```

`max` 保证 Wet 只提高光滑度，不把原本 Smoothness=0.98 的金属降低到目标 0.92。`Lerp` 保留 0~1 连续过程。

---

### Q12：Metallic/Smoothness 为什么能放在一张贴图里？

**面试者回答：**

Texture 的 RGBA 有四个 Channel，可以存放四组标量数据。与颜色贴图不同，Metallic、Smoothness、AO 都通常是单通道值，因此可以进行 `Texture Packing`，减少 Texture Sample 与资源数量。

当前角色资源中，Metallic/Smoothness Packed Map 主要使用：

```text
Metallic   = texture.r
Smoothness = texture.a × materialSmoothness
```

Shader Graph 用 `Sample Texture 2D` 后通过 `Split` 读取对应 Channel。

但 Channel 约定不是全行业固定标准，必须查看原 Shader/Material 或资源文档。把 Smoothness 错读成 G Channel 会让材质整体异常，因此迁移 Shader 时不能只看贴图缩略图猜测。

---

### Q13：Normal Map 为什么通常是蓝紫色？

**面试者回答：**

Normal Map 不是颜色纹理，而是在 Texture RGB 中编码方向。Tangent Space Normal 的默认方向大致是 `(0,0,1)`。为了存进 0~1 Texture Channel，通常把 `[-1,1]` 映射到 `[0,1]`：

```text
encoded = normal × 0.5 + 0.5
```

默认法线 `(0,0,1)` 编码后约为 `(0.5,0.5,1)`，所以视觉上呈蓝紫色。

Shader 采样后会解码，再通过 TBN 基底把 Tangent Space 法线变换到光照使用的空间。Unity 导入设置标记为 Normal Map 后，还可能根据平台使用特定压缩和解码方式。

它影响 `N·L`、`N·V` 等光照方向关系，不应该接到 Base Color。P1 的 Wet Fresnel 第一版使用稳定的几何 World Normal，而不是细碎 Normal Map 扰动后的法线，避免水膜边缘过于破碎。

---

### Q14：什么是 Texture Atlas？为什么共享材质后敌人没有变成玩家外观？

**面试者回答：**

Texture Atlas 是把多个部件或外观区域放进一张大贴图。Material 只引用整张 Atlas，Mesh 顶点中的 UV 决定三角形采样其中哪一块。

采样可以简化为：

```text
color = Texture(BaseMap, uv)
```

玩家与敌人的 Mesh 和 UV 不同，所以即使共享 `Costumes` Material，也会读取 Atlas 中不同区域。最终外观是 Mesh、UV、Texture、Shader 与参数共同作用，不是 Material 单独决定。

这套资源通过四类 Atlas Material 组织 BodyParts、Costumes、HeadParts 和 Weapons。状态强度由 MPB 独立覆盖，所以“基础外观差异”与“状态参数独立”可以同时成立。

---

### Q15：为什么 Base Map 一般使用 sRGB，而 Normal/Mask Map 不应该使用 sRGB？

**面试者回答：**

Base Color 是给人眼观察的颜色数据，通常以 sRGB 编码保存。渲染时需要转换到 Linear Space 后进行光照和颜色运算，因为加法、乘法和插值在 Linear Space 中才具有正确的能量意义。

Normal、Metallic、Smoothness、AO 是数值数据，不是显示颜色。如果错误启用 sRGB，GPU 采样时会做 Gamma 解码，数值被非线性改变，例如 0.5 不再代表原始 0.5，方向和材质参数都会错误。

在 Unity 中，Base Color Texture 通常保留 `sRGB (Color Texture)`；Normal Map 使用 Texture Type=Normal map；Mask/Packed Map 通常关闭 sRGB。P1 的具体第三方资源导入需保持原资源约定，不能仅凭文件名批量修改。

## 四、3D 数学与 Coordinate Space

### Q16：Object Space、World Space、View Space、Clip Space 分别是什么？

**面试者回答：**

`Object Space` 是以当前模型自身为基准的坐标；`World Space` 是场景统一坐标；`View Space` 是以 Camera 为原点和朝向的坐标；`Clip Space` 是经过投影矩阵后的齐次坐标，GPU 在透视除法和裁剪后得到 NDC 与屏幕位置。

典型位置变换是：

```text
p_world = M_model × p_object
p_view  = M_view × p_world
p_clip  = M_projection × p_view
```

P1 中 Burning Noise 选择 Object Position，因为图案要附着角色移动；Wet Fresnel 的 Normal 与 View Direction 选择 World Space，因为二者要在统一基底中做点积。

Coordinate Space 的选择不是节点偏好，而是视觉语义：图案应该跟随物体还是固定世界，方向比较要在哪个基底中进行。

---

### Q17：为什么两个向量做点积前必须在同一 Coordinate Space？

**面试者回答：**

向量的 XYZ 分量是相对于一组坐标轴的系数。Object Space 与 World Space 的坐标轴方向可能不同，同样的 `(0,1,0)` 在不同基底下不一定代表同一个世界方向。

点积公式是：

```text
a·b = axbx + ayby + azbz = |a||b|cos(theta)
```

只有两者使用同一组正交基底时，结果才能解释为夹角关系。P1 中 Normal 和 View Direction 都设为 World Space并 Normalize，`N·V` 才代表表面法线与视线夹角。

如果混用空间，节点仍能输出一个 Float，不会自动报错，但这个值没有我们想要的几何意义。这是 Shader 中很危险的一类“数值合法、语义错误”问题。

---

### Q18：为什么要 Normalize？如果不做会怎样？

**面试者回答：**

向量归一化是：

```text
normalize(v) = v / |v|
|v| = sqrt(vx² + vy² + vz²)
```

点积完整公式是 `a·b=|a||b|cos(theta)`。只有单位向量长度都为 1 时，点积才直接等于 `cos(theta)`。

如果不 Normalize，插值、变换或输入误差产生的向量长度会混入 Fresnel。相同观察角度可能因为长度不同得到不同边缘亮度。

Shader Graph 的某些 Direction Node 可能已经输出单位向量，但我在 HLSL Custom Function 中仍显式 Normalize，使函数输入契约更健壮、更适合独立复用。代价是增加归一化运算，因此在明确上游保证单位长度后可评估是否省略，但不能盲目删除。

---

### Q19：Fresnel 为什么使用 `1 - N·V`？

**面试者回答：**

单位法线 N 与单位视线 V 点积为夹角余弦。表面正对 Camera 时 `N·V≈1`；接近模型轮廓时二者接近垂直，`N·V≈0`。

所以：

```text
1 - saturate(N·V)
```

会把正面变为接近 0、轮廓变为接近 1。再计算：

```text
F = pow(1 - saturate(N·V), power)
```

Power 越大，中间灰度下降越快，边缘越窄。这个 Mask 乘 WetIntensity、EdgeStrength 与 EdgeColor，得到随 Camera 变化的水膜提示。

`Saturate` 等价于 Clamp 到 0~1，用来处理背面或浮点误差。当前公式是风格化近似，不包含真实 Fresnel 的 F0 和介质折射率。

---

### Q20：真实 Fresnel 和你的实现有什么区别？

**面试者回答：**

实时 PBR 常用 Schlick Approximation：

```text
F(theta) = F0 + (1-F0)(1-cos(theta))^5
```

`F0` 是正视角基础反射率。空气到水可由折射率近似计算：

```text
F0 = ((n1-n2)/(n1+n2))²
```

取空气 `n1≈1`、水 `n2≈1.33`，得到 `F0≈0.02`。因此真实水正面也有约 2% 基础反射，掠射角反射增强。

我的 `pow(1-N·V,power)` 只生成一个可调边缘 Mask，没有双层介质、折射、F0 和完整能量守恒。选择它是因为状态效果主要服务战斗可读性，并希望通过一个参数调边缘宽度。

如果升级，我会优先研究 Clear Coat 或在 Specular 路径中应用 Schlick，而不是简单继续把 Edge Color加到 Base Color。

---

### Q21：Normal 在非均匀缩放下为什么不能直接乘 Model Matrix？

**面试者回答：**

Position 表示点，方向变换通常可以使用模型矩阵的线性部分；Normal 必须始终与变换后的切平面保持垂直。非均匀缩放会破坏直接变换后的垂直关系。

正确的 Normal 变换使用模型矩阵线性部分的 `Inverse Transpose`：

```text
N_world = normalize((M_model^-1)^T × N_object)
```

Unity/Shader Graph 的 Normal Vector Node 会通过管线提供的正确变换处理这些细节，所以 P1 没有手写矩阵。但我需要知道它背后的原因，否则以后自己写 HLSL Transform 时容易出现光照随缩放错误。

如果模型只有旋转和统一缩放，普通方向矩阵与 Inverse Transpose 的方向结果可能一致；不能因此把这个特殊情况当通用规则。

---

### Q22：为什么 Burning 使用 Object Space，而 Fresnel 使用 World Space？

**面试者回答：**

两者表达的语义不同。

Burning Noise 表达“附着在角色表面的图案”。使用 Object Position 后，角色在 World 中移动时局部坐标不变，图案跟随角色。如果用 World Position，角色会穿过固定在世界里的 Noise。

Fresnel 表达“表面朝向与 Camera 观察方向的关系”。Camera 和角色都在世界中，因此把 Normal 和 View Direction统一到 World Space 更直观。

这也说明 Coordinate Space 没有固定的“最好选择”，要从效果是否跟随对象、世界或镜头来决定。

Object Space 的已知问题是模块化角色由多个 SkinnedMeshRenderer 组成，各自局部原点可能不同，火纹接缝不一定完全连续。未来可传入统一 Root Space 变换解决。

---

### Q23：向量和点的区别是什么？为什么位置变换常使用 float4？

**面试者回答：**

点表示空间中的位置，方向向量表示位移或方向。使用 Homogeneous Coordinate 时：

```text
point  = (x,y,z,1)
vector = (x,y,z,0)
```

矩阵最后一列的平移只会影响 `w=1` 的点，不影响 `w=0` 的方向。这使旋转、缩放、平移和投影可以统一写成矩阵乘法。

P1 的 Object Position 是点，Normal/View Direction 是方向。对方向错误应用平移会导致几何语义错误。Shader Graph 封装了大部分变换，但在手写 HLSL 或 Custom Function 时必须分清。

---

## 五、Burning 图形学追问

### Q24：Burning 的 Noise UV 是怎样从三维位置构造出来的？

**面试者回答：**

Simple Noise 接收二维坐标，而角色表面位置是三维。我使用：

```text
P = (x,y,z)
u = x + 0.37z
v = y + time × flowSpeed
noiseUV = (u,v) × noiseScale
```

`x+0.37z` 将前后差异混入横向坐标，避免只用 XY 时沿 Z 的表面重复图案；0.37 是打破对称的风格系数，不是物理常数。Y 加 Time 产生纵向流动，Scale 控制空间频率。

这相当于从三维表面位置构造一个 Procedural Mapping。它不依赖原 UV，因此不会受不同衣服 UV 岛布局影响；但不同 Renderer 的 Object Space 可能导致接缝。

---

### Q25：Noise 和随机数有什么区别？为什么火纹使用连续 Noise？

**面试者回答：**

普通随机数或白噪声在相邻采样点之间没有连续性，会产生逐像素跳变和闪烁。Gradient/Value/Simple Noise 会让空间相邻输入得到相近输出，形成连续云状区域。

Burning 需要大块连续火纹，并且坐标随时间移动时要平滑变化，因此使用连续 Noise。Noise 输出只是 `[0,1]` 标量场，后续还要通过 Threshold 和 `Smoothstep` 转成火焰区域 Mask。

如果追求更丰富细节，可以叠加不同频率和振幅的多层 Noise，即 `Fractal Brownian Motion`：

```text
fbm(p) = Σ amplitude_i × noise(frequency_i × p)
```

但 Texture Sample/ALU 成本也会上升，第一版 Simple Noise 已满足状态可读性。

---

### Q26：为什么使用 Smoothstep，而不是 Step？

**面试者回答：**

`Step` 是硬阈值：低于 Threshold 输出 0，高于输出 1。它会产生突兀边界，在角色移动和远距离采样时更容易闪烁与锯齿。

`Smoothstep(edge0,edge1,x)` 在两条边之间进行三次平滑插值：

```text
t = saturate((x-edge0)/(edge1-edge0))
smoothstep = t²(3-2t)
```

它在端点处一阶导数为 0，过渡更自然。P1 使用：

```text
lower = threshold - softness
upper = threshold + softness
mask  = smoothstep(lower, upper, noise)
```

`BurnMaskSoftness` 控制火纹边缘宽度。它是 Anti-aliasing 的辅助，不等价于真正基于屏幕导数的解析抗锯齿；若远距离仍闪烁，可进一步使用 `fwidth` 自适应宽度。

---

### Q27：为什么 BurningIntensity 要同时影响 Threshold 和最终 Mask？

**面试者回答：**

Threshold 控制“覆盖面积”，最终乘强度控制“局部贡献强度”。如果只降低 Threshold，低强度也可能出现完全亮的火斑；如果只乘强度，覆盖范围不变，只是整体变暗。

当前逻辑是：

```text
visualI  = pow(saturate(I),0.6)
threshold = lerp(0.95,0.35,visualI)
mask = smoothstep(threshold-softness,
                  threshold+softness,
                  noise)
finalMask = mask × visualI
```

这样状态增强时，火纹既扩散又变亮；I=0 时 finalMask 严格为 0，避免效果残留。

---

### Q28：为什么使用 `pow(I,0.6)`？这算 Gamma Correction 吗？

**面试者回答：**

它是视觉 Response Curve，不是颜色空间的 Gamma Correction。线性 BurningIntensity 在低于 0.5 时火纹可读性不足，我使用小于 1 的幂函数抬高低值：

```text
0.25^0.6 ≈ 0.435
0.5^0.6  ≈ 0.660
1^0.6    = 1
```

它保持单调和端点，让低强度更可见，但不修改 Gameplay 数据。

Gamma Correction 解决显示编码与 Linear Light 计算的问题，虽然数学上也常出现幂函数，但目的和数据语义不同。面试中不能因为都使用 `pow` 就把二者混为一谈。

---

### Q29：Emission 和 Bloom 有什么区别？

**面试者回答：**

Emission 是材质在 Shader 中输出的自发光颜色，可以使用 HDR 值超过 1。Bloom 是 Camera Post-processing：从最终图像提取超过 Threshold 的亮区，进行模糊，再叠回原画面形成光晕。

流程是：

```text
Shader HDR Emission
→ Camera 得到高亮像素
→ Bloom Threshold 提取
→ Blur / Scatter
→ Add 回画面
```

所以有 Emission 不代表一定有 Bloom。还要确保 Camera 开启 Post Processing、Global Volume 中 Bloom Active、HDR 亮度超过 Threshold，并在 Game View 观察。Material Preview 不一定执行场景 Camera 的 Volume。

---

### Q30：为什么火纹方向的加减号不能只靠公式判断？

**面试者回答：**

移动采样坐标与移动纹理内容在视觉上常呈反向关系。再加上模型 Object Space 的 Y 方向、Shader Graph Preview 与实际 SkinnedMesh Transform，单凭 `+Time` 或 `-Time` 的符号容易误判。

我的 Debug 方法是先让 Speed 取较大值，把其他 Mask 参数固定，在真实角色上观察 Object Position 的 Y 与时间项。最终确认 `Y + Time×Speed` 符合项目模型上的向上流动。

结论不是“所有 Shader 向上都必须加 Time”，而是要明确坐标定义，并在目标资产上验证采样运动的视觉方向。

---

## 六、Wet 图形学追问

### Q31：为什么 Wet 不直接使用蓝色覆盖？

**面试者回答：**

蓝色只是风格标签，不能说明材质为什么像湿的，而且容易与冰冻、魔法护盾或中毒混淆。

我把 Wet 拆成三种信号：提高 Smoothness 表达水膜填平微表面；用 Fresnel 表达掠射角反射增强；用很弱的冷色 Tint 补充正面可读性。主要质感来自 Lit 光照响应，颜色只是辅助。

这体现了图形效果设计的一条原则：先寻找现实或 PBR 中与语义对应的材质参数，再使用风格颜色增强可读性。

---

### Q32：为什么 Wet Edge 不接 Emission？

**面试者回答：**

水膜本质是反射增强，不是主动能量源。如果接入 HDR Emission，角色在没有任何灯光的黑暗中仍会发蓝，更像魔法护盾。

当前 Edge Color 以低强度加入 Base Color，并配合 Smoothness 让 URP Lit 继续处理光照。严格物理方案应让 Fresnel 调制 Specular/Clear Coat，并相应考虑能量守恒。

所以当前选择是风格化但语义正确：允许少量非物理 Base Color 加法换取战斗可读性，但拒绝把水当自发光。

---

### Q33：Camera 移动和 Light 移动分别会怎样影响 Wet？

**面试者回答：**

Fresnel 由 `N·V` 决定，其中 V 指向 Camera，所以移动或旋转 Camera 会改变边缘 Mask。Directional Light 不直接参与这个公式。

Smoothness 影响 URP Lit 的 Specular Highlight，因此移动灯光、Camera 或环境反射都会改变高光位置和形状。

Debug 时要分开变量：先固定 Light、移动 Camera 验证 Fresnel；再固定 Camera、移动 Light 验证 Smoothness。否则可能把光照高光误认为 Fresnel，或者反过来。

---

### Q34：为什么第一版 Fresnel 用几何 Normal，而不是 Normal Map 后的法线？

**面试者回答：**

几何 World Normal 变化稳定，主要反映模型大轮廓。Normal Map 包含布纹等高频细节，如果直接用于 Fresnel，水膜边缘可能变得破碎和闪烁，战斗镜头下可读性反而下降。

当前 Wet 的主要目标是稳定显示角色轮廓水膜，因此先使用几何 Normal。代价是水膜不响应微观凹凸。

升级时可以把 Tangent-space Normal Map 变换到 World Space，按较小权重混入 Fresnel Normal，或者用单独的动态水滴 Normal。是否值得要看视觉目标和 GPU 成本。

---

### Q35：Wet 的颜色加法是否符合能量守恒？

**面试者回答：**

不完全符合。严格的能量守恒要求表面反射能量增加时，漫反射或透射部分相应减少；当前 `finalBase = tintedBase + edgeColor×mask` 是风格化加法，可能增加总能量。

我把 EdgeStrength 控制得很低，并明确它只作为战斗提示。主要材质变化仍通过 Smoothness 进入 URP Lit。

更物理的方案是使用 Fresnel 在 Diffuse 与 Specular 之间分配能量，或增加 Clear Coat Layer。第一版没有这样做，是对复杂度和学习范围的控制，不应该在面试中把它包装成完全物理正确。

---

## 七、Shader Graph 与 HLSL

### Q36：Shader Graph 与手写 Shader 是什么关系？

**面试者回答：**

两者最终都要生成目标图形 API 能编译的 Shader 程序。Shader Graph 是可视化的代码生成和管线集成工具，节点代表采样、向量运算、分支或函数；手写 HLSL 则直接描述这些计算。

Graph 的优势是中间 Preview、参数暴露、与 URP Target 集成以及美术协作；HLSL 的优势是精确控制、复用、版本审查和复杂逻辑表达。

P1 先用节点搭建 Fresnel，帮助观察 `Dot → One Minus → Power` 的数据流；再用 HLSL Custom Function实现同一公式，建立从可视化节点到代码的对应关系。

---

### Q37：为什么 Unity 现在主要使用 HLSL，而不是 CG？

**面试者回答：**

Unity 历史上使用过 Cg/Cg-like 语法和 `CGPROGRAM`，但现代 Unity 渲染管线主要以 HLSL 为 Shader 编写语言，并由编译链转换到不同平台后端。NVIDIA Cg 已经停止发展，URP/HDRP 与 Shader Graph 的库和生成代码也围绕 HLSL 组织。

P1 的 `StatusFresnel.hlsl` 因此使用 HLSL，并放在项目 Shader 目录中由 Shader Graph 的 Custom Function File 引用。

语言选择不意味着 HLSL 文件可以被 C# 直接执行。它仍是 GPU 侧代码，需要通过 Shader 编译和渲染管线运行。

---

### Q38：Custom Function 是 C# 与 Shader Graph 的交互节点吗？

**面试者回答：**

不是。Custom Function 的作用是把 HLSL 函数嵌入 Shader Graph，它连接的是 Shader Graph 与手写 GPU 代码。

C# 与 Shader 的数据交互使用 Material 属性、`MaterialPropertyBlock`、Global Property、Buffer 等接口。P1 的链路是 C# 用 MPB 写 `_WetIntensity`，Custom Function 只负责根据 N、V 和 Power 算 Fresnel。

把这两类“交互”区分开很重要：一个跨 CPU/GPU 数据边界，一个只是 GPU 程序内部的代码组织。

---

### Q39：为什么 HLSL 文件同时实现 `_float` 和 `_half` 两个函数？

**面试者回答：**

Shader Graph Custom Function 会根据节点 Precision 寻找对应后缀。例如函数名填 `StatusFresnel`，Single Precision 会对应 `StatusFresnel_float`，Half Precision 对应 `StatusFresnel_half`。

`float` 通常是 32-bit，精度和范围较高；`half` 在部分移动 GPU 上可能使用较低精度并提高吞吐，但桌面 GPU 上不一定有明显收益。

同时提供两版让节点切换 Precision 时不会找不到实现。当前优先用 Single/float 便于学习和对照；是否改 half 应通过目标设备 GPU Profiler 与画面误差验证，而不是仅凭“half 更快”的口号。

---

### Q40：你怎样验证 HLSL Fresnel 与 Shader Graph 节点版一致？

**面试者回答：**

两条链使用同一个 World Normal、World View Direction 和 Power。节点版输出 A，HLSL 输出 B，计算：

```text
difference = abs(A - B)
```

如果结果接近黑色，说明两者误差接近 0。这个差值只用于诊断 Preview，生产 Wet Edge 应直接连接 HLSL Fresnel。

开发中曾把 Absolute Difference 误接到生产链，导致正确的两版越接近，Wet 输出反而越接近 0。这个问题说明验证信号和生产信号必须在 Graph 中明确分离。

---

## 八、Unity Material 与 Renderer 机制

### Q41：`sharedMaterial` 与 `material` 有什么区别？

**面试者回答：**

`renderer.sharedMaterial` 返回 Renderer 引用的共享 Material 资产，修改它会影响所有使用该资产的对象，并可能在 Editor 中污染项目资源。

`renderer.material` 为了允许对象独立修改，通常会实例化一份 Material。如果频繁或大量访问，会产生 `Material Instance`、额外内存和批处理问题，销毁管理也更复杂。

P1 不修改 Shared Material 的运行时状态，也不通过 `renderer.material` 复制材质。四份 Production Material 保存公共贴图和风格参数，每个 Renderer 的状态 Float 用 MPB 覆盖。

在 Editor 中给 Prefab 替换材质槽时，修改的是 Shared Materials 引用，这是资产配置行为，与运行时调用 `renderer.material` 不同。

---

### Q42：MaterialPropertyBlock 的本质是什么？

**面试者回答：**

MPB 是 Renderer 级的 Shader 属性覆盖集合。它不会复制整份 Material，而是在该 Renderer 提交 Draw 时覆盖特定 Property。

P1 中 Shared Material 保存贴图、Burn 风格颜色、Noise Scale 等公共数据；MPB 保存某个 Renderer 当前的 Burning/Wet/Poisoned/Sticky Float。

关键 API 是：

```csharp
renderer.GetPropertyBlock(block);
block.SetFloat(propertyId, value);
renderer.SetPropertyBlock(block);
```

它适合“材质相同、少量每对象参数不同”的场景。若每对象需要完全不同的贴图和大量参数，独立 Material 或其他数据组织可能更合适。

---

### Q43：用了 MPB 就一定能减少 Draw Call、提高性能吗？

**面试者回答：**

不能这样绝对化。MPB 的确定价值是避免为每个 Renderer 复制 Material，并表达每 Renderer 参数覆盖；它对 Draw Call、SRP Batcher 和 GPU Instancing 的影响取决于 Unity 版本、Shader、Renderer 类型和属性组织。

SkinnedMeshRenderer 本身也有骨骼动画和不同 Mesh，不一定具备合批条件。某些 MPB 属性可能使 Renderer 不再走特定 SRP Batcher 路径。

正确做法是用 Frame Debugger 比较是否产生 Material Instance、Pass 和 Draw Call，用 Profiler/Rendering Statistics 验证 CPU/GPU 数据。面试中我会把“内存与语义收益”和“Batching 性能结论”分开陈述。

---

### Q44：什么是 SRP Batcher？它与 GPU Instancing 有什么区别？

**面试者回答：**

SRP Batcher 主要优化 CPU 组织和切换 Shader 常量数据的成本，让使用兼容 Shader Variant 的对象更高效地提交；它不等价于把多个对象合并成一个 Draw Call。

GPU Instancing 则让多个相同 Mesh、Material/Shader 的对象通过一个或更少 Draw Call 绘制，并使用每实例数据区分 Transform 或属性。

P1 的角色是多个不同模块化 SkinnedMeshRenderer，并非典型的大量相同静态 Mesh Instancing 场景。当前重点是共享 Material 和避免实例污染，SRP Batcher/Draw Call 结果通过 Frame Debugger 观察，不预设结论。

---

### Q45：为什么要使用 `Shader.PropertyToID`？

**面试者回答：**

Material/MPB API 可以使用字符串查找属性，但热路径反复处理字符串没有必要，也容易散布拼写。

P1 在类型初始化时执行：

```csharp
private static readonly int BurningId =
    Shader.PropertyToID("_BurningIntensity");
```

后续 `SetFloat` 使用整数 ID。它减少重复字符串查找，并把属性名集中管理。

前提是 Shader Graph Blackboard 的 `Reference` 必须逐字一致。Display Name 只是 Inspector 显示，C# 真正匹配的是 Reference。PropertyToID 不能自动发现拼写错误，所以仍需测试和运行时验证。

---

### Q46：为什么 `StatusMaterialController` 自动收集 Renderer 只在 Awake 做？

**面试者回答：**

`GetComponentsInChildren` 会遍历层级并返回数组，属于初始化型操作，不应该每帧执行。角色表面 Renderer 在当前固定 Prefab 中不会频繁变化，因此在 `Awake` 缓存一次即可。

代码只保留 `MeshRenderer` 与 `SkinnedMeshRenderer`，排除粒子和 Trail，避免状态参数误写到 VFX Renderer。

边界是默认调用只收集 Awake 时激活的节点。模块化角色如果运行时启用一件原来 inactive 的装备，它不会自动进入缓存。后续应设计 `RefreshRenderers()`、显式列表或装备系统注册事件，而不是回到每帧扫描。

---

### Q47：SkinnedMeshRenderer 和 MeshRenderer 有什么区别？

**面试者回答：**

MeshRenderer 通常配合 MeshFilter 绘制静态或通过 Transform 整体运动的 Mesh。SkinnedMeshRenderer 会根据骨骼矩阵和 Bone Weight 对顶点进行 Skinning，角色动画时顶点位置持续变化。

P1 的角色衣服和身体主要是 SkinnedMeshRenderer，所以状态 Shader 必须兼容蒙皮后的顶点流程。Shader Graph/URP 会接入 Unity 的 Skinning 数据，P1 没有手写骨骼变换。

Burning 使用的 Object Position 是 Shader 管线中的表面位置，但模块化多个 Skinned Renderer 的局部空间未必统一，因此接缝仍是已知问题。状态参数则是 Renderer 级 MPB，每个模块都要写相同强度。

---

## 九、架构、事件与生命周期

### Q48：为什么使用 EventBus，而不是 StatusMaterialController 每帧查询 StatusController？

**面试者回答：**

事件让 Gameplay 在状态变化时通知表现层，避免每个表现组件每帧轮询全部状态，也保持跨 Assembly 单向依赖。

P1 的 Event 包含 TargetId、Kind、Intensity 和 IsActive。表现桥只在事件到达时更新 Target，然后在过渡期间 Update 平滑；稳定后立即 return。

但事件不是万能的。对象 Enable 时可能错过禁用期间的事件，所以 `OnEnable` 还会主动从 StatusController 同步一次权威值。这是 `Event + Snapshot` 的组合：事件负责增量通知，Snapshot 负责生命周期恢复。

---

### Q49：为什么事件一定要过滤 TargetId？

**面试者回答：**

项目 EventBus 是按事件类型广播，不是按对象建立独立 Channel。所有 `StatusMaterialController` 都会收到 `StatusChangedEvent`。

每个控制器在 Awake 缓存自己的 `gameObject.GetInstanceID()`，收到事件后先比较 `statusEvent.TargetId != _targetId` 并 return。否则一个敌人着火会让所有订阅者一起更新。

Instance ID 适合当前运行周期的对象寻址，但不适合存档或网络跨端稳定 ID。未来网络同步应使用明确的 Entity ID，而不是假设 Unity Instance ID 可持久化。

---

### Q50：为什么 OnEnable 订阅、OnDisable 取消订阅？

**面试者回答：**

这是 Unity `MonoBehaviour` 与全局事件的标准生命周期匹配。Enabled 且 Active 的组件才应该响应事件；Disable 或 Destroy 前取消订阅可避免失效对象继续被回调、形成引用残留或错误更新。

P1 在 `OnDisable` 还清零 `_current/_target` 并写回 MPB，防止对象池下次复用时短暂显示旧状态。`OnEnable` 再从 Gameplay Snapshot 直接同步。

需要注意 Unity 调用顺序：`Awake` 先创建 MPB 和缓存组件，随后 `OnEnable` 才能安全订阅与应用参数。

---

### Q51：为什么多个状态放在 Vector4 中？这有什么利弊？

**面试者回答：**

Vector4 的 XYZW 分别保存 Burning、Wet、Poisoned、Sticky。它是紧凑值类型，便于一次比较当前/目标并避免每帧创建对象。

优点是当前状态数量固定、代码简洁、`sqrMagnitude` 可以统一判断是否收敛。缺点是语义依赖分量约定，可读性弱于具名 struct；状态增加到五个以上时扩展性差。

当前四种固定状态适合 Vector4。若系统发展成可配置几十种元素状态，我会改用固定数组、具名状态结构或数据驱动 Buffer，并重新评估 GPU 属性布局，而不是无限堆 Vector。

---

### Q52：为什么使用 `sqrMagnitude` 与 Epsilon，而不直接比较 Vector4 相等？

**面试者回答：**

浮点数经过多帧运算后通常不应依赖绝对相等。`next-target` 的平方长度：

```text
|d|² = dx² + dy² + dz² + dw²
```

小于一个极小阈值时即可认为收敛。使用平方长度避免为了比较距离调用 Square Root。

当进入阈值后，代码把 `next` 直接设为 target 并关闭 `_isTransitioning`，保证最终稳定且 Update 可以提前 return。

这里 Epsilon 是工程容差，不是数学真理；太大可能提前截断可见变化，太小会多更新若干帧，需要结合 Float 精度和视觉单位选择。

---

## 十、性能、Shader Variant 与可扩展性

### Q53：这个 Shader 的主要 GPU 成本在哪里？

**面试者回答：**

原 PBR 基线包含多次 Texture Sample 和 URP Lit 光照。新增部分中，Burning 的 Simple Noise、`Smoothstep`、`pow` 与多次 ALU 是主要成本；Wet 的 Normalize、Dot、Power、Smoothness 和颜色混合也增加 Fragment 运算。

因为计算发生在 Fragment 阶段，成本与角色在屏幕上覆盖的像素、分辨率和 Overdraw 相关。近景角色比远景小角色更贵。

我会分别捕获 Neutral、Burning、Wet、Combined，在相同 Camera 下使用 GPU Profiler/RenderDoc 类工具比较，而不是只数 Shader Graph Node。编译器可能常量折叠、融合或以不同指令实现节点，Node 数不等于真实指令数。

---

### Q54：状态为 0 时，GPU 会自动跳过 Burning/Wet 计算吗？

**面试者回答：**

不一定。即使最终乘 0，Shader 编译器也不能总是消除依赖运行时 Uniform 的前置计算，因为它不知道每次 Draw 的值。统一 Shader 可能仍执行 Noise 和 Fresnel，再把结果乘 0。

可以加入动态 Branch，例如 `if (intensity<=0)`，但 GPU 分支是否有收益取决于分支一致性、计算量和硬件；如果同一个 Draw 中所有 Fragment 读取相同 Uniform，分支通常较一致，但仍需实测。

也可以用 Shader Keyword 编译关闭状态的 Variant，使编译期移除代码，但会增加 Variant 数量。当前先选择组合简单的统一计算，等 Profiler 证明是瓶颈再优化。

---

### Q55：为什么不为四种状态各用一个 Shader Keyword？

**面试者回答：**

四个 Boolean Keyword 理论组合数为：

```text
2^4 = 16
```

状态继续增加时组合指数增长。Variant 会增加 Shader 编译时间、Build 大小、加载/Warmup 成本，也需要确保不会被错误 Strip。

而 P1 状态不是纯 Boolean，还需要 0~1 连续强度和组合过渡。统一 Float 参数更自然。

如果未来统计表明绝大多数角色长期 Neutral，且 Noise 成本显著，我会考虑少量粗粒度 Variant，例如 `STATUS_EFFECTS_ON`，而不是每种状态独立 Keyword。选择应由实际状态分布和 GPU 数据决定。

---

### Q56：你如何保证 CPU 热路径没有 GC Alloc？

**面试者回答：**

初始化阶段创建一次 `MaterialPropertyBlock` 和 Renderer 数组；Update 中只操作 Float、Vector4 和已有数组，不使用 LINQ、Closure、字符串拼接或 `new`。

`Shader.PropertyToID` 静态缓存；稳定状态 `_isTransitioning=false` 时立即 return；只有参数真的变化时才循环 Renderer 并 SetPropertyBlock。

我会在 Unity Profiler 关闭 Deep Profile 后搜索 `StatusMaterialController.Update`，分别观察状态变化期与稳定期的 `GC Alloc`。代码审查只能说明没有明显托管分配，最终仍应以 Profiler 为证据。

---

### Q57：如果同屏有 100 个状态角色，你会怎么优化？

**面试者回答：**

我会先分 CPU 与 GPU 定位。

CPU 侧检查事件频率、MPB Set 次数和 Renderer 数量。可以把事件发布从每个细小 Float 变化改成可控频率，或只在百分比变化时发布；对稳定状态保持早退。运行时换装采用注册表而不是扫描。

GPU 侧按屏幕面积和距离分级。远距离 LOD 可以关闭动态 Noise/Fresnel，只保留低成本 Tint；近距离保留完整效果。若大量 Neutral，评估粗粒度 Keyword/Branch；若大量相同 Mesh，再研究 Instancing 与 GPU Buffer。

我不会在没有数据前直接把所有逻辑改成 Compute Shader。100 个角色的瓶颈也可能是 Skinning、阴影或 Overdraw，而不是状态公式。

---

### Q58：为什么没有给每个状态单独一个 Overlay Material Pass？

**面试者回答：**

Overlay Pass 可以独立开发、方便叠加透明动画，但每个状态可能增加额外 Draw Call 和 Overdraw，Skinned Mesh 还可能重复顶点处理。多个状态同时存在时成本按层增加，并带来透明排序和深度问题。

统一 Surface Shader 在一次 Lit Pass 内修改 Base Color、Smoothness 与 Emission，更适合贴合角色表面且状态组合明确的需求。

但 Overlay 仍适合体积火焰、护盾壳、溶解边缘等需要超出基础表面的效果。P1 保留 OnFire 粒子 VFX，说明统一 Shader 与外部 VFX 可以互补。

## 十一、测试与 Debug 压力题

### Q59：你的自动化测试具体测了什么？为什么不是只测 Shader？

**面试者回答：**

Shader 最终视觉很难仅靠普通 NUnit 做像素正确性测试，但 CPU 到 Renderer 的数据契约可以自动化。

我使用真实 EventBus、StatusController、Renderer 与 MPB 测了四件事：TargetId 过滤与 0~1 Clamp；Wet=50 写入 0.5 且保留已有 `_BaseColor`；两个 Renderer 共享 Material 时 MPB 值独立；组件 Disable 后取消订阅并清零视觉状态。

Shader 视觉则使用 Lab Material、节点 Preview、实际 SkinnedMeshRenderer 与 Game View A/B。两类测试互补：自动化保证数据合同，人工视觉验证图形表达。

---

### Q60：测试为什么曾经全部超时？你是怎么定位的？

**面试者回答：**

测试进入当前场景时继承了 Wand Editor 留下的 `Time.timeScale=0`。生产代码使用 `Time.deltaTime`，所以：

```text
maxDelta = responseSpeed × deltaTime = 0
```

平滑永远不前进，`WaitUntilSettled` 超时。

我先确认事件和 Target 已更新，再观察 `_isTransitioning` 一直为 true，继续追踪 `MoveTowards` 的 maxDelta，最终定位 Time 全局状态。

修复是在测试开头显式恢复 `Time.timeScale=1`，而不是把生产代码改成 Unscaled Time。因为暂停时是否继续播放状态变化属于设计语义，测试应该建立正确前置条件，不能为通过测试破坏生产行为。

---

### Q61：BurningIntensity=0 但角色仍然发红，你怎么排查？

**面试者回答：**

先验证 MPB 中 Burning 是否真的为 0；如果是，就从最终 Emission 逆向断开 Graph。

正确状态贡献必须满足：

```text
burnEmission = BurnEmissionColor × finalBurnMask
finalBurnMask = mask × visualIntensity
```

当 Intensity=0 时结果应严格为 0。实际问题是 Burn Emission Color 有一条路径绕过 Mask 直接进入最终 Emission。

修复后再测试 Burning=0、0.25、1 三个点，并关闭 Bloom 区分 Shader Emission 与后处理残影。这种 Debug 是从输出追到 Gate，而不是随意把颜色调黑。

---

### Q62：Wet 看起来没有变化，你会按什么顺序排查？

**面试者回答：**

第一步检查 Gameplay 与 MPB：StatusController Wet 是否大于 0，MPB `_WetIntensity` 是否正确。

第二步把 Material 上 WetIntensity、WetSmoothness、EdgeStrength 临时设高，证明 Graph 链路。

第三步分开看输出：Smoothness 单独接固定值；Fresnel 看灰度 Preview；Tint 单独提高。移动 Camera 验证 Fresnel，移动 Light 验证 Smoothness。

第四步检查 World Normal/View Direction 是否同空间、Power 端口是否接反、WetIntensity 是否乘到所有分支。

第五步检查场景是否缺少可见高光的灯光或环境反射。Smoothness 是光照响应，不是直接变白。

最后恢复合理参数，避免用过强蓝色掩盖真正问题。

---

### Q63：角色移动时火纹像固定在世界里，原因是什么？

**面试者回答：**

通常是 Noise 输入错误使用了 World Position。World 坐标在角色移动时变化，采样区域固定于世界，角色就像穿过 Noise。

P1 应使用 Object Position，让局部坐标随角色整体移动保持不变。检查 Shader Graph Position Node 的 Space，以及是否有 Transform Node 把它误转回 World。

如果改成 Object Space 后模块之间仍有接缝，则问题从“世界漂移”变成“多个 Renderer 局部空间不统一”，需要统一 Root Space，而不是继续调 Noise Scale 掩盖。

---

### Q64：为什么你要主动讲方案的缺点？面试不是应该突出成果吗？

**面试者回答：**

工程能力不仅是实现理想效果，还包括知道近似条件、性能风险和演进边界。如果把风格化 Fresnel 说成完整物理水膜，把 MPB 说成必然合批，面试官通过一两个追问就会发现理解不扎实。

我会先说明方案满足了什么需求，再说明主动接受的 trade-off，最后给出如何用数据验证和升级。例如 Wet Edge 非严格能量守恒，但强度低、服务战斗可读性；如果追求物理正确，升级到 Clear Coat/Specular。

这种回答不是贬低成果，而是证明我能做范围控制和技术判断。

## 十二、开放设计与系统扩展

### Q65：如果下一步实现 Poisoned，你会怎么设计？

**面试者回答：**

我不会先选择“全身变绿”，而会先从 Gameplay 语义反推视觉：Poisoned 是体内持续伤害还是表面腐蚀？是否需要与 Wet/Burning 同时可读？

如果是腐蚀型中毒，我可能使用低频脉动 Noise 控制黄绿 Tint、局部 Roughness 和较弱 Emission，避免与 Wet 的冷色 Fresnel、Burning 的橙色流动混淆。脉动强度仍由 `_PoisonedIntensity` 驱动。

架构上无需改变 Combat→Rendering→MPB 通道，只在统一 Shader 中加入视觉组合。但要先定义状态优先级、颜色空间和 GPU 预算，避免每增加一个状态就无条件堆昂贵 Noise。

---

### Q66：如果多个状态的视觉发生冲突，你如何决定优先级？

**面试者回答：**

先把每种状态拆成它拥有的 Surface Channel，例如 Base Color、Smoothness、Normal、Emission、Alpha。冲突不是简单“后者覆盖前者”，而是针对 Channel 定义组合规则。

例如 P1 中 Burning 先修改 Base Color并贡献 Emission，Wet 再轻微 Tint和提高 Smoothness；Wet 不直接覆盖 Burn Emission，灭火由 Gameplay 让 BurningIntensity下降。

未来可以建立显式组合表：颜色是顺序 Lerp、Smoothness 取 Max/Min、Emission Add 或 Max、Normal 使用 Reoriented Normal Mapping。每条规则都应对应状态语义，并测试极端组合。

---

### Q67：如果角色运行时换装，当前方案会遇到什么问题？

**面试者回答：**

`StatusMaterialController` 在 Awake 自动收集当时激活的 Renderer。运行时新启用或实例化的装备不会自动进入数组，所以它可能不显示状态。

短期方案是换装完成后调用显式 `RefreshRenderers()`；更好的方案是装备系统通过事件或接口向表现控制器注册/注销 Renderer。注册时立即应用当前 MPB 状态，避免装备出现一帧 Neutral。

不建议每帧 `GetComponentsInChildren`，因为层级遍历和数组分配会进入热路径。这个扩展应设计清晰的生命周期边界。

---

### Q68：如果要解决多个模块 Object Space 火纹接缝，你会怎么做？

**面试者回答：**

问题根源是每个 SkinnedMeshRenderer 的局部坐标基底或原点可能不同。即使状态参数相同，Object Position 输入也不连续。

一种方案是使用 World Position，再减去角色 Root 的 World Position，并乘 Root 的 World-to-Local 旋转/缩放，构造统一 Root Space。Root 变换可以通过 Shader 属性或矩阵传入。

另一种方案是使用模型作者统一的 UV/Vertex Color 作为状态坐标；或者 Tri-planar Mapping 减少 UV 依赖。

我会先记录实际接缝是否在战斗镜头可见，再决定是否承担矩阵参数与额外运算成本。不能为了理论连续性过度设计。

---

### Q69：如果让这个系统支持网络同步，你会同步 Shader 参数吗？

**面试者回答：**

通常不直接同步 Shader 参数，而是同步 Gameplay 权威状态，例如 Burning 强度、起始时间或状态增量。客户端表现层根据本地收到的 Gameplay Snapshot 计算和平滑 Shader 值。

原因是 Shader 参数属于 Presentation，可以按设备画质不同；直接同步会把表现细节耦合到网络协议，也增加带宽。

网络 Entity ID 需要替代 Unity `GetInstanceID()` 作为跨端身份。收到快照后应支持校正当前状态，视觉平滑可以掩盖小误差，但不能让客户端表现反向决定伤害。

---

### Q70：如果目标平台是移动端，你会关注什么？

**面试者回答：**

GPU 侧关注 Fragment ALU、Noise、Power、Texture Sample、角色屏幕覆盖和 Overdraw；测试 `half` Precision 是否可接受；给远距离 LOD 使用简化状态；控制 Bloom 分辨率和后处理成本。

CPU 侧关注大量 SkinnedMeshRenderer、MPB 提交、事件频率和 Skinning。内存侧关注 Texture Atlas 分辨率、压缩格式和 Shader Variant。

我会在真机 GPU Profiler 上比较 Neutral/Burning/Wet/Combined，而不是只在桌面 Editor 看帧率。移动 GPU 架构、带宽和热限制与桌面不同，桌面结论不能直接迁移。

## 十三、面试官可能要求你现场推导的公式

### Q71：现场推导 `Lerp`

**面试者回答：**

线性插值要求：`t=0` 得到 a，`t=1` 得到 b，中间按比例变化，所以：

```text
lerp(a,b,t) = a + t(b-a)
             = a(1-t) + bt
```

P1 中它用于从原颜色到 Burn Tint、从 Base Smoothness 到 Wet Target，以及从高 Threshold 到低 Threshold。

当 t 超出 0~1，普通 Lerp 会外插，因此 Gameplay 输入先 Clamp01。Shader Graph 中还要区分 `Lerp` 是否自动 Saturate，不能默认所有 API 都替你限制范围。

---

### Q72：现场解释点积的几何意义

**面试者回答：**

代数定义：

```text
a·b = axbx + ayby + azbz
```

几何定义：

```text
a·b = |a||b|cos(theta)
```

单位向量时等于夹角余弦：同向为 1，垂直为 0，反向为 -1。它也可以理解为一个向量在另一个单位方向上的投影长度。

P1 用单位 N 与 V 的点积判断表面朝向 Camera 的程度，再反转成轮廓 Mask。

---

### Q73：现场解释 Cross Product 在这个项目后续可能怎么用

**面试者回答：**

叉积 `a×b` 产生一个同时垂直于 a、b 的向量，方向由右手定则决定，长度为：

```text
|a×b| = |a||b|sin(theta)
```

P1 当前 Fresnel 主要使用 Dot，不直接需要 Cross。但 Normal Mapping 的 TBN 基底中，Bitangent 常可由 Normal 与 Tangent 的叉积构造，并结合 handedness 修正方向。

未来如果实现沿表面方向流动的湿痕，也可能用 Normal 与世界 Up 构造切向流动方向。需要处理两向量接近平行时叉积接近零的退化情况。

---

### Q74：现场解释 `Smoothstep` 为什么比线性插值更平滑

**面试者回答：**

先把 x 映射到 0~1：

```text
t = saturate((x-edge0)/(edge1-edge0))
```

再用三次 Hermite 多项式：

```text
f(t)=t²(3-2t)=3t²-2t³
```

它满足：

```text
f(0)=0, f(1)=1
f'(0)=0, f'(1)=0
```

端点斜率为 0，因此进入和离开过渡区时不会突然改变一阶速度。P1 使用它软化 Noise Threshold 的火纹边缘。

## 十六、考前速查公式

```text
归一化：
I_shader = clamp(I_gameplay / 100, 0, 1)

帧率无关平滑：
maxDelta = responseSpeed × deltaTime
current = MoveTowards(current, target, maxDelta)

线性插值：
lerp(a,b,t) = a(1-t) + bt = a + t(b-a)

向量长度与归一化：
|v| = sqrt(vx²+vy²+vz²)
normalize(v)=v/|v|

点积：
a·b = axbx+ayby+azbz = |a||b|cos(theta)

叉积长度：
|a×b|=|a||b|sin(theta)

Burning 视觉响应：
I_visual = pow(saturate(I),0.6)

Burning 动态坐标：
uv = float2(x+0.37z, y+time×speed)×scale

Smoothstep：
t=saturate((x-edge0)/(edge1-edge0))
smoothstep=t²(3-2t)

Wet Smoothness：
target=max(baseSmoothness,wetSmoothness)
final=lerp(baseSmoothness,target,WetIntensity)

风格化 Fresnel：
F=pow(1-saturate(dot(normalize(N),normalize(V))),power)

Schlick Fresnel：
F(theta)=F0+(1-F0)(1-cos(theta))^5

介质正视反射率：
F0=((n1-n2)/(n1+n2))²

Normal Matrix：
N_world=normalize((M_model^-1)^T N_object)
```

最后要记住：公式本身只是工具。面试官真正想听的是你为什么选择这个输入、它位于哪个 Coordinate Space、输出如何进入材质、运行成本在哪里、失败时如何验证，以及它与 Gameplay 架构怎样保持边界。
