# 轨道螺旋修正法术设计复盘

创建时间：2026-07-04 15:30:36  
功能状态：已在 Unity Editor / Play Mode 中测试通过  
目标读者：战斗系统设计新手，重点理解 3D 法术修正、运行时弹道控制、与现有法术编程架构的集成方式

---

## 1. 功能一句话总结

“轨道螺旋修正法术”不是一个新的火球，而是一个 `Modify` 法术。它会让后续 `Emit` 投射物围绕一个看不见的、沿发射方向移动的圆心旋转前进。

最典型的法杖组合是：

```text
[轨道螺旋] [三重射击] [火球] [火球] [火球]
```

玩家看到的效果是：

```text
三颗火球不是简单水平散开。
它们围绕一个看不见的移动圆心旋转。
圆心沿玩家瞄准方向前进。
三颗火球的相位不同，轨道面也尽量错开，所以看起来更像围绕一个球面旋转，而不是退化成一个平面圆环。
```

这次功能的核心训练点是：

> 当 2D 游戏里的法术设计迁移到 3D 游戏时，不能只把“左右散射”照搬过来。3D 战斗需要考虑高度、轨道面、空间覆盖和视觉可读性。

## 2. 基础知识和原理

### 2.1 这是“飞行过程修正”，不是“发射瞬间散射”

普通散射只在投射物生成的一瞬间改变方向：

```text
第 1 发向左飞
第 2 发向中间飞
第 3 发向右飞
```

之后它们各自直线飞行。

轨道螺旋不同。它每个 `FixedUpdate()` 都会改变投射物速度，让投射物持续围绕一个移动圆心运动：

```text
发射瞬间：确定圆心前进方向、轨道半径、角速度、初始相位、轨道面
飞行期间：圆心向前移动，投射物绕圆心旋转
```

所以它不能只放在 `SpellAiming` 里。`SpellAiming` 适合处理“发射瞬间的角度计算”，而轨道螺旋必须进入 `ProjectileBase`，因为它属于投射物生命周期中的运行时运动控制。

### 2.2 “看不见的圆心”是什么

可以把每颗投射物想象成绑定到一个虚拟中心点：

```text
center(t) = startPosition + forward * centerSpeed * t
```

这个 `center`：

- 不显示；
- 没有 `Collider`；
- 不造成伤害；
- 不参与碰撞；
- 只是数学参考点。

投射物真正的位置可以理解成：

```text
projectilePosition(t) = center(t) + orbitalOffset(t)
```

其中：

```text
center(t)        = 沿瞄准方向前进的虚拟圆心
orbitalOffset(t) = 投射物相对圆心的旋转偏移
```

这就是“看不见的球”的工程表达：我们不真的生成一个球对象，而是用数学变量模拟球心和球面偏移。

### 2.3 圆周运动的数学原理

要让投射物绕圆心旋转，需要先建立一组局部坐标轴：

```text
forward = 圆心前进方向
right   = 垂直于 forward 的横向轴
up      = 垂直于 forward 和 right 的纵向轴
```

然后使用 `sin/cos` 计算圆上的偏移：

```text
offset = right * cos(angle) * radius
       + up    * sin(angle) * radius
```

每个物理帧更新：

```text
center += forward * centerSpeed * fixedDeltaTime
angle  += angularSpeed * fixedDeltaTime
```

这套公式的含义是：

```text
圆心一直向前走。
投射物围绕圆心转。
圆心前进 + 投射物旋转 = 螺旋弹道。
```

### 2.4 为什么还要“轨道面倾斜”

只给三颗火球不同相位，例如：

```text
0° / 120° / 240°
```

确实能让三颗火球分开，但它们仍然在同一个圆平面内运动。视觉上容易变成：

```text
三颗火球绕一个圆环排队转。
```

这不是你想要的“围绕球面旋转”。

因此本功能额外加入了：

```text
OrbitPlaneTiltDegrees
```

它的作用不是改变投射物在圆上的位置，而是改变“这个圆所在的平面”。例如三发时：

```text
index 0 -> plane tilt 0°
index 1 -> plane tilt +35°
index 2 -> plane tilt -35°
```

这样三颗火球会走不同倾斜角的大圆路径，更接近“球面环绕”的视觉效果。

### 2.5 Unity 相关基础

本功能涉及的 Unity API 和组件：

| 技术点 | 作用 |
|---|---|
| `Rigidbody` | 投射物通过刚体参与物理移动和碰撞 |
| `Rigidbody.linearVelocity` | Unity 6 中设置刚体速度，替代旧版 `velocity` |
| `FixedUpdate()` | 物理更新入口，适合更新刚体速度 |
| `Time.fixedDeltaTime` | 物理帧间隔，用于角速度和圆心位移计算 |
| `Quaternion.LookRotation` | 根据前进方向构造局部坐标系 |
| `Quaternion.AngleAxis` | 让轨道平面绕某个轴倾斜 |
| `Vector3.Dot` | 判断发射方向是否接近世界向上方向，避免坐标系退化 |
| `Mathf.Sin / Mathf.Cos` | 计算圆周运动偏移 |
| `Mathf.Deg2Rad` | 把角度转换为弧度 |
| `Mathf.Approximately` | 判断浮点数是否接近 0 |

## 3. 常见实现方案与取舍

### 3.1 方案 A：初始 3D 散射

做法：

```text
发射时给每颗投射物不同 yaw/pitch。
之后每颗投射物直线飞行。
```

优点：

- 简单；
- 只需要改 `SpellAiming` / `SpellCaster`；
- 不需要改 `ProjectileBase`。

缺点：

- 只在发射瞬间覆盖 3D 空间；
- 投射物不会持续绕球面运动；
- 敌人跳跃、移动后，空间覆盖很快失效；
- 视觉特色弱，更像普通散弹。

结论：

不采用。它解决的是“初始方向分布”，不是你提出的“围绕看不见的球旋转”。

### 3.2 方案 B：用物理力模拟环绕

做法：

```text
每帧给投射物施加侧向力或向心力，让它绕中心点运动。
```

优点：

- 更像真实物理；
- 可以自然受质量、阻力、重力影响。

缺点：

- 参数很难调；
- 半径不稳定；
- 容易受碰撞和重力影响后失控；
- 不利于做成可预测的技能；
- Debug 成本高。

结论：

不采用。本项目的法术编程系统更需要“可控、可解释、可组合”的弹道，而不是不可预测的物理模拟。

### 3.3 方案 C：数学轨道控制速度

做法：

```text
用数学变量保存虚拟圆心、轨道半径、角速度、相位、轨道面。
每个 FixedUpdate 计算目标轨道点。
再通过 Rigidbody.linearVelocity 让投射物向目标点移动。
```

优点：

- 表现稳定；
- 参数直观；
- 易于和 `Modify` 法术数据绑定；
- 保留 `Rigidbody` 碰撞；
- 能和现有 `ProjectileBase -> IDamageable` 战斗漏斗兼容。

缺点：

- 不是完全真实物理；
- 会和追踪、重力、弹跳等其他速度控制功能产生优先级问题。

结论：

最终采用。

### 3.4 方案 D：单独做 `OrbitalFireball`

做法：

```text
新建一个特殊火球 prefab 或特殊投射物脚本，只让它拥有轨道运动。
```

优点：

- 初期实现局部简单；
- 不需要扩展法术解释器字段。

缺点：

- 破坏法术编程系统；
- 只能作用于火球，不能作用于未来其他投射物；
- 未来会膨胀出 `OrbitalTimedFireball`、`OrbitalTriggerFireball`、`OrbitalGravityFireball` 等组合爆炸；
- 面试时会显得是 hardcode，不是可扩展系统设计。

结论：

不采用。轨道螺旋应该是 `Modify`，不是特殊 `Emit`。

## 4. 最终用到的技术

### 4.1 `ScriptableObject` 数据驱动

轨道螺旋是一个 `SpellDefinition` 资产：

```text
Kind = Modify
DisplayName = 轨道螺旋
ModOrbitRadius = 0.8
ModOrbitAngularSpeedDegrees = 360
ModOrbitPhaseOffsetDegrees = 0
ModOrbitPlaneTiltDegrees = 35
```

这体现了项目的核心原则：

```text
新增法术内容优先改数据资产，不优先写一个新 MonoBehaviour。
```

### 4.2 `readonly struct` 快照

`CastModifierState` 和 `EmitCommand` 都是值快照。

`CastModifierState` 表示解释器读到当前位置时，已经累计了哪些修正：

```csharp
public readonly float OrbitRadius;
public readonly float OrbitAngularSpeedDegrees;
public readonly float OrbitPhaseOffsetDegrees;
public readonly float OrbitPlaneTiltDegrees;
```

`EmitCommand` 表示某一发投射物最终要使用的完整发射命令。

为什么要快照？

```text
因为投射物生成后，不能再回头查询法杖里当前的 SpellDefinition。
投射物应该携带本次施法瞬间的最终参数。
```

这和你项目里 `DamageRequest` 的思路类似：运行时事件要用“当时的值”，不要依赖未来可能变化的对象状态。

### 4.3 纯函数 `SpellAiming`

这次新增了两个纯函数：

```csharp
SpellAiming.PhaseOffsetDegrees(index, count)
SpellAiming.PlaneTiltDegrees(index, count, baseTiltDegrees)
```

它们的职责不同：

| 函数 | 解决的问题 |
|---|---|
| `PhaseOffsetDegrees` | 同一批投射物在圆周上的起始位置不同 |
| `PlaneTiltDegrees` | 同一批投射物的旋转平面不同 |

例如三发：

```text
PhaseOffsetDegrees -> 0 / 120 / 240
PlaneTiltDegrees   -> 0 / +35 / -35
```

这两个函数放在 `Game.Skills` 是合理的，因为它们是纯数学规则，不依赖场景对象。

### 4.4 `Rigidbody.linearVelocity`

轨道螺旋没有直接设置：

```csharp
transform.position = targetPosition;
```

而是设置：

```csharp
_rb.linearVelocity = (targetPosition - _rb.position) / safeDeltaTime;
```

原因：

- 投射物仍然通过 `Rigidbody` 运动；
- 碰撞检测仍然有效；
- `CollisionDetectionMode.ContinuousDynamic` 仍然能发挥作用；
- 不会完全绕开 Unity Physics。

### 4.5 `FixedUpdate`

轨道运动写在 `ProjectileBase.FixedUpdate()` 中：

```text
如果 orbit enabled：
    TickOrbit(Time.fixedDeltaTime)
否则：
    TickHoming(Time.fixedDeltaTime)
```

原因：

- `Rigidbody` 速度属于物理更新；
- `Time.fixedDeltaTime` 比 `Time.deltaTime` 更适合物理步进；
- 可以避免不同帧率下轨道速度明显变化。

## 5. 架构设计与脚本拆解

### 5.1 总体链路

轨道螺旋沿现有法术编程系统链路传递：

```text
SpellDefinition
    -> CastModifierState
    -> CastEvaluator
    -> EmitCommand
    -> SpellCaster
    -> ProjectileBase
```

你可以这样理解每一层：

| 层级 | 脚本 | 职责 |
|---|---|---|
| 数据资产层 | `SpellDefinition` | 暴露 Inspector 参数，告诉系统这个 Modify 提供哪些轨道修正 |
| 修正状态层 | `CastModifierState` | 从左到右累积 Modify 效果 |
| 解释器层 | `CastEvaluator` | 把法杖序列解释成 `EmitCommand` |
| 命令快照层 | `EmitCommand` | 保存某一发投射物最终参数 |
| 运行时桥接层 | `SpellCaster` | 实例化 prefab，并把命令参数配置到 projectile |
| 投射物执行层 | `ProjectileBase` | 每个物理帧执行轨道运动、碰撞、销毁、触发 |

这条链路非常重要。以后新增任何 `Modify` 法术，都可以先问：

```text
它是不是只影响后续 Emit？
它是否需要进入 CastModifierState？
它是否需要被 EmitCommand 快照？
它是否需要 SpellCaster 配置到运行时对象？
它是否需要 ProjectileBase 或其他 runtime component 执行？
```

### 5.2 `SpellDefinition.cs`

新增字段：

```csharp
public float ModOrbitRadius = 0f;
public float ModOrbitAngularSpeedDegrees = 0f;
public float ModOrbitPhaseOffsetDegrees = 0f;
public float ModOrbitPlaneTiltDegrees = 0f;
```

它们只在：

```text
Kind = Modify
```

时有意义。

字段含义：

| 字段 | 含义 |
|---|---|
| `ModOrbitRadius` | 轨道半径，投射物离虚拟圆心多远 |
| `ModOrbitAngularSpeedDegrees` | 每秒旋转多少度，负数可以反向旋转 |
| `ModOrbitPhaseOffsetDegrees` | 初始相位偏移 |
| `ModOrbitPlaneTiltDegrees` | 同批投射物轨道面错开的基础角 |

### 5.3 `CastModifierState.cs`

`CastModifierState.Apply()` 定义轨道修正如何叠加：

```text
OrbitRadius：取最大值
OrbitAngularSpeedDegrees：相加
OrbitPhaseOffsetDegrees：相加
OrbitPlaneTiltDegrees：取绝对值更大的值
```

为什么这样设计：

- 半径如果相加，多个轨道修正很容易让火球飞到很远，失控；
- 角速度相加直观，多个旋转修正可以让投射物转得更快；
- 相位相加直观，用来做起始角偏移；
- 轨道面倾斜取最大绝对值，避免叠加后轨道面过度翻转。

### 5.4 `CastEvaluator.cs`

`CastEvaluator` 的核心职责不变：

```text
读取法杖序列
遇到 Modify 就更新 mods
遇到 Emit 就 BakeEmit
```

这次只是让 `BakeEmit()` 多写入轨道字段：

```text
mods.OrbitRadius
mods.OrbitAngularSpeedDegrees
mods.OrbitPhaseOffsetDegrees
mods.OrbitPlaneTiltDegrees
```

注意：`CastEvaluator` 仍然不知道场景里有没有火球，也不知道 `Rigidbody`。它只是纯解释器。

这是良好的架构边界。

### 5.5 `EmitCommand.cs`

`EmitCommand` 新增轨道快照字段。

它的意义是：

```text
这一发投射物已经被解释器算完了。
运行时只需要照着命令生成，不再重新解释法杖。
```

这让触发类和定时类 payload 也能继承轨道配置，因为 `PayloadMods` 中保存了当时的修正状态。

### 5.6 `SpellAiming.cs`

这次 `SpellAiming` 没有负责整个轨道运动，只负责两个纯数学分布：

```text
PhaseOffsetDegrees(index, count)
PlaneTiltDegrees(index, count, baseTiltDegrees)
```

它适合放在 `Game.Skills`，因为：

- 不依赖场景；
- 不需要 `MonoBehaviour`；
- 能用 EditMode tests 验证；
- 是法术规则的一部分，而不是运行时物理行为。

### 5.7 `SpellCaster.cs`

`SpellCaster` 是纯逻辑和 Unity 运行时之间的桥。

这次它新增了三步：

```csharp
float orbitPhase = cmd.OrbitPhaseOffsetDegrees + SpellAiming.PhaseOffsetDegrees(i, count);
float orbitPlaneTilt = SpellAiming.PlaneTiltDegrees(i, count, cmd.OrbitPlaneTiltDegrees);
proj.ConfigureOrbit(cmd.OrbitRadius, cmd.OrbitAngularSpeedDegrees, orbitPhase, orbitPlaneTilt);
```

为什么这里要用 `i/count`？

因为 `SpellCaster` 正在循环本次 cast 产出的所有 `EmitCommand`：

```text
第 i 发 / 总共 count 发
```

只有它知道“这是同一批里的第几颗投射物”。所以同批相位和轨道面错开适合在这里计算。

### 5.8 `ProjectileBase.cs`

这是运行时核心。

新增状态：

```csharp
private float _orbitRadius;
private float _orbitAngularSpeedDegrees;
private float _orbitAngleDegrees;
private float _orbitPlaneTiltDegrees;
private bool _orbitEnabled;
private Vector3 _orbitCenter;
private Vector3 _orbitForward;
private Vector3 _orbitRight;
private Vector3 _orbitUp;
private float _orbitCenterSpeed;
```

新增方法：

```text
ConfigureOrbit(...)
InitializeOrbit(...)
TickOrbit(...)
```

运行顺序：

```text
SpellCaster.ConfigureOrbit(...)
ProjectileBase.Init(...)
    -> InitializeOrbit(velocity)
FixedUpdate()
    -> TickOrbit(Time.fixedDeltaTime)
```

`InitializeOrbit()` 建立局部坐标系：

```text
_orbitForward = 发射方向
_orbitCenter = 当前生成位置
_orbitCenterSpeed = 初速度大小
_orbitRight / _orbitUp = 垂直于 forward 的旋转平面轴
```

`TickOrbit()` 每个物理帧更新：

```text
_orbitCenter += _orbitForward * _orbitCenterSpeed * dt
_orbitAngleDegrees += _orbitAngularSpeedDegrees * dt
offset = right*cos(angle)*radius + up*sin(angle)*radius
targetPosition = center + offset
linearVelocity = (targetPosition - currentPosition) / dt
```

这就是整个功能的运行时本质。

## 6. 与现有系统的集成关系

### 6.1 与 `Multicast`

轨道螺旋本身不增加投射物数量。

```text
[轨道螺旋] [火球]
```

只产生一颗轨道火球。

```text
[轨道螺旋] [三重射击] [火球] [火球] [火球]
```

才产生三颗轨道火球。

这说明：

```text
Multicast 决定数量。
Orbit Modify 决定每颗投射物怎么飞。
```

### 6.2 与触发类 / 定时类

触发类、定时类的关键是 `PayloadMods`。

如果法杖是：

```text
[轨道螺旋] [触发火球] [普通火球]
```

那么：

```text
触发火球本体带轨道。
触发后释放的普通火球也能从 PayloadMods 继承轨道修正。
```

这体现了法术编程系统的一个重要设计：

```text
payload 不是重新从 Default 开始，它继承触发瞬间的 modifier snapshot。
```

### 6.3 与追踪修正

轨道和追踪都想控制速度：

```text
Orbit -> 写 Rigidbody.linearVelocity
Homing -> 写 Rigidbody.linearVelocity
```

如果两个系统同时写，最后谁生效会变得不清晰，弹道也难以预测。

所以本阶段规则是：

```text
如果 _orbitEnabled == true：
    TickOrbit()
否则：
    TickHoming()
```

也就是说：

```text
轨道优先于追踪。
```

这是 MVP 的正确取舍。后续如果要做更高级组合，可以设计“轨道圆心追踪敌人”，而不是让投射物本体同时被两个 controller 拉扯。

### 6.4 与弹跳修正

弹跳发生后：

```csharp
_orbitEnabled = false;
```

原因：

```text
弹跳改变了投射物方向。
如果继续用旧的 orbitForward 和旧圆心，火球会试图回到原来的轨道，视觉会非常怪。
```

所以本阶段规则是：

```text
弹跳前：轨道飞行。
弹跳后：关闭轨道，按反射方向继续飞。
```

这是清晰、可解释、容易调试的规则。

### 6.5 与重力修正

轨道和重力也都影响运动。

当前实现中：

```text
Rigidbody.useGravity 可以被设置。
但 TickOrbit 每个 FixedUpdate 会重新写 linearVelocity。
```

实际表现是：

```text
轨道控制优先，重力影响会被大幅覆盖。
```

这不是 bug，而是阶段性设计。后续如果想让轨道带下坠感，更合理的设计是：

```text
让 orbitCenter 受重力影响。
投射物仍然围绕下坠的 orbitCenter 旋转。
```

## 7. 踩坑与 Debug

### 7.1 容易误判成“立体散射”

最开始这个需求很容易被理解成：

```text
让三颗火球在 3D 中散开。
```

但你补充后，真正需求是：

```text
投射物围绕一个看不见的移动球面旋转。
```

这两者架构完全不同：

| 需求 | 主要改动位置 |
|---|---|
| 初始散射 | `SpellAiming` / `SpellCaster` |
| 轨道螺旋 | `ProjectileBase.FixedUpdate()` |

这也是本功能最重要的需求澄清点。

### 7.2 只分相位会退化成圆环

如果只做：

```text
0° / 120° / 240°
```

三颗火球会在同一个旋转平面上运动。

看起来是：

```text
一个圆环里三颗火球转圈。
```

为了解决这个问题，增加了：

```text
PlaneTiltDegrees(index, count, baseTiltDegrees)
```

让不同投射物的旋转平面错开。

### 7.3 发射方向接近世界 Up 时坐标系可能退化

`Quaternion.LookRotation(forward, Vector3.up)` 在 `forward` 接近 `Vector3.up` 时可能不稳定，因为 forward 和 up 太接近。

所以实现里做了判断：

```csharp
Vector3 upSeed = Mathf.Abs(Vector3.Dot(_orbitForward, Vector3.up)) > 0.95f
    ? Vector3.forward
    : Vector3.up;
```

含义：

```text
如果发射方向几乎朝上，就不要继续用世界 Up 当参考上方向，改用 Vector3.forward。
```

这是 3D 空间中非常常见的坐标系退化问题。

### 7.4 和 homing 的速度写入冲突

如果在同一帧中：

```text
TickOrbit 写 linearVelocity
TickHoming 也写 linearVelocity
```

那么弹道语义会混乱。

解决方式：

```csharp
if (_orbitEnabled)
    TickOrbit(Time.fixedDeltaTime);
else
    TickHoming(Time.fixedDeltaTime);
```

先定义清晰优先级，而不是让两个系统抢控制权。

### 7.5 轨道半径和角速度调参

常见现象：

| 现象 | 可能原因 | 调整 |
|---|---|---|
| 看起来像直线火球 | `ModOrbitRadius` 太小 | 增大半径 |
| 火球绕得太乱 | `ModOrbitAngularSpeedDegrees` 太大 | 降低角速度 |
| 三颗火球像一个平面圆环 | `ModOrbitPlaneTiltDegrees` 为 0 或太小 | 增大 plane tilt |
| 火球出膛后跳得太开 | 半径太大 | 降低半径 |
| 轨道火球不追踪 | 当前设计为轨道优先 | 不是 bug |
| 弹跳后不再轨道 | 当前设计为弹跳后关闭轨道 | 不是 bug |

## 9. 大厂面试 Q&A

### Q1：为什么把轨道螺旋做成 `Modify`，而不是做一个新的火球？

回答：

因为它改变的是“后续投射物的飞行方式”，不是定义一种新的投射物内容。做成 `Modify` 后，它可以作用于普通火球、触发火球、定时火球，甚至未来的其他 projectile prefab。如果做成 `OrbitalFireball`，每种组合都要做新 prefab 或新脚本，会导致组合爆炸，不符合 Noita-like 法术编程系统的扩展目标。

### Q2：这个功能为什么需要改 `ProjectileBase`？

回答：

因为轨道螺旋不是发射瞬间的角度偏移，而是飞行过程中的持续运动控制。它需要每个 `FixedUpdate()` 推进虚拟圆心、更新旋转角、计算目标轨道点，并写入 `Rigidbody.linearVelocity`。这些都属于 projectile lifecycle，因此应该放在 `ProjectileBase`，而不是只放在 `SpellAiming` 或 `CastEvaluator`。

### Q3：为什么不用 `transform.position` 直接设置位置？

回答：

直接改 `transform.position` 会绕过一部分物理移动语义，容易影响碰撞稳定性。这里使用 `Rigidbody.linearVelocity = (targetPosition - currentPosition) / fixedDeltaTime`，让投射物仍然通过刚体速度参与 Unity Physics，同时保留 `ContinuousDynamic` 对高速投射物的防穿透效果。

### Q4：如何避免三颗投射物看起来只是绕一个圆环？

回答：

只做圆周相位是不够的。例如三发用 `0° / 120° / 240°`，它们仍在同一个平面。为了解决这个问题，我增加了 `OrbitPlaneTiltDegrees`，并用 `SpellAiming.PlaneTiltDegrees(index, count, baseTilt)` 给同批投射物分配 `0° / +35° / -35°` 这样的轨道面倾斜。这样每颗火球走的是不同倾斜角的大圆路径，视觉上更接近围绕球面旋转。

### Q5：轨道和追踪都修改速度，怎么处理冲突？

回答：

我在 MVP 阶段定义了优先级：轨道启用时，不执行 homing。代码上就是 `if (_orbitEnabled) TickOrbit(); else TickHoming();`。原因是两个系统都写 `Rigidbody.linearVelocity`，如果同时运行会让弹道不可预测。后续更高级的组合可以设计为“轨道圆心追踪敌人”，但不应该让两个 controller 同时抢投射物本体速度。

### Q6：轨道和弹跳如何组合？

回答：

弹跳发生后关闭轨道。因为弹跳会根据碰撞法线改变飞行方向，如果继续使用旧的 `_orbitForward` 和旧圆心，投射物会试图回到原轨道，视觉不合理。当前设计是弹跳前按轨道飞，弹跳后按反射速度继续飞，这个行为简单、稳定、容易解释。

### Q7：如何保证这个功能不破坏纯逻辑层？

回答：

我把轨道参数沿现有链路传递，但 `Game.Skills` 仍然只处理纯数据：`SpellDefinition` 暴露参数，`CastModifierState` 累积修正，`CastEvaluator` bake 到 `EmitCommand`，`SpellAiming` 只提供纯函数。真正的 `Rigidbody` 和 `FixedUpdate` 逻辑放在 `ProjectileBase`。这样 `Game.Skills` 不依赖场景对象，也可以继续做 EditMode tests。

### Q8：这个功能怎么测试？

回答：

纯逻辑层用 EditMode tests：测试 modifier 默认值、叠加规则、BakeEmit 是否写入 orbit 参数、payload mods 是否保留 orbit 参数、相位和平面倾斜分布是否正确。运行时层用 Play Mode 验证：单发轨道、三重轨道、触发/定时 payload、和追踪/弹跳组合时的优先级是否符合预期。

## 10. 模拟面试者完整讲解

如果我是面试者，我会这样讲这个功能：

> 我在项目里实现了一个 Noita-like 法术编程系统，其中法杖是一段从左到右解释的程序，`Emit` 负责生成投射物，`Modify` 负责改变后续投射物，`Multicast` 负责增加发射预算。轨道螺旋法术就是在这个体系下新增的一个 `Modify` 法术。

> 这个需求的背景是，Noita 是 2D 游戏，很多散射类法术只需要在平面内分裂方向。但我的项目是 3D RPG，如果只做水平散射，敌人跳一下或站在高低差位置，就可能躲过整组投射物。所以我设计了一个更适合 3D 的投射物修正：让投射物围绕一个看不见的移动圆心旋转前进。这个圆心沿玩家瞄准方向移动，投射物围绕圆心形成螺旋弹道，从而持续覆盖上下左右空间。

> 架构上，我没有做一个特殊的 `OrbitalFireball`，因为那会破坏法术组合系统，也会导致未来组合爆炸。我把它做成 `Modify`：在 `SpellDefinition` 里新增轨道半径、角速度、初始相位和轨道面倾斜；`CastModifierState` 负责从左到右累积这些修正；`CastEvaluator` 在遇到 `Emit` 时把修正 bake 到 `EmitCommand`；`SpellCaster` 负责实例化 projectile，并根据同批投射物的 index/count 计算不同的相位和轨道面；最后 `ProjectileBase` 在 `FixedUpdate` 中执行真正的轨道运动。

> 实现时，我用数学轨道控制而不是物理力模拟。每颗投射物保存一个虚拟圆心 `_orbitCenter`、前进方向 `_orbitForward`、轨道半径、角速度和当前角度。每个物理帧圆心沿发射方向前进，角度根据角速度增加，然后通过 `right*cos(angle)+up*sin(angle)` 算出相对圆心的偏移，得到目标轨道点。为了保留物理碰撞，我没有直接设置 `transform.position`，而是通过 `Rigidbody.linearVelocity = (targetPosition - currentPosition) / fixedDeltaTime` 驱动投射物。

> 另外，单纯给三颗火球 `0° / 120° / 240°` 的相位还不够，因为它们仍然会在同一个旋转平面里，看起来只是绕一个圆环转。所以我额外加入了 `OrbitPlaneTiltDegrees`，通过 `SpellAiming.PlaneTiltDegrees` 给同批投射物分配不同轨道面，比如三发是 `0° / +35° / -35°`。这样视觉上更像围绕一个移动球面旋转，而不是一个平面圆环。

> 在和其他修正组合时，我明确了优先级。轨道和追踪都会写 `Rigidbody.linearVelocity`，所以 MVP 阶段轨道优先，启用轨道时不执行 homing。弹跳发生后关闭轨道，因为碰撞反射已经改变了飞行方向，如果继续沿旧圆心运动会很怪。重力也会被轨道速度控制部分覆盖，后续如果要让它更自然，可以让虚拟圆心受重力影响，而不是直接让 projectile 本体同时被重力和轨道控制。

> 这个功能的价值不只是一个视觉弹道，而是验证了法术编程系统的扩展能力。新增一个复杂修正时，我仍然遵守现有架构：纯数据层可测试，运行时桥接层只负责配置，投射物生命周期层负责实际物理运动。这样后续继续加穿透、分裂、延迟爆炸、轨道圆心追踪等功能时，也能沿同一条链路扩展，而不是为每种组合写特殊 case。

## 11. 后续可扩展方向

当前版本是 MVP，但已经留下了清晰扩展方向：

1. **轨道圆心追踪敌人**  
   不是让投射物本体 homing，而是让 `_orbitCenter` 朝目标偏移，这样能保留轨道视觉。

2. **轨道中心受重力影响**  
   让 `_orbitCenter` 下坠，投射物围绕下坠中心旋转，可形成“螺旋坠落”效果。

3. **轨道持续时间**  
   轨道只持续一段时间，到期后投射物按当前速度直线飞出。

4. **轨道半径渐变**  
   半径随时间变大或变小，可做收束/扩散弹道。

5. **反向旋转法术**  
   使用负 `ModOrbitAngularSpeedDegrees`，让弹道反向旋转。

这些都可以继续沿：

```text
SpellDefinition -> CastModifierState -> EmitCommand -> SpellCaster -> ProjectileBase
```

这条链路扩展。
