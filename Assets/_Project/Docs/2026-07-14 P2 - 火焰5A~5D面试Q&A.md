## 阅读说明：不要把答案背成固定模板

面试官想判断的通常不是“你是否记得某个 API 名字”，而是你能否把最终画面还原成数学、GPU Pipeline 与 Unity 数据流。例如，只说“`smoothstep` 可以柔化边缘”不够，还应该能写出它怎样把输入归一化、为什么边界处导数平滑，以及它在当前火焰 Shape Mask 的哪一段使用；只说“Core 用 Additive”也不够，还应能写出 Blend Equation、解释黑色为什么是 Additive 的中性元素，并说明重叠和过曝风险。

回答时不必机械套“是什么、为什么、怎么做”三个标题。更自然的方式是先直接回答面试官真正问的结论，再按需要展开定义、公式、当前项目实现、取舍与边界。如果面试官在中途打断，就先回答追问，不要强行念完准备好的整段。

# 第一组：项目介绍与难题拆解

## Q1 ⭐：先用两三分钟介绍一下你的程序化火焰，不要逐行念代码

**面试官：** 你简历里写了自研 Fire Shader 和 Particle System。先完整介绍一下你实现了什么。

**面试者：**

我实现的是 Unity 6.3、URP 17.3 下的一套风格化程序化火焰，目前完成了 P2 的 5A 到 5D。它不是体积燃烧或真实流体模拟，而是把“单片火焰的像素外观”和“多片火焰的生命周期”拆开处理：GPU Shader 决定每张 Billboard Quad 内哪些 Fragment 属于火焰、颜色和 Alpha 是多少；Unity Particle System 决定这些 Quad 在哪里出生、怎样上升、何时缩小和消失。

Shader 部分先利用 Quad 的 UV 构造下宽上窄的轮廓。横向上把 `uv.x` 从 `[0,1]` 映射到 `[-1,1]`，计算到中线的距离；纵向上用 `pow(uv.y,ShapePower)` 控制宽度随高度收窄，再用 `smoothstep` 做左右柔边、底部淡入和顶部淡出。动画部分手写两层二维 `Value Noise`：低频层主要移动火焰中线，高频层主要扰动局部宽度；采样坐标随 `_Time.y` 向下移动，所以屏幕上的特征向上流动。扰动再乘 `y²`，让根部稳定、顶部活跃。

渲染上我拆成 Body 和 Core 两个 Shader。Body 使用 `Blend SrcAlpha OneMinusSrcAlpha` 保留橙红外焰；Core 使用 `Blend SrcAlpha One` 增加黄白高温亮度。两者 Include 同一个 `ElementFireCore.hlsl`，复用 Hash、Noise、Shape 和 Temperature Mask，避免两份轮廓数学逐渐不一致。Additive Core 使用更窄的 Material 参数，并在 Transparent Queue 中比 Body 稍后绘制。

Particle 部分有三层。`PS_FireBody` 负责外焰密度、尺寸和生命周期；`PS_FireCore` 是 Body 的 `Birth Sub Emitter`，每个 Body 出生时生成一个更小、更短命的 Core，因此焰芯与外焰一一对应；`PS_FireSparks` 独立发射少量高速粒子，使用 Additive 与 `Stretched Billboard` 表现向上的火星。Particle 的 `Color over Lifetime` 通过 `COLOR` Vertex Stream 进入 Shader，控制每个粒子的淡入淡出。

我会明确说明当前边界：Steam、正式 `EV_FireArea` Prefab、反应事件接入以及 Frame Debugger/Profiler Gate 还没有完成；当前也没有体积密度、燃料传播、热折射、动态光照或真实黑体辐射。

**面试官追问：** 这项实现里，最能体现你能力的地方是什么？

**面试者：**

我觉得不是最后出现了一团橙色火，而是我能把它拆成可验证的数据链，并解释每层为什么存在。比如 Core 与 Body 最初错位，我没有继续调两个 Box Shape 去碰概率，而是确认 Shader 单独正常、Blend 能显示，最后定位到两套独立 Particle System 的随机出生不共享，改成 Birth Sub Emitter 从数据关系上解决。再比如 Additive Fog 不是直接复制 Body 的 `MixFog`，因为 Additive 的中性元素是黑色，所以远处要向黑色衰减。这些细节体现的是图形学、引擎和 Debug 思维的结合。

**学习复盘：**

- 开场先建立“效果、核心数学、引擎组织、诚实边界”四部分。
- 不要把 Material 参数列表当项目介绍。
- 不要把“程序化”自动等同于“物理真实”或“性能更快”。

## Q2 ⭐：你是怎样把“做一团火”拆成 5A～5D 的？

**面试官：** 火焰是一个很模糊的目标，你为什么按照这个顺序开发？

**面试者：**

我先从最终画面反向问“玩家为什么会把它识别成火”，得到几类视觉证据：下宽上窄的柔和轮廓、向上的连续运动、根部稳定顶部摆动、橙红主体、黄白高温核心，以及少量快速逸出的火星。然后把每个证据改写成有输入和输出的小问题。

5A 只回答“怎样在一张 Quad 上得到火焰 Shape Mask”，输入只有 UV 和宽度参数，输出只有 `[0,1]` Mask，不加入 Time、Noise 或 Particle。5B 在这个基线上加入稳定 Hash、Value Noise 和 Moving UV，输出 Center Offset、Width Offset 与 Temperature Mask。5C 不再改轮廓数学，而是讨论同一 Shape 怎样通过 Alpha 和 Additive 两种 Blend 承担外焰与高温核心。5D 最后才处理多片火焰的位置、数量、生命周期和配对关系。

这个顺序与依赖关系一致：动画建立在正确轮廓上，颜色分层建立在正确动态 Mask 上，Particle 组合又建立在单片 Shader 已经可控的前提上。每个 Gate 都能单独灰度输出或单独播放，因此画面出错时能判断属于 Shape、Noise、Blend 还是 Particle，而不是同时猜几十个参数。

**面试官追问：** 如果让你重做，还会保留这些 Gate 吗？

**面试者：**

会，而且我会更早固定每个 Gate 的诊断输出。例如 5A 固定 `shapeMask.xxx`，5B 固定 `noiseA/noiseB/combinedNoise`，5C 分别只开 Body/Core，5D 每次只添加一个 Particle Layer。复杂 VFX 很容易靠“看起来差不多”继续堆叠，最后性能和视觉问题都无法归因；小 Gate 是降低搜索空间，不是拖慢进度。

**学习复盘：**

- 需求拆解题要把“视觉描述”转成“输入 → 中间量 → 输出”。
- 开发顺序应体现依赖，而不是简单按文件名排列。

## Q3：这是真实火焰模拟吗？如果面试官说它只是几张假贴片，你怎么回答？

**面试官：** 你的火没有燃料、氧气和流体求解，本质不就是假效果吗？

**面试者：**

是视觉近似，我不会把它描述成真实燃烧。真实燃烧通常至少涉及流体速度、压力、密度、温度、燃料与氧化剂浓度，还可能要处理对流、扩散、浮力和化学反应。流体部分可能求解 Navier–Stokes，燃烧部分还要有额外反应模型；体积渲染则可能对密度场做 Ray Marching。当前方案没有保存这样的体素状态，也没有跨帧求解守恒方程，所以不能叫 Simulation。

但实时渲染的目标不是无限接近物理，而是在目标镜头和预算下提供足够强的视觉线索。我的需求是第三人称 RPG 中的局部元素火区，常见观察距离下，程序化 Billboard 能以较低资产依赖提供外形、上升、温度层次和火星反馈，并且容易被 Gameplay 状态强度驱动。它依然要求我理解 UV、Interpolation、Noise、Blend、Depth、Transparent Sorting、Particle Lifecycle 和 GPU Profiling。

如果需求变成近距离电影级火焰，我会重新评估 Volume Texture、Flipbook、VFX Graph 或离线 Fluid Simulation；如果需求变成火会沿 Cell 燃料传播，则需要 Gameplay/Simulation Grid，再把密度和温度场映射到 Rendering。不能用继续加几个 Noise 参数代替真正的状态模拟。

**面试官追问：** 那“假”效果的技术价值怎么证明？

**面试者：**

我会证明三件事：第一，近似是否覆盖目标镜头中的关键视觉证据；第二，输入与输出是否可解释、可调试，而不是黑盒；第三，成本是否被目标平台接受。真实与否不是唯一评价标准，很多工业实时 VFX 都是 Flipbook、Billboard、Mesh 和 Shader 的组合，关键是知道近似省略了什么、什么时候会穿帮，以及升级路径是什么。

**学习复盘：**

- 主动区分 `Simulation` 与 `Shading/Presentation`。
- 承认近似不会减分，夸大成真实物理反而容易被追问击穿。

## Q4 ⭐：为什么水主要靠一个 Shader，而 Fire 还需要多个 Particle Layer？

**面试官：** 你之前的水面主要是一张 Plane，为什么火不能也只放一张 Quad？

**面试者：**

差异在于是否存在稳定的几何载体。水池通常可以近似成一个连续水面 Mesh，Shader 只需对这个固定表面的每个 Fragment 改颜色、Normal、Depth 和 Fresnel。火焰没有稳定表面，它的宏观轮廓由许多火舌不断出生、上升和消亡构成；单张 Quad 内部的 Noise 只能改变贴片内部像素，不能自动产生多个独立生命周期，也不能覆盖一个较宽火区而不暴露矩形边界。

所以我把两种尺度分开。Shader 处理**片内空间**：某个 UV 上是不是火、颜色和 Alpha 是多少；Particle System 处理**片间空间与时间**：有多少张片、中心在哪里、速度多大、活多久。Body/Core/Sparks 又是不同视觉频率：Body 给大尺度主体，Core 给局部高亮，Sparks 给高速小细节。让一个 Shader 同时承担所有尺度，会导致参数耦合，也难以为 Sparks 使用 `Stretched Billboard` 或为 Core 建立一一配对。

**面试官追问：** 为什么不把三层都放进同一个 Particle Material 的一个 Pass？

**面试者：**

同一个粒子只有一套 Position、Size、Lifetime 和 Renderer Mode，无法让外焰寿命长、Core 更小更短、Sparks 高速拉伸。Blend 还是 Pass/Draw 级 Render State，不能在同一 Fragment 中按像素随意把一部分设成 Alpha、另一部分设成 Additive。拆层增加了 Draw 和 Overdraw，但换来职责、生命周期和混合方式可独立控制，适合当前低粒子数量的局部火区。

# 第二组：Graphics Pipeline、Coordinate Space 与基础数学

## Q5 ⭐：`Mesh`、`Shader`、`Material`、`Particle System` 和 `ParticleSystemRenderer` 分别做什么？

**面试官：** 这是基础题。不要把 Shader 和 Material 混在一起。

**面试者：**

`Mesh` 保存几何数据，包括 Vertex Position、UV、Normal 和 Triangle Index。当前单片火焰最终由一张 Quad 承载，UV 提供 `[0,1]²` 局部坐标。

`Shader` 定义 GPU 程序和 Render State。`ElementFireBody.shader` 与 `ElementFireAdditive.shader` 声明 Properties、Queue、Blend、ZWrite/ZTest、Vertex/Fragment Entry；公共 `.hlsl` 定义 Shape 和 Noise 数学。

`Material` 是 Shader 的参数实例。Body、Core、Sparks 可以引用不同 Material，从而拥有不同 Color、Width、Intensity 和 `_UseVertexColor`，但并不是每个 Material 都复制一份 Shader 源码。

`Particle System` 负责粒子模拟数据，例如 Birth Time、Position、Velocity、Lifetime、Size 和 Color。它不知道 Shape Mask 的像素公式。

`ParticleSystemRenderer` 把活着的 Particle 组织成 Billboard Quad，选择 Vertical 或 Stretched Render Mode，绑定 Material，并把 Particle Color 等 Vertex Stream 送到 GPU。可以概括为：Particle System 生成“实例状态”，Renderer 把它变成 Draw Data，Shader 决定最终像素。

**面试官追问：** 修改 Material 参数和修改 Shader 源码有什么工程区别？

**面试者：**

修改普通 Material Property 主要更新常量和序列化资产，不改变程序结构；修改 Shader 源码会触发 Import/Compile，并影响所有引用它的 Material。如果 Property 被 Keyword 驱动，可能切换 Shader Variant；当前大部分连续参数只作为 CBUFFER Float/Color，不需要为每个数值生成 Variant。

## Q6 ⭐：从一张 Fire Billboard 的一个顶点开始，讲到屏幕 Pixel 是怎样产生的

**面试官：** 沿 Graphics Pipeline 讲完整一些。

**面试者：**

CPU 侧 Unity 先更新 Particle Simulation，`ParticleSystemRenderer` 根据每个 Particle 的中心、Size、Rotation 和 Billboard Mode 构造或提交对应顶点数据。URP 做 Camera Culling、排序和批次组织后提交 Draw。GPU 从 Vertex Buffer 读取 `POSITION`、`TEXCOORD0` 和 `COLOR`。

Vertex Shader 调用 `TransformObjectToHClip`，概念上完成：

```text
p_world = M_model × p_object
p_view  = M_view  × p_world
p_clip  = M_proj  × p_view
```

Clip Space Triangle 经过 Clipping，随后做 Perspective Divide：

```text
p_ndc = p_clip.xyz / p_clip.w
```

Viewport Transform 把 NDC 映射到屏幕。Primitive Assembly 根据 Index 组成 Triangle，Rasterization 判断哪些 Sample 被覆盖，并插值 UV、Color 和 Fog Factor。Fragment Shader 对候选 Fragment 计算两层 Value Noise、Shape Mask、Temperature Mask、RGB 和 Alpha。之后执行 Depth Test；通过的 Fragment再按当前 Blend State 与 Framebuffer 的 Destination Color 合成。最终 Camera Color 还可能经过 Bloom、Tone Mapping 等 Post-processing 才显示为屏幕 Pixel。

**面试官追问：** Fragment 和 Pixel 是同一个概念吗？

**面试者：**

不是严格等同。Fragment 是 Rasterization 为某个 Primitive/Sample 产生的候选着色工作；它可能被 Depth/Stencil 丢弃，同一屏幕 Pixel 也可能因为多个透明层、MSAA Sample 或多次 Draw 接收多个 Fragment。当前火焰 Transparent、ZWrite Off，所以多个 Body/Core Billboard 重叠时，同一 Pixel 会反复执行 Fragment Shader 和 Blend，这正是 Overdraw 成本。

**学习复盘：**

- 高频追问包括 Clip Space、Perspective Divide、Rasterization、Fragment 与 Pixel 的区别。
- 不要把 `UniversalForward` Pass 名字误认为自动完成所有光照。

## Q7：为什么 Shape 和 Noise 主要放在 Fragment Shader，不放 Vertex Shader？

**面试官：** Vertex 数量更少，把 Noise 放 Vertex 不是更便宜吗？

**面试者：**

从执行次数看通常是，但当前每张 Billboard 只有四个 Vertex。如果在四个角上计算 Shape/Noise，再由 Rasterizer 插值，三角形内部只能得到很低频的线性变化，无法画出弯曲边缘、局部宽度变化和细碎明暗。我们的轮廓本身就是“这个 Fragment 到 y 对应半宽的距离”，天然是逐 Fragment 判断。

Vertex Stage 当前只负责坐标变换和转发 UV/Color。Fragment Stage 用连续 UV 在 Quad 内构造高分辨率 Mask，因此轮廓精度随屏幕覆盖而变化，而不是受 Mesh 顶点密度限制。代价是粒子靠近 Camera 或大量重叠时 Fragment ALU 与 Fill Rate 上升。

如果要做大尺度火舌弯曲，我可以在 Vertex 端加入低频位移，但四顶点 Quad 只能整体倾斜或变成简单四边形；更复杂轮廓需要增加 Mesh 细分。当前选择 Fragment Mask 是质量和复杂度之间的取舍。

**面试官追问：** Alpha 很低的 Fragment 会不会很便宜？

**面试者：**

不会因为最终 Alpha 小就自动免费。Fragment Shader 通常先执行完才能知道 Alpha，再做 Blend；除非使用 Alpha Clip/Discard 并且硬件路径允许提前退出，但那会失去柔边，还可能影响 Early-Z 和执行一致性。透明低 Alpha 仍可能支付完整 Noise 与 Blend 成本。

## Q8 ⭐：当前实现涉及哪些 Coordinate Space？为什么不能混着算？

**面试官：** 说说 Shader 和 Particle 两边的空间。

**面试者：**

Shader 顶点输入是 `Object Space positionOS`，通过 Model、View、Projection 变换到 Clip Space `positionCS`。火焰轮廓和 Noise 主要在 UV Space 中计算；UV 是表面参数空间，不是世界米。Fog Factor 根据 Clip Depth 计算，最后颜色在 Framebuffer/Color Space 中混合。

Particle System 还有 Simulation Space。`Local` 表示 Position/Velocity 相对 Particle System Transform，移动父物体时现有粒子可能随系统一起移动；`World` 表示出生后的粒子以世界坐标模拟，不再跟随父 Transform。Core 作为 Sub Emitter 时，我们需要明确 Parent Birth Position 与 Inherit Velocity 的空间，否则相同数值在 Local/World 下会产生不同方向。

向量或位置只有在同一空间才有可比较意义。例如 Local Y 的 `(0,1,0)` 经过旋转后不一定是 World Up；如果火区 Transform 倾斜，Local Velocity Y 会沿火区局部上方而不是世界上方。当前实验 Transform 没有复杂旋转，所以 Local Y 与 World Y 对齐，但正式 Prefab 若允许任意旋转，应明确设计“火焰跟随表面法线”还是“永远受世界浮力向上”。

**面试官追问：** Position 和 Direction 的矩阵变换有什么区别？

**面试者：**

齐次坐标中 Position 通常写成 `(x,y,z,1)`，会受到矩阵平移；Direction 写成 `(x,y,z,0)`，不受平移。Normal 还不能在非均匀缩放下直接乘普通 Model Matrix，通常需要 Inverse Transpose。当前 Fire Shader 没有参与 Lighting 的 Normal，但这个区别仍是理解 Object/World 变换的基础。

## Q9 ⭐：UV 是什么？为什么 `uv.x*2-1` 能构造火焰中线坐标？

**面试官：** 从定义和公式讲。

**面试者：**

UV 是绑定在 Mesh Vertex 上的二维表面参数。标准 Quad 四角通常是 `(0,0)`、`(1,0)`、`(0,1)`、`(1,1)`；Rasterizer 在三角形内部做透视正确插值，所以每个 Fragment 都能得到连续 UV。

当前火焰约定 `uv.y=0` 是底部、`uv.y=1` 是顶部，`uv.x=0.5` 是中线。为了让左右两侧对称，我做线性映射：

```text
xCentered = 2u - 1
```

因为：

```text
u=0   → -1
u=0.5 →  0
u=1   →  1
```

然后计算：

```text
d = |xCentered - CenterOffset|
```

`d` 就是当前 Fragment 到火焰中线的归一化横向距离。与当前高度的 `halfWidth` 比较，就能判断它在轮廓内部、柔边区还是外部。

**面试官追问：** UV Space 有什么限制？

**面试者：**

它没有世界单位。Particle Size 放大时，相同 Noise 格子和 Edge Softness 也一起放大；不同 Mesh UV 密度会让世界空间纹理频率不一致。当前每个粒子都是相同拓扑 Quad，所以问题可控。如果未来复用到不规则 Mesh，可能改用 Object/World Position 采样，或显式传入尺度补偿。

## Q10 ⭐：请解释 `lerp`、`saturate`、`smoothstep`、`pow`，以及它们在火焰中的作用

**面试官：** 不要只说 API 效果，写出核心公式。

**面试者：**

`lerp` 是线性插值：

```text
Lerp(A,B,t) = A(1-t) + Bt
```

`t=0` 选择 A，`t=1` 选择 B。火焰用它在 Base/Tip Width、Bottom/Top Color、BaseHeat/Noise、白色/Particle Vertex Color 之间连续混合。

`saturate(x)` 等价于 `clamp(x,0,1)`。它把 Mask、Alpha 和权重限制在合法区间，防止 Lerp 外插或负 Alpha。

`smoothstep(e0,e1,x)` 可以写成：

```text
t = saturate((x-e0)/(e1-e0))
result = t²(3-2t)
```

它在两个边界间从 0 平滑过渡到 1，且三次 Hermite 曲线在 t=0/1 的一阶导数为 0。当前用于横向柔边、底部淡入、顶部淡出，也用于 Value Noise 的局部坐标平滑。

`pow(x,p)=x^p` 用来重新分布 `[0,1]` 值。Shape 中 `p>1` 时 `y^p<y`，火焰中下部更久保持 BaseWidth，到顶部才快速变窄；Temperature 中 `Contrast>1` 会压低中间值，让高热区域更集中。

**面试官追问：** 为什么不用大量 `if`？

**面试者：**

连续 Mask 更容易获得柔边、连续调参和灰度 Debug，也常能避免 Wave/Warp 内动态分支发散。不是说 GPU 永远不能用 `if`，而是当前形状本来就是连续场，用 `lerp/smoothstep` 更符合问题表达。`pow` 也有成本，若 Profile 证明昂贵且指数固定，可以评估乘法近似或查表，但不能先优化掉可读性。

---

## Q11 ⭐：现场推导静态火焰 Shape Mask。它算不算 SDF？

**面试官：** 从一个 Fragment 的 UV 开始推导。

**面试者：**

先记 `y=saturate(uv.y)`，横向中心坐标为：

```text
x = 2uv.x - 1
d = |x - CenterOffset|
```

高度重映射：

```text
y_s = y^ShapePower
```

该高度的半宽：

```text
w(y) = saturate(
    lerp(BaseWidth, TipWidth, y_s) + WidthOffset
)
```

横向 Mask：

```text
inner = max(w-EdgeSoftness,0)
HorizontalMask = 1-smoothstep(inner,w,d)
```

底部与顶部：

```text
BottomMask = smoothstep(0,BaseFade,y)
TopMask = 1-smoothstep(TipFadeStart,1,y)
```

最后：

```text
ShapeMask = saturate(
    HorizontalMask × BottomMask × TopMask
)
```

它有一点“隐式形状函数”的味道，因为比较了横向距离 `d` 与高度相关宽度 `w(y)`，但我不会称它为严格 SDF。真正 Signed Distance Field 的值应该近似表示到二维边界的带符号欧氏最短距离，梯度长度通常接近 1；当前 `d-w(y)` 没有考虑边界斜率和顶部/底部组合后的真实最短距离，Softness 也是 UV 横向宽度，所以不同斜率处并非均匀距离柔边。

**面试官追问：** 如果要变成更正规的 SDF 有什么好处？

**面试者：**

可以更稳定地控制等宽 Outline、Glow、Soft Edge 和形态布尔运算，也容易用 `fwidth` 做抗锯齿。但要为弯曲火焰轮廓得到准确 SDF 需要更严谨的解析距离或预计算纹理，当前风格化 Mask 已满足需求。面试中我会区分“类似距离的控制量”和“严格 SDF”。

# 第三组：Hash、Value Noise、流动与 Temperature Mask

## Q12 ⭐：Shader 里的 Hash 是什么？为什么不能每帧调用普通随机数？

**面试官：** 解释你这个 `Hash21` 的输入输出与稳定性。

**面试者：**

`Hash21` 表示输入二维坐标、输出一个标量。当前函数通过乘常数、`frac`、`dot` 和乘法，把一个二维格点稳定映射到 `[0,1)`。它不是密码学 Hash，也不是均匀性经过严格证明的高质量随机数，只是图形学里低成本的伪随机打散函数。

关键性质是确定性：同一个格点每次返回相同值。Shader Fragment 本身没有适合这种用途的可变全局 RNG 状态；即使能每帧生成独立随机值，图案也会在时间上完全不相关，表现成闪烁。我们的动画来自采样坐标连续移动：空间随机场保持不变，观察位置沿场移动，所以相邻帧相关。

当前核心近似是：

```hlsl
p = frac(p * constants);
p += dot(p,p + constant);
random = frac(p.x * p.y);
```

这些常数是经验 Seed，不是燃烧参数。它还会受 Float 精度和周期性限制，坐标极大时可能出现重复或精度退化，所以当前只在小范围 UV 中使用。

**面试官追问：** Hash 和 Noise 是同一个东西吗？

**面试者：**

不是。Hash 给离散输入一个不连续伪随机值；Noise 通常要在空间中连续。Value Noise 是在格点取得 Hash 值，再对格内位置做平滑插值。把 Hash 直接当 Noise 输出，会看到明显格子跳变。

## Q13 ⭐：从头推导二维 Value Noise，为什么需要四个角点？

**面试官：** 假设我让你白板写出来。

**面试者：**

对采样位置 `p=(x,y)`，先拆成整数格子和格内坐标：

```text
i = floor(p)
f = frac(p)
```

二维格子有四个角：

```text
a = Hash(i + (0,0))
b = Hash(i + (1,0))
c = Hash(i + (0,1))
d = Hash(i + (1,1))
```

若只取最近角点，值会在格子边界跳变。先把局部坐标平滑：

```text
u = f²(3-2f)
```

然后做 Bilinear Interpolation：

```text
bottom = lerp(a,b,u.x)
top    = lerp(c,d,u.x)
value  = lerp(bottom,top,u.y)
```

之所以是四个角，是因为二维线性插值需要沿 X 在上下两条边分别插值，再沿 Y 在两条结果之间插值。推广到三维 Value Noise 会有立方体八个角。

**面试官追问：** `lerp` 本身已经连续，为什么还要平滑 `f`？

**面试者：**

直接用 `f` 做线性插值时，值本身在边界可以连续，但进入相邻格子后使用另一组随机角值，斜率通常突变。Hermite `f²(3-2f)` 在 0 和 1 处导数都是 0，让格子边界两侧的一阶导数更容易衔接，减少棋盘状折线感。它通常可视为 C1 连续，但二阶导数仍可能不连续；更高阶平滑如 Quintic `6f^5-15f^4+10f^3` 可以获得更平滑导数，成本也更高。

---

## Q14：Value Noise、Gradient/Perlin Noise、Noise Texture 有什么区别？

**面试官：** 你为什么选 Value Noise？

**面试者：**

Value Noise 在格点保存随机标量，再插值标量值。Gradient Noise，也就是经典 Perlin 思路，在格点保存伪随机 Gradient，计算采样点到角点的 Offset 与 Gradient 的 Dot Product，再插值这些贡献，因此方向性和频谱特征不同，通常比 Value Noise 少一些块状感。

Noise Texture 是把随机场预计算在纹理里，运行时做 Texture Sample。它把 ALU 换成 Texture Fetch、Bandwidth 和显存，并能由美术直接制作或压缩；程序化 Value Noise 没有外部纹理、连续可调，但每个 Fragment 要计算四个 Hash 和插值。哪个更快取决于目标 GPU、Cache、分辨率和 Overdraw，不能只凭“没有采样”判断。

当前选 Value Noise 一方面是为了学习完整生成过程，另一方面火焰是小面积粒子且只需要风格化连续扰动。若 5F 在多火区场景证明 ALU 成本过高，我会比较自制 Noise/Flipbook Texture，而不是坚持程序化一定更高级。

**面试官追问：** 纹理会不会出现平铺重复？

**面试者：**

会，有限尺寸 Texture 通过 Repeat 必然周期性平铺。可以用两层不同 Scale/Rotation、Texture Atlas、蓝噪声扰动或更大纹理降低重复；程序化 Hash 也不是无限无周期，Float 精度与函数结构同样可能产生相关性。两者都有重复问题，只是表现形式和成本不同。

---

## Q15 ⭐：为什么代码里 UV 减去 `Speed×Time`，视觉却向上运动？

**面试官：** 不要只说“Panning 方向相反”，推导一下。

**面试者：**

当前采样是：

```text
N((y - s·t) × scale)
```

假设 Noise 中某个特征位于固定采样坐标 `q0`。屏幕 UV 高度 `y` 想采到它，需要：

```text
(y-s·t) × scale = q0
```

所以：

```text
y = q0/scale + s·t
```

随着 `t` 增加，屏幕上看到该特征的位置 y 增大，也就是从 Quad 底部向顶部移动。因此“采样窗口向负 Y 移动”对应“图案在表面向正 Y 移动”。这与 Camera 移动时背景看起来反向移动是相似的相对运动关系。

**面试官追问：** Scale 会不会改变这个视觉速度？

**面试者：**

按当前写法 `(uv-speed×time)×scale`，对固定特征推导后 `y=q0/scale+speed×time`，所以 UV 表面上的平移速度仍是 `speed`，Scale 主要改变特征间距。如果写成 `uv×scale-speed×time`，视觉速度会变成 `speed/scale`。乘法顺序会改变参数语义，所以要结合公式而不是只看变量名。

## Q16：为什么使用两层 Noise？这算 fBM 吗？

**面试官：** 你代码里 A 权重 0.65、B 权重 0.35，这是什么依据？

**面试者：**

两层主要为了解耦大尺度摆动和小尺度边缘破碎。Noise A Scale 较低、权重更高，用中心化结果驱动 `centerOffset`；Noise B Scale 较高，驱动 `widthOffset`。第二层还镜像 X，并加 `(3.17,5.31)` 偏移，避免两层在相同格点采样而高度相关。权重 0.65/0.35 是风格化调参，让大结构主导，不是物理常数。

严格 fBM 通常表示多 Octave 叠加：

```text
fBM(p) = Σ amplitude_i × Noise(frequency_i × p)
frequency_{i+1} = frequency_i × lacunarity
amplitude_{i+1} = amplitude_i × gain
```

当前只有两层，而且它们不仅合并为 Combined Noise，还分别承担 Center 和 Width 职责，所以更准确地说是“双层程序化 Value Noise”，不是严格、通用的 fBM 实现。

**面试官追问：** 为什么不是层数越多越真实？

**面试者：**

层数增加会增加 Fragment ALU、寄存器压力和调参维度，高频细节在远处或小粒子上可能完全看不见，还可能造成闪烁。应根据屏幕尺寸和视觉频率选择；当前几十像素到几百像素的火焰片，两层已经能区分大摆动和细边缘，更多 Octave 要靠 Profiler 和画质 A/B 决定。

## Q17 ⭐：为什么扰动乘 `y²`？如果换成 `y`、`sqrt(y)` 或 `smoothstep` 会怎样？

**面试官：** 从曲线含义回答。

**面试者：**

当前：

```text
Influence(y)=y²
CenterOffset=(2NoiseA-1)×DistortionStrength×y²
WidthOffset =(2NoiseB-1)×DetailStrength×y²
```

在 `y=0` 时影响为 0，根部固定；`y=0.5` 时只有 0.25；`y=1` 才是完整强度。这让中下部比线性 `y` 更稳定，符合“根部附着、顶部受热流摆动更明显”的风格化观察。

如果用 `y`，中部是 0.5 强度，整片更早开始摆动；用 `sqrt(y)`，中下部影响更强，容易像整体漂浮；用更高次 `y³`，大部分区域很稳，只有顶部突然活跃。`smoothstep(a,b,y)` 可以指定从某个高度才开始增长，并在两端平滑，更适合美术想要明确静止区时使用。选择不是谁数学更高级，而是曲线是否符合目标动态。

**面试官追问：** 这是不是浮力公式？

**面试者：**

不是。浮力与密度差、重力、体积等有关，体积力常写成类似 `F_buoyancy ∝ (ρ_environment-ρ_fluid)g`。这里 `y²` 只是无状态的空间权重，不求解力、速度或温度，它是 Artistic Constraint。

## Q18 ⭐：Temperature Mask 是怎么得到的？为什么不能叫真实温度？

**面试官：** 写出公式，并说明每个参数。

**面试者：**

当前公式是：

```text
BaseHeat = 1-saturate(y)
MixedHeat = lerp(BaseHeat,CombinedNoise,HeatNoiseWeight)
TemperatureMask = saturate(MixedHeat)^HeatContrast
```

`BaseHeat` 给一个稳定的底热顶冷梯度；`CombinedNoise` 代表随时间上升的局部变化；`HeatNoiseWeight=0` 时完全按高度，`=1` 时完全按 Noise；`HeatContrast>1` 会压低中间灰度，让高值区更集中。Body 用它向 `_HotColor` 混合，Core 用它调制亮度与 Alpha。

我不把它叫真实温度，因为它没有单位，不是 Kelvin，也没有由能量、燃料或热传导求解。真实黑体辐射的光谱分布与温度有关，简化表达涉及 Planck Law；渲染里还要把光谱积分到 RGB、考虑曝光和 Tone Mapping。当前只是 `[0,1]` 的视觉权重，甚至“底部更热”的假设也取决于火焰类型和风格。

**面试官追问：** `pow` 的 Contrast 为什么会让高值集中？

**面试者：**

对 `x∈(0,1)`，若 `p>1`，则 `x^p<x`。例如 `0.5²=0.25`，中间值被压低，而 0 和 1 端点保持不变，因此只有原本接近 1 的区域仍然明显。若 `0<p<1`，例如平方根，会抬高中间值、扩大热区。

# 第四组：Blend、Depth、Fog、HDR 与 Shader 工程

## Q19：Body 的 RGB 与 Alpha 数据链分别是什么？为什么要分开理解？

**面试官：** 沿当前代码讲，不要只说“根据 Noise 变色”。

**面试者：**

Body RGB 先按高度做：

```text
HeightColor = lerp(BottomColor,TopColor,y)
```

然后：

```text
HotBlend = saturate(TemperatureMask×HotColorStrength)
TemperatureColor = lerp(HeightColor,HotColor,HotBlend)
BodyRGB = TemperatureColor×ParticleColor.rgb×ColorIntensity
```

Alpha 则是：

```text
AlphaVariation = lerp(1-AlphaNoiseStrength,1,CombinedNoise)
BodyAlpha = saturate(
    ShapeMask×GlobalAlpha×AlphaVariation×ParticleAlpha
)
```

Shape Mask 决定“哪里存在火焰”；Temperature Mask 主要决定“哪里更热”；Particle Alpha 决定“这整片火舌处于生命周期的哪个阶段”。如果把三种含义混成一条 Noise，就很难独立控制连续轮廓、内部明暗和淡入淡出。

`AlphaVariation` 最低仍是 `1-Strength`，是因为 Body 要保持主体连续。如果直接让 Alpha 乘 `CombinedNoise`，低 Noise 区可能形成大量透明孔洞，Body 就无法承担外形职责。

**面试官追问：** 为什么 Fragment RGB 还要乘 Particle Color RGB？

**面试者：**

Material Color 是整批粒子共享参数，Particle Color 是每个粒子的独立数据。乘起来后，可以用 Color over Lifetime 或随机 Start Color 给每片火舌微小差异，同时仍保留 Material 定义的温度梯度。当前主要使用 Particle Alpha，但数据链支持 RGB Tint。

## Q20 ⭐：解释 `Blend SrcAlpha OneMinusSrcAlpha`，并比较 Straight 与 Premultiplied Alpha

**面试官：** 写出 Source、Destination 和输出公式。

**面试者：**

当前 Body Fragment 输出是 Source，Framebuffer 已有颜色是 Destination。对 RGB：

```text
Cout = Csrc×Asrc + Cdst×(1-Asrc)
```

Alpha 0 时完全保留背景，Alpha 1 时完全选择火焰颜色，中间值做覆盖混合。这是 Straight Alpha，因为 Shader 输出的 RGB 没有预先乘 Alpha，Blend Stage 使用 `SrcAlpha` 再乘一次。

Premultiplied Alpha 会在 Shader 中先输出：

```text
C' = C×A
```

常配合：

```shaderlab
Blend One OneMinusSrcAlpha
```

如果 RGB 已预乘却仍用 `SrcAlpha`，会重复乘 Alpha，柔边容易变暗；如果 RGB 没预乘却使用 `One`，透明边缘颜色会贡献过多。Premultiplied 在某些发光柔边和纹理过滤场景更稳定，但要让纹理、Shader 输出和 Blend State 一致。

**面试官追问：** Alpha 是火焰的真实光学密度吗？

**面试者：**

不是，当前是 Artistic Coverage/Opacity Weight。更物理的介质透射可能参考 Beer–Lambert：`T=e^{-σd}`，再根据透射与发射积分颜色；当前没有体积厚度 `d` 和吸收系数 `σ`，所以不能把 GlobalAlpha 当真实密度。

## Q21 ⭐：解释 Additive Blend。为什么只用 Additive 做整团火不够？

**面试官：** 写公式，并解释黑色。

**面试者：**

Core/Sparks 使用：

```shaderlab
Blend SrcAlpha One
```

RGB 公式是：

```text
Cout = Csrc×Asrc + Cdst
```

Destination 不会被 `(1-A)` 压低，只是在原背景上增加 Source 贡献。若 `Csrc=0`，输出就是 `Cdst`，所以黑色是 Additive 的中性元素；重叠越多，结果越亮。

只用 Additive 做整团火的问题是：在很亮的背景上，橙红低强度区域可能缺少稳定轮廓；大量重叠还会很快过曝、颜色趋白，难以表达外焰厚度。Body Alpha Layer 负责可辨认主体，Additive 只负责黄白高温核心和火星。两层分别表达“覆盖”与“发光增强”。

**面试官追问：** Additive 顺序是否完全无关？

**面试者：**

理想线性颜色、相同 Render Target 且只做纯加法时，加法近似满足交换律，多个 Additive Layer 对彼此顺序不敏感。但它们仍要经过 Opaque Depth Test、Fog、不同 Queue/Post Process，Render Target 精度和 Clamp/Tone Mapping 也可能影响结果；Additive 与 Alpha Body 的前后关系更不能随意。所以我只说“通常比 Alpha Blend 对粒子内部排序不敏感”，不说完全没有排序问题。

## Q22：为什么 Body/Core 是两个 Shader，而不是一个 Shader 的 `if` 或一个 Multi-pass Material？

**面试官：** 这样不是增加维护成本吗？

**面试者：**

Blend、ZWrite、Cull、Queue 属于 Draw/Pass 级固定 Render State，不是 Fragment 内每个像素可以通过普通 `if` 随意改变的变量。所以一个 Fragment Shader 不能让外圈用 Alpha Blend、内圈同时用 Additive Blend。

可以写一个 Multi-pass Shader，在同一个粒子上画 Body Pass 和 Core Pass，但那会让每个 Body Particle 无条件多画一次 Core，二者共享同一 Position、Size、Lifetime 和 Renderer Mode，不能实现 Core 更小、更短命、由 Sub Emitter 控制；Sparks 也无法使用独立 Stretched Billboard。当前拆成两个 Shader/Material 与多个 Particle Layer，更符合数据职责。

维护成本通过 `ElementFireCore.hlsl` 降低：Hash、Noise、Shape、Temperature 数学只有一份，两个 Shader 只分别声明 Properties、Blend 与最终颜色链。若未来 Render State 越来越多，可以评估共享更多 Include 或统一 Custom Editor，但不能为了文件少而混淆职责。

---

## Q23 ⭐：为什么 Transparent 火焰使用 `ZWrite Off`、`ZTest LEqual`、`Cull Off`？

**面试官：** 每一个都说清楚效果和副作用。

**面试者：**

`ZWrite Off` 表示通过测试的火焰 Fragment 不把自己的 Depth 写入 Depth Buffer。透明物体需要看到后面的颜色并与多个层混合；如果第一张火焰片写了深度，后面的火焰片可能因为更远而被 ZTest 拒绝，即使它本应通过 Alpha 参与合成。副作用是火焰片之间不能靠 Depth Buffer 自动正确遮挡，必须依赖透明排序，而且同一像素容易 Overdraw。

`ZTest LEqual` 表示当前 Fragment Depth 小于等于已有 Depth 才通过。虽然不写 Depth，它仍读取 Opaque 场景的 Depth，所以墙后的火焰通常不会穿墙显示。

`Cull Off` 表示正反 winding 的三角形都不剔除，实验 Quad 和 Billboard 从两侧都能看到。它不是让正面三角形绘制两次，但相比 `Cull Back`，从背面观察时不会被直接剔除，可能增加实际 Fragment。Vertical Billboard 通常会朝向 Camera，正式性能 Gate 可以验证是否安全改为 `Cull Back`；当前先优先保证实验可见性。

**面试官追问：** 开启 ZWrite 再做透明排序能不能更快？

**面试者：**

可以设计 Depth Prepass、Alpha Clip 或特殊 OIT/Weighted Blended 方案，但普通半透明火焰开启 ZWrite 会改变视觉语义。是否值得要看交叠、Camera 进入火焰、移动端 Fill Rate 等条件，不能简单套模板。对于大量粒子，有时用 Soft Alpha Clip、低分辨率 VFX Buffer 或前后层拆分优化，但都会带来质量/复杂度取舍。

---

## Q24：`Queue=Transparent` 和 `Transparent+10` 解决了什么，又没解决什么？

**面试官：** Core 晚十个 Queue 就一定在 Body 上面吗？

**面试者：**

Unity 常把 Transparent 基准看作 3000，`Transparent+10` 是 3010。不同 Queue 的 Renderer 通常按 Queue 先后组织，所以 Core Material 比 Body 稍后绘制，有助于共面实验 Quad 和两层火焰稳定形成“先主体、后加亮”。

它没有解决所有透明排序。相同 Queue 内还会依据 Sorting Layer、Order、Camera Distance、Renderer Bounds 等排序；不同透明对象交叉时，按 Renderer 粒度排序不能达到逐像素正确。Queue 拉得过远还可能让 Core 与场景中的雾、水、其他魔法透明物出现不符合空间关系的固定前后顺序。

当前 Core 是 Body 的 Sub Emitter，空间相近且 Additive 对内部顺序较不敏感，所以 `+10` 是可控工程选择。最终仍要用 Frame Debugger 看 Draw 顺序，而不是只看 Inspector 数字。

**面试官追问：** 为什么不能依赖 ZBuffer 排 Body/Core？

**面试者：**

因为二者 `ZWrite Off`，只会与先前 Opaque Depth 比较，不会把彼此深度写进去；而且共面或近共面时会有精度问题。它们的视觉叠层主要由 Queue/Renderer Order 和 Blend 决定。

## Q25：为什么 Body Fog 向 Fog Color 混合，而 Additive Fog 要向黑色混合？

**面试官：** 这是你项目里一个有意思的点，解释一下。

**面试者：**

普通 Body 的颜色可以写成：

```text
C_fogged = lerp(C_fire,C_fog,FogFactor)
```

距离越远越接近场景 Fog Color，随后执行 Alpha Blend，符合普通表面融入雾的直觉。

Additive 的输出随后会加到 Destination：

```text
Cout = Cadd×A + Cdst
```

如果远处 `Cadd` 被混到 Fog Color，而 Fog Color 不是黑色，相当于又把一份雾色加到已经含雾的背景，可能越远越发亮。Additive 的“无贡献”是黑色，所以使用：

```text
Cadd_fogged = lerp(Cadd,0,FogFactor)
```

距离越远贡献归零。这个问题说明 Fog 不能脱离 Blend Mode 机械套用。

**面试官追问：** Alpha 也需要随 Fog 变化吗？

**面试者：**

当前主要通过 RGB 向黑衰减，Alpha 保持原公式。也可以让 Alpha 同时减弱，结果可能更快消失，但要避免 RGB/Alpha 双重衰减过度。正确方式取决于使用 Straight/Premultiplied、Fog 模型和美术预期，应该在统一公式下设计，而不是随意两边都乘一次。

---

## Q26 ⭐：这个 Shader 是 Lit 还是 Unlit？`UniversalForward` 是否意味着自动受光？

**面试官：** 你用了 URP 的 `UniversalForward` Tag，所以它是 PBR Lit 吗？

**面试者：**

不是。`LightMode=UniversalForward` 主要告诉 URP 这个 Pass 在 Forward 阶段如何被选择；它不会自动调用 Lighting。当前 Fragment Shader 自己计算 RGB，没有构造 `SurfaceData/InputData`，也没有调用 `UniversalFragmentPBR`、主光、Shadow 或 GI，所以本质上是自定义 Unlit/Emissive 风格 Transparent Pass，只复用了 URP 的坐标、Fog 和管线宏。

这适合火焰主体，因为火通常表现为自发光，不应被场景暗光直接压黑。但它也不会真实照亮周围墙面。Material 的 HDR Color 与 Additive 只是让 Camera Color 更亮；动态 Point Light 是另一套 Lighting 数据，会参与其他物体的光照计算，成本和效果完全不同。

**面试官追问：** HDR 和 Bloom 是什么关系？

**面试者：**

HDR Color 允许线性颜色值超过 1，Bloom 后处理通常对超过阈值的高亮区域做提取、模糊和叠加，形成光晕。Shader 输出高值不等于自动产生 Bloom，Camera/URP 还要启用 HDR 和对应 Post-processing。Tone Mapping 会把 HDR 映射到显示范围。没有 Bloom 时 Additive 仍能提高像素亮度，但不会自动照亮周围表面或产生大范围光晕。

---

## Q27 ⭐：`Attributes`、`Varyings` 和 Semantic 是什么？Particle Alpha 怎样走到 Fragment？

**面试官：** 沿代码的数据链回答。

**面试者：**

`Attributes` 描述 Vertex Shader 从 Vertex Buffer 读取的数据：

```hlsl
positionOS : POSITION
uv         : TEXCOORD0
color      : COLOR
```

Semantic 告诉编译器/管线每个字段对应哪类 Vertex Stream。Vertex Shader 把 `uv` 和 `color` 写入 `Varyings`，把变换后的位置写到 `SV_POSITION`。Rasterizer 对普通 Varyings 做插值，再交给 Fragment Shader。

Particle 颜色链是：

```text
Start Color × Color over Lifetime
  ↓ ParticleSystemRenderer COLOR Vertex Stream
Attributes.color
  ↓ Vertex Shader 转发
Varyings.color
  ↓ Fragment vertexTint
finalAlpha × vertexTint.a
```

同一 Particle Quad 的四个顶点通常具有相同 Particle Color，所以插值后仍一致；UV 四角不同，因此在片内连续变化。Material `_UseVertexColor=1` 时才使用该值，实验 Quad 设 0，强制使用白色。

**面试官追问：** 为什么已经设置 Color over Lifetime，画面可能还是不淡出？

**面试者：**

曲线只改变 Particle 数据，不保证 Shader 消费它。要检查 Renderer Vertex Stream 是否含 `COLOR`、Shader 是否声明/转发 `COLOR`、Fragment 是否乘 `input.color.a`、Material 开关是否为 1。这个问题跨越 Particle Simulation、Vertex Buffer、Vertex Stage 和 Fragment Stage，不能只看 Inspector 曲线。

## Q28：解释 `UnityPerMaterial CBUFFER`、SRP Batcher、Keyword、`half/float` 和数值保护

**面试官：** 这些经常被写进模板，但你真的理解吗？

**面试者：**

Material Property 在 HLSL 中放进：

```hlsl
CBUFFER_START(UnityPerMaterial)
...
CBUFFER_END
```

是 URP/SRP Batcher 期望的常量缓冲布局。它让同一 Shader Variant 的 Material 常量组织更稳定，主要优化 CPU 侧 Draw Submission/状态切换；不会减少 Value Noise 的 Fragment ALU，也不保证 Particle Billboard 自动合成一个 Draw，实际要看 Frame Debugger。

`_UseVertexColor` 当前虽然用 `[Toggle]` 显示，但 HLSL 是读取 Float 并 `lerp(white,input.color,value)`，没有对应 `#pragma shader_feature`，因此功能不依赖两个编译 Variant。优点是避免 Variant，代价是始终执行这段算术；Material Drawer 可能设置一个未被 Shader 声明的 Keyword，后续可以改用纯 UI Toggle 属性或明确清理 Keyword。只有当关闭功能能裁掉一大段昂贵代码、状态种类有限时，我才考虑 Shader Feature。

精度上，Noise 坐标、距离、`pow` 和 Mask 核心用 `float`，颜色和部分权重用 `half`。移动 GPU 可能从 FP16 获益，桌面 GPU 不一定；World/UV 大坐标和连续 Time 更容易需要 float。优化要看编译结果和目标设备。

数值保护如：

```text
max(edgeSoftness,0.0001)
min(tipFadeStart,0.9999)
saturate(halfWidth)
```

避免 `smoothstep` 上下界重合、`pow(0,0)`、负宽度或 Mask 外插。Inspector Range 不是唯一输入来源，运行时代码或旧资产仍可能写越界值，所以 GPU 侧保护有意义。

**面试官追问：** `#pragma multi_compile_instancing` 就代表一定启用 GPU Instancing 吗？

**面试者：**

不代表。它只是编译支持 Instancing 的 Variant，并配合 Instance ID 宏传递数据。Renderer、Material、Render Mode、平台和 Unity Batching 路径还必须满足条件；Particle Billboard 与 Mesh Particle 的 Instancing 路径也不同。是否合批应该看 Frame Debugger/Profiler，不能从一个 Pragma 推断。

# 第五组：Particle System 与 3D 数学

## Q29 ⭐：Particle 的 Lifetime、Emission Rate、Max Particles 怎样共同决定密度？

**面试官：** 如果 Rate=12，为什么画面不一定有 12 个粒子？

**面试者：**

Rate 是每秒出生数量，Lifetime 是每个粒子存活时长。稳定连续发射、进入稳态后，平均可见数可以用类似 Little's Law 的关系估算：

```text
Nvisible ≈ EmissionRate × AverageLifetime
```

Body Rate 约 12/s，Lifetime 0.75～1.15s，平均约 0.95s，因此期望可见数约 `12×0.95≈11.4`。实际瞬时数量会受随机 Lifetime、离散发射、Culling 和刚启动阶段影响。

`Max Particles=24` 是容量上限，不是目标数量。如果 Rate×Lifetime 超过上限，后续出生会受限制。调 Lifetime 不只改变数量，还改变单片上升距离与节奏；调 Rate 主要改变出生频率。面试中我会结合二者，而不是只说“Max=24 所以有 24 个”。

**面试官追问：** `Color/Size over Lifetime` 的横轴是什么？

**面试者：**

通常是归一化年龄：

```text
τ = age/lifetime
```

`τ=0` 出生，`τ=1` 死亡。不同实际 Lifetime 的粒子都会走完整条 0～1 曲线。Body 的 Size 先增长再缩小，Alpha 快速淡入后逐渐淡出，二者联合避免突然出现/消失。

---

## Q30 ⭐：Vertical Billboard 和 Stretched Billboard 的 3D 数学是什么？

**面试官：** 不要只念 Unity 下拉框，尝试从向量基底解释。

**面试者：**

Billboard 的本质是在 Particle Center 周围构造一个朝向 Camera 的局部二维基底。普通 Camera-facing Billboard 可以使用 Camera Right 与 Camera Up：

```text
P_vertex = Center + Right×localX + Up×localY
```

Vertical Billboard 要保持世界竖直。可以概念化为：

```text
Up = normalize(WorldUp)
ViewHorizontal = CameraPosition-Center
ViewHorizontal.y = 0
Forward = normalize(ViewHorizontal)
Right = normalize(cross(Up,Forward))
```

再用 Right/Up 展开 Quad。`cross(a,b)` 得到同时垂直于 a、b 的向量，方向由右手定则决定；如果 Cross 顺序反了，Right 会反向，可能改变 Winding/UV 方向。

Stretched Billboard 则把一条轴与 Particle Velocity 或其屏幕投影对齐，长度根据 Speed Scale/Length Scale 调整，另一条轴仍要与 Camera/速度方向正交。火星高速向上时，它会变成短光迹；Body 如果使用 Stretched，会让速度改变整个火焰片长宽比，破坏 Shader 设计的轮廓，所以 Body/Core 使用 Vertical，Sparks 使用 Stretched。

**面试官追问：** Camera 恰好在 Particle 正上方时 Vertical Billboard 有什么问题？

**面试者：**

`ViewHorizontal` 可能接近零向量，Normalize 不稳定，Right 基底退化。Unity 内部会处理退化/回退，但从数学上这是 Billboard Basis 的奇异情况。当前第三人称 Camera 不太会完全位于火焰正上方；若是俯视游戏，可能选择普通 Billboard、Axis-aligned Billboard 或自定义稳定回退轴。

---

## Q31 ⭐：为什么独立的 Body/Core 会错位？Birth Sub Emitter 怎样从根因上修复？

**面试官：** 讲讲你真实遇到的问题。

**面试者：**

最初 Body/Core 是两个 sibling Particle System。即使它们的 Box Shape 范围、Rate 和速度看起来接近，每个系统都有独立 Emission Time、Random Seed 和 Shape Sample：

```text
BodyPosition = Random(Box,seedA,timeA)
CorePosition = Random(Box,seedB,timeB)
```

统计分布相似不代表样本一一相等，所以画面出现焰芯和外焰分离。Shader 单独 Quad 正常、Core 也能正确 Additive 显示，说明根因不是 Shape Mask 或 Blend，而是 Particle 数据关系。

修复后，`PS_FireCore` 成为 Body 的 `Birth Sub Emitter`。每次 Body Particle Birth 事件触发 Core 在 Parent Particle 的出生位置发射一次，Core Rate over Time 为 0、Burst Count 为 1、Shape 关闭，继承 Size/Rotation，并使用更短 Lifetime 与更小 Size。关系变成：

```text
BodyBirth(position,size,rotation)
  → CoreBirth(same position,relative size,rotation)
```

这是从数据依赖上建立一一配对，而不是继续调参数碰巧重叠。

**面试官追问：** 把 Core GameObject 设为 Body 子物体为什么还不够？

**面试者：**

Transform Hierarchy 只定义局部坐标如何跟随父 Transform，不会让两个 Particle System 的每个 Particle 建立事件关系。真正触发 Parent Particle Birth → Child Emit 的是 Body 的 `Sub Emitters` 模块。GameObject 父子关系是配置 Sub Emitter 的常见层级组织，但不是配对机制本身。

---

## Q32：为什么 Core 不继承 Parent Color？`Inherit Velocity` 又要注意什么？

**面试官：** 你为什么只继承 Size 和 Rotation？

**面试者：**

Body 的 Color over Lifetime 在出生时 Alpha 接近 0，用于平滑淡入。如果 Core 继承 Parent Color，Birth 时可能拿到低 Alpha，再乘 Core 自己的 Particle Alpha 和 Shader GlobalAlpha，导致 Core 出生即透明或亮度异常。所以我只继承 Size 和 Rotation，让位置/几何配对，但颜色由 Core 自己的生命周期控制。

Velocity 需要关注 Simulation Space 与继承模式。`Initial` Inherit Velocity 表示 Core 出生时取得 Parent 的速度快照，之后按自己的模拟继续；若持续继承，则 Parent 后续变化也可能影响它。Unity 的 Inherit Velocity 对 World Simulation Space 有特定语义和限制，配置时不能只勾选模块，还要确认 Core 的 Simulation Space、Parent Velocity 来源和本地轴方向。

当前 Core 关闭独立 Shape 与 Velocity over Lifetime，减少出生后脱离 Body 的风险；它更短命、尺寸更小，所以即使继承 Parent 初速度，也会作为内部亮芯短暂跟随，而不是形成第二套漂移火焰。

**面试官追问：** 为什么 Core Lifetime 要更短？

**面试者：**

视觉上高温亮芯集中在火焰根部和早中期，不应比橙红外焰存活更久；工程上更短 Lifetime 也降低同时存在的 Additive 重叠数量，控制过曝。它是视觉职责和性能预算共同决定的参数。

---

## Q33：Shader Noise 与 Particle Noise 有什么本质区别？为什么两边都需要？

**面试官：** 都叫 Noise，是不是重复计算同一个效果？

**面试者：**

它们作用的数据和尺度不同。Shader Noise 在每个 Fragment 上以 UV/Time 采样，改变 Shape Center、Width、Temperature 和 Alpha；它不会移动 Particle Center，也不改变真实 Quad Transform。即使粒子完全不动，片内火焰纹路仍然会上升。

Particle Noise 作用在粒子模拟轨迹上，改变 Particle Position/Velocity，使整张 Billboard 的中心在 3D 空间中摆动。Sparks 使用轻微 Particle Noise，是为了让高速轨迹不完全平行；Body 暂时关闭 Particle Noise，避免整片火舌和 Shader 内部扰动叠加后过乱。

可以概括为：

```text
Shader Noise：片内、逐 Fragment、视觉形态
Particle Noise：片间/轨迹、逐 Particle、空间运动
```

两者都开得很强会产生双重随机性，玩家无法读出主要上升方向，也会增加 GPU ALU 和 CPU Particle Simulation 成本。每层 Noise 应有明确频率和职责。

---

## Q34：为什么当前用 Particle System，而不是直接上 VFX Graph？CPU/GPU 各承担什么？

**面试官：** VFX Graph 是 GPU Particle，不是一定更好吗？

**面试者：**

当前每个火区只有大约十余 Body、对应 Core 和少量 Sparks，数量很低；Shuriken Particle System 的模块、Sub Emitter 和 Inspector 曲线更适合逐步学习与快速验证，也容易与 GameObject/Prefab 生命周期结合。CPU 主要模拟 Particle State、事件和 Bounds，GPU 负责每个 Billboard 的 Vertex/Fragment Rendering。

VFX Graph 在成千上万 GPU Particle、复杂 Spawn/Update Context、GPU Buffer 和大规模并行时更有优势，但它也有 Graph 复杂度、平台支持、Bounds、事件回读和调试成本。当前最重的可能不是 CPU Particle 数，而是透明 Billboard 的 Fragment Noise 与 Overdraw；换成 GPU Simulation 并不会自动消除这些 Fragment。

如果未来是大范围火海、火星数量上千，VFX Graph 值得比较；如果需要 Gameplay 精确知道每个粒子碰撞，纯 GPU Particle 又会增加 CPU/GPU 同步难题。技术选型要看数量、交互、平台和瓶颈数据。

**面试官追问：** Shader 没有 GC Alloc，所以整个火焰是零 GC 吗？

**面试者：**

Shader 运行在 GPU，不属于 C# Managed Heap，本身谈不上每帧 GC Alloc。但控制 VFX 的 C# 如果每次反应 `Instantiate`、创建数组或闭包，仍会产生 Managed Allocation；Particle System 内部还有 Native/Engine 成本。后续正式反应视觉应池化，Profiler 要分别看 CPU Main Thread、Rendering Thread、GC 和 GPU，而不是用一个“零 GC”概括全部。

# 第六组：性能、Debug、架构与演进

## Q35 ⭐：这套火焰的主要 GPU/CPU 成本在哪里？你怎样证明和优化？

**面试官：** 不要泛泛说“减少粒子”，按频率和工具回答。

**面试者：**

GPU 端主要是 Fragment 成本。每个火焰 Fragment 计算两层 Value Noise，每层需要四个角点 Hash 和多次 `floor/frac/dot/lerp`，两层就是八次 Hash，再加 Shape 的 `pow/smoothstep`、Temperature `pow`、颜色与 Fog。Body/Core 是两层透明覆盖，Sparks 再增加小面积覆盖；`ZWrite Off` 意味着火焰片之间难以利用 Early-Z 淘汰，粒子越大、越靠近 Camera，Overdraw 越高。Bloom/Tone Mapping 还会增加后处理成本。

CPU 端主要是 Shuriken Particle Simulation、Sub Emitter 事件、Renderer Bounds/Culling 和 Draw Submission。当前数量低，CPU 可能不是瓶颈，但不能靠感觉判断。

我的验证方式是固定 Camera、分辨率、URP Asset、Bloom 与场景背景，分别测试 0、1、4、8 个火区。Frame Debugger 用来确认 Body/Core/Sparks 的 Draw、Queue、Blend 和 Variant；Rendering Debugger/Overdraw 看屏幕覆盖；Profiler GPU Module 或平台工具记录 Pass 时间；CPU Profiler 看 Particle Update、Render Thread 与 GC。然后做 A/B：关闭 Core、Sparks、第二层 Noise、Bloom，缩小 Particle Size 或降低 Rate，观察时间差。

优化顺序会优先减少不可见工作：控制 Bounds 和屏幕覆盖、减少大面积透明重叠、降低远处粒子数量；再考虑低质量 Shader 关闭第二层 Noise、用 `Cull Back`、降低 Precision；如果 ALU 明显是瓶颈，比较自制 Noise/Flipbook Texture。不能用 Draw Call 数代替 GPU 时间，也不能因为程序化无纹理就宣称更快。

**面试官追问：** 为什么 Overdraw 可能比 Particle Count 更关键？

**面试者：**

一个很大的近景 Particle 即使只有一张，也可能覆盖几十万 Pixel，每个 Pixel 执行昂贵 Fragment；几十个远处小 Particle 可能总覆盖更少。成本更接近“所有透明片的屏幕覆盖面积之和 × 每 Fragment 成本”，而不是只看粒子个数。Overdraw 视图和固定镜头 GPU Timing 比 Hierarchy 中的数量更有意义。

## Q36：如果程序化版本太贵，怎样把它转成自制 Flipbook？有什么新问题？

**面试官：** 讲完整一点，不要只说“烘成贴图”。

**面试者：**

我会先在固定视角或离线工具中把当前程序化 Shape/Noise/Temperature 动画渲染为多帧 RGBA，按 Atlas 排列成例如 `512×512` Flipbook。RGB 保存火焰颜色/发光，Alpha 保存柔和轮廓；Unity Import 先用 None Compression 做基准，再评估 BC/ASTC 等格式、Alpha 质量、sRGB/Linear 语义、Mip Map、Wrap 和边缘 Padding。运行时 Shader 根据 Particle Age 计算 Frame Index 和 Atlas UV，采样当前帧，必要时在相邻帧间插值。

它把每 Fragment 的多层 Hash/Noise ALU 换成 Texture Sample 与 Bandwidth，性能更稳定，也能容纳更复杂的离线形态；代价是显存、压缩伪影、固定循环、Atlas Bleeding、帧率感和重复可见。帧间插值减少跳帧，但增加一次采样；Mip 可能让相邻 Atlas Cell 泄漏，需要 Padding 或自定义采样。

我会保留“自研”属性，因为 Flipbook 来自自己的程序化/离线制作，而不是商城 Prefab。是否转换由 5F 的 GPU 数据决定，不是因为 Texture 一定更低级或更高级。

**面试官追问：** 程序化版本还有什么保留价值？

**面试者：**

它适合连续参数驱动，例如 Burning 强度改变宽度、速度、颜色或反应阶段；也方便学习和生成不同变体。可以采用混合方案：Flipbook 提供大形态，少量程序化 UV Distortion、Vertex Color 和 Sparks 提供变化，降低重复感。

## Q37 ⭐：如果火焰画面异常，你会怎样系统 Debug？请结合真实问题

**面试官：** 我不想听“多调参数”，给我可重复流程。

**面试者：**

我从 Pipeline 外层向中间信号逐层缩小范围。先看 Console/Editor.log 是否有 Shader Compile Error，Material 是否引用正确 Shader，Renderer/Camera Layer 是否可见。再用 Frame Debugger确认 Body/Additive Pass 是否执行、Queue 与 Blend 是否符合预期。之后回到单 Quad：先输出 `shapeMask.xxx`，确认 UV 方向、Base/Tip Width、Softness 和 Fade；再输出 `noiseA/noiseB/combinedNoise`，确认连续且向上；把 Distortion/Detail 设 0 后逐个恢复；再输出 `temperatureMask.xxx`。调试 Mask 时 Alpha 固定为 1，避免背景 Blend 干扰灰度。

Particle 端先单独播放 Body，检查 Emission、Lifetime、Color/Size Curve 和 Vertical Billboard；再单独播放 Core；最后检查 Sub Emitter 和 Sparks。一次只启用一层，避免无法判断亮度、速度和 Overdraw 来源。

真实遇到两个问题。第一个是 `Size over Lifetime` 看起来无法编辑，根因不是字段缺失，而是 Unity 6.3 的详细曲线编辑器位于 Inspector 底部 `Particle System Curves`，当区域折叠时只看到一条预览。第二个是 Core 与 Body 错位。我先确认 Shader 单独 Quad 正常、Core 能 Additive 显示，再发现两套独立 Shape/Random 没有共享 Birth，最终改为 Birth Sub Emitter，而不是继续猜位置参数。

若出现过曝，我会把贡献拆为 HDR Color、Intensity、GlobalAlpha、ParticleAlpha、Temperature Weight 和 Overlap Count，逐个 A/B；若出现排序问题，则查 ZWrite、Queue、Sorting、Bounds 与 Camera Distance，而不是只降低 Alpha。

**面试官追问：** Frame Debugger、Profiler、RenderDoc 分别回答什么？

**面试者：**

Frame Debugger 回答“一帧按什么顺序执行哪些 Draw/Pass、使用什么 Material/Keyword/Render Target”；Profiler 回答 CPU/GPU 时间和 GC 分布；Rendering Debugger 适合 Overdraw、Lighting 等管线调试视图；RenderDoc/PIX 等平台工具能进一步看资源绑定、Shader Invocation、纹理和 GPU Event。Frame Debugger 看到三个 Draw 不代表它们便宜，必须结合 Timing 和屏幕覆盖。

## Q38 ⭐：Fire Visual 怎样接入 Burning Gameplay？未来怎样继续扩展？

**面试官：** 你会让 Shader 直接读取角色 Burning 百分比并修改状态吗？

**面试者：**

Shader 只负责 GPU Presentation，不应该拥有 Gameplay 状态规则。Burning 的数值、DoT、Wet 中和、阈值和反应顺序属于 CPU Gameplay，需要可测试、可存档、可用于 AI/网络；Shader 无法可靠地反向驱动这些规则。

正式 `EV_FireArea` 应通过 Prefab 组合：不可见 Gameplay 部分用 Trigger/`StatusVolume(Burning)` 施加状态，Visual Child 使用当前 Body/Core/Sparks。两者共享空间范围但职责独立：关闭 Visual，Burning 仍工作；替换 Material，不改变状态数值。角色 OnFire 或 Steam 由 `Game.Rendering` 订阅 `Game.Core` EventBus 的状态/反应事件，不让 `Game.Combat` 反向引用 Rendering。

当前已完成的是 5A～5D 视觉基础。下一步 5E 会制作 `Extinguish Steam`：Alpha Blend 粒子上升、扩大并淡出，由 Reaction Event 控制 Play/Stop；5F 再做 Frame Debugger、Overdraw 和 Profiler Gate。之后才组装正式 Prefab。更远期可以加入热折射、Interactive Wind、角色表面附着点、Light Cookie 或 Flipbook LOD，但每项都应作为独立问题评估。

**面试官追问：** 如果只能优先做一个升级，你选什么？

**面试者：**

结合这个项目的 Noita-like 元素反应玩法，我会优先完成 Steam 与反应事件接入，而不是先做更炫的热折射。因为它直接向玩家解释 Burning+Wet 的 Gameplay 结果，提升系统可读性；完成后再依据 5F 性能数据决定 Flipbook、LOD 或热折射。视觉升级优先级应服务玩法信息，而不是术语越高级越先做。

**面试官追问：** 最后用一段话总结，这个项目体现了什么能力？

**面试者：**

它体现的是我能从最终火焰反向拆出轮廓、流动、温度、Blend 和粒子生命周期，再把它们落实为 UV Height Function、Smoothstep、Hash/Value Noise、Moving UV、Height Weight、Alpha/Additive Render State、Vertex Stream、Billboard 与 Birth Sub Emitter；我能从 Object/Clip Space、Rasterization 和 Blend Equation解释像素怎样产生，也能用中间 Mask、Frame Debugger、Overdraw 与 Profiler系统定位问题。在工程上，我把 Rendering 与 Burning Gameplay 分离，并诚实说明当前没有真实流体、体积、动态光照、Steam 和性能结论。对我来说，成果不仅是“看起来像火”，而是完整走通了需求拆解、数学实现、Unity Engine 配置、真实 Debug 与后续优化决策。
