# 可交互护盾法术：设计解析

创建时间：2026-07-05

本文复盘的是“可交互的护盾”这一版最终设计：护盾不是原地生成的静态防御场，而是一个可以像火球一样从法杖方向发射出去、在飞行过程中反弹其他投射物、并且可以被重力、弹跳、追踪、轨道等 Modify 法术影响的 Emit 法术。

你可以先记住一句话：

```text
可交互护盾 = 一个特殊的 ProjectileBase，外加一个负责反弹的 ProjectileShield 子 Trigger
```

这句话是理解整个功能架构的入口。

---

## 1. 这个功能到底实现了什么

玩家看到的结果是：

1. 在法杖栏中放入“护盾投射物”法术。
2. 点按施法后，护盾像普通投射物一样从玩家施法点飞出去。
3. 护盾飞行时，如果其他投射物进入护盾范围，会被反弹。
4. 玩家阵营的投射物也会被反弹，用来制造有趣的组合玩法。
5. 被反弹的敌方投射物会改变阵营归属，变成护盾释放者阵营，因此可以反过来伤害敌人。
6. 护盾有反弹次数，次数耗尽后销毁。
7. 护盾本体可以被已有 Modify 法术修正，例如：
   - `Gravity`：护盾飞出后受重力下坠。
   - `Bounce`：护盾撞到环境后弹跳。
   - `Homing`：护盾朝敌人偏移。
   - `Orbit`：护盾围绕轨道中心运动。
   - `Multicast`：一次发射多个护盾。

这里最重要的设计点是：护盾本体不是“技能特效”，而是“投射物”。只有把它放进投射物体系，它才能自然继承项目里已经存在的一整套投射物能力。

## 2. 基础知识和原理

### 2.1 投射物和静态投射物的区别

在你的法术系统里，当前已经有两种很重要的产出类法术：

```text
Emit：从施法点沿方向发射一个东西，例如火球、护盾投射物。
StaticProjectile：在某个点生成一个效果，例如陨石落点、原地护盾。
```

`Emit` 的关键语义是：

```text
有发射方向，有初速度，会沿方向飞出去。
```

`StaticProjectile` 的关键语义是：

```text
在当前法术上下文的位置生成效果，本身不强调“发射出去”。
```

一开始曾经考虑过把“可交互护盾”做成 `StaticProjectile + Rigidbody`，也就是在某个点生成后再让它物理运动。但你后来指出这个设计不符合目标效果：你想要的是“护盾像投射物一样被射出去”。这个判断是正确的。

所以最终方案改成：

```text
Kind = Emit
SpawnMode = ForwardProjectile
Prefab 根物体挂 ShieldProjectile
```

这一步不是单纯的分类问题，而是架构语义问题。法术分类决定后续系统怎么解释它。

### 2.2 Rigidbody 是什么

`Rigidbody` 是 Unity 物理系统用来让物体参与物理运动的组件。对投射物来说，它主要负责：

1. 保存速度：Unity 6 中使用 `Rigidbody.linearVelocity`。
2. 是否受重力：`Rigidbody.useGravity`。
3. 碰撞检测模式：`Rigidbody.collisionDetectionMode`。
4. 在物理世界中移动、碰撞、反弹。

本项目的普通角色移动使用 `CharacterController`，但投射物使用 `Rigidbody`。这符合项目规则，也符合常见游戏开发做法：角色控制需要精确手感，投射物更适合走物理或半物理逻辑。

### 2.3 Collider 和 Trigger 的区别

护盾这个功能同时用到了两种 Collider 语义：

```text
根物体 Collider：非 Trigger，用于护盾本体和环境发生实体碰撞。
子物体 Trigger Collider：Is Trigger = true，用于检测进入护盾范围的投射物。
```

普通 Collider 会参与物理碰撞。比如护盾撞到墙，Unity 物理系统会产生碰撞事件，`ProjectileBase.OnCollisionEnter` 会被调用。

Trigger Collider 不做实体阻挡，它更像一个检测区域。当别的 Collider 进入时，会触发 `OnTriggerEnter`。护盾用子 Trigger 检测“有投射物进入反弹范围”，这比直接依赖实体碰撞更合适，因为反弹范围通常要比视觉球体略大，而且不应该把所有东西都硬挡住。

### 2.4 反射向量 Vector3.Reflect

反弹投射物的核心数学是向量反射。Unity 内置了：

```csharp
Vector3.Reflect(inDirection, inNormal)
```

它的含义是：

```text
给定一个入射方向 inDirection 和一个表面法线 inNormal，计算出镜面反射方向。
```

比如火球从左前方撞到护盾球面，护盾会根据“火球相对护盾中心的位置”计算法线，再用 `Vector3.Reflect` 算出新的飞行方向。

本功能里反弹逻辑位于 `ProjectileBase.ReflectByShield(...)`：

```csharp
Vector3 reflected = Vector3.Reflect(incoming, normal);
```

然后保持原速度大小，只替换速度方向：

```csharp
float speed = velocity.magnitude;
Vector3 newVelocity = reflected * speed;
_rb.linearVelocity = newVelocity;
```

这就是“方向改变，速度大小基本不变”的反弹。

### 2.5 阵营归属为什么要改

你的需求里有一个关键点：

```text
如果反弹了敌方投射物，敌方投射物会对敌方造成伤害。
```

这意味着反弹时不能只改速度，还要改投射物的“伤害归属”：

```csharp
_attackerTeam = newTeam;
_attackerId = newAttackerId;
```

否则敌人的火球即使被反弹回去，仍然属于敌方阵营，最终可能不会伤害敌人。

这也是战斗系统设计里非常重要的概念：一个投射物的视觉来源和当前伤害归属不一定永远一致。反弹、魅惑、转化、召唤物控制权变化，都会用到类似思想。

## 3. 业界常见实现方案

### 方案 A：护盾作为静态区域

做法：

```text
在场景某个位置生成护盾区域。
护盾区域有 Trigger Collider。
投射物进入区域后被反弹。
```

优点：

1. 实现简单。
2. 适合防御罩、结界、原地屏障。
3. 不需要关心护盾本体运动。

缺点：

1. 不适合“被发射出去”的玩法。
2. 不容易自然吃到投射物 Modify。
3. 如果硬加 Rigidbody，容易变成一套平行于投射物系统的新运动体系。

你的旧“保护盾术”更接近这个方案。

### 方案 B：护盾作为普通投射物的一个子类

做法：

```text
ShieldProjectile 继承 ProjectileBase。
它像火球一样被 SpellCaster 发射。
它复用 ProjectileBase 的速度、重力、弹跳、追踪、轨道、生命周期。
反弹能力交给 ProjectileShield。
```

优点：

1. 最符合“护盾被射出去”的玩法语义。
2. 能自然接入已有 Modify 和 Multicast。
3. 不需要重复实现一套运动系统。
4. 和火球、箭、陨石属于同一个投射物生命周期模型。

缺点：

1. 需要在 `ProjectileBase` 里开一个 collision seam，避免护盾像火球一样撞到东西就销毁。
2. Prefab 组件配置要求更严格。

最终采用的是这个方案。

### 方案 C：独立 ShieldActor，不继承 ProjectileBase

做法：

```text
新建 ShieldActor，自己实现 Rigidbody 运动、生命周期、反弹、修正接入。
```

优点：

1. 行为完全自由。
2. 不受 `ProjectileBase` 默认命中逻辑限制。

缺点：

1. 会和已有投射物系统重复。
2. 所有 Modify 都要额外适配一次。
3. 后期维护成本高。
4. 容易破坏“法术编程系统 = 解释器 + EmitCommand + ProjectileBase”的统一架构。

这个方案不适合当前阶段。你的项目正在训练“系统化架构能力”，此时更应该复用已有主干，而不是为每个特殊法术开一条独立支线。

## 4. 最终选择的技术方案

最终方案是：

```text
SpellDefinition
-> CastEvaluator
-> EmitCommand
-> SpellCaster.SpawnForwardProjectile
-> ShieldProjectile : ProjectileBase
-> ProjectileShield
-> ProjectileBase.ReflectByShield
```

### 4.1 ScriptableObject：保存法术数据

文件：

```text
Assets/_Project/Scripts/Skills/SpellDefinition.cs
```

护盾投射物的法术资产配置为：

```text
Kind = Emit
SpawnMode = ForwardProjectile
ProjectilePrefab = Spell_Emit_Shield prefab
BaseDamage = 0
BaseSpeed = 10 左右
DamageType = Magical
ManaCost = 根据强度设置
ShieldReflectCount = 反弹次数
```

这里的 `ShieldReflectCount` 是护盾专属数据。它被放在 `SpellDefinition` 中，是因为它属于“法术配置”，不应该写死在 MonoBehaviour 里。

### 4.2 CastEvaluator：把法术数据解释成 EmitCommand

文件：

```text
Assets/_Project/Scripts/Skills/CastEvaluator.cs
Assets/_Project/Scripts/Skills/EmitCommand.cs
```

`CastEvaluator` 是纯逻辑解释器，不实例化 prefab，不访问场景。它只负责把法杖里的法术序列解释成一组 `EmitCommand`。

本功能让 `EmitCommand` 携带：

```csharp
public readonly int ShieldReflectCount;
```

也就是说，护盾反弹次数会从 `SpellDefinition` 被烘焙到 `EmitCommand`：

```text
SpellDefinition.ShieldReflectCount
-> EmitCommand.ShieldReflectCount
```

这个设计的好处是：运行时生成投射物时不需要回头查 ScriptableObject，所有本次施法需要的数据都已经被快照在 `EmitCommand` 里。

### 4.3 SpellCaster：把纯数据变成 Unity 对象

文件：

```text
Assets/_Project/Scripts/Character/Spells/SpellCaster.cs
```

`SpellCaster` 是桥接层。它把 `EmitCommand` 转换成真实场景对象。

普通 Emit 走：

```text
SpawnForwardProjectile
-> Instantiate prefab
-> GetComponent<ProjectileBase>
-> WirePayload
-> ConfigureProjectileMotion
-> 如果是 ShieldProjectile，注入 ShieldReflectCount
-> ProjectileBase.Init
```

关键代码逻辑是：

```csharp
if (proj is ShieldProjectile shieldProjectile)
    shieldProjectile.ConfigureShield(cmd.ShieldReflectCount);

proj.Init(team, attackerId, cmd.Damage, cmd.DamageType, dir * cmd.Speed, casterCollider, useGravity: cmd.UseGravity);
```

这里顺序很重要：

1. 先 `ConfigureProjectileMotion`，注入弹跳、追踪、轨道等修正。
2. 再 `ConfigureShield`，注入护盾反弹次数。
3. 最后 `Init`，让投射物真正带着速度和阵营进入运行状态。

### 4.4 ProjectileBase：投射物生命周期主干

文件：

```text
Assets/_Project/Scripts/Combat/Projectiles/ProjectileBase.cs
```

`ProjectileBase` 是火球、箭、陨石、护盾投射物共同复用的父类。它负责：

1. `Rigidbody` 初速度。
2. 重力开关。
3. 最大生命周期。
4. 同阵营投射物互相忽略碰撞。
5. 命中敌人后走 `IDamageable.ReceiveHit`。
6. 碰撞后触发 payload。
7. 弹跳、追踪、轨道等运动修正。

为了支持护盾这种“会碰撞但不应该像火球一样命中即销毁”的特殊投射物，本次在 `ProjectileBase` 中加入了一个 seam：

```csharp
protected virtual bool TryHandleCollisionBeforeDefault(Collision collision, IDamageable target)
{
    return false;
}
```

它在默认命中逻辑之前被调用：

```text
OnCollisionEnter
-> 同阵营过滤
-> TryBounce
-> TryHandleCollisionBeforeDefault
-> 默认伤害 / OnImpact / payload / Destroy
```

普通火球不重写这个方法，所以仍然保持旧行为。

护盾投射物重写它：

```csharp
protected override bool TryHandleCollisionBeforeDefault(Collision collision, IDamageable target)
{
    return true;
}
```

`return true` 表示：这次碰撞已经由子类处理，不要继续走默认伤害和销毁流程。

这就是架构上最关键的扩展点。

### 4.5 ShieldProjectile：会飞的护盾本体

文件：

```text
Assets/_Project/Scripts/Combat/Projectiles/ShieldProjectile.cs
```

职责：

1. 继承 `ProjectileBase`，因此它是合法投射物。
2. 接收 `SpellCaster` 注入的反弹次数。
3. 在 `Init` 后初始化子级 `ProjectileShield`。
4. 拦截默认碰撞消耗逻辑，不让自己像火球一样撞到东西就爆炸。

核心代码：

```csharp
public sealed class ShieldProjectile : ProjectileBase
{
    [SerializeField] private ProjectileShield _shield;

    private int _reflectCount;

    public void ConfigureShield(int reflectCount)
    {
        _reflectCount = Mathf.Max(0, reflectCount);
    }

    public override void Init(...)
    {
        base.Init(...);

        if (_shield == null)
            _shield = GetComponentInChildren<ProjectileShield>();

        if (_shield != null)
            _shield.Init(attackerTeam, attackerId, _reflectCount, casterCollider);
    }

    protected override bool TryHandleCollisionBeforeDefault(Collision collision, IDamageable target)
    {
        return true;
    }
}
```

这里用到了 `Mathf.Max(0, reflectCount)`，它是 Unity 内置数学 API，用来保证反弹次数不会小于 0。

### 4.6 ProjectileShield：反弹检测组件

文件：

```text
Assets/_Project/Scripts/Combat/Projectiles/ProjectileShield.cs
```

`ProjectileShield` 不负责飞行。它只负责一件事：

```text
当其他 ProjectileBase 进入护盾 Trigger 范围时，尝试反弹它。
```

关键 Unity API：

```csharp
private void OnTriggerEnter(Collider other)
```

这是 Unity 的 Trigger 事件函数。当前物体的 Collider 勾选 `Is Trigger` 后，其他 Collider 进入时 Unity 会调用它。

反弹流程：

```text
OnTriggerEnter
-> other.GetComponentInParent<ProjectileBase>()
-> 过滤空对象
-> 过滤自己的 ShieldProjectile
-> 计算护盾法线 normal
-> projectile.ReflectByShield(normal, ownerTeam, ownerAttackerId)
-> 成功后反弹次数 -1
-> 次数耗尽销毁护盾
```

这里用到了：

```csharp
other.GetComponentInParent<ProjectileBase>()
```

这是 Unity API。它会从 `other` 所在物体开始，向父级查找 `ProjectileBase`。这样即使投射物的 Collider 挂在子物体上，也能找到根投射物脚本。

还有一个关键保护：

```csharp
if (projectile == _ownerProjectile)
    return;
```

这是为了避免护盾子 Trigger 把自己的根物体 `ShieldProjectile` 也当作“进入护盾的投射物”处理。

## 5. 架构设计与集成

### 5.1 总体架构位置

可以把本功能放进项目架构图里看：

```text
Game.Skills
  SpellDefinition
  CastEvaluator
  EmitCommand
        |
        v
Game.Character
  SpellCaster
        |
        v
Game.Combat
  ProjectileBase
  ShieldProjectile
  ProjectileShield
```

职责边界非常清楚：

1. `Game.Skills`：只处理数据和解释器，不生成场景物体。
2. `Game.Character`：`SpellCaster` 作为施法运行时桥接层。
3. `Game.Combat`：负责真实投射物、碰撞、反弹、伤害归属。

这符合项目的 asmdef 依赖方向：

```text
Game.Skills 不能依赖 Game.Character
Game.Combat 不能依赖 Game.Skills
Game.Character 可以同时依赖 Game.Skills 和 Game.Combat
```

所以 `ShieldReflectCount` 的传递方式必须是：

```text
SpellDefinition -> EmitCommand -> SpellCaster -> ShieldProjectile
```

而不能让 `ShieldProjectile` 直接读取 `SpellDefinition`。那样会让 `Game.Combat` 反向依赖 `Game.Skills`，破坏模块边界。

### 5.2 为什么不新增 SpellKind

这个问题很重要。可交互护盾看起来像一个新类别，但最终没有新增 `SpellKind.Shield`。

原因是：它本质上仍然是一个“会被发射出去的东西”，所以属于 `Emit`。如果每种特殊法术都新增一个 `SpellKind`，解释器会逐渐变成大量分支：

```text
Emit
Modify
Multicast
StaticProjectile
Shield
Meteor
Laser
...
```

这会让法术编程系统变成“技能表”，而不是“解释器”。

更好的做法是：

```text
用 Kind 表达大的执行语义。
用 Prefab / Script / Data 表达具体行为。
```

所以护盾投射物是：

```text
Kind = Emit
Prefab = 带 ShieldProjectile 的 prefab
```

### 5.3 Prefab 结构为什么要拆成根物体和子 Trigger

推荐结构：

```text
Spell_Emit_Shield
  Rigidbody
  SphereCollider（Is Trigger = false）
  ShieldProjectile
  Visual / ParticleSystem
  ShieldReflectTrigger
    SphereCollider（Is Trigger = true）
    ProjectileShield
```

根物体负责“我是一个投射物”：

1. `Rigidbody`：移动。
2. 非 Trigger `SphereCollider`：实体碰撞。
3. `ShieldProjectile`：投射物生命周期。

子物体负责“我是反弹范围”：

1. Trigger `SphereCollider`：检测进入范围的投射物。
2. `ProjectileShield`：反弹逻辑。

如果只在根物体上挂 `ProjectileShield`，但没有 `ShieldProjectile`，就会出现你之前遇到的问题：

```text
mana 和音效都正常
但护盾看不到
```

根因是 `SpellCaster` 发射 Emit 时会查找：

```csharp
go.GetComponent<ProjectileBase>()
```

如果 prefab 没有 `ShieldProjectile`，就不是合法投射物，`SpellCaster` 会销毁它。

这说明 Editor 配置不是“美术资源问题”，而是架构接入的一部分。

## 7. 踩坑与 Debug

### 7.1 第一坑：把可交互护盾设计成 StaticProjectile

最开始的设计方向是：

```text
StaticProjectile + Rigidbody + SpellPhysicsBody
```

这个方案的直觉是：护盾是静态投射物的一种，只是它多了物理交互。

但这个前提后来被推翻了。因为你的目标不是“在某点生成一个会动的护盾”，而是：

```text
从法杖方向发射出去的护盾投射物
```

所以它应该是 `Emit`。

这个坑的教训是：设计法术类别时，不要先看美术表现，而要先问：

```text
这个法术在法术编程语言里的执行语义是什么？
```

如果它需要一个发射方向和初速度，就应该优先考虑 `Emit`。

### 7.2 第二坑：Prefab 没挂 ShieldProjectile

测试时出现：

```text
点按后看不到护盾飞出去，但 mana 和音效正常。
```

这说明：

1. `CastEvaluator` 成功了。
2. `SpellCaster` 已经执行到播放音效。
3. 问题大概率在 prefab 实例化之后。

沿链路检查：

```text
SpellCaster.SpawnForwardProjectile
-> Instantiate
-> GetComponent<ProjectileBase>
```

发现 prefab 根物体只有 `ProjectileShield`，没有 `ShieldProjectile`。所以它不是合法 Emit 投射物。

修复方式是：

```text
根物体挂 ShieldProjectile
子 Trigger 挂 ProjectileShield
```

这个问题非常适合作为学习案例：当你看到“资源消耗和音效成功，但实体看不到”，不要直接怀疑特效透明、速度太快，而要沿运行链路判断系统执行到了哪一层。

### 7.3 第三坑：护盾不能反弹自己

移动护盾的 prefab 通常是：

```text
Root: ShieldProjectile
Child: ProjectileShield Trigger
```

子 Trigger 和根投射物在父子层级里。如果不做过滤，`ProjectileShield.OnTriggerEnter` 可能通过：

```csharp
other.GetComponentInParent<ProjectileBase>()
```

找到自己的根 `ShieldProjectile`，然后试图反弹自己。

所以加了：

```csharp
if (projectile == _ownerProjectile)
    return;
```

这属于复杂 Prefab 层级下的自我过滤问题。很多投射物、近战判定、范围技能都会遇到类似情况。

### 7.4 第四坑：反弹后阵营和碰撞忽略关系要刷新

反弹敌方投射物时，投射物的阵营会从敌方改成玩家方。

但项目里有一个“同阵营投射物互相忽略碰撞”的机制。如果只改 `_attackerTeam`，不刷新 Physics ignore 关系，可能出现反弹后的投射物仍然和不该碰的对象发生碰撞。

所以 `ReflectByShield` 里调用：

```csharp
RefreshSameTeamProjectileIgnores();
```

这类问题属于“状态变化后，依赖该状态的缓存关系也要更新”。

## 8. Unity API 与字段解释

### Rigidbody.linearVelocity

Unity 6 中用于设置刚体速度：

```csharp
_rb.linearVelocity = velocity;
```

旧版本常见的是 `Rigidbody.velocity`。你当前项目使用 Unity 6，因此代码里用 `linearVelocity`。

### Rigidbody.useGravity

控制刚体是否受 Unity 物理重力影响：

```csharp
_rb.useGravity = useGravity;
```

本项目中，普通火球默认不受重力；如果前面有“重力修正”法术，`cmd.UseGravity` 会变成 true，再传入 `ProjectileBase.Init`。

### CollisionDetectionMode.ContinuousDynamic

用于高速物体防穿透：

```csharp
_rb.collisionDetectionMode = CollisionDetectionMode.ContinuousDynamic;
```

高速投射物如果使用默认离散碰撞检测，可能一帧前在墙前，一帧后已经穿过墙。连续碰撞检测可以减少这种问题。

### Physics.IgnoreCollision

让两个 Collider 互相忽略碰撞：

```csharp
Physics.IgnoreCollision(_collider, casterCollider);
```

用途：

1. 投射物生成瞬间不撞到施法者。
2. 同阵营投射物互相忽略，避免连发火球互相撞开。
3. 护盾 Trigger 忽略释放者 Collider。

### GetComponentInChildren / GetComponentInParent

查找子级或父级组件：

```csharp
GetComponentInChildren<ProjectileShield>()
other.GetComponentInParent<ProjectileBase>()
```

这两个 API 在复杂 prefab 中非常常用。护盾反弹范围在子物体上，所以 `ShieldProjectile` 用 `GetComponentInChildren` 找到它；进入 Trigger 的可能是投射物子 Collider，所以 `ProjectileShield` 用 `GetComponentInParent` 找到根投射物。

### Destroy

销毁 GameObject：

```csharp
Destroy(gameObject, _maxLifetime);
Destroy(_ownerProjectile != null ? _ownerProjectile.gameObject : gameObject);
```

护盾次数耗尽时，如果它属于移动护盾投射物，就销毁根 `ShieldProjectile`；否则销毁自己。

## 9. 大厂面试 Q&A

### Q1：为什么可交互护盾最终设计成 Emit，而不是 StaticProjectile？

答：因为它的核心语义是“从施法点沿方向发射出去”，而不是“在某个点生成一个静态区域”。如果做成 `StaticProjectile + Rigidbody`，它虽然能动，但会形成一套平行于 `ProjectileBase` 的运动系统，后续重力、弹跳、追踪、轨道都要重复适配。做成 `Emit + ShieldProjectile : ProjectileBase` 后，它能自然复用项目已有投射物生命周期和 Modify 系统。

### Q2：为什么不新增一个 SpellKind.Shield？

答：因为 `SpellKind` 应该表达解释器层面的执行语义，而不是具体技能类型。护盾投射物本质仍然是一个 Emit 产物，只是 prefab 上挂的是 `ShieldProjectile`。如果为每种特殊法术都加 `SpellKind`，解释器会退化成技能表分支，不利于法术编程系统扩展。

### Q3：为什么需要 `TryHandleCollisionBeforeDefault`？

答：`ProjectileBase` 的默认碰撞语义是命中后造成伤害、触发 payload、销毁。但护盾投射物不应该撞到墙或敌人就像火球一样爆炸，所以需要一个子类可重写的 seam。普通投射物不重写，行为不变；`ShieldProjectile` 重写并返回 true，表示拦截默认命中流程。

### Q4：反弹敌方投射物时为什么要修改 attackerTeam？

答：因为伤害结算使用投射物当前的阵营过滤目标。如果只改变速度，敌方投射物飞回敌人身边时仍然属于敌方阵营，可能不会伤害敌人。反弹后把 `_attackerTeam` 和 `_attackerId` 改为护盾释放者，才能实现“借敌人的火球反打敌人”的玩法。

### Q5：为什么 `ProjectileShield` 不直接继承 `ProjectileBase`？

答：因为它不是投射物本体，而是反弹检测区域。这样拆分后，旧静态护盾和新移动护盾都能复用同一个 `ProjectileShield`。移动能力放在 `ShieldProjectile`，反弹能力放在 `ProjectileShield`，职责更清晰。

### Q6：这个功能如何避免破坏已有火球、箭、陨石？

答：新增的 collision seam 默认返回 false，普通投射物不重写它，因此仍然走原来的命中、伤害、payload、销毁流程。只有 `ShieldProjectile` 重写该 seam。这样是开放封闭原则：对扩展开放，对已有行为修改最小。

### Q7：如果未来想让护盾有血量，你会怎么扩展？

答：我不会把血量硬写进 `ProjectileShield`。更合理的是抽象一个可受击的护盾组件，比如 `ShieldHealth` 或让护盾实现某种受击接口，再把“次数耗尽销毁”和“血量耗尽销毁”并列成两个资源维度。投射物反弹仍由 `ProjectileShield` 负责，护盾生命由独立组件负责，避免一个类职责过大。

### Q8：如果多个护盾互相反弹投射物，会不会有循环问题？

答：当前反弹只是改变投射物速度、阵营和方向，没有立刻递归触发新的反弹调用；下一次反弹必须等物理系统产生新的 Trigger 事件。因此不是同步递归，不会栈溢出。但可能出现玩法上的来回弹，这属于设计层面可以调反弹次数、生命周期、速度衰减来控制。

## 10. 模拟面试者完整讲解

这个功能的目标是做一个“可交互护盾法术”。它不是传统意义上原地生成的防御罩，而是一个可以像火球一样发射出去的护盾投射物。它在飞行过程中可以反弹进入范围的投射物，并且能被已有的重力、弹跳、追踪、轨道、多重射击等法术修正影响。

我首先做的是语义判断：这个法术应该属于 `Emit`，而不是 `StaticProjectile`。因为玩家预期是“从法杖方向发射出去”，这意味着它需要发射方向、初速度和投射物生命周期。如果把它做成静态投射物再额外加 `Rigidbody`，短期可以动，但长期会复制一套和 `ProjectileBase` 平行的运动系统，导致 Modify 法术需要适配两套目标。因此我最终把它设计成 `ShieldProjectile : ProjectileBase`。

在架构上，我保持了现有法术系统的解释器模型。`SpellDefinition` 保存护盾的配置，比如 `ShieldReflectCount`；`CastEvaluator` 把它 bake 到 `EmitCommand`；`SpellCaster` 负责运行时实例化 prefab，并在发现生成的是 `ShieldProjectile` 时把反弹次数注入进去。这样 `Game.Skills` 仍然是纯数据和纯解释器，`Game.Character` 仍然只是运行时桥接，真正的投射物和碰撞逻辑仍然放在 `Game.Combat`。

在 Combat 层，我把“会飞的护盾”和“反弹检测区域”拆成两个组件。`ShieldProjectile` 是根物体上的投射物脚本，它继承 `ProjectileBase`，所以能复用速度、重力、弹跳、追踪、轨道、生命周期等已有能力。`ProjectileShield` 是子 Trigger 上的反弹组件，它只负责检测进入范围的 `ProjectileBase`，计算护盾法线，然后调用 `ReflectByShield` 改变投射物速度和阵营归属。

为了不破坏普通火球的默认命中逻辑，我在 `ProjectileBase` 中加入了一个很小的扩展点 `TryHandleCollisionBeforeDefault`。默认返回 false，所以老投射物行为不变；`ShieldProjectile` 重写后返回 true，用来拦截默认的伤害、payload 和销毁流程。这个 seam 让护盾能参与碰撞，但不会像火球一样撞到东西就爆炸。

调试过程中最典型的问题是 prefab 配置错误。测试时出现过 mana 和音效正常，但看不到护盾飞出去。沿链路排查后发现 `SpellCaster` 已经执行到实例化，但 prefab 根物体没有 `ShieldProjectile`，因此 `GetComponent<ProjectileBase>()` 失败，运行时把对象销毁了。这个问题说明在 Unity 项目里，Prefab 组件结构本身就是架构的一部分，不只是资源配置。

最终这个功能的价值在于，它不是单独做了一个护盾技能，而是把护盾作为法术编程系统里的一个可组合元素接入了现有架构。它能被 Modify 影响，能被 Multicast 复制，能被 Trigger payload 延迟释放，也能和敌方投射物形成反弹玩法。这比单独写一个硬编码技能更符合 Noita-like 法术编程的核心。

## 11. 后续可扩展方向

1. 护盾血量：让护盾不只按反弹次数消耗，也能被攻击打破。
2. 反弹速度倍率：被反弹投射物可以加速或减速。
3. 反弹角度扰动：避免所有反弹都过于规则。
4. 阵营规则配置：允许某些护盾只反弹敌方、只反弹玩家方、或全部反弹。
5. 护盾碰撞伤害：让护盾本体撞到敌人时产生推开或少量伤害。
6. 护盾持续时间 UI：给玩家反馈剩余次数或剩余时间。

这些扩展都应该继续遵循当前边界：数据进 `SpellDefinition`，解释进 `EmitCommand`，运行时桥接放 `SpellCaster`，碰撞和物理行为放 `Game.Combat`。
