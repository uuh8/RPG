## P8 总体目标与学习路线

P7 已经证明 Wizard 可以完成一张连续关卡：进入 Encounter、击败 Enemy、打开 Gate、获得 Run-scoped Spell Reward、编辑 Runtime Wand，并通过 Pause、Fade、Main Menu 和 ElementWorld 形成一局可玩的 Demo。P8 不重新制作这套流程，而是在它的终点继续向前：地图一最终两名 Elite 被击败后，玩家获得一次“完整法术能力毕业”的奖励，并通过 Portal 进入一张开阔的地图二；离开 Safe Zone 后，一个不会因距离而脱战、不会主动后退、会根据战况选择不同 Wand Program 的三阶段法师 Boss 持续追击玩家。玩家必须利用完整 Spell Library、Water/Fire ElementWorld 和法术编程能力取胜，失败后可以重试 Boss 或重开整局，胜利后可以重开或返回 Main Menu。

这个阶段的学习重点不只是“多写一个 Enemy Controller”。它把多个 Unity 客户端常见难题放进同一条可验证链路：`DontDestroyOnLoad` 应该保存什么、不应该保存什么；如何让 Authoring `ScriptableObject` 与跨 Scene Runtime State 分离；如何用 Utility AI 选择人工设计的技能包；如何让 Phase Transition、Cast 和 Teleport 共享动作所有权；如何使用 `NavMesh` 与 Physics 查询随机一个不穿模的位置；如何让 UGUI Boss Bar 只展示权威 Gameplay 数据；以及如何用 Scene Reload 同时重置 Boss、Player、Status 和 Sparse ElementWorld。P8 完成后，它将成为比单个技能更完整的简历项目：既能展示玩法，也能展示架构、AI、Physics、性能和 Debug 方法。

# Task 0：冻结 P8 终局方案，建立跨模块实施基线

Task 0 的目的不是“先创建几个空脚本”，而是把一个容易无限膨胀的 Boss 想法收敛为可以逐项验收的工程方案。我们已经确认地图二使用商城 Scene 的项目副本，Boss 第一版复用放大的 Elite Magic Enemy，法术不由 AI 临时乱拼，而是由开发者事先设计 7 套 `WandLoadout` Program，再由 Utility 根据距离、Player 状态、Boss Phase、Cooldown 和最近使用记录选择。我们也明确了地图一 Reward 与 Portal 的双保险、Session 只在当前应用进程内存活、Boss Entry Trigger 后永久索敌、三段 Phase、动态安全 Teleport、Boss HUD，以及 Retry Boss 与 Restart Run 的不同数据语义。Task 0 在整体架构中的位置相当于“施工图”：它先决定每个模块拥有什么真相，避免后续把跨 Scene 数据塞进 Player、把 AI 决策塞进 UI，或者为了播放 Portal 特效让 Gameplay 依赖表现层。

## 1. 玩家看到的结果，系统内部实际上发生了什么

```text
地图一最终 Encounter 完成
-> 地图一只进入 StageCleared，不进入最终 Victory
-> 全法术 Reward 与 Stage Exit Portal 解锁
-> Reward 或 Portal 调用同一个 EnsureAllSpellsUnlocked
-> Fade 加载 P8_BossField
-> 持久化 Session 提供 Runtime Library / Runtime Wand
-> Scene-local Player、Camera、UI、Boss、ElementWorld 重新创建
-> Boss Entry Trigger 捕获 Wand Checkpoint 并激活 Boss
-> Utility AI 选择 Wand Program 或 Teleport
-> SpellCaster 继续调用 CastEvaluator
-> ProjectileBase 继续进入统一 Combat / Status / ElementWorld 链路
-> Boss 或 Player Death 产生最终 Victory / Defeat
```

最容易混淆的一点是：**跨 Scene 保留一局数据，不等于把整个游戏世界跨 Scene 搬过去。** 如果把 Player、Camera、UI、Boss 和 ElementWorld 全部放进 `DontDestroyOnLoad`，新 Scene 里的对象会与旧对象重复，Inspector 引用也容易指向已经卸载的对象；Sparse ElementWorld 还会把地图一的 Chunk 数据带到地图二。P8 只让 `RunSessionCoordinator + RunSpellSession` 常驻，因为它们保存的是体量小、含义明确的 Runtime Data。Player、Boss、Status 和 ElementWorld 继续属于 Scene；重新加载地图二时，它们自然回到干净初始值，这正是 `Retry Boss` 想要的结果。

## 2. 为什么地图一需要 `StageCleared`，而不是继续使用 `Completed`

P7 的 `RunProgressTracker` 认为“最后一个 Encounter 完成”就等于整局 `Completed`。这在只有一张地图时正确，因为 `DemoPauseMenuController` 收到 `Completed` 后会暂停并显示 Victory。但 P8 中，两名 Elite 只是地图一的终点，不是整局终点。如果仍然发布 `Completed`，Portal 刚出现游戏就会被 Terminal UI 暂停，玩家根本无法正常走进去。

因此 P8 会增加非 Terminal 状态 `StageCleared`：

- `Running`：地图一 Encounter 仍在进行。
- `StageCleared`：地图一已完成，但玩家还能拾取 Reward、编辑 Wand、进入 Portal。
- `Completed`：地图二 Boss 已死亡，整局最终胜利。
- `Failed`：Player 死亡，进入失败结算。

这不是简单增加一个 enum 值，而是在区分两种层级：“一个 Stage 完成”和“整个 Run 完成”。`DemoPauseMenuController`、`WandEditorController` 只能把 `Completed/Failed` 当作 Terminal；`StageCleared` 不得抢走 `Time.timeScale` 和 Cursor 所有权。

## 3. Reward 与 Portal 为什么必须调用同一个幂等规则

玩家拾取全法术 Reward 是正向反馈：击败两个 Elite 后看到奖励、主动走过去拾取，会产生明确的成就感。但完整 Spell Library 又是 Boss 战的基础条件。如果玩家没看到 Reward、故意绕开，或者 Portal 与 Reward 的位置允许先碰到 Portal，就不能让地图二的玩法基础随机缺失。

最终采用“双入口、单规则”：

```text
AllSpellsRewardPickup ─┐
                       ├─> RunSpellSession.EnsureAllSpellsUnlocked(fullLibrary)
StageExitPortal ───────┘
```

`EnsureAllSpellsUnlocked` 必须幂等：第一次补齐缺少的 SpellDefinition；第二次发现全部已存在，返回 false，不创建重复项，不重复发布 Reward Granted 事件。Runtime Library 的数组是独立容器，但其中的 SpellDefinition 仍引用只读 Project Asset，这叫 shallow copy。我们隔离的是“本局有哪些法术、顺序如何”，不是复制每一张不会在运行时修改的法术定义。

全解锁只影响 Palette，不自动把 15 张 Spell 塞进 Runtime Wand。原因是 Wand 本身是一段程序，顺序和 Draw Budget 会改变语义；自动填满等于替玩家做出构筑决策，也可能产生不可控的大量投射物。

Portal 也不能从 `Game.Run` 直接调用 `Game.UI.DemoSceneTransitionController`，否则底层流程模块会反向依赖表现模块。正确链路是 `StageExitPortal` 发布 `SceneTransitionRequestedEvent`，已经依赖 `Game.Run` 的 UI 层消费请求，再执行现有 Fade 和 `LoadSceneAsync`。同理，Portal Open/Idle/Close 由表现组件消费状态事件；它们不决定玩家是否满足进入条件。

## 4. Boss 为什么选择人工 Program + Utility，而不是随机拼法术

这里采用的是用户确认的 B 方案：开发者事先设计高质量 Wand Program，AI 只决定当前使用哪一套。它位于“完全脚本化技能序列”和“运行时自由生成法术”之间：

| 方案 | 优点 | 缺点 | P8 结论 |
|---|---|---|---|
| 固定循环 | 最容易调试和做 Telegraph | 玩家很快背板，状态系统没有参与决策 | 不采用 |
| 人工 Program + Utility | 组合质量可控，同时能响应距离、Status、Phase | 需要设计评分、Cooldown 与防重复 | **采用** |
| AI 现场拼 Spell | 组合空间最大 | 很难保证 Trigger、Draw Budget、可读性和性能 | P8 不采用 |

AI 的聪明不等于“随机性更大”。P8 的聪明体现在它观察明确的 Context，并在开发者配置的候选中选择更合适的动作。例如正值 Wet Modifier 可让某个 Program 随 Player Wet 强度提高分数，近距离偏好可承接贴身压力；刚用过的 Program 因 Recent-use Penalty 降权，避免连续重复；Phase 3 则可通过倍率和全局节奏开放更具压迫感的选择。

Utility Evaluator 必须是纯逻辑：输入值快照，输出 Program Index。它不调用 `Instantiate`、不访问 Scene、不播放 Animator，因此可以用 EditMode Test 精确验证。运行时 Controller 只在固定 Decision Interval（例如 0.2 秒）构造无分配 Context，并读取预分配的 Program Runtime State。这样比每帧遍历、LINQ 排序和创建临时 List 更符合项目的 0 B `GC Alloc` 规则。

## 5. Boss Wand Program 如何继续复用现有解释器

P8 不会按具体技能名为 Boss 编写一批硬编码施法方法。Boss 的 Wand 仍然是程序：

```text
WandLoadout
-> CastEvaluator
-> EmitCommand
-> SpellCaster
-> ProjectileBase
-> IDamageable / Status / ElementWorld
```

当前确定的七类组合是：加速直弹、三重散射、追踪弹、命中触发花火、延时区域封锁、增伤陨石、静态护盾加轨道 Water 控制。一个重要基础知识是：`Multicast` 只增加 Draw Budget，不会复制后面的 Fireball。因此三重散射必须写成：

```text
TripleShooting -> Scattering -> Fireball -> Fireball -> Fireball
```

Trigger Program 更能体现解释器价值：

```text
TriggerFireball
-> 捕获后面的严格 suffix 作为 payload
-> 命中时以 Draw Budget = 1 重新求值
-> TripleShooting 把预算增加到 3
-> 三张 Fireball 产生三条 EmitCommand
```

Boss 与 Player 的区别只在资源策略：Boss 不使用 Mana，而由 Cast Interval、Program Cooldown、Phase 和 Recent-use 约束；Player 仍使用现有 `ManaComponent`。因此 `SpellCaster` 会新增“显式 Wand + Mana Policy”入口，但底层 `RunCast`、Payload、Projectile 和 Combat Funnel 不分叉。

## 6. 为什么 Boss 使用独立 FSM，而不是继续继承普通 Ranged Enemy

普通 `RangedEnemyController` 的设计目标是杂兵：进入 Detect Radius 后索敌，超出 Lose Radius 后脱战，并在过近时 Kite/MoveAway；受到有 Hit Reaction 的攻击时会进入 Hurt State。P8 Boss 的契约正好不同：

- Entry Trigger 后永久索敌。
- 不主动后退。
- Cast、Teleport、Phase Transition 必须完整执行。
- Phase 切换需要 Pending 状态、Telegraph 与短暂无敌。
- 普通受击不能随意把 Action Lock 中的动作打断。

如果强行继承普通 Ranged Enemy，就需要不断绕开基类的 Perception Tick、Kite、Hurt 和 private Update，最后得到一个“名义复用、实际全覆盖”的脆弱子类。因此计划创建专用 `BossStateMachine`，但继续复用底层能力：`CharacterController`、`Animator`、`HealthComponent`、`StatusController`、`SpellCaster` 和 EventBus。这个 trade-off 是少量移动/转向代码重复，换来清晰且可测试的 Boss 行为边界；它不是复制伤害或法术系统。

Boss FSM 第一版包含：

```text
Inactive
-> Approach
-> Decision
   ├─ Cast
   ├─ Teleport
   └─ Approach
-> Pending Phase Transition（当前动作结束后）
-> Phase Transition
-> Decision
```

所有 State 都是普通 C# 对象，在 `Awake` 预创建并复用。`Action Lock` 是 Cast、Teleport、Phase Transition 的互斥所有权：谁先开始，谁负责在 `Exit/Complete` 时释放。这样不会出现同一帧既 Spawn Projectile 又禁用 CharacterController Teleport 的竞态。

Phase Transition 的无敌也不能只存在于 Boss Controller 的一个 bool，因为真正扣血发生在 `HealthComponent.ReceiveHit`。P8 会让 Combat 权威增加 `IsInvulnerable` 与 `SetInvulnerable(bool)`：Phase State 进入时设为 true，`Exit` 中无条件恢复 false；无敌时在进入 `DamagePipeline` 前直接拒绝该次伤害。当前只有 Phase Transition 一个无敌 Owner，所以 bool 足够清楚；未来若 Shield、Buff 等多个来源都能申请无敌，再升级为 Token 或引用计数。

## 7. 动态 Teleport 为什么不能只用 `Random.insideUnitCircle`

“在 Player 周围随机一个点”只解决了数学位置，没有解决游戏世界合法性。随机点可能在墙里、树里、Terrain 下、陡坡上、Arena 外，或者虽然脚底有地面，但 Boss 的头部与障碍重叠。

P8 的 Teleport 采用多层筛选：

1. 在 Player 周围 `[MinRadius, MaxRadius]` 环带生成候选角度与距离。
2. 检查候选是否位于明确的 Boss Arena Bounds 内。
3. 用 `NavMesh.SamplePosition` 找附近可行走位置。
4. 从上方向下做 Ground Raycast，得到真实地面点和 Normal。
5. 用 `Vector3.Angle(normal, Vector3.up)` 检查坡度。
6. 按 Boss `CharacterController.radius/height/center` 计算 Capsule，用 `Physics.CheckCapsule` 检查完整身体空间。
7. 最多尝试固定次数；全部失败就取消 Teleport，不使用“最不坏”的穿模点。

目标点在 Telegraph 开始前一次性确定，不在每帧追着 Player 改。真正位移时临时禁用 `CharacterController`，设置 Transform，再重新启用并清理垂直速度。PortalBlue Open/Idle/Close 只是对这个合法位移的视觉说明；VFX 不能反过来决定 Boss 坐标。

## 8. Scene 副本、Safe Zone 与 ElementWorld 的边界

地图二使用 `Scene_MeadowEnvironment_01_Summer` 的项目内副本 `P8_BossField.unity`。完整 Duplicate 的优点是保留商城作者已经调好的 Terrain、植物、Lighting 和 Volume 组合；缺点是未来商城包更新不会自动合并到项目副本。但对一个需要稳定录制和 Build 的 Boss Demo，这比直接修改 Vendor Scene 更安全。

副本中需要技术性处理的是“系统冲突”，不是要求重新设计地图：

- 保留目标开阔区域的 Terrain、TerrainCollider、Environment、Lighting。
- 移除或禁用 Vendor Main Camera、演示 Follow Target、重复 Audio Listener 和重复 EventSystem。
- 接入项目自己的 WizardPlayer、Camera Rig、Input、UGUI、Fade、Pause、Wand Editor。
- Safe Zone 负责无战斗的落点与编程时间；Boss Entry Trigger 是永久交战的唯一授权点。
- P8 使用独立 ElementWorld Profile，Interest Point 指向 WizardPlayer；商城 Terrain 仍是宏观世界，Sparse Cell 只承载 Water/Fire Gameplay。

这里要保留 P6 性能经验：`Resident Chunk` 表示数据仍存在，不等于该 Chunk 每个 Tick 都需要 Solver。地图二更宽广、商城草木和透明 VFX 更多，因此必须继续区分 ElementWorld Simulation 与 Rendering 成本，防止把 `FixedUpdate` catch-up 或 Solver 活跃集问题误判成“水面没画好”。

## 10. 测试策略、已知风险与 Debug 起点

P8 的测试分为四层：

1. **EditMode Pure Logic：** 全 Library 合并、Checkpoint Copy、Phase Resolver、Utility Score、Teleport Candidate Math。
2. **PlayMode Component Integration：** Reward 显隐、Portal 兜底、Boss 激活、Action Lock、Phase 延迟切换。
3. **完整双地图 Playthrough：** 拾/不拾 Reward、Retry Boss、Restart Run、Victory Main Menu。
4. **Development Build + Profiler：** Scene List、Fade、Cursor、Session 单例、CPU/GPU、0 B `GC Alloc`。

当前最值得提前防范的风险包括：

- `RunSpellSession` 没有跨 Scene 所有权，Scene 卸载时 Runtime Clone 被销毁。
- 地图一仍发 `Completed`，导致 Portal 出现时 Terminal UI 立即暂停。
- Map2 Inspector 无法引用 Map1 的 Scene Object，`SpellCaster/WandEditor` 回退到旧 Authoring Wand。
- Multicast Program 只放一张 Fireball，误以为会自动复制。
- Boss 复用普通 Perception 后，Player 拉远会意外脱战。
- Teleport 只检查脚底点、不检查 Capsule，放大 Boss 后头部/身体穿模。
- Phase 在 Cast 中立即切换，导致 Projectile Release 或 Action Lock 丢失。
- Retry 只 Reload Scene 但没有恢复 Checkpoint Wand，或者 Restart Run Reload 地图二却没有清 Session。
- Portal VFX Prefab 被误当作 Gameplay Portal，实际没有 Trigger/Session/Load 逻辑。

每次出现问题都要按“症状 -> 权威数据 -> 事件 -> Runtime Adapter -> Scene/Inspector 引用”的方向定位，而不是先随意改数值。例如地图二 Palette 为空但 Wizard 仍发旧火球，应首先检查 `RunSpellSession.Current`、Runtime Library/Wand 和 `SpellCaster` 数据源，而不是怀疑 CastEvaluator。

## 11. Trade-off 与当前不做的内容

- 不做跨应用 Save：省去版本迁移、序列化 Asset GUID 和坏档处理，符合当前单局 Demo；代价是退出应用后必须重玩。
- 不做自由生成 Wand：保证 Telegraph、伤害和性能可控；代价是 Boss 组合上限由 7 套 Program 决定。
- 不做手工 Teleport Point：提高不同地图区域的复用性；代价是运行时需要 NavMesh/Physics 多层查询。
- 不让 Player 常驻：Scene Reload 可以干净重置 Combat 与 ElementWorld；代价是必须显式从 Session 重新绑定 Runtime Spell Data。
- 不在 P8 更换专用 Boss 模型：优先验证 Gameplay/AI；代价是视觉唯一性先靠 Scale、HUD、Phase 和 VFX 表达。
- 不补 P3～P5：它们仍在总体路线图中，但不阻塞 P7 -> P8 的完整流程。

## 12. 模拟面试回答：如果面试官问“你如何设计这场法术型 Boss 战”

> 我先把 Boss 战拆成跨 Scene Run、Boss 决策和表现三层。地图一结束时没有直接进入最终 Completed，而是增加非 Terminal 的 StageCleared，让玩家可以拾取全法术奖励或进入 Portal。Reward 和 Portal 都调用同一个幂等 EnsureAllSpellsUnlocked，所以即使玩家跳过奖励，进入地图二前也一定拥有完整 Runtime Library，同时不会修改 Authoring ScriptableObject。
>
> 跨 Scene 时我只让轻量 Run Session 使用 DontDestroyOnLoad，保存 Runtime Library、Runtime Wand、当前 Stage 和 Boss Checkpoint；Player、Camera、Boss、Status 与 Sparse ElementWorld 都保持 Scene-local。这样 Retry Boss 只要保留 Session 并重新加载地图二，就能自然重置血量、法力、状态、Boss 和元素世界，再恢复进入 Boss 区域时的 Wand 快照。
>
> Boss 不会在 Runtime 随机拼 Spell，而是使用开发者在 Inspector 中编排的 Wand Program。Utility Evaluator 根据距离、Player Wet、移动速度、Phase、Program Cooldown 和 Recent-use Penalty 评分；它是纯逻辑并有 EditMode Tests。AI 只决定选择哪个 Program，真正施法仍走 CastEvaluator、EmitCommand、SpellCaster、ProjectileBase 和统一伤害管线，因此 Boss 没有复制第二套技能系统。
>
> 行为层使用预创建的 Boss FSM。Boss 通过 Entry Trigger 激活后永久锁定 Player，不依赖普通敌人的 Detect/Lose Radius，也不会主动后退。Cast、Teleport 和 Phase Transition 共享 Action Lock；跨越 70% 和 35% HP 阈值时先完成当前动作，再进入约 1.2 秒无敌但不回血的 Telegraph。
>
> Teleport 不用预设点，而是在 Player 周围环形采样，通过 Arena Bounds、NavMesh、Ground Raycast、坡度和 Capsule Clearance 多层验证，固定次数内找不到合法点就取消。这样既有随机性，也不会穿模。最后由 EventBus 驱动 Boss HUD、Portal 与 Teleport VFX，表现层不反向决定 Gameplay。整个系统用 EditMode、PlayMode、双地图 Playthrough、Development Build 和 Profiler 分层验收，并要求 Boss 热路径 0 B GC Alloc。

# Task 1：建立跨 Scene Run Session、全法术合并与 Boss Checkpoint

Task 1 解决的是 P7 单 Scene Runtime Data 无法自然延伸到两张地图的问题。P7 的 `RunSpellSession` 已经会从 `SpellLibrary` 和 `WandLoadout` Authoring Template 创建 Runtime Clone，因此玩家拾取奖励或编辑法杖不会污染 Project Asset；但它仍属于 `P7_DemoRun` Scene，Scene 卸载时 `OnDestroy` 会回收 Clone。P8 如果直接加载地图二，地图一获得的法术和玩家编排的 Wand 就会一起消失；反过来，如果简单把 Player、UI 或 ElementWorld 全部设为 `DontDestroyOnLoad`，又会制造重复 Camera、跨地图 Cell 污染和失效 Inspector 引用。本 Task 因此只让一个轻量 `RunSessionCoordinator + RunSpellSession` Root 跨 Scene 存活，并把本进程 Run Data 拆成 `RunStage`、`RunEntryMode`、Runtime Library/Wand 与 Boss Wand Checkpoint。全法术 Reward 和未来 Portal 共用幂等合并规则；Checkpoint 只复制法术数组与 `BaseDraws`，不保存 Player/Boss GameObject。代码位于 `Game.Run`，继续保持 `Game.Run -> Core/Combat/Skills` 的单向依赖；`SpellCaster`、`WandEditorController`、Portal、`StageCleared` 和 Scene Transition 仍留在后续 Task，没有在本 Task 越界修改。

## 1. 从 P7 的 Scene-local Clone 到 P8 的 Process-local Session

P7 的数据所有权是：

```text
P7_DemoRun Scene
-> RunSpellSession.Awake
-> Instantiate Starting SpellLibrary / Starting WandLoadout
-> Runtime Library / Runtime Wand
-> Scene 卸载
-> RunSpellSession.OnDestroy
-> 回收 Runtime Clone
```

这对“Restart 当前 Scene 就开始一局新游戏”是正确的，但不能表达 P8 的两张地图。Task 1 改为：

```text
P8_RunSessionRoot（DontDestroyOnLoad）
├─ RunSessionCoordinator
└─ RunSpellSession
     ├─ Runtime SpellLibrary
     └─ Runtime WandLoadout

地图一 Scene-local Player/UI ─┐
                              ├─ 读取同一 RunSpellSession.Current
地图二 Scene-local Player/UI ─┘
```

`DontDestroyOnLoad` 的关键不是“对象越多越安全”，而是只保留无法由新 Scene 自然重建的数据。Player HP、Mana、Status、Boss、Camera、UI 和 Sparse ElementWorld 都应在 Scene Reload 后回到初始状态；Runtime Library/Wand、当前 Stage 与 Checkpoint 才需要跨 Scene。这样 `Retry Boss` 可以重新加载 `P8_BossField`，让 Gameplay World 获得干净重置，再从轻量 Session 恢复进入 Boss 区域时的 Wand。

`RunSpellSession.Current` 是跨 Scene 消费者找到当前法术数据的稳定入口。`ClearRuntime()` 会销毁两个 Runtime Clone、清空实例字段，并且同步把 `Current` 设为 `null`，防止 Main Menu 或下一局读到 stale reference。`ResetFromTemplates()` 则先清理旧 Clone，再从 Starting Template 建立新容器；它只用于 New Run，不会在普通 Scene Load 中自动调用。

## 2. 全法术合并为什么使用“保留当前顺序 + 按 Authoring 顺序补缺”

完整 `SpellLibrary.asset` 是 15 张法术的权威集合，但 Runtime Library 可能已经包含地图一的起始法术和奖励。全解锁不能直接执行：

```csharp
RuntimeLibrary.Available = fullLibrary.Available;
```

这样会让 Runtime 与 Authoring Asset 共用可变数组，也会抹掉当前 Runtime 顺序。最终规则是：

1. 保留当前 Runtime Library 的全部顺序。
2. 从左到右扫描 Full Library。
3. 只把当前尚未拥有、且 Full Library 前面没有重复出现的 `SpellDefinition` 追加到末尾。
4. 若没有缺失项，返回 `false` 并复用原数组。
5. 比较采用 Asset 引用身份，而不是 `DisplayName` 字符串。

`RunSpellInventoryOps.TryMergeUniqueInOrder` 使用两次顺序扫描。对约 15 张法术，它的复杂度是 `O(n²)`，但发生在 Reward/Portal 这种低频离散事件；与创建临时 `List/HashSet` 相比，顺序和引用相等语义更直接，也不会把容器分配误带进未来的 Hot Path。只有确实存在缺失法术时才创建一次最终数组。第二次 Reward/Portal 调用返回 `false`、复用原数组，因此“玩家先拾 Reward、再进 Portal”不会生成重复法术或无意义分配。

这里继续使用 shallow copy：

```text
独立复制：SpellDefinition[] 数组容器
继续共享：每个 SpellDefinition Project Asset 引用
```

法术定义在运行时只读，没有必要 `Instantiate` 15 份；真正必须隔离的是“本局拥有哪些法术、排列顺序是什么”这组可变引用。

## 3. Boss Checkpoint 的深拷贝边界

`BossCheckpointSnapshot` 是 `readonly struct`，内部保存独立的 `SpellDefinition[]` 与 `BaseDraws`。构造 Snapshot 时复制一次数组；每次恢复时再次返回新数组：

```text
Runtime Wand A
-> Capture：复制数组
-> BossCheckpointSnapshot
-> Restore：再次复制数组
-> Runtime Wand B
```

为什么需要两次复制？第一次阻止玩家进入 Boss 区域后继续编辑 Runtime Wand 时污染 Checkpoint；第二次阻止恢复后的 Runtime Wand 再次编辑时反向污染 Checkpoint。SpellDefinition 资源引用仍然共享，所以空间成本只是很短的引用数组，不是复制完整 ScriptableObject。

Checkpoint 不保存 `WandLoadout` Runtime Object，也不保存 Player、Boss、Transform 或 Scene Handle。这一边界非常重要：跨 Scene 保存 Scene Object 引用，Scene 卸载后引用会变成 Unity 的 destroyed object 语义；保存纯数组和值数据才能稳定恢复。

`RunEntryMode` 明确区分三种入口：

- `NewRun`：从 Starting Template 开始。
- `EnterBossField`：第一次从地图一进入地图二，保留当前 Runtime Wand。
- `RetryBoss`：地图二重载后恢复 Boss Checkpoint。

`RunStage` 目前表示 `MapOne / BossField / Finished`。它与 `RunState` 不是同一个概念：`RunStage` 描述跨 Scene 位置；`RunState` 描述当前 Run 是否 `Running/Completed/Failed`。本 Task 没有提前增加 `StageCleared`，后者仍属于 Task 2。

## 4. 唯一 Coordinator、Unity 生命周期与重复 Root

`RunSessionCoordinator` 使用 `[RequireComponent(typeof(RunSpellSession))]`，确保两个所有者在同一独立 Root 上。它的 `Awake()` 执行三件事：

1. 检查是否已经存在权威 Coordinator。
2. 重复实例只记录诊断并销毁自身 Root，不覆盖旧 Session。
3. 首个实例若存在 Parent，先执行 `transform.SetParent(null, true)` 提升为 Scene Root，再调用 `DontDestroyOnLoad(gameObject)`；这是 Unity 对 DDOL 的硬性前提，不是可选的 Hierarchy 整理。

开发中识别到一个不能只靠“Coordinator 会去重”掩盖的 Unity 生命周期问题：同一 GameObject 上不同 `MonoBehaviour.Awake()` 的相对顺序不应被业务逻辑假定。新 Scene 的重复 Root 中，`RunSpellSession.Awake()` 可能先于 `RunSessionCoordinator.Awake()`。如果第二个 Spell Session 发现 `Current` 已存在就直接抛异常，Coordinator 还没获得执行机会，Scene Load 已经出现错误。因此最终行为是：重复 `RunSpellSession` 拒绝取得 `Current` 并保持未初始化；随后重复 Coordinator 回收整个 Root。测试 `SecondSession_DoesNotReplaceExistingCurrentOwner` 锁定了“旧 Current 保持不变、重复实例不初始化”的结果。

`RunSessionCoordinator` 的命令语义如下：

- `BeginNewRun()`：重建 Starting Runtime Clone，清空旧 Checkpoint，回到 `MapOne/NewRun`。
- `PrepareBossFieldEntry()`：只切换为 `BossField/EnterBossField`，不自动改变 Wand。
- `CaptureBossCheckpoint()`：从当前 Runtime Wand 捕获数组与 `BaseDraws`。
- `RestoreBossCheckpoint()`：恢复独立数组，并设置 `BossField/RetryBoss`。
- `ClearSession()`：回收 Runtime Clone、清除 Checkpoint；保留一个空 Coordinator，后续 Main Menu 可再次调用 `BeginNewRun()`。

保留空 Coordinator 而不是每次返回 Main Menu 都销毁并重建，减少了 DDOL Root 的竞争与初始化顺序；代价是 Main Menu 的 Start 流程必须显式调用 `BeginNewRun()`。该接入属于后续 Terminal/UI Task。

## 7. Trade-off、Debug 入口与面试表达

主要 trade-off 有三项：

- 使用 DDOL 轻量 Root，获得跨 Scene 数据连续性；代价是必须显式处理唯一实例、清理和 New Run 初始化。
- 使用 shallow copy，避免复制大量 ScriptableObject；代价是必须坚持 SpellDefinition 在运行时只读。
- 使用短数组的 `O(n²)` 顺序扫描，换取无临时容器、确定顺序和清楚的引用身份语义；如果未来 Library 扩展到数千项，再考虑缓存 Stable ID/HashSet，而不是为当前 15 张法术过度设计。

```text
-> Stage / EntryMode
-> HasBossCheckpoint
-> Runtime Wand 数组与 Snapshot 是否隔离
```

如果地图二 Palette 为空但仍能发旧火球，优先检查消费者是否仍回退到 Inspector Authoring Wand，而不是先怀疑 `CastEvaluator`。如果 Retry 后 Wand 变成 Boss 战中途的版本，检查 Capture 时机与 Snapshot 数组隔离；如果切 Scene 后出现两份 Root，检查每张 Scene 是否误放 Session Root，以及重复 Coordinator 是否在 Awake 自毁。

# Task 2：地图一 Stage Clear、全法术 Reward 与 Portal 双保险

Task 2 把地图一最终两名 Elite 的死亡从“整局已经胜利”改成“本张地图已经清场，但玩家仍可自由行动”。玩家看到的结果是：Victory Panel 不弹出，游戏不暂停；完整法术 Reward 与出口 Portal 同时开放。玩家可以先拾取 Reward、打开 Wand Editor 编排完整的 15 张法术，也可以故意绕过 Reward 直接进入 Portal。无论选择哪条路径，Portal 都会在发出 Scene Transition 请求前再次调用同一个幂等全解锁接口，因此地图二不会因为漏捡世界物品而缺少法术。Gameplay Root 只负责 Collider 权限、Session 更新和事件发布；三个现有 `PortalBlueOpen / Idle / Close` Prefab 由 `Game.UI` 的表现组件复用，不承担碰撞和 Scene Load。实现过程中还识别并修复了一个输入边界：`CanvasGroup.blocksRaycasts` 只能阻止 UGUI，不能阻止 `Input System` 的移动与施法，因此 Fade Out 期间新增独立 `SceneTransition` Pause Reason，真正冻结 Gameplay。

## 1. `StageCleared` 为什么不是另一种 Victory

P7 的 `RunProgressTracker` 在最后一个 Encounter 完成后固定进入 `Completed`。`DemoPauseMenuController` 收到该状态会申请 `TerminalResult` 暂停并显示 Victory Panel；这对单 Scene Demo 正确，但 P8 后面还有地图二 Boss。如果继续复用 `Completed`，就会出现“传送门已经打开，但玩家被胜利界面暂停，无法走进去”的逻辑矛盾。

Task 2 新增 `RunCompletionMode`：

```text
TerminalVictory -> 最后 Encounter -> RunState.Completed
AwaitStageExit   -> 最后 Encounter -> RunState.StageCleared
```

默认值保持 `TerminalVictory = 0`，因此旧的 `DemoRunDefinition` 即使尚未在 Inspector 修改，也不会突然改变 P7 行为。地图一的 Definition 显式选择 `AwaitStageExit` 后，`StageCleared` 只表示“没有下一场 Encounter 可以 Arm”；它不是 Terminal State。`DemoPauseMenuController`、`WandEditorController` 与 `DemoRunHudController` 原本就只对 `Completed/Failed` 执行 Terminal 行为，因此无需把 `StageCleared` 加入暂停条件。反过来，玩家如果清场后、进 Portal 前仍收到致命伤害，`FailRun()` 允许 `StageCleared -> Failed`，避免产生“已经清场所以不会死亡”的错误无敌窗口。

## 2. Reward 与 Portal 的双保险为什么必须共享同一个接口

`AllSpellsRewardPickup` 和 `StageExitPortal` 都调用：

```text
RunSpellSession.EnsureAllSpellsUnlocked(fullLibrary)
```

这个接口在 Task 1 已锁定三项语义：只向 Runtime Library 追加缺失引用；保持现有顺序并按 Full Library 的 Authoring 顺序补缺；没有变化时返回 `false` 且复用原数组。因此 Reward 先调用、Portal 再调用不会重复增加法术，也不会制造无意义数组分配。

运行顺序被刻意固定为：

```text
最终 EncounterCompletedEvent
  -> AllSpellsRewardPickup 开启 Trigger/Visual
  -> StageExitPortal 开启 Gameplay Trigger + 发布 Opening 表现事件

Player 进入 Portal
  -> 验证 Player Layer 与一次性 Gate
  -> EnsureAllSpellsUnlocked
  -> RunSessionCoordinator.PrepareBossFieldEntry
  -> 发布 Closing 表现事件
  -> 发布 SceneTransitionRequestedEvent("P8_BossField")
```

先补数据、后请求加载是可靠性边界。`EventBus.Publish` 是同步调用；如果先发布 Transition，再补法术，表现层可能立即启动 Scene Load，业务状态会依赖 Coroutine 与脚本执行顺序。现在即使玩家跳过 Reward，Scene 请求产生时 Runtime Library 已经完整，Coordinator 也已经是 `BossField/EnterBossField`。

两个世界对象的 GameObject Root 必须保持 active。所谓“初始隐藏”是指组件在 `Awake()` 中禁用自己的 Trigger Collider 和 Visual Root；如果把整个 Root 设为 inactive，它就不会订阅 `EncounterCompletedEvent`，最终战结束后也无法自行醒来。这是 Unity 生命周期中 `GameObject active` 与“表现是否可见”不能混为一谈的典型例子。

## 3. Fade 为什么需要独立的 Gameplay Pause Reason

`DemoSceneTransitionController` 已有全屏 `CanvasGroup`，Fade 时设置 `blocksRaycasts = true`。这个属性只参与 UGUI EventSystem 的 Raycast，不会屏蔽 `PlayerInput`、`InputAction` 或 `PlayerControllerBase.Update()`。如果只依赖黑色 Canvas，玩家仍可能在 Fade Out 的 0.25 秒内移动、施法或触发第二个 Gameplay Collider。

Task 2 为 `[Flags] RunPauseReason` 增加 `SceneTransition`。`LoadScene()` 接受首次请求后立即通过 `RunPauseCoordinator` 申请暂停；Fade Coroutine 使用 `Time.unscaledDeltaTime`，所以 `Time.timeScale = 0` 不会让淡出停止。等屏幕完全变黑、准备调用 `LoadSceneAsync` 时，再由 Transition Controller 调用 `PrepareForSceneTransition()`，把 `Time.timeScale` 恢复为 1 并解锁 Cursor，防止全局状态污染新 Scene。

这也解释了为什么不能让 `DemoPauseMenuController` 在调用 `LoadScene()` 后立刻恢复 Time Scale：那会马上撤销 Transition Controller 刚申请的输入锁。现在 Pause Menu 只在没有 Fade Controller 的兼容回退路径中自行清理暂停；正常路径的加载边界由 Transition Controller 统一拥有。

## 8. Portal Open/Idle/Close 视觉时序优化

地图二底座验证通过后，开发者发现 Portal 有两个连续但根因不同的表现问题。第一，`PortalBlueOpen` 播放结束时会先“闪一下”再进入 Idle。资源审计显示 Open 主粒子长度为 1 秒，Scene 中 `PortalVfxController.Open Duration` 也恰好是 1 秒；而 Idle 根粒子启用了 `Prewarm`，因此终止 Burst 与一个已经预热到稳定密度的 Idle 在同一切换点形成明显亮度阶跃。代码默认值改为 0.8 秒，使 Controller 在终止帧前切换；现有 Scene 已序列化旧值，仍须在 Inspector 手动改为 0.8 后以真实画面验收。

第二，玩家看不到 `PortalBlueClose`，不是 Prefab 没有播放，而是 `StageExitPortal.TryEnter()` 在同一帧先发布 `Closing`、紧接着发布 `SceneTransitionRequestedEvent`。`EventBus` 同步执行，Fade Controller 当帧便开始盖黑屏，所以 Close 实例即使已经 active 也没有可见时间。修复后的顺序是：

```text
首次有效 Enter
-> 锁定重复 Trigger
-> 全法术兜底 + BossField Session 更新
-> RunPauseCoordinator.RequestPause(SceneTransition)
-> 发布 Closing，显示 PortalBlueClose
-> WaitForSecondsRealtime(CloseDuration)
-> 发布 SceneTransitionRequestedEvent
-> Fade Out / Load P8_BossField
```

这里必须使用 `WaitForSecondsRealtime`。Close 开始前已经把 `Time.timeScale` 设为 0，如果使用受缩放时间控制的 `WaitForSeconds`，等待永远不会推进，Portal 会关闭但 Scene 永远不加载。`SceneTransition` Pause Reason 由 Portal 提前申请，Fade Controller 随后幂等地申请同一个 Reason，并在 Scene Load 边界统一清理；这样 Close 阶段玩家也不能移动、施法或打开 UI。

`StageExitPortalTests` 已改为先断言收到一次 `Closing`、Scene 请求仍为 0、Pause Reason 已持有；经过短暂 realtime 等待后才允许 Scene 请求变为 1。RED 阶段得到缺少 `CloseDuration` 的 `CS1061`，实现后 `Game.Run.PlayMode.Tests.csproj` 与 `Game.Run.Tests.csproj` 均为 0 warning、0 error。静态构建不等于 Unity Coroutine 已实际运行，最终仍以本轮 Test Runner 和 Play Mode 视觉结果为准。

第一轮真实 Play Mode 暴露了时钟所有权的第二层问题：玩家进入后确实暂停 1 秒，但这 1 秒看不到 Close。检查 Prefab 序列化数据后确认，`PortalBlueClose` 内三个 `ParticleSystem` 的 `useUnscaledTime` 都是 false；也就是说 Coroutine 使用 realtime 只能保证“等待计时器”继续走，不能自动让“粒子模拟器”继续走。`Time.timeScale=0` 时，Close 实例已经被激活，但粒子停在第 0 帧，所以 1 秒后直接进入 P8。

最终修复由表现层 `PortalVfxController` 在 `Awake` 创建 Close Runtime Instance 后，遍历其中全部 `ParticleSystem`，把 `MainModule.useUnscaledTime` 改为 true。修改只作用于 Runtime Clone，不污染三个 Authoring Prefab；数组只在 `Awake` 分配一次，不进入每帧 Hot Path。回归测试使用包含根/子两个 ParticleSystem 的最小 Close Prefab，发布 `Closing` 后验证 Runtime Instance 已激活且所有粒子都使用 unscaled time。

复核还发现一条竞态：Portal Trigger 在 Opening 开始时已经开放，玩家可能在 `Open Duration` 结束前进入。旧实现收到 `Closing` 后没有停止 `OpenThenIdleRoutine`，因此 Close 可能先出现，随后又被尚未结束的 Coroutine 切回 Idle。现在 Idle/Closing 接管视觉前都会取消旧 Open Coroutine，保证 Close 一旦开始就保持唯一视觉所有权，直到 Scene Transition。

## 9. 为什么“吸入玩家”只移动角色模型，不移动 Player Root

Close 能正常播放后，新的观感问题变得清楚：玩家碰到 Trigger 后虽然立即失去控制，但角色仍完整站在 Portal 前，接着 Portal 自己关闭，视觉叙事像“车门关了，乘客还没上车”。最直接的修补是把整个 `WizardPlayer` 拉到 Portal 中心，但这会同时移动 `CharacterController`、Gameplay Transform 和 `CameraRoot`。因为 Cinemachine 跟随的是 Player/Camera Rig，Camera 也会钻进 Portal；Collider 还可能在吸入途中穿过其他 Trigger、墙体或地面，产生与“这只是离场演出”无关的 Gameplay Side Effect。

最终选择把层级职责拆开：

```text
WizardPlayer                 保持原地：Gameplay 坐标、CharacterController
├─ CameraRoot                保持原地：镜头观看完整 Close
└─ MagicWand01               移动/缩小/隐藏：只承担“被吸入”的视觉叙事

P8_StageExitPortal
└─ TravelerAnchor            世界空间吸入终点
```

`StageExitPortal` 位于 `Game.Run`，不能反向引用 `Game.Character.PlayerPortalTraveler`，否则 Run 流程模块会依赖具体角色实现。为此新增 `IPortalTraveler.BeginPortalTransit(Transform destination, float duration)`：接口由较低耦合的 `Game.Run` 定义，已经依赖 Run 的 `Game.Character` 提供实现。Portal 从有效 Player Collider 的父级解析接口，只发送“终点 + 时长”；它不知道 Visual Root、Animator、Camera 或 Wizard。这里没有使用全局 `EventBus`，因为请求目标就是本次碰撞 Collider 所属的单个 Player，直接接口比广播后再用 ID 过滤更明确，也不会把一次局部交互扩散成全局事件。

`TravelerAnchor` 使用显式 Transform，而不是硬编码 `portal.transform.forward`。当前 Portal Collider 很薄的轴与美术 Prefab 的视觉朝向未必一致，模型也可能在未来被旋转或嵌套；显式 Anchor 让 Level Designer 在 Scene View 中直接决定吸入方向和高度。若方向错误，只移动 Anchor 到 Portal 平面另一侧，不需要修改代码。

Transit 与 Close 同一时刻开始：

```text
0.00 s  有效 Enter -> Pause -> BeginPortalTransit -> Portal Closing
0.00~0.60 s  MagicWand01 向 TravelerAnchor 插值并缩小
0.60 s  Visual Root 隐藏，Camera 仍留在原地
0.60~1.00 s  Camera 观看 PortalBlueClose 收尾
1.00 s  SceneTransitionRequested -> Fade -> Load P8
```

`PlayerPortalTraveler` 使用 `Time.unscaledDeltaTime`，原因与 Close Particle 相同：Transit 开始前 Gameplay 已经把 `timeScale` 设为 0。位移和缩放使用 `Mathf.SmoothStep` 生成 ease-in-out 参数，再分别传给 `Vector3.LerpUnclamped`；这比恒速 Linear 插值更像先被牵引、再加速进入并柔和收尾。Coroutine 最后一帧会精确写入目标 position/scale 后隐藏 Visual Root，避免累计误差留下一个仍可见的小模型。该 Coroutine 只在一次 Scene Exit 的离散事件中创建，不属于 `Update/FixedUpdate/LateUpdate` Hot Path；逐帧循环不创建集合、不用 LINQ，也没有 closure。

可靠性上，角色吸入属于 Presentation Enhancement，不是跨 Scene 数据正确性的前置条件。`StageExitPortal` 在 Session、Coordinator、Full Library、Scene Name 等权威配置验证通过后才锁定 Enter；如果 `TravelerAnchor` 缺失、Player 没有 `IPortalTraveler`，或 Traveler 因自身配置无效拒绝请求，只输出 `GameLog.Warn`，仍继续 Close 与 Fade。这样一个模型引用错误不会把玩家永久困在地图一。相反，Session 或 Scene Name 缺失仍然是 `GameLog.Error + 拒绝进入`，因为那会破坏 Gameplay 主链。

# Task 4：Boss 数据模型、纯 Utility 与可配置 Wand Program（完成）

Task 4 的目的不是立刻让 Boss 在 Scene 中追击玩家，而是先建立“Boss 为什么选择这套法术”的可测试决策核心。普通 Enemy 的攻击选择往往只有距离和 Cooldown 两三个条件，P8 Boss 则需要同时考虑 Phase、距离、Player Wet 强度、Player 移动速度、Program 自身 Cooldown 和近期重复使用。如果这些判断直接散落在 `WizardBossController.Update()` 中，后续每调一个权重都要进入 Play Mode 猜结果，而且很容易在每次决策时创建临时集合。现在把一次战况压缩为不可变 `BossDecisionContext`，把开发者设计的法术组合保存在 `WandLoadout`，把选择元数据保存在 `BossSpellProgramDefinition`，再由纯 `BossSpellUtilityEvaluator` 计算稳定 Index。Program 的名称、数量、指令和参数都不是代码契约；运行时只要求 `BossDefinition.Programs` 提供一个稳定数组。Cooldown 与 Recent History 单独保存在预分配状态中，不写回 `ScriptableObject`。同时，`SpellCaster` 新增显式 Program + `SpellManaPolicy` 入口：Boss 可以忽略 Mana，但仍经过同一个 `CastEvaluator -> EmitCommand -> Projectile -> Combat Funnel`，没有复制第二套“Boss 法术系统”。

## 1. 从“硬编码技能”转成“程序 + 选择元数据”

`WandLoadout` 回答“选中后执行哪些指令”，`BossSpellProgramDefinition` 回答“当前局面有多想选它”。两类数据分开很重要：同一套 Hunter Wand 将来可以被另一个 Enemy 复用，但两个 Enemy 对距离、Phase、Cooldown 的偏好不同；反过来，修改 AI 权重也不应改变 Player 使用同一 SpellDefinition 时的解释器语义。

Program Asset 保存 Base Weight、Phase Mask、三阶段倍率、Preferred Distance、距离衰减、Wet/Moving 修正、Cooldown、Recent Penalty 与 Fallback。哪些 Program 作为 Fallback 由开发者决定。Fallback 不是“永远忽略 Cooldown”，而是正常候选全部不可用后，第二遍选择才允许它绕过自身 Cooldown；否则高分技能的 Cooldown 就失去意义。

## 2. Utility 评分如何把多项因素变成一个可解释结果

评分采用加法模型：

```text
score =
    BaseWeight * PhaseMultiplier
  + DistanceScoreWeight * DistanceFit
  + PlayerWetScoreModifier * WetRatio
  + MovingTargetScoreModifier（达到速度阈值）
  - RecentUsePenalty * RecentOccurrenceCount
```

`DistanceFit` 在 Preferred Range 内等于 1，离开区间后在 `DistanceFalloff` 范围线性下降到 0。例如某 Program 的 Preferred Range 是 0～4 米、Falloff 是 4 米：Player 在 3 米时获得完整近身分，6 米时只剩一半左右，8 米外距离贡献为 0。它不是硬性距离 Gate，因此距离不理想时 Program 仍可能被其他分数组合选中；真正的硬 Gate 只有 Phase Mask 与 Cooldown。

Wet 修正直接乘 `WetRatio = Clamp01(WetIntensity / 100)`；正值表示 Wet 越高越偏好，负值表示 Wet 越高越回避。Moving Modifier 则在 Player Move Speed 达到阈值后一次性加入，可用正值偏好高速目标，也可用负值回避高速目标。具体哪套法术采用哪种倾向完全由开发者决定。

Evaluator 使用稳定 Tie-break：只有 `score > currentBest` 才替换，完全同分时保留数组中较小的 Index。这样同一 Context 与同一 Program 顺序必然得到同一结果，便于复现 Bug、录制 Replay 或对照测试；若使用随机 Tie-break，AI 看起来更随机，但同一问题很难重新出现。随机性以后可以作为显式、带 Seed 的小扰动加入，而不是藏在基础选择器里。

## 3. Phase 为什么只能向前，以及 Runtime State 为什么不能写回 Asset

`BossPhaseResolver` 使用 70% 和 35% 两个 inclusive threshold：

```text
HP > 70%       -> Phase 1
35% < HP ≤ 70% -> Phase 2
HP ≤ 35%       -> Phase 3
```

Resolver 最终取“当前 Phase 与 HP 推导 Phase 中更高的一个”。因此即使 Debug 工具、Retry 恢复或未来治疗把 HP 从 30% 拉回 80%，Boss 仍留在 Phase 3，不会反复触发 Phase Transition。阈值会 Clamp 到 `[0,1]`，Phase 3 threshold 还被限制为不高于 Phase 2，防止错误数据让第三阶段先于第二阶段。

`BossProgramRuntimeState` 构造时一次性分配 `float[] CooldownRemaining` 和固定容量 `int[] RecentProgramIndices`。`MarkUsed` 把 Program Index 写入 Ring Buffer；容量满后覆盖最旧记录。Decision Tick 只循环数组，不创建 `List`、不使用 LINQ，也不把 Cooldown 写回 `BossSpellProgramDefinition`。如果把运行态写回 ScriptableObject，多个 Boss 会共享同一份 Cooldown，Play Mode 还会污染 Authoring Asset；Runtime State 分离同时解决了实例隔离和资产安全。

## 4. Boss IgnoreMana 为什么必须沿 Payload 递归传播

Player 的入口仍是：

```text
CastWand -> SpellManaPolicy.SpendCasterMana
```

Boss 的入口是：

```text
CastProgram(explicitWand, ..., IgnoreMana)
```

二者最终进入同一个私有 `RunCast`。`IgnoreMana` 只让 `TrySpendMana` 直接通过，后面的 `CastEvaluator`、Trace、EmitCommand、Projectile 初始化、Trigger/Timed Payload 与 Damage Funnel 完全复用。这里有一个容易漏掉的递归边界：任意 Trigger/Timed Emit 执行 Payload 时都会再次调用 `RunCast(payload)`。如果 Mana Policy 没有被 closure 捕获并传入递归调用，就会出现“Boss 第一层不扣 Mana，但 Payload 因零 Mana 静默失败”的半正确 Bug。测试会用零 Mana Boss 发射 Trigger，再人工触发 Impact Event，确认 payload 仍实际求值。

这个设计的 trade-off 是 `SpellCaster` 的 Runtime 方法多传一个很小的 enum 参数，但换来 Policy 在整个递归调用链上显式可见。没有使用 `bool ignoreMana`，因为具名 enum 在调用点更不容易把 true/false 含义写反，将来若增加 `SpendSharedPool` 等策略也有明确扩展位置。

# Task 5：Boss Runtime FSM、永久索敌、施法与 Phase（完成）

本 Task 把 Task 4 的“纯数据与纯评分”接到真实 Unity Runtime，但仍没有把 Boss 写成一个塞满 `if` 的巨型 `MonoBehaviour`。`WizardBossController` 是唯一 Scene Runtime Owner：它在 `Awake` 缓存 `CharacterController`、`Animator`、`HealthComponent`、`StatusController`、`SpellCaster`，一次性创建全部 State 与 Program Runtime 数组；真正的行为阶段由普通 C# State 表达。Boss 在 Safe Zone 中停留于 `Inactive`，收到匹配自身 Health ID 的 `BossEncounterStartedEvent` 后只捕获一次 `PlayerControllerBase.Current`，以后不再做 Detect/Lose Radius 查询。施法会同时锁定 Program Index 和 Aim Snapshot；HP 在施法中越过阈值只更新 Pending Phase，必须等 Recovery 结束、Action Lock 经 `Exit()` 释放后才能进入无敌转阶段。这样 Projectile 生成、Trigger Payload 和 Phase Transition 不会互相截断。具体 Program 名称、组合、数量与参数仍完全属于开发者的 Authoring 数据，Runtime 没有任何按名称分支。

## 1. FSM、Action Lock 与永久 Target

`BossStateMachine.ChangeState` 继续采用项目统一的 `Exit -> swap -> Enter` 契约。`BossCastState` 与 `BossPhaseTransitionState` 在 `Enter` 申请 Action Lock，在 `Exit` 无条件释放；Phase State 还会在 `Exit` 兜底关闭 Invulnerability。把资源释放放在 `Exit` 的原因是：正常完成、GameObject Disable、Scene Unload 和以后可能出现的取消动作都能经过同一条清理路径。如果只在“计时自然结束”分支释放，一次异常中断就可能让 Boss 永久无敌或永远无法再施法。

永久 Target 并不意味着每帧 `FindObjectOfType`。Encounter Start 时 Controller 只解析一次 Player，并缓存其 `Transform`、`CharacterController`、`StatusController` 与 `HealthComponent`。后续 Decision Context 直接读取缓存：距离来自 Transform，移动速度来自 `CharacterController.velocity`，Wet 来自 `StatusController.GetIntensity(StatusKind.Wet)`。首次激活后 `TryActivate` 拒绝第二个 Target，因此 Player 跑出普通 Enemy 的 Lose Radius 不会脱战，也不会被场景中的其他角色意外抢走仇恨。

## 2. Approach、Decision 与 Cast 的运行链路

```text
Inactive
  -> Encounter Start / 永久 Target
  -> Approach（只 MoveTo，不 MoveAway）
  -> Decision（按 DecisionInterval 评分）
  -> Cast（Telegraph -> Release -> Recovery）
  -> Pending Phase ? PhaseTransition : Approach / Decision
```

`BossApproachState` 只在距离大于 `StopDistance` 时向 Player 移动，而且每帧步长会 Clamp 到“恰好停在 StopDistance”，不会越过目标后反向修正。`BossDecisionState` 每帧只递减 Timer；完整 Context 组装和 Program 遍历按 `DecisionInterval` 执行。`BossCastState.Enter` 锁定本次 Program Index 与 `LockedAimPoint`，Telegraph 中即使 Player 改变位置，本发法术也保持可读、可躲的瞄准承诺；到 Release 时仍调用统一的 `SpellCaster.CastProgram(..., IgnoreMana)`，Recovery 完成后才记录 Program Cooldown/Recent History 并进入下一状态。

## 3. Phase Pending 与 Health Invulnerability

Phase 检测仍由纯 `BossPhaseResolver` 完成。Controller 每帧可以发现 HP 已越过阈值，但只把结果写入单调递增的 `PendingPhase`。如果当前 Action Lock 被 Cast 占用，Current Phase 不变；Cast 完成后，路由优先进入 `BossPhaseTransitionState`。该 State 在 Telegraph 全程调用 `HealthComponent.SetInvulnerable(true)`，到期后提交 Current Phase、发布 `BossPhaseChangedEvent`，随后在 `Exit` 恢复可受伤状态。它不恢复 HP，因此阶段切换不是第二条生命。

Invulnerability 必须放在 `HealthComponent.ReceiveHit` 进入 `DamagePipeline` 之前。这样无敌命中不会扣血，也不会发布 `DamageReceivedEvent` 或 `DeathEvent`；HUD、受击闪白、Hit Reaction 和 Encounter 结算都不会收到一条伪造的“0 伤害命中”。当前只有 Phase Transition 一个无敌 Owner，所以简单 bool 最清晰；如果未来 Shield、Cutscene、Buff 能同时持有无敌，再升级为 Token/引用计数，否则现在提前复杂化只会增加 Owner 泄漏风险。

## 4. Encounter Authority 与跨 Assembly 事件

`BossEncounterController` 位于 `Game.Run`，只保存 Boss/Player 的 `HealthComponent` 引用并按 Instance ID 过滤 `DeathEvent`。外部对象死亡不会推进状态；Boss Death 只发布一次 `RunState.Completed`，Player Death 只发布一次 `RunState.Failed`，Terminal 后的重复 Death 会被拒绝。`BossEntryTrigger` 把 Safe Zone 边界分成两阶段：首次有效 Player Enter 只完成“玩家确实位于安全区内”的布防，不启动战斗；随后第一次有效 Player Exit 才要求 `RunSessionCoordinator.CaptureBossCheckpoint()` 成功并调用 Encounter Start，避免玩家加载进 P8 的第一帧就开战，也避免进入战斗后才发现 Retry 没有恢复点。

`BossEncounterStartedEvent` 只携带 BossId/PlayerId；`BossPhaseChangedEvent` 使用 byte Phase Snapshot，避免 `Game.Run` 反向依赖 `Game.Character` 的具体 Controller/enum。Character 层可以消费或发布这些 Event，但 Run 层不需要知道 Boss FSM 的实现细节，后续 HUD 也只读事件事实。

## 7. Safe Zone 为什么使用 Enter 布防、Exit 开战

P8 加载完成时 Player 已经出生在绿色圆环内。如果仍沿用旧版 `OnTriggerEnter -> TryActivate`，Unity Physics 在检测到 Player 的 `CharacterController` 与 Safe Zone Trigger 重叠后就会立刻捕获 Checkpoint 并启动 Boss，安全区实际上只剩视觉含义。现在 `OnTriggerEnter` 只把 `_armed` 设为 true，表达“这个 Player 的确从安全区内部开始”；`OnTriggerExit` 才复用 `TryActivate` 完成 Layer、Session、Checkpoint 与 Encounter 权限检查。要求先 Enter 再 Exit 还能避免场景中原本位于胶囊体外的其他 Player Layer Collider 因移动或启用状态变化而伪造一次离场。

成功启动 Encounter 后先禁用缓存的 Trigger Collider。原因不是 Encounter 本身不幂等，而是一个角色可能拥有多个 Collider，Unity 也可能在相邻 Physics Step 继续发送 Exit；在边界已经失去玩法职责后关闭它，可以从输入源头终止重复通知。Safe Zone 的视觉处理不阻塞 Boss：脚本立即遍历 `Awake` 中缓存的 `ParticleSystem[]`，对每项调用 `Stop(false, ParticleSystemStopBehavior.StopEmitting)`。`StopEmitting` 只禁止产生新粒子，已经生成的粒子仍按各自 `startLifetime` 和模块规则继续模拟；Coroutine 每帧用 `IsAlive(false)` 查询缓存数组，全部死亡后才隐藏 Visual Root。这里没有在 `Update` 中调用 `GetComponentsInChildren`，数组分配只发生在初始化阶段，出圈热路径只是固定长度循环。

`BossSafeZoneRoot` 的 Y-Axis `CapsuleCollider` 负责 Gameplay Boundary，子物体 `Safe Zone` Prefab 只负责 Presentation。胶囊体在 XZ 平面的投影是圆，适合绿色圆环；相比 `BoxCollider`，玩家不会在视觉圆角外仍被判定处于安全区。`RunSessionCoordinator` 字段允许保持 `None`，因为完整 P7 -> P8 流程会使用 P7 `P8_RunSessionRoot` 经 `DontDestroyOnLoad` 保留下来的 `RunSessionCoordinator.Current`；给 P8 再挂一套 Session Root 反而会制造重复 Authority。直接从 P8 Scene 点击 Play 时没有该 Current，因此 Checkpoint 捕获失败并拒绝开战，这是当前跨 Scene 架构的明确测试边界。

本次新增 PlayMode 覆盖“Enter 不开战”和“Exit 立即开战、禁用 Trigger、停止发射、等待粒子死亡后隐藏”两条行为。`dotnet build Game.Run.PlayMode.Tests.csproj --no-restore` 已得到 0 warning、0 error，证明程序集与测试代码静态可编译；由于当前环境未能连接到已打开的 Unity Test Runner，Physics/Coroutine 的真实执行结果仍需开发者在 Unity 中运行新增测试后确认，不能把静态构建写成 PlayMode 已通过。

## 8. Safe Zone 不消失与 Boss 模型升空的完整 Debug 链

本轮出现的两个现象不是同一个 Bug。Safe Zone 没有消失时，Console 已经给出 `[Run] Boss Entry 未能捕获 Run Checkpoint，已拒绝启动 Encounter`。沿调用链回溯，`BossEntryTrigger` 只有在 `CaptureBossCheckpoint -> Encounter.TryBegin` 都成功后才关闭 Trigger 并停止粒子；因此“圆环还在”是上游权限失败后的正确保护行为。继续检查 `Editor.log`，可以看到 Unity 在 `RunSessionCoordinator.Awake:43` 报告 `DontDestroyOnLoad only works for root GameObjects or components on root GameObjects`。P7 的 `P8_RunSessionRoot` 被放在 `_Gameplay` 之下，Unity 拒绝把这个子物体迁移到 DDOL Scene；加载 P8 时它与 P7 一起卸载，`RunSessionCoordinator.Current` 随之变成 null，所以 Checkpoint 必然失败。

修复分为 Authoring 与防御代码两层。Authoring 层把 `P8_RunSessionRoot` 移到 `P7_DemoRun` Hierarchy 最外层；代码层让唯一 Coordinator 在调用 `DontDestroyOnLoad` 前检查 Parent，并用 `transform.SetParent(null, true)` 自动提升为 Scene Root。后者不是让错误层级变得合理，而是防止未来一次误拖拽让整条跨 Scene Runtime Wand 链静默失效。新增 `Coordinator_NestedInAuthoringHierarchy_PromotesItselfToSceneRoot` PlayMode Test 锁定这个 Unity 生命周期前提。

Boss 升空来自另一条 Transform 补偿链。正常工作的 `MagicEnemy_Base` 使用动画骨骼 `root.localPosition.y = 0`，`CharacterController.Center.y = 0.82`；Boss Prefab 却把骨骼 root 改成 `y = -7.28186`，把 Scene Boss Root 抬到 `y = 15.44`，再把 Collider Center 压到 `y = -12.64`。Edit Mode 没有动画采样时，这些反向偏移恰好让模型和胶囊看起来重合；Play Mode 中 Animator 接管动画骨骼 root，静态的 `-7.28186` 补偿不再可靠，模型回到 15 米高的 Boss Root，而 Collider 继续依靠负 Center 留在地面。这是典型的“静态 Scene 视图正确、运行时骨骼空间错误”。

正确结构是让不同坐标层各负其责：Scene Boss Root 表示 Gameplay 世界位置并位于 Terrain 表面；`CharacterController.Center.y` 使用约等于 `Height / 2` 的正值，让胶囊底部落在 Root 平面；`BossVisual` 保持 `(2,2,2)`，只表达外观放大；其下会被 Animator 写入的骨骼 `root` 恢复到正常 Magic Enemy 的局部原点，不再承担场景高度补偿。第一轮修复只改变这组错误偏移，不同时切换 `Apply Root Motion`，因为工作参考 `MagicEnemy_Base` 同样启用了它；一次只改变一个变量，才能确认真正解决的是骨骼原点而不是偶然制造另一组补偿。

# Task：修复 Boss 追击时只有平移、没有 Run 动画

本 Task 处理的是 Gameplay 位移已经成立、但 Presentation 没有收到运动状态的集成缺口。`CharacterController.Move` 只修改角色在世界中的位置，不会自动通知 `Animator` 当前正在追击；挂载 `RuntimeAnimatorController` 也只代表 Animator 拥有可执行的状态图，并不代表 Transition 条件会自动读取角色速度。`Enemy_Wizard` 的 `Idle_Bow -> Run_MagicWand` Transition 明确依赖 Float 参数 `speed > 0.1`，而 P8 专用 `WizardBossController` 在原实现中只写入施法和阶段切换 Trigger，从未写入 `speed`，所以参数始终是默认值 0，模型只能保持 Idle 姿态被 Gameplay Root 平移。修复后 Boss 每帧在 FSM Tick 之后同步水平 `CharacterController.velocity`；非 `Approach` 状态主动写回 0，避免停止调用 `Move` 后仍残留上一笔速度而卡在 Run。

## 1. 运行链路与根因

```text
BossApproachState.Tick
-> WizardBossController.MoveTowardTarget
-> CharacterController.Move
-> Gameplay Root 发生世界位移
-> WizardBossController.SyncAnimator
-> Animator.SetFloat("speed", horizontalVelocity.magnitude)
-> Enemy_Wizard Transition 判断 speed
-> Idle_Bow / Run_MagicWand 切换
```

普通敌人的 `EnemyControllerBase` 原本已经包含相同的 `speed` 同步契约，但 Boss 为满足永久索敌、专用 FSM、Action Lock 和 Phase 等规则没有继承普通敌人基类，因此不能假定普通敌人的 Animator 同步会自动复用。这里不是让 Boss 重新继承 `EnemyControllerBase`，而是在专用 Runtime Owner 中补上它实际需要的最小表现契约，避免把 Detect/Lose Radius、Kite/Hurt 等不符合 Boss 规则的行为重新引入。

## 2. 为什么使用水平实际速度

`CharacterController.velocity` 表示 `Move` 产生的实际速度。同步前将 `y` 清零，是因为 Run 只表达 XZ 平面的 Locomotion；未来即使 Boss 加入重力、台阶或下落，垂直速度也不应该让 Idle 切成 Run。参数 Hash 通过 `static readonly Animator.StringToHash("speed")` 只计算一次，热路径中不做字符串查找、不产生 `GC Alloc`。此外，只有 `BossRuntimeStateKind.Approach` 才允许输出正速度；Cast、Decision、PhaseTransition 等原地状态直接写 0，使 FSM 的 Gameplay 语义与 Animator 表现保持一致。

## 5. Task 5 的最终 Editor Gate 与参数认知

开发者最终验证了三条容易混淆但相互独立的链路。第一条是 Gameplay Phase：`HealthComponent.CurrentHp / MaxHp` 低于等于 `0.7` 与 `0.35` 时，Controller 先登记 `PendingPhase`，等待当前 Cast 的 Action Lock 释放，再进入约 1.2 秒无敌的 `PhaseTransition`。第二条是 Program 可用性：`PhaseMask` 决定某个 Program 是否进入候选集合，`PhaseMultiplier` 只改变已进入集合的相对分数；一阶段 Program 若配置为 `Everything`，转阶段后继续出现是正确行为，不代表 Current Phase 没变化。第三条是 Animator Presentation：Trigger 参数和 Transition 只负责“看起来播放什么动作”，即使缺少动画连接也不能反向决定 Gameplay Phase。

在实际 Play Mode 中，Boss 已能追击 Player、在停止距离内选择七套 Authoring Program、跨越 70%/35% 阈值并使用后续阶段法术。这个结果证明 `BossPhaseResolver -> PendingPhase -> PhaseTransition -> CurrentPhase -> BossSpellUtilityEvaluator` 的数据链已经接通。Teleport 仍然不发生，是因为 Task 5 只预留了 `TeleportWeight`、`TeleportCooldown` 和采样参数，还没有任何 Runtime State 消费这些字段；它是 Task 6 的明确施工内容，不应继续通过调高 Inspector Weight 猜测修复。

# Task 6：动态安全 Teleport 与共享 Portal VFX（已收口）

Task 6 的目标不是简单执行一次 `transform.position = target`，而是建立一条“可解释、可取消、不会穿模”的空间移动流水线。玩家最终看到的是：第二阶段开始后，Boss 偶尔在原地与目标点同时展开传送门预警；预警期间目标位置保持不变，玩家可以读取意图；Boss 随后从源点消失并在目标点出现，Portal 完成关闭；第三阶段因为 Cooldown 更短、相对 Weight 更高而更加灵活。如果玩家站在墙边、树边或陡坡旁，系统会尝试其他候选点；如果所有候选都不合法，Boss 留在原地并继续使用本轮已经选出的 Spell，而不是被强行塞进 Collider。为了得到这个结果，代码把问题拆成纯数学候选、Unity 世界查询、FSM 动作所有权和事件驱动表现四层。这样既能用 EditMode Test 验证公式，也能把无法脱离 Scene 的 `NavMesh`、Physics、Particle 交给 PlayMode 与人工 Gate 验证。

## 1. 玩家周围的“环带”是什么，为什么不使用固定 Teleport Point

固定 Teleport Point 的优点是关卡设计师可以完全控制落点，但它会让 Boss 很快显得机械：玩家记住几个点后就能预判所有移动，而且换一张地图就要重新摆点。P8 的目标是让落点相对 Player 动态生成，因此输入是玩家当前位置与一个半径区间：

```text
PlayerPosition
MinRadius = 6
MaxRadius = 12
CandidateCount = 12
```

每个候选都满足“水平距离处于 6～12 米之间”。这里的 Y 暂时沿用 Player 高度，只是为了构造一个三维候选；后续 Ground Raycast 会把它投影到真实地表。

`BossTeleportCandidateGenerator` 使用黄金角 `137.50777°` 依次旋转候选方向。普通的 `360° / Count` 等角分布虽然整齐，但每次改变 Count 会形成明显的放射状重复；黄金角是一种低差异分布，相邻样本不容易落在同一方向簇中。半径没有直接做 `Lerp(Min, Max, t)`，而是在半径平方上插值：

```text
radius = sqrt(lerp(MinRadius², MaxRadius², t))
```

原因来自圆环面积公式 `A = πr²`。如果半径线性均匀，内圈较小面积会获得与外圈相同数量的样本，单位面积密度偏高；在 `r²` 上均匀更接近面积均匀采样。生成器不读取 Scene、不调用随机全局状态，给定相同输入必然产生相同结果，因此容易测试和回放。Controller 每次 Teleport 改变 `AngleOffset`，让玩家观察时不会觉得候选序列固定不变。

## 2. 为什么“点在 NavMesh 上”仍不等于 Boss 可以站在那里

`NavMesh.SamplePosition` 回答的是：“候选附近有没有一个可供 NavMesh Agent 行走的表面点？”它不回答以下问题：

- Boss 是一个有高度和半径的胶囊，而不是无体积的点；
- 该点下方是不是真实 Terrain/地面 Collider；
- 地面法线是否过陡；
- 树干、岩石、墙体是否占据了 Boss 身体空间；
- Boss 自己当前的 Collider 是否被误当成障碍。

因此 `BossTeleportSampler` 对每个候选严格按以下顺序过滤：

```text
数学候选点
-> NavMesh.SamplePosition：限制到已烘焙可行走区域
-> 向下 Ground Raycast：得到真实 Hit Point 与 Normal
-> Vector3.Angle(up, normal)：坡度不得超过 MaxGroundSlopeDegrees
-> 构造与 CharacterController 等价的世界空间 Capsule
-> Physics.OverlapCapsuleNonAlloc：目标身体空间不能被障碍占用
-> 第一个通过全部检查的点成为 Destination
```

顺序本身也是性能设计。`NavMesh.SamplePosition` 或 Ground Raycast 已经失败时，没有必要继续执行 Capsule Overlap。每次最多检查 `CandidateCount` 个点，候选 `Vector3[]` 和 Collider Buffer 都在 `Awake` 一次性分配；正常 `Update` 不创建数组、不使用 LINQ。Overlap Buffer 如果被完全填满，系统保守地把候选判为阻塞，因为“命中数量超过容量”时无法证明被截断的 Collider 都安全。Teleport 是低频离散动作，宁可取消一次，也不能为了成功率让 Boss 穿墙。

第一版没有再创建一套独立 Arena Bounds。P8 已有专用 `P8_NavMeshRoot` 和烘焙数据，因此“Boss Arena 内可站立区域”由 NavMesh 覆盖范围表达。如果再增加 Box Bounds，就会出现两份 Authoring 真相：NavMesh 改了但 Bounds 忘记改，或者相反。其 trade-off 是 NavMesh 必须确实只覆盖允许 Boss 到达的区域；Editor Gate 要在 Arena 边缘确认采样不会吸附到外围路径。

## 3. CharacterController 胶囊的 Center、Height、Radius 与 Skin Width

`CharacterController` 的 `Center` 是相对角色 Root 的局部中心；`Height` 是包含上下半球的总高度；`Radius` 是半球和圆柱的半径。构造 `Physics.OverlapCapsuleNonAlloc` 所需的两个球心端点时，圆柱半长为：

```text
halfCylinder = Height / 2 - Radius
bottomCenter = worldCenter - up * halfCylinder
topCenter    = worldCenter + up * halfCylinder
```

不能把 `Height / 2` 直接当成端点距离，否则上下球体还会额外延伸一个 Radius，实际检测高度会比 CharacterController 更高。`BossTeleportCapsuleShape` 同时读取 `transform.lossyScale`：水平 X/Z 最大 Scale 影响 Radius，Y Scale 影响 Height，Center 也要按 Scale 转换。P8 的推荐结构仍然是 Gameplay Root Scale 为 `(1,1,1)`、仅 `BossVisual` 放大；支持 lossyScale 是防御性处理，不鼓励继续靠缩放 Gameplay Root 修模型。

检测半径会减去按比例缩放的 `Skin Width`。Skin Width 是 CharacterController 为稳定接触和减少抖动保留的“皮肤层”；如果用完整 Radius 检测，胶囊底部刚好接触 Terrain 时可能被判为重叠。略微内缩只允许 Skin 范围内的接触，不会让真正穿入墙体的候选通过。

## 4. Spell 与 Teleport 如何做一次动作选择

Teleport 不是 Spell，也不应该伪装成一个没有 Projectile 的 `WandLoadout`。Spell Program 的分数仍由 `BossSpellUtilityEvaluator` 计算；Teleport 使用本阶段的 `TeleportWeight`，两者由 `BossActionUtilityEvaluator` 做最后一次相对权重选择：

```text
teleportShare =
    TeleportWeight /
    (TeleportWeight + SelectedSpellScore)
```

例如 Teleport Weight 为 1、最高 Spell Score 为 3，Teleport 在本次可用决策中的相对份额为 `1 / 4`。这不是“Inspector 填1就有1%概率”，而是同一个无单位 Utility Scale 上的相对倾向。Phase 1 的 Weight 为0，因此完全禁用；Phase 2 使用 Weight 1、Cooldown 8秒；Phase 3 使用 Weight 1.5、Cooldown 5秒。Controller 使用一个确定性的低差异序列提供 `roll01`，而不是依赖难以复现的全局 `Random`；玩家仍会看到分散的选择节奏，测试和 Debug 却能在相同输入下复现。

`BossTeleportRuntimeState` 单独保存剩余 Cooldown。这个值不能写回 `BossDefinition`，因为 ScriptableObject 是所有实例共享的 Authoring Asset；若把运行时秒数写进去，停止 Play 后可能污染资产，多只 Boss 也会共享同一个冷却。

## 5. Teleport State、Action Lock 与失败回退

完整状态链是：

```text
Decision
-> 先得到本轮最高分 Spell Index / Score
-> Teleport 相对权重胜出
-> BossTeleportState.Enter
-> 取得 Action Lock
-> 一次性采样并锁定 Source / Destination
-> 发布 Telegraph Event
-> 等待 TeleportTelegraphDuration
-> 发布 Departed Event
-> 临时禁用 CharacterController
-> 写入 Transform.position
-> 立即恢复 CharacterController
-> 发布 Arrived Event
-> 等待 TeleportRecoveryDuration
-> 写入 Teleport Cooldown 与全局 Cast Interval
-> Exit 释放 Action Lock
-> Approach / Decision
```

临时禁用 CharacterController 是 Unity API 的重要边界。启用的 CharacterController 由原生 Physics 管理内部位置与碰撞缓存，直接瞬移 Transform 可能让 Controller 在下一帧尝试纠正位置；禁用、移动、重新启用可以明确告诉 Unity 这是一次离散传送，而不是高速穿过中间路径。

如果所有候选都失败，Teleport State 发布 `Cancelled`，设置一个不超过1秒的短 Retry Delay，然后离开 State。若本轮已经选出一个合法 Spell，就在 `Exit` 释放旧 Action Lock 后进入 Cast；若没有 Spell，则回到 Decision。短 Retry Delay 的目的不是惩罚玩家，而是避免 Boss 站在极端封闭区域时每0.2秒重复执行12组 NavMesh/Physics 查询。

Phase 阈值如果在 Telegraph 中被跨越，只会更新 `PendingPhase`。因为 Teleport 持有 Action Lock，PhaseTransition 不能插入中间；Teleport 完整收尾后，`RouteAfterAction` 才优先提交阶段切换。这与 Cast 的延迟 Phase 契约完全一致。

## 6. 为什么 VFX 使用 Event，而不是让 Boss Controller Instantiate Prefab

`WizardBossController` 位于 `Game.Character`，负责“在哪里移动、什么时候移动、是否安全”；Portal 粒子属于 `Game.UI` 的世界表现。如果 Controller 直接引用 `PortalBlueOpen`，Gameplay Assembly 会开始拥有美术资源、Coroutine 和表现时长，后续替换特效会迫使修改 AI。现在 Controller 只发布 `BossTeleportEvent`：

```text
BossId
Stage = Telegraph / Departed / Arrived / Cancelled
SourcePosition
DestinationPosition
```

`BossTeleportVfxController` 按 Boss `HealthComponent.Id` 过滤事件，并在 `Awake` 为 Source/Destination 各创建一套 Open、Idle、Close 实例。Telegraph 时两个位置先 Open 再 Idle；Departed 时源点 Close；Arrived 时目标点 Close；Cancelled 时两端收尾。运行时事件只移动 Transform 和 `SetActive`，不会每次 Teleport 重复 Instantiate 六个粒子对象。粒子被设置为 unscaled time，使未来 Pause/Terminal 边界不会把一次性 Close 卡在第0帧。表现即使缺少或被禁用，Gameplay Teleport 仍然成立；反过来，VFX 也没有权限修改 Boss Transform。

# Task 6 补充修正：Portal Pivot 与 Homing 命中中心

这次修正处理的是两个“Gameplay 逻辑成立，但空间语义选错”的问题。Boss Teleport 已经能通过 NavMesh、Ground Raycast、坡度和 Capsule Clearance 找到安全位置，然而 Portal Prefab 的视觉圆心直接落在地面接触点，导致竖直圆盘有一半进入 Terrain；`Spell_Mdy_Homing` 也已经能找到敌方 `IDamageable`，但锁定后保存的是角色 Root Transform，而项目中的 Character Root 通常位于脚底，因此投射物会主动向脚底弯曲。两者都不能通过改高 Boss Transform 或简单增加法术 Turn Rate 解决：前者会破坏 CharacterController 的贴地关系，后者只会让投射物更快地追向错误位置。正确修复必须保留 Gameplay Authority，只校正 Presentation Pivot 与 Physics Hit Volume 的解释方式。

## 1. Ground Point、Prefab Pivot 与视觉中心不是同一个概念

Teleport Event 中的 `SourcePosition` 和 `DestinationPosition` 是 Gameplay Ground Point：它们经过 Ground Raycast，并作为 Boss Root 的安全贴地位置。Portal Prefab 的 Transform Position 则表示 Prefab Root Pivot 的世界坐标。Pivot 是美术资源的坐标原点，不保证位于模型底部；当前 Purple Portal 的 Root Scale 为 `(2.5, 2.5, 2.5)`，内部粒子围绕 Root 原点展开，因此原点更接近圆盘中心。

旧链路是：

```text
Ground Point
-> Portal Root Position
-> 圆盘中心位于地面
-> 下半圆进入 Terrain
```

修正后的链路是：

```text
Gameplay Ground Point（保持不变）
-> BossTeleportEvent（保持不变）
-> BossTeleportVfxController
-> Visual Position = Ground Point + World Up * Visual Height Offset
```

这里使用 `Vector3.up`，表示世界坐标系的竖直方向，而不是 Portal 自身可能被旋转后的 Local Up。原因是我们要表达“离开地面多少米”，它属于关卡世界空间，不属于粒子局部空间。默认 `_visualHeightOffset = 1.5f` 是当前 Portal 的起始 Authoring 值，Inspector 允许按美术半径继续微调。它只改变六个预创建 VFX 实例的位置，不改变 Boss Transform、NavMesh Destination、CharacterController 或 Capsule Clearance。

没有使用 Renderer/ParticleSystem Bounds 自动推导偏移。普通 Mesh Renderer 的 Bounds 通常能代表网格包围盒，但 ParticleSystem Bounds 可能来自预估、Custom Bounds 或尚未播放的模拟结果；Open、Idle、Close 三份 Prefab 还可能拥有不同瞬时范围。把不稳定的表现 Bounds 当成 Pivot 校正依据，会让传送门高度随粒子阶段跳动。显式 Authoring Offset 更简单、稳定，也不会修改 P7 已验证的 Portal Prefab Pivot。

## 2. 为什么 Character Root 经常位于脚底

角色系统通常让 Root 表示 Gameplay 位姿：`transform.position` 是角色在地面上的基准点，`CharacterController.center` 再描述胶囊相对 Root 的局部中心。这种结构便于移动、NavMesh、重力和地面检测，因为 Root 保持在脚底附近；模型骨架、武器、血条与 Collider 可以各自拥有局部偏移。

因此下面两个位置含义不同：

```text
HealthComponent.transform.position
= 角色 Gameplay Root，通常在脚底

Collider.bounds.center
= 实际 Physics Hit Volume 的世界空间中心
```

旧 Homing 代码在扫描时已经用 `hit.bounds.center` 比较哪个 Collider 最近，却在确定目标后改为保存 `HealthComponent.transform`。这造成了选择阶段和追踪阶段的空间标准不一致：

```text
选择：按身体 Collider Center 判断最近目标
追踪：朝角色脚底 Root 转向
```

修正后，`ProjectileBase` 保存本次真正选中的 Collider，并在每个 Homing `FixedUpdate` 读取同一个 `Collider.bounds.center`。Collider Bounds 会随目标 Transform 移动而更新；`Bounds` 本身是 value type struct，读取不会产生托管堆分配。投射物仍然保存 `IDamageable` 检查目标是否存活，因此“往哪里追”和“目标是否仍有效”各自使用最合适的契约。

## 3. 为什么不使用固定 Aim Height

最直接的临时修复是：

```csharp
target.position + Vector3.up * 1.5f
```

它对当前小型敌人可能有效，但 Boss、普通敌人和未来体型不同的单位高度不一致；同一个常量会从“瞄脚”变成“瞄腰”“瞄胸”甚至“瞄到头顶上方”。把 Aim Height 放进每个 Enemy Definition 虽然可调，却要求所有可追踪目标额外维护一份与 Collider 重复的数据，两者很容易在模型缩放或 Collider 调整后漂移。

`Collider.bounds.center` 的优势是复用 Combat 已经依赖的真实命中体积：只要目标能通过 Collision 被 Projectile 命中，它就天然提供一个合理的追踪中心。未来若出现必须瞄准特定弱点的 Boss，可以再增加显式 `IHomingAimProvider` 或 Aim Point Transform；当前问题没有必要提前引入该架构。

当被锁定 Collider 被禁用、GameObject 失活、目标死亡或 Collider 被销毁时，Homing 会停止继续转向。`ConfigureHoming` 重新配置和 `ReflectByShield` 改变阵营时也会清空 Collider 引用，避免反射后的投射物继续追踪旧敌人。

- `dotnet build` 或 Unity 生成的 `.csproj` 构建验证的是 C# 语法、类型、可访问性和 Assembly Reference，无法证明 `NavMesh.SamplePosition` 在当前 Scene 有可用数据，也无法推进 Coroutine 或模拟 `ParticleSystem`。

所以“全部测试通过”不能自动推出“表现一定正确”，“实机看起来正确”也不能推出“边界条件以后不会回归”。本 Task 同时保留自动化和实景证据，正是为了让二者互补。

## 7. 完整 Debug 复盘：从症状到根因，而不是看到哪里就改哪里

### 7.1 Portal 半截入地

最初症状是 Boss Teleport 功能已经成立，但紫色 Portal 的下半部分埋进 Terrain。排查时先确认 Boss 最终位置正确、`CharacterController` 没有悬空、Ground Raycast 的命中点也确实位于地表，因此 Gameplay Sampling 不是首要嫌疑。继续比较三个空间概念后才找到根因：

1. Ground Point 是 Physics 查询得到的地表接触点。
2. Boss Root Position 是角色 Gameplay Root 的世界坐标，必须与 `CharacterController` 的贴地语义一致。
3. Portal Prefab Position 是 Prefab Root Pivot 的世界坐标，而该 Pivot 位于圆盘视觉中心附近，不在圆盘底边。

旧代码把 1 直接当成 3，等价于把圆盘中心放到地面，所以自然有一半在地下。这个问题若通过抬高 Boss Root“修复”，会让角色碰撞体、NavMesh 落点和模型再次失配；若直接改公共 Portal Prefab 的 Pivot，还可能破坏 P7 已经验证的 Stage Exit Portal。最终选择在 `BossTeleportVfxController` 增加 Scene-level `Visual Height Offset`，使用 `Vector3.up` 只移动 Presentation Instance。它保留了 Gameplay Ground Point 的权威性，也允许不同 Portal 美术资源独立调节。

`Vector3.up` 是世界空间的 `(0, 1, 0)`。这里故意不用 `transform.up`：后者是对象的 Local Y Axis 转换到世界空间后的方向，如果 VFX Root 被旋转，偏移可能斜向移动；我们的语义是“离开地面向上”，所以应该固定使用 World Up。`[SerializeField] private float` 同时保留封装和 Inspector Authoring：字段不必公开给其他脚本随意改写，但 Unity Serializer 仍可保存 Scene 中的调参值。

### 7.2 Homing 朝脚底飞

旧实现扫描目标时使用 `Collider.bounds.center` 比较距离，选中后却只保存 `HealthComponent.transform`，随后每帧朝 `Transform.position` 转向。项目中的 Character Root 通常放在脚底，因为移动、贴地和 `CharacterController` 都需要稳定的地面参考；因此 `Transform.position` 不是身体中心。选择阶段与追踪阶段采用了两套不同坐标语义，这是根因。

最终实现保存实际选中的 `Collider`，并在 Homing 的 `FixedUpdate` 中读取其最新 `bounds.center`。`Collider.bounds` 是 Axis-Aligned Bounding Box（AABB），即始终与世界坐标轴对齐的包围盒；角色旋转后它会重新包住 Collider，因此 Center 仍是一个稳定的世界空间命中中心。`Bounds` 是 C# `struct`，属于 Value Type；读取 `bounds.center` 会得到 `Vector3` 值，不会像 `new class` 那样在 Managed Heap 上创建对象。与此同时仍保存 `IDamageable` 判断目标是否存活，因为“往哪里追”属于 Physics Geometry，“还能不能追”属于 Combat Contract，这两个责任不应该混成一个 Transform 猜测。

没有采用“给所有目标固定加 1.5 米”的方案。固定高度只对当前尺寸角色碰巧有效，遇到放大两倍的 Boss、矮小 Enemy 或不同 Collider Center 就会再次失配；也没有单纯提高 `Turn Rate`，因为更高的转向速度只会让 Projectile 更准确地追向错误的脚底目标。若未来要实现 Headshot、Weak Point 或飞行单位的专用瞄准点，再增加类似 `IHomingAimProvider` 的显式契约会更合适；当前使用 Collider Center 是满足现有需求的最小通用方案。

### 7.3 为什么要清理失效引用

Unity 的 `UnityEngine.Object` 有特殊的“伪 null”语义：底层 Native Object 被销毁后，C# Wrapper 变量可能仍存在，但重载后的 `== null` 会返回 true。Homing 每个 Physics Tick 都必须检查 Collider 是否已销毁、是否 disabled、GameObject 是否 inactive，以及 `IDamageable.IsAlive` 是否仍为 true。Projectile 被 Shield 反射或重新配置阵营时也必须清空旧 Collider，否则它可能改变 Team 后继续追踪原来的目标。这里的清理不是“为了不报 NullReference”这么简单，而是维护 Projectile 当前阵营、目标和运动意图的一致性。

## 8. 本轮优化的边界与后续性能验证

这次优化没有在 `FixedUpdate` 中使用 `FindObjectsOfType`、LINQ、Closure 或创建新数组。目标扫描继续复用既有 NonAlloc Buffer；锁定后每帧只读取已经保存的 Collider 状态和 Bounds Center。Portal Open/Idle/Close 实例由 Controller 预创建并复用，Teleport 时切换 Active State，而不是在每次传送中临时创建六个 VFX 对象。这样既减少 Instantiate/Destroy 带来的 CPU Spike，也避免短生命周期对象增加 Managed GC 压力。

但“代码中没有明显 `new`”不等于 Profiler 已证明 `GC Alloc = 0 B`。Unity 内部 API、第三方 VFX、Animator、ParticleSystem 和其他同时运行的系统仍可能产生分配。Task 8 需要在真实 P8 Boss 战中打开 Profiler，至少分别观察正常施法、连续 Homing、频繁 Teleport，以及 Water/Fire ElementWorld 与大量 Projectile 同时活跃的帧；记录 Main Thread、Physics、Rendering、GC Alloc 和 Spike 的调用栈，再决定是否继续优化。Task 6 的收口只证明功能、边界和当前表现正确，不提前替 Task 8 做性能结论。

## 2. 为什么 HUD 使用 Event Snapshot，而不是直接拖入 Boss Controller

最直接的写法是让 `BossHealthBarController` 持有 `WizardBossController` 或 `BossDefinition`，每帧读取 `HealthRatio` 和 `CurrentPhase`。它看起来省代码，却会让 `Game.UI` 依赖 `Game.Character`。当前项目的 Assembly 方向是 `Game.Character -> Game.Run` 和 `Game.UI -> Game.Run`；如果再增加 `Game.UI -> Game.Character`，表现层就开始认识具体 Boss 实现，未来替换 Boss Controller 或把 HUD 用在其他 Boss 时必须一起修改。

本实现新增 `BossHudInitializedEvent`，定义在 `Game.Run`：

| 字段 | 含义 |
|---|---|
| `BossId` | 与 `HealthComponent.Id` 同源的稳定 Scene Instance ID，用于过滤其他角色事件。 |
| `DisplayName` | 来自唯一 `BossDefinition.DisplayName`，UI 不再重复 Authoring 名称。 |
| `CurrentHp / MaxHp` | 初始化时的值快照，让 HUD 不需要持有 HealthComponent。 |
| `CurrentPhase` | 初始化 Phase；即使以后 Boss 不是满血激活也能正确显示。 |
| `Phase2Threshold / Phase3Threshold` | 来自 BossDefinition 的真实阶段阈值，只用于布局 Marker。 |

`struct` Event 是 Value Type。它在同步 `EventBus<T>.Publish` 中按值传递，字段本身不会像 `new class` 那样创建独立 Managed Heap 对象。`DisplayName` 仍是一个 string Reference，但这里复用 ScriptableObject 已有字符串，没有在每帧拼接新名称。初始化事件只发生一次，不属于 Hot Path。

为什么不只监听 `BossEncounterStartedEvent` 就显示？因为 Encounter Authority 开始不等于具体 Boss Runtime 一定成功激活。`WizardBossController` 还要验证 BossId、`PlayerControllerBase.Current` 和 PlayerId。如果 Player 引用错误，Encounter 已开始但 Boss 没有 Target；此时显示血条会掩盖配置错误。HUD Snapshot 在 `TryActivate` 成功后发布，表示“这个 Boss Runtime 已经真正进入战斗”，语义更准确。

## 3. UGUI 血条、Filled Image 与 RectTransform Anchor 基础

UGUI `Image.fillAmount` 的范围是 0～1。代码计算：

```text
fillAmount = Clamp01(CurrentHp / MaxHp)
```

但只有当 Inspector 中 `Image.Type = Filled` 时，画面才会根据 `fillAmount` 裁切；普通 `Simple` Image 即使数值变化，仍会完整绘制 Sprite。这是“代码和 Console 都正常，但血条视觉不动”的典型 Unity 配置问题。P8 使用：

- `Image Type = Filled`
- `Fill Method = Horizontal`
- `Fill Origin = Left`
- `Fill Amount = 1`
- `Preserve Aspect` 根据血条 Sprite 决定，通常关闭

阶段 Marker 不能只把 `anchorMin.x/anchorMax.x` 写成 0.7 或 0.35。Anchor 的归一化比例针对父 `RectTransform`，但玩家真正看到的 `HealthFill` 往往因为边框、Padding 或美术留白而比父 Rect 窄。例如父 Root 宽 1366 Pixel，可见 Fill 只有 1300 Pixel；直接取父宽 70% 会产生稳定但错误的偏移。所谓“响应式”不是只要用了 Anchor 就一定正确，而是所有参与计算的对象必须共享正确的坐标语义。

最终实现以真实 `HealthFill.rect` 为几何来源：

```text
Fill Local Left / Right
-> RectTransform.TransformPoint：Fill Local Space 转 World Space
-> Marker Parent.InverseTransformPoint：World Space 转共同 Parent Local Space
-> Vector3.Lerp(left, right, healthRatio)
-> 得到真实 Fill 上的 35% / 70% 点
```

`TransformPoint` 会把局部 Position、Rotation、Scale 组合进世界坐标；`InverseTransformPoint` 做相反转换。两步看似绕远，实际是在明确回答“这两个点现在属于哪个 Coordinate Space”。完成转换后，线性插值公式就是：

```text
target = left + (right - left) * ratio
```

`ratio=0` 对应 Fill 左端，`ratio=1` 对应右端，`0.35/0.70` 自然对应真实可见宽度。Marker Root 的 Anchor/Pivot 固定为父中心 `(0.5, 0.5)`，`anchoredPosition` 只表达目标点相对父中心的偏移。其子物体采用明确堆叠规则：

1. `MarkerLine`（当前视觉为红色 X）的局部中心固定在 `(0,0)`，因此 X 的中心就是阈值点；
2. Label 的 Pivot 设为顶部中央 `(0.5,1)`，横向位置归零；
3. Label Y 使用 `-(MarkerLine.rect.height × abs(localScale.y) / 2 + 4 px)`，因此文字始终位于 X 的显示下沿再向下 4 Pixel；
4. 百分比文本由 Snapshot 动态计算，阈值以后改成 65%/30% 时不需要手改字符串。

最终职责边界不是“Runtime 接管全部 Layout”，而是：Boss 名称、Phase、血条整体位置、Sprite、Font、Color 由 Editor Authoring 决定；只有与 Gameplay 数学直接相关的 Marker 点位及其内部 X/Label 关系由程序控制。这样既不会覆盖设计师已经调好的顶部排版，又能保证阶段标记不会因为手工拖动而失真。

一个非常重要的激活层级规则是：`BossHealthBarController` 不能挂在它自己隐藏的 `_hudRoot` 上。`GameObject.SetActive(false)` 会让该物体及子物体上的 MonoBehaviour 收到 `OnDisable`，Controller 会退订 EventBus；之后 Boss 激活事件到来时，它已经不再监听，HUD 永远不会重新出现。正确层级是：

```text
BossHUDController        <- 始终 active，挂 BossHealthBarController
└── BossHUDRoot          <- 初始 active，由 Start 隐藏，事件到来后重新显示
    ├── BossNameText
    ├── PhaseText
    └── HealthBarRoot
        ├── Background
        ├── HealthFill
        ├── Phase2MarkerRoot
        │   ├── MarkerLine
        │   └── Label70（程序放在 X 下方）
        └── Phase3MarkerRoot
            ├── MarkerLine
            └── Label35（程序放在 X 下方）
```

## 4. ClearSession 与 EndRun 为什么不是同一个操作

`RunSessionCoordinator.ClearSession()` 只清理 Runtime Library、Runtime Wand 和 Checkpoint，同时把 Stage/EntryMode 恢复初始值；Coordinator GameObject 仍然位于 `DontDestroyOnLoad` Scene。这个行为适合“清空数据但继续保留 Owner”的内部操作，却不适合 Restart Run。

原因是 P7 Scene 本身包含一份配置完整的 `P8_RunSessionRoot`。如果 P8 的旧 Coordinator 只是被清空但仍存活，加载 P7 后，新 Root 的 `Awake` 会发现已有 Singleton，把自己销毁。最终留下的是一份没有初始化 Runtime Clone 的旧空 Root，Starting Template 又来自旧对象，极易产生“场景加载成功但法术 Session 无效”的隐蔽错误。

因此新增 `EndRun()`：

1. 确认调用者确实是静态 `Current` Authority。
2. 调用 `ClearSession()`，立即释放 Runtime ScriptableObject Clone 并清空 Checkpoint。
3. Play Mode 使用 `Destroy(gameObject)`，让 Unity 在当前帧结束时安全销毁对象。
4. EditMode Test 使用 `DestroyImmediate(gameObject)`，因为没有运行时帧循环负责延迟销毁。
5. `OnDestroy` 清空 `RunSessionCoordinator.Current`。

`Destroy` 与 `DestroyImmediate` 的区别必须掌握。`Destroy` 是延迟销毁：本帧后续代码仍可能拿到 C# Wrapper，但 Unity 的伪 null 比较会在对象销毁后表现为 null。`DestroyImmediate` 当场移除对象，适合 EditMode 工具和测试，但不应在正常 Gameplay 中随意使用，因为它可能在遍历对象集合或执行生命周期回调时立刻改变世界结构。

Retry 与另外两条路径相反：它必须保留 Coordinator，只调用 `RestoreBossCheckpoint()`。Scene Reload 会重新创建 Boss、Player、Status、Projectile、ElementWorld 和 UI，所以它们自然回到初始状态；跨 Scene Session 只保留 Runtime Spell Library，并把 Runtime Wand 恢复成出 Safe Zone 时捕获的独立数组快照。这就是“让 Scene 生命周期替我们做大规模重置”，比逐个寻找并手动 Reset 所有对象更可靠。

## 5. DemoPauseMenuController 为什么仍然只是 Adapter

`DemoPauseMenuController` 没有自行复制 Wand，也不直接调用 `SceneManager` 跳过 Fade。它只做三件事：

- 根据 Button 意图调用 Session Authority 的公开方法；
- 选择明确的目标 Scene Name；
- 把加载交给 `DemoSceneTransitionController`。

`CanBeginNavigation` 同时检查 `_isLoadingScene`、空 Scene Name 和 `DemoSceneTransitionController.IsTransitioning`。必须在销毁 Session 前先通过这个 Gate，否则 Transition 已经忙碌时 Button 的第二次点击可能清掉 Session，却没有启动新的 Scene Load。

P8 Scene 无法在 Editor 中保存对 P7 `DontDestroyOnLoad` Runtime Object 的跨 Scene 引用，因此 `_sessionCoordinator` 在 P8 Inspector 中允许保持 `None`；按钮触发时使用 `RunSessionCoordinator.Current` 自动重绑定。这里的查找是静态属性访问，不是 `FindObjectOfType`，也不在 Update 中执行。

Terminal Result 和 Fade 都使用 `RunPauseCoordinator` 的 Flags Reason。Terminal Panel 持有 `TerminalResult`，Fade 再持有 `SceneTransition`；加载边界的 `PrepareForSceneTransition()` 一次性清空全部 Reason 并恢复 `Time.timeScale = 1`。Fade Coroutine 使用 `Time.unscaledDeltaTime`，因此即使 Gameplay 已暂停也能继续变黑并加载新 Scene。

### 7.1 第一轮：事件数据正确，不代表 UGUI 坐标正确

第一次真实 P8 HUD Playthrough 暴露了三个此前静态构建无法发现的问题：

- `PhaseText` 跑到角色附近，说明全屏坐标中的手工 Offset 被误当成局部 HUD Layout；
- 35%/70% 数值虽然写进 Marker Anchor，却没有与可见血条共享同一个 Parent Rect；
- P7 的 `GameplayHUD/NotificationRoot` 仍 active，默认占位文字 `New Text` 泄漏到 P8。

排查时先从截图确认 Boss Phase、HP 与阈值数据已经到达，因此排除 `BossPhaseResolver`、Damage Funnel 与 Event Snapshot 数值错误；随后读取 Scene YAML，发现 `HealthBarRoot=100×100`、Fill/Background `Y=356`、`PhaseText Y=-51`，并确认多个 Text 的序列化值仍为 `New Text`。第一版修复尝试由 Controller 统一规范整个 HUD 的 Anchor/Pivot/Offset，虽然消除了部分错位，却错误覆盖了开发者已经在 Editor 中调好的名称、Phase 和血条纵向排版。这是一个重要的反例：Runtime 能够设置 RectTransform，不代表它应该拥有所有 Layout。

因此第二版把职责缩小为“保留 Designer Layout，只让程序控制阈值的横向 Anchor”。真实 Playthrough 再次证明它仍不完整：红色 X 与百分比 Label 共享 Marker Root 的局部 `(0,0)`，所以文字和 X 重叠；Marker Root 的 Y 又继续沿用旧 `-21.409` Offset，X 没有落到 Fill 中线上。更关键的是，`HealthBarRoot` 与真实 `HealthFill` 宽度不同，哪怕直接把 Anchor X 写成 0.7，得到的也只是“父 Root 的 70%”，不是“可见血条的 70%”。

最终修复读取 `HealthFill.rect.xMin/xMax`，通过 `TransformPoint/InverseTransformPoint` 转入 Marker Parent 的共同坐标系，再用 `Vector3.Lerp` 计算阈值点；红色 X 居中于该点，Label 根据 X 的实际显示高度排到下方。回归测试故意构造 `HealthBarRoot=1366`、`HealthFill=1300` 且 Fill 带 `X=12/Y=50` Offset 的情形，锁定 70% 点为 `X=272`、35% 点为 `X=-183`，避免以后退回“父 Anchor 看似正确、可见 Fill 实际错误”的方案。

### 7.2 Tab 失效：inactive Parent 会切断 Input System 生命周期

为了消除 P8 的 `New Text`，Scene 中曾把整个 `DemoRunUIRoot` 保存为 inactive。这个 Root 下不只有 P7 HUD，还包含共享的 `WandEditorRoot`。Unity 的 `activeSelf` 只表示对象自己是否勾选，真正决定组件是否运行的是包含父层级结果的 `activeInHierarchy`；父物体 inactive 时，即使 `WandEditorRoot.activeSelf == true`，`WandEditorController.OnEnable()` 仍不会执行。

Tab 的 Runtime 链路本应是：

```text
DemoRunUIRoot activeInHierarchy
-> WandEditorController.OnEnable
-> _toggleAction.action.performed += OnTogglePerformed
-> Player 按 Tab
-> Toggle -> Open
-> PanelRoot.SetActive(true)
```

父 Root 被关闭后，链路在第一步就断开，因此问题不是 Tab Binding、`InputActionReference` Asset 或 `RunPauseCoordinator`。错误修复是继续对子节点调用 `PanelRoot.SetActive(false)`：它只能改变可见面板，无法让父层级下的 Controller 重新进入 `OnEnable`。最终 P8 UI Policy 先启用共享 `DemoRunUIRoot`，再只禁用 `GameplayHUD` 与 `NotificationRoot`；`WandEditorController.Start()` 负责初始关闭 Panel，`Toggle()` 独占后续开关。对应 PlayMode 回归先把整个 DemoRun Root 设为 inactive，再创建 Boss HUD Controller，断言 Root 被恢复、P7-only 子树保持隐藏，并直接调用 Toggle 验证 Panel 可以打开。

最新静态构建与开发者真实 P7 → P8 Playthrough 共同形成分层证据：构建证明 Assembly 与测试代码可编译；真实 Scene 证明名称、HP、Phase、Marker、P7-only UI 隔离和 Tab 交互符合预期。Task 8 才会用 Profiler 验证 CPU、Rendering 与 `GC Alloc`，本 Task 不把功能验收夸大为性能结论。

### 7.3 Portal 关闭后停在 P7 最后一帧：被关闭的是视觉，还是服务

第二次真实流程验证出现了一个表面上像“P8 加载卡死”的回归：玩家进入 Portal 后被吸入，Portal Close 已经播放，Gameplay 也进入暂停，但画面一直停留在 P7。排查时不能直接把这个症状归因于 P8 地图太大、`LoadSceneAsync` 太慢或 Boss HUD 抛异常，因为这些解释都需要“加载请求已经开始”作为前提。

实际 Runtime 链路是：

```text
StageExitPortal.TryEnter
→ RequestPause(SceneTransition)
→ 播放 Player Transit 与 Portal Close
→ WaitForSecondsRealtime(CloseDuration)
→ Publish(SceneTransitionRequestedEvent)
→ DemoSceneTransitionController.OnTransitionRequested
→ Fade Out
→ SceneManager.LoadSceneAsync("P8_BossField")
```

日志中没有出现本次尝试的 `Loaded scene 'P8_BossField'`，而 Scene YAML 显示 `PF_P7_SceneFade` 的 Scene Instance 被保存为 `m_IsActive: 0`。这正好切断了 EventBus 边界：`DemoSceneTransitionController` 位于 Fade Prefab Root 上，Root inactive 时 Unity 不会调用该组件的 `OnEnable`，所以它没有订阅 `SceneTransitionRequestedEvent`。`StageExitPortal` 仍然可以正常 Pause、隐藏角色并发布事件，但同步 EventBus 不会缓存事件、也不会等待未来 Subscriber；没有订阅者的这一帧发布会直接结束，因此画面永久停在关闭后的状态。

这里必须区分两个概念：

- `CanvasGroup.alpha = 0`：对象和 MonoBehaviour 仍然 active，只是像素透明；`OnEnable` 订阅、Coroutine 和事件接收仍正常工作。
- `GameObject.SetActive(false)`：整个层级停止参与 Unity Lifecycle；其组件会收到 `OnDisable` 并取消订阅，不能再承担 Scene Transition Service。

所以 Fade 的正确结构是“服务 Root 始终 active，视觉由 CanvasGroup 隐藏”，而不是“为了看不见黑色图片而禁用整个 Prefab”。同时发现 Fade Prefab Root 的 Local Scale 被保存成 `(0,0,0)`；这会让 Fade 即使 active 也无法可靠显示，因此一并恢复为 `(1,1,1)`。新增的 `SceneTransitionAuthoringTests` 使用 `EditorSceneManager.OpenPreviewScene` 读取磁盘上的 P7/P8 Scene，不替换开发者当前打开的 Scene，然后断言 Transition Controller 存在、Root/Parent active 且 Scale 非零。该测试保护的是 Authoring Contract，而不是再次测试 `EventBus` 本身。

本次 RED 证据为 `sceneFadeInactive=True`、`prefabScaleZero=True`；修正后磁盘 Guard 均为 `False`，`Game.Run.Tests.csproj` 与 `Game.UI.csproj` 静态构建均为 `0 warning / 0 error`。但这仍不能替代 Unity Test Runner 与真实 P7 Portal → Fade → P8 Playthrough；在开发者完成该 Gate 前，本回归保持“代码与 Authoring 已修正、Runtime 待验证”。

## 9. 常见故障定位

- **HUD 一直不出现**：先检查 Controller 是否错误地挂在 `BossHUDRoot` 上；再检查 Boss 是否真正响应 Encounter、Console 是否提示 PlayerId 不匹配。
- **HP 数值变但画面不缩短**：检查 `HealthFill.Image.Type` 是否为 `Filled`，不要先改 Damage Event。
- **Marker 与血条百分比不一致**：确认 `Marker Root` 与 `HealthFill` 共享同一个 RectTransform Parent；程序按真实 Fill Rect 插值，而不是按外层装饰框宽度猜位置。
- **红色 X 压住 35%/70%**：确认 Marker Root 的直接子物体中，一个是带 `Image` 的 `MarkerLine`，另一个是带 Legacy `Text` 的 Label。错误组件类型或多层嵌套会让一次性子节点识别找不到目标。
- **P8 按 Tab 没反应**：检查 `DemoRunUIRoot.activeInHierarchy` 与 `WandEditorRoot.activeInHierarchy`，不要只看子物体的 `activeSelf`；父 Root inactive 时 `OnEnable` 不会订阅 Input Action。
- **Retry 回 P8 但 Wand 没恢复**：检查 BossEntryTrigger 出圈时是否成功 Capture Checkpoint，以及 P8 Menu 的 Session 字段是否错误绑定了 Scene-local 空对象。
- **Restart 后仍在 P8**：检查 Button 是否仍绑定旧的 `ReloadCurrentScene` 或错误方法，正确入口是 `RestartRun`。
- **Main Menu 仍残留 Session Root**：确认 Button 绑定 `ReturnToMainMenu`，而不是直接调用 Scene Transition；直接 Load Scene 会绕过 `EndRun`。
- **点击按钮后游戏保持黑屏/暂停**：检查 `DemoSceneTransitionController` 与 `RunPauseCoordinator` 绑定，以及加载边界是否执行 `PrepareForSceneTransition`。

## 11. Task 7 收口证据、性能影响与剩余边界

本次收口重新顺序构建了 `Game.Run.Tests.csproj`、`Game.Character.PlayMode.Tests.csproj`、`Game.Run.PlayMode.Tests.csproj` 与 `Game.UI.csproj`，四个项目均得到 `0 warning / 0 error`。这属于 **Static Compilation Evidence**：它证明 C# 类型、Namespace、Assembly Reference 和测试代码能够编译，但不等于 NUnit Case 已经在 Unity Player Loop 中执行。

**Scene Playthrough Evidence** 来自开发者最终确认：P7 Portal 能进入 P8；Boss 名称、HP、Phase 正确；红色 X 精确落在 35%/70% 位置，数字位于对应 X 下方；P7-only UI 不再出现；P8 按 Tab 可以正常开关法术编程页面。开发者据此明确同意 Task 7 收口。两类证据互补，但不能互相冒充。

Task 7 的 Runtime 成本具有以下边界：

- Marker 几何只在收到一次 `BossHudInitializedEvent` 时计算，不在 `Update`/`LateUpdate` 中执行；
- `Vector2/Vector3` 是 Value Type，局部计算不会为每个向量创建 Managed Heap Object；

# 收口后修复：陨石术三段伤害数据化

这次修复的目的不是单纯把 Boss 的某个数字调小，而是纠正一条玩法层数据链：玩家在 `SpellDefinition` Inspector 和 Tooltip 中看到的伤害，必须能解释 Runtime 真正提交给 `IDamageable` 的每一段 `DamageRequest`。旧实现把陨石看成“只有一个 Damage 的投射物”，但陨石实际同时包含投射物直击、一次性爆炸 AOE、持续火场 AOE，此外还会向 ElementWorld 写入 Fire。一个标为 15 的字段被重复用于多个不同时间尺度的伤害阶段后，Inspector 不再是可靠的数据来源，设计师无法平衡，玩家也无法理解 Tooltip。修复后，`SpellDefinition` 明确保存直击、爆炸、火场每跳、Tick Interval 和 Duration；`CastEvaluator` 把 Damage Modifier 烘焙为一次施法快照；`SpellCaster` 只负责跨 Assembly 注入；`NovaFireball` 和 `AreaDamage` 执行各自阶段。玩家与 Boss 还使用不同资产，避免调 Boss 时无意改变玩家法术。

## 1. 症状、证据与真正根因

### 1.1 表面症状

玩家陨石资产原本显示：

```text
Base Damage = 15
```

如果把它理解为“陨石总伤害 15”，玩家 100 HP 理论上需要承受多颗陨石才会死亡。但实际现象是：玩家被一颗陨石碰到或站进火场后，HP 在几秒内迅速归零。仅把 `Base Damage` 从 15 调到更小虽然能缓解死亡速度，却没有回答“15 被结算了几次、哪些阶段受 Modifier 影响、爆炸究竟有没有伤害”。

### 1.2 先排除多个 Collider 重复直击

`ProjectileBase.OnCollisionEnter` 是第一条需要检查的链路。它会从碰撞 Collider 的父级获得一个 `IDamageable`，对敌方存活目标提交一次 `DamageRequest`，随后设置 `_consumed` 并销毁投射物。`_consumed` 是一次性防重入 Gate，因此同一颗陨石不会因为角色拥有 `CharacterController`、身体 Collider 和子级 Hurtbox，就在相邻 Physics 回调里反复执行完整 Impact。

`AreaDamage` 的每一次 `ApplyOnce` 也会复用 `_tickHitSet`，按 `IDamageable` 对应的 Unity Object InstanceID 去重。也就是说，同一个 Tick 内多个 Collider 只会命中同一角色一次。排除这一点很重要：如果误以为是 Collider 重复，可能会错误删除角色 Collider 或修改 Physics Layer，却完全触及不到真正的伤害倍增来源。

### 1.3 爆炸看起来很强，但旧配置实际为 0

`NovaFireball` 命中后生成的爆炸 Prefab 是 `NukeConeExplosionFire`。审计 Prefab 发现它只有 Particle System、Light、Audio Source 等表现组件，没有 `AreaDamage`。`NovaFireball.SpawnEffect` 虽然会执行：

```csharp
AreaDamage[] areas = go.GetComponentsInChildren<AreaDamage>(true);
```

但数组为空，循环不会进入。所以旧版本中的爆炸是纯 VFX，第二段爆炸伤害实际为 0。项目里另有带一次性 `AreaDamage` 的 `NovaExplosion_Hit`，但当前陨石并未引用它。这个事实说明视觉强度不能作为 Gameplay 证据：画面上“炸得很大”不代表 Damage Pipeline 收到了爆炸请求。

### 1.4 火场 Inspector 的 1 为什么变成了运行时的 15

`FireField` Prefab 原本配置：

```text
Damage Per Hit = 1
Tick Interval = 0.5
```

但 `NovaFireball.SpawnEffect` 在 Instantiate 后、`AreaDamage.Start` 前执行：

```csharp
areas[i].ConfigureDamage(_damage, _type);
```

`_damage` 是 `ProjectileBase.Init` 接收到的最终直击伤害，也就是 `CastEvaluator` 从 `SpellDefinition.BaseDamage` 与 Modifier 算出的值。于是 Prefab 的 1 会被覆盖为 15。Unity 的生命周期顺序允许 Instantiate 后立即配置 Component，而新对象的 `Start` 要到之后才执行，因此首跳读取到的已经是 15，不是 Inspector 中的 1。

这段代码最初是为了让 `[增伤] [陨石术]` 不只增强直击，也增强主要 AOE；设计动机正确，但它把“同一个最终伤害”注入爆炸和火场每一次 Tick，忽略了持续伤害会重复结算这一时间维度。

### 1.5 旧版本的实际伤害账单

`AreaDamage.Start()` 会立即执行一次 `ApplyOnce()`，然后在 `_tickInterval > 0` 时继续倒计时。火场持续 5 秒、间隔 0.5 秒，通常会在 `t=0, 0.5, 1.0 ... 4.5` 结算约 10 次；如果销毁和最后一帧 Update 的时序恰好允许 `t≈5.0` 再执行一次，理论上可能达到 11 次。因此旧版本单颗陨石为：

```text
直击：15 × 1 = 15
爆炸：0
火场：15 × 10～11 = 150～165
合计：165～180
```

玩家最大 HP 为 100。即使忽略爆炸，只需直击和约 6 次火场 Tick 就会达到 105，玩家大约三秒内死亡。

新实现没有继续依赖 `Destroy(go, duration)` 猜测最后一跳。`AreaDamage.ConfigureDuration` 会在 `Start` 前把持续时间转换为：

```text
TickLimit = ceil(Duration / TickInterval)
```

`Start` 的立即首跳也消费一个 Budget；当 `_remainingTicks == 0` 时，`Update` 不再结算。即使 Unity 延迟到本帧末尾才真正 Destroy VFX，也不会多出第 11 跳。因此玩家/Boss 的 45/50 是确定的设计上限（不含 Burning），而不是 45～47 或 50～52 的浮动区间。

`MeteorJudgment` 通过 Triple Multicast 抽取三个独立 Trigger Action，每个 Trigger Fireball 捕获一个 Meteor Payload。三颗陨石会生成三个独立火场；`AreaDamage` 的去重集合属于单个实例，只防止一个火场在一次 Tick 内因多个 Collider 重复命中，不会阻止三个不同火场分别伤害玩家。三场重叠时旧版本一次共同 Tick 为 `15 × 3 = 45`，每 0.5 秒一次，约等于 90 DPS，尚未计算触发火球和直击。

### 1.6 Fire Deposit 与 Burning 是第四条独立伤害链

`NovaFireball` 同物体上的 `ElementDepositOnImpact` 会在命中后向 `ElementRuntimeRegistry` 入队一个 Fire `ElementWriteRequest`。这不是直接的 `DamageRequest`：写入在 ElementWorld Simulation Tick 中处理，之后 `ElementWorldExposureSystem` 每 0.25 秒采样角色 Bounds 覆盖的 Fire Cell，并调用：

```text
StatusController.ApplySustainedStatus(Burning, ...)
```

`Status_Burning` 的满强度伤害为每 0.2 秒 0.1，即约 0.5 DPS。实际强度取决于火元素在 Cell 中的 Amount、扩散、衰减、角色覆盖位置和水火反应。它确实可能额外扣血，但量级远低于旧火场约 30 DPS，不是本次秒杀的主因。

修复后仍不把 Burning 合并进“理论完整伤害”，因为它属于可与 Water、Wet、Reaction Kernel 交互的环境状态链，而不是陨石固定保证的三段伤害。把两者混成一个数字会再次失去系统边界。

## 2. 新的数据模型与数值预算

### 2.1 SpellDefinition 是唯一权威 Authoring

`SpellDefinition` 新增：

```csharp
public float ExplosionDamage;
public float FireFieldDamagePerTick;
public float FireFieldTickInterval;
public float FireFieldDuration;
```

原 `BaseDamage` 在复合法术语境中明确解释为“投射物本体直接碰撞的一次性直击”，Tooltip 改名为“直击伤害”。Prefab 仍然保存：

- VFX 形状与生命周期；
- `AreaDamage.Radius`；
- `HitMask`；
- `TriggerHitReaction`；
- 爆炸/火场旋转等表现与空间参数。

Prefab 上的 `_damagePerHit` 只是没有 Runtime 注入时的 fallback，不再是陨石伤害的权威数据。这个分工的理由是：伤害属于法术内容设计，半径和 VFX 结构属于具体 Effect Prefab。如果未来需要让爆炸半径也被法术 Modifier 改变，再把 Radius 加入命令快照；当前不要一次把所有 Prefab 参数搬进 SpellDefinition，避免不必要的过度设计。

### 2.2 玩家与 Boss 使用不同资产

最终数值为：

| 使用者 | 直击 | 爆炸 | 火场每跳 | Interval | Duration | 设计 Tick 数 | 理论总量 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 玩家普通陨石 | 10 | 15 | 2 | 0.5 秒 | 5 秒 | 10 | 45 |
| Boss 专属陨石 | 12 | 18 | 2 | 0.5 秒 | 5 秒 | 10 | 50 |

“单颗 Boss 陨石理论 50”不等于每次技能必扣 50。直击要求陨石 Collider 真正撞到玩家；爆炸要求玩家位于 Radius；20 点火场需要玩家完整停留 5 秒。预警、走位和离场都会减少实际伤害。相反，三个落点重合且玩家不移动时仍可能叠加至高伤害，这是 Boss Pattern 的可规避惩罚，不应由全局去重强行消除。

## 3. Damage Modifier 的精确定义

### 3.1 为什么 Multiplier 作用于三段

当前 `[增伤]` 使用 `ModDamageMul = 1.5`。玩家的直觉是 `[增伤] [陨石术]` 强化整颗陨石，而不是只强化看起来最不明显的碰撞。因此：

```text
FinalDirect = max(0, (BaseDamage + Flat) × Multiplier)
FinalExplosion = max(0, ExplosionDamage × Multiplier)
FinalFieldPerTick = max(0, FireFieldDamagePerTick × Multiplier)
```

以玩家陨石为例，1.5 倍后为：

```text
直击 15
爆炸 22.5
火场每跳 3
理论完整伤害 67.5
```

Interval 与 Duration 不改变，因为它们描述伤害节奏和区域控制时间，不是伤害强度。如果增伤同时缩短 Interval 或延长 Duration，倍率会以非线性方式放大总 Tick 数，很难从 Tooltip 解释。

### 3.2 为什么 Flat Bonus 不加到每个阶段

`ModDamageAddFlat` 是一次 Action 的固定加值。如果把 Flat=5 同时加到直击、爆炸和十次火场 Tick，它对单颗陨石的总贡献会变成：

```text
直击 +5
爆炸 +5
火场 +5 × 10
= +60
```

这已不是“固定增加 5”，而是被复合结构重复 12 次。当前项目还没有正式使用非零 Flat Damage 资产，但必须在协议层提前定义，否则以后新增卡牌时会重现本次问题。因此本实现让 Flat 只加到一次性直击，Multiplier 才缩放整个复合法术。

另一种可选设计是把 Flat 先换算为相对比例，再同比缩放全部阶段，但当 BaseDamage=0 时会出现除零和语义不清；当前方案更简单、稳定，也符合 YAGNI。

```text
SpellCaster.ConfigureCompositeDamage
    ↓
NovaFireball.ConfigureImpactDamage
    ↓
ProjectileBase.Init
    ↓ 保存直击 Damage / Team / Attacker / Velocity
ProjectileBase.OnCollisionEnter
    ├─ 敌方目标：提交一次直击 DamageRequest
    └─ NovaFireball.OnImpact
         ├─ Spawn Explosion VFX
         │    └─ AreaDamage：ExplosionDamage，Tick=0
         └─ Spawn FireField
              └─ AreaDamage：DamagePerTick，TickInterval，按 Duration 销毁
                   ↓
              IDamageable.ReceiveHit
                   ↓
              HealthComponent → DamagePipeline → HP/EventBus
```

关键顺序是 `ConfigureCompositeDamage` 和 `ProjectileBase.Init` 都发生在首次碰撞前。爆炸/火场生成后，`NovaFireball` 又必须在 `AreaDamage.Start` 前依次调用 `Init`、`ConfigureDamage`、`ConfigureTickInterval`、`ConfigureDuration`。如果配置发生在 Start 之后，首跳会使用 Prefab fallback，第二跳才换成正确值，产生一次难以发现的混合伤害；如果 Duration 早于 Interval 配置，Tick Budget 也无法按最终节奏计算。

## 5. Assembly 职责为什么这样划分

### 5.1 Game.Skills：规则与纯数据

- `SpellDefinition`：设计师 Authoring。
- `CastModifierState`：当前 Action 累积的不可变 Modifier Snapshot。
- `CastEvaluator`：纯解释器，只做预算、顺序、Payload 与数值计算。
- `EmitCommand`：一次产出的只读值快照。

它不 Instantiate、不访问 Scene、不查询 Collider，所以可以用 EditMode 单元测试准确验证 `[增伤]` 对三个通道的结果。

### 5.2 Game.Character：Unity Runtime Adapter

`SpellCaster` 知道 `Game.Skills.EmitCommand`，也能依赖 `Game.Combat.ProjectileBase`。它负责把上层纯数据翻译为 Unity 对象配置，但不执行伤害查询。这里用：

```csharp
if (projectile is NovaFireball meteor)
```

识别当前复合投射物并注入快照。现阶段只有陨石需要该协议，直接类型检查比提前抽象一个只有一个实现的 Interface 更符合 YAGNI；如果未来火焰雨、毒雾弹等多个 Combat Projectile 都消费相同配置，再抽 `ICompositeDamageProjectile`。

### 5.3 Game.Combat：碰撞与统一伤害漏斗

`NovaFireball` 不引用 `SpellDefinition` 或 `EmitCommand`，只接收普通 float 与 `DamageType` 快照。`AreaDamage` 只负责：

- `OverlapSphereNonAlloc`；
- Team Filter；
- 单 Tick 多 Collider 去重；
- 构造 `DamageRequest`；
- 调用 `IDamageable.ReceiveHit`。

这保持了单向依赖：Combat 不需要认识 Skills，所有伤害来源仍进入统一漏斗。

### 5.4 Game.UI：只读展示

`SpellTooltipPresenter` 读取 `SpellDefinition` 的 Authoring 值，显示直击、爆炸、火场每跳/间隔/时长和理论完整伤害。Tooltip 的“理论完整伤害”采用：

```text
ceil(Duration / Interval) × DamagePerTick
```

它是平衡参考，不承诺玩家必然吃满，也不包含 ElementField Burning。文本只在第一次遇到某个 Spell 时构建并缓存，Pointer Move 仍只更新 RectTransform，避免 Hover 热路径反复产生字符串 `GC Alloc`。

## 6. 爆炸 Prefab 与 AreaDamage

`NukeConeExplosionFire` Root 新增一次性 `AreaDamage`：

```text
Radius = 5
Damage Per Hit = 0
Damage Type = Magical
Hit Mask = Everything
Tick Interval = 0
Trigger Hit Reaction = true
```

`Damage Per Hit = 0` 是有意的：这个 Prefab 单独拖进 Scene 时不会凭空造成伤害；由陨石生成时，Runtime 会在 Start 前注入 15 或 18。`Tick Interval = 0` 让爆炸只在 Start 结算一次。

`FireField` 保持：

```text
Radius = 6.7
Trigger Hit Reaction = false
```

持续火场不触发受击硬直，是为了避免玩家每 0.5 秒反复进入 Hurt 状态而失去操作。它的 Damage 与 Interval 均由本次 `EmitCommand` 注入；Duration 由 `NovaFireball` 对实例调用 `Destroy(go, duration)` 控制。

### 7.2 性能影响

- `EmitCommand` 增加四个 float，是 Value Type 快照增大，不会单独创建 Managed Heap Object。
- `CastEvaluator.BakeEmit` 只增加常数次 `Mathf.Max` 和乘法，复杂度仍由解释器读取的 Spell 数量决定。
- `ConfigureCompositeDamage` 是投射物生成时的一次类型检查，不在每帧热路径。
- `NovaFireball.SpawnEffect` 原本就会在命中时 `GetComponentsInChildren<AreaDamage>(true)` 并 Instantiate；本次只增加字段赋值。
- `AreaDamage.Update` 没有新增分配；仍复用 Collider Buffer 与 HashSet。
- `ConfigureDuration` 只在生成时做一次除法和 `CeilToInt`，之后每跳只递减整数 Tick Budget；它既避免销毁帧多跳，也不引入 Coroutine 或逐帧对象分配。
- 三段伤害变小不会自动减少 Physics 查询次数；火场数量、持续时间、Tick Interval 才决定查询次数。
- 爆炸新增一次 `OverlapSphereNonAlloc`，每颗陨石命中时执行一次，属于离散成本。

不能据此声称 `GC Alloc = 0 B` 或 CPU 可忽略。第三方 VFX、Instantiate/Destroy、Particle System、Audio 与 HashSet 首次扩容都可能产生真实成本，必须在 Development Build 或 Editor Profiler 中采样。

## 8. Unity Editor 验证与常见失败

### 8.1 必须验证的场景行为

1. 玩家陨石 Asset 显示 10/15/2、0.5 秒、5 秒，Tooltip 理论完整伤害为 45。
2. Boss 陨石 Asset 显示 12/18/2、0.5 秒、5 秒，Boss Wand 的所有 Element 均来自 BossSpell 目录。
3. 玩家只被陨石本体撞到但立刻离开爆炸/火场时，观察直击与爆炸分段扣血。
4. 玩家站在单个火场中，确认每 0.5 秒约扣 2，而不是 15。
5. 三个火场重叠时允许独立叠加，但离开重叠区域后停止 Tick。
6. 玩家 `[增伤] [陨石术]` 时，直击/爆炸/每跳均为 1.5 倍，Interval 与 Duration 不变。
7. Fire Deposit 仍能写入 ElementWorld 并施加 Burning；它不会被 Tooltip 的 45/50 重复计算。

### 8.2 常见失败定位

- **爆炸有 VFX 但不掉血**：检查 `NukeConeExplosionFire` Root/Child 是否有 `AreaDamage`，以及 NovaFireball 的 Explosion Prefab 引用是否仍指向该 Prefab。
- **火场仍每跳 15**：确认代码中不再存在 `ConfigureDamage(_damage, _type)`；检查 `EmitCommand.FireFieldDamagePerTick` 是否为 2。
- **火场完全不生成**：`FireFieldDuration=0` 会有意关闭火场；检查玩家/Boss Asset 是否已写入 5。
- **Boss 数值和玩家一样**：检查 `P8_BossWand_MeteorJudgment` 的 GUID，不要只看 Element 显示名称，因为两份资产都可能显示“陨石”。
- **Tooltip 仍显示旧文本**：退出并重新进入 Play Mode 或重新创建 Presenter；Tooltip 有 InstanceID 缓存，运行时改 Asset 后旧 Cache 不会自动刷新。
- **爆炸第一跳用 0**：检查 `NovaFireball` 是否在 `AreaDamage.Start` 前完成 `ConfigureDamage`；不要把注入延迟到 Coroutine 或下一帧。
- **一次 Tick 扣多次**：先看是否有多个独立火场实例；不要把合法的实例叠加误判为同一实例的 Collider 重复。
- **只调低 FireField Prefab Damage 就认为修好**：运行时会覆盖 fallback；权威值应在 `SpellDefinition`，Prefab 值不再承担平衡职责。
