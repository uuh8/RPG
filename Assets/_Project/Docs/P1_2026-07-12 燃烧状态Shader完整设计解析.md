# P1：燃烧状态 Shader 完整设计解析

> 创建时间：2026-07-12 01:00  
> 适用项目：Unity 6.3、URP 17.3、Shader Graph  
> 阅读对象：第一次完整开发 Gameplay 状态 Shader、正在学习图形学与实时渲染的开发者

## 一、先从最终效果反推问题：我们要实现的不是“把角色染红”

燃烧状态的 Gameplay 数据只是一个百分比：角色当前有多强的 Burning。可是在画面上，一个百分比本身什么也画不出来。Shader 必须把这个一维标量转化成随时间和空间变化的二维表面图案，再让图案同时影响颜色与能量表现。

最终效果可以拆成四个视觉目标：

```text
1. 空间分布：只有角色表面的部分区域出现火纹，而不是全身均匀变红。
2. 时间变化：火纹持续向角色上方流动，表现热量和火焰上升。
3. 材质变化：燃烧区域的表面变暗、焦黑、偏暗红，但原服装纹理仍能辨认。
4. 能量表现：高温区域产生橙红色 HDR Emission，并由 Bloom 形成外围辉光。
```

把它写成数据流，就是：

```text
Gameplay Burning（0~100）
    ↓ C# 归一化和平滑
Shader Burning Intensity（0~1）
    ↓ 非线性视觉响应
Burn Visual Intensity
    ↓ 控制阈值和亮度
动态程序化 Burn Mask
    ├──→ 修改 Base Color：焦黑暗红
    └──→ 修改 Emission：橙红高温
```

这里最重要的设计判断是：**状态强度不是最终颜色，而是生成视觉行为的控制信号。** 如果直接执行：

```text
FinalColor = Lerp(OriginalColor, Red, BurningIntensity)
```

那么角色只会随着强度增加而整体变红。这虽然能告诉玩家“有状态”，却没有空间结构、动态运动和材质质感，也无法体现你正在学习的图形学能力。

我们最终采用的是“程序化表面 Mask + PBR Base Color 修改 + HDR Emission + 外部火焰 VFX”的混合方案。角色皮肤内部的灼烧纹理由 Shader 表达；角色外围真实飘动的火焰仍由现有 `OnFire` Particle VFX 表达。Shader 擅长逐 Fragment 修改表面，Particle System 擅长表现脱离表面的体积与运动。让两者各做擅长的事情，比强迫一个系统包办全部效果更可靠。

## 二、常见方案与最终取舍：为什么选择程序化 Noise

业界实现角色燃烧，常见的不止一种方式。

第一种是只挂 Particle VFX。它开发快、轮廓明显，也适合火苗和烟雾，但无法自然改变衣服、皮肤和盔甲表面；火焰像“贴在角色外面”，缺少材质被烧灼的感觉。

第二种是使用预制的 Fire Mask 或 Flipbook Texture。美术可以精确控制图案，运行成本也容易估算，但需要额外纹理资源；不同角色 UV、体型和部件可能需要重新制作，并且重复播放后容易被玩家看出周期。

第三种是 UV 滚动。它让一张噪声贴图按 `UV + Time×Speed` 移动，成本低，但角色 UV 由许多不连续的 Texture Island 组成。帽子、身体、手套和武器的 UV 接缝会让火纹突然断开，不同 Island 的纹理密度也会让图案大小不一致。

第四种是 World Space Noise。它不依赖角色 UV，多个物体之间还能拥有连续图案；但 Noise 像固定在世界里，角色移动时会穿过它，火纹会在表面“游泳”，不适合需要附着角色的状态。

第五种是 Object Space 程序化 Noise。它也不依赖 UV，而且角色整体平移和旋转时局部坐标保持附着，因此适合当前目标。它的代价是：角色由多个独立 `SkinnedMeshRenderer` 组成时，每个 Renderer 可能有自己的 Object Space，部件交界处可能出现图案断层。当前第一版接受这一风险，后续在 WizardPlayer 与 MagicEnemy 上实测；如果接缝不可接受，再升级为“角色根节点相对坐标”或 Triplanar/3D Noise，而不是一开始就增加全部复杂度。

最终选择可以概括为：

```text
表面火纹：Object Space 程序化 Simple Noise
焦黑质感：Base Color 上的乘法与 Lerp
高温亮纹：HDR Emission
外围火焰：既有 OnFire Particle VFX
状态控制：C# MaterialPropertyBlock
```

这是一个面试中值得讲清楚的 trade-off：我们没有追求物理火焰模拟，而是在 Gameplay 可读性、资源依赖、角色复用和 GPU 成本之间选择了一个可扩展的实时方案。

## 三、从 Gameplay 到 GPU：燃烧强度如何抵达 Shader

燃烧首先是 Gameplay 状态，而不是 Shader 参数。`Game.Combat.StatusController` 维护权威状态：

```text
StatusKind.Burning
Intensity：0~100
NaturalDecayPerSecond：自然衰减速度
DamageInterval：DoT 间隔
BaseDamagePerTick：每次伤害
VfxPrefab：外围 OnFire 特效
```

每次施加、衰减到新的整数百分比或状态退出时，`StatusController` 发布 `StatusChangedEvent`。事件包含：

```csharp
TargetId
Kind
Intensity
IsActive
Icon
DisplayName
```

`TargetId` 是全局 EventBus 中的“收件人地址”。如果没有它，一个敌人着火时，所有订阅者都可能一起改变材质。

`Game.Rendering.StatusMaterialController` 是 Gameplay 与 Shader 之间的只读表现桥。它订阅事件，但不反向修改状态。收到属于自己的 Burning 事件后，先执行：

```csharp
normalized = Mathf.Clamp01(statusIntensity * 0.01f);
```

于是：

```text
0   → 0.00
25  → 0.25
50  → 0.50
100 → 1.00
150 → Clamp 后仍为 1.00
```

Gameplay 使用 0~100，是因为策划、UI 和玩家更容易理解百分比；Shader 使用 0~1，是因为 `Lerp`、Mask、`Smoothstep` 和颜色混合通常在归一化区间工作。

组件没有立即把 `_current` 跳到 `_target`，而是在 `Update()` 使用 Unity API：

```csharp
Mathf.MoveTowards(current, target, responseSpeed * Time.deltaTime)
```

默认 `_responseSpeed = 4`，理论上从 0 到 1 最快约 0.25 秒。这样 Gameplay 强度即使按整数事件更新，画面也不会一格一格跳变。`Time.deltaTime` 是 Unity 提供的上一帧时间间隔；乘以“每秒变化速度”后，得到这一帧最多推进多少。

最终通过：

```csharp
Shader.PropertyToID("_BurningIntensity")
MaterialPropertyBlock.SetFloat(...)
Renderer.GetPropertyBlock(...)
Renderer.SetPropertyBlock(...)
```

把数值写入 Renderer。

`Shader.PropertyToID` 是 Unity API，它把字符串属性名缓存为整数 ID，避免热路径反复做字符串查找。Shader Graph Blackboard 的 Reference 必须精确写成 `_BurningIntensity`，不能是自动生成的 `_Burning_Intensity`。

`MaterialPropertyBlock`，简称 MPB，允许多个角色继续共享同一份 Material，却拥有不同的 Renderer 参数：

```text
Wizard Renderer：_BurningIntensity = 1.0
Enemy Renderer： _BurningIntensity = 0.3
Shared Material：仍是同一份资产
```

如果使用 `renderer.material`，Unity 会为 Renderer 创建 Material Instance，角色数量增加后会造成材质副本膨胀。MPB 避免了这种副本，但它也可能影响 SRP Batcher 的批处理方式，因此最终必须用 Frame Debugger 和 Profiler 测量，而不能简单宣称“MPB 一定更快”。

`ApplyPropertyBlock()` 在写 Burning 前先调用 `GetPropertyBlock()`，是为了保留其他系统已经写入的 `_BaseColor`，例如 `CharacterCombatFeedback` 的受击闪红。若创建一个空 MPB 后直接 Set，可能把其他表现组件的参数覆盖掉。

需要明确区分两类 Shader 属性：

```text
代码实时控制：_BurningIntensity

Material 美术配置：
_BurnNoiseScale
_BurnFlowSpeed
_BurnMaskSoftness
_BurnSurfaceColor
_BurnEmissionColor
```

`Burn Emission Color` 常驻在 Material Inspector 中是正确的，它只保存“如果燃烧，应该用什么颜色”。真正输出是：

```text
BurnEmission = FinalBurnMask × BurnEmissionColor
```

当 Intensity 为 0 时 Mask 必须为 0，颜色虽然仍配置为橙色，最终贡献仍是 0。就像 C# 中 `fireColor` 可以常驻，但乘以 `fireIntensity=0` 后输出为黑色。

## 四、核心图形算法：从 Object Space Position 生成流动 Burn Mask

### 4.1 为什么从 Position 开始

`Position(Object)` 为每个 Fragment 提供模型局部位置：

```text
P = (x, y, z)
```

角色整体在世界中移动时，World Position 改变，但局部 Position 仍附着于模型。我们使用 Split 节点把向量拆成：

```text
Split.R = x
Split.G = y
Split.B = z
```

Shader Graph 用 RGB 和 XYZ 共用向量分量语义，所以 R/G/B 在这里不是颜色，而是 X/Y/Z。

`Simple Noise` 使用二维坐标。为了让三维角色前后方向也参与图案，而不是只按 X/Y 形成贯穿 Z 的规则条带，我们构造：

```text
horizontal = x + 0.37z
```

系数 0.37 不是物理常数，而是用于打破 X/Z 对称的经验值。它把一部分前后坐标折入横向采样，让图案在角色侧面也发生变化。这仍然只是 3D 到 2D 的投影，不是真正的 3D Noise，因此会存在方向偏置；第一版用较低复杂度换取可读性和性能。

### 4.2 时间为什么能让图案运动

Time 节点提供随运行时间增长的标量。我们计算：

```text
flowOffset = Time × _BurnFlowSpeed
vertical = y + flowOffset
```

在当前角色模型的 Object Space 轴约定下，经过 Game View 实测，这个加号使可见火纹向角色上方流动。理论上纹理相位方向还取决于采样函数与坐标轴约定，因此不能只凭纸面符号认定最终视觉方向；必须在目标 Mesh 上验证。

这次开发最初使用了减号，数学预期与实际导入模型的视觉结果不一致，最终通过检查 `Split.G`、Subtract 的 A/B 端口和 Game View 运动方向，将它改成 Add。这是图形开发的重要经验：**先推导预期，再用真实 Mesh、Coordinate Space 和画面验证。**

我们把两个标量组合为二维坐标：

```text
noiseCoordinate = float2(horizontal, vertical)
```

再乘：

```text
noiseUV = noiseCoordinate × _BurnNoiseScale
```

Scale 越大，同样大小的 Object Space 中经过更多 Noise 周期，所以图案越细碎；Scale 越小，图案越宽大。Lab Material 当前实测配置为约 5.24，而 Shader Graph 属性默认值是 3。

由于坐标已经乘 `_BurnNoiseScale`，`Simple Noise` 节点自己的 Scale 应保持 1，否则会重复缩放。例如外部 Scale=5、节点 Scale=2，实际频率相当于 10，Material Inspector 的参数就不再直观。

最终：

```text
noise = SimpleNoise(noiseUV)
```

得到大致处于 `[0,1]` 的连续灰度场。它还不是燃烧，只是空间中连续变化的随机值。

### 4.3 为什么低强度需要非线性视觉响应

最初直接使用 `_BurningIntensity`，同时让它控制阈值和最终亮度：

```text
threshold = Lerp(0.95, 0.35, intensity)
finalMask = mask × intensity
```

当 Intensity=0.25 时，Threshold 仍高达 0.80，只有很少 Noise 能超过它；随后这些少量区域又乘 0.25，亮度再被压低一次。因此低强度同时遭受“面积少”和“亮度低”两次衰减，0.5 以下几乎看不清。

Gameplay 数值线性，不代表人眼感知也必须线性。最终增加：

```text
visualIntensity = pow(saturate(intensity), 0.6)
```

`Saturate(x)` 等价于 `Clamp(x,0,1)`。Power 指数小于 1 会抬高 0~1 的中间值，同时保持两个端点：

```text
0^0.6 = 0
1^0.6 = 1

0.10^0.6 ≈ 0.25
0.25^0.6 ≈ 0.44
0.50^0.6 ≈ 0.66
```

于是 10% Burning 已有可辨认反馈，但 0 仍绝对关闭，100% 仍保持完整强度。这是一条面向感知的 Ease-Out/Gamma-like 曲线。面试时可以强调：我们没有篡改 Gameplay 状态，只在 Presentation 层做非线性映射，保证低强度状态的战斗可读性。

### 4.4 阈值如何把 Noise 变成“燃烧区域”

如果只做：

```text
mask = noise × intensity
```

所有区域会一起变亮或变暗，像透明度变化，不像火势蔓延。我们希望强度增加时，越来越多区域进入燃烧，所以让强度控制阈值：

```text
threshold = Lerp(0.95, 0.35, visualIntensity)
```

根据：

```text
Lerp(A,B,T) = A(1-T) + BT
```

低强度时 Threshold 接近 0.95，只有 Noise 最亮的少数区域燃烧；高强度时 Threshold 降到 0.35，大量中灰区域也被纳入燃烧。强度因此同时影响“火纹面积”与“火纹亮度”。

硬阈值 Step 会执行：

```text
noise < threshold  → 0
noise >= threshold → 1
```

边界从 0 突然跳到 1。当边界比屏幕像素还细，角色或 Camera 轻微移动会导致像素在相邻帧反复切换，出现 Alias、锯齿和爬动。因此使用：

```text
lower = threshold - _BurnMaskSoftness
upper = threshold + _BurnMaskSoftness
mask = Smoothstep(lower, upper, noise)
```

`Smoothstep` 可理解为先归一化：

```text
t = saturate((noise-lower)/(upper-lower))
```

再应用三次 Hermite 曲线：

```text
smooth = t²(3-2t)
```

它在区间两端的斜率趋近 0，边缘比线性插值更平滑。`_BurnMaskSoftness` 越小，边缘越硬；越大，过渡越宽。Lab Material 当前约为 0.165，Shader Graph 默认值为 0.08。

最后再执行：

```text
finalBurnMask = mask × visualIntensity
```

这一步不仅控制亮度，还建立严格关闭条件：即使 Intensity=0 时 Noise 偶然超过 0.95，乘 0 后仍绝对没有残留火点。

到这里完整 Mask 公式是：

```text
P = Position(Object)
horizontal = P.x + 0.37P.z
vertical = P.y + Time×BurnFlowSpeed
noiseUV = float2(horizontal,vertical)×BurnNoiseScale
noise = SimpleNoise(noiseUV)

visualIntensity = pow(saturate(BurningIntensity),0.6)
threshold = lerp(0.95,0.35,visualIntensity)
lower = threshold-BurnMaskSoftness
upper = threshold+BurnMaskSoftness
mask = smoothstep(lower,upper,noise)
finalBurnMask = mask×visualIntensity
```

## 五、同一个 Mask 如何同时驱动焦黑表面与 HDR 火纹

生成 Mask 后，不能直接把红色连接到 Fragment/Base Color。角色原本的 Base Map 包含服装图案、材质分区和细节；直接替换成纯红会丢失角色辨识度。

基础 PBR 分支先计算：

```text
originalBaseColor = Sample(_BaseMap,UV0).rgb × _BaseColor.rgb
```

然后用乘法创建焦色目标：

```text
burnTargetColor = originalBaseColor × _BurnSurfaceColor.rgb
```

当前 Lab Material 的 Burn Surface Color 约为 `(0.49,0.17,0.09)`。红色保留较多，绿色和蓝色衰减更强，同时整体变暗。因为目标仍然乘了 originalBaseColor，原贴图亮暗和花纹不会被纯色完全覆盖。

再计算：

```text
burnBlend = saturate(finalBurnMask × 0.75)
burnedBaseColor = lerp(originalBaseColor,burnTargetColor,burnBlend)
```

0.75 是视觉设计参数，不是物理常数。它限制最强区域只向焦色靠近 75%，保留部分原角色颜色，避免战斗中完全失去识别度。`Lerp` 对 RGB 每个通道独立执行连续混合，因此不会突然跳色。

Emission 分支保留角色原始发光：

```text
originalEmission = Sample(_EmissionMap,UV0).rgb × _EmissionColor.rgb
```

再添加燃烧贡献：

```text
burnEmission = finalBurnMask × _BurnEmissionColor.rgb
finalEmission = originalEmission + burnEmission
```

这里使用 Add 而不是 Lerp，是因为原角色未来可能有蓝色眼睛或武器符文发光，燃烧应当作为额外能量来源叠加，而不是替换原 Emission。

`_BurnEmissionColor` 是 HDR Color。Lab Material 当前值约为 `(5.99,0.50,0)`，红色通道明显大于 1。普通显示范围无法直接表达“比白色更亮”，但 URP 的 HDR 中间颜色缓冲可以保留这些高值，随后由 Tone Mapping 和 Bloom 使用。

不能在 Final Emission 后使用 Saturate，因为：

```text
saturate(5.99,0.50,0) = (1,0.50,0)
```

高动态范围信息会被截断，既改变色彩比例，也削弱 Bloom 的亮度层级。

Bloom 不是 Shader Graph 中的火焰节点，而是 Camera 后处理：

```text
Shader 输出 HDR 亮纹
→ Camera 得到 HDR 画面
→ Bloom 提取超过 Threshold 的像素
→ 降采样与模糊
→ 叠加回 Camera 画面
```

所以 Material Preview 不一定显示场景 Global Volume 的 Bloom。必须把 Material 用于场景 Renderer、让 Main Camera 开启 Post Processing，并在 Game View 对照 Bloom 开关。Emission 负责“制造高亮源”，Bloom 负责“让高亮向屏幕邻域扩散”。

## 六、架构位置与涉及文件：谁拥有状态，谁只负责画

燃烧视觉跨越 Combat、Rendering 和 GPU，但依赖方向必须保持单向：

```text
Game.Combat
StatusController
    ↓ 发布 StatusChangedEvent

Game.Rendering
StatusMaterialController
    ↓ 写入 MaterialPropertyBlock

URP / Shader Graph
SG_CharacterStatusLit
    ↓ 计算 Fragment Surface

Camera Post Processing
Bloom
```

主要文件和资产如下：

```text
Assets/_Project/Scripts/Combat/Status/StatusController.cs
    Gameplay 权威状态、自然衰减、Wet 加速灭火、DoT、VFX 生命周期、事件发布。

Assets/_Project/Scripts/Combat/Events/StatusChangedEvent.cs
    跨模块状态快照，包含 TargetId、Kind、Intensity、IsActive。

Assets/_Project/Scripts/Rendering/StatusMaterialController.cs
    只读表现桥；过滤 TargetId、0~100 归一化、MoveTowards 平滑、MPB 写入。

Assets/_Project/Scripts/Rendering/Game.Rendering.asmdef
    Rendering 增加对 Combat 的只读依赖；Combat 不反向依赖 Rendering。

Assets/_Project/Shader/SG_CharacterStatusLit.shadergraph
    统一 URP Lit Shader，保留 Base Map、Normal、Metallic、Smoothness、AO、Emission，增加 Burning/Wet。

Assets/_Project/Art/Materials/CharacterStatus/Lab/M_StatusLab_*.mat
    Neutral/Burning/Wet/Combined 四份 A/B 对照材质，全部共享同一 Shader。

Assets/_Project/Tests/Rendering/StatusMaterialControllerTests.cs
    验证 TargetId 过滤、归一化、MPB 保留 _BaseColor、共享材质下逐 Renderer 独立和 Disable 清理。
```

Shader 与 Gameplay 的边界尤其重要。Shader 不判断 Wet 是否应该灭火，也不计算 Burning DoT；它只显示 C# 给出的最新强度。`StatusController` 已经负责 Wet 状态存在时增加 Burning 衰减速度，所以 Shader 会随着事件自然看到 Burning 下降。这样更换 Shader 不会改变战斗规则，修改状态公式也不需要重写视觉算法。

当前 C# 桥和 Lab Shader 已完成，但正式 Prefab 集成仍是后续阶段：需要把生产材质复制到 `Assets/_Project`、替换 WizardPlayer/MagicEnemy 的 Shared Materials、挂 `StatusMaterialController`，并验证多个 `SkinnedMeshRenderer` 的 Object Space 接缝。复盘时应区分“算法已实现”和“全角色生产集成已完成”，不能在面试中夸大当前状态。

## 七、真实踩坑与 Debug：这部分比“第一次就写对”更有面试价值

第一个问题是低强度不明显。根因不是 Emission 颜色太暗，而是 Intensity 同时压缩覆盖面积和最终亮度。解决不是盲目把 HDR 调到几十，而是分析完整信号链后增加 `pow(intensity,0.6)` 的非线性感知映射。这体现了 Gameplay Linear Data 与 Visual Perception 可以分层设计。

第二个问题是流动方向与纸面推导不一致。我们检查了 `Split.G` 是否为 Y、Subtract 的 A/B 是否接反、Combine.G 是否接 Vertical，确认连接后以目标模型实际 Object Space 为准，把流动从减法改为加法。这说明 Coordinate Space 是图形 Debug 的第一优先级之一。

第三个问题是 `Simple Noise` 的 Scale 重复。坐标已经乘 `_BurnNoiseScale` 时，节点内部 Scale 再设 2 会让实际频率翻倍，Material 参数失去直观意义。最终节点内部固定为 1，频率只由一个外部参数控制。这是参数职责单一化。

第四个问题是 Burning Intensity 为 0 时仍有橙红发光。正确设计中 `BurnEmissionColor` 可以常驻，但必须经过 `FinalBurnMask` 相乘。问题来自 Emission 连线绕过 Mask，而不是“后续代码还没控制颜色”。Debug 方法是把 Burn Emission Color 临时设黑、断开 BurnEmission Add 分支、检查 Mask 乘法输出，逐段隔离信号。

第五个问题是 Bloom 看不出差异。原因是最初观察 Material Inspector Preview 和 Scene View，而 Bloom 是 Main Camera 的 Post Processing。最终在场景 Renderer 和 Game View 中，用夸张参数 `Threshold=0.5、Intensity=2、HDR=5~8` 先证明链路，再恢复克制值。这是图形 Debug 中常见的“极值验证法”。

第六个问题是调试默认值污染。当前实际 Shader Graph 文件中 `_BurningIntensity` 的 Graph 默认值仍是 0.6，这是调试节点 Preview 时留下的；四份 Lab Material 覆盖了各自数值，所以暂时没有全部燃烧，但新建 Material 可能继承 0.6。正式接入前必须把 Shader Graph Blackboard 默认值恢复为：

```text
Burning Intensity = 0
Wet Intensity = 0
Poisoned Intensity = 0
Sticky Intensity = 0
```

这条经验很重要：实验时修改 Default Value 很方便，但默认值属于资产协议，不应作为临时测试旋钮长期保留。测试状态应写在 Lab Material，而不是污染 Shader 的安全默认状态。

推荐的 Burning Debug 顺序是：

```text
1. 单独把 FinalBurnMask 临时输出到 Base Color，看黑白 Mask。
2. 检查 Intensity=0 是否绝对黑，Intensity 递增时面积是否扩大。
3. 检查 Time=0/FlowSpeed=0 时图案是否静止。
4. 检查移动角色时 Noise 是否附着 Object，而不是固定 World。
5. 恢复 Base Color，检查焦黑分支是否保留贴图。
6. 单独检查 BurnEmission，确认它乘了 Mask。
7. 最后打开 Bloom，区分 Shader 问题与 Post Processing 问题。
```

这比一上来同时看颜色、发光和辉光更高效，因为每一步只验证一个变量。

## 八、性能、局限与后续升级方向

程序化 Simple Noise 不需要额外 Fire Texture，减少资源依赖和一次显式纹理采样，但 Noise 会展开成多次数学运算，属于用 ALU 换 Texture Bandwidth。不能只因为“没有贴图”就断言更快，最终要在目标 GPU 上用 GPU Profiler 比较。

Shader 每个可见 Fragment 都会计算 Noise、Smoothstep、Power 和颜色分支。我们的节点是连续数学运算，没有真正的动态 `if`，因此不会产生明显的 GPU Warp/Wave Divergence；但即使 `_BurningIntensity=0`，除非编译器能静态消除，统一 Shader 仍可能计算 Burning 分支。未来角色数量巨大时，可以比较以下方案：

```text
统一 Shader 始终计算：组合简单、无 Shader 切换、成本固定。
Shader Keyword Variant：无状态时可裁剪分支，但 Variant 数量和切换管理复杂。
分离材质/Shader：单状态成本低，但多状态组合和 Batch 管理困难。
```

第一版选择统一 Shader，是因为项目核心是多状态组合，正确性和扩展性优先。等 Frame Debugger 和 GPU 数据证明它成为瓶颈，再考虑 Keyword 或更低成本 Noise。

当前 Object Space 二维投影存在两个局限。其一，多个 Renderer 的局部空间可能不连续；其二，`x+0.37z` 仍有投影方向偏置。升级方案依次可以是：

```text
1. 给 Shader 上传 Character Root Position，使用 Root-relative World Position。
2. 使用 Triplanar Mapping，按法线权重混合 XY/XZ/YZ 三个投影。
3. 使用真正的 3D Noise 或 3D Texture，换取更高成本。
```

这些方案不是越高级越好。Root-relative Position 每帧需要额外参数；Triplanar 通常需要三组采样；3D Noise 更贵。当前要先在 WizardPlayer 和 MagicEnemy 的真实镜头距离下判断接缝是否值得解决。

MPB 方案避免 Material Instance，但可能影响 SRP Batcher。最终验证必须包括：

```text
Frame Debugger：Draw Call、Pass、SRP Batcher 原因、是否意外透明。
Profiler CPU：StatusMaterialController.Update、GC Alloc 是否 0 B。
Profiler GPU：1/5/10 个状态角色时 Shader 成本。
Game View：Bloom Off/On、角色不同距离、移动和动画。
```

## 九、模拟大厂面试 Q&A

**Q：为什么不直接用 Particle System 表现燃烧？**

A：Particle System 擅长表现脱离角色表面的火苗和烟，但无法自然改变角色 PBR 表面。我采用混合方案：外围火焰继续用 OnFire VFX，Shader 用程序化 Mask 修改 Base Color 和 Emission。这样既有轮廓火焰，也有表面焦黑和高温裂纹。

**Q：为什么选择 Object Space，而不是 UV 或 World Space？**

A：UV 在角色多个 Texture Island 之间不连续，会产生接缝和密度差异；World Space 会导致角色移动时纹理在表面游动。Object Space 不依赖 UV并且跟随物体移动，适合第一版。它对多 Renderer 角色可能有局部空间接缝，所以我把真实角色验证作为后续 Gate，必要时升级 Root-relative World Position 或 Triplanar。

**Q：BurningIntensity 如何影响效果？**

A：它不是只控制透明度。先用 `pow(saturate(I),0.6)` 提升低强度视觉可读性，再用它降低 Noise Threshold 以扩大燃烧面积，同时乘到最终 Mask 控制亮度并保证 I=0 时绝对关闭。因此强度增加会同时改变覆盖面积和能量感。

**Q：为什么用 Smoothstep，不用 Step？**

A：Step 在阈值处从 0 突变到 1，边界在屏幕采样下容易产生 Alias 和帧间闪烁。Smoothstep 在 lower/upper 区间内使用三次 Hermite 曲线连续过渡，边缘更稳定；Softness 还能作为可调参数控制过渡宽度。

**Q：为什么焦黑颜色要乘原 Base Color？**

A：直接 Lerp 到纯暗红会覆盖服装花纹和材质细节。使用 `originalBaseColor×burnSurfaceColor` 创建目标，能按通道压暗并偏红，同时保留原贴图内部相对明暗；再用 Mask Lerp，使变化只发生在燃烧区域。

**Q：Burn Emission Color 为什么一直存在于 Material？**

A：它是美术配置，定义燃烧时的颜色；是否输出由 FinalBurnMask 决定。运行时代码通常只更新 `_BurningIntensity`，不需要每帧改颜色。`BurnEmission=Mask×Color`，Mask 为 0 时即使 Color 是 HDR 橙色也没有贡献。

**Q：Emission 和 Bloom 有什么区别？**

A：Emission 是 Material Shader 输出的 HDR 高亮颜色；Bloom 是 Camera 后处理，从最终 HDR 画面提取超过 Threshold 的像素，模糊后叠加。Emission 提供源，Bloom 提供屏幕空间扩散。Material Preview 没有场景 Bloom，所以必须在 Game View 验证。

**Q：为什么使用 MPB，而不是修改 Material？**

A：多个角色可以共享同一份 Material，同时通过 MPB拥有不同状态值，避免 `renderer.material` 产生 Material Instance。写入前 GetPropertyBlock 能保留其他系统参数。不过 MPB 与 SRP Batcher 的 trade-off 需要 Frame Debugger 实测，我不会把它绝对化为性能优化。

**Q：如何保证状态视觉与 Gameplay 解耦？**

A：StatusController 拥有 DoT、衰减和 Wet 灭火规则，通过 StatusChangedEvent 发布快照；Rendering 只读订阅并写 Shader，不修改状态。Shader 只解释 0~1 强度。因此更换材质不会改变伤害，修改战斗规则也不会破坏渲染模块依赖方向。

**Q：这个方案最大的局限是什么？**

A：当前 Simple Noise 是 Object Space 的二维投影，不是真正 3D Noise，多 SkinnedMeshRenderer 之间可能有接缝，也存在方向偏置；统一 Shader 在状态为 0 时可能仍有 ALU 成本。我的策略是先通过真实角色和 Profiler量化，再决定 Root-relative、Triplanar、3D Noise 或 Keyword，而不是提前复杂化。

## 十、模拟面试者从头到尾讲解开发流程

这个功能的目标，是把状态系统中的 Burning 百分比转化成连续、动态且保留角色材质特征的视觉反馈。我没有采用简单全身染红，也没有只依赖 Particle System，而是把效果拆成表面与外围两层：外围火焰复用已有 OnFire VFX，角色表面由统一的 URP Lit Shader Graph 生成流动焦纹和 HDR Emission。

在架构上，Combat 的 StatusController 是状态权威，它维护 0~100 强度、DoT、自然衰减和状态反应，并发布带 TargetId 的 StatusChangedEvent。Rendering 中的 StatusMaterialController 订阅事件，过滤目标，把强度归一化到 0~1，再通过 MoveTowards 平滑。最终使用 MaterialPropertyBlock 写入 `_BurningIntensity`，让多个角色共享 Material 的同时拥有独立状态。Gameplay 不引用 Rendering，Shader 也不负责伤害规则，依赖保持单向。

在 Shader 中，我先保留 Base Map、Normal、Metallic、Smoothness、AO 和原 Emission，保证状态为 0 时接近原 URP Lit。燃烧 Mask 使用 Object Space Position，因为 UV 会受角色 Texture Island 接缝影响，World Space 又会产生纹理游动。我把三维位置投影为 `float2(x+0.37z, y+Time×Speed)`，乘 Noise Scale 后输入 Simple Noise，生成附着角色并向上流动的灰度场。

为了让强度表现为火势蔓延，我没有直接用 Noise 乘 Intensity，而是用 Intensity 控制阈值。开发中发现 0.5 以下同时被面积和亮度双重压制，于是在表现层加入 `pow(I,0.6)`，提升低强度可读性但保持 0 和 1 不变。随后通过 `threshold=lerp(0.95,0.35,Ivisual)` 和 `smoothstep(threshold-softness,threshold+softness,noise)` 得到柔和 Mask，最后再乘视觉强度，确保状态为 0 时没有任何残留。

同一个 Mask 同时驱动两个材质通道。Base Color 分支先把原颜色乘深暗红得到焦色目标，再按 Mask 的 75% Lerp，保留服装纹理和角色辨识度；Emission 分支把 Mask 乘 HDR 橙红色，并加到原 Emission 上，保留未来眼睛或武器符文的原生发光。Camera 的 Bloom 再对 HDR 高亮做屏幕空间扩散，因此 Emission 与 Bloom 分开验证。

实现过程中有三个关键 Debug。低强度不明显通过非线性响应曲线解决；火纹方向与模型实际 Object Space 不一致，通过检查 Split、Combine 和目标 Mesh 后反转时间符号；Burning 为 0 仍发光则通过逐段隔离 Emission 链路，发现颜色绕过 Mask。除此之外，我还把 Shader 默认强度、Material 实验参数和运行时 MPB 区分开，避免调试值污染新材质默认状态。

最后我使用 Neutral、Burning、Wet、Combined 四份 Lab Material 做同场 A/B，对强度 0、0.25、0.5、1，移动、旋转、Bloom 开关和无状态回归进行验证。下一步是把生产材质接到 WizardPlayer 和 MagicEnemy，重点检查多个 SkinnedMeshRenderer 的 Object Space 接缝，并用 Frame Debugger、CPU/GPU Profiler 验证 MPB、SRP Batcher 和统一 Shader 的实际成本。
