# P0 可持续开发基线设计

创建时间：2026-07-10 17:18

对应路线图：[RPG 后续开发计划](../../../Assets/_Project/Docs/2026-07-10_1605_RPG后续开发计划.md)

适用项目：Unity 6.3 / URP / Noita-like 3D RPG

目标读者：第一次开发游戏诊断工具、第一次系统使用 Unity Profiler 的开发者

---

## 0. 一句话说明 P0 是什么

P0 不增加新法术，也不改变战斗规则。它为现有法术系统安装三种“观察仪器”：

```text
Console Trace：观察解释器为什么得到这个结果
Scene Gizmos：观察投射物在三维空间中怎样运动
Performance Lab：观察大量法术运行时消耗了多少 CPU、GPU 和内存
```

过去调试法术时，我们通常只能看到最终现象：

```text
火球没出来
追踪没生效
轨道方向不对
投射物一多就卡
```

但“最终现象”不能直接告诉我们错误发生在哪一层。P0 的目标是把黑盒拆成可观察的链路：

```text
WandLoadout
-> CastEvaluator 怎样读取法术
-> EmitCommand 最终携带了什么数据
-> SpellCaster 实际生成了什么
-> ProjectileBase 当前速度、目标、轨道和碰撞是什么
-> 大量实体同时存在时，性能瓶颈在哪
```

---

## 1. 先纠正一个容易误解的概念：“测试 mode”不是游戏模式

### 1.1 它不是玩家可以选择的玩法 Mode

这里所说的测试 mode，不是主菜单里的：

```text
Story Mode
Challenge Mode
Test Mode
```

也不是一套脱离真实代码的假战斗系统。

它是一组只服务开发者的 Diagnostics（诊断能力）。正式 Gameplay 仍然走原来的真实链路：

```text
玩家施法
-> CastEvaluator
-> EmitCommand
-> SpellCaster
-> ProjectileBase
-> Damage / Status
```

测试工具只站在链路旁边观察，不取代任何一层。

### 1.2 三种常见测试手段的区别

新手容易把 Unit Test、Debug Tool 和 Performance Test 混在一起。它们回答的问题不同。

| 手段 | 回答的问题 | 本项目例子 |
|---|---|---|
| EditMode Unit Test | 一条纯规则算得对不对 | Multicast 后 draw budget 是否正确 |
| Console Trace | 这一次真实施法经过了哪些步骤 | 为什么触发火球只输出一个外层 Emit |
| Scene Gizmos | 三维空间中的隐藏数据是什么 | Homing 搜索半径、Orbit 圆心、反射法线 |
| Unity Profiler | 时间和内存花在哪里 | 200 个投射物时 Physics 还是 Rendering 更贵 |
| Frame Debugger | 一帧是怎样被绘制出来的 | 后续 P1 检查状态 Shader 和 Draw Call |

P0 重点建设后三种中的 Console Trace、Scene Gizmos 和 Unity Profiler 基线。它们相互补充，不能互相代替。

### 1.3 为什么不能只看 Console

Console 适合显示离散事件，例如一次施法读取了哪些法术。它不适合每帧打印 200 个投射物的速度。

如果在 `FixedUpdate` 中不断输出日志，会产生：

- 字符串格式化成本。
- Console I/O 成本。
- 大量 GC Alloc。
- Editor 卡顿。
- Profiler 数据被诊断工具本身污染。

所以本设计明确划分：

```text
离散求值过程 -> Console Trace
连续空间状态 -> Scene Gizmos
性能数据     -> Unity Profiler
```

## 2. 当前系统中 P0 要观察的真实链路

### 2.1 求值层：Game.Skills

当前 `CastEvaluator` 是法术编程系统的解释器。它读取：

- `SpellDefinition` 序列。
- `baseDraws` 抽取预算。
- 可用 mana。
- `incomingMods` 继承修正快照。

它输出复用的：

```text
List<EmitCommand>
```

同时返回 `CastSummary`：

```text
ManaSpent
Fizzled
```

P0 不改变这些语义，只让我们看见求值过程中的中间状态。

### 2.2 运行时桥接层：Game.Character

当前 `SpellCaster` 负责：

- 调用 `CastEvaluator`。
- 检查并扣除真实 mana。
- `Instantiate` projectile prefab。
- 调用 `ProjectileBase.Init`。
- 配置 Bounce、Gravity、Homing、Orbit。
- 在命中或定时事件中递归执行 payload。

因此它最适合决定：

- 当前是否开启 Trace。
- Trace 用 Summary 还是 Detailed。
- 当前是外层施法还是第几层 payload。
- 怎样把结构化 Trace 格式化到 Console。

### 2.3 投射物层：Game.Combat

当前 `ProjectileBase` 已经拥有：

- `Rigidbody` 速度。
- Gravity 开关。
- Homing 的半径、计时器和目标。
- Orbit 圆心、基向量、半径和角度。
- Bounce 的碰撞法线和反射计算。
- `s_active` 活跃投射物注册表。

这些数据已经存在，只是没有面向开发者的只读观察出口。

P0 不重新计算第二份运动数据，而是读取真实运行时数据进行可视化。

## 3. 需求与成功标准

### 3.1 功能需求

P0 必须交付：

1. 可选的法术求值 Trace。
2. Summary 和 Detailed 两种 Trace 详细度。
3. 能区分外层施法与 payload 层级。
4. 能显示主要 `EmitCommand` 最终值。
5. 能显示投射物速度、Gravity、Homing、Orbit、碰撞和反射数据。
6. 能显示全部投射物或只显示选中投射物。
7. 暴露活跃投射物数量。
8. 新建独立 `SpellPerformanceLab` 场景。
9. 压力测试同时支持标准阶梯和自定义模式。
10. 在关键链路加入可识别的 `ProfilerMarker`。

### 3.2 非功能需求

- 不改变法术求值结果。
- 不改变 mana 扣除规则。
- 不改变投射物运动和碰撞结果。
- Trace 关闭时不产生 Trace step 和字符串。
- 不在投射物热路径使用 LINQ、closure、boxing 或每帧 `new`。
- 不让 `Game.Skills` 直接依赖 Console 或场景对象。
- 不让 `Game.Combat` 依赖 `Game.Character`。
- 只使用 `GameLog`，不直接调用 `Debug.Log`。
- 不手写 `.meta` 和 `.unity` 文件。

### 3.3 使用体验成功标准

当一个法术行为不正确时，开发者应能按顺序回答：

```text
解释器有没有读到这张法术？
Modify 有没有修改当前状态？
EmitCommand 最终值是否正确？
SpellCaster 是否生成了实体？
ProjectileBase 当前在执行哪种运动？
问题是逻辑错误、空间计算错误还是性能问题？
```

当性能下降时，开发者应能在同一个专用场景中重复相同压力档位，而不是每次靠手速发射一个大概数量。

## 4. 总体架构

```text
┌──────────────────── Game.Skills ────────────────────┐
│ CastEvaluator                                        │
│   ├─ Evaluate：正常求值                              │
│   └─ EvaluateWithTrace：求值 + 结构化记录            │
│                │                                     │
│                └─ CastTraceCollector                 │
└──────────────────────────┬───────────────────────────┘
                           │ EmitCommand + Trace Steps
                           v
┌─────────────────── Game.Character ───────────────────┐
│ SpellCaster                                           │
│   ├─ 实例化真实投射物                                 │
│   ├─ 标记 payload Depth                               │
│   └─ 用 GameLog 格式化 Trace                         │
│                                                       │
│ SpellPerformanceLabController                         │
│   └─ 重复调用真实 SpellCaster                        │
└──────────────────────────┬───────────────────────────┘
                           │ ProjectileBase.Init
                           v
┌──────────────────── Game.Combat ─────────────────────┐
│ ProjectileBase                                        │
│   ├─ ActiveCount / Debug Snapshot                     │
│   └─ 真实 Rigidbody / Homing / Orbit / Bounce         │
│                                                       │
│ ProjectileDebugGizmoDrawer                            │
│   └─ 只读 Snapshot 并在 Scene View 绘制              │
└───────────────────────────────────────────────────────┘
```

### 4.1 为什么不用 EventBus 传每个投射物的每帧数据

`EventBus` 适合跨模块的离散事件，例如伤害、死亡、状态变化。速度和轨道位置属于连续数据，如果每个投射物每帧发布事件，会产生大量调用和潜在开销。

Gizmo Drawer 与 `ProjectileBase` 同属 `Game.Combat`，可以直接读取同模块的只读 Debug Snapshot，不需要跨模块事件。

### 4.2 为什么不让 CastEvaluator 直接打印日志

如果 `CastEvaluator` 直接调用 `GameLog`：

- 纯解释器开始承担表现职责。
- 单元测试必须处理 Console 输出。
- 以后想把 Trace 显示到文件或 EditorWindow 时需要改解释器。
- 求值语义和字符串格式纠缠在一起。

正确拆分是：

```text
CastEvaluator：记录结构化事实
SpellCaster：决定怎样呈现这些事实
```

## 5. 子系统一：法术求值 Trace

### 5.1 玩家看不到，但开发者要看到什么

以法杖为例：

```text
[三重射击 | 重力修正 | 追踪修正 | 触发火球 | 普通火球]
```

Detailed Trace 应能表达：

```text
[Cast #18][Depth 0] Start: BaseDraws=1, AvailableMana=100
[0] 三重射击: Multicast, DrawBudget 1 -> 3
[1] 重力修正: Modify, UseGravity false -> true
[2] 追踪修正: Modify, Motion None -> Homing
[3] 触发火球: Emit #0, Damage=10, Speed=20, Motion=Homing, Gravity=true
[3] Capture Payload: StartIndex=4, Count=1, Trigger=OnImpact
[Cast #18][Depth 0] Complete: Emits=1, ManaSpent=..., Fizzled=false

命中后：
[Cast #18][Depth 1] Start Payload at hit point
[0] 普通火球: Emit #0, inherited Motion=Homing, Gravity=true
[Cast #18][Depth 1] Complete
```

这个输出不是正式格式的强制文本，而是说明必须具备的信息。

### 5.2 Trace 详细度

`SpellCaster` 使用枚举控制：

```csharp
public enum CastTraceLevel : byte
{
    Off = 0,
    Summary = 1,
    Detailed = 2
}
```

语义：

- `Off`：走原有 `Evaluate`，不收集 step。
- `Summary`：只输出施法编号、Depth、mana、Emit 数、fizzle 和 payload 摘要。
- `Detailed`：使用 `EvaluateWithTrace`，输出每条指令的求值变化。

为什么不使用四五个 bool：

- 多个 bool 会形成无意义组合，例如关闭总体 Trace 却开启 Modifier Detail。
- 枚举更容易在 Inspector 理解。
- 后续若增加 `ErrorsOnly`，可以继续扩展枚举。

### 5.3 CastTraceStepKind

建议定义：

```csharp
public enum CastTraceStepKind : byte
{
    CastStarted,
    NullSpellSkipped,
    ModifyApplied,
    MulticastApplied,
    EmitProduced,
    PayloadCaptured,
    ManaFizzle,
    CastCompleted
}
```

它回答“这一步是什么语义”，避免通过字符串猜测类型。

### 5.4 CastTraceStep

使用 `readonly struct` 保存一次步骤快照。建议字段包含：

- `Kind`。
- `SpellIndex`。
- `SpellDefinition Spell` 引用。
- `DrawBudgetBefore / After`。
- `ManaBefore / After`。
- `CastModifierState ModifiersBefore / After`。
- `EmitIndex`。
- `PayloadStartIndex / PayloadCount`。
- `PayloadTriggerMode`。

为什么保存 `SpellDefinition` 引用，而不是求值时复制 `DisplayName` 字符串：

- 不需要每一步创建新字符串。
- Formatter 输出时再读取名称。
- Trace step 保留和原始数据的关联。

`CastTraceStep` 只在离散施法时写入，不在每帧物理热路径中运行。

### 5.5 CastTraceCollector

职责：

- 持有预分配的 `List<CastTraceStep>`。
- 每次求值前 `Clear()`，复用容量。
- 提供只读 Count 和索引访问。
- 不负责 Console 格式化。

默认容量应覆盖当前一根法杖的常见指令数，例如 32 或 64 steps。即使极端法杖导致 List 扩容，扩容也发生在离散施法，而非每帧；但 P0 应通过合理预分配避免常见情况扩容。

### 5.6 Evaluate 与 EvaluateWithTrace 如何保证不分叉

禁止复制两份求值循环：

```text
Evaluate          -> 一套逻辑
EvaluateWithTrace -> 另一套复制逻辑
```

否则以后新增法术语义时很容易只改其中一份。

推荐结构：

```csharp
Evaluate(...)
    -> EvaluateCore(..., trace: null)

EvaluateWithTrace(..., collector)
    -> EvaluateCore(..., trace: collector)
```

`EvaluateCore` 是唯一求值实现。只有 Trace 不为空时才写步骤。

为了证明开启 Trace 不改变结果，必须写等价性测试：

```text
同一个 WandLoadout
-> Evaluate 输出 A
-> EvaluateWithTrace 输出 B
-> A 与 B 的每个 EmitCommand 字段相同
```

### 5.7 递归 payload 的编号

Trace 需要区分两个概念：

- `CastId`：玩家一次根施法以及它产生的所有 payload 共用一个编号。
- `Depth`：当前处于第几层 runtime payload。

例如：

```text
玩家按一次：CastId=18, Depth=0
触发火球命中：CastId=18, Depth=1
payload 中又有触发：CastId=18, Depth=2
```

这不会改变 `CastEvaluator` 的 payload 规则，只是 `SpellCaster.RunCast` 在递归时传递诊断上下文。

### 5.8 Trace 的性能原则

- Trace 默认 `Off`。
- `Off` 时不格式化字符串。
- `Summary` 不记录逐指令 step。
- `Detailed` 只用于复现逻辑问题。
- 压力测试前必须关闭 Trace。
- 不在 `Update` / `FixedUpdate` 打印 Trace。
- Release 构建依靠 `GameLog` 的 Conditional 属性移除日志调用；开发诊断分支也应尽量用编译条件隔离。

## 6. 子系统二：Projectile Scene Gizmos

### 6.1 什么是 Gizmos

`Gizmos` 是 Unity 为开发者提供的 Scene View 调试绘制 API。它画出的线、球、圆和箭头不是游戏世界中的真实 Mesh，也不会成为玩家画面的一部分。

用途是把不可见数学量变成可见图形，例如：

```text
Vector3 velocity -> 一条箭头
HomingRadius     -> 一个线框球
collision normal -> 从碰撞点向外的一条线
Orbit basis      -> 三根局部坐标轴
```

### 6.2 为什么不用 LineRenderer 做 Debug

`LineRenderer` 是正式运行时组件：

- 会创建真正的 Renderer。
- 进入 Game View。
- 影响 Draw Call 和性能数据。
- 需要管理生命周期。

Gizmos 只在 Editor Scene View 工作，更适合诊断。

### 6.3 ProjectileDebugSnapshot

建议使用只读快照把真实投射物数据暴露给 Debug Drawer：

```text
Position
Velocity
UseGravity
MotionMode
HomingEnabled
HomingRadius
HomingTargetPosition
OrbitEnabled
OrbitCenter
OrbitForward / OrbitRight / OrbitUp
OrbitRadius
LastCollisionPoint
LastCollisionNormal
LastReflectedDirection
LastCollisionTime
```

Snapshot 的意义不是复制一套模拟，而是在某一刻读取真实状态。

### 6.4 活跃投射物注册表

`ProjectileBase` 已有：

```csharp
private static readonly List<ProjectileBase> s_active;
```

它目前用于同阵营投射物之间的 `Physics.IgnoreCollision`。

P0 可以在不改变所有权的前提下提供：

- `ActiveCount`：压力测试读取数量。
- 同 assembly 的只读活动列表访问：Gizmo Drawer 遍历。

不要把 `List` 暴露为可修改的 public API，否则外部工具可能误删注册项，破坏碰撞逻辑。

### 6.5 绘制内容与颜色约定

第一版约定：

| 内容 | 建议颜色 | 图形 |
|---|---|---|
| Velocity | 白色 | 起点到速度方向的线/箭头 |
| Gravity | 黄色 | 向下箭头 |
| Homing Radius | 青色 | Wire Sphere |
| Homing Target | 青绿色 | 投射物到目标的连线 |
| Orbit Center Path | 蓝色 | 圆心和前进方向 |
| Orbit Plane | 橙色 | Right/Up 轴与圆环 |
| Collision Normal | 红色 | 碰撞点向法线方向 |
| Reflected Direction | 绿色 | 碰撞点向反射方向 |

这些颜色只用于开发约定，不属于正式美术规范。

### 6.6 全部显示与 Only Selected

`ProjectileDebugGizmoDrawer` 提供：

- `DrawVelocity`。
- `DrawGravity`。
- `DrawHoming`。
- `DrawOrbit`。
- `DrawCollision`。
- `OnlyDrawSelected`。
- `VectorScale`。
- `CollisionHistorySeconds`。

少量投射物时可以看全部。大量投射物时切换 `OnlyDrawSelected`，否则几百条 Gizmo 线会遮挡场景并拖慢 Editor。

### 6.7 最近碰撞数据为什么需要过期

Bounce 后投射物继续存在，因此可以显示最近一次碰撞法线。但如果永远保留，几秒后看到的线已经与当前运动无关。

所以只在：

```text
当前 Editor 时间 - LastCollisionTime <= CollisionHistorySeconds
```

时显示。默认可取 0.5 秒。

### 6.8 Gizmos 的性能边界

- Gizmos 只用于少量对象的数学观察。
- 压力测试时关闭总 Gizmos 或使用 Only Selected。
- 不在 Snapshot 捕获过程中创建数组或 List。
- 不为画圆每帧创建点数组；直接循环计算并绘线。
- 正式 Build 不应依赖 Gizmo 逻辑。

## 7. 子系统三：SpellPerformanceLab

### 7.1 为什么必须有独立场景

如果直接在 `SampleScene` 测试：

- Enemy AI、角色、UI、环境和 VFX 都会混入数据。
- 场景每次被修改后，性能基线也发生变化。
- 投射物可能提前撞墙或击中敌人，活跃数量无法稳定。

独立 Lab 的目的不是模拟最终游戏，而是控制变量。

```text
同一个场景
同一个 WandLoadout
同一个目标数量
同一个保持时间
不同代码版本
```

这样前后数据才有比较意义。

### 7.2 场景最小组成

建议：

```text
SpellPerformanceLab
├─ Main Camera
├─ Directional Light
├─ Ground
├─ Long Range Wall / Catcher
├─ WizardTestCaster
│  ├─ SpellCaster
│  ├─ ManaComponent（高上限/高恢复，仅 Lab 配置）
│  └─ Collider / HealthComponent（按现有施法依赖）
├─ SpawnPoint
├─ AimTarget
├─ PerformanceLabController
└─ ProjectileDebugGizmos（默认关闭）
```

场景由开发者在 Unity Editor 新建和保存，不由 Codex 手写 YAML。

### 7.3 Scenario 是什么

一个 Scenario 表示“用哪套真实施法器，朝哪里进行压力测试”：

```text
ScenarioName
Enabled
SpellCaster
SpawnPoint
AimTarget
```

推荐在 Scene 中准备多个已配置不同 `WandLoadout` 的 SpellCaster，例如：

- SingleFireball。
- TripleFireball。
- TriggerPayload。
- GravityHoming。
- OrbitProjectile。

为什么不让 Lab Controller 临时改 `SpellCaster._wand`：

- `_wand` 是正式组件的私有配置。
- Debug 工具不应通过反射或临时 setter 破坏封装。
- 多个配置好的 SpellCaster 更直观，也更容易在 Inspector 检查。

### 7.4 标准阶梯模式

标准目标：

```text
1 -> 10 -> 50 -> 100 -> 200 active projectiles
```

每一档的状态机：

```text
Preparing
-> Filling：按速率施法，直到 ActiveCount 达标
-> Holding：维持固定时间；数量下降时按上限补充
-> Completing：记录峰值与耗时
-> Next Tier
```

这里测的是活跃投射物数量，而不是简单“点击 200 次”。原因是 Multicast 一次可能产生多个投射物，投射物也可能因为 Lifetime 或碰撞提前销毁。

### 7.5 为什么要限制每帧施法次数

如果在一帧内瞬间生成 200 个对象，测到的主要是 Spawn Spike；如果分批生成并保持 200 个对象，测到的主要是稳定运行成本。

两者都重要，但不能混成一个数字。

标准模式建议提供：

- `MaxCastsPerFrame`：填充阶段单帧最多施法次数。
- `HoldSecondsPerTier`：每档保持时间。
- `FillTimeoutSeconds`：到不了目标时退出。

未来可以分别记录：

```text
生成峰值成本
稳定存活成本
销毁峰值成本
```

P0 第一版重点建立稳定存活基线，同时保留观察 Spawn Spike 的能力。

### 7.6 自定义模式

用于复现特殊问题：

- 指定 Scenario。
- 指定 TargetActiveCount。
- 指定 MaxCastsPerFrame。
- 指定 HoldSeconds。
- 指定是否循环维持。

例如：

```text
只测试 Orbit，目标 80
只测试 TriggerPayload，目标 30
测试某个新法术，目标 120
```

### 7.7 为什么测试场景仍然走真实 mana

不在 `SpellCaster` 中增加 `IgnoreManaForDebug`。压力测试角色使用独立的高 mana 配置。

原因：

- 测试仍走真实施法路径。
- 不给正式组件留下作弊分支。
- mana 检查本身也是施法成本的一部分。
- Lab 的特殊数值留在 Lab 资产和场景中。

### 7.8 到不了目标数量时怎么办

常见原因：

- Wand 没有 Emit。
- Projectile Lifetime 太短。
- 投射物过早撞墙。
- mana 不足。
- 法术触发条件未发生。

Controller 不能无限等待。达到 `FillTimeoutSeconds` 后：

- 停止当前档。
- 使用 `GameLog.Warn` 输出目标值、实际峰值和耗时。
- 不自动宣称性能不合格，因为可能是场景配置问题。

### 7.9 ProfilerMarker

`ProfilerMarker` 允许在 Unity Profiler CPU Timeline/Hierarchy 中看到自定义代码块。

第一版建议：

```text
Spell.Evaluate
Spell.RuntimeSpawn
Projectile.Motion
PerformanceLab.Fill
```

典型用法是静态复用 Marker：

```csharp
private static readonly ProfilerMarker s_marker = new ProfilerMarker("Spell.Evaluate");

using (s_marker.Auto())
{
    // 被测逻辑
}
```

不要每次调用时 `new ProfilerMarker`。

### 7.10 Profiler 初学者需要理解的指标

| 指标 | 含义 | P0 关注点 |
|---|---|---|
| Main Thread | 游戏主线程时间 | 求值、脚本 Update、Instantiate、Physics 调用 |
| Render Thread | 向 GPU 提交渲染工作的线程 | VFX 和大量 Renderer 的提交成本 |
| CPU Frame Time | CPU 完成一帧所需时间 | 是否超过目标帧预算 |
| GC Alloc | 本帧托管内存分配 | 热路径目标 0 B |
| GC.Collect | 垃圾回收停顿 | 是否出现明显尖峰 |
| Batches | 一帧提交的绘制批次 | 投射物/VFX 数量增加后的趋势 |
| SetPass Calls | 切换 Shader Pass/材质状态的次数 | 材质和 Shader 组织是否破坏批处理 |
| Physics.FixedUpdate | 物理步进成本 | Rigidbody 投射物数量增加后的趋势 |

P0 不预设“200 个投射物必须 60 FPS”。先记录基线，再根据目标平台和实际玩法确定预算。

## 8. 三种工具不能同时全开测性能

这是 P0 最重要的测量原则之一。

### 8.1 逻辑 Debug 配置

```text
Trace = Detailed
Gizmos = 按需
Profiler = 可开，但数据只作定位，不作正式基线
Projectile Count = 少量
```

### 8.2 空间 Debug 配置

```text
Trace = Off
Gizmos = On / Only Selected
Profiler = 可开
Projectile Count = 少量
```

### 8.3 正式性能基线配置

```text
Trace = Off
Gizmos = Off
Console = Clear，避免日志刷屏
Deep Profile = Off
Development Build / Editor 条件保持一致
Projectile Count = 标准阶梯
```

为什么关闭 Deep Profile：它会给大量方法注入额外采样开销，适合深入定位但不适合记录原始基线。

## 9. 错误处理与防失控规则

### 9.1 Trace 错误

- Collector 为空：`EvaluateWithTrace` 明确抛出 `ArgumentNullException`，因为这是开发 API 使用错误，不能静默回退后让调用方误以为已经记录 Trace。
- Null Spell：记录 `NullSpellSkipped`，保持现有跳过语义。
- mana 不足：记录在哪个 index fizzle，以及所需和剩余 mana。
- 空 payload：不假装存在 runtime trigger，保持当前行为。

### 9.2 Gizmos 错误

- 活跃列表出现 Unity 已销毁对象：跳过，不绘制。
- Rigidbody 缺失：Velocity 为零并显示警告仅一次，不能每帧刷日志。
- Homing 无目标：只画搜索范围，不画目标连线。
- Orbit 未初始化：不画轨道平面。

### 9.3 Performance Lab 错误

- Scenario 引用缺失：拒绝开始并指出字段。
- 场景没有产出：超时退出。
- 目标数量下降：Holding 阶段在 `MaxCastsPerFrame` 限制内补充。
- 达到 200 仍正常：结束，不无限递增。
- 用户停止 Play Mode：不保存运行时状态到正式资产。
- Trace 未关闭：开始前警告性能结果会失真。

## 12. 分阶段实施与 Editor Gate

### 阶段一：Trace

代码完成后，用户先验证：

- Console 输出可读。
- Summary 不刷过多细节。
- Detailed 能解释 Modifier/Multicast/Trigger。
- Trace Off 时没有输出。

通过后再做 Gizmos。

### 阶段二：Gizmos

用户验证：

- 速度、Gravity、Homing、Orbit 线条方向正确。
- Bounce 法线和反射方向正确。
- Only Selected 能控制复杂度。
- 关闭总 Gizmos 后无 Scene View 额外绘制。

通过后再做 Performance Lab。

### 阶段三：Performance Lab

用户创建场景并验证：

- 标准阶梯自动推进。
- 自定义模式可运行。
- 达不到目标会超时，不死循环。
- Profiler 中能找到自定义 Marker。
- Trace/Gizmos 关闭后记录第一版基线。

## 14. 方案比较与最终选择

### 方案 A：Console + Gizmos + Profiler Lab（采用）

优点：

- 使用 Unity 原生工具。
- 范围明确。
- 易于学习真实 Debug 工作流。
- 不增加正式 UI。
- 能覆盖逻辑、空间和性能三个维度。

缺点：

- 数据分散在 Console、Scene View、Profiler 三处。
- 需要开发者理解每个工具回答的问题。

### 方案 B：增加 Game View Debug Overlay（不采用）

优点：运行游戏时能直接看到计数。

缺点：需要新增 UI、事件和刷新逻辑，Overlay 自身也会影响测量。P0 暂不需要。

### 方案 C：完整 EditorWindow Dashboard（不采用）

优点：工具集中、可扩展。

缺点：会把 P0 变成 Editor 工具项目，需要序列化、列表筛选和窗口生命周期等额外工作。当前收益不足。

### 压力测试执行方式

最终采用标准阶梯 + 自定义模式并存：

- 标准阶梯用于版本间对比。
- 自定义模式用于复现特殊法术组合。

## 16. 学完 P0 后应该真正掌握什么

完成 P0 的价值不只是多了几个 Debug 脚本。你应该建立以下工程思维：

1. **Observability**：复杂系统必须能暴露中间状态，不能只看最终现象。
2. **Separation of Concerns**：计算事实和显示事实是两种职责。
3. **Controlled Variables**：性能比较必须在受控场景和相同输入下进行。
4. **Instrumentation Overhead**：测量工具本身会改变被测对象。
5. **CPU/GPU 分工**：卡顿不等于“代码慢”，也可能是 Physics、Rendering 或 GC。
6. **Regression Protection**：诊断入口不能改变正式求值结果。
7. **Budget Thinking**：不要只问“能不能跑”，要问“在多少实体下、花多少毫秒”。

这些能力会直接服务后续阶段：

- P1 Shader 状态可视化需要 Frame Debugger 和 GPU 基线。
- P2 元素反应需要结构化 Trace 和频率统计。
- P3 运动管线需要 Gizmos 解释空间数学。
- P6 元素场需要严格 CPU/GPU 预算。

P0 因此不是偏离游戏开发的工具工作，而是在为后续复杂玩法建立可持续的工程地基。
