> 创建时间：2026-07-02

> 前置：Phase A/B/C 法术求值、运行时施法、拖拽 UI；Phase D 命中触发类法术已完成并经 Play 验证  
> 目标读者：正在学习战斗系统设计与法术编程系统架构的开发者

## 0. 本阶段要做什么

本阶段要新增“定时类法术”。

它和 Phase D 的“触发类法术”共享同一套核心思想：一个投射物可以携带它后面的法术序列，也就是 payload。区别在于 payload 的释放条件不同。

```text
触发类法术：投射物命中敌人或环境时，释放 payload。
定时类法术：投射物存活满指定时间后，释放 payload，并销毁自己。
```

示例：

```text
[定时火球] [普通火球]
```

运行效果：

1. 玩家发射一颗定时火球。
2. 如果这颗火球在设定时间前命中敌人或墙体，它按普通投射物命中逻辑结算并销毁，不释放后续普通火球。
3. 如果这颗火球存活满设定时间，它在当前位置消失，并从当前位置沿当前飞行方向释放后续普通火球。

本阶段的核心语义已经确认：

> 定时触发必须以“投射物仍然存在”为前提。提前命中、提前销毁、场景卸载导致销毁，都不释放定时 payload。

---

## 1. 设计原则

### 1.1 定时类法术不是新的法术大类

定时火球仍然是一个 Emit 法术。它有投射物 prefab、伤害、速度、伤害类型、音效、图标等 Emit 数据。

它和普通火球的区别不是“它是不是发射类法术”，而是“它携带的 payload 在什么时候释放”。

所以本阶段不新增 `SpellKind.TimedTrigger`。我们会把 Phase D 的 `bool IsTrigger` 升级为更明确的枚举：

```text
PayloadTriggerMode.None       普通投射物，不携带 payload
PayloadTriggerMode.OnImpact   命中触发 payload
PayloadTriggerMode.AfterDelay 定时触发 payload
```

### 1.2 payload 仍然是严格后缀

Phase D 的安全不变量保持不变：

```text
payload = 当前触发法术之后的后缀
```

因此：

```text
[定时火球] [定时火球] [普通火球]
```

第一颗定时火球携带：

```text
[定时火球] [普通火球]
```

第二颗定时火球携带：

```text
[普通火球]
```

普通火球不再携带 payload，链条结束。

这保证了当前阶段不需要递归深度护栏。递归深度天然受法杖槽位长度限制。

### 1.3 Combat 层仍然不认识 Skills

`ProjectileBase` 位于 `Game.Combat`。它只能提供通用投射物生命周期事件，不能知道“法术”“payload”“SpellCaster”这些上层概念。

因此本阶段会给 `ProjectileBase` 增加一个通用定时事件，但不会把 payload 数据塞进 Combat 层。

上层绑定关系仍由 `SpellCaster` 负责：

```text
ProjectileBase 提供：命中事件、定时事件
SpellCaster 决定：这些事件是否用于释放 payload
```

## 2. 方案决策

### 2.1 候选方案

方案 A：把 `IsTrigger` 升级为 `PayloadTriggerMode` 枚举。

```csharp
public PayloadTriggerMode PayloadTrigger = PayloadTriggerMode.None;
public float PayloadDelaySeconds = 1f;
```

优点：

- 普通火球、命中触发火球、定时火球都还是 Emit 法术。
- 抽象更准确：它们的差异是 payload 的触发条件。
- 后续可继续扩展 `OnDeath`、`OnBounce`、`OnExpire` 等触发条件。
- 避免多个 bool 组合出非法状态。

缺点：

- 需要迁移已有触发火球资产：从 `IsTrigger=true` 改为 `PayloadTrigger=OnImpact`。

方案 B：保留 `IsTrigger`，额外增加 `IsTimedTrigger`。

优点：

- 代码改动最小。

缺点：

- 会出现非法组合：同时勾选命中触发和定时触发。
- 后续新增触发条件时字段会继续膨胀。
- 对长期演进不友好。

方案 C：新增 `SpellKind.TimedTrigger`。

优点：

- 表面概念清晰。

缺点：

- 定时火球仍然需要 Emit 的 prefab、伤害、速度等字段，会导致求值器分支重复。
- 它会把“投射物的 payload 触发条件”错误提升成“法术大类”。

### 2.2 最终选择

采用方案 A。

本阶段把系统从：

```text
Emit 是否是命中触发：bool IsTrigger
```

升级为：

```text
Emit 是否携带 payload，以及 payload 由什么条件触发：PayloadTriggerMode
```

这是一次小范围架构升级。它服务于当前“定时类法术”，也为后续更多触发条件留下干净入口。

## 3. 数据模型设计

### 3.1 新增枚举：PayloadTriggerMode

新增文件：

```text
Assets/_Project/Scripts/Skills/PayloadTriggerMode.cs
```

语义：

```csharp
namespace Game.Skills
{
    public enum PayloadTriggerMode : byte
    {
        None = 0,
        OnImpact = 1,
        AfterDelay = 2
    }
}
```

解释：

- `None`：普通 Emit。不会捕获 payload。
- `OnImpact`：命中触发。沿用 Phase D 已实现的触发类火球语义。
- `AfterDelay`：定时触发。投射物存活满 `PayloadDelaySeconds` 后释放 payload。

### 3.2 修改 SpellDefinition

修改文件：

```text
Assets/_Project/Scripts/Skills/SpellDefinition.cs
```

把原本 Emit 区域的：

```csharp
public bool IsTrigger = false;
```

升级为：

```csharp
public PayloadTriggerMode PayloadTrigger = PayloadTriggerMode.None;
public float PayloadDelaySeconds = 1f;
```

数据含义：

```text
普通火球：
PayloadTrigger = None

命中触发火球：
PayloadTrigger = OnImpact

定时火球：
PayloadTrigger = AfterDelay
PayloadDelaySeconds = 1.0f
```

### 3.3 资产迁移规则

已有资产需要在 Unity Inspector 手动检查：

| 资产类型 | 旧配置 | 新配置 |
|---|---|---|
| 普通火球 | `IsTrigger=false` | `PayloadTrigger=None` |
| 命中触发火球 | `IsTrigger=true` | `PayloadTrigger=OnImpact` |
| 新定时火球 | 无 | `PayloadTrigger=AfterDelay`，配置 `PayloadDelaySeconds` |

本阶段不要求写 Editor 迁移脚本。资产数量很少，手动配置更简单，也更适合当前学习流程。

## 4. 求值器设计

### 4.1 现有 Phase D 规则

Phase D 中，`CastEvaluator` 遇到 `IsTrigger=true` 的 Emit 时：

1. 产出这个触发投射物的 `EmitCommand`。
2. 捕获它之后的后缀作为 payload。
3. 保存当前修正快照 `PayloadMods`。
4. 结束当前层求值。

### 4.2 Phase E 升级规则

Phase E 后，求值器不再判断 `IsTrigger`，而是判断：

```text
spell.PayloadTrigger != PayloadTriggerMode.None
```

规则：

```text
读到普通 Emit：
  产出普通 EmitCommand
  不捕获 payload
  当前层继续往后读，直到预算用完或法力不足

读到 PayloadTrigger != None 的 Emit：
  产出携带 payload 的 EmitCommand
  payload = 该法术之后的后缀
  payloadMods = 当前修正快照
  payloadTrigger = OnImpact 或 AfterDelay
  payloadDelaySeconds = 该 SpellDefinition 的配置值
  结束当前层求值
```

### 4.3 修改 EmitCommand

修改文件：

```text
Assets/_Project/Scripts/Skills/EmitCommand.cs
```

新增字段：

```csharp
public readonly PayloadTriggerMode PayloadTrigger;
public readonly float PayloadDelaySeconds;
```

`HasPayload` 仍然表示 payload 列表是否非空：

```csharp
public bool HasPayload => Payload != null && Payload.Count > 0;
```

注意：`PayloadTrigger != None` 不等于一定会有 payload。

例如：

```text
[定时火球]
```

定时火球本身仍然可以是 `PayloadTrigger=AfterDelay`，但因为它后面没有法术，所以 `HasPayload=false`。运行时不需要绑定定时 payload 事件。

## 5. 投射物运行时设计

### 5.1 新增定时事件

修改文件：

```text
Assets/_Project/Scripts/Combat/Projectiles/ProjectileBase.cs
```

新增事件：

```csharp
public event System.Action<Vector3, Vector3> TimedTriggerElapsed;
```

事件参数：

```text
Vector3 position：定时时间到达时投射物当前位置
Vector3 direction：当前飞行方向；优先使用 Rigidbody.linearVelocity.normalized，退化时使用 transform.forward
```

命名说明：

`ProjectileBase` 不知道 payload，但它可以知道“有一个定时触发计时器到点了”。因此事件名使用 `TimedTriggerElapsed`，避免叫 `PayloadReady` 这类上层语义名称。

### 5.2 新增 ArmTimedTrigger 方法

新增公开方法：

```csharp
public void ArmTimedTrigger(float delaySeconds)
```

职责：

```text
开启这颗投射物的定时触发计时器。
只有 SpellCaster 在发现 EmitCommand.PayloadTrigger == AfterDelay 且 HasPayload 时才会调用。
```

内部字段：

```csharp
private bool _timedTriggerArmed;
private float _timedTriggerRemaining;
```

规则：

- `delaySeconds <= 0` 时可以视作下一帧触发，避免在 `ArmTimedTrigger` 内直接重入施法。
- 未调用 `ArmTimedTrigger` 的普通投射物不做定时检查。

### 5.3 Update 中计时

定时触发属于游戏逻辑计时，不是物理积分。因此建议在 `Update()` 中处理：

```text
Update:
  if _consumed return
  if !_timedTriggerArmed return
  _timedTriggerRemaining -= Time.deltaTime
  if _timedTriggerRemaining > 0 return

  _consumed = true
  TimedTriggerElapsed?.Invoke(transform.position, ResolveCurrentDirection())
  Destroy(gameObject)
```

`FixedUpdate()` 仍然只负责当前已有的“是否让模型朝向速度方向”逻辑。

### 5.4 与命中互斥

定时触发和命中触发必须互斥。

```text
先命中：
  OnCollisionEnter 设置 _consumed=true
  触发 Impacted
  Destroy
  后续 Update 不再触发定时

先定时：
  Update 设置 _consumed=true
  触发 TimedTriggerElapsed
  Destroy
  后续 OnCollisionEnter 不再结算

同队穿过：
  不设置 _consumed
  不触发 Impacted
  投射物继续飞行
  仍然可能在之后触发定时 payload
```

这正好符合本阶段确认过的语义：只有投射物存活到指定时间，才释放定时 payload。

### 5.5 与 _maxLifetime 的关系

`ProjectileBase` 已经有 `_maxLifetime`，用于兜底自毁：

```csharp
Destroy(gameObject, _maxLifetime);
```

定时触发和 `_maxLifetime` 不是同一个概念：

```text
PayloadDelaySeconds：玩法语义，时间到会释放 payload 并销毁自己。
_maxLifetime：安全兜底，防止投射物永远留在场上，不释放 payload。
```

因此需要注意：

如果 `PayloadDelaySeconds >= _maxLifetime`，投射物可能先被 `_maxLifetime` 销毁，导致定时 payload 不释放。

本阶段建议在文档和 Inspector 使用上约定：

```text
定时类法术的 PayloadDelaySeconds 应小于投射物 prefab 的 _maxLifetime。
```

后续可以加入 Editor 校验或运行时 `GameLog.Warn`，但 MVP 先不做复杂校验。

## 6. SpellCaster 设计

### 6.1 当前 Phase D 逻辑

当前 `SpellCaster` 在生成带 payload 的投射物时，只做一件事：

```csharp
if (cmd.HasPayload)
{
    proj.Impacted += (hitPoint, hitDir) =>
        RunCast(payload, 1, payloadMods, hitPoint, hitDir, team, attackerId, casterCollider);
}
```

### 6.2 Phase E 逻辑

Phase E 需要根据 `cmd.PayloadTrigger` 分流：

```text
if !cmd.HasPayload:
  不绑定任何 payload 事件

if cmd.PayloadTrigger == OnImpact:
  订阅 proj.Impacted
  命中时在 hitPoint / hitDir 运行 payload

if cmd.PayloadTrigger == AfterDelay:
  订阅 proj.TimedTriggerElapsed
  调用 proj.ArmTimedTrigger(cmd.PayloadDelaySeconds)
  到时间时在 position / direction 运行 payload

if cmd.PayloadTrigger == None:
  不绑定 payload 事件
```

仍然使用：

```csharp
RunCast(payload, 1, payloadMods, position, direction, team, attackerId, casterCollider)
```

也就是说，命中触发和定时触发都复用同一套递归施法入口。它们只是在“什么时候调用 RunCast”上不同。

### 6.3 方向选择

定时触发释放 payload 时，方向使用投射物当前方向：

```text
优先：Rigidbody.linearVelocity.normalized
兜底：transform.forward
```

这样玩家会直觉地理解为“火球飞到一半时爆成下一段法术，下一段继续沿当前飞行方向前进”。

后续如果需要更多玩法，可以扩展为：

- 朝向玩家瞄准点；
- 朝向最近敌人；
- 随机方向；
- 环形散射；
- 使用投射物法线或旋转方向。

但这些不属于本阶段范围。

## 7. UI 与资产表现

本阶段不强制修改 UI 代码。

UI 仍然通过：

```text
SpellDefinition.Icon
```

显示法术图标。

建议资产层采用新的视觉约定：

```text
无角标火球：普通火球
小太阳角标：命中触发火球
小时钟/沙漏角标：定时火球
```

这和 Phase D 的小太阳图标做法一致，优点是不用改 UI 结构。

需要注意：当前角标是图标资产约定，不是 UI 自动生成。真正决定行为的是：

```text
SpellDefinition.PayloadTrigger
```

后续如果法术数量变多，可以考虑让 `SpellSlotView` 根据 `PayloadTrigger` 动态叠加角标，减少资产配置错误。

6. 和命中触发共存：



## 9. 不在本阶段范围

本阶段不做：

- UI 动态角标。
- Editor 自动资产迁移。
- 全局投射物数量上限。
- 递归深度硬上限。
- 法力资源正式接入。
- 冷却系统。
- 计时触发时的专属 VFX/SFX。
- 多种定时方向策略。
- 时间停止或暂停期间的特殊计时规则。

关于暂停：当前 `Update()` 使用 `Time.deltaTime`，因此若游戏被 `Time.timeScale = 0` 暂停，定时触发也会暂停。这与法术编辑界面打开时暂停游戏的现有行为一致。

## 11. 决策记录

1. 定时类法术采用 `PayloadTriggerMode.AfterDelay`，不是新的 `SpellKind`。
2. Phase D 的 `IsTrigger` 将升级为 `PayloadTriggerMode.OnImpact`。
3. 定时触发要求投射物仍然存活；提前命中或销毁不释放 payload。
4. 定时触发到点后，旧投射物销毁，并在当前位置沿当前飞行方向释放 payload。
5. 定时触发和命中触发互斥，通过 `_consumed` 防止重复结算。
6. payload 仍然是严格后缀，递归自然收敛，本阶段不加递归护栏。
7. Combat 层只提供通用事件，不认识 payload。
8. UI 本阶段继续使用 Icon 资产区分普通、命中触发、定时触发。
