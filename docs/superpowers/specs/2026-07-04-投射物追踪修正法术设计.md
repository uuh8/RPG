# 投射物追踪修正法术设计 Spec

创建时间：2026-07-04 11:47:34  
功能名：Homing Modifier Spell / 投射物追踪修正法术  
阶段：设计规格，待用户 review 后进入 implementation plan  
范围：只设计“有限时间、有限转向”的追踪修正 MVP，不做完全追踪、不做必中导弹、不做复杂目标优先级系统。

---

## 0. 本功能要做什么

本功能新增一个 `Modify` 法术：投射物追踪修正。

玩家在法杖中配置：

```text
[追踪] [普通火球]
```

运行效果：

1. 普通火球仍然是普通火球。
2. 但这次生成的火球会获得“有限追踪能力”。
3. 火球飞行过程中会检测附近敌人。
4. 一旦检测到范围内存在敌方目标，就锁定一个目标，并启动追踪计时器。
5. 在计时器持续时间内，火球不会直接转向目标，而是按有限转向速度逐步把飞行方向偏向目标。
6. 计时结束后，火球停止追踪，继续沿当前速度方向飞行。

核心设计边界：

```text
这不是完全追踪。
这不是必中。
这不是持续到命中为止的导弹。
```

更准确的描述是：

```text
投射物在短时间内获得一次“自动修正弹道”的机会。
```

## 1. 需求拆解与基础知识

### 1.1 玩家可见效果

玩家看到的是：

```text
火球原本直线飞行。
当它靠近敌人一定范围后，火球开始轻微转向敌人。
转向持续一小段时间。
如果角度、距离、速度合适，火球更容易命中。
如果敌人离得太远、火球速度太快、角度太偏，仍然可能打空。
```

这正是本功能的目标：提高命中容错，但不剥夺走位价值。

### 1.2 为什么不能做“完全追踪”

完全追踪通常指：

```text
投射物每帧都把方向直接指向目标，直到命中或销毁。
```

这种设计的问题：

- 玩家或敌人的走位意义会下降。
- 投射物很容易变成必中。
- 一旦和多重、触发、定时、弹跳组合，强度会迅速失控。
- 后续平衡只能通过降低伤害硬砍，玩法空间变窄。

所以本功能采用“有限追踪”：

```text
检测范围有限。
追踪时间有限。
转向速度有限。
每颗投射物只触发一次追踪窗口。
```

### 1.3 基础数学：有限转向

投射物当前方向：

```text
currentDir
```

目标方向：

```text
desiredDir = (targetPosition - projectilePosition).normalized
```

如果完全追踪，会直接：

```text
currentDir = desiredDir
```

本功能不能这么做。我们要限制每秒最多转多少角度：

```csharp
Vector3 newDir = Vector3.RotateTowards(
    currentDir,
    desiredDir,
    turnRateRadiansPerSecond * Time.fixedDeltaTime,
    0f);
```

这样火球只能逐步偏移方向，而不是瞬间锁头。

### 1.4 Unity 相关知识

| 技术点 | 作用 |
|---|---|
| `Physics.OverlapSphereNonAlloc` | 在投射物周围无 GC 地检测候选目标 |
| `IDamageable` | 当前项目中“可受击目标”的统一接口 |
| `TeamId` | 用来过滤同阵营目标，避免追踪自己或队友 |
| `Rigidbody.linearVelocity` | 修改投射物当前速度方向 |
| `Vector3.RotateTowards` | 限制追踪转向角速度 |
| `FixedUpdate` | 更适合修改 `Rigidbody` 速度 |
| `Transform` / `Collider.bounds.center` | 用来获得目标位置 |

### 1.5 MVP 明确边界

本功能只做：

- 追踪作为 `Modify` 法术影响后续 `Emit`。
- 投射物飞行时检测敌方 `IDamageable`。
- 检测到敌人后锁定一个目标。
- 启动一次追踪计时器。
- 在计时器内以有限转向角速度偏向目标。
- 计时结束后停止追踪。
- EditMode tests 覆盖纯解释器数据传递。

本功能不做：

- 完全追踪。
- 多目标切换。
- 目标预测提前量。
- 穿墙追踪判定。
- 锁定 UI / 目标指示器。
- 追踪专属 VFX / SFX。
- 每个敌人威胁值排序。
- 通用 `ProjectileBehavior` 大框架。
- 运行时动态修改法术资产。

## 2. 可选实现方案

### 2.1 方案 A：完全追踪，每帧直接朝向目标

做法：

投射物每帧找到最近敌人，然后直接把速度方向设为目标方向：

```csharp
rb.linearVelocity = desiredDir * speed;
```

优点：

- 实现简单。
- 视觉效果明显。
- 命中率极高。

缺点：

- 太强，接近必中。
- 敌人走位意义下降。
- 和多重、触发、定时组合后很容易失控。
- 面试中不好解释平衡边界，因为这是一个比较粗暴的方案。

结论：

不采用。用户已经明确不要“完全追踪”，本方案也不适合当前项目的战斗设计目标。

### 2.2 方案 B：有限时间 + 有限转向的追踪窗口

做法：

投射物先正常飞行并扫描周围目标。检测到敌人后：

1. 锁定目标。
2. 开启追踪计时器。
3. 在计时器内使用 `Vector3.RotateTowards` 限制每秒转向角度。
4. 计时结束后停止追踪。

优点：

- 强度可控。
- 仍然保留命中失败可能。
- 参数清晰：范围、持续时间、转向速度。
- 可以自然作为 `Modify` 法术组合到任意投射物。
- 面试中容易讲清楚“为什么不是必中”。

缺点：

- 需要在 `ProjectileBase` 中增加扫描和运行时追踪状态。
- 参数调得太高时仍然可能接近完全追踪，需要 Editor 中控制数值。

结论：

本阶段推荐采用。

### 2.3 方案 C：目标预测追踪

做法：

根据目标速度预测未来位置，让投射物朝预测点偏移：

```text
predictedPosition = targetPosition + targetVelocity * leadTime
```

优点：

- 更像真实导弹。
- 对移动目标更有效。
- 面试中技术含量更高。

缺点：

- 当前敌人系统没有统一暴露目标速度接口。
- 需要处理目标加速度、停顿、转向。
- 更难平衡，也更容易变成“高级必中”。

结论：

暂不采用。当前阶段先做基础有限追踪，等需要更高阶弹道时再扩展。

### 2.4 方案 D：通用 ProjectileBehavior 系统

做法：

把弹跳、重力、追踪、穿透、分裂等全部抽象成 behavior pipeline：

```text
BounceBehavior
GravityBehavior
HomingBehavior
PierceBehavior
SplitBehavior
```

优点：

- 长期扩展性最好。
- 每种 projectile behavior 独立。

缺点：

- 当前阶段过重。
- 需要设计 behavior 生命周期、优先级、冲突规则、序列化方式。
- 会把一个明确的功能变成大型架构重构。

结论：

作为未来演进方向记录，不作为本次 MVP。

## 3. 最终选择的方案与技术

最终选择：方案 B。

完整数据流：

```text
SpellDefinition.ModHoming*
    ↓
CastModifierState.Homing*
    ↓
CastEvaluator.BakeEmit(...)
    ↓
EmitCommand.Homing*
    ↓
SpellCaster
    ↓
ProjectileBase.ConfigureHoming(...)
    ↓
ProjectileBase.FixedUpdate()
    ↓
Physics.OverlapSphereNonAlloc + Vector3.RotateTowards + Rigidbody.linearVelocity
```

### 3.1 新增参数建议

`SpellDefinition` 的 `Modify` 区新增：

```csharp
public float ModHomingRadius = 0f;
public float ModHomingDuration = 0f;
public float ModHomingTurnRateDegrees = 0f;
```

含义：

| 字段 | 含义 | 示例 |
|---|---|---|
| `ModHomingRadius` | 投射物扫描敌人的范围 | 6 |
| `ModHomingDuration` | 检测到目标后追踪持续时间 | 0.6 秒 |
| `ModHomingTurnRateDegrees` | 每秒最大转向角度 | 120 度/秒 |

判定一个投射物是否具备追踪能力：

```text
HomingRadius > 0
HomingDuration > 0
HomingTurnRateDegrees > 0
```

### 3.2 多个追踪修正如何叠加

推荐 MVP 叠加规则：

```text
HomingRadius：取最大值
HomingDuration：相加
HomingTurnRateDegrees：相加
```

原因：

- 范围相加容易失控，两个 8 米追踪不应直接变 16 米。
- 持续时间相加容易理解，两个追踪修正表示追踪窗口更久。
- 转向速度相加也容易理解，多个追踪修正表示转向更积极。

示例：

```text
[追踪A radius=6 duration=0.5 turn=90]
[追踪B radius=8 duration=0.4 turn=60]
[火球]
```

最终：

```text
radius = 8
duration = 0.9
turnRate = 150 deg/s
```

### 3.3 目标选择规则

MVP 目标选择：

```text
在检测半径内选择最近的敌方、存活 IDamageable。
```

过滤条件：

```text
target != null
target.IsAlive == true
target.TeamId != attackerTeam
```

目标位置：

```text
优先使用目标 HealthComponent/IDamageable 对应 Component 的 transform.position。
如果拿不到 Transform，则使用命中的 Collider.bounds.center。
```

本阶段不做：

- 优先锁 Boss。
- 优先锁血量最低。
- 优先锁准星附近。
- 优先锁当前正在攻击玩家的敌人。

### 3.4 追踪窗口规则

每颗投射物最多触发一次追踪窗口：

```text
未发现目标：
    按扫描间隔继续检测。

第一次发现目标：
    锁定目标。
    homingRemaining = HomingDuration。
    标记 hasAcquiredHomingTarget = true。

追踪计时中：
    每个 FixedUpdate 按 TurnRate 偏向目标。
    homingRemaining -= Time.fixedDeltaTime。

计时结束：
    停止追踪。
    不再重新扫描。
```

为什么不反复重新扫描？

因为反复重新扫描会让投射物持续寻找新目标，接近“智能导弹”。本功能要的是一次有限修正，而不是自动杀敌系统。

### 3.5 目标丢失规则

如果追踪窗口内目标死亡、销毁或失效：

```text
停止追踪，投射物保持当前速度继续飞行。
不重新锁定新目标。
```

原因：

- 简单、可控。
- 避免一颗火球连续改锁多个敌人。
- 强度更容易平衡。

## 4. 架构设计与拆解

### 4.1 所在架构层

追踪修正横跨五层：

```text
数据层：
    SpellDefinition

纯规则层：
    CastModifierState
    CastEvaluator

边界对象层：
    EmitCommand

运行时桥接层：
    SpellCaster

投射物执行层：
    ProjectileBase
```

它不应该进入：

- `DamagePipeline`：追踪不改变伤害公式。
- `HealthComponent`：追踪不属于生命值系统。
- `WizardController`：角色只负责施法，不关心投射物是否追踪。
- `EnemyControllerBase`：敌人不需要知道自己被火球追踪。
- `WandEditorController`：UI 只编辑法术顺序，不解释追踪语义。

### 4.2 数据层：`SpellDefinition`

新增字段：

```csharp
[Min(0f)]
public float ModHomingRadius = 0f;

[Min(0f)]
public float ModHomingDuration = 0f;

[Min(0f)]
public float ModHomingTurnRateDegrees = 0f;
```

一个追踪修正法术资产可以配置为：

```text
Kind = Modify
DisplayName = 追踪
ModHomingRadius = 6
ModHomingDuration = 0.6
ModHomingTurnRateDegrees = 120
```

### 4.3 纯规则层：`CastModifierState`

新增字段：

```csharp
public readonly float HomingRadius;
public readonly float HomingDuration;
public readonly float HomingTurnRateDegrees;
```

`Default`：

```text
HomingRadius = 0
HomingDuration = 0
HomingTurnRateDegrees = 0
```

`Apply`：

```text
HomingRadius = Max(HomingRadius, modify.ModHomingRadius)
HomingDuration = HomingDuration + modify.ModHomingDuration
HomingTurnRateDegrees = HomingTurnRateDegrees + modify.ModHomingTurnRateDegrees
```

### 4.4 边界对象层：`EmitCommand`

新增字段：

```csharp
public readonly float HomingRadius;
public readonly float HomingDuration;
public readonly float HomingTurnRateDegrees;
```

含义：

```text
这颗投射物本次生成时拥有的追踪运行时配置。
```

注意它是快照，不是运行时剩余计时。  
运行时剩余计时应放在 `ProjectileBase` 的实例字段里。

### 4.5 运行时桥接层：`SpellCaster`

生成 projectile 后调用：

```csharp
proj.ConfigureHoming(
    cmd.HomingRadius,
    cmd.HomingDuration,
    cmd.HomingTurnRateDegrees);
```

建议顺序：

```text
Instantiate
GetComponent<ProjectileBase>
绑定 payload 事件
ConfigureBounce
ConfigureHoming
Init
```

`SpellCaster` 的职责仍然是桥接：

```text
它懂 EmitCommand，也懂 ProjectileBase。
它不亲自扫描目标，不亲自修改速度。
```

### 4.6 投射物执行层：`ProjectileBase`

新增运行时字段：

```csharp
private float _homingRadius;
private float _homingDuration;
private float _homingTurnRateDegrees;

private bool _homingEnabled;
private bool _homingAcquired;
private float _homingRemaining;
private Transform _homingTarget;
```

建议增加扫描间隔：

```csharp
[SerializeField] private float _homingScanInterval = 0.1f;
private float _homingScanTimer;
```

原因：

```text
不要每个 FixedUpdate 都做 OverlapSphere。
0.1 秒检测一次通常足够。
```

目标检测使用静态缓冲：

```csharp
private static readonly Collider[] s_homingHits = new Collider[16];
```

用 `Physics.OverlapSphereNonAlloc`，避免每次扫描分配数组。

### 4.7 FixedUpdate 流程

`ProjectileBase.FixedUpdate` 建议扩展为：

```text
if (_consumed) return

TickHoming(Time.fixedDeltaTime)

if FaceVelocityInFlight:
    根据当前速度更新模型朝向
```

`TickHoming` 伪代码：

```text
if !homingEnabled:
    return

if !homingAcquired:
    scanTimer -= dt
    if scanTimer > 0:
        return
    scanTimer = scanInterval
    TryAcquireNearestEnemy()
    return

if homingRemaining <= 0:
    return

if target invalid:
    homingRemaining = 0
    return

currentVelocity = rb.linearVelocity
currentSpeed = currentVelocity.magnitude
if currentSpeed too small:
    return

desiredDir = (target.position - projectile.position).normalized
newDir = RotateTowards(currentDir, desiredDir, turnRate * dt)
rb.linearVelocity = newDir * currentSpeed
```

### 4.8 为什么放在 `ProjectileBase`，不是新脚本

当前阶段可以直接放进 `ProjectileBase`，原因：

- `ProjectileBase` 已经集中管理投射物生命周期、速度、碰撞、计时触发、弹跳。
- 本功能需要直接修改 `Rigidbody.linearVelocity`。
- 当前 projectile behavior 数量还没有多到必须拆出 behavior pipeline。

但要承认一个边界：

如果后续继续增加：

```text
穿透
分裂
吸附
环绕
返回施法者
```

那 `ProjectileBase` 会变胖。届时应考虑抽象：

```csharp
ProjectileRuntimeConfig
ProjectileBehaviorPipeline
```

本次 spec 不提前做这个重构，避免过度设计。

## 5. 与现有法术的组合关系

### 5.1 和普通火球

```text
[追踪] [普通火球]
```

普通火球获得有限追踪窗口。  
如果飞行路径附近没有敌人，它仍然直线飞行。

### 5.2 和重力修正

```text
[重力] [追踪] [普通火球]
```

结果：

```text
UseGravity = true
Homing enabled
```

运行语义：

- Unity gravity 会持续影响速度。
- Homing 会在追踪窗口内调整速度方向。
- 两者可能互相影响，这是允许的。

MVP 不做复杂优先级。可以理解为：

```text
重力负责持续下坠。
追踪负责短时间内修正方向。
```

### 5.3 和弹跳修正

```text
[弹跳] [追踪] [普通火球]
```

结果：

```text
BounceCount > 0
Homing enabled
```

推荐语义：

- 如果投射物先检测到敌人，启动追踪窗口。
- 追踪期间如果撞到环境并且还有弹跳次数，先执行弹跳。
- 弹跳后，若追踪窗口仍未结束，追踪可以继续偏向目标。
- 如果追踪窗口已经结束，则弹跳后按当前反射方向继续飞行。

这符合两个行为的职责：

```text
弹跳：碰撞瞬间改变方向。
追踪：追踪窗口内持续微调方向。
```

### 5.4 和触发类火球

```text
[追踪] [触发火球] [普通火球]
```

结果：

```text
触发火球本体有追踪能力。
payload 也通过 PayloadMods 继承追踪修正。
```

原因：

`EmitCommand.PayloadMods` 会保存触发前的 `CastModifierState` 快照。  
所以 payload 运行时会以这个修正状态作为起点。

这意味着触发出来的普通火球也会具备追踪能力。

### 5.5 和定时类火球

```text
[追踪] [定时火球] [普通火球]
```

结果：

- 定时火球本体可以追踪。
- 如果定时火球存活到 delay，会在当前位置释放 payload。
- payload 继承追踪修正。

注意：

如果追踪让定时火球提前命中敌人或环境，那么定时 payload 不释放。  
这是定时类法术既有语义：必须存活到时间。

### 5.6 和多重法术

```text
[追踪] [三重] [火球] [火球] [火球]
```

结果：

三个火球都会具备追踪能力。

每颗火球独立扫描、独立锁定、独立计时。  
它们可能锁定同一个敌人，也可能锁定不同敌人，取决于各自飞行位置和扫描结果。

## 6. 测试策略

### 6.1 EditMode tests：纯解释器语义

修改：

```text
Assets/_Project/Tests/Skills/CastModifierStateTests.cs
Assets/_Project/Tests/Skills/CastEvaluatorTests.cs
```

测试点：

1. `CastModifierState.Default` 的追踪字段均为 0。
2. 单个追踪修正会写入后续 `EmitCommand`。
3. 多个追踪修正按规则叠加：
   - radius 取最大；
   - duration 相加；
   - turn rate 相加。
4. 追踪修正只影响后续 `Emit`，不影响前面的 `Emit`。
5. payload 捕获时，`PayloadMods` 保留追踪修正快照。

### 6.2 Play Mode 手动验证

需要用户在 Unity Editor 中验证：

```text
[追踪] [普通火球]
[追踪] [重力] [普通火球]
[追踪] [弹跳] [普通火球]
[追踪] [触发火球] [普通火球]
[追踪] [定时火球] [普通火球]
[追踪] [三重] [火球] [火球] [火球]
```

观察点：

- 没有敌人在范围内时，火球不转向。
- 敌人进入范围后，火球开始有限偏移。
- 偏移不是瞬间锁头。
- 追踪时间结束后，火球不再继续追踪。
- 角度太偏时仍然可能打空。
- 触发 payload / 定时 payload 的继承符合预期。
- 多重火球各自独立追踪。

## 8. 成功标准

功能完成后应满足：

1. 追踪作为 `Modify` 法术影响后续 `Emit`。
2. 不创建 `HomingFireball` 特例。
3. 追踪参数沿现有解释器链路传递。
4. 投射物在检测到敌人后只启动一次有限追踪窗口。
5. 追踪使用有限转向，不是直接锁定目标。
6. 同阵营目标不会被追踪。
7. 已死亡目标不会被追踪。
8. 目标丢失后不重新锁死新目标。
9. 与重力、弹跳、触发、定时、多重组合时语义清晰。
10. 纯解释器逻辑有 EditMode tests。
11. 运行时扫描不产生 GC Alloc。

## 9. 风险与取舍

### 9.1 `ProjectileBase` 会继续变大

弹跳、定时、重力、追踪都逐渐接入 `ProjectileBase`。  
这是当前 MVP 可以接受的，但要记录风险。

如果后续继续增加 2-3 个 projectile behavior，应考虑抽象：

```text
ProjectileRuntimeConfig
ProjectileBehaviorPipeline
```

当前不做，是因为过早抽象会增加理解成本。

### 9.2 参数平衡会决定体验

追踪系统不是写完代码就结束。体验主要由三个参数决定：

```text
范围
持续时间
转向速度
```

这三个参数的乘积越大，越接近完全追踪。  
因此 Editor 测试阶段必须用“能打空”的标准来调参。

### 9.3 目标扫描可能带来性能压力

如果很多投射物同时存在，并且每个都每帧扫描，会有性能风险。

MVP 规避方式：

- 使用 `OverlapSphereNonAlloc`。
- 使用固定大小静态 buffer。
- 使用扫描间隔，例如 0.1 秒。
- 只在尚未锁定且追踪未触发过时扫描。

### 9.4 和重力组合时轨迹可能复杂

重力会持续改变速度，追踪会短时间改变速度方向。  
两者组合时轨迹可能不是简单平滑曲线。

本阶段接受这种结果，因为它本身也是组合系统的玩法表现。  
如果后续需要更严格控制，可以为追踪增加“只调整水平面方向”选项。

## 10. 面试表达点

可以这样描述：

> 我没有把追踪做成一个新的 `HomingFireball`，而是把它建模为法术编程系统中的 `Modify` 指令。它会沿 `SpellDefinition -> CastModifierState -> CastEvaluator -> EmitCommand -> SpellCaster -> ProjectileBase` 的主链路传递追踪参数。运行时投射物并不是完全锁头，而是在检测到范围内敌人后，只启动一次有限追踪窗口，在窗口内通过 `Vector3.RotateTowards` 限制每秒最大转向角度，把当前速度方向逐步偏向目标。这样它能提升命中容错，但仍然保留打空可能，避免成为必中导弹。

也可以补充：

> 为了保持模块边界，`Game.Skills` 只负责解释出追踪参数，不接触 Unity 物理对象；`SpellCaster` 负责把参数注入 `ProjectileBase`；`ProjectileBase` 才执行目标扫描和速度修正。目标扫描使用 `Physics.OverlapSphereNonAlloc` 和预分配 buffer，避免运行时 GC Alloc。同阵营和死亡目标会被过滤，目标一旦丢失不会重新锁定新目标，从设计上控制技能强度。
