# 轨道螺旋修正法术设计 Spec

创建时间：2026-07-04 14:29:16  
更新时间：2026-07-04  
功能名：Orbital Projectile Modifier Spell / 轨道螺旋修正法术  
阶段：设计规格，待用户 review 后进入 implementation plan  
范围：实现一种 3D 轨道式投射物修正：投射物围绕一个看不见的移动圆心旋转前进；不做随机散弹、不做完全追踪、不做复杂弹幕编辑器。

---

## 0. 用户想要的效果

这次需求不是普通“立体散射”。

你描述的效果是：

```text
有一个看不见的球。
这个球的圆心沿着玩家发射方向移动。
投射物不直接沿直线飞，而是在这个看不见的球面/圆环上绕着圆心旋转。
整体看起来像投射物围绕一条前进轴做螺旋运动。
```

更工程化地说：

```text
移动圆心 center(t) 沿 baseDir 前进。
投射物位置 projectile(t) = center(t) + orbitalOffset(t)。
orbitalOffset(t) 围绕 baseDir 旋转。
```

这个功能比普通 3D 散射更适合 3D 战斗，因为：

- 它不是只在发射瞬间分散方向。
- 它在飞行过程中持续覆盖一个空间管道。
- 它既能覆盖左右，也能覆盖上下。
- 从玩家视角看，投射物会形成螺旋/环绕弹道，辨识度强。

---

## 1. 玩家可见效果

玩家配置：

```text
[轨道螺旋] [三重] [火球] [火球] [火球]
```

发射后：

```text
三颗火球围绕一条看不见的前进轴旋转。
这条轴从施法点出发，沿玩家瞄准方向移动。
火球像绕着一个看不见的移动球面/圆环在飞。
```

如果只有一颗火球：

```text
[轨道螺旋] [火球]
```

它会沿着一个螺旋轨迹前进：

```text
中心点向前移动，火球绕中心点旋转。
```

如果有三颗火球：

```text
三颗火球分布在同一个圆环上的不同相位。
例如 0° / 120° / 240°。
```

补充要求：三颗火球不能只在同一个旋转平面里转。  
如果旋转面完全重合，视觉会退化成“绕一个圆环旋转”，看不出是在围绕球面运动。  
因此同一批投射物除了要有不同相位，还要尽量拥有不同的轨道面倾斜。

这样能够自然覆盖 3D 空间：

```text
一颗在上方，一颗在左下，一颗在右下。
随着旋转，它们会持续交换空间位置。
```

## 2. 基础知识和原理

### 2.1 这是“运动修正”，不是“初始散射”

普通散射只在生成瞬间决定方向：

```text
生成时把火球方向偏左/偏右/偏上。
之后火球按自己的速度飞。
```

轨道螺旋修正不同：

```text
投射物飞行过程中持续改变位置/速度。
```

所以它不应该只放在 `SpellAiming` 里。  
它需要运行时逻辑，应该进入 `ProjectileBase`。

### 2.2 看不见的圆心是什么

可以把每颗投射物想象成跟随一个虚拟中心点：

```text
center(t) = startPosition + forward * centerSpeed * t
```

这个中心点不显示、不碰撞、不造成伤害。  
它只是数学上的参考点。

投射物的位置由两部分组成：

```text
center(t)        圆心沿发射方向前进
orbitalOffset(t) 投射物相对圆心的偏移
```

最终：

```text
projectilePosition(t) = center(t) + orbitalOffset(t)
```

### 2.3 球面/圆环旋转如何计算

给定前进方向：

```text
forward = 发射方向
```

构造垂直于 `forward` 的两个局部轴：

```text
right
up
```

然后轨道偏移可以写成：

```text
offset = right * cos(angle) * radius
       + up    * sin(angle) * radius
```

其中：

```text
radius = 轨道半径
angle = 当前旋转角度
```

每一帧：

```text
angle += angularSpeed * deltaTime
center += forward * centerSpeed * deltaTime
```

这样投射物就会围绕前进方向做螺旋运动。

### 2.4 为什么说它兼顾 2D 和 3D

在 2D 里，你看到的是投射物围绕中心线左右摆动。  
在 3D 里，它会围绕前进轴形成完整空间覆盖。

因此它比“只在水平面分裂方向”的散射更适合本项目：

```text
敌人跳起来时，旋转弹道仍可能覆盖到上方。
敌人在坡上坡下时，旋转弹道仍有高度覆盖。
多颗投射物有不同相位时，可以形成空间包围感。
```

## 3. 可选实现方案

### 3.1 方案 A：只做初始 3D 散射

做法：

发射时给每颗投射物不同 yaw/pitch。

优点：

- 简单。
- 只影响初始方向。
- 不需要改 `ProjectileBase`。

缺点：

- 不是你现在描述的效果。
- 投射物不会围绕移动圆心旋转。
- 空间覆盖只发生在初始方向上，不是持续覆盖。

结论：

不采用。旧 spec 就是这个方向，需要改掉。

### 3.2 方案 B：用 `Rigidbody` 物理力模拟绕圈

做法：

每帧给投射物施加侧向力，让它绕中心运动。

优点：

- 看起来更物理。
- 可以产生自然曲线。

缺点：

- 很难稳定控制轨道半径。
- 容易受质量、阻力、碰撞、重力影响。
- 不利于确定性测试。
- 参数调试难。

结论：

不采用。这个功能更适合数学轨道控制，而不是真实物理力。

### 3.3 方案 C：数学轨道控制位置/速度

做法：

投射物保存一个虚拟圆心、轨道半径、角速度、相位。  
每个 `FixedUpdate` 根据公式计算目标位置和速度。

优点：

- 可控。
- 表现稳定。
- 参数容易理解。
- 可以用纯函数测试轨道点计算。
- 视觉效果符合“围绕看不见的球面旋转”。

缺点：

- 会让投射物运动不再完全由物理自由飞行决定。
- 需要谨慎和重力、追踪、弹跳组合。

结论：

推荐采用。

### 3.4 方案 D：为轨道法术单独做一个 `OrbitalFireball`

做法：

新建一种特殊投射物 prefab 或脚本。

优点：

- 局部实现简单。

缺点：

- 破坏法术组合系统。
- 只能作用于火球，不能作用于未来其他 Emit。
- 会产生 `OrbitalTimedFireball`、`OrbitalTriggerFireball` 等组合爆炸。

结论：

不采用。它应该是 `Modify`，不是特殊 `Emit`。

## 4. 最终推荐方案

采用：

```text
方案 C：数学轨道控制位置/速度。
```

功能类型：

```text
Modify 法术
```

完整数据流：

```text
SpellDefinition.ModOrbitRadius
SpellDefinition.ModOrbitAngularSpeedDegrees
SpellDefinition.ModOrbitPhaseOffsetDegrees
SpellDefinition.ModOrbitPlaneTiltDegrees
    ↓
CastModifierState.Orbit*
    ↓
CastEvaluator.BakeEmit(...)
    ↓
EmitCommand.Orbit*
    ↓
SpellCaster
    ↓
ProjectileBase.ConfigureOrbit(...)
    ↓
ProjectileBase.FixedUpdate()
```

### 4.1 新增字段建议

在 `SpellDefinition` 的 `Modify` 区新增：

```csharp
public float ModOrbitRadius = 0f;
public float ModOrbitAngularSpeedDegrees = 0f;
public float ModOrbitPhaseOffsetDegrees = 0f;
public float ModOrbitPlaneTiltDegrees = 0f;
```

含义：

| 字段 | 含义 |
|---|---|
| `ModOrbitRadius` | 投射物离虚拟圆心的半径 |
| `ModOrbitAngularSpeedDegrees` | 每秒绕圆心旋转多少度 |
| `ModOrbitPhaseOffsetDegrees` | 初始相位偏移，用来让多个修正或资产产生不同起始角 |
| `ModOrbitPlaneTiltDegrees` | 轨道平面倾斜角，用来避免多颗投射物共用同一个圆环平面 |

判定启用轨道：

```text
OrbitRadius > 0
OrbitAngularSpeedDegrees != 0
```

### 4.2 多个轨道修正如何叠加

推荐 MVP 规则：

```text
OrbitRadius：取最大值
OrbitAngularSpeedDegrees：相加
OrbitPhaseOffsetDegrees：相加
OrbitPlaneTiltDegrees：取最大绝对值
```

理由：

- 半径相加容易失控。
- 角速度相加代表旋转更快，直觉清晰。
- 相位相加可以给不同轨道法术做起始角调整。
- 平面倾斜取最大绝对值，避免多个修正叠加后旋转面翻转过度。

### 4.3 多颗投射物如何分相位

同一批发射中有 `count` 颗投射物。  
每颗投射物应获得不同相位：

```text
batchPhase = 360 * index / count
```

最终初始相位：

```text
initialPhase = OrbitPhaseOffsetDegrees + batchPhase
```

例如三重：

```text
index 0 -> 0°
index 1 -> 120°
index 2 -> 240°
```

这能形成一个围绕虚拟圆心的 3D 环。

但仅有相位还不够，因为所有投射物仍在同一个旋转面内。  
为了更像“围绕球面旋转”，还需要给同批投射物分配不同轨道面：

```text
batchPlaneTilt = PlaneTilt(index, count, OrbitPlaneTiltDegrees)
```

推荐分布：

```text
count = 1 -> 0°
count = 3, baseTilt = 35° -> 0° / +35° / -35°
count = 5, baseTilt = 25° -> 0° / +25° / -25° / +50° / -50°
```

这样每颗投射物都仍然绕移动圆心运动，但它们走的是球面上的不同“大圆路径”，视觉不会退化成一个平面圆环。

### 4.4 中心点速度

虚拟圆心移动速度建议使用投射物初始速度在前进方向上的速度：

```text
centerSpeed = initialVelocity.magnitude
```

原因：

```text
如果没有轨道修正，火球就是以这个速度向前飞。
有轨道修正后，虚拟圆心仍以这个速度向前，火球围绕圆心旋转。
```

这样可以保持整体飞行速度感。

### 4.5 如何驱动 Rigidbody

不建议每帧直接 `transform.position = targetPosition`，因为会绕过物理。

建议在 `FixedUpdate` 中计算下一目标点，然后设置：

```csharp
_rb.linearVelocity = (targetPosition - _rb.position) / deltaTime;
```

这样 Unity Physics 仍然通过刚体速度移动投射物，碰撞检测更稳定。

## 5. 架构设计

### 5.1 所在层级

轨道螺旋修正跨越：

```text
数据层：
    SpellDefinition

纯规则层：
    CastModifierState
    CastEvaluator

边界对象层：
    EmitCommand

运行时桥接层：
    SpellCaster

投射物执行层：
    ProjectileBase
```

它需要修改 `ProjectileBase`，因为：

```text
轨道螺旋不是生成瞬间的方向偏移。
它是飞行过程中的持续运动行为。
```

### 5.2 为什么不是 `SpellAiming`

`SpellAiming` 适合计算“发射瞬间的方向”。

但轨道螺旋需要：

```text
每个 FixedUpdate 更新中心点和旋转角。
修改 Rigidbody.linearVelocity。
处理碰撞、销毁、定时触发等生命周期。
```

这些都属于 `ProjectileBase` 的职责范围。

### 5.3 `SpellCaster` 的职责

`SpellCaster` 不计算轨道。  
它只负责把 `EmitCommand` 的轨道配置注入 projectile：

```csharp
proj.ConfigureOrbit(
    cmd.OrbitRadius,
    cmd.OrbitAngularSpeedDegrees,
    cmd.OrbitPhaseOffsetDegrees + SpellAiming.PhaseOffsetDegrees(i, count),
    SpellAiming.PlaneTiltDegrees(i, count, cmd.OrbitPlaneTiltDegrees));
```

`SpellCaster` 知道 `i/count`，所以“同批投射物相位分布”和“同批投射物轨道面错开”适合在这里决定，或委托给 `SpellAiming` 纯函数。

### 5.4 `ProjectileBase` 的职责

`ProjectileBase` 保存每颗投射物的轨道运行时状态：

```csharp
private bool _orbitEnabled;
private float _orbitRadius;
private float _orbitAngularSpeedDegrees;
private float _orbitAngleDegrees;
private float _orbitPlaneTiltDegrees;
private Vector3 _orbitCenter;
private Vector3 _orbitForward;
private Vector3 _orbitRight;
private Vector3 _orbitUp;
private float _orbitCenterSpeed;
```

在 `Init` 时，用初速度初始化：

```text
_orbitForward = velocity.normalized
_orbitCenter = transform.position
_orbitCenterSpeed = velocity.magnitude
```

在 `FixedUpdate` 中：

```text
center 前进
angle 增加
计算 targetPosition
设置 rb.linearVelocity 指向 targetPosition
```

## 6. 与现有法术组合关系

### 6.1 和三重射击

```text
[轨道螺旋] [三重] [火球] [火球] [火球]
```

三颗火球拥有不同相位，并且轨道面尽量错开，围绕同一个移动圆心做更接近球面的大圆运动。

这是最核心组合。

### 6.2 和重力

```text
[轨道螺旋] [重力] [火球]
```

MVP 建议：

```text
轨道控制优先，重力可开启但实际轨道会持续修正速度。
```

也就是说，重力可能被轨道运动部分覆盖。  
如果希望重力明显影响轨道中心点，下一个阶段可以让 `orbitCenter` 也受重力影响。

本阶段先保持简单：

```text
轨道中心沿发射方向匀速前进。
```

### 6.3 和追踪

```text
[轨道螺旋] [追踪] [火球]
```

两者都想修改速度，可能冲突。

MVP 推荐规则：

```text
如果启用轨道螺旋，追踪暂时不改变该投射物速度。
```

原因：

- 两套系统都在 `FixedUpdate` 写 `Rigidbody.linearVelocity`。
- 同时运行会导致轨迹难以预测。
- 先保证轨道螺旋可控。

后续可以设计“轨道圆心追踪目标”，但那是更高级功能。

### 6.4 和弹跳

```text
[轨道螺旋] [弹跳] [火球]
```

MVP 推荐：

```text
发生弹跳后，关闭轨道螺旋，按反射方向继续飞。
```

原因：

- 弹跳会改变飞行方向。
- 如果继续使用旧 orbitForward，视觉会很怪。
- 重新构造轨道也可以做，但复杂度更高。

本阶段先选择简单、可解释的规则。

### 6.5 和触发 / 定时

```text
[轨道螺旋] [触发火球] [普通火球]
[轨道螺旋] [定时火球] [普通火球]
```

触发/定时本体按轨道螺旋飞行。  
payload 是否继承轨道螺旋，沿用 `PayloadMods` 规则。

这意味着：

```text
如果轨道螺旋在触发火球前，payload 里的后续火球也可以获得轨道配置。
```

## 7. 测试策略

### 7.1 EditMode tests

需要覆盖：

1. `CastModifierState.Default` 轨道字段为 0。
2. 轨道修正会写入 `EmitCommand`。
3. 多个轨道修正叠加：
   - radius 取最大；
   - angular speed 相加；
   - phase offset 相加。
4. payload mods 保留轨道修正。
5. `SpellAiming.PhaseOffsetDegrees(index, count)`：
   - count <= 1 返回 0；
   - count = 3 返回 0 / 120 / 240；
   - count = 4 返回 0 / 90 / 180 / 270。

### 7.2 Play Mode 手动验证

推荐组合：

```text
[轨道螺旋] [火球]
[轨道螺旋] [三重] [火球] [火球] [火球]
[轨道螺旋] [定时火球] [火球]
[轨道螺旋] [触发火球] [火球]
```

观察：

```text
单发火球沿螺旋轨迹前进。
三重火球围绕同一前进轴不同相位旋转。
整体前进方向仍然是玩家瞄准方向。
轨道不是完全随机，也不是散射后直线飞。
```

## 9. 成功标准

功能完成后应满足：

1. 轨道螺旋是 `Modify` 法术，不是特殊火球。
2. 单颗投射物能围绕移动圆心做螺旋运动。
3. 多颗投射物能按相位分布，并且轨道面不完全重合。
4. 虚拟圆心沿发射方向前进。
5. 轨道参数沿法术解释器链路传递。
6. `Game.Skills` 不接触场景对象。
7. `ProjectileBase` 执行运行时轨道运动。
8. EditMode tests 覆盖纯数据语义和相位计算。

## 10. 风险与取舍

### 10.1 和追踪/弹跳存在速度写入冲突

轨道、追踪、弹跳都会修改速度。

MVP 明确：

```text
轨道启用时，追踪不介入速度。
弹跳发生后，关闭轨道。
```

这样先保证行为可控。

### 10.2 轨道运动可能绕过真实物理直觉

轨道是数学控制，不是物理力自然形成。  
但这是法术弹道效果，不是现实物理模拟。

使用 `Rigidbody.linearVelocity` 而不是直接改 `transform.position`，可以尽量保留碰撞检测稳定性。

### 10.3 三维视觉调参很重要

半径太小：

```text
看起来像普通直线火球。
```

角速度太快：

```text
视觉可能混乱。
```

建议先用：

```text
radius = 0.8
angularSpeed = 360 deg/s
```

## 11. 面试表达点

可以这样描述：

> 我们最初想把 2D 的散射扩展到 3D，但进一步分析后发现，用户想要的不是简单的初始方向散开，而是一个围绕移动圆心旋转的轨道弹道。于是我把它定义为新的 Modify 法术：轨道螺旋修正。它让投射物围绕一个沿发射方向移动的虚拟圆心旋转，形成螺旋式空间覆盖。

继续补充：

> 架构上它仍然沿 `SpellDefinition -> CastModifierState -> CastEvaluator -> EmitCommand -> SpellCaster -> ProjectileBase` 链路传递。`Game.Skills` 只保存和解释轨道半径、角速度、相位等纯数据；`SpellCaster` 根据同批发射的 index/count 计算初始相位；`ProjectileBase` 在 `FixedUpdate` 中推进虚拟圆心和旋转角，并通过 `Rigidbody.linearVelocity` 驱动投射物接近目标轨道点。这样它既不是特殊火球，也不破坏现有法术组合系统。
