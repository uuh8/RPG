# 通用状态系统设计 Spec

创建时间：2026-07-06

## 1. 背景与目标

当前项目已经有基础战斗系统、法术编程系统、投射物系统、生命值和法力值系统。下一步希望逐步构建一个 Noita-like 的元素交互世界，但完整 3D 沙盒世界过大，不适合直接开工。

因此第一阶段先做“角色身上的通用状态系统”。这个系统负责表达角色被火、水、毒、粘液等元素影响后的持续状态，例如：

```text
Burning：燃烧
Wet：潮湿
Poisoned：中毒
Sticky：粘稠
```

本系统的核心目标是：

1. 让角色身上可以同时存在多个状态。
2. 每个状态使用 `0-100` 的百分比强度表示当前状态程度。
3. 状态会随时间自然衰减。
4. 状态可以产生 gameplay 影响，例如持续扣血、降低移动速度。
5. 状态之间可以发生简单反应，例如 `Wet` 加速 `Burning` 衰减。
6. 状态可以显示在 UI 上：icon + 百分比。
7. 后续环境元素区域、元素沙盒、法术反应都可以复用这套系统。

一句话总结：

```text
Status System 是角色侧的元素承载层。
```

以后无论是火球、毒雾、水洼、粘液、可破坏元素块，都不应该各自写一套角色影响逻辑，而应该统一调用状态系统。

## 2. 已确认的设计决策

### 2.1 状态数值模型：百分比强度模型

第一版采用百分比模型：

```text
Intensity: 0-100
Intensity > 0：状态存在
Intensity <= 0：状态移除
```

例子：

```text
Burning = 80%：角色正在明显燃烧
Wet = 35%：角色有一定潮湿程度
Poisoned = 100%：角色处于满强度中毒
Sticky = 20%：角色轻微粘稠
```

选择这个模型的原因：

1. 它贴近 Noita 的“沾染程度”感觉。
2. UI 表达直观，直接显示百分比。
3. 后续环境元素很好接入，例如水区域每秒给玩家增加 `Wet +20`。
4. 状态反应好表达，例如 `Wet` 每秒额外减少 `Burning`。
5. 比“剩余秒数模型”更适合元素世界，因为元素影响通常不是开关，而是积累程度。

### 2.2 同类状态叠加规则：累加强度并 clamp 到 100

第一版同类状态采用累加：

```text
当前 Burning = 40
再次受到火焰影响 +35
结果 Burning = 75
```

超过 100 时 clamp：

```text
当前 Burning = 80
再次受到火焰影响 +50
结果 Burning = 100
```

选择这个规则的原因：

1. 直观：再次被火烧，燃烧程度就增加。
2. 适合元素积累：多次接触水、火、毒、粘液都会逐步加深状态。
3. 实现简单，便于第一版验证。
4. UI 反馈明确，玩家能看到百分比变化。

第一版不做“多个独立来源分别倒计时”。例如两个毒雾来源不会各自保存一个 timer，而是统一增加 `Poisoned` 的 Intensity。

## 3. 第一版范围

### 3.1 本次要做

第一版只做角色状态系统，包括：

1. `StatusKind`：状态类型枚举。
2. `StatusDefinition`：状态数据资产。
3. `StatusController`：挂在角色身上的状态管理组件。
4. `StatusInstance`：运行时状态实例数据。
5. `StatusEffectProcessor`：状态 tick、衰减、反应、gameplay 效果处理。
6. `StatusChangedEvent`：状态变化事件，供 UI 监听。
7. `StatusBarUI` 或类似 UI：显示玩家身上的状态 icon 和百分比。
8. 替换旧 `BurnStatus` 的职责方向：燃烧应进入通用状态系统，而不是继续作为单独组件长期扩展。

第一版状态包括：

```text
Burning
Wet
Poisoned
Sticky
```

### 3.2 本次不做

本次明确不做：

1. 不做完整 3D voxel sandbox。
2. 不做环境元素区域，例如 `WaterZone` / `FireZone` / `PoisonCloud`。
3. 不做元素方块、流体模拟、chunk、mesh rebuild。
4. 不做复杂元素反应链，例如水蒸发、油燃烧扩散、冰冻地面。
5. 不做敌人 AI 根据状态改变决策。
6. 不做抗性、免疫、状态层数、状态来源列表。
7. 不做网络同步。
8. 不做复杂 UI 动画，只做 icon + 百分比。

这些内容都是后续阶段。第一版必须控制范围，否则会变成一个过大的底层重构。

## 4. 状态规则设计

### 4.1 Burning

语义：

```text
角色正在燃烧。
```

数值：

```text
Intensity: 0-100
Natural Decay: 每秒自然下降
Damage Tick: 每隔固定时间造成一次伤害
```

效果：

1. 持续造成 Magical 或 True 类型伤害，第一版建议使用 `DamageType.Magical`。
2. 不触发受击硬直，避免角色因 DoT 每 tick 播放受击动作。
3. 可以显示 OnFire VFX。
4. 受到 `Wet` 影响时，衰减速度显著提高。

示例规则：

```text
Burning 自然每秒 -8
如果 Wet > 0，则 Burning 额外每秒 -35
Burning 每 1 秒造成一次伤害
伤害可以按 Burning 强度缩放
```

第一版建议伤害公式：

```text
DamagePerTick = BaseDamagePerTick * (BurningIntensity / 100)
```

这样 100% Burning 伤害最高，20% Burning 伤害较低。

### 4.2 Wet

语义：

```text
角色处于潮湿状态。
```

效果：

1. 自然随时间下降。
2. 加速 `Burning` 衰减。
3. 第一版不做导电、不做减速、不做冰冻联动。

示例规则：

```text
Wet 自然每秒 -10
Wet > 0 时，Burning 额外每秒 -35
```

注意：`Wet` 不一定直接移除 `Burning`，而是提高燃烧衰减速度。这样 UI 上会看到 Burning 百分比快速下降，更符合“水灭火”的直观反馈。

### 4.3 Poisoned

语义：

```text
角色中毒。
```

效果：

1. 持续造成毒性伤害。
2. 自然随时间下降。
3. 第一版不和 `Wet` / `Burning` 反应。

示例规则：

```text
Poisoned 自然每秒 -6
Poisoned 每 1 秒造成一次伤害
DamagePerTick = BaseDamagePerTick * (PoisonedIntensity / 100)
```

如果未来新增 `DamageType.Poison`，可以单独处理毒抗；但第一版不新增 DamageType，优先使用现有 `DamageType.Magical` 或 `DamageType.True`。

### 4.4 Sticky

语义：

```text
角色被粘液或胶状物影响，移动能力下降。
```

效果：

1. 降低移动速度。
2. 自然随时间下降。
3. 第一版只影响玩家移动速度；敌人移动速度接入可以作为扩展。

示例规则：

```text
Sticky 自然每秒 -8
MoveSpeedMultiplier = 1 - 0.4 * (StickyIntensity / 100)
```

也就是说：

```text
Sticky = 100% -> 移速变成 60%
Sticky = 50%  -> 移速变成 80%
Sticky = 0%   -> 移速恢复 100%
```

## 5. 架构设计

### 5.1 总体位置

状态系统应放在 `Game.Combat`，原因是：

1. 状态属于战斗规则，不属于某个具体角色。
2. 玩家和敌人都应该能拥有状态。
3. 状态需要调用 `IDamageable.ReceiveHit` 造成 DoT。
4. 状态要和 `HealthComponent`、`DamageRequest`、`DamageType` 协作。

推荐路径：

```text
Assets/_Project/Scripts/Combat/Status/
```

推荐模块关系：

```text
Game.Combat
  StatusKind
  StatusDefinition
  StatusController
  StatusInstance
  StatusChangedEvent
  StatusRuntime
```

UI 显示放在 `Game.UI`：

```text
Assets/_Project/Scripts/UI/
  PlayerStatusBar
  StatusIconView
```

跨模块通信使用 `EventBus<T>`：

```text
StatusController
-> EventBus<StatusChangedEvent>.Publish
-> PlayerStatusBar 订阅并刷新 UI
```

### 5.2 为什么不用每个状态一个 MonoBehaviour

当前项目已有 `BurnStatus : MonoBehaviour`，它能工作，但如果继续这样扩展，会变成：

```text
BurnStatus.cs
WetStatus.cs
PoisonStatus.cs
StickyStatus.cs
FrozenStatus.cs
StunnedStatus.cs
...
```

这种方式的问题：

1. 每个状态都要自己写 tick、衰减、移除、UI 通知。
2. 状态之间交互会变得混乱，例如 `WetStatus` 要找 `BurnStatus`，`BurnStatus` 也可能要找 `WetStatus`。
3. 不利于数据驱动。
4. 不利于统一 UI。
5. 后续元素世界会不断增加状态，脚本数量会膨胀。

所以第一版应把状态统一收敛到一个 `StatusController` 里，用数据驱动状态定义。

### 5.3 StatusController

`StatusController` 是挂在角色身上的核心组件。

职责：

1. 保存当前角色身上的所有状态实例。
2. 对外提供 `ApplyStatus` 接口。
3. 每帧处理状态衰减。
4. 按 tick 造成持续伤害。
5. 处理状态之间的反应。
6. 状态变化时发布事件给 UI。
7. 状态归零时移除状态。

示例接口：

```csharp
public void ApplyStatus(StatusKind kind, float amount, int sourceId, byte sourceTeam);
public bool TryGetIntensity(StatusKind kind, out float intensity);
public float GetIntensity(StatusKind kind);
public bool HasStatus(StatusKind kind);
```

`amount` 可以为正，也可以后续允许为负：

```text
ApplyStatus(Burning, +40)
ApplyStatus(Wet, +60)
ApplyStatus(Burning, -20)
```

第一版可以只对外暴露正向添加，内部衰减负责减少。

### 5.4 StatusInstance

`StatusInstance` 是运行时数据，不是 ScriptableObject。

它保存：

```text
Kind
Intensity
TickTimer
LastSourceId
LastSourceTeam
```

`LastSourceId` 和 `LastSourceTeam` 很重要，因为持续伤害需要知道伤害归属。例如毒是敌人施加的，那么 DoT 伤害也应该归属敌人；玩家用火球点燃敌人，那么 Burning DoT 伤害归属玩家。

这和现有 `BurnStatus` 的思路一致：攻击者数据按值快照保存，不回查已销毁的攻击者对象。

### 5.5 StatusDefinition

`StatusDefinition` 是 ScriptableObject，用来配置状态数据。

字段建议：

```text
StatusKind Kind
string DisplayName
Sprite Icon
float NaturalDecayPerSecond
bool DealsDamage
float DamageInterval
float BaseDamagePerTick
DamageType DamageType
bool TriggerHitReaction
bool AffectsMoveSpeed
float MaxMoveSpeedSlowRatio
GameObject VfxPrefab
```

说明：

1. `NaturalDecayPerSecond`：每秒自然下降多少百分比。
2. `DealsDamage`：是否造成持续伤害。
3. `DamageInterval`：多少秒 tick 一次伤害。
4. `BaseDamagePerTick`：100% 强度时每 tick 伤害。
5. `TriggerHitReaction`：DoT 通常为 false，不触发受击硬直。
6. `MaxMoveSpeedSlowRatio`：100% Sticky 时最大减速比例。
7. `VfxPrefab`：状态 VFX，例如 Burning 对应 OnFire。

### 5.6 StatusDatabase

为了让 `StatusController` 根据 `StatusKind` 找到 `StatusDefinition`，建议建立一个 `StatusDatabase` ScriptableObject：

```text
StatusDatabase
  StatusDefinition[] Definitions
```

运行时可通过 `StatusKind` 查对应 definition。

第一版状态数量少，用数组线性查找也可以；如果未来状态很多，再改为字典缓存。注意字典缓存应在初始化阶段创建，不要在热路径每帧分配。

## 6. 数据流

### 6.1 法术施加状态

未来火球或某个状态法术命中目标后：

```text
ProjectileBase / Fireball
-> target.GetComponent<StatusController>()
-> ApplyStatus(Burning, amount, attackerId, attackerTeam)
```

第一版可以先把当前 `Fireball` 对 `BurnStatus` 的调用替换为通用状态调用。

旧流程：

```text
Fireball.OnImpact
-> AddComponent<BurnStatus>
-> BurnStatus.Apply(...)
```

新流程：

```text
Fireball.OnImpact
-> target.StatusController.ApplyStatus(Burning, amount, attackerId, attackerTeam)
```

### 6.2 状态自然更新

每帧：

```text
StatusController.Update
-> 遍历当前 active statuses
-> 根据 NaturalDecayPerSecond 减少 Intensity
-> 根据反应规则额外修改 Intensity
-> 处理 Damage Tick
-> 处理 MoveSpeed Modifier
-> Intensity <= 0 时移除
-> 发布 StatusChangedEvent
```

### 6.3 UI 更新

状态变化时发布事件：

```text
StatusController
-> EventBus<StatusChangedEvent>
-> PlayerStatusBar
-> 刷新 icon + percentage
```

只显示玩家状态即可。敌人状态 UI 可以后续再做。

事件中应包含：

```text
TargetId
StatusKind
Intensity
IsActive
Icon
DisplayName
```

`TargetId` 应和 `HealthComponent.Id` 一致，方便 UI 过滤当前玩家。

## 7. 反应规则设计

第一版只做一条核心反应：

```text
Wet 加速 Burning 衰减
```

推荐规则：

```text
BurningDecay = Burning.NaturalDecayPerSecond
if Wet > 0:
    BurningDecay += WetExtinguishBurningPerSecond
```

这里的 `WetExtinguishBurningPerSecond` 可以先写在 `StatusController` 的配置字段中，也可以放进一个 `StatusReactionDefinition`。

第一版推荐简单实现：

```text
StatusController 里有一组 reaction tuning 字段
```

例如：

```text
WetExtinguishBurningPerSecond = 35
```

原因：当前只有一条反应，如果一开始就做完整 reaction graph，复杂度过高。

但 spec 里需要保留后续扩展方向：

```text
StatusReactionDefinition
  SourceStatus
  TargetStatus
  ReactionType
  Rate
```

以后可以把反应从代码字段迁移到数据资产。

## 8. Gameplay 效果接入

### 8.1 持续伤害

持续伤害应复用现有伤害漏斗：

```text
DamageRequest
-> IDamageable.ReceiveHit
-> HealthComponent
-> DamagePipeline
-> DamageReceivedEvent
```

这和当前 `BurnStatus` 的做法一致。

DoT 的 `DamageRequest.TriggerHitReaction` 应该为 false：

```csharp
triggerHitReaction: false
```

原因：

1. DoT 不应该每 tick 打断角色动作。
2. UI 和受击反馈仍可通过 `DamageReceivedEvent` 显示扣血。
3. 避免 Burning / Poisoned 让敌人或玩家持续硬直。

### 8.2 移动速度影响

`Sticky` 需要影响移动速度。这里有两种方案。

#### 方案 A：StatusController 提供移动倍率，角色控制器读取

接口：

```csharp
public float MoveSpeedMultiplier { get; }
```

`PlayerControllerBase` 移动时：

```text
finalMoveSpeed = baseMoveSpeed * status.MoveSpeedMultiplier
```

优点：

1. 逻辑清晰。
2. `StatusController` 不直接知道角色控制器细节。
3. 后续敌人也可以读取同一个 multiplier。

缺点：

1. 需要改角色移动代码接入 multiplier。

推荐采用此方案。

#### 方案 B：StatusController 直接改 PlayerControllerBase 字段

不推荐。

原因：

1. `Game.Combat` 不能依赖 `Game.Character`。
2. 会破坏 asmdef 单向依赖。
3. 状态系统会和玩家控制器强耦合，敌人复用困难。

## 9. UI 设计

第一版 UI 目标：

```text
玩家血条下方显示状态 icon + 百分比
```

显示规则：

1. 只显示 `Intensity > 0` 的状态。
2. 百分比向下取整或四舍五入均可，推荐四舍五入。
3. 顺序固定，避免 UI 跳动：

```text
Burning -> Wet -> Poisoned -> Sticky
```

UI 组件建议：

```text
PlayerStatusBar
  - 订阅 StatusChangedEvent
  - 维护多个 StatusIconView

StatusIconView
  - Image Icon
  - Text/TMP Percentage
```

如果当前项目 UI 主要使用 UGUI，则继续用 UGUI。不要为了状态 UI 引入新 UI 框架。

第一版可以使用固定 slot：

```text
4 个状态 = 4 个固定 icon slot
```

这样比动态创建销毁更简单，也避免运行时频繁 Instantiate UI。

## 10. 与现有 BurnStatus 的关系

当前已有：

```text
Assets/_Project/Scripts/Combat/Status/BurnStatus.cs
```

它是一个单独的燃烧 DoT 组件。第一版通用状态系统完成后，`BurnStatus` 不应继续作为主路径扩展。

迁移方向：

```text
BurnStatus 的职责
-> 合并进 StatusController 的 Burning 处理
```

旧 `BurnStatus` 可以有两种处理方式：

1. 删除或废弃，火球改为调用 `StatusController.ApplyStatus(Burning, amount, ...)`。
2. 临时保留但不再新增功能，等通用状态稳定后删除。

推荐方案：

```text
第一版实现时让 Fireball 改走 StatusController。
BurnStatus 如果没有其他引用，则移除或标记为 legacy。
```

## 11. 性能约束

状态系统会挂在很多角色身上，必须注意：

1. `Update` 热路径不要使用 LINQ。
2. 不要每帧 new 对象。
3. 不要每帧创建临时数组。
4. 状态数量固定且少，第一版可以用固定数组而不是字典。
5. UI 更新只在状态变化时触发，不要 UI 每帧主动扫描所有状态。

推荐运行时数据结构：

```text
StatusInstance[] _instances
```

数组长度可以等于 `StatusKind` 数量。用 `(int)StatusKind` 作为索引：

```text
_instances[(int)StatusKind.Burning]
```

这样好处是：

1. 无字典查找开销。
2. 无 GC。
3. 状态数量少时非常直接。
4. UI 固定顺序也容易实现。

## 14. 第一版验收标准

### 14.1 代码层

1. 玩家和敌人可以挂 `StatusController`。
2. 调用 `ApplyStatus` 可以增加对应状态强度。
3. 同类状态会累加并 clamp 到 100。
4. 状态随时间衰减。
5. `Wet` 会加速 `Burning` 衰减。
6. `Burning` 和 `Poisoned` 会造成 DoT。
7. DoT 不触发 hit reaction。
8. `Sticky` 能输出移动速度倍率。
9. 状态变化会发布事件。

### 14.2 UI 层

1. 玩家获得状态时，血条下方显示 icon。
2. icon 旁显示百分比。
3. 百分比随状态衰减变化。
4. 状态归零后 icon 消失。

### 14.3 Play Mode 层

1. 火球命中敌人或玩家后能施加 `Burning`。
2. 测试接口或临时调试入口能施加 `Wet`。
3. `Wet` 存在时，`Burning` 更快消失。
4. `Poisoned` 会持续扣血。
5. `Sticky` 会降低玩家移动速度。

## 16. 设计总结

第一版 `Status System` 不是为了“做几个 Buff”，而是为了建立未来元素世界的角色侧基础设施。

最终设计是：

```text
状态用 0-100 Intensity 表示
同类状态累加并 clamp 到 100
StatusController 统一管理状态
StatusDefinition 数据化状态参数
DoT 复用 DamageRequest / IDamageable / HealthComponent
UI 通过 EventBus 监听状态变化
Wet 与 Burning 先实现一条核心反应
```

这套设计的重点不是炫技，而是控制复杂度：先把角色状态承载层做稳，再逐步接环境元素、法术状态、元素反应和局部沙盒。
