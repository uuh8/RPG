## 1. 从玩家目标理解“只处理活跃区域”

### 1.1 我们要保护的体验

玩家可以相信此前学到的材料规则：水可以参与清洗，毒液和火可以发生反应，留下的物质可以成为稍后战斗的条件。世界规模增长时，首先应降低没有变化的部分所消耗的计算，保留物质本身和交互机会。

这并不要求所有历史物质始终保持最高精度。需要分别管理三件事：保存世界状态、推进变化、把可见状态画出来。当前粒子既承载物质又占用 GPU 槽位，因此停止求解只能减少部分工作，不能释放容量。

### 1.2 四种集合各自回答不同问题

| 集合 | 中文含义 | 是否必须每 Tick 更新 |
|---|---|---|
| 存在集合（Resident Set） | 世界仍然保存哪些物质 | 否；稳定物质可以长期保留 |
| 求解目标集合（Solver Active Set） | 这次需要更新位置、速度或状态的对象 | 是；只推进满足活动条件的部分 |
| 邻域支撑集合（Neighbor Support Set） | 求解目标周围仍会影响它的材料或边界 | 需要读取，未必需要更新 |
| 可见集合（Visible Set） | 当前相机需要显示哪些表面 | 需要绘制，未必需要重建 |

例如，新水落到稳定水池旁边，新水属于求解目标；稳定水池仍可能参与它的密度约束。若为了减少粒子数量直接把稳定邻居从查询里删掉，计算得到的密度和边界会改变。与此同时，角色踩进稳定水池仍应获得 Wet，水面也应继续显示。

“近期活跃”必须由明确的变化与依赖决定，不能只看最近几秒的位置是否变化。持续燃烧的材料即使位置不变，也可能仍在衰减或发生反应；液体上方承托物移开、邻接区发生流动，也可能让原本稳定的区域重新需要更新。

### 1.3 元胞自动机与当前 PBF 的联系和差别

元胞自动机（Cellular Automata）常以单元格或区块组织规则。可以维护发生变化的区域（Dirty Region），并将会受其影响的邻居加入后续工作。若并行或分阶段读写，还要保证每个 Tick 不会重复更新同一对象，边界事件也不能丢失。

全量扫描在小规模或高密度活动场景中仍然可以是合理实现，特别是规则简单、内存连续、并行效率高时。活动集合自身也有维护成本；本项目要验证的是在大量稳定残留的负载下，维护活动集合是否比重复全量工作更划算，不能把“只算活跃”当作任何负载下都更快的定律。

当前液体是连续位置上的基于位置流体（Position Based Fluids，PBF），邻居关系随运动而变。可以借鉴活动集合、脏区域、休眠唤醒的思想，但不能直接把“不移动像素就跳过”的判据照搬成完整的流体算法。

本计划只把这一思想用于 Norn 的设计推导。Noita 的公开介绍和 GDC 分享是方向参考，不能据此宣称已核实其当前引擎每个更新阶段的具体实现。

### 2.2 已确认机制与尚未证实的瓶颈

1. GPU 的 `SpawnParticles` 在 Free Stack 耗尽后累计丢弃数量并退出剩余生成；请求可以部分完成。
2. 远处粒子保留 Alive，仍占 GPU slot；远处新生粒子具有临时求解资格，不能误删这条 Remote Spawn 路径。
3. 存在 Awake 粒子时，多个 Solver Dispatch 覆盖完整池容量；排序阶段由容量决定。
4. 完整 Tick 后还会发布当前位置的 Spatial Hash；全部休眠不代表整条 GPU 链路没有工作。
5. 活动 Bounds 直接跟随 Transform，Bounds 改变会触发整体唤醒；站立和走动必须分别测。
6. 当前 Surface 的 Density 与 Marching Cubes 在 LateUpdate 每帧提交；只节流部分邻域外形计算并不等于缓存整张液面。
7. Gameplay 回读打包完整槽位数组，CPU 再按本次冻结的有效 Bounds 构建查询快照。
8. Exposure 的 Collider/目标缓存上限为 64；扩大单位规模时还需检测查询可能饱和。

以上可以从源码确认。各项实际 CPU/GPU 毫秒、热路径 GC、满池后的具体场景症状和优化倍率，当前均未测得。

### 2.3 现有证据和旧计划如何使用

- 7 月 CPU 路径有历史卡顿定位与 Sleep/Wake 修复记录；不能拿 262.95 ms 当作当前 GPU 的 before 值。
- 8 月 GPU 计划中的 CPU 1 ms、GPU 5/7 ms 属于当时预算，不是本机实测成绩，也不自动成为本阶段全部负载的标准。
- 8 月 25 日撤回 LOD 的计划是当前视觉基线约束。
- 9 月 2 日归档恢复计划可以作为后续历史容量阶段的设计输入。本次未发现其 Streaming 生产实现；其第一版暂停 Cold 区反应、不画 Cold 液体、不能解决 Warm 区无限生成。
- Phase A 不执行旧归档计划，也不自动继承旧计划中建议 SubAgent 的文字。

| 阶段 | 交付目标 | 进入下一阶段的依据 |

| D：局部持续累积 | 研究稳定液体的低成本表示，让附近残留不必一直占同等精细粒子数 | 同一战场持续生成、清洗可靠、体积与碰撞回归 |

### 3.1 B 阶段候选的判定表

| 若证据显示 | 优先研究 | 必须保留的正确性 |
|---|---|---|
| Awake 很少但 full-capacity 扫描/排序占比高 | 紧凑活动索引、分区候选范围、排序输入规模 | 稀疏高位 slot 不漏算；休眠邻居仍可读 |
| 移动时 Awake 激增、Sleep 收益消失 | Chunk 对齐的活动更新、进入区和扰动区局部唤醒 | AOI 边界、快速移动、远程落点、邻域缓冲带 |
| 静止时 Surface 仍占主要 GPU 时间 | 位置/材料/范围驱动的脏标记、缓存 Mesh、局部重建 | 水面不消失，边界连续；相机变化引起的范围更新有效 |
| 回读/CPU 投影占比高 | 紧凑有效样本、按区域聚合、受控更新频率 | 数据新鲜度、材料数量、发布原子性；不引入同步等待 |
| 主要是 CPU Fire/Exposure/Reaction | 活跃 Chunk 内脏 Cell、查询候选和反应工作集 | 持续反应和角色接触不因液体休眠漏掉 |

不规定“第一项一定最快”。粒子生成/消耗拓扑版本只描述 slot 的变化，不能单独作为表面缓存失效依据；粒子位置变化也会改变液面。

### 3.2 容量策略的 trade-off

- 扩大粒子池：适合作为受控对照，能测出容量与扫描、排序、内存成本的关系；只能推迟耗尽，不构成长时间残留方案。
- 远处归档：降低历史 GPU 占用；需要事务、恢复预加载和失败回滚，且无法单独解决局部满池。
- 稳定液体改变表示：有机会把物质总量与精细粒子数进一步解耦；需要新的数量守恒、碰撞、流动、表面和反应契约，开发风险最高。
- 给关键施法预留容量：改善短时可靠性；预留会耗尽，必须和持续容量管理结合。

单纯停止求解和单纯缓存液面都不会释放粒子 slot。也不能通过删除旧物质、降低材料 Amount 或减少正常法术写入来把“容量通过”伪装成优化。

## 4. Phase A 的实验与数据合同

### 4.1 两套帧率模式

1. **诊断模式**：1920×1080、VSync=0、targetFrameRate=-1，固定 Quality/URP Render Scale=1。用于观察余量、瓶颈和长帧；报告标记为 Uncapped，不能写成锁定 60 的体验。
2. **体验模式**：相同配置，VSync=0、targetFrameRate=60。用于观察 60 FPS 目标附近的帧间隔、卡顿、状态响应和长时间行为。

设置只作用于专用测试运行，保存进入前值，退出时恢复。单纯在锁帧模式看到接近 16.67 ms 不能证明 GPU 已满载；CPU/GPU 会重叠执行，不能把两者总时间直接相加。

每组基准执行 3 次独立运行，固定注入顺序、材料参数、位置、路线和相机。首次资源初始化、Shader 首次使用和导出阶段均不混入稳态窗口；首次施法成本另存证据，不隐藏。

### 4.2 时间窗口

- `Warmup`：10 s，准备本场景需要的资源；空场景可以单独记录第一次启用的成本。
- `Prefill`：每 0.1 s 一个 256 粒子的物质量等效请求，达到场景目标；最后一笔精确截取剩余数量。
- `Settle`：10 s，停写；只称为“等待稳定”，不能预先宣称全部 Sleeping。
- `Measure`：30 s；运动/持续写入/探针由场景配置决定。
- `DrainDiagnostics`：最多 5 s，不新增负载，等待一份在最后写入之后发起的有效 Pool Counter 回读与 Gameplay 发布；超时标记证据未闭合。
- `Export`：停止计时和 Recorder 后计算统计并写文件。
- 长时间场景使用 600 s Measure。暂停、窗口失焦或用户中断要记录状态；正式对照不混入暂停时间。

同一程序内跨场景残留会污染结果，第一版每组从干净的独立 Player 进程或停止后重新进入 Play 开始。不要用 Reset Pool 的临时私有入口替代正常生命周期。

| A07 | 与 A06 对应物质量，加固定 16 次 Fire 写入 | 固定时刻和位置接触毒液/粘液；测世界 Reaction、消耗与 Queue |
| A08 | 相同水池与 1 / 16 / 64 / 80 个预放置目标 | 目标都带有效 Collider/StatusController；观察 Exposure 候选、去重、可能饱和 |
| A09 | 干燥 / 空池后落水 / 饱和池后落水三组 | 单独对 Burning、Poisoned、Sticky 做成对清洗对照，见 4.4 |

液体标准目标描述的是“请求对应的粒子数”，实际存活量必须由 GPU 计数验证。选择 Amount 为每粒子单位数的整数倍，避免向上取整把负载目标改变。A06 与单液体对照按粒子数等量，报告同时保留各材料 Amount，不能把这种对照误称为玩法强度等量。

A04 的填充点远离清洗探针；A09 不允许探针预先站在 Water 中。A05 在当前版本预期会暴露失败，不预先要求基线通过。

A07 的 Fire 参数固定为每次 4096 Amount、半径 0.75 m、16 次、间隔 0.5 s，从 Measure 的第 2 s 开始；落点由 Preset 显式指定并与液体接触。这里不使用液体的“每粒子 Amount”换算。Profile 另保存 FireAmountPerWrite、FireWriteCount、FireWriteInterval 和 FireStartSeconds，冻结后写入 manifest。

### 4.4 清洗探针避免假阳性

每次干净运行只测一种负面状态。专用场景使用预放置目标，通过现有 `StatusController.ApplyStatus` 设置相同初始强度 80，随后不继续添加负面状态；避免 Burning 与 Poisoned 同时存在先触发另一种反应。

在 t=0 设置状态并记下四种强度。在 t=1 s，实验组向探针脚下提交 256 Water 粒子等效的世界写入；干燥对照不写水。使用同一目标位置、Collider、状态数据库、Reaction Profile 和采样间隔，记录 10 s 的强度曲线、世界查询水量与首次 Wet 时间。

必须同时检查：

1. 注入的是世界材料；不调用“直接给目标 Wet”作为清洗实现。
2. 液体查询首次出现 Water、目标首次 Wet，以及负面状态下降趋势分别有时间戳。
3. 与干燥对照相比，差异能支持水参与清洗；只看到负面状态下降不能排除自然衰减。
4. 另在 P7/P8 用真实水球打地面完成端到端回归，避免直接命中的 `ProjectileStatusOnImpact` 掩盖地面未生成水。
5. 当前基线原样记录饱和后的失败。未来优化验收要求在约定的有限标准压力负载下，实际生成水并恢复这条链路；不承诺有限机器支持无限局部注入。

### 4.5 数据内容与解释边界

| 数据流 | 必需字段 | 注意事项 |
|---|---|---|
| CPU 每帧 | frame、elapsed、frame interval、World/Fluid tick count、丢弃时间债务累计值、Queue depth | 固定 Tick 补算可能把负载集中到一帧 |
| GPU Pool 低频 | sample version、请求/完成时间、Alive、Free、Dropped | Alive+Free=Capacity 只在同一份有效 Pool Sample 内检查 |
| GPU Activity 低频 | 独立 version、请求/完成时间、Awake、Sleeping、Interest | 目前与 Pool 轮流回读；不能拼成同一时刻作等式 |
| Gameplay 低频 | 请求/完成/发布时间、SnapshotVersion、数据年龄、Readback errors | 数据年龄以最近成功快照的请求时间估算，不只看发布以来多久 |
| CPU 世界 | Resident/Active/Sleeping、PendingWrites、Processed/Rejected、ChangedCells、ReactionPairs | 累计 Tick 指标在实际 Tick 后累计，不每帧重复加 LastStats |
| Exposure | 候选数、唯一目标数、状态提交数、可能饱和标记 | NonAlloc 返回缓存长度只能说明“可能截断”，不能断言真实总数 |
| Rendering | 有效 Grid、Triangle 数/Overflow、Density/MC/Draw 调用次数 | GPU 输出沿用低频异步诊断；外部捕获负责 GPU 时间 |
| 端到端探针 | 请求序号、入队结果、首次材料可查、首次 Wet、各状态强度 | 全局 Dropped 不能在并发写入时直接归因到某一个请求 |

Phase A 不改 GPU 布局版本 8，不增加逐粒子全量诊断扫描。需要同一时刻的跨 Buffer 守恒证据时，在现有 GPU Test 中受控 Dispatch 后同步读取，明确这是测试专用证据。

### 4.6 帧时间、GPU 时间与采集开销

- `ProfilerRecorder` 收集 Main Thread、Render Thread、GC Allocated In Frame 等可用指标；启动时检查 Valid、UnitType 和实际名称，缺失为 Missing，不填 0。
- `FrameTimingManager` 可提供整帧 CPU/GPU timing；预分配接收数组，按 `frameStartTimestamp` 去重，结果按自身时间戳单独存储。不得把延迟返回结果硬贴到当前 C# frame。
- 自定义 `ProfilerMarker.Auto()` 围住 `ComputeShader.Dispatch` 只能说明 CPU 提交时间。
- 保留已有 Hash CommandBuffer 的 GPU Sample 标签。GPU 阶段细分由支持的 Unity GPU Profiler 或图形分析捕获提供；没有可信 GPU 阶段数据时标记 Missing，不能仅凭 CPU 标签决定哪个 Kernel 最慢。
- 每个采样窗口剔除边界不明确的延迟 GPU 样本；最后收尾阶段允许数据到达，但不会把收尾本身混入 Measure。
- 用相同空载和 4096 粒子负载比较完整采集开启/关闭的成本，保存结果。若 P95 变化超过 0.5 ms 或 CPU 主线程中位增量超过 0.2 ms，将其标记为采集扰动，优先改用短捕获或精简诊断；这些是建议的测量质量阈值，不是性能改善承诺。
- 不在测量期间排序、生成 JSON/CSV、写磁盘、截图、逐帧 Console 输出或 OnGUI。

### 4.7 产物和统计规则

输出至 `Application.persistentDataPath/ElementWorldPerformance/<runId>/`；runId 在开始前生成且目录唯一，不覆盖旧结果。

- `manifest.json`：场景、Preset、运行序号、提交标识与工作区改动说明、Unity/API/实际 GPU、分辨率/Render Scale、所有生效 Settings、诊断模式、供电模式人工记录。
- `frames.csv`：C# 侧每帧与最近诊断样本的引用版本；异步样本是否重复沿用明确标记。
- `gpu-frames.csv`：来自 FrameTiming 的独立时间戳和有效 timing。
- `events.csv`：实际提交、拒绝、排程延迟、测量窗口、探针事件、暂停/中断、错误。
- `summary.json`：有效样本量、P50/P95/P99/Max、>16.67/>33.33/>50 ms 比例、有效性、丢弃与查询延迟；缺失字段用 null 和原因。
- 手动保存的 Profiler `.data`、GPU/Frame Debugger 截图、短视频路径附在运行记录中；截图期间不参与同一次性能窗口。

统计采用 nearest-rank：排序后分位点下标为 `ceil(p * n) - 1`。只有停止测量后复制到预分配 scratch 并排序；无效样本、非有限数不进入分位统计。对 3 次运行分别报告，不能只保留最好的一次。

## 7. Task A2：构建能够重放的负载与清洗对照

手动连续点击很难保证每次位置、间隔、相机和负载数量相同。这个 Task 把实验输入变成数据驱动的序列，让两次对照只改变一个明确因素。注入仍通过世界的公开写入入口，因此保留材料路由、队列、GPU 生成和查询流程；它省去投射物动画与飞行对底层测量的干扰。专用测试中心与相机分开，使“玩家移动触发唤醒”和“相机变化影响渲染”可以分别测量。清洗探针则通过现有状态接口设置初始条件，之后完全依赖世界接触获得 Wet。固定输入不承诺 GPU 粒子逐位确定性，但足以建立相同配置、相同工作量和允许数值误差的对照。

## 8. Task A3：采集与导出可比较的报告

本 Task 把“我感觉卡了”变成一组能够比较的运行记录。采集器只保存数值和版本，测量期间不拼字符串、不落盘；阶段结束后再统计和导出。CPU 帧、GPU 延迟返回帧以及低频物质计数各有自己的时间来源，因此报告必须保留这些差别，不能把最近读到的数据伪装成同一瞬间。分位数帮助看到尾部卡顿，样本有效性则防止不支持 GPU timing 的设备输出看似漂亮的 0 ms。工具自身的内存、回读和计时成本也会作为实验的一部分比较，避免优化工作最终只是在测量采集器。

### 1. 样本和统计合同

- Capture 在开始前分配 CPU frame、GPU timing、事件数组。默认最大 frame 样本 262144，事件 16384；显式记录数组容量和估算内存。

- `PerformanceMetricSample` 为值类型，字段 `double Value`、`bool Valid`，构造函数接受相同两参数。
- `PerformancePercentiles` 为只读值类型，字段 `bool Valid`、`int ValidCount`、`double P50, P95, P99, Maximum`。

```csharp

```

过滤 Valid=false、NaN、Infinity；复制有效值到预分配 scratch，Array.Sort 只排序有效范围，按 4.7 计算。零有效样本返回 Valid=false。

## 10. 后续规模阶段的不可丢失验收要求

### 10.1 历史归档阶段

- 历史累计物质量可超过当前 GPU 池承载量；GPU Resident、CPU Archive、待处理写入分别有预算和满载策略。
- 保存确认后才释放，恢复成功且可查询后才切换权威；失败可重试，无双算、无丢失。
- Cold 区无绘制/暂停反应是旧计划边界；若可见远处残留或离屏规则是目标，必须另外补足，不能把“RAM 保存了”写成“完整世界已工作”。
- 归档/恢复不能造成大规模同帧重建或反应突发。

### 10.2 局部稳定表示阶段

- 对比保持粒子、聚合到 Cell/体积表示等候选，明确适用地形；多层地面、墙面液体、下落和狭窄通道不能被默认当成平面水池。
- Amount 守恒只是第一步，还需要合理空间占据、质量/密度、接触规则和体积表现。改变每粒子 Amount 不能独自解决 PBF 质量与重建一致性。
- 状态切换保留唯一权威，支持扰动唤醒；重建位置需要碰撞验证与受控稳定过程。
- 约定有限的压力工作负载和过载规则。无限注入不可能由有限内存无界承载；上限出现时也不能静默吞掉普通交互。

### 10.3 多活动源与离屏反应阶段

- 单位、投射物、反应前沿产生区域需求；世界统一去重推进。
- 模拟活动域、Gameplay 查询域与相机可见域分别调度；重叠区每 Tick 只推进一次。
- 不移动的 Fire 可能仍需反应；速度阈值不能替代材料生命周期判断。
- 低频/暂停会改变反应时间和因果顺序。哪些规则保持及时、哪些允许延迟必须显式定义；复杂连锁反应不能笼统用“回来补算”保证等价。

### B2 多材质 Surface 重建错峰补充
