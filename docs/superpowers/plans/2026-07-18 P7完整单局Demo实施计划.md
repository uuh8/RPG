# P7 完整单局 Demo 实施计划

> **执行方式：** 在当前任务中按 Task 顺序推进；每个 Task 都先完成代码/数据，再由开发者在 Unity Editor 中执行明确的 Gate，确认通过后才进入下一 Task。遵守学习模式，不使用 SubAgent，不自动修改用户正在编辑的 Scene YAML，不自动创建 Unity `.meta`。

**Goal：** 把当前已经能够单独验证移动、战斗、法术编程和 Water/Fire 连续元素世界的系统，组织成一局约 10～15 分钟的 Wizard 单人 Demo。玩家从 Main Menu 点击开始，进入安全起点后依次清理三个战斗区域，在区域之间至少获得一次会改变 Wand 编程选择的法术奖励，最终击败精英敌人并看到胜利结算；玩家死亡后能够进入失败结算。Pause、Restart、Return To Main Menu 和最小 Settings 共同构成完整游戏生命周期，而不是让 Demo 只能依靠 Unity Editor 的 Play/Stop 运行。

**Architecture：** 新增位于 `Game.Core / Game.Combat / Game.Skills` 之上的 `Game.Run` 模块，负责“本局状态”，但不进入具体 Player、Enemy AI 或 Rendering 内部。`Game.Run` 使用 `DeathEvent` 识别敌人与玩家死亡，用纯 C# Tracker 决定 Encounter/Run 状态，用 Scene Adapter 开关敌人和 Gate，并用 Runtime Clone 隔离本局 `SpellLibrary / WandLoadout` 与编辑资产。`Game.UI` 只读 Run Event 更新目标、奖励和 Victory/Defeat，通过 UGUI 驱动 Main Menu、Pause、Settings 与 Scene Transition；`Game.Character` 只从 Run Spell Session 读取当前 Runtime Wand。跨 Scene 的基础用户设置由 `Game.Core` 中的小型 `UserSettingsService` 保存，Character/UI 只能读取或提交设置，不把 Main Menu 逻辑塞进 Player。ElementWorld 继续是独立 Gameplay 模块，P7 只负责在 Scene 中正确装配和 Authoring，不复制 Cell/Reaction 规则。

**Tech Stack：** Unity 6.3、C#、URP 17.3、Unity Input System、UGUI、ScriptableObject、EventBus、NUnit EditMode Tests、Scene Trigger、`SceneManager.LoadSceneAsync`、Runtime ScriptableObject Clone、现有 CharacterController Enemy/Player、P6 Sparse ElementWorld。

### 1.3 三种常见方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| A. 只在 Scene 里用 Trigger 和 Inspector Event 串流程 | 最快看到画面，初学者容易开始 | 状态分散、无法纯测试、重开和漏配难 Debug | 仅用于 Task 1 灰盒，不作为最终流程逻辑。 |
| B. `Game.Run` 纯状态 + Scene Adapter + EventBus | 流程可测试；不污染 Player/Enemy；UI 只读；后续可替换房间来源 | 多一个 asmdef，需要明确初始化与事件生命周期 | **采用。** 最符合现有架构，也足够轻量。 |
| C. 直接做 Seed、Room Graph、Spawner、Loot Table | 接近完整 Roguelite，可扩展性强 | 会把 Demo 周期消耗在框架而不是一局体验 | P7-B 再做。 |

## 2. 最终运行链和模块位置

```text
P7_MainMenu Scene
  ├─ Start Game / Settings / Quit
  └─ DemoSceneTransitionController（Fade + LoadSceneAsync）
          ↓
P7_DemoRun Scene
  ├─ WizardPlayer + SpellCaster
  ├─ ElementWorldRoot + Water/Fire Presentation
  ├─ DemoRunController
  │    ├─ RunProgressTracker（纯 C#）
  │    ├─ DemoEncounterController[4]
  │    │    ├─ Entry Trigger
  │    │    ├─ Enemy Roots / HealthComponent
  │    │    └─ ArenaGate[]
  │    └─ RunSpellSession（Runtime Clone）
  └─ Demo UI
       ├─ Objective / Encounter / Reward HUD
       ├─ Wand Editor
       ├─ Pause Menu
       └─ Victory / Defeat Panel

Player 进入已 Armed 的 Encounter Trigger
  → Encounter 激活敌人并关闭 Gate
  → HealthComponent 发布 DeathEvent
  → EncounterProgressTracker 去重并统计存活敌人
  → EncounterCompletedEvent
  → DemoRunController 解锁下一区域 / Reward
  → 最终 Encounter 完成后 RunCompletedEvent
  → UI 显示 Victory
  → Restart 重新加载本 Scene，或 Return To Main Menu

任意 Running 时刻按 Pause
  → RunPauseCoordinator 记录 PauseMenu Reason
  → Time.timeScale = 0、解锁 Cursor、显示 Pause Menu
  → Resume 只释放 PauseMenu Reason；若 Wand Editor/Terminal 仍占用，不能错误恢复 Gameplay
```

程序集依赖预期如下：

```text
Game.Core
  ├─ UserSettingsService / UserSettingsChangedEvent
  ├─ Game.Combat
  │    └─ Game.Skills
  ├─ Game.ElementField
  └─ Game.Run（Core + Combat + Skills）
       ├─ Game.Character（新增对 Run 的只读 Runtime Wand 依赖）
       └─ Game.UI（新增对 Run Event / Session 的只读依赖）
```

`Game.Run` 不引用 `Game.Character` 或 `Game.UI`，因此不会形成循环依赖。它只认识 `GameObject`、`HealthComponent`、`SpellDefinition` 等低层数据。Enemy AI 仍由 `Game.Character` 自己运行；Run 只决定何时激活和何时判定清理。

Main Menu 和 Pause Menu 不拥有胜负真相。它们只调用 Scene Navigation、提交用户设置，或请求 `RunPauseCoordinator` 改变暂停原因。`RunPauseCoordinator` 统一管理 Wand Editor、Pause Menu 和 Terminal Result 三种 Pause Reason，避免多个 UI 分别执行 `Time.timeScale = 0/1` 后发生“关闭 Wand Editor 意外恢复结算画面中的 Gameplay”之类的状态覆盖。离散按钮点击和 Scene Load 允许产生少量分配；常驻 HUD 不得在 `Update()` 中用 LINQ、字符串反复拼接或场景搜索。

### 灰盒尺寸原则

- 安全起点约 `10m × 10m`。
- 普通 Arena 约 `14m～18m` 宽；最终 Arena 约 `20m × 18m`。
- Corridor 净宽至少 `4m`，Gate 净宽至少 `3m`，避免玩家和多个 Enemy 的 CharacterController 堵死。
- 全路线约 `60m～80m`，采用折返的 S 形，而不是 80m 直线；这样同样长度下 Camera 更容易隐藏后续区，ElementWorld 也能验证远近 Chunk 生命周期。

**Scene Adapter 职责：** `DemoEncounterController` 只把 Scene 对象翻译成纯 Tracker 输入：进入 Trigger 时激活预放置 Enemy、读取 `HealthComponent.Id`、关闭 Gate；收到 `DeathEvent` 时按 ID 交给 Tracker；清场后打开 Gate 并发布完成事件。它不修改 Enemy AI、不自己扣血，也不每帧扫描 `FindObjectsOfType`。

关键生命周期：

```text
Waiting（未轮到）
→ Armed（前一关已清，Entry Trigger 可响应）
→ Active（关闭 Gate、激活本区 Enemy、记录 ID）
→ Cleared（所有成员死亡、打开出口、只发布一次完成）
```

实现约束：

- `OnEnable` 订阅 `DeathEvent`，`OnDisable` 取消；Restart/换 Scene 不留 stale subscriber。
- Enemy 预放在 Scene 中但初始 inactive；激活是离散事件，允许一次性初始化，不属于 per-frame hot path。
- 不用 Enemy 名称判断死亡，使用 `HealthComponent.Id / DeathEvent.TargetId`。
- Entry Trigger 只接受 `Player` Layer；不使用 Legacy `Input`。
- Gate 只控制自己的 Collider/Visual；它不直接决定 Run 是否完成。
- Inspector 缺 Enemy、Trigger、Gate 或 Encounter 数量与 Definition 不匹配时，用 `GameLog.Warn/Error` 给出可定位信息。

## 4. 开发顺序为何不能打乱

先做 Task 1 空间灰盒，是因为错误的 Arena 尺度会让后续 Encounter 和 AI 测试失真；Task 2 先做纯流程，是为了不把“清场规则”写死在 Scene Trigger；Task 3 接真实 Enemy 后，才知道死亡与 Gate 是否闭环；Task 4 再做 Runtime Spell Session，避免奖励系统把资产污染问题带入后续；Task 5 形成完整战斗内容；Task 6 先闭合局内 HUD、Pause 与结算，Task 7 再把它包装成 Main Menu→Gameplay→Return 的应用生命周期；Task 8 把 ElementWorld 作为 Level Design 语言嵌入；Task 9 最后在真实内容与 UI 压力下做系统验收。每个 Task 都能独立定位错误，避免一次搭完整场景后面对几十个互相遮蔽的问题。
