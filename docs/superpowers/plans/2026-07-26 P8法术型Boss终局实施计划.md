# P8 法术型 Boss 终局实施计划

> **执行方式：** 本计划由主 Agent 在当前工作区按 Task 顺序实施，不使用 SubAgent。每个 Task 都以自动化测试、静态检查和开发者 Unity Editor Gate 作为进入下一 Task 的条件。用户已经明确不需要人为停留在 TDD RED 阶段，因此测试与正确实现会在同一 Task 内完成，但不会省略纯逻辑测试与回归证据。

**目标：** 在已经完结的 P7 四区连续关卡之后，增加“全法术奖励 -> Portal -> 地图二 Safe Zone -> 三阶段法术型 Boss -> Retry / Restart / Main Menu”的完整终局，让 Boss 使用人工设计的 Wand Program 和 Utility 决策验证现有法术编程、Combat 与 ElementWorld。

**Architecture：** `Game.Run` 负责跨 Scene Session、地图一 Stage Clear、Portal 进入保证与 Boss Encounter 生命周期；`Game.Character` 负责 Boss 的无分配 FSM、Utility 选招、施法和动态 Teleport；`Game.Skills` 的 `CastEvaluator` 保持不变并继续作为唯一法术解释器；`Game.UI` 负责 Portal/Boss Teleport 世界表现、Boss HUD 与结算交互；地图二使用项目内商城 Scene 副本，并复用 P6 Sparse ElementWorld。

**Tech Stack：** Unity 6.3（6000.3.16f1）、URP 17.3.0、C#、UGUI、Unity Input System、`CharacterController`、Unity Physics、`NavMesh.SamplePosition`、`ScriptableObject`、`EventBus<T>`、NUnit EditMode / PlayMode Test。

## 0. 已确认边界与不可变约束

1. 阶段命名固定为 **P8**。P3～P5 作为相对独立板块以后补，不把本阶段倒退命名为 P5。
2. P6 与 P7 已结束。P8 可以通过明确扩展缝复用其系统，但不把 P8 内容伪装成“继续补 P7”。
3. 只开发 Wizard；Warrior、Archer 不进入本阶段。
4. 地图一最终两名 Elite 死亡后，全法术 Reward 与 Portal 同时可用。
5. Reward 拾取和 Portal 进入都调用同一个幂等 `EnsureAllSpellsUnlocked`。进入 Portal 前必须拥有 `SpellLibrary.asset` 的全部 15 个 SpellDefinition。
6. 全解锁只扩充 Runtime Library，不自动重排或填满 Runtime Wand。玩家仍在 Safe Zone 主动编程。
7. Session 只在当前应用进程内存活；不写磁盘、不接 Save System。退出应用后进度消失。
8. Boss Entry Trigger 激活后永久索敌，不再使用普通 Enemy Detect/Lose Radius。
9. Boss 不主动后退；Teleport 到 Player 周围的动态安全点，绝不依赖预设 Teleport Point。
10. Phase 固定为 100%～70%、70%～35%、35%～0%。Phase Transition 约 1.2 秒、无敌、不回血，并等待当前动作结束。
11. Boss 不使用 Mana。施法压力由 Global Cast Interval、Program Cooldown、Phase 权重和 Recent-use Penalty 控制。
12. Boss Cast、Teleport、Phase Transition 由一个 Action Lock 串行化，不能相互打断或重叠。
13. Defeat 提供 `Retry Boss` 与 `Restart Run`；Victory 提供 `Restart Run` 与 `Main Menu`。
14. 地图二完整使用 Water / Fire Sparse ElementWorld。
15. Boss 第一版使用放大 Scale 的 `P7_EliteMagicEnemy`，后续替换模型不改变 AI 和数据架构。
16. 商城原 Scene 永不修改。项目只修改现有副本 `Assets/_Project/Scenes/P8_BossField.unity`。
17. 不直接编辑 `.unity` YAML；所有 Scene、Prefab、Inspector、Build Profile 操作由开发者在 Unity Editor 完成。
18. `Update` / FSM Tick / Utility Tick 中禁止 `new`、LINQ、Boxing 和 Closure；所有状态、数组、候选 Buffer 和 Recent-history Ring Buffer 在 `Awake` 初始化并复用。

## 1. 玩家运行链与权威状态

```text
P7_DemoRun 最终 Encounter 完成
  -> RunState.StageCleared
  -> AllSpellsRewardPickup 可见
  -> StageExitPortal 可见
      ├─ 拾取 Reward -> EnsureAllSpellsUnlocked()
      └─ 未拾取 -> Portal Enter 再次 EnsureAllSpellsUnlocked()
  -> Session 标记 BossField
  -> Fade / LoadSceneAsync("P8_BossField")
  -> Scene-local Player、Camera、UI、ElementWorld、Boss 初始化
  -> Safe Zone 可编辑 Runtime Wand
  -> BossEntryTrigger
       -> CaptureBossCheckpoint()
       -> BossEncounterStartedEvent
       -> Boss 永久锁定 Player
  -> Boss Death -> RunState.Completed -> Victory
  -> Player Death -> RunState.Failed -> Defeat
       ├─ Retry Boss -> 保留 Session + 恢复 Checkpoint Wand + Reload P8_BossField
       └─ Restart Run -> Clear Session + Load P7_DemoRun
```

权威边界如下：

- `RunProgressTracker` 只裁定地图一 Encounter 顺序与 `StageCleared`。
- `RunSessionCoordinator` 只保存跨 Scene 的本进程 Session：当前 Stage、Runtime Spell Session、Boss Checkpoint、下一次 Scene Entry Mode。
- `BossEncounterController` 是地图二 Boss Encounter 的 Scene Authority，只根据 Boss/Player 的 `DeathEvent` 发布最终胜负。
- `WizardBossController` 是 Boss 行为与 Phase Authority，不负责打开 UI 或加载 Scene。
- `BossHealthBarController`、Portal/Teleport VFX 只消费事件和只读组件，不反向修改 Gameplay。

## 3. Boss Wand Program 的 Authoring 边界

Boss 不把 Spell 组合硬编码进状态类。`WandLoadout` 保存程序指令序列，`BossSpellProgramDefinition` 保存 Utility 元数据，`BossDefinition.Programs` 可以引用任意数量、任意命名的 Program。具体组合、命名、数量和参数由开发者在 Unity Editor 中决定，自动化测试只锁定解释器、Utility 算法和 Runtime 生命周期，不锁定内容资产。

若开发者希望验证某一套具体 Wand 的行为，应使用 `CastEvaluator` 的 Trace/Test 检查 `EmitCommand` 数量、Trigger Payload、Modifier Snapshot 和 SpawnMode，而不是让通用 Runtime 测试依赖固定资产路径。Boss 不消耗 Mana，因此 `SpellCaster` 提供“显式 Wand + Mana Policy”的调用入口；Player 现有入口仍使用 Runtime Wand 和 Mana，不改变玩家规则。

Boss 使用独立的 Boss FSM，而不是继承 `RangedEnemyController`。普通 Ranged Enemy 的核心契约是 Detect/Lose Radius + Kite/Retreat + 受击 Hurt；P8 Boss 恰好要求永久索敌、不后退、动作不能被普通 Hurt 任意打断。强行继承会不断覆写基类私有 Update 和状态切换，风险高于少量专用状态。Boss 仍复用 `HealthComponent`、`StatusController`、`SpellCaster`、`CharacterController` 和 Combat Funnel，因此不是复制 Combat 系统。

**Task 4 锁定的数据接口与评分公式：**

```csharp
public enum BossPhase : byte { Phase1 = 1, Phase2 = 2, Phase3 = 3 }

public static BossPhase BossPhaseResolver.Resolve(
    BossPhase currentPhase,
    float healthRatio,
    float phase2Threshold,
    float phase3Threshold);

public static int BossSpellUtilityEvaluator.SelectProgram(
    BossSpellProgramDefinition[] programs,
    BossProgramRuntimeState runtimeState,
    in BossDecisionContext context,
    out float selectedScore);

public int SpellCaster.CastProgram(
    WandLoadout program,
    Vector3 spawnPos,
    Vector3 aimPoint,
    byte team,
    int attackerId,
    Collider casterCollider,
    SpellManaPolicy manaPolicy);
```

`BossDecisionContext` 是一次决策的值快照，至少保存 `Phase`、`DistanceToPlayer`、`PlayerWetIntensity`、`PlayerMoveSpeed`、`BossHealthRatio` 与 `PlayerHealthRatio`。Task 4 的纯 Evaluator 只消费前四项；HP 字段为 Task 5 接入 Controller 时保留，不能在 Evaluator 内查询 Scene、StatusController 或 Player Transform。

每个 `BossSpellProgramDefinition` 保存 `Wand`、`BaseWeight`、`PhaseMask`、三阶段倍率、`MinPreferredDistance/MaxPreferredDistance`、`DistanceFalloff`、`DistanceScoreWeight`、`Cooldown`、`RecentUsePenalty`、`PlayerWetScoreModifier`、`MovingTargetScoreModifier/Threshold` 与 `IsFallback`。评分使用可解释的加法模型：

```text
score =
    BaseWeight * PhaseMultiplier
  + DistanceScoreWeight * DistanceFit[0,1]
  + PlayerWetScoreModifier * WetRatio[0,1]
  + MovingTargetScoreModifier（达到阈值时）
  - RecentUsePenalty * RecentOccurrenceCount
```

距离位于 Preferred Range 内时 `DistanceFit = 1`；超出区间后在 `DistanceFalloff` 范围内线性降到 0。Phase 不允许或 Cooldown 未结束的 Program 在第一遍直接不可选；同分时固定选择较小数组 Index，保证相同 Context 得到确定结果。若第一遍没有候选，第二遍只在当前 Phase 可用且 `IsFallback=true` 的 Program 中评分，并允许它忽略自身 Cooldown；这条规则只防止 Boss 因所有技能冷却而永久发呆，不让普通技能绕过 Cooldown。

`BossProgramRuntimeState` 在构造时按 Program Count 与 History Capacity 一次性分配 `float[] CooldownRemaining` 和 `int[] RecentProgramIndices`。`TickCooldowns`、`MarkUsed` 与 `CountRecentUses` 都是原地循环；Decision Tick 不创建集合、不用 LINQ、不产生 closure。History 是固定长度 Ring Buffer，容量用尽后覆盖最旧记录。
