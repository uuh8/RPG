# GPU PBF 流体模拟 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:executing-plans` to implement this plan task-by-task. Every implementation step uses checkbox syntax。用户已在 2026-08-09 明确授权本轮连续执行全部 Task，并允许当前任务使用 SubAgent；该授权不延续到其他任务。

**Goal:** 用 GPU `Position Based Fluids (PBF)` 替换当前 Water Cell 的离散下落/横向转移，使水弹、预置水源与地形碰撞形成连续流动的粒子液体，再由 GPU `Density Field + Marching Cubes + Indirect Draw` 重建并绘制视频参考级别的连续表面，同时保留现有 Fire、Wet、元素写入契约和旧水回退路径。

**Architecture:** `Game.ElementField` 继续是环境 Gameplay 的所有者，并新增只负责液体粒子状态的 `GpuPbfFluidRuntime`；`ElementWorldRuntime` 仍是场景唯一 `IElementWriteSink`，只在入口处把 Water 写入路由到 PBF，把 Fire 等非液体写入留给现有 Cell World。`Game.Rendering` 只通过 `IFluidGpuSource` 读取 GPU Buffer，以 GPU Density Field、Marching Cubes 和 `Graphics.RenderPrimitivesIndirect` 生成画面；CPU Gameplay 通过低频 `AsyncGPUReadback` 得到派生的 Occupancy Snapshot，但绝不再运行第二套 Water Flow。

**Tech Stack:** Unity 6.3（6000.3.16f1）、URP 17.3、C#、HLSL、`ComputeShader`、`GraphicsBuffer`、`Graphics.RenderPrimitivesIndirect`、`AsyncGPUReadback`、NUnit EditMode/PlayMode、Unity Profiler、GPU Profiler、Frame Debugger、Windows Development Build。

## 1. 已确认范围与非目标

### 1.1 本轮玩家可见目标

1. Water Projectile 命中后不再出现按 `0.25m` Cell 跳动、横向铺格或阶梯式轮廓，而是生成具有惯性、碰撞、汇聚和飞溅的粒子水。
2. 水流撞上地面、墙体、斜面和简单容器后，由 PBF Collision Constraint 投影回可行区域，不穿过受支持的 Collider Proxy。
3. 最终画面不直接显示粒子球；粒子经 Density Kernel 形成连续 Scalar Field，再由 GPU Marching Cubes 输出封闭三角面。
4. 表面保留现有 URP Water 的 Depth、Fresnel、Foam、Triplanar Noise 与 PBR Lighting，并增加适合快速流动水团的 Anisotropic Kernel。
5. Water 仍能让角色获得 `Wet`，并能与现有 Cell Fire 发生灭火反应；允许这类 Gameplay Query 相对 GPU 位置存在一个低频 Snapshot 周期的延迟。
6. Legacy Cell Water 可通过 Profile 一键恢复，用于 Compute Shader 不支持、GPU 路径回归失败或视觉对照。

### 1.2 本轮明确不做

- Gas、Smoke、Poison Gas、Eulerian Grid、Navier-Stokes Pressure Projection 和 Volume Ray Marching。
- 水对角色、敌人或 Rigidbody 的双向力学反馈；本轮 Collider 只单向影响液体。
- Arbitrary Mesh Collider 的实时 GPU Voxelization；首版使用显式 `FluidColliderAuthoring` 的 Box/Sphere/Capsule Proxy。
- 多种液体同时接触时的互溶、分层、表面张力边界或化学反应。
- 网络同步、Replay Determinism、Save/Load 粒子状态和跨 Scene 持久化。
- 移动平台高速连续碰撞、复杂破碎容器和 GPU Mesh Shader。
- 在本轮顺带启用 URP Render Graph。当前项目 `m_EnableRenderGraph=0`，首版使用 Unity 6 公共 `Graphics.RenderPrimitivesIndirect`，避免把渲染管线迁移混入流体 Debug。

## 2. 当前根因与迁移边界

当前项目并不是“只会画方块水”。已有链路是：

```text
ElementWorldSimulator 中的 Water Cell / byte Amount
-> WorldWaterVisualDensityFilter
-> Rounded Primitive / Signed Distance
-> CPU Surface Nets
-> Unity Mesh Upload
-> ElementWater.shader
```

`WorldWaterVisualDensityFilter + Signed Distance + Surface Nets` 已经把 Cell 表现为连续 Mesh，但输入状态仍由 `ElementWorldSimulator` 每 10Hz 在 Global Cell 间做 Down Flow 和 Horizontal Flow。因此玩家看到的运动路径、最小水量单元、碰撞边界与传播速度仍然被 Cell 网格决定；继续调 `Smooth Union` 或 Shader Normal 只能柔化外观，不能获得真实的惯性、飞溅或连续轨迹。

迁移后链路是：

```text
ElementWriteRequest(Water)
-> GpuPbfFluidRuntime Spawn Queue
-> Predict Position
-> Spatial Hash + Bitonic Sort
-> Density / Lambda / Position Correction × SolverIterations
-> Collision Projection
-> Velocity / XSPH / Commit
-> GPU Particle Buffer（Water 唯一 Simulation Truth）
   ├-> Density Field -> Marching Cubes -> Indirect Draw
   └-> 低频 AsyncGPUReadback -> Gameplay Occupancy -> Wet / Fire Reaction
```

必须保留的现有边界：

- `ElementDepositOnImpact` 与 `ElementWorldInitialDeposit` 继续只创建 `ElementWriteRequest`，不认识粒子、GPU Buffer 或 Renderer。
- `ElementRuntimeRegistry` 继续只保存一个 `IElementWriteSink`。
- Fire Cell、Fire Decay、Persistent Fire Source 与 Fire Renderer 继续使用现有 CPU ElementWorld。
- `ElementWorldWaterRenderer` 和 CPU Surface Nets 继续服务 `LegacyCell` 模式。
- `Game.Rendering` 只能绑定 `IFluidGpuSource` 暴露的只读 Buffer，不得调用 Spawn、Consume 或修改粒子。

## 3. 方案研究与选择

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| CPU Jobs/Burst PBF + CPU Marching Cubes | 与参考视频实现接近，逐步调试直观，适合 2K 级演示 | CPU 邻居搜索、Constraint Iteration、Meshing 和 Mesh Upload 会共同占用主线程/Worker；扩展多液体后预算风险高 | 只作为数学与视觉参考，不作为本项目生产链 |
| GPU PBF + CPU Surface Nets/Marching Cubes | 可复用当前 CPU Mesher | 每帧必须把大量粒子或 Density Field 从 GPU 拉回 CPU，再上传 Mesh；同步与带宽抵消 GPU Solver 优势 | 拒绝 |
| GPU PBF + GPU Density + GPU Marching Cubes + Indirect Draw | 粒子、密度、三角面都留在 GPU；CPU 只提交参数；适合后续多液体 Profile | Buffer 生命周期、Shader Debug、GPU Overflow 和 Gameplay Query 更复杂 | **采用** |

主要参考：

- [Position Based Fluids 论文](https://matthias-research.github.io/pages/publications/pbf_sig_preprint.pdf)：Density Constraint、Lambda、Position Correction、Artificial Pressure 和 Vorticity/XSPH 的数学来源。
- [Reconstructing Surfaces of Particle-Based Fluids Using Anisotropic Kernels](https://faculty.cc.gatech.edu/~turk/my_papers/sph_surfaces.pdf)：粒子邻域协方差、方向拉伸与连续表面重建。
- [lamp-cap/Unity_Slime](https://github.com/lamp-cap/Unity_Slime)：用户提供视频的源码入口，验证 CPU PBF、Anisotropic Kernel、Density Grid 与 Marching Cubes 能得到目标外观。
- [Scrawk/PBD-Fluid-in-Unity](https://github.com/Scrawk/PBD-Fluid-in-Unity)：GPU PBD/PBF、Grid Hash 与 Bitonic Sort 的工程参考。只参考算法分层，不直接复制实现。
- [Unity Graphics.RenderPrimitivesIndirect](https://docs.unity3d.com/ja/current/ScriptReference/Graphics.RenderPrimitivesIndirect.html)：通过 GPU `IndirectDrawArgs` 决定顶点数，并用 `RenderParams.worldBounds` 做整批 Culling/Sorting。
- [Unity AsyncGPUReadback.RequestIntoNativeArray](https://docs.unity3d.com/cn/current/ScriptReference/Rendering.AsyncGPUReadback.RequestIntoNativeArray.html)：把 GPU Gameplay Snapshot 写入长期 `NativeArray`，避免阻塞主线程。

## 4. Assembly、状态所有权与数据流

### 4.1 Assembly 位置

```text
Game.Core
├── Game.Combat
├── Game.ElementField
│   ├── Legacy Cell Water / Fire
│   ├── GPU PBF Liquid Simulation
│   └── Gameplay Occupancy / Reaction Bridge
└── Game.Rendering
    ├── Legacy CPU Surface Nets Water Renderer
    └── GPU Density / Marching Cubes / Indirect Liquid Renderer
```

不新增 `Game.Fluid` 的原因：液体沉积、Wet 和灭火都已经属于 `Game.ElementField` 的环境 Gameplay。如果立即拆新 Assembly，`Game.ElementField` 仍必须依赖它，而 Renderer 也要同时依赖两者；在只有 Water 一个可玩材质时只会增加边界与序列化成本。代码先按 `Scripts/ElementField/Fluid/` 文件夹隔离，等多液体、Gas 或独立流体玩法真正形成第二个 Domain 后再评估 asmdef。

### 4.2 三种“状态”必须区分

1. **Resident Particle**：粒子仍占用固定 GPU Pool Slot，位置和材质数据存在。
2. **Interest Active**：粒子落在玩家附近的活动 Bounds 中，允许被模拟和表面重建。
3. **Requires Simulation**：粒子或其邻域当前真的需要执行 PBF；稳定粒子可以 Resident 且可见，但 Solver-Sleeping。

这延续现有 ElementWorld 的经验：Gameplay 数据是否存在、玩家是否在附近、Solver 是否必须工作是三个不同问题。不得因为粒子休眠就把它从 Renderer/Occupancy 中删除，也不得因为粒子 Resident 就强迫它永远参与所有 Constraint Pass。

### 4.3 CPU/GPU 真相边界

| 数据 | Owner | 写入者 | 读取者 |
|---|---|---|---|
| Particle Position/Velocity/Alive/MaterialId | `GpuPbfFluidRuntime` GPU Buffer | PBF Compute Kernel | PBF、Surface Renderer、Readback Bridge |
| Spatial Hash/Cell Range | `GpuPbfFluidRuntime` GPU Buffer | Spatial Hash Compute | PBF Neighbor Query、Density Field |
| Surface Density/Anisotropy/Triangles | `Game.Rendering` GPU Resource | Rendering Compute | Procedural Liquid Shader |
| Liquid Gameplay Occupancy | `FluidGameplayOccupancyBridge` CPU Snapshot | Async Readback 完成后的 Binning | Exposure、Reaction |
| Fire Cell/Amount | `ElementWorldRuntime` | 现有 Write/Decay + Reaction Delta | Fire Renderer、Exposure、Reaction |

## 6. 核心数据布局与数学约定

### 6.1 GPU Particle 使用 SoA

采用 `Structure of Arrays (SoA)`，而不是把所有字段塞进一个大 Struct：

```hlsl
RWStructuredBuffer<float4> _Positions;          // xyz=当前世界坐标，w=1 active / 0 free
RWStructuredBuffer<float4> _PredictedPositions; // xyz=Constraint 输入，w 保留 active
RWStructuredBuffer<float4> _Velocities;         // xyz=速度，w 不承载整数语义
RWStructuredBuffer<float2> _DensityLambda;      // x=density，y=lambda
RWStructuredBuffer<uint2>  _ParticleMetadata;   // x=MaterialId，y=Activity/Generation Flags
RWStructuredBuffer<uint2>  _SpatialEntries;     // x=hash bucket，y=particle index
RWStructuredBuffer<uint2>  _CellRanges;         // x=start inclusive，y=end exclusive
```

原因：不同 Kernel 只读写自己需要的 Buffer，降低带宽和误写；`MaterialId` 保持整数，不塞进 float 的小数位；C#/HLSL Stride 易于 Contract Test。所有 Buffer 长度固定为初始化 Capacity；空 Slot 使用 `active=0` 和 `hash=0xffffffff`。

### 6.2 Spatial Hash

1. 用 `cell=floor(position/smoothingRadius)` 得到整数邻域坐标。
2. 对 `int3 cell` 做稳定 32-bit Hash，再 `% hashTableCapacity` 得到 Bucket。
3. `SpatialEntries=(bucket, particleIndex)`，Inactive Entry 使用最大 `uint`。
4. 对固定 Power-of-two Capacity 做 Bitonic Sort，比较顺序为 Bucket→ParticleIndex。
5. 相邻排序 Entry 的 Bucket 发生变化时写入 `_CellRanges[bucket]`。
6. 查询 27 个相邻 Cell 时先定位 Bucket Range，再重新计算候选粒子的真实 `int3 cell`，过滤 Hash Collision。

Bitonic Sort 并非理论上最快，但实现、验证和固定容量行为更清晰；只有 Profiler 证明它成为瓶颈后，才单独规划 Radix Sort，不能在首版同时承担两套排序实现。

### 6.3 PBF Substep

```text
Apply Spawn/Consume Commands
-> External Force + Predict
-> Build/Sort Spatial Hash
-> for SolverIterations:
     Density + Lambda
     Delta Position + Artificial Pressure
     Apply Delta
     Collision Projection
-> Velocity = (Predicted - Previous) / dt
-> XSPH Viscosity + optional Vorticity Confinement
-> Commit Position
```

核心约束：

```text
C_i = density_i / restDensity - 1
lambda_i = -C_i / (sum_j |gradient C_ij|² + epsilon)
deltaP_i = (1 / restDensity) * sum_j (lambda_i + lambda_j + s_corr) * gradient W_spiky
```

- `epsilon` 防止邻居太少时除零。
- `s_corr` 是 Artificial Pressure，用于抑制粒子结团和表面空洞，不是额外重力。
- Position Correction 必须先写 `_DeltaPositions`，再统一 Apply；禁止同一个 Kernel 一边读邻居旧位置一边直接改当前位置，否则结果依赖 GPU Thread 调度顺序。
- PBF 每个 Substep 只 Build 一次 Spatial Hash；Position Correction 应小于 Smoothing Radius 的安全比例，越界由 Profile Clamp 和稳定性测试约束。

### 6.4 Surface Reconstruction

1. Active Interest Bounds 映射为固定 3D Lattice。
2. 每个 Voxel Thread 查询其 27 个 Spatial Hash 邻域，累加 Particle Kernel 得到 Scalar Density。
3. Isotropic 阶段使用球形 Kernel；Anisotropic 阶段用每粒子的 Covariance/Eigenvalue 生成方向缩放矩阵。
4. 每个 Marching Cubes Cell 读取 8 个 Corner Density，组成 8-bit Case Index。
5. 对 Lookup Table 指定的 Edge 做线性插值：`t=(iso-d0)/(d1-d0)`。
6. Normal 使用 Density Central Difference；高密度是内部，因此 Outward Normal 为 `-normalize(gradient)`。
7. 每个 GPU Thread 通过独立 Atomic Triangle Counter 一次保留一个 Triangle Slot，再连续写三个 Vertex，避免三个独立 Append 被其他 Thread 交错。
8. `BuildIndirectArgs` 写入 `vertexCountPerInstance=min(triangleCount,maxTriangles)*3`、`instanceCount=1`。

### 6.5 Gameplay Occupancy

- Readback 周期与当前 Exposure 默认周期对齐为 `0.25s`。
- 使用两个长期 `NativeArray<float4>`：一个正在由 GPU 写，一个可被 CPU Binning；请求完成前不得 Dispose 或复用目标数组。
- CPU 遍历 Active Particle，按现有 `ElementWorldCoordinates.WorldToGlobalCell` 写入固定 Dense Active-Region byte Grid。
- `amount = min(255, particleCountInCell * amountUnitsPerParticle)`。
- Occupancy 不参与 PBF，不写回 Water Cell，不触发 Legacy Flow。
- 同一时刻最多允许一个 Outstanding Readback；错误请求保留上一份有效 Snapshot，并通过 `GameLog.Warn` 限频报告。

## 9. 常见失败症状与固定排查顺序

### 9.1 粒子已经存在，但完全没有水面

1. Debug Particle Renderer 是否可见；不可见先查 Spawn/Alive/Bounds。
2. Density Slice 中心是否大于 Iso Level；全黑查 Spatial Hash/World-to-Grid。
3. Triangle Counter 是否为 0；为 0 查 MC Case/Table/Iso。
4. Triangle Count 非 0但不显示，查 Indirect Args、Shader Buffer、`worldBounds`、Cull/Winding。
5. 从下方可见而上方不可见，优先查 Gradient Normal 与 Triangle Winding，不要先改 Alpha。

### 9.2 水像爆炸或粒子飞走

1. 检查 `dt` 是否使用 Substep Delta，而不是整 Tick Delta。
2. 检查 Lambda Epsilon、Rest Density、Particle Mass 与 Smoothing Radius 单位。
3. 检查 Delta Position 是否两阶段写入以及 Max Correction Counter。
4. 检查 Collider 内部粒子退出方向是否反向。
5. 降低 dt/增加 Substep 做 A/B；不能先用 MaxSpeed 暴力掩盖根因。

### 9.3 画面流畅，但 Wet/灭火延迟或错误

1. 查看 Readback Outstanding、Age、Error Counter。
2. 检查 Snapshot Active Bounds 与 ElementWorld Global Cell Origin。
3. 检查 Exposure Interval 是否与 Snapshot 周期叠加成双重延迟。
4. 检查同一 Snapshot Version 是否重复运行 Reaction。
5. 视觉正确不能证明 CPU Occupancy 正确；必须单独看 Snapshot Debug。

### 9.4 连续施法后逐渐卡顿

1. 分开查看 Particle Capacity、RequiresSimulation Count、Surface Grid 和 Triangle Count。
2. CPU 看 `GpuFluid.*` Submission、Readback Callback/Binning 与 GC。
3. GPU 看 Spatial Sort、PBF Iterations、Density、Anisotropy、Marching Cubes。
4. 先确认是 Simulation 还是 Surface，不根据“看不到水”猜 Renderer。
5. 检查 Stable Particle 是否进入 Solver-Sleeping，以及 Spawn/Collider 是否造成 Wake Storm。
