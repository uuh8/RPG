# P8 元素世界跨场景一致性与 Compute Shader 警告修复计划

> 状态：已确认并执行中  
> 范围：P7 / P8 元素世界契约、P8 Status UI 接线、GPU PBF / Marching Cubes 数值警告  
> 不包含：修改元素反应数值、重做流体美术、引入新的 LOD 或跨场景持久化同一份粒子 Buffer

## 1. 问题与目标

P7 已经是当前生产版 ElementWorld，而 P8 曾由较早场景配置演进而来。两张地图虽然使用同一套玩法规则资产，但 Scene 内的可变 Runtime、GPU Renderer、Terrain Collision Proxy 和 UI 引用必须分别完整接线。本轮审计发现 P8 的 Sticky 状态视图错误复用了 Wet 的 `Image` 与 `Text`，所以两个状态会争写同一个 Presentation 对象；同时 D3D Shader compiler 对 `isnan/isinf`、未显式限定定义域的分数次幂以及 `uint/int` 比较发出警告。

目标是让 P7/P8 共享相同的材料与反应规则，同时各自拥有完整、独立的 Scene Runtime；让四个状态槽各自拥有 UI 子对象；并用数学等价且跨 Graphics API 更明确的 HLSL 写法消除警告，不改变粒子模拟和表面重建的设计结果。

## 2. 架构方案与取舍

- 共享 `MaterialCatalog`、Simulation Routing、Status Projection、Reaction Profile 与 Reaction Bindings。这些是只读规则，跨场景复制会产生配置漂移。
- 每张 Scene 独立持有 `ElementWorldRuntime`、GPU Buffer、Readback、Liquid Renderer、Fire Renderer 和地形碰撞代理。这些是可变运行状态，共用会把上一关粒子与生命周期泄漏到下一关。
- P8 修复工具继续通过 `SerializedObject` 修复 Scene 引用；UI 组件只按完整类型名定位，不让一次性 Editor 数据迁移工具扩大对 `Game.UI` Runtime Assembly 的编译依赖。
- 有限值检查改用 `asuint` 检查 IEEE 754 exponent；固定整数幂展开为乘法；分数幂先限定非负/正数域，再使用 `log2/exp2`。这保留数学目的，并避免 D3D fast-math 对通用内建函数的保守诊断。

## 4. 验证与回滚

自动验证：相关 C# Assembly 必须 0 Warning / 0 Error；源码扫描不得再出现目标 `isnan/isinf/pow` 写法；Scene Contract 必须证明四个状态槽拥有四组不同的 `Image/Text`；`git diff --check` 必须通过。

Editor 验证：等待 Shader 重新 Import 后确认 Console 不再出现本轮数值警告；分别从 P7 直接运行以及 P7 Portal 进入 P8，验证 Water、Poison、Sticky、Fire 的生成、反应、状态 Icon 与百分比；最后用 Profiler 确认本轮仅改变 Shader 数学表达，没有新增 CPU hot-path `GC Alloc`。

若 Shader 表现异常，可按单个 `.compute` 文件回退对应数学替换；若 P8 UI 异常，只需恢复 StickySlot 两个序列化引用。不得回退整张 P8 Scene，因为其中包含开发者其他尚未提交的场景修改。
