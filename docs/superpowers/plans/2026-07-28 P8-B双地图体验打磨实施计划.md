### 0.3 七项需求审计后的关键纠错

1. **失败页不是 Runtime 方法语义错误。** `DemoPauseMenuController.RetryBoss()` 会恢复 Boss Checkpoint 并重载 P8；`RestartRun()` 会结束 Session 并加载 P7；`ReturnToMainMenu()` 会结束 Session 并加载 Main Menu。现有 PlayMode Test 已证明这三条 API 语义。真实缺陷在 `P8_BossField.unity`：DefeatPanel 当前缺少指向 `RetryBoss()` 的按钮绑定。因此不能只改“重新开始”的文字，必须修 Scene 绑定并增加 Scene Authoring Test。
2. **法术槽不是逐帧重建。** `SpellPaletteView` 只在打开/重建时实例化槽位，`WandFrameView` 只在离散编辑时改数组。本轮应防止新增 Tooltip 在 `Update` 或 Pointer Move 中重复格式化文本，而不是误诊现有列表为 hot-path allocation。
3. **项目没有 BGM 管理基础设施。** 当前没有 `AudioManager`、Music Service 或 `AudioMixer`；总音量通过 `UserSettingsService -> AudioListener.volume` 生效。两张地图各一首 BGM 时，优先使用 Scene-local Controller，避免为了两个 Clip 过早引入 `DontDestroyOnLoad` 音乐服务。
4. **Wizard 当前没有空中 Dash 入口。** `PlayerDashState` 可在结束时回到 Airborne，但只有 Grounded 会进入 Dash。Wizard Animator 只有当前地面 `DashForward_MagicWand` 明确被代码使用；不能把疑似未使用的重复 State 当作空中冲刺，必须由开发者提供并确认 Air Dash Clip。
5. **Boss Phase 事件在过渡完成时发布。** 当前 `BossPhaseChangedEvent` 适合切换“整阶段持续 Loop VFX”；如果用户提供的是 1.2 秒 Phase Transition One-shot，现有事件时机太晚，需要另加“过渡开始”事件。资源语义必须先确认。

## 2. 总体 Architecture 与 Assembly 责任

```text
Game.Skills
  SpellDefinition：法术权威数据（描述、元素 + 已有行为字段）
        |
        v
Game.UI
  SpellTooltipPresenter：只读展示、缓存格式化、屏幕边界夹取
  GameplayGuideController：首次显示/手动重开、Pause Reason 所有权
  SceneMusicController：Scene-local BGM
  BossPhaseVfxController：消费 Boss/Run Event，切换表现
  DemoPauseMenuController：已有 Retry/Restart/Main Menu 命令
        |
        v
Game.Run
  RunSessionCoordinator：只保存“本 Run 是否已展示玩法说明”
  RunPauseCoordinator：组合 Wand、Pause Menu、Guide、Transition 等暂停原因

Game.Character
  PlayerControllerBase：共享 Jump/Dash Budget 与调参
  PlayerAirborneState：空中 Jump/Dash 转移
  PlayerDashState：按地面/空中来源使用不同动画与垂直速度策略
  Wizard Prefab：MaxJumpCount=2、MaxAirDashes=1、AirDash State Name
```

边界原则：

- `Game.Skills` 不引用 UI，只提供 Authoring Data；
- `Game.UI` 可以读取 `Game.Skills`、`Game.Run`、`Game.Combat`，但不裁定伤害、Boss Phase 或 Jump Budget；
- Boss Gameplay 只发布事实 Event，不直接引用 Phase VFX；
- 通用移动规则放在 `Game.Character` 基类，Wizard 只通过 Prefab 参数获得二段跳/空中冲刺；Warrior、Archer 默认值保持原行为；
- 所有新 Event 必须是 `struct + IGameEvent`，跨模块只走 `EventBus<T>`；
- `Update`、FSM Tick、Pointer Move 等 hot path 禁止 `new`、LINQ、Boxing、Closure 和字符串拼接。

## 4. 实施顺序与依赖理由

```text
Task 0 基线与资源 Gate
  -> Task 1 CastEvaluator DrawAction
  -> Task 2 法术信息数据 + Tooltip
  -> Task 3 Defeat 三按钮语义
  -> Task 4 Boss Phase VFX
  -> Task 5 双地图 BGM
  -> Task 6 首次玩法说明
  -> Task 7 二段跳
  -> Task 8 Air Dash
  -> 最终双地图回归与工程证据
```

排序理由：

1. Tooltip 与 Defeat 页是低风险、高可见度 UI 修正，能先建立 P8-B 的测试和 Scene Authoring 模式；
2. Boss Phase VFX 与 BGM 依赖用户资源，应在资源确认后尽早接入，避免最后才发现 Prefab 语义或 Clip Import 不合适；
3. 教程要展示最终按键与移动能力，因此在文案层面依赖 Double Jump / Air Dash 设计；实现顺序放在移动前，可先搭建数据与 UI，Task 6 完成后再做最终文案校对；
4. Double Jump / Air Dash 改动共享 FSM、Input Buffer、Animator 和 Boss 战平衡，是风险最高的功能，放在已有 UI/Presentation 改动稳定后单独验证；
5. 最终 Test Runner、Build、Profiler 必须覆盖所有改动，只做一次终局 Gate。

## 6. Task 1：法术元素、描述与零 hot-path 分配 Tooltip

### 6.1 玩家可见结果

鼠标悬停 Palette 或 Wand Frame 中任意 SpellSlot 时，出现一个不会超出 Canvas 的 Tooltip，展示：

- Icon；
- Display Name；
- `SpellKind`；

## 8. Task 3：三阶段 Boss VFX

### 8.1 推荐方案：整阶段 Loop VFX

若用户提供的三个 Prefab 是 Loop：

```text

  -> Phase 1 VFX active

BossPhaseChangedEvent(CurrentPhase=2)
  -> Phase 1 inactive
  -> Phase 2 active

BossPhaseChangedEvent(CurrentPhase=3)
```

## 11. Task 6：Wizard 二段跳与每次滞空一次 Air Dash

### 11.1 为什么放在共享 Base，而不是写死 Wizard State

Double Jump 与 Air Dash 都是“移动预算”，不是 Wizard Spell。共享基类负责预算与状态转移，Prefab 数据决定每个角色有几次：

- Warrior / Archer：`MaxJumpCount = 1`、`MaxAirDashes = 0`，行为不变；
- Wizard：`MaxJumpCount = 2`、`MaxAirDashes = 1`。

这样未来给 Archer 增加一次 Air Dash 只需改数据，不复制 FSM；同时没有用泛型或角色类型判断污染共享 State。

### 11.2 Jump Budget 语义

推荐规则：

1. Grounded Enter 重置 Jump Budget；
2. 地面 Jump 消耗第 1 次；
3. Coyote Jump 也消耗第 1 次；
4. 玩家直接走下平台时，Coyote Time 内仍保留地面 Jump；
5. Coyote Time 过期后视为地面机会已消耗，因此 Wizard 只剩 1 次 Air Jump；
6. Air Jump 消耗剩余次数；
7. Dash/Attack 不可被 Jump 打断，但未过期的 Jump Buffer 可在回到 Grounded/Airborne 后继续消费；
8. 只有可靠 Landing 才重置，不根据空中偶发 GroundChecker 命中反复刷新。

这避免“走下平台后还能在空中连跳两次”，导致实际变成三段位移。

第二跳使用独立 `_airJumpForce`，第一版数值与 `_jumpForce` 相同。独立字段的价值是允许后续调成 80% 或 110%，而不改变第一次起跳手感。

### 11.3 Air Dash 语义

推荐规则：

- Airborne 检查到 Dash Buffer、Cooldown <= 0 且本次滞空仍有 Air Dash Budget 时进入；
- 每次滞空最多一次，Landing 重置；
- 地面 Dash 与 Air Dash 共用 Dash Cooldown、Speed、Duration；
- 使用独立 `_airDashStateName` 与预计算 Hash；
- 进入 Air Dash 时 `VerticalVelocity = 0`，Dash 期间暂停 Gravity，退出后 Airborne 恢复 Gravity；
- Dash 不可被 Attack/Jump 打断；
- Dash 结束时依据 GroundChecker 回到 Grounded 或 Airborne；
- 当前地面 `DashForward_MagicWand` 保持不变。

### 11.4 状态优先级

Airborne 的建议优先级：

```text
Air Dash
-> Coyote Jump / Air Jump
-> Character-specific Air Attack
-> Landing
-> 普通移动与 Gravity
```

实际代码要避免“一帧既消费 Dash Buffer 又消费 Jump Buffer”。进入新 State 后立即返回，不继续执行旧 State 的剩余逻辑。

## 13. Debug 路线与回滚边界

### Tooltip 出界或有 GC

1. 先确认 Canvas Render Mode、Scale Factor、Tooltip Pivot；

5. 回滚边界：可独立禁用 Tooltip Presenter，不影响 Wand Edit Ops。

### Defeat 按钮错误

1. 检查 Button Persistent Call 的 Target 与 Method；
2. 检查 Label，不以 Label 猜方法；
3. 检查 Session `EntryMode/Stage/Checkpoint`；
4. 检查是否同帧重复 Transition；
5. 回滚边界：只回滚 Scene Authoring，不动已验证 Session API。

2. 确认 Loop/One-shot 语义和事件时机；
3. 检查挂点 Scale、Particle Simulation Space、Bounds/Culling；
4. 检查 Boss Teleport 前后 World/Local Position；
5. 回滚边界：禁用纯表现 Controller 不影响 Boss FSM。

### BGM 叠音

1. Hierarchy 搜索所有 AudioSource；
2. 检查 Scene-local Controller 是否误加 DDOL；
3. Retry 前后记录 Instance ID；
4. 检查第三方 VFX AudioSource，避免把 SFX 误判为 BGM；

4. 检查 Cursor Owner；
5. 回滚边界：关闭自动首次显示，仍保留 Pause Menu 手动入口。

### Double Jump / Air Dash 异常

1. 先记录 JumpCount、CoyoteCounter、JumpBuffer、AirDashCount、DashCooldown；

### 15.1 CastEvaluator 新语义

`FindActionEnd` 以 `Draw Budget = 1` 解析一个 Action：`Modifier` 不消耗 Draw，`Multicast` 增加预算，普通 Emit 消耗一份预算；遇到 Trigger Emit 时，它在外层只消耗一份 Draw，但递归越过其自身 Payload Action。这样：

```text
Triple
Trigger -> Meteor
Trigger -> Meteor
Trigger -> Meteor
```

会生成三个并行 Trigger，而不再让第一个 Trigger 吞掉整个 Wand Suffix。反过来：

```text
Orbit
Trigger -> Triple + Fireball + Fireball + Fireball
```

Trigger 捕获的仍是一个完整 Action，其中内部 Multicast 决定 Payload 有三个 Emit。保护边界为 `MaxActionDepth = 16`、每层 `MaxEmitCommands = 64`，并继续依赖“Payload 是严格更短切片”的收敛不变量。

### 15.4 2026-07-29 Standalone Build：Gameplay Guide Cursor 竞态修复

开发者在 Windows Development Build 发现：Main Menu 中 Cursor 可见，但进入 P7 后 Gameplay Guide 虽已打开，Cursor 却不可见，因而无法点击“下一页”。源码反向追踪得到：

```text
DemoMainMenuController.Start
  -> Cursor None + Visible
Scene Transition
  -> PrepareForSceneTransition 继续保持 None + Visible
P7 GameplayGuideController.Start
  -> RequestPause(GameplayGuide)
  -> TimeScale=0，Cursor None + Visible
P7 PlayerControllerBase.Start
  -> 无条件 Cursor Locked
  -> Guide 仍处于 Pause，但 Cursor 被另一个所有者覆盖
```

Unity 只保证所有启用对象的 `Awake` 在首次 `Start` 之前完成，并不保证两个不同 `MonoBehaviour.Start()` 之间的相对顺序。Editor 与 Standalone Build 的对象初始化、加载耗时或内部排序差异，使这个潜伏的全局状态竞态在 Build 中稳定暴露。

最终修复不是设置 Script Execution Order，也不是让 Guide 在 `Update` 中每帧重复显示 Cursor，而是建立单一所有权：

- `RunPauseCoordinator.Awake()` 初始化 Gameplay 的 `Locked + Hidden`；
- 任意 `RunPauseReason` 首次申请时统一变成 `None + Visible`；
- 最后一个 Reason 释放时统一恢复 `Locked + Hidden`；
- `PlayerControllerBase.Start()` 不再写 Cursor，只初始化角色朝向与 FSM。

新增 `RunPauseCoordinatorTests` 覆盖 Gameplay 初始化与 Guide Pause/Release 的 Cursor 状态。2026-07-29 已重新静态编译 `Game.Run.Tests`、`Game.Character.Tests`、`Game.UI`、`Game.Run.PlayMode.Tests`，均为 0 Warning / 0 Error。由于项目正被开发者的 Unity Editor 实例占用，第二个 BatchMode Editor 无法执行 Unity Test Runner，因此不能把静态编译写成测试通过；真实 EditMode Test 与修复后的 Standalone Build 路径仍由开发者完成。
