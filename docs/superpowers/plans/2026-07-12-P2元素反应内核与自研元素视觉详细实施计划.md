# P2 元素反应内核与自研元素视觉详细实施计划

> **执行规则：** REQUIRED SUB-SKILL：实施时使用 `superpowers:executing-plans`，按本计划逐项执行并在每个 Unity Editor Gate 停下等待用户验证。未经用户对当前任务明确授权，禁止使用 SubAgent；不创建 worktree，不手写 `.meta`，不提前进入下一阶段。

**Goal：** 在现有 Burning、Wet、Poisoned、Sticky 百分比状态之上，建立可被角色状态与未来 P6 Cell 共同复用的纯 `Element Reaction Kernel`，实现 Extinguish、Toxic Combustion、Ignite Goo、Wet Cleanse、四种环境状态来源，以及完全自研的 Water/Fire/Poison/Sticky 和反应视觉。

**Architecture：** `Game.Combat` 保存元素事实、纯规则、连续反应 Runtime、状态写回和伤害结算；`StatusController` 只是角色状态 Adapter，不把反应写成越来越长的 `if`。Combat 通过值类型事件发布离散阶段，`Game.Rendering` 只播放 Shader/VFX/Decal，不反向修改 Gameplay。P2 环境仍由 `StatusVolume` 承载；P6 再将 Cell 数据映射到同一个 Fire/Water/Poison/Goo 内核。

**Tech Stack：** Unity 6.3（6000.3.16f1）、URP 17.3、C#、NUnit/Unity Test Framework、`ScriptableObject`、`EventBus<T>`、`OverlapBoxNonAlloc`/`OverlapSphereNonAlloc`、Shader Graph、HLSL Custom Function、Particle System、VFX Graph 17.3.x、URP Decal、`MaterialPropertyBlock`、Profiler、Frame Debugger、Rendering Debugger。

## Global Constraints

- `Game.Core` 不依赖上层；`Game.Combat` 不依赖 `Game.Rendering`、`Game.Character` 或 `Game.UI`。
- 跨模块事件必须是 `struct + IGameEvent`；Gameplay 不持有 Rendering Prefab。
- `Update`、持续反应、环境 tick 和 Physics 查询热路径禁止 LINQ、闭包、boxing 和每帧 `new`。
- 状态、反应和环境数值放入 `ScriptableObject`，不写死在 `Fireball` 或 VFX 中。
- 使用 `GameLog`，禁止直接使用 `Debug.Log`。
- 水、毒、火、粘液及三个正式反应的核心视觉必须自研；Prefab 只是封装载体。
- P2 不实现体素、真实流体、Cell 流动、任意地形破坏或 Mobile Decal。
- 新脚本和实质修改必须包含解释架构边界、时序、数学和性能原因的简体中文注释。
- 每个阶段必须经过用户 Unity Editor 验证；不能把静态代码审查表述为“Unity 中已经正常运行”。

## 0. 已确认的产品规则

### 0.1 基础状态

| 状态 | 独立效果 | 当前资产基线 |
|---|---|---|
| Burning | 按强度造成 `Magical DoT` | 自然衰减 6/s，0.2s 一跳，每跳基准 1 |
| Wet | 无直接伤害或控制，提供灭火与清洗能力 | 自然衰减 8/s |
| Poisoned | 按强度造成 `Magical DoT` | 自然衰减 8/s，1s 一跳，每跳基准 3 |
| Sticky | 按强度降低普通移动速度 | 自然衰减 8/s，100% 时最多减速 40% |

这些基础效果继续由 `StatusController + StatusDefinition` 负责。Reaction 系统只能改变强度、产生反应伤害或发出表现事实，不能复制第二套 DoT/移动逻辑。

### 0.2 两两组合矩阵

| 组合 | 阈值以下 | 正式反应 |
|---|---|---|
| Burning + Wet | 10/s 的 1:1 低速中和 | 双方均 ≥10 后，Extinguish 以 50/s 连续 1:1 中和 |
| Burning + Poisoned | 两种 DoT 共存 | Burning ≥25、Poisoned ≥20 后启动 Toxic Combustion |
| Burning + Sticky | DoT 与减速共存 | Burning ≥15、Sticky ≥20、Wet <10 后启动 Ignite Goo |
| Wet + Poisoned | Wet Cleanse | 无命名反应 |
| Wet + Sticky | Poisoned 清洗完后，剩余预算清洗 Sticky | 无命名反应 |
| Poisoned + Sticky | DoT 与减速共存 | P2 无特殊反应 |

### 0.3 统一优先级

```text
1. 汇总本帧 ApplyStatus 输入并更新来源
2. Dirty 时执行 Reaction Evaluator
3. 推进 Extinguish
4. 分配 Wet Cleanse 预算：先 Poisoned，后 Sticky
5. 推进 Toxic Combustion Wind-up
6. 推进 Ignite Goo
7. 对未被独占处理的状态执行自然衰减
8. 更新 Sticky 移动倍率
9. 使用本帧最终强度结算到期 DoT
10. 发布 StatusChangedEvent 与离散 ElementReactionEvent
```

同一种反应最多一个 Process；Toxic Combustion 与 Ignite Goo 可以同时运行；每个目标最多三个 Process。新状态输入、Process 完成、Wet 穿过 10、状态穿过反应阈值时标记 `ReactionDirty`，下一次安全求值点自动重新判断，不要求玩家再命中一次。

### 0.4 数值基线

**Extinguish**

```text
低速中和：10 intensity/s
正式阈值：Fire >= 10 && Water >= 10
正式中和：50 intensity/s
比例：1 Water : 1 Fire
```

**Wet Cleanse**

```text
CleanseBudgetPerSecond = 30 * Wet / 100
Poison multiplier = 0.75
Goo multiplier = 1.25
预算先清 Poison，再用剩余预算清 Goo
Wet 不因通用 Cleanse 被额外消耗
```

**Toxic Combustion**

```text
阈值：Fire >= 25 && Poison >= 20
Wind-up：0.2s
最大计划消耗：40 Poison
最低有效消耗：5 Poison
Damage = 8 + ActualConsumedPoison * 0.4
Radius = 2.5m
DamageType = Magical
冷却：Resolved 后 1.0s
```

**Ignite Goo**

```text
阈值：Fire >= 15 && Goo >= 20 && Water < 10
要求 Fire 至少还有 10 点容量
Goo 消耗：40/s
转换：1 Goo -> 1.25 Fire
Wet >= 10 时禁止并暂停
完成后冷却：0.5s
```

### 0.5 来源归属

- 外部 `ApplyStatus` 更新该状态的 `SourceId/SourceTeam`。
- 自然衰减、Wet Cleanse、Extinguish 不改变来源。
- Burning/Poisoned DoT 使用该状态最近一次有效外部施加来源。
- Toxic Combustion 使用启动本次反应的外部输入来源。
- Ignite Goo 生成的 Burning 保留 Burning 催化来源。
- 目标死亡或禁用时取消未完成毒爆，不造成伤害。
- P2 不引入多人贡献账本；未来出现联机、助攻或召唤物归属需求时，再增加固定容量 Contribution Ledger。

## 1. 初学者需要理解的基础知识

### 1.1 “状态”“元素量”“反应”不是一件事

```text
StatusKind.Wet
= 角色表面潮湿百分比

ElementChannel.Water
= Reaction Kernel 使用的抽象水量

未来 MaterialKind.Water
= P6 空间 Cell 中真实保存的水量
```

角色 Adapter 把 Wet 映射为 Water，P6 Adapter 把 Cell Water 映射为 Water。Kernel 只看 Fire/Water/Poison/Goo，因此不会被某个 MonoBehaviour 锁死。

### 1.2 为什么“判定立即，结果连续”

命中帧立即判断能否反应，保证输入反馈及时；Extinguish/Ignite/Toxic Wind-up 使用 `deltaTime` 连续推进，保证 `80 Fire + 30 Water` 在约 0.6s 内变成 `50/0`，而不是 UI 和 Shader 瞬间跳变。

每帧消耗公式：

```text
consume = min(剩余可消耗量, rate * deltaTime)
```

它是 Frame-rate independent：30 FPS 和 120 FPS 每秒总消耗一致。

### 1.3 为什么需要 Snapshot、Result 和 Adapter

- Snapshot：求值器只读的某一时刻事实，避免判断过程中被写回影响。
- Result：求值器输出“应该改变多少”，不直接改 MonoBehaviour。
- Adapter：把抽象 Fire/Water/Poison/Goo 映射回角色状态或未来 Cell。

这和伤害系统的 `DamageRequest -> DamagePipeline -> DamageResult` 是同一种“纯逻辑与 Unity Runtime 分离”思路。

### 1.4 Alpha Blend、Additive 与 Overdraw

- Alpha Blend：保留轮廓和半透明层次，适合烟、蒸汽、毒雾。
- Additive：把颜色加到屏幕，适合火焰核心、火星、冲击环；层叠过多会过曝。
- Overdraw：同一像素被透明粒子反复绘制。毒雾、Steam、Fire 同屏时是 P2 主要 GPU 风险。

### 1.5 Scene Depth 与水面

PC RP Asset 已开启 Depth Texture 和 Opaque Texture；Water Shader 可以用当前像素的水面深度与场景深度之差估算“水有多深”，驱动浅水/深水颜色和接触边缘。Mobile RP Asset 两项都关闭，因此 P2 只保证 PC 效果，Mobile 使用无深度 fallback。

## 2. 业界常见方案与取舍

### 2.1 每个状态一个 MonoBehaviour

`BurnStatus/WetStatus/PoisonStatus` 互相 `GetComponent`。优点是上手快；缺点是组合数量增长后形成网状依赖，难以共享到 P6。项目已经从旧 `BurnStatus` 迁出，不回到该方案。

### 2.2 在 StatusController 中写所有 if/switch

适合两三个简单规则，但状态、反应、伤害、事件和 VFX 都堆进一个 Update 后无法独立测试。当前 Wet 加速 Burning 的硬编码正是 P2 要迁移的临时实现。

### 2.3 通用 Gameplay Ability/Effect 框架

类似大型项目的 Tag、Effect、Stack、Cue 系统，扩展性强，但当前会引入大量元数据和 Editor 工具，学习成本高于三条反应本身，违反 YAGNI。

### 2.4 数据驱动配置 + 纯 Kernel + Runtime Adapter（采用）

静态数值由 Profile 保存，纯 Kernel 计算，Runtime 只推进已激活 Process，Adapter 写回载体。它比重型 Ability System 小，又保留测试性与 P6 复用能力。

### 2.5 视觉方案比较

| 方案 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| 商城完成品 Prefab | 快 | 黑盒、难与强度/Cell 对接、学习价值低 | 禁止作为核心交付 |
| 全手写 HLSL/VFX | 底层清晰 | P2 风险和工期过大 | 不全量采用 |
| Shader Graph + Particle/VFX Graph + Decal，选 Water 手写 HLSL | 结果完整且能学习底层 | 需要控制透明成本 | 采用 |
| 真体积雾/流体/体素 | 接近沙盒 | 超出 P2 | 留给 P6 或更后阶段 |

## 4. 核心接口契约

### 4.1 抽象快照

```csharp
public readonly struct StatusSource
{
    public readonly int Id;
    public readonly byte Team;

    public StatusSource(int id, byte team)
    {
        Id = id;
        Team = team;
    }
}

public readonly struct ElementStateSnapshot
{
    public readonly float Fire;
    public readonly float Water;
    public readonly float Poison;
    public readonly float Goo;
    public readonly StatusSource FireSource;
    public readonly StatusSource WaterSource;
    public readonly StatusSource PoisonSource;
    public readonly StatusSource GooSource;
}
```

禁止让该类型保存 `StatusController`、`GameObject`、`Transform` 或数组引用。

### 4.2 调参结构

```csharp
[System.Serializable]
public struct ExtinguishTuning
{
    [Min(0f)] public float FormalThreshold;
    [Min(0f)] public float LowRatePerSecond;
    [Min(0f)] public float FormalRatePerSecond;
}

[System.Serializable]
public struct WetCleanseTuning
{
    [Min(0f)] public float BudgetPerSecondAtFullWet;
}

[System.Serializable]
public struct ToxicCombustionTuning
{
    public float FireThreshold;
    public float PoisonThreshold;
    public float WindUpSeconds;
    public float MaxPoisonConsume;
    public float MinEffectiveConsume;
    public float BaseDamage;
    public float DamagePerPoison;
    public float Radius;
    public float CooldownSeconds;
}

[System.Serializable]
public struct IgniteGooTuning
{
    public float FireThreshold;
    public float GooThreshold;
    public float WetInhibitThreshold;
    public float RequiredFireCapacity;
    public float GooConsumePerSecond;
    public float FirePerGoo;
    public float CooldownSeconds;
}
```

`ElementReactionProfile` 只保存这些配置并在 `OnValidate` Clamp 非法值；纯测试直接构造 tuning struct，不依赖 AssetDatabase。

### 4.3 Frame Result

`ElementReactionRuntime.Tick` 不直接修改状态：

```csharp
public ElementReactionFrame Tick(
    in ElementStateSnapshot snapshot,
    float deltaTime,
    in ElementReactionTuningSnapshot tuning);
```

`ElementReactionFrame` 至少输出：

```text
FireDelta / WaterDelta / PoisonDelta / GooDelta
HasAreaDamage + ReactionDamageCommand
SignalCount + Signal0/Signal1/Signal2
SuppressNaturalDecayMask
```

Delta 约定：减少为负，增加为正。`StatusController` 统一 Clamp 到 0–100，避免每个 Process 各自写数组。

### 4.4 离散事件

使用一个事件类型和 Phase，避免五个 EventBus 清理点：

```csharp
public struct ElementReactionEvent : IGameEvent
{
    public int CarrierId;
    public ElementReactionId Reaction;
    public ElementReactionPhase Phase;
    public Vector3 Position;
    public Vector3 Direction;
    public float NormalizedStrength;
    public float ExpectedDuration;
}
```

`CarrierId` 在 P2 等于角色 GameObject InstanceId；P6 可等于 Chunk/Field Id。
