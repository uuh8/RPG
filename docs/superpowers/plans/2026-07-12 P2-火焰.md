我们把 Fire 的开发拆成“一个可验证的小效果一关”，先解决火焰本身，再做分层、Steam 和 Gameplay 集成。这样你可以明确理解每一层解决了什么视觉问题。

## 一、三种常见实现路线

### 路线 A：纯 Particle System + 普通贴图

使用若干张火焰图片或 Flipbook，通过 Unity `Particle System` 播放。

优点是制作快、性能可控，也是商业项目很常见的方案；缺点是图形学学习深度有限，而且如果直接下载素材，本质上仍是在“使用别人做好的火”。

### 路线 B：纯 Procedural Shader

用 HLSL 的 `Noise`、UV 扭曲、渐变、阈值裁剪等公式，在 Shader 中直接生成完整火焰。

优点是高度自研，能够深入学习图形学；缺点是单个平面容易显得扁平，而且每个透明粒子都计算多层 `Noise` 时，GPU 成本和 `Overdraw` 会快速增加。

### 路线 C：手写 Shader + Particle System 分层

这是我推荐的方案。

- Shader 负责“一个火焰片长什么样、如何流动、颜色如何从白黄过渡到橙红”。
- Particle System 负责“火焰片如何出生、上升、缩小、消失以及如何组成一片火区”。
- 多种 Blend Mode 负责主体、亮芯和火星的不同光学表现。
- Gameplay 继续由 `StatusVolume` 负责，视觉系统不修改状态规则。

它兼顾了图形学学习、自研视觉、工程复用和性能控制。

# 二、推荐的 Fire 开发流程

## 阶段 0：先定义第一版的视觉边界

第一版目标不是物理正确的燃烧模拟，而是一个“风格化、可控、能够与 Gameplay 区域匹配的环境火区”。

我们暂时不做：

- 真实流体或燃烧方程；
- 烟雾体积渲染；
- 动态照亮所有场景；
- 火焰传播；
- 根据地形自动改变火焰边界；
- 大规模 `VFX Graph` GPU 粒子。

第一版采用大约：

- Fire Body：12～24 个粒子；
- Fire Core：6～12 个粒子；
- Sparks：4～12 个粒子；
- Steam：16～32 个粒子。

这些是初始范围，最终根据 `Profiler` 和视觉效果调整。

## 阶段 1：在单个 Quad 上生成“火焰片”

先不创建一整片火，也不连接 `StatusVolume`。我们先用一个 Quad 检验手写 Fire Shader。

一个火焰片主要需要解决四个问题：

1. 下宽上窄的轮廓；
2. 从下向上的流动；
3. 边缘不断破碎、摇摆；
4. 从高温白黄过渡到橙红并逐渐透明。

大致的数学流程是：

```
原始 UV
→ 将 UV 转换到以中心为原点的局部坐标
→ 根据高度计算火焰宽度
→ 使用随时间移动的 Noise 扰动横向位置
→ 用 Smoothstep 生成柔和轮廓
→ 用纵向渐变淡化顶部和底部
→ 根据高度与 Noise 计算颜色和 Alpha
```

火焰宽度可以抽象为：

```
width(y) = lerp(BaseWidth, TipWidth, pow(y, ShapePower))
```

其中：

- `y` 越接近 0，越靠近火焰底部；
- `y` 越接近 1，越靠近顶部；
- `BaseWidth` 控制底部宽度；
- `TipWidth` 控制尖端宽度；
- `ShapePower` 控制收尖速度。

动态 UV 类似于：

```
animatedUV = uv * NoiseScale + Time * FlowSpeed
```

然后利用 `Noise` 扰动轮廓：

```
distortedX = centeredX + (noise - 0.5) * DistortionStrength
```

最终用 `Smoothstep` 把“在轮廓内还是轮廓外”的硬判断变成柔和过渡。

阶段验收标准：

- 单个 Quad 已经像一片火焰，而不是一块移动噪声；
- 火焰总体向上流动；
- 底部稳定，顶部变化更明显；
- 没有 Particle System 也能看清 Shader 本身的作用。

## 阶段 2：把 Shader 拆成主体与高温核心

Fire Body 和 Fire Core 不适合使用完全相同的混合方式。

### Fire Body

使用：

```
Blend SrcAlpha OneMinusSrcAlpha
```

也就是标准 `Alpha Blend`：

```
Cresult = Csource × α + Cbackground × (1 - α)
```

它能保留橙红色轮廓，使火焰在明亮背景下仍然可辨认。

### Fire Core

使用：

```
Blend SrcAlpha One
```

也就是 `Additive Blend`：

```
Cresult = Csource × α + Cbackground
```

它会不断向背景叠加亮度，适合表现白色、黄色的高温核心，但单独使用容易在亮背景中消失，也容易过曝。

因此我建议使用三个文件：

```
ElementFireCore.hlsl
ElementFireBody.shader
ElementFireAdditive.shader
```

`ElementFireCore.hlsl` 保存共同的火焰轮廓、Noise、UV 动画和颜色公式；两个 ShaderLab 文件负责声明不同的 Render State 和 Blend Mode。这样既避免重复公式，又明确体现 Shader 算法和渲染状态之间的区别。

阶段验收标准：

- Body 单独显示时轮廓完整；
- Core 单独显示时像高温能量，而不是另一层橙色贴片；
- 两者叠加后，火焰中心更亮、外围更红；
- 在亮背景和暗背景下都能辨认。

## 阶段 3：使用 Particle System 组成环境火焰

Shader 只定义了“一片火焰”，Particle System 再把很多火焰片组合成一个火区。

Prefab 内部暂定：

```
FireVisualRoot
├── PS_FireBody
├── PS_FireCore
└── PS_FireSparks
```

### PS_FireBody

作用是形成总体轮廓：

- 粒子尺寸较大；
- 生命周期相对长；
- 缓慢向上运动；
- `Color over Lifetime` 从可见变为透明；
- `Size over Lifetime` 先略微增大，再缩小；
- 水平方向加入少量随机速度。

### PS_FireCore

作用是表现底部持续产生的高温区域：

- 数量比 Body 少；
- 尺寸更小；
- 生命周期更短；
- 位置集中在底部；
- 使用 Additive Material；
- 颜色偏白黄。

### PS_FireSparks

作用是补充能量方向和细节：

- 粒子很小；
- 上升速度明显高于火焰主体；
- 生命周期较短；
- 少量随机横向运动；
- 可以使用 `Stretched Billboard` 表现高速轨迹；
- 数量必须克制，不能变成烟花。

阶段验收标准：

- 暂停播放时，三层职责仍然能被辨认；
- 火焰整体有明确的向上运动趋势；
- 不依赖大量粒子堆叠；
- Scene 视图从常用游戏摄像机角度看，不会明显暴露单张 Billboard。

## 阶段 4：制作独立 Steam

Steam 不能直接复用火焰材质，因为蒸汽和火焰的视觉目标不同。

Steam 使用 `Alpha Blend`，核心运动是：

```
上升 + 扩散 + Alpha 衰减
```

Particle System 参数逻辑：

- 初始尺寸较小；
- `Size over Lifetime` 持续变大；
- `Color over Lifetime` 的 Alpha 持续降低；
- 速度整体向上；
- 使用低频 `Noise` 产生轻微摆动；
- 粒子数量保持在 16～32；
- 色彩为偏冷或中性的灰白，避免像烟或毒雾。

我们还需要区分两种强度：

- 低于正式阈值时：少量、较薄的 Steam；
- 正式 `Extinguish` 时：更明显、更密集的 Steam。

不一定需要两个 Prefab，可以通过 `Emission Rate`、尺寸或播放时长表达不同强度；具体取决于现有 `StatusReactionVisualController` 暴露的控制接口。

阶段验收标准：

- 一眼看出是蒸汽而不是白烟；
- 粒子出生后上升、扩大、消失；
- 不会持续积累；
- `Extinguish` 停止后，已有粒子自然消散，系统不再继续发射。

## 阶段 5：组装 `EV_FireArea`

建议的 Prefab 层次是：

```
EV_FireArea
├── Gameplay
│   ├── BoxCollider
│   └── StatusVolume（Burning）
└── Visual
    ├── PS_FireBody
    ├── PS_FireCore
    └── PS_FireSparks
```

Gameplay 和 Visual 分开是一个重要的架构边界：

- `StatusVolume` 决定角色在哪里受到 `Burning`；
- Fire Visual 只告诉玩家“这里很危险”；
- Shader 和 Particle System 不直接调用 `StatusController`；
- 调整视觉尺寸时，不会意外修改反应规则；
- 将来 P6 Cell 系统也能复用同一套视觉，而不依赖 `StatusVolume`。

碰撞区域建议略小于可见火焰范围。原因是玩家踩到视觉边缘却还看不出自己接触火焰时，不应该提前被灼烧；也要避免火焰明显碰到角色却完全不施加状态。

阶段验收标准：

- 进入可见火焰区域时持续增加 `Burning`；
- 离开区域后不再施加；
- 多 Collider 不会导致重复施加；
- 暂停游戏后 Gameplay tick 和粒子动画都冻结；
- Visual 与 Collider 的空间范围基本一致。

## 阶段 6：连接 Extinguish Steam

数据流保持单向：

```
StatusVolume
→ StatusController.ApplyStatus
→ ElementReactionRuntime
→ StatusReactionEvent
→ StatusReactionVisualController
→ RV_ExtinguishSteam
```

重点是 Steam 由反应事件启动，而不是 Fire Particle System 自己检测 Wet。否则 Rendering 会反过来包含 Gameplay 规则，破坏模块边界。

`RV_ExtinguishSteam` 应由现有 `StatusReactionVisualController` 预创建并复用：

- `Started`：开始发射；
- 重复 `Started`：刷新或保持，不重复实例化；
- `Resolved/Cancelled`：停止发射；
- 已生成的粒子自然消散。

这也符合当前系统的零热路径分配设计。

## 阶段 7：Gate A 联合验收

功能验收：

- `80 Fire + 30 Water` 连续变化到 `50 Fire + 0 Water`；
- 数值不是瞬间跳变；
- 低强度接触产生薄 Steam；
- 正式 `Extinguish` 产生明显 Steam；
- 水池和火区能够分别施加 Wet/Burning；
- 暂停时状态推进和视觉全部冻结。

Rendering 验收：

- Fire Body 保持轮廓；
- Fire Core 提供高温亮芯；
- Sparks 数量克制；
- Steam 不像烟雾或毒雾；
- Fire 和 Steam 重叠时不过度发白；
- 使用 `Frame Debugger` 能指出 Body 与 Core 的不同 Blend Pass；
- 使用 Overdraw 视图检查透明层叠。

性能验收：

- 状态与视觉控制热路径 `0 B GC Alloc`；
- 不在反应事件中重复 `Instantiate`；
- Particle System Bounds 不无限扩大；
- 同屏多个火区时，没有明显 CPU/GPU 峰值；
- 如果程序化 Fire Shader 成本偏高，再考虑把 Noise 动画烘焙成自制 Flipbook，而不是直接降低视觉目标。

# 三、实际执行顺序

接下来不应立刻把完整 Fire Prefab 一次做完，而是按下面顺序推进：

```
Fire 单 Quad 轮廓
→ Fire 动态 Noise
→ Fire 颜色与 Alpha
→ Body/Core 两种 Blend
→ Particle System 主体层
→ 核心层
→ 火星层
→ Steam
→ EV_FireArea
→ StatusVolume 与反应事件联调
→ Gate A
```

每完成一小步，你在 Unity Editor 中观察，我同时解释该步骤使用的 Shader 公式、Particle System 模块、Render State 和取舍。Fire 全部完成后，再把整个 Task 6 的 Fire/Steam 实现补充进 P2 学习解析文档。

如果认可这套流程，我下一步会先更新现有 P2 详细计划，然后开始第一小步：在独立 Quad 上制作 `Fire Body` 的静态轮廓，只解决“怎样用数学公式生成下宽上窄的火焰形状”，暂时不加入动画。
