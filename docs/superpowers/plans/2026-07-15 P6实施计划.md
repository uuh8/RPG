## 0. 初学者先读：我们究竟在构建什么

Cell 不是玩家看见的 Cube，而是内存中的一个“空间数据槽”。例如一个 `0.25m` 的 Cell 可能保存：

```text
MaterialKind = Water
Amount       = 180 / 255
```

这只回答“这一小块空间是什么、数量多少”。它不直接负责水面的颜色、火焰粒子的形状，也不直接给角色扣血。完整职责链是：

```text
法术与 Projectile
    ↓ 产生 ElementWriteRequest
Game.ElementField
    ↓ 保存和模拟 MaterialKind / Amount
    ├─ ElementFieldExposureSystem → StatusController → Wet/Burning
    └─ IElementFieldReadOnly → Game.Rendering
                              ├─ Water Chunk Mesh + ElementWater.shader
                              └─ Fire Particle Body/Core/Sparks
```

这种拆分的关键价值是：同一份 Cell Gameplay 数据可以换 Shader、换 Particle、关闭视觉，模拟结果仍然不变；同一套 P2 状态反应也可以同时服务角色百分比状态和 P6 空间 Cell，而不用把 Shader、Physics、状态机全部揉进一个脚本。

### 0.1 为什么先做 CPU 正确性而不是直接 Compute Shader

`Compute Shader` 适合并行更新大量 Cell，但相邻 Cell 同时读写会产生 Race Condition。若 CPU 版本的规则、双缓冲和守恒都没定义清楚，把它搬到 GPU 只会让 Debug 更困难。第一版 16,384 Cell、10 Hz 全扫描的 CPU 成本很低，足够先证明玩法；只有 Profiler 证明 CPU 成为瓶颈后，才值得引入 Job System/Burst 或 Compute Shader。

### 0.2 为什么不使用真正流体公式

真实流体常涉及 Navier–Stokes 方程、速度场、压力投影和不可压缩约束。本 Demo 需要的是可预测的玩法水，而不是物理实验。因此采用 Cellular Automata 风格的局部规则：优先向下、再水平均衡。Shader 负责把离散结果表现得连续，这正是 `Hybrid Element World` 的核心。

- [ ] **Step 4：实现坐标公式并解释 Floor**

```csharp
Vector3 local = worldPosition - origin;
int x = Mathf.FloorToInt(local.x / cellSize);
int y = Mathf.FloorToInt(local.y / cellSize);
int z = Mathf.FloorToInt(local.z / cellSize);

int index = x + size.x * (y + size.y * z);
```

必须使用 `FloorToInt`，不能使用强制转 `int`。强制转型会把 `-0.2` 截断为 `0`，错误地把 Field 外的负坐标判断为第 0 格；Floor 会得到 `-1`，随后被 Bounds Check 正确拒绝。

- [ ] **Step 5：实现 ElementGrid 的所有权边界**

`ElementGrid` 构造函数接收 `size` 与 Profile 中的 `maximumCellCount`，并验证：

```text
size.x/y/z > 0
cellCount = (long)size.x * size.y * size.z
cellCount <= 由 ElementFieldProfile 传入的 maximumCellCount
```

使用 `long` 先乘，防止 `int` 在验证前溢出。初始化时一次性分配：

```csharp
ElementCell[] _currentCells;
ElementCell[] _nextCells;
bool[] _solidMask;
int[] _amountDelta;
```

对外只能通过 `GetCell`、`IsSolid` 和 `IElementFieldReadOnly` 读取；写入方法保持 `internal`，防止 Rendering 反向修改 Gameplay。

- [x] **Step 2：实现固定容量 Ring Buffer**

初始化时分配 `ElementWriteRequest[]`，运行时只移动 `_head/_tail/_count`：

```text
enqueue index = tail
tail = (tail + 1) % capacity

dequeue index = head
head = (head + 1) % capacity
```

- [x] **Step 3：实现范围写入的两遍归一化分配**

只遍历命中球体的 Cell AABB：

```text
minCell = WorldToCellUnchecked(center - radius)
maxCell = WorldToCellUnchecked(center + radius)
```

随后将 Min/Max Clamp 到 Grid Bounds。不能直接使用会拒绝越界的 `TryWorldToCell`，否则命中球只要有一部分伸出 Field，就会错误地丢弃 Field 内仍然有效的部分。`radius == 0` 时跳过除法，只把总量写入命中点所在的单个 Cell。

第一遍计算：

```text
d = distance(CellCenter, ImpactPosition)
weight = saturate(1 - d / radius)
weightSum += weight
```

第二遍使用剩余量分配：

```text
share = round(remainingAmount × weight / remainingWeight)
remainingAmount -= share
remainingWeight -= weight
```

该写法不需要临时 List，并减少普通 `RoundToInt(total × weight/weightSum)` 造成的总量丢失。Solid Cell 不参与 WeightSum。

- [x] **Step 4：实现同材料和异材料写入**

```text

Water 200 + Water 100 → Water 255（45 因容量上限丢弃）
Fire 100 + Water 160 → Water 60
Water 160 + Fire 100 → Water 60
```

异材料公式：

```text
consumed = min(oldAmount, incomingAmount)
oldAmount -= consumed
incomingAmount -= consumed
```

只允许 Water/Fire 互相反应；Poison/Sticky 写入在本切片返回 Unsupported，不改变 Cell。

- [x] **Step 5：实现 Reaction Stage**

每个相邻 Pair 只检查一次：`+X`、`+Y`、`+Z`，不能同时检查正负六个方向，否则同一对 Cell 会反应两次。

把 byte 映射到 P2 百分比：

```text
intensity = amount × 100 / 255
```

调用共享公式后映射回 byte：

```text
consumedAmount = round(consumedIntensity × 255 / 100)
```

默认 Profile 必须保证 `LowRate × 0.1 × 2.55 >= 1`，否则 OnValidate 发出 `GameLog.Warn`，避免非零反应因 byte 量化长期变成 0。

- [x] **Step 6：实现 Down Flow Stage**

capacity = 255 - targetProjectedAmount
available = sourceOriginalAmount - sourceOutgoing
transfer = min(available, capacity, MaxDownFlowPerTick)

使用预分配 `int[] amountDelta` 记录出入量。目标本 Tick 收到的 Incoming 不允许再次成为 Source，因此水每个 Tick 最多向下移动一格。

- [x] **Step 7：实现 Horizontal Flow Stage**

```text
difference = sourceOriginalAmount - targetOriginalAmount
desired = max(difference / 2, 0)
transfer = min(desired, sourceAvailable, targetCapacity, MaxLateralFlowPerTick)
```

偶数 Tick 使用 `Left, Right, Forward, Back`，奇数 Tick 反向，减少固定方向偏差，但不用 Random，保证确定性。

_accumulator += Time.deltaTime;

### Task 6A：持续状态来源暂停自然衰减（Task 6 Gate 中发现）

Task 6 的实际 Gate 暴露了一个时间尺度冲突：`StatusController` 每帧执行 `NaturalDecayPerSecond`，而 `ElementFieldExposureSystem` 每 `0.25s` 才补充一次状态。即使角色一直站在水中，Wet 仍会在两次 Exposure 之间下降，形成锯齿、抵消甚至 `0%` 闪烁。这里不能简单降低 `Status_Wet.NaturalDecayPerSecond`，因为它会同时延长火球、一次性技能等所有来源留下的状态；也不能让所有 `ApplyStatus` 自动刷新暂停时间，否则一次性命中也会被误判成持续接触。

最终选择“来源显式声明 Sustained”的通用方案：`StatusController` 新增持续施加入口，调用方传入一个 `Natural Decay Hold Seconds`。普通 `ApplyStatus` 语义完全不变；Water/Fire Cell Exposure 与现有 `StatusVolume` 这类周期性环境来源改用持续入口。Hold 只暂停普通自然衰减，不拦截 `Extinguish`、`WetCleanse`、`ToxicCombustion`、`IgniteGoo` 等反应 Delta，也不暂停 DoT。这样角色站在来源中时状态单调累积或由反应消耗，离开来源一个很短的抗抖 Grace 后恢复原有自然衰减。

**方案对比与取舍：**

1. **降低全局 NaturalDecay（不采用）：** 改动最小，但一次性来源也会变得过久，无法表达“仍在接触来源”。
2. **任何 ApplyStatus 都刷新 Hold（不采用）：** API 简单，却把一次性 Projectile 与持续 Volume 混为同一语义。
3. **显式 `ApplySustainedStatus`（采用）：** 调用方多传一个时间窗口，但职责清晰、可测试，并允许未来 Poison/Sticky 环境来源主动接入而不影响直接命中。

每帧自然衰减使用帧率无关的剩余时间公式：

```text
heldTime = min(HoldRemaining, deltaTime)
HoldRemaining -= heldTime
decayDeltaTime = deltaTime - heldTime
Intensity -= NaturalDecayPerSecond × decayDeltaTime
```

因此当 Hold 在一帧中途到期，只对剩余的那部分时间计算衰减，而不是整帧全免或整帧全扣。Reaction 的 `SuppressNaturalDecay` 仍拥有更高优先级；即使 Hold 有效，Reaction Delta 仍照常应用。Intensity 归零时清空 Hold，避免下一次新状态继承旧来源的暂停时间。

`ElementFieldExposureSystem` 与 `StatusVolume` 均使用：

```text
holdSeconds = applicationInterval + 0.10s grace
```

Grace 用于吸收帧边界与低频采样误差，不代表离开区域后仍持续增加状态；它只把自然衰减的恢复延迟 `0.10s`。

## 全局 Debug 决策树

遇到异常时按数据流从前往后排查，不要直接修改 Shader：

```text
① Projectile 是否触发 Impacted？
② ElementDepositOnImpact 是否生成正确 Request？
③ Queue 是否接收，是否 Overflow？
④ WorldToCell 是否得到正确坐标？
⑤ Write Processor 是否修改 Cell？
⑥ Simulator 的 Reaction/Flow/Decay 哪一 Stage 改变了它？
⑦ Chunk Version 是否增加？
⑧ Exposure 是否采样到 Cell？
⑨ StatusController 是否收到 ApplyStatus？
⑩ Water/Fire Renderer 是否读到相同 Cell？
```

典型症状映射：

| 症状 | 优先检查 |
|---|---|
| Gizmo 没有 Cell | Queue、WorldToCell、Field Bounds |
| Gizmo 有水但 Mesh 没有 | Chunk Version、Water Renderer Material、Mesh Builder |
| Fire Cell 有值但无粒子 | Simulation Space、Emission 是否手动、Sample Cap |
| 玩家站水里没有 Wet | Target Layer、Collider Bounds、StatusController |
| 水火消耗不守恒 | Pair 重复检查、Amount Delta、byte/百分比转换 |
| 水一 Tick 穿到底 | Incoming 被错误作为同 Tick Source |
| 卡顿但 GC 为 0 | 全 Chunk 同帧重建、Fire 粒子 Overdraw、Physics Bake 是否误放进 Tick |
| GC Alloc 不为 0 | List 扩容、闭包、字符串插值、LINQ、每 Tick 新数组 |
